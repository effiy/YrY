# 事件复盘模板（无指责式 Postmortem）

> 使用方法：任何 P0/P1/P2 事件 5 个工作日内召开复盘会，按无指责原则（blameless）填写本模板。配套 qb-row「Incident postmortem」一键 prompt：Incident severity: P0/P1 / Impact scope: xxx / Root cause chain: xxx / Action items: xxx。复制到 `lessons/failures/{日期}-{事件名}-postmortem.md`。

## 1. 基本信息

| 字段 | 内容 |
|------|------|
| 事件编号 | （示例：INC-2026-0142） |
| 事件名称 | （示例： AI 大面积超时） |
| 严重度 | P0 / P1 / P2 |
| 影响范围 | （示例：6 个国家 12k 用户 4h 内无法响应） |
| 持续时长 | 触发 __ → 恢复 __，共 __ |
| 检测方式 | 告警 / 用户反馈 / 上游报错 |
| 事件时间 | （示例：2026-07-29 14:30 ~ 18:30） |
| 复盘日期 | （示例：2026-07-30） |
| 复盘主持 | （示例：SRE 张三） |
| 参与者 | 后端、模型组、运维、客服 |
| 事件责任人 | （示例：模型组 李四） |
| 状态 | Open / Action Items Pending / Closed |

## 4. 根因链（Root Cause Chain）

使用 5 Why 逐层追溯，禁止停留在「人为失误」。

| Why 层级 | 现象 | 直接原因 |
|---|---|---|
| Why 1 | 模型超时 | 算力被挤占 |
| Why 2 | 算力挤占 | 无配额机制 |
| Why 3 | 无配额机制 | 多团队共用 1 卡 |
| Why 4 | 共用 1 卡 | 成本控制 |
| Why 5 | 成本控制一刀切 | 无模型 SLA |

**根因类型**（多选）：
- [x] 流程缺失（配额 / SLA）
- [ ] 代码缺陷
- [ ] 配置错误
- [ ] 容量不足
- [ ] 监控缺失
- [ ] 第三方依赖
- [ ] 人为操作

## 7. 经验教训

- ✅ 做得好的：oncall 5 分钟拉群、临时限流快速止血。
- ❌ 待改进：算力没有配额机制，模型组被多团队挤压；告警阈值偏高导致检测滞后。
- 🧠 可复用：临时限流 + 配额预案模板（沉淀到 runbook）。
