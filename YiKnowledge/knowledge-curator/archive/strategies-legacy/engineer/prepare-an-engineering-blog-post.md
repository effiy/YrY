# I want to write an engineering blog

> **As an** engineer, **I want to** prepare an engineering blog post, **so that** launch is safe.

## Summary

- Four uses of a blog: knowledge sediment + employer brand + recruiting + feedback
- Three topic tiers: technical depth / engineering practice / lessons learned
- Structure: problem → solution → tradeoffs → result
- Honesty: do not hide failures; do not exaggerate
- Legal review: compliance / customer / data
- Write before publishing; not verbal
- Quantify: data / charts / code
- Feedback closed loop: comments must be replied to

## Scenario

An engineering blog is the carrier of externalized knowledge and the employer brand; not for showing off. This entry provides the full engineering blog path, covering the four uses, three topic tiers, structure, honesty without hiding failures, legal review, write before publishing, quantification, feedback closed loop, and links to write-documentation / prepare-a-tech-talk / do-a-proof-of-concept / launch-an-ai-product / collaborate-across-teams / run-a-retrospective and other leaves.

## Action recommendations

1. **Four uses in one**: knowledge sediment + employer brand + recruiting + feedback; do not neglect any
2. **Three topic tiers**: technical depth / engineering practice / lessons learned; do not neglect any
3. **Structure**: problem → solution → tradeoffs → result; not a stream-of-consciousness log
4. **Honesty**: do not hide failures; do not exaggerate; do not pile up jargon
5. **Legal review**: compliance / customer / data / secrets; do not publish without authorization
6. **Write before publishing**: draft + review + revision; not verbal
7. **Quantify**: data / charts / code; not vague
8. **Runnable code**: attach runnable snippets; not pseudocode
9. **Diagrams**: architecture diagrams / process diagrams / sequence diagrams; not only text
10. **Tradeoff section**: alternatives + tradeoffs; not only conclusions
11. **Honest failures**: write about failures too; do not hide
12. **Related**: link to internal wiki / upstream-downstream projects / RFC / ADR
13. **Author byline**: team + individual; not anonymous
14. **Feedback closed loop**: comments must be replied to; do not post and leave
15. **First principles**: why must write a blog; worst consequence of not writing
16. **Inversion thinking**: how much can internal wiki + talks solve; if solvable, do not publish externally
17. **Second-order thinking**: second-order consequences after the blog (recruiting / brand / compliance / competitors)
18. **Occam**: the simpler the blog, the better; cut redundant decoration
