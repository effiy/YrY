# 备份与灾难恢复计划

> 灾难恢复计划的价值在灾难发生前是零——在灾难发生后是无限。问自己一个问题：如果明天这台 Mac Mini 坏了，需要多久恢复服务？丢多少数据？

## 核心指标

| 指标 | 含义 | YrY 当前状态 |
|---|---|---|
| **RPO** (Recovery Point Objective) | 最多能接受丢失多久的数据 | 未定义（建议：24 小时） |
| **RTO** (Recovery Time Objective) | 最多能接受服务中断多久 | 未定义（建议：4 小时） |
| **备份频率** | 多久备份一次 | 手动——无自动化 |
| **备份保留** | 备份保留多久 | 未定义 |

**RPO/RTO 定义指南**：
- RPO = 24 小时意味着"丢一天的数据可以接受"——对于开发阶段的项目通常是合理的
- RTO = 4 小时意味着"服务中断 4 小时内恢复"——单人项目，取决于发现故障的时间
- 生产环境 RPO 通常要求 < 1 小时，RTO < 1 小时

## 灾难场景

| 场景 | 可能性 | 影响 | 恢复复杂度 |
|---|---|---|---|
| **磁盘故障** — Mac Mini SSD 损坏 | 低 | 所有数据丢失（代码、数据库、知识库） | 中——从 git + 备份恢复 |
| **误删数据** — `db.dropDatabase()` | 中 | MongoDB 数据丢失 | 低——从备份恢复 |
| **误删文件** — `rm -rf YiKnowledge/` | 低 | 知识库文件丢失 | 低——从 git 恢复 |
| **硬件丢失/被盗** | 极低 | 所有本地数据丢失 | 中——从 git + 异地备份恢复 |
| **勒索软件** | 极低 | 文件被加密 | 中——从干净备份恢复 |
| **依赖服务故障** — Ollama/MongoDB 不可用 | 中 | 相应功能不可用 | 低——多提供商路由/重启 |

## 备份策略

### 当前备份状态

| 数据 | 备份方式 | 频率 | 异地？ | 上次验证 |
|---|---|---|---|---|
| 源代码 (YiAi/YiVad/YiPet) | Git (GitHub) | 每次 push | ✅ | 持续 |
| 知识库 (YiKnowledge) | Git (GitHub) | 每次 push | ✅ | 持续 |
| MongoDB 数据 | **无** | — | — | — |
| 配置文件 (含密钥的) | **手动** | 按需 | ❌ | 未知 |
| Ollama 模型 | 可重新下载 | — | — | — |

**最大风险**：**MongoDB 无备份**。所有聊天会话、用户数据、菜单配置、知识库元数据都在 MongoDB 中。磁盘故障 = 数据丢失。

### 推荐备份方案

#### MongoDB 备份

```bash
# 全量备份
mongodump --uri="mongodb://localhost:27017" --out=/backup/mongodb/$(date +%Y%m%d)

# 恢复
mongorestore --uri="mongodb://localhost:27017" /backup/mongodb/20260915/

# 自动化脚本（crontab）
# 每天凌晨 3 点备份，保留最近 7 天
0 3 * * * mongodump --uri="mongodb://localhost:27017" --out=/backup/mongodb/$(date +\%Y\%m\%d) --gzip
0 4 * * * find /backup/mongodb/ -type d -mtime +7 -exec rm -rf {} \;
```

#### 配置文件备份

```bash
# 备份敏感配置
tar -czf /backup/config/$(date +%Y%m%d).tar.gz \
  YiAi/.env \
  YiAi/config.yaml \
  ~/.ollama/
```

#### 备份到异地

本地备份防不了硬件故障和物理灾难。关键数据需要异地副本：

| 方法 | 成本 | 复杂度 |
|---|---|---|
| GitHub (代码 + 知识库) | ✅ 免费 | 已完成 |
| 云对象存储 (MongoDB 备份) | ~$1/月 (10GB) | 推荐——`aws s3 sync` 或 `rclone` |
| 第二块硬盘 | ~$50 一次性 | 简单但非异地 |
| 纸质记录（密钥备份） | ~$0 | 密码管理器更实用 |

```bash
# 复制 MongoDB 备份到云存储
rclone sync /backup/mongodb/ s3:yry-backups/mongodb/
```

## 恢复流程

### 场景：MongoDB 数据丢失

**RPO**：取决于上次备份时间（建议 24 小时）
**RTO**：约 30 分钟

```
1. 确认数据丢失范围
   mongosh --eval "db.stats()"  # 各集合文档数

2. 停止 YiAi（防止写入脏数据）
   pkill -f "python main.py"

3. 从最近备份恢复
   mongorestore --uri="mongodb://localhost:27017" /backup/mongodb/20260914/ --drop

4. 验证恢复
   mongosh --eval "db.sessions.count()"  # 对比备份前记录

5. 重启 YiAi
   cd YiAi && python main.py

6. 验证功能
   - 聊天是否正常？
   - 菜单是否正常加载？
   - 知识库文件列表是否正常？
```

### 场景：Mac Mini 完全故障

**RPO**：取决于最新备份（git 实时 + MongoDB 上次备份）
**RTO**：约 2-4 小时（取决于新硬件就绪时间）

```
1. 获取新硬件（或云服务器）
   - Mac Mini 替代品 或 云服务器（4 核 16GB）

2. 安装依赖
   - brew install mongodb-community ollama python@3.10 node pnpm
   - pip install -r YiAi/requirements.txt

3. Clone 代码
   git clone <repo-url>
   cd YiAi && pnpm install  # YiVad

4. 恢复 MongoDB
   mongorestore --uri="mongodb://localhost:27017" <最新备份>

5. 拉取 Ollama 模型
   ollama pull qwen2.5

6. 启动服务
   cd YiAi && python main.py
   cd YiVad && pnpm dev

7. 验证所有功能正常
```

## 备份检查清单

### 每季度验证

- [ ] 从最新备份执行一次试恢复——备份不验证 = 没有备份
- [ ] 检查备份脚本是否正常运行（crontab 日志）
- [ ] 检查备份磁盘空间（> 2× 预计备份大小）
- [ ] 轮换密钥备份（如果适用）
- [ ] 更新本文件中的备份状态

### 每次重大变更前

- [ ] 手动执行一次完整备份
- [ ] 确认备份成功（检查文件大小和时间）

## 当前优先级

| 优先级 | 行动 | 工作量 | 风险缓解 |
|---|---|---|---|
| **P0** | 设置 MongoDB 每日自动备份 | 30 分钟 | 磁盘故障导致数据全丢 → 最多丢 24 小时数据 |
| **P1** | 首次试恢复——验证备份可用 | 30 分钟 | 备份脚本运行了但备份文件损坏——发现并修复 |
| **P2** | 配置文件异地备份 | 30 分钟 | 本地灾难时密钥和配置可恢复 |
| **P2** | RPO/RTO 正式定义并记录 | 15 分钟 | 利益相关者知道灾难恢复预期 |

## 反模式

| 反模式 | 失败原因 | 正确做法 |
|---|---|---|
| 有备份但从不验证恢复 | 备份脚本跑了半年但输出的文件是空的——灾难发生才知道 | 每季度试恢复一次 |
| 备份和源数据在同一块盘 | 磁盘故障→备份和数据一起没了 | 备份到不同物理介质或异地 |
| "代码在 GitHub 上，不需要备份" | MongoDB、配置、密钥、Ollama 模型不在 GitHub 上 | 识别所有不在 git 中的数据 |
| 恢复流程只在脑子里 | 灾难发生时你不在或忘了步骤 | 写成本文——runbook 级的详细步骤 |
| 只有全量备份没有增量 | 100GB 数据库每天全量备份→存储成本爆炸 | 全量每周 + 增量每天；或使用 MongoDB Atlas 自动备份 |
