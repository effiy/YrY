# 事后复盘方法论

> **何时使用**：每次 P1 或 P2 事故后，以及任何教会了团队新知识的事故后。事后复盘的目的在于**学习和预防**，而非追责。
>
> 事后复盘不是惩罚工具——它是组织的集体学习机制。一份好的事后复盘让其他人无需亲自经历同样的故障就能学到教训。

## 边界：方法论 vs 记录

| 方面 | 归属 | 位置 |
|---|---|---|
| **事后复盘方法论**（本文）| leader/risk/ | 如何写出好的事后复盘 |
| **事后复盘记录**（实际事故）| srer/incident-response/ | 具体事故的复盘报告 |
| **事后复盘教训**（实战笔记）| engineer/learn/lessons/ | 从复盘中提取出的通用模式 |

**为什么分离**：方法论告诉你"怎么做"，记录是"实际做了什么"。将两者放在同一个地方会稀释方法论的可复用性。

## 何时撰写事后复盘

| 触发条件 | 是否必需？|
|---|---|
| P1 事故（核心用户旅程中断）| **必需** — 24 小时内完成 |
| P2 事故（显著服务降级）| **必需** — 48 小时内完成 |
| P3 事故（轻微问题）| 可选 — 如果团队学到了新东西 |
| 侥幸避免的事故 | **推荐** — 这是学习成本最低的时候 |
| 成功及早恢复 | **推荐** — 什么做对了？|

**延迟撰写的风险**：超过 48 小时，记忆开始模糊——关键细节丢失。团队也会失去紧迫感，复盘沦为形式。

## 事后复盘结构

### 1. 摘要

一段话：发生了什么、影响范围、持续时间。

**示例**："2026-08-15，YiAi 服务不可用 23 分钟。根因是 MongoDB 连接池耗尽，由一次部署触发了默认连接池大小翻倍（从 50 到 100），但未同步增加服务器的 `maxIncomingConnections`。影响：142 次聊天请求失败。无数据丢失。"

### 2. 时间线（UTC）

| 时间 | 事件 |
|---|---|
| 14:32 | 部署 v2.1.0 上线（连接池从 50 翻倍到 100）|
| 14:35 | 日志中出现第一条 `connection pool exhausted` 错误 |
| 14:38 | PagerDuty 告警：错误率 > 5% |
| 14:40 | 值班人员确认告警，开始排查 |
| 14:45 | 定位连接池为根因 |
| 14:50 | 开始回滚 |
| 14:55 | 服务恢复；错误率回到基线 |

**关键时间点**：必须包含**问题开始时间**（故障发生）、**团队知悉时间**（告警触发/人工发现）和**恢复时间**（故障解除）。这三个时间点计算出的"检测耗时"和"恢复耗时"是衡量响应效率的核心指标。

### 3. 根因分析

使用**5-Why 分析法**，超越表面原因：

| 第 N 次追问 | 回答 |
|---|---|
| 1. 为什么聊天请求失败了？| MongoDB 连接池耗尽 |
| 2. 为什么连接池耗尽了？| 部署将连接池大小翻倍但未增加服务器限制 |
| 3. 为什么部署改了连接池大小？| 配置变更在一个只审查了代码逻辑但未审查基础设施影响的 PR 中 |
| 4. 为什么基础设施影响未被审查？| 部署流程中没有连接池变更的检查清单 |
| 5. 为什么没有检查清单？| 我们从未遇到过连接池事故 |

**根因**：流程缺失——对影响外部资源的配置变更缺少基础设施影响审查。

**5-Why 指南**：
- 第一个回答几乎从来不是真正的根因——继续追问
- 如果回答变成了"人的错误"（某人疏忽了、某人忘记了），再追问一层——什么流程或系统本可以防止这个疏忽？
- 追问到"流程/系统层面"即可停止——不需要追问到"为什么人是不完美的"

### 4. 影响

| 维度 | 详情 |
|---|---|
| **受影响用户** | 142 次聊天请求失败（23 个独立用户）|
| **持续时间** | 23 分钟（14:32 — 14:55 UTC）|
| **数据丢失** | 无 |
| **收入影响** | 无（内部工具）|
| **SLO 影响** | 可用性降至 99.7%（低于 99.9% SLO）|

### 5. 预防措施（行动项）

| # | 行动 | 负责人 | 截止日期 | 优先级 |
|---|---|---|---|---|
| 1 | 将连接池配置变更加入部署检查清单 | 张三 | 2026-08-20 | P0 |
| 2 | 添加 `maxIncomingConnections` 使用率 > 80% 告警 | 李四 | 2026-08-22 | P0 |
| 3 | 组织一次演习："MongoDB 连接池耗尽" | 王五 | 2026-09-01 | P1 |
| 4 | 在操作手册中记录连接池大小配置指南 | 张三 | 2026-08-25 | P1 |

**行动项指南**：
- 每一项行动必须有唯一负责人和具体截止日期——"大家看看"等于没人看
- 优先级定义：P0 = 必须在本次事后复盘关闭前完成或启动；P1 = 必须在下一个迭代完成
- 行动项不应过多——聚焦于真正能防止同类事故再次发生的措施（通常 3-5 项）

### 6. 经验教训

#### 做得好的
- 值班人员 3 分钟内确认了告警
- 回滚干净迅速（5 分钟）
- 事故频道中的沟通清晰及时

#### 做得不好的
- 无部署前检查清单捕获配置变更
- 告警在首条错误出现 6 分钟后才触发（延迟过长）
- 仪表盘未显示连接池使用率（监控盲区）

#### 意外发现
- MongoDB Atlas 不会拒绝连接——它将其排队，导致在错误出现之前先产生延迟飙升

## 无指责语言指南

| 不要写... | 改写为... |
|---|---|
| "张三在配置中犯了个错误" | "配置变更将连接池大小翻倍而未更新服务器限制" |
| "李四应该在审查中抓住这个问题" | "审查流程未检查基础设施影响" |
| "你为什么..." | "什么导致了..." |
| "谁负责？" | "什么流程变更能防止此类问题？" |

**核心规则**：每一个"谁的"问题都应转换为"什么的"问题。指责针对人，学习针对系统。人在压力下会犯错——好的系统设计承认这一点并提供防护。

## 事后复盘生命周期

```
草稿（24小时内） → 评审（团队 + 利益相关者） → 发布 → 行动项追踪 → 关闭（所有行动项完成）
```

**生命周期关键节点**：
- **草稿阶段**：事故处理者撰写初稿——越早越好，趁记忆新鲜
- **评审阶段**：团队和技术负责人阅读草稿，补充遗漏的视角，确保根因分析足够深入
- **发布阶段**：复盘文档对团队开放——透明是学习的前提
- **追踪阶段**：行动项进入正常的工作流（如 sprint 待办），而非搁置在复盘文档中
- **关闭阶段**：所有行动项完成后，复盘正式关闭——但文档保留作为历史参考

## 适用场景

- 事故发生后撰写复盘报告
- 评估事故响应的效率和效果
- 向新成员传授"无指责文化"的具体操作方式

## 常见问题

**Q: 如果有人真的犯了错误（比如误删了生产数据库），怎么做到无指责？**
A: 无指责不意味着无问责。它的意思是：不要停留在"谁犯了错"的层面，而是追问"为什么系统允许这个错误发生"。删除生产数据库的人可能确实犯了严重错误——但一个好的系统应该有防护措施（确认对话框、权限控制、备份）防止一个人就能造成灾难。复盘既要问责个人行为，也要追问系统漏洞。

**Q: 小事故（P3）需要写正式的 5-Why 吗？**
A: 不需要完整的 5-Why 分析，但建议至少记录"发生了什么"和"如何防止再次发生"。简版的复盘（半页文档）比没有复盘好得多。

## 反模式

| 反模式 | 失败原因 | 正确做法 |
|---|---|---|
| 事后复盘无 5-Why 分析 | 只有时间线没有根因；同类事故重复发生 | 始终追问 5 层；第一个回答从来不是根因 |
| 指责个人 | 团队隐藏事故不报；学习停止——恐惧文化取代学习文化 | 聚焦于流程和系统；使用无指责语言 |
| 行动项无负责人和截止日期 | 一切照旧；复盘成为只写不读的文档 | 每项行动有一位负责人和一个具体截止日期 |
| 事后复盘拖延数周 | 记忆模糊；细节丢失；团队已转向下一个任务——复盘失去意义 | P1 事故 24 小时内；P2 事故 48 小时内 |
| 行动项无后续跟进 | 复盘发布后就被遗忘 | 行动项与功能工作在同一系统中追踪；在下次事故审查中回顾状态 |
