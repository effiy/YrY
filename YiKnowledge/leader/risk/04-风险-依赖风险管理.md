# 依赖风险管理

> **何时使用**：新项目启动时、引入新的重要依赖时、每季度的依赖审计时。
>
> 每个外部依赖都是一项资产也是一项负债。资产是它为你解决的问题，负债是它带来的风险——停止维护、安全漏洞、不兼容升级、许可证变更。

## 依赖风险分类

### 按依赖类型

| 类型 | 风险特征 | YrY 示例 |
|---|---|---|
| **运行时依赖** | 服务运行必不可少；故障 = 服务中断 | Ollama、MongoDB、llama_index |
| **构建依赖** | 影响开发和部署；故障 = 无法发布 | Rsbuild、Vite、TypeScript |
| **开发依赖** | 影响开发效率；故障 = 开发者体验下降 | ESLint、Prettier、pytest |
| **外部服务** | 不受你控制；故障 = 功能降级 | 云 LLM API、MongoDB Atlas |
| **内部依赖** | 跨模块/跨项目依赖；故障 = 级联影响 | YiVad 调用 YiAi RPC |

### 按风险维度

| 维度 | 评估问题 | 权重建议 |
|---|---|---|
| **活跃度** | 项目最近有提交吗？issue 有响应吗？ | 25% |
| **社区规模** | 有多少贡献者？是否单人维护？ | 20% |
| **安全记录** | CVE 历史？修复响应速度？ | 20% |
| **许可证** | 许可证是否与项目兼容？ | 15% |
| **替代性** | 如果必须替换，难度多大？ | 10% |
| **版本稳定性** | API 变动频率？大版本升级成本？ | 10% |

## 依赖风险评估流程

### 第一步：盘点所有依赖

```bash
# YiAi
pip list --format=json | python -c "import json,sys; deps=json.load(sys.stdin); [print(f'{d[\"name\"]}=={d[\"version\"]}') for d in deps]"

# YiVad
pnpm ls --depth=0 --json

# YiPet
npm ls --depth=0 --json
```

### 第二步：对关键依赖评分

对每个**不可替代或故障影响大**的依赖，按六维度评分 (1-5)：

| 依赖 | 版本 | 活跃度 | 社区 | 安全 | 许可证 | 替代性 | 稳定性 | 总分 |
|---|---|---|---|---|---|---|---|---|
| llama_index | 0.12.x | 5 | 4 | 4 | 5 | 2 | 3 | 3.8 |
| motor (MongoDB) | 3.7.x | 4 | 4 | 5 | 5 | 4 | 5 | 4.5 |
| ollama | 0.6.x | 4 | 3 | 3 | 5 | 3 | 4 | 3.7 |

**评分**：1 = 风险极高，5 = 非常健康。总分 < 3.0 需要重点关注。

### 第三步：识别单点故障依赖

问：如果这个依赖明天消失了，哪些功能会中断？

| 依赖 | 影响范围 | 是否有 fallback | 迁移成本 |
|---|---|---|---|
| Ollama | 所有 AI 聊天、RAG、Agent | 有——云 LLM API 多提供商路由 | 低（已实现路由） |
| llama_index | 整个 RAG 引擎 | 无 | 高——需重写 RAG 抽象层 |
| MongoDB | 所有数据持久化 | 无 | 高——需迁移所有数据和查询 |
| Vue 3 | 整个 YiVad 前端 | 无 | 极高——需重写整个前端 |

### 第四步：制定缓解策略

| 策略 | 适用场景 | 成本 | 示例 |
|---|---|---|---|
| **抽象隔离** | 依赖可能被替换 | 中等 | llama_index 的 LLM 接口统一封装，切换提供商不需要改业务代码 |
| **多源冗余** | 外部服务依赖 | 中-高 | LLM 多提供商路由——Ollama 不可用时自动切换云 API |
| **版本冻结** | 稳定且无替代的依赖 | 低（短期）| MongoDB driver 不过早升级大版本 |
| **定期审计** | 所有依赖 | 低 | `pip audit` / `npm audit` 每季度执行 |
| **逐步解耦** | 深度耦合的依赖 | 高 | 将 llama_index 在 RAG 模块中隔离，不扩散到其他模块 |
| **寻找替代** | 高风险依赖 | 中 | 评估替代 Ollama 推理的方案；准备迁移路径 |

## YrY 依赖风险矩阵

### 高风险依赖（需主动管理）

| 依赖 | 风险 | 评分 | 缓解状态 |
|---|---|---|---|
| Ollama | 本地 GPU 故障 → 所有 AI 不可用 | 高风险 | 已缓解——多提供商路由已上线 |
| llama_index | API 变动、停止维护 → RAG 引擎需重写 | 中风险 | 部分缓解——RAG 模块已隔离 |
| MongoDB | 连接故障 → 所有数据不可用 | 中风险 | 未缓解——需灾备方案 |
| Vue 3 | 主版本升级 → YiVad 需大量改动 | 低风险 | 可接受——API 稳定 |
| YiPet 80+ CDN 厂商库 | 版本不对齐 → 扩展崩溃 | 高风险 | 未缓解——需自动化版本检查 |

### 已缓解的依赖风险

| 依赖 | 原风险 | 缓解方式 | 缓解日期 |
|---|---|---|---|
| FSEvents/watchdog | macOS 静默丢弃事件 | 替换为 apscheduler 轮询 | 2026-08 |
| 单一 LLM 提供商 | AI 功能单点故障 | 多提供商路由 | 2026-08 |

## 依赖审计检查清单

每季度执行：

- [ ] 更新所有依赖到最新的兼容版本（`pip install --upgrade` / `pnpm update`）
- [ ] 运行安全审计（`pip audit` / `npm audit` / `pnpm audit`）
- [ ] 检查是否有已停止维护的依赖（超过 12 个月无新版本）
- [ ] 检查是否有单人维护的关键依赖（巴士因子 = 1）
- [ ] 检查许可证兼容性（是否引入了 copyleft 许可证？）
- [ ] 审查是否有可以移除的未使用依赖
- [ ] 更新[风险登记册](./03-风险-风险登记册模板.md)中的依赖相关条目

## 引入新依赖的决策门

在 `pip install` 或 `npm install` 之前：

1. **确实需要吗？** 能否用现有依赖或标准库实现？（每多一个依赖 = 多一份维护负担）
2. **是否有更轻量的替代？** 不要为一个小功能引入重型框架
3. **它健康吗？** 检查 GitHub stars、最近提交、issue 响应速度
4. **许可证兼容吗？** 避免 copyleft 许可证在企业项目中
5. **团队有人熟悉吗？** 如果没人能维护它，它就是未来的技术债
6. **如果是 YiPet (Chrome 扩展)**：考虑 CSP 限制和包体积。优先使用 CDN 而非 npm

## 反模式

| 反模式 | 失败原因 | 正确做法 |
|---|---|---|
| "这个库很流行，我们用它吧" | 流行的库也可能停止维护（如 left-pad 事件） | 评估健康度，不只是流行度 |
| 从不更新依赖 | 安全漏洞和 bug 积累；最终无法升级 | 每季度更新；语义化版本范围内的自动更新 |
| 盲目追逐最新版本 | 新版本引入不兼容变更和未知 bug | 等第一个补丁版本；在 staging 环境测试 |
| 零依赖政策 | 重复造轮子；团队生产力下降 | 平衡自研和依赖——核心能力自研，通用能力依赖 |
| 没有 fallback 计划 | 关键依赖出问题时手忙脚乱 | 对不可替代的依赖必须有 fallback 方案 |
