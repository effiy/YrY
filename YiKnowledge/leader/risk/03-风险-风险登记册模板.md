## 字段说明

### 风险类别

| 类别 | 描述 | YrY 示例 |
|---|---|---|
| **安全** | 认证、授权、数据泄露、CVE | RPC 端点未认证；`target_file` 路径遍历 |
| **可靠性** | 可用性、性能、容灾 | Ollama 模型未加载；MongoDB 连接池耗尽 |
| **数据** | 数据丢失、迁移失败、兼容性 | 会话数据结构变更破坏 YiPet 兼容性 |
| **依赖** | 第三方服务、库、API 变更 | npm 包停止维护；Ollama 版本不兼容 |
| **人员** | 关键人依赖、知识孤岛 | 仅一人理解 Agent 状态机 |
| **合规** | 法律、监管、许可 | 开源许可证冲突；数据驻留要求 |
| **成本** | 预算超支、资源浪费 | 云 API 按量付费超出预期 |

### 评分标准

| 评分 | 可能性 | 影响 |
|---|---|---|
| 1 | < 5% — 极不可能 | 无用户影响或内部可见 |
| 2 | 5-15% — 不太可能 | 轻微不便，有 workaround |
| 3 | 15-35% — 可能 | 部分功能不可用，用户可感知 |
| 4 | 35-65% — 很可能 | 核心功能中断，用户无法使用 |
| 5 | > 65% — 几乎确定 | 服务完全不可用或数据丢失 |

### 风险等级

| 评分范围 | 等级 | 行动要求 |
|---|---|---|
| 1-4 | 低 | 记录并监控——不需要主动缓解 |
| 5-9 | 中 | 制定缓解计划——在下个迭代中安排 |
| 10-15 | 高 | 主动缓解——本迭代内必须启动 |
| 16-25 | 严重 | 立即行动——暂停其他工作直到风险降低 |

## 风险登记流程

```
发现风险 → 登记到册 → 评分 → 制定缓解措施 → 分配负责人 → 定期审查
    ↑                                                          │
    └──────────────────────────────────────────────────────────┘
```

### 发现渠道

| 渠道 | 触发条件 |
|---|---|
| 上线前风险评估 | 每次重大上线时识别的新风险 |
| 事后复盘 | 事故中暴露的未识别风险 |
| 技术选型 | 新技术引入的未知风险 |
| 依赖审计 | 依赖过期、安全漏洞 |
| 架构审查 | 架构偏离或过载的组件 |
| 团队回顾 | 工程师反馈的潜在问题 |

## 反模式

| 反模式 | 失败原因 | 正确做法 |
|---|---|---|
| 登记册写完后束之高阁 | 风险状态过时，登记册失去信任 | 每月更新；将审查加入日历 |
| 只登记技术风险 | 人员、成本、合规风险同样致命 | 使用完整的 7 类别分类 |
| 风险描述过于笼统 | "系统可能出问题"无法指导行动 | 描述具体的故障模式、触发条件和影响范围 |
| 缓解措施无负责人和截止日期 | 缓解措施永远不会被执行 | 每项缓解措施必须有负责人和时间线 |
| 已实现的风险不记录 | 失去了追踪缓解措施有效性的机会 | 已实现的风险移至"已实现"表，链接到事后复盘 |
