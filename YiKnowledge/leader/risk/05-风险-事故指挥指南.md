# 事故指挥指南

> 技术负责人在事故中的角色不是修 bug——是**指挥**。你的工作是让正确的人做正确的事，并确保信息流动。

## 核心角色（事故三角）

事故中必须有三个角色被明确认领。一个人可以兼任，但**绝不**能缺失：

| 角色 | 职责 | 典型承担者 | 禁止做的事 |
|---|---|---|---|
| **事故指挥官 (IC)** | 协调全局、做决策、确保角色就位 | 技术负责人 | **不能**亲自修 bug——一旦你陷入技术细节，全局协调就会丢失 |
| **处理者 (Handler)** | 排查问题、尝试修复、执行回滚 | 值班工程师 | 不能做跨团队沟通——专注解决问题 |
| **沟通者 (Communicator)** | 对内对外的状态更新、管理利益相关者期望 | 技术负责人（可兼任）或产品经理 | 不能自行宣布"已修复"——需处理者确认 |

### 角色就位的黄金 5 分钟

事故发生后**前 5 分钟**唯一要做的事：确认三个角色有人认领。

```
"我是 IC。张三处理排查。李四做沟通。现在开始计时。"
```

如果没人认领 IC，技术负责人**默认为 IC**。

## 事故严重等级

| 等级 | 定义 | IC 参与程度 | 示例（YrY 场景） |
|---|---|---|---|
| **P0** | 核心用户旅程完全中断 | 全程指挥，直到恢复 | YiAi 聊天 API 完全不可用 |
| **P1** | 显著服务降级，用户可感知 | 指挥至少 30 分钟，然后可委托 | RAG 查询大量超时，返回错误 |
| **P2** | 部分功能受影响，有 workaround | 确认角色就位后监控 | YiPet 特定角色加载失败 |
| **P3** | 轻微问题，个别用户受影响 | 不需要 IC 介入 | 某个会话的聊天记录丢失 |

## IC 决策框架

事故中的决策压力大、信息不全。使用此框架降低认知负担：

### 1. 首问：保服务还是保数据？

| 场景 | 决策 |
|---|---|
| 数据正在损坏（如错误写入覆盖了正确数据） | **先保数据**——立即停止写入，即使这意味着服务中断 |
| 服务不可用但数据完整 | **先恢复服务**——回滚是最快的恢复方式 |
| 两者都正常但性能极差 | **降级而非关闭**——让核心路径可用，牺牲非核心功能 |

### 2. 决定：修还是回滚？

| 条件 | 决策 |
|---|---|
| 最近一次部署在 30 分钟内 | **回滚**——最快、最安全 |
| 问题原因已明确且修复简单（< 5 分钟） | **修复**——但设置 10 分钟硬性上限 |
| 问题原因不明 | **回滚**——排查不应在事故中进行 |
| 回滚有数据风险（如 schema 已变更） | **修复**——回滚可能造成数据不一致 |

**黄金法则**：10 分钟内找不到原因 → 回滚。排查在生产环境上进行是制造二次事故。

### 3. 评估：升级还是不升级？

| 触发条件 | 行动 |
|---|---|
| 事故持续超过 30 分钟 | 升级——通知高管；可能影响 SLA |
| 事故影响扩大到新用户群 | 升级——通知受影响的客户团队 |
| 数据可能丢失 | 立即升级——数据丢失的恢复窗口极短 |
| 你感到不确定 | 升级——不确定时宁可升级，不要隐瞒 |

## IC 时间线操作指南

| 时间 | IC 必须做的事 |
|---|---|
| **0-2 min** | 确认三个角色就位。宣布事故开始计时 |
| **2-5 min** | 评估影响范围。决定是否需要升级 |
| **5-10 min** | 要求处理者给出根因假设。如果毫无头绪，准备回滚 |
| **10-15 min** | 如果没有进展，执行回滚或升级寻求帮助 |
| **15-30 min** | 如果持续中，安排人员轮换（单人项目无法轮换，则考虑降级方案） |
| **30+ min** | 通知高管。如果单人项目，考虑接受降级状态，先恢复部分功能 |

## IC 常见陷阱

| 陷阱 | 表现 | 解决 |
|---|---|---|
| **陷入技术细节** | IC 开始看日志、写代码 | 把排查交给处理者。IC 的唯一工具是通讯工具（Slack/电话） |
| **无人认领沟通** | 高管在问"怎么样了"，没人回复 | 指定沟通者或自己兼任。沉默比坏消息更糟糕 |
| **同时追多个假设** | 处理者在测 A，有人在测 B，没人协调 | IC 的职责是选择**一个**最高概率的假设优先验证 |
| **过早宣布恢复** | "应该好了吧"——没有验证就宣布 | 要求处理者提供恢复证据（监控截图、测试请求成功） |
| **单人项目无轮换** | 自己同时当 IC、Handler、Communicator | 承认限制。优先保数据 → 恢复服务 → 沟通。顺序执行而非并行 |

## 单人项目的特殊考量

YrY 当前是单人项目，事故指挥模式需要调整：

1. **公告优先**：如果不能同时修和沟通，先发一条"正在处理"的消息，然后静音去修
2. **回滚是朋友**：单人排查时不要深入调试——回滚比排查快
3. **接受降级状态**：不能恢复全部功能时，恢复核心路径（聊天 API），暂时牺牲非核心（RAG）
4. **5 分钟原则**：单人排查一个问题超过 5 分钟无进展，切换策略（回滚或降级）

## 事故结束后的 IC 工作

1. **确认恢复**：处理者提供恢复证据，不是 IC 自己判断
2. **解甲归田**："事故已恢复，IC 角色解除。张三负责写复盘。"
3. **安排事后复盘**：指定复盘负责人和截止时间（P0: 24h, P1: 48h）
4. **不要立即讨论根因**：事故刚结束时信息不全、情绪还在。回滚后休息 30 分钟再开始复盘
5. **更新风险登记册**：如果事故暴露了未识别的风险，立即 [登记](../risk/03-风险-风险登记册模板.md)

## IC 速查卡

```
事故发生时，IC 问这 6 个问题：

1. 三个角色有人了吗？IC / Handler / Communicator
2. 影响范围多大？哪些用户/功能受影响？
3. 严重等级是什么？P0 / P1 / P2 / P3？
4. 需要升级吗？高管 / 客户团队？
5. 回滚还是修复？最近部署 < 30min → 回滚
6. 谁在写复盘？指定人和截止时间

如果单人项目：
1. 先发公告
2. 修或回滚（10 分钟硬性上限）
3. 恢复后发更新
4. 30 分钟后开始写复盘
```

## 适用场景

- 任何 P0/P1 事故的指挥参考
- 新成员学习事故响应流程的起点（先读这个，再读 [事后复盘方法论](./02-风险-事后复盘.md)）
- 单人项目在事故中避免陷入排查死循环
