# ADR: RAG 评估基础设施

> **状态**：已接受 (2026-08-03) — 已规划，尚未实施
>
> 此 ADR 定义了 RAG 质量评估策略。RAG 模块（2026-07-31 构建）目前无自动化质量评估，任何对切分策略、嵌入模型或检索策略的变更都可能无声地降低回答质量。

## 上下文

RAG 模块的每一次变更（切分策略调整、嵌入模型升级、检索参数调整）都可能对回答质量产生正面或负面影响。没有自动化评估，这些影响是不可见的——RAG 质量可以无声地退化，直到用户投诉才发现问题。

**当前风险**：
- 切换分块大小从 512 到 1024 tokens 可能降低检索精度
- 更换嵌入模型可能改变语义匹配质量
- 调整检索 top-k 参数直接影响上下文相关性
- 对 YiKnowledge 目录结构的修改可能影响检索召回率

## 决策

**基于 `llama-datasets` + `ragas` 构建 RAG 评估基础设施，使用 4 个核心指标和 50 篇文档的双语言评估集。**

### 评估指标（4 个 ragas 指标）

| 指标 | 测量对象 | 退化信号 |
|--------|-----------------|----------|
| `faithfulness` | 回答是否基于检索到的上下文？| 模型开始编造上下文中不存在的信息 |
| `answer_relevancy` | 回答是否针对问题？| 回答开始偏离用户意图 |
| `context_precision` | 检索到的分块是否相关？| 检索结果中出现无关内容 |
| `context_recall` | 是否检索到了所有相关分块？| 相关知识点被遗漏 |

### 评估数据集

- 50 篇来自 YiKnowledge 的文档（双语言：中文 + 英文）
- 每篇文档配 3-5 个问题和预期答案
- 覆盖所有 7 个角色目录（leader、engineer、srer、producter、aier、executiver、curator）
- 包含不同文档类型：ADR、技术选型、方法论、流程指南、模板

### CI 集成

- 在每个涉及 `domain/rag/` 或 `services/rag/` 的 PR 上运行
- **召回率退化 > 5% 阻止合并** — 确保 RAG 质量不会无声退化
- 评估结果归档用于趋势分析（每个月的质量趋势图）

## 选择理由

- `ragas` 是 RAG 评估的事实标准框架
- 4 个指标覆盖检索到生成的完整管线
- 5% 召回率阈值足够保守以避免误报，同时能捕获真实的退化
- 双语言评估集反映 YrY 的多语言实际场景

## 后果

### 正面影响
- RAG 变更的影响变为可量化、可视化的指标
- 可以安全地实验不同的分块策略和嵌入模型
- 质量退化在 PR 阶段被阻止，而非上线后由用户发现

### 负面影响
- 评估数据集需要持续维护（新增知识文档时需要添加评估问题）
- CI 运行时间增加（评估可能需要几分钟）
- 存在评估指标好但实际用户体验差的情况（指标不能替代人工评估）

### 操作要求
- 评估数据集必须随知识库增长而维护
- 向 YiKnowledge 添加新内容可能需要更新评估问题
- RAG 索引重建时应触发评估重新运行

## 适用场景

- RAG 模块进行分块策略或嵌入模型变更时的质量把关
- YiKnowledge 目录结构重大调整后的质量验证
- 新 LLM 提供商接入时的生成质量对比

## 常见问题

**Q: 5% 的退化阈值是否太宽松？**
A: 不。RAG 评估指标本身有一定波动性（不同评估运行之间可能有 1-3% 的自然波动）。5% 阈值过滤掉噪声，只捕获真实的退化信号。如果发现阈值需要收紧，可以在积累足量历史数据后调整。

**Q: 评估频率如何？是否每次提交都运行？**
A: 仅对涉及 `domain/rag/` 或 `services/rag/` 的 PR 运行。全量评估（所有 50 个样本）预计需要 3-5 分钟，不会显著拖慢 CI。

## 反模式

- **仅依赖自动化指标而跳过人工评估。** Ragas 指标衡量的是技术维度的质量，但"回答是否有帮助"是用户的主观判断。自动化评估是质量基线（防止退化），人工评估是质量上限（判断是否更好）
- **评估数据集与 YiKnowledge 内容脱节。** 如果评估数据集长期不更新，它无法反映新知识的质量。添加重要知识文档时，同步添加评估问题是必需的维护工作
