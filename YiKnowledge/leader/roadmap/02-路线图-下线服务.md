# 下线服务

> **作为**技术负责人，**我想要**安全下线服务，**以便**减少运维负担、基础设施成本和架构复杂性。
>
> 服务下线是一个高风险的运营操作——它的失败模式不是"服务出问题"，而是"服务消失后才发现还有东西依赖它"。因此，下线流程的前半部分全部聚焦于"发现依赖"，而非"删除代码"。

## 定义

服务下线是安全关闭和移除服务的完整流程。与功能废弃（移除用户可见功能）不同，服务下线移除的是整个后端组件——包括其计算资源、数据存储和网络端点。

## 触发条件

- 服务已被新实现替代
- 服务不再需要（下游消费者已迁移）
- 服务正在被合并到另一个服务中
- 服务的维护成本相对于其价值过高
- 组织变更：拥有该服务的团队被解散

## 分步执行

### 第一步：发现所有依赖

在触碰任何东西之前，绘制完整的依赖图：

| 依赖类型 | 如何发现 |
|---|---|
| **上游调用者** | API 网关日志、服务网格、反向代理日志 |
| **下游服务** | 服务配置、连接字符串、客户端库引用 |
| **数据存储** | 数据库、缓存、消息队列、对象存储 |
| **基础设施** | DNS 记录、负载均衡器、防火墙规则、密钥 |
| **监控与告警** | 仪表盘、告警规则、运维手册 |
| **CI/CD** | 构建流水线、部署脚本、环境配置 |
| **文档** | 架构图、README、入职文档 |

**黄金法则**：如果你在下线之后才发现某个依赖，你已经造成了一次事故。宁可多花 50% 的时间在发现阶段，也不要事后修补。

### 第二步：制定迁移计划

对每个依赖，定义迁移路径：

| 依赖 | 迁移路径 | 负责人 | 截止日期 |
|---|---|---|---|
| 服务 A 调用我们的 API | 迁移到新服务 API | A 团队负责人 | 第 2 周 |
| 服务 B 使用我们的数据库 | 新服务将暴露数据 | B 团队负责人 | 第 3 周 |
| DNS：`old-service.example.com` | 更新指向新服务 | 基础设施团队 | 第 4 周 |

### 第三步：执行迁移

分阶段迁移以降低风险：

| 阶段 | 操作 | 回滚难度 |
|---|---|---|
| **阶段 1：双写** | 新旧服务同时接收流量 | 简单 — 直接切回流量即可 |
| **阶段 2：读新服务** | 读操作走新服务；写操作双写 | 中等 — 存在数据一致性风险 |
| **阶段 3：旧服务只读** | 旧服务只读；所有写操作走新服务 | 中等 — 可能需要数据回填 |
| **阶段 4：排空流量** | 旧服务不再接收流量 | 困难 — 旧服务数据已过时 |
| **阶段 5：移除** | 旧服务关闭；代码移除 | 非常困难 — 需要重新部署旧服务 |

**阶段说明**：
- 每个阶段至少持续数天到一周——足够观察到问题
- 在阶段 2 和 3 之间需要有数据一致性验证步骤
- 不要在阶段 5 之后立即删除基础设施（保留至少 2 周作为安全网）

### 第四步：切换

切换前检查清单：

- [ ] 所有上游调用者已完成迁移（日志验证：到旧服务的请求数为 0）
- [ ] 所有下游依赖不再需要
- [ ] 数据已完成迁移并通过验证
- [ ] 监控显示旧服务连续 1 周处理 0 流量
- [ ] 回滚计划已文档化并通过测试
- [ ] 值班团队已知悉下线计划

切换期间：
1. 停止旧服务（先不删除）
2. 监控 24-48 小时以发现任何意外错误
3. 如果一切正常，进入清理阶段

### 第五步：清理

移除服务的所有痕迹：

| 领域 | 清理操作 |
|---|---|
| **代码** | 删除仓库或标记为已归档 |
| **基础设施** | 删除虚拟机、容器、数据库、缓存、队列 |
| **DNS** | 移除 DNS 记录 |
| **CI/CD** | 移除构建流水线、部署脚本 |
| **密钥** | 轮换并移除密钥 |
| **监控** | 移除仪表盘、告警规则、运维手册 |
| **文档** | 更新架构图；移除或归档服务文档 |
| **值班** | 从值班轮换中移除 |

## 决策点与分支

| 决策点 | 选项 | 指导 |
|---|---|---|
| 部分调用者无法按时迁移 | 延长时间线 / 帮助迁移 / 强制迁移 | 如果是容量问题则帮助迁移；强制迁移仅作为最后手段 |
| 数据迁移太复杂 | 保留数据存储 / 简化迁移 / 接受数据丢失 | 除非数据明确标记为非关键，否则绝不接受数据丢失 |
| 服务在处理未知流量 | 调查 / 重新规划 / 暂停下线 | 暂停；影子流量说明依赖发现不完整 |
| 切换后需要回滚 | 重新部署旧服务 / 从备份恢复 | 这就是为何不立即删除基础设施 |

## 各阶段交付物

| 阶段 | 交付物 |
|---|---|
| 发现 | 完整的依赖关系图 |
| 规划 | 带负责人和截止日期的迁移计划 |
| 迁移 | 每个阶段有验证的分阶段迁移 |
| 切换 | 切换操作手册；回滚计划；监控期 |
| 清理 | 确认所有痕迹已被移除 |

## 适用场景

- 将 YiAi 某模块拆分为独立微服务后下线旧模块
- 从自建服务迁移到云服务后的旧服务清理
- 实验性功能验证失败后的资源回收

## 反模式

| 反模式 | 失败原因 | 正确做法 |
|---|---|---|
| 在迁移流量前删除服务 | 服务中断 | 阶段 4：排空流量至 0；验证 1 周后再进入阶段 5：移除 |
| 依赖发现不完整 | 遗留调用者在下线后崩溃 | 至少 50% 的项目时间花在发现阶段 |
| 无回滚计划 | 出问题时手忙脚乱 | 始终有回滚计划；在切换前演练一次 |
| 跳过监控期 | 切换看起来正常，但批处理作业在凌晨 3 点失败 | 至少监控 24-48 小时；覆盖所有时间段 |
| 遗漏非代码依赖 | DNS、密钥、仪表盘、文档残留 | 使用第五步的清理检查清单逐项检查 |
