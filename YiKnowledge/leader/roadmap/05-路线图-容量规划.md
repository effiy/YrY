# 容量规划

> **作为**技术负责人，**我想要**计算团队可用容量，**以便**做出现实可行的承诺，避免团队超负荷。
>
> 容量规划是路线图规划的数学基础。没有它，路线图承诺只是猜测——通常过于乐观的猜测。一个好的容量规划承认：不是所有的工作时间都等于开发时间。

## 定义

容量规划估算团队在给定期间（通常是一个季度）内实际可完成的工作量，计入所有形式的开销。它回答了"我们有多少人？他们有多少时间？这些时间中有多少可以用于路线图工作？"

## 触发条件

- **计划性触发**：每个季度开始前，在路线图规划之前
- **事件驱动触发**：
  - 团队规模变化（入职、离职、轮岗）
  - 运维负载显著变化
  - 重大组织重组或团队结构调整
  - 在承诺大型项目或截止日期前

## 分步执行

### 第一步：计算原始容量

```
原始容量（人周）= 团队人数 × 季度周数
```

示例：5 名工程师 × 13 周 = 65 人周

### 第二步：减去已知的休假时间

| 扣除项 | 如何计算 |
|---|---|
| **节假日** | 季度内的公司法定假日 |
| **计划休假** | 已知的假期、育儿假、长期休假 |
| **公司活动** | 全员大会、异地团建、团队建设活动 |

```
可用容量 = 原始容量 - 已知休假时间
```

### 第三步：减去运维开销

并不是所有可用时间都用于路线图工作：

| 开销类别 | 典型比例 | 包含内容 |
|---|---|---|
| **值班** | 5–10% | 值班轮换、事故响应 |
| **会议** | 10–15% | 站会、规划会议、审查、一对一 |
| **支持** | 5–10% | 客户升级、内部支持 |
| **招聘** | 0–5% | 面试、入职、指导 |
| **其他** | 0–5% | 培训、知识分享、开源贡献 |

**关键**：连续追踪 2-3 个季度的实际开销以获取团队的真实数值。典型的总开销为 25–35%。

### 第四步：计算净路线图容量

```
净容量 = 可用容量 × (1 - 开销比例)
```

示例：65 原始 - 5 节假日 = 60 可用 × 0.70（30% 开销）= **42 人周可用于路线图工作**

### 第五步：按类别分配

使用[技术路线图](./plan-tech-roadmap.md)定义的类别：

| 类别 | 目标比例 | 人周（示例）|
|---|---|---|
| 产品功能 | 55% | 23 |
| 技术投入 | 25% | 10.5 |
| 探索 | 10% | 4 |
| 缓冲 | 10% | 4.5 |
| **总计** | **100%** | **42** |

**缓冲的重要性**：10% 缓冲不是"空闲时间"——它是"未知的已知"的预留空间：你知道会有意外，但不知道具体是什么。不设缓冲意味着每一个意外都变成一个未兑现的承诺。

### 第六步：追踪实际并校准

每个季度结束后，比较计划 vs 实际：

| 指标 | 计划 | 实际 | 偏差 |
|---|---|---|---|
| 净容量（人周）| 42 | 38 | -10% |
| 交付功能数 | 5 | 4 | -20% |
| 非计划工作 | 4.5（缓冲）| 8 | +78% |

如果实际持续偏离计划，调整你的开销比例或缓冲大小。

**校准信号**：
- 缓冲总是被耗尽 → 增加缓冲比例，或将反复出现的"非计划工作"列入计划
- 功能交付持续低于计划 → 检查估算是否过于乐观，或障碍物是否未在估算中体现
- 净容量持续低于预期 → 开销比例需要调高（可能有隐形开销被遗漏了）

## 决策点与分支

| 决策点 | 选项 | 指导 |
|---|---|---|
| 开销高于预期 | 减少开销 / 接受并降低计划容量 | 优先自动化（CI/CD、告警）；然后减少会议 |
| 关键人物成为瓶颈 | 招聘 / 培训 / 重新分配 | 在瓶颈人物离开前培训其他人；所有关键系统的巴士因子 > 1 |
| 缓冲被非计划工作耗尽 | 调查根因 / 增加缓冲比例 | 如果非计划工作反复出现，它就是计划工作——把它放在路线图上 |
| 团队持续低于容量预期 | 缩小范围 / 增加人手 / 延长时间线 | 不要寄望于个人英雄主义；缩小范围以匹配容量 |

## 关键产出

| 阶段 | 产出 |
|---|---|
| 计算 | 包含所有扣除项的容量表格 |
| 分配 | 按类别的人周分配 |
| 追踪 | 季度计划 vs 实际对比 |
| 校准 | 下季度基于实际情况调整开销比例 |

## 适用场景

- 每个季度开始前的路线图规划输入
- 团队规模发生变化时的容量重新评估
- 向管理层说明"为什么我们不能同时做 X 和 Y"

## 常见问题

**Q: YrY 当前是单人项目——容量规划还需要吗？**
A: 需要，但可以简化。单人项目的容量规划重点是"自我诚实"——你每周有多少小时真正用于开发，多少被会议、调试、学习消耗。这为新成员加入时的容量估算提供了数据基础。

**Q: 非计划工作的占比太高怎么办？**
A: 连续几个季度追踪非计划工作的来源。如果每次都是事故修复，技术债务削减是关键。如果每次都是"领导层突然的要求"，需要更好的沟通机制。两周详细检测后，将其分类，将反复出现的列入下季度计划。

## 反模式

| 反模式 | 失败原因 | 正确做法 |
|---|---|---|
| 假设 100% 利用率 | 没有人投入 100% 时间在路线图项目上——会议、支持、学习都在消耗时间 | 追踪实际开销；使用 25–35% 作为起始估算 |
| 容量规划是一次性行为 | 无法适应团队或运维负载的变化——季度中期的变化无法反映 | 每季度更新；团队规模变化时重新计算 |
| 忽视巴士因子 | 计划中存在单点故障——如果某个关键人离职，计划完全失效 | 每个关键路径至少有 2 个人可以执行 |
| 为你希望拥有的团队做规划 | 5 人团队按 8 人输出来做规划——结果不可实现 | 按实际人数规划，而非预算人数 |
| 无缓冲 | 每一个意外都变成一个未兑现的承诺——团队永远在"延期" | 最低 10% 缓冲；在波动环境下增加 |
