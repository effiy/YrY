# 管理技术债务

> **作为**技术负责人，**我想要**追踪、优先级排序和削减技术债务，**以便**团队保持长期速度和系统可靠性。
>
> 技术债务就像是工程团队的"信用额度"——适度的技术债务可以在短期内加速交付，但如果不持续偿还，利息会侵蚀团队的交付能力。

## 定义

技术债务是任何以短期速度为代价换取长期成本的代码、架构或运维实践。就像金融债务一样，它会累积利息——拖延越久，修复成本越高。

**不是所有技术债务都是坏的**：有意识地接受技术债务（如先用最简单的方式实现功能，上线验证后再重构）是明智的工程策略。坏的技术债务是**无意识地积累的**——没有记录、没有优先级、没有偿还计划。

## 适用场景

- 团队稳定但交付速度在下降
- 值班负担增加；事故更频繁
- 新工程师入职需要过长时间
- 简单变更需要触碰很多文件或服务
- 依赖项落后数年；安全补丁无法应用

## 执行步骤

### 第一步：识别和记录技术债务

技术债务的识别来源：

| 来源 | 寻找什么 |
|---|---|
| **事故事后复盘** | 根因是不是已知的技术债务项？|
| **开发者摩擦** | 工程师在回顾会议上抱怨什么？|
| **代码审查** | 出现"我们以后修复这个"评论的模式 |
| **依赖审计** | 过时的库、不支持的版本、安全 CVE 漏洞 |
| **架构审查** | 超出原始设计的组件 |
| **入职痛点** | 新成员在哪些地方遇到困难？|

### 第二步：按类型和影响分类

| 类型 | 示例 | 典型利率 |
|---|---|---|
| **架构债务** | 应该拆分的单体应用；对访问模式而言错误的数据库 | 高 — 每个功能都更难做了 |
| **代码债务** | 重复逻辑、不清晰的命名、缺失测试 | 中等 — 拖慢该领域的变更 |
| **依赖债务** | 过时的库、不支持框架 | 中等 — 安全风险随时间增长 |
| **运维债务** | 手动部署、无监控、无运维手册 | 高 — 每次事故更严重 |
| **知识债务** | 只有一个人知道 X 如何工作 | 关键 — 巴士因子为 1 |

**YrY 典型技术债务实例**：

| 类型 | 具体项目 | 影响 |
|---|---|---|
| 架构债务 | YiVad 零测试覆盖 | 每次重构携带未知回归风险 |
| 代码债务 | ApiOptions 类型不匹配 | 临时 Workaround 积累 |
| 依赖债务 | YiPet 80+ 厂商库手动版本对齐 | React/ReactDOM 版本不匹配会崩溃 |
| 知识债务 | Agent 模式状态机仅一人理解 | 修改 Agent 逻辑风险极高 |
| 运维债务 | 无 CI/CD 流水线 | 每次部署是手动操作 |

### 第三步：量化成本

对每项技术债务，估算：

| 度量 | 如何估算 |
|---|---|
| **当前成本** | 每个迭代浪费了多少时间？（变更更慢、手动补救操作）|
| **未来成本** | 成本增长多快？（线性、指数？）|
| **修复成本** | 解决它需要多少人周？|
| **风险** | 如果不修复，最坏会发生什么？|

### 第四步：优先级排序

使用简化的 ROI 公式：

```
优先级分数 = (当前成本 × 增长率 × 风险系数) / 修复成本
```

同时考虑：

| 优先级信号 | 含义 |
|---|---|
| **修复它能解锁一个功能** | 高优先级 — 债务在阻碍价值交付 |
| **修复它能预防一个即将发生的事故** | 高优先级 — 风险迫在眉睫 |
| **修复它能每个迭代节省时间** | 中优先级 — 稳定的 ROI |
| **修复它"会更好"** | 低优先级 — 记录但暂不安排 |

### 第五步：分配容量

保护固定比例的时间用于技术债务削减：

| 情况 | 建议比例 |
|---|---|
| 绿地项目（< 6 个月）| 5–10% |
| 增长中的产品（6 个月 — 2 年）| 15–20% |
| 成熟产品（2 年以上）| 20–25% |
| 事故后或审计发现后 | 暂时 30%+ |

如果不能分配至少 15%，你正在从未来借款。记录这个风险。

### 第六步：追踪削减进展

| 指标 | 为什么重要 |
|---|---|
| **技术债务积压量** | 在增长还是减少？|
| **债务项平均存在天数** | 旧项目在解决还是被忽视？|
| **花在技术债上的容量占比** | 你是否在保护这个分配比例？|
| **已知债务引发的事故次数** | 你是否在支付利息？|
| **速度趋势** | 债务削减在改进速度吗？|

## 关键产出

- 技术债务登记册（带分类、成本和优先级的积压）
- 季度技术债务削减计划（将被解决的项目）
- 容量分配承诺（路线图的百分比）
- 趋势报告：债务积压量和存留时间随时间的变化

## 适用场景

- 季度路线图规划中确定技术投入的优先级
- 向管理层解释"为什么我们需要放慢功能开发速度"
- 事故后的根因分析——确定是哪个已知债务导致了事故

## 常见问题

**Q: 如何向产品经理解释"技术债削减"的价值？**
A: 用产品经理能理解的术语翻译技术债：不说"我们需要重构数据访问层"，而说"重构后，每个数据相关的功能开发速度会快 30%"。不说"我们需要升级 React"，而说"不升级的话，3 个月后安全审计会阻止我们上线新功能"。将技术债的"利息"翻译成"功能交付速度的下降"。

**Q: 净容量到底如何分配给技术削减和功能开发？**
A: 净容量是可用容量减去开销后的结果。其中，技术债务削减占比建议 15-25%，具体取决于项目的成熟度和其他需求。如果净容量不够，应首先审视开销是否有削减的空间。

## 反模式

| 反模式 | 失败原因 | 正确做法 |
|---|---|---|
| 一年一次技术债务冲刺 | 债务持续积累；一年一次的冲刺跟不上积累速度 | 每个迭代保护固定比例 |
| "下个项目再修" | 下个项目有自己的截止日期和自己的债务——承诺落空 | 在你已经在改动的区域中修债务——"童子军规则" |
| 记录但不做优先级 | 积压量增长成坟墓——无人问津的文档不产生价值 | 每月审查；如果某项目永远不会被修复，删掉它 |
| 只追踪代码债 | 运维和知识债务的破坏性丝毫不亚于代码债——但更不可见 | 使用 5 类型分类；审计所有类型 |
| 对利益相关者不可见 | 产品方不理解为什么速度在下降——只能猜测 | 用产品方能理解的语言报告技术债务成本：功能更慢、事故更多 |
