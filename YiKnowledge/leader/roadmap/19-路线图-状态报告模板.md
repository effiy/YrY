# 项目状态报告模板

> 状态报告的目的不是让你"汇报工作"——是让读者**不用问你**就知道他们在意的事。

## 周报模板

### 向上（技术负责人 → 高管，5 句话）

```markdown
## 本周关键进展
- [最多 3 条，每条一句话]
- 示例：聊天服务稳定性改进完成，预期连接池事故从月均 1 次降到 0

## 需要关注的阻碍
- [1 条，附带所需的决策]
- 示例：MongoDB 存储月增 20%，需要确定归档策略。建议下周三前决定

## 下周重点
- [1-2 条]
```

### 向外（技术负责人 → 产品经理）

```markdown
## 本周交付
| 功能 | 状态 | 备注 |
|---|---|---|
| ProTable 新布局 | ✅ 完成 | 已合并，下周上线 |
| Agent 工具调用 | 🔄 进行中 | 完成 70%，预计下周三 |
| RAG 分块优化 | ⏸️ 暂停 | 被 P0 事故阻塞，本周恢复 |

## 风险与阻碍
- Agent 工具调用可能延期 1 周——依赖 Ollama 工具调用格式升级

## 下周计划
- Agent 工具调用完成开发
- RAG 分块优化恢复
```

### 向内（技术负责人 → 工程团队）

```markdown
## 本周进展
- [本周完成的技术工作，团队内部可以包含技术细节]

## 技术决策
- [本周做出的技术决策——链接到 ADR]

## 值得关注的 PR
- [本周的亮点 PR——值得团队学习]
- PR #xxx: Agent 状态机改用状态模式重构——设计值得一看

## 技术债新增
- [本周新增的技术债务项]
```

### 单人项目周报简化版

单人项目不需要向团队汇报，但**写给自己看**的周报仍有价值——强迫自己回顾和规划：

```markdown
## 本周完成
- [ ] 目标 1: ✅/❌
- [ ] 目标 2: ✅/❌
- [ ] 目标 3: ✅/❌

## 意外消耗的时间
- [什么占用了计划外的时间？]

## 下周 3 个目标
1. 
2. 
3. 
```

## 报告编写规则

| 规则 | 说明 |
|---|---|
| **周报 5 句话以内** | 如果超过 5 句话，读者不会细读 |
| **先说结论** | 不要按时间顺序——按重要性排序 |
| **坏消息不延迟** | 本周的问题本周报，不要攒到"情况好一点再说" |
| **数据 > 形容词** | "合并了 12 个 PR" > "交付了很多功能" |
| **每条阻碍带解决方案** | 不只是"有问题"——"有问题+我建议的解决方案+需要你做什么决策" |

## 反模式

| 反模式 | 失败原因 | 正确做法 |
|---|---|---|
| 流水账 | "周一做了 A，周二做了 B..."——读者需要的是结果，不是日程 | 按重要性分类：进展/阻碍/计划 |
| 只有进展没有阻碍 | 显得一切顺利——当问题最终暴露时，信任已经受损 | 每个周报至少提一个风险或阻碍（如果有） |
| 技术术语轰炸高管 | "优化了 MongoDB 连接池 maxPoolSize"——高管不理解也不在意 | "聊天服务稳定性提升" |
| 周报太长 | 3 页的周报——没有人会读第二页 | 强制缩短；如果觉得不够，用链接指向详情 |
| 每周围绕同样的问题 | 连续 3 周同样的阻碍——说明问题没有被真正解决 | 如果一个问题出现了 3 次，升级处理方式 |
