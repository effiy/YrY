# 废弃功能

> **作为**技术负责人，**我想要**安全地废弃和移除功能，**以便**产品保持清洁、维护负担减少、用户平稳过渡。
>
> 功能废弃是一项"人"的流程，其难度不在于代码删除，而在于用户沟通和迁移。一份好的废弃计划让用户感觉"我在升级"，而非"我在失去功能"。

## 定义

功能废弃是从产品中移除功能的过程。它包含三个阶段：公告、警告、移除。

```
公告 ──► 警告（缓冲期）──► 移除
  │            │               │
告诉用户      用户在应用      功能消失；
功能将被      内看到废弃      代码被删除
移除          提示
```

## 触发条件

- 功能使用率接近零但消耗大量维护工作
- 功能正在被更好的替代方案取代
- 功能不再符合产品策略
- 功能正在引发安全或合规问题
- 功能是一个未通过验证的实验

## 分步执行

### 第一步：评估影响

在决定废弃之前，需要理解：

| 问题 | 如何回答 |
|---|---|
| **谁在用？** | 数据分析：DAU/MAU、功能使用率、用户分组 |
| **依赖程度如何？** | 是核心工作流还是辅助功能？|
| **替代方案是什么？** | 是否有迁移路径？是自助还是手动？|
| **维护成本多高？** | 每季度人周数、事故次数、技术债务量 |
| **风险有哪些？** | 流失风险、声誉风险、合同风险 |

### 第二步：做出废弃决策

| 如果... | 那么... |
|---|---|
| 使用率 < 1% 用户 且 低依赖 | **执行废弃**，短时间线（30 天）|
| 使用率 < 5% 用户 且 有迁移路径 | **执行废弃**，标准时间线（90 天）|
| 使用率 > 5% 用户 或 高依赖 | **重新考虑**——能否改进而非移除？|
| 企业客户有合同 | **检查合同**——可能有义务承诺 |

### 第三步：定义废弃时间线

| 阶段 | 持续时间 | 行动 |
|---|---|---|
| **公告** | 第 0 天 | 博客文章、给受影响用户发邮件、应用内通知、文档更新 |
| **警告** | 30–90 天 | 应用内废弃横幅、迁移指南、支持团队准备好回答问题 |
| **移除** | 时间线结束时 | 功能移除、代码删除、文档归档 |

对于企业客户：额外增加 30-60 天的扩展期，由客户经理直接联系。

### 第四步：构建迁移路径

| 迁移类型 | 示例 |
|---|---|
| **自助迁移** | "点击此处将你的数据迁移到新功能" |
| **导出** | "在 [日期] 之前以 CSV/JSON 格式导出你的数据" |
| **有指南的手动迁移** | 带截图的逐步迁移指南 |
| **辅助迁移** | 支持团队帮助企业客户迁移 |

### 第五步：沟通

沟通计划：

| 受众 | 渠道 | 时间 | 内容 |
|---|---|---|---|
| **所有用户** | 邮件、应用内通知、更新日志 | 第 0 天（公告）| 变化了什么、为什么、何时、怎么做 |
| **活跃用户** | 邮件、应用内通知 | 第 30 天、第 60 天 | 提醒 + 迁移指南 |
| **企业客户** | 客户经理 | 第 0 天 | 单独联系；延长时间线 |
| **内部** | Slack、会议 | 第 -7 天（提前公告）| 支持团队培训；FAQ 准备 |

### 第六步：执行移除

移除前检查清单：

- [ ] 所有用户已至少收到 3 次通知
- [ ] 迁移路径可用且已测试
- [ ] 支持团队有处理迁移问题的操作手册
- [ ] 数据分析确认使用率正在下降
- [ ] 功能开关已就绪（如需要可重新启用）

移除后：

- [ ] 删除功能代码和测试
- [ ] 删除功能专用基础设施
- [ ] 归档文档
- [ ] 更新[技术债务登记册](./manage-tech-debt.md)——移除相关项目
- [ ] 移除后监控：是否有意外错误或用户投诉？

## 决策点与分支

| 决策点 | 选项 | 指导 |
|---|---|---|
| 用户对抗废弃 | 延长时间线 / 改进迁移方案 / 重新考虑 | 如果迁移困难则延长；如果使用率高于估计则重新考虑 |
| 废弃可能导致用户流失 | 接受风险 / 推迟 / 取消 | 如果维护成本 > 流失风险则接受；如果流失风险高则推迟 |
| 功能仅被一个大客户使用 | 谈判 / 仅对该客户延期 / 构建定制迁移 | 不要让一个客户绑架产品；谈判过渡方案 |
| 构建迁移路径太贵 | 仅导出 / 手动迁移 / 延长时间线 | 仅导出是可接受的，如果数据是主要价值 |

## 各阶段交付物

| 阶段 | 交付物 |
|---|---|
| 评估 | 使用分析、影响评估、废弃建议 |
| 规划 | 废弃时间线、迁移路径、沟通计划 |
| 公告 | 博客文章、邮件、应用内通知、文档 |
| 警告 | 迁移指南、支持团队操作手册、监控设置 |
| 移除 | 代码删除、基础设施清理、移除后验证 |

## 适用场景

- YiVad 中某个页面或组件不再被使用时的废弃流程
- YiPet 中某个功能被更好的替代方案取代
- 实验性 Agent 模式功能未通过验证

## 反模式

| 反模式 | 失败原因 | 正确做法 |
|---|---|---|
| 无预警直接移除 | 用户感到意外和愤怒 | 至少 30 天通知；重大功能至少 90 天 |
| 废弃但无迁移路径 | 用户被困在无处可去的状态 | 至少提供数据导出功能 |
| "先隐藏起来就好了" | 代码仍然存在，仍需维护——隐藏的功能也是技术债 | 移除代码；隐藏是延期，不是解决 |
| 忽视企业客户 | 大客户有不同的期望和合同义务 | 单独的沟通渠道；延长时间线 |
| 无内部沟通 | 支持团队被用户问题打了个措手不及 | 在公开宣布前先培训支持团队 |
