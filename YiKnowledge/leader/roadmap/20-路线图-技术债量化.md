# 技术债务量化 — 如何计算技术债的成本

> "代码很烂，需要重构"——产品经理听不懂。"过去 3 个月，我们每周花 4 小时修复因缺少测试而漏掉的 bug"——产品经理听得懂。

## 为什么需要量化

不量化的技术债 = 不存在于利益相关者的决策框架中。

| 没有量化 | 量化后 |
|---|---|
| "我们需要还技术债" | "投入 2 周还这笔债，之后每季度节省 3 周" |
| "代码质量在下降" | "交付速度从每周 2 个功能降到 1.3 个" |
| "这个模块需要重写" | "这个模块的修改成本是其他模块的 3 倍" |

## 三类成本

### 1. 直接成本：额外的时间消耗

**定义**：因为技术债务，每次做类似操作时多花的时间。

**公式**：
```
直接成本（人周/季度）= 额外耗时（小时/次）× 操作频率（次/季度）÷ 40
```

**YrY 示例 — YiVad 零测试覆盖**：

| 操作 | 额外耗时 | 季度频率 | 季度浪费 |
|---|---|---|---|
| 修改 ProTable 数据管线后的手动回归测试 | 2 小时/次 | 6 次 | 12 小时 |
| 排查参数名不匹配 bug（`filter`/`query`） | 1.5 小时/次 | 3 次 | 4.5 小时 |
| 重构 composable 后的行为验证 | 1 小时/次 | 4 次 | 4 小时 |
| **合计** | | | **20.5 小时 ≈ 0.5 人周/季度** |

如果有 composable 测试覆盖，这些时间大部分可省去。

### 2. 间接成本：风险和机会损失

**定义**：技术债务导致的事故风险和交付延迟。

**事故风险成本**：
```
事故预期成本 = 事故概率（次/年）× 事故影响（小时/次）× 人时成本
```

**机会成本**：
```
机会成本 = 本可交付但因债务而推迟的功能数 × 功能价值
```

**YrY 示例**：

| 风险 | 概率 | 影响 | 年度预期成本 |
|---|---|---|---|
| YiPet React/ReactDOM 版本不匹配导致扩展崩溃 | 10%/年 | 4 小时排查 + 用户影响 | 0.1 × 4 = 0.4 小时 → 低 |
| Agent 状态机 bug 导致错误回答 | 20%/年 | 2 小时排查 + 用户信任损失 | 0.2 × 2 = 0.4 小时 → 低（目前用户少） |
| 无 CI/CD，手动部署失误 | 15%/年 | 1 小时回滚 | 0.15 × 1 = 0.15 小时 → 极低 |

### 3. 复合成本：债务利息

**定义**：技术债务随代码增长而加速恶化。

```
债务利息率 = （现在修复成本 - 最初引入成本）÷ 最初引入成本 × 100%

如果最初写测试需要 2 天，现在补测试需要 5 天（因为要理解已有代码的逻辑）：
利息率 = (5 - 2) / 2 × 100% = 150%
```

**利息随时间加速**：每推迟一个季度修复，修复成本增加约 20-50%。

## 量化报告模板

```markdown
# 技术债务成本报告 — [债务名称]

## 摘要
[一句话：什么债务，什么影响]

## 直接成本
| 成本项 | 季度浪费（小时） | 年度浪费（小时） |
|---|---|---|
| | | |
| **合计** | **X 小时** | **Y 小时 (≈ Z 人周)** |

## 风险成本
| 风险 | 年概率 | 单次影响 | 年度预期 |
|---|---|---|---|
| | | | |

## 修复方案
- 投入：[人周]
- 修复后季度节省：[人周/季度]
- ROI = 修复后年节省 / 修复投入
- 回本周期：[季度数]

## 不修复的后果
- 6 个月后：修复成本 +XX%
- 12 个月后：可能引发的事故
```

## YrY 实际量化示例

### 债务 1：YiVad 零测试覆盖

```
直接成本：0.5 人周/季度（手动回归测试）
风险成本：低（当前用户少，bug 影响范围有限）
修复投入：2-3 人周（composable 测试）
修复后季度节省：0.4 人周/季度
ROI = (0.4 × 4) / 2.5 = 0.64（年度节省 1.6 人周，投入 2.5 人周）
回本周期：6 个季度

判断：ROI < 1——纯财务角度看不算紧迫。但风险维度不同：
如果不修复，随着代码量增长，直接成本将非线性增长。
而且测试建立后，未来新功能的测试成本会显著下降。
综合判断：P0——在单人项目中是为未来团队扩展做准备。
```

### 债务 2：无 CI/CD 流水线

```
直接成本：0.1 人周/季度（手动部署时间短——单人项目）
风险成本：部署失误 0.15 次/年 × 1 小时 = 0.15 小时/年
修复投入：2-3 人周（GitHub Actions 搭建）
修复后季度节省：0.05 人周/季度
ROI = (0.05 × 4) / 2.5 = 0.08
回本周期：12+ 个季度

判断：ROI 极低——单人项目的部署成本微不足道。
待到团队 ≥ 2 人时重新评估。
当前优先级：P2——推迟至 2027 Q1。
```

## 如何用这些数据说服人

| 受众 | 给他们什么数据 |
|---|---|
| **产品经理** | "不修这笔债，每个新功能的开发时间每季度增加约 15%。修了之后，开发速度恢复到当前水平。" |
| **高管** | "目前这笔债每月消耗约 X 小时。按团队规模增长到 3 人计算，6 个月后消耗将翻倍。" |
| **工程师** | "这笔债使你在修改 ProTable 数据管线时每次多做 2 小时手动测试。修复后这 2 小时可以花在新功能上。" |

## 反模式

| 反模式 | 失败原因 | 正确做法 |
|---|---|---|
| 把所有债都算成"紧急" | 如果每项债务的 ROI 都 > 10，你的计算方式有问题 | 诚实计算；有些债的 ROI < 1——那就是不划算的——推迟 |
| 只算直接成本 | 风险和机会成本才是真正的大头 | 三类成本都算；风险成本即使概率低，影响可能极大 |
| 夸大数字 | "这个债每季度浪费 10 人周"——实际追踪后发现是 2 人周→失去信誉 | 保守估算；如果实际比估算高，那是好消息 |
| 一次报告再也不更新 | 债务成本会随时间变化——修复成本在涨，风险可能在变 | 每季度更新技术债务登记册中的成本估算 |
