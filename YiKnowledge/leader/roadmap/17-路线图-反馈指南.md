# 反馈指南

> 反馈不是年终绩效考核的那次谈话——反馈是**持续的小对话**。最好的反馈让人当场就知道自己做了什么以及如何改进，而非等到 6 个月后才发现方向错了。

## 反馈原则

1. **即时 > 延迟** — 事情发生后 24 小时内给反馈。6 个月后说"你上次那个 PR..."毫无意义——双方都忘了细节
2. **具体 > 笼统** — "你做得很好"无法复现。"你在处理那个连接池 bug 时，先写了复现测试再修复——这个流程非常好"
3. **行为 > 人格** — "这个函数的错误处理缺了超时分支"而非"你写代码不够仔细"
4. **私下给纠偏反馈，公开给正向反馈** — 批评在私下，赞扬在众人面前
5. **双向** — 问"我应该开始/停止/继续做什么？"和你告诉他们同等重要

## 正向反馈 (Reinforcing Feedback)

正向反馈的目的：让对方知道**什么做对了**，以便**继续这样做**。

### 何时给正向反馈

| 触发条件 | 示例 |
|---|---|
| 一个超出预期的结果 | "你写的 ADR 替代方案分析非常透彻，后来者不需要重新调研" |
| 一个值得复现的行为 | "你在 Code Review 中发现了一个并发 bug，这是高价值的审查" |
| 一个明显的进步 | "和上个月相比，你的 PR 描述清晰了很多，审查者能快速理解上下文" |
| 承担了困难的工作 | "那个 SSE 流解析的问题困扰了我们两周，你搞定了" |

### 正向反馈公式

```
SBI 模型：
Situation: 什么场景下
Behavior: 你做了什么
Impact: 带来什么影响

示例：
"上周处理知识监听器那个故障时（Situation），
你不只是在修 bug，还写了复现测试和事后文档（Behavior），
这让 future reviewer 不需要再推导一遍根因（Impact）。"
```

## 纠偏反馈 (Corrective Feedback)

纠偏反馈的目的：让对方知道**什么需要改变**，以及**为什么**。

### 何时必须给纠偏反馈

| 触发条件 | 为什么不等 |
|---|---|
| 同样的错误重复出现 | 第一次可能是误解，第二次就是模式了 |
| 行为影响了其他人 | 你的沉默 = 默许 |
| 代码质量问题有恶化趋势 | 今天的一个 `except: pass`，明天的十个 |
| 承诺未兑现 | 信任是基于可靠性的 |

### 纠偏反馈公式

```
SBI + Alternative:
Situation: 什么场景下
Behavior: 你做了什么
Impact: 带来什么影响
Alternative: 下次可以怎么做

示例：
"这次上线时（Situation），
风险评估检查清单没有填完就上线了（Behavior），
结果漏掉了 CORS 配置的检查，QA 环境测不出来但生产有问题（Impact）。
下次上线前，检查清单每一项都必须确认。如果有不确定的项，先讨论再上线（Alternative）。"
```

### 纠偏反馈对话模板

```
1. 开场（设定意图）：
   "我想和你聊一下昨天的 Code Review，目的是确保我们的审查流程在帮助而非阻碍。"

2. 描述观察（SBI）：
   "我看到你昨天审查张三的 PR 时，给了一条'这里改一下'的评论但没有说为什么。"

3. 说明影响：
   "张三改了你说的，但后来发现你的建议和性能有关，而他改的方向恰好降低了性能。
   如果没有解释原因，提交者只能猜测你的意图。"

4. 倾听对方视角：
   "你是怎么看待那次审查的？"

5. 共同确定改进方式：
   "以后在审查评论里加一句原因，比如'nit: 用 for...of 而非 forEach，
   因为前者支持提前 break 且在大数组上有性能优势'。你觉得可行吗？"

6. 确认：
   "好的。我下个月会留意一下，看看这种方式是否有效。"
```

## 反馈时机指南

| 场景 | 时机 | 方式 |
|---|---|---|
| 代码审查发现小问题 | 审查时直接评论 | 异步——PR comment |
| 代码审查发现模式性问题 | 当天或第二天 | 同步——5 分钟私聊 |
| 行为影响团队 | 24 小时内 | 同步——15 分钟私聊 |
| 超出预期的优秀工作 | 看到后立即 | 公开——团队频道表扬 |
| 需要正式讨论的严重问题 | 准备后安排 | 30 分钟正式会议（提前告知议题） |

## 接受反馈

技术负责人不仅要给反馈，还要**主动要反馈**——这建立双向信任。

### 主动要反馈

```
"我想改进我的 [代码审查/技术决策/沟通方式]。你有没有注意到
我最近在哪些地方可以做得更好？"
```

### 接受反馈时

| 要做 | 不要做 |
|---|---|
| 说"谢谢"——对方冒了风险告诉你 | 解释或辩解——"但你不知道当时的背景..." |
| 追问"能给我一个具体例子吗" | 反攻——"你自己也好不到哪去" |
| 确认理解——"你的意思是..." | 沉默或岔开话题 |
| 24 小时后跟进——"我思考了你的反馈，我的改进计划是..." | 口头答应但无后续 |

## 反馈的常见陷阱

| 陷阱 | 表现 | 纠正 |
|---|---|---|
| **三明治反馈** | "你做得不错...但是...总体还是好的"——对方只听开头和结尾的表扬，中间的批评被过滤 | SBI 直说；不必包裹在表扬中。正向和纠偏分开 |
| **反馈堆积** | 攒了半年的问题在一次谈话中倾泻 | 即时反馈；如果确实攒了，承认"我应该早点和你说" |
| **模糊反馈** | "你需要更积极主动"——什么叫更积极主动？ | 具体行为 + 期望行为 + 例子 |
| **只给纠偏不给正向** | 团队只听到你批评，觉得"永远不够好" | 正向:纠偏 ≈ 3:1 是一个好的比例 |
| **公开纠偏** | 在团队会议上批评个人——羞辱不是反馈 | 私下给纠偏反馈；公开场合说"我们"而非"你" |
| **不问同意** | 上来就说"我要给你一个反馈"——对方进入防御模式 | 先问："关于昨天的 Code Review，可以给你一个反馈吗？" |

## 单人项目的反馈

当前 YrY 是单人项目，没有团队成员可给反馈。但仍适用：

- **自我反馈**：每月回顾自己这个月的代码质量、决策质量、时间管理。和自己做月度回顾
- **从系统获取反馈**：测试覆盖率告诉你测试够不够，lint 告诉你代码是否规范，监控告诉你服务是否稳定
- **向未来团队成员要反馈**：入职流程回顾时，问新成员"过去一个月你看到哪些我应该改进的地方？"

## 适用场景

- 团队 Code Review 中发现模式性问题
- 工程师需要改进某个技能领域
- 季度绩效考核前的持续反馈积累
- 建立反馈文化——让团队成员之间也能安全地互相反馈
