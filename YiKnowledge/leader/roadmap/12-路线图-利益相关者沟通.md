# 利益相关者沟通指南

> **何时使用**：每周状态更新、季度汇报、事故沟通、路线图变更同步。
>
> 技术负责人的沟通能力直接影响团队的可信度。坏的沟通让好的工作被埋没；好的沟通让风险在变成事故之前被看见。

## 沟通原则

1. **先说结论，再说细节** — 高管和产品经理没有时间听你推导。先告诉他们"是什么"和"所以呢"，再解释"为什么"
2. **坏消息不延迟** — 隐藏坏消息不会让它变好，只会让它在你无法控制的时间以更糟的方式暴露
3. **用数据而非形容词** — "服务很慢"无法行动。"p99 延迟从 200ms 升到 800ms"可以
4. **区分事实和判断** — "系统在 14:32 宕机"是事实。"我认为是连接池问题"是判断。混淆两者会误导决策
5. **每次沟通都有明确的 ask** — 读者读完你的消息后应该知道：你需要他们做什么？

## 按受众的沟通模式

### 向上沟通（高管/executiver）

**他们关心什么**：风险、时间线、资源需求、对业务目标的影响。

**不要**：技术细节、实现方案、架构讨论。

| 场景 | 格式 | 频率 | 核心内容 |
|---|---|---|---|
| 周状态更新 | 3-5 句 Slack/邮件 | 每周 | 本周关键进展 + 1 个风险/阻碍 + 需要什么决策 |
| 季度汇报 | 一页纸文档 | 每季度 | 关键成果、关键数字、风险、下季度重点 |
| 事故通报 | 即时消息 → 事后简报 | 事件驱动 | 影响范围、当前状态、预计恢复时间、需要什么支持 |
| 路线图变更 | 提前沟通 | 事件驱动 | 变更内容、原因、影响、替代方案 |

**高管周更新模板**：
```
本周关键进展：
- [最多 3 条，每条一句话]

需要关注的风险/阻碍：
- [1 条，说明影响和需要的决策]

下周重点：
- [1-2 条]
```

**反面示例**："本周我们优化了 MongoDB 连接池配置，将 maxPoolSize 从 50 调整到 100，同时增加了服务器端 maxIncomingConnections..."
**正确写法**："本周完成了聊天服务稳定性改进，预期将连接池相关的事故从每月 1 次降到 0。"

### 向外沟通（产品经理）

**他们关心什么**：何时交付、功能是否完整、是否有阻塞、需要什么优先级决策。

**不要**：纯技术解释、未经翻译的技术债讨论。

| 场景 | 格式 | 核心内容 |
|---|---|---|
| 功能状态更新 | 进度看板截图 + 2-3 句说明 | 完成了什么、受阻的是什么、信心度变化 |
| 技术投入解释 | 类比翻译 | "做这件事让下个功能快 30%"而非"我们需要重构数据层" |
| 优先级冲突 | 选项对比 | A 方案：做 X，不做 Y，后果是 Z |

**技术→产品的翻译表**：

| 技术语言 | 产品语言 |
|---|---|
| 重构数据访问层 | 数据相关功能开发速度提升 30% |
| 升级框架版本 | 下季度安全审计不会阻塞新功能上线 |
| 添加测试覆盖 | 修改现有功能时不会意外破坏其他功能 |
| 偿还技术债 | 团队交付速度不再逐月下降 |
| 架构迁移 | 未来 6 个月的新功能都能基于新架构快速构建 |

### 向内沟通（工程师团队）

**他们关心什么**：为什么做、怎么做、上下文、技术决策的理由。

**不要**：只给结论不给原因、隐藏困难和风险。

| 场景 | 格式 | 核心内容 |
|---|---|---|
| 路线图同步 | 路线图文档 + 团队会议 | 本季度目标、为什么是这些、每个人的角色 |
| 技术决策分享 | ADR 审查 | 上下文、替代方案、为什么选这个 |
| 事故回顾 | 事后复盘 | 时间线、根因、预防措施（无指责） |
| 架构讨论 | RFC/设计文档 | 问题、方案选项、权衡 |

## 事故沟通

### 事故中的沟通节奏

| 时间点 | 沟通动作 | 受众 | 内容 |
|---|---|---|---|
| 0-5 min | 事故频道声明 | 团队 | "正在调查 X 问题，影响范围 Y，当前未知原因" |
| 15 min | 首次状态更新 | 团队 + 相关方 | 当前理解、正在尝试的方案 |
| 30 min | 客户/用户通知（如需要） | 用户 | 影响范围、预计恢复时间 |
| 60 min | 高管简报（如持续中） | 高管 | 影响、根因假设、恢复进展、需要什么支持 |
| 恢复后 24h | 事后复盘 | 团队 | 完整时间线 + 根因 + 预防措施 |

**事故状态更新模板**：
```
事故：<标题>
状态：<调查中 / 已定位 / 修复中 / 已恢复>
影响：<范围、用户数、功能>
时间线：<开始时间> — <当前时间/恢复时间>
当前行动：<正在做什么>
下一步：<预计何时有下次更新>
```

## 沟通反模式

| 反模式 | 失败原因 | 正确做法 |
|---|---|---|
| "没有消息就是好消息" | 利益相关者在信息真空中自行想象——通常是往坏的方向 | 定期更新，哪怕只是"进展如预期" |
| 承诺具体日期 | 软件估算天然不确定，每次延期都在消耗信任 | 给时间范围 + 信心度；更新而不是沉默 |
| 只报喜不报忧 | 问题积累到无法隐藏时爆发——信任已破裂 | 坏消息尽早说；同时带来解决方案 |
| 技术术语轰炸 | 高管和产品经理不会追问你不懂——他们会在心里打上"不重要"的标签 | 用受众的语言翻译技术概念 |
| 路线图悄悄变更 | 利益相关者基于旧路线图做决策——发现时已经晚了 | 任何路线图变更即时同步；写清楚原因和影响 |
| 事故沟通过于模糊 | "有问题在修"不能让任何人做出判断 | 说清楚影响范围、严重程度和预计时间线 |

## 适用场景

- 新晋升的技术负责人学习如何向不同受众沟通
- 准备季度汇报材料时参考模板
- 事故发生时确定沟通节奏和内容
