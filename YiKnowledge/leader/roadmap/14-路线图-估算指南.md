# 估算指南

> 估算不是预言——是对不确定性的管理。好的估算告诉利益相关者"我们有多大把握在 X 时间内完成"，而非"我们一定在 X 时间内完成"。

## 估算原则

1. **估算 = 工作量 × 不确定性** — 相同工作量的任务，不确定性越高，估算应该越宽
2. **由做事的人估算** — 技术负责人不应替工程师估算。如果必须（单人项目），用历史数据校准
3. **区分估算和承诺** — 估算是预测，承诺是约定。永远用范围（"2-3 周"）而非点值（"2 周"）
4. **每次估算后记录实际** — 校准是估算改进的唯一途径

## 估算单位选择

| 单位 | 适用场景 | 优势 | 劣势 |
|---|---|---|---|
| **人周** | 季度路线图、容量规划 | 与容量计算直接对应 | 精度低——"1 周"对初级/高级工程师意义不同 |
| **T-shirt 尺码** (S/M/L/XL) | 早期探索、不确定性高 | 快速、承认模糊性 | 无法做精确的容量规划 |
| **人天** | 迭代规划、明确范围的任务 | 精度更高 | 给人"精确"的错觉——实际偏差常在 2-3 倍 |

**YrY 建议**：季度路线图用人周，迭代规划用人天。T-shirt 尺码用于早期想法排序。

## T-shirt 尺码参考

| 尺码 | 人天 (单人) | 典型任务 (YrY) |
|---|---|---|
| **S** | 0.5-1 天 | 修复一个小 bug、添加一个配置项、写一个简单的 ADR |
| **M** | 2-3 天 | 新增一个 composable 及其测试、实现一个 RPC 端点 |
| **L** | 1-2 周 | 新增一个完整的 ProTable 页面、实现 Agent 模式新状态 |
| **XL** | 2-4 周 | LLM 多提供商路由、RAG 分块策略变更 |
| **XXL** | > 1 月 | 应拆分为多个 L/XL 任务 |

## 估算流程

### 第一步：分解到可估算的粒度

规则：如果一个任务估算超过 **3 天**，它需要继续分解。

| 太粗 | 刚好 |
|---|---|
| "做测试" (XXL, 无法估算) | `useAuthButtons` 单元测试 (S, 0.5 天) |
| "Agent 模式" (XL, 范围不清) | Agent `create` → `confirm` 状态转换测试 (M, 2 天) |

### 第二步：识别不确定性

对每个任务，评估不确定性：

| 不确定性 | 描述 | 乘数 | 示例 |
|---|---|---|---|
| **低** | 做过类似的事，技术方案明确 | 1.0-1.2× | 写一个 composable 测试（已有 vitest 框架） |
| **中** | 有参考但不完全一样 | 1.3-1.8× | 实现 RPC 契约测试（知道测什么，但测试方式需探索） |
| **高** | 全新领域，可能有隐藏障碍 | 2.0-3.0× | Agent 端到端测试（状态机行为尚未完全文档化） |

**注意**：如果乘数 > 3.0，说明不确定性太高——不应该估算，应该先做 PoC。

### 第三步：给出范围，不是点值

```
估算 = (工作量 × 不确定性) → [乐观, 悲观]

示例：
  useAuthButtons 测试: 0.5 天 × 1.0 (低不确定) = 0.5-1 天
  Agent 端到端测试: 2 天 × 2.0 (高不确定) = 4-6 天
```

### 第四步：加上隐性开销

| 开销类型 | 典型占比 | 说明 |
|---|---|---|
| 代码审查 + 修改 | +20% | 审查后通常需要修改 |
| 文档 | +10% | README、ADR、代码注释 |
| 调试和修复 | +30% | 初次做的东西总有 bug |
| 环境搭建/工具问题 | +10% | 依赖安装、配置调试 |

这些开销不总是显现，但在估算时应该考虑。一个"2 天写代码"的任务通常是 2 × 1.7 = 3.4 天。

## 估算校准

估算唯一可靠的方式是追踪实际数据：

| 日期 | 任务 | 估算 | 实际 | 偏差 | 根因 |
|---|---|---|---|---|---|
| | | | | | |
| | | | | | |

每个季度回顾估算准确性。如果偏差持续 > 50%，找出系统性的低估原因。

## YrY 估算示例（单人项目）

| 任务 | 分解 | 工作量估算 | 不确定性 | 范围 | 备注 |
|---|---|---|---|---|---|
| YiVad composable 测试 | `useAuthButtons` (S) + `useTable` (M) + `useSelection` (S) + `useAgent` (L) | 5 天 | 中 (1.5×) | **1.5-3 周** | 先从最简单 S 开始建立信心 |
| RPC 契约集成测试 | 3 个参数验证 (S) + 测试框架搭建 (M) | 2.5 天 | 低 (1.2×) | **2.5-4 天** | 框架用 vitest + msw |
| Agent 端到端测试 | 纯函数 (S, 已完成) + Store 集成 (M) + 完整生命周期 (L) | 4 天 | 高 (2.0×) | **1-2 周** | 先文档化状态机才能写测试 |
| 知识库链接检查 CI | 脚本 (S) + CI 集成 (S) | 1 天 | 低 (1.0×) | **0.5-1 天** | 简单——遍历 .md, 检查 [xxx](yyy) |

## 常见估算陷阱

| 陷阱 | 表现 | 纠正 |
|---|---|---|
| **乐观偏差** | "这个很简单，半天就做完了"→ 实际 2 天 | 用历史数据：上次"简单"的任务实际花了多久？ |
| **忽略非编码时间** | 只估算写代码的时间 | 加 70% 开销：审查、调试、文档、沟通 |
| **完美路径估算** | 假设一切顺利，不预留缓冲 | 所有估算 × 不确定性乘数；高不确定性任务用 2-3× |
| **锚定效应** | 被第一个数字锚定——"上次那个类似功能花了 2 天，这个应该也差不多" | 独立估算每个任务，不与历史类比直接取数字 |
| **范围蔓延不调整** | 任务范围变了但估算没更新 | 一旦范围变化，立即更新估算并同步利益相关者 |
| **"精确"数字的错觉** | "这个任务需要 3.7 天" | 永远给范围——"3-5 天"比"3.7 天"更诚实 |

## 什么时候不应该估算

| 场景 | 不估算的原因 | 做法 |
|---|---|---|
| 全新领域，没人做过 | 不确定性太高，任何数字都是猜测 | 先做 PoC（限时 1-2 天），PoC 后再估算 |
| 需求还在剧烈变化中 | 今天估算的，明天需求变了 | 等到需求稳定；如果必须给数字，给"最乐观/最悲观" |
| 有人催你要一个"大概数字" | 随口说的数字会变成承诺 | 说"我需要先理解范围才能给数字"；或给 T-shirt 尺码 |
| 任务依赖未验证的外部因素 | 你控制不了的部分占主导 | 拆分：你能控制的部分给估算，外部部分标注"取决于 X" |

## 适用场景

- 季度路线图规划时的容量估算
- 新功能需求的工期评估
- 评估技术债务削减的工作量
- 向产品经理解释"为什么这个功能需要这么久"
