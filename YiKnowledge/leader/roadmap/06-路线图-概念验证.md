# 概念验证 (PoC)

> **作为**技术负责人，**我想要**运行结构化的 PoC 探索，**以便**在投入大量工程精力之前验证技术假设。
>
> PoC 的核心价值是"花 2 天证明不行"而非"花 2 周做出来才发现不行"。快速失败是 PoC 的设计目标。

## 定义

PoC（概念验证）是一个限时的技术探索，旨在回答一个特定问题或验证一个特定假设。它**不是**原型或 MVP——PoC 代码设计为用完即弃。

```
PoC："我们能做到 X 吗？"→ 是/否 + 证据
Prototype："X 应该如何工作？"→ 设计探索
MVP："X 的最低可行版本是什么？"→ 交付给用户
```

这三者的混淆是最常见的 PoC 失败模式——PoC 被当作 MVP 来构建，结果既不是好的 PoC（太慢），也不是好的 MVP（质量不够）。

## 触发条件

- 在承诺某个技术选择之前（参见[技术选型方法论](./07-路线图-技术选型.md)）
- 当项目有关键技术未知项时（"我们能处理 X req/s 吗？""我们能和 Y 集成吗？"）
- 当架构决策依赖于未经验证的假设时
- 当团队提出一个在此上下文中未经验证的新颖方案时

## 分步执行

### 第一步：定义问题

一个 PoC 必须回答一个清晰的问题。如果有多个问题，运行多个 PoC。

| 糟糕的 PoC 问题 | 好的 PoC 问题 |
|---|---|
| "能用 Kafka 吗？" | "在我们的基础设施上，Kafka 能处理 100K 条消息/秒且端到端延迟 < 50ms 吗？" |
| "这个库能用吗？" | "库 X 能在 5 秒内解析我们特定的 10GB 日志格式吗？" |
| "这个方案可行吗？" | "能在零停机的情况下将 1M 条记录从旧模式迁移到新模式吗？" |

### 第二步：定义成功标准

在写任何代码之前，定义"是"长什么样：

| 标准 | 目标 | 测量方法 |
|---|---|---|
| 吞吐量 | >= 100K 条消息/秒 | 使用类生产数据的负载测试 |
| 延迟 | p99 < 50ms | 插桩指标 |
| 集成 | 成功调用 API、处理认证、解析响应 | 集成测试 |
| 开发体验 | 团队能在 1 小时内完成搭建 | 计时搭建过程 |

### 第三步：限时

| 复杂度 | 时限 | 示例 |
|---|---|---|
| **小** | 1–2 天 | 库评估、API 集成测试 |
| **中** | 3–5 天 | 性能基准测试、数据迁移探索 |
| **大** | 1–2 周 | 新架构模式、多服务集成 |

**硬性截止**：到了时限就停止。如果没回答问题，答案是"以可接受的投入做不到"——不是"再给一周"。

### 第四步：构建最小化实现

PoC 代码规则：
- **一次性代码**：写得快，不在意生产质量。用 `console.log` 而非结构化日志，硬编码而非配置驱动
- **先测最难的部分**：不要搭脚手架；直接攻克未知项
- **类生产数据和负载**：合成数据但符合真实数据的特征（大小分布、内容结构）
- **记录假设**：你在不测试什么？这在真实场景中可能很重要？

### 第五步：撰写 PoC 报告

一页纸的报告，包含：

| 章节 | 内容 |
|---|---|
| **问题** | 我们想要回答什么 |
| **方法** | 我们构建了什么，如何测试的 |
| **结果** | 数据而非观点——用图表比文字更有说服力 |
| **答案** | 是 / 否 / 是，但|
| **意外发现** | 我们没有预料到的事情 |
| **建议** | 继续 / 不继续 / 修改后继续 |
| **局限性** | 这个 PoC 没有测试什么 |

### 第六步：决策和行动

| PoC 结果 | 行动 |
|---|---|
| **明确是** | 进入实施阶段；撰写 ADR（参见[技术选型方法论](./07-路线图-技术选型.md)）|
| **是，但** | 带着已记录的注意事项继续；在计划中添加缓解措施 |
| **否** | 记录原因；探索替代方案；不继续 |
| **不确定** | 问题太模糊。重新定义并运行更聚焦的 PoC |

## 决策点与分支

| 决策点 | 选项 | 指导 |
|---|---|---|
| PoC 耗时太长 | 缩小范围 / 时间到 / 延长时间 | 仅在瓶颈是环境问题时延长（等待权限、数据）；绝不因范围蔓延而延长 |
| PoC 结果与初始假设相矛盾 | 接受数据 / 质疑测试 / 重新运行 | 如果结果出人意料，在接受它之前先验证测试是否正确 |
| PoC 证明可行但团队不喜欢它 | 接受 / 将开发体验纳入考量 | 开发体验是合理的考量因素；在决策中权衡它 |
| PoC 太人工化而缺乏意义 | 增加真实性 / 接受局限性 | 在报告中明确说明局限性；不要过分声称 |

## 关键产出

| 阶段 | 产出 |
|---|---|
| 定义 | PoC 问题和成功标准 |
| 执行 | 可工作的 PoC 代码（一次性）|
| 报告 | 一页纸的 PoC 报告 |
| 决策 | 通过/不通过及理由 |

## 适用场景

- 选择新的 LLM 提供商之前评估其 API 延迟和中文质量
- 评估 MongoDB 到其他数据库的迁移可行性
- 验证 RAG 分块策略变更是否提升检索质量

## 反模式

| 反模式 | 失败原因 | 正确做法 |
|---|---|---|
| PoC 变成了 MVP | "这段代码基本可用了，直接上线吧" | PoC 代码在设计上就是一次性的；正确重写比修复 PoC 更快 |
| 无界限的 PoC | "再测一个东西"——需求蔓延导致 PoC 永不结束 | 硬性限时；范围就是那个问题，不多不少 |
| PoC 无成功标准 | 无法判断它是成功还是失败——结论模糊 | 在写代码前定义标准 |
| 只测 happy path | PoC 通过但真实场景的边界情况会击溃它 | 用类生产数据、错误条件和故障模式来测试 |
| 过度工程化 PoC | 为一次性代码搭建 CI/CD、代码检查、测试 | PoC 是探索；用最简单的可行设置 |
