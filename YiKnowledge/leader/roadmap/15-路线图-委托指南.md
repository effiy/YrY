# 委托指南

> 技术负责人最常见的失败模式：**继续做高级工程师的工作，只是多了个 title**。委托不是放弃控制——是放大影响力。

## 为什么技术负责人需要委托

| 不委托的后果 | 正确委托的结果 |
|---|---|
| 你是所有技术决策的瓶颈 | 决策在合适的层级做出 |
| 团队成长停滞——没人有机会学习 | 工程师通过承担新责任成长 |
| 你 burnout——总是救火，从不策略思考 | 你有时间做只有你能做的事（战略、架构、利益相关者） |
| 巴士因子 = 1——你离开 = 项目危机 | 巴士因子 > 1——关键决策和能力分布在团队中 |

## 委托决策矩阵

不是所有事都应该委托。用这个矩阵判断：

| 任务类型 | 委托？ | 理由 | 示例 |
|---|---|---|---|
| **只有你能做的**（战略、关键利益相关者、架构方向） | **不委托** | 这是你存在的理由 | 季度路线图规划、高管汇报 |
| **你能做，但别人也能做** | **委托** | 你做的机会成本太高 | 代码审查、技术选型评估、bug 修复 |
| **别人比你做得更好** | **委托** | 你不应该成为瓶颈 | 前端动画优化、数据库调优 |
| **别人做得不如你，但可以学会** | **委托 + 指导** | 短期慢，长期快 | 写 ADR、事故响应、系统设计 |
| **没人想做但你不得不做** | **先委托，再轮换** | 不要一个人承担所有"脏活" | 依赖更新、文档维护、值班 |

### 决策树

```
这个任务只有我能做吗？
├── 是 → 我做
└── 否 → 别人能做吗？
    ├── 能，且能做得好 → 委托
    ├── 能，但需要指导 → 委托 + 投入指导时间
    └── 暂时不能 → 指导 + 设定"下次你来"的目标
```

## 委托的五个层次

委托不是二元的。根据被委托者的准备程度，选择不同层次：

| 层次 | 描述 | 沟通方式 | 适用场景 |
|---|---|---|---|
| **1. 执行** | "我已经决定了，你去做" | "这是我们选的技术方案，请实现它" | 时间紧急，且你对该领域有深度经验 |
| **2. 审查** | "你调研后提出建议，我审查决定" | "评估 3 个方案，推荐 1 个，我来审批" | 培养决策能力——关键是你会审批 |
| **3. 商量** | "你先思考，我们讨论后共同决定" | "你怎么看这个？我们聊一下" | 对方正在成长，你还想保持参与 |
| **4. 建议** | "你决定，需要时问我" | "这是你的领域，我相信你的判断。有问题找我" | 对方已证明能力 |
| **5. 完全委托** | "你全权负责，不需要通知我" | "这是你的了。除非业务影响 > X，否则不需要同步我" | 资深成员承担完全所有权 |

**核心规则**：永远明确你在哪个层次。最糟的情况是被委托者以为在层次 4，但你在心里期望层次 2。

## 如何有效委托

### 委托对话模板

```markdown
**任务**：[一句话描述]
**为什么是现在**：[业务/技术原因]
**为什么是你**：[匹配的能力或成长机会]
**期望产出**：[具体的、可验证的成果]
**委托层次**：[1-5，见上]
**截止日期**：[如果适用]
**边界条件**：[什么情况下需要升级/通知我]
**可用资源**：[参考文档、可咨询的人、工具]
**我会如何支持**：[检查点频率、审查方式]
```

### 委托后

- **抵抗微观管理**：如果你发现自己每天在问进度，说明层次选错了——要么选错了人，要么选错了层次
- **允许不同的方法**：他们可能用不同的方式达到同样的结果。只要结果正确，方法不重要
- **做好失败的准备**：第一次委托可能会出问题。除非影响生产环境，否则让失败发生——那是学习
- **公开给予信任**：在团队面前说"这是张三做的，他做得很好"。公开信任是最强的激励

## 技术负责人常见的委托陷阱

| 陷阱 | 表现 | 纠正 |
|---|---|---|
| **"我自己做更快"** | 每次都自己上手——短期确实快，但你在积累长期的技术债 | 算总账：这次花 1h 指导 + 2h 审查，下次只需要 30min 审查，再下次完全不需要你 |
| **委托了但不停检查** | 名义上委托了，实际上每 2 小时问一次进度 | 设定检查点（如每日 5 分钟站会），在检查点之间不干预 |
| **只委托脏活累活** | 你拿有趣的工作，把文档、测试、依赖更新丢给别人 | 轮换；确保每个人都有机会做有影响力的工作 |
| **没有明确的完成标准** | "把这个做好"——什么叫"做好"？ | 用委托对话模板；验收标准必须明确 |
| **委托了责任但没给权力** | 让张三负责，但所有决策还要你审批 | 责任和权力必须匹配；如果审批权在你手里，那还是你负责 |
| **失败后收回委托** | 第一次出问题就拿回来自己做 | 复盘失败原因 → 调整层次 → 再试一次。一次失败 = 学习，不是收回 |

## 单人项目的"委托"

当前 YrY 是单人项目，没有团队可委托。但委托思维仍然适用：

| 单人替代方案 | 为什么重要 |
|---|---|
| **委托给 CI/CD** | 自动化 = 委托给机器。lint、test、deploy 都是你不应该手动做的事 |
| **委托给文档** | 好的文档让未来的你（或新成员）不用问现在的你 |
| **委托给 AI 工具** | Claude/GitHub Copilot 做代码审查、写测试、写文档——你审查而非执行 |
| **委托给 checklist** | 检查清单能让一个不熟悉的人执行你原本需要亲自盯着的事 |

## 适用场景

- 团队从 1 人扩展到 2+ 人时——这是技术负责人从"自己做"转型的关键时刻
- 季度路线图规划时——确定哪些工作可以委托给团队成员
- 你发现自己连续一周都在做执行而非策略工作时——触发委托审计
