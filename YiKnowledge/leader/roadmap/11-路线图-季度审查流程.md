# 季度路线图审查流程

> **何时使用**：每季度最后两周执行。技术负责人主导，产品经理和高管参与特定环节。
>
> 季度审查是技术负责人最重要的仪式——它是路线图和现实的校准点。不做审查的路线图会逐渐脱离实际，从承诺变成装饰。

## 审查流程总览

```
第 1 周：数据收集 ──→ 第 2 周：回顾会议 ──→ 第 2 周：调整计划 ──→ 第 2 周：向上汇报
```

| 阶段 | 时间 | 参与者 | 产出 |
|---|---|---|---|
| 数据收集 | 季度倒数第 2 周 | 技术负责人 | 数据汇总表 |
| 回顾会议 | 季度倒数第 2 周 | 技术负责人 + 工程师 | 回顾结论 + 改进项 |
| 调整计划 | 季度最后一周 | 技术负责人 + 产品经理 | 下季度路线图初稿 |
| 向上汇报 | 季度最后一周 | 技术负责人 + 高管 | 一页纸摘要 |

## 第二阶段：回顾会议 (90 分钟)

### 议程

| 时间 | 议题 | 引导问题 |
|---|---|---|
| 0-15 min | 交付回顾 | 我们承诺了什么？实际交付了什么？差异的原因是什么？ |
| 15-30 min | 容量分析 | 容量分配是否符合计划？什么消耗了意料之外的容量？ |
| 30-45 min | 质量与事故 | 本季度发生了什么事故？根因是什么？SLO 是否达标？ |
| 45-60 min | 技术债务 | 债务在增加还是减少？哪些债务应该在下季度解决？ |
| 60-75 min | 风险审查 | 哪些风险升级了？哪些缓解了？有没有新风险？ |
| 75-90 min | 改进项 | 下季度我们要改变什么？什么做得好的应该继续保持？ |

### 回顾结论模板

```markdown
## YYYY QN 回顾结论

### 交付总结
- 交付了 X/Y 个计划功能（完成率 Z%）
- 未完成的原因：[范围膨胀 / 容量估算偏差 / 外部阻塞 / 优先级变更]

### 关键数字
- 净容量消耗：___ 人周（计划 ___ 人周，偏差 ___%）
- 运维占比：___%（目标 10-15%）
- P1/P2 事故：___ 次（上季度 ___ 次）
- 技术债务：___ 项（净增减 ___）

### 做得好的
1. 
2. 
3. 

### 需改进的
1. 
2. 
3. 

### 下季度重点
1. 
2. 
3. 
```

## 第三阶段：调整计划

基于回顾结论，调整下季度路线图：

1. **根据本季度实际速度重新估算容量**——如果本季度按时交付率只有 60%，下季度的估算应相应下调
2. **将回顾中的改进项纳入下季度计划**——不要只放在"待办"中，要分配容量
3. **更新技术债务优先级**——本季度新产生的债务应纳入下季度的削减计划
4. **审查依赖和风险**——下季度是否有外部依赖可能阻塞？是否有风险可能在下一季度实现？

### 路线图调整检查清单

- [ ] 容量估算是否基于本季度实际数据（而非理想数据）？
- [ ] 是否预留了 10-15% 缓冲？
- [ ] 技术投入是否至少占 15-20%？
- [ ] 高风险项是否排在本季度早期（而非全部堆在季末）？
- [ ] 是否有"关键人依赖"（一项工作只一个人能做）？
- [ ] 产品经理是否已对齐优先级？
- [ ] 是否考虑了假期、培训等非工作日？

## 第四阶段：向上汇报

### 高管一页纸模板

```markdown
# YrY 技术季度汇报 — YYYY QN

## 关键成果
- [最重要的 3 个交付成果，每个一句话]

## 关键数字
| 指标 | 本季度 | 上季度 | 趋势 |
|---|---|---|---|
| 功能按时交付率 | X% | Y% | ↑/↓ |
| P1/P2 事故数 | X | Y | ↑/↓ |
| 技术债务趋势 | +X 项 | +Y 项 | ↑/↓ |
| 季度基础设施成本 | $X | $Y | ↑/↓ |

## 风险与关注点
- [最多 3 个需要高管关注的风险或阻碍]

## 下季度重点
- [最多 5 个下季度关键目标]
```

## 审查检查清单

### 会前（技术负责人，提前一周）

- [ ] 收集所有数据（第一阶段）
- [ ] 更新[进度看板](./01-路线图-进度看板.md)
- [ ] 更新[架构成熟度评估](../architecture/03-架构-架构成熟度模型-2026-08.md)
- [ ] 更新[风险登记册](../risk/03-风险-风险登记册模板.md)
- [ ] 发送回顾会议邀请和预读材料

### 会中（回顾会议）

- [ ] 按议程逐项讨论
- [ ] 记录回顾结论
- [ ] 就改进项达成共识

### 会后（技术负责人，一周内）

- [ ] 完成回顾结论文档
- [ ] 制定下季度[技术路线图](./09-路线图-规划技术路线图.md)初稿
- [ ] 与产品经理对齐优先级
- [ ] 完成高管一页纸汇报
- [ ] 向团队同步下季度路线图

## 反模式

| 反模式 | 失败原因 | 正确做法 |
|---|---|---|
| 季度末匆忙审查 | 数据未收集，回顾靠印象——发现不了真正的模式和根因 | 提前两周开始数据收集 |
| 只看交付不看质量 | 交付了 10 个功能但引入了 5 个事故——净价值可能是负的 | 质量和交付并重 |
| 审查结论无行动项 | 讨论热烈但没有改变任何事情——下季度重复同样的问题 | 每个发现的问题必须有对应的行动项 |
| 只向上汇报不对内同步 | 团队不知道审查结论——继续按老方式工作 | 回顾结论在团队内公开；行动项进入正常的工作追踪系统 |
| 路线图调整不与产品对齐 | 技术单方面调整优先级——产品和工程师各自执行不同的计划 | 调整后的路线图必须与产品经理确认 |
