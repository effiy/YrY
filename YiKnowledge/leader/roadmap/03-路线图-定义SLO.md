# 定义 SLO

> **作为**技术负责人，**我想要**为服务定义服务水平目标 (SLO)，**以便**团队有数据驱动的可靠性目标，并能在可靠性和功能速度之间做出明智的权衡。
>
> SLO 是技术负责人最重要的决策工具之一。它用数据回答"我们应该继续做功能，还是停下来做可靠性？"这个问题。

## 定义

| 术语 | 定义 | 示例 |
|---|---|---|
| **SLI**（服务水平指标）| 服务行为的测量指标 | "p99 请求延迟" |
| **SLO**（服务水平目标）| 在时间窗口内的 SLI 目标值 | "28 天内 p99 延迟 < 200ms" |
| **SLA**（服务水平协议）| 带有后果的合同承诺 | "p99 延迟 < 200ms 否则赔偿 10%" |
| **错误预算** | 允许的不可靠程度 | "99.9% 可用性 = 每月允许 43 分钟不可用" |

**核心关系**：SLI 是你测量的东西。SLO 是你的目标。SLA 是你的承诺（通常比 SLO 更宽松）。错误预算是不可靠性的"预算"——花光了就不能再做有风险的功能变更了。

### YrY 场景中的 SLO 示例

| 服务 | SLI | SLO 目标 | 测量窗口 |
|---|---|---|---|
| YiAi 聊天 API | 成功请求比例 | 99.9% | 28 天滚动窗口 |
| YiAi RAG 查询 | p95 端到端延迟 | < 3 秒 | 28 天滚动窗口 |
| YiVad 页面加载 | p90 首次内容绘制 | < 2 秒 | 7 天滚动窗口 |
| YiPet 扩展启动 | 注入成功率 | 99.5% | 28 天滚动窗口 |

## 触发条件

- 新服务上线生产
- 已有服务尚无 SLO
- 用户可见的可靠性问题或投诉
- 建立新的值班轮换
- 季度可靠性审查

## 分步执行

### 第一步：识别用户关心的指标

不要测量一切。选择 2-4 个能反映用户实际体验的 SLI：

| SLI 类别 | 示例指标 | 为什么重要 |
|---|---|---|
| **可用性** | 成功请求的比例 | 服务不可用时用户无法使用 |
| **延迟** | p95 或 p99 请求耗时 | 慢等同于令人沮丧；用户会离开 |
| **吞吐量** | 每秒请求数 | 容量规划的输入 |
| **错误率** | 失败请求的比例 | 用户可见错误的直接度量 |
| **时效性** | 数据延迟（上次更新距现在的时间）| 对数据管线和搜索很重要 |
| **持久性** | 保留数据的比例 | 对存储服务很重要 |

### 第二步：详细定义 SLI

SLI 是一个公式，而非名称：

| 组成部分 | 示例 |
|---|---|
| **指标** | HTTP 请求延迟 |
| **过滤器** | `/api/*` 端点，排除 `/api/health` |
| **聚合方式** | 1 分钟窗口的 p99 |
| **测量方式** | 服务器端负载均衡器日志 |

```
SLI = "好"事件的计数 / 所有有效事件的计数
     = count(req.latency < 200ms) / count(所有 /api/* 请求)
```

### 第三步：设定 SLO 目标

| 考量因素 | 指导 |
|---|---|
| **用户期望** | 用户能注意到什么延迟？（<100ms = 即时，<1s = 快，<10s = 烦人）|
| **当前性能** | 目标可实现吗？如果当前 p99 是 500ms，不要设 SLO 在 100ms |
| **依赖关系** | 如果你的服务依赖另一个 99.9% 可用性的服务，你不能承诺 99.99% |
| **关键程度** | 收入关键型服务比内部工具的 SLO 更严格 |

示例 SLO：
```
SLO: 99.9% 的 /api/* 请求在 28 天滚动窗口内以 < 200ms 完成
错误预算: 0.1% 的请求 = 每 28 天约 43 分钟的服务降级
```

### 第四步：选择测量窗口

| 窗口 | 优点 | 缺点 |
|---|---|---|
| **7 天** | 反馈快；预算快速燃烧/恢复 | 对短时事故敏感 |
| **28 天** | 平滑了周模式；标准选择 | 预算恢复较慢 |
| **90 天** | 非常稳定 | 预算变化太慢，无法指导行动 |

标准选择：28 天滚动窗口。

### 第五步：定义错误预算策略

错误预算是你的决策工具：

| 预算剩余 | 行动 |
|---|---|
| **> 50%** | 正常运营。自由发布功能。 |
| **25–50%** | 谨慎。审查近期变更。增加测试严格度。 |
| **10–25%** | 暂停功能。聚焦可靠性改进。 |
| **< 10%** | 紧急。全员投入可靠性。预算恢复前停止所有功能工作。 |

### 第六步：仪表化和告警

| 告警类型 | 燃烧速率 | 通知方式 |
|---|---|---|
| **慢燃烧** | 预算在稳定消耗中 | 向团队提工单；下次迭代规划中审查 |
| **快燃烧** | 1 小时内消耗 2% 预算 | 告警值班人员；立即调查 |
| **预算耗尽** | 错误预算为 0 | 升级到领导层；仅进行可靠性工作 |

燃烧速率公式：
```
燃烧速率 = (错误率 / 错误预算) × 告警窗口
快燃烧告警：1 小时窗口内燃烧速率 > 10
慢燃烧告警：6 小时窗口内燃烧速率 > 1
```

## 关键产出

- SLI 定义（每个服务 2-4 个）
- 带测量窗口的 SLO 目标
- 错误预算计算和策略
- 告警规则（快燃烧和慢燃烧）
- 显示 SLO 合规和预算剩余的仪表盘

## 适用场景

- 新服务上线前的可靠性目标设定
- 用户投诉"服务慢"但无量化数据的场景
- 功能和稳定性之间的资源优先级争议

## 常见问题

**Q: YiVad 是单页应用在浏览器中运行——需要为前端定义 SLO 吗？**
A: 需要，但测量方式不同。前端 SLO 从真实用户监控 (RUM) 获取数据而非服务器端日志。指标包括：页面加载时间、首次内容绘制、交互到响应时间等。YiVad 至少应有"页面加载时间 < 2s"的 SLO。

**Q: 单人项目需要 SLO 吗？**
A: 需要，但范围可以缩小。选择 1-2 个关键 SLI（如"聊天 API 可用性 99.5%"），目的是建立用数据说话的思维习惯。随着项目和团队增长，再扩展到更多 SLI。

## 反模式

| 反模式 | 失败原因 | 正确做法 |
|---|---|---|
| 100% 可用性 SLO | 不可能实现；错误预算失去意义——任何一次故障都算"失败" | 从 99.9% 开始；仅在持续超越它之后再收紧 |
| SLI 太多 | 10 个 SLI 意味着没有一个 SLI 得到关注——注意力被稀释 | 每个服务 2-4 个；选择用户实际关心的 |
| 有 SLO 但无错误预算 | 没有在可靠性和速度之间做权衡的机制——SLO 成为装饰 | 定义错误预算策略；强制执行 |
| 告警 SLO 违规而非燃烧速率 | SLO 被突破时已经太晚——预算已耗尽 | 告警燃烧速率，而非 SLO 阈值交叉 |
| SLO 与用户体验不匹配 | 服务器端延迟很好，但客户端体验很差——SLO 没有反映真实感受 | 尽可能从用户视角测量 |
