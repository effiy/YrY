# 入职指南 — 新成员前 30 天

> 入职不是"把文档丢给他，让他自己看"——入职是**有结构的知识传递**。好的入职让新成员在 30 天内具备独立贡献能力，坏的入职让他们在 3 个月后仍在问"这个怎么跑"。

## 入职目标

| 时间 | 目标 | 验证方式 |
|---|---|---|
| **Day 1** | 环境跑起来，能启动所有项目 | 四个项目成功启动 |
| **Week 1** | 理解架构全景和数据流，完成一个小修复 | 提交并合并 1 个 PR |
| **Week 2** | 独立完成一个 M 级功能或改进 | 从设计到合并独立完成 |
| **Week 4** | 具备独立贡献能力，理解所有核心模块 | 能独立处理该领域的任务 |

## 入职前准备清单

新成员到岗前，技术负责人需完成：

- [ ] 开发环境准备：机器、权限、账号（GitHub、MongoDB Atlas、Ollama）
- [ ] 分配入职伙伴 (onboarding buddy)——新成员有任何问题先找伙伴，不要直接找你（防止你成为瓶颈）
- [ ] 准备"第一个任务"——一个小而明确的任务，能在第一周内完成并合并
- [ ] 创建入职文档阅读清单（见下）
- [ ] 安排第一周的每日 15 分钟 check-in

## Day 1：环境搭建

### 目标：四个项目都能跑起来

**顺序**（必须按此顺序——存在依赖关系）：

```
1. 确保 MongoDB 运行（本地或 Atlas 连接字符串）
2. 确保 Ollama 运行（ollama serve + ollama pull qwen2.5）
3. 启动 YiAi: cd YiAi && python main.py
   → 验证: curl http://localhost:10086 返回响应
4. 启动 YiVad: cd YiVad && pnpm install && pnpm dev
   → 验证: 打开 http://localhost:8848
5. 构建 YiPet: cd YiPet && npm install && npm run build
   → 在 Chrome 中加载 dist/ 为解压扩展
```

**常见环境问题速查**：

| 问题 | 可能原因 | 解决 |
|---|---|---|
| YiAi 启动失败 | MongoDB 未运行 | `mongod --dbpath /data/db` |
| 聊天功能无响应 | Ollama 模型未拉取 | `ollama pull qwen2.5` |
| YiVad `pnpm install` 失败 | Node 版本不匹配 | 检查 `package.json` 中的 `engines` 字段 |
| YiPet 扩展加载失败 | `dist/` 未生成 | 确认 `npm run build` 无报错 |

### Day 1 阅读清单（按顺序）

1. 根目录 [CLAUDE.md](../../../CLAUDE.md) — RPC 协议、跨项目关系
2. [架构全景图](../architecture/09-架构-架构全景图.md) — 4 个项目如何协作
3. YiAi/YiVad/YiPet 各自的 CLAUDE.md — 模块边界和约束
4. [ADR 目录](../decisions/README.md) — 关键架构决策（选 3 篇阅读：知识监听器、LLM 提供商、双世界架构）

## Week 1：第一个 PR

### 目标：理解数据流，提交并合并一个修复

**第一个任务的理想特征**：
- 代码改动约 10-50 行
- 不涉及跨项目契约变更
- 有明确的验收标准
- 能在一周内完成

**YrY 第一个任务示例**：
- 修复 YiVad 的一个 UI bug（如某个表格列宽不对）
- 为 YiAi 的一个端点添加参数验证
- 修复 YiKnowledge 中的一处链接断链
- 添加一个简单的 composable 测试

### 审查新成员第一个 PR 的要点

这不是普通代码审查——这是教学机会：

- 不仅指出问题，**解释为什么**这是问题
- 介绍项目的代码风格和约定时，链接到对应文档
- 对于风格问题，用 `nit:` 前缀标记（"这样更好但非阻塞"）
- 至少有一条正面评论——第一个 PR 是建立信心的时刻
- 审查完成后，简短回顾："你做得好的 3 件事 + 下次可以改进的 1 件事"

## Week 2-4：独立贡献

### 目标：独立完成一个 M 级功能或改进

- 新成员从"需要指导"过渡到"需要审查"
- 任务从 bug 修复升级到功能开发
- 开始参与架构讨论（旁听 → 提问 → 发表意见）

### Week 2-4 里程碑

| 时间 | 里程碑 | 验证 |
|---|---|---|
| Week 2 末 | 独立完成第二个 PR（M 级） | 从设计到实现独立完成，仅需审查 |
| Week 3 末 | 理解核心数据流 | 能画出聊天请求的完整路径（用户→前端→RPC→YiAi→Ollama→返回） |
| Week 4 末 | 独立贡献能力 | 能独立承担一个领域的任务，不再需要每日 check-in |

## 单人→双人的特殊考量

当 YrY 从 1 人扩展到 2 人，入职流程有特殊挑战：

1. **你从未"被入职"过** — 你创建的流程没有经过验证。第一个入职者的反馈 = 你改进流程的唯一输入。在第 4 周专门做一次入职流程回顾
2. **知识全在你脑子里** — 很多"显而易见"的事对新人完全不是。用"告诉我你怎么理解 X"取代"你理解 X 了吗"
3. **你的节奏不等于新人的节奏** — 你花了数月熟悉这个代码库。不要期望新人 1 周内达到同样的熟悉度
4. **第一次委托会不习惯** — 参考[委托指南](./15-路线图-委托指南.md)。从层次 2（审查）开始，不要直接跳到层次 5（完全委托）
5. **Code review 节奏调整** — 从"自我审查"切换到"审查他人的代码"。参考[代码审查标准](../architecture/10-架构-代码审查标准.md)

## 入职伙伴 (Onboarding Buddy)

入职伙伴是新成员的第一联系人——所有"这个怎么跑""这个是什么"的问题都先问伙伴。

| 伙伴的职责 | 不是伙伴的职责 |
|---|---|
| 回答日常问题和环境问题 | 做正式的性能评估 |
| 审查第一个 PR | 替技术负责人做架构决策 |
| 介绍团队文化和不言明的规则 | 承担新成员的交付责任 |
| 每天 5 分钟 check-in（前两周） | — |

**YrY 当前限制**：单人项目，技术负责人同时是入职伙伴。将来 >= 3 人时，入职伙伴应由另一名工程师担任。

## 入职检查清单

### Day 1
- [ ] 环境搭建完成——四个项目均可启动
- [ ] 阅读清单前 2 篇已完成
- [ ] 已分配入职伙伴
- [ ] 第一个任务已分配并讨论

### Week 1
- [ ] 第一个 PR 提交并合并
- [ ] 阅读清单全部完成
- [ ] 每日 check-in（15 min / day）
- [ ] 能画出请求流程图（用户 → 数据库 → 返回）

### Week 2
- [ ] 第二个 PR 独立完成（仅需审查）
- [ ] check-in 频率降至隔天
- [ ] 理解 RPC 参数名称契约（`filter`≠`query`, `target_file`≠`path`）

### Week 4
- [ ] 独立贡献能力达成
- [ ] check-in 频率降至每周
- [ ] 入职流程回顾——哪些地方做得不好？
- [ ] 新成员可以回答其他（未来的）新成员的环境问题

## 适用场景

- 第二名开发者加入 YrY 时（最重要的场景）
- 任何新成员加入（工程师、实习生、外包）
- 你的团队从 N 人扩展到 N+1 人

## 反模式

| 反模式 | 失败原因 | 正确做法 |
|---|---|---|
| "文档都在那里，自己看" | 文档不能替代对话——新人不知道哪些文档重要，哪些已过时 | 精选阅读清单（< 5 篇），按优先级排序 |
| 第一个任务太大 | 两周后还没合并任何代码——新人失去信心 | 10-50 行改动，明确的验收标准 |
| 没有人可问 | 新人卡住 2 小时不敢问——入职伙伴解决这个问题 | 分配入职伙伴；前两周每天 5-15 min check-in |
| "你看着做" | 没有明确期望——新人不知道"做好"长什么样 | 每周目标 + 验证方式；第一个任务有详细描述 |
| 过度帮助 | 新人学会了依赖你而不是自己思考 | 回答问题前先问"你觉得应该怎么做？" |
