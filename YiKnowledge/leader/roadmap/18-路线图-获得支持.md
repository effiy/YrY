# 获得支持 — 如何向非技术利益相关者推销技术投入

> 技术负责人最重要的能力不是技术判断——是**让组织为正确的技术决策买单**。好的技术方案如果没有支持，只是你电脑里的一个 markdown 文件。

## 为什么技术提案会被拒绝

技术提案最常见的失败模式不是"方案不好"——是**对方听不懂为什么要现在做**。

| 利益相关者听到的 | 你想表达的 | 差距 |
|---|---|---|
| "我们要花 3 周重写代码" | "重构后每个数据功能开发快 30%" | 投入→产出未翻译 |
| "需要升级框架版本" | "不升级的话 3 个月后无法通过安全审计" | 风险未被量化 |
| "技术债太多了" | "过去 3 个月交付速度从每周 2 个功能降到 1 个" | 没有数据 |

## 第一步：翻译——技术→业务

每个技术提案必须回答业务方的三个问题：

| 问题 | 错误回答 | 正确回答 |
|---|---|---|
| **为什么是现在？** | "因为代码很烂" | "因为过去 3 个月有 2 次事故根因是这个问题。下次事故预计影响 X 用户 Y 分钟" |
| **不做的后果？** | "以后更难维护" | "不升级的话，6 个月后不再有安全补丁。届时要么停机升级（3 周），要么承担风险" |
| **做完的收益？** | "代码更干净" | "做完后新功能开发时间从 2 周→1 周。Q4 计划中的 3 个功能总共节省 3 周" |

### 翻译对照表

| 技术语言 | 业务语言 |
|---|---|
| 重构 | "每个同类功能开发时间从 X 降到 Y" |
| 升级依赖 | "安全审计可通过，不会阻塞上线" |
| 还技术债 | "团队交付速度不再逐月下降" |
| 写测试 | "修改现有功能不会再意外破坏其他功能" |
| 架构迁移 | "未来 12 个月的新功能都在新架构上构建，速度 2×" |
| 自动化部署 | "从提交到上线从 2 小时→10 分钟，出错率降 90%" |

## 第二步：选择时机

| 时机 | 适合推什么 | 不适合推什么 |
|---|---|---|
| **事故后** | 与事故根因直接相关的改进 | 无关的"顺便优化"——显得你在利用事故推进议程 |
| **季度规划** | 大型技术投入（> 2 周） | 紧急修复——季度规划不是处理紧急事务的地方 |
| **新项目启动** | 架构和基础设施选型 | — |
| **高管问"有什么风险"** | 风险相关的技术投入 | 功能开发——他们问的是风险，不是功能 |

### 时机判断规则

- **紧急 + 重要**（事故根因修复）→ 事后复盘会上直接提。不需要长篇提案
- **不紧急 + 重要**（技术债削减、架构升级）→ 季度规划时提。准备数据驱动的提案
- **紧急 + 不重要**→ 不做
- **不紧急 + 不重要**→ 不做

## 第三步：构建提案

### 一页纸提案模板

```markdown
# 提案：[一句话标题]

## 我们推荐做什么
[1-2 句话。先说结论]

## 为什么是现在
[具体的、有数据的理由——不是"代码不好"，而是"导致 X 次事故"或"拖慢 Y% 交付速度"]

## 投入
- 人力：[人周]
- 时间：[起止时间]
- 风险：[可能出错的事及缓解措施]

## 不做的后果
[6 个月后/12 个月后的具体影响]

## 做完后的收益
[可衡量的——时间节省、事故减少、速度提升]

## 替代方案
- 方案 B：[简述 + 为什么不选]
- 什么都不做：[简述 + 为什么不行]

## 我需要你做
[具体的决策/资源/支持]
```

### 数据 vs. 轶事

| 用数据（更好） | 用轶事（次好） | 都不要用 |
|---|---|---|
| "过去 3 个月交付速度下降 30%" | "上周一个新功能花了比预期多 2 倍的时间" | "代码质量在下降" |
| "本月 2 次事故都是连接池耗尽" | "上次事故我们花了 2 小时排查" | "偶尔会出现问题" |
| "92% 的类似项目在升级后速度提升 40%+" | "XX 公司做了类似升级后效果好" | "这是行业最佳实践" |

## 第四步：处理反对意见

### 常见反对及回应

| 反对 | 对方的真实关切 | 回应 |
|---|---|---|
| "现在不是时候" | 担心影响当前交付节奏 | "可以在不占用功能开发时间的前提下，用 20% 的技术投入容量来做。不会影响 Q4 的功能交付" |
| "这个真的有这么重要吗" | 没有被说服 ROI | "不做的话，按当前趋势，6 个月后每次部署需要手动操作 30 分钟且有 5% 的失败率" |
| "能不能再等等" | 希望推迟而非拒绝 | "可以等到 Q1——但每等一个季度，修复成本增加约 25%（技术债利息）。建议 Q4 做" |
| "我们以前没有也过来了" | 不理解为什么现在不同 | "以前数据量是 100MB，现在是 500MB。以前用户 5 个，访客没人在意 5 秒延迟。现在情况变了" |
| 沉默 | 可能没听懂但不方便说 | "我用一个具体的例子——假设下周我们要上线 XX 功能，由于当前的 YY 问题，可能会遇到 ZZ。你觉得这个风险可以接受吗？" |

### 反对处理原则

1. **先理解，再回应** — "你能详细说一下你的顾虑吗？"先于"不，你理解错了"
2. **不要赢了辩论输了支持** — 你的目标不是证明对方错了，是获得支持
3. **给台阶** — "之前没有解释清楚，是我没做好"而非"你之前没听懂"
4. **提供替代方案** — 如果对方坚持拒绝，提供缩小范围的方案。"那我们先做最关键的 30%，剩下的 Q1 做"

## YrY 场景示例

### 提案：Q4 停止功能开发，聚焦测试体系

**背景**：YiVad 和 YiPet 零测试覆盖。每次修改 ProTable 数据管线或 Agent 状态机都有未知回归风险。

**面向产品经理的提案**：

> 我建议 Q4 不开发新功能，用 7 周集中建立测试体系。
>
> **为什么是现在**：过去 3 个月我们遇到了 2 次参数名不匹配的 bug（`filter`/`query`、`target_file`/`path`）。每次排查花了 1-2 小时，且都是在用户报告后才发现。如果继续在不测试的情况下添加功能，这类 bug 的频率会随代码量线性增长。
>
> **投入**：7 人周（整个 Q4 的净容量）
>
> **不做的后果**：Q1 的 3 个新功能每次上线都有未知回归风险。按历史频率推算，至少 1-2 次用户可见的 bug。
>
> **做完的收益**：从 Q1 开始，每次功能上线前有自动化测试验证核心路径。预期回归 bug 减少 70% 以上，排查时间从 1-2 小时→10 分钟。
>
> **我需要你做**：接受 Q4 无新功能交付。Q4 末我们有一套验证过的测试套件，Q1 恢复功能开发时速度会显著提升。

## 反模式

| 反模式 | 失败原因 | 正确做法 |
|---|---|---|
| "你不懂技术" | 傲慢——关闭对话。对方不是不懂，是你的翻译不够好 | 用对方的语言重新解释；用类比 |
| 一次推太多 | 预算、架构升级、技术债、招聘——全部堆在一次提案中→无法聚焦 | 一次推一件事。一个季度一个重大提案 |
| 没有数据全靠直觉 | "我觉得应该做"→直觉不是论据 | 用事故次数、速度趋势、行业基准做支撑 |
| 只在危机时推 | 只有出了事故才提技术投入→被看作"在利用事故"而非"在预防事故" | 在季度规划时主动推；用趋势数据说明"不变就会出事" |
| 拒绝后就不再提 | 一次被拒就放弃→重要的事值得推多次。每次带新的数据或视角 | 记下拒绝原因；下次带着新数据再提 |
