# 架构决策记录 (ADR) — 模板

> **ADR = 上下文 + 决策 + 后果。** 一份 ADR 记录一项重大技术决策，说明为什么做出该决策，以及接受了哪些权衡。它一经接受即不可修改——只能被替代 (supersede)，不能被编辑。

## 何时编写 ADR

以下情况需要编写 ADR：
- 在多个可行的技术方案之间做选择（例如，选择库 A 还是库 B）
- 做出的决策影响多个项目或模块
- 引入新的架构模式或约束
- 废弃或替换现有系统
- 做出涉及重大成本、风险或不可逆性的决策

以下情况可以跳过 ADR：
- 决策是显而易见的（仅有一个可行方案）
- 决策可低成本回滚（例如配置项的修改）
- 决策纯粹是单个模块内部的实现细节

### 适用场景

| 场景 | 是否需 ADR | 说明 |
|---|---|---|
| 选择 LLM 提供商（Ollama vs 云 API）| 是 | 涉及成本、延迟、供应商锁定等关键权衡 |
| 将单个接口从 REST 改为 SSE | 是 | 改变前后端通信协议 |
| 调整 config.yaml 中的超时时间 | 否 | 低风险配置变更，可随时回滚 |
| 重构单个函数内部实现 | 否 | 纯粹实现细节 |

### 常见问题

**Q: ADR 和普通技术文档的区别是什么？**
A: ADR 的核心价值在于记录决策的"上下文"和"替代方案"。一份好的 ADR 回答的是"我们为什么选择了 X 而非 Y"，而非仅描述"X 是如何工作的"。普通技术文档回答后者，ADR 回答前者。

**Q: 一篇 ADR 应该覆盖一个决策还是多个相关决策？**
A: 一个决策。如果多个决策紧密关联（例如"选择 LLM 提供商"与"多提供商路由策略"），应写成两篇独立的 ADR，并通过 `related` 字段交叉引用。

**Q: ADR 写多长合适？**
A: 平均 1-3 页。如果超过 5 页，说明决策范围可能过大，应拆分为多篇 ADR。

**Q: ADR 需要评审吗？评审人是谁？**
A: 需要。至少由一名技术负责人和一名受影响的团队成员评审。对于跨项目决策（如 RPC 协议变更），需要 YiAi、YiVad、YiPet 的代表共同评审。

## 模板

### 1. 标题

一个简短、描述性的短语，使用祈使句形式。以动词开头。

**示例**："使用 apscheduler 轮询替代 FSEvents 实现知识监听器"

### 2. 状态

取值为：`proposed`（讨论中）、`accepted`（已批准并生效）、`deprecated`（不再执行）、`superseded`（被新 ADR 替代）。

如果状态为 `superseded`，必须链接到新 ADR。

### 3. 上下文

该决策要解决的问题是什么？描述施加在决策上的各种因素：

- **业务上下文**：什么用户需求或业务目标驱动此决策？
- **技术上下文**：什么现有系统或约束创造了这个需求？
- **约束条件**：哪些是我们无法改变的？（预算、时间线、现有技术栈、团队技能）

**示例**："macOS 的 FSEvents 在本机上会静默丢弃文件变更事件，导致知识监听器遗漏更新。监听器必须在合理延迟内检测到 YiKnowledge 的文件变更，以保持 MongoDB 和 RAG 索引的同步。"

### 4. 决策

我们决定做什么？清晰、无歧义地陈述。使用主动语态。

**示例**："用 5 秒间隔的 apscheduler 轮询替换 FSEvents。轮询循环遍历 YiKnowledge 目录树，将文件哈希与上次已知状态进行比对，并将变更的文件同步到 MongoDB。"

### 5. 已考虑的替代方案

列出我们评估过的其他选项以及拒绝原因：

| 替代方案 | 拒绝原因 |
|---|---|
| FSEvents（保留） | 当前机器上不可靠——存在静默事件丢失 |
| inotify | 仅支持 Linux，macOS 不可用 |
| 1 秒轮询间隔 | CPU 使用率更高，相比 5 秒并无实质延迟改善 |
| 30 秒轮询间隔 | 延迟过大——知识变更需等待 30 秒才能反映到 RAG |

### 6. 后果

因为此决策，哪些事情变得更简单、更困难、或有所不同？

**正面影响**：
- 知识文件变更可在 5 秒内被可靠检测
- 不依赖平台特定的文件监听 API
- 在 macOS、Linux、容器环境中行为一致

**负面影响**：
- 5 秒轮询产生持续的低级别 CPU 开销
- 文件变更非即时（<1 秒）——存在 5 秒延迟上限
- 每 5 秒遍历约 1000 个文件的目录树

**中性影响**：
- 监听器架构从事件驱动变为轮询驱动
- 未来迁移到更高效的监听器需回退到事件驱动模式

### 7. 实施计划

如何实施此决策？列出高层次步骤：

1. 将 `apscheduler` 添加到 requirements.txt
2. 实现 `KnowledgeWatcher` 类，包含 `scan_and_sync` 方法
3. 在 `app.py` 生命周期中配置 5 秒间隔调度
4. 移除 FSEvents/watchdog 依赖
5. 添加监听器状态健康检查接口
6. 验证：创建测试文件，确认 5 秒内在 MongoDB 中出现

### 8. 回滚计划

该决策可逆吗？如果可以，如何操作？

**示例**："可以——恢复 watchdog 依赖并移除 apscheduler 任务即可回退到 FSEvents。监听器接口 (`scan_and_sync`) 保持不变，仅调度机制变化。"

### 9. 相关决策

该决策依赖或影响哪些其他 ADR？

**示例**："依赖 ADR: Knowledge Watcher 部署（确立了监听器作为 YiAi 组件的定位）。影响未来关于 RAG 索引时效性保证的 ADR。"

## 命名规范

ADR 文件遵循以下模式：`<项目名>/<序号>-<简述>.md`

**示例**：`yiai/001-knowledge-watcher-polling.md`

序号在项目目录内递增。简述是该决策的简短描述（kebab-case）。

## 反模式

- **在实现之后编写 ADR 而未记录替代方案。** ADR 的价值在于决策理由，而非决策本身。如果已经实现，就已丢失了被拒绝方案的上下文。
- **过于笼统而不可用。** "我们决定使用微服务"不是 ADR。"我们决定将单体拆分为 3 个服务（auth、chat、data），边界定义如下..."才是 ADR。
- **缺少后果章节。** 每个决策都有权衡。如果你找不到任何负面后果，说明你思考得不够深入。
- **滥用 ADR 记录琐碎决策。** 不是所有选择都需要 ADR。如果决策无需权衡、可低风险回滚、且影响范围限于单一模块，请跳过 ADR。过多的低价值 ADR 会淹没重要决策。
- **ADR 之间互相矛盾而不标注替代关系。** 当新 ADR 替代旧 ADR 时，必须在旧 ADR 的 frontmatter 中将 `status` 设为 `superseded`，并通过 `acceptance_criteria` 中的 `superseded by` 字段链接到新 ADR。否则，后来者不知道应遵循哪篇。
