# 性能优化指南

> 优化第一原则：**不要优化**。第二原则：**先测量，再优化（仅限专家）**。过早优化是万恶之源，但永远不优化是另一条通往失败的路。

## 优化四步法

```
1. Profiling → 2. 找瓶颈 → 3. 优化 → 4. 验证
    ↑                                      │
    └──────────── 未达目标则重复 ────────────┘
```

**核心规则**：没有 profiling 数据的优化 = 猜测。优化你不测量的东西，你不知道是否真的变快了。

## 第一步：Profiling（确定测量基线）

### YiAi (Python)

```python
# 方法 1：cProfile — 函数级 profiling
python -m cProfile -s cumulative main.py

# 方法 2：py-spy — 生产环境安全（无需重启）
pip install py-spy
py-spy top -- python main.py          # 实时 top
py-spy record -o profile.svg -- python main.py  # 生成火焰图

# 方法 3：内置计时器 — 快速定位慢端点
import time
start = time.perf_counter()
result = await some_function()
elapsed = time.perf_counter() - start
logging.info(f"some_function: {elapsed*1000:.0f}ms")
```

**关键指标**：
| 指标 | 含义 | 警戒线 |
|---|---|---|
| p50 延迟 | 50% 请求快于此值 | — |
| p95 延迟 | 95% 请求快于此值 | > 500ms 需关注 |
| p99 延迟 | 99% 请求快于此值 | > 2s 需优化 |
| 每秒请求数 | 吞吐量 | — |

## 第二步：找瓶颈

### 常见瓶颈及排查

| 瓶颈类型 | 症状 | 排查工具 | YrY 典型场景 |
|---|---|---|---|
| **CPU 密集** | 进程 CPU 100%，请求排队 | py-spy, Chrome Profiler | LLM token 处理、大 JSON 序列化 |
| **I/O 等待** | CPU 低但响应慢 | 数据库慢查询日志 | MongoDB 全表扫描、无索引查询 |
| **内存泄漏** | 内存持续增长直至 OOM | memory-profiler, Chrome Memory | 未关闭的 SSE 连接、未清理的定时器 |
| **网络延迟** | 跨服务调用慢 | curl -w timing, Network 标签 | YiVad→YiAi RPC 调用链 |
| **锁竞争** | 并发时性能骤降 | MongoDB currentOp | 写入冲突、连接池竞争 |

### 找瓶颈的黄金问题

在每个层级问："这个操作为什么慢？"

```
用户："聊天回复慢"（5 秒）
  → 是 LLM 推理慢？还是网络传输慢？
    → LLM 推理：模型生成 token 耗时 4 秒 → GPU 瓶颈
    → 网络：SSE 流正常，前端渲染慢 → 前端渲染瓶颈
```

## 第三步：优化

### 优化策略（按投入产出比排序）

| 策略 | 投入 | 收益 | YrY 示例 |
|---|---|---|---|
| **加索引** | 低 | 极高（100× 不罕见） | MongoDB 查询 `find({category})` 无索引→建索引 |
| **减少数据量** | 低 | 高 | API 返回 100 条→改为分页 20 条 |
| **缓存** | 中 | 高 | RAG 检索结果缓存 5 分钟 |
| **异步化** | 中 | 中-高 | 非关键路径（日志、通知）异步处理 |
| **算法优化** | 高 | 中-高 | O(n²)→O(n log n) |
| **硬件升级** | 高（成本） | 中 | 换更快的 GPU、加内存 |

### YiAi 特定优化

| 优化项 | 方法 | 预期收益 |
|---|---|---|
| **Ollama 模型预热** | 启动时加载模型到 VRAM，避免冷启动 | 首次请求从 10s → 2s |
| **RAG 检索缓存** | 相同 query 的检索结果缓存（TTL 5min） | 热门查询延迟减半 |
| **MongoDB 查询优化** | 添加缺失索引、使用 projection 限制返回字段 | 10-100× 提升 |
| **知识监听器间隔** | 60s→30s 可配置（平衡实时性和 CPU） | — |
| **LLM token 限制** | 限制聊天上下文长度，避免超长 prompt | Token 数减少→推理加速 |

### YiVad/YiPet 特定优化

| 优化项 | 方法 | 预期收益 |
|---|---|---|
| **列表虚拟滚动** | 大列表只渲染可视区域 | 滚动从卡顿→流畅 |
| **组件懒加载** | `defineAsyncComponent` / `React.lazy` | 首次加载减 50% |
| **防抖/节流** | 搜索输入 debounce 300ms | 减少无效 API 调用 |
| **SSE 消息批量更新** | 收集 50ms 内的 token，批量更新 DOM | 渲染次数降 90% |

## 第四步：验证

优化后必须验证——用**相同的数据和条件**对比前后指标：

```
基线（优化前）：
  p50: 450ms  p95: 1200ms  p99: 3500ms

优化后：
  p50: 180ms  p95: 400ms   p99: 900ms

结论：p95 延迟降低 67%，符合 < 500ms 的目标
```

**如果没有改善**：你的优化没有命中真正的瓶颈。回到第一步重新 profiling。

## YrY 常见性能问题

| 问题 | 根因 | 解决 |
|---|---|---|
| 聊天首次响应慢 (5-10s) | Ollama 模型冷启动——模型未加载到 VRAM | 启动时预热模型（`ollama run ... "ping"`) |
| RAG 查询慢 (> 5s) | 知识库文件多，检索未缓存 | 检索结果缓存；索引优化 |
| YiVad 表格翻页卡顿 | 一次渲染过多行 | 分页 20 条/页；虚拟滚动（如超过 100 行） |
| MongoDB 查询越来越慢 | 集合增长无索引 | 检查 `explain()`；添加缺失索引 |
| 开发服务器内存占用高 | Rsbuild HMR + Ollama + MongoDB 同时运行 | 分配给 Ollama 的 VRAM 限制；关闭不用的服务 |

## 优化检查清单

在开始优化之前：
- [ ] 有具体的性能指标和数据吗？（不是"感觉慢"）
- [ ] 已经 profiling 并确定了瓶颈在哪里吗？
- [ ] 优化的预期收益值得投入吗？（1 天优化节省 100ms → 不值得；节省 5s → 值得）

优化完成后：
- [ ] 优化前后的数据对比记录了吗？
- [ ] 优化的副作用考虑了吗？（缓存 = 数据可能过期）
- [ ] 代码变更经过审查了吗？

## 反模式

| 反模式 | 失败原因 | 正确做法 |
|---|---|---|
| "感觉慢"就优化 | 没有数据——不知道慢在哪里、慢了多久 | 先测量，得到具体数字 |
| 优化非瓶颈 | Profiling 显示数据库占 80% 耗时，却在优化前端代码 | Profiling 后找到占比最高的部分 |
| 缓存一切 | 缓存过期策略错误→返回过期数据→比慢更糟 | 每个缓存有明确的 TTL 和失效策略 |
| 不做基线对比 | 不知道优化是否有效——"感觉快了" | 优化前记录精确指标，优化后对比 |
| 一次性大优化 | 一次改太多→引入了 bug 但不知道是哪处修改导致的 | 小步优化；每次改一个东西并验证 |
