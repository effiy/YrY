# 代码审查标准

> 代码审查的目的不是找茬——是**知识共享**、**架构一致性**和**防止回归**。好的审查让团队整体水平上升，坏的审查让提交者感到被审判。

## 审查原则

1. **审查代码，而非审查人** — "这个函数在空数组时会抛异常"而非"你忘处理空数组了"
2. **区分必须改和建议改** — 用 `nit:` 前缀标记非阻塞性建议，用 `must:` 标记必须修改的问题
3. **审查不超过 400 行/次** — 超过则要求拆分为多个 PR。审查效率随代码量指数下降
4. **24 小时内完成审查** — 超过 24 小时的审查阻塞交付节奏
5. **作者先自我审查** — 提交 PR 前，作者自己过一遍 diff，标注需要审查者特别关注的地方

## 单人项目审查模式

YrY 当前为单人项目，审查 = **自我审查**。但自我审查仍然必要——用检查清单替代审查者。

### 自我审查流程

```
写完代码 → 休息 30 分钟（或第二天） → 过检查清单 → 合并
```

30 分钟间隔至关重要——刚写完的代码在你眼中"运行正常"，冷却后再看会发现遗漏。

### PR 自我审查模板

```markdown
## 变更概述
- [一句话描述做了什么、为什么]

## 自我审查检查清单
- [ ] 类型检查通过（pyright / vue-tsc / tsc --noEmit）
- [ ] 相关测试通过（pytest / vitest）
- [ ] 没有硬编码的密钥、URL 或配置值
- [ ] 新的 API 调用使用了正确的参数名（filter 而非 query，target_file 而非 path）
- [ ] 错误状态有用户友好的提示信息（如适用）
- [ ] 变更没有破坏已有的 ADR 决策
- [ ] 如果变更涉及跨项目契约，已在相关 CLAUDE.md 中更新

## 审查者需关注
- [需要特别审查的复杂逻辑或风险区域]
```

## 按项目的审查检查项

### YiAi (Python)

**架构一致性**：
- [ ] 新代码放在正确的层：`domain/`（业务逻辑）、`services/`（服务编排）、`server/`（路由）
- [ ] 公共 API 通过 `__init__.py` 导出，不直接导入内部模块
- [ ] 新端点使用 RPC 信封格式 `{module_name, method_name, parameters}`

**代码质量**：
- [ ] 函数类型注解完整（参数 + 返回值）
- [ ] 异常处理不吞掉错误——至少 log 后重新抛出
- [ ] 没有 `except Exception: pass` 这样的裸异常处理
- [ ] 数据库操作使用 `motor` 异步驱动，不是同步 `pymongo`
- [ ] 文件路径操作使用 `pathlib.Path`，不是字符串拼接

**安全**：
- [ ] `target_file` 参数经过路径遍历检查（不能访问 YiKnowledge 之外的路径）
- [ ] RPC 端点的参数已验证（必需字段、类型检查）
- [ ] 没有在日志中输出敏感信息（token、密钥）

**测试**：
- [ ] 新功能有对应的 pytest 测试
- [ ] 关键路径（聊天、RAG、知识同步）的测试至少覆盖 happy path

### YiVad (Vue 3 / TypeScript)

**架构一致性**：
- [ ] Composables 放在 `src/composables/`，使用 `use` 前缀
- [ ] Stores 放在 `src/stores/`，使用 Pinia `defineStore`
- [ ] API 调用通过 `RequestHttp`，不直接使用 `axios` 或 `fetch`
- [ ] 使用 Composition API（`<script setup lang="ts">`），不使用 Options API

**代码质量**：
- [ ] `vue-tsc --noEmit` 通过
- [ ] Props 有明确的 TypeScript 类型定义
- [ ] 组件的响应式数据使用 `ref` 或 `reactive`，明确区分
- [ ] 没有在 `watch`/`watchEffect` 中修改被监听的数据（死循环风险）

**权限**：
- [ ] 需要权限控制的按钮使用了 `v-auth` 指令
- [ ] 权限判断逻辑在 store 中，不在组件中硬编码

**RPC 契约**：
- [ ] `callService.query_documents` 的参数使用 `filter`（不是 `query`）
- [ ] 文件操作发送 `target_file`（不是 `path`）

### YiPet (React 18 / TypeScript / Chrome MV3)

**双世界边界**：
- [ ] Content Script 代码不直接访问 `chrome.storage`（通过消息传递）
- [ ] Service Worker 代码不访问 DOM
- [ ] 跨世界消息使用定义好的消息类型，不是随意字符串

**API 分层**：
- [ ] API 调用遵循四层结构：`client → endpoints → types → services`
- [ ] 不绕过 `ApiClient` 直接使用 `fetch`

**状态管理**：
- [ ] 流式状态使用 `useSyncExternalStore` + Controller，不是 `useState` + 轮询
- [ ] Controller 的 `getSnapshot` 返回不可变引用（用于渲染优化）

**Chrome 扩展约束**：
- [ ] CSP 兼容——不使用 `eval()`、内联脚本
- [ ] 包体积敏感——新增 npm 依赖有充分理由
- [ ] `manifest.json` 权限申请最小化

**代码质量**：
- [ ] `tsc --noEmit` 通过
- [ ] Biome lint 通过

## 审查反模式

| 反模式 | 为什么失败 | 正确做法 |
|---|---|---|
| "LGTM"（Looks Good To Me） | 没有真正审查——鬼魂审查。让作者觉得被重视了，实际上没有任何反馈 | 至少留一条有意义的评论；如果实在完美，说**为什么**它好 |
| 审查变成重写 | 审查者按自己的偏好而非项目标准来审查——"我会这样写"不是有效审查 | 区分风格偏好和正确性问题；风格问题用自动化工具（Biome/ESLint）管 |
| 阻塞性审查拖数天 | 作者等待中——交付节奏被打破 | 24 小时规则；如果无法详细审查，告知作者预计时间 |
| 只审查代码不审查设计 | 实现可能是正确的，但设计方向错了——在审查时纠正比重构时纠正成本低 | 审查前先问"这个方案解决了正确的问题吗？"再问"代码写对了吗？" |
| 审查范围过大 | 一次审查 2000 行——审查者认知过载，只能浏览表面 | 超过 400 行要求拆分；审查的粒度 = 审查的质量 |
| 阿谀奉承式审查 | 怕伤害感情，有问题不提——代码质量下降 | 用"代码"而非"人"来框架化反馈。具体的问题 > 模糊的赞扬 |

## 架构审查拓展

对于涉及架构变更的 PR（新增模块、跨项目契约变更、数据模型变更），除代码审查外还需：

- [ ] 变更与已有 ADR 一致吗？如果不一致，需要新的 ADR 吗？
- [ ] 跨项目影响评估——YiAi 的变更影响 YiVad 和 YiPet 吗？
- [ ] 数据模型变更向后兼容吗？需要迁移吗？
- [ ] 如果是新增依赖，通过[依赖决策门](../risk/04-风险-依赖风险管理.md)了吗？
- [ ] 参数名称遵循[跨项目契约](../../CLAUDE.md#关键参数名称契约)吗？

## 适用场景

- 所有 PR/MR 提交的自我审查和团队审查
- 新成员入职时了解项目的代码质量标准
- 季度代码质量回顾时的基准参考
