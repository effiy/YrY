# 异步与后台任务模式

> FastAPI 的 `async def` 并不意味着"所有操作都会自动异步执行"。理解四种异步模式，在正确场景用正确的工具。

## 四种模式总览

| 模式 | 适用场景 | 执行时机 | 是否等待结果 | YrY 使用 |
|---|---|---|---|---|
| **BackgroundTask** | 请求后需要做的轻量收尾工作 | 响应返回后 | 不等待——fire and forget | 日志记录、统计上报 |
| **apscheduler** | 定时重复执行的任务 | 按 cron 表达式 | 不等待 | 知识监听器轮询 |
| **asyncio.create_task** | 请求内并发执行多个独立操作 | 请求处理期间 | 等待（并发） | 并发调用多个外部服务 |
| **SSE 流** | 长时间运行、需要逐步返回结果 | 请求处理期间 | 逐步返回 | 聊天流式响应、Agent 工具调用 |

## 模式 1：BackgroundTask（fire and forget）

**何时用**：请求处理完了，但还有一些不紧急的收尾工作——记录日志、发送通知、更新缓存。

**特点**：
- 在响应返回给客户端**之后**执行
- 客户端不知道后台任务的存在
- 如果后台任务失败，客户端已经收到成功响应——需要单独的错误处理

```python
from fastapi import BackgroundTasks

@app.post("/")
async def handle_request(params: dict, background_tasks: BackgroundTasks):
    # 主逻辑——这部分的结果返回给客户端
    result = await process_request(params)

    # 后台任务——响应返回后执行
    background_tasks.add_task(log_to_file, result)
    background_tasks.add_task(update_cache, params)

    return {"code": 0, "data": result}
```

**YrY 适用场景**：
- 聊天请求完成后，异步归档会话摘要（不阻塞聊天响应）
- 知识库文件变更后，批量更新 RAG 索引（响应优先返回，索引稍后再生效）

**陷阱**：BackgroundTask 和请求在同一进程中。如果进程崩溃，后台任务也丢失了。不适合关键任务。

## 模式 2：apscheduler（定时任务）

**何时用**：需要按固定间隔重复执行——轮询、定期清理、定期同步。

```python
from apscheduler.schedulers.asyncio import AsyncIOScheduler

scheduler = AsyncIOScheduler()

@scheduler.scheduled_job("interval", seconds=60)
async def knowledge_watcher():
    """每 60 秒扫描 YiKnowledge 目录变更"""
    changed = await scan_and_sync()
    if changed:
        logger.info("knowledge_sync", files_changed=len(changed))

scheduler.start()
```

**YrY 现有场景**：

| 任务 | 间隔 | 文件 |
|---|---|---|
| 知识监听器扫描 | 60s | `YiAi/src/domain/knowledge/watcher.py` |
| (建议) MongoDB 备份 | 每夜 | 待实现 |
| (建议) 会话归档 | 每夜 | 待实现 |

**陷阱**：
- 如果任务执行时间 > 间隔时间，任务会重叠——使用 `max_instances=1` 防止
- 任务中的异常被静默吞掉——必须显式 try/except + logging

## 模式 3：asyncio.create_task（请求内并发）

**何时用**：一个请求需要从多个独立的数据源获取数据——并发请求，缩短总耗时。

```python
async def handle_complex_query(user_query: str):
    # 串行（差）：总时间 = A + B + C
    # rag_result = await rag_search(user_query)
    # db_result = await db_query(user_query)
    # llm_result = await llm_analyze(user_query)

    # 并发（好）：总时间 = max(A, B, C)
    rag_task = asyncio.create_task(rag_search(user_query))
    db_task = asyncio.create_task(db_query(user_query))

    rag_result = await rag_task
    db_result = await db_task
    # 两个操作并发执行，而非串行
```

**YrY 适用场景**：
- RAG 查询时并发执行向量检索和 BM25 检索
- 聊天时并发加载会话历史和用户偏好

**陷阱**：
- `create_task` 的异常不会自动传播——需要显式 `await` 来获取异常
- 如果其中一个任务失败且你 cancel 了其他任务，确保 cancel 是安全的

## 模式 4：SSE 流（逐步返回）

**何时用**：操作耗时较长（> 2 秒），且用户可以逐步消费结果。

```python
from fastapi.responses import StreamingResponse

@app.post("/")
async def chat_stream(params: dict):
    async def generate():
        async for token in llm_stream(params["message"]):
            yield f"data: {json.dumps({'type': 'token', 'content': token})}\n\n"
        yield f"data: {json.dumps({'type': 'done'})}\n\n"

    return StreamingResponse(generate(), media_type="text/event-stream")
```

**YrY 现有场景**：
- 聊天流式响应（`services.ai.chat_service.chat`）
- Agent 工具调用状态推送

## 选择决策树

```
这个操作...
├── 需要在响应返回前完成？
│   ├── 是 → 同步处理
│   └── 否 → BackgroundTask
├── 需要按时间间隔重复执行？
│   ├── 是 → apscheduler
│   └── 否 → 继续
├── 需要调用多个独立的 I/O 操作？
│   ├── 是 → asyncio.create_task（并发）
│   └── 否 → 继续
├── 耗时 > 2 秒且用户想逐步看到结果？
│   ├── 是 → SSE StreamingResponse
│   └── 否 → 常规 async def
```

## 反模式

| 反模式 | 为什么失败 | 正确做法 |
|---|---|---|
| 在 `async def` 中调用同步阻塞代码 | 阻塞事件循环——所有请求排队 | 耗时同步操作用 `run_in_executor` 包裹 |
| `time.sleep()` 在 async 函数中 | 阻塞整个事件循环 | `await asyncio.sleep()` |
| apscheduler 任务无异常处理 | 任务静默失败——无人知晓 | try/except + structured_log("ERROR") |
| BackgroundTask 用于关键操作 | 进程崩溃 = 任务丢失 | 关键任务用消息队列或数据库任务表 |
| 为简单操作用 SSE | 查询只需 50ms——SSE 连接建立的开销比处理还大 | 常规 JSON 响应 |
