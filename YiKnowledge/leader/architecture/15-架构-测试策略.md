# 测试策略

> 测试的目标不是覆盖率数字——是**安全地修改代码的能力**。一个好的测试策略让你在重构时不害怕，在添加功能时不担心回归。

## 测试金字塔（YrY 适配版）

```
         ╱  E2E  ╲         少量——关键用户旅程
        ╱  集成   ╲        中量——跨模块/跨项目契约
       ╱   单元    ╲       大量——纯函数、composable、工具
```

| 层级 | 范围 | 速度 | 维护成本 | YrY 目标比例 |
|---|---|---|---|---|
| **单元测试** | 纯函数、工具函数、composable 逻辑 | 毫秒 | 低 | 60% |
| **集成测试** | API 端点、RPC 契约、数据库操作 | 秒 | 中 | 25% |
| **E2E 测试** | 关键用户旅程（聊天、RAG 查询） | 分钟 | 高 | 15% |

## 按项目的测试策略

### YiAi (Python / pytest)

| 层级 | 当前状态 | Q4 目标 | 框架 | 示例 |
|---|---|---|---|---|
| **单元测试** | shared 模块 92%+ | domain 层 ≥ 40% | pytest + pytest-asyncio | `ErrorCode` 枚举测试、`validate_required` 参数验证 |
| **集成测试** | 76 个测试 | + RPC 端点集成 | httpx AsyncClient | 完整的 RPC 请求→响应周期 |
| **E2E 测试** | 无 | Agent 确定性测试（stub LLM） | pytest + mock | Agent 状态转换：create→confirm→steer→resume |

**测试目录**：`YiAi/tests/`

**关键模式**：
- 使用 `pytest-asyncio` 测试异步 Motor 操作
- 集成测试使用真实 MongoDB（或内存 MongoDB）
- Agent 测试 stub LLM 响应——确定性的输入输出，不依赖真实 Ollama

### YiVad (Vue 3 / Vitest)

| 层级 | 当前状态 | Q4 目标 | 框架 | 示例 |
|---|---|---|---|---|
| **单元测试（Composable）** | 0% | ≥ 60% | Vitest + @vue/test-utils | `useAuthButtons` 权限解析、`useTable` 表格逻辑 |
| **集成测试（RPC 契约）** | 0% | 3 个契约测试 | Vitest + mock | 验证 RequestHttp 发送 `filter` 而非 `query` |
| **E2E 测试** | 0% | 暂缓 | — | 优先级最低——手动测试成本可控 |

**测试目录**：`YiVad/src/__tests__/`

**优先级排序（ROI 降序）**：
1. `useAuthButtons` — 最简单，快速建立信心
2. RPC 契约集成测试 — 防止已知 bug 模式
3. `useTable` — 核心数据流
4. `useAgent` — 最复杂，需要框架熟悉后再做

## 测试 ROI 优先级

如果只能写一个测试，写哪个？优先级排序：

| 优先级 | 测什么 | 为什么 | 项目 |
|---|---|---|---|
| **P0** | 曾导致过 bug 的代码路径 | 已知风险——不测会再次发生 | RPC 参数名契约（filter/query, target_file/path） |
| **P0** | 数据流核心路径 | 坏了影响所有人 | ProTable 数据管线、聊天 SSE 解析 |
| **P1** | 复杂状态机 | 人工测试无法覆盖所有路径 | Agent 状态转换 |
| **P1** | 权限和认证逻辑 | 安全影响——错了不是 bug 是漏洞 | v-auth 指令、Token 拦截器 |
| **P2** | UI 组件渲染 | 视觉问题易于发现——ROI 低 | 表格渲染、弹窗交互 |
| **P3** | 纯展示页面 | 没有逻辑——测试的价值接近零 | 静态内容页面 |

## 测试是否充分的判断标准

不是因为覆盖率达到了某个数字——是因为团队能自信地回答：

- [ ] 修改核心数据流时，CI 能捕获回归吗？
- [ ] 添加新功能时，测试先于代码写好了吗？
- [ ] 有人离职时，他们的代码有测试保护吗？
- [ ] 曾经导致过事故的代码路径有测试吗？
- [ ] 重构时你害怕吗？如果怕——测试不够。

## 测试反模式

| 反模式 | 失败原因 | 正确做法 |
|---|---|---|
| 追求覆盖率数字 | 100% 覆盖率的低质量测试 = 虚假安全感 | 测行为，不测实现。改实现不改行为的重构不应破坏测试 |
| 只测 happy path | 边界情况和错误处理才是 bug 的温床 | 每个功能至少一个错误路径测试 |
| 测试依赖测试顺序 | 测试 B 依赖测试 A 的副作用——排查时地狱 | 每个测试独立——自己准备数据，自己清理 |
| mock 一切 | 测了 mock 框架而非实际行为 | 集成测试用真实依赖（或可控的本地替代）；单元测试才 mock |
| 测试比被测代码还复杂 | 测试本身需要测试 | 保持测试简单。如果测试太复杂，说明被测代码需要重构 |
| 不运行测试 | CI 有测试但没人看结果——红灯亮了继续合并 | 测试失败 = 阻塞合并。不允许带着红灯合并 |
