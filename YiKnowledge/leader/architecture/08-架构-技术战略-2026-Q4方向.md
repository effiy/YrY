# 技术战略 — 2026 Q4 方向

> **当前状态**：YrY 单体仓库包含 4 个子项目（YiAi、YiVad、YiPet、YiKnowledge），处于从"单人原型"向"可持续工程体系"的转型期。
>
> 此文档定义 2026 Q4 的技术战略方向——我们将有限的技术资源投向哪里，以及**不投向**哪里。

## 当前架构状态总结

基于 [2026-08 架构成熟度评估](./03-架构-架构成熟度模型-2026-08.md)：

| 项目 | 成熟度 | 最大短板 | Q3 已解决的问题 |
|---|---|---|---|
| YiAi | 3 (定义级) | domain 层测试覆盖率不足 | pytest 引入（76 个测试）、LLM 多提供商路由 |
| YiVad | 3 (定义级) | 零测试覆盖，每次重构有回归风险 | Vitest ADR 已审批 |
| YiPet | 3 (定义级) | 双世界边界无集成测试 | Biome 代码检查、四层 API 架构 |
| YiKnowledge | 2 (管理级) | 交叉引用完整性无自动化保障 | frontmatter 强制执行、15+ 断链修复 |

**关键数字 (Q2 基线)**：部署频率按需、变更前置时间 < 1h、变更失败率 ~5%（估算）、恢复时间 < 30min（本地环境）。

## Q4 战略主题

### 主题 1：测试体系建立 — 最高优先级

**为什么现在做**：YiVad 和 YiPet 的零测试覆盖是当前最大的系统性风险。每次功能变更都伴随未知回归风险。Q3 已完成了 ADR 和框架选型，Q4 是落地季。

| 行动 | 项目 | 目标 | 预计人周 |
|---|---|---|---|
| Composable 单元测试 | YiVad | `useTable`、`useSelection`、`useAgent` 覆盖率 ≥ 60% | 2-3 |
| RPC 契约集成测试 | YiVad | `filter`/`query`、`target_file`/`path` 参数名自动验证 | 1 |
| 双世界边界集成测试 | YiPet | content-script ↔ service-worker 通信契约 | 2 |
| domain 层测试补充 | YiAi | domain 模块覆盖率从 0% 提升到 40% | 1-2 |

### 主题 2：Agent 模式成熟化

**为什么现在做**：Agent 模式是 YiAi 的核心差异化能力（确认门、引导、追问、按会话恢复），但状态机复杂度高且仅一人理解。

| 行动 | 目标 |
|---|---|
| Agent 状态机文档 | 状态转换图 + 每个状态的进入/退出条件 |
| Agent 端到端测试 | 完整生命周期：create → confirm → steer → followup → resume |
| 多提供商 Agent 路由 | Ollama 不可用时的云 API fallback（已有基础设施） |

### 主题 3：知识库链接完整性自动化

**为什么现在做**：YiKnowledge 作为 RAG 数据源，交叉引用断链直接影响 RAG 检索质量。2026-08 手动修复了 15+ 处断链，但无持续保障机制。

| 行动 | 目标 |
|---|---|
| CI 链接完整性检查 | 每次提交自动验证 `related` 和内部链接 |
| `last_verified` 时效性告警 | 超过 90 天未验证的文档发出警告 |

### 主题 4：成本与可观测性基础

**为什么现在做**：当前基础设施成本低（~$45/月），但随数据增长和云 API 引入将快速攀升。Q4 建立监控和成本追踪基础，为 Q1 2027 可能的云部署做好准备。

| 行动 | 目标 |
|---|---|
| 成本追踪仪表盘 | 按服务/环境的月度成本可视化 |
| YiAi 健康检查接口 | 供 uptime 监控使用 |

## Q4 不做的事

明确说"不"和说"是"同等重要：

| 不做 | 原因 | 推迟到 |
|---|---|---|
| CI/CD 流水线搭建 | 单人项目，手动部署成本 < CI 搭建成本 | 2027 Q1（团队扩展时） |
| 架构适应性函数 | 等级 4 对当前规模过度工程化 | 2027 Q2 |
| 云生产环境部署 | 无业务驱动；本地开发满足当前需求 | 视业务需求 |
| 新 LLM 提供商评估 | llama_index + Ollama + 云 API 路由已覆盖当前场景 | 有明确需求时 |
| 微服务拆分 | 单体架构在当前规模下运行良好 | 有明确瓶颈时 |

## 架构方向原则

Q4 及以后的架构决策遵循以下原则：

1. **测试优于功能** — 在添加重要新功能之前，先为已有功能建立测试安全网。没有测试的功能 = 不可维护的功能。
2. **单体优先** — 在明确的性能或组织瓶颈出现之前，保持单体架构。微服务解决的是组织扩展问题，而非技术问题。
3. **llama_index 作为 LLM 唯一接口** — 不为新提供商引入额外的 LLM 抽象层。所有 LLM 调用统一走 `llama_index.llms`。
4. **RPC 信封保持不变** — `{module_name, method_name, parameters}` 是跨项目通信的唯一协议。不引入 RESTful 或 GraphQL 端点。
5. **知识库是 RAG 的单一数据源** — 不引入额外的知识存储（如向量数据库独立管理的内容）。YiKnowledge 目录树是唯一的真实来源。

## 关键风险

| 风险 | 可能性 | 影响 | Q4 缓解 |
|---|---|---|---|
| 单人项目关键人风险 | 中 | 极高 | Agent 文档 + 测试；所有核心模块补充文档 |
| LLM 提供商单点故障 | 低（已有多提供商路由） | 高 | 多提供商路由验证 + fallback 演练 |
| MongoDB 存储无限增长 | 中 | 中 | 制定会话归档策略 |
| 前端测试推进受阻 | 中 | 高 | 先从最高 ROI 的 composable 开始 |
