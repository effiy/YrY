# 数据模型设计原则

> YrY 使用 MongoDB 作为唯一数据库。MongoDB 的灵活性是一把双刃剑——没有 schema 约束意味着 schema 设计完全依赖纪律。这些原则确保集合设计的一致性。

## 核心原则

### 1. 数据在一起访问，就放在一起存储

MongoDB 没有 JOIN（或 JOIN 代价极高）。如果两个数据总是一起被读取，它们应该在同一文档中。

| 场景 | 设计 | 理由 |
|---|---|---|
| 聊天消息总是和它所属的会话一起加载 | 消息嵌入会话文档 | 一次查询加载整个会话 |
| 用户信息被多个集合独立引用 | 用户存为独立集合，其他集合存 `user_id` 引用 | 用户信息独立更新，不污染其他集合 |

**YrY 实例**：`sessions` 集合中 `messages` 是嵌入数组——每次加载会话都需要所有消息。反面例子：如果把消息拆成独立集合，加载一个会话需要 2 次查询。

### 2. 嵌入数组不应无限增长

MongoDB 文档有 16MB 上限。无限增长的嵌入数组会突破这个限制。

| 处理方式 | 适用场景 | YrY 实例 |
|---|---|---|
| **嵌入（默认）** | 数组长度可预测且有限 | `sessions.messages`——单个会话的消息量可控（通常 < 1000 条） |
| **分桶 (bucketing)** | 数组会增长但可分段 | 如果聊天消息量极大，按月分桶——每月一个文档 |
| **引用（独立集合）** | 数组不可预测且数量大 | `knowledge_files`——知识库文件独立存储，不嵌入其他文档 |

**反模式**：将 `knowledge_files` 的全部内容嵌入一个文档——YiKnowledge 持续增长，文档会超出 16MB 限制。

### 3. 优先为查询设计索引，而非为写入

MongoDB 的写入速度通常不是瓶颈——查询速度是。索引应该基于实际的查询模式而非假设。

| 原则 | 说明 |
|---|---|
| **为每个查询模式创建索引** | 如果代码中有 `find({category: "leader"})`，必须有 `{category: 1}` 索引 |
| **复合索引字段顺序 = 查询条件顺序** | `find({category, status})` → 索引 `{category: 1, status: 1}` |
| **覆盖索引** | 如果查询只需要索引中的字段，MongoDB 不读文档直接返回索引数据 |
| **不要过早优化** | 先上线，用 `explain()` 看慢查询，再加索引 |

### 4. Schema 变更必须向后兼容

在持续部署的环境中，新旧代码可能同时运行。Schema 变更不能破坏旧代码。

| 变更类型 | 兼容性 | 操作 |
|---|---|---|
| **新增字段（有默认值）** | ✅ 向后兼容 | 旧代码忽略新字段；新代码处理字段缺失 |
| **新增字段（必需）** | ❌ 不兼容 | 需要两阶段：先写入新字段（默认值），再部署需要该字段的代码 |
| **重命名字段** | ❌ 不兼容 | 需要过渡期：同时写入新旧字段，等旧代码全部下线后删除旧字段 |
| **删除字段** | ⚠️ 谨慎 | 先确认无代码读取该字段，再停止写入，最后删除 |
| **修改字段类型** | ❌ 不兼容 | 需要新增字段（新类型），过渡期后删除旧字段 |

### 5. 命名约定

| 约定 | 示例 | 理由 |
|---|---|---|
| 集合名：snake_case 复数 | `knowledge_files`, `static_files` | 与 Python/MongoDB 惯例一致 |
| 字段名：snake_case | `created_at`, `target_file`, `page_content` | 与 Python 代码直接映射（无需 camelCase 转换） |
| Boolean 字段：`is_` 前缀 | `is_base64`, `is_active` | 一眼看出是布尔值 |
| 时间字段：`_at` 后缀 | `created_at`, `updated_at`, `last_verified` | 一眼看出是时间戳 |
| 外键字段：`_id` 后缀 | `user_id`, `session_id` | 一眼看出是引用 |

## YrY 集合设计评注

### `sessions` — 聊天会话

```
{
  key: "uuid",           // 唯一会话标识
  title: "str",          // 会话标题
  messages: [{           // 嵌入——一起访问
    role: "user"|"assistant",
    content: "str",
    timestamp: datetime
  }],
  tags: ["str"],         // 用于分类和搜索
  pageContent: "str",    // 去格式化的纯文本（用于 RAG 检索）
  created_at: datetime,
  updated_at: datetime
}
```

**设计要点**：`messages` 嵌入是正确选择——加载会话时总是需要所有消息。`pageContent` 是冗余字段——从 `messages` 提取纯文本用于 RAG 索引，避免每次检索时解析 Markdown。

**风险**：单会话消息量可能超过 16MB 上限（约 50K+ 条消息）。如果未来某个会话无限增长，需改为分桶模式。

### `menus` — 动态菜单

```
{
  path: "/path",         // 路由路径
  name: "MenuName",      // 组件名
  parent: "ParentName",  // 父菜单（null = 顶级）
  meta: {                // 元信息
    title: "str",
    icon: "str",
    permission: ["str"]
  },
  component: "str"       // 对应组件文件路径
}
```

**设计要点**：树形结构通过 `parent` 字段实现（邻接表模式）——适合菜单这种层数浅（≤ 3 层）且节点数少（< 100）的场景。

**替代方案**：物化路径 (`path: "/a/b/c"`)——适合需要查子树但不需查父节点的场景。当前菜单场景两种都可以，邻接表更容易维护。

### `knowledge_files` — 知识库文件

```
{
  path: "leader/architecture/file.md",  // 文件路径（相对 YiKnowledge）
  title: "str",          // frontmatter title
  tags: ["str"],         // frontmatter tags
  category: "str",       // frontmatter category
  content_hash: "str",   // 文件内容哈希（用于变更检测）
  frontmatter: {...},    // 完整的 frontmatter JSON
  indexed_at: datetime,
  updated_at: datetime
}
```

**设计要点**：独立集合——YiKnowledge 文件数量持续增长，不适合嵌入。`content_hash` 用于知识监听器的变更检测，避免每次轮询都重新索引未变更的文件。

**性能注意**：`path` 字段需要唯一索引。`tags` 字段如果有查询需求，建议建立多值索引。

### `bugs` — 缺陷追踪

```
{
  key: "uuid",
  title: "str",
  project: "YiAi"|"YiVad"|"YiPet"|"YiKnowledge",
  module: "str",
  severity: "P0"|"P1"|"P2"|"P3",
  status: "open"|"in_progress"|"resolved"|"closed",
  created_at: datetime,
  updated_at: datetime
}
```

**设计要点**：频繁查询模式——按 `project` + `status` 和 `severity` + `status` 查询。需要复合索引 `{project: 1, status: 1}` 和 `{severity: 1, status: 1}`。

### `static_files` — 文件备份

```
{
  path: "str",
  content: "str",        // 文本内容或 base64
  is_base64: bool,
  tags: ["str"],
  created_at: datetime
}
```

**设计要点**：`is_base64` 字段区分文本文件和二进制文件（二进制存 base64）。**风险**：单文件可能接近或超过 16MB 限制——大文件应存 OSS，MongoDB 只存元数据和路径。

### `users` — 用户账户

```
{
  username: "str",
  password_hash: "str",  // bcrypt 哈希
  roles: ["str"],        // RBAC 角色
  permissions: ["str"],  // 细粒度权限
  created_at: datetime
}
```

**设计要点**：`password_hash` 永远不存明文。`permissions` 是 `roles` 的补充——角色定义大权限，细粒度权限覆盖例外情况。`username` 需要唯一索引。

## 索引策略

### 索引检查清单

- [ ] 为每个查询模式创建索引（用 `explain()` 验证）
- [ ] 高频查询字段建索引
- [ ] 排序字段建索引（与查询条件一起建复合索引）
- [ ] 唯一约束字段建唯一索引（`username`, `path`）
- [ ] 监控索引大小——索引也是存储成本
- [ ] 定期检查未使用的索引并删除

### YrY 建议索引

| 集合 | 建议索引 | 理由 |
|---|---|---|
| `sessions` | `{key: 1}` unique, `{updated_at: -1}` | 按 key 查会话；按更新时间排序 |
| `menus` | `{parent: 1}` | 查子菜单 |
| `knowledge_files` | `{path: 1}` unique, `{tags: 1}`, `{category: 1}` | 按路径查文件；按标签/分类搜索 |
| `bugs` | `{project: 1, status: 1}`, `{severity: 1, status: 1}` | 按项目和状态筛选缺陷 |
| `users` | `{username: 1}` unique | 登录查询 |

## 反模式

| 反模式 | 为什么失败 | 正确做法 |
|---|---|---|
| 无索引的全表扫描 | 集合变大后查询秒级→分钟级 | 每个查询模式加索引 |
| 嵌套过深 (> 3 层) | 查询和更新深层嵌套字段困难 | 考虑提取为独立文档或扁平化结构 |
| 文档大小无限制 | 超出 16MB 上限时写入失败 | 监控文档大小；大文档拆分为分桶或独立集合 |
| Schema 无文档化 | 只有代码知道 schema 长什么样 | 每个集合至少有一个字段说明文档（即本文件） |
| 把 MongoDB 当关系型数据库用 | JOIN 模拟、多文档事务滥用 | 利用嵌入和反范式化——这是 MongoDB 的优势 |
