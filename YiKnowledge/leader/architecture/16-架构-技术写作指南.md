# 技术写作指南

> 你写的每一个文档被阅读的次数远多于被编写的次数。为读者而写，非为写者而写。

## 写作原则

1. **先说结论，再说推导** — 读者不需要跟你的思路重走一遍。告诉他们答案，再解释为什么
2. **一句话一个观点** — 长句是思考不清晰的标志。每句话超过 30 字就该拆
3. **具体 > 模糊** — "性能提升了 30%"优于"性能大幅提升"
4. **删掉所有可以删掉的字** — 写完后删掉 20%。你不删，读者的大脑替你删
5. **一个文档回答一个问题** — 如果文档回答了多个不相关的问题，拆成多个文档

## 按文档类型的写作指南

### ADR（架构决策记录）

**读者**：未来想理解"为什么当时选了 X 而非 Y"的开发者。

**核心价值**：不是记录选了什么——是记录**为什么没选其他方案**。

**写作公式**：
```
标题 = 祈使句，以动词开头
  好："使用 apscheduler 轮询替代 FSEvents"
  差："关于知识监听器技术方案的决策"

上下文 = 业务需求 + 技术约束 + 为什么是现在
  好："macOS FSEvents 在本机上静默丢弃事件，导致知识监听器漏更新。
       业务需要 60 秒内检测文件变更。"（具体的、可验证的事实）
  差："文件监听需要更高的可靠性。"（模糊的——多高？什么算可靠？）

决策 = 主动语态，清晰无歧义
  好："用 5 秒间隔的 apscheduler 轮询替换 FSEvents"
  差："我们决定使用轮询机制"（什么轮询？轮询什么？5 秒还是 30 秒？）

替代方案 = 至少 2 个 + 具体拒绝原因
  好："inotify：仅支持 Linux，macOS 不可用"（具体的、事实性原因）
  差："其他方案不够好"（什么方案？哪里不够好？）

后果 = 正面 + 负面 + 中性
  好："正面：文件变更 5 秒内可检测。
        负面：5 秒轮询产生持续 CPU 开销。
        中性：架构从事件驱动变为轮询驱动。"
```

### 技术提案（Proposal / RFC）

**读者**：需要审查和批准你方案的技术负责人和同事。

**核心价值**：让审查者在 5 分钟内理解方案，把时间花在找盲点上而非理解上。

**检查清单**：
- [ ] 问题描述有具体数据（不是"性能不好"而是"p99 延迟 800ms，超出 200ms SLO"）
- [ ] 方案有架构图（ASCII 图优于纯文字，比 Visio 图快 10 倍）
- [ ] 替代方案不被描述成"愚蠢的"——认真对待每一个你拒绝的方案
- [ ] 风险不是"没有风险"——每个方案都有负面后果
- [ ] 实施计划不是"先做这个再做那个"——有阶段、有验证点、有回滚方案

### 状态更新

**读者**：高管、产品经理、团队——每类人关心的不同。

**向上（高管）**：
```
好："本周完成了聊天服务稳定性改进，预期每月事故从 1 次降到 0。
    需关注：MongoDB 存储月增 20%，6 个月后可能需要归档策略。"
差："优化了 MongoDB 连接池配置，将 maxPoolSize 从 50 调整到 100..."（技术细节）
```

**向外（产品）**：
```
好："升级 React 版本让下个功能快 30%。不升级的话，3 个月后安全审计可能阻塞上线。"
差："我们需要做 React 18 迁移，把 class component 改成 hooks..."（技术细节）
```

### README / 项目文档

**读者**：第一次接触这个项目的新人。

**规则**：
1. 前 30 秒必须回答：这是什么项目？怎么跑起来？
2. 安装步骤必须逐行可执行——不能跳过任何隐含步骤
3. 架构概述用一个 ASCII 图，不要用 5 段文字

## 常见写作问题和修正

| 问题 | 示例（差） | 修正（好） |
|---|---|---|
| **被动语态隐藏责任** | "系统出现了一个故障" | "MongoDB 连接池在 14:32 耗尽" |
| **模糊形容词** | "这个方案性能较好" | "p99 延迟从 800ms 降至 120ms" |
| **不完整的对比** | "新方案更快" | "新方案 p99 延迟 120ms（旧方案 800ms，提升 85%）" |
| **"显然""显而易见"** | "显然，我们应该用 Redis" | "我们应该用 Redis，因为查询延迟 < 1ms 且已有运维经验" |
| **没有数据的声称** | "用户抱怨速度慢" | "过去 30 天有 12 个用户反馈聊天响应超过 5 秒" |
| **`this/that` 指代不明** | "这个方案解决了那个问题" | "轮询方案解决了 FSEvents 静默丢事件的问题" |
| **段落过长** | 15 行的段落 | 拆成 3 段，每段 3-5 行；用标题或列表分割 |

## 写作流程

```
1. 写草稿（快写——不在意质量）
2. 放 30 分钟（或第二天再看）
3. 删减 20%——删掉"显然""非常""基本上"这些无意义的词
4. 大声读一遍——如果你在读的时候喘不过气，句子太长了
5. 让别人读——他们卡住的地方就是你写得不清楚的地方
```

## 反模式

| 反模式 | 失败原因 | 正确做法 |
|---|---|---|
| 写给未来的自己 | 你 3 个月后已经不记得上下文了 | 写给一个刚加入团队的同事——他什么都不知道 |
| 过度使用缩写 | RPC、SSE、MV3、CSP 堆在一起 | 首次使用时写出全称；如果缩写不通用，避免使用 |
| 文档越长越好 | 越长越没人读——读者的时间比你的时间更贵 | 如果核心观点可以在 200 字内说完，不要写 2000 字 |
| 完美的初稿 | 追求完美让你不敢开始写——"还在写"比"还没开始写"好 | 先写垃圾初稿；好文章是改出来的，不是写出来的 |
| 写完不维护 | 过时的文档比没有文档更危险——它提供错误的假设 | 每次修改代码时检查相关文档是否需要更新 |
