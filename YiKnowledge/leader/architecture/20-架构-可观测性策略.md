# 可观测性策略

> 可观测性回答三个问题：**系统在做什么？**（指标）**为什么这么做？**（日志）**请求走了什么路径？**（追踪）。三者互补，缺一不可。

## 三大支柱

| 支柱 | 回答的问题 | 粒度 | 成本 | YrY 当前状态 |
|---|---|---|---|---|
| **日志 (Logging)** | 具体事件发生了什么？ | 单次请求 | 低（存储成本） | 有基础日志，无结构化 |
| **指标 (Metrics)** | 系统总体表现如何？ | 聚合统计 | 低 | 无 |
| **追踪 (Tracing)** | 一个请求经过了哪些服务？ | 请求级 | 中（采样降低） | 无 |

**当前 YrY**：三大支柱中只有日志有基础覆盖。指标和追踪是空白。Q4 目标：建立基础指标采集。

## 日志策略

### 日志级别

| 级别 | 含义 | 使用场景 | 示例 |
|---|---|---|---|
| **ERROR** | 需要立即关注——用户受影响 | 异常、服务不可用、数据丢失 | `MongoDB 连接失败，重试 3 次后放弃` |
| **WARNING** | 需要关注但不紧急——可能预示问题 | 接近限制、降级、重试成功 | `连接池使用率 > 80%`、`RAG 检索超时，降级到纯 LLM` |
| **INFO** | 关键业务事件——用于审计和理解系统行为 | 请求处理、配置变更、服务启停 | `聊天请求完成: session_id=xxx, tokens=150` |
| **DEBUG** | 诊断信息——仅在排查问题时开启 | 详细的变量值、中间步骤 | `查询参数: filter={...}, projection={...}` |

### 结构化日志

不要写自由文本日志——用结构化格式（JSON），便于搜索和聚合：

```python
# 差
logging.info(f"用户 {user_id} 查询了 {query}，返回 {len(results)} 条结果")

# 好
logging.info("search_completed", extra={
    "user_id": user_id,
    "query": query[:100],  # 截断长查询
    "result_count": len(results),
    "duration_ms": elapsed_ms,
    "source": "rag" | "llm"
})
```

### 每条日志必须包含

| 字段 | 说明 | 示例 |
|---|---|---|
| `timestamp` | ISO 8601 格式 | `2026-09-15T14:32:00Z` |
| `level` | ERROR/WARNING/INFO/DEBUG | `INFO` |
| `message` | 简短的人类可读描述 | `chat_request_completed` |
| `trace_id` | 请求级别的唯一 ID（关联前后端） | `uuid` |
| `context` | 业务上下文（用户、会话、操作） | `{session_id, user_id}` |

### 安全红线——绝不出现在日志中

- 密码、Token、API Key
- 完整的用户聊天内容（隐私）
- 个人身份信息（邮箱、手机号）
- 信用卡号、支付信息

### YiAi 日志实现建议

```python
# src/utils/logging.py
import logging
import json
import uuid
from contextvars import ContextVar

trace_id_var: ContextVar[str] = ContextVar("trace_id", default="")

def set_trace_id():
    trace_id_var.set(str(uuid.uuid4())[:8])

def structured_log(level: str, msg: str, **kwargs):
    log_data = {
        "timestamp": datetime.utcnow().isoformat(),
        "level": level,
        "message": msg,
        "trace_id": trace_id_var.get(),
        **kwargs
    }
    # 过滤敏感字段
    log_data = {k: v for k, v in log_data.items()
                if k not in ("password", "token", "api_key")}
    logging.getLogger("yiai").log(
        getattr(logging, level), json.dumps(log_data, default=str)
    )
```

## 指标策略

### 应该采集的指标

| 类别 | 指标 | 类型 | 用途 |
|---|---|---|---|
| **请求** | 请求数、错误数、延迟分布 | Counter + Histogram | SLO 合规检查 |
| **资源** | CPU、内存、磁盘使用率 | Gauge | 容量规划和告警 |
| **业务** | 聊天请求数、RAG 查询数、活跃会话数 | Counter | 业务健康度 |
| **依赖** | MongoDB 查询延迟、Ollama 推理延迟 | Histogram | 依赖健康度 |
| **应用** | 连接池使用率、队列深度、重试次数 | Gauge | 内部健康度 |

### RED 方法（每个服务的核心指标）

| 指标 | 含义 | 告警条件 |
|---|---|---|
| **Rate** (请求速率) | 每秒请求数 | 骤降 50%——可能服务故障 |
| **Errors** (错误率) | 失败请求占比 | > 1%（或超过错误预算燃烧速率） |
| **Duration** (延迟) | p95/p99 请求延迟 | p95 > SLO 阈值 |

### 实现路径

```
Q4: 手动指标 → Python logging 输出结构化指标
  ├── 请求计数和延迟（中间件级别）
  ├── 错误计数
  └── 健康检查端点（/health）

Q1 2027: Prometheus + Grafana（如果需要）
  ├── prometheus_client 库暴露 /metrics
  ├── Grafana 仪表盘
  └── 告警规则
```

### 最小可行指标（Q4 目标）

```python
# YiAi 中间件——最小可行指标
@app.middleware("http")
async def metrics_middleware(request, call_next):
    start = time.perf_counter()
    response = await call_next(request)
    duration_ms = (time.perf_counter() - start) * 1000

    structured_log("INFO", "request_completed", extra={
        "method": request.method,
        "path": request.url.path,
        "status": response.status_code,
        "duration_ms": round(duration_ms, 1),
    })
    return response
```

## 告警策略

### 告警设计原则

1. **告警症状，不告警原因** — "用户聊天请求失败率 > 1%"（症状）而非"CPU > 80%"（原因可能是正常的批处理）
2. **每条告警需要对应一个 runbook** — 收到告警的人知道该做什么
3. **告警要有足够的噪音比** — 如果 90% 的告警被忽略，剩下的 10% 也会被忽略
4. **告警燃烧速率，不告警阈值** — "错误预算在 1 小时内消耗了 2%"而非"错误率 > 1%"

### YrY 告警分级

| 等级 | 含义 | 通知方式 | 响应时间 |
|---|---|---|---|
| **P0 — 紧急** | 核心用户旅程中断 | 电话/即时通知 | 5 分钟内响应 |
| **P1 — 警告** | 显著服务降级 | Slack 通知 | 30 分钟内响应 |
| **P2 — 关注** | 趋势异常或接近阈值 | 工单 | 下一个工作日 |

### 当前告警设置（手动检查）

截至 2026 Q3，YrY 无自动化告警。当前依赖手动检查：

| 检查项 | 频率 | 方法 |
|---|---|---|
| YiAi 是否响应？ | 每次开发前 | `curl http://localhost:10086` |
| Ollama 是否加载模型？ | 需要时 | `ollama list` |
| MongoDB 是否运行？ | 需要时 | `pgrep mongod` |
| 磁盘空间 | 每月 | `df -h` |

Q4 目标：YiAi 健康检查端点 + 自动检测。

## 前端可观测性

### YiVad (Vue 3)

- **错误边界**：全局 `app.config.errorHandler` 捕获未处理的 Vue 错误
- **API 调用追踪**：RequestHttp 拦截器记录所有 RPC 调用的延迟和状态
- **关键用户交互**：聊天发送、搜索查询（打印到 console 或发送到后端）

```typescript
// RequestHttp 拦截器埋点
request.interceptors.response.use(
  (response) => {
    console.debug(`[RPC] ${config.data.module_name}.${config.data.method_name}`,
      `duration=${Date.now() - start}ms`, `code=${response.data.code}`);
    return response;
  },
  (error) => {
    console.error(`[RPC] ${config.data.module_name}.${config.data.method_name}`,
      `error=${error.message}`);
    return Promise.reject(error);
  }
);
```

### YiPet (React 18 / Chrome 扩展)

- Content Script 错误：通过消息通道报告给 Service Worker
- Service Worker 错误：记录到 `chrome.storage.local` 的诊断区
- 关键断言：双世界消息格式验证失败时输出结构化错误

## 可观测性成熟度路线

| 阶段 | 日志 | 指标 | 告警 | 目标时间 |
|---|---|---|---|---|
| **1. 手动** | print/logging 自由文本 | 无 | 手动检查 | 当前 |
| **2. 结构化** | JSON 结构化日志 + trace_id | 请求计数/延迟 | 健康检查端点 | Q4 2026 |
| **3. 仪表化** | 集中日志收集 | Prometheus + Grafana | 告警规则 | Q1-Q2 2027 |
| **4. 全栈** | 日志+指标+追踪关联 | SLO 仪表盘 | 燃烧速率告警 | 团队 ≥ 3 人时 |

**当前阶段 1 → Q4 目标阶段 2**：这是性价比最高的跳跃——结构化日志和基础指标让排查问题从"盲飞"变为"有数据"。

## 反模式

| 反模式 | 失败原因 | 正确做法 |
|---|---|---|
| 日志太多 | 100GB/天的 DEBUG 日志——没人看，磁盘先满 | 生产环境 INFO 及以上；DEBUG 仅在排查时临时开启 |
| 日志中记录敏感信息 | Token/密码在日志中——安全事件 | 结构化日志自动过滤敏感字段 |
| 有指标无上下文 | 知道错误率 5% 但不知道是哪个端点、哪个用户 | 指标带标签（endpoint, method, status_code） |
| 告警太多 | 每周 200 条告警→所有人静音通知 | 告警症状而非原因；告警前确认需要人工干预 |
| 仅监控生产环境 | Staging 环境问题在生产才暴露 | Staging 环境同样采集指标 |
