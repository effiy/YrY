# 数据库迁移指南

> MongoDB 的 schemaless 特性意味着"没有 schema 迁移工具"——但也意味着"没有 schema 迁移保护"。所有迁移逻辑都在应用代码中，需要更谨慎的手动管理。

## 迁移原则

1. **向后兼容优先** — 新代码能读旧数据，旧代码能读新数据。破坏此原则的迁移需要多阶段
2. **小步快跑** — 大迁移拆成多个小迁移。一个迁移改一个字段比一次改 5 个安全得多
3. **先写后读** — 新字段先开始写入（旧代码忽略它），等所有读代码都部署后再依赖新字段
4. **迁移可回滚** — 每一项迁移都应有回滚方案。如果回滚意味着恢复数据库备份——这不算可回滚
5. **生产数据量测试** — 在 staging 环境用生产级数据量（至少 10% 样本）测试迁移耗时

## 三种变更模式

### 模式 1：兼容性变更（无风险）

最简单——不需要多阶段。直接部署。

| 变更 | 示例 | 为什么安全 |
|---|---|---|
| 新增可选字段 | 给 `sessions` 加 `tags: []` | 旧代码忽略新字段；新代码处理缺失 |
| 新增集合 | 新建一个独立集合 | 不影响已有集合的读写 |
| 新增索引 | `sessions.ensureIndex({tags: 1})` | 不影响读写；注意索引构建期间的性能影响 |

### 模式 2：可控不兼容变更（需多阶段）

| 变更 | 风险 | 迁移阶段 |
|---|---|---|
| 新增必填字段 | 旧代码不写这个字段，新代码读到 null | 必须两阶段 |
| 重命名字段 | 新旧字段名不一致期间，两边都要处理 | 必须三阶段 |
| 修改字段类型 | 旧类型和新类型不兼容 | 必须三阶段 |
| 修改字段语义 | `status: 1/2/3` → `status: "active"/"inactive"/"deleted"` | 必须三阶段 |

### 模式 3：需停机变更（尽量避免）

仅在以下情况可接受：
- 数据量极小（< 1000 文档），迁移耗时 < 1 秒
- 系统尚未上线生产（无用户受影响）
- 旧数据已确认无代码读取

## 多阶段迁移模板

### 两阶段：新增必填字段

**场景**：`sessions` 集合需要新增必填字段 `owner`。

```
阶段 1（部署 v1）：新增字段 + 默认值
  - 写入：每次创建/更新 session 时写入 owner 字段（默认值 = "system"）
  - 读取：优先读 owner 字段，缺失时 fallback 到 "system"
  - 回填：后台脚本为已有 session 补上 owner 字段

阶段 2（部署 v2）：设为必填
  - 确认：所有文档都有 owner 字段（查询 count({owner: {$exists: false}}) = 0）
  - 写入：owner 为必填，不再有默认值
  - 读取：直接读 owner，不需要 fallback
```

**部署间隔**：阶段 1 和 2 之间至少等 1 天——确保回填脚本完成且观察无异常。

### 三阶段：重命名字段

**场景**：将 `sessions` 中的 `pageContent` 重命名为 `plain_text`。

```
阶段 1（部署 v1）：双写
  - 写入：同时写入 pageContent 和 plain_text（相同值）
  - 读取：仍从 pageContent 读取

阶段 2（部署 v2）：切换读取
  - 写入：继续双写
  - 读取：从 plain_text 读取，缺失时 fallback 到 pageContent
  - 确认：所有新文档都有 plain_text

阶段 3（部署 v3）：清理
  - 写入：只写 plain_text
  - 读取：只读 plain_text
  - 删除：删除 pageContent 字段（后台脚本逐批删除）
```

**关键**：三阶段之间有间隔（各 ≥ 1 天）。不要在同一次部署中完成两个阶段。

## 回填脚本模式

大量已有文档需要补新字段时，使用批量回填而非逐条更新：

```python
# YiAi 回填脚本模式
async def backfill_sessions_owner(db, batch_size=100):
    """为缺少 owner 的 session 补默认值"""
    updated_total = 0
    while True:
        result = await db.sessions.update_many(
            {"owner": {"$exists": False}},
            {"$set": {"owner": "system"}},
        )
        if result.modified_count == 0:
            break
        updated_total += result.modified_count
        await asyncio.sleep(0.1)  # 让出 CPU，避免影响正常请求
    return updated_total
```

**回填原则**：
- 批量操作（`update_many` 而非 `update_one`）
- 批次之间有间隔（避免 CPU 峰值）
- 幂等——重复执行不产生副作用
- 记录回填进度（可中断、可恢复）

## 迁移检查清单

### 迁移前
- [ ] 确认当前 schema 状态——所有使用该字段的代码路径已梳理
- [ ] 在 staging 环境用生产级数据量测试迁移
- [ ] 估算迁移耗时（基于 staging 测试结果）
- [ ] 确定回滚方案并测试
- [ ] 数据库备份已完成（如数据量允许）

### 迁移中
- [ ] 在低流量窗口执行（凌晨或周末）
- [ ] 监控数据库 CPU/内存/IOPS（迁移不应显著提升）
- [ ] 监控应用错误率（迁移不应导致业务错误增加）
- [ ] 记录迁移开始/结束时间和影响行数

### 迁移后
- [ ] 验证：查询 `count({new_field: {$exists: false}})` = 0
- [ ] 监控 24 小时——是否有迁移相关的异常？
- [ ] 更新[数据模型文档](./12-架构-数据模型设计原则.md)中的集合描述
- [ ] 如果涉及参数名变更，更新 [API 设计指南](./14-架构-API设计指南.md) 中的参数契约表

## 索引迁移注意事项

索引变更不是免费的——在生产集合上建索引会阻塞写入：

| 操作 | 影响 | 缓解 |
|---|---|---|
| **新建索引** | 构建期间写入排队——大集合可能阻塞数分钟 | `createIndex({...}, {background: true})`；或使用 rolling index build (MongoDB 4.4+) |
| **删除索引** | 即刻生效——但依赖该索引的查询会变慢 | 删除前确认无查询依赖该索引（检查 `explain()`） |
| **修改索引** | 需要删除 + 重建——重建期间的性能间隙 | 先建新索引，确认查询使用新索引后，再删旧索引 |

## 反模式

| 反模式 | 失败原因 | 正确做法 |
|---|---|---|
| 手动逐个更新文档 | 100K 文档逐条更新——花数小时 | `update_many` + 批量循环 |
| 部署代码和迁移脚本同一次 | 迁移失败回滚不了 | 分阶段部署 |
| 没有回填就设为必填 | 新代码读到旧文档的 null → 崩溃 | 先回填，确认 100% 覆盖，再设必填 |
| 迁移在业务高峰期执行 | 索引构建拖慢查询——用户受影响 | 低流量窗口执行 |
| 删除字段太快 | 旧代码某处还在读这个字段 → NPE | 三阶段迁移；删除前全局搜索字段名 |
