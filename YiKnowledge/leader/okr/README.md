## OKR 撰写指南

### 目标 (Objective)

目标应描述一个**期望的最终状态**，而非任务清单。好的目标是定性的、鼓舞人心的，读起来像一个已完成的状态。

| 好 | 差 |
|---|---|
| 技术评审可闭环 — 每条需求产出可回溯的 ADR | 写 5 篇 ADR |
| 前端测试覆盖率达到 60% | 引入 Vitest |
| 部署流水线全自动化 | 配置 GitHub Actions |

### 关键结果 (Key Result)

KR 是**可衡量的成果**，而非活动。每个目标 3-5 个 KR。

| 好 | 差 |
|---|---|
| ADR 覆盖所有当前已实现的重大需求（覆盖率 100%） | 多写 ADR |
| Composable 单元测试覆盖率 ≥ 60% | 写一些测试 |
| 从提交到部署的前置时间 < 30 分钟 | 搭建 CI |

### OKR 生命周期

```
起草 (季度前 2 周) → 对齐 (季度前 1 周) → 执行 (季度中) → 评分 (季度末) → 复盘 (季度末 + 1 周)
```

| 阶段 | 时间 | 活动 |
|---|---|---|
| 起草 | 季度前 2 周 | 技术负责人起草 OKR 初稿 |
| 对齐 | 季度前 1 周 | 与产品和工程师对齐，确认 KR 可衡量 |
| 执行 | 季度中 | 每周检查进度，更新信心度 |
| 评分 | 季度末 | 按 KR 逐项评分 (0-100%) |
| 复盘 | 季度末+1 周 | 什么达成了？什么没达成？为什么？ |

### 评分标准

| 分数 | 含义 | 解读 |
|---|---|---|
| 0-30% | 未达成 | 目标过大、执行受阻或优先级变更 |
| 40-60% | 部分达成 | 有进展但未完全达成 — 正常的"拉伸目标" |
| 70-100% | 达成 | 目标圆满完成 |

**注意**：OKR 不是绩效考核工具。60-70% 的达成率是健康的拉伸目标，100% 通常意味着目标设得过于保守。


### 反模式

- **OKR 写成任务清单** — "完成 10 个功能"是任务，不是目标。目标应描述完成后带来的变化
- **KR 不可衡量** — "提升代码质量"无法衡量。"测试覆盖率从 0% 提升到 60%"可以衡量
- **OKR 与日常工作混淆** — OKR 是季度重点改进项，不是日常运维。日常值班和 bug 修复不应占满 OKR
- **季度中从不检查** — 季度末才想起来有 OKR，此时已无法调整
