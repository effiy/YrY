# 基础设施规模估算

> "我们需要多大服务器？"——回答这个问题不需要精确数字，需要一个**数量级正确**的估算框架。过度配置浪费钱，配置不足导致故障。目标是：用最小的资源安全地运行服务。

## 估算原则

1. **从测量开始，不从猜测开始** — 如果有现有系统，用监控数据；没有的话用负载测试
2. **为峰值估算，为均值付费** — 配置能处理峰值，但利用 auto-scaling 或预留实例降低均值成本
3. **留 30% 余量** — 100% 利用率 = 零缓冲。任何微小波动都会触发故障
4. **每季度重新评估** — 基础设施需求随业务增长变化。年度配置 = 11 个月的机会损失

## 四维估算框架

### 1. CPU

```
所需 CPU 核心 = (单请求 CPU 时间 × 峰值请求数/秒) / 目标利用率

示例：
  单请求 CPU 时间 = 50ms = 0.05s
  峰值请求数 = 20 req/s
  目标利用率 = 70%
  所需 CPU = (0.05 × 20) / 0.7 = 1.4 核心 → 配置 2 核心
```

### 2. 内存

```
所需内存 = 基线内存 + (单请求内存 × 并发请求数) + 30% 余量

基线内存 = 进程启动后的空闲内存占用
单请求内存 = 处理一个请求时的内存峰值 - 基线内存
```

| 组件 | 典型基线内存 | 备注 |
|---|---|---|
| FastAPI (uvicorn) | 100-200 MB | Python 进程本身 |
| Ollama (7B 模型) | 4-6 GB VRAM | 量化模型可降低 |
| MongoDB | 500 MB - 2 GB | 取决于索引大小和 working set |
| Node.js (Rsbuild dev) | 200-500 MB | 开发模式更高 |

### 3. 存储

```
所需存储 = 当前数据量 × (1 + 月增长率)^月数 + 索引开销 + 30% 余量

索引开销 ≈ 数据量的 10-30%
```

**YrY 存储增长估算**：

| 数据类型 | 当前量 | 月增长率 | 6 个月后 | 12 个月后 |
|---|---|---|---|---|
| 聊天会话 (MongoDB) | ~10 MB | 20% | ~30 MB | ~90 MB |
| 知识库文件 (YiKnowledge) | ~5 MB | 10% | ~9 MB | ~16 MB |
| 向量索引 (RAG) | ~50 MB | 10% | ~88 MB | ~155 MB |
| 文件备份 (static_files) | ~20 MB | 5% | ~27 MB | ~36 MB |
| **合计** | **~85 MB** | — | **~154 MB** | **~297 MB** |

**结论**：当前单人项目存储需求极小（< 1 GB）。即使 12 个月后也仅约 300 MB。不需要对存储做特殊规划。

### 4. 带宽

```
所需带宽 (Mbps) = 峰值请求/秒 × 平均响应大小 (Mb)

示例：
  峰值请求 = 20 req/s
  平均响应大小 = 50 KB = 0.4 Mb
  所需带宽 = 20 × 0.4 = 8 Mbps
```

对于 SSE 流式响应（聊天），计算方式不同：
```
SSE 带宽 = 并发 SSE 连接数 × 平均 token 速率 × 平均 token 大小
         = 5 连接 × 30 token/s × ~4 bytes/token
         ≈ 600 bytes/s ≈ 0.005 Mbps  # 带宽需求极小
```

## YrY 各组件规模估算

### YiAi (FastAPI)

| 维度 | 当前需求 | 未来 12 个月预估 |
|---|---|---|
| CPU | 0.5 核心（本地开发） | 1-2 核心（如有多个并发聊天请求） |
| 内存 | 200 MB + Ollama 模型 | 500 MB + Ollama 模型 |
| 关键瓶颈 | Ollama GPU VRAM | 同左；LLM 推理是瓶颈，不是 API 服务 |

### Ollama (LLM 推理)

| 模型大小 | VRAM 需求 (Q4 量化) | 推理速度 (Mac Mini M2) |
|---|---|---|
| 7B (qwen2.5) | ~4 GB | ~30 token/s |
| 14B | ~8 GB | ~15 token/s |
| 32B | ~18 GB | ~5 token/s（可能超出可用 VRAM） |

**建议**：当前 Mac Mini 16GB 统一内存适合运行 7B 模型。如需运行更大模型，需要更多 RAM 或切换到云 API。

### MongoDB

| 维度 | 当前需求 | 注意事项 |
|---|---|---|
| 存储 | < 1 GB | 本地或 Atlas M10 (10 GB 存储) 绰绰有余 |
| 内存 | 512 MB | MongoDB 尽可能将 working set 放在内存中 |
| 连接数 | < 10 | 默认最大连接 100，完全够用 |

### YiVad (静态站点)

| 维度 | 开发 (Rsbuild dev) | 生产 (静态文件) |
|---|---|---|
| CPU | 1 核心（HMR 编译） | 几乎为零（CDN 分发） |
| 内存 | 300-500 MB | 几乎为零 |
| 带宽 | 本地 localhost | 取决于静态资源大小（CDN 处理） |

## 何时从本地开发切换到云服务器

当前 YrY 在本地 Mac Mini 上运行。什么时候需要迁移到云服务器？

| 触发条件 | 说明 |
|---|---|
| 需要 24/7 外部访问 | YiVad/YiPet 需要公网访问 YiAi |
| GPU 内存不足 | 需要运行更大 LLM 模型（> 14B） |
| 多人协作需要共享环境 | 第二个开发者需要访问同一套服务 |
| 需要生产级可用性 | 99%+ uptime 要求需要云基础设施 |

## 规模估算速查

| 如果... | 大约需要... |
|---|---|
| 单人开发，本地运行 | Mac Mini 16GB RAM + 本地 MongoDB + 本地 Ollama |
| 2-5 人团队，共享开发环境 | 1 台 4 核 8GB 云服务器 (YiAi) + MongoDB Atlas M10 |
| 生产环境 (< 100 用户) | 2 核 4GB (YiAi) + 4 核 8GB GPU (Ollama 或云 API) + Atlas M10 |
| 生产环境 (100-1000 用户) | 4 核 8GB × 2 (YiAi 负载均衡) + 云 API (不自己托管 LLM) + Atlas M30 |

## 反模式

| 反模式 | 失败原因 | 正确做法 |
|---|---|---|
| 为峰值 100% 配置 | 资源 90% 时间闲置 | 配置基线 + auto-scaling 处理峰值 |
| 存储不考虑增长 | 6 个月后磁盘满了 | 估算月增长率；设置存储告警（> 80%） |
| 只看 CPU 不看内存 | CPU 够但内存不足导致 OOM Kill | 内存和 CPU 一起估算 |
| 从不重新评估 | 一年前配置的，现在负载变了 | 每季度检查资源利用率 |
| "更多总是更好" | 4 核够用但配了 16 核——4× 成本 | 测量实际使用量，向下调整过度配置 |
