# 自研还是采购 — 决策框架

> 技术负责人最昂贵的决策之一：为了一时兴起自研一个已有成熟方案的服务，或者为了一点方便采购了一个不适合的服务然后花数年时间 workaround。

## 决策原则

**核心规则**：如果它是你的**核心差异化能力**——自研。如果它是**通用能力**——采购。

| 如果是核心差异化 | 如果是通用能力 |
|---|---|
| 你的用户为此付费 | 所有人都需要但没人为此付费 |
| 自己做能比市面方案好 2× 以上 | 市面已有成熟方案，自己做的不会更好 |
| 市场竞争依赖此能力 | 它只是支撑你核心业务的管道 |

**YrY 示例**：
- Agent 模式的状态机和确认门逻辑 → **自研**（核心差异化——这是 YiAi 的独特能力）
- LLM 推理引擎 → **采购**（Ollama + 云 API——通用能力，不需要自己训练模型）
- MongoDB 数据库 → **采购**（存储是通用能力）
- 知识库 RAG 引擎 → **自研**（llama_index 是库，但 RAG 策略、分块、混合检索逻辑是 YiAi 的核心）

## 决策矩阵

| 评估维度 | 权重 | 说明 |
|---|---|---|
| **功能匹配度** | 25% | 采购方案能覆盖多少需求？自研需要多少开发量？ |
| **总拥有成本 (TCO)** | 25% | 不只是价格——包含集成、维护、迁移成本 |
| **核心/通用判断** | 20% | 这是我们的差异化能力吗？ |
| **时间-to-价值** | 15% | 多快能用上？采购通常更快 |
| **灵活性与控制** | 10% | 未来需求变化时能否适应？ |
| **供应商风险** | 5% | 供应商倒闭、被收购、涨价的风险 |

### 自研总成本估算

```
自研 TCO = 初始开发 + 年度维护 + 机会成本

初始开发 = 人周 × 人周成本
年度维护 = 初始开发的 15-25%（bug 修复、依赖更新、文档）
机会成本 = 这些人力如果做其他事的价值
```

### 采购总成本估算

```
采购 TCO = 订阅费 + 集成成本 + 迁移成本 + 年度运营

集成成本 = 接入、配置、培训的人周成本
迁移成本 = 如果将来要换供应商，迁移数据/逻辑的成本
年度运营 = 管理供应商关系、处理账单、升级
```

## 三种路径对比

| 维度 | 自研 (Build) | 采购 SaaS (Buy) | 开源自托管 (Open Source) |
|---|---|---|---|
| **前期成本** | 高（开发人力） | 低-中（订阅费） | 中（部署 + 配置） |
| **持续成本** | 中（维护） | 中-高（订阅费随规模增长） | 低-中（运维人力） |
| **灵活性** | 最高 | 最低（受限于供应商路线图） | 高（可修改源码） |
| **上线速度** | 慢 | 快 | 中 |
| **供应商锁定** | 无 | 高 | 低（可自己维护 fork） |
| **运维负担** | 高 | 低 | 中-高 |
| **适用场景** | 核心差异化能力 | 通用能力、非核心 | 需要控制但不想从零开始 |

## 决策流程

### 第一步：识别核心/通用

问 3 个问题：
1. 如果我们的竞品也用了同样的方案，我们还有优势吗？
2. 用户是为这个能力付费，还是为基于这个能力的上层产品付费？
3. 如果我们自己做一个更好的版本，市场会关心吗？

如果答案分别是"没有"、"上层产品"、"不关心" → **这是通用能力，采购**。

### 第二步：评估 TCO (3 年视角)

| 成本项 | 自研 | SaaS | 开源 |
|---|---|---|---|
| Year 1 | | | |
| Year 2 | | | |
| Year 3 | | | |
| **3 年总计** | | | |

**计算时注意**：
- SaaS 的订阅费通常随用量增长——用 3 年后的预估用量而非当前用量
- 自研的维护成本不是零——每年代码需要适配依赖升级、修 bug
- 开源"免费"但运维不免费——谁负责升级、打安全补丁、排查故障？

### 第三步：评估非成本因素

如果 TCO 差距在 20% 以内，非成本因素决定：

| 因素 | 倾向于自研 | 倾向于采购 |
|---|---|---|
| 团队有此领域经验吗？ | 有 | 无 |
| 供应商健康度（融资/盈利/团队）？ | — | 健康且稳定 |
| 数据驻留/合规要求？ | 严格 | 宽松 |
| 需要深度定制吗？ | 需要 | 不需要 |
| 市场上有 3+ 竞争方案吗？ | 只有 1-2 家 | 充分竞争 |

### 第四步：做出决策并记录

不管选自研还是采购，写一个简短的决策记录（不一定是完整 ADR）：

```markdown
# 决策：自研/采购 [方案名称]

**问题**：我们需要 [能力] 来实现 [目标]。
**决策**：[自研/SaaS/开源] [方案名称]。
**替代方案**：
- [方案 B]：拒绝——[原因]
- [方案 C]：拒绝——[原因]
**关键假设**：[如果这个假设不成立，决策需要重新评估]
**审查日期**：[6 个月后]
```

## YrY 场景决策示例

### 示例 1：LLM 推理 — 自托管 Ollama vs. 云 API

| 维度 | 自托管 Ollama | 云 API |
|---|---|---|
| 功能匹配 | 满足基本需求 | 模型选择更多 |
| TCO (年) | 已有 GPU（边际成本 ~$360/年电费） | 按量付费，取决于使用量 |
| 核心/通用 | 通用能力 | 通用能力 |
| 灵活性 | 高（可选任何兼容模型） | 受限于提供商模型列表 |

**决策**：**两者都用**——Ollama 为默认（成本低），云 API 为 fallback（可靠性）。这不是二选一——多提供商路由是正确答案。

### 示例 2：监控/可观测性 — 自研 vs. SaaS

当前 YrY 无监控。如果将来需要：

| 维度 | 自研（Prometheus + Grafana 自托管） | SaaS（Datadog 等） |
|---|---|---|
| 功能匹配 | 需自己搭建仪表盘 | 开箱即用 |
| TCO (年) | 约 $240（服务器） + 运维人力 | 约 $1800+/年（按主机收费） |
| 核心/通用 | 通用 | 通用 |
| 规模 | 适合 1-5 台服务器 | 规模化后价值更高 |

**建议**：单人/小团队时自托管 Prometheus + Grafana。团队 > 5 人或服务 > 10 个时重新评估 SaaS。

## 反模式

| 反模式 | 失败原因 | 正确做法 |
|---|---|---|
| NIH (Not Invented Here) | 排斥一切外部方案——"我们自己做更好" | 诚实评估：你的团队真的能比专门做这个的公司做得更好？ |
| 只看订阅费不看 TCO | SaaS 月费 $50 看似便宜，但集成花了 2 周（人力成本 $X000） | 算 3 年 TCO，包含集成和迁移成本 |
| "开源 = 免费" | 开源软件不花钱但花时间——部署、运维、升级、排查故障 | 估算年度运维人周，计入 TCO |
| 供应商锁定不自知 | 数据格式专有、API 不标准——将来迁移成本极高 | 评估迁移成本；优先选择标准 API 和数据可导出的方案 |
| 自研通用能力 | 花 3 个月做内部 CI/CD 平台——世界上已经有 Jenkins/GitHub Actions | 非核心差异化能力不一定是自研 |
