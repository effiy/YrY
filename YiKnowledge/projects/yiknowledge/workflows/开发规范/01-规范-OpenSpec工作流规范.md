# OpenSpec 工作流规范

> Claude Code 在 OpenSpec 项目中的行为规范。定义子代理协作策略、内容质量门禁、上下文管理、大规模任务处理等核心约定。

## 一、子代理协作策略

在 OpenSpec 工作流中，根据阶段特点自动使用子代理：

| 阶段 | 执行模式 | 拆分策略 |
|------|----------|----------|
| 提案（Proposal） | 并行搜索 | 同时启动多个 Explore 子代理搜索知识库内容、角色目录、已有模式 |
| 设计（Design） | 主代理独立 | 决策性强，不适合拆分子代理 |
| 实现（Apply） | 混合模式 | 识别 tasks.md 中无依赖关系的任务组并行实现，有依赖的串行执行 |
| 验证（Verify） | 并行检查 | 同时启动子代理检查 frontmatter 完整性、命名规范、角色边界、RAG 就绪 |
| 落地（Land） | 主代理独立 | 回写和提交步骤短，拆分子代理无收益 |

### 子代理使用规则

- 子代理只做搜索和确定的子任务，不做架构决策
- 并行子代理的结果由主代理综合判断
- 有依赖关系的任务必须串行执行，不可强行并行

## 二、内容质量门禁

### 动手前

1. 列出假设，逐条验证
2. 复杂任务有多种解释时全部列出，有更简单方案时提出，必要时坚持己见
3. 不清楚的地方停下来，明确困惑点再提问

### 动手时

- **只写被要求的东西**：不添加"灵活"、"可配置"的过度设计，不为单次使用创建抽象，不添加未要求的内容。200 行能压缩到 50 行则重写。
- **精准修改**：只改必要的，改完清理自己造成的垃圾。匹配现有风格，不改进无关内容。每一行改动都应追溯到用户的具体请求。
- **禁止非通用性改动**：
  - 不写只适配特定场景的内容
  - 假设所有外部数据都有效 → 必须校验完整性
  - 处理内容时考虑边界情况（空 frontmatter、缺失字段、格式异常）
  - 禁止魔法值 → 使用标准术语或引用规范
  - 禁止隐式正确假设 → 所有声明必须可验证
  - 禁止不完整的反模式 → 必须包含错误/正确/原因三列

### 动手后

- **frontmatter + 命名 + 结构 通过是底线**：8 个必需字段完整、kebab-case 命名、目录层级 ≤ 3
- 每步有可验证的退出条件：多步骤任务先列计划，动手后循环验证直到成功

## 三、上下文管理

### 文件读取

- 超过 500 行的文件，不要假设单次读取覆盖完整内容，根据需要分次读取
- 超过 10 条消息后，编辑任何文件前强制重新读取

### 上下文压缩恢复后（Apply 阶段）

1. `git status` — 确认已改动的内容
2. 重读 `changes/<name>/proposal.md` + `design.md` + `tasks.md` — 确认范围、设计决策、任务状态
3. 对照 design.md 检查关键实现（文件路径、命名、角色归属）
4. 运行 frontmatter + 命名规范验证
5. 然后继续实施

### 阶段隔离

- 所有 OpenSpec 阶段均由用户手动触发，不自动进入下一阶段
- `/opsx:explore`、`/opsx:propose`、`/opsx:apply`、`/opsx:verify` 均需用户明确调用
- 禁止在同一阶段内触发其他阶段（如 explore 阶段不能调用 apply，verify 阶段不能调用 e2e）

### 重构前清理

过时的内容、错误的引用、不一致的术语先修正，单独提交，再做重构。

## 四、大规模任务处理

**200 行以上修改或显著架构变更必须走 OpenSpec**：内容改动超过 200 行，或涉及角色目录重构、分类标准变更、知识治理流程调整时，禁止直接修改，必须通过 OpenSpec 工作流（`/opsx:propose`）。

## 五、工具使用与编辑安全

### 搜索策略

- 使用 Grep 搜索内容，Glob 搜索文件名，两者缺一不可
- 搜索知识库时默认包含所有 `.md` 文件，跳过 `.git/`、`archive/` 等目录
- 重命名文件时覆盖所有引用（INDEX.md、其他文件中的链接），不得假设一次覆盖所有情况

### 编辑规则

- 编辑后重新读取文件确认变更正确应用
- 变更完成后，明确告知用户可能遗漏的区域（交叉引用、INDEX 更新等），提示人工复查
- 修改源文件只能使用内置编辑工具（Read/Edit/Write），禁止用 sed/awk 等管道命令改文件

### 安全边界

- 不主动推送代码，除非用户明确要求
- 中文回复用户

## 六、完整生产工作流

```
 1. 探索与提案   → /opsx:explore → /opsx:propose
 2. 内容与架构评审 → /plan-ceo-review / /plan-eng-review（按需触发）
 3. 设计审查     → /plan-design-review
 4. 实现         → /opsx:apply
 5. 自审         → /opsx:verify
 6. 发布         → /ship 或 /land-and-deploy（用户手动触发）
 7. 迭代回顾     → /retro
```

### 各阶段详解

**1. 探索与提案**：现有知识库先探索再写 proposal；新领域直接生成 proposal + scenarios。方向不明确时可用 `/office-hours` 做创意验证。

**2. 内容与架构评审**（按需触发）：
- `/plan-ceo-review`：知识库战略影响、角色边界变更时
- `/plan-eng-review`：目录结构重构、分类标准变更时

**3. 设计审查**：实现前进行设计评审，确保方案合理。

**4. 实现**：执行 `/opsx:apply` 进行内容编写。

**4.1 变更边界检查**：
- 实施前：对照 proposal.md 确认范围
- 实施中：禁止修改其他 `changes/<name2>/` 目录下的文件
- 完成后：逐条对照 proposal.md 确认 scope 内的已交付，scope 外的未改动

**4.2 任务类型区分**：
- 构建任务：创建文件/内容 → frontmatter + 命名规范验证通过后可标记
- 验证任务：需实际检查 → 必须验证后才能标记
- 依赖任务：等前置完成 → 不提前标记

**4.3 自动化门禁**：frontmatter 完整性、kebab-case 命名、目录层级自动检查，任一失败则停止。

**5. 发布**：由用户手动触发。知识库变更直接提交推送。

**6. 迭代回顾**：`/retro` 总结本次迭代的经验教训。

## 七、YiKnowledge 项目特定约束

### 知识库规范引用

实施 OpenSpec 变更时，必须参考以下规范：

| 规范 | 文件 | 适用阶段 |
|------|------|----------|
| 文件标准规范 | `specs/file-standards.md` | Design + Apply |
| 知识治理规范 | `specs/governance.md` | Design + Apply |
| 知识条目模式 | `specs/knowledge-entry.md` | Design + Apply |

### 强制约束检查

- 所有文件必须包含 8 个必需 frontmatter 字段
- 文件名使用 kebab-case，禁止下划线和数字
- 目录层级不超过 3 级：`role/problem-domain/file.md`
- 每条知识属于唯一角色目录（物理位置）
- 多角色覆盖使用 frontmatter `roles:` 字段声明
- 内容结构遵循三段式：Summary → Core viewpoints → Key information
- 反模式示例必须包含错误/正确/原因三列

### 角色边界约束

- 文件归属使用决策树判定，不创建模糊分类
- 架构决策 → leader/，架构模式 → engineer/
- 安全策略 → leader/risk/，安全加固 → engineer/ship/
- 每个角色目录必须有 INDEX.md 索引文件
