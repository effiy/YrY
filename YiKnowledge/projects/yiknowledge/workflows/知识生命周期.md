# YiKnowledge 知识生命周期 — 创建 → 评审 → 发布 → 更新 → 归档

> 知识文件在 YiKnowledge 中的完整生命周期，从创建到归档的每个阶段都有明确的操作步骤和检查清单。

## 生命周期概览

```
创建 (inbox) → 评审 (triage) → 发布 (active) → 更新 (active) → 归档 (archive)
  │               │               │               │               │
  │               │               │               │               └── 内容过时，保留备份
  │               │               │               └── 内容更新，维护版本
  │               │               └── 审核通过，对外可用
  │               └── 质量检查，就绪检查清单
  └── 确定主题，编写内容
```

## 阶段一：创建 (inbox)

### 目标

创建新的知识文件，内容编写完成，但尚未经过质量检查。

### 步骤

1. **确定主题** — 明确要记录的知识主题
2. **选择角色目录** — 根据内容归属选择正确的角色目录
3. **选择 problem-domain** — 在角色目录下选择合适的子目录
4. **创建文件** — 使用 kebab-case 命名，放在正确的目录下
5. **填写 frontmatter** — 按模板填写所有必填字段
6. **编写内容** — 按标准结构编写内容
7. **添加交叉引用** — 在 related 字段中添加相关文件链接
8. **设置 lifecycle 为 inbox** — 标记为待评审状态

### 检查清单

- [ ] 文件名符合 kebab-case 规范
- [ ] 目录深度不超过 3 级
- [ ] 文件在正确的角色目录下
- [ ] 8 个 frontmatter 必填字段齐全
- [ ] `category` 字段与文件路径匹配
- [ ] `lifecycle` 设置为 `inbox`
- [ ] 内容结构完整（标题、摘要、核心内容、关键约定）
- [ ] 交叉引用链接正确

### 角色职责

| 角色 | 职责 |
|---|---|
| 内容作者 | 编写内容，确保质量 |
| Curator | 无（此阶段不介入） |

## 阶段二：评审 (triage)

### 目标

对内容进行质量检查，确保符合知识库规范，准备发布。

### 步骤

1. **更新 lifecycle 为 triage** — 提交评审
2. **执行就绪检查清单** — 逐项检查 10 项内容
3. **检查 frontmatter** — 验证所有字段正确
4. **检查内容质量** — 验证内容准确、完整、有价值
5. **检查角色边界** — 确认内容在正确的角色目录下
6. **检查重复内容** — 确认没有与已有内容重复
7. **评审通过** — 更新 status 为 stable，lifecycle 为 active
8. **评审不通过** — 标注修改项，lifecycle 退回 inbox

### 检查清单

- [ ] 就绪检查清单 10 项全部通过
- [ ] frontmatter 所有字段正确
- [ ] 内容准确、完整、有价值
- [ ] 没有重复已有内容
- [ ] 代码示例可运行
- [ ] 交叉引用链接有效
- [ ] 语言通顺，无错别字

### 评审意见模板

```markdown
## 评审结果：[通过/不通过]

### 优点
- ...

### 需要修改
- [ ] 修改项 1
- [ ] 修改项 2

### 建议
- ...
```

### 角色职责

| 角色 | 职责 |
|---|---|
| 内容作者 | 提交评审，响应评审意见 |
| Curator | 执行评审，决定通过/驳回 |

## 阶段三：发布 (active)

### 目标

将评审通过的内容发布到活跃状态，对外可用。

### 步骤

1. **更新 frontmatter** — `status: stable`，`lifecycle: active`
2. **更新日期** — `updated` 和 `last_verified` 更新为当前日期
3. **提交到 Git** — 创建提交，推送到仓库
4. **通知相关方** — 如有需要，通知相关人员
5. **YiAi 同步** — YiAi 知识监听器自动扫描并同步到 MongoDB

### 检查清单

- [ ] `status` 已更新为 `stable`
- [ ] `lifecycle` 已更新为 `active`
- [ ] `updated` 和 `last_verified` 日期正确
- [ ] 已提交到 Git 仓库
- [ ] 确认 YiAi 知识监听器已同步（可选）

### 角色职责

| 角色 | 职责 |
|---|---|
| 内容作者 | 执行发布操作 |
| Curator | 确认发布，监控同步状态 |

## 阶段四：更新 (active)

### 目标

对已发布的内容进行更新维护，保持内容准确性。

### 更新类型

| 类型 | 说明 | 操作 |
|---|---|---|
| 内容修正 | 修正错误、补充信息 | 直接修改，更新 `updated` 日期 |
| 结构调整 | 重组内容结构 | 修改后重新检查 frontmatter |
| 交叉引用更新 | 添加新的相关链接 | 更新 `related` 字段 |
| 生命周期变更 | 从 active 转为 reference | 更新 `lifecycle` 字段 |

### 步骤

1. **识别更新需求** — 发现内容过时、错误或需要补充
2. **修改内容** — 更新文件内容
3. **更新 frontmatter** — 更新 `updated` 日期
4. **检查交叉引用** — 确认相关链接仍然有效
5. **提交更新** — 提交到 Git 仓库

### 定期评审

根据 `review_cycle` 设定的周期进行定期评审：

| 评审动作 | 说明 |
|---|---|
| 检查内容准确性 | 内容是否仍然准确 |
| 检查代码示例 | 代码示例是否仍然有效 |
| 检查链接 | 相关链接是否仍然有效 |
| 更新 `last_verified` | 更新最后验证日期 |
| 评估生命周期 | 是否仍适合 active 阶段 |

### 角色职责

| 角色 | 职责 |
|---|---|
| 内容作者 | 维护和更新内容 |
| Curator | 提醒定期评审，监控内容质量 |

## 阶段五：归档 (archive)

### 目标

将过时或不再需要的内容归档，保留备份。

### 归档触发条件

| 条件 | 说明 |
|---|---|
| 内容过时 | 技术栈、流程、规范已变更 |
| 内容被替代 | 新内容已创建，旧内容不再需要 |
| 长期未更新 | 超过 1 年未更新，且无参考价值 |
| 内容重复 | 与已有内容高度重复 |

### 步骤

1. **确认归档** — 确认内容确实不再需要
2. **更新 frontmatter** — `status: deprecated`，`lifecycle: archive`
3. **添加归档说明** — 在内容开头添加归档原因和替代文件
4. **提交归档** — 提交到 Git 仓库
5. **保留文件** — 归档文件不删除，保留在仓库中

### 归档文件模板

```markdown
---
title: 旧版架构设计（已归档）
tags: [archived, architecture]
category: curator/archive
created: 2025-01-01
updated: 2026-09-02

>
> **归档日期**：2026-09-02

## 原始内容

...
```

| 角色 | 职责 |

## 常见问题

### 问题 1：评审不通过怎么办？

1. 查看评审意见
2. 逐项修改不通过的内容
3. 重新提交评审
4. 如果对评审意见有异议，与 curator 讨论

### 问题 2：如何判断内容是否应该归档？

判断标准：
- 内容是否还有读者会查阅？
- 内容是否还有参考价值？
- 是否有替代内容？

如果以上三个问题都是"否"，则应该归档。

### 问题 3：归档后内容可以恢复吗？

可以。归档文件保留在仓库中，可以随时恢复：
1. 更新 `lifecycle` 为 `active`
2. 更新 `status` 为 `stable`
3. 更新内容（如有需要）
4. 移除归档说明

## 关键约定

1. **所有内容必须经过 triage** — 不能直接从 inbox 到 active
2. **就绪检查清单是强制门禁** — 10 项全部通过才能发布
3. **定期评审不可跳过** — 按 review_cycle 设定的周期执行
4. **归档优先于删除** — 过时内容先归档，确认无用后再删除
5. **更新要更新日期** — 每次修改必须更新 `updated` 字段
6. **归档要说明原因** — 归档文件必须添加归档说明和替代文件
