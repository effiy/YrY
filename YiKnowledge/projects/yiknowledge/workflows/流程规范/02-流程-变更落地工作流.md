# 变更落地工作流

> 知识库变更完成后的收口流程：确保内容与规范文档同步，验证一致性，提交推送。

## 一、适用场景

当对 YiKnowledge 知识库做了修改（新增文件、修改内容、调整结构、更新元数据等），且这些修改涉及 `openspec/changes/` 下的某个变更时，必须执行此流程确保内容和文档保持同步。

## 二、流程步骤

```
内容修改完成
  │
  ▼
1. 回写 OpenSpec 产出物
  │  - 对照内容变更，更新 spec.md 中的场景描述
  │  - 更新 tasks.md，标记已完成任务并修正描述
  │  - 新增内容：在 spec 中添加 ADDED Requirements
  │  - 删除内容：从 spec 中移除对应场景或条目
  │
  ▼
2. 验证（opsx:verify <change-name>）
  │  - 检查完整性（completeness）
  │  - 检查正确性（correctness）
  │  - 检查一致性（coherence）
  │  - CRITICAL 问题必须修复
  │  - WARNING 记录但不阻塞流程
  │
  ▼
3. ⏸️ 确认卡点：是否提交并推送？
  │  - 询问用户是否继续提交推送
  │  - 用户可选择：全部提交 / 仅提交不推送 / 跳过提交
  │  - 用户可在此步骤审查验证结果后再决定
  │
  ▼
4. 提交并推送（用户确认后执行）
  │  - 内容和产出物变更一起提交
  │  - 提交信息描述实际改动内容
  │
  ▼
完成
```

## 三、回写原则

### spec 回写

内容改了什么，spec 就描述什么。决不允许 spec 和内容不一致：

| 变更类型 | 回写操作 |
|----------|----------|
| 新增文件 | 在 spec 场景中添加文件路径和描述 |
| 删除文件 | 从 spec 场景中移除对应文件 |
| 修改内容 | 更新场景的 WHEN/THEN 描述 |
| 调整目录结构 | 更新 spec 中的目录树描述 |
| 修改 frontmatter | 更新 spec 中的元数据字段说明 |

### tasks 回写

- 已完成的内容改动，在 tasks 中标记 `[x]`
- 更新任务描述使其准确反映实际实现
- 如果实现与原任务描述有偏差，修正描述而非保留旧描述

### 不回写的情况

纯格式修正或错别字修复（不涉及 spec 定义的变更）时，可以只改内容不回写 spec。判断标准：

- 修复的是已有内容的格式/错别字 → 不需要回写
- 新增/删除了知识条目 → 需要回写
- 调整了目录结构或分类 → 需要回写

## 四、验证检查项

### 完整性检查

- [ ] spec.md 中的所有场景都有对应的内容实现
- [ ] 所有新增内容都在 spec 中有对应描述
- [ ] tasks.md 中的所有任务状态正确（已完成/未完成）

### 正确性检查

- [ ] 所有文件 frontmatter 包含 8 个必需字段（title, tags, category, created, updated, source, type, status）
- [ ] 文件名使用 kebab-case，无下划线或数字
- [ ] 目录层级不超过 3 级
- [ ] 文件放在正确的角色目录和子目录中

### 一致性检查

- [ ] spec 中的文件引用与实际文件路径一致
- [ ] tags 在 spec 和 frontmatter 中一致
- [ ] 角色归属在 spec 和实际目录中一致
- [ ] 多角色覆盖使用 `roles:` 字段声明

## 五、YiKnowledge 特定检查

### 知识治理检查

- [ ] 文件状态符合生命周期阶段（draft → review → stable → deprecated → archived）
- [ ] 新文件通过了就绪检查清单（`curator/governance/readiness-checklist.md`）
- [ ] 分类标准符合 `curator/governance/classification-standards.md`
- [ ] 角色边界判定符合决策树规则

### RAG 就绪检查

- [ ] frontmatter 完整，RAG 引擎可正确索引
- [ ] 内容结构清晰，Summary → Core viewpoints → Key information 三段式
- [ ] 代码示例完整可运行，标注了语言类型
- [ ] 反模式示例包含错误/正确/原因三列

### 跨项目影响检查

- [ ] 内容变更是否影响 YiAi 的知识监视器扫描
- [ ] 目录结构调整是否影响 RAG 检索路径
- [ ] 角色边界变更是否影响知识库导航

## 六、使用方式

在 Claude Code 中执行 `/opsx:land <change-name>` 一键执行完整流程。

其他 AI 工具参考本文档手动执行：回写 → 验证 → 确认 → 提交。

## 七、示例

**场景**：在 `engineer/build/` 下新增 `vue-dark-mode-pattern.md`，描述暗色主题实现模式。

**回写操作**：
- `spec.md`：在"构建模式"场景中添加新文件路径和描述，标注 ADDED
- `tasks.md`：标记任务 2.1 完成，更新描述为实际文件名

**验证**：`opsx:verify dark-mode-pattern` → 检查 frontmatter 完整性、命名规范、角色归属 → 无 CRITICAL 问题

**确认**：用户审查验证结果，确认继续 → 提交并推送

**提交**：`feat: 新增 Vue 暗色主题实现模式文档`
