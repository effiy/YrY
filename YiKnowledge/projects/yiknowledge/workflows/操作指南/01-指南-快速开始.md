# 快速开始

> YiKnowledge 完整使用指南：查阅知识、添加知识、AI 集成、工具链配置、常见问题、故障排查。YiKnowledge 是纯 Markdown 知识库，同时服务于人类查阅和 AI RAG 检索。

## 一、环境准备

### 前置条件

| 工具 | 用途 | 安装 |
|------|------|------|
| `ripgrep` (rg) | 全文搜索，比 grep 快 10x | `brew install ripgrep` |
| `yq` | YAML frontmatter 处理 | `brew install yq` |
| `fzf` | 交互式文件搜索 | `brew install fzf` |
| Python 3.10+ | 验证脚本运行 | 系统自带或 `brew install python` |

### 可选工具

| 工具 | 用途 | 安装 |
|------|------|------|
| `bat` | 语法高亮预览 | `brew install bat` |
| `fd` | 快速文件查找 | `brew install fd` |
| `delta` | Git diff 增强 | `brew install git-delta` |
| `glow` | Markdown 终端渲染 | `brew install glow` |

### Shell 别名配置

```bash
# 添加到 ~/.zshrc 或 ~/.bashrc
alias yk="cd ~/YrY/YiKnowledge"
alias ykf="rg -l"                          # 搜索文件内容
alias ykt="rg '^tags:'"                    # 按标签搜索
alias ykc="rg '^category:'"                # 按分类搜索
alias ykh="head -20"                       # 快速预览 frontmatter
alias yks="rg '^status:'"                  # 按状态搜索
alias ykv="python3 ~/YrY/YiKnowledge/scripts/validate_knowledge.py"  # 验证文件
```

## 三、添加知识

### 完整流程

```bash
# 1. 确定角色目录（参见角色边界决策树）
#    → 业务策略、市场分析 → executiver/
#    → 产品需求、用户故事 → producter/
#    → 技术决策、架构选择 → leader/
#    → 实现模式、开发工具 → engineer/
#    → 发布流程、监控告警 → srer/
#    → AI/ML 理论、RAG → aier/
#    → KB 结构、规则 → curator/

# 2. 确定问题域子目录
ls leader/                      # decisions/ architecture/ capacity/ risk/ roadmap/

# 3. 创建文件（kebab-case，无下划线和数字）
#    ✅ leader/decisions/choose-microservices-framework.md
#    ❌ leader/decisions/01_choose_framework.md
#    ❌ leader/decisions/选择微服务框架.md

# 4. 填写 YAML frontmatter（8 个必填字段）
# 5. 编写正文（遵循统一结构：Summary → Core viewpoints → Key information → Action recommendations）
# 6. 运行验证脚本
python3 scripts/validate_knowledge.py leader/decisions/choose-microservices-framework.md

# 7. 运行就绪检查清单
cat curator/governance/readiness-checklist.md
```

### Frontmatter 模板

```yaml
---
title: 选择微服务框架
tags: [microservices, framework, decision]
category: leader/decisions
created: 2026-09-07
updated: 2026-09-07
source: internal
type: analysis
status: draft
lifecycle: active
review_cycle: quarterly
last_verified: 2026-09-07
roles: [leader, engineer]
benefit: "为微服务技术选型提供决策参考"
---
```

### 正文结构

```markdown
# 选择微服务框架

> 基于业务需求、团队能力和技术生态的微服务框架选型决策分析

## Summary
对比 Spring Cloud 和 Kubernetes 原生方案，从性能、运维成本、团队技能三个维度评估，推荐团队采用 Spring Cloud 作为主要微服务框架。

## Core viewpoints
- 观点 1：Spring Cloud 生态成熟，社区活跃，适合团队现有 Java 技术栈
- 观点 2：Kubernetes 原生方案运维复杂度高，适合已有 K8s 经验的团队
- 观点 3：混合方案可作为过渡策略，逐步迁移

## Key information
### 性能对比
| 框架 | 启动时间 | 内存占用 | 吞吐量 |
|------|----------|----------|--------|
| Spring Cloud | 5s | 256MB | 1000 req/s |
| K8s Native | 2s | 128MB | 800 req/s |

### 决策矩阵
| 维度 | 权重 | Spring Cloud | K8s Native |
|------|------|-------------|------------|
| 团队技能 | 40% | 9/10 | 4/10 |
| 运维成本 | 30% | 7/10 | 5/10 |
| 性能 | 20% | 7/10 | 8/10 |
| 生态 | 10% | 9/10 | 6/10 |

## Action recommendations
1. 采用 Spring Cloud 作为主要微服务框架
2. 搭建 Spring Cloud 脚手架项目，集成服务发现、配置中心、网关
3. 制定微服务开发规范，包括服务拆分原则和通信协议
4. 在 3 个月后评估是否需要引入 K8s 原生方案

## Anti-patterns
| 反模式 | 错误做法 | 正确做法 |
|--------|----------|----------|
| 过度拆分 | 每个功能一个服务 | 按业务边界拆分 |
| 忽视运维 | 只关注开发效率 | 同步评估运维复杂度 |

## Related links
- [微服务架构模式](../specs/microservices-patterns.md)
- [ADR-001: 使用 FastAPI](./adr-001-use-fastapi.md)
```

## 四、AI 集成

### 数据管线

```
写入 Markdown 文件
  ↓ 60s 内
YiAi Knowledge Watcher 检测到变更
  ↓ 三步处理：
  │  1. 遍历目录树，检测文件变更（新增/修改/删除）
  │  2. 解析 YAML frontmatter → 结构化元数据
  │  3. 提取正文 → 文本内容
MongoDB knowledge_files 集合更新
  ↓ llama_index 增量索引
Vector Index（data/rag_store/）更新
  ↓ 混合检索可用
RAG 检索 → Agent → 用户
```

### 优化 RAG 检索质量

| 策略 | 具体做法 | 效果 |
|------|----------|------|
| **精准标签** | tags 使用 3-5 个英文标签，避免宽泛 | 提升 BM25 关键词匹配精度 |
| **高密度 Summary** | blockquote 和 Summary 包含关键术语 | 提升向量检索相关性 |
| **benefit 字段** | 写清楚独特价值，10-200 字 | 帮助 RAG 判断内容相关性 |
| **结构化正文** | 使用 H2/H3 标题层级，表格对比 | 提升分块索引质量 |
| **关键词覆盖** | 正文中自然包含同义词和相关术语 | 覆盖更多查询方式 |
| **代码示例** | 关键实现提供代码片段 | BM25 匹配 API 名称 |

### 验证 RAG 检索效果

```bash
# 查看知识文件数
curl http://localhost:10086/knowledge/stats
# → { "total": 1234, "active": 1100, "draft": 50, "archived": 84 }

# 查看索引状态
curl http://localhost:10086/rag/status
# → { "indexed_files": 1100, "index_size_mb": 85, "last_built": "2026-09-07T10:00:00" }

# 测试 RAG 检索
curl -X POST http://localhost:10086/rag/query \
  -H "Content-Type: application/json" \
  -d '{"query": "微服务架构", "top_k": 5, "scope": "leader/"}'

# 手动触发索引重建
curl -X POST http://localhost:10086/rag/build-index
```

## 六、常见问题

### 不确定内容属于哪个角色？

参考 [角色边界决策树](../specs/role-boundaries.md#四决策树)。快速判断：

```
业务策略、市场分析、竞品研究？ → executiver/
产品需求、用户故事、优先级？   → producter/
技术决策、架构选择、ADR？      → leader/
实现模式、开发工具、代码质量？ → engineer/
发布流程、监控告警、事件响应？ → srer/
AI/ML 理论、RAG、Agent？       → aier/
KB 结构、规则、模板？          → curator/
```

### 一条知识涉及多个角色？

使用 frontmatter `roles:` 字段声明多角色，文件放在主要角色目录中：

```yaml
---
title: 微服务拆分决策
roles: [leader, engineer]     # 多角色覆盖
category: leader/decisions     # 物理位置：主要角色目录
---
```

### 如何检查内容是否过期？

```bash
# 查找 6 个月未验证的内容
rg "^last_verified: 2025" YiKnowledge -l
rg "last_verified: 2026-0[1-3]" YiKnowledge -l

# 查找已废弃的内容
rg "^status: deprecated" YiKnowledge -l

# 查找需要季度审查的内容
rg "^review_cycle: quarterly" YiKnowledge -l | while read line; do
  file=$(echo "$line" | cut -d: -f1)
  echo "$file: $(rg '^last_verified:' "$file")"
done
```

### 如何查找重复内容？

```bash
# 按标题查找可能的重复
rg "^title:.*" YiKnowledge -l | while read f; do
  echo "$f: $(rg '^title:' "$f" | head -1)"
done | sort -t: -k2 | uniq -f1 -D

# 按标签组合查找相似内容
rg "^tags:" YiKnowledge -l | xargs -I{} sh -c 'echo "{}: $(rg "^tags:" "{}")"'
```

### 如何处理大文件？

```bash
# 检查文件大小
find YiKnowledge -name "*.md" -size +1M -exec ls -lh {} \;

# 大文件拆分建议
# - 超过 100KB：拆分为多个子主题文件
# - 超过 1MB：提取核心内容，剩余内容使用外部链接
# - 超过 10MB：Knowledge Watcher 会跳过，必须拆分
```

## 八、故障排查

| 问题 | 症状 | 解决方案 |
|------|------|----------|
| RAG 搜不到新文件 | 文件已创建但检索不到 | 检查 status 是否为 `stable`（`draft` 不检索）；等待 60s Watcher 轮询周期；检查 `curl /rag/status` |
| frontmatter 验证失败 | 验证脚本报错 | 检查日期是否加引号；检查 tags 是否为英文；检查 category 格式 |
| 文件编码错误 | 中文乱码 | 确认文件编码为 UTF-8：`file -I filename.md`；转换：`iconv -f GBK -t UTF-8 file.md` |
| 目录层级过深 | 创建文件时路径超 3 级 | 合并中间层级，使用连字符分隔：`engineer/build/api/auth.md` → `engineer/build/api-auth.md` |
| 标签被 RAG 忽略 | 中文标签匹配不到 | 全部改为英文小写标签 |
| 索引构建失败 | `curl /rag/build-index` 返回错误 | 检查 Ollama 是否运行；检查 MongoDB 连接；检查磁盘空间 |
| 文件被 Watcher 跳过 | 文件存在但 MongoDB 中没有 | 检查文件大小是否超 10MB；检查文件编码是否为 UTF-8；检查 frontmatter 格式 |

## 九、约束

### 必须遵守

- 文件命名使用 kebab-case，禁止下划线和数字
- 目录层级最多 3 层（`role/problem-domain/file.md`）
- YAML frontmatter 必填（8 个字段）
- 正文遵循统一结构（4 个必填章节）
- 修改内容后更新 `updated` 字段
- 新增内容前运行验证脚本
- 新增内容前运行就绪检查清单

### 禁止

- 不使用中文文件名
- 不使用下划线或数字作为文件名前缀
- 不跳过 frontmatter 必填字段
- 不创建超过 3 级的目录层级
- 不创建空文件（只有 frontmatter 无正文）
- 不让 status 为 `draft` 或 `archived` 的文件进入 RAG 检索
