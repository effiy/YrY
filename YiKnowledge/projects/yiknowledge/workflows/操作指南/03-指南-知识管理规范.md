# 知识管理规范

> 文件命名、YAML Frontmatter 规范、内容结构、知识生命周期、RAG 优化策略、质量维度、审查流程、协作规范。所有知识文件必须遵守此规范，确保一致性和 RAG 检索精度。

## 一、文件命名

### 基本规则

| 规则 | 说明 | 正则 | 示例 |
|------|------|------|------|
| 格式 | kebab-case（小写字母 + 连字符） | `^[a-z][a-z0-9-]*[a-z0-9]$` | `implement-an-api.md` |
| 禁止 | 下划线 `_`、数字前缀、空格 | — | ❌ `01_implement_api.md` |
| 语义 | 中文语义保留在 frontmatter `title:` 中 | — | `title: 实现 API 接口` |
| 目录层级 | 最多 3 层 — `role/problem-domain/file.md` | — | `engineer/build/implement-an-api.md` |
| 动词短语 | 使用描述性的动词短语作为 slug | — | `choose-microservices-framework.md` |

### 命名示例

| 正确 | 错误 | 原因 |
|------|------|------|
| `implement-an-api.md` | `implement_an_api.md` | 禁止下划线 |
| `choose-microservices-framework.md` | `01-choose-framework.md` | 禁止数字前缀 |
| `handle-auth-failure.md` | `HandleAuthFailure.md` | 禁止大写 |
| `rag-hybrid-search.md` | `RAG混合检索.md` | 禁止中文文件名 |
| `setup-grafana-dashboard.md` | `setup-grafana.md` | 太简略，缺少语义 |
| `adr-001-use-postgres.md` | `adr-001.md` | 缺少决策主题 |
| `migrate-vue2-to-vue3.md` | `migrate-from-vue2-to-vue3.md` | 避免冗余介词 |

### 常见动词前缀

| 前缀 | 适用场景 | 示例 | 角色 |
|------|----------|------|------|
| `implement-` | 实现指南 | `implement-an-api.md` | engineer |
| `choose-` | 技术选型 | `choose-microservices-framework.md` | leader |
| `setup-` | 环境搭建 | `setup-grafana-dashboard.md` | srer |
| `handle-` | 异常处理 | `handle-auth-failure.md` | engineer |

| `optimize-` | 性能优化 | `optimize-database-queries.md` | engineer |
| `debug-` | 调试技巧 | `debug-memory-leaks.md` | engineer |
| `design-` | 设计方案 | `design-event-driven-architecture.md` | leader |
| `deploy-` | 部署指南 | `deploy-to-kubernetes.md` | srer |

### 项目文件命名

项目文档（`engineer/projects/`）遵循特定命名：

| 项目 | 前缀 | 示例 |
|------|------|------|
| YiVad | 无前缀，直接描述 | `search-form.md`, `list-page.md` |
| YiAi | 无前缀，直接描述 | `domain-service.md`, `repository.md` |
| YiPet | 无前缀，直接描述 | `chat-controller.md`, `ipc-bridge.md` |
| 跨项目 | 项目名作为前缀 | `yivad-dark-mode-prd.md` |

## 二、YAML Frontmatter 规范

### 必填字段（8 个）

| 字段 | 类型 | 说明 | 示例 | 验证规则 |
|------|------|------|------|----------|
| `title` | string | 文件标题（中文） | `"实现 API 接口"` | 非空，5-50 字符 |
| `tags` | array | 3-5 个英文小写标签 | `[api, fastapi, implementation]` | 3 ≤ len ≤ 5 |
| `category` | string | 角色/问题域分类 | `engineer/build` | 格式 `^[a-z]+/[a-z-]+$` |
| `created` | date | 创建日期 | `2026-09-07` | YYYY-MM-DD，无引号 |
| `updated` | date | 最后更新日期 | `2026-09-07` | YYYY-MM-DD，无引号 |
| `source` | string | 来源 | `internal` / `external` | 枚举值 |
| `type` | string | 内容类型 | `analysis` / `howto` / `reference` / `summary` | 枚举值 |
| `status` | string | 内容状态 | `draft` / `review` / `stable` / `deprecated` / `archived` | 枚举值 |

### 可选字段（7 个）

| 字段 | 类型 | 说明 | 示例 | 何时必填 |
|------|------|------|------|----------|
| `lifecycle` | string | 生命周期阶段 | `active` | 建议始终填写 |
| `review_cycle` | string | 审查周期 | `quarterly` | status=stable 时建议 |
| `last_verified` | date | 最后验证日期 | `2026-09-07` | status=stable 时必填 |
| `roles` | array | 适用角色 | `[leader, engineer]` | 多角色覆盖时必填 |
| `benefit` | string | 知识价值描述 | `"为微服务技术选型提供决策参考"` | 建议始终填写 |
| `acceptance_criteria` | array | 验收标准 | `["可通过 curl 调用"]` | type=howto 时建议 |
| `related` | array | 关联文件路径 | `[./related-file.md]` | 有关联文件时填写 |

### 完整模板

```yaml
---
title: 文件标题
tags: [tag1, tag2, tag3]
category: role/domain
created: YYYY-MM-DD
updated: YYYY-MM-DD
source: internal
type: analysis
status: draft
lifecycle: active
review_cycle: quarterly
last_verified: YYYY-MM-DD
roles: [role1, role2]
benefit: "简短描述"
acceptance_criteria:
  - "可验证的条款"
related:
  - relative/path/to/file.md
---
```

### 字段选择决策

```
创建文件时：
├── 来源是外部内容？ → source: external + 双文件模式
├── 涉及多个角色？   → roles: [role1, role2]
├── 是操作指南？     → type: howto + acceptance_criteria
├── 是技术分析？     → type: analysis + benefit（必填）
├── 是 API 文档？    → type: reference + review_cycle: weekly
└── 是学习笔记？     → type: summary + source 标注
```

## 三、内容结构

### 标准正文结构

每篇知识文件应遵循统一结构，确保 AI 可读性和人类可浏览性：

```markdown
# 文件标题（H1）

> 一句话概述核心内容（blockquote，高信息密度，用于 RAG 检索）

## Summary（必填）
一句话概述核心内容，包含关键术语

## Core viewpoints（必填）
- 观点 1：详细说明（含数据支撑）
- 观点 2：详细说明

## Key information（必填）
详细的技术信息、数据、配置、代码示例

## Action recommendations（必填）
具体可执行的行动建议（含命令/步骤/预期结果）

## Anti-patterns（可选）
常见错误和避免方法

## Related links（可选）
- [相关文件](./related-file.md)
- [外部参考](https://example.com)
```

### 章节内容要求

| 章节 | 最低要求 | 优秀标准 | 常见问题 |
|------|----------|----------|----------|
| blockquote | 1 句话，含核心术语 | 2-3 句，高信息密度 | 太简短如 "这是一个文档" |
| Summary | 1 句话概述 | 2-3 句，含关键词和结论 | 与 blockquote 完全重复 |
| Core viewpoints | 至少 2 个观点 | 3-5 个观点，每个有数据支撑 | 观点无数据，纯主观 |
| Key information | 至少 1 个表格或代码块 | 多维度信息（表格+代码+配置+数据） | 只有文字描述，无可直接引用的数据 |
| Action recommendations | 至少 1 个可执行建议 | 3-5 个建议，含命令/步骤 | 建议太通用如 "建议使用" |
| Anti-patterns | 至少 2 个反模式 | 4-6 个，含错误示例+正确做法+原因 | 只有错误示例，无正确做法 |
| Related links | 至少 1 个关联链接 | 3-5 个，内部+外部组合 | 只有外部链接，无内部关联 |

### 内容质量维度

| 维度 | 权重 | 要求 | 检查方法 |
|------|------|------|----------|
| 准确性 | 30% | 信息经过验证，有数据支撑 | 交叉验证、引用来源 |
| 完整性 | 25% | 覆盖核心观点、关键信息、行动建议 | 正文结构检查（4 个必填章节） |
| 可操作性 | 20% | 行动建议具体可执行 | 是否包含命令/代码/步骤 |
| 时效性 | 15% | `last_verified` 在 6 个月内 | 日期检查 |
| 独特性 | 10% | 不与已有内容重复 | 标题/tags 去重检查 |

### 内容格式规范

| 元素 | 规范 | 示例 |
|------|------|------|
| 标题层级 | H1（文件标题）→ H2（章节）→ H3（子主题） | `# Title` → `## Summary` → `### Detail` |
| 代码块 | 使用语言标记，不省略 | ` ```python ` 而非 ` ``` ` |
| 表格 | 对齐管道符，表头加粗 | `\| Column \| Desc \|` |
| 链接 | 内部用相对路径，外部用完整 URL | `[file](./file.md)` |
| 列表 | 无序列表用 `-`，有序列表用 `1.` | 统一列表符号 |
| 强调 | 关键术语用 `**粗体**`，文件路径用 `` `反引号` `` | `**重要**` |
| 图片 | 使用相对路径，放在 `diagrams/` 目录 | `![arch](./diagrams/arch.png)` |

## 四、知识生命周期

### 生命周期状态机

```
inbox → triage → active → reference → archive
  ↓        ↓        ↓         ↓          ↓
 新入库   分类中   活跃使用   参考归档   已废弃
(status:  (status:  (status:  (status:   (status:
 draft)   review)   stable)   deprecated) archived)
```

### 生命周期阶段详解

| 阶段 | status | lifecycle | 触发条件 | 操作 | RAG 检索 |
|------|--------|-----------|----------|------|----------|
| `inbox` | `draft` | `inbox` | 新建文件 | 作者填写 frontmatter + 正文 | 不检索 |
| `triage` | `review` | `triage` | 提交 curator 审核 | curator 验证分类、tags、结构 | 不检索 |
| `active` | `stable` | `active` | curator 审核通过 | 定期 review，保持新鲜度 | 正常检索 |
| `reference` | `stable` | `reference` | 不再频繁更新 | 降低 review_cycle 为 yearly | 正常检索 |
| `deprecated` | `deprecated` | `reference` | 6 个月未验证 | 标记为 deprecated | 降低权重 |
| `archived` | `archived` | `archive` | curator 归档 | 移入 curator/archive/ | 不检索 |

### 状态转换规则

```
draft ──→ review      作者提交审核
review ──→ stable     curator 审核通过
review ──→ draft      curator 退回修改
stable ──→ deprecated 6 个月未验证 或 内容过时
stable ──→ review     内容需要重新审核
deprecated ──→ stable 内容重新验证通过
deprecated ──→ archived curator 归档
```

### 审查周期选择

| 周期 | 适用内容 | 过期阈值 | 典型文件 |
|------|----------|----------|----------|
| `weekly` | 快速变化的 API 文档、配置 | 2 周 | API 端点文档 |
| `monthly` | 开发实践、工具链、依赖 | 2 月 | 构建配置、lint 规则 |
| `quarterly` | 架构决策、方法论、模式 | 6 月 | ADR、架构模式 |
| `yearly` | 基础理论、行业分析 | 18 月 | 设计原则、安全基础 |

## 五、RAG 优化策略

### 提升检索质量的 7 个技巧

1. **精准标签** — tags 使用 3-5 个具体英文标签，避免过于宽泛
   - ❌ `tags: [tech, code]` → 无区分度
   - ✅ `tags: [fastapi, middleware, auth, jwt]` → 精准匹配

2. **高密度 Summary** — blockquote 和 Summary 章节提供高信息密度
   - ❌ `> 这是一个 API 文档`
   - ✅ `> FastAPI 中间件认证实现，支持 JWT + bcrypt，包含 Token 刷新和权限校验`

3. **结构化正文** — 使用清晰的 H2/H3 标题层级，每个 H2 是独立语义单元
   - 每个 H2 章节控制在 200-400 tokens，确保分块边界与章节边界对齐

4. **benefit 字段** — 写清楚知识的独特价值，帮助 RAG 判断相关性
   - ❌ 空
   - ✅ `"为微服务框架选型提供完整决策依据，包含性能对比和迁移成本评估"`

5. **关键词覆盖** — 正文中自然包含同义词和相关术语
   - 写 "认证" 时同时提及 "auth"、"authentication"、"login"、"token"、"JWT"

6. **表格数据** — 对比信息使用表格，向量检索对结构化数据更敏感

7. **代码示例** — 关键实现提供代码片段，BM25 可匹配 API 名称

### 检索信号映射

| Frontmatter 字段 | 检索信号 | 权重 | 索引方式 |
|------------------|----------|------|----------|
| `title` | 标题向量匹配 | 高 | VectorStoreIndex |
| `tags` | BM25 关键词精确匹配 | 高 | BM25 索引 |
| `category` | Scope 过滤 | 中 | MongoDB `$regex` |
| `benefit` | 相关性评估 | 中 | LLM Rerank 输入 |
| `status` | 内容过滤 | — | MongoDB `$nin` |
| `roles` | 角色过滤 | 低 | MongoDB `$in` |
| 正文 `content` | 全文向量 + BM25 | 高 | VectorStoreIndex + BM25 |

### 反模式

| 反模式 | 问题 | 影响 | 改进 |
|--------|------|------|------|
| tags 过于宽泛 | `[tech, code]` 无区分度 | BM25 匹配噪音大 | `[fastapi, middleware, auth]` |
| Summary 过于简短 | "这是一个 API 文档" | 向量检索相关性低 | "FastAPI 中间件认证实现，支持 JWT + bcrypt" |
| 正文无标题层级 | 大段文字无 H2/H3 | 分块索引质量差 | 使用 H2/H3 组织内容 |
| benefit 为空 | 不填写知识价值 | RAG 无法判断相关性 | 填写具体的知识价值 |
| 中文标签 | `[API, 认证]` | BM25 匹配精度低 | 全部使用英文标签 |
| 日期加引号 | `"2026-09-07"` | YAML 类型错误 | 去掉引号 |
| 不更新 updated | 修改后不更新日期 | 新鲜度检测失效 | 每次修改后更新 |

## 六、协作规范

### 审查流程

```
1. 作者创建文件（status: draft）
   ↓
2. 作者自检（运行验证脚本 + 就绪检查清单）
   ↓
3. 提交审核（status: review）
   ↓
4. curator 审核（分类、tags、结构、质量）
   ↓
5. 审核通过（status: stable）或 退回修改（status: draft）
   ↓
6. 定期审查（按 review_cycle 自动提醒）
```

### 审核清单

- [ ] 文件命名符合 kebab-case 规范
- [ ] 目录层级不超过 3 级
- [ ] 8 个必填 frontmatter 字段完整
- [ ] tags 使用 3-5 个英文小写标签
- [ ] category 使用 `role/domain` 格式
- [ ] 日期无引号，格式 YYYY-MM-DD
- [ ] 正文包含 4 个必填章节
- [ ] benefit 字段填写了具体价值
- [ ] 文件编码为 UTF-8
- [ ] 文件大小不超过 10MB
- [ ] 内容不与已有文件重复
- [ ] 角色归属正确（参考角色边界决策树）

### 分支命名

| 类型 | 格式 | 示例 |
|------|------|------|
| 新增知识 | `knowledge/<slug>` | `knowledge/choose-microservices-framework` |
| 更新知识 | `update/<slug>` | `update/api-endpoints` |
| 修复错误 | `fix/<slug>` | `fix/frontmatter-dates` |
| 批量操作 | `batch/<description>` | `batch/migrate-chinese-tags` |

### 提交信息格式

```bash
# 新增知识
docs(leader): add microservices framework selection ADR

# 更新知识
docs(engineer): update API implementation guide with FastAPI 0.100 changes

# 修复错误
fix(engineer): correct frontmatter date format in build docs

# 归档
docs(curator): archive deprecated Vue 2 migration guide
```

## 七、约束

### 必须遵守

- 文件命名使用 kebab-case，禁止下划线和数字
- 目录层级最多 3 层（`role/problem-domain/file.md`）
- YAML frontmatter 8 个必填字段完整
- 正文遵循统一结构（4 个必填章节）
- 每条知识属于唯一角色目录，多角色用 `roles:` 字段声明
- 修改内容后更新 `updated` 字段
- 外部内容使用双文件模式（`*-original.md` + `*-summary.md`）
- 新增内容前运行验证脚本和就绪检查清单
- status=stable 时必须填写 `last_verified`
- 文件编码为 UTF-8，换行符为 LF

### 禁止

- 不使用中文文件名
- 不使用下划线或数字作为文件名前缀
- 不使用中文 frontmatter key
- 不使用中文标签
- 不跳过 frontmatter 必填字段
- 不创建超过 3 级的目录层级
- 不创建空文件（只有 frontmatter 无正文）
- 不将文件放在错误的角色目录中
- 不让 status 为 `draft` 或 `archived` 的文件进入 RAG 检索
- 不创建超过 10MB 的文件
