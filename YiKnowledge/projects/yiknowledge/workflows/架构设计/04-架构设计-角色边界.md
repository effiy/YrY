## 二、角色责任链

角色在流水线中不是平级的，有明确的上游/下游关系：

```
executiver ──→ producter ──→ leader ──→ engineer ──→ srer
  (why)         (what)       (which)     (how)       (run)

  Business       Product      Tech        Impl        Ops
  strategy       requirements decisions   patterns    procedures
```

### 上下游依赖

| 角色 | 上游依赖 | 下游消费者 |
|------|----------|-----------|
| executiver | 市场数据、财报 | producter（战略方向） |
| producter | executiver（战略方向） | leader（PRD、用户故事） |
| leader | producter（PRD、用户故事） | engineer（ADR、技术方案） |
| engineer | leader（ADR、技术方案） | srer（代码、架构文档） |
| srer | engineer（代码、架构文档） | executiver（运营数据反馈） |
| aier | 所有角色（AI 需求） | 所有角色（AI 方法论） |
| curator | 所有角色（内容产出） | 所有角色（知识库结构） |

## 三、Chip 契约

每个管道阶段有明确的 Input chips（从上游消费）和 Output chips（为下游产出）：

| 阶段 | 角色 | Input Chips | Output Chips | 交付格式 |
|------|------|-------------|--------------|----------|
| 0. 战略 | executiver | 市场数据、财报、行业趋势 | 战略方向、优先级、组织目标 | 战略文档、OKR |
| 1. 需求 | producter | 战略方向、用户反馈 | PRD、用户故事、验收标准 | PRD 文档、用户故事卡片 |
| 2. 决策 | leader | PRD、用户故事 | ADR、技术方案、容量评估 | ADR 文档、架构图 |
| 3. 构建 | engineer | ADR、技术方案 | 代码、架构文档、测试用例 | 代码仓库、API 文档 |
| 4. 发布 | srer | 代码、架构文档 | 发布计划、回滚方案 | 发布清单、部署配置 |
| 5. 运营 | srer | 监控数据、用户反馈 | 事件记录、优化建议 | 事故报告、优化方案 |

### Chip 契约示例

```markdown
# 从 producter 到 leader 的 Chip 传递

## Input Chips（producter 产出）
- PRD: yivad-dark-mode-prd.md
  - 核心功能：暗色主题切换
  - 验收标准：一键切换，持久化偏好
  - 优先级：P1

## Output Chips（leader 产出）
- ADR: adr-003-dark-mode-implementation.md
  - 决策：使用 CSS Variables + Pinia 状态管理
  - 备选方案：Tailwind dark mode（已拒绝：增加构建复杂度）
  - 容量评估：无需额外后端资源
```

## 五、高频边界冲突

这些是实际中出现过的分类争议，按此规则解决：

| 冲突 | 归属 | 判定规则 |
|------|------|----------|
| 架构决策 vs 架构模式 | 决策 → leader/，模式 → engineer/ | 决策 = 为什么选 A 不选 B（含备选方案对比）；模式 = A 怎么实现（含代码示例） |
| 安全加固 vs 安全策略 | 加固 → engineer/ship/，策略 → leader/risk/ | 加固 = 代码层面实现（如 CSP 配置）；策略 = 组织层面规范（如安全审查流程） |
| 事件响应 vs 风险预防 | 响应 → srer/，预防 → leader/risk/ | 时间线区分：事发中归 srer，事发前/后归 leader |
| 技术选型 vs 技术实现 | 选型 → leader/decisions/，实现 → engineer/build/ | 选型 = 选什么（含对比分析）；实现 = 怎么用（含代码示例） |
| 产品指标 vs 技术指标 | 产品指标 → producter/，技术指标 → srer/observability/ | 产品指标 = 用户价值；技术指标 = 系统质量 |
| 部署配置 vs 开发工具 | 部署 → srer/release/，工具 → engineer/build/ | 部署 = 生产环境配置；工具 = 开发环境配置 |
| AI 方法论 vs AI 实现 | 方法论 → aier/methodology/，实现 → engineer/build/ | 方法论 = 通用 RAG/Agent 模式；实现 = 具体项目的 AI 集成 |

### 边界冲突示例

```markdown
# 场景：一篇关于 JWT 认证的文章

问题：属于 leader/decisions/ 还是 engineer/build/？

分析：
- 如果重点是"为什么选 JWT 而不是 Session" → leader/decisions/
- 如果重点是"如何在 FastAPI 中实现 JWT" → engineer/build/

判定：看内容重心——决策对比还是实现细节
```

## 六、多角色覆盖

当一条知识涉及多个角色时，使用 frontmatter `roles:` 字段声明，不改变文件物理位置：

```yaml
---
title: 微服务拆分决策
roles: [leader, engineer]    # 多角色覆盖声明
category: leader/decisions    # 物理位置：主要角色目录
tags: [microservices, architecture, decision]
---

# 微服务拆分决策

## Summary
本文档记录微服务拆分的技术决策，涉及 leader（决策）和 engineer（实现）两个角色。

## Core viewpoints
- 按业务边界拆分，非按技术层拆分
- 每个微服务拥有独立数据库
- 服务间通过 RPC 通信

## Key information
### 对 leader 的关键信息
- 决策依据：业务边界清晰，团队结构匹配
- 风险评估：分布式事务复杂度增加

### 对 engineer 的关键信息
- 实现模式：Domain Service + Repository
- 通信协议：RPC 信封（module_name.method_name）
```

### roles 字段使用规则

| 规则 | 说明 |
|------|------|
| 物理位置 | 文件始终放在主要角色目录中 |
| roles 声明 | 在 frontmatter 中声明所有适用角色 |
| 内容覆盖 | 正文中为每个角色提供针对性信息 |
| 检索影响 | RAG 可按 `roles` 字段过滤内容 |

## 八、反模式

| 反模式 | 错误示例 | 正确做法 | 原因 |
|--------|----------|----------|------|
| 文件放错角色 | 架构模式放在 `leader/architecture/` | 架构模式放在 `engineer/build/` | leader 关注决策，engineer 关注实现 |
| 多角色文件不声明 roles | 内容涉及 leader + engineer 但不声明 | frontmatter 添加 `roles: [leader, engineer]` | RAG 无法跨角色检索 |
| 创建重复角色内容 | 同一主题在多个角色目录中重复 | 放在主要角色，用 roles 声明覆盖 | 维护成本翻倍，内容不一致 |
| 角色目录无索引 | 角色目录下没有 INDEX.md | 创建 INDEX.md 列出所有子目录和关键文件 | 导航困难 |
| 边界冲突时创建新目录 | 不确定时创建 `misc/` 或 `other/` | 使用决策树判定，或标记 `review` 状态等待 curator 审核 | 分类混乱 |

## 九、约束

### 必须遵守

- 每条知识属于唯一角色目录（物理位置）
- 多角色覆盖使用 frontmatter `roles:` 字段声明
- 边界冲突按判定规则解决，不创建模糊分类
- 每个角色目录应有 INDEX.md 索引文件
- 为每个角色在正文中提供针对性信息

### 禁止

- 不将同一文件放在多个角色目录中
- 不创建 `misc/`、`other/` 等模糊分类目录
- 不绕过决策树自行判定角色归属
- 不在 frontmatter 中省略 `roles` 字段（当内容涉及多角色时）

## 十一、多角色内容覆盖策略

### 何时使用 roles 字段

```yaml
# 场景 1：技术决策涉及实现指导
---
title: 选择 FastAPI 作为 Web 框架
roles: [leader, engineer]  # leader 关注决策，engineer 关注实现
category: leader/decisions
tags: [fastapi, python, web-framework, decision]
---

## Summary
选择 FastAPI 作为 YiAi 的 Web 框架。

## 对 leader 的关键信息
- 决策依据：原生 async/await、自动 OpenAPI、类型安全
- 备选方案：Django REST（同步阻塞）、Flask（无内置验证）
- 风险评估：FastAPI 生态较新，长期维护需关注

## 对 engineer 的关键信息
- 实现模式：Domain Service + Repository 分层
- 路由注册：使用 APIRouter + include_router
- 中间件：CORS → Observer → Auth（按顺序注册）
```

### 多角色内容模板

```markdown
---
title: <标题>
roles: [<角色1>, <角色2>]
category: <主要角色>/<子目录>
---

## Summary
<一句话概述，覆盖所有角色关注点>

## Core viewpoints
<核心观点，覆盖所有角色>

## 对 <角色1> 的关键信息
<角色1 专属的决策依据、评估标准、风险考量>

## 对 <角色2> 的关键信息
<角色2 专属的实现模式、操作步骤、代码示例>

## Action recommendations
<跨角色行动建议>
```

### roles 字段最佳实践

| 实践 | 说明 | 示例 |
|------|------|------|
| 最多 3 个角色 | 超过 3 个角色说明内容过于宽泛 | `roles: [leader, engineer]` |
| 主要角色为物理位置 | 物理位置与主要角色一致 | `category: leader/decisions` |
| 为每个角色写专属段落 | 不同角色关注不同信息 | "对 leader 的关键信息" |
| RAG 友好 | roles 字段帮助 RAG 按角色过滤 | `rag_query("FastAPI", scope="leader/")` |

## 十二、角色成长路径

### 从初级到高级的知识消费路径

```
executiver（战略思维）
  ↑
leader（决策能力）
  ↑
engineer（实现能力）→ srer（运维能力）
  ↑
producter（产品思维）
  ↑
aier（AI 赋能 — 横向加速）
```

### 角色学习路径

| 角色 | 新人入门 | 进阶 | 专家 |
|------|----------|------|------|
| executiver | 行业分析、竞品研究 | 战略规划、OKR 制定 | 组织变革、文化塑造 |
| producter | PRD 模板、用户故事 | 优先级排序、路线图 | 产品策略、数据驱动决策 |
| leader | ADR 模板、技术选型 | 架构设计、容量规划 | 技术战略、组织级架构 |
| engineer | 编码规范、开发工具 | 架构模式、性能优化 | 领域建模、系统设计 |
| srer | 监控工具、部署流程 | 故障排查、容量规划 | 混沌工程、SRE 文化 |
| aier | AI 基础概念、Prompt 工程 | RAG/Agent 方法论 | 模型训练、AI 系统设计 |

## 十三、角色目录健康检查

### 健康指标

| 指标 | 健康标准 | 检查方法 |
|------|----------|----------|
| INDEX.md 覆盖率 | 100% 角色目录有 INDEX.md | `ls */INDEX.md` |
| 文件分类正确率 | 95%+ 文件在正确的角色目录 | 随机抽查 10% |
| 空目录数 | 0 | `find . -type d -empty` |
| 重复内容率 | < 5% | 定期审查 tags 重叠 |
| 归档及时性 | 90 天内更新 | `rg "^updated: 2025" -l` |

### 检查命令

```bash
# 检查所有角色目录是否有 INDEX.md
for dir in executiver producter leader engineer srer aier curator; do
  [ -f "$dir/INDEX.md" ] && echo "$dir: OK" || echo "$dir: MISSING INDEX.md"
done

# 检查空目录
find YiKnowledge -type d -empty

# 检查过期文件（6 个月未更新）
rg "^updated: 2025" YiKnowledge -l

# 检查文件分类（按 category 统计）
rg "^category:" YiKnowledge --no-line-number | sort | uniq -c | sort -rn
```

## 十四、与其他知识库的关系

### 角色目录 vs 项目目录

| 维度 | 角色目录（executiver/等） | 项目目录（engineer/projects/） |
|------|--------------------------|-------------------------------|
| 内容 | 通用方法论、最佳实践 | 项目特定文档 |
| 粒度 | 角色级别 | 项目级别 |
| 复用性 | 跨项目复用 | 项目特定 |
| 示例 | `rag-best-practices.md` | `yiai/architecture/api.md` |

### 何时放在角色目录 vs 项目目录

```
问题是"这个角色怎么做 X"？
  → 角色目录（如 engineer/build/implement-an-api.md）

问题是"YiAi 的 API 怎么设计"？
  → 项目目录（如 engineer/projects/yiai/architecture/api.md）
```

### 跨项目知识流

```
角色目录（通用方法）
  │ 指导
  ▼
项目目录（项目文档）
  │ 实践反馈
  ▼
角色目录（方法更新）
```
