# YiKnowledge 架构概览

> 软件交付流水线、8 角色体系、知识管线、AI 检索集成、知识治理、设计原则的完整概览。YiKnowledge 是纯 Markdown 知识库，同时服务于人类（文档查阅）和 AI（YiAi Agent 的 RAG 数据源）。

## 一、技术定位

| 属性 | 值 |
|------|-----|
| 项目类型 | Markdown 知识库 |
| 文件格式 | Markdown + YAML Frontmatter |
| 文件数量 | 1000+ |
| 角色目录 | 8 个（executiver, producter, leader, engineer, srer, aier, curator, projects） |
| 目录层级 | 最多 3 级（`role/problem-domain/file.md`） |
| 文件命名 | kebab-case，禁止下划线和数字 |
| 消费者 | 人类（文档查阅）+ AI（YiAi RAG 数据源） |
| 同步机制 | YiAi Knowledge Watcher（apscheduler 每 5s 轮询） |
| 检索方式 | 混合检索（向量相似度 + BM25 关键词）+ 可选 LLM Rerank |

### 与 YiAi 的关系

```
YiKnowledge（Markdown 文件树）
  │ apscheduler 每 5s 轮询
  ▼
YiAi Knowledge Watcher（src/domain/knowledge/watcher.py）
  │ 解析 YAML frontmatter + 正文
  ▼
MongoDB knowledge_files 集合
  │ llama_index VectorStoreIndex
  ▼
RAG 混合检索 → YiAi Agent → 用户
```

YiKnowledge 不包含任何代码逻辑——它是纯数据。所有处理（扫描、解析、索引、检索）由 YiAi 后端的 Knowledge Watcher 和 RAG 引擎完成。

## 二、软件交付流水线

```
                    ┌──────────────────────────────────┐
                    │  Business Strategy (executiver/)  │
                    │  Why: market, competition, goals  │
                    └──────────────────────────────────┘
                                      ↓
  ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
  │ 1. 需求   │ → │ 2. 决策   │ → │ 3. 设计构建│ → │ 4. 质量发布│ → │ 5. 运营学习│
  │ producter │    │ leader   │    │ engineer  │    │ srer      │    │ srer      │
  │ What      │    │ Which    │    │ How       │    │ Ship      │    │ Run       │
  └──────────┘    └──────────┘    └──────────┘    └──────────┘    └──────────┘
       ↑               ↑               ↑               ↑               ↑
       └───────────────┴───────────────┴───────────────┴───────────────┘
                    ┌──────────────────────────────────┐
                    │  AI Enablement (aier/)            │
                    │  How to accelerate with AI        │
                    └──────────────────────────────────┘
```

### 阶段 Chip 契约

每个阶段有明确的输入和产出：

| 阶段 | 角色 | Input Chips | Output Chips |
|------|------|-------------|--------------|
| 0. 战略 | executiver | 市场数据、财报、行业趋势 | 战略方向、优先级、组织目标 |
| 1. 需求 | producter | 战略方向、用户反馈 | PRD、用户故事、验收标准 |
| 2. 决策 | leader | PRD、用户故事 | ADR、技术方案、容量评估 |
| 3. 构建 | engineer | ADR、技术方案 | 代码、架构文档、测试用例 |
| 4. 发布 | srer | 代码、架构文档 | 发布计划、回滚方案 |
| 5. 运营 | srer | 监控数据、用户反馈 | 事件记录、优化建议 |

> Chip 契约确保上下游角色对彼此的产出有明确预期，减少沟通成本。

## 四、3 层架构

### 业务战略层（executiver/）

贯穿整个管道的商业上下文。提供市场分析、竞争策略、组织目标等战略视角，为下游所有角色提供方向性指导。

**关键文件**：
- `strategy/` — 企业战略文档
- `industry/` — 行业趋势分析
- `roadmap/` — 组织级路线图
- `reading-list/` — 管理者推荐阅读

### 管道执行层（producter/ → leader/ → engineer/ → srer/）

软件交付的核心流程，从需求到运营的完整链路。每个阶段有明确的 Chip 契约（输入/输出）。

### AI 赋能层（aier/）

AI 不是独立的管道阶段，而是渗透每个阶段的加速器：
- `foundations/` — AI 基础理论（Transformer、Attention、Embedding）
- `methodology/` — RAG/Agent 方法论、Prompt Engineering
- `platform/` — 向量库选型、嵌入模型对比
- `ml/` — 传统机器学习（分类、回归、聚类）

### 知识治理层（curator/）

元层，不产出领域知识，维护知识库的结构和健康：
- `governance/` — 生命周期管理、就绪检查清单、分类标准
- `diagrams/` — 架构图和流程图
- `templates/` — 文档模板（知识条目、ADR、PRD）
- `archive/` — 已归档内容

## 六、知识管线（AI 检索集成）

```
YiKnowledge（Markdown 文件树，1000+ 文件）
  ↓ apscheduler 每 5s 轮询
YiAi Knowledge Watcher（src/domain/knowledge/watcher.py）
  ↓ 三步处理：
  │  1. 遍历目录树，检测文件变更（新增/修改/删除）
  │  2. 解析 YAML frontmatter → 结构化元数据
  │  3. 提取正文 → 文本内容
MongoDB knowledge_files 集合
  ↓ llama_index 索引构建（VectorStoreIndex + BM25）
Vector Index（data/rag_store/）
  ↓ 混合检索：向量相似度 + BM25 关键词
  ↓ 可选增强：LLM Rerank + HyDE + Sentence Window
  ↓ 内联引用编号 [Source 1], [Source 2], ...
RAG 查询 → YiAi Agent → 用户
```

### 检索策略详解

| 策略 | 原理 | 配置 | 适用场景 |
|------|------|------|----------|
| 混合检索 | 向量相似度 + BM25 关键词，权重可配置 | `rag.hybrid_search: true` | 通用检索 |
| LLM Rerank | 二阶段重排序，提升 Top-K 精度 | `rag.use_rerank: false` | 高精度需求 |
| HyDE | 用 LLM 生成假设文档再检索 | `rag.use_hyde: true` | 短查询增强 |
| Sentence Window | 检索句子级片段，返回周围窗口 | `rag.chunk_size: 512` | 上下文保留 |
| Scope 过滤 | 文件级和文件夹级 scope 限定 | `scope` 参数 | 按角色/目录检索 |
| 内联引用 | 自动添加 `[Source N]` 引用编号 | `rag.use_citations: true` | 可追溯性 |

### 关键配置

```yaml
# YiAi config.yaml
rag:
  embed_model: "nomic-embed-text"   # Embedding 模型
  chunk_size: 512                    # 分块大小（tokens）
  chunk_overlap: 50                  # 分块重叠（tokens）
  top_k: 5                           # 返回片段数
  hybrid_search: true                # 混合检索开关
  use_rerank: false                  # LLM Rerank 开关
  use_hyde: true                     # HyDE 增强开关
  use_sentence_window: true          # Sentence Window 开关
  use_citations: true                # 内联引用开关

knowledge:
  base_dir: "../YiKnowledge"         # 知识库根目录
  watcher_enabled: true              # 是否启用监视器
  watcher_poll_seconds: 60           # 轮询间隔（秒）
```

> 详细 RAG 集成架构见 [rag-integration.md](./架构设计/05-RAG检索引擎集成.md)。

## 七、Frontmatter 作为检索信号

每个知识文件的 YAML frontmatter 被 Knowledge Watcher 解析为结构化检索信号。字段质量直接影响 RAG 检索精度：

```yaml
---
title: 微服务架构选型决策              # 标题向量匹配（高权重）
tags: [microservices, architecture, decision]  # BM25 关键词（高权重）
category: leader/decisions             # Scope 过滤（中权重）
status: stable                         # 内容过滤（draft 不检索）
roles: [leader, engineer]             # 角色过滤（低权重）
benefit: "为微服务框架选型提供完整决策依据，包含性能对比和迁移成本评估"
---
```

### 字段 → 检索信号映射

| Frontmatter 字段 | 检索信号 | 权重 | 说明 |
|------------------|----------|------|------|
| `title` | 标题向量 | 高 | 标题与查询的语义相似度 |
| `tags` | BM25 关键词 | 高 | 标签与查询关键词的精确匹配 |
| `category` | Scope 过滤 | 中 | 分类限定检索范围 |
| `benefit` | 相关性评估 | 中 | 帮助判断内容与查询的相关性 |
| `status` | 内容过滤 | — | `draft`/`archived` 不检索 |
| `roles` | 角色过滤 | 低 | 按角色筛选内容 |
| 正文 `content` | 正文向量 + BM25 | 高 | 全文检索 |

> 详细 Frontmatter 规范见 [./frontmatter.md](./开发规范/02-Frontmatter模式.md)。

## 八、知识生命周期

```
inbox → triage → active → reference → archive
  ↓        ↓        ↓         ↓          ↓
 新入库   分类中   活跃使用   参考归档   已废弃
```

### 生命周期阶段

| 阶段 | 含义 | 对应 status | 触发条件 |
|------|------|------------|----------|
| `inbox` | 新入库，待分类 | `draft` | 新建文件 |
| `triage` | 分类中，待审核 | `review` | curator 审核 |
| `active` | 活跃使用中 | `stable` | 审核通过 |
| `reference` | 参考归档 | `stable` | 不再频繁更新 |
| `archive` | 已废弃 | `deprecated` / `archived` | 6 个月未验证 |

### 新鲜度维护

```bash
# 查找 6 个月未验证的内容
rg "^last_verified: 2025" YiKnowledge -l

# 查找已废弃的内容
rg "^status: deprecated" YiKnowledge -l

# 查找需要季度审查的内容
rg "^review_cycle: quarterly" YiKnowledge -l
```

## 十、设计原则

### 1. 角色优先，边界清晰

每条知识属于唯一角色目录。多角色覆盖用 frontmatter `roles:` 字段声明，不改变文件物理位置：

```yaml
---
title: 微服务拆分决策
roles: [leader, engineer]  # 跨角色覆盖
category: leader/decisions  # 物理位置：leader/
---
```

### 2. 描述性文件名

使用 kebab-case 动词短语 slug，中文语义保留在 frontmatter `title:` 中：

| 正确 | 错误 | 原因 |
|------|------|------|
| `implement-an-api.md` | `implement_an_api.md` | 禁止下划线 |
| `choose-microservices-framework.md` | `01-choose-framework.md` | 禁止数字前缀 |
| `rag-hybrid-search.md` | `RAG混合检索.md` | 禁止中文文件名 |

### 3. 外部内容双文件

`*-original.md`（源文件）+ `*-summary.md`（合成）模式：
- 原始文件用于引用追溯
- 摘要文件用于 RAG 检索（结构化、高信息密度）

### 4. YAML Frontmatter 必填

8 个必填字段 + 7 个可选字段，作为 RAG 检索信号：

```yaml
# 必填
title, tags, category, created, updated, source, type, status

# 可选
lifecycle, review_cycle, last_verified, roles, benefit, acceptance_criteria, related
```

### 5. 统一正文结构

每篇知识文件遵循统一结构，提升 AI 可读性：

```markdown
## Summary              # 一句话概述
## Core viewpoints      # 核心观点
## Key information      # 详细信息和数据
## Action recommendations # 具体行动建议
## Anti-patterns        # 常见错误（可选）
## Related links        # 关联文件（可选）
```

### 6. 新鲜度标记

`last_verified` + `review_cycle` 字段确保内容时效性。6 个月未验证自动标记 `deprecated`。

### 7. 最多 3 层目录

`role/problem-domain/file.md` 的 3 层结构在导航便利性和分类粒度之间取得平衡。更深层级会降低 AI 检索效率（路径过长稀释语义信号）。

### 8. Chip 契约

每个管道阶段有明确的 Input chips（从上游消费）和 Output chips（为下游产出），确保上下游角色对彼此的产出有明确预期。

## 十一、内容质量维度

| 维度 | 要求 | 检查方法 |
|------|------|----------|
| 准确性 | 信息经过验证，有数据支撑 | 交叉验证、引用来源 |
| 完整性 | 覆盖核心观点、关键信息、行动建议 | 正文结构检查 |
| 可操作性 | 行动建议具体可执行 | 是否包含命令/代码/步骤 |
| 时效性 | `last_verified` 在 6 个月内 | 日期检查 |
| 独特性 | 不与已有内容重复 | 标题/tags 去重检查 |
| RAG 友好 | 高信息密度 Summary + 精准 tags | RAG 检索质量评估 |

---

## 十二、反模式

| 反模式 | 错误示例 | 正确做法 | 原因 |
|--------|----------|----------|------|
| 中文文件名 | `RAG混合检索.md` | `rag-hybrid-search.md` | grep/URL 兼容性差 |
| 文件名含下划线 | `implement_api.md` | `implement-an-api.md` | 不符合 kebab-case 规范 |
| 跳过 frontmatter | 文件没有 `---` 分隔符 | 始终包含 8 个必填字段 | RAG 无法检索 |
| 中文标签 | `tags: [API, 认证]` | `tags: [api, auth]` | BM25 英文匹配更精准 |
| 标签过于宽泛 | `tags: [tech, code]` | `tags: [fastapi, middleware, auth]` | 无区分度，检索噪音 |
| 日期加引号 | `created: "2026-09-07"` | `created: 2026-09-07` | YAML 解析为字符串 |
| category 缺少层级 | `category: engineer` | `category: engineer/build` | Scope 过滤粒度太粗 |
| 忘记更新 updated | 修改内容后不更新日期 | 每次修改后更新 `updated` | 新鲜度检测失效 |
| 不写 benefit | benefit 字段为空 | 填写具体的知识价值 | RAG 无法判断相关性 |
| 超过 3 层目录 | `engineer/build/api/fastapi/auth.md` | `engineer/build/fastapi-auth.md` | 路径过长稀释语义 |
| 正文无结构 | 大段文字无标题 | 使用 H2/H3 组织内容 | AI 分块索引质量差 |

## 十三、关键约束

### 必须遵守

- 文件命名使用 kebab-case，禁止下划线和数字
- 目录层级最多 3 层（`role/problem-domain/file.md`）
- YAML frontmatter 必填（8 个字段：`title, tags, category, created, updated, source, type, status`）
- 正文遵循统一结构（Summary → Core viewpoints → Key information → Action recommendations）
- 每条知识属于唯一角色目录，多角色用 `roles:` 字段声明
- 修改内容后更新 `updated` 字段
- 外部内容使用双文件模式（`*-original.md` + `*-summary.md`）
- 新增内容前运行[就绪检查清单](../../curator/governance/readiness-checklist.md)

### 禁止

- 不包含代码（纯文档/知识，代码示例除外）
- 不超过 3 级目录层级
- 不在 frontmatter 中使用中文 key
- 不使用中文文件名
- 不使用下划线或数字作为文件名
- 不跳过就绪检查清单
- 不创建空文件或不完整的 frontmatter
