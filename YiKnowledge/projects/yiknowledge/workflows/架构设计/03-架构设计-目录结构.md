## 三、3 层架构详解

### 业务战略层（executiver/）

贯穿整个管道的商业上下文。子目录：

| 子目录 | 内容 | 典型文件 |
|--------|------|----------|
| `strategy/` | 企业战略、市场定位 | `market-positioning-2026.md` |
| `industry/` | 行业趋势、技术雷达 | `tech-radar-2026-h2.md` |
| `roadmap/` | 组织目标、年度计划 | `2026-okr-planning.md` |
| `reading-list/` | 推荐阅读 | `recommended-books-2026.md` |

### 管道执行层（producter/ → leader/ → engineer/ → srer/）

软件交付的核心流程，从需求到运营的完整链路。每个阶段有明确的 Chip 契约。

### AI 赋能层（aier/）

AI 不是独立的管道阶段，而是渗透每个阶段的加速器。子目录：

| 子目录 | 内容 | 典型文件 |
|--------|------|----------|
| `foundations/` | AI 基础理论 | `transformer-architecture-explained.md` |
| `methodology/` | RAG/Agent 方法论 | `rag-best-practices.md` |
| `platform/` | 向量库/嵌入模型 | `embedding-model-comparison.md` |
| `ml/` | 传统机器学习 | `classification-algorithms-guide.md` |

### 知识治理层（curator/）

元层，不产出领域知识，维护知识库的结构和健康。子目录：

| 子目录 | 内容 | 典型文件 |
|--------|------|----------|
| `governance/` | 生命周期管理 | `lifecycle.md`, `readiness-checklist.md` |
| `diagrams/` | 架构图 | `knowledge-pipeline.png` |
| `templates/` | 文档模板 | `knowledge-entry-template.md` |
| `archive/` | 已归档内容 | 废弃的知识文件 |

## 四、跨领域索引

跨领域索引聚合跨角色主题，解决单一角色目录无法覆盖的横向关注点：

| 索引 | 聚合内容 | 文件 | 适用角色 |
|------|---------|------|----------|
| SECURITY | 供应链安全、应用安全、风险管理、事件响应、合规 | `engineer/SECURITY.md` | engineer, srer, leader |
| COLLABORATION | 团队流程、会议管理、知识共享、入职培训、PM | `curator/COLLABORATION.md` | 所有角色 |
| ENGINEERING | 架构模式、质量保证、数据工程、工具链、经验教训 | `engineer/ENGINEERING.md` | engineer, leader |

### 何时使用索引 vs 角色目录

| 场景 | 使用方式 |
|------|----------|
| 知道角色但不确定具体主题 | 进入角色目录，浏览子目录 |
| 知道主题但跨多个角色 | 使用领域索引（SECURITY/COLLABORATION/ENGINEERING） |
| 知道具体关键词 | 使用 `rg` 搜索 frontmatter tags |
| 不确定属于哪个角色 | 参考[角色边界决策树](./架构设计/04-角色边界.md) |

## 五、文件命名规范

### 基本规则

| 规则 | 说明 | 示例 |
|------|------|------|
| 格式 | kebab-case（小写字母 + 连字符） | `implement-an-api.md` |
| 禁止 | 下划线 `_`、数字前缀、空格 | ❌ `01_implement_api.md` |
| 语义 | 中文语义保留在 frontmatter `title:` 中 | `title: 实现 API 接口` |
| 目录层级 | 最多 3 层 | `role/problem-domain/file.md` |
| 动词短语 | 使用描述性的动词短语作为 slug | `choose-microservices-framework.md` |

### 命名示例

| 正确 | 错误 | 原因 |
|------|------|------|
| `implement-an-api.md` | `implement_an_api.md` | 禁止下划线 |
| `choose-microservices-framework.md` | `01-choose-framework.md` | 禁止数字前缀 |
| `handle-auth-failure.md` | `HandleAuthFailure.md` | 禁止大写 |
| `rag-hybrid-search.md` | `RAG混合检索.md` | 禁止中文文件名 |
| `setup-grafana-dashboard.md` | `setup-grafana.md` | 太简略，缺少语义 |
| `adr-001-use-postgres.md` | `adr-001.md` | 缺少决策主题 |

### 常见动词前缀

## 六、设计决策

### 6.1 为什么按角色而非按技术栈组织？

软件交付是人的活动，角色边界比技术边界更稳定。按角色组织使每个人能快速找到自己关心的内容，跨角色主题通过领域索引和 frontmatter `roles:` 字段覆盖。

**对比**：
- 按技术栈：`frontend/`, `backend/`, `database/` — 跨技术栈的知识难以归类
- 按角色：`engineer/`, `leader/`, `producter/` — 每个角色关注的内容自然汇聚

### 6.2 为什么最多 3 层目录？

`role/problem-domain/file.md` 的 3 层结构在导航便利性和分类粒度之间取得平衡。更深层级的目录会：

- 降低 AI 检索效率（路径过长稀释语义信号）
- 增加文件定位难度（需要记住多层嵌套路径）
- 导致过度分类（分类维度过多，难以决策）

### 6.3 为什么外部内容使用双文件？

`*-original.md`（源文件）+ `*-summary.md`（合成）模式：

- 原始文件保留完整内容，用于引用追溯和深度阅读
- 摘要文件提供结构化、高信息密度的 AI 可读版本
- 摘要文件优化了 RAG 检索（统一正文结构、精准 tags）

### 6.4 为什么使用 kebab-case 文件命名？

kebab-case 是 URL 友好的格式，在 grep/ripgrep 搜索中表现一致，且与 frontmatter 中的中文 `title:` 字段配合使用——中文语义保留在元数据中，文件名仅作为标识符。

```bash
# kebab-case 在 grep 中表现一致
rg "rag-hybrid-search" YiKnowledge -l  # 精确匹配

# 中文文件名在 grep 中不可靠
rg "RAG混合检索" YiKnowledge -l  # 编码问题，可能漏匹配
```

## 八、新增内容指南

### 新增知识文件

```
1. 确定角色目录
   ├── 业务策略、市场分析 → executiver/
   ├── 产品需求、用户故事 → producter/
   ├── 技术决策、架构选择 → leader/
   ├── 实现模式、开发工具 → engineer/
   ├── 发布流程、监控告警 → srer/
   ├── AI/ML 理论、RAG → aier/
   └── KB 结构、规则 → curator/
   (详细决策树见 role-boundaries.md)

2. 确定问题域子目录（如不存在则创建）
   → leader/decisions/  (已存在)
   → engineer/build/    (已存在)

3. 创建 kebab-case 文件
   → leader/decisions/choose-microservices-framework.md

4. 填写完整 frontmatter（8 个必填字段）
   → title, tags, category, created, updated, source, type, status

5. 遵循统一正文结构
   → Summary → Core viewpoints → Key information → Action recommendations

6. 运行就绪检查清单
   → curator/governance/readiness-checklist.md
```

### 新增角色子目录

1. 在角色目录下创建子目录（确保不超过 3 级）
2. 更新角色 INDEX.md（如有）
3. 确保新目录有明确的职责边界

### 新增领域索引

1. 确定跨角色主题（如 SECURITY、COLLABORATION、ENGINEERING）
2. 在合适角色目录下创建 `TOPIC.md`
3. 聚合所有相关角色目录中的文件链接
4. 在 `INDEX.md` 中注册新索引

## 九、反模式

| 反模式 | 错误示例 | 正确做法 | 原因 |
|--------|----------|----------|------|
| 超过 3 层目录 | `engineer/build/api/fastapi/auth.md` | `engineer/build/fastapi-auth.md` | 路径过长稀释语义 |
| 中文文件名 | `RAG混合检索.md` | `rag-hybrid-search.md` | grep/URL 兼容性差 |
| 文件名含下划线 | `implement_api.md` | `implement-an-api.md` | 不符合 kebab-case |
| 文件名含数字前缀 | `01-choose-framework.md` | `choose-microservices-framework.md` | 数字前缀无语义 |
| 文件名太简略 | `setup.md` | `setup-grafana-dashboard.md` | 缺少语义信息 |
| 文件放错角色 | 架构模式放在 `leader/` | 架构模式放在 `engineer/build/` | 角色边界混淆 |
| 空目录 | 创建了目录但没有文件 | 先创建文件，再创建目录 | 空目录无意义 |
| 不写 INDEX.md | 角色目录没有索引文件 | 在角色目录下创建 INDEX.md | 导航困难 |

## 十、约束

### 必须遵守

- 文件命名使用 kebab-case，禁止下划线和数字
- 目录层级最多 3 层（`role/problem-domain/file.md`）
- 每个角色目录应有 INDEX.md 索引文件
- 新增内容前运行就绪检查清单
- 每条知识属于唯一角色目录

### 禁止

- 不创建超过 3 级的目录层级
- 不使用中文文件名
- 不使用下划线或数字作为文件名前缀
- 不创建空目录
- 不将文件放在错误的角色目录中

## 十一、文件生命周期

### 知识文件状态流转

```
                    ┌─────────┐
                    │  draft  │  ← 初始创建，内容不完整
                    └────┬────┘
                         │ 内容完善、通过就绪检查
                         ▼
                    ┌─────────┐
                    │ active  │  ← 正式发布，RAG 可检索
                    └────┬────┘
                         │
              ┌──────────┼──────────┐
              │          │          │
              ▼          ▼          ▼
         ┌────────┐ ┌────────┐ ┌─────────┐
         │ review │ │ stale  │ │ archive │
         └───┬────┘ └───┬────┘ └─────────┘
             │          │          ▲
             │ 更新通过  │ 超过 90 天│
             ▼          │ 未更新    │
         ┌────────┐     │          │
         │ active │     ▼          │
         └────────┘ ┌─────────┐    │
                    │ archive  │◄───┘
                    └─────────┘
```

### 状态说明

| 状态 | 含义 | 触发条件 | 动作 |
|------|------|----------|------|
| `draft` | 草稿 | 新建文件 | 完善内容，运行就绪检查 |
| `active` | 活跃 | 通过就绪检查 | RAG 可检索，人类可参考 |
| `review` | 待审查 | 内容可能过时 | 指定审查人，更新或归档 |
| `stale` | 陈旧 | 90 天未更新 | 标记为 review 或 archive |
| `archive` | 已归档 | 不再适用 | 移入 curator/archive/ |

### 就绪检查清单

```
新增/修改文件前必须:

□ title: 描述性中文标题
□ tags: 至少 3 个标签，覆盖角色、主题、类型
□ category: 正确的 category 路径
□ created: 创建日期 (YYYY-MM-DD)
□ updated: 更新日期 (YYYY-MM-DD)
□ source: 知识来源（项目名/人名）
□ type: 正确的类型（architecture/pattern/guide/reference/bug/requirement）
□ status: 正确的状态（draft/active/review/stale/archive）
□ 文件命名: kebab-case，无语义丢失
□ 目录层级: 不超过 3 级
□ 角色归属: 属于唯一角色目录
□ 内容: 有实质内容，非空壳
```

## 十二、跨项目知识流

### YiKnowledge 作为 RAG 数据源的数据流

```
YiKnowledge/*.md
  │
  ├── YiAi Knowledge Watcher (apscheduler 每 60s)
  │     │
  │     ├── 1. 遍历目录树，检测文件变更
  │     │     ├── 新增文件 → 解析 frontmatter → 插入 MongoDB
  │     │     ├── 修改文件 → 更新 MongoDB 文档
  │     │     └── 删除文件 → 标记 MongoDB 文档为 archived
  │     │
  │     ├── 2. MongoDB 存储
  │     │     db.knowledge_files {
  │     │       file_path, title, tags, category, content,
  │     │       status, source, type, created_at, updated_at
  │     │     }
  │     │
  │     └── 3. RAG 索引构建
  │           ├── 读取 MongoDB 中 status=active 的文档
  │           ├── 分块 (chunk_size=512, overlap=50)
  │           ├── 向量化 (Ollama Embedding)
  │           └── 存入 VectorStoreIndex
  │
  ├── YiVad / YiPet 前端
  │     │
  │     ├── 知识库页面 → 浏览/搜索 YiKnowledge 文件

        │

```

## 十三、搜索与发现策略

### 三种发现路径

| 路径 | 方法 | 适用场景 |
|------|------|----------|
| 角色导航 | 进入角色目录 → 浏览子目录 → 找到文件 | 不确定精确关键词，按角色浏览 |
| 领域索引 | 使用 SECURITY/COLLABORATION/ENGINEERING 索引 | 跨角色横向主题 |
| 关键词搜索 | `rg <keyword> YiKnowledge -l` | 知道精确关键词 |

### 搜索示例

```bash
# 按标签搜索
rg "tags:.*rag" YiKnowledge/projects --files-with-matches

# 按分类搜索
rg "category: projects/yiai" YiKnowledge --files-with-matches

# 按类型搜索
rg "type: pattern" YiKnowledge --files-with-matches

# 全文搜索
rg "Repository 模式" YiKnowledge -l

# 组合搜索（RAG 相关 + 活跃状态）
rg "tags:.*rag" YiKnowledge -l | xargs rg "status: active" -l
```

### Frontmatter 索引

YiAi 的知识监视器解析所有文件的 frontmatter，建立以下查询索引：

```python
# 按分类查询
db.knowledge_files.find({"category": "projects/yiai/architecture"})

# 按标签查询
db.knowledge_files.find({"tags": {"$in": ["rag", "pattern"]}})

# 按类型+状态查询
db.knowledge_files.find({"type": "pattern", "status": "active"})

# 全文搜索
db.knowledge_files.find({"$text": {"$search": "Repository 模式"}})
```

## 十四、角色边界决策树

```
新增一条知识，应该放在哪个角色目录？

1. 是否涉及商业战略、市场分析、组织目标？
   → 是 → executiver/
   → 否 → 继续

2. 是否涉及产品需求、用户研究、PRD？
   → 是 → producter/
   → 否 → 继续

3. 是否涉及技术决策、架构选择、ADR？
   → 是 → leader/
   → 否 → 继续

4. 是否涉及实现模式、开发实践、代码、Bug？
   → 是 → engineer/
   → 否 → 继续

5. 是否涉及发布流程、监控告警、事件响应？
   → 是 → srer/
   → 否 → 继续

6. 是否涉及 AI/ML 理论、方法、平台？
   → 是 → aier/
   → 否 → 继续

7. 是否涉及知识库结构、规则、模板？
   → 是 → curator/
   → 否 → 重新评估，可能不属于任何角色
```

### 边界模糊案例

| 案例 | 分析 | 归属 |
|------|------|------|
| RAG 实现模式 | 涉及实现细节 → engineer/ | `engineer/build/rag-hybrid-search.md` |
| RAG 方法论 | 涉及 AI 方法 → aier/ | `aier/methodology/rag-best-practices.md` |
| ADR 选择 RAG 方案 | 涉及技术决策 → leader/ | `leader/decisions/adr-rag-framework.md` |
| 安全漏洞修复 | 涉及实现 → engineer/ | `engineer/ship/security-patch-process.md` |
| 安全策略制定 | 涉及决策 → leader/ | `leader/risk/security-policy.md` |
