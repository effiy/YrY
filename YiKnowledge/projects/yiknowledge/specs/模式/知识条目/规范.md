# YiKnowledge 知识条目模式 — 如何编写知识文件

> 本文档提供编写高质量 YiKnowledge 知识文件的标准方法。涵盖 frontmatter 填写、内容结构组织和不同内容类型的编写指南。

## 知识文件编写流程

```
确定主题 → 选择角色目录 → 选择 problem-domain → 创建文件 → 填写 frontmatter → 编写内容 → 自检 → 提交评审
```

## Frontmatter 模板

### 完整模板

```yaml
---
title: 文件标题（中文，描述性短语）
tags: [tag1, tag2, tag3, tag4]
category: <role>/<subdir>
created: YYYY-MM-DD
updated: YYYY-MM-DD
source: internal
type: summary
status: draft
lifecycle: inbox
review_cycle: quarterly
last_verified: YYYY-MM-DD
roles: [role1, role2]
benefit: "一句话描述读者收益"
acceptance_criteria:
  - "可验证的条款 1"
  - "可验证的条款 2"
  - "可验证的条款 3"
related:
  - ./relative/path/to/file.md
  - ../other/file.md
---
```

### 字段填写指南

#### title

- 使用中文
- 用描述性短语，不是单个词
- 让读者一眼就知道文件内容

```yaml
# 好的 title
title: 文件约定 — kebab-case 命名、3 级目录限制、Frontmatter Schema
title: 微信小程序用户授权流程
title: 微服务间通信的最佳实践

# 不好的 title
title: 文档
title: 笔记
title: 东西
```

#### tags

- 3-5 个标签
- 第一个标签通常是项目名或角色
- 后续标签描述内容主题
- 全小写英文

```yaml
# 好的 tags
tags: [yiknowledge, conventions, frontmatter, naming]
tags: [yivad, architecture, pro-table, pagination]

# 不好的 tags
tags: [a]                        # 太少
tags: [a, b, c, d, e, f, g, h]   # 太多
tags: [中文标签]                   # 不用中文
```

#### benefit

- 一句话，回答"读者能获得什么"
- 具体、可量化
- 用动词开头

```yaml
# 好的 benefit
benefit: "掌握编写高质量知识文件的标准方法"
benefit: "快速找到适合当前场景的 API 调用模式"
benefit: "理解前端性能优化的 5 个关键指标"

# 不好的 benefit
benefit: "有用"
benefit: "good to know"
```

#### acceptance_criteria

- 可验证的陈述
- 每条用一句话描述一个可检查的结果
- 5-8 条为宜

```yaml
# 好的 acceptance_criteria
acceptance_criteria:
  - "列出所有 8 个必填字段"
  - "提供 3 个完整示例"
  - "列出 5 个常见错误及修正方法"

# 不好的 acceptance_criteria
acceptance_criteria:
  - "好的内容"
  - "有用的信息"
```

## 内容结构

### 标准结构

```markdown
# 文件标题（一级标题）

> 一句话摘要（引用块），概括文件内容。

## 背景/概述（可选）

描述为什么需要这个知识文件，解决什么问题。

## 核心内容（多个二级标题）

按逻辑组织内容，每个二级标题覆盖一个子主题。

详细说明。

总结关键规则，便于快速回顾。

## 交叉引用

链接到相关文件。
```

## 内容编写最佳实践

### 使用渐进式阅读

1. **标题一目了然** — 读者看一眼就知道内容
2. **摘要概括核心** — 引用块一句话总结
3. **二级标题可扫描** — 读者扫一遍二级标题就知道结构
4. **关键约定可快速回顾** — 结尾的关键约定让读者快速记住要点

### 使用代码块

```markdown
## 代码示例

### 正确示例

\`\`\`javascript
// 正确：使用 Options API

  data() {

\`\`\`

### 错误示例

\`\`\`javascript
// 错误：使用 Composition API
import { ref } from 'vue';

\`\`\`
```

# Vue 组件通信方式总结

> 5 种 Vue 组件通信方式及其适用场景，帮助选择正确的通信方案。

## 通信方式概览

| 方式 | 适用场景 | 复杂度 |
|---|---|---|
| props / $emit | 父子组件 | 低 |
| provide / inject | 祖先-后代 | 中 |
| Vuex | 全局状态 | 高 |
| EventBus | 兄弟组件 | 低 |
| $refs | 直接调用 | 低 |

## 1. Props / $emit

### 使用场景

父组件向子组件传递数据，子组件向父组件传递事件。

### 代码示例

\`\`\`vue
<!-- 父组件 -->
<child-component :data="parentData" @update="handleUpdate" />

<!-- 子组件 -->
<script>
export default {
  props: {
    data: { type: Object, required: true },
  },
  methods: {
    handleClick() {
      this.$emit('update', newData);
    },
  },
};
</script>
\`\`\`

## 关键约定

1. 优先使用 props/$emit，最简单直接
2. 跨层级组件通信用 provide/inject 或 Vuex
3. 避免使用 EventBus（难以追踪数据流）
4. 全局状态必须走 Vuex

## 交叉引用

- [Vue 组件模式](./vue-component-patterns.md)
- [Vue 速查表](../learn/vue-cheatsheet.md)

## 写作风格指南

### 基本原则

| 原则 | 说明 | 示例 |
|---|---|---|
| 中文优先 | 所有正文使用中文，代码和术语保留英文 | "使用 Vue 3 Composition API 重构组件" |
| 简洁直接 | 短句优先，一段一个主题，避免长难句 | 见下方示例 |
| 主动语态 | 使用主动语态，明确主语和动作 | "curator 审核内容" 而非 "内容被 curator 审核" |
| 具体而非抽象 | 用具体数字和事实代替模糊描述 | "减少 30% 构建时间" 而非 "显著提升性能" |
| 一致术语 | 同一概念使用同一术语，在首次出现时给出全称 | "RAG（检索增强生成，Retrieval-Augmented Generation）" |
| 面向读者 | 从读者视角出发，回答"我能获得什么" | 见 benefit 字段示例 |

### 好 vs 不好的写作风格

```markdown
# 不好的写作风格

这个功能其实挺复杂的，有很多东西需要考虑，比如说你要注意各种边界情况，还有性能方面的问题，反正就是要注意很多地方，不然很容易出问题。

# 好的写作风格

该功能涉及 3 个关键注意点：

1. **边界情况**：空状态、加载中、错误状态需分别处理
2. **性能**：列表超过 100 条时必须启用虚拟滚动
3. **兼容性**：需在 Chrome 90+、Safari 14+ 上测试通过
```

## 交叉引用最佳实践

### 引用原则

| 原则 | 说明 | 正确示例 | 错误示例 |
|---|---|---|---|
| 双向链接 | 如果 A 引用 B，B 也应引用 A（除非 B 是通用参考） | A 和 B 互相在 `related` 中列出对方 | A 引用 B，但 B 未引用 A |
| 就近引用 | 优先引用同目录或父目录的文件 | `./sibling-file.md` 或 `../parent-file.md` | `../../../far-away-file.md` |
| 有说明的引用 | 每条引用附带一句话说明，解释为什么相关 | `- [文件约定](./spec.md) — 命名规范` | `- [文件约定](./spec.md)` |
| 不重复引用 | 不引用已经通过其他方式引用的文件 | 在 `related` 中列出，正文中不再重复 | 正文和 `related` 重复引用同一文件 |
| 避免循环引用 | A → B → C → A 的引用链应避免 | 两个文件互相引用是允许的 | 三个以上文件形成闭环应避免 |

### 引用更新工作流

```bash
# 当文件被移动或重命名时，更新所有引用

# 1. 查找所有引用旧路径的文件
grep -rl "old-file-name.md" YiKnowledge/ --include="*.md"

# 2. 批量更新引用（谨慎操作，先确认）
find YiKnowledge/ -name "*.md" -exec sed -i '' 's/old-file-name.md/new-file-name.md/g' {} +

# 3. 验证更新后的引用是否有效

```

## AI 检索优化（RAG）

### 为什么 RAG 优化很重要

YiKnowledge 同时服务人类和 AI（YiAi 的 RAG 引擎）。文件内容会被 llama_index 分割成块（chunk），嵌入为向量，用于语义检索。优化内容结构可以显著提升 AI 检索的准确性和召回率。

### 检索优化策略

| 策略 | 说明 | 效果 |
|---|---|---|
| 标题层级清晰 | 一级标题 = 文件主题，二级标题 = 独立知识点 | 提升分块精度，每个 chunk 包含完整语义单元 |
| 摘要提纲挈领 | 引用块摘要 = 文件的核心语义锚点 | 帮助向量模型理解文件主题 |
| 关键词密度 | 核心术语在正文中自然出现 3-5 次 | 提升关键词匹配和语义相似度 |
| 标签语义化 | tags 使用领域标准术语，不用缩写 | 提升标签过滤的准确率 |
| 自包含段落 | 每个二级标题下的内容可独立理解 | 分块后的每个 chunk 都是完整的知识单元 |
| 避免隐式引用 | 不用"如上所述""详见上文"等依赖上下文的表达 | 每个 chunk 脱离上下文仍可理解 |
| 结构化数据 | 表格和列表优于长段落 | 向量模型对结构化数据的语义理解更好 |
| 明确实体关系 | 用"X 是 Y 的 Z""X 包含 Y"等明确关系表达 | 帮助 RAG 引擎理解实体间关系 |

### 分块友好 vs 不友好的内容

```markdown
# 分块不友好（长段落，语义混合）

Vue 3 引入了 Composition API，它提供了更好的逻辑复用和类型推导。同时，
Vue 3 还改进了响应式系统，使用 Proxy 替代 Object.defineProperty。另外，
Teleport 组件允许将内容渲染到 DOM 的其他位置，Suspense 组件提供了更好的
异步依赖处理。这些特性共同构成了 Vue 3 的核心改进。

# 分块友好（结构化，每个二级标题是独立语义单元）

## Composition API

Vue 3 的 Composition API 提供以下改进：
- **逻辑复用**：通过 composable 函数提取和复用逻辑
- **类型推导**：完整的 TypeScript 支持
- **代码组织**：按功能而非选项组织代码

## 响应式系统升级

Vue 3 使用 Proxy 替代 Object.defineProperty：
- 支持数组索引和 length 修改的响应式追踪
- 支持 Map、Set、WeakMap、WeakSet 等数据结构
- 性能提升约 2 倍

## 新增内置组件

### Teleport

将组件内容渲染到 DOM 树的指定位置，适用于模态框、通知等场景。

### Suspense

协调异步依赖，在等待异步组件解析时显示后备内容。
```

| 指标 | 说明 | 目标值 |
|---|---|---|

| 精确率 | 检索结果中相关文件的比例 | >= 80% |

## 关键约定

1. **frontmatter 先写** — 创建文件后第一时间填写 frontmatter
2. **标题用中文** — 描述性短语，让读者一目了然
3. **使用二级标题组织内容** — 方便读者扫描和检索
4. **关键约定放在结尾** — 方便读者快速回顾
5. **交叉引用不遗漏** — 相关内容必须双向链接
6. **代码示例要完整** — 正反示例都要有
7. **自检后再提交** — 对照就绪检查清单逐项检查
8. **按类型选择模板** — summary/original/template/prompt 各有专用结构
9. **为 RAG 优化内容** — 结构化、自包含、关键词自然分布
10. **避免依赖上下文的表达** — 每个二级标题下的内容可独立理解
11. **验收标准必须可验证** — 不能用"好""有用"等模糊词汇
12. **引用附带说明** — 每条交叉引用解释为什么相关
