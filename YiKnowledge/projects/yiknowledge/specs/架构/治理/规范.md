# YiKnowledge 治理规范 — 生命周期阶段、评审周期、就绪检查清单、Curator 角色

> YiKnowledge 的治理体系确保知识库内容质量、一致性和可维护性。治理覆盖生命周期管理、定期评审、质量门禁和 curator 角色职责。

## 生命周期阶段

### 5 个阶段

```
inbox ──→ triage ──→ active ──→ reference ──→ archive
 新创建      评审中      活跃        参考         归档
```

### 阶段定义

| 阶段 | 状态 | 说明 | 典型停留时间 |
|---|---|---|---|
| `inbox` | 收件箱 | 文件刚创建，内容可能不完整，等待分类和评审 | 1-7 天 |
| `triage` | 评审中 | 内容已完整，正在进行质量检查（就绪检查清单） | 1-3 天 |
| `active` | 活跃 | 已发布，内容经过验证，正在被使用和维护 | 持续 |
| `reference` | 参考 | 内容稳定成熟，不再频繁更新，但仍有参考价值 | 持续 |
| `archive` | 归档 | 内容已过时或不再需要，保留备份但不活跃使用 | 永久 |

### 阶段流转规则

| 流转 | 触发条件 | 操作 |
|---|---|---|
| `inbox → triage` | 内容编写完成，作者认为可评审 | 更新 `lifecycle: triage`，提交评审 |
| `triage → active` | 通过就绪检查清单全部 10 项 | 更新 `lifecycle: active`，`status: stable` |
| `triage → inbox` | 评审不通过，需要大幅修改 | 更新 `lifecycle: inbox`，标注修改项 |
| `active → reference` | 内容稳定，超过 3 个月无更新 | 更新 `lifecycle: reference` |
| `reference → archive` | 内容过时，不再适用 | 更新 `lifecycle: archive`，`status: deprecated` |
| `reference → active` | 内容重新需要维护更新 | 更新 `lifecycle: active` |
| `archive → active` | 归档内容重新激活 | 更新 `lifecycle: active`，`status: stable`，更新内容 |

### 流转示意图

```
                    ┌──────────────────┐
                    │     inbox        │
                    │   (新创建)        │
                    └────────┬─────────┘
                             │ 内容完成
                             ▼
                    ┌──────────────────┐
              ┌─────│     triage       │─────┐
              │     │   (评审中)        │     │
              │     └────────┬─────────┘     │
              │ 评审不通过    │ 评审通过       │ 需要大幅修改
              │              ▼               │

              │     │   (活跃)          │◄────┘
              │     └────────┬─────────┘
              │              │ 3个月无更新
              │              ▼
              │     ┌──────────────────┐
              │     │   reference      │
              └─────│   (参考)          │
                    └────────┬─────────┘
                             │ 内容过时
                             ▼
                    ┌──────────────────┐
                    │    archive       │
                    │   (归档)          │
                    └──────────────────┘
```

## 评审周期

### 4 种评审周期

| 周期 | 频率 | 适用场景 | 示例 |
|---|---|---|---|
| `weekly` | 每周 | 快速变化的内容 | 项目状态更新、周报 |
| `monthly` | 每月 | 需要定期验证的内容 | 配置参考、依赖清单 |
| `quarterly` | 每季度 | 稳定的架构文档和规范 | 架构摘要、模式规范 |
| `yearly` | 每年 | 长期稳定的参考内容 | 设计原则、团队章程 |

### 评审内容

每次评审需检查：

1. 内容是否仍然准确
2. 代码示例是否仍然有效
3. 相关链接是否仍然有效
4. frontmatter 日期是否需要更新
5. 生命周期阶段是否仍然合适

评审完成后更新 `last_verified` 字段。

## 就绪检查清单

### 10 项检查

发布到 `active` 阶段前，必须通过全部 10 项检查：

| # | 检查项 | 通过标准 |
|---|---|---|
| 1 | 标题清晰 | `title` 是一个完整的句子或描述性短语，不是模糊标签 |
| 2 | 角色目录正确 | 文件在正确的角色目录下 |
| 3 | 文件名规范 | 符合 kebab-case 约定，无下划线，无数字 |
| 4 | 必填字段齐全 | 8 个必填字段全部存在且非空 |
| 5 | benefit 具体 | 回答"读者能获得什么"，一句话 |
| 6 | 验收标准可验证 | 每条标准是可证伪的陈述 |
| 7 | category 字段正确 | 与实际文件路径匹配 |
| 8 | 相关链接有效 | 所有 `related` 路径指向存在的文件 |
| 9 | 内容在角色边界内 | 内容回答该角色的核心问题 |
| 10 | 内容不重复 | 不是已有内容的重新表述 |

### 检查清单使用方法

```bash
# 1. 在 curator/governance/readiness-checklist.md 中逐项检查
# 2. 10 项全部通过后，更新 lifecycle 为 active
# 3. 如有不适用项，在提交信息中说明原因
```

## Curator 角色

### 职责

| 职责 | 说明 | 频率 |
|---|---|---|
| 内容审核 | 审核新内容，确保通过就绪检查清单 | 按需 |
| 定期评审 | 按评审周期检查内容准确性和有效性 | 按评审周期 |
| 目录维护 | 确保目录结构合理，角色边界清晰 | 持续 |
| 归档管理 | 识别过时内容并归档 | 每季度 |
| 规范更新 | 根据实践更新知识库规范 | 按需 |
| 质量报告 | 生成知识库健康度报告 | 每季度 |

### 权限

| 操作 | 权限 |
|---|---|
| 修改任何文件 | 是 |
| 修改 frontmatter | 是 |
| 移动文件 | 是（需更新所有引用） |
| 删除文件 | 是（归档优先于删除） |
| 批准内容发布 | 是 |
| 拒绝内容发布 | 是（需给出具体原因） |

### 日常操作

```bash
# 每日扫描新文件

# 检查过期评审
# 查找 review_cycle: monthly 且 last_verified 超过 30 天的文件
# 查找 review_cycle: quarterly 且 last_verified 超过 90 天的文件

# 检查死链
# 遍历所有文件的 related 字段，验证路径是否存在
```

## 知识库健康度指标

| 指标 | 计算方式 | 健康阈值 |
|---|---|---|
| 内容覆盖率 | 有内容的角色目录数 / 总角色目录数 | >= 80% |
| 活跃度 | `active` 阶段文件数 / 总文件数 | >= 60% |
| 归档率 | `archive` 阶段文件数 / 总文件数 | <= 15% |
| 评审及时率 | 已按时评审文件数 / 应评审文件数 | >= 90% |
| 规范合规率 | 通过 frontmatter 检查的文件数 / 总文件数 | >= 95% |

## 评审工作流

### 标准评审流程

```
作者提交评审 → curator 初审 → 就绪检查清单 → 内容评审 → 批准/驳回 → 发布
```

### 详细步骤

| 步骤 | 角色 | 操作 | 时间限制 |
|---|---|---|---|
| 1. 提交评审 | 作者 | 更新 `lifecycle: triage`，发起 MR/PR | — |
| 2. 初审 | curator | 检查 frontmatter 完整性、文件命名、目录位置 | 1 个工作日内 |
| 3. 就绪检查 | curator | 逐项核对 10 项就绪检查清单 | 与初审同步 |
| 4. 内容评审 | curator + 领域专家 | 检查内容准确性、完整性、角色边界 | 2 个工作日内 |
| 5. 修改 | 作者 | 根据评审意见修改内容 | 3 个工作日内 |
| 6. 复评 | curator | 确认修改已满足要求 | 1 个工作日内 |
| 7. 批准发布 | curator | 更新 `lifecycle: active`，`status: stable`，合并 MR | — |
| 8. 驳回 | curator | 更新 `lifecycle: inbox`，附驳回原因，关闭 MR | — |

### 评审检查清单模板

```markdown
## 评审检查清单 — [文件标题]

**文件路径**: `YiKnowledge/xxx/xxx/file.md`
**评审日期**: YYYY-MM-DD
**评审人**: [curator 姓名]

### Frontmatter 检查
- [ ] title: 描述性短语，中文，10-60 字符
- [ ] tags: 3-5 个，全小写英文
- [ ] category: 与文件路径匹配
- [ ] created/updated: 日期格式正确，updated >= created
- [ ] source: internal 或 url
- [ ] type: summary / original / template / prompt
- [ ] status: draft / stable / deprecated
- [ ] lifecycle: 当前阶段正确

### 推荐字段检查
- [ ] benefit: 一句话描述读者收益
- [ ] acceptance_criteria: 可验证的条款（3-8 条）
- [ ] roles: 目标角色明确
- [ ] related: 相对路径有效

### 内容检查
- [ ] 角色目录正确
- [ ] 内容在角色边界内
- [ ] 不与其他文件重复
- [ ] 代码示例有效
- [ ] 交叉引用链接有效
- [ ] 无拼写/语法错误

### 评审结论
- [ ] 通过 — 批准发布
- [ ] 需修改 — 见修改意见
- [ ] 驳回 — 见驳回原因

**修改意见**:
1. ...
2. ...

**驳回原因**:
[具体说明为什么驳回，而非简单说"不通过"]
```

## 过期内容检测规则

### 自动检测条件

| 检测条件 | 判定标准 | 触发操作 |
|---|---|---|
| 超期未评审 | `review_cycle: weekly` 且 `last_verified` 超过 7 天 | 标记为待评审 |
| 超期未评审 | `review_cycle: monthly` 且 `last_verified` 超过 30 天 | 标记为待评审 |
| 超期未评审 | `review_cycle: quarterly` 且 `last_verified` 超过 90 天 | 标记为待评审 |
| 超期未评审 | `review_cycle: yearly` 且 `last_verified` 超过 365 天 | 标记为待评审 |
| 长期未更新 | `lifecycle: active` 且 `updated` 超过 6 个月 | 建议降级为 `reference` |
| 代码示例过期 | 引用的 API 版本号与当前版本不一致 | 标记为需更新 |
| 外部链接失效 | `source: url` 且原 URL 返回 404 | 标记为需修复 |
| 无人引用 | 无任何文件的 `related` 字段引用此文件（孤立文件） | 建议评估是否归档 |

### 过期检测脚本

```bash
#!/bin/bash
# check-stale-content.sh — 检测过期内容
# 用法: bash check-stale-content.sh

TODAY=$(date +%s)
STALE_FILES=""

echo "=== 过期内容检测报告 ==="
echo "检测日期: $(date +%Y-%m-%d)"
echo ""

# 检查超期未评审的 weekly 文件
echo "## 超期未评审 (weekly, 超过 7 天)"
for f in $(grep -rl "review_cycle: weekly" YiKnowledge/ --include="*.md"); do
    last_verified=$(grep "last_verified:" "$f" | head -1 | awk '{print $2}')
    if [ -n "$last_verified" ] && [ "$last_verified" != "null" ]; then
        verified_ts=$(date -j -f "%Y-%m-%d" "$last_verified" +%s 2>/dev/null || echo 0)
        diff_days=$(( (TODAY - verified_ts) / 86400 ))
        if [ $diff_days -gt 7 ]; then
            echo "  [逾期 ${diff_days} 天] $f"
            STALE_FILES="$STALE_FILES $f"
        fi
    fi
done

# 检查超期未评审的 monthly 文件
echo "## 超期未评审 (monthly, 超过 30 天)"
for f in $(grep -rl "review_cycle: monthly" YiKnowledge/ --include="*.md"); do
    last_verified=$(grep "last_verified:" "$f" | head -1 | awk '{print $2}')
    if [ -n "$last_verified" ] && [ "$last_verified" != "null" ]; then
        verified_ts=$(date -j -f "%Y-%m-%d" "$last_verified" +%s 2>/dev/null || echo 0)
        diff_days=$(( (TODAY - verified_ts) / 86400 ))
        if [ $diff_days -gt 30 ]; then
            echo "  [逾期 ${diff_days} 天] $f"
            STALE_FILES="$STALE_FILES $f"
        fi
    fi
done

# 检查超期未评审的 quarterly 文件
echo "## 超期未评审 (quarterly, 超过 90 天)"
for f in $(grep -rl "review_cycle: quarterly" YiKnowledge/ --include="*.md"); do
    last_verified=$(grep "last_verified:" "$f" | head -1 | awk '{print $2}')
    if [ -n "$last_verified" ] && [ "$last_verified" != "null" ]; then
        verified_ts=$(date -j -f "%Y-%m-%d" "$last_verified" +%s 2>/dev/null || echo 0)
        diff_days=$(( (TODAY - verified_ts) / 86400 ))
        if [ $diff_days -gt 90 ]; then
            echo "  [逾期 ${diff_days} 天] $f"
            STALE_FILES="$STALE_FILES $f"
        fi
    fi
done

# 检查长期未更新的 active 文件
echo "## 长期未更新 (active, 超过 180 天)"
for f in $(grep -rl "lifecycle: active" YiKnowledge/ --include="*.md"); do
    updated=$(grep "^updated:" "$f" | head -1 | awk '{print $2}')
    if [ -n "$updated" ] && [ "$updated" != "null" ]; then
        updated_ts=$(date -j -f "%Y-%m-%d" "$updated" +%s 2>/dev/null || echo 0)
        diff_days=$(( (TODAY - updated_ts) / 86400 ))
        if [ $diff_days -gt 180 ]; then
            echo "  [未更新 ${diff_days} 天] $f"
            STALE_FILES="$STALE_FILES $f"
        fi
    fi
done

echo ""
echo "=== 检测完成 ==="
if [ -n "$STALE_FILES" ]; then
    echo "建议操作: 评审以上过期文件，更新内容或调整生命周期阶段"
fi
```

## 废弃流程

### 废弃决策矩阵

| 情况 | 操作 | 时间线 |
|---|---|---|
| 内容已过时，但仍有参考价值 | 移至 `reference`，`status` 保持 `stable` | 立即 |
| 内容已过时，不再有参考价值 | 移至 `archive`，`status: deprecated` | 立即 |
| 内容包含错误信息 | 修正内容或移至 `archive`（如无法修正） | 1 周内 |
| 内容被新文件替代 | 在旧文件 frontmatter 添加 `superseded_by: ./new-file.md`，移至 `archive` | 立即 |
| 文件从未完成（draft 超过 30 天） | 通知作者，7 天无响应则移至 `archive` | 30 天后 |
| 内容违反角色边界 | 移动到正确角色目录，更新 `category` | 立即 |

### 废弃执行步骤

```markdown
1. **评估**: 确认内容确实已过时，不是暂时性过时
2. **通知**: 在提交信息中说明废弃原因
3. **标记**: 更新 frontmatter
   ```yaml
   lifecycle: archive
   status: deprecated
   updated: YYYY-MM-DD
   # 如果被新文件替代，添加：
   superseded_by: ./new-file.md
   ```
4. **更新引用**: 检查所有文件的 `related` 字段，将指向此文件的链接更新为替代文件
5. **归档**: 将文件保留在仓库中，不执行物理删除
6. **记录**: 在相关变更日志中记录废弃操作
```

### 废弃文件恢复

```yaml
# 如果已归档文件需要恢复
---
lifecycle: active          # 从 archive 改为 active
status: stable             # 从 deprecated 改为 stable
updated: 2026-09-02        # 更新日期
---
# 移除 superseded_by 字段（如果存在）
```

## 合并冲突解决

### 知识文件合并冲突的常见场景

| 场景 | 原因 | 解决方案 |
|---|---|---|
| frontmatter 冲突 | 两人同时修改元数据 | 手动合并，保留更完整的字段集合 |
| 内容冲突 | 两人修改同一段落 | 评估两版内容，选择更准确/完整的版本 |
| 交叉引用冲突 | 两人添加了不同的 `related` 链接 | 合并两份 `related` 列表，去重 |
| 目录冲突 | 两人将文件移动到不同位置 | 协商确定正确位置，更新所有引用 |

### 冲突解决策略

```markdown
# 策略 1：优先准确性
- 当内容冲突时，以更准确、更完整的版本为准
- 如果无法判断，保留两个版本并标注为待评审

# 策略 2：保留元数据完整性
- frontmatter 冲突时，合并所有非冲突字段
- 冲突字段取两者中更完整的值
- updated 日期取两者中较新的

# 策略 3：引用完整性
- related 列表冲突时，合并去重
- 移动文件后，必须更新所有引用

# 策略 4：升级评审
- 如果冲突无法自行解决，标记为 triage 并请求 curator 介入
```

### 冲突解决示例

```yaml
# 版本 A (作者甲)
---
title: Vue 组件通信方式总结
tags: [yivad, vue, components]
updated: 2026-09-01
roles: [工程师]
related:
  - ./vue-patterns.md
---

# 版本 B (作者乙)
---
title: Vue 组件通信方式总结
tags: [yivad, vue, components, communication]
updated: 2026-09-02
roles: [工程师, leader]
related:
  - ./vue-patterns.md
  - ./state-management.md
---

# 合并结果 (curator)
---
title: Vue 组件通信方式总结
tags: [yivad, vue, components, communication]   # 取更完整的 tags
updated: 2026-09-02                              # 取较新的日期
roles: [工程师, leader]                           # 合并 roles
related:                                         # 合并 related 去重
  - ./vue-patterns.md
  - ./state-management.md
---
```

## 质量评分指标

### 评分体系

| 维度 | 权重 | 评分标准 | 满分 |
|---|---|---|---|
| 元数据完整性 | 20% | 所有必填字段齐全，推荐字段有值 | 20 |
| 内容准确性 | 25% | 信息准确，代码示例可运行，链接有效 | 25 |
| 结构清晰度 | 15% | 二级标题可扫描，摘要概括核心，关键约定突出 | 15 |
| 角色契合度 | 15% | 内容回答该角色的核心问题，未越界 | 15 |
| 可维护性 | 10% | 生命周期合理，评审周期适中，有验收标准 | 10 |
| 引文完整性 | 10% | 交叉引用双向链接，无死链，引用合理 | 10 |
| 更新及时性 | 5% | updated 日期反映实际修改时间，在评审周期内 | 5 |

### 评分计算

```
总分 = 元数据完整性 + 内容准确性 + 结构清晰度 + 角色契合度 + 可维护性 + 引文完整性 + 更新及时性

等级:
  90-100: A (优秀) — 可直接发布
  80-89:  B (良好) — 少量修改后发布
  70-79:  C (及格) — 需要修改后再评审
  60-69:  D (不及格) — 需要大幅修改
  <60:    F (不合格) — 建议重写或归档
```

### 评分脚本

```python
def score_file(filepath: str) -> dict:
    """对单个文件进行质量评分"""
    scores = {
        'metadata_completeness': 0,  # 20
        'content_accuracy': 0,       # 25
        'structure_clarity': 0,      # 15
        'role_fitness': 0,           # 15
        'maintainability': 0,        # 10
        'reference_integrity': 0,    # 10
        'update_timeliness': 0,      # 5
    }

    # 元数据完整性 (20): 检查必填和推荐字段
    fm = get_frontmatter(filepath)
    required = ['title', 'tags', 'category', 'created', 'updated', 'source', 'type', 'status']
    recommended = ['lifecycle', 'review_cycle', 'last_verified', 'roles', 'benefit', 'acceptance_criteria', 'related']
    filled_required = sum(1 for f in required if f in fm and fm[f])
    filled_recommended = sum(1 for f in recommended if f in fm and fm[f])
    scores['metadata_completeness'] = min(20, (filled_required / len(required)) * 14 + (filled_recommended / len(recommended)) * 6)

    # 内容准确性 (25): 需要人工评估，此处给默认分
    # 实际应用中应结合自动化检查
    scores['content_accuracy'] = 20  # 默认分

    # 结构清晰度 (15): 检查二级标题数量和摘要
    content = get_content(filepath)
    h2_count = len(re.findall(r'^## ', content, re.MULTILINE))
    has_summary = bool(re.match(r'^> ', content.split('\n')[0]))
    has_key_takeaways = '关键约定' in content
    scores['structure_clarity'] = min(15, h2_count * 2 + (3 if has_summary else 0) + (3 if has_key_takeaways else 0))

    # 引用完整性 (10): 检查 related 链接
    if 'related' in fm and isinstance(fm['related'], list):
        valid = sum(1 for link in fm['related'] if link_exists(filepath, link))
        total = len(fm['related'])
        scores['reference_integrity'] = (valid / total * 10) if total > 0 else 10

    # 更新及时性 (5): 检查 updated 日期
    if 'updated' in fm and fm['updated']:
        try:
            updated = datetime.strptime(str(fm['updated']), '%Y-%m-%d')
            days_ago = (datetime.now() - updated).days
            if days_ago <= 90:
                scores['update_timeliness'] = 5
            elif days_ago <= 180:
                scores['update_timeliness'] = 3
            else:
                scores['update_timeliness'] = 1
        except ValueError:
            pass

    total = sum(scores.values())
    grade = 'A' if total >= 90 else 'B' if total >= 80 else 'C' if total >= 70 else 'D' if total >= 60 else 'F'

    return {'scores': scores, 'total': total, 'grade': grade}
```

### Git Pre-commit Hook

```bash
#!/bin/bash
# .git/hooks/pre-commit — 提交前自动检查知识文件
# 安装: cp pre-commit .git/hooks/pre-commit && chmod +x .git/hooks/pre-commit

echo "=== YiKnowledge 提交前检查 ==="

STAGED_FILES=$(git diff --cached --name-only --diff-filter=ACM | grep '^YiKnowledge/.*\.md$')

if [ -z "$STAGED_FILES" ]; then
    echo "无知识文件变更，跳过检查"
    exit 0
fi

HAS_ERROR=0

for FILE in $STAGED_FILES; do
    echo "检查: $FILE"

    # 1. 文件名检查
    BASENAME=$(basename "$FILE")
    if echo "$BASENAME" | grep -qE '[A-Z_]|^[0-9]'; then
        echo "  [错误] 文件名不符合 kebab-case 规范: $BASENAME"
        HAS_ERROR=1
    fi

    # 2. 目录深度检查
    DEPTH=$(echo "$FILE" | tr '/' '\n' | grep -c '')
    if [ "$DEPTH" -gt 4 ]; then  # YiKnowledge/ 算一级
        echo "  [错误] 目录深度超过 3 级: $FILE"
        HAS_ERROR=1
    fi

    # 3. 编码检查
    if file -I "$FILE" | grep -qv 'charset=utf-8'; then
        echo "  [错误] 编码不是 UTF-8: $FILE"
        HAS_ERROR=1
    fi

    # 4. 换行符检查
    if grep -q $'\r' "$FILE"; then
        echo "  [错误] 包含 CRLF 换行符: $FILE"
        HAS_ERROR=1
    fi

    # 5. Frontmatter 检查
    if ! head -1 "$FILE" | grep -q '^---$'; then
        echo "  [错误] 缺少 frontmatter: $FILE"
        HAS_ERROR=1
    fi

    # 6. 文件大小检查
    LINES=$(wc -l < "$FILE")
    if [ "$LINES" -gt 500 ]; then
        echo "  [警告] 文件行数超过 500 行: $FILE ($LINES 行)"
    fi
done

if [ "$HAS_ERROR" -eq 1 ]; then
    echo ""
    echo "检查失败！请修复以上错误后再提交。"
    echo "如需跳过检查，请使用: git commit --no-verify"
    exit 1
fi

echo "检查通过！"
exit 0
```

## 反模式

### 反模式 1：不要跳过 triage 阶段

```yaml
# 不要这样做 — 直接从 inbox 跳到 active
---
lifecycle: inbox
status: draft
---
# 修改后直接变成
---
lifecycle: active
status: stable
---

# 应该这样做 — 经过 triage 阶段
---
lifecycle: inbox
status: draft
---
# 第一步：提交评审
---
lifecycle: triage
status: draft
---
# 第二步：评审通过后发布
---
lifecycle: active
status: stable
---
```

### 反模式 2：不要忽视评审周期

```yaml
# 不要这样做 — 设了 review_cycle 但从不更新 last_verified
---
review_cycle: monthly
last_verified: 2025-01-15   # 8 个月前，从未更新
---

# 应该这样做 — 每次评审后更新 last_verified
---
review_cycle: monthly
last_verified: 2026-09-02   # 反映最后一次评审时间
---
```

### 反模式 3：不要物理删除文件

```bash
# 不要这样做 — 直接删除文件
git rm YiKnowledge/engineer/old-patterns.md

# 应该这样做 — 先归档，确认无用后再删除
# 1. 更新 frontmatter
# lifecycle: archive
# status: deprecated
# 2. 提交变更
git add YiKnowledge/engineer/old-patterns.md
git commit -m "归档: engineer/old-patterns.md — 内容已过时"
# 3. 等待一个评审周期，确认无引用后再删除
```

### 反模式 4：不要在不更新引用的情况下移动文件

```bash
# 不要这样做 — 直接移动文件，不更新引用
git mv YiKnowledge/engineer/old-location.md YiKnowledge/engineer/new-location.md

# 应该这样做 — 移动文件 + 更新所有引用
# 1. 查找所有引用此文件的文件
grep -rl "old-location.md" YiKnowledge/
# 2. 移动文件
git mv YiKnowledge/engineer/old-location.md YiKnowledge/engineer/new-location.md
# 3. 更新所有引用
# 更新 frontmatter category 字段
# 更新其他文件的 related 字段
# 更新正文中的交叉引用链接
# 4. 提交时在 commit message 中说明移动操作
```

### 反模式 5：不要忽略质量评分

# 不要这样做 — 从不检查知识库健康度

# 不要这样做 — 个人决定归档团队共用的内容
# 某工程师认为某文件"过时了"，直接归档

## 关键约定

1. **所有内容必须经过 triage** — 不能直接从 inbox 到 active
2. **就绪检查清单是强制门禁** — 10 项全部通过才能发布
3. **归档优先于删除** — 过时内容先归档，确认无用后再删除
4. **定期评审不可跳过** — 到期的评审必须在 2 周内完成
5. **curator 有最终决定权** — 关于内容质量和目录结构的争议由 curator 裁定
6. **移动文件需更新引用** — 移动文件时必须更新所有 `related` 字段中的引用
7. **每次评审更新 last_verified** — 评审通过后立即更新验证日期
8. **废弃内容标记 superseded_by** — 当文件被新文件替代时，必须标记替代关系
9. **合并冲突优先准确性** — 以更准确、更完整的版本为准
10. **每季度运行健康度检查** — 生成质量报告，跟踪改进进展
