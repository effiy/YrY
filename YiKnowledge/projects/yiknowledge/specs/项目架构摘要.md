# YiKnowledge 项目架构摘要

> YiKnowledge 是 YrY 单仓的共享知识库，服务于人类（文档）和 AI（RAG 数据源）。8 个角色目录，4 个流水线阶段，严格的 frontmatter 和命名规范。

## 核心定位

| 维度 | 说明 |
|---|---|
| 类型 | Markdown 知识库 |
| 服务对象 | 人类（文档阅读）+ AI（YiAi RAG 数据源） |
| 内容语言 | 中文为主，英文为辅 |
| 存储方式 | Git 仓库 + MongoDB（YiAi 知识监听器同步） |

## 8 个角色目录

| 角色目录 | 核心问题 | 主要子目录 |
|---|---|---|
| `engineer/` | 如何实现？ | 架构、开发、质量、数据、可靠性、流程、经验教训、项目 |
| `leader/` | 如何决策？ | 架构决策、能力规划、风险管理、路线图 |
| `producter/` | 做什么产品？ | 框架、需求发现、交付、策略、项目 |
| `aier/` | 如何使用 AI？ | 基础、方法论、平台、机器学习 |
| `srer/` | 如何确保稳定性？ | 事件响应、可观测性、发布管理 |
| `executiver/` | 如何做业务？ | 战略、行业、路线图、阅读清单 |
| `curator/` | 如何管理知识库？ | 治理、图表、模板、归档 |
| `projects/` | 项目知识中心 | 8 个项目的需求、文档、缺陷 |

## 4 个流水线阶段

```
inbox → triage → active → reference → archive
  │       │         │          │          │
  │       │         │          │          └── 已归档（不再使用但保留）
  │       │         │          └── 参考（稳定，偶尔查阅）
  │       │         └── 活跃（正在使用和维护）
  │       └── 评审中（内容已创建，待验证）
  └── 收件箱（新创建，待分类）
```

### 阶段流转规则

| 阶段 | 标识 | 进入条件 | 退出条件 |
|---|---|---|---|
| `inbox` | 收件箱 | 文件刚创建 | 通过 triage 评审 |
| `triage` | 评审中 | 内容完整待验证 | 通过就绪检查清单 |
| `active` | 活跃 | 内容已发布并验证 | 不再需要频繁更新 |
| `reference` | 参考 | 内容稳定，偶尔查阅 | 内容过时 |
| `archive` | 归档 | 内容已过时 | — |

## 文件命名约定

### 规则

| 规则 | 说明 |
|---|---|
| kebab-case | 全小写英文，连字符分隔 |
| 无下划线 | 禁止 `_` |
| 无数字 | 禁止数字（文件名中） |
| 无空格 | 禁止空格 |
| 中文语义 | 保留在 frontmatter `title` 中，不出现在文件名 |

### 示例

```

bad:  knowledge_lifecycle.md
bad:  knowledge123.md
bad:  Knowledge Lifecycle.md
```

## 目录层级约束

- **最多 3 级**：`role/problem-domain/file.md`
- 示例：`engineer/learn/projects/yivad-architecture.md`
- 超过 3 级的目录结构会被拒绝

## 与 YiAi RAG 的关系

```
YiKnowledge/ (Markdown tree)
     │
     │ YiAi knowledge watcher (apscheduler, 每 5s 轮询)
     │
     ├── MongoDB (文件元数据 + 内容)
     │
     └── llama_index 向量索引 (RAG 语义检索)
           │
           └── YiAi BRD Agent (基于知识库的智能问答)
```

YiAi 的知识监听器：
- 每 5 秒扫描 YiKnowledge 目录变化
- 解析 frontmatter 元数据
- 将内容和元数据写入 MongoDB
- 构建 llama_index 向量索引用于语义检索

## RAG 检索优化

### 分块策略

YiAi 的 llama_index 使用以下分块策略将 YiKnowledge 文件转换为向量索引：

| 参数 | 默认值 | 说明 |
|---|---|---|
| 分块大小 | 512 tokens | 每个 chunk 的 token 数，约 300-400 中文字符 |
| 分块重叠 | 50 tokens | 相邻 chunk 之间的重叠 token 数，保证语义连续性 |
| 分块模式 | 按二级标题 | 优先以 `## ` 标题为边界切分，保持语义完整性 |
| 最小分块 | 100 tokens | 不足此长度的段落与相邻段落合并 |
| 元数据注入 | frontmatter 全量 | 每个 chunk 注入文件 frontmatter 元数据，提升过滤精度 |

### 分块对内容结构的影响

```
文件结构 → 分块结果

# 一级标题 (文件主题)
> 摘要 (注入每个 chunk 的元数据)

## 二级标题 A (独立 chunk 1)
内容 A...

## 二级标题 B (独立 chunk 2)
内容 B...

## 二级标题 C (独立 chunk 3)
内容 C...

# 效果：每个二级标题成为一个独立的知识单元，可被单独检索
```

### 嵌入模型

| 属性 | 当前配置 |
|---|---|
| 模型 | Ollama 本地嵌入模型（如 nomic-embed-text） |
| 向量维度 | 768 维 |
| 相似度算法 | 余弦相似度 |
| 索引类型 | llama_index VectorStoreIndex |
| 检索模式 | 混合检索（语义 + 关键词） |
| 检索 Top-K | 默认 5，可配置 |

### 检索优化建议

| 优化方向 | 具体措施 | 预期效果 |
|---|---|---|
| 标题优化 | 二级标题包含领域关键词，结构清晰 | 提升分块质量，提高检索精度 |
| 摘要增强 | 引用块摘要包含核心关键词和主题 | 作为语义锚点，提升向量匹配质量 |
| 内容结构化 | 多用表格和列表，少用长段落 | 向量模型对结构化数据语义理解更好 |
| 自包含段落 | 每个二级标题下内容可独立理解 | 分块后每个 chunk 都是完整知识单元 |
| 关键词密度 | 核心术语在正文中自然出现 3-5 次 | 提升关键词匹配的召回率 |
| 元数据丰富 | frontmatter 字段完整，标签语义化 | 提升元数据过滤的精确率 |

### 检索效果指标

| 指标 | 说明 | 目标值 |
|---|---|---|
| 召回率 (Recall) | 相关文件被检索到的比例 | >= 90% |
| 精确率 (Precision) | 检索结果中相关文件的比例 | >= 80% |
| 首条命中率 (Hit@1) | 第一个结果就是最相关文件的比例 | >= 70% |
| 平均倒数排名 (MRR) | 最相关文件在结果中排名的倒数均值 | >= 0.8 |

| 关系类型 | 推断方式 | 示例 |
|---|---|---|
| 主题相似 | 相同 tags 或 category 前缀 | 同一 `category` 下的文件属于同一主题域 |

### 监听器工作流程

| 步骤 | 操作 | 触发条件 | 耗时 |
|---|---|---|---|
| 1. 目录扫描 | 遍历 YiKnowledge 目录，获取所有 .md 文件列表 | 定时器触发（每 5s） | < 100ms |
| 2. 变更检测 | 对比文件哈希值与上次扫描结果 | 文件哈希变化 | < 50ms |
| 3. Frontmatter 解析 | YAML 解析 frontmatter，提取元数据 | 文件有变更 | < 10ms |
| 4. MongoDB 写入 | 使用 motor 异步写入/更新 MongoDB 文档 | 解析成功 | < 50ms |
| 5. 向量索引更新 | 重新分块、嵌入、索引变更文件 | MongoDB 写入成功 | 1-5s |

```
用户查询 → YiAi BRD Agent
              │
              ▼
        查询嵌入 (Ollama embedding)
              │
              ▼
        llama_index 混合检索
              │
              ├── 语义检索 (向量相似度)
              │   └── Top-K 最相关的 chunk
              │
              ├── 关键词检索 (BM25)
              │   └── 关键词匹配的 chunk
              │
              └── 元数据过滤 (frontmatter)
                  └── 按 tags/category/roles 过滤
              │
              ▼
        结果融合 (RRF: Reciprocal Rank Fusion)
              │
              ▼
        返回 Top-K 结果 + 源文件引用
              │
              ▼
        LLM 生成回答（基于检索到的知识）
```

### 新鲜度监控脚本

```bash
#!/bin/bash
# freshness-check.sh — 检查内容新鲜度

echo "=== YiKnowledge 内容新鲜度检查 ==="
echo "日期: $(date +%Y-%m-%d)"
echo ""

TODAY=$(date +%s)

# 统计总文件数
TOTAL=$(find YiKnowledge/ -name "*.md" | wc -l | tr -d ' ')
echo "总文件数: $TOTAL"

# 平均最后更新天数
TOTAL_DAYS=0
COUNT=0
for f in $(find YiKnowledge/ -name "*.md"); do
    updated=$(grep "^updated:" "$f" | head -1 | awk '{print $2}')
    if [ -n "$updated" ] && [ "$updated" != "null" ]; then
        updated_ts=$(date -j -f "%Y-%m-%d" "$updated" +%s 2>/dev/null || echo 0)
        if [ "$updated_ts" -gt 0 ]; then
            diff_days=$(( (TODAY - updated_ts) / 86400 ))
            TOTAL_DAYS=$((TOTAL_DAYS + diff_days))
            COUNT=$((COUNT + 1))
        fi
    fi
done
if [ "$COUNT" -gt 0 ]; then
    AVG_DAYS=$((TOTAL_DAYS / COUNT))
    echo "平均最后更新天数: $AVG_DAYS 天"
else
    echo "平均最后更新天数: 无数据"
fi

# 长期未更新文件 (active 但超过 180 天未更新)
echo ""
echo "=== 长期未更新文件 (active, >180 天) ==="
FOUND=0
for f in $(grep -rl "lifecycle: active" YiKnowledge/ --include="*.md"); do
    updated=$(grep "^updated:" "$f" | head -1 | awk '{print $2}')
    if [ -n "$updated" ] && [ "$updated" != "null" ]; then
        updated_ts=$(date -j -f "%Y-%m-%d" "$updated" +%s 2>/dev/null || echo 0)
        diff_days=$(( (TODAY - updated_ts) / 86400 ))
        if [ $diff_days -gt 180 ]; then
            echo "  [${diff_days} 天] $f"
            FOUND=$((FOUND + 1))
        fi
    fi
done
if [ "$FOUND" -eq 0 ]; then
    echo "  无"
fi

# 超期未评审文件
echo ""
echo "=== 超期未评审文件 ==="
FOUND=0
for f in $(find YiKnowledge/ -name "*.md"); do
    review_cycle=$(grep "review_cycle:" "$f" | head -1 | awk '{print $2}')
    last_verified=$(grep "last_verified:" "$f" | head -1 | awk '{print $2}')
    if [ -z "$last_verified" ] || [ "$last_verified" = "null" ]; then
        continue
    fi
    verified_ts=$(date -j -f "%Y-%m-%d" "$last_verified" +%s 2>/dev/null || echo 0)
    diff_days=$(( (TODAY - verified_ts) / 86400 ))

    case "$review_cycle" in
        weekly)   [ $diff_days -gt 7 ]   && echo "  [${diff_days} 天] $f" && FOUND=$((FOUND + 1)) ;;
        monthly)  [ $diff_days -gt 30 ]  && echo "  [${diff_days} 天] $f" && FOUND=$((FOUND + 1)) ;;
        quarterly) [ $diff_days -gt 90 ] && echo "  [${diff_days} 天] $f" && FOUND=$((FOUND + 1)) ;;
        yearly)   [ $diff_days -gt 365 ] && echo "  [${diff_days} 天] $f" && FOUND=$((FOUND + 1)) ;;
    esac
done
if [ "$FOUND" -eq 0 ]; then
    echo "  无"
fi

echo ""
echo "=== 检查完成 ==="
```

# 不要这样做 — 600 行的超大文件

# 不要这样做 — 没有 frontmatter 的文件

# 即使内容不完整，frontmatter 也必须完整

title: 草稿标题

### 反模式 5：不要忽略内容新鲜度

```markdown
# 不要这样做 — 创建后从不更新
# 2025 年的内容，2026 年仍在用，但信息已过时
# RAG 检索到过时信息，AI 基于错误知识生成回答

# 应该这样做 — 定期评审和更新
# 1. 按 review_cycle 定期检查内容准确性
# 2. 更新 last_verified 字段
# 3. 如果内容过时无法更新，标记为 deprecated 并归档
```

### 反模式 6：不要建立单向知识孤岛

```yaml
# 不要这样做 — 文件没有任何交叉引用
# frontmatter 中没有 related 字段
# 这个文件在知识图谱中是一个孤岛，无法被关联检索到

# 应该这样做 — 建立双向交叉引用
related:
  - ./related-file-1.md
  - ./related-file-2.md
# 同时在 related-file-1.md 和 related-file-2.md 中也引用此文件
```

## 关键约束

1. **Frontmatter 必填** — 所有知识文件必须包含完整的 frontmatter
2. **kebab-case 命名** — 文件名必须遵循 kebab-case 约定
3. **3 级目录限制** — 目录深度不超过 3 级
4. **角色边界** — 内容必须放在正确的角色目录下
5. **就绪检查清单** — 发布前必须通过 10 项自检
6. **中文内容** — 所有内容使用中文编写
7. **RAG 优化** — 每个二级标题为自包含知识单元，方便分块检索
8. **内容新鲜度** — 按 review_cycle 定期评审，确保内容准确有效
9. **交叉引用** — 所有文件建立双向链接，避免知识孤岛
10. **文件大小控制** — 单文件不超过 500 行，超大文件拆分为多个主题文件
