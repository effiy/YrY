# YK-09-105: 自定义元数据模式 — 可扩展的 Schema 定义与动态表单生成

> 需求编号：YK-09-105 · 优先级：P2 · 人天：0.3d · 状态：需求已编写
> 依赖：YK-09-01（Frontmatter 规范）、YK-09-05（项目知识中心）、YK-09-102（自动化分类与标签体系）

## 背景

YiKnowledge 当前所有文件使用统一的 frontmatter 格式（`title`、`tags`、`category`、`created`、`updated`、`source`、`type`、`status`、`priority` 等），由 YK-09-01 定义。这种统一格式保证了基础元数据的一致性，但无法满足不同内容类型的特殊需求。

**已知案例：** 2026-08-25 策展人收到 `projects/` 目录下 3 个项目的需求文档贡献，贡献者希望在 frontmatter 中添加项目特有的元数据：YiPet 需求文档需要 `chrome_api_version` 和 `manifest_version` 字段，YiVad 需求文档需要 `vue_version` 和 `component_count` 字段，YiAi 需求文档需要 `python_version` 和 `endpoint_count` 字段。这些字段无标准定义，贡献者自行在 frontmatter 中添加后，YiAi 的知识扫描器因前端未定义字段而忽略它们，RAG 检索也无法利用这些元数据提升搜索精准度。更严重的是，3 个贡献者使用了不同的字段命名（如 `vueVersion` vs `vue_version` vs `Vue版本`），导致相同含义的元数据无法聚合分析。

当前元数据体系的核心痛点：
- **Frontmatter 字段固定**：YK-09-01 定义了 10 个标准字段，所有文件必须使用相同字段，无法按内容类型定制
- **无 Schema 验证**：贡献者自行添加字段时无格式校验，字段名不规范（camelCase、snake_case、中文混用），字段类型不确定（版本号可能是字符串 "3.5" 或数字 3.5）
- **RAG 无法利用自定义元数据**：知识扫描器只解析已知字段，自定义字段被忽略，搜索时无法按自定义字段过滤
- **无 Schema 版本管理**：元数据字段变更时（如 `vue_version` → `vue_major_version` + `vue_minor_version`），已有文件无法自动迁移
- **无 UI 辅助**：贡献者通过文本编辑器手动编写 frontmatter YAML，无表单提示，容易出错

**目标：** 构建自定义元数据 Schema 系统，实现 Schema 定义（字段名、类型、约束）、Schema 验证（保存时自动校验 frontmatter）、按分类的 Schema 模板、Schema 版本化与迁移、Schema 导入/导出、UI 表单自动生成和 Schema 使用分析。

### 影响范围

- **贡献者体验**：表单化的元数据编辑器降低 frontmatter 编写门槛，类型校验防止格式错误
- **策展人治理**：按分类定义 Schema 确保不同类型内容有合适的元数据，策展人可统一管理字段规范
- **RAG 检索质量**：自定义元数据被索引后，搜索可按 `python_version:3.10` 等字段过滤，提升精准度
- **知识库扩展性**：Schema 系统支持未来新增内容类型时快速定义专属元数据，无需修改核心代码

| 含义 | 实际使用的字段名 | 文件数 | 问题 |

**结论：** 30 个自定义字段使用了 19 种不同的命名风格，规范化率仅 37%。无 Schema 约束是命名混乱的根本原因。

### 1.3 当前工作流

```
贡献者编写文件
  → 手动编写 frontmatter（凭记忆复制已有文件的字段）
  → 需要自定义字段时自行添加（凭感觉命名，无校验）
  → 提交 PR / 文件
  → 策展人审查（手动检查 frontmatter 格式，无法校验自定义字段）
  → 发现问题 → 反馈修正（命名不统一、类型错误）
  → 合并
  → YiAi 知识扫描器解析 frontmatter（仅解析已知字段，自定义字段忽略）
```

**问题：** 自定义字段从创建到使用全程无规范约束。贡献者自行命名 → 策展人无法校验 → 扫描器忽略 → RAG 无法利用。自定义字段形同虚设。

## 二、设计决策

### 决策 1：Schema 存储方式 — YAML 文件 vs MongoDB vs 两者兼有

| 维度 | YAML 文件（Git 版本控制） | MongoDB（动态查询） | 两者兼有 |
|------|------|------|------|
| 版本控制 | 好（Git 历史 + PR 审核） | 差（无版本历史） | 好（YAML 为主，MongoDB 为缓存） |
| 查询性能 | 差（需读取文件） | 好（数据库查询 < 10ms） | 好（MongoDB 缓存） |
| 策展人编辑体验 | 中（需编辑 YAML 文件） | 好（YiVad 可视化编辑） | 好（可视化编辑 → 同步 YAML） |
| Schema 迁移 | 中（手动编辑 YAML） | 好（程序化迁移） | 好 |
| 实现复杂度 | 低 | 中 | 中 |

**选择：两者兼有。** YAML 文件作为 Schema 的权威来源（Git 版本控制），MongoDB 作为运行时缓存（快速查询）。YiVad 可视化编辑器修改时同步写入 YAML 文件和 MongoDB。

### 决策 2：Schema 验证时机 — 保存时验证 vs 提交时验证 vs 两者

| 维度 | 保存时验证 | 提交时验证 | 两者兼有 |
|------|------|------|------|
| 用户体验 | 好（即时反馈） | 中（延迟反馈） | 最好 |
| 覆盖范围 | YiVad 编辑器保存 | Git 提交、API 写入 | 全场景覆盖 |
| 实现复杂度 | 低 | 中 | 中 |

**选择：两者兼有。** YiVad 编辑器保存时即时验证（前端表单校验），YiAi API 写入时服务端验证（后端 Schema 校验），确保所有写入路径都经过验证。

### 决策 3：UI 表单生成 — 纯前端渲染 vs 服务端驱动

| 维度 | 纯前端渲染（Schema → Vue 组件） | 服务端驱动（后端返回表单配置） |
|------|------|------|
| 灵活性 | 高（前端完全控制渲染） | 中（后端定义表单结构） |
| Schema 同步 | 需前端拉取 Schema | 后端自动同步 |
| 实现复杂度 | 中 | 低 |

**选择：服务端驱动。** 后端根据 Schema 定义生成表单配置（JSON Schema Form 格式），前端使用通用表单渲染器（如 `vue-json-schema-form`）渲染。降低前端实现复杂度，确保表单逻辑与 Schema 定义一致。

### 设计决策记录

| 决策 | 选项 A | 选项 B | 选项 C | 选择 | 理由 |
|------|--------|--------|--------|------|------|
| Schema 存储方式 | YAML 文件 | MongoDB | 两者兼有 | **两者兼有** | YAML 为权威来源（Git），MongoDB 为运行时缓存 |
| Schema 验证时机 | 保存时 | 提交时 | 两者兼有 | **两者兼有** | 覆盖前端编辑和后端 API 所有写入路径 |
| UI 表单生成 | 纯前端渲染 | 服务端驱动 | — | **服务端驱动** | 确保表单逻辑与 Schema 一致，降低前端复杂度 |

## 三、目标架构

### 3.1 自定义元数据 Schema 系统整体流程

```
策展人定义 Schema
  → 选择分类（如 "projects/yivad/requirements"）
  → 定义自定义字段
      ├── 字段名（field_name: "vue_version"）
      ├── 字段类型（type: string）
      ├── 是否必填（required: false）
      ├── 默认值（default: "3.5"）
      ├── 字段描述（description: "Vue 主版本号"）
      └── 枚举值（enum: ["3.0", "3.5"]）（仅 enum 类型）
  → Schema 保存（YAML 文件 + MongoDB 缓存）
  → Schema 版本号自动递增

贡献者编辑文件
  → 前端根据 Schema 生成表单
  → 填写自定义字段
  → 保存时 Schema 验证
      ├── 必填字段检查
      ├── 类型检查（string/number/date/enum/list/reference）
      ├── 枚举值检查（值必须在 enum 列表中）
      └── 引用完整性检查（reference 类型指向的文件存在）
  → 验证通过 → 保存
  → 验证失败 → 显示错误提示

Schema 版本迁移
  → 策展人更新 Schema（新增字段、修改类型、删除字段）
  → 系统检测已有文件与新 Schema 不兼容
  → 生成迁移计划（显示受影响文件列表）
  → 策展人确认迁移
  → 批量更新文件 frontmatter（自动填充默认值、转换类型）
  → 迁移完成，Schema 版本号递增
```

### 3.2 Schema 数据模型

```python
# YiAi/src/domain/knowledge/schema/models.py — 新增

@dataclass
class MetadataSchema:
    """元数据 Schema 定义"""
    schema_id: str                      # Schema ID（如 "projects/yivad/requirements"）
    category: str                       # 适用的分类路径
    version: int                        # Schema 版本号（从 1 开始递增）
    display_name: str                   # 显示名称（如 "YiVad 需求文档元数据"）
    description: str                    # Schema 描述
    extends: str | None                 # 继承的父 Schema ID（如 "base_requirement"）
    fields: list[SchemaField]           # 自定义字段列表
    standard_frontmatter: list[str]     # 继承的标准 frontmatter 字段（来自 YK-09-01）
    created_at: datetime
    updated_at: datetime
    created_by: str

@dataclass
class SchemaField:
    """Schema 字段定义"""
    field_name: str                     # 字段名（snake_case，如 "vue_version"）
    display_name: str                   # 显示名称（如 "Vue 版本"）
    field_type: str                     # 字段类型：string | number | date | enum | list | reference
    required: bool                      # 是否必填
    default: Any | None                 # 默认值
    description: str                    # 字段描述（帮助文本）
    placeholder: str | None             # 输入框占位符
    order: int                          # 排序（表单中显示顺序）
    # 类型特定属性
    min_length: int | None              # string 最小长度
    max_length: int | None              # string 最大长度
    min_value: float | None             # number 最小值
    max_value: float | None             # number 最大值
    enum_values: list[str] | None       # enum 枚举值列表
    list_item_type: str | None          # list 元素类型
    reference_category: str | None      # reference 引用的分类
    pattern: str | None                 # 正则验证模式
    deprecated: bool                    # 是否已废弃（保留用于迁移）

@dataclass
class SchemaValidationResult:
    """Schema 验证结果"""
    valid: bool                         # 是否通过验证
    errors: list[SchemaValidationError] # 验证错误列表
    warnings: list[SchemaValidationWarning]  # 警告列表

@dataclass
class SchemaValidationError:
    """验证错误"""
    field_name: str                     # 字段名
    error_type: str                     # 错误类型：missing_required | type_mismatch | enum_invalid | reference_invalid | pattern_mismatch
    message: str                        # 错误消息（中文）
    expected: str                       # 期望值
    actual: str                         # 实际值

@dataclass
class SchemaValidationWarning:
    """验证警告"""
    field_name: str                     # 字段名
    message: str                        # 警告消息
    suggestion: str                     # 修复建议
```

| 回滚场景 | 回滚方式 | 影响范围 | 恢复时间 |

- MongoDB Schema 缓存可用作 YAML 文件的备份恢复源

## 九、设计决策记录

### D-01: 为什么使用 JSON Schema Form 标准而非自定义表单协议？

JSON Schema Form 是业界标准（如 React JSON Schema Form、Vue JSON Schema Form），定义了从 JSON Schema 到表单 UI 的映射规则。使用标准格式意味着前端可直接使用成熟的组件库（`vue-json-schema-form`），无需自行实现字段类型 → 表单控件的映射逻辑。自定义表单协议虽然灵活，但需要维护前端渲染器，工作量远超使用标准格式。

### D-02: 为什么 Schema 继承使用 `extends` 而非 `includes`？

`extends`（继承）语义更准确：子 Schema 继承父 Schema 的所有字段，并可覆盖字段属性。`includes`（包含）意为"引用"，暗示子 Schema 和父 Schema 是并列关系而非层级关系。继承关系更符合实际场景：基础需求 Schema 定义了通用字段，各项目需求 Schema 在此基础上扩展专属字段。

### D-03: 为什么 Schema 版本化使用递增整数而非语义化版本（SemVer）？

Schema 版本化场景简单：每次 Schema 修改都是一个新版本，不存在 Major/Minor/Patch 的语义区分。递增整数（1, 2, 3...）简单直观，避免语义化版本的认知负担。如果未来需要区分"破坏性变更"（Major）和"兼容性变更"（Minor），可引入语义化版本，但当前需求不涉及此复杂度。

### D-04: 为什么前端表单由服务端驱动而非前端自行解析 Schema？

前端自行解析 Schema 存在两个问题：1) 前端需要内嵌 Schema 解析逻辑，与后端逻辑重复；2) Schema 定义变更时前端需要同步更新。服务端驱动方案中，后端根据 Schema 生成表单配置，前端仅负责渲染，确保表单逻辑始终与 Schema 定义一致。前端只需维护一个通用表单渲染器，降低了维护成本。

### D-05: 为什么 Schema 模板同时存储在 YAML 文件和 MongoDB 中？

YAML 文件是 Schema 的权威来源，受 Git 版本控制，支持 PR 审核流程。MongoDB 缓存提供快速查询（< 10ms），避免每次验证时读取 YAML 文件（文件 I/O > 50ms）。两者通过同步机制保持一致：YAML 文件变更时自动更新 MongoDB 缓存，YiVad 可视化编辑时同步写入 YAML 文件和 MongoDB。

## 十二、回归问题预测

| # | 问题 | 发现场景 | 根因 | 修复方式 |
|---|------|---------|------|---------|
| 1 | Schema 验证引擎在 frontmatter 包含嵌套对象时崩溃：贡献者在 frontmatter 中添加了嵌套 YAML 结构（如 `dependencies: { vue: "3.5", pinia: "2.1" }`），Schema 验证引擎仅支持扁平字段，解析嵌套对象时抛出 `TypeError` | 贡献者参考其他项目的 frontmatter 格式，在 YiKnowledge 文件中添加了嵌套依赖信息。保存时验证引擎崩溃（500 错误），文件无法保存。贡献者去掉嵌套结构后保存成功，但丢失了依赖信息 | Schema 验证引擎假定所有自定义字段为扁平类型（string/number/enum/list），未处理嵌套对象和数组。`list` 类型仅支持 `list[str]`，不支持 `list[dict]` | 扩展 `field_type` 支持 `object` 和 `list[object]` 类型；嵌套对象 Schema 定义为子 Schema（`nested_schema` 引用）；验证引擎递归处理嵌套结构；首期可标记嵌套字段为"跳过验证"（仅保存，不校验结构） |
| 2 | Schema 迁移脚本在批量更新文件时因编码问题导致中文乱码：迁移脚本读取文件 → 修改 frontmatter → 写回文件，但文件包含中文内容（如 `description: "需求涉及的 Vue 主版本号"`），写回时编码从 UTF-8 变为 ASCII，中文字符变为乱码 | 迁移执行后，策展人发现 12 个文件的中文内容（标题、描述、正文）出现乱码（如 "Vue \\u4e3b\\u7248\\u672c\\u53f7"）。文件内容不可读，策展人从 Git 历史恢复文件 | 迁移脚本使用 Python 的 `open(file, 'w')` 写入文件，默认编码为平台相关（Windows 为 GBK，Linux/macOS 为 UTF-8）。YAML 序列化时 `yaml.dump()` 未指定 `allow_unicode=True`，中文字符被转义为 Unicode 转义序列 | 迁移脚本强制使用 UTF-8 编码读写文件（`open(file, 'w', encoding='utf-8')`）；YAML 序列化使用 `yaml.dump(data, allow_unicode=True)`；迁移前检查文件编码，非 UTF-8 文件先转换编码 |
| 3 | 表单生成器为 `reference` 类型字段生成的文件选择器性能差：文件选择器需要加载所有 800+ 文件列表供贡献者选择，页面加载时一次性请求全部文件，导致表单渲染耗时 > 3 秒 | 贡献者编辑文件时，表单中有一个 `reference` 类型字段（引用关联文件），文件选择器下拉框加载了 800+ 个文件选项。页面卡顿 3 秒后渲染完成，贡献者反馈"下拉框太卡，滚动不流畅" | 文件选择器使用同步加载模式，一次性获取全部文件列表。800+ 文件 × 平均 80 字节文件名 = 64KB 数据，但 DOM 渲染 800+ 个 `<option>` 元素导致浏览器重排性能问题 | 文件选择器改为异步搜索模式（输入关键词后搜索，延迟 300ms 防抖）；搜索结果限制 20 条；支持分类过滤（按角色目录缩小范围）；虚拟滚动渲染大量选项 |
| 4 | Schema 使用分析将临时测试文件计入统计，导致字段使用率数据失真：策展人在 `projects/` 目录下创建了 5 个测试文件（文件名包含 `test-` 前缀），用于验证 Schema 功能。这些测试文件包含所有自定义字段，但分析引擎将其计入正式统计，导致"字段使用率 100%"的假象 | 策展人查看 Schema 使用分析，发现 `vue_version` 字段使用率 100%，但实际正式需求文档中仅 60% 填写了该字段。排查发现 5 个测试文件被计入统计，拉高了使用率 | 分析引擎的 `get_schema_usage()` 方法查询所有匹配分类的文件，未过滤测试文件。测试文件与正式文件在同一分类下，无法区分 | 分析引擎排除 `status=测试` 或 `type=测试` 的文件（基于 frontmatter 的 `status` 和 `type` 字段）；文件名包含 `test-` 或 `-test` 的文件默认排除；提供 `include_test_files` 参数允许策展人选择 |
| 5 | Schema 版本升级后，RAG 索引中仍保留旧字段名，搜索过滤使用旧字段名无结果：Schema v1 定义 `vue_version`（string），v2 改为 `vue_major_version`（enum）。迁移后文件 frontmatter 已更新，但 RAG 索引未重建，搜索 `vue_version:3.5` 无结果，搜索 `vue_major_version:3.5` 也无结果（索引中字段名仍为 `vue_version`） | 贡献者搜索 `vue_major_version:3.5` 过滤需求文档，返回 0 条结果。但实际上有 12 个文件已迁移到 v2 Schema 且 `vue_major_version` = "3.5"。排查发现 RAG 索引中仍使用旧字段名 `vue_version`，搜索新字段名无法匹配 | Schema 迁移仅修改了文件 frontmatter，未触发 RAG 索引重建。Knowledge Watcher 的文件变更检测依赖文件修改时间，迁移脚本批量修改文件后，部分文件的 `updated` 时间戳未更新（迁移脚本仅修改 frontmatter 字段，未更新 `updated` 字段），Watcher 未检测到变更 | Schema 迁移完成后触发受影响的文件重新索引（调用 `knowledge.reindex_files`）；迁移脚本更新文件的 `updated` 字段为迁移时间；RAG 搜索支持字段别名（旧字段名 `vue_version` 映射到新字段名 `vue_major_version`） |
| 6 | 多个 Schema 匹配同一文件时，验证引擎选择错误的 Schema：文件 `projects/yivad/requirements/2026-09/xxx.md` 的分类路径为 `projects/yivad/requirements`，同时匹配 `projects/yivad/requirements` Schema 和 `projects/` Schema（通配 Schema）。验证引擎选择了 `projects/` Schema，导致缺少 `vue_version` 必填字段验证 | 贡献者提交文件后，策展人审查时发现 `vue_version` 字段为空（应为必填），但验证引擎未报告错误。排查发现验证引擎匹配了 `projects/` Schema（该 Schema 无 `vue_version` 字段），而非更具体的 `projects/yivad/requirements` Schema | Schema 匹配使用第一个匹配的 Schema（按注册顺序），而非最具体的 Schema。`projects/` Schema 在注册表中排在 `projects/yivad/requirements` Schema 之前，导致通配匹配优先 | Schema 匹配使用"最长路径匹配"策略：优先匹配分类路径最长的 Schema（`projects/yivad/requirements` 优先于 `projects/`）；匹配失败时回退到父分类 Schema；Schema 注册表按分类路径长度排序 |

## 十三、性能分析

### 自定义元数据 Schema 系统操作耗时

| 操作 | 耗时 | 说明 |
|------|------|------|
| Schema 加载（YAML 文件） | ~10ms | 读取 YAML 文件 + 解析 |
| Schema 加载（MongoDB 缓存） | ~5ms | 单次 MongoDB 查询 |
| Schema 验证（单文件） | ~5ms | 遍历字段 + 类型检查 |
| Schema 验证（复杂嵌套） | ~15ms | 递归验证嵌套对象 |
| 表单配置生成 | ~20ms | Schema → JSON Schema Form 映射 |
| 迁移试运行（100 文件） | ~2s | 100 × (读取 + 模拟变更 + 对比) |
| 迁移执行（100 文件） | ~5s | 100 × (读取 + 修改 + 写入) |
| Schema 使用分析（单 Schema） | ~50ms | MongoDB 聚合查询 |
| Schema 导入/导出 | ~10ms | YAML 序列化/反序列化 |
| **单文件保存流程（含验证）** | **~20ms** | 文件写入 + Schema 验证 |

### 存储开销

| 项目 | 大小 | 说明 |
|------|------|------|
| 单个 Schema（YAML 文件） | ~2KB | 约 5 个字段的 Schema 定义 |
| Schema 模板目录（10 个 Schema） | ~20KB | 覆盖主要分类 |
| MongoDB Schema 缓存 | ~20KB | 与 YAML 文件同步 |
| Schema 迁移历史 | ~1KB/次 | 每次迁移记录 |
| Schema 使用分析缓存 | ~5KB | 聚合统计数据 |
| 单文件自定义字段（frontmatter） | ~200B | 额外 3-5 个字段 |
