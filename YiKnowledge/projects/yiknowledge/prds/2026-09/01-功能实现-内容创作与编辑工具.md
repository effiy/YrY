## 背景

### 问题陈述

YiKnowledge 知识库的内容创作工具链存在严重的能力缺口。当前编辑体验停留在基础 textarea 级别——编辑与预览分离、无字数统计、无文档大纲、无专注模式、无快捷工具栏、图片插入需手动操作、Frontmatter 手写易出错。作为知识库使用频率最高的工具，编辑器缺乏现代编辑器应具备的标准能力。

更严重的是，围绕编辑器的辅助工具链几乎全部缺失：写作者面对空白页时无 AI 大纲生成和模板辅助；多人协作时无协同编辑和审阅机制；内容修改后无版本历史回溯能力；内容分发时无翻译管道和导出管道；外部内容引入时无导入向导和迁移助手。

**核心矛盾**：内容创作是知识库价值的起点，但当前工具链迫使创作者自行处理所有辅助工作——大纲规划、模板套用、格式转换、协作沟通、版本回溯——将大量时间消耗在"写"之外的事务上。一篇 3000 字架构设计文档的编写时间中，真正的"写作"仅占 30%，其余 70% 花在大纲规划、结构设计、图片处理、格式转换等辅助事务上。

| 挑战 | 说明 |

## 二、设计决策

### 决策 1：编辑器技术选型 — CodeMirror 6 vs Monaco vs 自研

| 维度 | CodeMirror 6 | Monaco Editor | 自研 textarea |
|------|-------------|--------------|--------------|
| 包大小 (gzip) | ~150KB | ~5MB | ~10KB |
| Markdown 支持 | 好（官方语言包） | 好 | 基础 |
| 扩展性 | 高（模块化架构） | 高 | 低 |
| 学习曲线 | 中 | 低（VS Code 核心） | 低 |
| 移动端适配 | 中 | 差（桌面优先） | 好 |
| 社区活跃度 | 高 | 高 | — |
| 与 YiKnowledge 适配 | 好（轻量知识库） | 差（体积过大） | 差（功能不足） |

**选择：CodeMirror 6。** Monaco 5MB 的体积对于知识库静态站点是不可接受的——单次页面加载的传输成本远超编辑器本身的价值。CodeMirror 6 的模块化设计允许按需加载 Markdown 语言包、预览扩展、折叠扩展，总计 gzip 约 150KB。虽然学习曲线略高于 Monaco，但 YiKnowledge 的编辑器场景不需要 Monaco 的完整 IDE 功能（代码补全、调试、重构等），CodeMirror 6 的 Markdown 编辑能力完全满足需求。

### 决策 2：分屏布局 — 左右分屏 vs 上下分屏 vs 可切换

| 维度 | 左右分屏 | 上下分屏 | 可切换 |
|------|---------|---------|--------|
| 空间利用效率 | 中（各50%宽度） | 高（全宽） | 高 |
| 长行文档体验 | 好（行宽不受限） | 差（长行需水平滚动） | 好 |
| 宽屏显示器（>1920px）| 最优 | 浪费垂直空间 | 最优 |
| 小屏设备（<1024px） | 差（太窄） | 好 | 好 |
| 实现复杂度 | 中 | 低 | 高 |

**选择：左右分屏（默认）+ 可切换。** 左右分屏是 VS Code、Notion 等主流编辑器的默认布局，用户习惯。针对不同场景提供切换按钮：上下分屏适合小屏设备或纵向文档，仅编辑模式适合专注写作，仅预览模式适合最终审核。分屏比例默认为 50:50，支持拖拽调整（25%-75%）。

### 决策 3：图片处理策略 — Base64 内嵌 vs 本地文件 vs OSS 上传

| 维度 | Base64 内嵌 | 本地文件（images/） | OSS/CDN |
|------|------------|-------------------|---------|
| 便携性 | 高（单文件自包含） | 中 | 低（依赖外部服务） |
| 文件大小 | 差（增大 33%） | 好 | 好 |
| 可维护性 | 差（不可独立管理） | 好 | 好 |
| 编辑体验 | 差（污染 Markdown 源文件） | 好 | 好 |
| 部署复杂度 | 低 | 低 | 高 |

**选择：本地文件（images/ 目录）。** 拖拽/粘贴的图片自动保存到文档同级或上级的 `images/` 子目录，生成规范的 Markdown 引用路径 `![描述](images/img-{timestamp}.{ext})`。Base64 方案会严重污染源文件——一个 100KB 的 PNG base64 编码后约 133KB 文本——Markdown 阅读体验极差。OSS 方案引入外部依赖——YiKnowledge 的设计原则是自包含。本地文件存储与 Git 版本管理天然兼容。

### 决策 4：Frontmatter 编辑 — 仅图形化 vs 仅源码 vs 双模式

| 维度 | 仅图形化面板 | 仅源码编辑 | 双模式 |
|------|------------|-----------|--------|
| 易用性 | 高（表单操作） | 低（需懂 YAML） | 高 |
| 灵活性（自定义字段） | 低 | 高 | 高 |
| 错误率 | 低（有校验） | 高（手动编写） | 低 |
| 实现复杂度 | 中 | 低 | 中 |

**选择：双模式（图形化面板 + 源码切换）。** 图形化面板显示标准字段（title/tags/category/created/updated/source/type/status），提供下拉选择、日期选择、标签输入等表单控件，带实时格式校验和必填字段红色提示。"编辑源码"按钮切换到 YAML 文本编辑器，支持编辑非标准自定义字段。两种模式的数据双向同步——在面板中修改后立即反映到 YAML 源码中。

### 决策 5：协同编辑冲突解决 — OT vs CRDT vs Git Merge

| 维度 | OT | CRDT | Git Merge + 编辑锁 |
|------|-----|------|-------------------|
| 实现复杂度 | 高（需中心服务器） | 高（复杂数据结构） | 低 |
| 离线支持 | 差 | 优秀 | 中 |
| 适用场景 | 实时高频协作 | 离线+实时 | 异步低频协作 |
| 并发上限 | 高 | 极高 | 低（2-3人） |
| 与 YiKnowledge 适配 | 过度设计 | 过度设计（远期） | **适合（近期）** |

**选择：近期 Git Merge + 编辑锁，远期规划 CRDT。** 知识库场景的协同编辑频率远低于 Google Docs——同一文件同时编辑的概率低于 5%。Git 的三路合并策略 + 编辑锁提示（文件打开时显示"xxx 正在编辑"）已满足 95% 的实际需求。远期（1-2 年后）当协作密度增长、出现高频协作场景时，可以引入 CRDT（如 Yjs）实现真正的实时协作。CRDT 的实现复杂度不应在早期阶段引入。

### 决策 6：AI 内容生成策略 — 纯 Prompt vs RAG 增强 vs Agent 迭代

| 维度 | 纯 Prompt | RAG 增强 | Agent 迭代 |
|------|----------|---------|-----------|
| 领域适配度 | 低（通用知识） | 高（注入 YiKnowledge 上下文） | 极高（自我改进） |
| 内容质量 | 中 | 高 | 极高 |
| 生成延迟 | < 3s | < 5s | 10-30s |
| 实现复杂度 | 低 | 中 | 高 |
| 适用场景 | 简单文案 | 常规内容生成 | 关键文档/高质量要求 |

**选择：RAG 增强作为默认模式，Agent 迭代作为高级选项。** RAG 增强从 YiKnowledge 已有知识库中检索同类文档，提取结构模式和领域术语，用于指导 LLM 生成——确保生成内容与项目保持一致。Agent 迭代模式（生成 → 评估 → 改进 × 3 轮）提供最高质量，但延迟 10-30 秒，作为可选的高级按钮。纯 Prompt 模式作为兜底——当 RAG 索引不可用时自动降级。

### 决策 7：翻译管道策略 — 纯机翻 vs 机翻+审阅 vs 纯人工

| 维度 | 纯机器翻译 | 机翻 + 人工审阅 | 纯人工翻译 |
|------|----------|---------------|-----------|
| 翻译质量 | 中（70-80% 可接受） | 高（95%+ 可接受） | 极高 |
| 时间成本 | < 10s/篇 | 人工审阅 5-15 分钟 | 人工翻译 30-60 分钟 |
| 术语一致性 | 差（无上下文） | 高（翻译记忆库） | 中（取决于译者） |
| 适用场景 | 快速了解、内部分享 | 公开发布的标准工作流 | 关键对外文档 |

**选择：机翻 + 人工审阅作为标准工作流。** 翻译记忆库（TM）是核心组件——存储已翻译的术语和段落，新翻译任务自动匹配。术语表确保关键词汇在全部文章中翻译一致。翻译质量评分（BLEU 1-4 gram + COMET 神经评分）辅助人工判断——评分 < 3.5 的翻译自动打回修改。

### 决策 8：大纲模板管理 — 硬编码 vs 文档提取 vs LLM 动态

| 维度 | 硬编码固定模板 | 从现有文档提取 | LLM 动态生成 |
|------|--------------|--------------|-------------|
| 模板数量 | 5 | 动态 | 无限 |
| 维护成本 | 低 | 中 | 低 |
| 领域适应性 | 低 | 中 | 高 |
| 结构一致性 | 高（统一标准） | 低（各文档各样式） | 中 |
| 实现复杂度 | 低 | 中 | 中 |

**选择：硬编码基础模板 + LLM 动态增强。** 5 种文档类型（需求文档/架构设计/故障复盘/操作手册/技术规范）的基础模板提供最低保证——确保常规文档的结构完整性。在 RAG 增强模式下，LLM 基于检索到的同类文档自动扩展基础模板——添加领域特定的章节。既保证了标准约束，又提供了领域灵活性。

## 四、核心功能设计

---

### 4.1 编辑器增强 (YK-09-203)

#### 4.1.1 功能概览

增强编辑器包含 7 个子功能：分屏预览、快捷工具栏、字数统计、文档大纲、专注模式、图片拖拽/粘贴处理、Frontmatter 图形化编辑面板。这些功能彼此独立但通过编辑器核心（EditorCore.vue）和状态管理（editor store）统一协调。

#### 4.1.2 分屏预览

**四种模式：**

| 模式 | 布局 | 适用场景 |
|------|------|----------|
| 左右分屏 | 编辑区 50% + 预览区 50% | 宽屏写作——默认模式 |
| 上下分屏 | 编辑区 50% + 预览区 50% | 小屏/纵向文档 |
| 仅编辑 | 编辑区 100% | 专注写作 |
| 仅预览 | 预览区 100% | 审核/阅读 |

**同步滚动机制：** 编辑区和预览区通过行号比例映射实现双向同步滚动：`scrollRatio = scrollTop / maxScroll`。使用 `requestAnimationFrame` 确保 60fps 流畅度。debounce 300ms 的预览更新避免 Markdown 解析开销——编辑时预览稍有延迟但不影响同步滚动的流畅性。

**分屏比例调整：** 拖拽分屏分隔线可调整比例（25%-75% 范围），比例值持久化到 localStorage。

**性能保障：** CodeMirror 6 的视口虚拟化仅渲染可见区域的文本行——2000 行文档实际 DOM 节点仅约 50 个（可见行）。预览区使用 unified/remark 解析 AST 后增量渲染——仅更新变更段落的 HTML。

#### 4.1.3 快捷工具栏

12 种快捷插入操作，支持两种插入模式：选中文本包裹（如选中文本后点击加粗 → `**选中文本**`）和光标处插入（如点击表格 → 在光标处插入表格模板）。

| 操作 | 快捷键 | 模板 | 模式 |
|------|--------|------|------|
| 加粗 | Ctrl+B | `**$SELECTION**` | wrap |
| 斜体 | Ctrl+I | `*$SELECTION*` | wrap |
| 删除线 | — | `~~$SELECTION~~` | wrap |
| 标题 | — | `\n## ` | insert |
| 无序列表 | — | `\n- ` | insert |
| 有序列表 | — | `\n1. ` | insert |
| 表格 | — | `\n\| 列1 \| 列2 \| 列3 \|\n\|-----\|-----\|-----\|\n\|  \|  \|  \|\n` | insert |
| 代码块 | — | `\n\`\`\`\n$SELECTION\n\`\`\`\n` | insert/wrap |
| 链接 | — | `[$SELECTION](url)` | insert/wrap |
| 图片 | — | `![$SELECTION](path)` | insert |
| 引用 | — | `\n> ` | insert |
| Mermaid | — | `\n\`\`\`mermaid\ngraph TD\n    A --> B\n\`\`\`\n` | insert |
| 分隔线 | — | `\n---\n` | insert |

#### 4.1.4 字数统计

实时统计四个维度：中文字符数（`[\u4e00-\u9fff]` 正则匹配）、英文单词数（`[a-zA-Z]+` 正则匹配）、总行数（`split('\n')`）、段落数（`split('\n\n')` 过滤空段落）、预估阅读时间（中文 400 字/分钟 + 英文 200 词/分钟 + 代码块 50-100 字/分钟修正）。

字数统计显示在编辑器底部状态栏，格式：`字符：1,234 · 行数：567 · 段落：89 · 阅读时间：~8 分钟`。支持设置目标字数——状态栏显示进度条（当前/目标），达标时进度条变绿色。

#### 4.1.5 文档大纲

基于 Markdown 标题层级（`#` 到 `######`）提取文档大纲，使用 unified/mdast 解析而非正则——避免代码块和 Frontmatter 中的 `#` 被误识别为标题。大纲以树形组件展示在侧边栏，支持折叠/展开，默认展开到 H3。

点击大纲中的标题 → 编辑器自动滚动到对应行并聚焦。当前章节高亮（基于编辑器可视区域中最上方的标题）。大纲与编辑器双向同步——编辑器滚动时大纲高亮跟随变化。

#### 4.1.6 图片拖拽/粘贴处理

**拖拽处理流程：**
1. 监听编辑器的 `dragover` 和 `drop` 事件
2. 校验 `event.dataTransfer.files` 中的文件类型（仅 image/*）
3. 读取文件 → ArrayBuffer → Base64 转换（> 1MB 图片通过 Web Worker 转换避免阻塞 UI）
4. 调用 YiAi `/write-file` API 保存到 `images/img-{timestamp}.{ext}`
5. 在编辑器光标处插入 `\n![文件名](images/img-{timestamp}.{ext})\n`

**粘贴处理流程：**
1. 监听编辑器的 `paste` 事件
2. 检查 `event.clipboardData.items` 中是否有 image/* 类型
3. 优先处理剪贴板中的图片（如截图工具的截图），而非剪贴板中的 HTML/文本
4. 后续流程同拖拽处理

**文件命名规则：`img-{timestamp}.{ext}`** —— `timestamp` 保证唯一性和可排序性，短名称利于 Markdown 引用可读性。不使用原始文件名（可能含中文/特殊字符）或 UUID（过长影响阅读）。

#### 4.1.7 Frontmatter 图形化编辑面板

**标准字段定义（9 个字段）：**

| 字段 | 标签 | 类型 | 必填 | 选项/说明 |
|------|------|------|------|----------|
| title | 标题 | text | 是 | 文件标题 |
| tags | 标签 | tags | 是 | 逗号分隔，支持已有标签自动补全 |
| category | 分类 | text | 是 | 分类路径，如 "项目/知识库/需求" |
| created | 创建日期 | date | 是 | 自动填充当前日期 |
| updated | 更新日期 | date | 是 | 保存时自动更新 |
| source | 来源 | select | 是 | 内部/外部/社区/AI生成 |
| type | 类型 | select | 是 | 需求/规格/架构/工作流/经验/缺陷 |
| status | 状态 | select | 是 | 草稿/审阅中/已发布/已归档 |
| priority | 优先级 | select | 否 | P0/P1/P2/P3/P4 |

**双向同步：** 图形化面板使用 js-yaml 的 `load()` 和 `dump()` 进行 Frontmatter 的解析和生成。面板修改 → `dump()` 生成 YAML → 替换编辑器中的 Frontmatter 区域。编辑器源码修改 → `load()` 解析 → 更新面板显示。YAML 解析错误时保留原文并在面板显示错误提示。

**格式一致性处理：** tags 字段在图形化面板中以逗号分隔显示（`tag1, tag2, tag3`），在 YAML 源码中可以是 flow style `[tag1, tag2, tag3]` 或 block style `\n- tag1\n- tag2\n- tag3`。面板始终以逗号分隔格式展示和处理，保存时统一使用 flow style。

#### 4.1.8 专注模式

全屏编辑器 + 隐藏所有侧边栏、工具栏、通知、底部状态栏。仅保留编辑区和（如果分屏模式）预览区。白名单快捷键保留：
- `Ctrl+S` / `Cmd+S`：保存
- `Ctrl+B/I` / `Cmd+B/I`：加粗/斜体
- `Ctrl+Z/Y` / `Cmd+Z/Y`：撤销/重做
- `ESC`：退出专注模式

**注意：** 专注模式下需捕获 `Ctrl+W` / `Cmd+W` 事件并 `preventDefault`——防止用户误关闭浏览器标签页。

### 4.2 大纲生成 (YK-09-144)

#### 4.2.1 功能设计

输入主题和文档类型后，AI 自动生成层级化大纲。生成流程：

```
用户输入 ──→ 文档类型选择 ──→ AI 模式选择 ──→ 大纲生成 ──→ 可视化编辑 ──→ 导出/展开
```

#### 4.2.2 三种生成模式

| 模式 | 工作方式 | 延迟 | 质量 | 适用场景 |
|------|---------|------|------|----------|
| 基础 | 硬编码模板 + LLM 主题微调 | < 3s | 中 | 快速启动，有模板可参考 |
| RAG 增强（默认） | 检索同类文档 → 提取结构 → LLM 融合生成 | < 5s | 高 | 常规写作 |
| Agent 迭代 | 生成 → 质量评估 → 改进 × 3 轮 | < 20s | 极高 | 高质量要求的关键文档 |

**RAG 增强模式的 Prompt 构建：**

系统检索 YiKnowledge 中与用户主题和文档类型相似的文章（通过向量相似度），提取它们的章节结构（标题层级树），将结构模式注入到 LLM Prompt 中：
- "以下是 YiKnowledge 中同类型的 5 篇架构设计文档的结构：{structured_outlines}"
- "请参考这些结构模式，为'{topic}'生成一个{detailed_level}级大纲"
- "确保大纲包含：背景分析、设计决策、目标架构、实施步骤、测试规格、风险与缓解"
- "大纲层级不超过 4 级（H1-H4），主章节数 5-8 个"

#### 4.2.3 大纲可视化编辑器

**树形组件功能：**
- 层级缩进展示标题树（H1 一级缩进 → H2 二级缩进 → H3 三级缩进 → H4 四级缩进）
- 折叠/展开任意层级
- 拖拽改变章节顺序（同级拖拽 = 改变顺序，跨父节点拖拽 = 改变层级）
- 内联编辑章节标题（双击进入编辑模式）
- 添加新章节（在选中章节下方添加同级或子级章节）
- 删除章节（含子章节确认提示）
- 撤销/重做（大纲编辑器内独立的操作历史）

**大纲质量评分（0-100）：**
- 章节完整性（30 分）：是否覆盖了该文档类型的标准章节
- 层级合理性（25 分）：层级深度是否在 3-4 级范围内
- 逻辑连贯性（25 分）：章节排列顺序是否合理
- 领域覆盖度（20 分）：是否涵盖了主题相关的关键子领域

#### 4.2.4 大纲展开为正文

选中大纲中的某个章节，点击 "展开" 按钮，AI 根据以下上下文生成该章节的正文内容：
- 章节标题和层级
- 父章节和兄弟章节的上下文
- 文档类型和整体主题
- RAG 检索到的相关知识片段

生成的内容以 Markdown 格式插入到编辑器中对应标题下方。用户可以逐节展开，也可以在展开后继续手动编辑。

#### 4.2.5 大纲模板定义

**5 种文档类型的标准章节结构：**

需求文档 (`requirement`):
```
H1: 背景 → H2: 问题陈述, 影响范围, 挑战
H1: 现状分析 → H2: 当前能力矩阵, 流程现状, 根因分析
H1: 设计决策 → H2: 决策 {1..N}, 决策汇总
H1: 目标架构 → H2: 系统架构, 数据流, 性能指标
H1: 具体改动 → H2: 核心功能设计, 接口定义, 文件变更清单
H1: 实施步骤 → H2: 阶段划分, 人天估算, 依赖关系
H1: 测试规格 → H2: 功能测试, 边界测试, 回归预测
H1: 风险与缓解 → H2: 风险评估, 缓解措施
```

架构设计 (`architecture`):
```

H1: 现状分析 → H2: 现有架构, 痛点识别, 技术债务
H1: 备选方案 → H2: 方案 {A..C}, 方案对比, 选型理由
H1: 目标架构 → H2: 组件图, 数据流, 接口契约, 部署拓扑
H1: 迁移方案 → H2: 分阶段迁移, 回滚策略, 灰度发布
H1: 性能评估 → H2: 性能模型, 压力测试, 容量规划
H1: 安全考量 → H2: 威胁模型, 安全措施, 合规检查
```

故障复盘 (`postmortem`):
```
H1: 事件概述 → H2: 时间线, 影响范围, 严重程度
H1: 根因分析 → H2: 直接原因, 根本原因, 5-Why 分析
H1: 影响评估 → H2: 用户影响, 业务影响, 数据影响
H1: 修复措施 → H2: 紧急修复, 长期修复, 时间线
H1: 预防措施 → H2: 监控告警, 流程改进, 自动化检查

```

操作手册 (`guide`):
```
H1: 概述 → H2: 用途说明, 适用人群, 前置知识
H1: 前置条件 → H2: 环境要求, 依赖安装, 权限配置
H1: 操作步骤 → H2: 步骤 {1..N}, 预期结果, 截图/示例
H1: 验证方法 → H2: 成功标准, 验证命令, 常见输出

```

技术规范 (`spec`):
```
H1: 背景 → H2: 动机, 范围, 术语定义

H1: 实现指南 → H2: 推荐实现, 代码示例, 反模式
H1: 测试方法 → H2: 测试用例, 验收标准, 兼容性测试
H1: API 定义 → H2: 接口签名, 参数说明, 返回格式
H1: 版本演进 → H2: 版本历史, 废弃说明, 迁移指南
```

### 4.3 模板体系 (YK-09-156, YK-09-153, YK-09-25, YK-09-211)

#### 4.3.1 结构化内容模板

**核心概念：** 预定义章节结构的模板——创建文件时选择模板即获得预设的章节框架。

**模板特性：**
- **必填/可选章节标记**：每个章节标记为必填或可选，保存时验证必填章节是否存在
- **章节验证**：基于模板定义验证生成的文件是否包含所有必填章节，缺失章节标注警告
- **模板继承**：子模板从父模板继承基础结构，添加或覆盖特定章节
- **章节重排序**：模板中章节的顺序可调整，创建后的文件也可以基于模板重新排序
- **模板版本管理**：模板更新后，基于旧模板创建的文件可选择是否更新结构

**模板数据模型：**
```typescript
interface StructuredTemplate {
  id: string;
  name: string;
  description: string;
  docType: DocType;
  version: string;
  parentTemplateId?: string;  // 继承的父模板
  sections: TemplateSection[];
  metadata: {
    author: string;
    createdAt: string;
    updatedAt: string;
    usageCount: number;
    rating: number;
  };
}

interface TemplateSection {
  id: string;
  title: string;
  level: 1 | 2 | 3 | 4;  // 标题层级
  required: boolean;       // 是否必填
  description?: string;    // 章节说明（作为占位内容）
  placeholder?: string;    // 占位文本
  children: TemplateSection[];
  order: number;           // 排序序号
}
```

#### 4.3.2 模板智能推荐

**推荐算法：** 当用户输入文章标题或选择文档类型时，系统自动推荐最匹配的模板。

**匹配维度：**
1. **文档类型匹配度（40%）**：模板的 docType 与用户选择的文档类型是否一致
2. **关键词匹配度（30%）**：用户输入的标题/主题关键词与模板描述、标签的相似度
3. **使用频率/评分（20%）**：模板的使用次数、完成率、用户评分
4. **上下文匹配度（10%）**：用户最近的创建历史和所属团队/角色

**推荐展示：** 模板卡片展示——模板名称、描述、匹配度评分、章节预览、使用次数、用户评分。排序按匹配度降序，前 3 名以 "推荐" 标签高亮。

**模板使用分析：**
- 每个模板追踪：使用次数、完成率（创建后保存的比例）、平均编辑时间、用户评分分布
- 仪表盘展示：模板使用趋势、模板有效性评分、模板改进建议
- 低完成率模板自动标记 "需要优化"

#### 4.3.3 模板市场

**功能设计：**
- **模板发布**：用户可以将自定义模板发布到模板市场
- **模板发现**：按分类、标签、使用量、评分浏览模板
- **模板安装**：一键安装模板到个人/团队模板库
- **模板卸载**：移除已安装的模板（不影响已基于该模板创建的文件）
- **模板评分与评论**：用户对模板打分和评论
- **模板版本**：模板更新时通知已安装用户

**模板市场规则：**
- 发布的模板需经过审核（检查结构完整性、描述清晰度）
- 模板的父模板不能是 "仅自己可见" 的私有模板
- 已安装模板数量 >= 100 的为 "热门模板"

#### 4.3.4 结构模板生成

**从内容分析中提取模式：** AI 分析已有的优质文章（评分高、阅读量高、结构完整），提取其章节结构特征，生成新模板建议。

**生成流程：**
1. 选择一批同类型的高质量文章（评分 >= 4.0，阅读量 top 20%）
2. AI 提取每篇文章的章节结构（标题树）
3. 聚类分析——找出公共章节和差异章节
4. 生成模板草案——公共章节标记为必填，差异章节标记为可选
5. 人工审核和调整
6. 发布到模板市场

**结构改进建议：** 对已有文章进行分析，对比同类型模板，建议添加缺失的必填章节或调整章节顺序。

### 4.4 协同编辑与审阅 (YK-09-106, YK-09-131, YK-09-155, YK-09-216, YK-09-24)

#### 4.4.1 实时协同编辑

**编辑锁机制（近期方案）：**

```
用户 A 打开文件编辑
  → 请求编辑锁: POST /edit-lock/acquire { file_path, user_id }
  → 获取成功: 文件上锁，其他用户看到 "A 正在编辑——只读模式"
  → 编辑完成保存: 自动释放编辑锁
  → 超时释放: 30 分钟无操作自动释放

用户 B 尝试编辑同一文件
  → 请求编辑锁: POST /edit-lock/acquire { file_path, user_id }
  → 获取失败: 返回 { locked_by: "A", since: "14:30" }
  → UI 显示: "A 正在编辑此文件——你可以查看但不能修改"
  → 可排队: 用户 B 选择加入等待队列——A 释放锁后自动通知 B
```

**Git Merge 策略（保存时合并）：**

```
用户 A 基于 V1 编辑 → 保存 V2 (成功，基版本 V1 无冲突)
用户 B 基于 V1 编辑 → 保存时检测到当前版本已是 V2
  → 系统尝试 Git 三路合并 (V1, V2, 用户的修改)
  → 场景 1: 修改不重叠 → 自动合并成功 → 生成 V3
  → 场景 2: 修改重叠 → 合并冲突 → 展示冲突解决 UI
    → 用户 B 逐冲突选择: 保留我的 / 保留 A 的 / 手动合并
    → 解决所有冲突后 → 提交 V3
```

**用户光标位置展示：** 当多个用户同时在线查看同一文件时，在编辑器的只读/预览视图中显示其他用户的光标位置（不同颜色标记），让用户感知他人的阅读位置。

#### 4.4.2 协同审阅工作流

**审阅流程：**
```
提交审阅 → 分配审阅者 → 审阅者内联评论 → 审阅清单检查 → 通过/驳回
                ↓ 驳回
            作者修改 → 重新提交审阅
```

**内联评论：**
- 选中文章中的文本 → 创建内联评论（评论锚定到选中的文本位置）
- 评论支持 Markdown 格式
- 评论线程化——可回复和解决
- 已解决的评论折叠但保留历史

**审阅清单：**
- 自定义检查项列表（如 "Frontmatter 字段完整"、"代码示例可运行"、"无拼写错误"）
- 审阅者对每项勾选通过/不通过
- 所有必选项通过 + 无未解决的评论 = 审阅通过

**审阅统计：**
- 审阅者统计：审阅次数、平均审阅时间、驳回率
- 作者统计：提交次数、首次通过率、平均修改次数
- 团队统计：审阅队列长度、平均响应时间、审阅瓶颈识别

#### 4.4.3 协作请求管理

**协作请求类型：**
- 创建请求：指定协作者创建新文件
- 更新请求：指定协作者修改现有文件
- 审核请求：指定审阅者审核文件
- 翻译请求：指定翻译者翻译文件

**请求状态流转：** 待分配 → 已分配/进行中 → 已完成 → 已关闭（超时/取消）

**技能路由匹配：** 基于协作者的技能标签（如 "Python", "架构设计", "前端"）和历史协作记录自动推荐最合适的协作者。

#### 4.4.4 协作编辑通知

**通知类型：**

| 通知 | 触发条件 | 渠道 | 频率限制 |
|------|---------|------|----------|
| 编辑提醒 | 另一用户开始编辑你最近编辑过的文件 | 站内通知 + 邮件摘要 | 每日最多1封 |
| @提及 | 评论/审阅中被 @提及 | 站内通知 + 即时邮件 | 无限制 |
| 冲突警告 | 尝试保存时检测到编辑冲突 | 编辑器内弹窗 | — |
| 审阅请求 | 被分配为审阅者 | 站内通知 + 邮件 | 无限制 |
| 审阅完成 | 提交的审阅通过/驳回 | 站内通知 | 无限制 |
| 协作活动摘要 | 关注的文件的协作动态 | 邮件摘要 | 每日/每周 |

**活动源：** 展示用户关注的文件的最近协作动态——谁编辑了、谁评论了、审阅状态变更。

### 4.5 版本管理 (YK-09-151, YK-09-90, YK-09-157, YK-09-129)

#### 4.5.1 编辑历史

**版本记录内容：**
- 版本号（自增）
- 作者（user_id + 用户名）
- 时间戳（保存时间）
- 变更摘要（自动生成：修改了多少行、增加了多少内容、删除了多少内容）
- 变更类型（新建/编辑/恢复/合并）
- Git commit hash（关联到 Git 历史）

**历史时间线视图：** 左侧版本列表（按时间倒序），右侧选中版本的完整内容预览。当前活跃版本高亮。支持分页加载（每页 20 个版本）。

**编辑统计面板：**
- 编辑频率图（每日/每周的编辑次数热力图——类似 GitHub 贡献图）
- 时间段分布（上午/下午/晚上的编辑分布）
- 贡献者统计（各贡献者的编辑次数、新增行数、删除行数）
- 文件成长曲线（文件大小随时间的变化）

#### 4.5.2 版本差异对比

**并排差异视图：** 左栏旧版本，右栏新版本。差异行三色标记：
- 绿色背景：新增行
- 红色背景：删除行
- 黄色背景：修改行

**版本选择器：** 两个下拉菜单分别选择"对比版本 A"和"对比版本 B"。默认对比：当前版本 vs 上一版本。

**语义变更检测：**
- 格式变更（仅调整缩进/空行/标点）：归为 "格式调整"
- 内容添加（新增段落/章节）：归为 "内容添加"
- 内容修改（修改已有段落）：归为 "内容修改"
- 内容删除（删除段落/章节）：归为 "内容删除"
- 重构（大规模结构调整）：归为 "重构"

#### 4.5.3 差异与合并

**三路合并策略：** 基础版本 O + 修改 A + 修改 B → 自动合并。

**合并场景：**
- **无冲突（修改不重叠）**：自动合并成功——不同章节的修改天然无冲突
- **伪冲突（相邻行修改）**：自动合并——修改行不相邻但 Git 可能会标记冲突，系统自动判断
- **真冲突（同一行修改）**：展示冲突解决 UI——用户选择保留哪个版本或手动合并

**冲突解决 UI：**
```
┌─────────────────────────────────────────┐
│ 冲突 1/3：第 150 行                       │
│                                         │
│ 版本 A (你的修改):                        │
│ │ "使用 CodeMirror 6 作为编辑器核心"      │
│                                         │
│ 版本 B (对方的修改):                      │
│ │ "使用 Monaco Editor 作为编辑器核心"     │
│                                         │
│ ○ 保留我的  ○ 保留对方的  ○ 手动编辑     │
│                                         │
│          [解决此冲突]  [跳过]             │
└─────────────────────────────────────────┘
```

**合并历史：** 记录每次合并操作的来源版本、目标版本、冲突数、解决方式、合并者、时间戳。

#### 4.5.4 版本恢复

**恢复流程：**
1. 在版本历史中选择目标版本
2. 点击 "预览恢复效果" → 展示恢复后的内容（差异高亮）
3. 确认恢复 → 执行 Git checkout → 写入文件系统
4. 恢复操作创建新的版本记录（版本 N+1），而非覆盖历史

**恢复后操作：**
- 恢复后的文件仍保留完整的版本历史
- 可以撤销恢复——回到恢复前的最新版本（本质上是再次恢复到恢复前的版本）

### 4.6 AI 辅助写作 (YK-09-22, YK-09-88)

#### 4.6.1 AI 草稿生成

**生成流程：**
1. 用户输入文章主题（如 "Go 语言并发模型详解"）
2. 选择文档类型（如 "技术规范"）
3. 设置目标字数（可选，如 3000 字）
4. 选择写作风格（可选，如 "技术教程/简洁/深入浅出"）
5. AI 执行生成：
   - RAG 检索 YiKnowledge 中相关知识片段
   - 构建 Prompt（注入主题、文档类型、结构模板、RAG 上下文、字数要求、风格要求）
   - LLM 生成 Markdown 格式的初稿
6. 初稿展示在编辑器中，标注 AI 生成标识

**质量控制：**
- 生成内容标注 `<!-- AI Generated Content - Please Review -->` 注释
- 质量评分（完整性、相关性、流畅性三个维度）
- 明显错误检测（矛盾陈述、事实性错误、格式错误）

#### 4.6.2 AI 改写建议

**段落级改写：** 选中文本 → 选择改写目标：
- **更简洁**：减少冗余，精炼表达
- **更正式**：调整语气为正式文体
- **更详细**：补充解释和示例
- **更技术性**：增加技术深度和术语准确性
- **更通俗**：简化技术术语，适合非技术读者

**结构优化：** AI 分析全文结构，建议：
- 章节合并（两个相似内容的章节合并）
- 章节拆分（一个过长的章节拆分为多个子章节）
- 章节重排（逻辑顺序优化）
- 缺失内容补充（识别到的信息缺口）

**风格检查：**
- 术语一致性：检测同一概念的不同称呼（如 "API 接口" 和 "API 端点" 混用）
- 语气一致性：检测正式/非正式语气的混用
- 人称一致性：检测 "你/您/我们/笔者" 的混用

#### 4.6.3 AI 质量预检

**保存前自动检查清单：**

| 检查项 | 类型 | 说明 |
|--------|------|------|
| Frontmatter 完整性 | 阻塞 | 必填字段 (title/tags/category/created/type/status) 是否完整 |
| 必填章节完整性 | 警告 | 基于文档类型的必填章节是否全部存在 |
| 标题层级合理性 | 警告 | H1 → H2 → H3 跳级检测（如 H1 直接跳到 H4） |
| 交叉引用有效性 | 警告 | 文章中引用的其他文件路径是否存在 |
| 外部链接可达性 | 信息 | HTTP 链接是否可访问（200 OK） |
| 代码块语法正确性 | 警告 | 代码块的语言标注是否正确，代码是否有明显语法错误 |
| 图片路径有效性 | 警告 | `![]()` 引用的图片路径是否存在 |
| 字数达标 | 信息 | 是否达到目标字数（如果设置了目标） |
| 拼写检查 | 信息 | 中英文拼写和常见错别字检测 |
| 术语一致性 | 信息 | 同一术语在不同段落的表达是否一致 |

**预检结果展示：** 以清单形式（类似 GitHub Actions 的检查结果），每项标注通过/警告/错误状态。阻塞项（红色）必须修复才能保存，警告项（黄色）可跳过，信息项（蓝色）仅展示。

### 4.7 翻译管理 (YK-09-119, YK-09-156, YK-09-42)

#### 4.7.1 翻译工作流

```
源语言文章（如中文）
    │
    ├──→ 机翻初稿（LLM + 翻译记忆库注入）
    │      │
    │      ├── BLEU/COMET 自动评分
    │      │
    │      ├── 评分 >= 4.0 → 标记为 "可发布"
    │      │
    │      └── 评分 < 4.0 → 进入人工审阅
    │             │
    │             ├── 人工审阅 + 评分（准确性/流畅性/术语/风格）
    │             │
    │             ├── 评分 >= 3.5 → 发布
    │             │
    │             └── 评分 < 3.5 → 打回修改/重新机翻
    │
    └──→ 翻译记忆库更新（新增的术语和段落）
```

**翻译仪表盘：**
- 各语言的内容状态概览（已翻译/待翻译/审阅中/已发布）
- 翻译进度百分比
- 待审阅文章列表
- 翻译质量趋势图（近 30 天的质量评分趋势）
- 翻译记忆库覆盖率（匹配命中的比例）

#### 4.7.2 翻译记忆库

**TM 数据模型：**
```
Source (原文) ──→ Target (译文) ──→ Metadata
"系统架构设计"  → "System Architecture Design" → {domain: "architecture", frequency: 42}
"故障复盘"      → "Postmortem Analysis"          → {domain: "operations", frequency: 28}
```

**TM 匹配策略：**
- 完全匹配：源段落在 TM 中有完全相同记录 → 直接复用
- 模糊匹配（> 80% 相似度）：相似源段落的翻译作为参考 → 人工确认
- 术语匹配：源段落中的特定术语在术语表中有标准翻译 → 自动替换
- 无匹配：LLM 翻译 → 翻译结果存入 TM

**术语表管理：**
- 手动添加/编辑关键术语的标准翻译（如 "微服务" → "Microservices"、"Frontmatter" → "Frontmatter（不翻译）"）
- 术语一致性扫描：检测已翻译文章中的术语是否与术语表一致，不一致的标记警告
- 术语覆盖率分析：哪些术语未被术语表覆盖（所有翻译中频繁出现但未定义的词汇）

#### 4.7.3 翻译质量评分

**自动化评分（机翻后自动运行）：**

| 指标 | 方法 | 权重 | 说明 |
|------|------|------|------|
| BLEU-4 | n-gram 精确匹配 | 30% | 与参考译文的 1-4 gram 重叠度 |
| COMET | 神经评分模型 | 40% | 基于预训练模型的语义质量评估 |
| 术语一致性 | 术语表匹配率 | 20% | 翻译中术语与术语表的一致性 |
| 格式保持 | HTML/代码块完整性 | 10% | Markdown 格式和代码块是否完整保留 |

**人工审阅评分（人工审阅时填写）：**

| 维度 | 分值 | 说明 |
|------|------|------|
| 准确性 | 1-5 | 翻译是否准确传达了原文意思 |
| 流畅性 | 1-5 | 译文是否通顺自然 |
| 术语一致性 | 1-5 | 术语使用是否与术语表一致 |
| 风格一致性 | 1-5 | 译文风格是否与原文一致 |

**发布质量门槛：**
- 自动化评分 >= 4.0 → 可跳过人工审阅直接发布
- 自动化评分 < 4.0 → 必须人工审阅
- 人工审阅综合评分 < 3.5 → 自动打回修改

#### 4.7.4 跨语言翻译 Pipeline

**自动化中英互译工作流：**
1. 检测源语言（基于字符集和语言检测模型）
2. RAG 增强——检索目标语言中同类型文档的术语和表达风格
3. 注入翻译记忆库匹配的术语和段落
4. LLM 翻译（使用专门的翻译 Prompt——禁用"创意"模式，temperature 0.3）
5. 后处理——检查 Markdown 格式完整性、代码块保留、链接转换
6. 术语一致性检查——扫描翻译结果，标记与术语表不一致的词汇
7. 输出翻译结果并更新 TM

**批量翻译：** 选择多篇文章或整个分类目录 → 提交批量翻译任务 → 异步处理 + 进度回调 → 翻译完成通知。

### 4.9 导入与迁移 (YK-09-154, YK-09-176, YK-09-98, YK-09-143, YK-09-32)

#### 4.9.1 内容导入向导

**多步骤导入流程：**

**步骤 1 — 选择导入源：**
- 文件上传（支持 .md/.txt/.html/.docx/.pdf）
- URL 导入（输入网页 URL 自动抓取内容）
- 剪贴板粘贴（直接从剪贴板粘贴内容）

**步骤 2 — 格式检测与转换：**
- 基于文件扩展名和 Content-Type 自动检测格式
- 基于内容特征补充检测（如 .txt 可能是 Markdown）
- 转换为标准 Markdown 格式（HTML → Markdown 转换、DOCX → Markdown 提取）

**步骤 3 — Frontmatter 提取：**
- 自动解析已有的 YAML Frontmatter
- 自动生成缺失字段（created→当前日期, source→外部, type→基于内容推测）
- 手动补充和编辑

**步骤 4 — 内容预览与编辑：**
- 在增强编辑器中预览转换后的 Markdown 内容
- 手动编辑和调整格式
- 图片资源处理（提取并保存到 images/）

**步骤 5 — 重复检测与处理：**
- 基于标题相似度检测重复（已有文章的标题 Levenshtein 距离 < 3）
- 基于内容相似度检测重复（向量相似度 > 0.85）
- 用户选择：跳过/覆盖/创建新版本

**步骤 6 — 目标位置选择：**
- 选择目标分类和标签
- 确认导入

#### 4.9.2 批量导入 API

**API 设计：**

```
POST /api/import/batch
Content-Type: multipart/form-data
Body:
  - files: File[] (多个文件)
  - target_category: string (目标分类)
  - auto_detect: boolean (是否自动检测格式)
  - extract_frontmatter: boolean (是否自动提取 Frontmatter)
  - dry_run: boolean (预览模式——仅验证不实际导入)

Response:
{
  "task_id": "import-20260909-001",
  "status": "processing",
  "total": 50,
  "progress": { "success": 15, "failed": 2, "skipped": 1, "remaining": 32 },
  "results": [
    { "file": "article1.md", "status": "success", "new_path": "技术/后端/article1.md" },
    { "file": "article2.html", "status": "failed", "error": "HTML conversion failed: malformed structure" },
    { "file": "article3.md", "status": "skipped", "reason": "Duplicate of existing article" }
  ]
}
```

**异步处理：** 大批量导入（> 10 个文件）使用异步任务处理：
1. 客户端提交导入任务 → 获得 task_id
2. 服务端后台处理 → 可查询进度 `GET /api/import/tasks/{task_id}`
3. 处理完成后 → Webhook 回调通知 `POST {webhook_url}`
4. 客户端也可轮询 `GET /api/import/tasks/{task_id}/progress`

#### 4.9.3 内容迁移助手

**迁移场景：**
1. **分类重组**：将 "技术/后端" 的所有文章迁移到 "工程/服务端"
2. **多文件整理**：将分散在多个草稿目录的文章批量迁移到正式分类
3. **目录重命名**：重命名 "old-name" 为 "new-name" → 自动更新所有引用

**迁移流程：**
1. 选择源目录/文件 → 选择目标目录
2. 预览影响范围：
   - 直接影响的文件列表（哪些文件会被移动）
   - 间接影响的文件列表（哪些文件引用了被移动的文件——需要更新引用）
   - 可能产生的死链（引用更新后仍需人工验证的链接）
3. 确认执行迁移
4. 迁移记录保存——支持一键回滚

**引用自动更新：** 迁移时扫描知识库中所有文章，检测对被移动文件的交叉引用（如 `[链接文字](../old-path/file.md)`），自动更新引用路径为新路径。

**迁移回滚：** 每次迁移操作记录快照（所有被移动文件的原路径和新路径映射），支持一键回滚到迁移前状态。回滚操作也更新引用路径。

#### 4.9.4 跨项目知识迁移

**自动化批量路径更新：** 当知识库目录结构发生重大调整时（如重新组织分类体系），自动扫描所有文章的 Frontmatter category 字段和交叉引用，批量更新为新路径结构。

**路径映射配置：**
```yaml
migration_rules:
  - from: "技术/后端/"
    to: "工程/服务端/"
  - from: "技术/前端/"
    to: "工程/客户端/"
  - from: "项目/旧项目/"
    to: "项目/已归档/旧项目/"
```

**干运行模式：** 执行迁移前先运行预览——展示所有变更但不实际执行，变更报告以 diff 形式展示。

### 4.10 定时发布 (YK-09-157)

#### 4.10.1 定时发布调度

**调度器设计：** 基于 APScheduler（Python）的定时任务调度。用户设置发布时间（日期 + 时间，精确到分钟），调度器在设定时间自动将文章状态从"草稿"切换为"已发布"。

**发布时间设置：**
- 日期选择器（日历控件）
- 时间选择器（小时:分钟，15 分钟步进）
- 时区选择（默认 Asia/Shanghai）
- 重复发布规则（可选）：无重复/每日/每周/每月

**发布队列管理：** 查看、编辑、暂停、取消、立即发布任一待发布任务。

**发布预览：** 在定时时间到达前，可以预览文章发布后的效果（最终渲染样式、公开页面效果）。

#### 4.10.2 发布管理

**发布历史：** 所有已发布和定时发布任务的完整记录——发布时间、文章标题、操作者、状态。

**取消发布：** 将已发布内容撤回（而非删除），内容保留但不再公开可见。已撤回的内容可以再次发布。

**版本回退：** 发布后发现严重问题 → 快速回退到发布前版本（编辑器中的 "回退到上一版本" 按钮结合版本管理功能）。

### 4.12 数学公式增强 (YK-09-215)

#### 4.12.1 渲染引擎与扩展

**KaTeX 作为渲染引擎（已在 YiKnowledge 中使用）：**
- 优势：渲染速度快（比 MathJax 快 5-10 倍），纯客户端渲染
- 扩展支持：`mhchem`（化学式）、`amsmath`/`amssymb`（数学符号扩展）

#### 4.12.2 LaTeX 宏支持

在文章 Frontmatter 或文章开头定义自定义 LaTeX 宏：

```yaml
katex_macros:
  "\\RR": "\\mathbb{R}"
  "\\NN": "\\mathbb{N}"
  "\\argmin": "\\operatorname*{arg\\,min}"
  "\\vect": "\\mathbf{#1}"
```

全局宏定义（YiKnowledge 配置级别）预加载常用宏：数学、物理、计算机科学的常用符号。

#### 4.12.3 公式编号与交叉引用

**自动编号：** 使用 `\tag{label}` 或 `\label{label}` 语法为公式编号：
```
$$
E = mc^2 \tag{einstein-mass-energy}
$$
```

**交叉引用：** 在文中通过 `\ref{einstein-mass-energy}` 引用公式编号，渲染为 "公式 (1)"。

#### 4.12.4 化学式渲染

通过 mhchem 扩展支持化学式：
- 分子式：`\ce{H2O}` → H2O
- 化学反应：`\ce{Fe2O3 + 3CO -> 2Fe + 3CO2}`
- 同位素：`\ce{^{227}_{90}Th+}`
- 化学键：`\ce{A-B=C#D}`

#### 4.12.5 交换图

通过 amscd 支持交换图（数学中常用的图表类型）：
```
$$
\begin{CD}
A @>f>> B \\
@VgVV    @VVhV \\
C @>>i> D
\end{CD}
$$
```

#### 4.14.1 GitHub/GitLab 代码嵌入

**嵌入语法：**
```
:github[owner/repo:src/main.py#L1-L20]
:gitlab[group/repo:src/utils.js#L50-L80]
```

**渲染效果：** 实时从 GitHub/GitLab API 获取代码内容，渲染为带行号的代码块，行号与实际文件行号对应。

**链接到特定提交/行：** 代码块标题栏包含源仓库链接——点击跳转到特定 commit 或 branch 的对应行。

#### 4.14.2 代码同步策略

**配置代码源：**
```yaml
code_sources:
  - name: "YiAi Core"
    provider: "github"
    repository: "owner/YrY"
    branch: "main"
    access_token: "${GITHUB_TOKEN}"
    sync_interval: "daily"
```

**同步机制：**
- **手动同步**：编辑器中点击 "刷新代码嵌入" 按钮
- **定时同步**：配置的 sync_interval 自动同步（每日/每周）
- **Webhook 触发**：监听仓库的 Push Webhook → 自动同步嵌入的代码

**变更检测：** 同步时对比代码当前内容与嵌入时的内容——如有变更，生成通知提醒作者审核更新。

**版本冻结：** 支持将代码嵌入锁定到特定 commit hash——避免源仓库的变更意外影响文档准确性：
```
:github[owner/repo:src/main.py#L1-L20 commit=a1b2c3d]
```

**WHEN** 用户在图形化面板中清空 title（必填字段）
**THEN** title 字段应显示红色边框和 "标题是必填字段" 提示
**WHEN** 用户切换到源码视图 → 手动编辑 YAML → 切换回图形化面板
**THEN** 图形化面板应反映源码中的修改

### 场景 10：迁移助手引用更新

**GIVEN** 知识库中有 20 篇文件引用了 `技术/后端/数据库优化.md`
**WHEN** 管理员将 `技术/后端/` 目录迁移到 `工程/服务端/`

**WHEN** 确认迁移
**THEN** 所有文件移动到新路径

**AND** 迁移记录保存——支持一键回滚

### 场景 11：定时发布

**WHEN** 用户设置发布时间为 "明天 09:00"

## 十一、回归问题预测

| # | 预测问题 | 原因 | 验证方法 |
|---|---------|------|----------|
| 1 | 分屏模式下输入中文（IME 组合输入），composition 事件与 debounce 300ms 预览更新冲突，预览区在 IME 组合过程中闪烁或显示拼音字母 | 编辑期间多次触发 update 事件，debounce 可能在 compositionend 之前触发 | 用中文输入法输入 "测试" → 观察预览区是否出现拼音 → 仅在 compositionend 后更新预览 |
| 2 | 图片拖拽后 `btoa` 对 > 1MB 图片的 Base64 转换阻塞 UI 线程 1-3 秒 | 同步 Base64 转换对大文件的处理时间不可忽略 | 拖拽 5MB PNG → 测量从释放到插入的总耗时 → 验证 < 500ms |
| 3 | Frontmatter 面板 tags 字段保存后回显格式不一致（flow style vs block style） | js-yaml dump 默认 block style，用户手动编辑后可能用 flow style | 输入 "a, b, c" → 保存 → 切换源码 → 再切回面板 → 验证始终显示 "a, b, c" |
| 4 | 专注模式下 Ctrl+W 关闭浏览器标签页而非退出专注模式 | 浏览器快捷键优先级高于页面事件 | 进入专注模式 → 验证 Ctrl+W 被捕获并 preventDefault |
| 5 | 大纲面板用正则提取标题，代码块内的 `#` 注释被误识别为标题 | 正则不考虑代码块和 Frontmatter 上下文 | 创建含代码块和 Frontmatter 的文档 → 提取大纲 → 使用 unified/mdast 而非正则 |
| 6 | 阅读时间估算公式低估技术文档的阅读时间——代码块阅读速度远低于正文 | 代码块占 30% 时阅读时间低估 30-50% | 统计含 30% 代码块的文档 → 计算阅读时间 → 偏差 > 30% 时增加代码块阅读速度参数 |
| 7 | AI 大纲生成依赖 RAG 索引——索引未及时更新时生成的大纲基于过期知识 | RAG 索引更新频率为 5 秒，但在大量写入后可能有短暂延迟 | 创建新文档后立即请求大纲生成 → 验证是否引用了新创建的内容 |
| 8 | 协同编辑 Git Merge 在 Windows 上的换行符处理不一致 | Windows 的 CRLF vs Unix 的 LF 换行符会导致 Git diff 全部标记为变更 | 在 Windows 和 Mac 之间交叉编辑测试 → 验证 Git 配置 autocrlf 正确 |
| 9 | 批量导入时 Frontmatter 提取错误地将正文第一段解析为 YAML | Frontmatter 解析器没有正确识别 `---` 边界 | 导入无 Frontmatter 的文件 → 验证不会错误创建 Frontmatter |
| 10 | 翻译记忆库匹配的术语不在当前上下文中合适——同一术语在不同领域有不同翻译 | "token" 在认证领域译"令牌"，在 NLP 领域译"标记" | 在认证文档和 NLP 文档中分别翻译含 "token" 的句子 → 验证 TM 上下文感知 |
| 11 | 代码块验证超时——无限循环的代码导致 Docker 容器长时间运行 | 用户代码中的 `while True` 或长时间操作 | 执行超时 30s + 容器资源限制 → 验证超时被正确终止 |
| 12 | 大量 Mermaid 图表的页面加载缓慢——每个图表独立渲染阻塞主线程 | 页面上有 20+ 个 Mermaid 图表时的渲染累积时间 | 加载含 20 个图表的页面 → 测量渲染时间 → 验证使用 IntersectionObserver 懒加载 |
