## 1. 内容知识卡生成 (YK-09-208, P2)

### 背景与问题

### 问题陈述

YiKnowledge 中有大量长篇文档——用户在查找特定信息时需要完整阅读。知识卡（Knowledge Card）是一种紧凑的信息展示格式——将文档的核心信息压缩为卡片化的结构化摘要——提升信息发现效率。当前 YiKnowledge 缺乏自动从内容生成知识卡的能力——所有卡片式展示（如搜索结果摘要）均依赖手工提取或简单的首段截取。

1. **信息密度低**：用户在搜索/浏览时需要扫描整段文字才能定位关键信息——效率低
2. **卡片格式不统一**：不同文档生成的知识卡格式不一致——用户困惑
3. **无法按卡片类型筛选**：搜索"API 参考"类卡片时需要进入文档全文查找——无法按卡片类型快速定位
4. **知识卡无模板**：每次手动创建知识卡都需要从零开始设计格式

**核心矛盾**：文档包含大量信息但检索时用户只需要关键洞察。知识卡 = 从文档中自动提取结构化关键信息——以统一格式呈现——用户在搜索结果中直接获得答案而不必打开完整文档。

## 2. 内容关系图谱 (YK-09-141, P2)

### 背景与问题

### 问题陈述

YiKnowledge 中的文章之间存在丰富的关联关系——A 引用了 B 的架构方案、C 是 D 的前置知识、E 和 F 讲的是同一个主题但角度不同。然而当前的浏览模式是"一篇接一篇"的线性阅读——读者无法直观地看到文章之间的关联网络。

1. **关系不可见**：文章之间的引用/前置/相似关系存储在 frontmatter 和链接中——但没有任何可视化表达
2. **学习路径不清晰**：读者想知道"学完这篇后应该看哪篇"——但当前没有前置/后续关系
3. **相关文章难以发现**：基于标签的相关推荐不够精准——两篇文章可能标签相同但内容无关
4. **知识孤岛**：同一主题的文章散布在不同目录中——读者只看到一个点而非一个网
5. **导航低效**：当前只能通过目录树或搜索找到下一篇——缺少基于关系的导航

**核心矛盾**：知识是一个网络而非一棵树——但当前的知识库只提供了树形目录导航——割裂了文章之间的语义联系。

## 3. 内容编排与学习路径 (YK-09-121, P2)

### 背景与问题

YiKnowledge 当前是平面的知识库——所有文件存储在同一目录层级中，虽然按角色和领域分类，但没有序列化的学习路径。新成员加入团队后面对 800+ 文件不知所措：不知道从哪开始、学习的先后顺序、每个阶段应掌握什么。这导致了：

1. **学习无方向**：新成员随机阅读文件，缺乏系统化的学习路径
2. **进度不可追踪**：管理者不知道团队成员的知识掌握情况
3. **知识体系断裂**：核心概念和进阶内容没有清晰的依赖关系
4. **能力无法验证**：缺少认证机制来确认学习成果
5. **教学内容难优化**：不知道哪些文章最受欢迎、哪些路径的完成率低

**核心矛盾**：知识库包含丰富的知识内容，但缺乏结构化学习体验，降低了知识的可消费性和团队 onboarding 效率。

## 4. 内容个性化推荐 (YK-09-134, P2)

### 问题陈述

YiKnowledge 知识库有数百篇文章，读者在浏览知识库时面临"选择困难"——不知道应该读什么、哪些文章对自己最有价值。当前知识库的文章列表按文件系统顺序排列，没有个性化排序。新读者尤其缺乏引导。

1. **文章无个性化排序**：所有读者看到的文章列表完全一样
2. **新读者无引导**：不知道从哪开始，只能随机浏览

5. **跨角色内容无推荐**：前端开发者看不到后端最佳实践文章（虽然是互补知识）

**核心矛盾**：知识库有大量优质内容，但读者缺少发现匹配自身兴趣的文章的机制。

## 5. 自动关联与推荐引擎 (YK-09-115, P2)

### 背景与问题

### 问题陈述

YiKnowledge 作为团队知识库，内容量持续增长（目标 2000+ 文件），但用户发现相关内容的能力严重不足。当前的内容发现方式存在以下问题：

1. **导航仅限目录结构**：用户只能通过目录层级浏览，无法发现跨目录的相关内容
2. **无推荐机制**：读完一篇文章后，不知道接下来应该读什么
3. **学习路径缺失**：新团队成员不知道应该按什么顺序阅读知识库内容
4. **内容关联不可见**：相关知识散落在不同目录中，缺乏显式的关联链接
5. **个性化缺失**：无法根据用户的角色和阅读历史推荐内容
6. **趋势内容不可见**：不知道团队中最近流行/热议的内容

**核心矛盾**：内容数量增长导致发现成本增加，但当前仅靠目录导航的方式无法帮助用户高效发现相关内容。

### 影响范围

### 核心改动

### 4.1 推荐引擎核心

```python
# YiAi/src/domain/recommendation/recommendation_engine.py (新增)

"""推荐引擎——混合推荐（基于内容 + 协同过滤 + 图谱）。"""

from typing import Optional
from dataclasses import dataclass, field
from enum import Enum
from src.shared.logging import get_logger

logger = get_logger(__name__)


class RecommendationType(Enum):
    SIMILAR = 'similar'
    PREREQUISITE = 'prerequisite'
    NEXT_IN_SERIES = 'next_in_series'
    RELATED_TOPIC = 'related_topic'
    PERSONALIZED = 'personalized'
    TRENDING = 'trending'
    EDITOR_PICK = 'editor_pick'


@dataclass
class RecommendationItem:
    """推荐项。"""
    content_path: str
    title: str
    category: str
    score: float  # 推荐得分 0-100
    reason: str  # 推荐理由
    rec_type: RecommendationType
    tags: list[str] = field(default_factory=list)


class ContentBasedRecommender:
    """基于内容的推荐器。"""

    def __init__(self, rag_service):
        self._rag = rag_service

    async def recommend_by_tags(self, tags: list[str], exclude_path: str, limit: int = 5) -> list[dict]:
        """根据标签推荐相似内容。"""
        # 查询共享标签最多的其他内容
        results = await self._rag.search_by_tags(tags, exclude=exclude_path, limit=limit)
        return results

    async def recommend_by_vector(self, content_path: str, limit: int = 5) -> list[dict]:
        """根据向量相似度推荐。"""
        # 使用 RAG 向量索引查找最相似的内容
        results = await self._rag.search_similar(content_path, limit=limit)
        return results


class CollaborativeRecommender:
    """协同过滤推荐器（基于阅读行为）。"""

    def __init__(self, analytics_repo):
        self._analytics_repo = analytics_repo

    async def recommend_by_covisit(self, content_path: str, limit: int = 5) -> list[dict]:
        """基于共访问模式推荐：读了 X 的人也读了 Y。"""
        # 查询与当前文章有共同读者的其他文章
        covisits = await self._analytics_repo.get_covisits(content_path, limit=limit)
        return covisits

## 6. 内容实验与AB测试 (YK-09-125, P2)

### 背景与问题

### 问题陈述

知识库的内容质量优化长期依赖 Curator 的直觉和经验，缺乏数据驱动的决策机制。当前内容优化面临以下问题：

1. 不确定哪种写法更好——两种写作风格的讲解效果无法量化对比
2. 内容修改无法验证——改了标题/结构/示例后，不知道效果提升还是下降

5. 决策缺乏权威——团队对内容方向的争论无法用数据解决

**核心矛盾**：知识库有 RAG 检索和网页阅读两个消费渠道，天然具备 A/B 实验条件（读哪篇、搜索排序），但当前完全没有实验框架来量化内容效果。

## 10. 内容翻译质量评分 (YK-09-156, P2)

### 背景与问题

### 问题陈述

YiKnowledge 已经在进行多语言内容翻译（中→英）——但翻译质量评估完全依赖人工主观判断——缺乏系统化的质量标准：

1. **翻译质量主观**：两篇翻译——一篇由资深双语人员翻译——另一篇由机器翻译后简单润色——但它们在发布流程中没有质量区分——读者看到的是"一篇质量好一篇差"——损害知识库声誉
2. **质量检查低效**：人工审阅者需要逐句对比原文和译文——一篇 3000 字的文章需要 1-2 小时——但审阅者时间有限——往往浅度审阅即通过——质量问题滑入生产
3. **质量标准不统一**：什么是"好的翻译"——没有数值化的标准——不同的审阅者评判尺度不同——同一篇译文可能被张三通过、被李四打回

5. **质量趋势不可见**：不知道翻译整体的质量在提升还是下降——不知道新的翻译工具对质量有没有改善

**核心矛盾**：翻译质量是内容国际化的基石——但当前的质量保证完全依赖不可靠的"人工感觉"。翻译质量评分引入自动化(BLEU/COMET)和标准化人工评分的双层评估——让质量标准从主观变为客观。

## 22. 内容无障碍合规 (YK-09-197, P2)

### 背景与问题

### 问题陈述

YiKnowledge 知识库的服务对象不仅是人类——也是 AI（通过 RAG 引擎消费 Markdown 内容）。但就人类读者而言——当前的知识库完全未考虑无障碍访问——排除了视觉障碍、运动障碍、认知障碍用户。作为技术文档类知识库——其受众主要是开发者和产品经理——这一群体中无障碍需求比一般网站更高（屏幕阅读器用户比例高于平均水平）：

1. **无 ARIA 地标**：页面结构仅依赖 HTML 语义标签——缺少 ARIA landmarks（banner/main/navigation/contentinfo/search）——屏幕阅读器用户无法快速导航页面区域——需要通过逐行阅读或标题跳转来定位——效率极低
2. **无跳转链接（Skip Link）**：键盘用户每次进入新页面都需要按 Tab 键穿越顶部导航栏（可能有 20+ 个可聚焦元素）才能到达正文——对于 30 篇文章的浏览会话——累计浪费 10+ 分钟的重复 Tab 操作
3. **键盘导航缺失**：交互元素（目录折叠/展开、标签页切换、搜索框）未绑定键盘事件——仅支持鼠标点击——键盘用户无法使用这些功能——等于被排除在功能之外
4. **焦点管理混乱**：SPA 路由切换后焦点停留在原位置——屏幕阅读器用户对页面已变化毫不知情——需要自己从头阅读来发现新内容——失去 SPA 的路由体验优势
5.

interface A11yConfig {
  enableSkipLink: boolean;
  enableFocusManagement: boolean;
  enableAriaLive: boolean;
  mainContentId: string;
  skipLinkText: string;
  ariaLiveMessagePrefix: string;
}

const DEFAULT_A11Y_CONFIG: A11yConfig = {
  enableSkipLink: true,
  enableFocusManagement: true,
  enableAriaLive: true,
  mainContentId: 'main-content',
  skipLinkText: '跳到内容',
  ariaLiveMessagePrefix: '已加载：',
};

class A11yManager {
  private config: A11yConfig;
  private liveRegion: HTMLElement | null = null;

  constructor(config: Partial<A11yConfig> = {}) {
    this.config = { ...DEFAULT_A11Y_CONFIG, ...config };
  }

  /** 初始化——注入 skip link + aria-live 区域 */
  init(): void {
    if (this.config.enableSkipLink) {
      this.injectSkipLink();
    }
    if (this.config.enableAriaLive) {
      this.injectAriaLiveRegion();
    }
  }

  /** 注入跳转链接——第一个可聚焦元素 */
  private injectSkipLink(): void {
    const existing = document.getElementById('skip-link');
    if (existing) return; // 已存在——不重复注入

    const skipLink = document.createElement('a');
    skipLink.id = 'skip-link';
    skipLink.href = `#${this.config.mainContentId}`;
    skipLink.textContent = this.config.skipLinkText;
    skipLink.className = 'sr-only focus:not-sr-only';
    skipLink.setAttribute('aria-label', '跳到主要内容');

    // 插入 body 最前面
    document.body.insertBefore(skipLink, document.body.firstChild);
  }

  /** 注入 ARIA live 公告区域 */
  private injectAriaLiveRegion(): void {
    if (document.getElementById('aria-live-region')) return;

    const liveRegion = document.createElement('div');
    liveRegion.id = 'aria-live-region';
    liveRegion.setAttribute('aria-live', 'polite');
    liveRegion.setAttribute('aria-atomic', 'true');
    liveRegion.className = 'sr-only';

    document.body.appendChild(liveRegion);
    this.liveRegion = liveRegion;

### 关键设计决策

1. **知识卡类型系统**: 实体卡、概念卡、API参考卡、流程卡四种类型，根据文档 type 字段自动推断
2. **力导向图可视化**: D3.js force simulation，节点大小按重要性评分，边按关系类型着色
3. **学习路径模型**: 前置条件 → 核心内容 → 后续推荐，支持技能等级标签和进度追踪
4. **推荐引擎融合**: 协同过滤 + 内容相似度 + 知识图谱路径，三路召回 + 排序
5. **i18n 文件组织**: `{locale}/{original-path}.md`，frontmatter 支持 locale 特定字段
6. **翻译质量双层评估**: BLEU/COMET 自动评分 + 人工审阅评分，发布门槛 BLEU > 0.4
7. **Git 驱动版本管理**: 基于 Git 历史记录的内容差异对比，无需额外存储
8. **WCAG 2.1 AA 合规**: 自动化审计引擎检查 38 项标准，集成到审核工作流
9. **REST + GraphQL 双协议 API**: REST 用于 CRUD，GraphQL 用于灵活查询
10. **异步批量导入**: 分块上传 → YAML 解析 → 后台处理 → Webhook 通知
