## 1. 内容审核工作流 (YK-09-86, P1)

### 背景与问题

YiKnowledge 当前有 800+ 文件，内容审核完全依赖人工审查。YK-09-09 定义了审查工作流的基本框架（审查分配 + SLA 追踪），但缺少**审核状态机**的完整实现、**审核检查清单自动化**、**内容质量评分**以及**审核人与通知机制**的系统化设计。

**已知案例：** 2026-09-03 开发者提交了一份 `engineer/build/rsbuild-config.md`，内容包含错误的构建配置示例。由于没有自动化的 frontmatter 校验和链接检查，该文件在 `inbox` 中停留了 5 天才被策展人发现，且审查时遗漏了 3 个死链。更严重的是，该文件未经充分审核就被标记为 `active`，导致后续 2 名开发者参考了错误配置。

当前审核流程的痛点：
- 无明确的审核状态机（draft → in_review → approved → published → archived）
- 审核人分配靠人工 @mention，缺乏自动化
- 审核检查清单执行靠人工，遗漏率高
- 无内容质量评分机制，无法量化内容质量
- 审核通知依赖手动发送，缺乏系统化通知

**目标：** 构建完整的审核工作流基础设施，包括审核状态机、自动化检查清单、审核人分配、质量评分、通知机制。

## 2. 内容可读性评分与优化 (YK-09-96, P2)

### 背景与问题

YiKnowledge 当前有 800+ 文件，内容质量评估仅依赖人工判断。YK-09-86 引入了质量评分模型，其中可读性维度仅占 10%，缺少独立的可读性量化评估。策展人无法快速识别"写得不好但内容正确"的文件，也无法通过数据驱动的方式指导作者改进写作质量。

**已知案例：** 2026-09-05 策展人审查 `aier/rag/hybrid-search-guide.md` 时，发现内容质量评分（0.72，B 级）尚可，但实际阅读体验极差：单个段落超 500 字、无列表分割、代码块缺少注释、中文句子平均长度 45 字（远超推荐的 25-35 字）。策展人花费 40 分钟逐段标注了 12 处可读性问题，但无法量化问题严重程度，也无法跟踪改进效果。

当前可读性评估的痛点：
- 无可读性量化指标，策展人凭主观感受判断
- 中文内容缺少专门的 readability 公式（Flesch-Kincaid 仅适用于英文）

- 无写作风格一致性检查，术语使用混乱
- 无目标读者等级匹配，内容难度与受众不匹配

**目标：** 构建内容可读性评分体系，支持中英文双语言评估，提供自动优化建议，集成到审核工作流中。

## 3. 内容句子复杂度分析 (YK-09-204, P2)

### 背景与问题

### 问题陈述

YK-09-96 引入了中文可读性指数的 5 维度模型——但句子复杂度这一核心维度仅占 30% 权重——评估粒度粗糙。当前系统仅计算"平均句子长度"一个指标——无法区分句子长度的分布特征、词汇多样性和中英文的差异。策展人无法回答"这篇文档的句子复杂度是否适合目标读者"——也无法量化写作复杂度随时间的改善。

1. **单一指标粗糙**：平均句子长度掩盖了分布信息——一篇文档可能 80% 短句 + 20% 超长句——平均恰好在正常范围——但长句严重影响阅读体验
2. **中英文公式分离不足**：中文可读性指数（YK-09-96）和英文 Flesch-Kincaid 分别在两个模块中——集成时维度权重不一致
3. **词汇多样性缺失**：TTR（Type-Token Ratio）评估词汇丰富度——但不评估其对复杂度的影响
4. **年级评估缺失**：无法将写作复杂度映射到"适合初中/高中/大学/研究生"读者——缺乏直观的受众指引
5. **句子结构深度未评估**：仅看长度不看结构——复杂的嵌套从句和简单的并列句被同等对待

**核心矛盾**：句子复杂度是内容质量的核心维度——但当前评估停留在"平均句子长度"这一肤浅层面。本需求构建精细化的句子复杂度分析——覆盖中英文双语言、分布特征、词汇多样性、结构深度——为内容质量和受众匹配提供数据基础。

## 4. 内容信息密度分析 (YK-09-206, P2)

### 背景与问题

### 问题陈述

YiKnowledge 作为 RAG 系统的知识源——内容的信息密度直接影响检索质量。信息密度过高（如纯代码——无解释）导致 LLM 难以理解——信息密度过低（如大量重复、啰嗦的描述）浪费索引存储和检索 token。当前系统通过 YK-09-110 进行重复内容检测——但仅识别"几乎相同"的文档——无法识别文档内部的冗余段落和"信息空洞"。

1. **信息密度不可量化**：不知道哪些文档信息密度高（适合 RAG 检索）——哪些低（浪费索引资源）
2. **冗余内容未被发现**：文档内部存在重复论述——相同观点用不同措辞说了 3 遍——未被检测
3. **信息增量不透明**：升级文档时——v2 比 v1 多了多少新信息——无法量化
4. **最优密度缺失**：不知道 YiKnowledge 的"最佳信息密度"是什么——无法指导作者
5. **低密度文档浪费 RAG 资源**：低信息密度文档被索引——降低检索效率——增加 token 消耗

**核心矛盾**：信息密度是 RAG 检索质量的关键因素——但当前仅依赖人工判断。本需求构建自动化的信息密度评分——覆盖事实计数、冗余检测、信息增益——为内容质量优化和 RAG 检索效率提升提供数据基础。

## 5. 内容情感倾向分析 (YK-09-205, P2)

### 背景与问题

### 问题陈述

技术文档通常被期望保持客观中立的写作风格——但实际内容中情感倾向的偏差可能影响读者的判断和信任。过于消极的文档（"这个方案有很多问题——目前没有好的解决方案"）可能让读者失去信心——过于积极的文档（"这是完美的方案——没有任何缺点"）可能显得不够专业。当前 YiKnowledge 没有任何情感倾向分析——策展人无法识别情感异常的内容——也无法确保内容在风格上与知识库的定位一致。

1. **情感倾向不可知**：不知道 800+ 文件中哪些带有强烈情感色彩——是否适合作为中立参考
2. **分段情感不一致**：文档前半段积极——后半段消极——整体平均掩盖了内部矛盾
3. **写作风格无分类**：教程/需求/参考文档的写作风格应该不同——但无自动识别和检查
4. **语气不专业检测**：过于口语化——过于情绪化的文档未标记
5. **作者风格无反馈**：作者不知道自己的写作是否偏离了目标风格

**核心矛盾**：技术文档要求客观中立——但写作过程自然带有情感倾向。情感分析的目的不是消除所有情感——而是识别过度偏差——帮助作者保持适当的专业语气。

### 影响范围

### 核心改动

### 4.1 数据模型

### 4.1 SimHash 核心实现

```python
# YiAi/services/knowledge/dedup/simhash.py (新增)

import hashlib
from typing import List, Set, Tuple
import re
import jieba

class SimHash:
    """SimHash 指纹生成器 — 64 位指纹"""

    def __init__(self, hash_bits: int = 64):
        self.hash_bits = hash_bits
        self.stop_words: Set[str] = self._load_stop_words()

    def _load_stop_words(self) -> Set[str]:
        """加载中英文停用词表"""
        return {'的', '是', '在', '和', '了', 'the', 'is', 'a', 'an', 'in', 'on', 'of', 'to', 'and'}

    def _tokenize(self, text: str) -> List[str]:
        """分词（中英文混合）"""
        # 中文分词
        chinese_words = list(jieba.cut(text))
        # 英文分词
        english_words = re.findall(r'[a-zA-Z]+', text.lower())
        return [w for w in chinese_words + english_words if w not in self.stop_words and len(w) > 1]

    def _hash_word(self, word: str) -> int:
        """计算单词的哈希值（64 位）"""
        h = hashlib.md5(word.encode('utf-8')).hexdigest()
        return int(h[:16], 16)  # 取前 64 位

    def compute(self, text: str) -> int:
        """
        计算文本的 SimHash 指纹

        Args:
            text: 输入文本

        Returns:
            64 位 SimHash 指纹
        """
        tokens = self._tokenize(text)
        if not tokens:
            return 0

        # 初始化向量（64 位）
        vector = [0] * self.hash_bits

        # 计算每个 token 的哈希，加权累加
        for token in tokens:
            token_hash = self._hash_word(token)
            # 权重：词频越高权重越大（这里简化为 1）
            weight = 1

            for i in range(self.hash_bits):
                bit = (token_hash >> i) & 1
                if bit == 1:
                    vector[i] += weight
                else:
                    vector[i] -= weight

        # 降维：正数 → 1，负数 → 0
        fingerprint = 0
        for i in range(self.hash_bits):
            if vector[i] > 0:
                fingerprint |= (1 << i)

        return fingerprint

## 16. 内容版权管理 (YK-09-168, P2)

### 背景与问题

### 问题陈述

YiKnowledge 知识库作为团队的共享知识资产，其中的内容来源多样化——部分为团队原创、部分引用外部资料、部分使用 AI 辅助生成。当前任何内容都没有版权或许可信息——对于知识资产的保护和合规性存在隐患：

1. **原创内容无版权保护声明**：团队成员精心撰写的架构设计、技术方案等原创内容——没有明确的版权声明——无法阻止未经授权的使用或传播
2. **引用外部资源无许可追踪**：团队在学习外部文章后撰写的总结或翻译——原始内容的许可要求（如 CC-BY 署名要求）未被记录——存在合规风险
3. **AI 生成内容无标识**：使用 AI 辅助生成的内容（如 Claude/ChatGPT 生成的初稿）——缺乏明确的 AI 生成标注——读者可能误以为是人类原创

5. **许可类型不透明**：读者无法判断一篇文章是否可以自由分享、翻译、修改——因为没有许可信息

**核心矛盾**：团队知识库最初以"内部使用"为默认假设——不重视版权管理。但随着内容质量提升和对外分享需求增加——缺乏版权管理成为知识资产保护和合规性的关键短板。知识资产的价值越高——版权管理的紧迫性就越强。

## 17. 内容自动化测试 (YK-09-136, P2)

### 背景与问题

### 问题陈述

YiKnowledge 知识库作为 RAG（检索增强生成）的数据源，其内容质量直接影响 AI 回答的准确性。但是，知识库在持续更新中会积累各种"坏数据"——链接失效（指向已删除的文件或外部页面）、代码示例过时（依赖的 API 已变更）、frontmatter 字段缺失或格式错误、长期未更新的内容与实际代码不一致。这些问题靠人工发现效率极低，需要一个自动化的内容测试系统。

1. **链接失效**：文章中的内部链接（`[某文章](../other/file.md)`）和外部链接（`https://...`）会随时间失效
2. **代码示例不可执行**：Python/JavaScript/Shell 示例代码的 API 可能已变更
3. **frontmatter 格式错误**：缺少必填字段、日期格式错误、tags 为空
4. **内容过时**：文章更新日期超过 90 天，但对应代码已大幅重构
5. **截图与实际匹配**：文章中引用的截图可能基于旧版 UI，与当前实际界面不一致

**核心矛盾**：知识库是 RAG 的"考试资料"，资料本身的错误被 RAG 放大后会产生更严重的后果——AI 基于错误的代码示例生成错误答案。

## 24. 内容重要性评分 (YK-09-159, P2)

### 背景与问题

### 问题陈述

YiKnowledge 中知识文件数量持续增长（当前 ~200 篇，每月新增 ~20 篇），但所有内容在搜索和导航中平等对待——无论是核心架构文档还是边角笔记，检索排序仅依赖 RAG 相关性分数。缺少内容重要性评估导致以下问题：

1. **核心内容淹没**：重要的架构设计文档和边角笔记在搜索结果中混排
2. **维护优先级不明**：不知道哪些文档最需要更新和维护
3. **新读者迷路**：缺少"必读文档"标记，新贡献者不知道从何开始
4. **价值无法量化**：无法衡量每篇文档对知识库的贡献度
5. **趋势不可见**：无法看到文档重要性的变化趋势（上升/下降/稳定）

**核心矛盾**：知识库内容的数量在增长，但缺少对内容价值的量化评估。所有文档被平等对待，用户无法区分核心内容和辅助内容。

## 架构整合

### 质量分析流水线

整个内容质量与分析系统形成一条完整的分析流水线：

```
内容提交 → 审核工作流 (86)
              ├── 格式检查: Frontmatter 校验
              ├── 可读性分析: 可读性评分 (96) + 句子复杂度 (204) + 词汇难度 (161)
              ├── 内容分析: 信息密度 (206) + 情感倾向 (205) + 受众匹配 (207)
              ├── 质量评分: 健康报告 (152) + 重要性评分 (159) + 难度评级 (167)
              ├── 合规检查: 安全分类 (116) + 合规检查 (118) + 版权管理 (168)
              ├── 一致性: 术语扫描 (145) + 去重检测 (110) + 同义检测 (210)
              ├── 事实核查: 自动化事实核查 (133)
              └── 测试验证: 自动化测试 (136) + 代码测试 (131) + 测验 (170)
         → 统计仪表盘 (97) + 性能分析 (114)
```

### 健康评分模型

内容健康报告 (152) 是整个质量体系的聚合层，综合以下维度：

1. **时效性** (25%): 基于更新日期和内容新鲜度扫描
2. **可读性** (20%): 综合可读性评分 (96)、句子复杂度 (204)、词汇难度 (161)
3. **完整性** (15%): 检查必填章节、frontmatter 完整度
4. **一致性** (15%): 术语一致性 (145)、格式一致性
5. **准确性** (15%): 事实核查 (133)、代码测试 (131)、行业标准对齐 (135)
6. **合规性** (10%): 安全分类 (116)、合规检查 (118)、版权管理 (168)

### 关键设计决策

1. **审核状态机**: draft → in_review → approved → published → archived，集成自动化检查清单
2. **双语言可读性**: 中文使用自定义可读性指数（句子长度、汉字复杂度），英文使用 Flesch-Kincaid
3. **SimHash + 语义相似度**: 两级去重策略，SimHash 快速海明距离初筛，语义向量精排
4. **健康评分加权**: 不同类型文档使用不同的维度权重（技术文档偏重准确性，教程文档偏重可读性）
5. **LLM 辅助分析**: 情感分析、受众匹配、事实核查等依赖 LLM 推理能力
