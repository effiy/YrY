# 角色边界

## 8 个角色职责

| 角色 | 目录 | 流水线阶段 | 核心问题 | 产出物 |
|------|------|-----------|----------|--------|
| executiver | `executiver/` | 业务策略 (跨阶段) | 为什么做？ | 市场分析、竞争策略、组织目标 |
| producter | `producter/` | 1. 需求 | 做什么？ | PRD、用户故事、优先级排序 |
| leader | `leader/` | 2. 决策 | 选哪个方案？ | ADR、技术选型、容量规划 |
| engineer | `engineer/` | 3. 设计构建 | 怎么实现？ | 架构模式、开发实践、质量安全 |
| srer | `srer/` | 4. 发布 + 5. 运营 | 怎么运行？ | 发布流程、事件响应、可观测性 |
| aier | `aier/` | AI 赋能 (跨阶段) | 怎么用 AI 加速？ | AI 基础、RAG/Agent 方法论、ML |
| curator | `curator/` | 知识治理 (元层) | 怎么维护 KB？ | 生命周期管理、模板、分类标准 |

## 角色责任链

角色在流水线中不是平级的，有明确的上游/下游关系：

```
executiver ──→ producter ──→ leader ──→ engineer ──→ srer
  (why)         (what)       (which)     (how)       (run)

  Business       Product      Tech        Impl        Ops
  strategy       requirements decisions   patterns    procedures
```

## Chip 契约

每个管道阶段有明确的 Input chips (从上游消费) 和 Output chips (为下游产出)：

| 阶段 | Input chips | Output chips |
|------|-------------|--------------|
| executiver | 市场数据、财报 | 战略方向、优先级 |
| producter | 战略方向、优先级 | PRD、用户故事 |
| leader | PRD、用户故事 | ADR、技术方案 |
| engineer | ADR、技术方案 | 代码、架构文档 |
| srer | 代码、架构文档 | 监控、事件记录 |

## 决策树

```
内容属于哪个角色？
├── 业务策略、市场、竞品？ → executiver/
├── 产品需求、用户故事、优先级？ → producter/
├── 技术决策、架构选择、ADR？ → leader/
├── 实现模式、开发工具、代码？ → engineer/
├── 发布流程、监控、事件响应？ → srer/
├── AI/ML 理论和实践？ → aier/
└── KB 结构和规则？ → curator/
```

## 高频边界冲突

| 冲突 | 归属 | 原因 |
|------|------|------|
| 架构决策 vs 架构模式 | leader/ | 决策 = 为什么选 A 不选 B，模式 = A 怎么实现 |
| 安全加固 vs 安全策略 | engineer/ | 加固 = 代码层面实现，策略 = 组织层面规范 |
| 事件响应 vs 风险预防 | srer/ → 中, leader/ → 前后 | 时间线区分：事发中 vs 事发前/后 |
| 技术选型 vs 技术实现 | leader/ | 选型 = 选什么，实现 = 怎么用 |
| 产品指标 vs 技术指标 | producter/ | 产品指标 = 用户价值，技术指标 = 系统质量 |

## 多角色覆盖

当一条知识涉及多个角色时，使用 frontmatter `roles:` 字段声明：

```yaml
---
标题: 微服务拆分决策
角色: [leader, engineer]
---
```

`roles` 字段用于跨角色检索，不改变文件在目录树中的物理位置。文件始终属于唯一的角色目录。
