# Kanban 视图状态通过 localStorage 保存但无版本号管理

## 现象

多个视图将 UI 状态持久化到 `localStorage`（通过 `pinia-plugin-persistedstate`），但保存的数据结构变更时无版本管理：

```typescript
// stores 中的 persist 配置
persist: piniaPersistConfig("yivad-global")
persist: piniaPersistConfig("yivad-user")
persist: piniaPersistConfig("yivad-bug")
// ... 16 个持久化 store
```

如果 Store 的 state 结构在未来版本中改变（字段重命名、新增必填字段、类型变更），旧版本存储在用户浏览器中的 JSON 数据会导致反序列化失败或静默数据丢失。

## 根因分析

- `pinia-plugin-persistedstate` 默认使用 `JSON.parse` 反序列化
- 没有版本号标记和迁移逻辑
- 与 bug #34（注销时未清理持久化数据）相关——如果有一个 store 数据版本号，可在版本变更时自动清理

## 涉及文件

- `src/stores/helper/persist.ts` — 持久化配置
- 16 个持久化 Store 的 state 定义

## 修复方案

在 `persist.ts` 中添加版本检查和迁移支持：
```typescript
const STORE_VERSION = 1;
afterRestore: (ctx) => {
  if (ctx.store.$state._version !== STORE_VERSION) {
    // 执行迁移或重置
  }
}
```

## 预防措施

- 所有持久化数据必须有版本号
- 不兼容的 state 变更提供迁移函数

## 影响范围

- **影响组件/页面**：详见描述章节
- **影响用户**：所有用户
- **是否影响 API 契约**：否
- **是否影响其他前端项目**：否（仅 YiVad）

## 经验教训

- **localStorage 数据几乎没有 Schema 演进能力**：16 个持久化 Store 的状态结构会随时间变化，但 `JSON.parse` 反序列化没有版本检查机制。一次字段重命名就会导致所有用户的旧数据静默丢失
- **`afterRestore` 钩子是天然版本检查点**：`pinia-plugin-persistedstate` 提供了 `afterRestore` 钩子，可以在反序列化后检查 `_version` 字段并执行迁移或重置
