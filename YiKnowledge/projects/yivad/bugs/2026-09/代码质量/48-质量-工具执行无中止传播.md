# useToolRegistry 中工具执行结果未做超时和 AbortSignal 传递

## 现象

`hooks/useToolRegistry.ts:160` 的 `executeTool` 函数执行 MCP 工具调用时，未将外部的 `AbortSignal` 传递给工具执行：

```typescript
async function executeTool(name: string, args: any, signal?: AbortSignal) {
  const result = await tool.execute(args);
  // signal 参数已声明但未传递给 tool.execute
}
```

如果用户在 AI 对话中取消了请求（`stopSending()` → `abortController.abort()`），流式响应停止，但已触发的工具调用仍在后台运行直到完成——浪费资源且可能产生副作用。

## 根因分析

- `executeTool` 接受 `signal` 参数表示设计意图，但未实现
- 工具调用是异步的（可能涉及文件 I/O、网络请求），取消传播很重要

## 涉及文件

- `hooks/useToolRegistry.ts:160` — executeTool
- `hooks/useToolRegistry.ts:201` — executePreStreamTools

## 修复方案

将 `signal` 传递给工具执行函数，工具执行时检查 `signal.aborted` 或传递给底层 fetch/API 调用。

## 预防措施

- 所有异步操作如果接受 AbortSignal，必须实际使用它

## 影响范围

- **影响组件/页面**：详见描述章节
- **影响用户**：所有用户
- **是否影响 API 契约**：否
- **是否影响其他前端项目**：否（仅 YiVad）

## 经验教训

- **`signal` 参数声明了但未使用是更危险的 false safety**：调用方看到函数签名接受 `AbortSignal`，以为取消会生效，实际上 signal 在函数体内被忽略。这比不声明 signal 更危险——它给了调用方错误的安全感
- **工具执行的副作用管理**：AI Chat 的工具调用可能涉及文件写入、网络请求，用户取消对话后这些操作在后台继续执行。`AbortSignal` 是 Web 平台标准的取消机制，应传递到底层 fetch 调用
