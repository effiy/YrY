# 交互式元素缺少无障碍属性

## 现象

YiVad 管理后台中仅 **8 处** 使用了 `aria-label` 属性，全部集中在 4 个组件中。大量交互式元素（表格排序、筛选按钮、侧边栏切换、标签页关闭、操作按钮）缺少可访问的名称，屏幕阅读器用户无法有效操作。

具体缺失：
- **ProTable** — 排序/筛选/分页控件无 aria-label
- **侧边栏菜单** — 折叠/展开按钮无 aria 描述
- **标签页管理** — 关闭标签页按钮无识别标签
- **ECharts 图表** — 图表区域无替代文本
- **文件上传** — 上传按钮和进度无状态描述
- **模态框** — 打开/关闭按钮无 aria 标记

## 根因分析

- 项目依赖 Element Plus 组件库，但 Element Plus 的部分组件默认不带充分的 ARIA 属性
- 团队未将无障碍性作为需求优先级
- 缺乏自动化无障碍测试（axe-core、pa11y）

## 涉及文件

- `components/ProTable/` — 表格交互控件
- `layouts/components/` — 侧边栏、标签页、头部导航
- `components/ECharts/` — 图表区域
- `components/Upload/` — 文件上传
- 等 30+ 个组件

## 修复方案

1. 为关键交互元素添加 `aria-label`（分页按钮、排序表头、筛选触发）
2. ECharts 实例添加 `aria-label` 描述图表用途
3. 在 CI 中集成 `axe-core` 或 `pa11y` 自动化检测
4. 建立组件无障碍清单，迭代补充

## 预防措施

- 新组件审查中检查基本无障碍要求
- 核心流程（导航、数据查看、表单提交）优先保障可访问性

## 影响范围

- **影响组件/页面**：详见描述章节
- **影响用户**：所有用户
- **是否影响 API 契约**：否
- **是否影响其他前端项目**：否（仅 YiVad）

## 经验教训

- 此类问题属于常见开发疏忽，可通过静态分析和自动化检查提前发现
- 建议将典型问题模式记录到团队知识库，避免重复踩坑
- 代码审查应重点关注此类边界情况
