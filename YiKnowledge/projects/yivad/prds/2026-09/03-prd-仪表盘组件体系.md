## 一、背景与问题陈述

### 1.1 核心问题

YiVad 当前缺少系统化的数据可视化和仪表盘能力：

| # | 问题 | 严重程度 | 影响 |
|---|------|----------|------|
| 1 | **无统一图表库** -- 各页面散落使用不同图表方案 | 高 | 视觉不一致、维护分散、性能参差 |
| 2 | **仪表盘不可自定义** -- 无法按需添加/排列图表 | 高 | 不同用户/场景需查看的数据维度不同 |
| 3 | **图表无交互** -- 无钻取、无联动、无刷选 | 中 | 数据探索停留在表面，无法深入分析 |
| 4 | **无实时更新** -- 数据变化后需手动刷新页面 | 中 | 监控类场景（健康大盘、资源利用率）体验差 |
| 5 | **无报告能力** -- 无法将多个图表组合为报告导出 | 中 | 汇报场景需手动截图拼接 |
| 6 | **仪表盘不可共享** -- 无法分享视图或嵌入到外部系统 | 中 | 协作效率低 |
| 7 | **大数据量图表卡顿** -- 10 万+ 数据点渲染阻塞 | 中 | 时间跨度大的趋势分析体验差 |


### 1.2 现状基线

| 维度 | 现状 |
|------|------|
| 图表方案 | 各页面散落使用不同图表方案，无统一标准 |
| 仪表盘 | 无自定义仪表盘，无法按需添加/排列图表 |
| 图表交互 | 无钻取、无联动、无刷选 |
| 实时更新 | 数据变化需手动刷新页面 |
| 报告能力 | 无法将多图表组合为报告导出 |
| 大数据量 | 10 万+ 数据点渲染阻塞 |

### 1.3 用户角色

| 角色 | 核心场景 | 关键需求 |
|------|----------|----------|
| 项目经理 | 项目健康监控、周报生成 | 项目健康大盘、报告构建器、仪表盘分享 |
| 开发负责人 | 代码质量追踪、团队效能 | 代码质量仪表盘、趋势分析、钻取 |
| 运维/SRE | 资源监控、容量规划 | 资源利用率仪表盘、实时更新、异常告警 |
| 数据分析师 | 多维分析、趋势预测 | 数据分析控制台、自定义查询、导出 |
| 普通用户 | 日常数据查看 | 仪表盘收藏、定时刷新、全屏模式 |

<a id="sec-2"></a>
## 二、目标与非目标

### 2.1 目标

1. **统一图表标准**：ECharts 作为唯一图表库，封装 10 种图表组件，提供一致接口。
2. **仪表盘可自定义**：用户可创建多个仪表盘，自由添加/排列/配置小部件。
3. **交互闭环**：钻取 → 联动 → 刷选 → 导出，形成完整数据探索链。
4. **实时数据**：WebSocket 推送 + 平滑动画，监控场景秒级更新。
5. **性能可伸缩**：LTTB 降采样 + WebGL 渲染 + 懒加载，确保大数据量体验。

### 2.2 非目标

| 非目标 | 说明 |
|--------|------|
| 替换 ECharts 底层库 | 本次为**增量封装**，不另选图表库 |
| 实时数据管道 | 不做 Kafka/Flink 等流处理管道，WebSocket 推送由 YiAi 承载 |
| 第三方小部件市场 | Widget SDK 仅定义接口，不做应用商店分发 |
| 移动端原生图表 | 桌面端优先，移动端仅保证基本可用 |

<a id="sec-3"></a>
## 三、设计原则

1. **统一图表标准** -- ECharts 作为唯一图表库，封装统一接口
2. **组件化图表** -- 每种图表类型独立封装为 Vue 组件，提供一致 props/events
3. **仪表盘即配置** -- 仪表盘布局、小部件、数据源全部可配置
4. **交互闭环** -- 钻取 -> 联动 -> 刷选 -> 导出，形成完整数据探索链
5. **性能可伸缩** -- 降采样、WebGL、渐进渲染确保大数据量体验

## 七、依赖与约束

### 7.1 上游依赖

| 依赖 | 类型 | 说明 |
|------|------|------|
| ECharts 6.x | 外部 | 唯一图表渲染引擎，按需引入模块 |
| YiAi 后端 | 外部 | WebSocket 实时推送端点、RPC 数据查询、导出任务 |
| ProTable（YV-09-29） | 内部 | 表格视图小部件复用 |
| data_service | 内部 | 仪表盘数据查询与聚合 |
| localStorage | 平台 | 仪表盘配置持久化（pinia-plugin-persistedstate） |

### 7.2 约束

- **必须使用 ECharts** 作为唯一图表库，禁止引入其他图表方案。
- **禁止前端直连 MongoDB**，数据操作一律经 RPC 信封。
- **参数名契约**：collection 参数为 `cname`，查询条件为 `filter`。
- **TypeScript 严格模式**，`vue-tsc --noEmit` 必须通过。
- 所有用户可见文本必须国际化。

<a id="sec-8"></a>
## 八、需求风险


| 风险 | 概率 | 影响 | 等级 | 缓解措施 | 应急预案 |
|------|------|------|------|----------|----------|
| ECharts 包体积过大 | 高 | 中 | 中 | 按需引入模块；路由懒加载图表页面 | 首屏仅加载必要图表类型 |
| WebSocket 连接不稳定 | 中 | 中 | 中 | 自动重连（指数退避）；降级为轮询（60s 间隔） | 显示"实时数据不可用"提示 |
| 大数据量图表卡顿 | 中 | 高 | 高 | 降采样（LTTB）；WebGL 渲染；Web Worker | 限制最大显示点数为 10,000 |
| 仪表盘配置损坏 | 低 | 中 | 低 | 版本管理自动保存；配置 JSON Schema 校验 | 回滚到上一个有效版本 |
| 实时更新导致页面性能下降 | 中 | 中 | 中 | 节流更新频率（100ms）；暂停非可见图表更新 | 暂停所有实时更新 |
| iframe 嵌入安全风险 | 低 | 高 | 高 | Token 认证；域名白名单; X-Frame-Options | 禁用嵌入功能 |
| 仪表盘嵌入链接泄露 | 中 | 中 | 中 | 有效期限制；密码保护；访问日志 | 撤回所有分享链接 |
| 图表主题与亮色/暗色模式切换冲突 | 低 | 低 | 低 | 主题预设同时提供亮色和暗色版本 | 自动跟随系统主题 |
| ECharts 版本升级导致图表渲染异常 | 低 | 中 | 低 | 锁定 ECharts 版本号；升级前回归测试 | 回滚 ECharts 版本 |
| localStorage 超出配额 | 低 | 中 | 低 | 仪表盘配置 < 100KB 典型值；存储前检查剩余空间 | 提示用户清理旧仪表盘 |

### 23.1 风险评分矩阵

```
影响
高  │  R3 (中/高)  │  R6 (低/高)  │  —
    │  大数据量卡顿  │  iframe 安全   │
    │              │              │
中  │  R1 (高/中)  │  R2 (中/中)  │  R8 (低/中)
    │  包体积       │  WebSocket   │  localStorage
    │  R7 (中/中)  │  R5 (中/中)  │  配额
    │  链接泄露     │  实时更新性能  │
    │              │              │
低  │  R9 (低/低)  │  R4 (低/中)  │  R10 (低/中)
    │  主题冲突     │  配置损坏     │  ECharts升级
    │              │              │
    └──────────────┴──────────────┴──────────────
        高概率          中概率          低概率
```

**R1（ECharts 包体积）为最需关注风险** — 高概率 + 中等影响，已通过按需引入将 gzip 体积控制在 ~300KB。**R3（大数据量卡顿）为最高等级风险** — 中概率 + 高影响，已通过 LTTB 降采样 + WebGL 双重缓解。
