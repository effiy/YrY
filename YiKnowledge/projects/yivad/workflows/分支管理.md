# 发布与分支管理规范

> 本文档定义 YiVad 项目的分支策略、环境映射、发布流程及紧急修复流程。

---

## 一、分支与环境映射

| 分支 | 环境 | 用途 |
|------|------|------|
| `dev` | dev | 开发联调环境 |
| `test` | sit | 系统集成测试环境 |
| `release` | uat | 主迭代 UAT 验证通道 |
| `release-hotfix` | uat | 紧急修复 UAT 验证通道 |
| `master` | prod | 生产代码快照（保持分支，不参与构建） |

**注意**：UAT 环境由 `release` 和 `release-hotfix` 共享，同一时刻只能部署一个分支的镜像，需协调使用。

---

## 二、分支核心规则

### 2.1 功能分支到环境分支（单向）

功能分支分别合入各环境分支，环境分支之间不合并：

```
feat-A ──┬──→ dev
         ├──→ test
         └──→ release（或 release-hotfix）
```

- `dev` 不合入 `test`
- `test` 不合入 `release`
- 各环境分支独立维护

### 2.2 master 是保持分支

- master **不参与 CI/CD 构建**，不触发任何环境部署
- master 只做记录，保持与生产环境代码一致
- 每次 prod 部署后，从对应发布分支合入 master 并打 tag
- 紧急 hotfix 可从 master 切出（基于生产代码）

### 2.3 唯一允许的回汇：master 回汇

生产发布后，需将 master 合回 `release` / `test` / `dev`，同步已上生产的代码，避免后续迭代丢失 hotfix 内容。

---

## 三、正常迭代发布流程

### 3.1 流程图

```
feat-A,B,C ──┬──→ dev        → dev环境验证
             ├──→ test       → sit环境验证
             └──→ release    → uat环境验证
                                    │
                              验证通过 │
                                    ↓
                          release 构建生产镜像 → 部署 prod
                                    │
                                    ↓
                          release → master（打 tag）
                                    │
                                    ↓
                          master → 回汇 release / test / dev
```

### 3.2 步骤

1. 功能分支分别合入 `dev`，触发 dev 环境构建，验证通过
2. 功能分支分别合入 `test`，触发 sit 环境构建，验证通过
3. 功能分支分别合入 `release`，触发 uat 环境构建，验收通过
4. 从 `release` 构建生产镜像，部署 prod
5. 将 `release` 合入 `master`，打 tag（如 `v1.2.0`）
6. 将 `master` 回汇到 `release` / `test` / `dev`

---

## 四、紧急修复（Hotfix）流程

当主迭代正在 UAT 验证时，部分功能需要单独走发布通道。

### 4.1 流程图

```
feat-D ──┬──→ dev                → dev环境验证
         ├──→ test               → sit环境验证
         └──→ release-hotfix     → uat环境验证（时分复用）
                                        │
                                  验证通过 │
                                        ↓
                        release-hotfix 构建生产镜像 → 部署 prod
                                        │
                                        ↓
                        release-hotfix → master（打 tag）
                                        │
                                        ↓
                        master → 回汇 release / test / dev
```

### 4.2 release-hotfix 切出方式

**从 `master` 切出**，不从 `release` 切：

```bash
# 正确：从 master 切（基于生产代码，干净无污染）
git checkout master
git pull origin master
git checkout -b release-hotfix

# 合入需要单独发布的功能分支
git merge feat-D
git push origin release-hotfix
```

**为什么不从 release 切：**

```
从 release 切（错误）：
  release-hotfix = 生产代码 + 主迭代未发布的功能 + feat-D
                                   ↑ 多了主迭代未发布的内容

从 master 切（正确）：
  release-hotfix = 生产代码 + feat-D
                               ↑ 干净，只有要单独发布的内容
```

### 4.3 UAT 环境协调

`release` 和 `release-hotfix` 共享 UAT 环境，需按优先级协调：

| 策略 | 适用场景 | 做法 |
|------|---------|------|
| 单独发布优先 | 紧急修复、时效性要求高 | 暂停主迭代 UAT，切换部署 release-hotfix，验证完切回 release |
| 主迭代优先 | 单独发布不紧急 | 主迭代先走完 UAT，上生产，再部署 release-hotfix 到 UAT |

### 4.4 完整步骤

1. 从 `master` 切出 `release-hotfix`
2. 将 hotfix 功能分支合入 `release-hotfix`
3. hotfix 功能分支分别合入 `dev`，dev 环境验证
4. hotfix 功能分支分别合入 `test`，sit 环境验证
5. 推送 `release-hotfix`，协调 UAT 环境使用权，部署 UAT 验证
6. UAT 验收通过，从 `release-hotfix` 构建生产镜像，部署 prod
7. 将 `release-hotfix` 合入 `master`，打 tag（如 `v1.2.1-hotfix`）
8. 将 `master` 回汇到 `release` / `test` / `dev`
9. 删除 `release-hotfix` 分支（用完即弃）

---

## 五、master 回汇

### 5.1 为什么需要回汇

单独发布上生产后，如果不同步到 `release` / `test` / `dev`，后续迭代会丢失 hotfix 的代码，导致：

- 主迭代下次上生产时覆盖掉 hotfix 的修复
- sit / dev 环境与生产不一致，难以复现线上问题

### 5.2 回汇步骤

```bash
# 1. 确保 master 是最新的（已合入发布分支并打 tag）
git checkout master
git pull origin master

# 2. 回汇到 release
git checkout release
git merge master
git push origin release

# 3. 回汇到 test
git checkout test
git merge master
git push origin test

# 4. 回汇到 dev
git checkout dev
git merge master
git push origin dev
```

## 六、分支命名规范

| 类型 | 格式 | 示例 |
|------|------|------|
| 功能分支 | `claude/[feat\|fix]-[描述]` | `claude/feat-dark-mode`, `claude/fix-table-loading` |
| 发布分支（主迭代） | `release` | `release` |
| 发布分支（紧急修复） | `release-hotfix` | `release-hotfix` |
| 生产快照 | `master` | `master` |

---

## 七、Tag 规范

| 场景 | Tag 格式 | 示例 |
|------|---------|------|
| 主迭代发布 | `v{版本号}` | `v1.2.0` |
| 紧急修复 | `v{版本号}-hotfix` | `v1.2.1-hotfix` |

每次 prod 部署后必须打 tag，标记生产代码快照。

---

## 八、流程速查表

| 场景 | 操作 |
|------|------|
| 功能开发 | feat → 合入 dev → 合入 test → 合入 release |
| 主迭代发布 | release 部署 UAT → 构建生产镜像 → 部署 prod → 合入 master 打 tag → 回汇 |
| 紧急修复 | master 切 release-hotfix → 合入 hotfix → 合入 dev/test → 部署 UAT → 构建生产镜像 → 部署 prod → 合入 master 打 tag → 回汇 → 删 release-hotfix |
| 紧急线上修复 | master 切 release-hotfix → 修 bug → 同紧急修复流程 |

---

## 九、提交规范

YiVad 使用 Conventional Commits 规范，通过 commitlint 和 cz-git 强制执行：

| 类型 | 说明 | 示例 |
|------|------|------|
| `feat` | 新功能 | `feat: 添加暗色主题切换` |
| `fix` | 修复 Bug | `fix: 修复 ProTable 加载状态错误` |
| `refactor` | 重构 | `refactor: 提取 ProTable 组件` |
| `style` | 样式调整 | `style: 调整按钮间距` |
| `docs` | 文档更新 | `docs: 更新 README` |
| `chore` | 构建/工具 | `chore: 升级 Rsbuild 版本` |

所有提交使用 `Co-Authored-By: Claude Opus 4.7 <noreply@anthropic.com>` 签名。
