# 性能优化规范

> **读完你将能够**：理解 YiAi 的性能优化体系，知道如何添加新的缓存层、优化数据库查询、监控响应时间

## 一、优化总览

YiAi 的性能优化从 4 个层面切入：

| 层面 | 策略 | 收益 |
|------|------|------|
| **RPC 调度** | 函数引用缓存 | 消除每次调用的 `importlib` 开销 |
| **数据库** | `$facet` 单查询分页 + 复合索引 | 减少 50% 的 DB 往返 |
| **缓存** | Redis/Memory 二级缓存 + Cache-Aside | 热数据毫秒级响应 |
| **启动** | 模块预热 + 种子数据缓存 | 消除首次请求的冷启动延迟 |

## 二、缓存体系

### 2.1 缓存架构

```
请求 → 路由处理器
         │
         ├── cache.get_or_set(key, factory, ttl)
         │     │
         │     ├── Redis (主) ─── 连接失败自动降级
         │     └── MemoryLRU (备) ─── 最多 1000 条，LRU 淘汰
         │
         └── 数据库 / 文件系统
```

### 2.2 缓存 Key 规范

所有 key 统一使用前缀 + 冒号分隔：

```
yiai:system:menus           # 系统菜单（静态数据，TTL 3600s）
yiai:knowledge:scan:all     # 知识库扫描结果（TTL 30s）
yiai:data:doc:{cname}:{key} # 单文档缓存（TTL 60s）
yiai:data:query:{cname}:*   # 查询缓存（写入时批量失效）
yiai:rag:status             # RAG 索引状态（TTL 10s）
yiai:knowledge:search:{hash} # 知识搜索（TTL 60s）
```

模块定义在 `shared/cache_keys.py`，禁止在业务代码中硬编码 key。

### 2.3 Cache-Aside 模式

读操作使用 `cache.get_or_set` 避免缓存击穿（内置 per-key 锁）：

```python
data = await cache.get_or_set(
    cache_key,
    factory=async_lambda_to_fetch_from_db,
    ttl=60,
)
```

写操作使用 fire-and-forget 失效（不阻塞响应）：

```python
# services/database/data_service.py
def _fire_invalidate(collection, doc_key=None):
    loop = asyncio.get_running_loop()
    loop.create_task(_invalidate_doc_cache(collection, doc_key))
```

### 2.4 TTL 策略

| 数据类型 | TTL | 原因 |
|---------|-----|------|
| 系统菜单 | 3600s | 几乎不变，仅在后台修改时失效 |
| 知识库扫描 | 30s | 文件变更频率低，监视器 60s 轮询 |
| 数据文档 | 60s | 可能被 CRUD 修改，写入时主动失效 |
| 数据查询 | 60s | 同上，写入时整集合失效 |
| RAG 状态 | 10s | 索引构建进度需近实时 |
| LLM 响应 | 600s | 相同 prompt 的幂等缓存 |
| 知识搜索 | 60s | 文件变更频率低 |

### 2.5 缓存失效策略

写入操作（create/update/delete/upsert）通过 `_fire_invalidate` 触发：

```
写入操作 → 响应返回（不等待失效完成）
              │
              └── create_task → _invalidate_doc_cache
                    ├── cache.delete(data:doc:{cname}:{key})
                    ├── cache.delete_pattern(data:query:{cname}:*)
                    └── cache.delete_pattern(data:count:{cname}:*)
```

**注意**：失效是 pattern-based 的，会清理整个 collection 的查询缓存。对于高频写入的集合，查询缓存命中率会较低，这是设计取舍。

## 三、数据库优化

### 3.1 $facet 单查询分页

`query_documents` 原实现执行两次 DB 查询（`find` + `count_documents`），现改为 `$facet` 聚合管道单次查询：

```python
pipeline = [
    {"$match": filter_dict},
    {"$sort": sort_dict},
    {
        "$facet": {
            "data": [
                {"$skip": (page_num - 1) * page_size},
                {"$limit": page_size},
                {"$project": projection},
            ],
            "total": [{"$count": "count"}],
        }
    },
]
results = await collection.aggregate(pipeline).to_list(length=1)
data = results[0]["data"]
total = results[0]["total"][0]["count"] if results[0]["total"] else 0
```

如果 `$facet` 查询失败（罕见，通常是兼容性问题），自动回退到原来的 `find` + `count_documents` 方案。

### 3.2 复合索引

在 `data/database.py::_ensure_indexes()` 中定义了所有索引：

| 集合 | 索引 | 用途 |
|------|------|------|
| `sessions` | `{"updatedTime": -1}` | 会话列表排序 |
| `sessions` | `{"projectName": 1, "storyName": 1}` | 故事任务面板 |
| `bugs` | `{"status": 1, "severity": 1}` | 缺陷筛选 |
| `bugs` | `{"project": 1, "createdTime": -1}` | 项目缺陷列表 |
| `issues` | `{"project_key": 1, "status": 1}` | 任务筛选 |
| `rss` | `{"createdTime": -1}` | RSS 列表排序 |
| `menus` | `{"order": 1}` | 菜单树构建 |
| `chat_records` | `{"createdTime": -1}` | 聊天记录排序 |
| `state_records` | `{"skill_name": 1, "createdTime": -1}` | 状态记录查询 |
| `audit_logs` | `{"collection": 1, "action": 1}` | 审计日志筛选 |
| `knowledge_files` | `{"category": 1, "path": 1}` | 知识库分类查询 |

所有业务索引使用 `background=True` 避免阻塞启动。

### 3.3 查询优化要点

- **Regex 走索引前**：`_build_filter` 中的字符串搜索使用 `re.compile` + `lru_cache(maxsize=512)` 缓存编译后的正则
- **字段投影**：`sessions` 查询自动排除 `pageContent`（可能很大的字段），`users` 查询排除 `password`
- **RSS 特殊路径**：`published_parsed` 字段存在历史格式漂移，走 Python 侧过滤而非 MongoDB 比较

## 四、RPC 调度优化

### 4.1 函数引用缓存

`domain/execution/executor.py` 中的 `_import_target_function` 将解析结果缓存到 `_FUNC_CACHE` 字典中：

```python
_FUNC_CACHE: dict[tuple[str, str], Any] = {}

def _import_target_function(module_path, function_name):
    cache_key = (module_path, function_name)
    if cache_key in _FUNC_CACHE:
        return _FUNC_CACHE[cache_key]
    module = importlib.import_module(module_path)
    func = getattr(module, function_name)
    _FUNC_CACHE[cache_key] = func
    return func
```

Python 的 `sys.modules` 已经缓存了模块对象，此缓存额外跳过了 `getattr` 查找开销。对于高频 RPC 调用（如 `data_service.query_documents`），这消除了每次请求的函数解析开销。

### 4.2 模块预热

`app.py` 的 `_warmup_cache()` 在启动时预导入 5 个热模块：

```python
_HOT_MODULES = [
    "services.database.data_service",
    "services.ai.chat_service",
    "services.knowledge.knowledge_service",
    "services.rag.rag_service",
    "data.repository",
]
```

这意味着第一个 RPC 调用不需要等待 `importlib.import_module` 的首次加载。

## 五、响应序列化

### 5.1 orjson

`shared/response.py` 使用 `orjson` 替代 stdlib `json`：

```python
class ORJSONResponse(Response):
    media_type = "application/json"

    def render(self, content: Any) -> bytes:
        return orjson.dumps(content, default=_default_serializer, ...)
```

`orjson` 比 stdlib 快 2-5×，且返回 bytes，避免了 `str → bytes` 的额外拷贝。

### 5.2 GZip 压缩

`app.py` 中注册了 `GZipMiddleware(minimum_size=512)`，对大于 512 字节的响应开启压缩，API 响应体积通常减少 60-80%。

### 5.3 响应时间头

`ResponseTimeMiddleware` 在所有响应中添加 `X-Response-Time-Ms` 头，便于前端和负载均衡器监控延迟。

### 5.4 SSE 帧 orjson 序列化

`shared/sse_utils.py::format_sse` 使用 `orjson.dumps` 替代 stdlib `json.dumps`：

```python
import orjson

def format_sse(data: Any) -> bytes:
    ...
    return b"data: " + orjson.dumps(payload, option=orjson.OPT_APPEND_NEWLINE) + b"\n"
```

对于高频 SSE 流（AI 聊天每 token 一个帧），此举将帧序列化延迟降低 2-5×。

### 5.5 HTTP 连接池复用

**问题**：原 `OllamaProvider.chat()` / `embed()` 每次调用创建新的 `httpx.AsyncClient`，丢弃 TCP 连接和 TLS 会话，每次请求重新握手（+50-200ms）。

**方案**：三处关键路径使用共享连接池：

| 模块 | 共享客户端 | 位置 |
|------|----------|------|
| LLM Provider | `services/ai/llm_provider.py::_get_http_client()` | OllamaProvider chat/embed 复用同一池 |
| RAG Engine | `domain/rag/engine.py::_get_http_client()` | Ollama 流式聊天 + 前置检查复用 |
| Web Search | `domain/search/__init__.py::_get_http()` | Wikipedia + AI 查询生成复用 |

```python
# 共享客户端模式（三处一致）
_shared_client: httpx.AsyncClient | None = None

def _get_http_client() -> httpx.AsyncClient:
    global _shared_client
    if _shared_client is None or _shared_client.is_closed:
        _shared_client = httpx.AsyncClient(
            timeout=httpx.Timeout(120.0, connect=10.0),
            limits=httpx.Limits(max_keepalive_connections=10, max_connections=50),
        )
    return _shared_client
```

**额外优化**：
- `DeepSeekProvider` 的 `AsyncOpenAI` 客户端从每次调用创建改为 `__init__` 时创建一次，内部 httpx 连接池被保留
- `_stream_ollama_chat` 从创建新 `ollama.AsyncClient` 改为直接使用共享 `httpx.AsyncClient.stream()` 发起原始 HTTP 流式请求，完全消除 ollama SDK 包装开销
- 应用关闭时 (`app.py` shutdown) 清理所有共享客户端

## 六、监控与诊断

### 6.1 查看响应时间

每个 HTTP 响应都带有 `X-Response-Time-Ms` 头，可在浏览器 DevTools 或 curl 中查看：

```bash
curl -s -o /dev/null -w "%{time_total}s" -X POST http://localhost:10086/ \
  -H "Content-Type: application/json" \
  -d '{"module_name":"services.database.data_service","method_name":"query_documents","parameters":{"cname":"menus"}}'
```

### 6.2 缓存统计

通过 `cache.stats()` 获取运行时信息：

```python
stats = await cache.stats()
# {"backend": "memory", "memory_size": 42, "memory_max_size": 1000, "redis_available": false}
```

### 6.3 RPC 调度日志

`executor.py` 中每条 RPC 调用都记录 INFO 日志：

```
RPC dispatch: module=services.database.data_service function=query_documents
```

可用于分析热点调用路径。

### 6.4 MongoDB 慢查询监控

`data/database.py` 注册了 PyMongo 全局 `CommandListener`，当任何 MongoDB 命令超过阈值时自动输出 WARNING 日志：

```python
_SLOW_QUERY_THRESHOLD_MS = 200  # configurable via config.yaml

class _SlowQueryLogger(monitoring.CommandListener):
    def succeeded(self, event):
        elapsed_ms = (time.monotonic() - t0) * 1000
        if elapsed_ms >= self._threshold:
            logger.warning(f"Slow query: {cmd} — {elapsed_ms:.0f}ms")
```

配置：在 `config.yaml` 中设置 `mongodb_slow_query_threshold_ms`（默认 200ms）。

### 6.5 Batch RPC 端点

`POST /batch` 端点允许前端在单次 HTTP 请求中发送多个 RPC 调用，并发执行：

```json
POST /batch
{
  "calls": [
    {"module_name": "services.database.data_service", "method_name": "query_documents", "parameters": {"cname": "menus"}},
    {"module_name": "services.database.data_service", "method_name": "query_documents", "parameters": {"cname": "users"}}
  ]
}
```

响应按输入顺序返回每个调用的结果，单个失败不影响其他调用。流式端点（SSE）不支持批量模式。

## 七、基础设施优化

### 7.1 uvloop 事件循环

`main.py` 和 `app.py` 在启动时自动检测并安装 `uvloop`（如果已 pip 安装）：

```python
try:
    import uvloop
    uvloop.install()  # replaces asyncio event loop with libuv
except ImportError:
    pass
```

uvloop 是 asyncio 事件循环的 Cython 实现，基于 libuv（Node.js 使用的同一个库），对 I/O 密集型异步代码有 2-4× 的吞吐量提升。`pip install uvloop` 即可启用。

### 7.2 MongoDB 写关注分级

非关键集合的写入使用 `w=0`（fire-and-forget），减少写入延迟：

| 集合 | 写关注 | 原因 |
|------|--------|------|
| `audit_logs` | `w=0` | 审计日志非核心路径 |
| `state_records` | `w=0` | 状态快照可容忍丢失 |
| `chat_records` | `w=0` | 聊天记录可容忍丢失 |
| `sessions`、`users`、`menus` 等 | `w=1` | 核心数据需确认写入 |

```python
_LIGHTWRITE_COLLECTIONS = frozenset({"audit_logs", "state_records", "chat_records"})

def _write_concern(collection_name: str) -> int:
    return 0 if collection_name in _LIGHTWRITE_COLLECTIONS else 1
```
