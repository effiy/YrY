## 二、目录职责速查

| 目录 | 职责 | 框架/库 | 禁止 |
|------|------|---------|------|
| `server/` | HTTP 请求处理、路由匹配、中间件 | FastAPI | 直接访问 data/，包含业务逻辑 |
| `services/` | 业务编排、参数校验、RPC 分发 | — | 直接操作 MongoDB，导入 server/ |
| `domain/` | 核心业务逻辑、算法实现 | — | 导入 server/，直接处理 HTTP |
| `data/` | MongoDB 操作、数据持久化 | Motor | 包含业务逻辑，导入 domain/ |
| `shared/` | 配置、响应、错误码、工具函数 | pydantic-settings | 依赖任何业务模块 |
| `models/` | Pydantic 数据模型定义 | pydantic | 包含运行时逻辑 |
| `middleware/` | 请求拦截、认证、限流 | Starlette | 包含业务逻辑 |
| `tests/` | 单元测试 + 集成测试 | pytest | 依赖外部服务状态 |

## 三、模块依赖关系

### 依赖方向

```
server/routes/ ──────────── HTTP 层
  │ 依赖
  ▼
services/ ──────────────── 服务层
  │ 依赖
  ▼
domain/ ────────────────── 业务逻辑层
  │ 依赖
  ▼
data/ ──────────────────── 数据访问层
  │ 依赖
  ▼
shared/ ────────────────── 共享层（被所有层依赖）
```

**规则**：依赖方向严格自上而下。上层可以依赖下层，下层不能反向依赖上层。

### 导入规则矩阵

| 层 | 可导入 | 禁止导入 |
|----|--------|----------|
| `server/` | `shared/`, `services/`, `middleware/` | `data/`, `domain/` |
| `services/` | `shared/`, `domain/` | `server/`, `data/` |
| `domain/` | `shared/`, `data/` | `server/`, `services/` |
| `data/` | `shared/` | `server/`, `services/`, `domain/` |
| `middleware/` | `shared/` | `server/`, `services/`, `domain/`, `data/` |
| `shared/` | — | 所有业务模块 |

### 循环依赖禁令

| 禁止方向 | 原因 |
|----------|------|
| `domain/*` → `server/*` | 业务逻辑不应依赖 HTTP 层 |
| `data/*` → `domain/*` | 数据层不应依赖业务逻辑 |
| `services/*` → `server/*` | 服务层不应依赖 HTTP 层 |
| `shared/*` → 任何业务模块 | 共享层必须保持独立 |

## 四、文件命名约定

| 约定 | 示例 | 适用于 |
|------|------|--------|
| snake_case 文件 | `chat_service.py`, `error_codes.py` | 所有 Python 文件 |
| `__init__.py` 控制公开 API | `domain/files/__init__.py` 导出 `read/write/delete` | 领域模块 |
| 路由文件按功能命名 | `agent.py`, `auth.py`, `knowledge.py` | routes/ |
| 服务文件 `<domain>_service.py` | `data_service.py`, `chat_service.py` | services/ |
| 测试文件 `test_<module>.py` | `test_config.py`, `test_response.py` | tests/ |
| 配置 `config.yaml` | 全局配置 | 项目根目录 |

## 五、设计决策

### 为什么 domain/ 和 services/ 分离？

- **domain/**：核心业务逻辑，可独立测试，不依赖 HTTP 框架
- **services/**：业务编排层，封装 domain 供 routes 调用，处理参数校验和响应格式化

分离后，domain 层可以独立单元测试，services 层可以 mock domain 进行集成测试。

### 为什么使用 MongoDB 单例？

MongoDB 连接是昂贵的资源。单例模式确保：
- 整个应用共享一个连接池（pool_size=10, max_pool_size=50）
- 生命周期管理中统一初始化和关闭
- 避免重复创建连接导致的资源泄漏

### 为什么文件使用双写策略？

磁盘（主）+ MongoDB（备份）的双写策略：
- 磁盘作为主存储，读写性能最优
- MongoDB 作为备份，支持元数据查询和跨服务共享
- 备份写入失败不影响主存储操作（尽力而为 upsert）
- OSS 不可用时自动降级为纯磁盘存储

### 为什么使用 YAML + pydantic-settings 配置？

- YAML 支持嵌套结构和注释，比 JSON/INI 更易读
- pydantic-settings 提供类型安全的环境变量覆盖
- 支持多环境配置（通过环境变量覆盖）

## 六、新增模块指南

### 新增领域模块

1. 在 `domain/` 下创建 `<name>/` 目录
2. 创建 `__init__.py` 定义公共 API 表面（`__all__`）
3. 内部实现文件保持私有（不导出）
4. 在 `services/` 中创建对应的 service 封装
5. 在 `server/routes/` 中创建路由模块（如需要）
6. 添加单元测试到 `tests/`

### 新增 API 端点

1. 在 `server/routes/` 中创建 `<name>.py`
2. 定义路由处理函数，使用 `StandardResponse` 封装响应
3. 在 `src/app.py` 的 `create_app()` 中注册路由模块
4. 添加对应的 pydantic 请求/响应模型（如需要）
5. 添加单元测试

### 新增 MongoDB 集合

1. 在 `models/` 中定义集合名称常量（如需要）
2. 如需专用操作，在 `data/` 中添加专用方法
3. 在 `data/seeds/` 中添加种子数据（如果需要默认数据）
4. 在 `data/indexes.py` 中添加索引创建
5. 通用 CRUD 操作通过 `repository.py` 的 `query_documents` 等方法

### 新增中间件

1. 在 `middleware/` 中创建 `<name>.py`
2. 继承 `BaseHTTPMiddleware`，实现 `dispatch` 方法
3. 在 `src/app.py` 的 `create_app()` 中按正确顺序注册
4. 中间件注册顺序：CORS → Observer → Auth → 路由

## 七、反模式

| 反模式 | 错误示例 | 正确做法 | 原因 |
|--------|----------|----------|------|
| 跨层导入 | `domain/` 中 `from server.routes import ...` | 遵循分层导入规则 | 循环依赖 |
| 在 `__init__.py` 外暴露内部实现 | 外部直接导入 `domain.ai.agent._internal` | 通过 `__init__.py` 的 `__all__` 控制 | 封装破坏 |
| 路由中直接操作 MongoDB | 路由中 `await db.find_one(...)` | 路由 → Service → Domain → Repository | 分层破坏 |
| 推测性添加文件 | 为「可能」需要的功能创建文件 | 仅在调用者需要时创建 | 死代码 |
| 忽略 `__init__.py` | 空 `__init__.py`，无 `__all__` | 定义 `__all__` 明确公开 API | API 不稳定 |

---

## 八、约束

### 必须遵守
- 严格遵循分层导入规则，不跨层导入
- 文件命名使用 snake_case
- 每个领域模块通过 `__init__.py` 的 `__all__` 控制公开 API
- 新增模块时遵循现有的目录结构模式
- 测试文件命名 `test_<module>.py`，放在 `tests/` 目录

### 禁止
- 不创建循环依赖
- 不在 `__init__.py` 之外暴露内部实现
- 不推测性地添加文件和目录
- 不破坏分层架构的依赖方向
- 不将业务逻辑放在 `server/` 或 `data/` 层

## 九、启动流程与模块初始化

### 应用启动时序

```
main.py
  │ uvicorn.run("src.app:app", port=10086)
  ▼
src/app.py :: create_app()
  │
  ├── 1. 创建 FastAPI 实例
  │     app = FastAPI(lifespan=lifespan, ...)
  │
  ├── 2. 注册中间件（按顺序）
  │     ├── CORS 中间件（允许跨域）
  │     ├── Observer 中间件（限流/采样/深度防护）
  │     └── Auth 中间件（JWT X-Token 验证）
  │
  ├── 3. 注册异常处理器
  │     ├── business_exception_handler → BusinessException
  │     └── global_exception_handler → Exception
  │
  ├── 4. 注册路由模块（20 个）
  │     app.include_router(router, prefix="/api")
  │
  └── 5. 返回 app 实例

lifespan（异步上下文管理器）
  │
  ├── startup:
  │   ├── 1. MongoDB.connect(uri, db_name)  # 连接池初始化
  │   ├── 2. seed_database(db)              # 种子数据（仅空集合）
  │   ├── 3. create_indexes(db)             # 索引创建（幂等）
  │   ├── 4. 启动知识库 Watcher             # apscheduler 每 60s 轮询
  │   └── 5. 启动 RSS Scheduler             # 定时抓取
  │
  └── shutdown:
      ├── 1. 停止 Scheduler
      └── 2. MongoDB.disconnect()           # 关闭连接池
```

### 依赖注入装配

```
create_app() 中的依赖装配顺序：

1. 数据层
   db = MongoDB()                    # 全局单例
   repository = Repository(db)       # 通用仓库

2. 领域层（注入 repository）
   data_domain = DataDomain(repository)
   chat_domain = ChatDomain(ollama_runtime, data_domain)
   knowledge_domain = KnowledgeDomain(data_domain, repository)
   rag_domain = RagDomain(repository)
   auth_domain = AuthDomain(repository)

3. 服务层（注入 domain）
   data_service = DataService(data_domain)
   chat_service = ChatService(chat_domain)
   knowledge_service = KnowledgeService(knowledge_domain)
   rag_service = RagService(rag_domain)

4. 注册到 app.state（供路由通过 Request 获取）
   app.state.data_service = data_service
   app.state.chat_service = chat_service
   ...
```

## 十、模块通信模式

### 内部调用链

```
HTTP 请求 → routes/ → services/ → domain/ → data/ → MongoDB
                │           │           │          │
                │           │           │          └── Motor 异步驱动
                │           │           └── 核心业务逻辑
                │           └── 参数校验 + 业务编排
                └── 路由匹配 + 响应包装
```

### RPC 分发流程

```
POST /  body: { module_name, method_name, parameters }
  │
  ▼
routes/app.py :: rpc_dispatcher()
  │
  ├── 1. 解析 module_name（如 "services.database.data_service"）
  │      → 查找 handler 路由表
  │
  ├── 2. 从 app.state 获取对应 Service 实例
  │      request.app.state.data_service
  │
  ├── 3. 解析 method_name（如 "query_documents"）
  │      → 查找 method_map
  │
  ├── 4. 调用 Service 方法
  │      result = await handler(**params)
  │
  └── 5. 包装响应
         StandardResponse.success(result)
         → { code: 0, message: "ok", data: result }
```

### SSE 流式通信（AI 聊天）

```
POST /  body: { module_name: "services.ai.chat_service", method_name: "chat", parameters: { model, messages, stream: true } }
  │
  ▼
services/ai/chat_service.py
  │
  ▼
domain/ai/chat.py :: stream_chat
  │
  ├── StreamingResponse(media_type="text/event-stream")
  │
  └── async generator:
      ├── data: {"data": {"message": "..."}}  →  token delta
      └── data: {"done": true}                →  stream end
```

## 十三、文件大小与复杂度指南

| 文件类型 | 建议行数 | 超过时考虑 |
|----------|----------|-----------|
| 路由文件 (`routes/*.py`) | 50-150 | 拆分路由或提取公共逻辑到 service |
| Service 文件 | 50-200 | 拆分为多个 service 或提取到 domain |
| Domain 文件 | 50-300 | 拆分为多个领域模块 |
| 数据访问文件 | 50-200 | 提取专用查询方法到独立文件 |
| 模型文件 | 10-50 | 一个模型文件一个核心实体 |
| 工具函数 | 10-50 | 按功能分组到独立文件 |

### 拆分信号

当文件出现以下情况时考虑拆分：
- 单个文件超过 300 行
- 一个类有超过 10 个公共方法
- 一个文件包含多个不相关的功能
- 文件内有明显的功能分组注释（`# === Section ===`）
