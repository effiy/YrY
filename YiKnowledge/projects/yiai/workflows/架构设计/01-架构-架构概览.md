# YiAi 架构概览

> 技术栈、分层架构、数据流、请求生命周期、RPC 分发、Agent 循环、RAG 引擎、降级策略、目录结构、反模式的完整概览。YiAi 是 YrY 单体仓库的唯一后端，为 YiVad 和 YiPet 提供统一的 RPC 服务。

## 三、分层架构

YiAi 采用严格的分层架构，从上到下依次为：

```
┌──────────────────────────────────────────────────────────────┐
│  HTTP Layer (server/)                                         │
│  Middleware → Routes (20 个路由模块) → Exception Handlers     │
│  统一 RPC 分发器，CORS/Auth/Observer 中间件                    │
├──────────────────────────────────────────────────────────────┤
│  Service Layer (services/)                                    │
│  封装 domain 逻辑，提供 routes 调用接口                        │
│  ai/ database/ execution/ knowledge/ rag/ rss/ storage/       │
├──────────────────────────────────────────────────────────────┤
│  Domain Layer (domain/)                                       │
│  核心业务逻辑：AI/Agent、Files、RAG、Knowledge、RSS、Auth     │
│  Execution、State、WeWork                                     │
├──────────────────────────────────────────────────────────────┤
│  Data Layer (data/)                                           │
│  MongoDB 单例 → Repository → Session/Store                    │
│  Motor async driver，种子数据自动导入                          │
├──────────────────────────────────────────────────────────────┤
│  Shared Layer (shared/)                                       │
│  Config、Response、ErrorCodes、Exceptions、Logging、Utils      │
│  pydantic-settings + YAML 配置源，跨模块共享                   │
└──────────────────────────────────────────────────────────────┘
```

### 分层职责与导入规则

| 层 | 目录 | 职责 | 可导入 | 禁止导入 |
|----|------|------|--------|----------|
| HTTP | `server/` | 请求处理、路由匹配、中间件 | shared/, services/ | data/, domain/ |
| Service | `services/` | 业务编排、参数校验 | shared/, domain/ | server/, data/ |
| Domain | `domain/` | 核心业务逻辑、算法 | shared/, data/ | server/, services/ |
| Data | `data/` | MongoDB 操作、持久化 | shared/ | server/, services/, domain/ |
| Shared | `shared/` | 配置、响应、错误码、工具 | — | 所有业务模块 |

## 四、请求生命周期

```
HTTP Request
  → CORS 中间件（Origin 检查，allow_any_origin: true）
  → Auth 中间件（可选，auth_enabled 配置控制，X-Token 验证）
  → Observer 中间件（可选，限流/采样/深度防护）
  → 路由匹配（20 个路由模块）
  → 路由处理函数
    → RPC 分发器：解析 module_name.method_name → 定位 service
    → services 层：参数校验 + 业务编排
    → domain 层：核心业务逻辑
    → data 层：MongoDB 操作（Motor async）
  → 响应（StandardResponse 统一信封）
  → 异常时：BusinessException → ErrorCode → StandardResponse
```

### 生命周期管理

```python
# src/app.py
from contextlib import asynccontextmanager

@asynccontextmanager
async def lifespan(app: FastAPI):
    """应用生命周期管理"""
    # ── 启动 ──
    logger.info("YiAi starting...")

    # 1. 连接 MongoDB
    await db.connect(config.mongodb.uri, config.mongodb.db_name)

    # 2. 导入种子数据
    await seed_database()

    # 3. 创建索引
    await create_indexes()

    # 4. 启动 Knowledge Watcher
    if config.knowledge.watcher_enabled:
        start_knowledge_watcher()

    # 5. 预加载 RAG 索引
    if os.path.exists("data/rag_store/docstore.json"):
        preload_rag_index()

    # 6. 启动 RSS 定时抓取
    if config.rss.enabled:
        start_rss_scheduler()

    logger.info("YiAi started")

    yield  # 应用运行中

    # ── 关闭 ──
    logger.info("YiAi shutting down...")
    stop_knowledge_watcher()
    stop_rss_scheduler()
    await db.disconnect()
    logger.info("YiAi stopped")
```

## 五、RPC 分发器

根路由 `/` 作为 RPC 分发器，解析 `module_name` 和 `method_name` 定位到对应的 service 方法：

```
POST /  body: { module_name, method_name, parameters }
  → _resolve_service(module_name)
  → getattr(service, method_name)(**parameters)
  → StandardResponse(code=0, message="ok", data=result)
```

### RPC 模块映射

| module_name | Service | 说明 |
|-------------|---------|------|
| `services.database.data_service` | DataService | 通用 CRUD（query/create/update/delete） |
| `services.ai.chat_service` | ChatService | AI 聊天（SSE 流式，多后端） |
| `services.ai.agent_service` | AgentService | Agent 模式（工具调用循环） |
| `services.database.session_service` | SessionService | 会话管理 |
| `services.knowledge.knowledge_service` | KnowledgeService | 知识库扫描/读写 |
| `services.rag.rag_service` | RagService | RAG 检索/聊天/索引构建 |
| `services.rss.feed_service` | FeedService | RSS 源管理/抓取 |

### 标准响应格式

```json
// 成功
{ "code": 0, "message": "ok", "data": { "list": [...], "total": 100 } }

// 业务错误
{ "code": 401, "message": "登录已过期", "data": null }

// 服务器错误
{ "code": 500, "message": "内部服务器错误", "data": null }
```

## 六、核心数据流

### 通用 RPC 数据流

```
YiPet / YiVad
  │ fetch() POST /  body: {module_name, method_name, parameters}
  ▼
FastAPI 根路由处理器
  │ 解析 module → Python 模块，method → 可调用对象，parameters → kwargs
  ▼
services.<domain>.<service>.<method>(**parameters)
  │ （如果是 data_service.query_documents）
  │   弹出 filter，合并到 query_params
  │   弹出 pageNum/pageSize/limit/page/fields/exclude/orderBy
  │   _build_filter(query_params) → Mongo 过滤字典
  │   collection.find(filter_dict, projection).sort().skip().limit()
  ▼
MongoDB（Motor 异步）
  ▼
{ list: [...], total, pageNum, pageSize, totalPages }
```

### AI 聊天 SSE 流式

```
client → fetch POST /  body: { services.ai.chat_service.chat, stream: true }
  → chat_service.chat()
  → StreamingResponse(text/event-stream)
    yields: data: {"data": {"message": "..."}}\n\n
    ends:   data: {"done": true}\n\n
  → Ollama (http://localhost:11434/api/chat)
```

### 文件双写持久化

```
POST /write-file { target_file, content }
  │ 1. 写入本地磁盘（主存储 — 此步骤失败则返回失败）
  │ 2. 尽力而为 upsert 到 MongoDB static_files（备份）
  ▼
success
```

## 七、Agent 循环架构

```
POST /agent/chat  { messages, model, max_turns, system?, tools? }
  → Agent.run()
    ┌─────────────────────────────────────────┐
    │  turn_start                             │
    │  → LLM 推理（Ollama/OpenAI/Anthropic）   │
    │  → 解析响应（text + tool_calls）         │
    │  → 工具调用：                            │
    │    tool_execution_start                 │
    │    → 确认门控（写操作需用户确认）         │
    │    → 执行工具（ToolRegistry.execute）     │
    │    tool_execution_end                   │
    │  → turn_end（总结本轮）                  │
    │  → 循环直到 stop=completed 或 max_turns  │
    └─────────────────────────────────────────┘
  → agent_end { stop_reason, turns, trajectory }
```

### Agent 关键特性

| 特性 | 说明 | 实现位置 |
|------|------|----------|
| 确认门控 | 写操作需用户确认，120s 超时自动拒绝 | `domain/ai/agent.py` |
| 拒绝记忆 | 同 session 内拒绝的调用自动拦截（最近 20 条） | `domain/ai/agent.py` |
| 模型切换 | 弱模型停滞时自动升级到更强模型 | `domain/ai/agent.py` |
| 预算感知 | 剩余轮次不足时提醒模型压缩步骤 | `domain/ai/agent.py` |
| 旋转检测 | 连续 3 次相同观察触发 nudge | `domain/ai/agent.py` |
| 结果裁剪 | 超大工具结果自动裁剪（默认 6000 字符） | `domain/ai/agent.py` |
| 断连检测 | 客户端断开时自动中止 | `domain/ai/agent.py` |
| 任务恢复 | 按 session 恢复完整轨迹 | `domain/ai/agent.py` |
| 即时引导 | 运行中实时重定向 Agent 行为 | `server/routes/agent.py` |
| XML 回退 | Ollama 工具调用 XML 解析错误时回退 | `domain/ai/agent.py` |

### 完整性检查点

| 检查点 | 触发条件 | 行为 |
|--------|----------|------|
| 命名工具检查 | 模型命名了工具但从未执行 | 注入 `[TASK]` 提示具体缺失的工具 |
| 无写入提示 | 零工具执行且用户消息是任务请求 | 注入 `[TASK]` 要求模型调用工具 |
| 计数感知 | 任务要求 N 个写入但执行了 < N 个 | 注入 `[TASK]` 指出确切差距 |
| 叙述守卫 | 模型叙述了工具但未调用 | 注入 `[CONTINUE]` 要求执行 |
| 预算警告 | 剩余轮次 ≤ 3 | 注入 `[BUDGET]` 提示压缩步骤 |

## 八、RAG 检索引擎

```
YiKnowledge Markdown 文件树
  ↓ apscheduler 每 60s 轮询
Knowledge Watcher → 解析 frontmatter + 正文
  ↓ 同步到 MongoDB knowledge_files 集合
llama_index 索引构建
  ↓ VectorStoreIndex + BM25
混合检索（向量 + BM25）
  ↓ 可选 LLM Rerank
  ↓ HyDE 查询增强
  ↓ Sentence Window 检索
  ↓ 内联引用编号 [Source N]
RAG 查询结果 → 用户
```

### 检索策略

| 策略 | 说明 | 配置 | 延迟 |
|------|------|------|------|
| 混合检索 | 向量相似度 + BM25 关键词 | `rag.hybrid_search: true` | 1-3s |
| LLM Rerank | 可选二阶段重排序 | `rag.use_rerank: false` | +2-5s |
| HyDE | 查询增强：用 LLM 生成假设文档 | `rag.use_hyde: true` | +1-3s |
| Sentence Window | 检索句子级片段，返回周围窗口 | `rag.chunk_size: 512` | — |
| Scope 过滤 | 文件级和文件夹级 scope 限定 | `scope` 参数 | — |

## 十、降级策略

| 场景 | 行为 | 恢复方式 |
|------|------|----------|
| MongoDB 不可用 | 写入快速失败，读取返回空结果 | MongoDB 恢复后自动恢复 |
| Ollama 不可用 | 聊天端点返回 `ErrorCode.AI_UNAVAILABLE` | Ollama 恢复后自动恢复 |
| OSS 不可用 | 文件存储回退到本地磁盘（双写降级为单写） | OSS 恢复后自动恢复 |
| Auth 禁用（默认） | 所有端点公开，无门控 | 生产环境开启 `auth_enabled: true` |
| Agent 模型停滞 | 自动切换到 fallback 模型 | 模型切换后继续执行 |
| Agent 断连 | `asyncio.CancelledError` → 保存状态 → 清理 | 客户端重连后恢复 |
| RAG 索引缺失 | 返回空结果 → 提示先构建索引 | 手动触发 `/rag/build-index` |
| Observer 禁用 | 无限流/采样/沙箱/重入保护 | 生产环境开启 |

## 十一、设计原则

### 关注点分离
- **server/**：只负责 HTTP 请求处理和路由，不包含业务逻辑
- **services/**：业务编排和参数校验，不直接操作 MongoDB
- **domain/**：核心业务逻辑，不导入 server/ 或处理 HTTP
- **data/**：数据持久化，不包含业务逻辑
- **shared/**：跨模块共享，不依赖任何业务模块

### 类型安全
- pydantic 模型验证所有请求/响应
- ErrorCode 枚举统一错误码管理
- BusinessException 携带结构化错误信息
- 所有 API 响应使用 StandardResponse 统一信封

### 异步优先
- 全局使用 async/await，不混用同步/异步
- Motor 异步 MongoDB 驱动
- httpx 异步 HTTP 客户端
- aiofiles 异步文件操作

### 配置驱动
- config.yaml + pydantic-settings 统一配置管理
- 环境变量覆盖 YAML 配置
- 功能开关（auth_enabled、observer、watcher）通过配置控制

## 十二、反模式

| 反模式 | 错误示例 | 正确做法 | 原因 |
|--------|----------|----------|------|
| 路由中直接操作 MongoDB | `@router.get("/data") async def get(): return await db.find_one(...)` | 路由 → Service → Repository → MongoDB | 分层架构破坏 |
| 混用同步/异步 | `import pymongo; client = pymongo.MongoClient()` | 统一使用 Motor `AsyncIOMotorClient` | 阻塞事件循环 |
| 推测性扩展 | 给 MongoDB 单例添加未使用的方法 | 仅在调用者需要时扩展 | 死代码积累 |
| 参数名使用 `query` | `parameters: { query: {...} }` | `parameters: { filter: {...} }` | 后端静默忽略 |
| 在 `__init__.py` 外暴露内部实现 | `from src.domain.ai.agent import _internal_func` | 通过 `__all__` 控制公开 API | 封装破坏 |
| 硬编码配置值 | `connect("mongodb://localhost:27017")` | 从 config 读取 `config.mongodb.uri` | 不可配置 |

## 十五、实践建议

### 日常开发

1. **始终使用 async/await**：整个项目异步优先，避免混用同步代码阻塞事件循环
2. **分层原则不妥协**：server 不直接调 data，domain 不导入 server。每次编写路由代码前，先确认调用的 service 方法已存在
3. **配置管理**：新增配置项时在 config.yaml 中定义对应字段，在 shared/config.py 中添加 pydantic 模型，不硬编码任何值
4. **RPC 参数验证**：每次新增 RPC 方法时，确认参数名使用 `filter`（非 `query`）、`target_file`（非 `path`）、`cname`（非 `collection_name`）
5. **错误处理**：使用 ErrorCode 枚举 + BusinessException，不使用裸 Exception 或字符串错误

### 性能优化

1. **连接池配置**：根据负载调整 pool_size 和 max_pool_size（见配置参考），避免连接数不足导致排队
2. **索引优先**：新增查询前先考虑是否需要创建索引，MongoDB 索引在启动时通过 create_indexes 自动创建
3. **分页限制**：pageSize 上限 100，避免单次查询过大拉垮数据库
4. **聚合管道优化**：$match 前置、$project 精简字段、避免 $unwind 大数组

### 代码规范

1. **__init__.py 控制公共 API**：domain 层模块通过 __init__.py 的 __all__ 导出，外部不应直接导入内部实现文件
2. **文件操作使用双写**：文件写入先写磁盘（主存储），再尽力而为写 MongoDB 备份，磁盘写入失败立即返回错误
3. **SSE 流式规范**：yield 格式统一使用 `data: {json}\n\n`，事件类型使用 snake_case 命名（如 turn_start、agent_end）
4. **应用工厂初始化顺序**：CORS → Observer → Auth → 路由 → 异常处理器，此顺序不可调整

### 跨项目协作

1. **RPC 契约变更通知**：修改 module_name、method_name 或 parameters 结构时，同步通知所有消费端（YiVad 前端、YiPet 扩展）
2. **错误码统一管理**：新增错误码时，更新 ROOT CLAUDE.md 中的标准错误码表
3. **YiKnowledge 灵敏度**：Knowledge Watcher 每 60s 轮询 YiKnowledge 目录，新增知识文件后等待最多 60s 才能被 RAG 检索

## 十六、关键约束

### 必须遵守
- 使用 StandardResponse 统一响应信封 `{code, message, data}`
- 使用 ErrorCode 枚举 + BusinessException 处理业务错误
- RPC 参数名使用 `filter`（非 `query`）、`target_file`（非 `path`）、`cname`（非 `collection_name`）
- 文件持久化使用双写策略：磁盘（主）+ MongoDB（备份）
- 所有异步操作使用 async/await
- Domain 层不导入 server/，Routes 不直接调用 data/
- 应用工厂初始化顺序不可调换

### 禁止
- 不在 routes 中直接调用 data/ 层
- 不混用同步和异步代码
- 不推测性地扩展 MongoDB 单例
- 不在 __init__.py 之外暴露内部实现
- 不破坏 RPC 信封协议
- 不硬编码配置值
