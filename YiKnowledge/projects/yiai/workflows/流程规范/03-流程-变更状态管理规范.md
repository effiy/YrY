# 变更状态管理规范

> OpenSpec 变更（Change）的生命周期状态、状态推进规则、产出物要求、状态流转检查清单、异常处理与恢复、多变更协调。

## 一、变更生命周期

```
proposed → designing → applying → verifying → landed → archived
```

| 状态 | 含义 | 触发条件 | 持续时间 |
|------|------|----------|----------|
| `proposed` | 提案已创建，等待设计 | 执行 `/opsx:new` 或 `/opsx:propose` 后 | 数小时 ~ 1 天 |
| `designing` | 设计方案编写中 | 开始编写 design.md 时 | 数小时 ~ 1 天 |
| `applying` | 按任务清单实现代码 | 执行 `/opsx:apply` 后 | 数小时 ~ 数天 |
| `verifying` | 实现完成，验证中 | 执行 `/opsx:verify` 后 | 数分钟 ~ 1 小时 |
| `landed` | 已落地，待归档 | 执行 `/opsx:land` 后 | 数天 ~ 永久 |
| `archived` | 已归档 | 执行 `/opsx:archive` 后 | 永久 |

---

## 二、配置文件格式

每个变更使用 `.openspec.yaml` 记录元信息：

```yaml
schema: spec-driven
created: YYYY-MM-DD
status: <当前状态>
depends_on:                    # 可选：依赖的其他变更
  - change: <change-name>
    status: <期望状态>         # 通常为 landed
```

---

## 三、状态推进规则

### 核心规则

- **单向推进**：状态只能向前推进，不可回退。如需回退，必须手动修改配置文件。
- **依赖检查**：`/opsx:continue` 读取当前状态决定从哪个阶段继续执行。
- **前置条件**：`depends_on` 中声明的变更未达到期望状态时，`/opsx:apply` 应提醒用户先处理依赖。

### 状态不可跳过

```
proposed → designing → applying → verifying → landed → archived
```

每个状态必须经过，不可跳过中间状态直接进入后续状态。例如：
- 不可从 `proposed` 直接跳到 `applying`（缺少 design.md）
- 不可从 `applying` 直接跳到 `landed`（未经过验证）

---

## 四、状态与产出物对照

| 状态 | 必须存在的产出物 | 可选产出物 |
|------|-----------------|-----------|
| `proposed` | proposal.md | — |
| `designing` | proposal.md + design.md（进行中） | — |
| `applying` | proposal.md + design.md + tasks.md | — |
| `verifying` | proposal.md + design.md + tasks.md + 代码实现 | 测试报告 |
| `landed` | 以上全部 + spec/tasks 已同步回写 | 部署记录 |
| `archived` | 已移至 archive/ 目录 | — |

## 五、状态流转检查清单

### proposed → designing

- [ ] proposal.md 内容完整（Why / What Changes / Impact）
- [ ] 待确认项已全部解决
- [ ] 用户已确认提案方向

### designing → applying

- [ ] design.md 覆盖所有 proposal 中列出的变更点
- [ ] 技术方案经过评审（必要时走 `/plan-design-review`）
- [ ] tasks.md 已拆分为可独立验证的任务
- [ ] 架构决策已记录（ADR 或 design.md 中的决策章节）

### applying → verifying

- [ ] 所有 task 实现完成
- [ ] `ruff check` 代码检查通过
- [ ] `mypy` 类型检查通过
- [ ] 变更未超出 proposal 范围
- [ ] 新增/修改的 API 端点有对应的测试用例

### verifying → landed

- [ ] 代码与 spec 一致性检查通过
- [ ] RPC 信封格式正确性检查通过
- [ ] API 契约参数名检查通过（`filter` 而非 `query`）
- [ ] 边界情况处理完备
- [ ] 数据库查询有分页限制

### landed → archived

- [ ] 代码已合并到目标分支
- [ ] spec 和 tasks 已回写到规范目录
- [ ] 变更记录已归档到 archive/ 目录

## 六、异常处理

### 状态卡住

| 场景 | 处理方式 |
|------|----------|
| `proposed` 中待确认项长时间未解决 | 提醒用户处理待确认项，或标记为 blocked |
| `applying` 中任务超出预期范围 | 回退到 `designing`，更新 design.md 和 tasks.md |
| `verifying` 中发现关键问题 | 回退到 `applying`，修复后重新验证 |
| `landed` 后代码未合并 | 确认合并策略，手动完成合并 |

### 状态回退（例外情况）

正常情况下不允许回退。以下情况可手动回退：

```bash
# 手动修改配置文件中的 status 字段
# 从 .openspec.yaml
status: verifying → status: applying

# 然后重新执行上一阶段
/opsx:apply
```

回退前必须：
1. 明确回退原因
2. 在变更记录中注明回退原因和时间
3. 确认回退不会影响依赖此变更的其他变更

### 依赖变更失败

当 `depends_on` 中的变更失败或被取消时：
- 当前变更自动进入 `blocked` 状态
- 需等待依赖变更恢复或寻找替代方案
- 依赖变更不可恢复时，当前变更需重新评估可行性

## 七、多变更协调

### 并行变更

当多个变更同时进行时：

| 场景 | 处理方式 |
|------|----------|
| 两个变更修改同一文件 | 按提交顺序，后提交的需处理冲突 |
| 两个变更修改同一模块 | 提前沟通，协调修改顺序 |
| 变更 A 依赖变更 B | A 的 `depends_on` 中声明 B，B 先推进到 `landed` |
| 两个变更无依赖关系 | 可并行推进，独立管理状态 |

### 变更冲突解决

```yaml
# 变更 A 的 .openspec.yaml
depends_on:
  - change: change-b
    status: landed

# 变更 B 的 .openspec.yaml
depends_on: []  # 无依赖
```

处理顺序：变更 B 先完成（`proposed → designing → applying → verifying → landed`），然后变更 A 开始。

## 八、YiAi 特定状态约束

### 涉及 API 契约变更

当变更涉及 RPC 方法签名修改时，`verifying` 阶段必须额外检查：

- [ ] 前端（YiVad/YiPet）调用方是否已同步更新
- [ ] 参数名遵守跨项目 RPC 契约（`filter` 而非 `query`）
- [ ] 响应格式保持 `{code, message, data}` 结构
- [ ] 向后兼容性评估（是否影响现有调用方）

### 涉及数据模型变更

当变更涉及 MongoDB 集合结构修改时：

- [ ] 提供数据迁移方案（向后兼容）
- [ ] Repository 层的 `_build_filter` 方法适配新字段
- [ ] 种子数据在 `data/seeds/` 中同步更新

### 涉及 LLM/RAG 变更

当变更涉及 AI 推理或 RAG 检索时：

- [ ] 模型切换后验证推理质量
- [ ] RAG 检索参数变更后验证召回率
- [ ] 向量索引重建方案已确认

## 九、状态查询

```bash
# 查看单个变更状态
cat openspec/changes/<change-name>/.openspec.yaml

# 列出所有变更状态
for d in openspec/changes/*/; do
  echo "$(basename $d): $(grep 'status:' $d/.openspec.yaml)"
done
```
