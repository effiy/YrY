# 变更落地工作流

> 代码变更完成后的收口流程：确保代码与规范文档同步，验证一致性，提交推送。

## 一、适用场景

当对代码做了修改（Bug 修复、功能调整、API 变更等），且这些修改涉及 `openspec/changes/` 下的某个变更时，必须执行此流程确保代码和文档保持同步。

## 二、流程步骤

```
代码修改完成
  │
  ▼
1. 回写 OpenSpec 产出物
  │  - 对照代码变更，更新 spec.md 中的场景描述
  │  - 更新 tasks.md，标记已完成任务并修正描述
  │  - 新增行为：在 spec 中添加 ADDED Requirements
  │  - 删除行为：从 spec 中移除对应场景或字段
  │
  ▼
2. 验证（opsx:verify <change-name>）
  │  - 检查完整性（completeness）
  │  - 检查正确性（correctness）
  │  - 检查一致性（coherence）
  │  - CRITICAL 问题必须修复
  │  - WARNING 记录但不阻塞流程
  │
  ▼
3. ⏸️ 确认卡点：是否提交并推送？
  │  - 询问用户是否继续提交推送
  │  - 用户可选择：全部提交 / 仅提交不推送 / 跳过提交
  │  - 用户可在此步骤审查验证结果后再决定
  │
  ▼
4. 提交并推送（用户确认后执行）
  │  - 代码和产出物变更一起提交
  │  - 提交信息描述实际改动内容
  │
  ▼
完成
```

## 三、回写原则

### spec 回写

代码改了什么，spec 就描述什么。决不允许 spec 和代码不一致：

| 变更类型 | 回写操作 |
|----------|----------|
| 移除字段/参数 | 从场景字段列表中删除对应字段 |
| 新增功能 | 添加 ADDED Requirements 或在现有场景中补充 |
| 修改行为 | 更新场景的 WHEN/THEN 描述 |
| 修改 API 契约 | 更新 spec 中的 RPC 方法签名和参数说明 |
| 修改数据模型 | 更新 MongoDB 集合/字段描述 |

### tasks 回写

- 已完成的代码改动，在 tasks 中标记 `[x]`
- 更新任务描述使其准确反映实际实现
- 如果实现与原任务描述有偏差，修正描述而非保留旧描述

### 不回写的情况

纯 Bug 修复（不涉及 spec 定义的变更）时，可以只改代码不回写 spec。判断标准：

- 修复的是已有功能的错误行为 → 不需要回写
- 改变了已有功能的行为定义 → 需要回写
- 修改了 API 契约（参数名、返回结构）→ 必须回写

## 四、验证检查项

### 完整性检查

- [ ] spec.md 中的所有场景都有对应的代码实现
- [ ] 代码中的所有新增功能都在 spec 中有对应描述
- [ ] tasks.md 中的所有任务状态正确（已完成/未完成）

### 正确性检查

- [ ] spec 中描述的字段名与代码中的实际字段名一致
- [ ] API 参数名遵守 RPC 协议约定（`filter` 而非 `query`，`target_file` 而非 `path`，`cname` 而非 `collection_name`）
- [ ] RPC 信封格式正确：`{module_name, method_name, parameters}`
- [ ] Service 层方法签名与 Domain 层一致

### 一致性检查

- [ ] spec 中的模块引用与代码中的实际模块一致
- [ ] MongoDB 集合名在 spec 和代码中一致
- [ ] 类型注解在 spec 和代码中一致
- [ ] 依赖注入链在 spec 和代码中一致

## 五、YiAi 特定检查

### API 契约检查

- [ ] 新增 API 端点已在 `services/` 中正确注册
- [ ] 路由注册使用 `APIRouter + include_router` 模式
- [ ] 响应格式遵循 `{code, message, data}` 结构
- [ ] 错误码在 spec 中有对应说明

### 数据模型检查

- [ ] 新增 MongoDB 集合在 spec 中有字段说明
- [ ] Repository 模式的 `_build_filter` 方法正确处理查询参数
- [ ] ObjectId 序列化使用 `_serialize_id` 辅助方法

### 安全与性能检查

- [ ] JWT 认证中间件覆盖所有需认证的端点
- [ ] 新增外部调用有超时控制和重试策略
- [ ] 数据库查询有分页限制（默认 20，最大 100）

## 六、使用方式

在 Claude Code 中执行 `/opsx:land <change-name>` 一键执行完整流程。

其他 AI 工具参考本文档手动执行：回写 → 验证 → 确认 → 提交。

## 七、示例

**场景**：RAG 混合检索中，将 `query` 参数统一改为 `filter`，以符合跨项目 RPC 契约。

**回写操作**：
- `spec.md`：更新 `data_service.query_documents` 场景中的参数名从 `query` 改为 `filter`
- `tasks.md`：更新任务 3.2 的描述，标注参数名变更

**验证**：`opsx:verify rag-filter-rename` → 检查 API 契约、Repository 层、Service 层一致性 → 无 CRITICAL 问题

**确认**：用户审查验证结果，确认继续 → 提交并推送

**提交**：`fix: 统一 RPC 参数名 query → filter`
