# 跨项目开发工作流

> 跨 YiVad/YiPet/YiAi 三个项目的端到端开发流程。涵盖需求分析、后端实现、前端实现、契约验证、常见陷阱、真实验证方法。

## 一、前置条件

1. 阅读所有涉及的 CLAUDE.md 文件（根目录 + 各项目目录）
2. 确保 YiAi 后端正在运行（`cd YiAi && python main.py`）
3. 了解 [RPC 协议详细规范](../../specs/开发规范/09-规范-RPC协议规范.md)

## 二、完整数据流回顾

```
YiPet（浏览器扩展）──RPC 信封──→ YiAi（FastAPI :10086）←──RPC 信封── YiVad（SPA :8848）
     │                                   │
     │ chrome.storage                    │ MongoDB（Motor 异步）
     │ CDN 资源注入                       │ Ollama（LLM 推理）
     │                                   │ llama_index（RAG）
     └── 不直接访问 MongoDB ─────────────┘
```

**铁律**：YiVad 和 YiPet 不能直接访问 MongoDB——所有数据操作必须通过 YiAi RPC 信封。

## 三、跨项目变更决策树

```
需求来了
  │
  ├── 只需前端修改？
  │     ├── 现有 API 够用 → 只改 YiVad/YiPet
  │     └── 需要新 API → 需要改 YiAi + 前端
  │
  ├── 只需后端修改？
  │     ├── 不影响 RPC 契约 → 只改 YiAi（低风险）
  │     └── 修改 RPC 方法签名 → 需同步更新所有消费端
  │
  └── 涉及 3 个项目？
        └── 按以下顺序：YiAi 后端 → YiVad 前端 → YiPet 扩展
```

## 四、标准流程

### 阶段 1：需求分析与契约设计（最重要）

**关键原则：API 先行——在写任何代码前，先定义好前后端之间的契约。**

```markdown
## 契约草稿

### 需要的数据
- 功能列表（支持分页、按状态筛选、按名称搜索）
- 功能详情（单个查询）
- 功能 CRUD（创建、更新、批量删除）

### RPC 方法设计
| module_name | method_name | 参数 | 返回 |
|-------------|-------------|------|------|
| services.my_feature.my_feature_service | query_my_features | filter, page, page_size | { list, total } |
| services.my_feature.my_feature_service | create_my_feature | document | { key, name, ... } |
| services.my_feature.my_feature_service | update_my_feature | key, update | { key, name, ... } |
| services.my_feature.my_feature_service | delete_my_features | keys | { deleted_count } |

### 参数名审计（对照 RPC 契约表）
- [ ] filter（非 query）✓
- [ ] cname（非 collection_name）✓
- [ ] target_file（非 path）✓ — 如涉及文件操作
```

### 阶段 2：YiAi 后端实现

标准步骤：

```bash
# 1. 创建领域模块
src/domain/my_feature/__init__.py
src/domain/my_feature/core.py           # 核心业务逻辑
src/domain/my_feature/models.py         # Pydantic 模型

# 2. 创建服务层
src/services/my_feature/__init__.py
src/services/my_feature/my_feature_service.py

# 3. 注册到应用（如需要 REST 端点）
# src/app.py — include_router

# 4. RPC 方法自动发现
# 无需额外注册——前端通过 services.my_feature.my_feature_service 调用

# 5. 编写测试
tests/domain/test_my_feature.py

# 6. 运行测试
python -m pytest tests/ -v

# 7. 启动服务验证
python main.py
curl -X POST http://localhost:10086/ \
  -H "Content-Type: application/json" \
  -d '{"module_name": "services.my_feature.my_feature_service", "method_name": "query_my_features", "parameters": {"filter": {}, "page": 1, "page_size": 5}}'
```

### 阶段 5：端到端契约验证

**这是最容易被跳过的步骤，但最关键。**

```bash
# 1. 后端 API 验证
curl -X POST http://localhost:10086/ \
  -H "Content-Type: application/json" \
  -d '{"module_name": "services.my_feature.my_feature_service", "method_name": "query_my_features", "parameters": {"filter": {}, "page": 1, "page_size": 20}}'

# 预期响应：
# {"code": 0, "message": "ok", "data": {"list": [...], "total": N, "page": 1, "page_size": 20}}

# 2. 前端 Network 验证
# 打开浏览器 DevTools → Network 面板
# 检查 RPC 请求体中的参数名是否正确

# 3. 前端类型检查
pnpm type:check   # YiVad
npm run typecheck # YiPet

# 4. 关键参数名审查
grep -rn '"query"' YiVad/src/api/     # 应返回空（参数名应该是 filter）
grep -rn '"collection_name"' YiVad/src/api/  # 应返回空（应该是 cname）
grep -rn '"path"' YiVad/src/api/      # 应只在文件操作中使用 target_file
```

## 五、RPC 契约验证清单

### 请求格式验证

```typescript
// 前端发出的请求（浏览器 DevTools Network 面板中可查看）
{
  "module_name": "services.my_feature.my_feature_service",  // ✓ 完整模块路径
  "method_name": "query_my_features",                       // ✓ snake_case
  "parameters": {
    "cname": "my_features",        // ✓ cname，非 collection_name
    "filter": { "status": "active" }, // ✓ filter，非 query
    "page": 1,                      // ✓ page，非 pageNum（与后端约定一致）
    "page_size": 20                 // ✓ page_size，非 pageSize
  }
}
```

### 响应格式验证

```json
// 后端返回的响应
{
  "code": 0,           // ✓ 成功为 0
  "message": "ok",     // ✓ 默认消息
  "data": {
    "list": [...],     // ✓ 列表在 data.list 中
    "total": 25,       // ✓ 总数
    "page": 1,
    "page_size": 20
  }
}
```

### 参数名契约表（强制遵守）

| 正确 | 错误 | 使用场景 | 曾导致 bug |
|------|------|----------|-----------|
| `filter` | `query` | 所有查询参数 | ✓ 后端静默忽略 query |
| `cname` | `collection_name` | 指定 MongoDB 集合 | ✓ |
| `target_file` | `path` | 文件读写 | ✓ 后端返回 422 |
| `page` | `pageNum`, `page_num` | 分页页码 | 与后端约定一致 |
| `page_size` | `pageSize`, `pageSize` | 每页条数 | 与后端约定一致 |
| `sort` | `sort_field`, `sort_order` | 排序 | 统一用 sort 对象 |

## 六、常见陷阱与真实现象

### 陷阱 1：参数名不匹配（最高频 Bug）

**现象**：前端看似正常工作，但筛选/搜索不生效

**原因**：使用了 `query` 而非 `filter`，后端静默忽略

```typescript
// 错误 — 后端会忽略 query 参数，返回全部数据
parameters: {
  cname: "projects",
  query: { status: "active" },  // ← 应该是 filter
}

// 正确
parameters: {
  cname: "projects",
  filter: { status: "active" },
}
```

**为什么后端不报错？** RPC 路由使用 `**kwargs` 接收参数，无法识别的参数名只是不被使用，不会触发错误。

### 陷阱 2：前后端分页参数不一致

**现象**：分页页码错乱或每页条数不符合预期

**原因**：前端用 `pageNum`/`pageSize`（驼峰），后端期望 `page`/`page_size`（snake_case）

**修复**：统一使用 `page` 和 `page_size`（Python snake_case 是后端标准）

### 陷阱 3：直接修改已有 RPC 方法签名

**现象**：改了后端方法签名，只测了 YiVad，YiPet 默默坏了

**原因**：未识别所有消费端

**修复**：修改 RPC 方法签名前，先搜索所有消费端：
```bash
grep -rn "method_name.*method_name" YiVad/src/api/ YiPet/src/api/
```

### 陷阱 4：忘记更新 YiKnowledge

**现象**：做了跨项目变更，但经验未沉淀

**修复**：变更完成后，将新增的模式、陷阱、坑点更新到 YiKnowledge 对应项目目录

## 七、检查清单（提交前）

### 后端（YiAi）
- [ ] `python -m pytest tests/ -v` 全部通过
- [ ] `ruff check src/` 零错误
- [ ] 新模块分层正确（domain 不导入 server）
- [ ] RPC 方法参数名使用 `filter`/`cname`/`target_file`
- [ ] ObjectId 在返回前序列化为字符串
- [ ] 分页参数有范围限制

### 前端（YiVad）
- [ ] `pnpm type:check` 零错误
- [ ] `pnpm lint && pnpm lint:style` 零错误
- [ ] RPC 请求参数名审查通过（grep `query`/`collection_name` 无结果）
- [ ] 新增 i18n key 中英文齐全
- [ ] 权限使用 `v-auth` 指令
- [ ] DevTools Network 面板验证请求格式正确

### 前端（YiPet）
- [ ] `npm run typecheck` 零错误
- [ ] `npm run build` 成功
- [ ] RPC 请求通过 ApiClient 封装（非直接 fetch）
- [ ] 双世界通信使用正确的 IPC 模式
- [ ] Storage 读写有错误处理

### 知识沉淀
- [ ] 新增模式/陷阱已更新到 YiKnowledge
- [ ] 如涉及新集合，已在根 CLAUDE.md MongoDB 集合概览中更新
