## 第一部分：排序优化体系

### 1.1 检索结果重排序

#### 背景

YiAi 当前使用单阶段混合检索（BM25 + 向量检索 + RRF 融合）——检索精度不足——BM25 和向量检索都无法精确判断文档与查询的深层语义相关性——导致 Top-5 结果中混入不相关文档。

#### 解决方案

**两阶段检索重排序系统**：第一阶段快速检索（BM25+向量+RRF）获取 Top-50 候选——第二阶段使用 CrossEncoder 精细重排序返回 Top-5。

**CrossEncoder 重排序**：与 Bi-Encoder 不同——CrossEncoder 同时接收查询和文档——通过Transformer进行深度语义交互——精准判断相关性。延迟约 20-50ms/文档对——对 Top-50 候选文档重排序总延迟约 1-2.5s——通过批量推理优化到 < 500ms。

**可插拔重排器架构**：
- `BaseReranker` 抽象基类——定义 `rerank(query, documents) -> ranked_documents` 接口
- `CrossEncoderReranker`：基于 CrossEncoder 模型
- `LLMReranker`：基于 LLM 判断文档相关性
- `RuleBasedReranker`：基于规则（新鲜度/权威性/用户偏好）
- `EnsembleReranker`：组合多个重排器的加权融合

**质量指标**：
- MRR（Mean Reciprocal Rank）：第一个相关文档的排名倒数平均值
- NDCG（Normalized Discounted Cumulative Gain）：考虑位置权重的排序质量
- Recall@K：前 K 个结果中包含相关文档的比例
- Precision@K：前 K 个结果中相关文档的比例

**两阶段延迟预算**：
- 第一阶段（检索+融合）：< 200ms
- 第二阶段（CrossEncoder 重排）：< 500ms
- 总延迟目标：< 700ms

### 1.2 检索排序学习（LTR）

#### 背景

固定权重的混合排序策略（RRF k=60）存在固有局限：不同查询类型的"最佳排序"不同——用户行为隐含了宝贵排序信号（点击、停留、复制、收藏）——排序质量无法持续优化——新文档缺乏历史数据难以获得合理排序。

#### 解决方案

**轻量级排序学习系统**：Pointwise + Pairwise 双模式——多维度特征工程——点击日志训练数据——基于 LambdaMART 的轻量模型。

**LTR 三种标准范式**：
- **Pointwise**：单文档评分——预测每个查询-文档对的相关性分数——回归或分类
- **Pairwise**：文档对偏好——判断文档 A 是否比文档 B 更相关——排序问题转化为分类问题
- **Listwise**：整列表优化——直接优化整个排序列表的指标（NDCG/MAP）

**YiAi 选择**：Pointwise（主模式——轻量——易于部署）+ Pairwise（补充——处理偏好信号）——不使用 Listwise（需要更大训练集和计算资源）。

**特征工程（5 大类 20+ 特征）**：
1. **查询-文档匹配特征**：BM25 得分、向量相似度、短语匹配率、同义词覆盖度
2. **文档质量特征**：文档长度、新鲜度（创建时间衰减）、代码块比例、更新频率
3. **文档结构特征**：段落数、标题层级深度、标签数量、引用数
4. **用户行为特征**：历史点击率、停留时间、复制/收藏次数、查询改写率
5. **上下文特征**：查询类型（概念/代码/HowTo）、会话深度、查询长度

**训练数据构建**：从点击日志中提取隐式反馈——点击=正样本（3分）——停留 > 30s +1分——复制/收藏 +2分——未点击但排名靠前=负样本（0分）——未曝光=缺失。

**模型选择**：LambdaMART（LightGBM 实现）——GBDT 变体——直接优化 NDCG——支持特征重要性分析——推理 < 1ms——模型文件 < 1MB。不使用深度神经网络——训练数据不足以支撑——推理延迟不可控。

**冷启动处理**：新文档无行为数据——使用内容特征的先验排序——文档质量特征 + 查询匹配特征——随着行为数据积累——行为特征权重逐渐增加（时间衰减权重）。

**在线评估**：定期对线上流量离线评估排序效果——NDCG@5 月度趋势——各类别 NDCG 对比——特征重要性漂移检测。

### 1.3 检索个性化排序

#### 背景

不同用户查询相同关键词可能有不同的信息需求。"Python 部署"对新手需要入门教程——对老手需要生产环境最佳实践。当前排序对所有用户一视同仁——没有任何个性化信号。

#### 解决方案

**用户画像驱动的个性化排序**：基于用户历史行为构建轻量级用户画像——在排序阶段注入个性化信号。

**用户画像维度**：
- **技能水平**：入门/中级/高级——基于查询复杂度和文档阅读深度推断
- **技术栈偏好**：FastAPI/Django/Flask——基于查询和点击频率推断
- **内容偏好**：代码优先/概念优先/操作指南优先——基于点击类型分布推断
- **活跃时段**：上午/下午/晚间——用于时效性排序（最近活跃时段的文档优先）

**个性化信号注入**：
1. **文档难度匹配**：用户技能水平与文档难度标签（入门/进阶/专家）的匹配度
2. **技术栈匹配**：文档中提及的技术栈与用户偏好的技术栈的余弦相似度
3. **内容类型匹配**：文档类型（代码/概念/操作指南）与用户偏好类型的匹配度
4. **新鲜度偏好**：用户历史点击的文档时间分布——用于调整时效性权重

**个性化权重配置**：基础排序分数 × 0.7 + 个性化分数 × 0.3——个性化是改善而非颠覆——基础相关性仍占主导。

**隐私保护**：所有用户画像存储为匿名 session_id 关联——不存储用户真实身份——7 天未活跃自动清除画像。

### 1.4 检索时效性排序

#### 背景

知识的时效性在不同领域差异巨大。技术文档：新版本信息比旧版本更有价值——1 年前的 API 文档可能已过时。法律文档：法规本身具有时效性——新法优于旧法。但有些知识（如基础数学概念）时效性无关。

#### 解决方案

**时间感知排序（TemporalRanker）**：基于文档创建/更新时间——结合领域时效性衰减曲线——动态调整文档权重。

**时效性衰减函数**：
```
temporal_weight = base_weight × exp(-λ × age_in_days)
```
- λ（衰减率）根据领域配置：
  - 技术文档：λ=0.005（半衰期约 138 天）
  - 法律文档：λ=变化率——根据法规有效期
  - 基础知识：λ=0.0001（几乎不衰减）
  - 新闻/公告：λ=0.05（半衰期约 14 天）

**领域自动识别**：基于文档的 category 和 tags 自动匹配领域——使用对应的衰减率。未匹配任何领域时使用默认衰减率（λ=0.002——半衰期约 346 天）。

**时间窗口过滤**：
- 用户可指定时间范围："最近一周"、"最近一月"、"最近一年"
- 搜索结果默认不隐藏旧文档——而是通过衰减权重降低排名
- 提供"最新优先"和"最相关优先"切换选项

**事件时间敏感处理**：某些查询天然具有时间敏感性（"2026 年最新"、"最近发布"）——系统识别时间关键词——大幅提升时效性权重。

### 1.5 检索字段加权

#### 背景

不同文档字段对检索相关性的贡献不同。title 字段的匹配比 content 字段的匹配更重要——tags 字段的精确匹配比 content 的模糊匹配更具指示性。当前 BM25 和向量检索对所有字段一视同仁。

#### 解决方案

**字段感知检索权重（FieldWeightedRetriever）**：在检索和排序阶段对不同的文档字段赋予不同的权重。

**默认字段权重（BM25F 风格）**：
| 字段 | 权重 | 说明 |
|------|------|------|
| title | 3.0 | 标题匹配最重要——直接反映文档主题 |
| tags | 2.0 | 标签精确匹配——强相关信号 |
| summary | 1.5 | 摘要匹配——内容浓缩 |
| content | 1.0 | 正文匹配——基准权重 |
| category | 0.5 | 分类匹配——弱信号——辅助 |

**字段长度归一化**：结合字段长度归一化避免短字段（如 title）天然占优——匹配分数 / sqrt(field_length)。

**BM25F 实现**：扩展 BM25 支持多字段——每个字段独立计算词频和文档长度——加权求和：
```
BM25F(q, d) = Σ(field_weight[f] × BM25(q, d, field=f))
```

**向量检索字段加权**：对多字段分别计算向量相似度——加权融合：
```
vector_score(q, d) = Σ(field_weight[f] × cosine_sim(emb_q, emb_d(f)))
```

**字段权重可配置**：通过配置文件调整权重——不同知识库可定制——无需修改代码。

### 1.6 检索多目标优化

#### 背景

检索排序不仅需要"相关性"一个目标——还需要同时优化"多样性"（避免结果同质化）、"新鲜度"（包含最新信息）、"权威性"（优先可信来源）。多个目标之间存在冲突——需要多目标优化框架。

#### 解决方案

**多目标排序优化（MultiObjectiveRanker）**：将多个排序目标形式化为标量优化问题——通过权重融合或帕累托优化。

**四维目标**：
1. **相关性**（Relevance）：查询与文档的内容匹配度——基于 BM25+向量+CrossEncoder
2. **多样性**（Diversity）：结果集中文档之间的差异度——基于 Jaccard/embedding 距离
3. **新鲜度**（Freshness）：文档的时间维度——新鲜内容加分
4. **权威性**（Authority）：文档来源可信度——基于引用数/作者信誉

**融合策略**：
- **加权求和**（默认）：`score = w1×rel + w2×div + w3×fresh + w4×auth`——权重通过 A/B 测试调优
- **帕累托优化**（高级）：保留非受支配解——让用户在相关性-多样性之间滑动调节
- **约束满足**：相关性为主目标——其他目标作为约束（如 diversity_score > 0.3）

**默认权重**：相关性 0.5——多样性 0.2——新鲜度 0.2——权威性 0.1。权重通过 A/B 测试持续调优。

**应用场景**：
- 探索性搜索：提升多样性权重（0.3）——展示不同类型的文档
- 精确搜索：提升相关性权重（0.7）——严格匹配
- 综述搜索：提升新鲜度+权威性——获取最新、最权威的信息

### 1.7 检索结果多样性

#### 背景

搜索结果中 10 个结果可能都来自同一篇长文档的不同段落——或者都是同一类型的文档（全是概念介绍——没有操作指南）。用户看到的不是多样化的信息——而是重复内容。需要结果多样化——确保不同来源、不同类型、不同子主题的文档都有展现。

#### 解决方案

**结果多样性保证（DiversityRanker）**：MMR（最大边际相关性）算法在重排序阶段注入多样性约束。

**MMR 公式**：
```
MMR = argmax[ λ × Rel(d, q) - (1-λ) × max(Sim(d, d_selected)) ]
```
- λ=0.7：70% 权重给相关性——30% 给多样性
- Sim(d, d_selected)：文档与已选择文档的 Jaccard/embedding 相似度

**多样性维度**：
- **来源多样性**：限制同一来源文档的最大数量（如最多 3 篇）
- **类型多样性**：确保不同类型（概念/操作/代码/参考）各有代表
- **子主题多样性**：通过 embedding 聚类——确保不同子主题簇都有文档入选
- **时间多样性**：新老文档混合——避免仅有新文档或仅有旧文档

**贪心选择算法**：
1. 从候选集中选择相关性最高的文档
2. 迭代选择：选择与已选文档集最不相似且相关性最高的文档
3. 重复直到选满 K 个文档

**聚类增强多样性**：对 Top-100 候选结果做 embedding 聚类（K-Means——K=5-10）——从每个聚类中选择相关性最高的 1-2 个文档——保证主题覆盖。

### 1.8 检索语言偏好

#### 背景

多语言知识库中——用户搜索"deployment"时——期望看到英文文档还是中文文档？当前检索对语言无偏好——中英文文档按分数混排——可能导致用户更偏好的语言被次要语言的文档挤出 Top-K。

#### 解决方案

**语言感知检索（LanguageAwareRetriever）**：自动检测查询语言——识别用户语言偏好——在排序中给予偏好语言文档适当加权。

**查询语言检测**：统计 CJK 字符占比——CJK > 50%→中文——ASCII > 80%→英文——其他→自动检测或用户指定。

**用户语言偏好推断**：
- 当前查询语言：最直接的信号
- 历史点击语言分布：用户更经常阅读哪种语言的文档
- 用户配置语言：用户设置中的默认语言
- 知识库默认语言：知识库主要语言作为回退

**语言加权**：偏好语言文档排序分数 ×1.1——其他语言文档排序分数 ×0.9——避免非偏好语言完全不可见。

**跨语言搜索**：查询"RAG 检索"同时检索中文和英文文档——提供"查看英文结果"的切换入口。

### 1.9 检索地理感知

#### 背景

YiAi 作为内部知识库——不同团队/地理位置可能使用不同的术语、关注不同的内容、遵循不同的规范。当前检索对所有地区一视同仁——不考虑地理差异。

#### 解决方案

**地理感知检索（GeoAwareRetriever）**：基于用户的地理位置/团队归属——调整检索的相关性排序。

**地理维度**：
- **团队归属**：用户所在团队（前端/后端/测试/运维）
- **物理位置**：办公楼/城市/时区
- **组织架构**：部门/产品线

**地理信号注入**：
- **团队术语偏好**：同一概念在不同团队有不同术语（后端"服务" vs 前端"组件"）——查询时基于团队偏好重写
- **团队文档优先**：本团队创建的文档排序优先
- **跨团队知识推荐**：在排序中加入其他团队的相关但不重复的文档

**隐私保护**：地理信息来自用户可选配置——不自动追踪地理位置。

### 1.10 检索难度评估

#### 背景

不是所有查询的难度相同。简单查询（"什么是 Python"）和困难查询（"Kubernetes 中 Pod 间网络策略如何影响 Service Mesh 的 sidecar 注入"）需要的检索策略和 top-k 数量完全不同。统一策略导致：简单查询结果过多、困难查询结果不足。

#### 解决方案

**查询难度自适应检索（DifficultyAdaptiveRetriever）**：评估查询难度——根据难度调整检索参数。

**难度评估维度**：
1. **查询长度**：< 10 字符→低难度——10-30 字符→中难度——> 30 字符→高难度
2. **查询具体性**：包含具体术语（"Ollama/BM25/RRF"）→高难度——泛化查询（"如何优化"）→中难度
3. **术语稀有度**：查询词在知识库中的 IDF 分布——高 IDF 词多→精确查询（低难度）——高 IDF 词少→泛化查询（高难度）
4. **历史成功率**：相似查询的历史检索成功率

**难度分类**：
| 难度 | top_k | 检索策略 | 说明 |
|------|-------|---------|------|
| 简单 | 5 | 精确匹配为主 | 查询明确——小范围精确结果 |
| 中等 | 10 | 混合检索 | 标准策略 |
| 困难 | 20 | 高召回——语义优先 | 需要更广泛的匹配 |
| 极难 | 30+ | 多级松弛+重排序 | 可能零结果——多级恢复 |

**动态 top_k**：`top_k = base_k + difficulty × expansion_factor`——简单查询 base_k=5——每增加一个难度等级 +5——最大 30。

**难度标签返回**：在搜索结果中附带 `difficulty: "medium"` 标签——前端可根据难度调整展示策略（如困难查询展示更长的摘要片段）。

## 第二部分：缓存优化体系

### 2.1 检索结果缓存分层

#### 背景

相同或相似的查询被反复执行——每次都要重新进行向量检索和 BM25 检索——浪费计算资源。高频查询（如新用户常见"什么是 RAG"）的缓存收益巨大。

#### 解决方案

**分层缓存策略（LayeredCache）**：L1 内存 LRU + L2 Redis + L3 MongoDB——逐层回退。

**L1 内存 LRU 缓存**：
- 存储：查询→结果列表——序列化后结果
- 容量：1000 条（约 20MB）
- 命中延迟：< 1ms
- 淘汰策略：LRU + TTL（5 分钟）
- 适用：高频热点查询

**L2 Redis 缓存**：
- 存储：查询→结果列表——压缩后结果
- 容量：10000 条
- 命中延迟：< 5ms
- TTL：30 分钟
- 适用：中频查询——跨进程共享

**L3 MongoDB 持久缓存**：
- 存储：预计算的高成本查询结果（如嵌套查询、聚合查询）
- TTL：24 小时
- 适用：低频但高成本的查询

**缓存键设计**：`cache_key = md5(query_text + filter_params + top_k + session_context_hash[:8])`——确保缓存键的精确性同时考虑上下文差异。

**缓存失效策略**：
- TTL 过期：时间驱动的自动失效
- 主动失效：知识库文档更新时——通过 MongoDB Change Stream 触发缓存清理
- 版本失效：embedding 模型更新时——所有向量检索结果缓存全量失效

**缓存命中率目标**：L1 > 40%——L2 > 25%——总命中率 > 65%。

---

### 2.2 检索缓存策略优化

#### 背景

缓存不是越多越好——缓存对象的大小、TTL 时长、淘汰策略都需要针对检索场景优化。过大的缓存占用内存——过短的 TTL 命中率低——过长的 TTL 返回陈旧结果。

#### 解决方案

**自适应缓存策略（AdaptiveCache）**：基于查询频率、结果稳定性、内存压力动态调整缓存参数。

**查询分类缓存策略**：
- **热门查询**（> 10 次/小时）：L1 缓存——TTL 5 分钟——结果变化时主动更新
- **常规查询**（1-10 次/小时）：L2 缓存——TTL 30 分钟
- **低频查询**（< 1 次/小时）：不缓存或 L3 缓存——TTL 24 小时
- **实时查询**（指定 no_cache）：不缓存——每次实时检索

**缓存大小控制**：
- L1 内存上限：50MB——超过后增大淘汰速率
- L2 Redis 上限：200MB——接近上限时降低 TTL
- 压力感知：内存使用 > 80% 时——降低所有 TTL 50%——加速淘汰

**结果稳定性评估**：相同查询在时间窗口内结果的变化程度——高稳定性查询（知识库变化小）延长 TTL——低稳定性查询（知识库频繁更新）缩短 TTL。

**预热策略**：
- 启动时：加载 Top-100 热门查询到 L1 缓存
- 知识库更新后：预测受影响的高频查询——主动重新计算并更新缓存

---

### 2.3 检索同义扩展缓存

#### 背景

同义词扩展需要进行短语匹配+词匹配+组合生成+去重——每次检索都要重复执行——对于相同查询这是浪费。同义词扩展结果（查询变体列表）可以缓存——直接复用。

#### 解决方案

**同义词扩展缓存（SynonymExpansionCache）**：LRU 缓存同义词扩展结果——与同义词词典版本关联——词典更新时缓存失效。

**缓存内容**：`cached_expansion = {original_query → [{variant_query, weight}, ...]}`

**版本关联**：同义词词典有 version 字段——缓存 key 包含 `synonym_version`——词典更新时所有缓存自动失效（版本号不匹配）。

**缓存命中流程**：
1. 查询到达→检查同义词扩展缓存
2. 命中→直接获取变体列表→跳过扩展计算→仅执行检索
3. 未命中→执行扩展→缓存结果→执行检索

**缓存命中率预算**：高频查询（如"MCP（Model Context Protocol）的 MCP Server"）的扩展结果固定——命中率 > 90%。

## 第三部分：性能管理体系

### 3.1 检索性能剖析

#### 背景

检索质量需要量化——优化效果需要对比。当前缺乏系统化的性能追踪——不知道检索各阶段的耗时分布——无法定位瓶颈——优化方向靠猜测。

#### 解决方案

**检索性能剖析系统（RetrievalProfiler）**：全链路耗时追踪——分阶段指标采集——趋势分析——异常检测。

**分阶段耗时追踪**：
| 阶段 | 追踪指标 | 正常范围 |
|------|---------|---------|
| 查询预处理 | 分词/同义词/拼写纠正 | < 30ms |
| 向量检索 | Embedding+ANN 搜索 | < 100ms |
| BM25 检索 | 关键词检索 | < 50ms |
| RRF 融合 | 结果融合排序 | < 10ms |
| 重排序 | CrossEncoder 重排 | < 500ms |
| 后处理 | 高亮/摘要/缓存 | < 100ms |
| **总计** | **全链路** | **< 800ms** |

**关键指标（KPI）**：
- P50/P95/P99 延迟
- 各阶段耗时占比
- 不同查询类型的延迟分布（概念/代码/HowTo）
- 不同并发下的延迟表现（1/5/10/20 并发）
- 失败率/超时率

**趋势分析**：每日自动生成性能趋势图——对比前 7 天和 30 天——异常波动自动告警。

**异常检测**：基于历史 P95 建立基线——P95 超过基线 2σ 时触发告警——自动关联最近的代码变更/配置变更。

**性能剖析仪表盘**：Graphana/Metrics 可视化——实时延迟热力图——各阶段耗时瀑布图——查询类型延迟对比。

---

### 3.2 检索质量报告

#### 背景

检索质量无法量化——"感觉"变好了但没有数据支撑。需要定期生成检索质量报告——追踪核心质量指标的趋势——识别退化——指导优化方向。

#### 解决方案

**检索质量报告系统（QualityReporter）**：每周/每月自动生成检索质量报告——包含 8 大维度指标。

**8 大质量维度**：
1. **召回率（Recall）**：相关文档被检索到的比例——基于标注测试集
2. **精确率（Precision）**：检索结果中相关文档的比例
3. **NDCG@5**：前 5 个结果的归一化折损累计增益
4. **MRR**：第一个相关文档的平均倒数排名
5. **零结果率**：返回空结果的查询比例
6. **低质量率**：Top-1 分数 < 0.3 的查询比例
7. **用户满意度**：点击率、停留时间、追问率
8. **分类质量**：不同查询类型的质量差异——识别短板类型

**报告内容**：
- 质量趋势图（周/月）
- 与上周/上月的对比（Delta 值）
- Top-10 退化查询（质量下降最多的查询）
- Top-10 零结果查询
- 各重排器贡献分析
- 改进建议

**自动告警**：NDCG@5 周环比下降 > 10%→自动告警——零结果率上升 > 20%→自动告警。

**报告分发**：邮件/企微定时推送——管理后台可在线查看。

## 第四部分：稳定性体系

### 4.1 检索降级策略

#### 背景

RAG 检索是多层流水线——任何环节的故障或性能劣化都可能导致整个检索不可用。embedding 服务超时→整个检索 500 错误——但 BM25 仍可用。重排序服务变慢→请求堆积→线程池耗尽→影响其他正常请求。

#### 解决方案

**多级优雅降级系统（GracefulDegradation）**：5 级降级链——熔断器保护——半开探测——自动恢复。

**5 级降级链**：
| 级别 | 名称 | 功能描述 | 触发条件 |
|------|------|---------|---------|
| L0 | 全功能 | 所有组件正常 | 无故障 |
| L1 | 无重排序 | 跳过 CrossEncoder 重排——使用 RRF 排序 | 重排器延迟 > 500ms 或错误率 > 10% |
| L2 | 无向量检索 | 仅 BM25 关键词检索 | Embedding 模型不可用或超时 |
| L3 | 无 BM25 | 仅向量语义检索 | MongoDB 故障——仅内存索引可用 |
| L4 | 仅缓存 | 返回缓存结果——不执行新检索 | 大规模故障 |
| L5 | 零结果+提示 | 返回友好提示 | 全面不可用 |

**熔断器模式**：
- **CLOSED**：正常状态——请求通过
- **OPEN**：熔断——直接返回降级结果——不调用故障服务
- **HALF_OPEN**：半开——允许少量探测请求通过——测试服务是否恢复

**熔断参数**：
- 错误阈值：连续 5 次失败或 1 分钟内错误率 > 50%
- 超时阈值：P95 延迟超过基线 3 倍
- 熔断冷却时间：30 秒（CLOSED→OPEN 后——30 秒后进入 HALF_OPEN）
- 探测请求：3 次——1 次成功→恢复 CLOSED——3 次全部失败→回 OPEN

**自动恢复**：
- HALF_OPEN 状态下——每 30 秒发送一个探测请求
- 探测成功→恢复 CLOSED——全功能检索
- 探测失败→保持 OPEN——继续降级

**降级监控**：实时显示当前降级级别——各级别持续时间——降级触发原因——恢复时间。

### 4.2 检索实验平台

#### 背景

检索优化需要安全可控的实验环境——在线直接修改检索参数风险高——一旦参数不当——影响所有用户——难以回退。

#### 解决方案

**检索实验平台（RetrievalExperimentPlatform）**：支持离线评估和在线灰度实验——参数对比——效果量化。

**离线实验模式**：
- 固定查询集（1000+ 标注查询）——测试不同检索参数的效果
- 自动计算 NDCG/MRR/Recall 指标
- 参数空间自动搜索（Grid Search / Bayesian Optimization）
- 生成参数效果对比报告

**在线灰度实验**：
- 按百分比分流（5% → 20% → 50% → 100%）
- 分流策略：一致性哈希（session_id）——确保同一用户始终在同一实验组
- 并行运行多个实验组+对照组——自动收集质量指标
- 统计显著性检验（t-test / Mann-Whitney U）——p < 0.05 判定显著

**实验配置**：JSON/YAML 格式——定义实验组参数（embedding_model/chunk_size/top_k/reranker_type/weights）——支持热更新——无需重启。

**胜者自动选择**：实验结束后——自动比较实验组和对照组的 OEC（Overall Evaluation Criterion——如 NDCG@5）——胜者自动提升为默认策略——失败策略自动归档。

## 第五部分：AB测试框架

### 5.1 检索AB测试框架

#### 背景

检索质量优化是持续迭代过程——每次变更都需要验证效果。缺乏系统化的 A/B 测试框架导致：变更效果不可量化——回退无依据——多策略无法公平对比——噪声干扰判断——实验结论不可复现。

#### 解决方案

**完整 A/B 测试框架（ABTestFramework）**：流量分割 + 指标采集 + 统计显著性 + 胜者声明。

**流量分割**：
- 按 session_id 哈希分桶——保证同一 session 始终在同一实验组
- 多层实验：支持嵌套实验（在 A/B 组内再做 A/B）
- 互斥层：确保一个用户不会同时在多个冲突实验中
- 默认分配比例：对照组 50% + 实验组 50%

**核心指标体系（OEC）**：
- **主指标**（Overall Evaluation Criterion）：NDCG@5——衡量排序质量的改善
- **护栏指标**（Guardrail Metrics）：
  - P99 延迟：不能因优化质量而大幅牺牲性能
  - 零结果率：不能因追求精确而降低召回
  - 错误率：不能因新策略引入 bug
- **从指标**：MRR、CTR、停留时间、追问率——辅助解释主指标变化

**统计显著性**：
- 样本量计算：基于期望效应量（2% NDCG 改善）和统计功效（80%）计算所需最小样本量
- 统计检验：独立双样本 t-test（连续指标）——Chi-square test（比例指标）
- 显著性阈值：p < 0.05
- Peeking 防护：不在实验过程中多次检验并提前终止——使用固定时间窗口

**胜者声明流程**：
1. 实验达到最小样本量（如 1000 次搜索）
2. 主指标有统计显著改善（p < 0.05）
3. 护栏指标无显著退化
4. 自动声明胜者——推荐推全——人工确认
5. 实验组策略提升为默认——原默认策略归档

**实验隔离**：
- 缓存隔离：实验组不使用对照组的缓存——防止数据污染
- 日志隔离：实验组和对照组的日志打上实验标签——便于事后分析
- 配置隔离：每个实验有独立的检索参数配置

## 第七部分：统一设计原则

1. **两阶段架构**：粗筛→精排是排序优化的核心模式——第一阶段快速获取候选——第二阶段精细排序
2. **多目标平衡**：排序不是单一目标——相关性与多样性/新鲜度/权威性需要权衡
3. **缓存分层**：L1 内存→L2 Redis→L3 MongoDB 三级缓存——热点查询零延迟——长尾查询可降级
4. **降级保护**：5 级降级链确保任何组件故障不影响核心检索可用性
5. **数据驱动**：排序参数通过 A/B 测试优化——质量指标持续追踪——退化自动告警
6. **可插拔架构**：重排器、缓存策略、降级策略都可插拔可配置——支持灵活的实验和切换

## 经验教训

1. **根本原因**：开发过程中对边界情况和异常路径的考虑不足是此类问题的共同根因
2. **设计阶段**：在接口设计和模块实现时，应主动考虑异常输入、空值、超时等边界场景
3. **代码审查**：审查时应检查是否存在类似的反模式（如未捕获异常、无超时控制、缺少参数校验等）
4. **测试覆盖**：异常路径的测试覆盖率应与正常路径同等重视
5. **团队分享**：此类问题应在团队周会或技术分享中讨论，形成团队共识
