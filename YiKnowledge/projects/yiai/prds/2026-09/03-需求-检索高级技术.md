## 第一部分：高级检索算法

### 1.1 检索语义哈希

#### 背景

当前检索系统依赖 768 维稠密向量进行相似度搜索——每次查询需遍历全部文档向量计算余弦相似度。在 10000 文档规模下——单次向量检索耗时 50-200ms——当并发查询增多时延迟线性增长。语义哈希将高维稠密向量压缩为低维二值码（如 64-bit）——用 Hamming 距离替代余弦相似度——检索速度提升 10-50 倍。

#### 解决方案

**两阶段语义哈希检索**：粗筛（Hamming 距离快速过滤）→ 精排（余弦相似度精确排序）。

**哈希函数学习**：
- 目标：将 768 维向量映射为 64-bit 二值码——保持语义相似性
- 方法：LSH（局部敏感哈希）——随机投影——ITQ（迭代量化）——最小化量化误差
- 训练：使用知识库文档的 embedding 向量作为训练数据——ITQ 迭代优化投影矩阵

**Hamming 距离搜索**：
- 64-bit 二值码的 Hamming 距离计算使用 CPU 的 POPCNT 指令——单次比较 < 1ns
- 全量比较 10000 文档耗时约 10us——远小于余弦相似度（30ms）
- 粗筛阶段：Hamming 距离 < 12（保留约 10% 候选即 1000 个文档）
- 精排阶段：对粗筛候选进行余弦相似度精确排序 Top-K

**哈希碰撞处理**：
- 多个语义不同的文档可能产生相同的 64-bit 哈希码——识别碰撞桶
- 碰撞桶中的文档在精排阶段全部参与——通过余弦相似度消歧
- 碰撞率监控——碰撞率 > 5% 时——增加哈希码长度（64→128 bit）

**增量更新**：新文档加入时——使用学习到的哈希函数直接映射——无需重新训练。但知识库文档数增长超过 50% 时——建议重新训练哈希函数以适应分布变化。

**内存优势**：10000 文档 × 64-bit 哈希码 = 80KB vs 768 维 × 4字节 × 10000 = 30.7MB——内存减少 384 倍。

### 1.2 检索对比学习

#### 背景

标准的有监督学习依赖人工标注数据——在搜索场景中标注成本高且标注质量不稳定。对比学习（Contrastive Learning）通过构造正负样本对——让模型学习区分"相似"和"不相似"的查询-文档对——无需人工标注即可提升 embedding 质量。

#### 解决方案

**对比学习训练嵌入模型**：正样本（点击的文档+查询）vs 负样本（未点击的文档+查询）——通过对比损失优化 embedding——使相关对靠近、不相关对远离。

**训练数据构建**：
- **正样本**：用户点击的查询-文档对 + 停留时间 >= 10 秒
- **难负样本**：高排名但未被点击的文档 + 随机采样负样本
- **数据增强**：同义词替换、随机词删除、回译——扩展正样本多样性

**损失函数**：
- **InfoNCE Loss**：标准对比损失——正样本对相似度最大化——负样本对相似度最小化
- **温度参数 τ**：控制正负样本区分的"锐度"——较小 τ 让模型更关注难负样本
- **Batch Size**：越大越好（更多负样本）——受限于 GPU 内存——使用梯度累积模拟大 batch

**在线对比学习**：从用户点击日志实时提取正负样本对——增量更新 embedding 模型——无需离线全量重训练——延迟 1 天即可反映最近的用户偏好。

**模型评估**：在标准检索测试集上评估 embedding 模型质量（NDCG/MRR）——对比训练前后的改善。

### 1.3 检索蒸馏模型

#### 背景

大型检索模型（如 CrossEncoder BERT-large）精度高但推理慢（50-100ms/对）——小型模型（DistilBERT/BERT-tiny）推理快但精度低。模型蒸馏（Knowledge Distillation）将大模型（Teacher）的知识迁移到小模型（Student）——实现精度和速度的最佳平衡。

#### 解决方案

**Teacher-Student 蒸馏**：使用 CrossEncoder BERT-large 作为 Teacher——DistilBERT 或 BERT-tiny 作为 Student——通过蒸馏将 Teacher 的排序能力迁移到 Student。

**蒸馏策略**：
1. **软标签蒸馏**：Teacher 输出每个文档对的相关性分数（软标签）——Student 学习预测这些软标签
2. **排序蒸馏**：Teacher 对 Top-100 候选排序——Student 学习复制这个排序
3. **特征蒸馏**：Teacher 的中间层表示迁移到 Student——Student 学习 Teacher 的内部表征

**蒸馏损失**：
```
L_total = α × L_hard(Student预测, 真实标签) + β × L_soft(Student预测, Teacher软标签)
```
- α=0.3（真实标签权重——如有的话）
- β=0.7（软标签权重——知识迁移主信号）

**蒸馏效果**：Student 模型推理速度提升 5-10 倍（5-10ms vs 50-100ms）——精度保留 90-95%（NDCG@5 从 0.85→0.82）。

**自动更新**：当 Teacher 模型更新时（换用更强的 CrossEncoder）——自动重新蒸馏 Student——保持 Student 精度跟随 Teacher 进步。

### 1.4 检索零样本学习

#### 背景

新领域上线时——缺乏标注的查询-文档对——检索模型需要从零开始积累数据。零样本学习（Zero-Shot Learning）让模型在没有任何目标领域训练数据的情况下——基于通用知识完成检索——缩短冷启动时间。

#### 解决方案

**零样本检索**：使用大规模通用领域预训练的 CrossEncoder/Embedding 模型——通过 prompt 工程注入领域信息——无需领域特定训练。

**Prompt 工程**：
- 为查询-文档相关性判断设计零样本 prompt：
  ```
  "查询: {query}\n文档: {doc_text}\n\n该文档是否与查询相关? 回答 是/否"
  ```
- 将二分类转换为相关性分数（"是"的 logit 概率）
- 多条文档并行推理——批量化提升效率

**领域适配策略**（低资源场景）：
- **Few-Shot Prompt**：在 prompt 中提供 2-3 个该领域的标注示例——引导模型理解领域特征
- **In-Context Learning**：在 prompt 上下文提供领域关键词表——帮助模型进行术语映射
- **主动学习**：从零样本检索结果中选择不确定性最高的文档——请求人工标注——进行少样本微调

**冷启动评估**：在新领域的检索基准测试上——零样本 CrossEncoder 的 NDCG@5 应达到该领域最优模型的 70-80%——弥补训练数据积累初期的检索质量差距。

### 1.5 检索在线学习

#### 背景

用户的搜索行为持续产生新的偏好数据——但离线模型训练是周期性的（每周/每月）——模型更新滞后于用户变化。在线学习（Online Learning）让模型实时从用户反馈中学习——持续适应最新的检索偏好。

#### 解决方案

**增量在线学习**：基于用户点击/未点击反馈——实时更新排序模型参数——无需全量重训练。

**学习信号来源**：
- 即时信号：点击（正）vs 跳过（负）——查询后 < 1s 内产生
- 短期信号：停留时间 > 30s（正）vs < 5s（负）——查询后 30s 产生
- 长期信号：收藏、复制、引用——查询后数小时至数天产生

**增量更新算法**：
- FTRL（Follow The Regularized Leader）：Google 使用的在线学习算法——稀疏更新——内存高效——适合大规模特征
- 每个特征独立维护学习率——频繁特征用小学习率——稀疏特征用大学习率
- 更新延迟 < 10ms——不影响检索响应

**特征工程**：在线学习使用与离线 LTR 相同的特征集——确保在线和离线模型兼容——在线学习定期合并回离线模型（每月）。

**遗忘机制**：过时行为自动衰减——timestep 权重 = exp(-λ × days_since)——λ=0.01——100 天前的行为权重为 0.37。

**Exploration-Exploitation 平衡**：以 0.95 概率使用当前最优策略（Exploitation）——以 0.05 概率探索新策略（Exploration——随机顺序或新特征测试）。

### 1.6 检索对抗训练

#### 背景

检索模型可能被利用——用户输入恶意构造的查询——诱使模型返回特定排序结果（SEO 攻击）。模型对轻微的输入扰动应该保持鲁棒——不应该因一两个无关词的增删导致排序剧变。

#### 解决方案

**对抗训练增强鲁棒性**：在训练过程中加入对抗样本——让模型学会抵抗恶意扰动和自然噪声。

**对抗样本生成**：
1. **词替换**：同义词替换——通过 BERT 预测被 mask 的词——替换为相似但不改变语义的词
2. **词插入**：插入停用词或不影响查询意图的修饰词
3. **词删除**：删除非关键词——保留查询核心意图
4. **字符级扰动**：模拟打字错误——插入/删除/替换单个字符

**对抗训练损失**：
```
L_adv = L_clean(query, doc) + λ × L_clean(query_adv, doc)
```
- λ=0.5——对抗损失权重
- query_adv：对抗扰动后的查询

**鲁棒性评估**：
- 检索结果稳定性：同一查询 + 轻微扰动 → Top-5 排序变化的 Normalized Kendall Tau < 0.1
- 对抗攻击防御：构造恶意查询——验证排序结果不会被恶意操控

**在线对抗检测**：
- 检测异常查询模式（重复词过多、特殊字符比例过高）
- 检测检索结果中单个文档分数异常突出（可能是 SEO 攻击）
- 异常查询标记——降级处理——人工审核

### 1.7 检索知识增强

#### 背景

Embedding 模型的知识截止于训练日期——无法理解训练后出现的新术语、新概念、新产品名。纯检索依赖 embedding 相似度——对未见过的术语缺乏理解。

#### 解决方案

**知识增强检索（Knowledge-Enhanced Retrieval）**：将知识图谱的结构化知识注入到检索过程——补充 embedding 模型的盲区。

**知识注入方式**：
1. **查询端知识扩展**：从知识图谱查询实体的属性、别名、上位词——扩展查询表达
2. **文档端知识标注**：文档中识别的实体链接到知识图谱——检索时利用图谱关系计算关联度
3. **知识图谱嵌入**：TransE/RotatE 等图谱嵌入模型——将实体和关系映射到向量空间——作为检索排序的补充特征

**新术语处理**：
- 新术语出现在查询中但不在知识图谱中→触发实体发现流程
- 从搜索结果中提取新术语的上下文描述→LLM 生成临时定义→加入临时知识库
- 累计出现 5 次以上→提交人工审核→加入正式知识图谱

**知识融合权重**：检索分数 = 0.7 × embedding_score + 0.3 × kg_score（知识图谱相关度分数）

## 第二部分：多模态检索

### 2.1 检索多模态查询

#### 背景

当前 YiAi RAG 检索仅处理纯文本查询。用户可能上传图片并提问"这个电路图里的元件是什么型号？"——需要同时理解图片内容和文本问题。知识库中也有图表/截图——需要跨模态检索。

#### 解决方案

**多模态检索管道**：文本+图片混合查询——CLIP 视觉编码——跨模态向量空间对齐——多模态排序融合。

**图片向量提取**：
- 使用 CLIP ViT-B/32 作为视觉编码器——将图片转换为 512 维嵌入向量
- 文本编码器（CLIP Text Encoder）将文本转换为同维度的嵌入向量
- 图片和文本嵌入在 CLIP 的联合向量空间中对齐——可直接比较余弦相似度

**查询模态自动检测**：
- 纯文本查询：仅使用文本嵌入检索
- 纯图片查询：使用图片嵌入——检索视觉相似文档
- 图文混合查询：文本嵌入 + 图片嵌入加权融合（默认 0.5/0.5）

**跨模态检索**：
- 文本查图片：文本嵌入 vs 知识库中文档的图片嵌入
- 图片查文本：图片嵌入 vs 知识库中文本嵌入
- 图片查图片：图片嵌入 vs 图片嵌入——以图搜图

**多模态排序融合**：
- 文本检索分数（BM25+向量）+ 图片检索分数（CLIP 相似度）
- 归一化处理：两种模态的分数范围不同——使用 Min-Max 归一化到 [0, 1]
- 加权融合：用户可指定 text_weight 和 image_weight

**性能优化**：
- 图片嵌入预计算并缓存——检索时不重新计算
- 图片数量 > 100 时——使用语义哈希粗筛——缩小候选范围
- 图片嵌入维度 512——比文本嵌入 768 小——检索更快

### 2.2 检索批量查询优化

#### 背景

某些场景需要批量执行检索——如批量评估实验（100 个查询对比两种策略）——知识缺口扫描（500 个主题查询）——数据导入验证。顺序执行 100 个查询耗时长——并行执行资源消耗大。

#### 解决方案

**批量查询优化器（BatchQueryOptimizer）**：查询去重合并——共享 embedding 计算——并行调度——结果分流。

**优化策略**：
1. **查询去重**：相同或高度相似（embedding cos > 0.95）的查询合并为一个——结果共享
2. **共享 Embedding**：批量查询的 embedding 一次性计算——减少模型调用次数
3. **共享检索**：去重后的查询——检索结果共享——减少检索执行次数
4. **并发控制**：最大并发数 = min(CPU 核数, 查询数)——使用 asyncio.Semaphore 控制
5. **分批调度**：将大批量查询分批次执行——每批 50 个——批间间隔 500ms——避免瞬时压力

**批量查询 API**：
```
POST /retrieval/batch
{
  "queries": [{"text": "查询1", "top_k": 10}, {"text": "查询2", "top_k": 5}, ...],
  "max_concurrency": 10,
  "timeout_ms": 30000
}
```

**性能提升**：100 个查询——顺序执行 ~20s——批量优化后并行执行 ~2-3s——去重后可能进一步减少到 1.5s。

### 2.3 检索跨集合搜索

#### 背景

用户查询可能需要在多个知识库集合中搜索——"Python 部署"可能涉及技术文档（knowledge_files）、Bug 记录（bugs）、会话记录（sessions）等多个集合。当前每次只能搜索一个集合——跨集合搜索需要多次请求。

#### 解决方案

**跨集合搜索引擎（CrossCollectionSearcher）**：并行检索多个 MongoDB 集合——统一排序——结果合并标注来源。

**跨集合检索流程**：
1. 查询分发：同一查询并行发送到所有指定集合的检索管道
2. 各自排序：每个集合独立进行检索+排序——返回 Top-K 结果
3. 分数归一化：不同集合的检索分数不可直接比较——使用 Min-Max 归一化或 Rank 归一化
4. 全局合并：归一化后合并——按统一分数排序——或按集合分区分组展示
5. 来源标注：每个结果标注 `source_collection`——前端可按来源分组/过滤

**集合权重**：不同集合的重要性不同——可配置集合权重——在合并排序时加权。

**跨集合去重**：相同文档可能存在于多个集合中——使用文档签名（title+content hash）去重——保留分数更高的那条。

**MongoDB 视角优化**：跨集合搜索使用 MongoDB 的并行查询（多集合并发——而非单集合串行）——总延迟 = max(各集合延迟)——非 sum。

## 第三部分：对话上下文检索

### 3.1 检索对话历史利用

#### 背景

在多轮对话场景中——用户的当前查询往往省略了之前轮次中已经提到过的主体。例如：
- 用户："RAG 检索的流程是怎样的？"
- AI："RAG 检索分为检索和生成两个阶段..."
- 用户："它的性能瓶颈在哪？"
- 系统需要理解"它"指代"RAG 检索"——这需要利用对话历史。

#### 解决方案

**对话历史感知检索（ConversationAwareRetriever）**：从对话历史中提取上下文——补全当前查询——生成上下文感知的完整查询。

**上下文提取策略**：
1. **指代消解**：检测查询中的代词（它/这个/那个/这）——在对话历史中查找最近提到的实体——替换代词
2. **话题延续**：检测当前查询是否为前一话题的延续（无新实体、无话题切换词）——维持同一检索上下文
3. **话题切换检测**：检测"另外"、"对了"、"换个话题"等切换词——话题切换后清空上下文——全新查询

**上下文窗口**：保留最近 5 轮对话历史——每次新对话触发时重置上下文。

**查询补全方法**：
- **简单拼接**（默认）：`完整查询 = 前一轮用户查询 + " " + 当前查询`
- **LLM 补全**（高级）：让 LLM 基于对话历史生成独立完整的查询——消除指代和省略
- **混合**：优先使用简单拼接——置信度低时使用 LLM 补全

**上下文权重衰减**：距离当前查询越远的对话轮次——其上下文权重越低——使用指数衰减 weight = exp(-λ × round_distance)——λ=0.5。

### 3.2 检索会话上下文感知

#### 背景

用户在同一个会话中的多次查询通常具有主题连贯性。如果前面在搜索 "Kubernetes 部署"——后面问 "Pod 网络策略"——系统应该理解用户仍在 Kubernetes 的上下文中——检索结果应偏向 Kubernetes 领域而非通用网络文档。

#### 解决方案

**会话上下文感知检索（SessionContextAwareRetriever）**：维护会话级别的上下文向量——在检索排序中注入会话上下文信号。

**会话上下文向量（Session Vector）**：
- 初始：首次查询的 embedding
- 更新：每次新查询后——会话向量 = 0.7 × 旧会话向量 + 0.3 × 新查询 embedding（指数移动平均）
- 作用：代表当前会话的"主题重心"

**上下文感知排序**：
- 每个候选文档的最终分数 = 基础检索分数 × 0.8 + 会话上下文匹配分数 × 0.2
- 会话上下文匹配分数 = cosine_sim(文档 embedding, 会话向量)
- 结果：与当前会话主题一致的文档获得轻微 boost

**会话上下文可视化**：
- 前端展示当前会话的主题标签（从会话向量推理）
- 用户可以看到会话的主题演变——确认系统理解正确

**上下文重置条件**：
- 用户明确切换话题——检测到显式切换词
- 新查询与当前会话向量的余弦相似度 < 0.3（话题偏离超过阈值）
- 会话超过 30 分钟无新查询（会话超时）
- 用户手动重置

### 3.3 检索知识点图谱

#### 背景

知识库中文档之间存在隐式的知识点关联——知识点 A（"RAG 检索"）引用了知识点 B（"向量检索"）——知识点 B 使用了知识点 C（"HNSW 索引"）。用户查询一个知识点时——展示关联知识点可以辅助知识发现和导航。

#### 解决方案

**知识点图谱（Knowledge Point Graph）**：从文档中提取知识点实体及其关联关系——构建知识点关系图——在检索结果中展示关联知识点。

**知识点提取**：
- 从文档标题、章节标题、关键词、实体识别中提取知识点
- 每个知识点 = 一个知识图谱节点——含名称、类型（概念/技术/工具）、来源文档
- 知识点间的关系 = 引用/包含/先修/相关——通过文档中的超链接和语义分析识别

**知识点检索增强**：
- 查询匹配到知识点节点 → 返回该知识点关联的文档——以及关联知识点
- 知识卡片中展示关联知识点——用户点击可继续探索

**关联知识点推荐**：
- 1-hop 邻居：直接关联的知识点——关系明确的
- 协同过滤推荐：与当前知识点相关的其他知识点（类比"看了A的人也看了B"）
- 学习路径推荐：前驱知识点（先修）→ 当前知识点 → 后继知识点（进阶）

**知识点图谱更新**：
- 新文档加入时——自动提取新知识点——在图中建立关联
- 定期重建图谱——迭代优化关系

## 第四部分：用户反馈与行为分析

### 4.1 检索反馈学习

#### 背景

用户对检索结果的满意度可以通过隐式反馈推断——点击、停留时间、复制、收藏、追问——以及显式反馈——点赞/点踩、评分。这些反馈信号是提升检索质量的最直接数据——但当前未被系统化利用。

#### 解决方案

**反馈学习闭环**：采集多维度反馈信号 → 构建训练样本 → 定期重训练模型 → 评估效果 → 推送更新。

**反馈信号采集**：
| 信号类型 | 信号 | 正/负 | 权重 | 采集方式 |
|---------|------|------|------|---------|
| 隐式 | 点击 | 正 | 1.0 | 前端埋点 |
| 隐式 | 停留 > 30s | 正 | 1.5 | 前端埋点 |
| 隐式 | 复制文本 | 正 | 2.0 | 前端埋点 |
| 隐式 | 收藏文档 | 正 | 3.0 | API 记录 |
| 隐式 | 未点击 (排名高但未点) | 负 | -0.5 | 前端埋点 |
| 隐式 | 快速离开 < 5s | 负 | -1.0 | 前端埋点 |
| 隐式 | 追问/修改查询 | 负 | -0.3 | 查询日志分析 |
| 显式 | 点赞 | 正 | 5.0 | 前端按钮 |
| 显式 | 点踩 | 负 | -5.0 | 前端按钮 |

**训练样本生成**：每个查询-文档对——根据反馈信号计算综合标签（加权和 > 0→正样本——< 0→负样本）——样本权重基于反馈信号数量（多信号→高置信度→高权重）。

**反馈驱动的模型更新**：
- 日更新：在线学习——基于当天反馈增量更新排序特征权重
- 周更新：小批量重训练——合并人工标注+自动反馈样本
- 月更新：全量重训练——使用所有历史反馈数据

**反馈质量监控**：追踪反馈信号分布（正/负比例）——检测反馈噪音（单个用户大量负反馈可能是主观偏好问题而非系统问题）——过滤异常反馈。

### 4.2 检索用户行为分析

#### 背景

用户的搜索行为模式揭示了信息需求和系统质量——什么时间搜索多（系统负载预测）——什么主题搜索多（知识库建设方向）——什么查询改写好（查询改写优化）——但当前这些行为数据未被分析利用。

#### 解决方案

**用户行为分析系统（UserBehaviorAnalyzer）**：搜索行为漏斗分析——Session 行为序列分析——用户搜索画像——行为驱动的优化建议。

**搜索行为漏斗**：
```
输入查询 → 浏览结果 → 点击文档 → 阅读文档 → 满意(收藏/复制) / 不满意(修改查询/关闭)
```
各阶段转化率追踪——漏斗瓶颈定位——数据驱动的 UX 优化。

**Session 行为序列分析**：
- 平均 Session 查询次数——首次查询成功率——重复查询率
- 查询改写模式："A" → "A 的 B"（加限定词——前次不够精确）vs "A" → "C"（完全改变话题）
- 分析最常见的改写路径——优化查询建议和自动补全

**用户搜索画像**：
- 搜索主题偏好——活跃时段——平均 Session 深度——搜索熟练度
- 用于个性化排序——上下文感知建议
- 隐私保护：画像与 session_id 关联——不绑定用户真实身份

**行为驱动的优化建议**：
- 高频改写路径 → 优化查询建议——让用户无需改写就获得想要的结果
- 高跳出率查询 → 零结果/低质量分析——触发知识补充
- 用户搜索熟练度 → 新手看到更多引导（模板、建议）——高级用户看到更精简的界面

## 第五部分：索引管理体系

### 5.1 检索索引压缩

#### 背景

知识库持续增长——10000 文档的向量索引大小为 30MB——100000 文档时增长到 300MB+——加上 BM25 倒排索引——总索引大小可能超过 1GB。在内存受限环境——索引压缩是必备能力。

#### 解决方案

**索引压缩策略**：

**向量索引压缩**：
- **标量量化（SQ）**：Float32→Int8——精度损失 < 1%——内存减少 75%
- **乘积量化（PQ）**：768 维向量切分为 M 个子向量——每子向量独立量化——内存减少 90%+
- **PCA 降维**：768 维 → 256 维——保留 95% 方差——内存减少 67%
- **组合方案**：PCA（768→256）+ SQ（Float32→Int8）= 内存减少 92%+（30MB→2.4MB）

**BM25 索引压缩**：
- 停用词过滤：移除高频低信息量词——减少 term-doc 对数量
- Stemming：词干化——将不同形态归并为同一 term——减少 term 数量
- Delta 编码：位置信息使用 Delta 编码——相邻位置差值用更少字节存储
- 压缩倒排列表：使用 Variable Byte Encoding 或 PForDelta——典型压缩率 4-10x

**压缩效果评估**：
- 检索精度损失：NDCG@5 下降 < 2%
- 检索速度影响：解压缩开销 < 5ms——可忽略
- 离线压缩：不阻塞在线检索——异步执行

**自适应压缩**：根据可用内存动态选择压缩级别——内存充足时使用轻量压缩（SQ）——内存紧张时使用强力压缩（PQ+PCA+Delta）。

### 5.2 检索索引健康监控

#### 背景

索引的健康状况直接影响检索质量和性能——碎片化索引导致查询慢——孤立文档（被索引但源文档已删除）导致召回异常——索引大小异常增长可能预示内存溢出。

#### 解决方案

**索引健康监控系统（IndexHealthMonitor）**：定期检查索引的 5 大健康指标——异常告警——自动修复建议。

**5 大健康指标**：
1. **索引完整性**：知识库文档数 = 索引文档数——差异 > 5% 告警
2. **孤立文档检测**：索引中存在但知识库中已删除的文档——定期清理——比例 > 2% 自动清理
3. **索引碎片率**：倒排索引的空间碎片——碎片率 > 30% 建议重建索引
4. **索引大小趋势**：索引大小的日增长率——超过预期 2 倍告警（可能遗漏停用词大文档）
5. **查询延迟分布**：随机采样 100 个查询——P95 延迟趋势——周末比上周五增长 > 20% 告警

**健康检查频率**：
- 完整性检查：每小时
- 孤立文档检测：每天
- 碎片率检查：每周
- 索引大小趋势：每天
- 查询延迟分布：每 5 分钟

**自动修复**：
- 孤立文档 > 2%：自动清理——保留日志
- 碎片率 > 50%：自动触发索引重建（凌晨低峰期）
- 完整性差距 > 10%：触发增量索引——补缺失文档

**健康仪表盘**：实时展示 5 大指标——绿色/黄色/红色状态指示——最近 30 天趋势图。

### 5.3 检索索引备份恢复

#### 背景

索引是耗时构建的资产——索引损坏或 MongoDB 数据丢失时——全量重建索引可能需要数小时——期间检索不可用。需要定期备份索引并能够快速恢复。

#### 解决方案

**索引备份恢复策略**：

**备份内容**：
- BM25 倒排索引（JSON/二进制格式）
- 向量索引（ANN 索引结构——如 HNSW 图）
- 索引元数据（文档映射、统计信息、时间戳）
- 索引配置（字段权重、同义词词典版本、停用词版本）

**备份策略**：
- **全量备份**：每周一次——完整索引快照——保留最近 4 周
- **增量备份**：每天一次——仅备份新增/修改的文档索引——依赖上一次全量备份
- **备份存储**：本地文件系统 + 远程对象存储（OSS/文件服务器）——双重保障

**恢复流程**：
1. 加载最近全量备份（恢复大部分索引）
2. 依次加载增量备份（恢复全量备份后的变更）
3. 验证索引完整性（文档数一致）
4. 切换在线索引为新恢复的索引
5. 恢复期间使用备用索引或降级模式

**恢复时间目标（RTO）**：
- 小索引（< 10K 文档）：< 5 分钟
- 中索引（10K-100K 文档）：< 30 分钟
- 大索引（> 100K 文档）：< 2 小时

**备份验证**：每次备份后自动验证——随机采样 100 个文档在备份索引中检索——对比线上索引结果——差异应 < 1%。

---

### 5.4 检索索引迁移

#### 背景

索引可能需要迁移：MongoDB 实例迁移（自建→Atlas）——存储升级（HDD→SSD）——架构调整（单集合→分片集合）。迁移过程中检索不能中断——数据不能丢失。

#### 解决方案

**零停机索引迁移方案**：

**双写模式**：
1. 新增文档同时写入旧索引和新索引
2. 后台批量迁移历史索引数据
3. 迁移完成后——检索切换为新索引——旧索引保留 7 天作为回退
4. 确认新索引稳定后——删除旧索引

**迁移验证**：
- 一致性校验：随机采样 1000 个文档——两个索引检索结果对比——Top-10 重叠率 > 99%
- 性能校验：随机采样 100 个查询——新索引 P95 延迟不高于旧索引的 120%
- 完整性校验：新索引文档数 = 旧索引文档数

**迁移回滚**：
- 步骤 3 后 7 天内发现问题→切换回旧索引（秒级回滚）
- 步骤 4 后需要恢复→从备份恢复旧索引（小时级恢复）

---

### 5.5 检索索引热备份

#### 背景

常规备份需要索引处于一致状态——但索引在持续更新——备份过程中新增的文档可能未被包含——造成备份不完整。热备份（Hot Backup）在不停止索引更新的情况下进行一致性备份。

#### 解决方案

**MVCC 快照热备份**：利用 MongoDB 的 WiredTiger 存储引擎的 MVCC 特性——在事务中创建一致性快照——基于快照进行备份——期间索引正常更新。

**热备份流程**：
1. 开启 MongoDB 事务——获取当前时间戳 T
2. 在事务中——读取 T 时刻所有索引文档的快照
3. 导出快照数据到备份文件
4. 提交事务（实际是只读事务——无需回滚）
5. 记录备份完成时间戳——用于增量备份的基准

**一致性保证**：
- 备份包含 T 时刻之前所有已提交的索引更新
- 不包含 T 时刻之后开始的索引更新
- 备份是一个确定的一致性快照——不是模糊的不一致中间态

**备份频率**：每天一次热备份——凌晨 3 点低峰期执行——与增量备份配合——实现任意时间点恢复（PITR）。

---

### 5.6 检索词典热更新

#### 背景

同义词词典、停用词词典、拼写词典等在检索过程中被频繁读取——词典更新需要在不重启服务、不影响进行中请求的情况下生效。

#### 解决方案

**词典热更新机制（HotReloadDictionary）**：内存字典 + 版本号 + 原子替换。

**热更新流程**：
1. 从数据源加载新版本词典（MongoDB/文件）
2. 在内存中构建新的词典数据结构（如新 SynonymDict 对象）
3. 原子替换引用：`self._active_dict = new_dict`（Python 引用赋值是原子的）
4. 旧词典的引用会在所有进行中的请求完成后被 GC 回收
5. 词典版本号递增——缓存失效检测

**版本号管理**：
- 每个词典有 version 字段（语义版本 或 递增整数）
- 同义词扩展缓存 key 包含 synonym_version——版本变化时缓存自动失效
- API 返回当前词典版本——运维可确认更新已生效

**更新触发**：
- MongoDB Change Stream：监听词典集合的变更——自动触发热更新
- 文件监听（watchdog）：监听词典文件的修改——自动触发热更新
- API 手动触发：运维通过管理 API 强制刷新

**更新验证**：热更新后——随机测试 10 个查询——验证新词典生效（如新增同义词出现或删除的停用词不再过滤）。

## 第七部分：统一设计原则

1. **精度与速度平衡**：语义哈希、蒸馏、压缩等技术的本质是在精度和速度之间寻找最优平衡点
2. **离线训练 + 在线推理**：对比学习、蒸馏、对抗训练等重计算在离线完成——在线仅快速推理
3. **增量优于全量**：在线学习、反馈学习、增量索引——最小化重计算——持续适应变化
4. **零停机运维**：热备份、热更新、迁移双写——所有索引操作不影响在线检索
5. **多模态统一**：文本和图在 CLIP 联合空间中统一——一个检索管道同时服务两种模态
6. **上下文持续**：对话历史、会话上下文、知识图谱——从多个维度利用上下文增强检索
7. **可观测驱动**：健康监控、行为分析、反馈采集——形成数据驱动的持续优化闭环

## 经验教训

1. **根本原因**：开发过程中对边界情况和异常路径的考虑不足是此类问题的共同根因
2. **设计阶段**：在接口设计和模块实现时，应主动考虑异常输入、空值、超时等边界场景
3. **代码审查**：审查时应检查是否存在类似的反模式（如未捕获异常、无超时控制、缺少参数校验等）
4. **测试覆盖**：异常路径的测试覆盖率应与正常路径同等重视
5. **团队分享**：此类问题应在团队周会或技术分享中讨论，形成团队共识
