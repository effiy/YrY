## 第一部分：同义词扩展体系

### 11.1 检索同义词扩展

#### 背景

用户查询中的用词往往与知识库中的文档用词不一致——"API接口" vs "应用程序接口"、"数据库连接" vs "DB连接"——导致关键词检索无法匹配——召回率低。核心问题包括：

1. **同义词不匹配**：知识库使用"Ollama 模型服务"——用户查询"AI 推理引擎"——词汇完全不同
2. **缩写与全称不对称**：文档使用"RAG"——用户查询"检索增强生成"——关键词检索漏掉关键文档
3. **中英文混用**：知识库使用"embedding 向量"——用户查询"嵌入向量"——跨语言同义词未建立关联
4. **领域术语变体**：同一概念在团队中有多种称呼（"知识库"/"文档库"/"YiKnowledge"）

**核心矛盾**：检索系统的准确率取决于查询词与索引词的一致性——但用户用词多变且不可预测。

#### 解决方案

**同义词扩展引擎（SynonymEngine）**：在查询进入检索管道前——对查询词进行同义词扩展——生成多个查询变体——并行检索——加权融合。

**扩展流程**：
1. 分词：将查询切分为短语和词汇两个粒度
2. 短语级别扩展：使用最长匹配算法优先匹配短语级别同义词（如"检索增强生成"→"RAG"）
3. 词级别扩展：对短语匹配后的剩余词进行词级别同义词扩展
4. 组合变体生成：不同同义词同时替换——生成组合变体
5. 权重分配：原始查询 weight=1.0——短语扩展 weight=0.7——词扩展 weight=0.7——组合扩展 weight=0.7^n
6. 去重截断：移除与原始查询相同的变体——最多保留 max_expansions=5 个变体

**设计决策**：
- **词典存储**：JSON 种子文件 + MongoDB 可选覆盖。启动时加载 JSON 种子到内存——运行时 MongoDB 增量合并
- **同义词发现**：手工种子（50-100 对核心术语）+ LLM 辅助发现（从检索日志分析）
- **扩展权重**：固定权重（原词 1.0——同义词 0.7）+ 用户可配置
- **扩展粒度**：混合——短语优先。短语级别先匹配——避免"检索增强生成"被拆为三个单词分别扩展

**初始种子数据**（约 50 对）：
- 短语级别：检索增强生成↔RAG、大语言模型↔LLM、知识库↔YiKnowledge、向量检索↔dense retrieval
- 词级别：模型↔model、推理↔inference、检索↔search/retrieval、配置↔config、接口↔API

#### 性能指标

| 指标 | 目标值 |
|------|--------|
| 同义词词典加载 | < 10ms |
| 单次查询扩展 | < 5ms |
| 扩展后检索延迟增加 | < 30% |
| 最大扩展变体数 | 5 |
| 词典大小上限 | 10000 对 |

### 11.2 检索同义词词典管理

#### 背景

同义词扩展的基础是同义词词典的维护。当前同义词词典是硬编码的静态 JSON 文件——缺乏管理界面和动态更新能力。痛点包括：同义词词典无法跨领域区分、新增/修改同义词需要修改代码并重新部署、同义词变更无版本记录。

#### 解决方案

**同义词词典管理系统**：基于 MongoDB 的多领域同义词词典管理——提供 CRUD 操作、版本管理和共现分析建议。

**数据模型**：
- `SynonymDictionary`：词典定义——包含名称、领域(domain)、语言、同义词条目列表、语义版本号、版本历史
- `SynonymEntry`：单条同义词——术语(term)、同义词列表(synonyms)、状态(active/deprecated/pending_review)
- `SynonymSuggestion`：同义词建议——候选词、置信度、证据

**核心功能**：
1. **多领域隔离**：不同领域（tech/finance/medical）的同义词词典完全隔离——避免"apple"在不同领域混淆
2. **语义版本管理**：major.minor.patch——major=不兼容变更（删除）——minor=新增——patch=修正
3. **版本回滚**：记录每次变更历史——支持回滚到任意历史版本
4. **导入导出**：支持 JSON 和 CSV 格式的词典导入导出——CSV 便于人工编辑
5. **共现分析建议**：基于 PMI（点互信息）计算在文档集中共现频率高的词对——生成候选同义词建议——LLM 验证过滤噪音

**与同义词扩展的关系**：此模块为同义词扩展提供管理界面——产品运营人员可通过 API 动态管理同义词——无需重新部署。

#### 实施要点

- MongoDB 集合：`synonym_dictionaries`
- 内存缓存 + 写入时刷新——写入操作同步更新内存字典和 MongoDB
- 领域隔离：同义词查询时使用 `domain` 字段过滤——不同领域不交叉
- 每领域上限 1000 条同义词——防止膨胀

### 11.3 检索同义词图构建

#### 背景

扁平同义词词典存在局限：同义词关系的传递性丢失（A与B同义——B与C同义——但A与C的关系需要显式定义）、同义词强度无法区分、术语社区无法自动发现。

#### 解决方案

**同义词图（SynonymGraph）**：将同义词对构建为带权图——节点为术语、边为同义词关系、权重为关系强度——使用 NetworkX 实现图算法。

**数据结构**：
- **节点（GraphNode）**：术语 ID、术语类型(word/phrase)、语言、社区 ID、节点度
- **边（GraphEdge）**：源节点、目标节点、权重(0.0-1.0)、关系类型(synonym/related/abbreviation/translation)、共现次数
- **图持久化**：JSON 邻接表格式——人类可读写——方便调试和手动编辑

**核心算法**：
1. **图构建**：从种子同义词词典构建初始图——每个同义词对创建边——权重默认 0.9
2. **权重更新**：基于共现数据使用贝叶斯平均更新权重——融合先验(种子权重)和观测(共现频率)
3. **社区检测**：Louvain 算法检测术语社区——模块度量化社区质量
4. **图查询扩展（BFS）**：从查询词节点出发——BFS 遍历最多 2 跳——路径权重 = ∏(边权重) × 衰减因子^(深度-1)——多路径取最大权重
5. **社区感知扩展**：同社区术语获得额外 30% 权重提升——社区内优先——社区外补充

**BFS 扩展参数**：
- 最大深度：2（覆盖直接同义词和同义词的同义词）
- 最小权重：0.2（低于此阈值的扩展被丢弃）
- 衰减因子：0.7

**设计决策**：
- **图存储**：NetworkX 内存图 + JSON 持久化——算法丰富+格式简单
- **边权重**：手动种子 + 共现增强——先验可信度高+自动学习
- **社区检测**：Louvain——快速（<100ms）+ 高质量
- **持久化**：JSON 邻接表——可读+兼容现有格式

## 第二部分：停用词管理体系

### 12.1 检索停用词管理

#### 背景

停用词（"的"/"了"/"是"/the/a/an）在检索中需要被过滤——但不同知识库需要不同的停用词策略。当前硬编码的停用词列表无法按索引/领域定制——无法动态调整——缺乏影响分析。

#### 解决方案

**多语言/多索引可配置停用词管理系统**：基于 MongoDB + 本地文件缓存的停用词管理——支持双阶段过滤。

**核心设计**：
1. **存储方案**：MongoDB 管理 + 本地文件缓存保证离线可用。服务启动时从 MongoDB 加载——写入本地缓存文件
2. **双阶段过滤**：索引阶段过滤（控制索引大小）+ 检索阶段二次过滤（处理新增停用词——无需重建索引）
3. **领域隔离**：不同领域（tech/finance）的停用词集独立管理——查询时优先使用领域特定停用词——回退到通用停用词
4. **多语言支持**：中文(zh)、英文(en)、日文(ja)、韩文(ko)、自定义(custom)

**停用词建议算法**：TF-IDF 低分词 + 词频阈值。TF-IDF 天然识别高频低信息量词——计算成本低——语言无关。

**应用阶段选择**：
- `index`：仅在索引阶段过滤——最安全——性能最优
- `query`：仅在检索阶段过滤——保留索引完整性
- `both`：双阶段过滤——平衡索引大小和检索精度

### 12.2 检索停词自适应

#### 背景

停用词来源仍依赖人工定义——存在人工维护滞后、领域差异未利用、语言特性未自适应等问题。不同领域、不同语言的高频词模式完全不同——人工无法为每个索引定制停用词。

#### 解决方案

**自适应停用词发现系统**：基于语料库自动分析词频分布——计算多维特征评分——给出停用词置信度评分——辅助运营决策。

**多维特征融合评分模型**（总分 100）：
- 词频 rank 特征（0-30分）：基于查询集中的词频排名——高频词的停用词概率更高——使用 log 映射防止少数极高频词独占分数
- 文档频率占比特征（0-25分）：出现在越多文档中的词越可能是停用词（DF > 80% 高分）
- 词性特征（0-20分）：语言特定——中文助词/介词/连词天然是停用词——英文冠词/限定词/介词
- 文本覆盖率特征（0-15分）：该词占总 token 的比例——覆盖率极高=停用词可能性高
- 信息熵特征（0-10分）：文档分布的信息熵——熵值高=分布均匀=停用词特征

**三级推荐机制**：
- 评分 >= 80：高置信度——自动标记为停用词——可直接应用
- 评分 60-79：中置信度——建议人工审核——显示详细指标辅助判断
- 评分 < 60：不推荐——此词在领域中有区分价值

**小样本惩罚**：文档数 < 100 时——所有评分 × 0.7——标注警告——降低自动应用风险。

**多触发源策略**：
- 定时分析：每日凌晨对活跃索引执行分析
- 阈值触发：文档增量超过 20% 或新增超过 100 篇时自动触发——冷却期 6 小时
- 手动触发：运营人员在管理后台随时触发

**与静态停用词管理的关系**：自适应分析生成的推荐——通过 YA-09-253 的 API 写入停用词管理——形成从分析到应用的闭环。

## 第三部分：查询纠错体系

### 13.1 检索拼写纠正

#### 背景

用户输入查询时经常出现拼写错误——"配置"写为"配制"、"embedding"写为"embeddingg"——导致关键词检索完全无法匹配——召回率为零。

中文字形混淆、英文拼写错误、拼音输入错误、术语拼写不标准——各类错误缺乏统一的纠正机制。

#### 解决方案

**拼写感知检索（SymSpell + 领域词典）**：查询进入检索前——SymSpell 拼写检查引擎进行逐词纠错——中文使用拼音相似+编辑距离联合评分——纠正查询和原查询并行检索——返回纠错建议（Did-You-Mean）。

**中文纠错策略**：拼音相似 + 编辑距离联合评分。中文拼写错误 80%+ 来自拼音输入——同音字选错。用 pypinyin 获取词/字的拼音——拼音相同的候选加分。字符级编辑距离处理增删改字场景。拼音相似权重 0.6 + 编辑距离权重 0.4 联合排序候选。

**英文纠错策略**：SymSpell 对称删除算法——在词典构建时预计算所有删除变体——查询时 O(log n) 查找——< 5ms 完成。

**纠错决策**：
- 自动纠正+建议——混合检索+提示
- 原查询权重 0.7——纠正查询权重 1.0——RRF 融合
- 返回 `did_you_mean` 字段——前端显示"您是不是要搜索: xxx?"
- 纠正置信度 < 0.7——仅显示建议不自动纠正

**领域词典保护**：从 YiKnowledge 提取领域术语——注册为正确词——不可被纠正——防止"Ollama"→"Ollama"→"Olama"之类的错误纠正

**模糊搜索**：查询端模糊——先修正再检索。fuzziness 参数控制激进程度——1=编辑距离 1——2=编辑距离 ≤2。

#### 设计决策

- **纠错实现**：本地 SymSpell + 领域词典。LLM 不参与在线纠错（延迟太高）——用于离线生成领域词典候选条目
- **模糊搜索策略**：查询端模糊——先修正再检索。索引不膨胀——灵活可控
- **建议方式**：自动纠正+建议。兼顾检索质量和用户体验

### 13.2 检索短语匹配提升

#### 背景

BM25 关键词检索将查询拆分为独立词——每个词独立评分再求和——忽略了词的顺序和相邻关系。"机器学习模型部署"和"部署机器学习模型"在 BM25 中得分完全相同。用户查询中的完整短语（如"检索增强生成"）在 BM25 中被拆为三个独立词——丢失了短语作为一个整体的语义权重。

#### 解决方案

**短语感知检索增强（PhraseSearchEngine）**：在 BM25 之上叠加短语级评分——精确短语匹配获得额外加分——词间距近的匹配获得 proximity bonus——保持 BM25 速度的同时提升检索精度。

**核心组件**：
1. **查询短语提取器**：jieba 词性标注提取名词短语+动词短语——N-gram 回退处理英文/混合文本
2. **短语索引**：关键短语索引存储 phrase→doc→frequency→positions——仅存储 2-4 词有意义短语
3. **位置倒排索引**：word→doc→positions 映射——用于邻近度计算
4. **短语匹配评分**：Phrase Bonus = base_bonus × phrase_length × avg_idf——上限 phrase_max_bonus=2.0
5. **邻近度评分**：最小跨度+密度——Proximity Score = 查询词数 / 最小跨度

**短语加分策略**：长度加权 + IDF 加权。长短语（3-4 词）的精确匹配比短语（2 词）更有价值——加分与长度成正比。IDF 调制——罕见短语的精确匹配加分更高。

**邻近度算法**：多指针滑动窗口找到包含所有查询词的最短区间——O(k*n) 复杂度（k 为查询词数）——远远快于动态规划的 O(n^2)。

**集成方式**：检索后重排序。将 phrase scoring 作为 BM25 结果的后处理步骤——对 BM25 返回的 top-K 文档计算短语加分——与现有系统解耦——易于开关和调整。

### 13.3 检索正则表达式支持

#### 背景

语义搜索擅长"意思相近"的检索——但"格式精确"的检索同样重要。用户无法通过模式匹配精确查找符合特定格式的内容——如查找所有包含特定格式标识符的文档（`YA-09-\d{3}`）——或在日志中执行结构化模式检索。

#### 解决方案

**正则检索管道（RegexScanner）**：集成 Python `re` 引擎——提供正则验证与 ReDoS 安全沙箱——正则+语义混合评分——匹配高亮与上下文提取——模式预编译 LRU 缓存。

**ReDoS 安全沙箱**：
- 静态分析：检测嵌套量词（(a+)+、交替+星号组合等危险模式）
- 语法检查：正则编译验证——语法错误返回友好提示
- 复杂度评分：0-100 分——基于嵌套量词深度、重复次数、捕获组数量
- 限制：最大正则长度 500 字符——最大重复次数 100——最大嵌套量词深度 2
- 执行超时：ThreadPoolExecutor 并发隔离——per_doc_timeout 500ms——总超时 5s

**混合评分**：加权求和——regex_weight（默认 0.4）和 semantic_weight（默认 0.6）可配置。正则匹配产生连续分数（匹配次数/文档长度——归一化到 0-1）——与语义相似度加权求和。当 regex_weight=1.0 时退化为纯正则检索。

**匹配高亮**：服务端返回 `match_spans: [{start, end, context_before, context_after}]`——前端自行渲染高亮。传输量最小——保持渲染灵活性。

**LRU 编译缓存**：`@lru_cache(maxsize=256)` 缓存编译后的 `re.Pattern` 对象——热点正则可达到 90%+ 缓存命中率。

## 第四部分：结果增强体系

### 14.1 检索高亮片段

#### 背景

搜索结果的"可浏览性"严重依赖高亮片段的质量——用户快速判断结果相关性主要依靠阅读高亮片段。当前实现仅提供基础的关键词标记——仅支持单一字段高亮——缺少上下文窗口——片段没有合并去重——高亮标签不可自定义。

#### 解决方案

**高级高亮片段管道**：多字段高亮 + 上下文窗口 + 片段合并 + MMR 多样性选择 + 自定义高亮标签。

**处理流程**：
1. **多字段匹配收集**：在 title、content、tags、summary 等多个字段中收集匹配位置——每个字段有独立权重
2. **上下文窗口截取**：每 span 前后取 context_size（默认 50）字符——词边界感知优化
3. **边界优化**：CJK 字符间使用字符级边界——英文跳转到空格或标点——不在单词中间截断
4. **片段合并**：两个片段距离 < merge_threshold（默认 50 字符）则合并为一个
5. **MMR 多样性选择**：lambda=0.7——平衡相关性（70%）和多样性（30%）——返回前 K=3 个最大边际相关性片段
6. **高亮标签注入**：用可配置的标签包裹匹配词——默认 `<mark class="search-highlight">word</mark>`

**多字段权重**：基础权重 title=3.0, content=1.0, tags=2.0, summary=1.5——结合字段长度归一化避免短字段天然占优。

### 14.2 检索摘要生成

#### 背景

RAG 检索返回文档后——用户需要快速判断文档是否与自己查询相关——而不必阅读完整文档。当前结果仅显示固定开头 100 字——通常不包含与查询相关的信息。

#### 解决方案

**查询偏置摘要（Query-Biased Summarization）**：为每个检索文档生成以用户查询视角的简短摘要——提取文档中与查询最相关的句子——重组为连贯摘要。

**摘要生成流程**：
1. **句子切分**：多级切分——句号/感叹号/问号→分号→逻辑逗号——最小句子长度 3——最大 500
2. **预筛选**：Jaccard 关键词重叠筛选——过滤明显无关的句子——减少需要精确评分的句子数（保留率约 20-40%）
3. **句子评分（混合）**：Embedding 余弦相似度（优先——权重 0.7）+ BM25 评分（权重 0.3）——降级为纯 BM25
4. **Top-N 句选取**：选取最相关句子——累计长度不超目标——最多 5 句
5. **原文顺序重组**：保持文档的自然叙述流——句子间间隙 > 50 字符时添加省略标记
6. **高亮标记生成**：分数越高——高亮越强（深黄/浅黄/更浅）

**片段长度自适应**：
```
snippet_length = clamp(median(query_length × 3, log2(doc_length) × 30), 50, 300)
```
- 短查询（5 字）：片段约 50-80 字
- 常规查询（20 字）：片段约 100-150 字
- 长查询（50 字）：片段约 200-300 字

**多文档整合摘要（可选）**：多文档句子混合——按相关性排序——去重（Jaccard > 0.85 的句子只保留一个）——选取 Top-15 句——生成综合摘要。

**核心设计决策**：使用抽取式而非 LLM 生成式——因为检索摘要的核心价值是"忠实反映文档内容"——抽取式保证每个字都来自原文——真实性 100%——不会有幻觉。

### 14.3 检索搜索预览

#### 背景

YA-09-248 和 YA-09-240 分别实现了基础高亮和检索摘要——但预览不围绕查询词——无图片结果预览——结构化数据无预览——预览未缓存。

#### 解决方案

**智能预览系统（SearchPreview）**：动态片段窗口 + 多类型预览 + 预览缓存。

**动态片段算法**：评分制滑动窗口——对文档中每个可能的位置计算窗口评分：
```
score = keyword_density × 0.4 + keyword_diversity × 0.3 + position_bonus × 0.2 + sentence_boundary × 0.1
```
选择评分最高的窗口作为片段。窗口大小 = min(200, query_len × 15)。

**多类型结果预览**：
| 结果类型 | 预览策略 |
|---------|---------|
| text/md | 动态片段——围绕关键词窗口——<mark> 高亮 |
| image | 按需生成 200×200 缩略图——PIL 缩放——返回 URL |
| table | 表头+前 3 行结构化渲染 |
| json | 格式化 JSON 前 500 字符——含顶层 key 列表 |
| code | 语言检测——语法高亮——前 10 行 |

**预览缓存**：文档级缓存 + 短 TTL（5 分钟）。文档级缓存固定存储每文档的全文 token 位置信息——片段生成基于索引快速计算——成品预览不缓存。缩略图和结构化预览是文档级的——自然适合文档级缓存。

### 14.4 检索知识卡片

#### 背景

传统搜索返回文档列表——用户需要逐篇点击阅读才能获取关键信息。知识卡片在搜索结果中直接展示结构化信息——类似于 Google 搜索的知识面板。

#### 解决方案

**知识卡片系统（KnowledgeCard）**：声明式 JSON 模板 + 检索结果 + 知识图谱 + LLM 验证——生成不同类型的结构化知识卡片。

**卡片类型**：
1. **实体摘要卡片**：搜索实体名时——展示实体定义、关键属性、关联实体
2. **定义卡片**：搜索"什么是 X"时——直接展示定义——触发关键词：什么是/是什么/定义/概念
3. **统计卡片**：搜索对比类查询时——聚合数据——表格展示
4. **关联实体卡片**：展示实体在知识图谱中的 1-hop 邻居

**触发策略**：关键词触发（快速路径）+ LLM 判断（高质量路径）。预定义触发词覆盖高频场景——延迟 < 10ms。复杂查询由 LLM 判断。

**数据来源**：检索文档（标题+摘要+关键词）+ 知识图谱（结构化关系）+ LLM 格式化（改写已有信息——不凭空创作）。

**声明式 JSON 模板**：卡片模板定义在 JSON 中——包含卡片类型名、触发条件、字段列表（字段名、数据来源、提取方式、显示标签）。新增卡片类型 = 新增一个 JSON 模板文件——无需改代码。

**缓存策略**：按实体缓存——TTL 24 小时。实体定义和基本属性属于稳定知识——不会频繁变化。统计卡片不缓存——底层数据可能随时更新。

### 14.5 检索结果分面统计

#### 背景

搜索结果返回扁平的文档列表——用户在大规模结果中面临"大海捞针"的困境——无法按分类/标签/时间/作者缩小范围——不了解结果分布——无法多维度组合过滤。

#### 解决方案

**分面搜索（Faceted Search）**：MongoDB `$facet` 聚合管道——一次查询并行执行多个子管道——每个子管道产生一个分面的统计结果。

**分面维度**：
- **分类分面**：`$group by category`——按计数降序——单选
- **标签分面**：`$unwind tags` + `$group by tag`——按计数降序——多选
- **日期直方图**：自适应粒度——时间跨度 < 30 天→按天——30 天-1 年→按周——1-5 年→按月——>5 年→按年
- **作者分面**：`$group by author`——按计数降序
- **动态分面**：自动发现 string/enum 字段且唯一值在 2-100 之间的字段

**分面值排序**：按计数降序 + 已选择值置顶。用户选择的值固定在列表顶部——方便取消选择。每分面最多返回 20 个值——超过显示"查看更多"。

**分面过滤叠加**：用户选择分面值后——前端发送 filter 参数——后端重新查询——主查询+分面查询都使用相同的 filter——分面计数实时更新反映过滤后的分布。

**分面缓存**：相同 query+filter 组合的分面统计结果缓存 30 秒（内存 LRU）——减少数据库查询。

## 第五部分：查询理解体系

### 15.1 检索查询意图分类

#### 背景

当前检索系统对所有查询采用相同的检索策略——不区分用户查询的意图类型。信息型查询需要高召回——导航型查询需要精确匹配——事务型查询需要步骤化内容——复合型查询需要分解处理。

#### 解决方案

**意图感知检索（IntentClassifier + IntentAwareRetriever）**：五分类体系 + 意图特定检索策略。

**五分类体系**：
| 意图 | 检索策略 | top_k | 向量权重 | BM25权重 | 特殊处理 |
|------|---------|-------|---------|---------|---------|
| 信息型 | 高召回——概念覆盖 | 20 | 0.7 | 0.3 | 结果按主题聚类 |
| 导航型 | 精确匹配——标题优先 | 5 | 0.2 | 0.8 | 标题相似度加权 |
| 事务型 | 步骤化内容优先 | 10 | 0.5 | 0.5 | 含 code block 文档加权 |
| 复合型 | 子查询独立检索 | 10×N | 0.5 | 0.5 | 合并去重——子查询标记 |
| 模糊型 | 不检索——返回澄清问题 | 0 | — | — | 直接返回澄清提示 |

**分类实现**：规则匹配（关键词+句式——延迟 < 1ms）+ LLM 分类兜底（小模型 0.5B——延迟 50-100ms）。LRU 缓存（500 条）——相同查询复用分类结果——减少 LLM 调用。

**规则优先级**：
- 信息型触发词：什么是/什么叫/解释/定义/区别/对比/vs
- 导航型触发词：在哪/哪里有/查找/定位
- 事务型触发词：如何/怎么/配置/报错/错误/解决
- 模糊型触发词：这个/那个/它（代词语境缺失）
- 复合型检测：多问号或多"和"连接

**子意图分解**（复合型查询）：标点分割预筛（按问号/分号）→ LLM 验证每段是否为独立问题并改写为完整查询。

---

### 15.2 检索意图重写

#### 背景

用户查询中的模糊表达需要被转换为精确检索词。"怎么优化数据库"→"数据库性能调优/索引优化策略"。"跑得慢怎么办"→"性能瓶颈分析与优化/慢查询诊断"。

#### 解决方案

**三层混合重写引擎（HybridQueryRewriter）**：
- **L1 规则层**：同义词映射+常见口语→专业短语替换。延迟 < 5ms——覆盖 40% 查询
- **L2 缓存层**：历史 LLM 重写记录匹配——embedding 相似度 > 0.9 复用。延迟 < 10ms——覆盖 30% 查询
- **L3 LLM 层**：深度意图重写+约束补充。延迟 500ms-2s——覆盖 30% 查询

**隐式约束提取**：从会话上下文（最近 3 轮对话）提取技术栈/版本等约束——从知识库元数据提取领域/语言约束。

**多义词消歧**：基于会话上下文和知识库元数据推断正确的词义。

**A/B 测试**：影子流量模式——每次查询同时执行重写检索和原始检索——但仅向用户返回原始结果——后台记录两个版本的检索效果指标——积累足够数据后转为在线 A/B 灰度。

**降级保护**：置信度 < 0.7 时使用原始查询——保留原意——不做错误重写。

---

### 15.3 检索查询建议

#### 背景

用户不确定用什么关键词搜索——输入过程中无法获得实时建议——拼写错误无法纠正——无法快速重复之前的搜索。

#### 解决方案

**查询建议系统（SuggestionService）**：内存双索引 Trie 树 + MongoDB 文档标题前缀匹配 + 拼写纠正建议——debounce 150ms 触发。

**双索引 Trie**：
- `char_trie`（汉字索引）：直接按输入的汉字前缀匹配
- `pinyin_trie`（拼音索引）：对每个词生成全拼后按拼音前缀匹配

前端判断输入是否为纯 ASCII（可能为拼音）——若为 ASCII 则查询拼音索引——否则查询汉字索引。

**建议来源优先级**：
1. 历史查询前缀匹配（Trie 树——极快）
2. 文档标题前缀匹配（MongoDB `$regex` 查询）
3. 拼写纠正建议（编辑距离 < 2）
4. 热门查询（短前缀 < 2 字符时——返回 Top 10）

**排序策略**：流行度（查询频率）×0.6 + 新鲜度（最近查询时间衰减）×0.3 + 上下文相关性×0.1。

**上下文感知**：建议词与用户当前页面/模块的匹配度作为微调信号。

---

### 15.4 检索查询模板

#### 背景

知识库检索中最常见的用户行为模式是"重复查询模式"——不同用户、不同时间询问相同结构的问题——只是参数不同。当前系统缺乏对这些重复查询模式的抽象和复用。

#### 解决方案

**参数化查询模板系统（QueryTemplate）**：自定义 DSL + JSON Schema 参数定义——半自动模板发现——模板推荐——查询计划缓存。

**模板语法**：`{project}项目最近{days}天的Bug统计`——`{param_name}` 占位符 + JSON Schema 参数定义（类型/验证/默认值）。

**模板自动发现**：从查询日志中识别重复模式——正则替换具体参数为占位符（项目名→{project}、日期→{time_range}、数字→{count}、版本号→{version}）——统计骨架频率——高频骨架（>10 次/30天）生成模板建议——管理员审核发布。

**模板推荐**：空查询页展示热门模板 Top-10——输入时实时匹配模板名称和描述。

**查询计划缓存**：模板执行后——查询计划（子查询分解、扩展后的查询向量）被 LRU 缓存。下次使用相同模板时复用查询计划——仅重新计算参数相关部分。

---

### 15.5 检索嵌套查询

#### 背景

用户查询"Bug管理中项目A的P0和P1缺陷分别有多少？其中已关闭的占比是多少？"是天然的嵌套查询——包含多个子查询——子查询之间有依赖关系。当前 RAG 检索管道将其视为单一查询——无法分解处理。

#### 解决方案

**嵌套查询处理系统（QueryDecomposer + NestedQueryExecutor）**：查询分解 + DAG 执行计划 + 结果合成。

**查询分解**：混合方式——规则分解（检测"和"/"其中"/"对比"/"基于"等分解点）+ LLM 补充分解（语义依赖——规则无法覆盖的）。

**DAG 执行计划**：
- 构建子查询间的依赖 DAG
- Kahn 算法拓扑排序——识别执行层级
- 同一层级的无依赖子查询并行执行（asyncio.gather）
- 有依赖的子查询串行等待——中间结果结构化传递

**子查询类型**：
- `RETRIEVAL`：RAG 检索
- `DATA_QUERY`：结构化数据查询
- `FILTER`：依赖上游结果进行过滤
- `COMPUTATION`：依赖上游结果进行计算/聚合

**结果合成**：LLM 总结（默认）+ 模板化渲染（对比类查询——Markdown 表格）。

**限制**：最大子查询数 10——总超时 30s——防止过度分解和长时间等待。

---

### 15.6 检索分类器路由

#### 背景

不同类型查询（代码搜索、概念解释、操作指南、故障排查）对检索策略的要求完全不同——统一检索策略导致各种类型的查询都"不够好"。代码搜索需要关键词精确匹配——概念解释需要语义泛化——操作指南需要步骤匹配。

#### 解决方案

**分类器路由检索（QueryClassifier）**：双层分类（规则 + TF-IDF+NB）+ 分层路由决策 + 类别特定检索策略。

**5 类别体系**：
| 类别 | 规则示例 | 检索策略 | BM25权重 | 向量权重 |
|------|---------|---------|---------|---------|
| code | `import/class/def` | 代码索引 | 0.8 | 0.2 |
| concept | `什么是/定义/概念` | 知识索引 | 0.3 | 0.7 |
| howto | `如何/怎么/配置` | 知识索引 | 0.5 | 0.5 |
| troubleshoot | `error/报错/异常` | 知识索引 | 0.7 | 0.3 |
| other | 兜底 | 通用策略 | 0.5 | 0.5 |

**双层分类器**：
- L1 规则层：正则+关键词匹配——延迟 < 1ms——覆盖 50%+ 查询
- L2 ML 层：TF-IDF + 朴素贝叶斯——延迟 < 5ms——从标注的查询日志训练

**分层路由**：
- 置信度 >= 0.7：单路路由——仅该类别索引
- 置信度 0.4-0.7：双路路由——top-2 类别融合
- 置信度 < 0.4：多路路由——所有 4 个类别索引融合

**代码索引独立**：标准 tokenization 按空格和标点分词——会拆分 `fastapi.APIRouter`。代码索引使用特殊 tokenizer——保留 `.` `_` `()` 等符号——将 API 名称作为整体 token。

## 第六部分：反馈与分析体系

### 16.1 检索查询日志分析

#### 背景

查询日志是检索优化的金矿——但当前仅以原始文本形式存在于日志文件中——未被结构化、未被分析、未被利用。

#### 解决方案

**结构化查询日志系统（QueryLog + QueryAnalyzer）**：每次检索后异步写入结构化日志到 MongoDB `query_logs` 集合——提供实时分析（热门查询、失败查询、查询建议）和离线分析（查询模式挖掘、知识缺口分析）。

**数据模型字段**：
- `query_text`：原始查询文本
- `query_hash`：MD5（用于去重统计）
- `timestamp`：查询时间
- `session_id`：会话标识
- `results_count`：结果数量
- `top_score`：Top-1 检索分数
- `avg_score`：平均分数
- `query_result`：success/low_quality/zero_result/error
- `failure_reason`：失败原因
- `retrieval_time_ms`：检索耗时

**失败查询定义**：
- 0 结果：检索返回空——明确失败
- 低质量：Top-1 检索分数 < 0.3——标记为"疑似低质量"
- 综合判断：记录 `failure_reason` 字段——区分失败类型

**分析能力**：
- **热门查询**：过去 24h Top-50——MongoDB 聚合管道——按查询计数降序
- **失败查询追踪**：0 结果 + 低质量查询列表——关联到知识缺口分析
- **查询建议**：前缀匹配历史查询——按频率降序——Top 5 建议
- **知识缺口分析**：0 结果高频查询聚类——生成知识空白报告——辅助知识库建设
- **查询模式挖掘**：查询类型/时间分布/长度分布——指导检索策略优化

**存储管理**：保留上限 100K 条——超过后 FIFO 归档到 JSON lines 文件——归档保留 90 天。

### 16.2 检索零结果处理

#### 背景

当用户查询在知识库中找不到任何匹配结果时——当前系统仅返回空列表——没有提供任何替代方案或帮助信息。零结果是系统的一个关键时刻——处理得好可以引导用户找到相关信息——处理不好用户会感到挫败并放弃。

#### 解决方案

**多级查询松弛管线（ZeroResultHandler）**：L1 拼写纠正 → L2 术语扩展 → L3 回退推荐。

**零结果阈值**：最高检索分数 < 0.3（可配置）视为"有效零结果"——触发松弛流程。

**L1 拼写纠正**：
- 仅在零结果/低质量时触发纠正——不影响正常查询
- 使用知识库术语词典——已知术语不受纠正（防止"ReLU"→"Rule"误纠正）
- 纠正后重新检索——若恢复出结果——返回 + 提示"已自动纠正拼写"

**L2 术语扩展**：
- 口语→专业术语映射：预定义映射表（如"电脑变快"→"性能优化"）
- 同义词扩展——复用同义词词典
- 扩展后重新检索

**L3 回退推荐**：
- 返回 Top-3 最接近匹配（即使分数低）
- 生成查询改写建议（移除修饰词、提取核心词、泛化查询）
- 明确告知用户"未找到精确匹配——以下是最接近的结果"

**零结果记录与分析**：
- 记录每次零结果查询到 MongoDB——包含松弛尝试记录
- 每周对零结果查询做 embedding 聚类——生成 Top-10 高频未覆盖主题报告
- 自动化知识空白标记——关联到知识覆盖率仪表盘

## 第八部分：统一设计原则

1. **最小干预原则**：查询处理应从最小修改开始——逐级松弛——避免过度改变用户原意
2. **缓存优先**：所有查询理解组件都有 LRU 缓存层——命中率是降低延迟的关键
3. **降级保护**：每个组件都有降级路径——LLM 不可用时降级到规则/缓存——确保核心检索可用
4. **配置可调**：所有阈值（置信度、权重、超时）都可通过配置文件调整——无需重新部署
5. **可观测性**：每个组件暴露标准化指标（延迟分布、命中率、错误率）——支撑数据驱动的持续优化
6. **领域词典驱动**：同义词、停用词、拼写词典都基于 YiKnowledge 领域知识——从知识库中自动提取术语——人工审核确认

## 经验教训

1. **根本原因**：开发过程中对边界情况和异常路径的考虑不足是此类问题的共同根因
2. **设计阶段**：在接口设计和模块实现时，应主动考虑异常输入、空值、超时等边界场景
3. **代码审查**：审查时应检查是否存在类似的反模式（如未捕获异常、无超时控制、缺少参数校验等）
4. **测试覆盖**：异常路径的测试覆盖率应与正常路径同等重视
5. **团队分享**：此类问题应在团队周会或技术分享中讨论，形成团队共识
