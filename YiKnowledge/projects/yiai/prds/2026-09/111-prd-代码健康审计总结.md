## 3. 关键发现

### 3.1 错误码体系缺陷 (B01-B02)

`ErrorCode` 枚举中存在 2 对业务码冲突：
- `RATE_LIMITED`(1005→被错误改为 1003) 与 `RESOURCE_ALREADY_EXISTS`(1003) 冲突
- `INTERNAL_ERROR`(5001→改为 5005) 与 `DATABASE_ERROR`(5001) 冲突

**根因**：错误码重构时未进行唯一性校验。`test_all_business_codes_unique` 测试中原先通过 aliases 集合容忍冲突（注释为 "intentional alias"），但实际并非有意为之。

### 3.2 运行时崩溃风险 (B03, B19-B20)

- **B03**：`notification.py` 导入不存在的 `verify_token`（实际函数为 `verify_jwt`），开启认证时 SSE 通知连接即崩溃
- **B19-B20**：`observer` 可选依赖包未安装，但 `config.py` 默认 `observer_enabled=True`，新部署若未显式禁用则启动崩溃

### 3.3 安全漏洞 (B21)

`/web-fetch` 端点无 SSRF 防护，可请求任意内网地址（MongoDB 27017、Ollama 11434、AWS 元数据 169.254.169.254）。修复后通过 `_is_private_url()` 拦截 9 个 RFC 保留 IP 段。

### 3.4 异常处理规范化 (B17)

2 处 RPC 服务方法使用裸 `ValueError` 替代 `BusinessException`：
- `notification_service.mark_as_read()` — 参数校验失败返回 500 而非 400
- `notification_service.delete_notification()` — 同上

**影响面**：所有通过 RPC 信封调用的客户端收到 `code: 9999`（未知错误）而非 `code: 1002`（参数验证失败）。

## 6. 建议

1. **CI 门禁**：将 `test_all_business_codes_unique` 从单元测试提升为 CI 必须检查项，防止未来回归
2. **废弃 API 迁移**：统一将 14 处 `datetime.utcnow()` 替换为 `datetime.now(timezone.utc)`
3. **状态常量统一**：将 `quality.py`/`live.py` 中的硬编码状态集迁移到 `shared/status.py`
4. **可选依赖管理**：建立 `extras_require` 或条件导入模式，避免可选包缺失导致启动崩溃
5. **SSRF 补充防护**：对 `/web-fetch` 添加请求速率限制，防止被用作扫描器
