# M16-功能实现-检索数据管理 — 多轮迭代、可解释性、多语言、时间感知与结果聚类

> 合并文档 · 人天总计：1.5d · 状态：多需求合并
> 合并了 5 个原需求文档，覆盖检索迭代优化、可解释性、多语言能力、时间感知与结果聚类。

---

## 第一部分：多轮检索迭代优化

### 1.1 背景

YiAi 当前的 RAG 检索是单轮的：用户输入查询 → embedding 检索 → 返回 Top-K 结果 → 喂给 LLM。这种单轮检索在查询模糊、答案分散在多个文档、检索过度偏向高频文档等场景中效果极差。真实用户的查询往往是模糊的、需要多角度信息的、需要系统主动澄清和迭代的。

### 1.2 解决方案

**多轮检索迭代优化系统**：检索→分析→精炼→再检索的迭代闭环——在每轮中基于前一轮的检索结果分析缺失信息——生成改写查询——进行下一轮检索——直到收敛。

**核心迭代流程**：
1. **第 1 轮**：原始查询 → 基础检索 → 获得 Top-K 结果 R1
2. **分析阶段**：LLM 分析 R1——评估结果充分性——识别信息缺口
3. **精炼阶段**：基于信息缺口——生成改写查询（补充缺失维度/去除歧义）
4. **第 N 轮**：改写查询 → 检索 → 获得增量结果 Rn
5. **收敛检测**：评估是否达到"足够好"状态——是则终止——否则继续

**查询改写策略**：
- **维度补充**：原始查询缺少某个角度的信息 → 改写查询添加该角度关键词
- **泛化 / 具体化**：检索结果太少 → 泛化查询（移除限定词）——检索结果太多/太散 → 具体化查询（增加限定词）
- **同义改写**：保留语义但使用不同表达——触发检索系统中不同的匹配路径
- **分解**：复杂查询无法一次检索覆盖 → 分解为多个子查询——各子查询独立检索

**多样性强制**：多轮迭代容易返回相似结果——通过 MMR 算法和跨迭代去重——确保每一轮新增的文档与前几轮已有差异。

**跨迭代去重**：维护所有已有文档的签名集合（title + content_hash）——新结果与已有集合比较——去重后再加入结果池。

**收敛检测条件**：
- 新增文档数 < 阈值（如 < 3）——说明检索已穷尽
- 新增文档的相关性分数低于已有文档的最低分——说明新找到的都不如已有的
- 达到最大迭代轮次（5 轮）——强制终止防止超时
- 分析阶段判断"当前结果已充分"（LLM 评估）

**延迟与 Token 控制**：
- 最大迭代轮次：5
- 每轮超时：检索 500ms + 分析 1s
- 总延迟上限：5s
- 总 Token 上限：改写查询的 LLM token < 2000/轮

## 第二部分：检索结果解释

### 2.1 背景

当前 RAG 检索是一个"黑盒"——用户不知道为什么检索到这些文档——无法验证检索质量——"为什么没有检索到 X 文档"无法回答——检索调优缺乏反馈。可解释性不足导致了信任缺失和调试困难。

### 2.2 解决方案

**检索结果可解释性系统**：相关性因子分解——多维度可视化——缺失文档分析——解释质量评分。

**相关性因子分解**：将每个文档的综合排序分数分解为子因子——用户可以看到"这个文档为什么排在这里"。

| 因子 | 说明 | 权重范围 |
|------|------|---------|
| 向量语义相似度 | 文档与查询的 embedding 余弦相似度 | 0-1 |
| 关键词匹配度 | BM25 关键词匹配分数 | 0-1 |
| 短语匹配加分 | 查询短语在文档中的精确匹配 bonus | 0-2 |
| 时效性新鲜度 | 文档的新鲜度衰减权重 | 0-1 |
| 权威性 | 文档来源可信度（引用/作者） | 0-1 |
| 字段权重加成 | 标题/标签等字段的匹配加成 | ×1.0-3.0 |

**每结果可视化相关性条形图**：每个检索结果附带一个相关性分解条形图——显示各因子的贡献——用户一目了然。

**"为什么没检索到 X 文档"分析**：
- 用户可输入"期望但缺失"的文档名称/描述——系统执行反向分析
- 检查该文档是否在 Top-100 候选中但被重排淘汰（排名靠后的原因——列出各因子得分）
- 检查该文档的关键词是否被同义词/停用词处理过滤
- 检查该文档的 embedding 是否与查询的语义距离过大
- 生成"缺失原因报告"——指出可改进的检索参数

**解释质量评分**：对检索结果整体的可解释性进行评分——覆盖度（是否解释了所有 Top-5 结果）——区分度（不同结果之间的因子差异化程度）——可读性（解释文本是否对非技术用户友好）。

**检索性能影响**：因子分解的计算在检索时同步完成（各因子本来就已计算——仅需记录和返回）——额外延迟 < 5ms——额外响应大小 < 2KB/文档。

## 第三部分：多语言检索

### 3.1 背景

知识库以中文为主——但随着技术文档国际化——英文文档占比从 0% 增长到 15%。中文查询无法检索到英文文档——英文查询无法检索到中文文档——语言成为信息检索的无形屏障。

### 3.2 解决方案

**跨语言检索系统**：多语言 Embedding（BGE-M3）——查询翻译 + 多语言扩展——语言路由——结果翻译。

**多语言 Embedding 模型**：使用 BGE-M3（BAAI 的多语言模型）——支持 100+ 语言——在联合向量空间中——中文"Docker 部署"和英文"Docker deployment"的 embedding 相近——可直接跨语言检索。

**查询翻译策略**：
- **检索前翻译**：将查询翻译为目标语言——用翻译后的查询进行检索
- **翻译方式**：本地 Ollama 翻译（快速——< 100ms）或外部 API——缓存翻译结果
- **双语扩展**：原始查询（中文）+ 翻译查询（英文）——两者都参与检索——生成的查询变体列表去重后并行检索

**多语言查询扩展**：中文查询词的同义词扩展同时包含中文和英文同义词——反之亦然。例如：查询"嵌入向量"→扩展为["embedding", "嵌入", "向量表示"]。

**语言检测与路由**：
- 查询语言检测：CJK 字符占比 > 50%→中文——ASCII > 80%→英文——其他→混合
- 语言路由策略：
  - 查询语言 = 知识库主力语言 → 单语言检索
  - 查询语言 ≠ 知识库主力语言 → 跨语言检索（双语扩展）
  - 混合语言查询 → 跨语言检索

**结果翻译**：检索到的英文文档——前端可选项——将文档片段翻译为用户查询语言——用于预览。翻译缓存——避免重复翻译。

**性能指标**：
- 跨语言检索额外延迟：翻译 < 100ms + 双语检索增加 < 50ms = 总计 < 150ms
- 跨语言检索召回率提升：+30-50%（新增英文文档）
- 翻译准确率：> 90%（技术文档领域——通用翻译 API 表现良好）

## 第四部分：时间感知检索

### 4.1 背景

技术知识具有鲜明的时效性——2022 年的教程和 2025 年的最新文档在排序上无差别——时间查询不被理解——无时间过滤能力——文档新鲜度被忽略——不同领域的"保鲜期"差异被无视。

### 4.2 解决方案

**时间感知检索系统**：新鲜度加权——时间查询理解——时间范围过滤——领域差异化衰减曲线。

**新鲜度加权评分**：
```
final_score = semantic_score × 0.7 + recency_score × 0.3
recency_score = exp(-λ × age_in_days)
```
- λ（衰减率）根据领域配置：
  - 前端框架：λ=0.02（半衰期约 35 天）
  - AI/ML：λ=0.01（半衰期约 69 天）
  - 后端框架：λ=0.005（半衰期约 138 天）
  - 数据库原理：λ=0.001（半衰期约 693 天）
  - 编程基础：λ=0.0005（半衰期约 1386 天）

**时间查询理解**：从自然语言查询中解析时间表达式。
- 绝对时间：`"2024 年"、"2026 年 9 月"`→ 精确时间范围过滤
- 相对时间：`"最近一周"、"上个月"、"今年以来"`→ 计算相对时间范围
- 趋势词：`"最新"、"最近"、"新版"`→ 提升新鲜度权重（×2）
- 版本词：`"React 18"、"Python 3.11"`→ 匹配版本号而非纯粹时间

**时间范围过滤**：
- 基于解析的时间表达式——在检​​索前添加 MongoDB 时间过滤
- 支持前端时间滑块：用户可手动调整时间范围
- 时间过滤不隐藏文档——而是排除——用户可切换"显示所有时间"

**领域自动识别**：基于文档的 category 和 tags 自动匹配领域——使用对应的衰减率。未匹配任何领域时使用默认衰减率（λ=0.002）。

**文档时间元数据不完整的处理**：
- created_at 缺失 → 使用 updated_at
- updated_at 也缺失 → 使用文件修改时间（mtime）
- 全部缺失 → 使用知识库导入时间——并标记"时间数据不精确"

**时间与版本混淆处理**：
- "React 18 的最新特性"→ 需要 React 18 版本范围内的最新文档——不是所有 React 文档中的最新
- 版本号检测 → 先按版本过滤 → 再按时间新鲜度排序

## 第五部分：检索结果聚类

### 5.1 背景

搜索结果以线性列表呈现——但人类的认知模型是层级化的（主题 → 子主题 → 文档）。当搜索返回 20+ 文档时——用户面临"信息过载"——不知道这些文档覆盖了哪些主题——无法按主题快速定位——重复内容难以识别。

### 5.2 解决方案

**检索结果聚类系统**：层次化 Agglomerative 聚类——自动关键词标签生成——聚类质量指标——可视化聚类地图。

**聚类算法选择**：Agglomerative Clustering（自底向上的层次聚类）
- vs K-Means：不需要预设 K——自动确定最优聚类数
- vs DBSCAN：适合任意形状的簇——不需要调 eps 和 min_samples
- 使用 Ward 链接（最小化簇内方差）或 Average 链接

**自适应聚类数确定**：使用 Silhouette Score 或 Calinski-Harabasz Index——在可能的 K 值（2-10）中搜索最优。

**聚类关键词标签生成**：
- TF-IDF 提取每个簇中权重最高的 2-3 个词作为标签
- 不使用"Cluster 1"这类无意义名称
- 标签示例："RAG 配置"、"嵌入模型"、"性能优化"
- 标签去重：不同簇的标签应有区分度

**分面导航**：聚类结果作为搜索结果的分面导航结构——用户可点击聚类标签快速跳转到该主题的文档组——替代 M13 中基于 metadata 的分面统计（此处基于文档内容的语义聚类）。

**聚类质量指标**：
- Silhouette Score：衡量簇内紧密度 vs 簇间分离度——范围 [-1, 1]——越接近 1 越好
- Davies-Bouldin Index：衡量簇间相似度——越低越好
- 聚类质量仪表盘：搜索 API 返回聚类质量分数——方便调优

**跨聚类文档标记**：有些文档可能属于多个主题——使用软聚类（Fuzzy C-Means）或基于距离的模糊归属——标注 Top-2 可能归属的聚类——前端展示为"同时属于 X 和 Y"。

**可视化聚类地图**：使用 embedding 降维（UMAP 优于 t-SNE——保留更多全局结构）——将文档映射到二维空间——着色区分聚类——展示文档间的空间关系和主题分布。

**性能优化**：
- 仅在结果数 > 10 时触发聚类（少量结果聚类无意义）
- 聚类超时：500ms——超时则不聚类——返回扁平列表
- 降维可视化作为可选参数——按需生成

## 第六部分：统一设计原则

1. **迭代优于单次**：多轮检索通过分析→精炼→再检索的闭环——像人类搜索一样不断优化——直到找到满意的结果
2. **透明建立信任**：可解释性让用户理解"为什么是这个结果"——将黑盒变为白盒——建立用户对检索系统的信任
3. **语言不应成为壁垒**：多语言检索让用户用自己的语言查询所有知识——通过多语言 Embedding + 翻译——消除语言鸿沟
4. **时间是最重要的上下文**：知识有"保质期"——时间感知检索让新鲜度与相关性平衡——避免过时信息误导用户
5. **结构优于扁平**：聚类将线性列表变为层级导航——符合人类认知模型——降低信息过载——提升检索效率

## 经验教训

1. **根本原因**：开发过程中对边界情况和异常路径的考虑不足是此类问题的共同根因
2. **设计阶段**：在接口设计和模块实现时，应主动考虑异常输入、空值、超时等边界场景
3. **代码审查**：审查时应检查是否存在类似的反模式（如未捕获异常、无超时控制、缺少参数校验等）
4. **测试覆盖**：异常路径的测试覆盖率应与正常路径同等重视
5. **团队分享**：此类问题应在团队周会或技术分享中讨论，形成团队共识
