# YA-09-89: 自愈恢复机制 — 测试规格

> 来源 PRD：[93-需求-自愈恢复机制.md](../../prds/2026-09/93-需求-自愈恢复机制.md)
> 需求编号：YA-09-89 · 优先级：P2 · 人天：0.5d

> **文档职责**：本文档定义**怎么验证**（VERIFY），不含产品目标与实现方案。

---

## 一、测试范围与策略

### 1.1 测试范围

| 模块 | 测试重点 | 层级 |
|------|---------|------|
| FaultDetector | 5 类故障检测逻辑（Ollama/MongoDB/Agent/磁盘/索引） | 单元 |
| 检测阈值 | 多次确认 + hysteresis 防抖机制 | 单元 |
| RecoveryStrategies | 5 级恢复策略编排（重试 -> 重启 -> 清理 -> 重建 -> 人工） | 单元 |
| SelfHealingEngine | 故障检测 -> 策略匹配 -> 执行恢复 -> 结果记录 | 单元 |
| 审计日志 | 全部恢复操作记录到 `audit_logs` | 集成 |
| 幂等性 | 重复执行恢复操作不产生副作用 | 集成 |

### 1.2 测试策略

| 层级 | 框架 | 覆盖内容 | 占比 |
|------|------|---------|------|
| 单元测试 | pytest + mock | 故障检测器、恢复策略、自愈引擎逻辑 | 70% |
| 集成测试 | pytest + mongomock | 完整自愈流程、审计日志写入、幂等性 | 30% |

| 恢复验证 | Mock 恢复操作返回值（成功/失败计数） |

## 三、测试用例

### 3.1 故障检测（5 条）

| 编号 | 用例 | 步骤 | 预期 | 优先级 |
|------|------|------|------|--------|
| UT-FD-01 | Ollama 不可用检测 | Mock Ollama 健康检查返回超时 | `detect()` 标记故障类型 `ollama_crash` | P0 |
| UT-FD-02 | MongoDB 慢查询检测 | 连续 3 次 `db.ping()` > 500ms | 触发 `mongo_slow` 故障事件 | P0 |
| UT-FD-03 | Agent 线程阻塞检测 | Agent 工作线程超过 30s 无心跳 | 标记 `agent_stuck` | P1 |
| UT-FD-04 | 磁盘空间不足检测 | 磁盘使用率 > 90% | 标记 `disk_full`，触发清理恢复 | P1 |
| UT-FD-05 | FAISS 索引损坏检测 | 索引文件 load 抛出 `IOError` | 标记 `index_corrupt`，触发重建策略 | P1 |

### 3.2 故障确认与防抖（3 条）

| 编号 | 用例 | 步骤 | 预期 | 优先级 |
|------|------|------|------|--------|
| UT-HY-01 | 单次误报不触发 | 仅 1 次健康检查超时 | 不触发恢复，状态标记为 `suspect` | P0 |
| UT-HY-02 | 连续确认后触发 | 连续 3 次（间隔 5s）检测到 Ollama 超时 | 确认故障，触发恢复策略 | P0 |
| UT-HY-03 | 恢复成功后的退出延迟 | 故障恢复后 30s 不退出 `recovering` 状态 | 防止状态翻转抖动 | P1 |

### 3.3 恢复策略（4 条）

| 编号 | 用例 | 步骤 | 预期 | 优先级 |
|------|------|------|------|--------|
| UT-RS-01 | 1 级恢复-重试 | Ollama 短暂不可用（< 10s）| 自动重试连接 3 次，恢复后不升级 | P0 |
| UT-RS-02 | 2 级恢复-重启服务 | 重试 3 次失败后 | 执行 `systemctl restart ollama`，记录审计日志 | P0 |
| UT-RS-03 | 恢复升级-人工介入 | 连续恢复失败 3 次 | 标记 `escalated`，发送告警通知 | P0 |
| UT-RS-04 | 恢复成功率统计 | 各策略记录成功/失败计数 | 成功率 < 50% 的策略自动降级为人工介入 | P1 |

## 四、边界与异常测试

### 4.1 边界场景（4 条）

| 编号 | 场景 | 输入 | 预期 |
|------|------|------|------|
| BE-01 | 多故障同时发生 | Ollama 崩溃 + 磁盘满 | 按优先级顺序处理（Ollama > 磁盘 > Agent > 索引） |
| BE-02 | 恢复操作超时 | 重启 Ollama 超过 30s | 超时视为失败，升级到下一级策略 |
| BE-03 | 无故障时自检 | 所有组件健康 | 检测器不触发任何恢复操作 |
| BE-04 | 磁盘清理后需验证 | 清理临时文件后 | 再次检查磁盘使用率，确认已降到 < 70% |

### 4.2 异常场景（3 条）

| 编号 | 场景 | 触发条件 | 预期 |
|------|------|---------|------|
| EX-01 | 恢复操作权限不足 | 执行 `systemctl restart` 无 sudo | 记录错误，直接升级为人工介入 |
| EX-02 | 审计日志写入失败 | MongoDB 故障时无法写审计 | 本地文件降级记录，MongoDB 恢复后补录 |
| EX-03 | 自愈引擎自身异常 | `SelfHealingEngine` 内部抛出异常 | 引擎自身不崩溃，记录异常并休眠后重试 |

## 七、覆盖率缺口

| 缺口 | 原因 | 建议 |
|------|------|------|
| 真实系统级恢复操作 | 需要 root 权限和实际服务进程 | 在集成测试环境补充 |
| 磁盘清理的副作用验证 | 需真实磁盘数据和文件系统 | 使用 tmpfs 隔离测试 |
| 长时间运行稳定性 | 自愈循环运行数小时的稳定性 | 添加 1 小时持续运行测试 |
| FAISS 索引重建性能 | 需要大量真实知识库文件 | 使用 1000+ 文件的数据集 |
