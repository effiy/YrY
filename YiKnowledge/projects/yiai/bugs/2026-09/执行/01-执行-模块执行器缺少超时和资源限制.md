## Description

`src/domain/execution/executor.py` 提供通用模块执行功能，允许通过 API 触发 Python 代码/脚本执行。虽然 observer 中间件提供了 `sandbox_enabled` 选项（默认 `False`），但执行器本身缺少以下关键安全控制：

1. **执行超时** — 无限循环代码会永久占用 worker
2. **内存限制** — 大量内存分配可导致 OOM
3. **子进程限制** — 代码可 fork 大量子进程
4. **文件系统隔离** — 可读写服务文件系统任意位置
5. **网络隔离** — 可访问内部网络资源

**当前 observer 配置：**
```yaml
observer:
  sandbox_enabled: false  # 沙箱默认关闭
  sandbox_fs_allowlist: ""
  sandbox_network_allowlist: ""
```

`observer.sandbox_enabled` 默认为 `False`，且 observer 中间件本身默认不启用（`observer.enabled: false`）。这意味着执行器在没有任何资源限制的情况下运行。

## Steps to Reproduce

1. 设置 `observer.enabled: true` 和 `observer.sandbox_enabled: true`
2. 通过 API 提交一个无限循环的执行任务
3. 任务永久占用执行 worker，后续任务排队等待
4. 没有超时机制终止该任务

## Expected Result

执行器应强制执行：
- 超时限制（默认 30s，可配置）
- 内存限制（默认 256MB）
- 子进程在父进程终止时自动清理

## Actual Result

执行器依赖 observer 中间件提供沙箱保护，但 observer 默认禁用。即使启用，也缺少执行级别的超时控制。

## Root Cause

执行器设计时依赖 observer 中间件提供沙箱能力，但 observer 是可选组件（默认禁用）。执行器本身没有内置的超时和资源限制。

**根本原因：** 安全控制分散在两个组件中（执行器 + observer），且默认都是不安全的配置。纵深防御原则要求每层都应有独立的保护机制。

## Fix

### 1. 执行器内置超时

```python
# src/domain/execution/executor.py
import asyncio
import resource

EXECUTION_TIMEOUT = 30  # 默认 30s
EXECUTION_MAX_MEMORY_MB = 256

async def execute(code: str, timeout: int = EXECUTION_TIMEOUT) -> dict:
    """Execute code with timeout and resource limits."""
    try:
        # 设置内存限制
        memory_limit = EXECUTION_MAX_MEMORY_MB * 1024 * 1024
        resource.setrlimit(resource.RLIMIT_AS, (memory_limit, memory_limit))

        # 设置 CPU 时间限制
        resource.setrlimit(resource.RLIMIT_CPU, (timeout, timeout))

        async with asyncio.timeout(timeout):
            result = await _execute_impl(code)
        return {"success": True, "result": result}
    except asyncio.TimeoutError:
        return {"success": False, "error": f"Execution timed out after {timeout}s"}
    except MemoryError:
        return {"success": False, "error": f"Memory limit exceeded ({EXECUTION_MAX_MEMORY_MB}MB)"}
```

### 2. 强制启用 observer 沙箱

```python
# 在 executor 中检查 observer 状态
if not settings.observer_enabled or not settings.observer_sandbox_enabled:
    logger.warning(
        "Execution module running without sandbox protection. "
        "Set observer.enabled=true and observer.sandbox_enabled=true in production."
    )
```

## Verification

- 无限循环代码 → 30s 后超时，返回错误
- 大量内存分配 → 触发 MemoryError，返回错误
- 正常执行 → 在限制内完成，行为不变

## Prevention

- **安全层面：** 执行器 MUST 内置超时和资源限制，不依赖外部中间件
- **配置层面：** 生产环境 MUST 启用 observer 沙箱
- **架构层面：** 执行器应使用独立进程/容器隔离，而非进程内执行
- **监控层面：** 记录每次执行的资源使用量（CPU 时间、内存峰值）

## 经验教训

1. **根本原因**：开发过程中对边界情况和异常路径的考虑不足是此类问题的共同根因
2. **设计阶段**：在接口设计和模块实现时，应主动考虑异常输入、空值、超时等边界场景
3. **代码审查**：审查时应检查是否存在类似的反模式（如未捕获异常、无超时控制、缺少参数校验等）
4. **测试覆盖**：异常路径的测试覆盖率应与正常路径同等重视
5. **团队分享**：此类问题应在团队周会或技术分享中讨论，形成团队共识
