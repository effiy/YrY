## Description

`header_verification_middleware` 的顶层 `try/except Exception` 块（`src/server/middleware.py:127-133`）捕获所有异常后返回 `SERVER_ERROR` 响应。这虽然防止了中间件崩溃导致整个请求失败，但也**掩盖了中间件内部的逻辑缺陷**——当中间件代码有 bug 时，异常被静默转换为 500 响应，开发者无法从响应中区分"中间件内部错误"和"真正的服务器错误"。

**当前代码：**
```python
# src/server/middleware.py:127-133
except Exception as e:
    logger.error(f"Middleware processing exception: {str(e)}", exc_info=True)
    error_response = fail(
        error=ErrorCode.SERVER_ERROR,
        message="Internal Server Error"
    )
    return _add_cors_headers(error_response, request)
```

**问题：**
1. `message="Internal Server Error"` 对客户端和开发者都无区分度
2. 中间件内部的 `AttributeError`（如 `request.state.xxx` 拼写错误）和真正的业务异常返回相同的错误信息
3. 日志中虽然有 `exc_info=True`，但需要主动查看日志才能发现，开发阶段容易漏掉

## Steps to Reproduce

1. 在 `header_verification_middleware` 中故意引入一个 bug（如 `request.state.nonexistent_field`）
2. 发送任意请求
3. 响应 `{ "code": 5000, "message": "Internal Server Error" }`
4. 响应中没有任何信息指示这是中间件内部错误 vs 业务逻辑错误
5. 日志中有异常堆栈，但前端/API 调用方无法感知

## Expected Result

开发环境下，中间件内部异常应返回更有区分度的错误信息（如 `"Middleware error: ..."`），帮助开发者快速定位问题。

## Actual Result

所有中间件异常统一返回 `"Internal Server Error"`，与业务逻辑异常无法区分。

## Root Cause

异常处理器的 `message` 字段使用硬编码的通用字符串，没有区分异常来源（中间件 vs 业务逻辑）或运行环境（开发 vs 生产）。

**根本原因：** 缺乏分层异常标记机制。中间件层、服务层、数据层的异常在全局异常处理器中被统一处理，丢失了来源信息。

## Fix

### 1. 开发环境返回详细错误信息

```python
# src/server/middleware.py
import os

except Exception as e:
    logger.error(f"Middleware processing exception: {str(e)}", exc_info=True)

    # In development, return the actual error for faster debugging
    is_dev = os.getenv("ENV", "development") == "development"
    message = (
        f"Middleware error: {type(e).__name__}: {str(e)}"
        if is_dev
        else "Internal Server Error"
    )

    error_response = fail(
        error=ErrorCode.SERVER_ERROR,
        message=message
    )
    return _add_cors_headers(error_response, request)
```

### 2. 添加中间件异常类型标记

```python
# src/shared/error_codes.py
class ErrorCode(Enum):
    # ...
    MIDDLEWARE_ERROR = ErrorInfo(5005, http_status.HTTP_500_INTERNAL_SERVER_ERROR, "Middleware Error")
```

## Verification

- 开发环境（`ENV=development`）→ 中间件异常返回 `"Middleware error: AttributeError: ..."`
- 生产环境（`ENV=production`）→ 中间件异常返回 `"Internal Server Error"`
- 正常请求 → 行为不变

## Prevention

- **代码层面：** 中间件内部逻辑保持简单，复杂逻辑提取到独立函数中单独测试
- **测试层面：** 添加中间件异常场景测试，验证响应格式和错误码
- **监控层面：** 区分中间件错误和业务错误的告警阈值

## 经验教训

1. **根本原因**：开发过程中对边界情况和异常路径的考虑不足是此类问题的共同根因
2. **设计阶段**：在接口设计和模块实现时，应主动考虑异常输入、空值、超时等边界场景
3. **代码审查**：审查时应检查是否存在类似的反模式（如未捕获异常、无超时控制、缺少参数校验等）
4. **测试覆盖**：异常路径的测试覆盖率应与正常路径同等重视
5. **团队分享**：此类问题应在团队周会或技术分享中讨论，形成团队共识
