# 模块级可变状态导致测试隔离问题

## 现象

多个模块在模块级别定义了可变数据结构（dict、list），这些状态在进程生命周期内持续存在，导致：

1. **测试隔离问题**：不同测试用例共享同一个模块级缓存/历史记录，测试之间可能相互干扰
2. **内存泄漏风险**：`_fetch_cache` 和 `_cache` 无容量上限，长时间运行会导致内存不断增长
3. **并发的数据竞争**：多个请求可能同时修改模块级字典/列表

涉及的模块级可变状态：

| 文件 | 变量 | 类型 | 清理方式 |
|------|------|------|---------|
| `domain/search/__init__.py` | `_cache` | `Dict[str, tuple[float, List[Dict]]]` | `clear_cache()` 手动清理，有 TTL 但无容量上限 |
| `domain/rag/history.py` | `_history` | `List[Dict[str, Any]]` | 有上限（MAX_HISTORY=20）|
| `domain/rag/chat_history.py` | `_chat_history` | `List[Dict[str, Any]]` | 有上限（MAX_CHAT_HISTORY=20）|
| `server/routes/search.py` | `_fetch_cache` | `Dict[str, Tuple[float, dict]]` | 无上限，无清理 |

## 根因分析

模块级可变状态是 Python 中常见的便捷模式，但对于服务端应用有以下问题：

1. `_fetch_cache`（`server/routes/search.py`）无容量上限，长时间运行会导致内存不断增长。每个被 fetch 的 URL 都会在缓存中保留 5 分钟，但如果有大量不同的 URL 被请求，缓存会在 5 分钟窗口内无限增长
2. `_cache`（`domain/search/__init__.py`）虽然有 TTL，但无容量上限，大量不同查询会持续占用内存
3. 测试需要显式调用 `clear_cache()` / `clear_history()` 来清理状态，否则测试之间会相互影响
4. 模块级状态无法在多进程部署中共享（每个 uvicorn worker 有独立的缓存）

## 涉及文件

- `src/domain/search/__init__.py:22` — `_cache` 字典无容量上限
- `src/domain/rag/history.py:23` — `_history` 列表有上限但不适合多 worker
- `src/domain/rag/chat_history.py:23` — `_chat_history` 列表有上限但不适合多 worker
- `src/server/routes/search.py:49` — `_fetch_cache` 字典无容量上限

## 修复方案

1. **为所有缓存添加容量上限**：`_cache` 和 `_fetch_cache` 应使用 LRU 策略限制最大条目数
2. **考虑使用 `cachetools.TTLCache`**：提供了带 TTL 和容量上限的缓存实现
3. **测试中显式清理**：在 `conftest.py` 中添加 fixture 在每个测试前后清理模块级状态

示例修复（`_fetch_cache`）：
```python
from cachetools import TTLCache

_fetch_cache = TTLCache(maxsize=100, ttl=300)
```

或者使用简单的 LRU 封装：
```python
_MAX_CACHE_SIZE = 100

_fetch_cache: Dict[str, Tuple[float, dict]] = {}

def _cache_put(key, value):
    if len(_fetch_cache) >= _MAX_CACHE_SIZE:
        oldest = next(iter(_fetch_cache))
        del _fetch_cache[oldest]
    _fetch_cache[key] = value
```

## 预防措施

| 层面 | 措施 |
|------|------|
| 代码 | 模块级可变状态必须设置容量上限和 TTL |
| 测试 | 每个测试模块的 setup/teardown 中清理模块级缓存 |
| 审查 | 新增模块级可变状态时须有明确的清理策略 |

## 经验教训

1. **根本原因**：开发过程中对边界情况和异常路径的考虑不足是此类问题的共同根因
2. **设计阶段**：在接口设计和模块实现时，应主动考虑异常输入、空值、超时等边界场景
3. **代码审查**：审查时应检查是否存在类似的反模式（如未捕获异常、无超时控制、缺少参数校验等）
4. **测试覆盖**：异常路径的测试覆盖率应与正常路径同等重视
5. **团队分享**：此类问题应在团队周会或技术分享中讨论，形成团队共识
