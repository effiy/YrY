# 文件中 text/bytes 两种读取模式重复打开同一文件

## 现象

`src/domain/files/local.py` 中 `read_file` 和 `read_project_file` 对同一文件打开两次以支持不同的编码模式。还有多处 `aiofiles.open` 连续调用同一路径但不同模式：

```python
# local.py:62-66 — 同一文件打开两次判断是否为图片
async with aiofiles.open(found_path, encoding="utf-8") as f:
    # 先尝试文本模式读取
async with aiofiles.open(found_path, "rb") as f:
    # 如果是图片再用二进制模式

# local.py:193-196 — read_project_file 同样模式
async with aiofiles.open(abs_path, encoding="utf-8") as f:
    content = await f.read()
async with aiofiles.open(abs_path, "rb") as f:
    # 重复读取
```

这不是每次都需要的——如果文件不是图片，只有第一个 open 是必需的。反之亦然。

## 根因分析

- 图片检测逻辑在打开文件之后（先尝试文本读取，失败后再用二进制）
- 在 `local.py` 文件中有大量顺序的文件操作（read/write/delete/rename），每步都独立打开文件
- `_resolve_project_path` 调用多次安全验证

## 涉及文件

- `src/domain/files/local.py:62-66,193-196` — 重复打开同一文件

## 修复方案

1. 先用 `os.path.splitext` 检查扩展名是否为已知图片格式
2. 根据扩展名决定以文本还是二进制模式打开
3. 或以二进制模式读取所有文件，再根据内容判断类型

## 预防措施

- 单个文件操作不应在同一代码路径中多次 open

## 经验教训

1. **根本原因**：开发过程中对边界情况和异常路径的考虑不足是此类问题的共同根因
2. **设计阶段**：在接口设计和模块实现时，应主动考虑异常输入、空值、超时等边界场景
3. **代码审查**：审查时应检查是否存在类似的反模式（如未捕获异常、无超时控制、缺少参数校验等）
4. **测试覆盖**：异常路径的测试覆盖率应与正常路径同等重视
5. **团队分享**：此类问题应在团队周会或技术分享中讨论，形成团队共识
