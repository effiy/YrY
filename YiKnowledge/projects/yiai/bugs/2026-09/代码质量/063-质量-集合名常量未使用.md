# models/collections.py 中集合名常量未被所有 data 层引用

## 现象

`models/collections.py` 定义了 MongoDB 集合名常量，但 `data/repository.py`、`server/routes/users.py` 等文件中仍使用硬编码字符串字面量：

```python
# models/collections.py — 定义的常量
COLLECTION_MENUS = "menus"
COLLECTION_BUGS = "bugs"

# data/repository.py — 使用字符串而非常量
collection = db.db["menus"]       # 应为 db.db[COLLECTION_MENUS]
collection = db.db[settings.collection_seeds]  # 或从 settings 读取
```

不一致的引用方式使得重命名集合时需要搜索多个位置。

## 根因分析

- 部分集合名通过 `settings.collection_*` 配置（可在 config.yaml 中覆盖）
- 另一部分硬编码在代码中
- `models/collections.py` 存在但未被充分利用

## 涉及文件

- `src/models/collections.py` — 定义了常量但未广泛使用
- `src/data/repository.py` — 使用字符串字面量
- `src/server/routes/` — 多个路由直接使用字符串

## 修复方案

统一使用 `models/collections.py` 的常量或 `settings.collection_*` 配置项。

## 预防措施

- 禁止在路由/数据层中使用裸字符串指定集合名

## 影响范围

- **影响模块**：待补充
- **涉及文件**：
- `src/models/collections.py`
- `src/data/repository.py`
- **是否影响 API 契约**：否
- **是否影响其他项目（YiVad/YiPet）**：否
- **用户感知**：待确认

## 经验教训

1. **根本原因**：开发过程中对边界情况和异常路径的考虑不足是此类问题的共同根因
2. **设计阶段**：在接口设计和模块实现时，应主动考虑异常输入、空值、超时等边界场景
3. **代码审查**：审查时应检查是否存在类似的反模式（如未捕获异常、无超时控制、缺少参数校验等）
4. **测试覆盖**：异常路径的测试覆盖率应与正常路径同等重视
5. **团队分享**：此类问题应在团队周会或技术分享中讨论，形成团队共识
