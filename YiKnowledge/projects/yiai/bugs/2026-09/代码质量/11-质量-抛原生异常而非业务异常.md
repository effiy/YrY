# code-quality: 使用裸 Exception 而非 BusinessException

## 现象

ruff 检查报 TRY002（raise-vanilla-class）：

```
src/domain/execution/executor.py:104:19: TRY002 Create your own exception
```

## 复现步骤

1. 运行 `cd YiAi && python -m ruff check src/ --select=TRY002`
2. 观察使用了裸 `Exception` 的地方

## 预期行为

应使用项目标准的 `BusinessException` 配合适当的 `ErrorCode`

## 实际行为

脚本执行超时时使用 `raise Exception(f"Script execution timeout ({timeout}s)")`，而非项目统一的 `BusinessException`

## 根因分析

`executor.py` 中的超时处理使用裸 `Exception` 而非 `BusinessException(ErrorCode.INTERNAL_ERROR, ...)`，导致：
1. 前端接收到 HTTP 500 而非结构化的错误响应
2. 错误码缺失，前端无法区分超时和其他内部错误
3. 与项目其他模块的异常处理方式不一致

## 修复方案

```diff
- raise Exception(f"Script execution timeout ({timeout}s)") from None
+ raise BusinessException(
+     ErrorCode.INTERNAL_ERROR,
+     message=f"Script execution timeout ({timeout}s)"
+ ) from None
```

## 影响范围

- **影响模块**：src/domain/execution/executor.py
- **是否影响 API 契约**：是（异常类型从裸 Exception 变为 BusinessException，响应格式更规范）
- **是否影响其他项目**：是（YiVad/YiPet 将收到标准化的错误响应格式）

## 验证方法

- [x] `ruff check --select=TRY002` 清洁
- [x] `pytest tests/ -q` 通过（559 个测试）

## 预防措施

| 层面 | 措施 |
|------|------|
| 代码 | 所有 raise 应使用 BusinessException + ErrorCode |
| 测试 | CI 中启用 `ruff check --select=TRY002` |
| 流程 | 代码审查时检查异常类型 |

## 经验教训

1. **根本原因**：开发过程中对边界情况和异常路径的考虑不足是此类问题的共同根因
2. **设计阶段**：在接口设计和模块实现时，应主动考虑异常输入、空值、超时等边界场景
3. **代码审查**：审查时应检查是否存在类似的反模式（如未捕获异常、无超时控制、缺少参数校验等）
4. **测试覆盖**：异常路径的测试覆盖率应与正常路径同等重视
5. **团队分享**：此类问题应在团队周会或技术分享中讨论，形成团队共识
