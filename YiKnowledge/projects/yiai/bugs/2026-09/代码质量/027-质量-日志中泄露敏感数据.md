# execute_module 路由将完整请求参数记录到日志

## 现象

`src/server/routes/execution.py:73` 使用 `logger.info` 记录完整的请求参数：

```python
logger.info(f"Execute module: {request.module_name}, method: {request.method_name}")
logger.info(f"Parameters: {request.parameters}")
```

`request.parameters` 可能包含敏感数据（API 密钥、用户凭证、个人数据），这些数据被明文写入日志文件。

此外，`src/data/repository.py:331` 记录完整的 MongoDB 查询过滤条件：
```python
logger.info(f"Querying collection: {collection_name}, Filter: {filter_dict}, ...")
```

## 根因分析

- 调试日志在生产环境中默认启用
- 没有对敏感字段（password、token、secret、key）做日志脱敏
- 日志文件可能被未授权人员访问或通过日志聚合系统泄露
- `middleware.py:61` 也记录请求详情，但仅限方法和 URL，风险较低

## 涉及文件

- `src/server/routes/execution.py:73` — 完整参数日志
- `src/data/repository.py:331` — 完整过滤条件日志

## 修复方案

1. 将参数日志降级为 `logger.debug`（生产环境默认不输出）
2. 对已知敏感字段名做脱敏处理（password、token、secret、key、authorization）
3. 记录参数长度和键名而非完整值
4. 添加 `settings.log_sensitive_data = False` 配置开关

## 预防措施

- 禁止 `logger.info` 记录请求体或参数
- Code review 检查日志中的敏感数据泄露

## 经验教训

1. **根本原因**：开发过程中对边界情况和异常路径的考虑不足是此类问题的共同根因
2. **设计阶段**：在接口设计和模块实现时，应主动考虑异常输入、空值、超时等边界场景
3. **代码审查**：审查时应检查是否存在类似的反模式（如未捕获异常、无超时控制、缺少参数校验等）
4. **测试覆盖**：异常路径的测试覆盖率应与正常路径同等重视
5. **团队分享**：此类问题应在团队周会或技术分享中讨论，形成团队共识
