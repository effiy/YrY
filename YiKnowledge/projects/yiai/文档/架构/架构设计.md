# 架构设计

## 分层架构

```
┌──────────────────────────────────────────────┐
│  HTTP Layer (server/)                         │
│  Middleware → Routes → Exception Handlers     │
│  18 个路由模块，统一 RPC 分发器                │
├──────────────────────────────────────────────┤
│  Service Layer (services/)                    │
│  封装 domain 逻辑，提供 routes 调用接口        │
│  ai/ database/ execution/ knowledge/ rag/     │
│  rss/ storage/                                │
├──────────────────────────────────────────────┤
│  Domain Layer (domain/)                       │
│  业务逻辑: AI/Agent, Files, RAG, Knowledge,   │
│  RSS, Auth, Execution, State, WeWork          │
├──────────────────────────────────────────────┤
│  Data Layer (data/)                           │
│  MongoDB 单例 → Repository → Session/Store    │
│  Motor async driver, 种子数据                  │
├──────────────────────────────────────────────┤
│  Shared Layer (shared/)                       │
│  Config, Response, ErrorCodes, Utils, Logging │
│  pydantic-settings + YAML 配置源              │
└──────────────────────────────────────────────┘
```

## 请求生命周期

```
HTTP Request
  → CORS 中间件
  → Auth 中间件 (可选，auth_enabled 配置控制)
  → Observer 中间件 (可选，请求日志)
  → 路由匹配
  → 路由处理函数
    → RPC 分发器: 解析 module_name.method_name → 定位 service
    → services 层: 参数校验 + 业务编排
    → domain 层: 核心业务逻辑
    → data 层: MongoDB 操作 (Motor async)
  → 响应 (StandardResponse 统一信封)
```

## RPC 分发器

根路由 `/` 作为 RPC 分发器，解析 `module_name` 和 `method_name` 定位到对应的 service 方法：

```
POST /  body: { module_name, method_name, parameters }
  → _resolve_service(module_name)
  → getattr(service, method_name)(**parameters)
  → StandardResponse(code=0, message="ok", data=result)
```

| module_name | Service | 说明 |
|-------------|---------|------|
| `services.database.data_service` | DataService | 通用 CRUD |
| `services.ai.chat_service` | ChatService | AI 聊天 |
| `services.database.session_service` | SessionService | 会话管理 |
| `services.knowledge.knowledge_service` | KnowledgeService | 知识库 |
| `services.rag.rag_service` | RagService | RAG 检索 |
| `services.rss.feed_service` | FeedService | RSS 订阅 |

## Agent 循环架构 (Pi 风格)

```
POST /agent/chat  { messages, model, max_turns, system?, tools? }
  → Agent.run()
    ┌─────────────────────────────────────────┐
    │  turn_start                             │
    │  → LLM 推理 (Ollama/OpenAI/Anthropic)    │
    │  → 解析响应 (text + tool_calls)          │
    │  → 工具调用:                             │
    │    tool_execution_start                 │
    │    → 确认门控 (写操作需用户确认)          │
    │    → 执行工具 (ToolRegistry.execute)      │
    │    tool_execution_end                   │
    │  → turn_end (总结本轮)                   │
    │  → 循环直到 stop=completed 或 max_turns  │
    └─────────────────────────────────────────┘
  → agent_end { stop_reason, turns, trajectory }
```

Agent 关键特性：
- **确认门控** — 写操作需用户确认，120s 超时自动拒绝
- **拒绝记忆** — 同 session 内拒绝的工具调用自动拦截
- **模型切换** — 弱模型停滞时自动升级到更强模型 (`model_fallback`)
- **预算感知** — 剩余轮次不足时提醒模型压缩步骤
- **旋转检测** — 连续 3 次相同观察触发 nudge
- **结果裁剪** — 超大工具结果自动裁剪，防止上下文溢出
- **断连检测** — 客户端断开 (`asyncio.CancelledError`) 时自动中止

## RAG 检索引擎

```
YiKnowledge Markdown 文件树
  ↓ apscheduler 每 60s 轮询
Knowledge Watcher → 解析 frontmatter + 正文
  ↓ 同步到 MongoDB knowledge_files 集合
llama_index 索引构建
  ↓ VectorStoreIndex + BM25
混合检索 (向量 + BM25)
  ↓ 可选 LLM Rerank
  ↓ HyDE 查询增强
  ↓ Sentence Window 检索
  ↓ 内联引用编号
RAG 查询结果 → 用户
```

## 降级策略

| 场景 | 行为 |
|------|------|
| MongoDB 不可用 | 写入失败，读取返回空结果 |
| Ollama 不可用 | 聊天端点返回 `ErrorCode.AI_UNAVAILABLE` |
| OSS 不可用 | 文件存储回退到本地磁盘 |
| Auth 禁用 | 所有端点公开 (开发环境默认) |
| Agent 模型停滞 | 自动切换到 fallback 模型 |
| Agent 断连 | `asyncio.CancelledError` → 保存当前状态 → 清理 |
| RAG 索引缺失 | 返回空结果 → 提示先构建索引 |
