## 二、多窗口架构

YiPot 使用 Tauri 多窗口模式，每个功能运行在独立窗口中：

```
┌────────────────────────────────────────┐
│  daemon (隐藏窗口) — 进程保活            │
│  ┌──────────────────────────────────┐  │
│  │ translate — 翻译结果展示            │  │
│  │ recognize — OCR 结果展示            │  │
│  │ screenshot — 截图选框 (全屏)        │  │
│  │ config — 设置管理 (800×600)        │  │
│  │ updater — 更新管理 (600×400)       │  │
│  └──────────────────────────────────┘  │
└────────────────────────────────────────┘
```

### 窗口创建流程

```rust
// window.rs
fn build_window(label: &str, title: &str) -> (Window, bool) {
    // 1. 检测鼠标位置 → 确定目标显示器
    // 2. 检查窗口是否已存在 → 存在则聚焦返回
    // 3. 不存在 → 创建新窗口 → 设置位置/大小
    // 4. macOS: TitleBarStyle::Overlay + hidden_title
    // 5. Win/Linux: transparent + decorations(false)
}
```

## 三、前后端通信

### Tauri invoke (前端 → Rust)

```javascript
// 前端调用 Rust 命令
import { invoke } from "@tauri-apps/api/tauri";

const text = await invoke("get_text");              // 获取选中文本
const ocrResult = await invoke("system_ocr", {      // 系统 OCR
  imageBase64: "...",
  language: "zh"
});
```

### Tauri event (Rust → 前端)

```rust
// Rust 发送事件到前端
window.emit("new_text", text).unwrap();
```

```javascript
// 前端监听 Rust 事件
import { listen } from "@tauri-apps/api/event";

listen("new_text", (event) => {
  handleTranslate(event.payload);
});
```

## 补充：架构演进记录

记录 YiPot 架构从 v2.x 到 v3.x 的关键演进。

| 版本 | 日期 | 变更 | 动机 | 影响 |
|------|------|------|------|------|
| v2.x → v3.0.0 | 2024-Q3 | 插件化重构 | 翻译/OCR服务从硬编码迁移到插件系统 | 社区贡献从0增长到80%插件 |
| v3.0.0 → v3.0.4 | 2025-Q1 | 多窗口架构 | 每个功能独立窗口，替代单窗口多面板 | 性能提升，内存隔离，但跨窗口通信复杂度增加 |
| v3.0.4 → v3.0.7 | 2025-Q2 | 配置存储迁移 | `tauri-plugin-store` 替代自定义`config.json` | 支持版本迁移、原子写入、Rust+JS双端读写 |
| v3.0.7+ | 2025-Q3+ | Rust模块化 | 14个Rust模块独立文件替代单一`main.rs` | 可维护性提升，但模块间依赖需明确定义 |
| 计划中 | 待定 | Tauri 1.6 → 2.x | 移动端支持、权限系统增强、IPC性能提升 | 需要评估插件生态迁移成本 |

### 架构决策原则（从演进中总结）

1. **前端承担复杂度优先于Rust端**：插件系统、i18n、主题等可扩展性需求优先在前端实现
2. **Rust负责操作系统边界**：剪贴板、快捷键、系统OCR、窗口管理 —— 这些是FFI不可简化的
3. **配置持久化走tauri-plugin-store**：不直接操作文件系统，保证跨平台一致性和原子性
4. **新增窗口需评估必要性**：每增加一个窗口类型增加约200KB内存（Tauri webview overhead），需ROI评估

## 补充：技术债务清单

| 编号 | 债务项 | 优先级 | 预计工时 | 说明 |
|------|--------|--------|---------|------|
| TD1 | Tauri 1.x → 2.x 迁移 | 中 | 2-3周 | 1.x已稳定但2.x有移动端支持和权限增强，迁移需处理API breaking changes |
| TD2 | React Router 6.27 → 7.x | 低 | 1天 | 当前版本满足需求，7.x有更好的types和loader/action模式 |
| TD3 | `tiny_http` → `axum` 或 `actix-web` | 低 | 3-5天 | 当前本地HTTP服务流量低，暂时无需迁移，但需关注后续外部调用场景 |
| TD4 | Vite 5.4 构建配置碎片化 | 中 | 2天 | build target、minify、sourcemap配置分散，建议抽取shared配置 |
| TD5 | 部分Rust模块缺少单元测试 | 中 | 1周 | `clipboard.rs`、`server.rs`等核心模块测试覆盖率<30% |
| TD6 | NextUI 2.4 自定义样式覆盖过多 | 低 | 3天 | ~50处`!important`标记和组件样式覆盖，升级时需回归测试 |
| TD7 | Tauri `invoke`泛型包装缺失 | 中 | 2天 | 前端`invoke`调用返回类型是`unknown`，缺少统一的类型包装层 |
