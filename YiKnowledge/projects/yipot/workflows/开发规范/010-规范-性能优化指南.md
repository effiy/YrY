> 基于 20 轮审计的性能相关发现和改进建议 · 版本 1.0

## 一、已完成的优化（3.0.8）

| # | 优化项 | 位置 | 技术方案 | 效果 | 轮次 |
|---|--------|------|---------|------|------|
| 1 | `Lazy<LanguageDetector>` 单例 | `lang_detect.rs` | `once_cell::sync::Lazy` 全局静态初始化 | 首次 ~200ms → 后续 <1ms | R1 |
| 2 | `Mutex<bool>` 替代 `Mutex<String>` | `clipboard.rs` | 零分配 bool 替换堆分配 String | 类型安全 + 微性能提升 | R1 |
| 3 | `unwrap()` → `unwrap_or()` / `?` | 14 Rust 文件 | 消除 panic unwind 开销 | 零 panic 路径 | R1-R3 |
| 4 | `ApiClient` 超时控制 | `client.ts` | `AbortController` + 30s timeout | 30s 超时 vs 无限挂起 | R4 |

### 技术细节

#### Lazy<LanguageDetector> 单例模式

```rust
// lang_detect.rs
use once_cell::sync::Lazy;

static DETECTOR: Lazy<LanguageDetector> = Lazy::new(|| {
    LanguageDetector::new().expect("Failed to init language detector")
});

pub fn detect(text: &str) -> Option<String> {
    DETECTOR.detect(text)  // 首次调用初始化，后续零开销
}
```

**性能特征**：
- 冷启动：~200ms（加载 whatlang 模型）
- 热路径：<1ms（已初始化的 HashMap 查找）
- 内存：~2MB（whatlang 模型常驻）

#### ApiClient 超时控制

```typescript
// client.ts
async get(url: string, opts?: { timeout?: number }): Promise<Response> {
  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort(), opts?.timeout ?? 30_000);
  try {
    return await fetch(url, { signal: controller.signal });
  } finally {
    clearTimeout(timer);
  }
}
```

**保护场景**：
- 第三方翻译 API 无响应 → 30s 后自动放弃
- 网络断开但 TCP 未检测到 → 不永久挂起
- 用户可感知的超时错误提示

## 二、推荐优化（3.1+）

### 2.1 HTTP 连接池复用（中优先级 · 预估 0.5d）

**现状**：翻译/OCR 服务各自创建 fetch 请求，无连接复用。YiAi 后端已实现共享 `httpx.AsyncClient`。

**建议**：前端 `ApiClient` 实例化为单例，复用底层 HTTP 连接。

```typescript
// 推荐：模块级单例
class ApiClient {
  private static instance: ApiClient;
  static getInstance(): ApiClient {
    if (!this.instance) this.instance = new ApiClient();
    return this.instance;
  }
}
```

**预期收益**：
- 减少 TLS 握手（后续请求 0-RTT）
- 减少 DNS 解析（连接池缓存）
- 节省 ~50-100ms/请求

**风险**：需验证浏览器/WebView 对 keep-alive 的支持。

### 2.2 翻译结果缓存策略（中优先级 · 预估 1d）

**现状**：YiAi 后端有 MongoDB 翻译记忆缓存。前端直接调用第三方 API 时无缓存。

**建议**：SQLite 本地 LRU 缓存（最近 100 条），避免重复翻译相同文本。

```rust
// 推荐：LRU 缓存结构
use lru::LruCache;
use std::sync::Mutex;

static TRANSLATION_CACHE: Lazy<Mutex<LruCache<String, String>>> =
    Lazy::new(|| Mutex::new(LruCache::new(NonZeroUsize::new(100).unwrap())));

fn cached_translate(text: &str, from: &str, to: &str) -> Option<String> {
    let key = format!("{from}:{to}:{text}");
    TRANSLATION_CACHE.lock().unwrap().get(&key).cloned()
}
```

**预期收益**：
- 缓存命中延迟 <1ms（vs API 调用 500-1000ms）
- 减少 API 配额消耗（热门短语复用率高）

### 2.3 Tesseract WASM 预加载（低优先级 · 预估 0.3d）

**现状**：`worker.min.js` 按需加载，首次 OCR 延迟明显。

**建议**：应用启动时后台预加载 worker，首次 OCR 无冷启动延迟。

```typescript
// 推荐：启动时预加载
async function preloadTesseract() {
  const worker = await Tesseract.createWorker('eng');
  // 保持 worker 存活，OCR 时复用
  return worker;
}
```

**预期收益**：首次 OCR 延迟 -200~500ms。

**风险**：预加载占用内存（~10MB），需要评估低内存设备影响。

### 2.4 截图图像压缩（低优先级 · 预估 0.3d）

**现状**：截图保存为原始分辨率 PNG，传递给 OCR API 为完整 base64。

**建议**：OCR 前将图像压缩至 1080p，减少传输数据量。

```rust
// 推荐：压缩至 OCR 所需最小分辨率
fn compress_for_ocr(img: &DynamicImage) -> DynamicImage {
    img.resize(1920, 1080, image::imageops::FilterType::Lanczos3)
}
```

**预期收益**：
- 传输体积减少 50-80%（4K → 1080p）
- OCR API 响应时间减少 20-40%
- 无识别精度损失（OCR 引擎对分辨率不敏感）

## 三、性能基准

### 3.1 目标 SLO

| 操作 | 目标延迟 | 测量方法 | 当前状态 |
|------|---------|---------|---------|
| 划词翻译（缓存命中） | < 50ms | `performance.now()` | ⚠️ 未测量 |
| 划词翻译（API 调用） | < 1000ms | 同上 | ⚠️ 未测量 |
| 语言检测 | < 5ms | `invoke('lang_detect')` 计时 | ✅ ~1ms |
| TTS 首次播放 | < 500ms | AudioContext 初始化 | ⚠️ 未测量 |
| 截图 OCR | < 2000ms | 截图 → 文字显示 | ⚠️ 未测量 |

### 3.2 测量方法

```rust
// Rust 侧性能计时
use std::time::Instant;

pub fn timed_operation() -> Duration {
    let start = Instant::now();
    // ... 操作 ...
    start.elapsed()
}
```

```typescript
// 前端性能计时
const t0 = performance.now();
await translate(text);
console.debug(`translate: ${(performance.now() - t0).toFixed(0)}ms`);
```

### 3.3 持续监控建议

- **Rust 侧**：集成 `tracing` crate，关键路径打印 `elapsed` 日志
- **前端**：集成 `web-vitals` 或自定义 `PerformanceObserver`
- **CI**：`cargo bench` 基准测试（需 `#[bench]` nightly）纳入 PR 检查
