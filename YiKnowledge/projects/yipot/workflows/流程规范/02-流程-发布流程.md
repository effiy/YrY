# 发布流程

> YiPot 版本发布的标准操作流程。

## 一、发布前检查

- [ ] 所有 PR 已合并到 `dev`
- [ ] `dev` → `main` 已合并
- [ ] CHANGELOG 已更新
- [ ] 版本号已更新（package.json + Cargo.toml + tauri.conf.json）
- [ ] 三平台构建通过
- [ ] macOS 签名 + 公证通过
- [ ] 冒烟测试通过

## 二、版本号更新

```bash
# 1. 更新 package.json
npm version 3.0.8 --no-git-tag-version

# 2. 更新 src-tauri/Cargo.toml
# version = "3.0.8"

# 3. 更新 src-tauri/tauri.conf.json
# "version": "3.0.8"
```

## 三、构建

```bash
# macOS
pnpm tauri build --target universal-apple-darwin

# Windows
pnpm tauri build --target x86_64-pc-windows-msvc

# Linux
pnpm tauri build --target x86_64-unknown-linux-gnu
```

## 四、macOS 签名与公证

```bash
# 签名
codesign --deep --force --verify --verbose \
  --sign "Developer ID Application: Your Name (TEAM_ID)" \
  src-tauri/target/release/bundle/dmg/*.app

# 公证
xcrun notarytool submit Pot.dmg \
  --apple-id "your@email.com" \
  --team-id "TEAM_ID" \
  --password "@keychain:AC_PASSWORD" \
  --wait

# 装订票据
xcrun stapler staple Pot.dmg
```

## 五、创建 Release

```bash
# 打 tag
git tag -a v3.0.8 -m "Release v3.0.8"
git push origin v3.0.8

# GitHub Release
gh release create v3.0.8 \
  --title "Pot v3.0.8" \
  --notes-file CHANGELOG.md \
  Pot_3.0.8_x64.dmg \
  Pot_3.0.8_x64.msi \
  Pot_3.0.8_amd64.deb \
  Pot_3.0.8_amd64.AppImage
```

## 六、发布后

- [ ] 验证 GitHub Release 页面
- [ ] 验证自动更新检查
- [ ] 更新官网/文档
- [ ] 发布公告

## 补充：回滚流程

### 回滚决策树

```
发现生产问题
├── 严重程度 P0（核心功能完全不可用 → 紧急回滚）
│   └── 立即回滚 → 修复 → 热修复发布
├── 严重程度 P1（主要功能受影响 → 评估回滚 vs 修复）
│   ├── 修复时间 < 2h → 直接修复发布 hotfix
│   └── 修复时间 > 2h → 回滚当前版本
└── 严重程度 P2/P3（非阻塞 → 计划修复）
    └── 下个版本修复

回滚操作步骤:
1. 删除有问题的 GitHub Release
2. 删除有问题的 Git Tag
3. 恢复上一个已知好的 Release
4. 更新官网/文档的版本号
5. 通知用户（GitHub Discussion + Discord）
```

### 回滚命令

```bash
# 1. 标记问题版本
git tag -d v3.0.8           # 删除本地 tag
git push origin :refs/tags/v3.0.8  # 删除远程 tag

# 2. 删除 GitHub Release
gh release delete v3.0.8 --yes

# 3. 恢复上一个稳定版本
gh release view v3.0.7  --json tagName,name,assets
# 确认 v3.0.7 的 Release Assets 完好

# 4. 更新自动更新清单
# 编辑 updater/latest.json → version 回退到 v3.0.7

# 5. 验证自动更新
# 启动旧版本 Pot → 检查更新 → 确认不提示升级到 v3.0.8
```

### 回滚后行动

```
回滚完成后（1天内）:
├── 根因分析 → 写入 YiKnowledge/projects/yipot/bugs/
├── 修复开发 → hotfix 分支
├── 回归测试 → 重点测试触发回滚的问题场景
├── 发布检查清单增加对应检查项
└── 团队复盘 → 更新经验教训

长期改进:
├── 功能开关 (Feature Flag): 高风险功能可远程关闭
├── 阶段发布: 先 Linux → Windows → macOS（按用户量递增）
└── 金丝雀通道: 提供给愿意尝鲜的用户的 pre-release 通道
```

## 补充：灰度发布策略

### 三层发布渠道

```
Canary (金丝雀通道)
├── 频率: 每周末自动构建
├── 用户: 自愿加入（GitHub Discussion 申请）
├── 版本号: v3.0.8-canary.1
├── 不签名/不公证
└── 仅 GitHub Release pre-release

Beta (测试通道)
├── 频率: 发布前 1 周
├── 用户: 自动邀请活跃社区贡献者
├── 版本号: v3.0.8-beta.1
├── 基本签名（macOS ad-hoc）
└── GitHub Release pre-release + 自动更新

Stable (稳定通道)
├── 频率: 随正式发布
├── 用户: 全部用户
├── 版本号: v3.0.8
├── 完整签名 + 公证
└── GitHub Release + 自动更新 + 官网
```

### 灰度发布流程

```
Week 1 (Release -7d)
├── 功能冻结: dev 分支不再接受新功能
├── 仅合并 P1+ Bug 修复
└── Beta Release: 推送到 Beta 通道

Week 1 (Release -3d)
├── Beta 用户反馈收集
├── P0/P1 Bug 修复
└── 回归测试

Week 1 (Release Day)
├── 确认 Beta 无 P0/P1 问题
├── dev → main 合并
├── 正式 Release + 签名 + 公证
├── 发布公告
└── 监控 GitHub Issues/Discord

Week 2 (Release +7d)
├── 稳定期监控
├── 收集用户反馈
└── 规划下个版本修复项
```

### 功能开关设计

```javascript
// 使用配置项控制高风险功能的灰度发布
// src/hooks/useConfig.js
function useFeatureFlag(flagName) {
  const [config] = useConfig();
  // 配置示例: { "feature_flags": { "new-ocr-engine": false } }
  return config.feature_flags?.[flagName] ?? false;
}

// 使用
function OcrEngine() {
  const useNewEngine = useFeatureFlag("new-ocr-engine");
  return useNewEngine ? <NewOcrEngine /> : <StableOcrEngine />;
}
```

### 阶段发布（Staggered Rollout）

| 阶段 | 时间 | 覆盖比例 | 操作 |
|------|------|---------|------|
| Linux | Day 0 | 10%用户量 | GitHub Release Assets 上传 |
| macOS | Day 0+2h | 40%用户量 | 确认Linux无异常后上传 |
| Windows | Day 0+4h | 50%用户量 | 确认macOS无异常后上传 |
| 全量 | Day 0+6h | 100% | 更新自动更新清单，发布公告 |

> 阶段发布目前手动执行，未来可考虑通过 CI/CD 自动化。优先级：Linux（最少用户，问题影响最小）→ macOS → Windows（最多用户）。
