# ADR-003: 插件化服务架构

> 状态：已采纳 · 日期：2023 年

## 背景

翻译/OCR/TTS/生词本服务需要持续扩展。硬编码每个服务会使得核心代码膨胀，且第三方开发者的贡献门槛高。

## 决策

采用**三文件插件模式**（info.ts / index.jsx / Config.jsx）。

## 理由

| 方案 | 优势 | 劣势 |
|------|------|------|
| 硬编码 | 简单 | 不可扩展 |
| 动态加载 | 灵活 | 安全风险 |
| 约定式插件 | 标准化、可发现 | 灵活性受限 |

**决定因素**：
- 三文件模式强制了最小接口，降低了实现复杂度
- `services/` 目录的文件系统约定让插件自动被发现（无需注册）
- info.ts 声明式元信息足够 Vite/运行时使用
- Config.jsx 让每个插件自带配置 UI

## 插件接口

```
services/{type}/{name}/
├── info.ts    — { id, name, type, languages, configurable, needs }
├── index.jsx  — 默认导出 async function
└── Config.jsx — React 配置组件
```

## 后果

- 插件开发标准化，社区贡献门槛低
- 插件配置 UI 和后端逻辑解耦
- Vite 构建时自动扫描 services/ 目录

## 备选方案详细对比

### 硬编码 vs 文件系统约定 vs Webpack 动态加载 vs npm 包 vs WASI

| 维度 | 硬编码 | 文件系统约定 (采纳) | Webpack 动态加载 | npm 包注册 | WASI 沙箱 |
|------|--------|-------------------|-----------------|-----------|----------|
| 扩展性 | 无 (需改核心代码) | 高 (加文件即可) | 中 (需配置) | 高 (npm install) | 高 (独立 runtime) |
| 代码隔离 | 差 (全局耦合) | 中 (import 边界) | 中 (代码分割) | 好 (node_modules) | 极好 (沙箱) |
| 发现机制 | 手动注册 | 目录扫描 | 手动注册 | package.json | 目录扫描 |
| 安全风险 | 低 | 中 (文件系统) | 中 | 高 (npm 供应链) | 低 |
| 开发体验 | 简单 | 简单 (约定优于配置) | 中等 | 复杂 | 复杂 |
| 版本管理 | 无 (与核心同版) | 无 (文件级) | 无 (bundle 内) | 内置 (npm version) | 需自行实现 |
| 热更新 | 无 (需重启) | 需 Tauri 重启 | Vite HMR | 需重启 | 需重启 |
| 配置 UI | 硬编码 | Config.jsx | Config.jsx | 外部 | 外部 |
| 社区贡献门槛 | 高 (需 fork) | 低 (3 个文件) | 低 | 中 (需发布) | 中 |

### 淘汰方案分析

- **硬编码**：不可扩展。新增翻译/OCR 服务需要修改核心代码，不适合需要快速添加新 API 的场景。
- **Webpack 动态加载 (`import()`)**: 需要手动维护 `require.context` 配置。每次新增服务需要修改配置。不如文件系统约定直观。
- **npm 包注册**：安全性差 (npm 供应链攻击风险)。对翻译工具这种小型插件来说过于复杂。版本管理是优势但本项目不需要 npm 级别的版本控制。
- **WASI 沙箱**：给每个插件独立运行时隔离最安全，但实现复杂度极高 (配置通信、内存共享)。只有在安全问题成为严重瓶颈时才考虑。

### 最终候选: 文件系统约定 (采纳) vs Webpack 动态加载

两者在 "Config.jsx 自带配置 UI" 这一点上相同。关键差异：

| 对比维度 | 文件系统约定 | Webpack 动态加载 |
|----------|------------|----------------|
| 自动发现 | `fs.readdirSync("services/")` 扫描即可 | 需要维护 `require.context` 或 import map |
| 新增服务 | 创建 3 个文件到对应目录 | + 需更新 module 配置 |
| Vite 构建 | `import.meta.glob` 预扫描 | 需要额外配置 |
| 社区贡献 | "放 3 个文件到 services/" | "放文件 + 改注册配置" |
| 复杂度 | 极低 | 一般 |

## 决策后果与迁移路径

### 正向后果

1. **零配置自动发现**：Vite `import.meta.glob("services/**/info.ts")` 自动收集所有插件
2. **社区贡献友好**：贡献一个翻译服务 = 创建 `services/translate/my-service/` + 3 个文件
3. **配置 UI 内置**：每个插件的 Config.jsx 可以被设置页面自动嵌入
4. **按需编译**：Vite tree-shaking 仅打包被引用的插件

### 负向后果

1. **插件质量不可控**：文件系统约定不校验 info.ts 的类型正确性，需运行时验证
2. **插件冲突**：两个插件使用相同的 `id` 会互相覆盖，需文档约定
3. **热更新**：新增/删除插件文件需要 Tauri 重启才生效
4. **安全风险**：插件代码与核心代码同一进程运行，恶意插件可能读取配置文件

### 潜在演进方向

| 场景 | 触发条件 | 演进方案 |
|------|----------|----------|
| 插件数量 > 50 | 服务种类增多 | 引入插件评分/精选机制 |
| 插件安全性 | 发现恶意插件 | 引入 WASM 沙箱隔离 |
| 插件依赖管理 | 插件需要额外 npm 包 | npm 包注册 + 文件系统约定混合 |
| 插件市场 | 社区贡献活跃 | 在线插件商店 + 一键安装 |

### 如果将来需要迁移

迁移到 npm 包注册的触发条件：
- 社区贡献插件 > 100 个，质量良莠不齐，需要版本管理
- 供应链安全检查变得刚需

迁移成本：
- 需要发布 npm registry 或私有 registry
- 每个插件从 `services/` 目录迁移到 npm 包
- 修改 Vite 构建配置：从 glob 扫描改为 package.json dependencies
- 估计工时：2-3 周
