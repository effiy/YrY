## M06-01: SVG转PNG工具

### 背景与问题

SVG在非浏览器环境（邮件、PPT、Word、社交媒体头像）中不被支持，用户需要将SVG转为PNG。核心是通过HTML5 Canvas的drawImage()方法将SVG Data URL绘制到Canvas，然后toBlob()导出PNG。整个过程可在浏览器端完成，无需后端。

**影响范围**：SVG无法直接用于不支持的环境（高）、输出尺寸不可定制（中）、透明通道丢失（中）、批量转换低效（高）、外部SVG跨域污染Canvas（中）。

### 核心挑战

| 挑战 | 说明 |
|------|------|
| Canvas绘制SVG | SVG需先序列化为Data URL（`data:image/svg+xml;utf8,<svg>...</svg>`），再通过Image对象加载到Canvas |
| 保持透明背景 | Canvas默认背景为透明，但某些SVG内部指定了背景色，需处理内联`<rect>`背景 |
| 输出尺寸控制 | SVG的viewBox定义了坐标系，导出尺寸需要重新指定Canvas宽高，缩放SVG适配 |
| 跨域SVG | 外部URL加载的SVG，Image跨域需设置`crossOrigin = 'anonymous'`，否则Canvas被污染 |
| 批量并行 | 50个SVG逐个渲染导出，需控制并发数，避免浏览器卡顿 |
| SVG内嵌样式 | 使用`<style>`标签的SVG在Data URL中可能样式失效，需内联样式或使用blob URL |

### 核心设计决策

| 决策 | 选项A | 选项B | 选项C | 选择 | 理由 |
|------|--------|--------|--------|------|------|
| SVG渲染 | Canvas drawImage（Image(SVG DataURL)→Canvas） | DOM foreignObject→XMLSerializer→Canvas | SVG String→Blob URL→ImageBitmap→Canvas | Canvas drawImage | 浏览器标准，质量高，实现简单 |
| 输出尺寸 | 锁定比例——修改宽度时高度自动计算 | 自由宽高——独立设置（可能变形） | viewBox倍数——输出尺寸=viewBox×N | 锁定比例为主，自由宽高可选 | 防变形，预设1x/2x/3x快捷 |
| 批量策略 | 串行——逐个转换 | 并行N=4——最多4个同时 | 全并行——50个同时 | N=4并行 | 速度与内存平衡，交互流畅 |
| 跨域处理 | 仅本地文件（拖入/粘贴） | 本地+URL（通过YiAi代理加载） | 本地+URL+CORS自动检测+提示 | CORS检测+提示 | fetch+DataURL避免Canvas跨域污染 |

### 核心渲染流程

```
SVG输入(File/String/URL) → DOMParser.parseFromString(content, 'image/svg+xml')
→ 获取viewBox属性 → svgContent → DataURL: data:image/svg+xml;utf8,encodeURIComponent
→ const img = new Image(); img.src = svgDataUrl
→ img.onload: canvas.width=targetW, canvas.height=targetH
→ {透明背景?} 透明: ctx.clearRect | 不透明: ctx.fillStyle=bgColor, ctx.fillRect
→ ctx.drawImage(img, 0, 0, targetW, targetH)
→ canvas.toBlob('image/png') → PNG Blob
```

### 批量转换并发控制

```typescript
async exportBatch(entries: SVGEntry[], onProgress?: (p: BatchProgress) => void): Promise<PNGResult[]> {
  const concurrency = 4;
  const results: PNGResult[] = [];
  for (let i = 0; i < entries.length; i += concurrency) {
    const batch = entries.slice(i, i + concurrency);
    const batchResults = await Promise.allSettled(
      batch.map(async (entry) => {
        onProgress?.({ ...progress });
        return await this.exportPNG(entry);
      })
    );
    for (const r of batchResults) {
      if (r.status === 'fulfilled') results.push(r.value);
      else progress.failed++;
    }
  }
  return results;
}
```

| 高倍缩放（5x+）后SVG路径锯齿 | 中 | 中 | Canvas drawImage仅为2D渲染，非矢量缩放 |

### 设计决策记录

**D-01：为什么选择data:image/svg+xml Data URL而非Blob URL？**
Data URL方式直接内联SVG内容，不涉及网络请求，new Image().src = dataUrl立即加载。Blob URL也能工作但需要额外Blob创建步骤，且在批量场景下需要管理revokeObjectURL生命周期。Data URL在SVG文件<1MB时性能足够好。

**D-02：为什么批量转换使用N=4而不是N=6？**
Canvas渲染操作占用CPU和GPU资源，不仅消耗网络连接数。N=4是渲染密集型任务的经验值，在速度（4个Canvas并行渲染）和主线程响应性之间取得平衡。N=6会导致主线程阻塞，Popup界面卡顿。

**D-03：为什么默认透明背景而不是白色背景？**
SVG格式的设计初衷就是支持透明，绝大多数SVG图标、logo、插图使用透明背景。如果默认填充白色，用户导出的PNG会丢失透明通道，且用户可能不自知，导致logo放在彩色背景上出现白色方块。

## M06-02: ICO图标生成器

### 背景与问题

Web开发者和设计师需要为网站生成Favicon。ICO格式本质上是将多个BMP/PNG图像打包到一个容器文件中。浏览器端可通过Canvas将任意图片缩放/裁剪到各个目标尺寸，再组装为ICO二进制格式，全程浏览器端完成。

**影响范围**：无ICO生成能力→需外部工具（高）、多尺寸需分别生成再手动合并（中）、原图非正方形构图破坏（中）、16×16小图标模糊不可辨（高）。

### ICO文件二进制结构

```
ICO文件结构：
├── ICONDIR（6字节）
│   ├── idReserved: 2 bytes (must be 0)
│   ├── idType: 2 bytes (1 = ICO, 2 = CUR)
│   └── idCount: 2 bytes (图标数量)
├── ICONDIRENTRY[N]（16字节 × N）
│   ├── bWidth: 1 byte (0 = 256，遵循ICO规范)
│   ├── bHeight: 1 byte (0 = 256)
│   ├── bColorCount: 1 byte (0 if >= 8bpp)
│   ├── bReserved: 1 byte (must be 0)
│   ├── wPlanes: 2 bytes (1)
│   ├── wBitCount: 2 bytes (32 for RGBA)
│   ├── dwBytesInRes: 4 bytes (图像数据大小)
│   └── dwImageOffset: 4 bytes (数据在文件中的偏移)
└── 图像数据[N]（PNG格式，Vista+推荐）
```

### 核心设计决策

| 决策 | 选项A | 选项B | 选项C | 选择 | 理由 |
|------|--------|--------|--------|------|------|
| ICO内部格式 | PNG-only | BMP-only | 混合（小尺寸BMP+大尺寸PNG） | PNG-only | 现代系统均支持，实现简单 |
| 裁剪策略 | 居中裁剪 | 智能裁剪（内容感知） | 手动裁剪 | 居中+手动可选 | 平衡复杂度与灵活性 |
| 缩放算法 | 直接缩放 | 阶梯缩放（256→128→64→32→16） | Lanczos重采样 | 阶梯缩放 | 小图标清晰，实现简单 |
| 尺寸预设 | 固定16/32/48 | 扩展6种 | 配置文件 | 扩展6种+全选/自定义 | 覆盖主流平台 |

### 架构设计

```

  ├── ImageImporter: 拖入图片/粘贴/URL
```

### 阶梯缩放算法

阶梯缩放使用256→192→144→128→96→72→64→48→32→24→20→16的序列，每次缩小约25%，保留更多细节信息。Canvas drawImage使用硬件加速的双线性/双三次插值。

```typescript
private stagedScale(targetSize: number): HTMLCanvasElement {
  const stages = [256, 192, 144, 128, 96, 72, 64, 48, 32, 24, 20, 16]
    .filter(s => s >= targetSize && s <= this.cropRegion.size);
  if (stages.length <= 1) {
    // 直接缩放
    ctx.drawImage(source, cropX, cropY, cropSize, cropSize, 0, 0, targetSize, targetSize);
  } else {
    // 多阶段缩放
    tempCtx.drawImage(source, cropX, cropY, cropSize, cropSize, 0, 0, stages[0], stages[0]);
    for (let i = 1; i < stages.length; i++) {
      nextCtx.drawImage(tempCanvas, 0, 0, stages[i], stages[i]);
    }
  }
}
```

### ICO二进制构建关键代码

```typescript
// ICONDIR（6字节，小端序）
const header = new ArrayBuffer(6);
const headerView = new DataView(header);
headerView.setUint16(0, 0, true);    // reserved
headerView.setUint16(2, 1, true);    // type: ICO
headerView.setUint16(4, entries.length, true); // count

// ICONDIRENTRY（16字节 × N，小端序）
for (const entry of entries) {
  const view = new DataView(entryBuf);
  view.setUint8(0, entry.size === 256 ? 0 : entry.size); // 256→0
  view.setUint16(4, 1, true);    // planes
  view.setUint16(6, 32, true);   // bit count (32 = RGBA)
  view.setUint32(8, entry.pngArrayBuffer.byteLength, true);
  view.setUint32(12, dataOffset, true);
  dataOffset += entry.pngArrayBuffer.byteLength;
}

// 合并：ICONDIR + N×ICONDIRENTRY + N×PNG Data
const blob = new Blob([icoBuffer], { type: 'image/x-icon' });
```

### 设计决策记录

**D-01：为什么使用PNG-only方案而不是实现完整的BMP编码器？**
BMP位图编码涉及BITMAPINFOHEADER（40字节）+调色板+像素数据（BGR顺序，与Canvas RGBA不同），需手动实现字节顺序转换和行对齐。PNG-only直接使用Canvas toBlob('image/png')输出，一行代码完成编码。Windows XP市场份额<0.1%。

**D-02：为什么256×256的ICONDIRENTRY宽高设置为0？**
ICONDIRENTRY的bWidth/bHeight是1字节（0-255），无法表示256。ICO规范规定：当尺寸为256时，bWidth和bHeight都设为0，应用程序解读0为256。

## M06-03: 图片转Base64

### 背景与问题

Base64图片编码在前端开发（内联小图标减少HTTP请求）、邮件HTML模板（嵌入图片避免外部加载被阻止）、API请求（传输Base64编码图片）中频繁使用。

**影响范围**：无便捷的图片→Base64桌面工具（中）、手动拼接Data URI前缀易出错（中）、批量转换无支持（中）、无即用的HTML/CSS代码生成（中）、URL安全编码不熟悉（低）。

### 核心设计决策

| 决策 | 选项A | 选项B | 选择 | 理由 |
|------|--------|--------|------|------|
| 编码方式 | FileReader+readAsDataURL（快速，保持原格式） | Canvas+toDataURL（支持格式转换+质量控制） | 两者互补 | FileReader用于快速模式，Canvas用于高级模式 |
| 输出格式 | 仅Data URI | 6种输出tab切换（DataURI/纯Base64/URLSafe/HTML img/CSS bg/Markdown） | 6种输出 | 覆盖所有使用场景，一键复制即用 |
| 大文件处理 | >100KB截断显示+下载按钮 | 虚拟滚动渲染长文本 | 截断+下载 | 避免剪贴板长字符串导致浏览器卡顿 |
| URL Safe | 去除=填充，+→-，/→_ | 保留所有字符 | 去除=填充 | RFC 4648 Section 5标准，JWT同样做法 |

### 转换流程

```
图片输入（选择文件/剪贴板粘贴/拖拽/URL加载）
→ 编码引擎选择：
  ├── FileEncoder: FileReader.readAsDataURL → 完整Data URI（快速，保持原格式）
  └── CanvasEncoder: Canvas.toDataURL → 格式转换+质量控制（高级模式）
→ 提取纯Base64（去除"data:image/...;base64,"前缀）
→ URL Safe转换（+→-, /→_, 去除=填充）
→ 代码生成器生成6种输出格式
→ 图片预览 + 元信息（格式/尺寸/文件大小/Base64长度/编码耗时）
```

### 6种输出格式

| 输出格式 | 示例 | 场景 |
|----------|------|------|
| Data URI | `data:image/png;base64,iVBORw0KGgo...` | 通用嵌入 |
| 纯Base64 | `iVBORw0KGgo...` | 需要手动拼接前缀时 |
| URL Safe | `iVBORw0KGgo...`（+/=已替换） | URL参数/JSON传输 |
| HTML img | `<img src="data:image/png;base64,..." alt="image" />` | 直接粘贴到HTML |
| CSS bg | `background-image: url('data:image/png;base64,...');` | 直接粘贴到CSS |
| Markdown | `![image](data:image/png;base64,...)` | 文档嵌入 |

### 代码生成器

```typescript
function generateHtmlImgTag(result: EncodeResult, alt?: string): string {
  return `<img src="${result.dataUri}" alt="${alt || 'image'}" width="${result.width}" height="${result.height}" />`;
}

function generateCssBackground(result: EncodeResult): string {
  return `background-image: url('${result.dataUri}');\nbackground-size: ${result.width}px ${result.height}px;`;
}

function generateMarkdownImage(result: EncodeResult, alt?: string): string {
  return `![${alt || 'image'}](${result.dataUri})`;
}

function toUrlSafe(base64: string): string {
  return base64.replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');
}

function fromUrlSafe(urlSafe: string): string {
  let base64 = urlSafe.replace(/-/g, '+').replace(/_/g, '/');
  while (base64.length % 4) base64 += '=';  // 恢复填充
  return base64;
}
```

## M06-04: WebP转换

### 背景与问题

WebP在同等视觉质量下比JPEG小25-35%，比PNG小26-50%。Chrome/Edge支持Canvas WebP编码（toBlob('image/webp')），Firefox/Safari不支持，需服务端libwebp兜底。

**影响范围**：网站图片体积大---JPEG/PNG非WebP多30%+流量（高）、透明图片体积大---PNG-24转WebP可减至30%（高）、GIF动画体积大---2MB GIF转动画WebP仅500KB（高）。

### 核心设计决策

| 决策 | 选项A | 选项B | 选项C | 选择 | 理由 |
|------|--------|--------|--------|------|------|
| 编码实现 | Canvas API（仅Chrome/Edge） | 服务端libwebp | WASM libwebp | Canvas + 服务端兜底 | 覆盖全浏览器 |
| 压缩模式 | 自动选择 | 手动选择 | 智能推荐+手动可切换 | 智能推荐+可切换 | 降低认知负担 |
| 动画支持 | 不支持 | 仅预览 | 完整转换 | 完整转换 | 动画是高频需求 |
| 质量预设 | 固定质量80 | 滑块0-100 | 场景预设 | 场景预设+微调 | 对标Squoosh |

### WebP质量预设

| 预设 | 模式 | quality | 适用场景 |
|------|------|---------|----------|
| 照片优化 | 有损 | 80 | JPEG照片，视觉效果无损 |
| 图标无损 | 无损 | 100 | PNG图标/Logo，保留透明度 |
| 缩略图 | 有损 | 60 | 最大化压缩 |
| 近无损 | near_lossless | 90 | 视觉无损但有微量压缩，比无损小30% |
| 极致压缩 | 有损 | 40 | 大图预览或带宽受限场景 |

### 转换流程

```
图片拖入 → 格式检测（PNG/JPEG/GIF） → Alpha通道检测
→ GIF帧数检测（是否为动画）
→ 智能推荐模式（透明PNG→无损，JPEG照片→有损80，动画GIF→动画WebP）
→ Chrome/Edge → Canvas.toBlob('image/webp', quality)
→ Firefox/Safari → YiAi服务端libwebp转换
→ 动画GIF → 始终服务端gif2webp
→ 对比预览 + 大小对比（原始vs转换后vs节省比例） + 下载
```

### Alpha通道检测

```typescript
static async detectAlpha(file: File): Promise<boolean> {
  const bitmap = await createImageBitmap(file);
  const canvas = document.createElement('canvas');
  canvas.width = bitmap.width; canvas.height = bitmap.height;
  const ctx = canvas.getContext('2d')!;
  ctx.drawImage(bitmap, 0, 0);
  const imageData = ctx.getImageData(0, 0, canvas.width, canvas.height);
  // 每10像素采样检测Alpha
  for (let i = 3; i < imageData.data.length; i += 4 * 10) {
    if (imageData.data[i] < 255) {
      bitmap.close();
      return true;
    }
  }
  bitmap.close();
  return false;
}
```

### 动画GIF检测

通过解析GIF二进制数据遍历图形控制扩展块（0x21 0xF9）计数来检测帧数。静态GIF frameCount=1，动画GIF frameCount>1。检测到动画后自动提示"可转为动画WebP（预估减少60-80%体积）"。

### 智能模式推荐逻辑

```typescript
static recommendMode(format: string, hasAlpha: boolean, isAnimated: boolean): { mode: WebPMode; reason: string } {
  if (isAnimated) return { mode: 'lossy', reason: '动画GIF推荐有损模式（体积减少60-80%）' };
  if (hasAlpha) return { mode: 'lossless', reason: '包含透明通道，推荐无损模式保留透明度' };
  if (format === 'image/png') return { mode: 'lossless', reason: 'PNG推荐无损模式（截图/图标类）' };
  if (format === 'image/jpeg') return { mode: 'lossy', reason: 'JPEG照片推荐有损模式（质量80视觉效果无损）' };
  return { mode: 'lossy', reason: '推荐有损模式' };
}
```

|------|------|------|

拖入500KB PNG-24透明Logo→系统检测到Alpha通道→自动推荐"无损"模式→输出WebP保留透明度→输出大小<200KB。

## M06-05: AVIF转换

### 背景与问题

AVIF基于AV1视频编码关键帧技术，比WebP再小20-30%，比JPEG小50-60%，同时支持HDR、广色域、无损压缩和动画。但Chrome客户端AVIF编码极慢（5-30s/张），因此全部使用服务端libavif编码。

**影响范围**：静态资源体积可优化但未优化---CDN全用WebP而非AVIF（高）、编码时间过长导致放弃（高）、不知道何时用AVIF（中）、浏览器兼容性未知（中）。

### 核心设计决策

| 决策 | 选项A | 选项B | 选项C | 选择 | 理由 |
|------|--------|--------|--------|------|------|
| 编码实现 | 客户端Canvas（仅Chrome，极慢5-30s） | 服务端libavif | Canvas+服务端兜底 | 纯服务端 | 客户端太慢，用户体验不可接受 |
| 速度配置 | 固定speed=6 | 用户可调0-10 | 智能调整 | 固定6+可调 | 默认平衡，高级可控 |
| 兼容指示 | 全局提示"覆盖率92%" | UA检测 | 动态检测+真实解码测试 | 动态检测+评分 | 最准确 |
| 格式推荐 | 手动选择 | 固定推荐AVIF | 场景分析推荐 | 场景分析 | 降低决策负担 |

### AVIF编码速度预设

| 速度 | 标签 | 压缩率 | 预估时间 | 场景 |
|------|------|--------|----------|------|
| 0 | 最慢（最佳质量） | 极致 | ~10s/张 | 最终部署 |
| 3 | 慢（高压缩率） | 高 | ~5s/张 | 最终部署 |
| 6 | 默认（平衡） | 中 | ~2s/张 | 日常使用 |
| 8 | 快（预览用） | 较低 | ~1s/张 | 快速预览 |
| 10 | 最快 | 低 | ~0.5s/张 | 快速预览 |

### 浏览器兼容性检测

```typescript
static async detectAVIFCompat(): Promise<AVIFCompatResult> {
  // 真实解码测试：创建1×1 AVIF图片并尝试解码
  const testAVIF = 'data:image/avif;base64,AAAAIGZ0eXBhdmlm...';
  const img = await new Promise<HTMLImageElement>((resolve, reject) => {
    const el = document.createElement('img');
    el.onload = () => resolve(el);
    el.onerror = () => reject(new Error('AVIF decode failed'));
    el.src = testAVIF;
  });
  const decodeSupported = img.naturalWidth > 0;

  // 编码测试：Canvas.toBlob('image/avif')
  const canvas = document.createElement('canvas');
  canvas.width = 1; canvas.height = 1;
  const avifBlob = await new Promise<Blob | null>((resolve) => {
    canvas.toBlob((blob) => resolve(blob), 'image/avif', 0.8);
  });
  const encodeSupported = avifBlob !== null && avifBlob.type === 'image/avif';

  return { decodeSupported, encodeSupported, globalCoverage: 92 };
}
```

## M06-06: 渐进式JPEG

### 背景与问题

JPEG有Baseline（从上到下逐渐显示）和Progressive（模糊到清晰）两种模式。Progressive JPEG感知加载更快（200ms即见轮廓）、通常体积更小3-7%、减少CLS。但大量JPEG仍是Baseline模式，因为Photoshop默认导出Baseline、在线工具缺乏转换功能。

**影响范围**：页面感知加载慢（高）、Baseline体积更大（中）、Cumulative Layout Shift（中）、无法预览渐进加载效果（中）。

### 核心设计决策

| 决策 | 选项A | 选项B | 选项C | 选择 | 理由 |
|------|--------|--------|--------|------|------|
| 转换实现 | jpegtran无损（仅重排DCT系数） | cjpeg/mozjpeg重编码 | 两者都提供 | 两者都提供 | 覆盖无损和重编码场景 |
| 扫描脚本 | 固定脚本（3次扫描） | 预设选择（3/4/5次扫描） | 自定义JSON脚本 | 预设选择 | 降低门槛+保留灵活性 |
| 加载模拟 | 图片序列（静态） | Canvas逐层叠加 | 真实慢速网络加载 | 真实限速加载 | 最真实体验 |
| 适用性检查 | 不检查 | 简单阈值（<10KB不推荐） | 智能分析 | 简单阈值+提示 | 简单有效 |

### JPEG模式检测

通过解析JPEG二进制数据中的SOF（Start of Frame）标记段来检测模式：
- SOF0（0xFF 0xC0）= Baseline DCT
- SOF2（0xFF 0xC2）= Progressive DCT
- 检测EXIF段（0xFF 0xE1 + "Exif"）

### 转换流程

```

  ├── 已是Progressive → "已是渐进式JPEG，无需转换"
  ├── 文件<10KB → "小文件转Progressive可能增大体积，建议保持Baseline"
  └── Baseline且适合转换 → "推荐转为Progressive JPEG（提升加载体验）"
→ 选择转换方式：
  ├── jpegtran无损转换（默认，仅重排DCT系数，质量不变，速度快<100ms）
```

## M06-07: SVGO优化

### 背景与问题

设计师从Figma/Illustrator/Sketch导出的SVG包含大量冗余数据：编辑器元数据（占体积10-30%）、4-6位小数路径精度（屏幕仅需1-2位）、冗余命名空间和ID、未使用的group元素。SVGO优化通常可减少20-60%体积。

**影响范围**：SVG体积浪费（高，50个图标500KB→200KB）、编辑器元数据泄露（中）、路径精度过高（中）、缺少viewBox（高）、未使用的ID和命名空间（中）。

### 核心设计决策

| 决策 | 选项A | 选项B | 选项C | 选择 | 理由 |
|------|--------|--------|--------|------|------|
| 运行环境 | 服务端Node.js SVGO | SVGO WASM编译 | 纯前端实现 | 服务端SVGO | 完整+简单 |
| 插件配置 | 全启/全关 | 预设配置（3档） | 逐插件切换（类似SVGOMG） | 预设+逐插件切换 | 渐进复杂度 |
| viewBox处理 | 不处理 | 仅提示 | 自动检测+可选修复 | 检测+可选修复 | 安全+有用 |
| 对比方式 | 文本diff | 视觉并排 | 两者都提供 | 视觉并排+可选diff | 覆盖所有人 |

### 三档预设

**安全优化**（典型节省10-20%）：
仅移除不影响显示的冗余数据——removeDoctype、removeXMLProcInst、removeComments、removeMetadata、removeTitle、removeDesc、removeEditorsNSData、removeEmptyAttrs、cleanupAttrs、removeUnusedNS。不改路径/颜色/ID。

**标准优化**（典型节省30-50%）：
安全优化基础上 + cleanupIds(minify)、cleanupNumericValues(floatPrecision=2)、convertColors(currentColor=false)、convertPathData(floatPrecision=2)、convertTransform(floatPrecision=2)、removeEmptyContainers、removeUselessStrokeAndFill、removeUnknownsAndDefaults、removeNonInheritableGroupAttrs、sortAttrs。视觉效果完全一致。

**激进优化**（典型节省50-70%）：
标准优化基础上 + removeUselessDefs、cleanupIds(remove=true)、cleanupNumericValues(floatPrecision=1)、convertPathData(floatPrecision=1)、removeOffCanvasPaths、reusePaths、mergeStyles、inlineStyles、minifyStyles。可能影响可编辑性和某些渲染场景。

### SVG分析器

前端DOMParser解析SVG，统计：元素数量、属性数量、路径数量、group数量、defs数量。检测关键问题：viewBox缺失、编辑器元数据（Adobe Illustrator/Figma/Sketch/Inkscape）、HTML注释、高精度路径（4+位小数）、冗余XML命名空间。

### SVGO优化核心流程

```
拖入SVG文件或粘贴SVG代码 → SVG分析器（统计元素/属性/路径精度/检测问题）
→ viewBox检测（缺失时警告，可选自动修复）
→ 预设选择（安全/标准/激进）或逐插件切换
→ 服务端SVGO.optimize(svgString, config)
→ 返回优化后SVG + 统计信息
→ 视觉并排对比（原图 vs 优化后）
→ 统计面板（体积/减少百分比/移除元素/路径精度变化）
→ 代码diff视图（可选）
→ 下载优化后SVG / ZIP批量下载
```

### 性能指标

| 操作 | 耗时 | 说明 |
|------|------|------|
| SVG分析（前端DOMParser） | < 20ms | 解析+统计 |
| 上传SVG（15KB） | < 100ms | 小文件上传 |
| SVGO优化（服务端，标准预设） | 50-200ms | Node.js SVGO处理 |
| 下载优化后SVG（5KB） | < 50ms | 小文件下载 |
| 视觉对比渲染 | < 30ms | 两个inline SVG渲染 |
| 批量10个（3并发） | 2-5s | 并发处理 |

### 测试场景

**场景1：标准SVG优化（Figma导出）**
拖入Figma导出的15KB SVG（含metadata/注释/高精度路径）→分析检测到元数据、5条注释、路径精度4位→选择"标准优化"→优化后体积<6KB（减少60%+）→视觉对比显示原图和优化后完全一致。

**场景2：安全优化（仅清理元数据）**
拖入含Illustrator元数据的SVG→选择"安全优化"→仅移除doctype/注释/元数据/编辑器命名空间→不修改路径数据/颜色/ID→视觉对比像素级一致。

**场景3：激进优化警告**
选择"激进优化"→系统显示警告："激进优化可能影响SVG的可编辑性和某些渲染场景"→自动切换到代码diff视图展示具体变更→用户确认后才能执行。

**场景4：viewBox缺失检测和修复**
拖入缺少viewBox但有width/height的SVG→检测到缺少viewBox→显示黄色警告→推荐viewBox值（从width/height推断）→点击"添加viewBox"→SVG增加viewBox属性。

**场景5：批量优化10个SVG**
拖入10个SVG图标文件→选择"标准优化"→逐个显示优化进度和结果→全部完成后显示批量统计（总节省体积、平均节省百分比）→提供"逐个下载"和"下载全部（ZIP）"两个选项。

### 设计决策记录

**D-01：路径精度默认值。** 标准预设floatPrecision=2，激进预设=1。屏幕渲染分辨率下，2位小数精度（0.01px）远超设备像素精度（1px=1/96 inch）。1位小数（0.1px）在极端缩放场景下可能出现亚像素偏移。

**D-02：cleanupIds是否默认启用。** 标准预设禁用，激进预设启用。ID可能被外部CSS（#icon:hover）、JS（getElementById）、或`<use>`元素引用。安全起见默认不清理。

**D-03：removeViewBox默认行为。** 始终保留viewBox（即使SVGO默认是移除）。viewBox对SVG响应式缩放至关重要。前端始终传removeViewBox: false。

## M06-08: 精灵图生成

### 背景与问题

CSS Sprite将多个小图标合并为一张大图，减少HTTP请求。尽管HTTP/2支持多路复用，精灵图仍有价值：减少连接开销、更好的缓存策略（一张图vs 100张图）、避免并发限制。

**影响范围**：图标请求数量多---50个独立图标=50个HTTP请求（高）、手工制作精灵图耗时---20个图标需20-30分钟（高）、background-position计算错误（中）、维护困难（中）。

### 核心设计决策

| 决策 | 选项A | 选项B | 选项C | 选择 | 理由 |
|------|--------|--------|--------|------|------|
| 生成方式 | 客户端Canvas | 服务端 | WASM | 客户端Canvas | 即时响应 |
| 布局策略 | 水平/垂直 | 网格 | 自动最优+手动指定 | 自动最优+可指定 | 智能默认+灵活 |
| 尺寸处理 | 统一缩放 | 保持原始 | 用户可选 | 用户可选 | 覆盖所有场景 |
| CSS输出 | 仅CSS | CSS+SCSS | CSS+SCSS+LESS | CSS+SCSS+LESS | 覆盖主流预处理器 |

### 4种布局模式

**水平排列**：单行排列，所有图标y=0，x依次递增。适合等高的图标集。

**垂直排列**：单列排列，所有图标x=0，y依次递增。适合等宽的图标集。

**对角排列**：x和y同时偏移，形成对角线。适合少量图标展示。

**网格排列（默认）**：自动计算最优M×N布局，最小化画布面积。公式：`columns = ceil(sqrt(n * w/h))`，考虑图标宽高比修正因子使画布接近正方形。

### 网格布局核心算法

```typescript
private calculateGrid(icons: IconEntry[], config: SpriteConfig): SpritePosition[] {
  let columns = config.columns;
  if (!columns) {
    // 自动计算最优列数：最小化画布面积
    const maxW = Math.max(...icons.map(i => i.targetWidth));
    const maxH = Math.max(...icons.map(i => i.targetHeight));
    columns = Math.ceil(Math.sqrt(icons.length * (maxW / maxH)));
  }
  const rows = Math.ceil(icons.length / columns);
  // 逐格计算x,y坐标，考虑每列实际最大宽度和每行实际最大高度
  // 使用colWidth/rowHeight确保尺寸不统一的图标对齐
}
```

## M06-09: 格式检测

### 背景与问题

文件扩展名不可信（.png可能是JPEG编码），损坏的图片文件在Canvas绘制时静默失败或显示空白，不支持的格式（BMP/TIFF/HEIC）需提前检测并提示。

**影响范围**：格式不匹配导致转换失败（高）、损坏图片导致Canvas空白（高）、不支持的格式静默失败（中）、无扩展名文件无法分类（中）。

### 双重检测架构

```
第一道防线（上传时快速检测，<3ms）：
  选择文件 → 读取文件头256字节（FileReader.slice）
  → 魔数匹配（10种格式魔数映射表）
  → 验证扩展名与魔数一致性
  → 结果：known(一致)/mismatch(不一致)/unknown(无法识别)

第二道防线（处理前深度检测，<200ms）：
  需要处理图片时触发 → 文件结构验证（PNG chunk/JPEG marker/GIF trailer）
  → createImageBitmap解码验证
  → 结果：valid/suspicious/corrupted/unknown
```

### 支持的格式魔数

| 格式 | 魔数(hex) | 偏移 | 浏览器支持 |
|------|----------|------|-----------|
| JPEG | FF D8 FF | 0 | true |
| PNG | 89 50 4E 47 0D 0A 1A 0A | 0 | true |
| GIF87a | 47 49 46 38 37 61 | 0 | true |
| GIF89a | 47 49 46 38 39 61 | 0 | true |
| WebP | 52 49 46 46 ... 57 45 42 50 | 0/8 | true |
| AVIF | ... 61 76 69 66 | 8 | true |
| BMP | 42 4D | 0 | true |
| ICO | 00 00 01 00 | 0 | true |
| TIFF(LE) | 49 49 2A 00 | 0 | false |
| TIFF(BE) | 4D 4D 00 2A | 0 | false |
| HEIC | ... 68 65 69 63 | 8 | false |
| SVG | 3C 73 76 67（文本`<svg`） | 0 | true |

### 核心设计决策

| 决策 | 选项A | 选项B | 选项C | 选择 | 理由 |
|------|--------|--------|--------|------|------|
| 检测时机 | 上传时 | 处理前 | 双重检测（上传浅+处理前深） | 双重检测 | 分阶段，快速+深度 |
| 魔数检测 | 自建魔数库（~1KB） | 第三方库file-type（~15KB） | FileReader+手动对比 | 自建魔数库 | 覆盖10种格式，无额外依赖 |
| 损坏检测 | 仅魔数 | 魔数+文件结构 | 魔数+结构+实际解码 | 分层：魔数+结构+解码 | 85%→99%准确率 |
| 不支持格式 | 拒绝 | 警告 | 警告+可选自动转换 | 警告+可选转换 | 用户可选择 |

### 损坏检测实现

```typescript
private validateStructure(header: Uint8Array, format: FormatInfo | null): boolean {
  if (!format) return false;
  switch (format.mime) {
    case 'image/png':
      return header[0]===0x89 && header[1]===0x50 && header[2]===0x4E && header[3]===0x47;
    case 'image/jpeg':
      return header[0]===0xFF && header[1]===0xD8 && header[2]===0xFF;
    case 'image/gif':
      return header[header.length-1] === 0x3B; // GIF trailer
    case 'image/webp':
      return header[0]===0x52 && header[1]===0x49; // RIFF header
    default:
      return true; // 其他格式仅检查魔数
  }
}
```

### SVG特殊检测

SVG是基于XML的文本格式，无二进制魔数。使用正则`/<svg[\s>]/i`搜索前100字节的文本内容进行检测。部分SVG以XML声明`<?xml`开头，部分以`<svg`开头，部分包含空白行前导。

| 操作 | 耗时 |
|------|------|
| 文件头读取（256B） | < 1ms |
| 魔数匹配（10种格式） | < 0.1ms |
| 结构验证 | < 0.5ms |
| SVG文本检测 | < 1ms |
| **快速检测总计** | **< 3ms** |

| **深度检测总计** | **< 60ms** |

### 测试场景

**场景1：格式匹配——扩展名与魔数一致**
文件photo.jpg，文件头FF D8 FF→actualFormat.mime为image/jpeg→mismatch为false→integrity为valid。

**场景2：格式不匹配——扩展名与魔数不一致**
文件image.png，文件头FF D8 FF（实际是JPEG）→actualFormat.mime为image/jpeg→declaredFormat.extension为png→mismatch为true→warnings包含"扩展名与实际格式不匹配"。

**场景3：损坏的PNG文件**
头部正确但数据不完整→quickDetect返回integrity: valid→deepDetect返回corrupted: true→integrity变为corrupted。

**场景4：SVG文件检测**
文件icon.svg，文本内容`<svg xmlns="...">...</svg>`→actualFormat.mime为image/svg+xml→browserSupported为true。

**场景5：不支持的格式——提醒用户**
文件scan.tiff（TIFF LE魔数49 49 2A 00）→actualFormat.browserSupported为false→warnings包含"浏览器兼容性有限"。

### 设计决策记录

**D-01：为什么只读前256字节而非整个文件头？**
大多数图片格式的魔数和关键结构信息位于文件前256字节内。JPEG的SOI marker在前2字节，PNG的IHDR chunk在前33字节。读取256字节覆盖所有已知格式的头部检测需求，且不随文件大小增长。

**D-02：为什么SVG单独检测而非纳入魔数表？**
SVG是基于XML的文本格式，没有二进制魔数。部分SVG以XML声明开头，部分以`<svg`开头。使用正则搜索前100字节是最可靠的检测方式。

**D-03：为什么createImageBitmap解码作为最终验证？**
即使魔数和文件结构都正确，图片数据仍可能因传输损坏、编码错误而无法解码。createImageBitmap是浏览器最轻量的图片解码API，解码失败会抛出异常。这是最终的、最可靠的完整性验证。

## M06-10: 颜色空间转换

### 背景与问题

不同使用场景需要不同颜色空间：网页显示用sRGB、印刷用CMYK、设计调色用HSL/HSV、专业校色用Lab。Canvas 2D API仅支持sRGB，通过数学转换矩阵在软件层面实现跨颜色空间转换。

**影响范围**：印刷颜色偏差（高，屏幕与印刷不一致）、无法获取精确HSL值（中）、颜色配置文件被忽略（中）、色域信息丢失（中）。

### 核心设计决策

| 决策 | 选项A | 选项B | 选项C | 选择 | 理由 |
|------|--------|--------|--------|------|------|
| 实现层级 | 纯JS数学转换 | WebGL着色器 | WASM | 纯JS | 简单+精度够 |
| 色域警告 | 像素叠加标记 | 区域高亮+统计 | 仅统计摘要 | 区域高亮+统计 | 直观+全面 |
| ICC Profile | 读取并保留 | 忽略 | 检测+用户选择 | 检测+用户选择 | 灵活+透明 |
| 精度策略 | 整数量化 | 浮点保留 | 内部浮点+输出量化 | 内部浮点+输出量化 | 精度+兼容 |

### 转换管道

```
图片加载 → Canvas → ImageData
→ RGB归一化（0-255 → 0.0-1.0）
→ 目标颜色空间转换：
  ├── RGB ↔ HSL（H∈[0,360] S∈[0,1] L∈[0,1]）
  ├── RGB ↔ HSV（H∈[0,360] S∈[0,1] V∈[0,1]）
  ├── RGB ↔ CMYK（K=min(C,M,Y) + UCR）
  └── RGB ↔ Lab（sRGB线性化→XYZ D65→Lab L∈[0,100] a,b∈[-128,127]）
→ 显示（反向转换回RGB→Canvas渲染）/ 数值查看 / 色域警告（超色域像素叠加蒙层）
```

### 关键转换矩阵

**sRGB线性化**：
```
linearize(c) = c ≤ 0.04045 ? c/12.92 : ((c+0.055)/1.055)^2.4
```

**sRGB→XYZ (D65)**：
```
X = R*0.4124564 + G*0.3575761 + B*0.1804375
Y = R*0.2126729 + G*0.7151522 + B*0.0721750
Z = R*0.0193339 + G*0.1191920 + B*0.9503041
```

**XYZ→Lab (D65参考白点)**：
```
f(t) = t > 0.008856 ? cbrt(t) : 7.787*t + 16/116
L = 116*f(Y/Yn) - 16
a = 500*(f(X/Xn) - f(Y/Yn))
b = 200*(f(Y/Yn) - f(Z/Zn))
```

### CMYK色域警告

```
逐像素RGB→CMYK转换 → 检查C/M/Y/K ∈ [0,1]
→ 超出范围标记为"超出CMYK色域"
→ 在原图上叠加半透明红色蒙层覆盖超色域像素
→ 显示"X%的像素无法在CMYK中精确呈现"
```

### 性能指标

| 转换路径 | 单像素耗时 | 4MP图片逐像素耗时 | 分片优化后（不阻塞UI） |
|---------|-----------|-----------------|---------------------|
| RGB→HSL | ~0.5μs | ~200ms | ~300ms |
| RGB→Lab | ~2.0μs | ~800ms | ~1.2s |
| RGB→CMYK | ~0.2μs | ~80ms | ~120ms |
| 色域检测 | ~0.4μs | ~160ms | ~250ms |

分片优化使用requestAnimationFrame，每帧处理50K像素，UI保持响应。

### 测试场景

**场景1：RGB↔HSL往返转换**
RGB(0.5, 0.2, 0.8) → HSL → RGB → 输出每个通道误差<0.001。

**场景2：CMYK色域外的RGB颜色**
RGB(0.0, 1.0, 0.0)纯绿色 → isOutOfCmykGamut返回true → RGB→CMYK得到的C通道>1或<0。

**场景3：Lab空间感知均匀性**
RGB红色(1.0,0.0,0.0)和蓝色(0.0,0.0,1.0) → 均转换为Lab → L值均>0 → a和b通道分别位于正负方向（红→+a, 蓝→-b）。

**场景4：图片像素级HSL转换**
100×100纯色图片（R=100,G=150,B=200） → convertImageData目标HSL → 所有像素HSL值一致 → H∈[200,220]（蓝色调）→ S>0.2 → L∈[0.5,0.7]。

**场景5：色域蒙层覆盖率**
包含大量霓虹色的图片 → 生成色域警告蒙层 → 超色域像素百分比>10% → 蒙层红色区域可见。

**场景6：ICC Profile检测**
嵌入Display P3 Profile的图片 → ICC检测识别为"Display P3" → 非标准sRGB → 提示"建议转换为sRGB"。

### 设计决策记录

**D-01：为什么使用D65标准光源作为XYZ转换的白点？**
D65（6504K）是sRGB和大多数现代显示器的标准白点。使用D65与浏览器Canvas 2D的sRGB默认行为一致。使用D50（印刷标准）需要额外的色适应矩阵（Bradford变换），增加复杂度和误差。

**D-02：为什么CMYK使用简单的CMY→K公式而非ICC-based分色？**
标准印刷使用ICC Profile定义CMYK分色曲线，不同纸张/油墨组合的Profile不同。简单公式仅作为近似。YiPet提供快速预览和色域警告，非替代专业印前软件。

**D-03：为什么内部使用0.0-1.0归一化而非0-255整数？**
RGB 0-255是显示相关的编码，而颜色空间转换公式设计为0.0-1.0范围。内部归一化避免每次转换都需要/255和*255的散乱代码。HSL的S/L、HSV的S/V、CMYK的C/M/Y/K自然范围都是0-1。
