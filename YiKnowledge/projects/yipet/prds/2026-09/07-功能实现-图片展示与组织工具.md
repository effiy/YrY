## 公共基础设施

### 图层管理模型

图片装饰类工具（贴纸/文字/框架/水印）共享逻辑坐标图层模型：每个装饰元素是一个对象 `{id, transform, opacity, zIndex, ...}`，渲染时按zIndex排序依次绘制到Canvas，编辑时修改图层对象，导出时合成所有图层。

### 变换交互模式

贴纸/文字/水印类功能共享四角手柄变换交互：四角缩放手柄 + 顶边旋转手柄 + 主体拖拽。以中心点为锚点进行缩放和旋转，符合Photoshop/Canva/Figma的通用做法。

### EXIF读写基础设施

管理类工具（评分/关键词/地理标记/时间戳）共享piexifjs EXIF读写能力，支持XMP dc:subject、lr:hierarchicalSubject、GPS坐标、DateTimeOriginal/OffsetTimeOriginal等标签。

### Canvas像素操作基础设施

调整类工具（模糊/锐化/降噪）共享高斯模糊分离卷积算法、Canvas getImageData/putImageData操作、Web Worker大图异步处理。

# A. 图片装饰 (7个子功能)

## A01: 图片添加贴纸

### 背景与问题

用户在社交媒体分享截图或图片时需要贴纸/Emoji装饰、敏感信息遮挡、品牌水印。需要一个带图层管理的贴纸叠加系统。

**影响范围**：无贴纸装饰能力（高）、敏感信息遮挡方式有限（中）、品牌水印无法添加（中）、无Emoji叠加（高）、多贴纸层叠不可控（低）。

### 核心设计决策

| 决策 | 选项A | 选项B | 选项C | 选择 | 理由 |
|------|--------|--------|--------|------|------|
| 贴纸库存储 | 内置本地贴纸包（精选30个~60KB） | CDN远程贴纸库 | 用户上传自定义贴纸 | 内置+CDN可选+用户上传 | 离线可用+丰富性+个性化 |
| Emoji实现 | Canvas fillText渲染 | Emoji→Image预渲染 | Twemoji SVG | fillText渲染 | 简单+矢量无损+零额外资源 |
| 变换交互 | 四角手柄（缩放/旋转）+主体拖拽 | 滑块面板数值调节 | 纯手势（移动端） | 四角手柄（主力）+面板微调 | 精确+类似主流编辑器 |
| 图层管理 | 图层面板列表拖拽排序 | 右键菜单 | 无管理（后加在上层） | 图层面板+右键菜单 | 直观+灵活 |

### 数据模型

```typescript
interface StickerObject {
  id: string; assetId: string;
  type: 'sticker' | 'emoji' | 'custom';
  emojiChar?: string; emojiFontSize?: number;
  transform: {
    x: number; y: number;    // 中心点坐标（图片坐标）
    scaleX: number; scaleY: number;  // 缩放0.1-5.0
    rotation: number;         // 旋转角度0-360
    width: number; height: number;   // 贴纸自然尺寸
  };
  opacity: number;            // 0.0-1.0
  zIndex: number;             // 图层顺序，数字越大越靠上
}

interface StickerAsset {
  id: string; name: string; category: string;
  source: 'builtin' | 'remote' | 'custom';
  url?: string; dataUrl?: string;
  tags: string[];
}
```

### 贴纸渲染流程

```
选择贴纸 → StickerManager.addSticker(asset, centerPosition)
→ 创建StickerObject: transform=identity, opacity=1.0
→ StickerRenderer按zIndex排序，从底到顶逐层drawImage
→ 每个贴纸应用ctx.setTransform（平移+旋转+缩放）
→ globalAlpha应用透明度
→ 选中贴纸显示四角缩放手柄+顶边旋转手柄+虚线边框
→ 命中检测：拖拽检测旋转后的AABB
```

### 内置贴纸库

5个分类，30个精选贴纸：形状（6个）、箭头（6个）、装饰（8个）、遮罩（5个）、Emoji增强（5个）。每个贴纸64×64到128×128，TinyPNG压缩后总体积~60KB。层叠覆盖最常用场景。

### 3种Emoji渲染模式

| 模式 | 实现 | 适用 |
|------|------|------|
| fillText（默认） | ctx.fillText(emoji, x, y) | 日常使用，矢量缩放不失真 |
| 预渲染图片 | 离屏Canvas→Image→drawImage | 追求跨平台外观一致性 |
| 自定义图片 | 用户上传PNG | 完全个性化 |

### 测试场景

**场景1：添加内置贴纸**
打开贴纸库→点击"箭头"分类→选择红色箭头贴纸→箭头贴纸出现在图片中央→默认大小，透明度100%→保持原始宽高比不变形。

**场景2：贴纸缩放和旋转**
点击贴纸→选中状态显示四角缩放手柄和顶边旋转手柄→拖拽右下角缩放手柄向外拉→等比例放大→拖拽旋转手柄顺时针45度→贴纸绕中心旋转45度。

**场景3：贴纸透明度**
属性面板拖动透明度滑块到50%→贴纸变为半透明→下方内容隐约可见→0%完全透明但仍在图层列表中→100%完全不透明。

**场景4：多贴纸图层管理**
3个贴纸A（最先加）、B、C（最后加）→在图层面板中将A拖到C上方→A移到顶层→右键B选择"置底"→B移动到最底层。

**场景5：Emoji贴纸**
点击"Emoji"标签→打开Emoji选择器→搜索"笑"→选择"哈哈"→Emoji出现在图片中央，默认字号48px→放大到200%→保持清晰（fillText矢量渲染）。

### 风险与缓解

| 风险 | 缓解 |
|------|------|
| Emoji不同OS外观不一致 | 属性面板提示"外观因操作系统而异"，可选预渲染为图片 |
| 内置贴纸增加扩展包体积 | 精选30个，使用SVG路径或压缩PNG，总大小<100KB |
| 贴纸手柄在小贴纸上重叠误操作 | 贴纸<30px时隐藏旋转手柄，仅保留缩放手柄和拖拽 |

### 设计决策记录

**D-01：为什么贴纸变换以"中心点"为锚点而非"左上角"？**
以中心为锚点的缩放和旋转在视觉上最自然---贴纸从中心向外缩放，绕视觉中心旋转。主流图片编辑软件（Photoshop/Canva/Figma）的通用做法。

**D-02：为什么Emoji贴纸使用fillText而非预渲染图片？**
fillText渲染的Emoji是矢量的---放大后不失真---且零额外存储。缺点各OS Emoji外观不同。追求一致外观的用户可选"预渲染模式"将Emoji转为固定外观的图片再叠加。

## A02: 图片添加贴纸文字

### 背景与问题

基础文字工具（YP-09-217）仅支持纯文本覆盖。用户在社交媒体场景中需要气泡对话、Meme文字、漫画风格、渐变文字等装饰性文字效果。

### 4种贴纸风格

| 风格 | 实现方式 | 核心数据 | 适用场景 |
|------|----------|----------|----------|
| 气泡文字 | Canvas路径绘制圆角矩形+小三角 | bubble.type: speech/thought/shout | 模拟聊天截图 |
| Meme文字 | Impact字体+黑色描边+顶部/底部半透明背景条 | meme.position: top/bottom | 表情包制作 |
| 漫画文字 | 呐喊气泡（锯齿状边缘） | 同气泡shout类型 | 漫画风格标注 |
| 渐变文字 | createLinearGradient/createRadialGradient | gradient.type: linear/radial | 视觉冲击力 |

### 3种气泡类型详解

**对话气泡（speech）**：`ctx.roundRect(x, y, w, h, r)` 圆角矩形 + 小三角（left/right/top/bottom四方向）。小三角使用moveTo+lineTo+closePath。最常用的气泡类型。

**思考气泡（thought）**：圆角矩形 + 3个圆圈（从大气泡底部向下延伸，逐渐变小）。使用arc绘制圆圈。模拟漫画思考效果。

**呐喊气泡（shout）**：锯齿状边缘代替平滑圆角。顶部有8个棘刺（spikeHeight=8px），模拟大声喊叫的视觉效果。

### 文字效果叠加

```
渲染一个贴纸文字时：
1. ctx.save → 应用旋转
2. ctx.font设置 → ctx.measureText测量宽度
3. shadow效果（shadowBlur/shadowColor/shadowOffset）→ fillText
4. stroke效果（strokeStyle/lineWidth/lineJoin='round'）→ strokeText
5. 渐变填充（createLinearGradient/createRadialGradient）→ fillText
6. ctx.restore
```

### Meme文字默认配置

```typescript
const MEME_DEFAULTS = {
  fontFamily: 'Impact, Arial Black, sans-serif', // 字体栈降级
  fontSize: 48,
  fontWeight: 'bold',
  fill: '#FFFFFF',
  stroke: { enabled: true, width: 3, color: '#000000' },
  textTransform: 'uppercase', // 自动大写
};
```

### 气泡文字自动换行

使用ctx.measureText()精确测量每行宽度。当累计宽度超过maxWidth时换行，支持中英文混排、手动`\n`换行符、整词换行（英文单词不截断）。

### 拖拽文字时实时预览优化策略

拖拽过程中：降精度渲染（取消投影/描边效果，仅纯色填充），保持60fps。拖拽结束后：全精度渲染（恢复所有效果）。视觉差异在拖拽过程中不可感知。

### 测试场景

**场景1：对话气泡渲染**
添加对话气泡文字"Hello World"，气泡类型speech，小三角位置left→渲染圆角矩形气泡背景→左下角有小三角指向左侧→文字居中显示在气泡内。

**场景2：Meme文字生成**
选择Meme风格，输入"WHEN YOU FINALLY"，位置top→文字自动转为大写→在图片顶部居中→半透明黑色背景条→白色填充+黑色描边。

**场景3：渐变文字效果**
选择渐变风格，线性渐变（红→橙→黄），角度90°→文字渲染为从上到下的红橙黄渐变→渐变起止点对齐文字范围。

**场景4：文字描边和投影**
启用描边（宽度3px，颜色#000）和投影（偏移2x2px，模糊4px）→文字有3px黑色描边→2x2px偏移投影，模糊半径4px。

**场景5：气泡文字自动换行**
气泡文字内容为长句→气泡最大宽度200px→文字在200px处自动换行→气泡高度随行数增加→measureText精确测量中英文字符宽度。

**场景6：导出含贴纸文字的图片**
已添加贴纸文字的图片→导出为PNG→导出图片包含完整贴纸文字效果→气泡背景/渐变/描边/投影均正确渲染。

### 风险与缓解

| 风险 | 缓解 |
|------|------|
| Impact字体不可用 | 字体栈降级：Impact→Arial Black→sans-serif |
| 中英文混排宽度计算不准 | 使用ctx.measureText()精确测量，不依赖字符数估算 |
| 长文本气泡溢出 | 气泡最大宽度限制，超出自动换行 |
| 渐变坐标计算错误 | 渐变坐标基于文字实际渲染位置，非Canvas原点 |

## A03: 图片添加框架

### 背景与问题

用户需要为截图、照片添加装饰性边框（拍立得、相框、胶片、数字框架）来增强视觉效果。当前仅有基础颜色边框（YP-09-222），缺乏装饰性增强能力。

### 4种边框风格详细设计

**拍立得（Polaroid）**：
- 底部留白比例0.25（图片高度的25%为白色底部区域）
- 白色边框20px + 投影（offsetX=2, offsetY=4, blur=8, rgba(0,0,0,0.3)）
- 适合模拟实体照片效果

**相框（Picture Frame）**：
- 木色边框40px（#8B4513）+ 圆角4px
- 卡纸垫20px（#FAFAFA，白色内框）
- 投影（offsetX=3, offsetY=6, blur=12, rgba(0,0,0,0.4)）
- 适合模拟装裱效果

**胶片（Film Strip）**：
- 黑色边框16px（#1A1A1A）
- 左右两侧齿孔（白色8×8px方块，间距16px）
- 无投影
- 适合模拟胶片摄影效果

**数字框架（Digital Frame）**：
- 深色边框30px（#333333）+ 圆角12px
- 屏幕反光效果（可选）
- 投影（offsetX=0, offsetY=8, blur=20）
- 适合模拟设备截图展示

### Canvas渲染管线

```
原始图片 → 计算新画布尺寸（考虑边框宽度×2 + 卡纸垫宽度×2 + 投影偏移 + 底部留白）
→ 1. 绘制投影（ctx.shadowBlur/shadowColor/shadowOffset → fillRect）
→ 2. 绘制卡纸垫（mat.color填充）
→ 3. 绘制边框（config.color填充，支持圆角roundRect）
→ 4. 绘制图片（ctx.putImageData）
→ 5. 绘制特殊元素（拍立得底部留白/胶片齿孔/屏幕反光）
```

### 胶片齿孔绘制

```typescript
private drawSprockets(ctx, imgX, imgY, imgW, imgH, filmStrip) {
  const { sprocketSize, sprocketSpacing } = filmStrip;
  ctx.fillStyle = '#FFFFFF';
  for (let y = imgY; y < imgY + imgH; y += sprocketSpacing) {
    ctx.fillRect(imgX - sprocketSize - 4, y + sprocketSpacing/2, sprocketSize, sprocketSize); // 左侧齿孔
    ctx.fillRect(imgX + imgW + 4, y + sprocketSpacing/2, sprocketSize, sprocketSize); // 右侧齿孔
  }
}
```

### 关键性能

- 800×600拍立得边框渲染 < 30ms
- 4K图片边框渲染 < 300ms（使用OffscreenCanvas离屏渲染）
- 参数滑块拖拽实时预览 < 16ms（60fps，debounced）

### 测试场景

**场景1：拍立得边框渲染**
800×600图片→拍立得风格，底部留白0.25→输出图片高度=800+边框宽度×2+800×0.25+投影偏移→底部白色留白区域→图片居中显示。

**场景2：相框+卡纸垫渲染**
1024×768图片→相框风格，边框40px，卡纸垫20px→输出图片在图片外有20px卡纸垫（#FAFAFA）→卡纸垫外有40px边框（#8B4513）→有投影效果。

**场景3：胶片齿孔渲染**
600×400图片→胶片风格，齿孔8px，间距16px→左右两侧白色齿孔→齿孔数量=图片高度/16（向上取整）→尺寸8×8px。

**场景4：基础边框兼容性**
使用新边框系统选择basic风格→渲染结果应与原有基础边框（YP-09-222）一致→原有API仍可正常使用。

### 设计决策记录

**D-01：边框宽度上限。** 200px。4K图片上约占5%宽度，视觉合理。更大边框导致导出图片尺寸过大。

**D-02：拍立得底部留白是否支持添加文字。** 仅空白（本需求）。文字添加由贴纸文字功能覆盖，避免功能重叠。

**D-03：边框渲染线程。** OffscreenCanvas主线程。渲染时间<300ms，不需要Web Worker。OffscreenCanvas已提供足够离屏渲染能力。

## A04: 图片添加文字

### 背景与问题

用户在图片上需要添加文字说明（截图标注、水印、标题、注释），支持多图层独立管理和拖拽重定位。YiPet已有截图和裁剪能力，但缺少文字叠加能力。

### 核心设计决策

| 决策 | 选项A | 选项B | 选项C | 选择 | 理由 |
|------|--------|--------|--------|------|------|
| 图层模型 | 像素级（直接绘制到Canvas） | 逻辑坐标（维护图层对象） | HTML overlay（绝对定位div） | 逻辑坐标 | 可编辑+导出一致 |
| 输入方式 | 内联编辑（contentEditable） | 属性面板输入 | 弹窗输入 | 内联+面板混合 | 空间准确+属性灵活 |
| 描边/阴影 | Canvas strokeText+shadowBlur | CSS text-shadow | SVG text嵌入Canvas | Canvas API | 标准+高性能 |
| 图层管理 | 扁平数组+z-order排序 | 树形结构（组嵌套） | z-index数值排序 | 扁平数组+z-order | 够用+简洁 |

### 文字图层完整属性

```typescript
interface TextLayer {
  id: string;
  text: string;           // 支持\n换行
  x: number; y: number;   // 文字锚点
  zIndex: number;
  visible: boolean;
  fontFamily: string;     // 如'Arial, sans-serif'
  fontSize: number;       // px
  fontWeight: 'normal' | 'bold';
  fontStyle: 'normal' | 'italic';
  color: string;          // 填充色HEX
  opacity: number;        // 0-1
  strokeColor: string;    // 描边色
  strokeWidth: number;    // 0=无描边
  shadowColor: string;
  shadowBlur: number;     // 0=无阴影
  shadowOffsetX: number;
  shadowOffsetY: number;
  textAlign: 'left' | 'center' | 'right';
  maxWidth: number;       // 0=不限制自动换行
}
```

### 文字渲染核心

```
渲染单个文字图层：
1. ctx.save()
2. ctx.font = `${style} ${weight} ${size}px ${family}`
3. ctx.textAlign / ctx.textBaseline = 'top'
4. ctx.globalAlpha = opacity
5. shadow效果：ctx.shadowBlur/shadowColor/shadowOffset
6. 文字换行：wrapText(text, maxWidth, fontSize) → lines[]
7. for each line：
   a. strokeText(lines[i], x, lineY)（描边在填充之前）
   b. fillText(lines[i], x, lineY)（填充覆盖描边内部）
8. ctx.restore()
```

### 文字自动换行

wrapText使用ctx.measureText()逐字测量宽度。超出maxWidth时换行。同时支持手动`\n`换行符。英文单词不截断（整词换行）。中文字符可在任意位置换行。

### 关键性能

| 操作 | 1图层 | 5图层 | 10图层 |
|------|-------|-------|--------|
| 图层渲染 | < 5ms | < 15ms | < 25ms |
| 属性修改→重绘 | < 5ms | < 15ms | < 25ms |
| 拖拽移动图层 | < 3ms | < 10ms | < 15ms |
| 导出PNG | < 50ms | < 50ms | < 50ms |

### 设计决策记录

**D-01：为什么选择内联编辑而非纯属性面板输入？**
纯属性面板输入需要用户在面板中打字然后对照Canvas位置。对于空间敏感的文字（需要在精确位置标注），内联编辑（在Canvas位置创建contentEditable div）所见即所得，大幅减少位置调整次数。

**D-02：为什么描边使用strokeText而非绘制多次偏移fillText？**
多次偏移fillText（上下左右各绘制一次）性能差（4次fillText调用），且复杂文字（含阴影）绘制次数翻倍。strokeText是Canvas标准API，一次调用完成描边，lineJoin: 'round'确保边角圆滑。

**D-03：为什么图层管理用扁平数组而非树形？**
文字标注不需要分组嵌套，标注之间是平级关系。树形结构增加30%代码量（嵌套渲染、选择逻辑、z-order递归计算）。扁平数组+zIndex排序满足所有需求。

## A05: 图片添加倒影

### 背景与问题

倒影效果是产品展示、电商图片中广泛使用的视觉增强手段。通过Canvas实现镜像倒影、透视倒影和地板反射。

### 3种倒影类型

**镜像倒影（Mirror）**：垂直翻转 + 渐变蒙版。原图绘制在上方，翻转图绘制在下方，通过destination-in合成模式应用渐变蒙版从倒影顶部（不透明）到底部（完全透明）。

**透视倒影（Perspective）**：垂直压缩 + 渐变蒙版。在y轴方向压缩倒影，模拟从上方俯视地板的效果。使用Canvas 2D transform近似3D透视。

**地板反射（Floor）**：模糊 + 强渐变。倒影区域从顶部到底部逐渐模糊，模拟光线在粗糙地板上的散射反射。

### 渐变曲线

| 曲线 | 说明 | 适用 |
|------|------|------|
| linear | 均匀过渡 | 镜面反射 |
| easeOut | 顶部长时间保持高不透明度→中后段快速衰减 | 高反射率镜面（Apple风格） |
| easeIn | 顶部快速衰减→底部长时间低不透明度 | 粗糙表面反射 |
| easeInOut | 两端缓中间快 | 通用平滑过渡 |
| custom | 自定义贝塞尔停止点 | 高级调整 |

### Canvas渲染核心

```
1. 计算画布大小 = 原图高度 + 偏移 + 倒影高度 + 边距
2. 绘制背景色
3. 绘制原图（顶部）
4. 创建倒影：
   ctx.save()
   ctx.translate(padding, padding + imgH + offset + reflectionH)
   ctx.scale(1, -1)  // 垂直翻转
   ctx.drawImage(source, 0, imgH-reflectionH, imgW, reflectionH, 0, 0, imgW, reflectionH)
   ctx.restore()
5. 渐变蒙版：
   const gradient = ctx.createLinearGradient(0, y, 0, y + h)
   gradient.addColorStop(0, `rgba(255,255,255,${topOpacity})`)
   gradient.addColorStop(1, 'rgba(255,255,255,0)')
   ctx.globalCompositeOperation = 'destination-in'
   ctx.fillStyle = gradient
   ctx.fillRect(x, y, w, h)
```

### 测试场景

**场景1：镜像倒影基础功能**
导入800×600产品图→选择"镜像倒影"→默认参数（高度40%，不透明度50%，偏移5px，渐变线性）→预览显示原图在上，倒影在下→倒影高度为原图的40%（240px）→倒影和原图间5px间距→从上到下逐渐透明。

**场景2：调整倒影高度和不透明度**
当前高度40%→调整滑块到70%→倒影区域变长为420px→调整不透明度到80%→倒影顶部更不透明→预览实时更新。

**场景3：渐变曲线切换**
从"线性"切换到"缓出"→倒影顶部较长时间高不透明度→中后段快速衰减。切换到"缓入"→顶部快速衰减→底部长时间低不透明度。

**场景4：透视倒影——3D地板效果**
切换到"透视倒影"→透视角度20度→消失点Y=0.7→倒影在垂直方向被压缩→底部比顶部窄→形成透视收敛效果→有空间深度感。

**场景5：地板反射——模糊效果**
切换到"地板反射"→模糊半径8px，高度50%，不透明度40%→倒影从顶部到底部逐渐模糊→模拟粗糙地板散射反射→比镜面倒影更真实。

**场景6：背景色+导出**
预览中背景为透明→设置背景为纯色#F5F5F5→倒影渐变终点从透明变为融入浅灰背景→导出为JPEG质量95%→背景浅灰色→可直接用于网站。

### 设计决策记录

**D-01：为什么使用destination-in合成模式而非逐像素Alpha修改？**
destination-in利用Canvas的GPU加速合成，性能优异且效果一致。逐像素操作（遍历ImageData.data）在大图上性能差，CPU密集且阻塞主线程。destination-in一行渐变代码即可实现完整效果。

**D-02：为什么导出PNG透明背景是默认而非白底？**
透明背景PNG具有最大灵活性，用户可将其放置在任意背景上，倒影效果依然正确显示。白底JPEG虽文件更小但丧失灵活性。符合"工具提供最大灵活性"的设计理念。

## A07: 图片马赛克拼贴

### 背景与问题

用数百/数千张小图片作为"瓷砖"拼接成一幅大图的视觉效果。是YP-09-216像素化马赛克的照片拼贴增强版。远看是完整图像，近看每块"瓷砖"都是独立小图片。

### 核心算法流程

```
目标图片 → 按gridColumns×gridRows划分网格
→ 遍历每个网格：计算该网格区域的RGB平均色
→ 从瓷砖图库中查找最匹配的瓷砖（颜色匹配）
→ 绘制最佳匹配瓷砖到对应位置
→ 分块渲染（每块16×16网格）→ setTimeout让出主线程
```

### 颜色匹配算法

**RGB欧氏距离** + **颜色桶索引（4×4×4=64桶）**加速：
```typescript
// 构建颜色索引——将RGB量化到64个桶
const bucketR = Math.floor(tile.averageColor.r / 64); // 0-3
const bucketG = Math.floor(tile.averageColor.g / 64); // 0-3
const bucketB = Math.floor(tile.averageColor.b / 64); // 0-3
const bucketKey = (bucketR << 4) | (bucketG << 2) | bucketB; // 0-63

// 查找时搜索当前桶+相邻27个桶的候选瓷砖
for (let dr = -1; dr <= 1; dr++)
  for (let dg = -1; dg <= 1; dg++)
    for (let db = -1; db <= 1; db++)
      candidates.push(...colorIndex.get(getNeighborKey(dr, dg, db)));

// 计算最佳匹配——RGB欧氏距离平方
const bestTile = candidates.reduce((best, tile) =>
  colorDistance(target, tile.avgColor) < colorDistance(target, best.avgColor) ? tile : best
);
```

### 抖动策略

为避免大片同色区域重复使用同一瓷砖，添加随机抖动：
```typescript
const jitter = (Math.random() - 0.5) * 2 * jitterAmount * 255;
searchColor = {
  r: clamp(targetColor.r + jitter, 0, 255),
  g: clamp(targetColor.g + jitter, 0, 255),
  b: clamp(targetColor.b + jitter, 0, 255),
};
```

### 核心设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 颜色匹配 | RGB欧氏距离+颜色桶索引 | 性能最优，1000瓷砖<1ms |
| 图库来源 | 内置50张+用户上传 | 开箱即用+个性化 |
| 大图导出 | 分块渲染（2048×2048块） | 内存可控 |
| 重复策略 | 允许重复+抖动 | 图库小时避免颜色匹配质量下降 |
| 缩略图尺寸 | 50×50 | 颜色信息足够（2500像素），存储占用小（~2.5KB/张） |

### 关键性能

| 操作 | 耗时 |
|------|------|
| 瓷砖缩略图生成（单张） | < 10ms |
| 颜色匹配（单次，1000瓷砖） | < 1ms |
| 40×30网格（1200格） | < 500ms |
| 100×75网格（7500格） | < 2s |
| 高分辨率导出（4x缩放） | < 5s |

### 测试场景

**场景1：基本马赛克生成**
400×300目标图片，图库50张内置瓷砖→网格40×30，瓷砖20px→生成800×600马赛克图片→每个网格被一张瓷砖填充。

**场景2：颜色匹配精度**
目标图片含红色区域和蓝色区域→红色区域瓷砖主要为红色系→蓝色区域瓷砖主要为蓝色系。

**场景3：瓷砖图库管理**
用户上传10张自定义瓷砖→图库共60张（50内置+10自定义）→每张自动生成缩略图和平均色。

**场景4：抖动策略效果**
图库中红色系仅3张→使用jittered策略（jitterAmount=0.2）→相邻网格使用不同红色系瓷砖→不出现同一瓷砖连续重复>3次。

### 风险与缓解

| 风险 | 缓解 |
|------|------|
| 大图库颜色匹配性能瓶颈 | 颜色桶索引64桶+预计算平均色，1000瓷砖<1ms |
| IndexedDB图库存储超限 | 瓷砖缩略图限制50×50px，单张<10KB |
| 大图导出内存溢出 | 分块渲染2048×2048px块，拼接后释放 |

# B. 图片调整 (6个子功能)

## B01: 图片马赛克工具

### 背景与问题

用户在分享截图前需要遮盖敏感信息（手机号、身份证号、人脸、金额）。提供画笔式涂抹打码，支持马赛克和模糊两种模式。

### 核心设计决策

| 决策 | 选项A | 选项B | 选项C | 选择 | 理由 |
|------|--------|--------|--------|------|------|
| 马赛克实现 | 像素块均值（getImageData→分块求平均→putImageData） | Canvas scale缩小再放大 | CSS image-rendering: pixelated | 像素块均值 | 精确+可逆（支持撤销） |
| 画笔模型 | 圆形画笔 | 矩形画笔 | 自由套索 | 圆形+矩形双模式 | 覆盖快速+精确场景 |
| 撤销策略 | 全量快照（每步几MB） | 增量操作记录（重放） | 区域快照（仅保存受影响区域） | 区域快照 | 内存高效+快速 |
| 模糊/马赛克共存 | 互斥 | 各自独立 | 组合 | 各自独立 | 不同区域可用不同方式 |

### 马赛克像素块均值算法

```
获取画笔覆盖区域 → 按blockSize分块
→ 计算每块RGB平均值：
  for each block:
    sumR += pixelR; sumG += pixelG; sumB += pixelB; count++
  avgColor = { r: sumR/count, g: sumG/count, b: sumB/count }
→ 将块内所有像素设为avgColor
→ putImageData更新Canvas
→ 保存受影响区域的原始像素到历史栈（RegionSnapshot）
```

### 5个粒度预设

| 预设 | blockSize | 场景 |
|------|-----------|------|
| 极细 | 4px | 小文字/手机号后4位 |
| 细 | 8px | 普通文本/姓名 |
| 中 | 16px | 人脸/证件号 |
| 粗 | 24px | 大面积遮盖 |
| 极粗 | 32px | 完全不可辨识 |

### 模糊替代方案

| 预设 | 模糊半径 | 场景 |
|------|---------|------|
| 轻微 | 4px | 人脸轮廓模糊 |
| 中等 | 8px | 文档排版保留但不可读 |
| 重度 | 16px | 大面积模糊 |
| 完全 | 24px | 完全不可辨识 |

### 撤销/重做历史栈

```
存储结构：HistoryEntry[] = [{ snapshots: RegionSnapshot[], mode, config }]
栈上限：50步
超出处理：合并最早两个条目（一次撤销恢复两步内容）
currentIndex：指向当前状态，推入新条目时截断"未来"的redo条目

撤销操作：Pop currentIndex条目 → Restore originalPixels到Canvas → currentIndex--
重做操作：currentIndex++ → Re-apply mosaic/blur到该区域
```

### 关键性能

| 操作 | 800×600 | 3840×2160 |

### 设计决策记录

**D-01：为什么马赛克采用像素块均值而非Canvas scale方式？**
Canvas scale方式（drawImage缩小到1/10再放大）由GPU硬件加速，性能极佳。但无法实现局部马赛克（只能整图），原始像素丢失无法撤销，缩小再放大的插值算法在不同浏览器中不一致。像素块均值精确可控+支持局部+支持撤销。

**D-02：为什么历史栈上限50步合并最早条目而非阻止新操作？**
如果阻止新操作，用户的打码工作会丢失当前状态。合并最早条目虽然可能使早期的2步合并为1步（撤销时一次恢复两步的内容），但这种退化对用户影响最小，且保证了打码操作可以继续。

## B02: 图片网格裁剪

### 背景与问题

将一张大图分割成多个网格块，用于Instagram九宫格发布、拼图制作、分区标注。手动裁剪9个格子需要严格对齐，稍有偏差就出现接缝或重叠。

### 非整数像素处理——余数均匀分配

```
baseCellW = floor(imgWidth / columns)
remainderW = imgWidth % columns
→ 前remainderW列宽度 = baseCellW + 1
→ 后(columns-remainderW)列宽度 = baseCellW
→ 确保所有格子宽高和 = 原图宽高，无像素丢失
```

### 核心计算算法

```typescript
function calculateGrid(imgWidth, imgHeight, config): GridSplitResult {
  const baseCellW = Math.floor(imgWidth / config.columns);
  const baseCellH = Math.floor(imgHeight / config.rows);
  const remainderW = imgWidth % config.columns;
  const remainderH = imgHeight % config.rows;
  const cells = [];
  for (let row = 0; row < config.rows; row++) {
    const cellH = baseCellH + (row < remainderH ? 1 : 0);
    const y = row * baseCellH + Math.min(row, remainderH);
    for (let col = 0; col < config.columns; col++) {
      const cellW = baseCellW + (col < remainderW ? 1 : 0);
      const x = col * baseCellW + Math.min(col, remainderW);
      cells.push({ row, col, x, y, width: cellW, height: cellH, index });
    }
  }
  return { cells, remainderX: remainderW, remainderY: remainderH };
}
```

### 核心设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 分割实现 | 自动等分+Canvas drawImage切片 | 精度最高，像素完美对齐 |
| 非整数处理 | 均匀分配 | 视觉差异最小 |
| 导出方式 | ZIP打包（JSZip）+ 单格导出 | 减少下载弹窗次数 |
| 命名规则 | image_r{row}c{col}.png（行号列号从0开始） | 自然排序友好 |
| 行列限制 | 最大20×20=400格 | 防止恶意输入导致卡死 |

### 可拖拽网格线调整

用户可拖拽网格线微调分割位置。网格线热区8px，不与图片平移/缩放交互冲突。拖拽范围受相邻网格线约束（不越过相邻线）。

### 关键性能

| 操作 | 耗时 |
|------|------|
| 网格计算（3×3） | < 1ms |
| 单格提取（drawImage切片，360×360） | ~2ms |
| 9格全部提取 | ~18ms |
| ZIP打包（9张360×360 PNG） | ~100ms |
| 网格线拖拽预览 | < 16ms（60fps） |

### 测试场景

**场景1：标准3×3九宫格分割**
1080×1080正方形图片→3×3网格→2条横线+2条竖线→9个等大360×360格子→右侧9个100×100缩略图。

**场景2：非整数像素处理**
1000×1000图片→3×3网格→333不整除，余1→前1列334px，后2列333px→前1行334px，后2行333px→所有格子宽高和=1000。

**场景3：拖拽网格线调整**
3×3网格→拖拽第一条竖线向右移动20px→第1列变宽20px，第2列变窄20px→第3列不变→所有格子宽度总和仍为原始图片宽度。

**场景4：ZIP批量导出**
3×3分割→导出ZIP→ZIP包含9个PNG→命名为image_r0c0.png到image_r2c2.png→解压后9张图片可无缝拼接回原图。

## B03: 图片局部放大镜

### 背景与问题

用户在浏览网页图片时需要快速放大局部区域查看细节。实现类似物理放大镜的loupe工具，鼠标变成放大镜。

### 双画布架构

**源画布**：隐藏Canvas，绘制完整图片。用于提供像素数据源。
**镜头画布**：可见圆形Canvas，显示放大后的局部区域。使用drawImage的裁剪参数从源画布截取区域并放大。

### 3种触发模式

| 模式 | 交互 | 实现 | 场景 |
|------|------|------|------|
| 悬停模式 | mousemove跟随鼠标 | mousemove→requestAnimationFrame渲染 | 快速查看 |
| 点击固定 | 点击固定位置，可拖拽 | click→锁定坐标，拖拽更新 | 精细查看 |
| 拖拽模式 | 按住鼠标扫过图片 | mousedown→mousemove→mouseup释放 | 扫描式查看 |

### 插值与像素网格策略

| 放大倍数 | 插值模式 | 像素网格 |
|----------|----------|----------|
| 1.5x-4x | 双线性插值（imageSmoothingEnabled=true, quality='high'） | 不显示 |
| 4x-8x | 双线性插值 | 叠加半透明网格线（rgba(0,0,0,0.3)，每格对应一个源像素） |
| 8x+ | 最近邻插值（imageSmoothingEnabled=false） | 自然显示像素块 |

### 放大镜渲染核心

```typescript
render(sourceCanvas, lensCanvas, cx, cy, magnification, lensRadius, dpr) {
  const ctx = lensCanvas.getContext('2d')!;
  ctx.clearRect(0, 0, size, size);

  // 源区域半径 = 镜头半径 / 放大倍数
  const srcRadius = lensRadius / magnification;

  // 裁剪绘制
  ctx.save();
  ctx.beginPath();
  ctx.arc(size/2, size/2, lensRadius*dpr, 0, Math.PI*2);
  ctx.clip();

  // 缩放绘制——源区域物理像素→目标区域
  ctx.drawImage(sourceCanvas,
    (cx-srcRadius)*dpr, (cy-srcRadius)*dpr, srcRadius*2*dpr, srcRadius*2*dpr,
    0, 0, size, size);
  ctx.restore();

  // 绘制镜头边框+十字准星
  ctx.arc(size/2, size/2, lensRadius*dpr, 0, Math.PI*2);
  ctx.strokeStyle = '#e0e0e0'; ctx.lineWidth = 2*dpr; ctx.stroke();

  // 十字准星（半透明红色）
  ctx.strokeStyle = 'rgba(255, 0, 0, 0.5)'; ctx.lineWidth = 1*dpr;
  // 水平+垂直短线
}
```

### 跨域图片三层降级

1. 设置`img.crossOrigin='anonymous'`重新加载（标准CORS解决方式）
2. 通过YiAi代理下载（突破所有CORS限制，转换为base64 Data URI）
3. CSS fallback（仅放大，无像素网格，无像素级操作）

### 性能指标

| 操作 | 耗时 |
|------|------|
| 单帧渲染（3x, bilinear） | < 2ms |
| 单帧渲染（8x, nearest+像素网格） | < 3ms |
| 单帧渲染（16x, nearest） | < 1ms |
| 放大镜激活（首次show） | < 50ms |
| 跨域代理传输 | 0.5-3s |

### 测试场景

**场景1：悬停放大镜基础功能**
网页800×600图片→激活放大镜→鼠标悬停出现圆形放大镜（直径200px，默认3x）→放大镜内显示鼠标周围约33px区域的3x放大→鼠标移动平滑跟随→无明显延迟。

## B04: 图片拼接长图

### 背景与问题

多张图片拼接为一张长图（聊天记录、网页长截图、设计稿合并）。真正耗时的是对齐——两张图片的重叠部分需要精确检测和对齐。

### 重叠检测算法——像素行/列相似度

```
对于垂直拼接：比较图A底部N行和图B顶部N行
for overlap = 1 to searchRange:
  avgDiff = 逐像素RGB欧几里得距离平均（图A底部overlap行 vs 图B顶部overlap行）
  confidence = 1 - avgDiff/255
  取最高confidence且≥threshold(默认0.6)的overlap值
→ 裁剪掉overlap行重复内容 → 无缝拼接
```

### 滚动截图——Content Script实现

```
记录初始scrollTop → 获取scrollHeight
loop until scrollTop+viewportHeight >= scrollHeight:
  截取当前视口（captureVisibleTab）
  添加截图到拼接列表
  window.scrollBy(0, viewportHeight * 0.85)  // 保留15%重叠用于对齐
  await setTimeout(300ms)  // 等待页面渲染完成（懒加载图片/动画）
  检测scrollTop是否变化（若未变化则到达底部）
→ 所有截图就绪→自动重叠检测拼接→渲染完整长图
```

### 拼接样式

| 样式 | 实现 | 说明 |
|------|------|------|
| 纯色间隔条 | fillRect(separatorColor, gap区域) | 默认白色10px |
| 虚线分隔线 | setLineDash+strokeRect | 专业设计稿风格 |
| 阴影/投影 | shadowBlur分隔线 | 模拟物理卡片堆叠 |

### 固定元素去重

滚动截图中导航栏等固定定位元素会重复出现。检测每张截图的顶部/底部区域：如果连续多张截图的顶部N行高度相似（相似度>95%），标记为"固定元素"并去重。

### 关键性能

| 操作 | 耗时 |
|------|------|
| 重叠检测（2张1080×1920截图） | 50-200ms（取决于搜索范围） |
| 拼接渲染（5张1080×1920） | 100-300ms |
| 滚动截取单屏 | 0.5-1s（含等待渲染300ms+captureVisibleTab） |
| 降采样预览（超大长图） | < 50ms（50%缩放） |

## B05: 图片对比视图

### 背景与问题

所有图片编辑工具都需要"前后对比"能力。当前每个工具各自实现简单对比功能，导致代码重复、体验不一致、缺少高级对比模式。提取为统一组件供所有图片编辑工具复用。

### 3种对比模式

**并排（Side-by-Side）**：左右排列两个Canvas，同步缩放平移。评估整体效果。

**滑块分割（Split）**：两张Canvas绝对定位叠加。上层（处理后图片）使用CSS `clip-path: inset(0 ${100-pos}% 0 ${pos}%)`仅显示右半。拖动滑块更新百分比。GPU加速，60fps，零像素拷贝。

**透明度叠加（Overlay）**：下层处理后的图片，上层原图+`globalAlpha=opacity`。拖动透明度滑块0-100%。

### 同步缩放平移——状态共享

使用Vue reactive共享状态`{zoom, panX, panY}`。两个Canvas的渲染循环读取同一个状态。缩放和平移使用归一化坐标（0-1相对位置）独立于实际像素尺寸。缩放以鼠标位置为中心。

### 差异高亮

```
逐通道差值：abs(R1-R2)+abs(G1-G2)+abs(B1-B2) > threshold（默认10，可调0-255）
→ 差异像素红色高亮标注（R=255, G/B降低到30%）
→ 差异统计：changedPixels/totalPixels/percentage/maxDiff/avgDiff
→ 支持rgb和luma两种比较通道模式
```

### 3种对比模式适用分析

| 模式 | 最适合场景 | 用户认知 |
|------|-----------|----------|
| 并排 | 宽屏显示器，评估整体效果 | 完整观看两张图 |
| 分割 | 找到"从哪开始不一样" | 最直观，拖拽滑块动态对比 |
| 叠加 | 检测微小差异 | 人眼对闪烁变化敏感 |

### 关键性能

| 操作 | 1080p×2 | 4K×2 |
|------|---------|------|
| 并排渲染（双Canvas更新） | < 8ms | < 30ms |
| 分割滑块拖拽（CSS clip-path） | < 1ms | < 1ms |
| 叠加透明度调整 | < 4ms | < 15ms |
| 差异高亮计算+渲染 | < 15ms | < 60ms |
| 同步缩放平移 | < 8ms | < 30ms |
| 导出——并排拼接 | < 50ms | < 200ms |

### 测试场景

**场景1：并排对比——基本功能**
CompareView接收原图和亮度+30的处理后图片→左侧原图右侧处理后→中间分隔线→顶部标签"原图"（左）和"处理后"（右）→缩放容器两张图同步缩放→拖拽平移同步移动。

### 设计决策记录

**D-01：为什么使用CSS clip-path而非Canvas裁剪实现滑块分割？**
CSS clip-path操作GPU合成层，不触发重绘或回流。Canvas裁剪需要两次完整Canvas绘制（ctx.beginPath→clip→drawImage→restore）。4K图片Canvas两次绘制约30ms，CSS clip-path<1ms。仅当差异高亮需要像素级渲染时使用Canvas模式。

**D-02：为什么缩放平移使用归一化坐标（0-1）而非像素坐标？**
原图和处理后的图片可能有轻微尺寸差异（如裁剪后）。归一化坐标表示"显示图片的百分之多少位置"，独立于实际像素尺寸。`panX=0.5`表示图片水平中心，无论图片是1920px还是3840px。

## B06: 图片模糊/锐化/降噪工具

### 三者关系

模糊（信号衰减）、锐化（信号增强，USM依赖模糊生成差异层）、降噪（边缘保持算法避免抹掉细节）共享底层高斯模糊算法和Canvas像素操作基础设施。三者形成完整的图片清晰度调整工具链。

### B06a: 模糊工具

**5种模糊类型**：

| 类型 | 算法 | 关键参数 | 性能（1000×1000） |
|------|------|----------|--------------------|
| 高斯模糊 | 分离卷积（水平→垂直两次1D pass） | radius 0-50px | radius=10: <30ms, radius=50: <150ms |
| 运动模糊 | 方向卷积（指定角度和距离） | angle 0-360°, distance 1-200px | distance=30: <50ms |
| 镜头模糊 | 光圈形状kernel（圆形/六边形）+亮度阈值加权 | radius, 光圈形状, 亮度阈值 | radius=15: <80ms |
| 径向模糊 | 以中心点为圆心，沿径向采样平均 | samples 1-100, 中心点 | samples=30: <200ms |
| 移轴模糊 | 渐变蒙版+高斯模糊（中央清晰，上下模糊） | 焦点带位置/宽度, blur radius | <50ms |

**分离卷积优化**：高斯核可分离性——2D卷积O(w×h×r²) → 两次1D卷积O(2×w×h×r)。radius=10时速度提升20倍（4亿次→2千万次运算）。

**选择性模糊**：独立蒙版Canvas + 画笔涂抹。蒙版合成：`result = original×(1-mask/255) + blurred×(mask/255)`。支持蒙版羽化（对蒙版做高斯模糊后混合，创建自然过渡）。

### B06b: 锐化工具

**USM算法三参数**：

- `amount`（0-500%）：细节增强倍数。100%=原始差异，200%=2倍增强
- `radius`（0.1-250px）：模糊半径，决定锐化范围。小radius(0.5-2)=纹理/细节，大radius(5-50)=边缘/轮廓
- `threshold`（0-255）：差异过滤阈值。小于此值的差异不锐化，避免平坦区域（天空/皮肤）噪点

**6个预设**：

| 预设 | amount | radius | threshold | 说明 |
|------|--------|--------|-----------|------|
| 清晰度增强 | 20% | 30 | 3 | 模拟Lightroom Clarity |
| 纹理增强 | 50% | 1.5 | 2 | 表面纹理/布料/木纹 |
| 标准锐化 | 80% | 2.5 | 5 | 日常使用 |
| 强锐化 | 150% | 3 | 3 | 严重模糊图片 |
| 智能锐化 | 100% | 2 | 2 | Sobel边缘检测，仅锐化边缘 |
| 截图锐化 | 60% | 1 | 8 | 高阈值避免文字白边 |

**智能锐化核心**：
```
Sobel边缘检测 → 生成边缘强度蒙版（0-255灰度图）
→ 边缘蒙版→锐化权重蒙版（edge<edgeStrength→20%，edge≥edgeStrength→20%-100%线性）
→ USM锐化全图 → 根据权重蒙版混合原图和锐化图
→ result = original×(1-weight) + sharpened×weight
```

### B06c: 降噪工具

**4种降噪算法**：

| 算法 | 原理 | 复杂度 | 适用场景 |
|------|------|--------|----------|
| 中值滤波 | 邻域像素排序取中值 | O(w×h×r²×log(r)) | 椒盐噪点/扫描灰尘，radius=2 |
| 双边滤波（主力） | 空间权重×颜色权重，保持边缘 | O(w×h×r²) | 通用降噪，spatialSigma=5, colorSigma=30 |
| 色彩噪点分离 | RGB→YCbCr，色度通道强降噪（中值滤波），亮度通道弱降噪 | O(w×h) | 高ISO照片彩色斑点 |
| 小波降噪 | Haar分解（LL/LH/HL/HH四子带）→阈值处理→重构 | O(w×h×log(n)) | 高级选项 |

**6个降噪预设**：

| 预设 | 算法 | 关键参数 | 场景 |
|------|------|----------|------|
| 低光降噪 | 色彩噪点分离 | colorStrength=80, lumaStrength=25 | 夜景/室内暗光 |
| 高ISO降噪 | 双边滤波 | spatialSigma=5, colorSigma=30 | 高ISO混合噪点 |
| 扫描件降噪 | 中值滤波 | radius=2 | 扫描件/老照片灰尘 |
| JPEG伪影消除 | 双边滤波 | spatialSigma=3, colorSigma=20 | 高压缩比JPEG |
| 轻度降噪 | 双边滤波 | spatialSigma=2, colorSigma=15 | 最大限度保留细节 |
| 强力降噪 | 小波降噪 | threshold=30, levels=3 | 噪点严重时 |

**色彩噪点分离实现**：
```
RGB→YCbCr转换（Y=0.299R+0.587G+0.114B）
→ Cb/Cr色度通道：中值滤波强降噪（radius=3）
→ Y亮度通道：小半径高斯弱降噪（radius=1）
→ 混合：result = original×(1-strength) + denoised×strength
→ YCbCr→RGB转换
```

### Web Worker大图处理

>2000px图片使用Web Worker异步处理，主线程不阻塞。数据传输使用postMessage传递ImageData buffer。小图（<2000px，处理<100ms）直接主线程处理（Worker传输开销>节省时间）。

### 测试场景

**模糊测试**：
- 高斯模糊全图：800×600照片 radius=10→均匀模糊
- 选择性模糊：画笔在车牌和人脸区域涂抹→仅涂抹区域模糊→橡皮擦恢复清晰
- 运动模糊：角度0度（水平）距离30px→水平拖影→切换90度→垂直拖影
- 移轴模糊：城市俯瞰图→焦点带150px居中→上下逐渐模糊→微缩模型效果
- 镜头模糊：夜景灯光→六边形光圈半径15→灯光亮点呈六边形光斑→暗部均匀模糊

**锐化测试**：
- 标准USM锐化：轻微模糊照片→amount=80,radius=2.5→明显更清晰→天空无噪点

# C. 图片展示 (1个子功能)

## C01: 图片幻灯片放映

### 背景与问题

将静态照片变为动态叙事。支持过渡效果、背景音乐、Ken Burns效果和视频导出。

### 5种过渡效果

| 效果 | Canvas实现 | 风格 |
|------|-----------|------|
| 淡入淡出 | globalAlpha 0→1（旧照片），globalAlpha 1→0（新照片） | 柔和经典 |
| 滑动 | ctx.drawImage偏移（旧照片滑出+新照片滑入） | 动态方向感 |
| 缩放 | ctx.scale + globalAlpha（旧照片缩小淡出+新照片放大淡入） | 戏剧性冲击 |
| 擦除 | ctx.drawImage裁剪区域从右到左 | 翻页感 |
| 溶解 | 确定性伪随机像素替换 | 颗粒过渡 |

### Ken Burns效果

缓慢缩放+平移动画模拟摄像机在照片上的运动：
```
progress = elapsed / totalDuration (0→1)
zoom = minZoom + (maxZoom - minZoom) × progress
panOffset = calculatePanOffset(panDirection, progress, drawW, drawH)
ctx.translate(canvasCenter + panOffset)
ctx.scale(zoom, zoom)
ctx.drawImage(img, -drawW/2, -drawH/2)
```

### 视频导出

`Canvas.captureStream(30fps)` + `MediaRecorder`（WebM VP9, 5Mbps），浏览器原生API，零额外依赖。

```
const stream = canvas.captureStream(30);
const mediaRecorder = new MediaRecorder(stream, {
  mimeType: 'video/webm;codecs=vp9',
  videoBitsPerSecond: 5000000,
});
mediaRecorder.ondataavailable = (e) => chunks.push(e.data);
mediaRecorder.start(100); // 每100ms收集数据
// 驱动播放完整幻灯片...
mediaRecorder.stop();
const blob = new Blob(chunks, { type: 'video/webm' });
```

### 视频大小估算

| 配置 | 20s（5张） | 100s（20张） | 250s（50张） |
|------|----------|------------|------------|
| 1080p WebM VP9 5Mbps | ~12MB | ~60MB | ~150MB |
| 720p WebM VP9 3Mbps | ~8MB | ~38MB | ~95MB |

### 核心设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 渲染引擎 | Canvas 2D | 效果+导出的平衡，CSS无法导出视频 |
| 过渡效果 | 5种核心 | 覆盖主要视觉风格，过多效果分散注意力 |
| 视频导出 | Canvas.captureStream+MediaRecorder | 零依赖+原生API，输出WebM VP9 |
| Ken Burns | requestAnimationFrame驱动60fps | 纪录片行业标准技术 |

**场景1：基本幻灯片播放——淡入淡出**
选择20张照片相册→过渡"淡入淡出"→每张4秒→全屏播放→Ken Burns缩放1.0→1.2→4秒后1秒淡入淡出过渡到下一张→播放到最后循环。

**场景4：视频导出——WebM格式**

**场景5：全屏模式与播放控制**

# D. 图片管理 (7个子功能)

## D01: 图片评分系统

### 背景与问题

专业摄影师需要1-5星评分、色彩标签（红/黄/绿/蓝/紫）和旗标系统来筛选照片。评分数据写入EXIF XMP并缓存到chrome.storage。

### 评分体系

| 维度 | 值 | EXIF存储 | chrome.storage缓存 | 键盘快捷键 |
|------|-----|----------|-------------------|------------|
| 星级评分 | 0-5星 | XMP Rating (xmp:Rating=0~5) | photoRatings[hash].rating | 1-5键 |
| 色彩标签 | 红/黄/绿/蓝/紫/无 | XMP Label (xmp:Label) | photoRatings[hash].colorLabel | Ctrl+1~5 |
| 旗标 | Pick/Reject/None | EXIF Urgency | photoRatings[hash].flag | P/X/U键 |

### 键盘快捷键设计（Lightroom风格）

| 按键 | 功能 | 说明 |
|------|------|------|
| 1-5 | 设置1-5星评分 | 数字键对应星级 |
| 0 | 清除评分 | 设为0星（未评分） |
| Ctrl+1~5 | 色彩标签（红/黄/绿/蓝/紫） | 与Lightroom 6-9对应 |
| Ctrl+0 | 清除色彩标签 | |
| P | Pick旗标（入选） | |
| X | Reject旗标（拒收） | |
| U | 清除旗标 | |
| 左右方向键 | 上一张/下一张 | 导航 |
| 上下方向键 | 增加/减少星级 | 微调评分 |

### 数据流

```
照片评分 → chrome.storage缓存（<10ms写入，debounce 500ms合并写入）
         → EXIF XMP写入（<100ms，piexifjs写入Rating/Label/Urgency字段）
         → 评分随图片文件持久化，Lightroom等软件可读取

加载照片 → 优先从chrome.storage缓存读取（<1ms）
         → 缓存未命中→读取EXIF XMP（<50ms）→写入缓存
```

### 筛选引擎

组合筛选使用AND逻辑（跨维度）和OR逻辑（维度内多选）：
```
filter:
  minRating: 3（评分>=3星）
  maxRating: 5
  colorLabels: ['green', 'blue']（标签=绿或蓝）
  flagStatus: 'pick'（仅入选）
  showUnrated: false（不含未评分照片）
→ 结果显示同时满足所有条件的照片
```

### 评分统计

```
getStats() → {
  total: 200,
  distribution: { 0:20, 1:25, 2:50, 3:60, 4:30, 5:15 },
  labelDistribution: { red:30, yellow:25, green:40, blue:10, purple:5 },
  pickCount: 25, rejectCount: 15
}
```

### 关键存储分析

| 场景 | chrome.storage | EXIF增量 |
|------|---------------|----------|
| 每条评分记录（~150B） | 1000张~150KB | 单张+500B |
| 10000张 | ~1.5MB | 总计~5MB |

### 测试场景

**场景1：键盘快捷键评分——全屏浏览模式**
加载50张照片→全屏浏览→看到好照片按"5"→5颗星高亮→按右键下一张→觉得一般按"3"→3颗星→按左键回到第一张→仍显示5星。

**场景2：色彩标签筛选**
100张照片中20张绿色、10张红色、其余未标记→过滤器条点击绿色→仅显示20张绿色→同时点击红色→显示30张（OR逻辑）。

**场景3：旗标Pick/Reject工作流**
浏览照片→好照片按P→出现白色旗标→废片按X→黑色旗标带X→按U清除→打开"仅显示Pick"→仅显示入选照片。

**场景4：组合筛选——评分+标签+旗标**
500张照片→筛选：评分>=3 AND 标签=绿色 AND 旗标=Pick→同时满足三条件的结果→清除旗标筛选→仅保留评分>=3 AND 标签=绿色。

**场景5：评分写入EXIF XMP持久化**

### 设计决策记录

**D-01：为什么评分存储选择EXIF XMP+chrome.storage双写？**
EXIF XMP确保标准化和跨软件兼容（用户用YiPet评分的照片在Lightroom中打开评分一致）。chrome.storage缓存确保浏览性能（<1ms vs 50-100ms EXIF解析）。双写策略：评分操作同时更新缓存和EXIF。

**D-02：为什么键盘快捷键完全模仿Lightroom？**
Lightroom的快捷键设计经过数十年迭代优化，已被数百万摄影师内化为肌肉记忆。用户从Lightroom切换到YiPet浏览照片时快捷键操作完全一致，体验无缝衔接。

**D-03：为什么筛选使用AND逻辑而非OR逻辑？**
照片筛选核心场景是"缩小范围"——评分高AND标签绿AND已入选——这些条件应同时满足。跨维度筛选AND逻辑，维度内多选OR逻辑。与Lightroom筛选行为一致。

## D02: 图片关键词标签

### 背景与问题

关键词是照片可发现性的基础——没有关键词的照片像没有索引的书籍。提供层级关键词、智能建议、集合管理、导入导出。

### 关键词存储——双格式策略

同时写入两个XMP字段：

1. **dc:subject**（XMP标准，平面关键词列表）：所有软件读取。写入平面列表如`["日本","东京","旅行"]`
2. **lr:hierarchicalSubject**（Adobe扩展，层级关键词）：使用`|`分隔层级，如`"地点|日本|东京"`。Lightroom完美读取

### 关键词树结构

```typescript
interface KeywordTree {
  roots: string[];          // 根节点ID列表
  nodes: Record<string, KeywordNode>;
}
interface KeywordNode {
  id: string; name: string;
  fullPath: string;         // "地点/日本/东京"
  parent: string | null;    // 父节点ID
  children: string[];       // 子节点ID列表
  photoCount: number;       // 使用此关键词的照片数
}
```

### 关键词建议引擎——混合策略

```
用户输入"东" → 三种来源建议：
1. 前缀匹配（score=100）："东京"(photoCount=45) > "东京塔"(15) > "东京迪士尼"(8)
2. 全文包含匹配（score=50）："北海道"（含"东"字的不同位置）
3. 已选关键词的父级推荐（score=80）：如已选"日本/东京"→推荐"日本"
→ 按综合分数降序，去重，取前10条
```

### 关键词集合（组）

持久化到chrome.storage.sync（支持跨设备同步）：

```typescript
interface KeywordGroup {
  id: string; name: string; description: string;
  keywords: string[];       // 完整路径关键词列表
  createdAt: string; updatedAt: string;
}
```

应用组时：检查所有关键词是否存在→不存在的跳过并提示→去重（不添加已有关键词）→批量应用。

### 关键词导入导出

**导出JSON**（YiPet原生格式）：结构化嵌套表示层级树
**导入JSON**：解析嵌套结构，按fullPath去重
**导入Lightroom TXT**（缩进表示层级）：
```
地点
  日本
    东京
    京都
  法国
    巴黎
```
每行根据前导空格/tab数判断层级（缩进=0为根节点，缩进=4为第二层...）

## D03: 图片集合管理

### 背景与问题

相册是照片最自然的组织单元。手动相册+基于元数据的智能相册。使用IndexedDB存储成员列表，chrome.storage.sync同步相册元数据。

### 手动相册 vs 智能相册

| 类型 | 创建方式 | 成员管理 | 更新机制 |
|------|----------|----------|----------|
| 手动相册 | 选择照片→添加到相册 | 手动添加/移除 | 手动 |
| 智能相册 | 设置规则（日期+位置+评分+关键词+标签+旗标+相机） | 自动评估匹配 | 元数据变化时自动重新评估 |

### 智能规则引擎

```
规则结构：
SmartRule { groups: [规则组], operator: 'and'|'or' }
规则组 { conditions: [条件], operator: 'and'|'or' }

支持的条件类型和操作符：
- date: gt/lt/between（日期范围）
- location: contains/not_contains/eq（位置匹配）
- rating: gt/gte/lt/lte/eq（评分范围）
- keyword: contains/not_contains（关键词筛选）
- colorLabel: eq/neq（色彩标签）
- flag: eq/neq（旗标状态）
- camera: contains/eq（相机型号）
```

### 规则评估示例

```
"2024年日本精选"智能相册：
  组1（AND）：date between 2024-01-01,2024-12-31 AND rating gte 4
  OR
  组2（AND）：location contains "日本" AND colorLabel eq "green"
→ 匹配：2024年内评分4+的照片，或日本拍摄的绿色标签照片
```

### 存储方案

- IndexedDB：Album表（keyPath='id'）+ Member表（indexes: albumId, photoHash）
- chrome.storage.sync：相册元数据（名称、规则、封面设置）< 100KB总量支持跨设备同步

## D04: 图片地理标记

### 背景与问题

为无GPS的相机照片添加地理位置。支持地图选择、GPX轨迹关联和反向地理编码。

### 三种标记模式

| 模式 | 操作 | 实现 | 场景 |
|------|------|------|------|
| 地图手动 | Leaflet地图点击/搜索→标记位置 | Leaflet+OpenStreetMap免费瓦片 | 单张/少量照片 |
| GPX轨迹匹配 | 导入GPX→根据时间戳二分查找匹配轨迹点 | DOMParser解析GPX+二分查找 | 徒步/骑行照片批量 |
| 批量手动 | 选择多张照片→统一设置位置 | 同地图手动 | 同一地点拍摄 |

### GPX解析与时间匹配

**GPX文件结构**：XML格式，`<trkpt lat="" lon=""><ele/><time/></trkpt>`。浏览器原生DOMParser解析，无需额外依赖。

**二分查找时间匹配**：
```
GPX轨迹点按时间戳排序→对每张照片时间戳二分查找最近的轨迹点
时间复杂度：O(n log m)（n=照片数，m=轨迹点数）
→ 500张照片+1000轨迹点：O(500×log1000)≈5000次比较
  vs 线性扫描O(500×1000)=500000次（性能提升100倍）

匹配信心度：
  high: 时间差<30s（绿色标记）
  medium: 30-300s（黄色标记）
  low: >300s或未匹配（红色标记）
```

### 时间偏移校准

```typescript
// 相机时间比GPS设备快5分钟（相机09:35，GPS 09:30）
// 用户输入偏移量-300秒（相机时间减去5分钟）
const adjustedTime = photoTimestamp.getTime() - timeOffset * 1000;
// 重新二分查找匹配→匹配置信度全面提升
```

### 反向地理编码

- **服务**：Nominatim（OpenStreetMap），免费无密钥
- **频率限制**：1 req/s，前端防抖500ms
- **缓存**：Map<"lat,lng", ReverseGeocodeResult>，相同坐标不重复请求

```typescript
async reverseGeocode(lat, lng): Promise<ReverseGeocodeResult> {
  const cacheKey = `${lat.toFixed(5)},${lng.toFixed(5)}`;
  if (this.cache.has(cacheKey)) return this.cache.get(cacheKey)!;
  // 调用 https://nominatim.openstreetmap.org/reverse?format=json&lat=...&lon=...
  // 返回：displayName/city/state/country/countryCode
  this.cache.set(cacheKey, result);
  return result;
}
```

### 核心设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 地图库 | Leaflet+OpenStreetMap（~150KB） | 免费无密钥，满足标记需求 |
| GPX解析 | 浏览器原生DOMParser | 零依赖，代码<50行 |
| 时间匹配 | 预建排序+二分查找 | 500照片×1000轨迹点=5000次比较vs 500000次 |
| 反向地理编码 | Nominatim+内存缓存 | 免费，缓存命中率90%+ |

### 全局照片地图视图

使用MarkerCluster聚合标记。100个照片标记分布在地图上→缩放时动态聚合/拆分→点击聚合标记(45)→地图放大+拆分→点击单个标记→弹出缩略图和拍摄时间→点击缩略图→跳转照片详细视图。

## D05: 图片时间戳编辑

### 背景与问题

跨时区旅行相机时间错误、扫描老照片无日期、文件名包含日期等场景需要修正照片时间戳。

### 四种修正方式

| 方式 | 操作 | 数据来源 | 场景 |
|------|------|----------|------|
| 手动编辑 | 日历选择日期+时钟选择时间+时区选择 | 用户手动输入 | 单张精确修正 |
| 批量偏移 | 选中多张→输入±HH:MM:SS | 增量计算 | 时区校正/设备时间校准 |
| 文件名提取 | 正则匹配20+设备命名格式 | 文件名 | 照片文件名含日期 |
| GPS推断 | 从GPS坐标+拍摄时间推断UTC日期 | GPS元数据 | 补充方案（精度有限） |

### 文件名日期提取——20+正则模式

从具体到通用排序（避免通用模式误匹配）：

| 优先级 | 设备/格式 | 正则模式 | 示例 |
|--------|----------|----------|------|
| 1 | iPhone | IMG_(\d{8})_(\d{6}) | IMG_20240615_143052.jpg |
| 2 | Samsung | (\d{8})_(\d{6}) | 20240615_143052.jpg |
| 3 | Google Pixel | PXL_(\d{8})_(\d{6}) | PXL_20240615_143052.jpg |
| 4 | DJI | DJI_(\d{4})(\d{2})(\d{2})(\d{2})(\d{2})(\d{2}) | DJI_20240615143052.jpg |
| 5 | GoPro | G(\d{2})(\d{2})(\d{4}) | G06152024.jpg |
| 6 | WhatsApp | IMG-(\d{8})-WA\d+ | IMG-20240615-WA0001.jpg |
| 7 | 截图 | Screenshot_(\d{4}-\d{2}-\d{2}) | Screenshot_2024-06-15.png |
| 8-10 | 通用格式 | (\d{4})(\d{2})(\d{2}) / (\d{4})-(\d{2})-(\d{2}) | 20240615_photo.jpg |

日期有效性验证：年份在1990至当前年+1范围内，月/日合法。提取结果需用户确认，预览面板标注置信度。

### 时区处理

使用EXIF 2.3标准OffsetTimeOriginal标签存储时区偏移（如+08:00）。内部存储本地时间+时区偏移。使用Intl.DateTimeFormat获取时区列表和转换，不自行维护时区数据库。

### 批量时间偏移

增量模式（默认）：所有选中照片统一加/减固定时长。保留照片间的相对时间差（拍摄顺序和间隔不变）。

```typescript
async shiftBatch(files: File[], offsetSeconds: number, onProgress): Promise<BatchTimeShiftResult[]> {
  for (const file of files) {
    const exif = await readExif(file);
    const originalDate = exif.datetime.dateTimeOriginal;
    if (originalDate) {
      const newDate = new Date(originalDate.getTime() + offsetSeconds * 1000);
      // 自动处理跨月/跨年/跨DST边界（使用UTC时间计算偏移）
      // 同时更新DateTimeOriginal和DateTimeDigitized
      // 写入OffsetTimeOriginal保持时区信息
    } else {
      result.success = false; result.error = '无原始日期时间——无法偏移';
    }
  }
}
```

|------|------|------|-------|
| EXIF日期读取 | < 20ms | < 1s | < 4s |
| 文件名日期提取 | < 5ms | < 200ms | < 800ms |
| EXIF日期写入 | < 50ms | < 2.5s | < 10s |

### 设计决策记录

**D-01：为什么使用增量模式作为默认批量偏移策略？**
增量模式覆盖90%+场景——时区校正和设备时间偏差。保留照片间相对时间差——修正后旅行照片的拍摄顺序和间隔不变——这是摄影师和用户最看重的。绝对模式仅在特殊场景使用（扫描照片统一设置日期）。

**D-02：为什么文件名提取使用正则模式而非AI推断？**
20+正则模式覆盖主流设备85%+场景。AI推断在0.2d预算内不可行且增加网络依赖和延迟。预留自定义格式入口作为补充。

**D-03：为什么时区使用OffsetTimeOriginal而非仅本地时间？**
EXIF 2.3标准定义OffsetTimeOriginal专门用于存储时区偏移。本地时间+时区偏移保留拍摄时的本地时间（对回忆场景很重要）并提供UTC转换能力。
