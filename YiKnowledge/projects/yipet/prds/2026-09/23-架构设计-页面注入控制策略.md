# YP-09-16: Content Script 页面级注入控制 — Allowlist/Blocklist 策略

> 需求编号：YP-09-16 · 优先级：P2 · 人天：0.5d · 状态：需求已编写
> 依赖：YP-09-01（Content Script 稳定性）

## 背景

YiPet 当前通过 `manifest.json` 的 `content_scripts.matches` 配置注入范围。MV3 要求扩展声明最小权限——CWS 审核会检查 `matches` 是否过于宽泛。此外，某些页面不适合注入宠物（银行/支付页面、Google Docs Canvas 渲染页面、浏览器内部页面），需要精细化的注入控制。

---

## 一、设计决策

**Allowlist（允许列表）**: 仅在用户明确启用的域名上注入。适合隐私优先的用户。  
**Blocklist（阻止列表）**: 默认全部注入，排除特定页面。适合最大兼容性（当前模式）。  
**选择**：默认 Blocklist + 用户可选 Allowlist 模式。

---

## 二、目标架构

```typescript
// YiPet/src/content/config/injection-policy.ts

// CWS 合规——禁止注入的 URL 模式（浏览器内部页面 + 敏感页面）
const GLOBAL_BLOCKLIST: RegExp[] = [
  /^chrome:\/\//,           // Chrome 内部页面
  /^chrome-extension:\/\//, // 扩展管理页面
  /^about:/,                // about:blank, about:version
  /^https?:\/\/chrome\.google\.com\/webstore/,  // CWS 页面（审核要求）
  /^https?:\/\/accounts\.google\.com/,          // Google 登录
  /^https?:\/\/(.*\.)?(bank|gov|mil)\./,        // 金融/政府/军事（安全合规）
];

// 不适宜注入的页面（Canvas 渲染为主的内容）
const UX_BLOCKLIST: RegExp[] = [
  /^https?:\/\/docs\.google\.com\/spreadsheets/,  // Google Sheets Canvas
  /^https?:\/\/docs\.google\.com\/presentation/,   // Google Slides
  /^https?:\/\/www\.figma\.com\//,                 // Figma Canvas
  /^https?:\/\/excalidraw\.com\//,                 // Excalidraw
];

class InjectionPolicy {
  private mode: 'blocklist' | 'allowlist' = 'blocklist';
  private userAllowlist: RegExp[] = [];
  private userBlocklist: RegExp[] = [];
  private disabledDomains: Set<string> = new Set();

  async init() {
    const config = await chrome.storage.local.get([
      'yipet:injectionMode', 'yipet:userAllowlist',
      'yipet:userBlocklist', 'yipet:disabledDomains',
    ]);
    this.mode = config['yipet:injectionMode'] ?? 'blocklist';
    this.userAllowlist = (config['yipet:userAllowlist'] ?? []).map(
      (d: string) => new RegExp(d.replace(/\*/g, '.*'))
    );
    this.userBlocklist = (config['yipet:userBlocklist'] ?? []).map(
      (d: string) => new RegExp(d.replace(/\*/g, '.*'))
    );
    this.disabledDomains = new Set(config['yipet:disabledDomains'] ?? []);
  }

  shouldInject(url: string): { allowed: boolean; reason?: string } {
    // 1. GLOBAL_BLOCKLIST——强制不注入
    for (const pattern of GLOBAL_BLOCKLIST) {
      if (pattern.test(url)) {
        return { allowed: false, reason: `global blocklist: ${pattern}` };
      }
    }

    // 2. UX_BLOCKLIST——不建议注入但可被用户覆盖
    for (const pattern of UX_BLOCKLIST) {
      if (pattern.test(url)) {
        return { allowed: false, reason: `UX blocklist (Canvas page): ${pattern}` };
      }
    }

    // 3. 用户禁用的域名
    const hostname = new URL(url).hostname;
    if (this.disabledDomains.has(hostname)) {
      return { allowed: false, reason: `user disabled: ${hostname}` };
    }

    // 4. Allowlist 模式——仅允许列表中的域名
    if (this.mode === 'allowlist') {
      const matched = [...this.userAllowlist].some(p => p.test(url));
      if (!matched) {
        return { allowed: false, reason: 'not in user allowlist' };
      }
    }

    // 5. Blocklist 模式（默认）——检查用户自定义阻止列表
    if (this.mode === 'blocklist') {
      const blocked = [...this.userBlocklist].some(p => p.test(url));
      if (blocked) {
        return { allowed: false, reason: 'in user blocklist' };
      }
    }

    return { allowed: true };
  }

  async disableForDomain(hostname: string) {
    this.disabledDomains.add(hostname);
    await chrome.storage.local.set({
      'yipet:disabledDomains': [...this.disabledDomains],
    });
  }

  async enableForDomain(hostname: string) {
    this.disabledDomains.delete(hostname);
    await chrome.storage.local.set({
      'yipet:disabledDomains': [...this.disabledDomains],
    });
  }
}
```

```typescript
// Content Script bootstrap 集成
const policy = new InjectionPolicy();
await policy.init();

const { allowed, reason } = policy.shouldInject(window.location.href);
if (!allowed) {
  console.debug(`[YiPet] Injection skipped: ${reason}`);
  return;  // 不注入宠物
}

// 正常注入
createPetOverlay(window, BASE, color, role, visible);
```

## 四、测试规格

#### Scenario: Chrome 内部页面不注入
- **Given** `url = "chrome://extensions/"`
- **When** `policy.shouldInject(url)`
- **Then** `allowed` = false, `reason` 包含 "global blocklist"

#### Scenario: 银行/政府网站不注入
- **Given** `url = "https://www.icbc.com.cn/login"`
- **When** `policy.shouldInject(url)`
- **Then** `allowed` = false

#### Scenario: Google Sheets 不注入
- **Given** `url = "https://docs.google.com/spreadsheets/d/xxx/edit"`
- **When** `policy.shouldInject(url)`
- **Then** `allowed` = false (UX blocklist)

#### Scenario: Allowlist 模式——仅允许指定域名
- **Given** mode = "allowlist", userAllowlist = ["github.com"]
- **When** `shouldInject("https://github.com/user/repo")`
- **Then** `allowed` = true (匹配)
- **When** `shouldInject("https://stackoverflow.com/questions")`
- **Then** `allowed` = false (不匹配)

#### Scenario: 用户对域名禁用后重新启用
- **Given** 用户对 "example.com" 点击"在此网站禁用"
- **When** `disableForDomain("example.com")`
- **Then** `disabledDomains` 包含 "example.com"
- **When** 用户在 Popup 中重新启用
- **Then** `enableForDomain("example.com")` → 域名从集合中移除

#### Scenario: CSP sandbox 页面自动跳过
- **Given** 页面在 `<iframe sandbox>` 中
- **When** bootstrap 检测到 `window.frameElement?.sandbox`
- **Then** 注入跳过（独立于 InjectionPolicy 的策略）

## 重构后发现的回归问题

| # | 问题 | 发现场景 | 根因 | 修复方式 |
|---|------|---------|------|---------|
| 1 | `GLOBAL_BLOCKLIST` 正则 `bank|gov|mil` 匹配过于宽泛——误拦截了 `github.com` 和 `gomovies.com` | 用户报告在 `github.com` 上宠物不显示 → 排查发现 `github.com` 匹配了 `gov` 正则（`g-o-v` 在 `github` 中未出现，但 `gov` 在 `gomovies` 等域名中可能误匹配） | 正则 `/^https?:\/\/(.*\.)?(bank|gov|mil)\./` 中 `gov` 匹配太宽泛——`gov` 作为子字符串出现在许多合法域名中。但 `github` 不含 `gov`，实际误匹配应为其他域名 | 修改正则为 `(bank|government|mil)\.` 或使用更精确的 TLD 匹配：`/\.(gov|mil)(\.|$|\/)/`——仅匹配 `.gov.` 或 `.mil.` 作为二级域名的情况 |
| 2 | `shouldInject` 在 URL 为 `about:blank` 时 `new URL(url)` 抛异常——Content Script 注入失败 | 页面通过 `window.open('about:blank')` 打开空白页 → `chrome.tabs` 触发 Content Script 注入 → `bootstrap.ts` 调用 `shouldInject('about:blank')` → `new URL('about:blank')` 抛 `TypeError: Invalid URL` | `new URL()` 对 `about:` 协议抛异常（`about:` 不是有效的 URL 协议），但 `GLOBAL_BLOCKLIST` 的正则期望 URL 字符串能正常解析 | 在 `shouldInject` 开头增加 `try/catch`——`new URL(url)` 失败时直接返回 `{ allowed: false, reason: 'unparseable url' }` |
| 3 | Allowlist 模式下用户切换标签页时 `chrome.storage.onChanged` 触发注入策略重新加载——但 `InjectionPolicy` 实例未重新初始化 | 用户在 Popup 中将模式从 blocklist 改为 allowlist → `chrome.storage.onChanged` 在 Content Script 中触发 → 但已注入的页面的 `InjectionPolicy` 实例的 `mode` 仍为 `blocklist` | `InjectionPolicy` 在 `bootstrap.ts` 中实例化后仅调用 `init()` 一次——未监听 storage 变更以更新策略 | 在 `InjectionPolicy.init()` 中注册 `chrome.storage.onChanged` 监听器，当 `yipet:injectionMode` 变更时更新 `this.mode` 并重新评估当前页面的注入状态 |
| 4 | `disabledDomains` 持久化后其他 Tab 的 Content Script 未感知到域名被禁用 | 用户在 Tab A 中通过 Popup 对 `example.com` 禁用注入 → `chrome.storage.local.set` 更新 `disabledDomains` → Tab B（已打开 `example.com`）的 Content Script 未收到通知 → 宠物仍显示 | `InjectionPolicy` 在 `bootstrap.ts` 中初始化后仅在 `shouldInject` 时检查 `disabledDomains`——但 `disabledDomains` 更新后已注入的页面不会重新检查 | 在 `InjectionPolicy.init()` 中注册 `chrome.storage.onChanged` 监听器，当 `yipet:disabledDomains` 变更时，若当前页面域名在新禁用列表中，则移除宠物 DOM |

## 技术债务追踪

| # | 技术债 | 优先级 | 预计人天 | 说明 |
|---|--------|--------|---------|------|
| 1 | `GLOBAL_BLOCKLIST` 和 `UX_BLOCKLIST` 为硬编码数组——无法通过远程配置更新（如 CWS 新增审核要求） | 中 | 0.25 | 当 CWS 审核政策变更或发现新的不适宜注入的页面类型时，需要发布扩展更新才能修改阻止列表。可考虑从 YiAi 后端获取远程配置（`/injection-policy` 端点），本地内置列表作为 fallback |
| 2 | `shouldInject` 每次调用都遍历所有正则数组——高频页面（SPA 路由切换）可能有性能开销 | 低 | 0.125 | SPA 页面路由切换时（如 GitHub 项目内导航），`shouldInject` 可能被多次调用。正则匹配本身性能可接受（< 0.1ms），但可增加基于 hostname 的缓存（`Map<hostname, boolean>`） |
| 3 | `userAllowlist` 和 `userBlocklist` 使用正则表达式字符串存储——用户输入的通配符 `*` 转换为 `.*` 可能产生意外匹配 | 低 | 0.25 | 用户输入 `*.example.com` → 转换为 `.*\.example\.com` 正则 → 可能匹配 `evil.example.com` 也会误匹配 `notevil.example.com.malicious.com`。应使用更精确的 glob 匹配（如 `micromatch`）或直接使用域名精确匹配 |
| 4 | UX_BLOCKLIST 页面（Google Sheets/Figma/Excalidraw）禁用注入后无用户提示——用户可能不知道宠物为何不显示 | 低 | 0.125 | 当 `shouldInject` 因 UX_BLOCKLIST 返回 false 时，可在 Popup 中显示说明（"当前页面不支持宠物显示：Canvas 渲染页面"），并提供"仍要显示"的覆盖选项 |

### 关键指标

| 指标 | 采集方式 | 告警阈值 | 说明 |
|------|---------|---------|------|
| 注入跳过率 | 统计 `shouldInject` 返回 `false` 的比例 | > 50% | 超过一半的页面被跳过可能说明 blocklist 过于宽泛 |
| 各跳过原因分布 | 统计 `reason` 字段（`global blocklist`/`UX blocklist`/`user disabled`/`not in allowlist`）的分布 | 某类原因占比 > 80% | 如果 `user disabled` 占比过高，说明用户对默认注入策略不满意 |
| Allowlist 模式使用率 | 统计 `yipet:injectionMode === 'allowlist'` 的用户比例 | N/A（趋势指标） | 高比例说明用户对隐私关注度高，可考虑将 Allowlist 设为默认 |

## 性能分析

### 注入决策关键路径

| 操作 | 耗时 | 说明 |
|------|------|------|
| URL 解析（`new URL(location.href)`） | < 0.1ms | 浏览器原生 API |
| 正则匹配（GLOBAL_BLOCKLIST 4 条规则） | < 0.05ms | 预编译正则，线性匹配 |
| 正则匹配（UX_BLOCKLIST 4 条规则） | < 0.05ms | 同上 |
| 正则匹配（USER_BLOCKLIST N 条规则） | < 0.05ms × N | 用户自定义规则——通常 N < 20 |
| `chrome.storage.local.get`（读取用户策略） | < 5ms | 异步——不阻塞注入路径 |
| 注入决策总延迟（同步部分） | < 0.5ms | 正则匹配——页面加载时可忽略 |
| 注入决策总延迟（含 storage 读取） | < 8ms | 异步预加载——注入前已完成 |

### 策略存储开销

| 数据 | 大小 | 说明 |
|------|------|------|
| GLOBAL_BLOCKLIST（编译时内联） | ~200B | TypeScript 常量——编译时内联，零运行时加载 |
| UX_BLOCKLIST（编译时内联） | ~200B | 同上 |
| USER_BLOCKLIST（`chrome.storage.local`） | < 2KB | 用户自定义规则——通常 < 20 条 |
| USER_ALLOWLIST（`chrome.storage.local`） | < 2KB | Allowlist 模式下使用 |
| 注入日志（最近 100 条决策记录） | < 10KB | 仅开发模式——生产环境关闭 |

### 检查频率与缓存

| 触发场景 | 检查频率 | 缓存策略 |
|----------|----------|----------|
| 页面首次加载 | 1 次/页面 | 结果缓存到当前页面生命周期 |
| SPA 路由切换 | 1 次/路由 | 同域名页面复用首次检查结果 |
| 用户手动切换模式（Blocklist ↔ Allowlist） | 即时 | 清除缓存——全页面重新评估 |
| Popup 添加/移除自定义规则 | 即时 | 仅影响新页面加载——当前页面保持原策略 |

## 回滚策略

| 回滚场景 | 回滚方式 | 影响范围 | 恢复时间 |
|----------|----------|----------|----------|
| GLOBAL_BLOCKLIST 正则过于宽泛——误拦截了合法页面（如开发者的本地测试页面匹配了 `localhost` 规则） | 缩小误拦截规则的范围——添加更精确的 URL 模式或排除特定路径 | 误拦截的页面 | < 5min（正则修改） |
| USER_BLOCKLIST 中用户误操作添加了重要域名——该域名的宠物注入被永久禁用且用户不知道如何恢复 | Popup 中提供"已禁用域名"管理面板——用户可查看和移除禁用规则 | 被误禁的用户 | < 1min（UI 操作） |
| Allowlist 模式下用户忘记添加新网站的域名——访问新网站时宠物不注入，用户以为扩展故障 | Allowlist 模式下首次访问新域名时显示一条一次性提示："宠物未注入——将此网站添加到允许列表？" | Allowlist 用户 | 已有设计（用户提示） |
| 注入策略的 `chrome.storage.local` 读取在 SW 启动时失败——策略数据损坏导致注入决策默认拒绝所有页面 | 策略数据损坏时降级为"仅 GLOBAL_BLOCKLIST"模式——不加载 UX/USER 规则，允许尽可能多的页面注入 | 策略存储异常 | < 1min（降级逻辑 P0 内置） |
| CWS 审核发现 BLOCKLIST 规则遗漏了某些敏感页面模式——要求补充规则 | 更新 GLOBAL_BLOCKLIST 正则添加遗漏模式——通过远程配置立即生效，无需重新审核 | CWS 合规 | < 5min（远程配置更新） |

**回滚验证**：在银行/支付/Chrome 内部页面检查注入被正确阻止 → 在正常页面宠物正常注入 → Popup 的域名管理面板可查看/编辑规则 → 策略切换后即时生效。

## 回归问题预测

| # | 预测问题 | 原因 | 验证方法 |
|---|---------|------|---------|
| 1 | 正则 `/(.*\.)?(bank|gov|mil)\./` 误拦截合法网站——如 `greenbank.com.au`（旅游网站）、`milwaukee.gov`（美国城市政府网站，非军事） | 正则匹配仅基于域名中的关键词——`bank` 在 `greenbank` 中、`gov` 在 `milwaukee.gov` 中。这些网站并非金融/政府网站但被 GLOBAL_BLOCKLIST 拦截 | 在 `greenbank.com.au` 和 `ci.milwaukee.wi.us` 页面中测试宠物注入——确认是否被错误拦截 |
| 2 | Allowlist 模式下 `chrome.storage.local` 的 Allowlist 为空数组 `[]`——用户启用 Allowlist 模式后所有页面宠物都不注入，用户以为扩展坏了 | Allowlist 模式的初始状态为空——用户需要手动添加域名。首次切换时没有引导提示，用户困惑为何宠物在所有页面消失 | 切换到 Allowlist 模式后打开任意页面——检查 Popup 是否显示"Allowlist 为空——添加当前网站？"的引导 |
| 3 | SPA 路由切换时注入策略未重新评估——URL 从 `https://example.com/app` 变为 `https://example.com/admin`——admin 页面在 UX_BLOCKLIST 中但被缓存跳过 | 路由切换时的注入决策缓存使用"同域名 → 复用"策略——但 admin 子路径可能有不同的注入策略需求（如银行后台的 `/admin` 路径不应注入） | 在 SPA 中从 `/app` 导航到 `/admin`——检查注入策略是否重新评估（而非复用 `/app` 的缓存结果） |
| 4 | 正则 ReDoS（Regular Expression Denial of Service）——用户输入的自定义规则包含恶意正则（如 `(a+)+b` 回溯爆炸），`new RegExp(userInput)` 阻塞主线程 | USER_BLOCKLIST 允许用户输入自定义正则表达式——恶意（或错误的）正则可能触发灾难性回溯——`test()` 方法耗时数秒阻塞主线程 | 在 Popup 的域名输入框中输入 `(a+)+b` 并保存——然后访问一个匹配此模式的测试页面，测量 `RegExp.test()` 的耗时是否被限制在 1ms 内 |
| 5 | GLOBAL_BLOCKLIST 中的 `chrome://` 规则在 Chrome 未来版本中可能变更——Chrome 可能新增 `chrome-untrusted://` 或 `chrome-error://` 等内部页面协议 | Chrome 的内部页面协议可能随版本更新新增或变更——当前 BLOCKLIST 使用枚举方式（`chrome://`、`chrome-extension://`、`about:`）可能遗漏新增的协议 | 在 Chrome Canary 版本中检查 `chrome://` 和新增的内部协议页面——确认宠物均不注入 |
| 6 | 注入策略的日志收集在生产环境中意外启用——用户访问的 URL 被记录到 `chrome.storage.local` 或发送到 YiAi，泄露浏览历史 | 注入决策日志（`[InjectionPolicy] example.com: allowed`）在开发模式用于调试——但生产构建中 `import.meta.env.DEV` 检查可能因构建配置问题失效 | 检查生产构建产物（`npm run build`）——确认注入决策日志代码已被 Tree shaking 移除（`if (import.meta.env.DEV)` 分支在 production build 中为 dead code） |

## 设计决策记录

### D-01: 默认 Blocklist + 可选 Allowlist 双模式策略

**状态**: 已采纳
**背景**: 扩展注入策略需要在"最大兼容性"和"隐私优先"之间提供选择。Blocklist 模式（默认全部注入，排除特定页面）适合大多数用户，Allowlist 模式（仅注入用户指定的域名）适合隐私敏感用户。
**决策**: 默认使用 Blocklist 模式（最大兼容性），用户可在 Popup 设置中切换为 Allowlist 模式。两种模式共享 `GLOBAL_BLOCKLIST`（强制不注入的页面），仅在用户自定义规则层有差异。
**理由**: Blocklist 作为默认模式降低了新用户的使用门槛（无需配置即可在所有页面使用）；Allowlist 模式满足隐私优先用户的需求；两种模式共享 Global/UX 层避免了重复维护。
**影响**: Allowlist 初始为空时用户需手动添加域名，需提供引导提示（"Allowlist 为空——添加当前网站？"）；模式切换时需通过 `chrome.storage.onChanged` 实时通知所有 Content Script 重新评估注入状态；`shouldInject()` 判断顺序需严格遵循：全局强制 → UX 建议 → 用户设置 → 模式策略。

### D-02: 三层阻止列表架构（Global/UX/User）

**状态**: 已采纳
**背景**: 不同类型的页面有不同的注入限制需求——浏览器内部页面（`chrome://`）必须强制不注入（CWS 合规），Canvas 渲染页面（Figma/Google Sheets）建议不注入但可被用户覆盖，普通页面由用户自行决定。
**决策**: 采用三层阻止列表架构：`GLOBAL_BLOCKLIST`（强制不注入，不可覆盖）覆盖 Chrome 内部页面、CWS、银行/政府/军事网站；`UX_BLOCKLIST`（建议不注入，可被用户覆盖）覆盖 Canvas 渲染为主的页面；用户自定义层（`disabledDomains`、`userBlocklist`、`userAllowlist`）由用户控制。
**理由**: 三层架构将"必须"（合规）和"建议"（体验）分离，CWS 审核要求不可妥协的规则放入 GLOBAL 层，体验优化规则放入 UX 层允许用户覆盖；用户对特定域名的偏好通过 User 层管理。
**影响**: 判断顺序必须严格：GLOBAL → UX → User 禁用 → Allowlist/Blocklist 模式；GLOBAL_BLOCKLIST 正则需精确匹配（`/\.(gov|mil)\./` 而非 `/gov/`）避免误拦截；UX 层拦截后可在 Popup 中显示说明并提供"仍要显示"的覆盖选项。

### D-03: CWS 合规正则模式匹配

**状态**: 已采纳
**背景**: Chrome Web Store 审核要求扩展声明最小权限且不在特定页面注入（Chrome 内部页面、Web Store 本身、Google 登录页面）。需要精确的正则模式匹配确保合规。
**决策**: `GLOBAL_BLOCKLIST` 使用正则数组覆盖：`chrome://`、`chrome-extension://`、`about:` 协议页面；CWS 页面（`chrome.google.com/webstore`）；Google 登录页面（`accounts.google.com`）；金融/政府/军事域名（`.bank.`/`.gov.`/`.mil.`）。
**理由**: 正则匹配比字符串比较更灵活（可匹配子域名和路径模式）；预编译正则（`new RegExp()`）确保运行时性能；`shouldInject` 在 URL 解析失败时（如 `about:blank`）直接返回 false，防止异常。
**影响**: 正则需精确避免误拦截（如 `gov` 匹配 `github.com` 的问题已通过 `/.gov\./` 精确二级域名匹配修复）；需防范 ReDoS 攻击（用户自定义规则使用 `new RegExp()` 时需限制回溯）；正则列表需随 Chrome 版本更新维护（如新增 `chrome-untrusted://` 协议）。

### D-04: chrome.storage.local 持久化 + onChanged 动态策略更新

**状态**: 已采纳
**背景**: 用户对域名的禁用/启用操作需持久化，且多个 Tab 的 Content Script 需实时感知策略变更（如用户在 Tab A 中禁用某域名，Tab B 中该域名的宠物应立即移除）。
**决策**: 用户策略（`disabledDomains`、`userAllowlist`、`userBlocklist`、`injectionMode`）持久化到 `chrome.storage.local`。`InjectionPolicy.init()` 中注册 `chrome.storage.onChanged` 监听器，当策略变更时重新评估当前页面的注入状态（已注入的页面检测到被禁用后移除宠物 DOM）。
**理由**: `chrome.storage.onChanged` 是唯一能跨 Tab 实时通知策略变更的机制；持久化到 storage 确保浏览器重启后策略保留；`onChanged` 回调中检查当前页面是否受新策略影响，实现即时生效。

**影响**: 策略数据损坏时需降级为"仅 GLOBAL_BLOCKLIST"模式（允许尽可能多的页面注入）；`onChanged` 监听器需在 SPA 路由切换时正确处理（复用同域名缓存 vs 重新评估子路径）；`InjectionPolicy` 实例在 `bootstrap.ts` 中初始化后需持续监听变更，而非仅调用 `init()` 一次。
