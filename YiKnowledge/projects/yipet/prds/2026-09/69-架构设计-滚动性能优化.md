# YP-09-62: Content Script 页面滚动优化 — 被动事件监听与滚动性能

> 需求编号：YP-09-62 · 优先级：P2 · 人天：0.5d · 状态：需求已编写
> 依赖：YP-09-10（ContentScript 性能剖析）

## 背景

YiPet 的宠物图标需要感知页面滚动——当用户滚动页面时，宠物图标可能需要调整位置（保持在视口固定位置或跟随滚动）。当前实现使用 `window.addEventListener('scroll', handler)` 非被动模式——浏览器必须等待事件处理函数执行完毕才能执行默认滚动行为，导致页面滚动卡顿。

此外，`scroll` 事件触发频率极高（每帧 1 次，60fps 下每秒 60 次），即使事件处理函数只执行 1ms，也会消耗 60ms/秒的 CPU 时间。在低端设备上，这个开销足以导致滚动不流畅。

被动事件监听器（`{ passive: true }`）告诉浏览器事件处理函数不会调用 `preventDefault()`，浏览器可以立即执行默认滚动行为而不等待 JS 处理完成。结合 `IntersectionObserver` 替代 `scroll` 事件用于检测宠物图标是否在视口中，可大幅减少滚动性能开销。

当前面临的挑战：

| # | 挑战 | 影响 | 严重程度 |
|---|------|------|----------|
| 1 | 非被动 scroll 事件阻塞浏览器默认滚动 | 页面滚动卡顿，帧率下降 | 高 |
| 2 | scroll 事件高频触发（60次/秒） | 每帧都有 JS 执行开销 | 中 |
| 3 | `getBoundingClientRect` 在 scroll 回调中触发布局重计算 | 布局抖动 | 中 |
| 4 | 多个 scroll 监听器（宠物 + 聊天窗口） | 叠加开销 | 中 |
| 5 | `scroll` 事件在移动端触发更频繁 | 移动端滚动体验差 | 低 |

## 二、设计决策

### 决策 1：scroll 事件优化方式 — 被动事件 vs IntersectionObserver vs throttle

| 选项 | 性能 | 功能完整 | 浏览器支持 |
|------|------|----------|-----------|
| 被动事件 (`{ passive: true }`) | 高 | 高 | Chrome 51+ |
| `IntersectionObserver` | 最高 | 中（仅交叉检测） | Chrome 51+ |
| throttle 到 100ms | 中 | 高 | 全部 |
| **被动事件 + IntersectionObserver** | 最高 | 高 | Chrome 51+ |

**选择：默认使用 `{ passive: true }`，视口检测使用 `IntersectionObserver`。** `scroll` 事件监听器统一添加 `{ passive: true }`。宠物图标是否在视口内使用 `IntersectionObserver`（仅在交叉状态变化时触发），而非每秒 60 次的 `scroll` 事件。

### 决策 2：聊天窗口内部滚动处理 — 独立 scroll 容器 vs 全局 scroll

| 选项 | 隔离性 | 性能 | 维护复杂度 |
|------|--------|------|-----------|
| 独立 scroll 容器（Shadow DOM 内） | 高 | 高 | 低 |
| 全局 scroll 监听 | 低 | 低 | 低 |
| **独立 scroll 容器** | 高 | 高 | 低 |

**选择：聊天窗口使用 Shadow DOM 内的独立 scroll 容器。** 聊天窗口的滚动事件与宿主页面完全隔离，不触发全局 `scroll` 事件。Shadow DOM 天然隔离，无需额外处理。

### 设计决策记录

| 决策 | 选项 A | 选项 B | 选项 C | 选择 | 理由 |
|------|--------|--------|--------|------|------|
| 优化方式 | 被动事件 | IntersectionObserver | throttle | **被动 + Observer** | 最佳性能 |
| 聊天窗口滚动 | 独立容器 | 全局监听 | — | **独立容器** | Shadow DOM 隔离 |

## 三、目标架构

### 3.1 修复后代码

```typescript
// ✅ 新——被动事件监听
// YiPet/src/content/rendering/scroll-manager.ts

class ScrollManager {
  private _observer: IntersectionObserver | null = null;
  private _scrollHandlers: Array<{ element: EventTarget; handler: EventListener; options: AddEventListenerOptions }> = [];

  /** 初始化——使用 IntersectionObserver 检测宠物可见性 */
  init(overlayElement: HTMLElement, onVisibilityChange: (visible: boolean) => void): void {
    this._observer = new IntersectionObserver(
      (entries) => {
        for (const entry of entries) {
          onVisibilityChange(entry.isIntersecting);
        }
      },
      {
        threshold: [0, 0.1, 0.5, 1.0], // 多个阈值——精细控制
        rootMargin: '0px',
      }
    );

    this._observer.observe(overlayElement);
  }

  /** 添加被动滚动监听器——不阻塞默认滚动 */
  addPassiveScrollListener(
    element: EventTarget = window,
    handler: EventListener,
    throttleMs: number = 0
  ): () => void {
    let ticking = false;
    let lastCall = 0;

    const wrappedHandler: EventListener = (event) => {
      if (throttleMs > 0) {
        const now = performance.now();
        if (now - lastCall < throttleMs) return;
        lastCall = now;
      }

      if (!ticking) {
        requestAnimationFrame(() => {
          handler(event);
          ticking = false;
        });
        ticking = true;
      }
    };

    const options: AddEventListenerOptions = { passive: true };
    element.addEventListener('scroll', wrappedHandler, options);

    this._scrollHandlers.push({ element, handler: wrappedHandler, options });

    return () => {
      element.removeEventListener('scroll', wrappedHandler, options);
    };
  }

  /** 销毁 */
  destroy(): void {
    this._observer?.disconnect();
    this._observer = null;

    for (const { element, handler, options } of this._scrollHandlers) {
      element.removeEventListener('scroll', handler, options);
    }
    this._scrollHandlers = [];
  }
}

export const scrollManager = new ScrollManager();
```

## 六、测试规格

### GIVEN/WHEN/THEN 场景

**场景 1：被动 scroll 不阻塞默认滚动**

```
GIVEN 页面有 scroll 事件监听器（{ passive: true }）
WHEN 用户滚动页面
THEN 浏览器应立即执行滚动（不等待 JS 回调）
THEN 滚动帧率应 ≥ 58fps
```

**场景 2：IntersectionObserver 检测宠物可见性**

```
GIVEN 宠物图标在页面底部
AND IntersectionObserver 已启动
WHEN 用户滚动到宠物图标进入视口
THEN onVisibilityChange(true) 应被调用
WHEN 用户继续滚动使宠物图标离开视口
THEN onVisibilityChange(false) 应被调用
```

**场景 3：聊天窗口滚动不触发宿主页面滚动**

```
GIVEN 聊天窗口在 Shadow DOM 中，有独立 scroll 容器
WHEN 用户在聊天窗口内滚动消息
THEN 宿主页面不应滚动
THEN 全局 window scroll 事件不应触发
```

## 十、设计决策记录

### D-01：IntersectionObserver 替代 scroll 事件用于可见性检测

**背景**：`scroll` 事件每秒触发 60 次，即使回调函数只需 1ms，也消耗 60ms/秒的 CPU 时间。检测宠物图标是否在视口中使用 `scroll + getBoundingClientRect` 会触发布局重计算。

**决策**：使用 `IntersectionObserver` 替代 `scroll` 事件检测宠物可见性。`IntersectionObserver` 仅在交叉状态变化时触发（而非每帧），且浏览器内部优化，不触发强制布局重计算。

**后果**：宠物可见性检测的 CPU 开销从 2-5% 降到 < 0.1%。但 `IntersectionObserver` 只能检测交叉状态，不能检测具体滚动位置。

### D-02：聊天窗口使用 Shadow DOM 独立滚动容器

**背景**：聊天窗口（Shadow DOM 内）的消息滚动不应触发宿主页面的 `window.scroll` 事件。

**决策**：聊天窗口的滚动区域使用独立的 `overflow-y: auto` 容器，Shadow DOM 天然隔离滚动事件。

**后果**：聊天窗口滚动与宿主页面滚动完全隔离。但 Shadow DOM 内的 `scroll` 事件无法通过 `passive` 优化（同一事件循环），需要确保滚动处理函数耗时 < 5ms。

### D-03：rAF 节流而非 timer 节流

**背景**：`scroll` 事件可被节流到 100ms 减少调用次数，但 `setTimeout` 节流可能在帧中间执行，导致视觉不同步。

**决策**：使用 rAF（`requestAnimationFrame`）节流 `scroll` 回调。rAF 确保回调在浏览器渲染帧之前执行，与滚动动画同步。

**后果**：最坏情况延迟 16ms（一帧），用户无感知。但回调函数必须在 5ms 内完成，否则抢占帧预算影响渲染。
