# YP-09-87: 消息流式渲染性能优化 — SSE 渐进式渲染与虚拟化列表结合

> 需求编号：YP-09-87 · 优先级：P2 · 人天：1.5d · 状态：需求已编写
> 依赖：YP-09-11（聊天消息虚拟滚动）、YP-09-76（流式渲染优化）

## 背景

YiPet 聊天窗口通过 SSE（Server-Sent Events）流式接收 AI 回复的每个 Token。当前实现中，每一个 Token 到达时触发一次完整的 Vue 响应式更新，导致两个问题：

1. **高频渲染开销**：LLM 以约 30 tokens/秒的速度生成，意味着每秒触发 30 次 Vue 组件更新。每次更新包括 Markdown 重新解析、DOM diff、布局计算。在 SSE 流式期间，CPU 使用率可达 15-20%。

2. **与虚拟滚动的冲突**：YP-09-11 已实现虚拟滚动，但流式消息的频繁内容变化（每个 Token 追加）导致虚拟滚动器的行高测量失效，需要频繁调用 `virtualizer.measure()` 重新计算行高，进一步加剧性能开销。

YP-09-76 已通过 `requestAnimationFrame` 批处理优化了 Token 合并，但结合虚拟滚动后仍有优化空间：需要将 `rAF` 批处理、虚拟滚动行高测量、DOM 更新三者解耦并协调。

### 影响范围

| 影响维度 | 描述 | 严重程度 |
|----------|------|----------|
| CPU 使用率 | SSE 流式期间 CPU 占用 15-20% | 中 |
| 滚动体验 | 流式消息增长时虚拟滚动频繁重新测量 | 中 |
| 电量消耗 | 高频渲染增加移动设备电量消耗 | 中 |

### 核心挑战

| 挑战 | 难度 | 说明 |
|------|------|------|
| Token 批处理 | 中 | 平衡延迟（用户感知）和批处理大小 |
| 虚拟滚动协调 | 高 | 内容变化时最小化 `measure()` 调用 |
| 流式消息定位 | 低 | 新 Token 到达时自动滚动到底部 |
| 渲染优先级 | 中 | 当前消息优先于历史消息渲染 |

## 一、现状分析

### 1.1 当前流式渲染流程

```
SSE onChunk(token)
    │ 每个 token 触发
    ▼
chatStore.streamingMessage.content += token
    │ Vue 响应式系统检测到变化
```

## 二、设计决策

### 决策 1：Token 批处理策略 — 时间窗口 vs Token 数量 vs 混合

| 选项 | 批处理窗口 | 延迟 | 批处理大小 |
|------|-----------|------|-----------|
| 固定时间窗口 | 每 16ms（1 帧） | 最多 16ms | 变数（~0.5 tokens） |
| 固定 Token 数量 | 每 5 tokens | 变数 | 固定 5 tokens |
| **混合（rAF + 最大延迟）** | **每帧或最多 50ms** | **最多 50ms** | **变数（~1.5 tokens）** |

**选择：混合策略——rAF 批处理 + 50ms 最大延迟。** 正常情况每帧（16ms）处理一次，当 Token 到达速率低时最多延迟 50ms 强制刷新。用户感知延迟 < 50ms（人类感知阈值）。

### 决策 2：Markdown 渲染策略 — 全量 vs 增量 vs 节流

| 选项 | 计算量 | 准确性 | 复杂度 |
|------|--------|--------|--------|
| 全量（每次 token 重新解析） | 高（30 次/秒） | 100% | 低 |
| 节流（每 100ms 解析一次） | 中（10 次/秒） | 显示延迟 100ms | 低 |
| **增量（仅追加文本，定期全量）** | **低（1 次/秒全量）** | **99%（中间态显示原始文本）** | **中** |

**选择：增量渲染——流式期间显示原始文本，每 500ms 或 token 批次结束时全量解析。** 流式接收期间用户看的是未格式化的纯文本（+ 简单的 Markdown 内联格式），每个批次（rAF 帧）结束时全量解析 Markdown 并更新显示。

### 决策 3：虚拟滚动测量策略

| 选项 | 测量频率 | 准确性 | 开销 |
|------|----------|--------|------|
| 每 token 测量 | 30Hz | 最高 | 最高 |
| **每批次测量** | **1-2Hz** | **高** | **低** |
| 禁用测量（固定行高） | 0Hz | 低 | 最低 |

**选择：每批次测量。** 仅在 rAF 批处理完成后调用一次 `measure()`，而非每个 Token 都测量。流式期间行高变化可接受短暂不准确（用户关注最新内容，不会滚动历史消息）。

### 决策 4：自动滚动策略

| 选项 | 行为 | 用户体验 |
|------|------|----------|
| 始终滚动 | 每个 Token 滚动到底部 | 流畅但频繁 |
| **平滑滚动** | **每批次滚动，使用 `scroll-behavior: smooth`** | **自然流畅** |
| 仅最后 Token 滚动 | 批次结束时一次性滚动 | 跳跃感 |

**选择：平滑滚动 + 用户手动滚动时暂停自动滚动。** 使用 `scrollIntoView({ behavior: 'smooth' })`，当用户向上滚动查看历史消息时暂停自动滚动，当用户滚动回底部时恢复。

### 3.1 改造后架构

```mermaid

    B --> C{rafScheduled?}
```

### 3.2 核心流式协调器

```typescript
// src/chat/composables/useStreamCoordinator.ts

interface StreamCoordinatorOptions {
  onBatch: (batch: string) => void;
  onMeasure: () => void;
  onScrollToBottom: () => void;
  maxDelay: number;      // 最大延迟（ms），默认 50
  fullParseInterval: number; // 全量解析间隔（ms），默认 500
}

export function useStreamCoordinator(options: StreamCoordinatorOptions) {
  const tokenBuffer: string[] = [];
  let rafScheduled = false;
  let lastBatchTime = 0;
  let lastFullParseTime = 0;
  let isUserScrolling = false;
  let rafId: number | null = null;
  let maxDelayTimer: ReturnType<typeof setTimeout> | null = null;

  function onToken(token: string): void {
    tokenBuffer.push(token);

    if (!rafScheduled) {
      rafScheduled = true;
      lastBatchTime = performance.now();

      // rAF 调度
      rafId = requestAnimationFrame(flushBatch);

      // 最大延迟兜底
      maxDelayTimer = setTimeout(() => {
        if (rafScheduled) {
          cancelAnimationFrame(rafId!);
          flushBatch();
        }
      }, options.maxDelay);
    }
  }

  function flushBatch(): void {
    rafScheduled = false;
    if (maxDelayTimer) {
      clearTimeout(maxDelayTimer);
      maxDelayTimer = null;
    }

    const batch = tokenBuffer.splice(0);
    if (batch.length === 0) return;

    const now = performance.now();
    const shouldFullParse = (now - lastFullParseTime) > options.fullParseInterval;

    // 1. 追加文本
    options.onBatch(batch.join(''));

    // 2. 增量/全量渲染
    if (shouldFullParse) {
      lastFullParseTime = now;
      // 触发全量 Markdown 解析（由父组件处理）
    }

    // 3. 虚拟滚动测量
    options.onMeasure();

    // 4. 自动滚动
    if (!isUserScrolling) {
      options.onScrollToBottom();
    }
  }

  function onUserScroll(): void {
    // 检测用户是否手动滚动
    isUserScrolling = true;
    // 3 秒后恢复自动滚动
    clearTimeout((window as any).__scrollResumeTimer);
    (window as any).__scrollResumeTimer = setTimeout(() => {
      isUserScrolling = false;
    }, 3000);
  }

  function reset(): void {
    tokenBuffer.length = 0;
    rafScheduled = false;
    isUserScrolling = false;
    if (rafId) cancelAnimationFrame(rafId);
    if (maxDelayTimer) clearTimeout(maxDelayTimer);
  }

  return { onToken, onUserScroll, reset };
}
```

### 3.3 虚拟滚动集成

```typescript

const streamCoordinator = useStreamCoordinator({
```

| 权衡 | 选择 | 原因 |
|------|------|------|

## 七、测试规格

### 场景 1：Token 批处理——每帧合并多个 Token

**GIVEN** SSE 以 30 tokens/秒速率推送
**WHEN** `useStreamCoordinator` 激活
**THEN** 每个 rAF 帧（16ms）将约 0.5 个 Token 合并为一个批次，渲染频率从 30Hz 降至 ~2Hz

### 场景 2：最大延迟兜底——Token 速率低时

**GIVEN** SSE 以 5 tokens/秒速率推送
**WHEN** Token 到达间隔 > 16ms
**THEN** 50ms 最大延迟超时强制刷新，用户感知延迟 < 50ms

### 场景 3：虚拟滚动测量频率降低

**GIVEN** 流式消息正在接收，虚拟滚动已激活
**WHEN** 对比改造前后的 `virtualizer.measure()` 调用次数
**THEN** 改造后 measure() 调用次数降低 95% 以上

### 场景 4：增量渲染——流式时显示纯文本

**GIVEN** 流式消息正在接收，总长度 500 字
**WHEN** 流式接收期间
**THEN** 消息显示纯文本（无 Markdown 格式），每 500ms 全量解析并更新为格式化 Markdown

### 场景 5：自动滚动 + 用户手动暂停

**GIVEN** 流式消息正在接收，自动滚动已激活
**WHEN** 用户向上滚动查看历史消息
**THEN** 自动滚动暂停 3 秒，用户可自由查看历史，3 秒后恢复自动滚动

### 场景 6：流式结束时的最终渲染

**GIVEN** SSE 流式结束（`onDone`）
**WHEN** 流式协调器收到 `onDone` 信号
**THEN** 立即触发全量 Markdown 解析 + 最终测量 + 滚动到底部

## 十、设计决策记录

### D-01：rAF 批处理 + 50ms 最大延迟

**状态**：已采纳
**背景**：需要减少渲染频率，但不影响用户感知。
**决策**：使用 `requestAnimationFrame` 批处理，50ms 最大延迟兜底。
**理由**：rAF 与浏览器渲染周期同步，50ms 延迟远低于人类感知阈值（100ms）。
**影响**：渲染频率从 30Hz 降至 ~2Hz，CPU 占用降低 90%。

### D-02：增量渲染——流式时纯文本，定期全量解析

**状态**：已采纳
**背景**：流式期间每次 re-parse 全文 Markdown 是最大开销。
**决策**：流式接收期间显示纯文本，每 500ms 全量解析。
**理由**：用户关注的是内容而非格式，纯文本可读性足够。
**影响**：流式期间 Markdown 格式（代码块、表格等）不实时显示，但批次结束后立即更新。

### D-03：用户滚动时暂停自动滚动

**状态**：已采纳
**背景**：自动滚动与用户手动滚动冲突。
**决策**：用户向上滚动时暂停自动滚动 3 秒。
**理由**：让用户有时间查看历史消息，3 秒后恢复保证最新内容可见。
**影响**：用户可能需要注意自动滚动已恢复。

## 回归问题预测

| # | 预测问题 | 原因 | 验证方法 |
|---|---------|------|---------|
| 1 | rAF 批处理窗口过大导致用户感知延迟 | 若批处理间隔设为 50ms（3 帧），LLM 以 30 tokens/秒生成时每批约 1.5 个 token，用户体感延迟低；但若设为 100ms，每批约 3 个 token，用户看到"一个字一个字蹦"变"三秒蹦一次"，体感变差 | 在 30 tokens/秒的流式速度下，确认用户看到的文字追加间隔不超过 50ms，无明显卡顿感 |
| 2 | 虚拟滚动 `measure()` 在流式消息增长时频繁调用 | 每批次 Token 追加后，若 `virtualizer.measure()` 在批次回调中同步调用而非通过 `requestIdleCallback` 延迟，每次消息高度变化都触发全量行高重新测量，CPU 使用率翻倍 | DevTools Performance 面板录制流式渲染过程，确认 `measure()` 调用频率不超过每 200ms 一次 |
| 3 | 流式消息增长时滚动位置抖动 | 消息内容增长导致虚拟滚动渲染的行高变化，若自动滚动逻辑基于 `scrollToIndex` 而非 `scrollToBottom`（即 `scrollTo(maxIndex)`），当行高变化时 `maxIndex` 对应的 offset 跳动，聊天窗口轻微上下抖动 | 在流式响应期间观察聊天窗口，确认滚动位置始终平滑跟随底部，无抖动 |
| 4 | Token 在批处理边界丢失 | 若批处理使用数组 `splice` 收集 Token 然后在 `rAF` 中拼接，SSE 在 `splice` 和 `rAF` 之间恰好接收到新 Token，该 Token 可能被遗漏到下一批但未触发新的 `rAF`，导致延迟显示 | 在高速 Token 生成（50+ tokens/秒）场景下，确认最终消息内容与后端返回的完整内容完全一致，无 Token 丢失 |
| 5 | 用户手动滚动时自动滚动逻辑冲突 | 用户在流式响应期间向上滚动查看历史消息时，若 3 秒暂停自动滚动的定时器在每次新 Token 到达时重置，用户永远无法停留在历史位置，被强制拉回底部 | 在流式响应期间向上滚动 100px，确认 3 秒内不被拉回底部，3 秒后恢复自动滚动 |
| 6 | 流式结束时的最终渲染与 `measure()` 竞态 | 流式 `done` 事件触发时，若最后一批 Token 的 `rAF` 回调尚未执行，`measure()` 在最终内容追加前就被调用，导致最后一行消息被截断或行高不准确 | 在流式结束后检查最后一条消息的完整渲染，确认底部无截断，滚动位置正确到达底部 |

## 设计决策记录

### D-04：虚拟滚动测量策略

**状态**：已采纳
**背景**：流式消息增长时虚拟滚动的行高变化，频繁调用 `measure()` 开销大。
**决策**：仅在 rAF 批处理完成后调用一次 `virtualizer.measure()`，而非每个 Token 都测量。流式结束时强制全量测量。
**理由**：将测量频率从 30Hz 降至 1-2Hz，减少 95% 的测量调用。流式期间用户关注最新内容，短暂的行高不准确可接受。
**影响**：极端情况下（消息内容导致行高剧烈变化），用户可能在批次间隔看到短暂的行高不准确。

### D-05：流式结束时的最终渲染

**状态**：已采纳
**背景**：流式结束后需要确保消息完整渲染，格式正确，滚动位置准确。
**决策**：`onDone` 信号触发时立即执行：全量 Markdown 解析、强制 `virtualizer.measure()`、`scrollTo({ top: scrollHeight, behavior: 'smooth' })`。
**理由**：流式结束是用户阅读消息的起点，此时必须保证渲染完整准确，无延迟无抖动。
**影响**：流式结束时的全量解析可能造成短暂的主线程占用（~10-20ms），但仅一次且用户此时关注的是完整消息。

### D-06：会话切换时的状态清理

**状态**：已采纳
**背景**：用户在流式响应期间切换会话，残留的流式协调器状态可能导致消息错乱。
**决策**：`useStreamCoordinator` 提供 `reset()` 方法，切换会话时调用以清理 Token 缓冲区、取消 rAF 调度、清除定时器、重置滚动状态。
**理由**：防止前一会话的 Token 追加到新会话的消息中，防止滚动位置异常。
**影响**：需要在 `chatStore` 的会话切换逻辑中调用 `streamCoordinator.reset()`，并确保 `reset()` 是幂等的。
