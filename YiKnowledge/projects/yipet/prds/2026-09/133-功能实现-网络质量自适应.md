# YP-09-126: 网络质量自适应 — 网络质量检测、弱网降级、离线模式、重试退避、带宽感知加载、SSE重连策略、质量指示器

> 需求编号：YP-09-126 · 优先级：P2 · 人天：0.3d · 状态：需求已编写
> 依赖：YP-09-01（ContentScript 稳定性）、YP-09-03（SSE 流式）、YP-09-23（离线模式）、YP-09-92（缓存策略）

## 背景

### 问题陈述

YiPet 作为浏览器扩展，其核心功能（AI 聊天、SSE 流式响应、宠物动画渲染）严重依赖网络连接。当前系统对所有网络环境一视同仁，未区分 4G/5G/WiFi/离线等场景，导致：

1. **弱网体验差**：在 2G/3G 或信号不佳环境下，SSE 连接频繁断开，聊天窗口反复显示"正在重连"，用户等待时间过长甚至放弃使用
2. **资源浪费**：在弱网环境下仍尝试加载高分辨率宠物动画帧和完整模型响应，加重网络负担，加剧连接超时
3. **离线无感知**：用户从 WiFi 切换到移动数据或进入离线状态时，扩展未做任何降级处理，直接显示连接错误，用户不知道发生了什么
4. **重连策略粗暴**：SSE 断连后使用固定间隔重试（1s/2s/4s），未根据网络类型调整，快速网络下过于保守，弱网下过于激进
5. **带宽利用不充分**：所有图片资源使用同一分辨率，未根据当前带宽动态选择低分辨率或高分辨率版本

**核心矛盾**：在浏览器扩展受限的运行环境中，利用有限的网络信息 API（`navigator.connection`），实现感知网络质量的自适应策略，在功能完整性和用户体验之间取得平衡。

### 影响范围

| # | 影响 | 严重程度 | 典型场景 |
|---|------|----------|----------|
| 1 | 弱网下 SSE 反复断连，聊天体验极差 | 高 | 地铁通勤中使用 4G 不稳定网络，聊天窗口频繁显示"连接断开" |
| 2 | 弱网下加载宠物动画卡顿或失败 | 中 | 2G 网络下加载高清宠物动画帧超时，宠物显示为空白 |
| 3 | 离线切换无提示，用户困惑 | 中 | 进入电梯后网络断开，扩展显示红色错误但无解释 |
| 4 | 固定重试间隔不适用所有网络 | 中 | 千兆 WiFi 下断连后等待 4s 才重试，浪费 3.5s |
| 5 | 图片资源不分级加载 | 低 | 弱网下加载 2x 分辨率宠物图片，耗时 8s 而 1x 只需 2s |

### 挑战

| 挑战 | 说明 |
|------|------|
| API 兼容性 | `navigator.connection` 在 Firefox 中不支持，需要 polyfill 和降级策略 |
| 网络类型映射 | `effectiveType`（slow-2g/2g/3g/4g）到具体降级策略的映射需要经验数据支撑 |
| 离线检测可靠度 | `navigator.onLine` 可能误报（能访问局域网但无法访问外网），需要主动探测 |
| SSE 重连策略 | 不同网络类型需要不同的重连间隔和退避系数，需平衡恢复速度和服务器压力 |
| 动画帧率切换平滑 | 降低动画帧率时不能出现明显的跳帧或卡顿感 |
| 跨标签页同步 | 网络质量变化需要同步到所有打开的标签页，避免不一致 |

## 二、设计决策

### 决策 1：网络质量检测 API — navigator.connection vs 主动探测 vs 混合方案

| 选项 | 准确度 | 实时性 | 兼容性 | 实现复杂度 |
|------|--------|--------|--------|------------|
| 仅 `navigator.connection` | 中（浏览器估算） | 高（事件驱动） | Chrome/Edge 支持，Firefox 不支持 | 低 |
| 仅主动探测（ping YiAi） | 高（真实延迟） | 低（轮询开销） | 全平台 | 中 |
| 混合方案（connection API + 主动探测） | 高 | 高 | 高（降级到主动探测） | 中 |

**选择：混合方案。** 优先使用 `navigator.connection` 获取初始网络类型和监听变化事件。在 Firefox 或不支持 `connection` API 的环境下降级为主动探测（每 30s ping YiAi `/health` 端点）。两者结合：`connection` API 提供即时分类，主动探测提供精确的 RTT 和可用性验证。

### 决策 2：弱网降级策略 — 全局开关 vs 分级降级 vs 动态策略

| 选项 | 粒度 | 用户体验 | 实现复杂度 | 维护成本 |
|------|------|----------|------------|----------|
| 全局开关（弱网/正常） | 粗 | 差（一刀切） | 低 | 低 |
| 分级降级（slow-2g/2g/3g/4g） | 中 | 中 | 中 | 中 |
| 动态策略（基于 RTT + downlink 实时计算） | 细 | 好 | 高 | 高 |

**选择：分级降级。** 基于 `effectiveType` 分为 4 级（slow-2g、2g、3g、4g），每级对应不同的降级策略。动态策略虽然更精细，但 RTT 和 downlink 波动大，频繁切换降级策略反而造成体验不稳定。4 级分类足够覆盖绝大多数场景，且与 Chrome 的网络限速工具（DevTools Network throttling）保持一致，便于测试。

### 决策 3：SSE 重连策略 — 固定退避 vs 自适应退避 vs 网络感知退避

| 选项 | 弱网恢复速度 | 服务器压力 | 实现复杂度 |
|------|-------------|-----------|------------|
| 固定退避（1s/2s/4s/8s/30s） | 慢 | 低 | 低 |
| 自适应退避（根据失败次数） | 中 | 中 | 中 |
| 网络感知退避（根据 effectiveType） | 快 | 低 | 中 |

**选择：网络感知退避。** 基础退避公式：`delay = baseDelay[effectiveType] * 2^(attemptCount - 1)`，其中 `baseDelay` 根据网络类型不同：4g = 500ms、3g = 1s、2g = 2s、slow-2g = 3s。上限 30s。快速网络下缩短初始等待，弱网下增加初始等待避免频繁重连浪费资源。

### 决策 4：离线检测策略 — navigator.onLine vs 主动探测 vs 两者结合

| 选项 | 即时性 | 准确度 | 额外开销 |
|------|--------|--------|----------|
| 仅 `navigator.onLine` | 即时 | 低（误报率高） | 无 |
| 仅主动探测 | 延迟（30s 轮询） | 高 | 有（网络请求） |
| 两者结合（onLine 触发 + 探测确认） | 即时 | 高 | 低（仅在状态变化时探测） |

**选择：两者结合。** 监听 `online`/`offline` 事件作为触发器，事件触发后立即发起一次主动探测（ping YiAi `/health`）确认真实可达性。主动探测超时 3s，3s 内无响应判定为离线。同时每 60s 做一次定期探测作为兜底（处理 `navigator.onLine` 误报场景）。

### 设计决策记录

| 决策 | 选项 A | 选项 B | 选项 C | 选择 | 理由 |
|------|--------|--------|--------|------|------|
| 网络检测 API | connection API | 主动探测 | 混合方案 | **混合方案** | 兼顾实时性和兼容性 |
| 降级策略粒度 | 全局开关 | 分级降级 | 动态策略 | **分级降级（4 级）** | 粒度适中，与 DevTools 对齐 |
| SSE 重连 | 固定退避 | 自适应退避 | 网络感知退避 | **网络感知退避** | 快速网络快恢复，弱网不浪费 |
| 离线检测 | onLine | 主动探测 | 两者结合 | **两者结合** | 即时触发 + 准确确认 |

### 4.2 网络检测器

```typescript
// src/content/network/NetworkDetector.ts (新增)

class NetworkDetector {
  private currentInfo: NetworkInfo;
  private listeners: Set<(event: NetworkQualityChangeEvent) => void> = new Set();
  private probeTimer: ReturnType<typeof setInterval> | null = null;

  constructor() {
    this.currentInfo = this.getConnectionInfo();
    this.setupListeners();
    this.startProbing();
  }

  /**
   * 获取当前网络连接信息
   */
  getConnectionInfo(): NetworkInfo {
    const conn = (navigator as any).connection
      || (navigator as any).mozConnection
      || (navigator as any).webkitConnection;

    if (!conn) {
      // Firefox 或不支持 connection API 的环境
      return {
        effectiveType: '4g',
        downlink: 10,
        rtt: 50,
        saveData: false,
        type: 'unknown',
      };
    }

    return {
      effectiveType: conn.effectiveType || '4g',
      downlink: conn.downlink || 10,
      rtt: conn.rtt || 50,
      saveData: conn.saveData || false,
      type: conn.type || 'unknown',
    };
  }

  /**
   * 设置网络变化监听
   */
  private setupListeners(): void {
    const conn = (navigator as any).connection
      || (navigator as any).mozConnection
      || (navigator as any).webkitConnection;

    if (conn) {
      conn.addEventListener('change', () => {
        const previous = { ...this.currentInfo };
        this.currentInfo = this.getConnectionInfo();
        this.notifyListeners(previous, this.currentInfo);
      });
    }

    // 监听 online/offline 事件
    window.addEventListener('online', () => this.handleOnline());
    window.addEventListener('offline', () => this.handleOffline());
  }

  /**
   * 主动探测网络可达性
   */
  async probeNetwork(): Promise<{ reachable: boolean; latency: number }> {
    const start = performance.now();
    try {
      const controller = new AbortController();
      const timeoutId = setTimeout(() => controller.abort(), 3000);

      const response = await fetch('http://localhost:10086/health', {
        method: 'HEAD',
        signal: controller.signal,
        cache: 'no-cache',
      });

      clearTimeout(timeoutId);
      const latency = performance.now() - start;
      return { reachable: response.ok, latency };
    } catch {
      return { reachable: false, latency: -1 };
    }
  }

  /**
   * 处理上线事件（需主动探测确认）
   */
  private async handleOnline(): Promise<void> {
    const { reachable } = await this.probeNetwork();
    if (reachable) {
      const previous = { ...this.currentInfo, effectiveType: 'slow-2g' as const };
      this.currentInfo = this.getConnectionInfo();
      this.notifyListeners(previous, this.currentInfo);
    }
    // 如果不可达，保持离线状态，等待定期探测
  }

  /**
   * 处理离线事件
   */
  private handleOffline(): void {
    const previous = { ...this.currentInfo };
    this.currentInfo = {
      effectiveType: 'slow-2g',
      downlink: 0,
      rtt: Infinity,
      saveData: true,
      type: 'none',
    };
    this.notifyListeners(previous, this.currentInfo);
  }

  /**
   * 定期主动探测（处理 onLine 误报）
   */
  private startProbing(): void {
    this.probeTimer = setInterval(async () => {
      const { reachable } = await this.probeNetwork();
      const isCurrentlyOffline = this.currentInfo.downlink === 0;

      if (reachable && isCurrentlyOffline) {
        const previous = { ...this.currentInfo };
        this.currentInfo = this.getConnectionInfo();
        this.notifyListeners(previous, this.currentInfo);
      } else if (!reachable && !isCurrentlyOffline) {
        this.handleOffline();
      }
    }, 60000); // 每 60s 探测一次
  }

  /**
   * 注册网络质量变化监听器
   */
  onQualityChange(listener: (event: NetworkQualityChangeEvent) => void): () => void {
    this.listeners.add(listener);
    return () => this.listeners.delete(listener);
  }

  private notifyListeners(previous: NetworkInfo, current: NetworkInfo): void {
    const quality = this.classifyQuality(current);
    const strategy = this.getStrategy(current);
    const event: NetworkQualityChangeEvent = {
      previous,
      current,
      quality,
      strategy,
      timestamp: Date.now(),
    };
    this.listeners.forEach(fn => fn(event));
  }

  /**
   * 根据网络信息分类质量等级
   */
  private classifyQuality(info: NetworkInfo): NetworkQuality {
    if (info.downlink === 0) return 'offline';
    if (info.effectiveType === 'slow-2g') return 'online-very-slow';
    if (info.effectiveType === '2g') return 'online-very-slow';
    if (info.effectiveType === '3g') return 'online-slow';
    return 'online-fast';
  }

  /**
   * 根据网络信息获取降级策略
   */
  getStrategy(info: NetworkInfo): DegradationStrategy {
    const strategies: Record<string, DegradationStrategy> = {
      'slow-2g': {
        animationFps: 5, imageQuality: 'low', maxResponseTokens: 200,
        sseRetryBaseDelay: 3000, deferNonCritical: true, preloadEnabled: false,
        cacheOnly: true, requestTimeout: 15000, offlineMode: false,
      },
      '2g': {
        animationFps: 10, imageQuality: 'low', maxResponseTokens: 500,
        sseRetryBaseDelay: 2000, deferNonCritical: true, preloadEnabled: false,
        cacheOnly: true, requestTimeout: 10000, offlineMode: false,
      },
      '3g': {
        animationFps: 20, imageQuality: 'medium', maxResponseTokens: 1000,
        sseRetryBaseDelay: 1000, deferNonCritical: false, preloadEnabled: true,
        cacheOnly: false, requestTimeout: 8000, offlineMode: false,
      },
      '4g': {
        animationFps: 30, imageQuality: 'high', maxResponseTokens: Infinity,
        sseRetryBaseDelay: 500, deferNonCritical: false, preloadEnabled: true,
        cacheOnly: false, requestTimeout: 5000, offlineMode: false,
      },
    };
    return strategies[info.effectiveType] || strategies['4g'];
  }

  destroy(): void {
    if (this.probeTimer) clearInterval(this.probeTimer);
    this.listeners.clear();
  }
}
```

### 4.3 重试管理器

```typescript
// src/content/network/RetryManager.ts (新增)

class RetryManager {
  private queue: RetryTask[] = [];
  private activeTimers: Map<string, ReturnType<typeof setTimeout>> = new Map();
  private networkDetector: NetworkDetector;

  constructor(networkDetector: NetworkDetector) {
    this.networkDetector = networkDetector;
  }

  /**
   * 调度重试任务（网络感知退避）
   */
  schedule(task: RetryTask): void {
    this.queue.push(task);
    this.processQueue();
  }

  /**
   * 网络感知退避延迟计算
   */
  private calculateDelay(task: RetryTask): number {
    const info = this.networkDetector.getConnectionInfo();
    const strategy = this.networkDetector.getStrategy(info);
    const baseDelay = strategy.sseRetryBaseDelay;
    const delay = baseDelay * Math.pow(2, task.attemptCount - 1);
    return Math.min(delay, 30000); // 上限 30s
  }

  private async processQueue(): Promise<void> {
    for (const task of this.queue) {
      if (task.attemptCount >= task.maxAttempts) {
        this.queue = this.queue.filter(t => t.id !== task.id);
        continue;
      }

      const delay = this.calculateDelay(task);
      const timerId = setTimeout(async () => {
        try {
          task.attemptCount++;
          await task.execute();
          // 成功，移出队列
          this.queue = this.queue.filter(t => t.id !== task.id);
          this.activeTimers.delete(task.id);
        } catch {
          // 失败，重新调度
          this.activeTimers.delete(task.id);
          this.processQueue();
        }
      }, delay);

      this.activeTimers.set(task.id, timerId);
    }
  }

  /**
   * 网络恢复后立即重试所有等待中的任务
   */
  async retryAll(): Promise<void> {
    for (const [id, timer] of this.activeTimers) {
      clearTimeout(timer);
      this.activeTimers.delete(id);
    }
    // 重置所有任务的 attemptCount 并立即执行
    this.queue.forEach(t => { t.attemptCount = 0; });
    this.processQueue();
  }

  /**
   * 取消指定任务
   */
  cancel(taskId: string): void {
    const timer = this.activeTimers.get(taskId);
    if (timer) {
      clearTimeout(timer);
      this.activeTimers.delete(taskId);
    }
    this.queue = this.queue.filter(t => t.id !== taskId);
  }

  destroy(): void {
    this.activeTimers.forEach(timer => clearTimeout(timer));
    this.activeTimers.clear();
    this.queue = [];
  }
}
```

## 九、设计决策记录

### D-01：网络检测 API 选择

- **问题**：如何检测当前网络质量——使用浏览器 API 还是主动探测
- **选项**：仅 `navigator.connection`、仅主动探测、混合方案
- **选择**：混合方案，`connection` API 为主，主动探测为辅
- **理由**：`connection` API 提供即时分类（不产生额外网络请求），主动探测作为兼容性降级和准确度补充。两者结合覆盖所有浏览器，且主动探测间隔 60s 开销极小。

### D-02：降级策略粒度

- **问题**：降级策略应该多细粒度——基于 `effectiveType` 的 4 级分类还是基于实时 RTT/downlink 的动态计算
- **选项**：4 级分类（slow-2g/2g/3g/4g）、动态计算
- **选择**：4 级分类
- **理由**：动态计算虽然理论上更精确，但 RTT 和 downlink 波动大（尤其是移动网络），频繁切换降级策略会造成体验不稳定。4 级分类稳定且与 Chrome DevTools 对齐，便于测试和调试。

### D-03：SSE 重连退避策略

- **问题**：SSE 断连后如何计算重连延迟
- **选项**：固定退避（1s/2s/4s...）、网络感知退避（baseDelay 随网络类型变化）
- **选择**：网络感知退避，`delay = baseDelay[effectiveType] * 2^(attempt-1)`，上限 30s
- **理由**：快速网络（4G/WiFi）下断连通常是瞬时波动，短等待后即可恢复；弱网（2G/slow-2g）下断连可能是持续性的，长等待避免频繁重连浪费资源。网络类型变化时立即重置退避，避免在已恢复的网络上继续等待。

### D-04：离线模式判定策略

- **问题**：如何可靠判定离线状态——仅依赖 `navigator.onLine` 还是结合主动探测
- **选项**：仅 `navigator.onLine`、仅主动探测、两者结合
- **选择**：两者结合，`online`/`offline` 事件触发即时探测确认
- **理由**：`navigator.onLine` 即时但不可靠（局域网通但外网不通时返回 true），主动探测准确但有延迟。两者结合：事件触发即时响应，探测确认真实状态，定期探测兜底误报。

## 回归问题预测

| # | 预测问题 | 原因 | 验证方法 |
|---|---------|------|---------|
| 1 | 网络恢复正常后 SSE 仍未重连，聊天窗口持续显示"连接断开"，但网络指示器已显示绿色 | 网络恢复事件触发后，SSE 重连未正确响应 `NetworkEventBus` 的 `network:online` 事件，重试队列中的 SSE 任务未被重新调度 | 在网络恢复事件处理中显式调用 `RetryManager.retryAll()`，确保所有等待中的任务（包括 SSE）立即重试 |
| 2 | 在 2G 和 3G 之间频繁切换时（如移动中信号波动），宠物动画帧率在 10fps 和 20fps 之间反复跳变，出现明显的卡顿-流畅-卡顿循环 | 网络类型变化事件未做防抖处理，每次 `effectiveType` 变化都立即触发降级策略切换，动画帧率突变无过渡 | 在 `NetworkDetector` 中增加 2s 防抖窗口，网络类型变化后等待 2s 确认稳定再触发策略切换；动画帧率切换使用 `requestAnimationFrame` 渐变过渡 |
| 3 | 用户在离线模式下发送了多条聊天消息，网络恢复后消息以错误的顺序发送到 YiAi，导致对话上下文混乱 | 离线消息队列按 FIFO 顺序存储，但批量同步时未保持原始顺序，异步请求的响应顺序不确定 | 离线消息队列严格按时间戳排序，恢复后逐条顺序发送（下一条在上一条成功后发送），而非并行批量发送 |
| 4 | 主动探测 `/health` 端点返回 200 但实际 AI 服务不可用（Ollama 离线），系统误判为在线正常状态，用户发送消息后收到错误 | 健康检查仅验证 HTTP 可达性，未验证 AI 服务可用性，两种状态不绑定 | 扩展 `/health` 端点返回 AI 服务状态字段，或新增 `/health/ai` 端点；NetworkDetector 根据 AI 服务状态设置 `quality` 为 `online-slow` 并提示用户 |
| 5 | 图片质量切换逻辑在 `ImageLoader` 中实现，但宠物动画组件直接使用 `<img src>` 而非通过 `ImageLoader` 加载，导致降级策略不生效 | 宠物动画组件的图片加载路径未统一，部分组件绕过 `ImageLoader` 直接设置 src | 统一所有图片加载入口为 `ImageLoader.loadImage(url, options)`，禁止组件直接设置 `src` 属性；在 ESLint 规则中禁止直接使用图片 URL 字符串 |
| 6 | 用户启用了 Chrome 的"省流量"模式（`saveData: true`），但降级策略未强制使用最低配置，用户流量消耗超出预期 | `saveData` 标志仅在 `getStrategy` 中作为参考，未强制覆盖其他降级维度 | 当 `saveData === true` 时，强制应用 slow-2g 级别的降级策略（无论实际 effectiveType），在 UI 中显示"省流量模式已激活"标签 |
