# YP-09-14: 扩展更新机制与静默升级策略 — 版本迁移与兼容性保障

> 需求编号：YP-09-14 · 优先级：P2 · 人天：1.0d · 状态：需求已编写
> 依赖：YP-09-12（SW 生命周期状态机）

## 背景

Chrome 扩展通过 Chrome Web Store 自动更新——用户在浏览器重启时静默获取新版本。YiPet 当前无版本迁移机制：

| 问题 | 影响 |
|------|------|
| `chrome.storage.local` 数据结构变更——旧版本存储格式与新版本代码不兼容 | 用户升级后扩展崩溃 |
| 无版本号记录——无法判断是否需要执行数据迁移 | 每次启动都尝试迁移（浪费） |
| 更新失败无回滚机制 | 用户停留在损坏的新版本 |
| 无更新日志展示 | 用户不知道更新了什么（CWS 审核要求） |

---

## 一、现状分析

### 1.1 升级风险矩阵

| 变更类型 | 风险 | 示例 |
|----------|------|------|
| **新增 storage key** | 无风险 | 新增 `yipet:sw:state` |
| **修改 storage value 结构** | **高**——旧格式代码不兼容 | `session.messages[]` 从 `{text}` 改为 `{content, role}` |
| **删除 storage key** | 低 | 废弃 `yipet:legacyConfig` |
| **修改 manifest.json 权限** | **高**——需要用户重新授权 | 新增 `tabs` 权限 |
| **修改 Content Script 匹配模式** | 中——影响注入范围 | hosts 从 `<all_urls>` 改为特定域名 |

---

## 二、设计决策

### 决策 1：版本迁移策略 — 声明式 vs 命令式 vs 混合

**选择：声明式迁移链。** 定义 `v1.0→v1.1`、`v1.1→v1.2` 的纯函数迁移。SW 激活时自动执行从当前版本到最新版本的迁移链。

### 决策 2：权限变更处理 — 静默 vs 用户提示

**选择：可选权限静默添加 + 必需权限在更新说明中提示。** Chrome 对 `optional_permissions` 静默添加，`permissions` 变更需用户批准。

### 决策 3：回滚策略 — 无 vs Web Store 回滚 vs 内置回滚

**选择：storage 数据迁移前备份。** 迁移前将 `chrome.storage.local` 完整备份到 `yipet:backup:v{version}`，迁移失败时自动恢复。

## 三、目标架构

### 3.1 迁移链

```typescript
// YiPet/src/background/migration.ts

interface Migration {
  from: string;     // 源版本 "1.0.0"
  to: string;       // 目标版本 "1.1.0"
  migrate: () => Promise<void>;
  description: string;
}

const MIGRATIONS: Migration[] = [
  {
    from: '1.0.0',
    to: '1.1.0',
    description: 'session.messages 字段从 text 迁移为 content',
    migrate: async () => {
      const { sessions } = await chrome.storage.local.get('sessions');
      if (!sessions) return;

      for (const session of sessions) {
        session.messages = session.messages.map((msg: any) => ({
          role: msg.sender === 'user' ? 'user' : 'assistant',
          content: msg.text ?? msg.content ?? '',
          timestamp: msg.timestamp ?? Date.now(),
        }));
      }
      await chrome.storage.local.set({ sessions });
    },
  },
  {
    from: '1.1.0',
    to: '1.2.0',
    description: '用户偏好从前缀 yipet: 迁移到命名空间格式',
    migrate: async () => {
      const all = await chrome.storage.local.get(null);
      const migrated: Record<string, any> = {};

      for (const [key, value] of Object.entries(all)) {
        if (key.startsWith('yipet:') && !key.startsWith('yipet:backup:')) {
          migrated[key] = value;
        } else if (['locale', 'role', 'skin', 'model'].includes(key)) {
          migrated[`yipet:${key}`] = value;
          await chrome.storage.local.remove(key);
        }
      }
      await chrome.storage.local.set(migrated);
    },
  },
];

class VersionMigrationManager {
  private currentVersion: string;

  constructor() {
    this.currentVersion = chrome.runtime.getManifest().version;
  }

  async runMigrations(): Promise<boolean> {
    // 1. 获取上次记录的版本
    const { 'yipet:version': storedVersion } =
      await chrome.storage.local.get('yipet:version');
    const lastVersion = storedVersion ?? '0.0.0';

    if (lastVersion === this.currentVersion) {
      console.debug('[Migration] 版本未变，跳过迁移');
      return true;
    }

    console.info(
      `[Migration] 版本迁移: ${lastVersion} → ${this.currentVersion}`
    );

    // 2. 筛选需要执行的迁移
    const pending = MIGRATIONS.filter(
      m => m.from >= lastVersion && m.to <= this.currentVersion
    );

    if (pending.length === 0) {
      await this._setVersion(this.currentVersion);
      return true;
    }

    // 3. 备份当前 storage
    await this._backup(lastVersion);

    // 4. 顺序执行迁移链
    for (const migration of pending) {
      try {
        console.info(`[Migration] 执行: ${migration.description}`);
        await migration.migrate();
      } catch (err) {
        console.error(`[Migration] 失败: ${migration.description}`, err);
        await this._restore(lastVersion);
        return false;
      }
    }

    // 5. 更新版本号
    await this._setVersion(this.currentVersion);

    // 6. 清除旧备份（保留最近 2 个版本的备份）
    await this._cleanupOldBackups();

    console.info(`[Migration] 迁移完成: ${pending.length} 步骤`);
    return true;
  }

  private async _backup(version: string) {
    const all = await chrome.storage.local.get(null);
    await chrome.storage.local.set({
      [`yipet:backup:v${version}`]: { data: all, timestamp: Date.now() },
    });
  }

  private async _restore(version: string) {
    const backup = await chrome.storage.local.get(`yipet:backup:v${version}`);
    if (backup[`yipet:backup:v${version}`]) {
      await chrome.storage.local.clear();
      await chrome.storage.local.set(
        backup[`yipet:backup:v${version}`].data
      );
      console.warn(`[Migration] 已恢复到版本 ${version}`);
    }
  }

  private async _setVersion(version: string) {
    await chrome.storage.local.set({ 'yipet:version': version });
  }

  private async _cleanupOldBackups() {
    const all = await chrome.storage.local.get(null);
    const backups = Object.keys(all)
      .filter(k => k.startsWith('yipet:backup:v'))
      .sort()
      .reverse();

    // 保留最近 2 个备份
    for (const key of backups.slice(2)) {
      await chrome.storage.local.remove(key);
    }
  }
}
```

### 3.2 SW 激活时执行

```typescript
// YiPet/src/background/index.ts

self.addEventListener('activate', async (e) => {
  e.waitUntil((async () => {
    // 1. 版本迁移（最优先——确保存储格式兼容）
    const migrationMgr = new VersionMigrationManager();
    const migrated = await migrationMgr.runMigrations();

    if (!migrated) {
      console.error('[SW] 版本迁移失败，扩展可能不兼容');
      // 不阻塞 SW 激活——让用户看到错误提示
    }

    // 2. 继续正常初始化 (YP-09-12)
    await lifecycle.onActivate();
  })());
});
```

## 四、存储 Key 命名规范

为避免升级冲突，所有 storage key 统一使用 `yipet:` 命名空间前缀：

| 用途 | Key | 类型 | 迁移兼容 |
|------|-----|------|----------|
| 用户语言 | `yipet:locale` | `'en' \| 'zh_CN'` | 新增字段向后兼容 |
| 当前角色 | `yipet:role` | `string` | 新增角色→default fallback |
| 皮肤 | `yipet:skin` | `string` | 新增皮肤→default fallback |
| 版本号 | `yipet:version` | `string` | 自动管理 |
| 备份 | `yipet:backup:v{version}` | `object` | 自动清理 |
| SW 状态 | `yipet:sw:state` | `SwState` | YP-09-12 |
| 性能数据 | `yipet:perf:lastAnomaly` | `object` | YP-09-10 |

## 重构后发现的回归问题

| # | 问题 | 发现场景 | 根因 | 修复方式 |
|---|------|---------|------|---------|
| 1 | 迁移失败后 `_restore` 覆盖了用户在迁移期间写入的新数据 | 迁移链执行到第 2 步失败 → `_restore` 调用 `chrome.storage.local.clear()` + `set(backup)` → 覆盖了用户在迁移开始时（SW 激活前）通过 Content Script 写入的 `yipet:skin` 偏好 | 备份是迁移前（`activate` 事件开始时）拍摄的快照，但 Content Script 在 SW 激活期间可能已写入新数据。`clear()` 删除了一切 | 将 `_restore` 中的 `clear()` 改为选择性覆盖——仅恢复备份中存在的 key，不删除备份中不存在的 key；或 `_backup` 后立即将 storage 标记为 `migration:inProgress`，Content Script 在此期间写入时先检查标记 |
| 2 | `chrome.storage.local` 备份（`_backup`）在 storage 数据量大时超时——SW 被终止 | 用户有大量聊天数据（50+ 会话，每会话 100+ 消息）→ `chrome.storage.local.get(null)` 返回 ~8MB 数据 → `_backup` 的 `set()` 写入 8MB → 总耗时 > 30s → SW 被浏览器终止 | `chrome.storage.local.get(null)` 全量读取大 storage 时耗时与数据量成正比，加上 `set()` 写入 8MB 可超过 SW 30s 生命期 | 将 `_backup` 改为分片备份——按 key 前缀分组（`yipet:session:*`、`yipet:messageArchive:*`），每片备份后调用 `checkpoint()` 延长 SW 生命期 |
| 3 | 版本号比较使用字符串比较 `m.from >= lastVersion`——语义化版本号比较错误 | `lastVersion = "1.10.0"`, `m.from = "1.2.0"` → 字符串比较 `"1.2.0" >= "1.10.0"` 为 `true`（因为 `"1.2" > "1.1"`）→ 错误地跳过了迁移 | 字符串比较逐字符比较——`"1.2.0"` 和 `"1.10.0"` 比较时 `"2" > "1"` 为真 | 引入 `semver` 比较工具（或自实现 `parseVersion` → 数字数组比较），用 `compareVersions(from, lastVersion)` 替代字符串比较 |
| 4 | 迁移完成后 `_cleanupOldBackups` 删除备份时 `chrome.storage.local.remove` 异步执行——SW 可能在删除完成前被终止 | 迁移完成 → `_setVersion` 写入 → `_cleanupOldBackups` 调用 `remove` → 在 remove 回调执行前 SW 被终止 → 旧备份残留 | `chrome.storage.local.remove` 是异步的，SW 没有等待其完成的机制 | 在 `_cleanupOldBackups` 返回前 `await` 所有 `remove` 调用（`Promise.all`），并在 `activate` 事件的 `e.waitUntil` 中包含清理操作 |

## 技术债务追踪

| # | 技术债 | 优先级 | 预计人天 | 说明 |
|---|--------|--------|---------|------|
| 1 | 迁移链 `MIGRATIONS` 数组在当前版本持续增长——每次数据结构变更都追加一个迁移条目，1 年后可能累积 20+ 个迁移 | 中 | 0.5 | 长期来看，过长的迁移链增加 SW 激活耗时和失败概率。应引入"基线版本"机制——当迁移链超过 10 个时，将前 5 个迁移合并为一个基线迁移（直接迁移到基线版本，跳过中间步骤） |
| 2 | 备份恢复（`_restore`）依赖 `chrome.storage.local` 的完整性——如果备份本身在写入时被截断，恢复将使用损坏的备份 | 低 | 0.25 | 可通过在备份中添加 `checksum`（MD5 哈希）来验证备份完整性，恢复前先校验 |
| 3 | `yipet:version` 仅在迁移完成后更新——迁移失败时版本号不变，下次 SW 激活将重试整个迁移链 | 低 | 0.25 | 迁移失败时不应无限制重试。可增加"失败计数"和"最大重试次数"（3 次），超过后跳过该迁移并记录错误日志 |
| 4 | 权限变更提示缺少用户界面——当 `manifest.json` 的 `permissions` 变更时，用户在 CWS 自动更新后可能看到"需要新权限"弹窗但无解释 | 低 | 0.25 | 在 Popup 中增加"权限变更说明"页面，从 `yipet:version` 变化和历史版本 CHANGELOG 中读取权限变更信息 |

## 安全合规

### 安全需求

| 需求 | 实现方式 | 验证方法 |
|------|---------|---------|
| 备份数据不包含敏感字段 | `_backup` 在备份前过滤 `yipet:*:key`（session token）和 `yipet:*:token` 字段，仅备份用户数据（会话内容、偏好设置） | 代码审查：检查 `_backup` 方法中的 key 过滤逻辑 |
| 迁移脚本不执行远程代码 | 所有 `MIGRATIONS` 条目为纯函数（`migrate: async () => { ... }`），不包含 `fetch`/`importScripts`/`eval` 调用 | 代码审查：搜索 `MIGRATIONS` 数组中所有 `migrate` 函数体，确认无远程代码执行 |
| `chrome.storage.local` 备份不离开用户设备 | 备份仅存储在 `chrome.storage.local`（`yipet:backup:v{version}` key），不上传到任何服务器 | 代码审查：确认 `_backup` 和 `_restore` 仅使用 `chrome.storage.local` API，无 `fetch` 调用 |
| 版本迁移不修改其他扩展的 storage | 所有 storage key 使用 `yipet:` 前缀，`_backup` 的 `get(null)` 后仅恢复 `yipet:` 前缀的 key——`_restore` 中恢复时也仅恢复 `yipet:` 前缀的 key | 单元测试：mock `chrome.storage.local` 包含非 `yipet:` 前缀的 key，验证迁移后这些 key 未被修改 |

### 合规检查

| 检查项 | 要求 | 状态 |
|--------|------|------|
| 用户数据可恢复 | 迁移失败时自动恢复到迁移前状态，用户数据不丢失 | 待实现 |
| 迁移日志可追溯 | 每次迁移执行记录到 `yipet:migration:log`（含时间戳、版本、状态、耗时），支持问题排查 | 待实现 |
| CWS 更新静默——不中断用户操作 | 扩展更新（SW 版本切换）在用户无活跃聊天时执行，有活跃 SSE 连接时延迟切换 | 待实现 |
| 权限变更需用户知情同意 | `optional_permissions` 静默添加，`permissions` 变更在更新说明中提示并在 Popup 中展示 | 待实现 |

| 操作 | 耗时 | 说明 |
|------|------|------|
| 迁移链执行（单版本迁移） | < 50ms | 纯数据转换操作 |

| 更新日志 fetch（从 YiAi 获取 release notes） | < 200ms | 仅首次更新时触发 |

### 更新时机对用户体验的影响

| 更新时机 | 用户感知 | 风险 |
|----------|----------|------|
| 浏览器启动时（默认） | 无感知——SW 在后台静默更新 | 最低 |

## 回滚策略

| 回滚场景 | 回滚方式 | 影响范围 | 恢复时间 |
|----------|----------|----------|----------|
| 迁移链执行失败——`chrome.storage.local` 数据被部分迁移，处于不一致状态 | 从备份恢复 → 回退 SW 版本 → 用户数据无损 | 已执行迁移的用户 | < 5min（远程触发恢复） |
| 新版本 SW 导致 crash loop——SW 启动后立即崩溃，Chrome 反复重启 SW | Chrome 自动停止重试 → CWS 回滚到上一版本（需 1-3 天审核）或用户手动卸载重装旧版 | 所有用户 | 1-3 天（CWS 回滚） |
| 权限变更后用户拒绝授权——扩展功能降级但不应崩溃 | 功能检测 `chrome.permissions.contains()` — 缺失权限的功能隐藏而非崩溃 | 拒绝授权的用户 | < 1min（运行时检测） |
| Storage schema 变更导致旧版 SW 无法读取新版数据 | 在 schema 中添加 `version` 字段——旧版 SW 检测到未知版本时跳过该 key 而非崩溃 | 降级到旧版的用户 | < 5min（代码兼容） |
| 迁移链中的 `JSON.parse` 在数据损坏时抛出异常——迁移中断，后续版本迁移不执行 | 每个迁移步骤包裹 try-catch——单步失败不影响其他步骤，失败步骤记录到 `migration:log` | 数据损坏的用户 | < 5min（错误隔离） |

**回滚验证**：`chrome.storage.local` 备份 → 执行迁移 → 验证数据完整性 → 恢复备份 → 验证旧版 SW 可正常读取。

## 回归问题预测

## 设计决策记录

### D-01: 声明式迁移链

**状态**: 已采纳
**背景**: `chrome.storage.local` 数据结构随版本迭代变更（如 `session.messages[]` 从 `{text}` 改为 `{content, role}`），旧版本存储格式与新版本代码不兼容，可能导致扩展崩溃。
**决策**: 采用声明式迁移链——定义 `{from, to, migrate, description}` 的纯函数迁移条目数组。SW 激活时对比 `yipet:version`（上次记录版本）与 `manifest.json` 版本，自动执行从当前版本到最新版本的迁移链。
**理由**: 声明式迁移链比命令式迁移（在代码各处散落 `if (oldVersion)` 判断）更易维护和测试；每个迁移步骤是纯函数，可独立测试；版本号驱动执行避免了每次启动都尝试迁移的浪费。
**影响**: 迁移链在 SW `activate` 事件中执行，需在 5s 内完成（Chrome SW install 超时限制）；版本号比较需使用 semver 而非字符串比较（回归风险：`"1.10.0" > "1.2.0"` 字符串比较错误）；长期来看迁移链可能累积 20+ 条目，需引入"基线版本"机制合并历史迁移。

### D-02: 迁移前全量备份 + 失败自动恢复

**状态**: 已采纳
**背景**: 迁移链执行过程中可能因数据损坏、storage 配额不足、SW 超时终止等原因失败，导致 `chrome.storage.local` 数据处于不一致状态。
**决策**: 迁移前将 `chrome.storage.local` 完整备份到 `yipet:backup:v{version}` key。迁移失败时从备份自动恢复。保留最近 2 个版本的备份，旧备份自动清理。
**理由**: 全量备份是最安全的回滚策略——任何迁移失败都能完整恢复到迁移前状态。相比增量备份，全量备份实现简单且恢复时无需重放操作。
**影响**: 备份在 storage 数据量大时（50+ 会话）可能超时（> 30s），需改为分片备份；`_restore` 中的 `clear()` 会覆盖迁移期间 Content Script 写入的新数据，需改为选择性覆盖；备份需过滤敏感字段（`yipet:*:key`、`yipet:*:token`）。

### D-03: yipet: 命名空间前缀统一存储 Key 规范

**状态**: 已采纳
**背景**: 历史代码中 storage key 命名不一致——部分使用 `yipet:` 前缀，部分使用裸 key（如 `locale`、`role`），导致迁移时难以区分扩展数据与其他数据。
**决策**: 所有 storage key 统一使用 `yipet:` 命名空间前缀（如 `yipet:locale`、`yipet:role`、`yipet:skin`、`yipet:sw:state`）。子命名空间使用 `:` 分隔（如 `yipet:backup:v{version}`、`yipet:perf:lastAnomaly`）。
**理由**: 命名空间前缀确保 `_backup` 的 `get(null)` 后恢复时仅修改 `yipet:` 前缀的 key，不会误修改其他扩展的数据；前缀约定便于迁移脚本识别和转换旧格式 key。
**影响**: 需在 v1.1→v1.2 迁移中将旧裸 key 转换为 `yipet:` 前缀；所有新 storage 调用需遵循前缀规范；代码审查需检查 `chrome.storage.local` 调用是否使用了正确前缀。

### D-04: 可选权限静默添加 + 必需权限用户提示

**状态**: 已采纳
**背景**: 扩展版本更新时，`manifest.json` 中权限变更的处理方式直接影响用户体验和 CWS 审核。`permissions` 变更需要用户重新批准，`optional_permissions` 可静默添加。
**决策**: `optional_permissions` 静默添加（Chrome 自动处理），`permissions` 变更在 Popup 更新说明中提示用户，并提供权限变更说明页面。缺失权限的功能在运行时通过 `chrome.permissions.contains()` 检测，隐藏而非崩溃。
**理由**: 最小化用户打扰——大多数权限变更应为 `optional_permissions`（按需请求），仅核心功能依赖的权限放入 `permissions`；运行时权限检测确保用户拒绝授权后扩展仍可降级运行。

**影响**: 需在 Popup 中增加"权限变更说明"页面；`optional_permissions` 的请求时机需精心设计（在用户需要使用相关功能时请求，而非启动时弹窗）；回归风险：CWS 审核可能要求 `permissions` 变更需重新审核。
