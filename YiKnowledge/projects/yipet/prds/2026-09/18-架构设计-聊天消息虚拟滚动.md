# YP-09-11: 聊天消息虚拟滚动与长会话渲染性能优化

> 需求编号：YP-09-11 · 优先级：P1 · 人天：2.0d · 状态：需求已编写
> 依赖：YP-09-01（Content Script 稳定性）、YP-09-10（性能剖析）

## 背景

YiPet 聊天窗口以全量 DOM 渲染方式展示所有历史消息。短会话（< 20 条消息）性能良好，但当用户与 AI 进行长对话（100+ 条消息，尤其是知识库辅助的深度讨论）时，出现可感知的性能退化：

| 消息数 | DOM 节点数（估算） | 渲染耗时 | 滚动帧率 | 内存占用 |
|--------|-------------------|----------|----------|----------|
| 20 | ~200 | < 50ms | 60 fps | ~1MB |
| 50 | ~500 | ~100ms | 55-60 fps | ~3MB |
| 100 | ~1000 | ~250ms | 30-45 fps | ~8MB |
| 200 | ~2000 | ~600ms | 15-25 fps | ~18MB |
| 500 | ~5000 | ~2s | < 10 fps | ~50MB |

**核心问题**：每条消息渲染为独立的 Vue 组件（`MessageBubble`），含 Markdown 渲染、代码高亮、来源卡片、操作按钮。500 条消息 = 500 个 `MessageBubble` 组件实例全部挂载在 DOM 树中——即使用户只看最近的 5 条。

## 一、现状分析

### 1.1 消息渲染架构（改造前）

```
ChatMessages.vue
  │ v-for="msg in messages" :key="msg.id"
  ▼
MessageBubble.vue × N   ← 全部渲染，N = 消息总数
  ├── UserMessage.vue   (Markdown 渲染 + 操作按钮)
  ├── PetMessage.vue    (Markdown 渲染 + 来源卡片 + 工具调用卡片)
  ├── MessageActions.vue (复制/分支/在YiVad中打开)
  └── 代码高亮 (highlight.js)
```

### 1.2 性能瓶颈定位

| 瓶颈 | 根因 | 影响量级 (500 条消息) |
|------|------|---------------------|
| **DOM 节点爆炸** | 每条消息 ~10 个 DOM 节点 × 500 = 5000 节点 | Layout 耗时 ~200ms |
| **Vue 响应式开销** | 500 个组件实例，每个含多个 computed/watch | 内存 ~50MB |
| **Markdown 重复渲染** | marked 解析 500 次，highlight.js 高亮 500 次 | 首次渲染 ~2s |
| **滚动事件卡顿** | `scroll` 事件触发 Vue 响应式更新（未 throttle） | 帧率 15-25 fps |
| **SSE 流式更新** | 每次 `onToken` 追加文本 → 触发所在组件的 Markdown 重渲染 | 高频更新期间帧率 < 10 fps |

### 1.3 消息大小分布（典型会话）

```
消息内容长度分布:
  < 100 字符:  40%  (短回复)
  100-500:     35%  (正常回复)
  500-2000:    20%  (详细回复/RAG增强回复)
  > 2000:       5%  (代码块/长文档)
```

## 二、设计决策

### 决策 1：虚拟滚动实现 — 自实现 vs vue-virtual-scroller vs @tanstack/virtual

| 选项 | 体积 | Vue 3 兼容 | 动态行高 | 维护成本 |
|------|------|-----------|----------|----------|
| 自实现 | 最小 | ✅ | 需自行处理 | 高 |
| `vue-virtual-scroller` | ~30KB | ✅ | ✅ | 低 |
| `@tanstack/virtual` | ~10KB | ✅ (框架无关) | ✅ | 低 |

**选择：`@tanstack/virtual`。** 体积最小，框架无关设计，动态行高支持完善。YiPet 已有内容安全策略限制，小体积优势明显。

### 决策 2：消息裁剪策略 — 仅虚拟滚动 vs 虚拟滚动 + 内存裁剪

| 选项 | DOM 优化 | 内存优化 | 滚动体验 |
|------|----------|----------|----------|
| 仅虚拟滚动 (DOM 按需渲染) | ✅ | ❌ (数据仍在内存) | 向上滚动流畅 |
| **虚拟滚动 + 内存裁剪 (保留最近 200 条)** | ✅ | ✅ | 向上滚动需重新加载 |

**选择：虚拟滚动 + 内存裁剪。** 仅保留最近 200 条消息在 Pinia Store 中，超出部分持久化到 `chrome.storage.local` 或 MongoDB，向上滚动时按需加载。

### 决策 3：Markdown 渲染缓存 — 无缓存 vs 组件级缓存 vs 内容哈希缓存

| 选项 | 重复渲染开销 | 失效检测 | 实现 |
|------|-------------|----------|------|
| 无缓存 (当前) | 每次消息更新重渲染 | N/A | — |
| Vue `<KeepAlive>` | 切换 Tab 时保留 | 自动 | 低 |
| **内容哈希缓存** | 仅内容变化时重渲染 | MD5 哈希比较 | 中 |

**选择：内容哈希缓存。** 对每条消息的 `content` 计算 MD5 哈希，仅在内容变化时才触发 Markdown 重渲染。SSE 流式场景下——每个 `onToken` 追加文本——内容哈希变化→重渲染→但仅渲染变化的部分。

### 设计决策记录

| 决策 | 选项 A | 选项 B | 选项 C | 选择 | 理由 |
|------|--------|--------|--------|------|------|
| 虚拟滚动库 | 自实现 | vue-virtual-scroller | @tanstack/virtual | **@tanstack/virtual** | 最小体积+动态行高 |
| 消息裁剪 | 仅虚拟滚动 | 虚拟+裁剪 | — | **虚拟+裁剪** | DOM+内存双重优化 |
| Markdown 缓存 | 无缓存 | KeepAlive | 内容哈希 | **内容哈希** | SSE 流式场景最优 |

## 三、目标架构

### 3.1 虚拟滚动实现

```typescript
// YiPet/src/chat/components/ChatMessages.vue

import { useVirtualizer } from '@tanstack/vue-virtual';
import { ref, computed, watch } from 'vue';

const chatContainerRef = ref<HTMLElement>();
const messages = computed(() => chatStore.visibleMessages);  // 最近 200 条

const virtualizer = useVirtualizer({
  count: messages.value.length,
  getScrollElement: () => chatContainerRef.value,
  estimateSize: () => 120,  // 默认消息高度估算
  overscan: 5,               // 上下各预渲染 5 条
  // 动态测量实际行高
  measureElement: (el) => el.getBoundingClientRect().height,
});

// 自动滚动到底部（新消息到达时）
watch(
  () => messages.value.length,
  () => {
    // 仅当用户在底部附近时自动滚动（避免干扰用户阅读历史）
    const scrollEl = chatContainerRef.value;
    if (scrollEl) {
      const distanceFromBottom = scrollEl.scrollHeight -
        scrollEl.scrollTop - scrollEl.clientHeight;
      if (distanceFromBottom < 200) {
        virtualizer.value.scrollToIndex(messages.value.length - 1);
      }
    }
  }
);
```

Vue 模板：

```vue
<template>
  <div ref="chatContainerRef" class="chat-messages" @scroll.passive="onScroll">
    <div
      :style="{ height: `${virtualizer.getTotalSize()}px`, position: 'relative' }"
    >
      <div
        v-for="virtualRow in virtualizer.getVirtualItems()"
        :key="messages[virtualRow.index].id"
        :ref="virtualizer.measureElement"
        :style="{
          position: 'absolute',
          top: `${virtualRow.start}px`,
          width: '100%',
        }"
        :data-index="virtualRow.index"
      >
        <MessageBubble
          :message="messages[virtualRow.index]"
          :content-hash="messageHashes[virtualRow.index]"
        />
      </div>
    </div>
  </div>
</template>
```

### 3.2 消息内存裁剪

```typescript
// YiPet/src/chat/stores/chat.ts

const MAX_IN_MEMORY_MESSAGES = 200;   // 内存中最多保留 200 条
const ARCHIVE_BATCH_SIZE = 50;        // 每次裁剪 50 条

function trimOldMessages() {
  const messages = currentSession.value?.messages ?? [];
  if (messages.length <= MAX_IN_MEMORY_MESSAGES) return;

  // 1. 裁剪最旧的 ARCHIVE_BATCH_SIZE 条
  const toArchive = messages.slice(0, ARCHIVE_BATCH_SIZE);
  const remaining = messages.slice(ARCHIVE_BATCH_SIZE);

  // 2. 归档到 chrome.storage.local（异步，不阻塞 UI）
  chrome.storage.local.get(['yipet:messageArchive'], (result) => {
    const archive = result['yipet:messageArchive'] ?? {};
    archive[currentSession.value!.id] = [
      ...(archive[currentSession.value!.id] ?? []),
      ...toArchive,
    ];
    chrome.storage.local.set({ 'yipet:messageArchive': archive });
  });

  // 3. 更新会话消息（仅保留最近的）
  currentSession.value!.messages = remaining;
}

// 向上滚动加载更多
async function loadMoreMessages() {
  const archive = (await chrome.storage.local.get('yipet:messageArchive'))
    ['yipet:messageArchive'] ?? {};
  const archived = archive[currentSession.value?.id ?? ''] ?? [];

  if (archived.length === 0) return;  // 无更多历史消息

  // 加载最近归档的一批
  const batch = archived.slice(-ARCHIVE_BATCH_SIZE);
  currentSession.value!.messages = [
    ...batch,
    ...currentSession.value!.messages,
  ];

  // 从归档中移除已加载的
  archive[currentSession.value!.id] = archived.slice(0, -ARCHIVE_BATCH_SIZE);
  await chrome.storage.local.set({ 'yipet:messageArchive': archive });
}
```

### 3.3 Markdown 内容哈希缓存

```typescript
// YiPet/src/chat/composables/useMarkdownCache.ts

import { computed, ref, watch } from 'vue';
import { md5 } from 'js-md5';  // 轻量哈希 (~5KB)

const renderCache = new Map<string, string>();

export function useMarkdownCache(content: () => string) {
  const rendered = ref('');
  const lastHash = ref('');

  const hash = computed(() => md5(content()));

  watch(hash, (newHash) => {
    if (newHash !== lastHash.value || !renderCache.has(newHash)) {
      // 缓存未命中 → 重新渲染
      const result = marked.parse(content());
      renderCache.set(newHash, result);
      rendered.value = result;
      lastHash.value = newHash;

      // 限制缓存大小 (最多 500 条消息的渲染结果)
      if (renderCache.size > 500) {
        const firstKey = renderCache.keys().next().value;
        if (firstKey) renderCache.delete(firstKey);
      }
    } else {
      // 缓存命中
      rendered.value = renderCache.get(newHash)!;
    }
  }, { immediate: true });

  return rendered;
}
```

## 七、风险与缓解

| 风险 | 缓解 |
|------|------|
| 动态行高测量不准（首次渲染估算偏差） | `estimateSize` 保守估算 (120px) → `measureElement` 精确修正 |

## 重构后发现的回归问题

| # | 问题 | 发现场景 | 根因 | 修复方式 |
|---|------|---------|------|---------|
| 1 | 虚拟滚动后 `scrollToBottom` 失效 | 新消息到达时聊天窗口未自动滚动到底部 | `virtualizer.scrollToIndex` 在动态行高未完成测量时调用，目标索引位置计算偏差 | 延迟 `scrollToIndex` 至 `measureElement` 回调完成后执行，增加 `{ align: 'end' }` 参数 |
| 2 | 向上加载历史消息后虚拟列表位置跳动 | 滚动到顶部触发 `loadMoreMessages` 后，用户当前阅读位置被新插入的消息挤到下方 | 新消息插入到数组头部后，`virtualizer` 默认维持 `scrollTop` 绝对值而非相对位置 | 加载前记录 `scrollTop` 和第一条可见消息的 `offsetTop`，加载后通过 `scrollToIndex` 恢复到加载前可见的第一条消息 |
| 3 | Markdown 缓存中 `marked.parse` 偶发 XSS（`<script>` 标签未过滤） | AI 回复中包含 ` ```html<script>alert(1)</script>``` ` 代码块时，marked 渲染后 HTML 直接设置 `innerHTML` | `marked` 默认不启用 `sanitize`（已废弃），需手动调用 `DOMPurify` 或使用 `marked` 的 `renderer` 覆盖 | 渲染管道增加 `DOMPurify.sanitize(html)` 步骤，配置白名单允许 `pre/code/table/details/summary` 等安全标签 |
| 4 | SSE 流式更新期间内容哈希频繁变化导致 `watch` 触发过于频繁 | `onToken` 每个 token 追加后 `content` 变化 → `md5` 重新计算 → `watch` 触发 → `marked.parse` 重新渲染。每个 token 一次重渲染 | 无 debounce 机制，每个 token 都触发完整渲染管道 | 在 `watch` 中增加 50ms `debounce`，利用 `requestAnimationFrame` 合并同一帧内的多次更新 |

## 技术债务追踪

| # | 技术债 | 优先级 | 预计人天 | 说明 |
|---|--------|--------|---------|------|
| 1 | 归档消息的 `chrome.storage.local` 无分片——单 key 存储所有归档消息 | 中 | 0.5 | 当多个长会话同时归档时，单个 `yipet:messageArchive` key 可能超过 chrome.storage 的单个 item 大小限制（实际约 10MB 可用），需按会话 ID 分 key 存储 |
| 2 | `estimateSize` 估算值 (120px) 未根据消息类型区分——代码块消息实际高度常为 300-500px | 低 | 0.25 | 首次渲染时 `estimateSize` 用于占位高度估算，代码块消息会导致首次测量时列表跳动。可改为根据消息内容长度初步估算：`<100 字符 → 80px, 100-500 → 160px, >500 → 320px` |
| 3 | `js-md5` 哈希计算在每次内容变化时同步执行——长消息 (>5000 字符) 哈希计算耗时 >5ms | 低 | 0.25 | 可考虑使用更轻量的哈希算法（如 `cyrb53` 非加密哈希）或对长消息截取前 2000 字符 + 总长度作为哈希输入 |
| 4 | 虚拟滚动 `overscan: 5` 在 SSE 流式更新场景下可能不足——`measureElement` 回调触发频繁导致重排 | 低 | 0.25 | 流式更新期间 `overscan` 可临时提升至 10，流式结束后恢复为 5 |

## 安全合规

### 安全需求

| 需求 | 实现方式 | 验证方法 |
|------|---------|---------|
| Markdown 渲染 XSS 防护 | `marked.parse()` 输出经 `DOMPurify.sanitize()` 过滤，白名单允许 `pre/code/table/a/details/summary/blockquote` 等标签，禁止 `script/iframe/object/embed` | 单元测试：输入含 `<script>alert(1)</script>` 的 Markdown 代码块，验证输出 HTML 不含 `<script>` 标签 |

| 归档消息的 chrome.storage 数据不包含敏感 token | `trimOldMessages` 归档前过滤 `session.key`（session token）字段，仅保留 `id/role/content/timestamp` | 单元测试：归档后的消息对象不包含 `key` 属性 |

## 回滚策略

| 回滚场景 | 回滚方式 | 影响范围 | 恢复时间 |
|----------|----------|----------|----------|
| `@tanstack/virtual` 与 Vue 3.5 兼容性异常——虚拟列表空白或闪烁 | 通过 Feature Flag 关闭虚拟滚动，回退到全量渲染模式 | 聊天消息列表 | < 1min（开关控制） |
| 动态行高测量不准确——消息内容被截断或重叠 | 降级为固定行高模式（`estimateSize: 120`），关闭 `ResizeObserver` 动态测量 | 消息渲染 | < 5min（配置修改） |
| 消息裁剪逻辑触发后用户无法访问历史消息 | 回退裁剪——临时禁用裁剪，保留全量消息在内存 | 历史消息访问 | < 1min（开关控制） |
| `content-visibility` 导致消息气泡内图片/代码块延迟渲染 | 移除 `content-visibility` 属性，恢复 eager 渲染 | 消息内容可见性 | < 1min（CSS 修改） |
| IndexedDB 归档消息读取失败（IDB 损坏或配额满） | 降级为仅内存模式，归档功能临时关闭，提示用户导出历史消息 | 归档消息访问 | < 5min（降级逻辑） |

**回滚验证**：`npm run typecheck && npm run build` 通过 → 聊天窗口消息列表正常渲染 → 滚动流畅度 ≥ 30 fps → 历史消息可访问。

## 回归问题预测

| # | 预测问题 | 原因 | 验证方法 |
|---|---------|------|---------|
| 1 | `@tanstack/virtual` 在 Shadow DOM 内运行时，`ResizeObserver` 测量到的行高为 0——Shadow DOM 的 `offsetHeight` 在某些 Chrome 版本中不可靠 | `ResizeObserver` 测量元素的实际渲染尺寸，Shadow DOM 内的元素在 `display: none` 或初始挂载时 `offsetHeight` 为 0。`@tanstack/virtual` 的 `estimateSize` 降级逻辑可能被错误触发 | 在 Shadow DOM 挂载的聊天窗口中发送 50 条不同长度的消息（含代码块、图片、长文本），检查虚拟列表的行高是否准确 |
| 2 | 消息裁剪（200 条热 → IndexedDB）时用户正在查看被裁剪的消息，消息从视图中突然消失 | 裁剪逻辑按时间顺序移除旧消息（第 1-N 条），但用户可能正在向上滚动查看这些消息。裁剪触发时用户的可视区突然跳变 | 滚动到第 50 条消息（总 250 条），触发裁剪（保留最近 200 条），检查前 50 条被裁剪后视图是否自动滚动到第 1 条热消息 |
| 3 | `content-visibility: auto` 在 Chromium 88-90 版本中行为不稳定——包含 `position: sticky` 子元素的容器设置 `content-visibility` 导致渲染错误 | `content-visibility: auto` 在 Chromium 85+ 支持，但早期版本（88-90）对 `position: sticky/fixed` 子元素的处理有已知 bug——子元素不可见或位置偏移 | 在 Chrome 88 虚拟机中打开 200 条消息的聊天窗口，滚动到包含 `position: sticky` 的消息时间戳分隔条，检查其是否可见且位置正确 |
| 4 | Markdown 内容哈希缓存键碰撞——两条不同内容的消息产生相同的 `contentHash`，第二条消息使用第一条的缓存渲染 | 使用非加密哈希（如 `hashCode()` 字符串简单累加）作为内容哈希，不同 Markdown 内容可能产生哈希碰撞。错误缓存的渲染结果导致消息内容显示错误 | 生成 1000 条随机 Markdown 内容的消息，检查每条消息的渲染结果是否与其原文匹配 |
| 5 | IndexedDB 异步读取归档消息时，用户快速滚动到归档区域——归档消息仍在加载中，虚拟列表显示空白行或 loading 占位符 | 归档消息存储在 IndexedDB，读取为异步操作（10-50ms）。用户向上滚动触发虚拟列表的 `onChange` 回调，回调中同步检查消息是否存在——归档消息尚未加载完成即被渲染为空白 | 在 300 条消息的聊天中向上滚动到第 1-50 条（已归档），观察是否出现空白行或骨架屏，测量从滚动到消息内容显示的总延迟 |
| 6 | 虚拟滚动 `scrollToIndex` 在消息列表高度动态变化时（流式消息增量更新导致行高变化）跳转到错误位置 | AI 正在流式回复时用户点击"滚动到底部"——流式消息的高度持续增长（新增 token 导致 Markdown 渲染内容变化），`scrollToIndex` 计算的目标偏移量基于调用时刻的行高，在实际滚动时已失效 | 在 AI 流式回复期间（消息高度持续变化）点击"滚动到底部"按钮 3 次，确认每次都能正确滚动到最新消息的底部 |
