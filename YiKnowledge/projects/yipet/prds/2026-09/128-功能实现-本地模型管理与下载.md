# YP-09-121: 本地模型管理与下载 — Ollama 模型列表、下载进度追踪、模型切换、存储管理、硬件推荐、离线检测、更新通知

> 需求编号：YP-09-121 · 优先级：P2 · 人天：0.5d · 状态：需求已编写
> 依赖：YiAi Ollama 集成、YP-09-66（设置跨设备同步）

## 背景

### 问题陈述

YiPet 当前通过 YiAi 后端调用 Ollama 进行 AI 推理，但用户无法在前端直接管理本地模型。所有模型操作（列表查看、下载、删除、切换）都需要用户手动执行 `ollama` CLI 命令，这对非技术用户极不友好。这导致：

1. **操作门槛高**：用户需要打开终端执行 `ollama list`、`ollama pull` 等命令，普通用户无法完成
2. **下载进度不可见**：`ollama pull` 在终端中显示进度，但用户离开终端后无法感知下载状态
3. **模型切换繁琐**：切换模型需要修改 YiAi 配置或通过 API 调用，无法在聊天界面一键切换
4. **存储空间不透明**：用户不知道每个模型占用多少磁盘空间，无法判断是否需要清理
5. **模型选择困难**：Ollama 有数百个可用模型，用户不知道哪个适合自己（硬件配置、使用场景）

**核心矛盾**：在不暴露底层 CLI 的前提下，通过浏览器扩展提供直观的本地模型管理界面，既要覆盖模型生命周期的全流程（发现→下载→使用→更新→删除），又要适配不同硬件配置的用户。

### 影响范围

| # | 影响 | 严重程度 | 典型场景 |
|---|------|----------|----------|
| 1 | 非技术用户无法管理模型 | 高 | 用户想下载新模型但不知道如何操作 |
| 2 | 下载进度不可见，体验差 | 中 | 下载 10GB 模型时无法知道进度，以为卡住了 |
| 3 | 模型切换需要离开聊天界面 | 中 | 想从通用模型切换到代码模型，需要终端操作 |
| 4 | 存储空间不足时无提醒 | 中 | 模型下载到一半磁盘满，无法继续 |
| 5 | 用户不知道选择哪个模型 | 中 | 面对 100+ 模型列表无从下手 |

### 挑战

| 挑战 | 说明 |
|------|------|
| 跨进程通信 | 浏览器扩展 → YiAi REST API → Ollama REST API，三层调用链 |
| 下载进度实时推送 | Ollama pull API 返回流式 JSON，需解析并实时推送到前端 |
| 硬件检测 | 检测用户设备的 CPU、RAM、GPU 信息，推荐合适的模型 |
| 离线可用性 | 需要区分哪些模型已下载（可离线用）和哪些仅云端可用 |
| 存储管理 | 需要可靠地获取模型磁盘占用，并与用户可用空间对比 |

## 二、设计决策

### 决策 1：模型管理界面位置 — Popup 面板 vs 设置页 vs 聊天窗口内嵌

| 选项 | 空间 | 信息密度 | 操作便捷性 | 实现复杂度 |
|------|------|----------|------------|------------|
| Popup 面板 | 小（300x400） | 低 | 高（随时可打开） | 低 |
| 设置页（options page） | 大 | 高 | 中 | 中 |
| 聊天窗口内嵌面板 | 中 | 中 | 高 | 高 |

**选择：聊天窗口内嵌面板（模型选择器）+ 设置页（完整管理）。** 聊天窗口头部提供精简的模型切换下拉框（当前模型名 + 切换按钮），点击展开完整模型管理面板。设置页提供模型列表、下载进度、存储管理、推荐等完整功能。

### 决策 2：模型数据获取方式 — 前端直连 Ollama vs 通过 YiAi 代理 vs 混合

| 选项 | 安全性 | 离线能力 | 延迟 | 复杂度 |
|------|--------|----------|------|--------|
| 前端直连 Ollama API | 需暴露 Ollama 端口 | 完全离线 | 低 | 低 |
| 通过 YiAi 代理 | 安全（不暴露 Ollama） | 需 YiAi 运行 | 中 | 中 |
| 混合（列表走 YiAi，下载进度走 SSE） | 安全 | 需 YiAi 运行 | 中 | 高 |

**选择：通过 YiAi 代理。** 安全考虑：不直接暴露 Ollama 端口到浏览器。YiAi 提供模型管理 RPC 接口（list、pull、delete、show），pull 进度通过 SSE 流式推送到前端。前端无需知道 Ollama 地址，所有请求经过 YiAi 的认证和频率限制。

### 决策 3：下载进度推送方式 — 轮询 vs SSE vs WebSocket

| 选项 | 实时性 | 服务端复杂度 | 扩展兼容性 | 资源消耗 |
|------|--------|-------------|-----------|----------|
| 轮询（每 500ms） | 低 | 低 | 好 | 中 |
| SSE | 高 | 中 | 好 | 低 |
| WebSocket | 高 | 高 | 中 | 中 |

**选择：SSE（Server-Sent Events）。** SSE 天然支持单向流式推送，适合下载进度场景。YiAi 已有 SSE 基础设施（聊天流式响应），可复用。轮询方案延迟高且浪费资源，WebSocket 对于单向数据流是过度设计。

### 决策 4：硬件检测方案 — 前端 navigator API vs YiAi 服务端检测 vs 两者

| 选项 | 信息完整度 | 实现复杂度 | 隐私影响 |
|------|-----------|------------|----------|
| 前端 navigator.hardwareConcurrency | 低（仅 CPU 核心数） | 低 | 低 |
| YiAi 服务端检测（psutil + GPUtil） | 高（CPU/RAM/GPU/磁盘） | 中 | 中 |
| 两者结合 | 高 | 中 | 中 |

**选择：两者结合。** 前端获取 `navigator.hardwareConcurrency`（CPU 核心数）和 `navigator.deviceMemory`（RAM），YiAi 后端通过 `psutil` 获取完整 CPU 信息、可用 RAM、磁盘空间，通过 `GPUtil` 或 `nvidia-smi` 获取 GPU 信息。前端展示推荐时，优先使用后端数据，前端数据作为兜底。

### 设计决策记录

| 决策 | 选项 A | 选项 B | 选项 C | 选择 | 理由 |
|------|--------|--------|--------|------|------|
| 管理界面位置 | Popup | 设置页 | 聊天内嵌 | **聊天内嵌 + 设置页** | 操作便捷 + 功能完整 |
| 数据获取方式 | 直连 Ollama | 通过 YiAi | 混合 | **通过 YiAi 代理** | 安全可控 |
| 进度推送 | 轮询 | SSE | WebSocket | **SSE** | 复用已有基础设施 |
| 硬件检测 | 前端 | 服务端 | 两者结合 | **两者结合** | 信息完整 |

### 4.2 模型管理服务

```typescript
// src/services/ModelService.ts (新增)

class ModelService {
  private apiClient: ApiClient;
  private downloadListeners: Map<string, Set<(progress: DownloadProgress) => void>> = new Map();
  private currentDownloads: Map<string, AbortController> = new Map();

  constructor(apiClient: ApiClient) {
    this.apiClient = apiClient;
  }

  /**
   * 获取已安装模型列表
   */
  async getInstalledModels(): Promise<InstalledModel[]> {
    const response = await this.apiClient.call('services.ollama.list_models', {});
    return response.data.models;
  }

  /**
   * 搜索可用模型
   */
  async searchModels(query: string, page: number = 1): Promise<{
    models: AvailableModel[];
    total: number;
    hasMore: boolean;
  }> {
    const response = await this.apiClient.call('services.ollama.search_models', {
      query,
      page,
      limit: 20,
    });
    return response.data;
  }

  /**
   * 开始下载模型，通过 SSE 接收进度
   */
  async pullModel(
    modelName: string,
    onProgress: (progress: DownloadProgress) => void
  ): Promise<void> {
    // 注册进度监听器
    if (!this.downloadListeners.has(modelName)) {
      this.downloadListeners.set(modelName, new Set());
    }
    this.downloadListeners.get(modelName)!.add(onProgress);

    const abortController = new AbortController();
    this.currentDownloads.set(modelName, abortController);

    try {
      const response = await this.apiClient.callSSE(
        'services.ollama.pull_model',
        { model_name: modelName },
        abortController.signal
      );

      // 解析 SSE 流式响应
      for await (const event of response) {
        const progress: DownloadProgress = JSON.parse(event.data);
        this.notifyListeners(modelName, progress);

        if (progress.status === 'completed') {
          break;
        }
        if (progress.status === 'failed') {
          throw new Error(progress.error || 'Download failed');
        }
      }
    } finally {
      this.downloadListeners.delete(modelName);
      this.currentDownloads.delete(modelName);
    }
  }

  /**
   * 暂停下载
   */
  pauseDownload(modelName: string): void {
    const controller = this.currentDownloads.get(modelName);
    if (controller) {
      controller.abort();
    }
  }

  /**
   * 删除模型
   */
  async deleteModel(modelName: string): Promise<void> {
    await this.apiClient.call('services.ollama.delete_model', {
      model_name: modelName,
    });
  }

  /**
   * 获取模型详细信息
   */
  async getModelInfo(modelName: string): Promise<{
    modelfile: string;
    parameters: Record<string, unknown>;
    template: string;
    details: {
      format: string;
      family: string;
      parameterSize: string;
      quantizationLevel: string;
    };
    size: number;
  }> {
    const response = await this.apiClient.call('services.ollama.show_model', {
      model_name: modelName,
    });
    return response.data;
  }

  /**
   * 切换当前使用的模型
   */
  async switchModel(modelName: string): Promise<void> {
    await this.apiClient.call('services.ollama.set_default_model', {
      model_name: modelName,
    });
    // 更新本地记录
    await this.updateLastUsed(modelName);
  }

  /**
   * 获取硬件信息
   */
  async getHardwareInfo(): Promise<HardwareInfo> {
    const response = await this.apiClient.call('services.ollama.hardware_info', {});
    return response.data;
  }

  /**
   * 获取模型推荐
   */
  async getRecommendations(): Promise<ModelRecommendation[]> {
    const hw = await this.getHardwareInfo();
    const response = await this.apiClient.call('services.ollama.recommend_models', {
      hardware: hw,
      useCase: 'general', // 根据用户使用场景可调整
    });
    return response.data.recommendations;
  }

  /**
   * 检查模型更新
   */
  async checkUpdates(): Promise<{
    modelName: string;
    currentDigest: string;
    latestDigest: string;
    hasUpdate: boolean;
  }[]> {
    const response = await this.apiClient.call('services.ollama.check_updates', {});
    return response.data.updates;
  }

  /**
   * 获取存储概览
   */
  async getStorageOverview(): Promise<{
    models: { name: string; size: number; lastUsed: number }[];
    totalSize: number;
    diskFree: number;
    canDownloadMore: boolean;
  }> {
    const response = await this.apiClient.call('services.ollama.storage_overview', {});
    return response.data;
  }

  private notifyListeners(modelName: string, progress: DownloadProgress): void {
    const listeners = this.downloadListeners.get(modelName);
    if (listeners) {
      listeners.forEach(fn => fn(progress));
    }
  }

  private async updateLastUsed(modelName: string): Promise<void> {
    await this.apiClient.call('services.ollama.update_last_used', {
      model_name: modelName,
    });
  }
}
```

## 九、设计决策记录

### D-01：模型管理架构

- **问题**：模型管理功能应该放在前端（直连 Ollama）还是后端（通过 YiAi 代理）
- **选项**：前端直连 Ollama API、通过 YiAi 代理、混合模式
- **选择**：通过 YiAi 代理
- **理由**：安全性——不暴露 Ollama 11434 端口到浏览器；统一认证——模型管理复用 YiAi 的认证和权限控制；简化前端——前端只需调用 RPC 接口，无需处理 Ollama 协议细节；易于扩展——后续可添加模型使用统计、配额管理等后端功能。

### D-02：下载进度推送协议

- **问题**：如何将 Ollama 的下载进度实时推送到前端
- **选项**：轮询、SSE、WebSocket、长轮询
- **选择**：SSE（Server-Sent Events）
- **理由**：Ollama pull API 本身就是流式 JSON（每行一个状态），SSE 完美匹配。YiAi 已有 SSE 基础设施（聊天流式响应），无需引入新依赖。WebSocket 对于单向数据流是过度设计，轮询会导致不必要的请求开销。

### D-03：模型推荐算法

- **问题**：如何基于用户硬件推荐合适的模型
- **选项**：固定规则表、LLM 推荐、用户调研
- **选择**：固定规则表 + 用户可调参数
- **理由**：模型推荐的核心逻辑是内存匹配（模型参数大小 * 量化系数 <= 可用 RAM 的 70%），规则简单明确。LLM 推荐引入额外的推理开销和不确定性。提供"使用场景"筛选（通用、编程、写作、分析）作为辅助过滤条件。

### D-04：离线模型检测

- **问题**：如何判断模型是否可用（离线 vs 需要 Ollama 运行）
- **选项**：仅检测模型是否已下载、检测 Ollama 服务是否运行、两者都检测
- **选择**：两者都检测
- **理由**：已下载的模型在 Ollama 未运行时不可用，仅检测下载状态会误导用户。同时检测下载状态和 Ollama 服务状态，提供准确的三态指示：在线可用（绿色）、已下载但 Ollama 未运行（黄色）、未下载（灰色）。

## 回归问题预测

| # | 预测问题 | 原因 | 验证方法 |
|---|---------|------|---------|
| 1 | ModelService 在 Service Worker 中运行时，SSE 连接因 Service Worker 生命周期限制被意外终止，导致下载进度中断 | Service Worker 在空闲时会被浏览器终止，正在进行的 SSE 连接也会断开 | 使用 `chrome.runtime.connect` 维持长连接，或在下载时使用 `chrome.storage.session` 持续写入进度保持 SW 活跃 |
| 2 | 下载进度 SSE 解析时，Ollama 返回的部分 JSON 行被截断（TCP 分片），导致 JSON.parse 抛出异常，进度条卡住 | SSE 流式数据可能在任何位置被分片，前端可能收到不完整的 JSON 行 | 实现 SSE 数据缓冲器，累积不完整的行直到收到完整 JSON 再解析，参考 `SSEClient` 已有的行缓冲逻辑 |
| 3 | 用户删除模型后，其他标签页的模型选择器仍显示已删除的模型，点击切换时报错 | 模型列表数据未跨标签页同步，其他标签页仍使用旧缓存 | 在 `ModelService` 中监听 `chrome.storage.onChanged` 事件，模型列表变更时自动刷新所有标签页的 UI |
| 4 | 硬件检测在 Windows 上通过 `wmic` 获取 GPU 信息时，因权限不足或命令不存在而失败，返回空的 GPU 信息 | 不同操作系统的硬件检测工具不同，`nvidia-smi` 可能未安装，`wmic` 可能被禁用 | 实现多策略硬件检测：1) nvidia-smi 2) wmic 3) 前端 `navigator.gpu` (WebGPU API) 4) 降级为仅 CPU 推荐 |
| 5 | 模型推荐中，8GB RAM 用户被推荐了 7B 模型（约需 4GB），但浏览器本身占用 2GB+，实际可用内存不足，导致模型加载后系统卡顿 | 推荐算法仅考虑模型大小，未考虑浏览器和其他应用的内存占用 | 推荐算法使用 `可用内存 * 0.6` 作为上限（保留 40% 给系统和其他应用），并对内存紧张的设备推荐更小的模型（如 3B） |
| 6 | 用户下载模型时关闭了浏览器标签页，但下载仍在 Service Worker 中继续，重新打开后无法看到下载进度，导致重复下载 | 下载任务在 SW 中运行，但 UI 状态丢失，用户以为下载失败重新点击 | 使用 `chrome.storage.session` 持久化下载任务状态，UI 重新打开时从 storage 恢复进度条和状态 |
