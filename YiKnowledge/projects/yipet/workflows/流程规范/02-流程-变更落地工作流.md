# 变更落地工作流

> 代码变更完成后的收口流程：确保代码与规范文档同步，验证一致性，提交推送。

## 一、适用场景

当对代码做了修改（Bug 修复、功能调整、API 变更等），且这些修改涉及 `openspec/changes/` 下的某个变更时，必须执行此流程确保代码和文档保持同步。

## 二、流程步骤

```
代码修改完成
  │
  ▼
1. 回写 OpenSpec 产出物
  │  - 对照代码变更，更新 spec.md 中的场景描述
  │  - 更新 tasks.md，标记已完成任务并修正描述
  │  - 新增行为：在 spec 中添加 ADDED Requirements
  │  - 删除行为：从 spec 中移除对应场景或字段
  │
  ▼
2. 验证（opsx:verify <change-name>）
  │  - 检查完整性（completeness）
  │  - 检查正确性（correctness）
  │  - 检查一致性（coherence）
  │  - CRITICAL 问题必须修复
  │  - WARNING 记录但不阻塞流程
  │
  ▼
3. ⏸️ 确认卡点：是否提交并推送？
  │  - 询问用户是否继续提交推送
  │  - 用户可选择：全部提交 / 仅提交不推送 / 跳过提交
  │  - 用户可在此步骤审查验证结果后再决定
  │
  ▼
4. 提交并推送（用户确认后执行）
  │  - 代码和产出物变更一起提交
  │  - 提交信息描述实际改动内容
  │
  ▼
完成
```

## 三、回写原则

### spec 回写

代码改了什么，spec 就描述什么。决不允许 spec 和代码不一致：

| 变更类型 | 回写操作 |
|----------|----------|
| 移除字段/组件 | 从场景字段列表中删除对应字段 |
| 新增功能 | 添加 ADDED Requirements 或在现有场景中补充 |
| 修改行为 | 更新场景的 WHEN/THEN 描述 |
| 修改 API 调用 | 更新 spec 中的 ApiClient 方法签名和参数说明 |
| 修改 IPC 通信 | 更新 spec 中的 IPC Relay 消息格式（action-based + dispatchSecureEvent） |

### tasks 回写

- 已完成的代码改动，在 tasks 中标记 `[x]`
- 更新任务描述使其准确反映实际实现
- 如果实现与原任务描述有偏差，修正描述而非保留旧描述

### 不回写的情况

纯 Bug 修复（不涉及 spec 定义的变更）时，可以只改代码不回写 spec。判断标准：

- 修复的是已有功能的错误行为 → 不需要回写
- 改变了已有功能的行为定义 → 需要回写
- 修改了 API 契约（参数名、返回结构）→ 必须回写

## 四、验证检查项

### 完整性检查

- [ ] spec.md 中的所有场景都有对应的代码实现
- [ ] 代码中的所有新增功能都在 spec 中有对应描述
- [ ] tasks.md 中的所有任务状态正确（已完成/未完成）

### 正确性检查

- [ ] spec 中描述的字段名与代码中的实际字段名一致
- [ ] API 参数名遵守 RPC 协议约定（`filter` 而非 `query`，`target_file` 而非 `path`）
- [ ] ApiClient 四层调用链正确（Component → Chat Store（Pinia）→ ApiClient → fetch）
- [ ] IPC Relay 消息格式正确（action-based 判别联合 + IPC_SECRET + 时间戳验证）

### 一致性检查

- [ ] spec 中的组件引用与实际使用的组件一致
- [ ] i18n key 在 spec 和代码中一致
- [ ] Chrome API 权限声明在 spec 和 manifest.json 中一致
- [ ] 双世界执行边界在 spec 和代码中一致（ISOLATED vs MAIN world）

## 五、YiPet 特定检查

### Chrome 扩展检查

- [ ] manifest.json 中的权限声明与实际使用的 API 一致
- [ ] Content Script 和 Service Worker 的职责边界清晰
- [ ] `chrome.storage` 读写操作有错误处理
- [ ] 消息通信使用 `chrome.runtime.sendMessage` 标准接口

### API 调用检查

- [ ] 所有 API 调用通过 ApiClient 封装，不直接使用 fetch
- [ ] RPC 信封格式正确：`{module_name, method_name, parameters}`
- [ ] SSE 流式响应有断连检测和重试机制
- [ ] 跨域请求在 manifest.json 中声明了 host_permissions

### 构建与发布检查

- [ ] Rsbuild 多入口配置正确（content + service worker + popup）
- [ ] CDN 资源加载策略正确（外部依赖通过 CDN 引入）
- [ ] 扩展包体积在 Chrome Web Store 限制内

## 六、使用方式

在 Claude Code 中执行 `/opsx:land <change-name>` 一键执行完整流程。

其他 AI 工具参考本文档手动执行：回写 → 验证 → 确认 → 提交。

## 七、示例

**场景**：修复 Chat Store 中 SSE 流式消息的 token 缓冲问题，将 50ms 批量改为 30ms。

**回写操作**：
- `spec.md`：更新"SSE 流式渲染"场景中的缓冲时间描述
- `tasks.md`：更新任务 2.3 的描述，标注参数变更

**验证**：`opsx:verify chat-sse-buffer` → 检查 SSE 流、Chat Store、ApiClient 一致性 → 无 CRITICAL 问题

**确认**：用户审查验证结果，确认继续 → 提交并推送

**提交**：`fix: 优化 SSE token 缓冲时间 50ms → 30ms`
