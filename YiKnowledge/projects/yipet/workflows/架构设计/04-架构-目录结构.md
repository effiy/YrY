## 二、目录职责速查

| 目录 | 职责 | 运行环境 | 框架 | 禁止 |
|------|------|----------|------|------|
| `api/` | HTTP 请求封装、RPC 信封、SSE 解析 | 所有环境 | 原生 TS | 直接使用 fetch |
| `background/` | 命令分发、消息路由、chrome API 调用 | Service Worker | 原生 TS | 访问 DOM |
| `chat/` | 聊天窗口 UI、流式消息处理、状态管理 | MAIN World | Vue 3 | 使用 chrome.* API |
| `content/` | 双世界注入、跨世界通信、宠物渲染 | ISOLATED + MAIN | 原生 TS | 混用两个世界的状态 |
| `popup/` | 皮肤中心、配置管理 | 扩展弹窗 | Vue 3 | 访问页面 DOM |
| `shared/` | 国际化、存储封装、工具函数 | 所有环境 | 原生 TS | 依赖特定世界的 API |
| `types/` | 全局类型声明 | 编译时 | — | 包含运行时逻辑 |

## 三、多入口构建

| 入口 | 配置文件 | 输出 | 目标环境 | 构建约束 |
|------|----------|------|----------|----------|
| popup | `rsbuild.config.ts` | `dist/popup.html` + `popup.js` | 扩展弹窗 | 独立 HTML，可代码分割 |
| background | `rsbuild.config.ts` | `dist/assets/background.js` | Service Worker | 单文件，禁用代码分割 |
| chat | `rsbuild.config.chat.ts` | `dist/assets/chat.js` | MAIN World 注入 | 禁用文件名哈希 |
| cdn | `rsbuild.config.cdn.ts` | `dist/cdn/` | 按需注入 | 独立 chunk，可缓存 |
| bootstrap | `rsbuild.config.bootstrap.ts` | `dist/assets/bootstrap.js` | Content Script | 单文件，轻量（< 50KB） |

### 构建约束

| 约束 | 说明 | 原因 | 影响入口 |
|------|------|------|----------|
| 文件名哈希禁用 | 输出固定文件名（如 `chat.js`） | MV3 manifest 引用固定路径 | 所有 |
| 代码分割禁用 | Service Worker 单文件输出 | Service Worker 不支持动态导入 | background, bootstrap |
| 自动导入 | Vue API + Pinia | unplugin-auto-import 减少手动导入 | chat, popup |
| 构建元数据 | 自动生成 `dist/build-meta.json` | 版本追踪和调试 | 所有 |
| 外部化 CDN 依赖 | Vue/Bootstrap 等不打包到 chat.js | 减少体积，多入口共享 | chat |

### 构建命令

```bash
npm run dev           # 开发模式（所有入口 watch）
npm run build         # 生产构建（所有入口）
npm run build:chat    # 仅构建聊天窗口
npm run build:cdn     # 仅构建 CDN 资源
npm run typecheck     # TypeScript 类型检查
npm run lint:eslint   # ESLint 检查
npm run lint:prettier # Prettier 格式化
```

## 四、模块依赖关系

### 依赖方向

```
chat/ + popup/ ──────────── UI 层（Vue 3）
  │ 依赖
  ▼
api/services/ ───────────── 服务层
  │ 依赖
  ▼
api/client.ts ───────────── ApiClient 核心
  │ 依赖
  ▼
YiAi Backend ────────────── 后端服务（HTTP :10086）
```

### 跨世界依赖

```
┌─ MAIN World ─────────────────────────────────────┐
│  chat/（Vue 3 SPA）                               │
│  content/rendering/overlay.ts（DOM 渲染）          │
│    │ 需要 chrome API 时                            │
│    │ dispatchSecureEvent('yipet:...', { ... })       │
│    ▼                                               │
├─ ISOLATED World ─────────────────────────────────┤
│  content/ipc/relay.ts（消息验证 + 转发）           │
│    │ chrome.runtime.sendMessage({ action: ... })    │
│    ▼                                               │
├─ Service Worker ─────────────────────────────────┤
│  background/index.ts（命令分发 + 消息路由）         │
│    │ chrome.* API                                  │
│    ▼                                               │
└─ Chrome Browser ─────────────────────────────────┘
```

### 禁止的依赖方向

```
❌ chat/ → chrome.* API          （MAIN World 不可用）
❌ chat/ → content/state         （跨世界隔离）
❌ background/ → DOM             （Service Worker 无 DOM）
❌ popup/ → 页面 DOM              （弹窗隔离）
❌ content/ → background/ 状态    （通过消息通信）
```

## 六、设计决策

### 为什么使用 4-Tier API 架构？

ApiClient → Endpoints → Types → Services 的分层设计：
- **ApiClient**：统一的 fetch 封装，处理拦截、重试、错误、Token 管理
- **Endpoints**：路径常量集中管理，避免硬编码，一处修改全局生效
- **Types**：请求/响应类型定义，确保 TypeScript strict 模式下的类型安全
- **Services**：领域服务类，封装业务逻辑，提供清晰的调用接口

修改后端 API 时只需更新 Endpoints 和 Types，不影响上层调用。

### 为什么 Chat Window 在 MAIN World 而非 ISOLATED World？

MAIN World 可以访问页面的 DOM 和 window 全局变量，Chat Window 需要完整的 DOM 操作能力和 Vue 3 运行环境。ISOLATED World 的 Content Script 环境受限，不适合运行完整的 SPA。此外，MAIN World 中的 Vue 实例可以访问页面上下文信息（如页面标题、URL、选中文本）。

### 为什么使用多入口构建而非单一入口？

Chrome 扩展的不同部分运行在不同的上下文中（弹窗、Service Worker、Content Script、页面注入），各自有不同的构建约束。多入口构建允许每个入口独立配置，优化各自的输出。例如：Service Worker 必须单文件输出，弹窗可以代码分割。

### 为什么使用 CDN 资源而非打包所有依赖？

Vue 3、Bootstrap 等大型库如果打包到每个入口会导致重复和体积膨胀。CDN 资源按需注入，多个入口共享同一份资源，减少总体积。同时，CDN 资源可以被浏览器缓存，加快后续页面加载速度。

## 七、新增模块指南

### 新增 API Service

1. 在 `src/api/services/` 下创建 `<Domain>Service.ts`
2. 在构造函数中接收 `ApiClient` 实例
3. 在 `src/api/types.ts` 中添加请求/响应类型
4. 在 `src/api/index.ts` 的 `createApiServices` 中注册
5. 确保参数名遵循 RPC 契约（`filter` 非 `query`，`target_file` 非 `path`）

### 新增聊天组件

1. 在 `src/chat/components/` 下创建 `.vue` 文件
2. 在 `ChatWindow.vue` 中引入并使用
3. 如需状态管理，通过 Pinia store 访问
4. 如需持久化，通过 Chat Store（Pinia）的 watch 自动写入 chrome.storage

### 新增 Popup 功能

1. 在 `src/popup/components/` 下创建 `.vue` 文件
2. 在 `App.vue` 中引入
3. 配置数据通过 `chrome.storage.local` 持久化
4. 变更通过 `chrome.tabs.sendMessage` 通知 Content Script

### 新增 Content Script 功能

1. 在 `src/content/` 下创建模块文件
2. 如需跨世界通信，在 `relay.ts` 的 `setupMessageRelay` 中添加消息处理
3. 如需 DOM 渲染，在 `rendering/` 下创建渲染模块
4. 确保不混用 ISOLATED 和 MAIN World 的状态

## 八、反模式

| 反模式 | 错误示例 | 正确做法 | 原因 |
|--------|----------|----------|------|
| 跨世界直接导入 | `import { state } from "../content/state"` 在 chat/ 中 | 通过 IPC Relay 通信 | 两个世界隔离 |
| 在 chat/ 中使用 chrome API | `chrome.storage.local.get()` | 通过 IPC Relay 请求 | MAIN World 无 chrome API |
| 在 background/ 中操作 DOM | `document.querySelector()` | 通过消息通知 Content Script | Service Worker 无 DOM |
| 循环依赖 | `api/ → chat/ → api/` | 遵循分层依赖方向 | 构建失败 |
| 硬编码路径 | `fetch("http://localhost:10086")` | 使用 `API_BASE` 环境变量 | 不可配置 |
| 在 popup 中直接操作页面 | `document.querySelector(".pet")` | 通过消息通知 Content Script | 弹窗隔离 |

## 九、约束

### 必须遵守
- 遵循分层依赖方向：UI → Service → ApiClient → Backend
- 跨世界通信通过 IPC Relay，不直接导入跨世界模块
- 文件命名遵循约定（PascalCase 组件、camelCase 模块、kebab-case 目录）
- 新增 API 调用时验证参数名遵循 RPC 契约
- 构建禁用文件名哈希和代码分割（background、bootstrap）

### 禁止
- 不在 chat/ 中直接导入 content/ 模块
- 不在 background/ 中操作 DOM
- 不在 popup/ 中直接操作页面内容
- 不创建循环依赖
- 不破坏分层架构的依赖方向
