# 项目规范

> YiPet 编码规范、命名约定、代码质量门禁、提交规范、代码审查清单。

## 一、组件风格

强制 `<script setup lang="ts">` + Composition API。Props/Emits 使用泛型：`defineProps<{...}>()`、`defineEmits<{...}>()`。样式 `<style scoped>`。

| 领域 | 标准 | 反模式 |
|------|------|--------|
| 组件风格 | `<script setup lang="ts">` | Options API |
| Props | `defineProps<{...}>()` 泛型 | PropTypes |
| 状态管理 | Pinia Store + Actions | 组件内直接调 API |
| 样式 | `scoped` SCSS | 内联样式、全局污染 |
| 路径导入 | `@/` 别名 | 深层 `../../../` |
| 类型导入 | `import type` | 运行时导入类型 |

## 二、命名约定

| 约定 | 适用范围 | 示例 |
|------|----------|------|
| PascalCase | 组件、类型/接口、Service 类 | `ChatWindow`, `ApiClient` |
| camelCase | 函数、变量、Store 操作 | `sendMessage`, `currentSessionId` |
| kebab-case | CSS 类名 | `.chat-window` |
| UPPER_SNAKE_CASE | 常量、枚举值 | `DEFAULT_MODEL` |
| snake_case | RPC 信封字段 | `module_name`, `target_file` |

### 文件命名

| 类型 | 命名 | 示例 |
|------|------|------|
| Vue 组件 | PascalCase 目录 + `index.vue` | `ChatWindow/index.vue` |
| Store | camelCase | `stores/chat.ts` |
| API Service | PascalCase + `Service` | `ChatService.ts` |
| 入口文件 | camelCase | `bootstrap.ts` |

### 导入顺序

Vue 核心 → 第三方库 → Store → API Services → Hooks/Utils → 组件 → 类型导入

## 三、TypeScript 规则

- 接口用于对象形状，类型别名用于联合/交叉类型
- 禁止 `any`（用 `unknown` + 类型收窄）、`as` 断言（用类型收窄）、`@ts-ignore`、`!` 非空断言（用 `?.`/`??`）

## 四、代码质量门禁

| 阶段 | 检查 | 失败行为 |
|------|------|----------|
| 保存时 | Prettier 格式化 | 自动修复 |
| 保存时 | ESLint 自动修复 | 自动修复 |
| pre-commit | lint-staged（ESLint + Stylelint） | 阻止提交 |
| commit-msg | commitlint | 阻止提交 |
| CI | `vue-tsc --noEmit` + `npm run build` | 阻止构建 |

**工具链**：TypeScript 6.x（strict）、ESLint 10、Prettier 3、Stylelint 17、Husky 9、lint-staged 17、commitlint 21、Vitest 2

## 五、提交规范

Conventional Commits：`<type>: <description>`。类型：feat/fix/refactor/style/docs/perf/test/chore/ci。

提交频率：每完成一个功能点或修复一个 Bug 后提交，避免一个提交包含多个不相关修改。提交前运行 `typecheck` 和 `build`。

## 六、代码审查清单

**架构**：正确使用 ApiClient（非直接 fetch）、遵守 4-Tier API、使用 `chrome.i18n.getMessage`（非硬编码）、遵守双世界边界。

**类型**：避免 `any`、Props 明确接口、API 请求/响应明确类型、`vue-tsc --noEmit` 通过。

**设计**：避免不必要抽象、不添加未要求功能、命名符合约定、导入顺序正确。

**Chrome 扩展**：MV3 CSP 合规（无远程代码/eval/内联脚本）、`dispatchSecureEvent` 跨世界通信、`chrome.storage` 持久化、manifest 权限声明正确。

## 七、架构约束

**必须遵守**：4-Tier API 架构、禁止直接 fetch、RPC 信封格式、参数名契约（`filter`/`target_file`/`cname`）、双世界边界、Pinia Store 模式。

**禁止**：组件中直接 fetch、API Service 层外组装 RPC 信封、MAIN 世界调 chrome.*、ISOLATED 世界操作页面 DOM、`any` 类型、单次使用创建抽象、`eval`/`new Function`。
