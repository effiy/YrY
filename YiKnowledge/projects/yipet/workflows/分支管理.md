# 分支管理规范

> 本文档定义 YiPet 项目的分支策略、环境映射、发布流程。

---

## 一、分支与环境映射

| 分支 | 环境 | 用途 |
|------|------|------|
| `dev` | dev | 开发联调环境 |
| `test` | sit | 系统集成测试环境 |
| `release` | uat | UAT 验证通道 |
| `master` | prod | 生产代码快照（保持分支，不参与构建） |

YiPet 是 Chrome 扩展项目，无 CI/CD 自动部署。环境映射主要用于：

- **dev**: 本地开发，加载 `dist/` 为未打包扩展
- **test**: 内部测试，打包 `.zip` 分发给测试团队
- **release**: UAT 验证，打包发布候选版本
- **master**: 生产代码，对应 Chrome Web Store 已发布版本

---

## 二、分支核心规则

### 2.1 功能分支到环境分支（单向）

功能分支独立合入各环境分支，环境分支之间不存在合并关系：

```
feat-A ──┬──→ dev
         ├──→ test
         └──→ release
```

- `dev` 不合入 `test`
- `test` 不合入 `release`
- 各环境分支独立维护

### 2.2 master 是保持分支

- master 不参与构建，只做记录
- 保持与 Chrome Web Store 已发布版本一致
- 每次发布后，从 release 合入 master 并打 tag
- 紧急 hotfix 可从 master 切出

### 2.3 master 回汇

生产发布后，需将 master 合回 `release` / `test` / `dev`，同步已发布代码，避免后续迭代丢失 hotfix 内容。

---

## 三、正常迭代发布流程

### 3.1 流程

```
feat-A,B,C ──┬──→ dev        → 本地开发验证
             ├──→ test       → 内部测试验证
             └──→ release    → UAT 验证
                                    │
                              验证通过 │
                                    ↓
                          release 打包 .zip → 上传 Chrome Web Store
                                    │
                                    ↓
                          release → master（打 tag）
                                    │
                                    ↓
                          master → 回汇 release / test / dev
```

### 3.2 步骤

1. 功能分支合入 `dev` → 本地加载验证
2. 功能分支合入 `test` → 打包 `.zip` 分发给测试团队
3. 功能分支合入 `release` → 打包发布候选版本，内部 UAT 验证
4. UAT 验收通过 → 打包 `.zip` → 上传 Chrome Web Store
5. 将 `release` 合入 `master`，打 tag（如 `v1.3.0`）
6. 将 `master` 回汇到 `release` / `test` / `dev`

---

## 四、Hotfix 流程

### 4.1 流程

```
master 切出 hotfix 分支
    │
    ├── 修复 bug
    ├── 合入 dev → 本地验证
    ├── 合入 test → 测试验证
    │
    ▼ 验证通过
hotfix 打包 .zip → 上传 Chrome Web Store
    │
    ▼
hotfix → master（打 tag）
    │
    ▼
master → 回汇 release / test / dev
```

### 4.2 步骤

1. 从 `master` 切出 hotfix 分支
2. 修复 bug，提交代码
3. 合入 `dev` → 本地验证
4. 合入 `test` → 测试验证
5. 验证通过 → 打包 `.zip` → 上传 Chrome Web Store
6. 将 hotfix 合入 `master`，打 tag（如 `v1.3.1-hotfix`）
7. 将 `master` 回汇到 `release` / `test` / `dev`
8. 删除 hotfix 分支

---

## 五、分支命名规范

| 类型 | 格式 | 示例 |
|------|------|------|
| 功能分支 | `feat/[描述]` | `feat/chat-export-markdown` |
| 修复分支 | `fix/[描述]` | `fix/api-filter-param` |
| 热修复分支 | `hotfix/[描述]` | `hotfix/csp-violation-fix` |
| 发布分支 | `release` | `release` |
| 生产快照 | `master` | `master` |

---

## 六、Tag 规范

| 场景 | Tag 格式 | 示例 |
|------|---------|------|
| 主迭代发布 | `v{major}.{minor}.{patch}` | `v1.3.0` |
| Hotfix 发布 | `v{major}.{minor}.{patch}-hotfix` | `v1.3.1-hotfix` |

每次 Chrome Web Store 发布后必须打 tag，标记生产代码快照。

---

## 七、版本号规则

遵循语义化版本（SemVer）：

| 版本号 | 变更类型 |
|--------|---------|
| **Major** (X.0.0) | 不兼容的 API 变更、重大架构调整 |
| **Minor** (0.X.0) | 向后兼容的功能新增 |
| **Patch** (0.0.X) | 向后兼容的 bug 修复 |

### 当前版本

YiPet 当前版本为 `1.2.0`（定义于 `manifest.json` 的 `version` 字段）。

---

## 八、流程速查表

| 场景 | 操作 |
|------|------|
| 功能开发 | feat → 合入 dev → 本地验证 → 合入 test → 测试验证 → 合入 release |
| 主迭代发布 | release 打包 → UAT 验证 → 上传 Chrome Web Store → 合入 master 打 tag → 回汇 |
| 紧急修复 | master 切 hotfix → 修 bug → 合入 dev/test → 验证 → 打包上传 → 合入 master 打 tag → 回汇 → 删 hotfix |
| 版本回退 | 从 master 历史 tag 切出修复分支，按 hotfix 流程处理 |

---

## 九、Chrome Web Store 注意事项

- 版本号必须在 `manifest.json` 中更新
- 提交审核前确保 `npm run build` 成功
- `.zip` 包仅包含 `dist/` 目录内容
- 提交时需提供更新说明（What's new）
- 审核周期通常为 1-3 个工作日
- 紧急更新可申请快速审核（limited quota）
