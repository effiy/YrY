# 扩展未使用 chrome.alarms API 定期心跳保活

## 现象

`manifest.json` 的 `permissions` 仅包含 `["storage", "scripting"]`，未申请 `"alarms"` 权限。Service Worker (`background/index.ts`) 仅响应 `chrome.commands.onCommand` 和 `chrome.runtime.onInstalled` 事件。

Chrome MV3 Service Worker 在空闲约 30 秒后会被终止。当 SW 终止后：
- 键盘快捷键（`Ctrl+Shift+X`）在 SW 重新启动前无效
- 状态恢复需要等待 SW 冷启动（约 50-200ms）
- `chrome.runtime.onMessage` 监听器在 SW 休眠期间丢失

## 根因分析

- 开发者认为 `chrome.commands` 会触发 SW 自动唤醒（确实会），但延迟可感知
- 未使用 `chrome.alarms` 创建定期心跳保持 SW 活跃
- Bug #2 已修复了 SW 空闲后 IPC 消息丢失，但本缺陷关注的是保持 SW 活跃以避免冷启动

## 涉及文件

- `manifest.json:7` — 缺少 `"alarms"` 权限
- `src/background/index.ts` — 无心跳逻辑

## 修复方案

1. 添加 `"alarms"` 权限
2. 创建每分钟的心跳 alarm：`chrome.alarms.create('heartbeat', { periodInMinutes: 1 })`
3. 在心跳回调中执行轻量操作（检查存储版本是否过期）
4. 或仅在 `persistent: false` 时接受冷启动延迟（权衡电池消耗）


## 影响范围

**影响模块**：`manifest.json` 权限配置和 `src/background/index.ts` Service Worker。
**影响用户**：SW 空闲终止后，键盘快捷键和消息响应有 50-200ms 冷启动延迟。对延迟敏感的用户可能感知到响应迟钝。
**影响范围**：所有需要通过 Service Worker 中转的功能（Popup 消息、键盘快捷键、扩展图标点击）。
## 预防措施

| 层面 | 措施 | 责任人 |
|------|------|--------|
| 架构 | 评估 SW 冷启动延迟对用户体验的影响，决定是否需要 keep-alive | 架构师 |
| 代码 | 如果启用 keep-alive，使用 `chrome.alarms` 而非 `setInterval`（SW 终止后 `setInterval` 丢失） | 开发者 |
| 权衡 | keep-alive 会增加电池消耗，需权衡用户体验和功耗 | 架构师 |


## 经验教训

Chrome MV3 Service Worker 的空闲终止是设计行为，不是 bug。虽然可以通过 `chrome.alarms` 保持 SW 活跃，但这样做的代价是电池消耗。大多数场景下，接受 50-200ms 的冷启动延迟是更好的选择。关键是让冷启动对用户透明——在 UI 上给即时反馈，后台异步完成 SW 唤醒。
