# 缺少聊天 Store 和 API 服务层的单元测试覆盖

## 现象

YiPet 测试套件（898 行，12 个测试文件）仅覆盖配置、工具和共享模块，缺少以下关键路径的测试：

| 模块 | 测试状态 |
|------|---------|
| `chat/stores/chat.ts` (1615 行) | 无测试 |
| `api/client.ts` (SSE 流式处理) | 仅 endpoint 常量测试 |
| `api/services/*.ts` (会话/知识库/RAG/聊天) | 无测试 |
| `background/index.ts` (消息路由) | 无测试 |
| `content/rendering/overlay.ts` (宠物覆盖层) | 无测试 |
| `content/ipc/relay.ts` (跨世界通信) | 无测试 |

## 根因分析

- 测试框架配置为 `jsdom` 环境，但 Chrome 扩展 API（`chrome.storage`、`chrome.runtime`）需要 mock
- Chat store 高度依赖 API 服务层和浏览器 API，难以隔离测试
- 测试基础设施未建立 Chrome API mock 模式

## 涉及文件

- `tests/` — 缺少上述模块的测试文件
- `vitest.config.ts` — 需要配置 Chrome API mock

## 修复方案

1. 创建 `tests/__mocks__/chrome.ts` mock Chrome API（storage、runtime、tabs）
2. 为 API 服务层编写单元测试（mock fetch/ApiClient）
3. 为 chat store 核心逻辑（session CRUD、消息管理）编写测试
4. 优先覆盖：消息发送/接收、会话持久化、RAG 范围切换


## 影响范围

**影响模块**：`chat/stores/chat.ts`（1615 行）、`api/client.ts`、`api/services/*.ts`、`background/index.ts`、`content/` 等核心模块。
**影响用户**：缺乏测试覆盖意味着回归 bug 可能在不知情的情况下引入，用户遇到未检测到的问题。
**影响范围**：扩展的所有核心功能（聊天、API 通信、Service Worker、Content Script）。
## 预防措施

| 层面 | 措施 | 责任人 |
|------|------|--------|
| 流程 | 新功能开发时同步编写测试，不允许无测试的 PR 合并 | 开发者 |
| 目标 | 核心模块（store、API）测试覆盖率目标 60%+ | QA |
| 基础设施 | 创建 `tests/__mocks__/chrome.ts` mock Chrome API | 开发者 |
| 优先 | 优先覆盖消息发送/接收、会话持久化、RAG 范围切换等关键路径 | QA |


## 经验教训

测试基础设施的缺失会形成恶性循环：因为难写测试所以不写，因为没有测试所以代码耦合度越来越高，更难测试。投资 Chrome API mock 基础设施是一次性成本，但收益是持续的——它让所有后续开发都可以享受测试保护。
