# notify/persist 等工具函数缺少统一的错误报告

## 现象

YiPet 中有多处静默失败的工具函数——`persistSetting`、`copyMessage`、`notify` 等——失败时仅捕获异常但不产生任何形式的错误报告：

```typescript
// persistSetting — 静默失败
function _persistSetting(key: string, value: unknown) {
  chrome.storage.local.set({ [key]: value }).catch(() => {});
}

// copyMessage — 剪贴板静默失败  
navigator.clipboard.writeText(text).catch(() => {});
```

虽然这些是"尽力而为"操作，但没有任何机制（console.warn、ErrorCounter、EventEmitter）让开发者或用户感知这些失败。

## 根因分析

- 没有统一的错误报告中间层
- `console.warn` 分散在少数文件中（`popup/services/chrome.ts`），但没有全局约定
- 开发者需要主动检查 console 才能发现存储/剪贴板失败

## 涉及文件

- `src/chat/stores/chat.ts` — `_persistSetting`、`copyMessage`
- `src/content/state/persistence.ts` — 存储持久化
- `src/shared/i18n/locale.ts` — locale 存储
- `src/content/ipc/relay.ts` — IPC 状态持久化

## 修复方案

1. 创建 `src/utils/report.ts` 统一错误报告函数
2. 在生产环境用 `console.warn`，开发环境用 `console.error`
3. 或在 `window.__YIPET_ERRORS__` 中累积错误计数，通过 `window.YiPet.help()` 暴露


## 影响范围

**影响模块**：整个扩展的错误处理路径。
**影响用户**：错误发生时，用户可能看到不一致的错误提示或无任何反馈，无法判断问题是网络、后端还是扩展自身导致的。
**影响范围**：所有模块的错误处理和用户反馈逻辑。
## 预防措施

| 层面 | 措施 | 责任人 |
|------|------|--------|
| 架构 | 实现 `ErrorReporter` 统一错误收集和上报 | 架构师 |
| 代码 | 所有 catch 块通过 `ErrorReporter.capture(error, context)` 上报 | 开发者 |
| 体验 | 根据错误类型（网络/后端/扩展）提供差异化的用户提示 | 开发者 |
| 监控 | 记录错误频率和类型分布，用于优先级排序 | DevOps |


## 经验教训

统一的错误上报机制是产品成熟度的标志。没有它，团队只能在用户反馈后被动发现 bug。有了它，团队可以主动监控错误趋势，在用户发现之前修复问题。
