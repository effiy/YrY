# background/index.ts 中切换可见性未区分 toggle-pet 无效状态

## 现象

`background/index.ts:56-59` 的 `toggle-pet` 命令处理逻辑中，状态持久化依赖于内容脚本返回的实际可见性：

```typescript
if (response?.success !== undefined) {
  const current = await getTabState(tab.id);
  const nextVisible = response.visible !== undefined ? response.visible : !current.visible;
  await setTabState(tab.id, { visible: nextVisible });
}
```

但如果内容脚本未响应（超时 5 秒后的 reject 在 catch 中被忽略），标签页的持久化状态不会更新。用户下次打开该页面时，popup 显示的宠物状态与实际情况不一致。

此外，`getTabState(tab.id)` 读取的是 Chrome Storage，如果该键从未被初始化，`current.visible` 将是 `undefined`，导致 `!current.visible` 为 `true`——合理但不够明确。

## 根因分析

- 持久化状态更新依赖于 IPC 往返成功
- 单向失败（SW → content script 成功但 content script → SW 响应丢失）下状态不同步
- 没有 SW 端的乐观更新机制

## 涉及文件

- `src/background/index.ts:53-60` — toggle-pet 状态同步

## 修复方案

在 sendMessage 前乐观更新状态：
```typescript
const current = await getTabState(tab.id);
await setTabState(tab.id, { visible: !current.visible }); // 乐观更新
sendMessageWithTimeout(tab.id, msg).catch(() => {
  setTabState(tab.id, { visible: current.visible }); // 回滚
});
```


## 影响范围

**影响模块**：宠物状态切换（可见/隐藏、角色变更、颜色变更）的 Pinia store 逻辑。
**影响用户**：乐观更新失败时，UI 显示的状态与实际状态不一致，用户可能重复点击或困惑于宠物行为异常。
**影响范围**：Popup 控制面板和 Content Script 之间的状态同步。
## 预防措施

| 层面 | 措施 | 责任人 |
|------|------|--------|
| 代码 | 乐观更新必须包含回滚机制——操作失败时恢复 UI 到操作前状态 | 开发者 |
| 代码 | 状态变更操作应记录 pending 状态，操作完成后清除 | 开发者 |
| 体验 | 操作失败时显示非阻塞的 Toast 通知，而非静默回滚 | 开发者 |
| 测试 | 模拟操作失败场景，验证 UI 正确回滚 | QA |


## 经验教训

乐观更新提升用户体验，但必须以可靠的错误处理为前提。先更新 UI 再发起请求是好的，但如果请求失败后 UI 不回滚，用户会困惑于"明明切换了为什么没反应"。乐观更新的黄金法则：乐观更新 + 失败回滚 + 用户通知。
