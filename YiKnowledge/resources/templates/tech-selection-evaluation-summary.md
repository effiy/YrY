# 技术选型评估（Tech Selection Evaluation）摘要

> 本摘要说明选型方法与权衡；空白可填表单见 [tech-selection-evaluation-template.md](./tech-selection-evaluation-template.md)。

## 1. 是什么

选一个技术（框架、库、服务）时做结构化评估：

- 列候选选项
- 定义评估维度（性能、成本、生态、可维护性）
- 标注约束（合规、语言、团队技能）
- 打分排序
- 记录决策（ADR）

## 2. 为什么做

凭直觉选技术的后果：

- 半年后发现生态差，社区萎
- 与现有系统不兼容，集成成本高
- 团队不熟，上手慢
- 厂商绑定，迁移成本爆炸
- 合规问题（GDPR、数据出境、自部署要求）

结构化评估能避免 80% 的此类后悔。

## 3. 候选选项

至少列 3 个：

- 主流方案
- 轻量 / 小众方案（备选）
- "什么都不做"方案（基线对照）

每候选列：

- 出品方与商业模式
- 开源 / 闭源 / SaaS
- 许可证
- 社区活跃度（GitHub stars / commit / release 节奏）
- 主流用户案例

## 4. 评估维度

### 4.1 性能

- 吞吐 / 延迟（与本场景 benchmark）
- 扩展性（水平 / 垂直）
- 资源占用（CPU / 内存 / GPU）

### 4.2 成本

- 直接成本：许可、订阅、API 调用费
- 间接成本：运维、学习、迁移
- 隐性成本：厂商绑定、数据出境、合规

### 4.3 生态

- 社区活跃度（stars、PR、release）
- 文档质量
- 与现有栈兼容性
- 第三方扩展与插件

### 4.4 可维护性

- 学习曲线
- 调试工具
- 监控 / 可观测性
- 升级路径

### 4.5 风险

- 厂商绑定
- 单点维护（单人项目风险）
- 许可证变更历史
- 安全漏洞历史

## 5. 约束

明确不可妥协的约束：

- 合规（数据不出境、自部署要求）
- 性能基线（p99 < Xms）
- 预算上限
- 团队技能（不学新语言）
- 集成（必须与 X 兼容）

约束是用来排除候选的，不是用来打分的。

## 6. 评估方法

### 定量

- benchmark（自己跑，不靠厂商数据）
- 成本计算（3 年总拥有成本 TCO）
- 集成工作量估算（人天）

### 定性

- 团队调研（用过的人反馈）
- 案例研究（同行业落地）
- PoC（关键场景跑通）

### 打分

每维度 1-5 分，加权求和。权重根据场景：

- 高吞吐场景：性能权重 40%
- 资金紧张：成本权重 40%
- 团队新手多：可维护性 30%

## 7. 决策与记录

- 选 1 个赢家
- 保留 1 个备选（若赢家失败）
- 写 ADR（[adr-template.md](./adr-template.md)）记录决策、候选、权衡、可证伪信号
- 安排复审时间点

## 8. 反模式

| 反模式 | 现象 | 修复 |
|---|---|---|
| 只看一个候选 | 没有对比 | 至少 3 个 |
| 厂商数据代替自测 | benchmark 失真 | 自己跑关键场景 |
| 不标约束 | 重要维度漏 | 强制列约束 |
| 不写 ADR | 半年后不知为何选 | 必写 |
| 不留备选 | 赢家失败时从零开始 | 保留第二选择 |
| 过度求新 | 新技术不成熟 | 主流方案优先 |
| 不算迁移成本 | 切换成本被低估 | TCO 必含迁移 |

## 9. 与其他流程关系

- 输入：PRD（业务需求）、ADR 历史
- 输出：ADR（决策记录）、PoC 代码
- 联动：[tech-review-process](../../work/processes/tech-review-process.md)（重大选型进评审）

## 10. 落地要点

- 选型不是一个人的事：PM + 开发 + 运维参与
- 给评估设时间盒（1-2 周），避免无限调研
- 上线后 6 个月复审，验证假设是否成立
