# 依赖升级流程

## 1. 目的与适用范围

规范第三方库、框架、运行时升级动作；平衡安全合规与稳定性，避免"不升级"和"乱升级"两端。

适用于：所有生产项目依赖（npm/pip/cargo/maven 等）、运行时（Node/Python/JVM）、基础镜像。

## 2. 角色与职责

| 角色 | 职责 |
|---|---|
| 升级 owner（R） | 评估影响；执行升级；回归 |
| 技术负责人（A） | 决策升级时机与范围 |
| 安全 / 合规（C） | 评估 CVE 与合规要求 |
| 测试负责人（C） | 回归策略 |
| 迭代 PM（I） | 排期与对外协调 |

## 3. 升级分级

| 等级 | 触发条件 | 时效 | 评审 |
|---|---|---|---|
| 紧急 | 高危 CVE 在野利用；安全通报 | 24 小时内 | 简化评审，事后补记录 |
| 高 | 中危 CVE；官方停止维护 | 1 周内 | 走正常评审 |
| 中 | minor 版本；功能/性能改进 | 1 个月内 | 走正常评审 |
| 低 | patch 版本；噪音降低 | 季度集中 | 批量评审 |

## 4. 步骤拆解

```
触发 → 影响评估 → 升级方案评审 → 分支验证 → 灰度发布 → 观测 → 收尾
```

| 步骤 | 关键动作 | 退出标准 |
|---|---|---|
| 1. 触发 | 安全通报 / 依赖扫描 / 官方公告 | 触达 owner |
| 2. 影响评估 | breaking changes；调用面；兼容性；性能 | 评估文档完成 |
| 3. 升级方案评审 | 升级路径、回滚方式、灰度策略 | 方案通过 |
| 4. 分支验证 | 单元 + 集成回归；关键路径手测 | 测试通过 |
| 5. 灰度发布 | 走 [灰度发布流程](./canary-release-process.md) | 灰度全量 |
| 6. 观测 | 至少 24 小时盯核心指标 | 无回归 |
| 7. 收尾 | 更新 lockfile、CHANGELOG、归档记录 | 归档完成 |

## 5. 度量指标

- 依赖过期率（> N 个版本落后的依赖占比）
- 高危 CVE 平均修复时长
- 升级引发事故数
- 升级回滚率

## 6. 异常处理与升级路径

| 场景 | 处理 |
|---|---|
| breaking changes 影响大 | 拆分多个迭代；先兼容层后切换 |
| 无替代方案 | 评估自维护 fork；记录风险 |
| 升级后性能劣化 | 回滚；专项优化后再上 |
| 升级引发事故 | 立即回滚；按 [事件响应流程](./incident-response-process.md) 处理 |
| 无法灰度（如构建工具） | 双跑验证；并行期足够长 |

## 7. 注意点

- **依赖不升级不是稳定，是债务**——按节奏治理
- 升级与业务需求解耦；不要混在一个迭代里
- 锁定版本范围；避免隐式升级
- 升级 PR 必须独立；不与业务改动混提
- 紧急 CVE 走 [hotfix 流程](./hotfix-release-process.md)
- 升级记录沉淀到 `projects/<项目>/` 便于追溯
