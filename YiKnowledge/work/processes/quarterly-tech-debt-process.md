# 季度技术债治理流程

## 1. 流程目的

把"重构"从口头承诺变成有节奏、有资源、有追踪的工程产物。避免：

- 债务清单涨不还
- 业务规划挤掉重构
- 团队不知道下季度该还什么

## 2. 角色与职责

| 角色 | 职责 |
|---|---|
| TL | 维护债务清单、定优先级 |
| PM | 分配偿还产能 |
| 开发 | 执行偿还 + 验证 |
| 架构师 | 战略级债务审查 |

## 3. 季度节奏

| 时点 | 事项 |
|---|---|
| 季末前 3 周 | TL 更新债务清单 |
| 季末前 2 周 | PM + TL 联合评审，定下季度偿还项 |
| 季末前 1 周 | 偿还项进下季度规划 |
| 每迭代 | 偿还 1-2 项 |
| 季末 | 复审清单，新增 / 还清 / 撤销 |

## 4. 债务清单维护

### 字段（参见 [tech-debt-inventory-template](../../tech/infra/tech-debt-inventory-template.md)）

- 域分类（代码 / 测试 / 架构 / 依赖 / 数据 / 文档 / 部署 / 监控）
- 严重度（高 / 中 / 低）
- 当前利息（人天 / 月）
- 偿还成本（人天）
- 优先级（P0-P3）
- 责任人

### 季度更新

- 新增：本季度发现的新债
- 还清：已偿还的债
- 撤销：评估不再相关的债
- 升降级：根据利息变化调整优先级

## 5. 偿还产能分配

### 推荐比例

- 每迭代分配 15-20% 产能给债务偿还
- P0/P1 进入迭代规划
- P2/P3 机会主义偿还

### 决策矩阵

| 影响范围 | 利率 | 偿还成本 | 优先级 |
|---|---|---|---|
| 阻碍战略主题 | 高 | 低 | P0 |
| 阻碍战略主题 | 高 | 高 | P1 |
| 阻碍日常开发 | 高 | 低 | P1 |
| 阻碍日常开发 | 中 | 中 | P2 |
| 单点问题 | 低 | 低 | P3 |
| 单点问题 | 低 | 高 | 不还 |

## 6. 偿偿执行

### 单债务偿还流程

1. 写 ADR：为何偿还、风险、回滚
2. 估算工作量
3. 进迭代规划
4. 开发 + 测试 + 验证
5. 上线后监控：债务影响指标是否改善
6. 关闭债务条目

### 偿偿原则

- 增量偿还（strangler fig 模式）：不一次性重写
- 配合业务：碰到相关代码时一起还
- 验证生效：上线后看监控指标
- 记录过程：ADR 留存决策

## 7. 季度治理会议

### 参与者

- TL + PM + 架构师 + 关键开发

### 议程（90 分钟）

1. 上季度偿还复盘（20 分钟）
   - 计划还 X 条，实际还 Y 条
   - 未完成原因
   - 偿还后指标变化
2. 新增债务评审（30 分钟）
   - 每条新增：是否进清单
3. 优先级调整（20 分钟）
   - 现有债务优先级复审
4. 下季度偿还计划（20 分钟）
   - 选 P0/P1 进下季度
   - 产能分配

## 8. 度量与追踪

| 指标 | 含义 |
|---|---|
| 债务总数 | 全清单规模 |
| 季度新增 | 本季度新发现 |
| 季度偿还 | 本季度还清 |
| 净债务 | 总数 - 偿还（应保持净下降） |
| 高严重度债务数 | 应优先偿还 |
| 偿偿产能占比 | 实际 vs 目标 15-20% |

## 9. 反模式

| 反模式 | 现象 | 修复 |
|---|---|---|
| 债务清单涨不还 | 季度净增 | 强制产能分配 |
| 业务挤掉重构 | 季度 0 偿还 | 与业务并列规划 |
| 不评估利息 | 不知哪个紧急 | 必填当前利息 |
| 大爆炸重构 | 一切重写 | 增量偿还 |
| 偿还不验证 | 不知是否生效 | 上线后监控 |
| 不记 ADR | 半年不知为何选 | 必写 ADR |

## 11. 文化建设

- 偿偿产能是承诺，不是"有空再做"
- PM 不把偿还看作"非业务"
- 公开债务清单，全员可加
- 季度看净债务趋势，目标是净下降
