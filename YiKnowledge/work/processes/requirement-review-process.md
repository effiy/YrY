# 需求评审流程

## 1. 目的与适用范围

在需求正式进入研发前，确保产研测各方对背景、价值、目标、流程、核心功能达成共识，避免开发中变更与返工。

适用于：所有进入迭代的新需求、需求变更、缺陷转需求。

## 2. 角色与职责（RACI）

| 角色 | 职责 |
|---|---|
| 产品经理（R） | 输出 PRD；召集评审；记录结论与 action |
| 迭代 PM（A） | 把控节奏；识别关联方；跟踪 action 闭环 |
| 技术负责人（C） | 评估可行性、技术风险、关联系统 |
| 测试负责人（C） | 识别验收点、边界、异常场景 |
| 设计负责人（C） | 识别交互与视觉复杂度 |
| 业务方（I） | 确认需求价值与优先级 |

## 3. 步骤拆解

```
需求内审 → 预排期 → 评审前预沟通 → 正式评审 → 结论同步 → 进入技术/设计评审
```

| 步骤 | 负责人 | 关键动作 | 退出标准 |
|---|---|---|---|
| 1. 需求内审 | 产品 | 提前 1 天发 PRD；产品/业务/设计/技术负责人到场；对齐背景/价值/目标/流程/核心功能 | PRD 完整度通过内审 |
| 2. 预排期 | 迭代 PM | 日常迭代对齐后 1 天内给出；分歧上升 | 预排期发出 |
| 3. 评审前预沟通 | 产品 + 迭代 PM | 确定技术/设计成员；识别关联方并联动；确定评审时间；关键人必须到场 | 关联方已识别且通知 |
| 4. 正式评审 | 产品 + 迭代 PM | 相关人到场；指定记录人；记录问题/结论/action；现场确认是否通过；通过后确定技术方案与视觉评审时间；结束前对齐纪要 | 结论明确：通过 / 再评审 / 不通过 |
| 5. 结论同步 | 产品 | 纪要 @相关人同步项目群；开始记录需求变更 | 纪要发出、群内确认 |

## 4. 输入 / 输出工件

- **输入**：PRD（含背景、目标、流程图、功能清单、验收标准）
- **输出**：评审纪要、需求变更记录、技术/设计评审时间、action 列表

## 5. 度量指标

- 评审一次通过率
- 评审后需求变更率（目标 ≤ 10%）
- 评审到提测的周期

## 6. 异常处理与升级路径

| 场景 | 处理 |
|---|---|
| 关键人未到场 | 评审改期，禁止口口相传 |
| 需求不完整 | 不通过，返回内审 |
| 关联方未识别 | 暂停评审；补充联动后重审 |
| 分歧无法对齐 | 上上升至产品总监/迭代 PM 仲裁 |
| 评审问题多 | 再评审，禁止带病进入技术评审 |

## 7. 注意点

- **识别并确定关联方非常重要**——延期常因未识别清楚或未达成共识
- 相关人必须参加评审，避免口口相传
- 结论必须当场对齐并会后发出
- 开始记录需求变更；非必要不变更，有分歧上升
