# 知识沉淀与传承流程

## 1. 目的与适用范围

将个人经验、项目教训、技术决策转化为团队可复用资产，降低人员流动带来的知识流失。

适用于：项目里程碑节点、人员变动（入职/转岗/离职）、事件复盘后、技术决策后。

## 2. 角色与职责

| 角色 | 职责 |
|---|---|
| 知识 owner（R） | 撰写并维护文档；定期复审 |
| 迭代 PM（A） | 触发沉淀动作；跟踪闭环 |
| 技术负责人（C） | 审核技术准确性 |
| 团队成员（I） | 阅读、反馈、复用 |

## 3. 触发时机

| 触发点 | 沉淀动作 | 产出位置 |
|---|---|---|
| 项目上线 | 项目 README、架构图、技术方案归档 | `projects/<项目>/` |
| 事件复盘 | postmortem；失败案例 | `lessons/failures/` |
| 技术决策 | ADR；技术选型评估 | `resources/templates/adr-template.md` |
| 个人成长 | 经验总结、坑点记录 | `lessons/gotchas/` |
| 人员变动 | 交接文档；知识传承会议 | `projects/<项目>/handover.md` |
| 季度复盘 | 路线图审查、技术债盘点 | `work/processes/` |

## 4. 步骤拆解

```
触发 → 草稿 → 审核 → 归档 → 复审 → 传承
```

| 步骤 | 负责人 | 关键动作 | 退出标准 |
|---|---|---|---|
| 1. 触发 | 迭代 PM | 在上述触发点提醒 owner 沉淀 | 触达 owner |
| 2. 草稿 | 知识 owner | 按 frontmatter 与模板撰写；脱敏；引用关联文档 | 草稿完成 |
| 3. 审核 | 技术负责人 | 审核技术准确性；检查与现有知识是否冲突 | 审核通过 |
| 4. 归档 | 知识 owner | 放到对应 leaf 目录；更新 INDEX.md 与 leaf README | 已收录清单更新 |
| 5. 复审 | 知识 owner | 每季度复审；过期内容标注或删除 | 复审记录归档 |
| 6. 传承 | 迭代 PM | 入职/转岗/项目交接时引导阅读 | 交接记录归档 |

## 5. 输入 / 输出工件

- **输入**：PRD、技术方案、会议纪要、事件复盘、个人笔记
- **输出**：归档文档、INDEX 更新、交接清单

## 6. 度量指标

- 文档覆盖率（关键模块有文档的比例）
- 文档活跃度（近 90 天有复审的比例）
- 复用率（被其他文档/项目引用的次数）
- 交接完成率（人员变动时完成交接的比例）

## 7. 异常处理与升级路径

| 场景 | 处理 |
|---|---|
| Owner 拖延 | 迭代 PM 跟进；必要时升级 |
| 文档与现状不符 | 标注"已过期"；分配 owner 更新 |
| 无人接手 | 升级至技术负责人指派 |
| 交接时间紧 | 优先沉淀核心模块；次要模块列入 backlog |
| 知识冲突 | 以最新实践为准；旧文档归档或删除 |

## 8. 注意点

- 写比不写好；80 分比 0 分好
- 文档不是写完就完成——要复审与传承
- 复用现有模板：ADR、postmortem、tech-design、tech-selection-evaluation
- 入职第一周安排新人阅读 `projects/<项目>/README.md` 与 `lessons/` 关键文档
- 季度复盘与 `tech-roadmap-review-template.md`、`tech-debt-inventory-template.md` 联动
