# 容量评估与扩容流程

## 1. 目的与适用范围

在新功能上线、大促/活动、用户增长前评估资源容量，提前扩容，避免容量事故；同时避免过度预留浪费成本。

适用于：所有生产服务（应用、数据库、缓存、消息队列、存储、带宽）。

## 2. 角色与职责

| 角色 | 职责 |
|---|---|
| 容量 owner（R） | 撰写容量评估报告；执行扩容 |
| 技术负责人（A） | 审核评估结论；决策扩容范围 |
| 运维 / SRE（C） | 执行资源变更；监控告警配置 |
| 业务方（C） | 提供流量预期与节奏 |
| 迭代 PM（I） | 协调窗口与对外沟通 |

## 3. 步骤拆解

```
容量需求输入 → 基线评估 → 压测验证 → 扩容决策 → 执行 → 观测 → 收缩
```

| 步骤 | 关键动作 | 退出标准 |
|---|---|---|
| 1. 容量需求输入 | 业务方提供预期 QPS/UV/数据量；明确峰值与持续时间 | 需求文档确认 |
| 2. 基线评估 | 现状资源盘点；单实例容量基准；找出瓶颈 | 评估报告产出 |
| 3. 压测验证 | 在影子环境压测；验证瓶颈与扩容线性度 | 压测报告产出 |
| 4. 扩容决策 | 计算所需资源；考虑冗余系数；评估成本 | 决策文档通过 |
| 5. 执行 | 按计划扩容；配置监控与告警；预热缓存 | 扩容完成 |
| 6. 观测 | 峰值期间盯盘；记录关键指标 | 峰值平稳度过 |
| 7. 收缩 | 峰值后评估是否回收资源；优化成本 | 收缩完成或保留决策归档 |

## 4. 输入 / 输出工件

- **输入**：业务流量预期、资源基线、历史压测数据、监控大盘
- **输出**：容量评估报告、压测报告、扩容决策、执行记录

## 5. 度量指标

- 容量评估准确率（实际 vs 预期）
- 扩容时效（需求到执行）
- 峰值期事故数
- 资源利用率（目标 60%~80%，不过度预留）

## 6. 异常处理与升级路径

| 场景 | 处理 |
|---|---|
| 压测发现瓶颈难解 | 拆分专项优化；评估是否降级/限流兜底 |
| 扩容资源不足 | 升级至运维 + 业务方；调整预期或推迟活动 |
| 峰值超预期 | 启动 [事件响应流程](./incident-response-process.md)；应急扩容 + 限流 |
| 扩容后不稳定 | 立即排查；必要时回缩到稳定水位 |
| 成本超预算 | 升级至业务方 + 迭代 PM；决策取舍 |

## 7. 注意点

- **容量评估要早做**——大促前 2 周才评估通常来不及
- 压测不是"测过"——要找到真实瓶颈
- 冗余系数留 30%~50%；但不要过度预留变成浪费
- 扩容同时必须配监控告警；盲扩等于没扩
- 峰值后必须评估收缩——长期保留是成本黑洞
- 与 [data-migration-process](./data-migration-process.md) 联动：数据库扩容常涉及迁移
