# 灰度发布流程

## 1. 目的与适用范围

通过分批放量降低发布风险；小流量发现问题即止损，避免全量事故。

适用于：所有有用户流量且影响主流程的发布；纯后端数据修复可豁免。

## 2. 角色与职责

| 角色 | 职责 |
|---|---|
| 发布负责人（R） | 制定灰度计划；执行分批；监控 |
| 技术负责人（A） | 评估灰度策略、回滚阈值 |
| 测试负责人（C） | 灰度验收用例 |
| 产品（C） | 灰度范围与业务沟通 |
| 业务方（I） | 灰度放量节奏确认 |

## 3. 灰度策略

| 阶段 | 流量比例 | 观察时长 | 退出标准 |
|---|---|---|---|
| 内部 | 内部账号 100% | 30 分钟 | 无功能/性能问题 |
| 小流量 | 1%~5% | 2 小时 | 核心指标不劣化 |
| 中流量 | 10%~30% | 4 小时 | 核心指标不劣化 |
| 大流量 | 50%~80% | 4 小时 | 核心指标不劣化 |
| 全量 | 100% | 持续观测 | 进入常规观测 |

## 4. 步骤拆解

```
灰度计划评审 → 准备灰度能力 → 内部 → 小流量 → 中流量 → 大流量 → 全量
```

| 步骤 | 关键动作 | 退出标准 |
|---|---|---|
| 1. 灰度计划评审 | 流量比例、阶段、回滚阈值、监控大盘、责任人 | 计划通过 |
| 2. 准备灰度能力 | 开关/路由/AB 平台就位；监控就位；回滚脚本就位 | 全部就位 |
| 3. 内部 | 内部账号验证；快速发现功能问题 | 30 分钟无问题 |
| 4. 小流量 | 按计划放量；盯核心指标 | 指标不劣化 |
| 5. 中流量 | 继续放量；关注长尾问题 | 指标不劣化 |
| 6. 大流量 | 接近全量；关注容量与稳定性 | 指标不劣化 |
| 7. 全量 | 进入常规观测；归档灰度记录 | 归档完成 |

## 5. 度量指标

- 灰度发现问题的比例（目标：在灰度阶段拦截的事故占比）
- 灰度平均时长
- 灰度回滚率

## 6. 异常处理与升级路径

| 场景 | 处理 |
|---|---|
| 核心指标劣化 | 立即回滚；不上调流量 |
| 用户投诉 | 评估影响；必要时回滚 |
| 灰度平台故障 | 暂停；评估是否全量回退 |
| 数据不一致 | 暂停；数据修复后再放量 |
| 紧急修复 | 暂停当前灰度；修复后重新启动 |

## 7. 注意点

- 灰度不是绕过测试的借口——冒烟必须先通过
- 每个阶段必须有明确的观察时长与回滚阈值
- 灰度期间不做需求变更
- 全量前确认数据迁移、缓存预热、容量评估
- 配合 [上线发布流程](./release-process.md) 与 [事件响应流程](./incident-response-process.md) 使用
