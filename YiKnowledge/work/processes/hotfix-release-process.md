# 紧急修复（hotfix）发布流程

## 1. 目的与适用范围

在事件响应止损或线上紧急缺陷场景下，跳过完整评审快速上线修复；保证动作可追溯、可回滚。

适用于：P0/P1 事件止损、阻塞主流程的线上缺陷、安全漏洞紧急补丁。

不适用于：常规需求、非紧急优化（走正常 [上线发布流程](./release-process.md)）。

## 2. 角色与职责

| 角色 | 职责 |
|---|---|
| 修复作者（R） | 定位与修复；最小改动 |
| 技术负责人（A） | 决策是否走 hotfix；审核修复方案 |
| 迭代 PM（C） | 协调资源；简化评审；事后补全记录 |
| 测试负责人（C） | 最小用例验证 |
| Oncall（I） | 协同观测与回滚决策 |

## 3. 步骤拆解

```
判定 → 最小修复方案 → 快速评审 → 发布 → 观测 → 事后补记录
```

| 步骤 | 关键动作 | 时限 |
|---|---|---|
| 1. 判定 | 技术负责人确认紧急程度；是否符合 hotfix 标准 | 5 分钟 |
| 2. 最小修复方案 | 修复作者描述根因、改动范围、回滚方式；禁止顺手重构 | 15 分钟 |
| 3. 快速评审 | 技术负责人 + 测试负责人口头或群内评审；记录结论 | 30 分钟内 |
| 4. 发布 | 走 [上线发布流程](./release-process.md) 简化版；冒烟必须通过 | — |
| 5. 观测 | 至少 30 分钟盯核心指标 | — |
| 6. 事后补记录 | 24 小时内补全 PR 描述、发布记录、复盘 | — |

## 4. 输入 / 输出工件

- **输入**：事件响应记录 / 缺陷描述、根因分析
- **输出**：hotfix PR、发布记录、复盘文档（见 [incident-postmortem-template](../../lessons/failures/incident-postmortem-template.md)）

## 5. 度量指标

- hotfix 数量（目标趋势下降）
- hotfix 平均时长（发现到恢复）
- hotfix 引发二次事故率（目标 0）

## 6. 异常处理与升级路径

| 场景 | 处理 |
|---|---|
| 修复方案不清晰 | 不走 hotfix；转入正常流程 |
| 改动范围超出"最小修复" | 拆分；非紧急部分进入 backlog |
| hotfix 引发新问题 | 立即回滚；按 [事件响应流程](./incident-response-process.md) 升级 |
| 同一问题反复 hotfix | 升级至技术负责人；立项根治 |

## 7. 注意点

- hotfix 是例外，不是常态——高频 hotfix 说明流程有问题
- 改动必须最小化；顺手重构是事故温床
- 评审可简化但不能省——必须留文字记录
- hotfix 后必须复盘；根治项进入技术债清单
- 24 小时内补齐所有文档；不要"先发了再说"
