# 代码冻结期流程（release freeze）

## 1. 目的与适用范围

在关键业务节点（大促、重大活动、合规窗口、节假日）暂停非必要变更，降低线上事故概率。

适用于：所有生产环境发布；冻结窗口由业务方 + 迭代 PM 联合确定。

## 2. 角色与职责

| 角色 | 职责 |
|---|---|
| 迭代 PM（R） | 发布冻结期日历；审批例外 |
| 业务方（A） | 决定冻结起止与范围 |
| 技术负责人（C） | 评估例外请求 |
| Oncall（C） | 冻结期值守与应急 |
| 项目 owner（I） | 遵守冻结；提交例外申请 |

## 3. 冻结分级

| 级别 | 描述 | 典型场景 |
|---|---|---|
| 硬冻结 | 仅允许 P0 修复；其他一律拒绝 | 双 11、监管检查、重大发布 |
| 软冻结 | 需迭代 PM + 技术负责人双签 | 节假日、月底结算 |
| 黄金周 | 全员休；仅 Oncall 值守 | 春节、国庆 |

## 4. 步骤拆解

```
冻结日历发布 → 冻结前准备 → 冻结期值守 → 例外审批 → 解冻 → 复盘
```

| 步骤 | 关键动作 | 退出标准 |
|---|---|---|
| 1. 冻结日历发布 | 迭代 PM 每季度发布冻结日历；通报全员 | 日历发出 |
| 2. 冻结前准备 | 排完关键发布；遗留 bug 清零；Oncall 排班确认 | 准备完成 |
| 3. 冻结期值守 | Oncall 值守；监控告警；禁止非必要发布 | 值守记录归档 |
| 4. 例外审批 | 申请人提交例外请求；技术负责人 + 迭代 PM 双签 | 审批结论发出 |
| 5. 解冻 | 解冻后批量发布；按优先级排队 | 解冻公告发出 |
| 6. 复盘 | 记录冻结期事故与例外；评估有效性 | 复盘归档 |

## 5. 例外审批标准

- **允许例外**：P0/P1 线上事故止损、安全合规要求、监管通报、资金/订单阻塞
- **不允许**：常规需求、非紧急优化、技术债治理、新功能上线

## 6. 度量指标

- 冻结期事故数（目标 0）
- 例外请求数与通过率
- 解冻后批量发布的拥堵情况
- 冻结期值守告警数与处理率

## 7. 异常处理与升级路径

| 场景 | 处理 |
|---|---|
| 紧急事故 | 按 [事件响应流程](./incident-response-process.md) 处理；走 [hotfix 流程](./hotfix-release-process.md) |
| 例外被拒 | 申请人升级至业务方；业务方决策 |
| 冻结前未排完 | 评估是否延期或保留到解冻后 |
| 解冻后拥堵 | 按优先级排队；禁止一次性挤占 |
| 黄金周紧急事故 | Oncall 应急；业务方远程支持 |

## 8. 注意点

- **冻结不是不发**——是只发该发的
- 冻结日历要早发（提前 1 季度）；让产研测安排节奏
- 冻结前的"抢发"是事故温床——不要拖到最后一天
- 例外审批必须双签；不要口口相传
- 解冻后排队发布；不要一次性挤爆
- 与 [release-process](./release-process.md) 与 [incident-response-process](./incident-response-process.md) 联动
