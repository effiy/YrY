# 监控告警治理流程

## 1. 流程目的

防止告警泛滥导致 oncall 疲劳与真正紧急被淹没。核心命题：**告警必须可执行、可归因、可恢复**。

不可执行告警 = 噪声；噪声多 = 真告警被忽略。

## 2. 告警分类

| 类型 | 含义 | 处置 |
|---|---|---|
| 紧急告警（Page） | 立即响应，需 oncall | P0/P1 |
| 工单告警（Ticket） | 工作时间处理 | P2 |
| 通知告警（Info） | 仅记录，不响应 | P3 |
| 自愈告警 | 系统自动处理，仅记录 | 不通知 |

## 3. 告警质量标准

每条告警必须满足：

1. **可执行**：接到能做什么？不能执行 → 删 / 改
2. **可归因**：原因可追溯（监控上下文齐全）
3. **可恢复**：明确"恢复"信号，告警自动关闭
4. **低噪声**：避免抖动（同告警 5 分钟内不重复）
5. **分级正确**：严重度匹配影响范围

## 4. 治理流程

### 4.1 新告警上线

1. 需求评估：要监控什么、为什么、谁响应
2. 设计：指标、阈值、持续时间、严重度、通知渠道
3. 评审：与现有告警对比是否重复
4. 试运行：先 Ticket 模式跑 1 周，确认稳定
5. 升级为 Page：试运行无噪声后转 Page

### 4.2 现有告警治理

每周跑告警统计：

| 告警 | 触发次数 | 响应时长 | 是否有效 | 处置 |
|---|---|---|---|---|
| A | 200 | 0s（无响应） | 否 | 删 / 改 |
| B | 50 | 30 分钟 | 是 | 保留 |
| C | 5 | 5 分钟 | 是 | 保留 |

### 4.3 删 / 改 / 保留决策

| 标准 | 处置 |
|---|---|
| 无响应（不看） | 删 |
| 看了不执行 | 删或改（加可执行建议） |
| 响应但无原因 | 加监控上下文 |
| 噪声大（频繁） | 调阈值 / 加持续时间 / 聚合 |
| 真紧急 | 保留，定期演练 |

## 5. 告警设计原则

### 阈值与持续时间

- 阈值：基于历史数据 + SLA，不拍脑袋
- 持续时间：避免瞬时抖动，5-15 分钟持续
- 多段阈值：warning（Ticket）→ critical（Page）

### 上下文齐全

每告警触发要带：

- 触发条件（指标 + 阈值 + 时间）
- 影响范围（哪些用户 / 服务）
- 排查指引（链接到 runbook）
- 相关图表（Grafana 链接）

### 自愈优先

能用脚本自动恢复的，不要告警让人处理。例：磁盘满 → 自动清理旧日志。

## 6. SLO 与告警联动

- SLO 达成率 < 50% → Page
- SLO 达成率 < 80% → Ticket
- SLO 错误预算耗尽 → Page

错误预算 = 100% - SLO。例：99.9% SLO 月内允许 43 分钟错误，超 50% 即 22 分钟时告警。

## 7. 工具栈

| 用途 | 工具 |
|---|---|
| 指标采集 | Prometheus / Datadog |
| 告警路由 | Alertmanager / PagerDuty |
| 日志告警 | Loki / ELK |
| 自愈脚本 | runbook automation |
| 告警治理 | 自研或 OpsGenie Analytics |

## 8. 反模式

| 反模式 | 现象 | 修复 |
|---|---|---|
| 告警泛滥 | oncall 一天 200 告警 | 每周治理 |
| 不可执行 | 告警说"CPU 高"，无指引 | 必带 runbook |
| 无自愈 | 凡事先告警 | 自愈优先 |
| 不删旧告警 | 半年前的还在响 | 定期清理 |
| 严重度错位 | 小事标 Page | 重新分级 |
| 抖动告警 | 同告警 1 分钟响 5 次 | 加持续时间 + 聚合 |
| 无 SLO 联动 | 告警与 SLA 脱节 | 必关联 SLO |

## 9. 落地节奏

| 时点 | 事项 |
|---|---|
| 每日 | Primary oncall 看告警群 |
| 每周 | 告警统计与治理 |
| 每月 | 告警质量复盘 |
| 每季 | 全告警库复审 |
