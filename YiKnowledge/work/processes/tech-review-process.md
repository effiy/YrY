# 技术评审流程

## 1. 目的与适用范围

在研发进入开发前，确保各方对技术方案、接口契约、风险、里程碑达成共识，方案与 PRD 匹配。

适用于：所有进入开发的需求；简单改动可走轻量评审。

## 2. 角色与职责（RACI）

| 角色 | 职责 |
|---|---|
| 方案作者（R） | 输出技术方案文档；召集评审 |
| 迭代 PM（A） | 组织内审与正式评审；把控节奏；跟踪 action |
| 域技术负责人 / TO（C） | 评估架构、性能、安全、可维护性 |
| 相关开发（C） | 评估接口契约、依赖、联调点 |
| 测试负责人（C） | 评估可测性、测试策略 |
| 产品（C） | 确认方案满足 PRD；**必须参加且认真对待** |

## 3. 步骤拆解

```
技术方案内审 → 正式技术评审 → 确定里程碑 → 进入开发
```

| 步骤 | 负责人 | 关键动作 | 退出标准 |
|---|---|---|---|
| 1. 技术方案内审 | 迭代 PM | 确保相关人到场；把控节奏；指定记录人；纪要同步群；整改 action 后再进入正式评审 | 内审 action 全部闭环 |
| 2. 正式技术评审 | 迭代 PM | 确保日程与在场；把控节奏；指定记录人；现场确认是否通过；问题多则再评审；通过后确定里程碑给出时间；结束前对齐纪要；纪要同步群 | 结论明确：通过 / 再评审 / 不通过 |
| 3. 确定里程碑 | 迭代 PM | 确认联调/测试/上线时间并留沟通记录；拆分任务并审查合理性；确认各人投入与完成时间；检查最长路径与最短路径；拉会确定里程碑与例会制度 | 里程碑同步群并写群公告 |

## 4. 输入 / 输出工件

- **输入**：PRD、设计稿、现有架构图
- **输出**：技术方案文档、接口契约、里程碑计划、action 列表

## 5. 度量指标

- 技术方案一次通过率
- 评审到提测的偏差天数
- 提测后方案返工率

## 6. 异常处理与升级路径

| 场景 | 处理 |
|---|---|
| 内审 action 未闭环 | 不进入正式评审 |
| 方案与 PRD 不匹配 | 暂停；产品确认取舍后重审 |
| 架构争议 | 上上升至 TO / 域技术负责人仲裁 |
| 需求变更 | 控制变更，非必要不变更；有分歧上升；扩散记录 |
| 里程碑无法对齐 | 上升至迭代 PM 仲裁；考虑分批提测/分批上线 |

## 7. 注意点

- 内审目的是在正式评审前内部对齐方案，避免浪费产品/测试/设计时间
- 产品必须参加且认真对待
- 开发/测试任务颗粒度 ≤ 4 小时
- 里程碑确定距技术评审通过 ≤ 1 天
- 关注非 100% 投入同学的投入比
- 提前识别风险，开发中定期例会扫清
