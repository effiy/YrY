## 实施上下文

### 背景与动机

Q3 初期，YiAi Agent 在执行复杂任务（如跨项目代码修改、知识库批量更新）时频繁出现中途失败的场景。根因分析发现三个核心问题：
1. **任务完成率低**：Agent 在遇到不确定情况时倾向于放弃而非重试或降级
2. **写操作无防护**：Agent 可以直接修改文件和数据库，没有人工确认机制
3. **模型能力瓶颈**：默认使用的小模型（stall）在复杂推理任务上频繁卡住，需要升级到更强模型

### 关键决策

| 决策 | 说明 |
|------|------|
| 确认门（approve/reject）机制 | Agent 在执行写操作（文件修改、数据库写入）前必须请求用户确认，默认超时 30 秒不确认则拒绝 |
| 模型升级策略 | stall→stronger 链路：当 Agent 在同一任务上连续 2 轮无进展时自动切换到更强模型 |
| 任务完成率基准 70% | 结合 Q2 的实际完成率（约 40%）和行业基准，设定 70% 为 Q3 目标值 |
| 5 轮上限策略 | 超过 5 轮未完成的任务自动终止并生成失败报告，避免无限循环消耗资源 |

### 实施路径

1. **第一阶段**：实现确认门机制——在写操作执行前注入用户确认检查点
2. **第二阶段**：实现模型升级链路——检测 stall 状态并自动触发 stronger 模型切换
3. **第三阶段**：实现 5 轮上限 + 失败报告——超限任务自动终止并落盘诊断信息
4. **第四阶段**：全量任务统计追踪——建立任务完成率监控面板

## 预防措施

1. **确认门超时策略**：默认 30 秒超时自动拒绝，防止 Agent 因等待确认而永久挂起
2. **模型升级频率限制**：单任务模型升级不超过 2 次，防止无限升级消耗资源
3. **失败报告完整性**：5 轮超限任务必须生成完整诊断报告（做了什么、卡在哪里、建议），否则后续排查困难

## 经验教训

1. **确认门是 Agent 安全的底线**：写操作确认门不仅保护了数据安全，还让用户对 Agent 行为建立了信任
2. **模型升级比预想的更频繁触发**：初期约 30% 的任务需要升级模型，后续通过优化 prompt 和上下文压缩降低到 15%
3. **5 轮上限需要可配置**：固定 5 轮在某些复杂任务（如大规模重构）中过于严格，建议按任务类型设置不同的上限值
