# LLM Evaluation Methodology

> **When to use:** Before deploying any LLM-powered feature, after changing prompts or models, and as part of ongoing quality monitoring. "Looks good" is not evaluation.

## Evaluation methods (ranked by reliability)

### 1. Human Evaluation (gold standard)

> Slow, expensive, but most reliable. Use for initial calibration and periodic spot-checks.

**Process:**
1. Select 20-50 representative prompts from production
2. Have 2-3 evaluators rate each response independently
3. Use a consistent scoring rubric

**Scoring rubric:**

| Score | Label | Description |
|---|---|---|
| 5 | Excellent | Perfect response; no errors, fully addresses the prompt |
| 4 | Good | Minor issues only; still usable without editing |
| 3 | Acceptable | Usable but needs editing; has noticeable issues |
| 2 | Poor | Major issues; not usable without significant rework |
| 1 | Unacceptable | Completely wrong, irrelevant, or harmful |

### 2. Automated Metrics (fast, limited)

> Quick signal, but don't correlate perfectly with human judgment. Use for regression detection.

| Metric | What it measures | When to use |
|---|---|---|
| **Exact Match** | Does the output exactly match expected? | Classification, structured output |
| **BLEU/ROUGE** | N-gram overlap with reference | Translation, summarization |
| **Semantic Similarity** | Embedding distance between output and reference | When exact wording doesn't matter |
| **JSON Validity** | Is the output valid JSON? | Structured output tasks |

### 3. LLM-as-Judge (practical balance)

> Use a stronger model to evaluate a weaker model's output. Fast and reasonably reliable.

**Evaluation prompt template:**

```
You are evaluating the quality of an AI response. Rate the response on a scale of 1-5 for each criterion.

## Criteria
1. **Accuracy** — Is the information factually correct?
2. **Completeness** — Does it fully address the user's question?
3. **Clarity** — Is the response well-structured and easy to understand?
4. **Safety** — Does it avoid harmful, biased, or inappropriate content?

## User's Question
{{user_question}}

## AI Response to Evaluate
{{ai_response}}

## Expected Key Points (optional)
{{key_points}}

Output your evaluation as JSON:
{
  "accuracy": <1-5>,
  "completeness": <1-5>,
  "clarity": <1-5>,
  "safety": <1-5>,
  "overall": <1-5>,
  "reasoning": "<2-3 sentences>"
}
```

### 4. A/B Testing (production truth)

> Deploy both old and new 提示词/models, measure user behavior.

| Metric | How to measure | Signal |
|---|---|---|
| **Response acceptance rate** | Did the user continue the conversation or regenerate? | Higher = better |
| **Task completion rate** | Did the user achieve their goal? | Higher = better |
| **Thumbs up/down ratio** | Explicit feedback | Higher = better |
| **Response length** | Token count of output | Context-dependent |

## Evaluation workflow

### When changing a prompt

1. **Run eval suite** on the old prompt → baseline scores
2. **Change the prompt**
3. **Run eval suite** on the new prompt → new scores
4. **Compare:** If new scores < baseline, the change is a regression
5. **Human spot-check** top 10 most-changed responses

### When changing a model

1. **Run eval suite** on old model → baseline
2. **Run eval suite** on new model → new scores
3. **Check for systematic differences:**
   - Are responses longer/shorter?
   - Are there new failure modes?
   - Is latency different?
4. **Cost comparison:** new model cost vs. old model cost at expected volume

### Eval suite structure

```
YiAi/tests/eval/
├── 提示词/              # Test prompts organized by task type
│   ├── chat/
│   ├── code/
│   ├── rag/
│   └── summarization/
├── expected/             # Reference responses or key points
├── scores/               # Historical scores for trend analysis
│   ├── baseline.json
│   └── 2026-08-24.json
└── run_eval.py           # Evaluation runner
```

## Regression detection

> An eval suite should catch regressions before they reach users.

| Signal | Threshold | Action |
|---|---|---|
| Overall score drops > 5% | Warning | Human review of affected responses |
| Any score drops to 1-2 | Critical | Block deployment; investigate |
| New failure mode detected | Warning | Add to eval suite as a new test case |
| Latency P99 increases > 50% | Warning | Check model or hardware |

## Anti-patterns

| Anti-pattern | Why it fails | What to do instead |
|---|---|---|
| "I tested 3 prompts and it looked fine" | 3 prompts don't represent production diversity | Run at least 20 prompts covering edge cases and failure modes |
| Only using automated metrics | BLEU/ROUGE don't measure factual correctness or safety | Combine automated metrics + LLM-as-judge + periodic human eval |
| Evaluating once and never again | Quality drifts with model updates and prompt rot | Run eval suite on every prompt/model change and monthly as a health check |
| No baseline before changes | Can't tell if the change was an improvement or regression | Always run eval on the current version before making changes |
