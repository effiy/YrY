# Agent Harness Plugin Architecture

> **Summary.** An *agent harness* is the model-agnostic execution skeleton around an LLM — the loop that turns model output into tool calls, feeds results back, and enforces policy. [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) (`dsh`) is a reference implementation where **everything is a plugin**: the model adapter, the tool registry, the session log, and the agent loop itself are all plugins contributing to one shared context, composed at boot. This note distills that architecture and maps each concept onto YiAi's own `domain/ai/agent.py`.

## Applicable scenarios

Use a **plugin-based harness** when:

- You need to swap model providers, sandboxes, or filesystems without rewriting the loop.
- Multiple products (web app, headless runner, CLI) share the same agent semantics.
- You must attach policy (approval, telemetry, guardrails) without editing the core loop.

Prefer a **hand-rolled loop** when:

- The agent is a single fixed workflow (one provider, one tool, no policy variance).
- The cost of learning a plugin framework exceeds the flexibility it buys.

YiAi sits between these: it hand-rolls the loop but has been growing harness-like seams (tool registry, confirmation gate, model fallback) incrementally — the mapping table below shows exactly where.

## Key concepts

### 1. Everything is a plugin (Cordis)

[Cordis](https://github.com/cordiverse/cordis) is the framework under `dsh`: plugins contribute **services**, **typed events**, and **reversible effects** to a shared context. There is **no privileged core to patch** — you extend the harness by mounting a plugin beside the others, and every registration is an effect that unwinds when its plugin unloads.

> Consequence: the model adapter, tool registry, session log, and agent loop are all replaceable from configuration. "Change the whole product" = "swap one provider".

### 2. Profiles and bundles (composition)

A running harness is a **plugin tree composed at boot** from ordered layers:

- A **profile** is a named composition (stored in the harness home): the bundles it stacks, out-of-tree plugins it installs, and the user's `cordis.patch.yml`.
- A **bundle** is a distribution format for config rows + the code they mount. `web` and `headless` ship as template profiles.
- **Patches** target a row by `id` and replace its whole config, or insert new rows. `--dump-config` prints the exact tree your machine boots.

This is the "config as code" answer to "how do I ship a customized agent": ship a profile + a patch, not a fork.

### 3. Capability seams

A **seam** is a swappable capability with three roles:

1. **Service Definition** — declares the interface.
2. **Service Provider** — implements it.
3. **Consumer** — uses it (commonly a model-facing tool).

Seams are why one provider swap changes the whole product: filesystem and subprocess providers share one execution world, so pointing them at a remote sandbox moves Bash, PTY, and LSP together with **no provider forks**.

### 4. Events as extension points

Three event domains, and the rule is to pick the right one:

| Domain | Shape | When |
|---|---|---|
| **Session events** | Durable facts appended to a log, broadcast via `session/event` | The fact must survive a reload (messages, tool results, turn boundaries) |
| **Agent events** (`agent/*`) | Live events carrying a live `Agent` (inbox, step, status, request, validation) | Observe or intercept work *in flight* |
| **Capability events** (`tools/*`, `fs/*`, `telemetry/*`) | Policy/adapter attachment on a seam | Add policy without importing the loop |

Waterfall events (`agent/pre-step`, `agent/request`, `llm/stream`, `tools/*`) require listeners to call `next()` to delegate; `agent/turn-stopping` is serial and has no `next()`.

### 5. Turn flow (step ⊂ turn)

- A **step** = one model request + the tools it calls.
- A **turn** = zero or more steps; it opens before its first input is claimed and closes once nothing is owed.

`agent/pre-step` decides what the model sees — listeners may rewrite the claimed messages or **reject** them outright; a rejected first claim still closes a durable turn so the log records the attempt.

### 6. "Model-visible means logged"

The session log is the *source of the context the model sees*: `deriveMessages()` projects model history from it, and raw `assistant/chunk` events preserve replay and UI fidelity. **Anything that reaches a model request must be reconstructable from the log** — a runtime invariant asserts this. New model-visible input ⇒ new session event.

## Pattern decomposition

```
boot          profile + bundles + patches → plugin tree
extension     new behavior attaches to a documented event / seam (never to the loop)
turn/step     pre-step (rewrite/reject) → request → stream → tool/* → post-execute → owe-another?
context       session log = the only model-visible context; fork/resume/transcript all derive from it
```

## Anti-patterns

- **Hard-coding policy into the loop** instead of a seam — approval, telemetry, and guardrails should be events/seams, not `if` blocks in the driver.
- **Writing durable facts to live agent events** — a fact that must survive reload belongs in the session log, not `agent/*`.
- **Non-idempotent plugin trees** — if registrations aren't reversible effects, reload can't cleanly unwind and the log can't replay.
- **Patching the core** instead of mounting a plugin — the harness has no privileged core; a fork is a sign you should have added a seam.

## Evaluation metrics

- **Provider-swap cost** — how many files change to swap the model / sandbox / fs. Seams ⇒ one config row.
- **Log replayability** — can a transcript be reconstructed from the session log alone, byte-for-byte?
- **Event-domain correctness** — audit that every fact lives in the right domain (durable vs live vs capability).

## YiAi implementation case study

YiAi hand-rolls its loop but has organically grown the same seams. The mapping:

| deepseek-harness concept | YiAi counterpart (`domain/ai/agent.py`) |
|---|---|
| `ctx.tools` tool registry + guarded execution | `get_tool_registry()` → `ToolRegistry.execute` with `_validate_arguments` |
| Approval policy (sandbox/approval) | Confirmation gate — `_wait_for_confirmation` + rejection memory (`_session_rejections`) |
| Model adapter seam (`ctx.llm`) | `OllamaRuntime.stream_chat` + `model_fallback` escalation chain |
| Session log (durable, replayable) | `save_session_history` / `load_session_history` (1h TTL, faithful `tool_result` trajectory) |
| Turn / step budget | `max_turns` + turn-budget warning (`_budget_warning`) |
| `agent/pre-step` rewrite/reject | Mission re-injection (`_inject_mission_if_needed`) + steer drain (`agent_messages`) |
| Capability events (policy on a seam) | `on_event` / `AgentEvent` surface (confirmation, tool start/end, model switch) |
| Extension points (add behavior without editing the loop) | Nudge/escalation checkpoints injected as `[TASK]`/`[MODEL SWITCH]` messages rather than new loop branches |

**Where YiAi diverges from a full harness:** policy still lives *inside* the loop (confirmation, escalation, nudge guards are `if` branches), and there is no Cordis-style reversible plugin tree. The next step toward harness parity would be to extract those `if` branches into event listeners — the seams already exist, the composition layer does not.
