# Agent Architecture Patterns

> **An AI agent is a loop: observe → think → act → observe.** The patterns below are based on YiAi's agent loop (2026-08-08).

## Core loop

```
User task → [LLM thinks] → tool call → execute → tool result → [LLM thinks] → ... → done
```

## Resilience patterns (from YiAi agent loop)

### 1. Narrate-and-stop guard
**Problem**: Model describes a tool but never invokes it.  
**Solution**: Check if response text names registered-but-unexecuted tools. If so, inject `[CONTINUE]` nudge. Bounded by `max_nudges`.

### 2. Failure-based model escalation
**Problem**: Weak model stalls on complex tasks.  
**Solution**: After nudges exhausted, swap to a stronger fallback model. Emit `model_switch` event. Bounded to one escalation per run.

### 3. Confirmation gate
**Problem**: Write operations need user approval.  
**Solution**: Emit `confirmation_required` event, pause loop, poll decision store (120s timeout). Auto-block rejected calls via rejection memory.

### 4. Turn-budget awareness
**Problem**: Model doesn't know its own turn limit, over-plans and gets cut off.  
**Solution**: Inject `[BUDGET]` note when within 3 turns of `max_turns`. One-shot per run.

### 5. Repeated-observation spin guard
**Problem**: Model re-issues the same tool call, gets the same result, loops.  
**Solution**: Detect 3 consecutive identical observations. Inject `[TASK]` nudge. Narration-only turns reset the chain.

### 6. Oversized result bounding
**Problem**: `db_list` returns 75K tokens — exceeds context window.  
**Solution**: Bound tool results at LLM-context boundary (head 70% + tail 22% + note). Persistence + UI keep full content.

### 7. Resume-by-session
**Problem**: After `max_turns_reached`, resuming re-runs completed writes.  
**Solution**: Persist full `agent_messages` trajectory per session. Resume restores trajectory + injects `[RESUME]` note.

## Tool design patterns

| Pattern | Description | Example |
|---------|------------|---------|
| **Generic tools** | One tool handles many collections via schema | `db_create(collection, data)` vs `menu_create(...)` |
| **Schema-as-context** | Tool returns collection schema so LLM reasons over structure | `db_schema` returns field definitions + rules |
| **Read-before-write** | Read tools are unrestricted; writes are gated | `db_list` (read-only) vs `db_create` (confirmation-gated) |
| **Orphan guard** | Delete checks for children via `parent_ref_field` | `db_delete` refuses when children exist |

## Anti-patterns

- **Hard-coding per-domain tools.** `menu_create`, `bug_create`, `story_create` → code explosion. Use generic tools with schema-as-context.
- **No confirmation gate for writes.** An agent that can write without approval is a liability. Always gate destructive operations.
- **No turn budget.** An agent without `max_turns` can loop forever on a bad tool call. Always set a limit.
- **No disconnect detection.** A user who closes the tab should abort the agent, not leave it running for 120s.
