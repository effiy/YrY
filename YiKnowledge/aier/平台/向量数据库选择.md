# Vector Database Selection Guide

> **When to use:** When setting up a RAG pipeline or evaluating whether the current vector store is still the right choice.

## Key dimensions

| Dimension | What to evaluate |
|---|---|
| **Scale** | How many vectors? (1K, 1M, 100M+) |
| **Query latency** | P99 for nearest-neighbor search at expected scale |
| **Recall** | How accurate are the search results? (recall@10, recall@100) |
| **Filtering** | Can you combine vector search with metadata filters? |
| **Index type** | HNSW, IVF, DiskANN — affects latency/recall tradeoff |
| **Operational cost** | Self-hosted vs. managed; maintenance burden |
| **Ecosystem fit** | Does it integrate with your existing stack? |

## Comparison

| Database | Type | Best for | Scale limit | Managed option | YiAi fit |
|---|---|---|---|---|---|
| **MongoDB Atlas Vector** | Document DB + Vector | Apps already on MongoDB | 10M+ vectors | Yes (Atlas) | Current — best fit |
| **Chroma** | Embedded vector DB | Prototyping, small-scale | 100K vectors | No | Prototyping |
| **Qdrant** | Dedicated vector DB | High-performance search | 1B+ vectors | Yes (Cloud) | If MongoDB outgrown |
| **Milvus** | Distributed vector DB | Large-scale production | 10B+ vectors | Yes (Zilliz) | Overkill for current scale |
| **Pinecone** | Managed vector DB | Zero-ops, fast setup | 1B+ vectors | Yes (managed only) | Good if moving to managed |
| **pgvector** | PostgreSQL extension | Apps already on Postgres | 10M vectors | Via Postgres | If using Postgres |
| **Weaviate** | Vector DB + GraphQL | Hybrid search out of the box | 1B+ vectors | Yes (Cloud) | Good hybrid search |

## Decision tree

```
How many vectors will you store?
├─ < 100K → Chroma (embedded, zero setup)
├─ 100K — 10M → Check existing DB first
│   ├─ Already on MongoDB? → MongoDB Atlas Vector Search
│   ├─ Already on Postgres? → pgvector
│   └─ Neither → Qdrant or Pinecone
└─ > 10M → Milvus or Pinecone

Do you need hybrid search (vector + keyword)?
├─ Yes → Weaviate or MongoDB Atlas (with text index)
└─ No → Any from the comparison table

Self-hosted or managed?
├─ Self-hosted → Qdrant, Milvus, Chroma
└─ Managed → Pinecone, MongoDB Atlas, Zilliz (Milvus), Weaviate Cloud
```

## YiAi's Current Setup: MongoDB Atlas Vector Search

YiAi uses **MongoDB Atlas Vector Search** — the right choice because:

1. **Single DB for all data** — No need to maintain a separate vector store
2. **Already on MongoDB** — Documents, sessions, and vectors all in one place
3. **Hybrid search** — Combine `$vectorSearch` with `$search` (text) for hybrid retrieval
4. **Metadata filtering** — Pre-filter by `tags`, `category`, `roles` before vector search

### Index configuration

```javascript
// YiAi vector search index
{
  "mappings": {
    "dynamic": true,
    "fields": {
      "embedding": {
        "type": "knnVector",
        "dimensions": 1536,        // matches embedding model
        "similarity": "cosine"
      }
    }
  }
}
```

### Query pattern (hybrid retrieval)

```python
# YiAi's hybrid retrieval: vector + keyword
pipeline = [
    {
        "$vectorSearch": {
            "index": "vector_index",
            "path": "embedding",
            "queryVector": query_embedding,
            "numCandidates": 100,
            "limit": 10
        }
    },
    {
        "$match": {
            "tags": {"$in": context_tags},   # metadata filter
            "status": "stable"               # only active content
        }
    }
]
```

## Migration triggers

When to move from MongoDB Atlas Vector to a dedicated vector DB:

| Trigger | Recommendation |
|---|---|
| > 10M vectors and latency P99 > 200ms | Evaluate Qdrant or Milvus |
| Need sub-10ms query latency at scale | Qdrant (Rust-based, optimized) |
| Need disk-based index for cost efficiency | Milvus (DiskANN) |
| MongoDB Atlas cost exceeds dedicated vector DB cost | Compare TCO |

## Anti-patterns

| Anti-pattern | Why it fails | What to do instead |
|---|---|---|
| Reaching for a dedicated vector DB when MongoDB already works | Adds operational complexity for no benefit | Use what you have until you outgrow it |
| Choosing based on benchmark alone | Benchmarks use ideal conditions; your data and queries are different | Test with your actual data and query patterns |
| Ignoring metadata filtering performance | Vector search alone returns irrelevant results; filtering is essential | Test combined vector + metadata queries before deciding |
| No migration plan | Switching vector DBs later is painful (re-indexing all embeddings) | Document the migration triggers and process upfront |
