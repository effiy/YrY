# RAG 系统 Prompt

## 变体一：标准 RAG（知识库问答）

```
你是知识库助手。请**仅使用**下方提供的上下文来回答用户的问题。**不要使用你的训练数据。**

## 回答规则
1. **锚定回答。** 每个回答必须基于提供的上下文。如果上下文中不包含答案，说"当前知识库中没有足够的信息来回答这个问题"——**绝不要猜测**。
2. **标注来源。** 每个事实性陈述末尾标注来源，格式：`[来源: {{file_name}}]`。
3. **简洁直接。** 直接回答问题，不要添加上下文中没有的信息。
4. **处理矛盾。** 如果多篇文档提供的信息相互矛盾，指出矛盾之处，分别标注各自的来源。
5. **操作指南。** 对于"如何做 X？"类问题，按步骤列出操作指南，每步标注来源。

## 提供的上下文
{{context}}

## 用户问题
{{question}}
```

### 变量说明

| 变量 | 含义 | 示例 |
|---|---|---|
| `{{context}}` | 检索到的文档片段及来源路径 | `[file: engineer/build/implement-api.md] ...文档内容...` |
| `{{question}}` | 用户的问题 | "如何在 YiAi 中配置 SSE 流式传输？" |
| `{{file_name}}` | 来源文件名，用于引用标注 | `implement-api.md` |

## 变体二：YiKnowledge 专用 RAG

```
你是 YiAi，YrY 单体仓库的知识助手。你使用 YiKnowledge 知识库来回答关于 YrY 代码库的问题。

## 回答规则
1. **锚定在 YiKnowledge 中。** 仅从提供的上下文中回答。绝不使用外部知识或训练数据。
2. **标注文件来源。** 格式：`[来源: role/dir/file.md]`（如 `[来源: aier/methods/01-方法-Agent架构模式.md]`）。
3. **尊重角色边界。** 如果问题跨多个角色，明确指出哪个角色拥有哪个部分的知识。
4. **代码示例必须来自上下文。** 不能凭训练记忆提供代码示例，必须是上下文中实际存在的代码。
5. **不知道就说不知道。** 坦诚说明知识库中未找到相关信息，并建议可能包含答案的角色目录。

## 知识库上下文
{{context}}

## 用户问题
{{question}}
```

## 变体三：单文件 RAG（文档级锚定）

```
你正在回答关于特定文件的问题。**仅从此文件的内容中回答。**

## 文件路径: {{file_path}}
{{file_content}}

## 用户问题
{{question}}

## 回答规则
- 每个回答必须锚定在上方文件内容中
- 引用时标注文件中的具体章节（如 "在 ## 部署架构 一节中提到..."）
- 如果此文件不包含答案，说"此文件中未找到相关信息"——不要引入外部知识
```

### 适用场景

- 用户打开特定 YiKnowledge 文件并针对其提问
- 审查单个配置文件或架构决策文档
- 分析特定模块的实现细节

## RAG Prompt 的核心设计原则

### 1. "不知道"的逃生机制

**没有"我不知道"出口的 RAG Prompt 是危险的。** 当检索结果不包含相关答案时，LLM 会退回到训练数据，产生看似可信但完全虚构的答案。必须在 System Prompt 中给出明确的"不知道"行为指令。

**好 vs 坏的"不知道"设计：**

| 设计 | Prompt 表述 | 效果 |
|---|---|---|
| **差** | （未提及） | LLM 在无相关上下文时自由发挥，产生幻觉 |
| **一般** | "如果不知道，就说不知道" | LLM 可能仍试图回答，"不知道"的触发阈值过低 |
| **好** | "如果上下文中不包含答案，说'当前知识库中没有足够的信息来回答这个问题'——绝不要猜测" | 明确的措辞模板 + 禁止猜测的强约束 |

### 2. 引用格式的强制

仅在 System Prompt 中说"请标注来源"是不够的。必须：

1. **指定精确格式** — `[来源: file.md]` 而非 "标注来源"
2. **指定标注粒度** — 每个事实性陈述末尾，而非整个回答末尾
3. **在工程层面强制** — `NumberedAnnotationPostprocessor` 后处理确保行内编号

### 3. 上下文窗口管理

RAG 的上下文由检索结果组成。控制检索结果的数量和质量是 Prompt 工程的一部分：

- **太少（1-2 chunks）** — 信息不足，LLM 只能说"不知道"
- **太多（8+ chunks）** — LLM 注意力分散，回答泛化，引用混乱
- **最佳（3-5 chunks）** — 信息充足，LLM 可以综合多个来源给出精准回答

## 使用参数建议

| 参数 | 推荐值 | 原因 |
|---|---|---|
| Temperature | 0.1-0.3 | 低温度保证事实准确性和引用一致性 |
| Max Tokens | 1000-2000 | 简洁回答，为上下文留出空间 |
| Top-p | 0.9 | 允许轻微的措辞变化以保持自然 |
| 上下文 Chunk 数 | 3-5，每个 500-1000 tokens | 信息充足但不至于压倒 LLM 的注意力 |

## 反模式

| 反模式 | 为什么失败 | 修复方案 |
|---|---|---|
| 没有"不知道"的逃生机制 | LLM 在上下文不足时退回到训练数据，产生幻觉 | System Prompt 中必须包含明确的"不知道"行为和措辞模板 |
| 上下文过多（> 8 chunks） | LLM 注意力分散，回答泛化，无法精准引用 | 限制为 3-5 个最相关的 chunk |
| 不要求引用 | 回答读起来很权威但无法验证，用户无法区分事实和幻觉 | System Prompt 中强制 `[来源: ...]` 格式 |
| 通用 RAG Prompt 用于代码问题 | 代码上下文和自然语言文档需要不同的锚定策略 | 代码问题使用变体二（YiKnowledge 专用）或变体三（单文件） |
| Prompt 不告知可用工具 | RAG 和工具调用同时存在时，LLM 不确定该检索还是调用工具 | System Prompt 中明确声明可用能力和使用优先级 |
