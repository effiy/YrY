# 代码审查 Prompt

## 变体一：基础代码审查

```
你是一位资深代码审查专家。请从以下四个维度审查下列代码：

1. **安全性** — SQL 注入、XSS 跨站脚本、认证绕过、密钥泄露、不安全反序列化、路径遍历
2. **性能** — N+1 查询、不必要的内存分配、阻塞操作、缺失的数据库索引、低效的数据结构
3. **可读性** — 命名不清晰、边界情况处理缺失、过于复杂的逻辑、缺少关键注释（非显而易见的逻辑）
4. **正确性** — 逻辑错误、边界条件错误（off-by-one）、null/undefined 处理、竞态条件、异常处理缺失

对于发现的每个问题，请按以下格式报告：
- **严重程度**: 严重 / 重要 / 建议
- **位置**: 行号或函数名
- **问题**: 哪里不对？为什么是问题？
- **修复**: 具体的代码修复建议

如果代码看起来正确，请明确说明"未发现问题"。不要凭空臆造问题。

```
```

### 变量说明

| 变量 | 含义 | 示例 |
|---|---|---|
| `{{language}}` | 编程语言 | `python`、`typescript`、`vue` |

### 使用参数

- **Temperature:** 0.0-0.2（审查结果必须确定，同一段代码每次给出一致的反馈）
- **Max Tokens:** 2000（审查意见应简洁精准）

## 变体二：PR 审查

```
你正在审查一个 Pull Request。PR 描述如下：

> {{pr_description}}

## 变更文件（diff）
{{diff}}

## 审查要点
1. 变更是否与 PR 描述一致？是否有描述之外的修改？
2. 是否存在预期之外的副作用？（如修改了共享模块但未更新所有调用方）
3. 变更是否最小化？（是否有不相关的重构混入？）
4. 是否有缺失的测试？（新增功能是否覆盖了正常路径和边界情况？）
5. 是否存在安全性或性能隐患？

## 输出格式
- **审查结论**: Approve（批准）/ Request Changes（要求修改）/ Comment（仅评论）
- **变更摘要**: 2-3 句话总结本次变更
- **问题清单**: 如有，按严重程度排序（严重 → 重要 → 建议）
- **测试建议**: 建议补充的测试用例（如适用）
```

### 变量说明

| 变量 | 含义 | 示例 |
|---|---|---|
| `{{pr_description}}` | PR 描述文本 | "修复参数名不匹配：query → filter" |
| `{{diff}}` | Git diff 输出 | `git diff main...feature-branch` |

### 使用建议

- **提供上下文** — 包含 PR 描述和模块背景，帮助 AI 理解设计意图
- **控制 diff 大小** — 单次审查不超过 500 行变更，过大的 diff 会导致遗漏
- **配合人工审查** — AI 审查作为第一道防线，人工审查关注设计层面和业务逻辑

## 变体三：增强建议审查

```
请审查下列代码并提出 3-5 个具体的优化建议。按投入产出比排序：

1. 投入最低、收益最高的排在最前面
2. 每个建议必须包含：
   - **建议内容**: 具体改什么？
   - **原因**: 为什么改？
   - **预期收益**: 改之后能得到什么？（性能提升、安全性增强、可维护性改善等）
   - **风险**: 改动可能带来的副作用是什么？

## YrY 项目专项审查要点

审查 YiVad、YiAi、YiPet 代码时，额外关注：

| 项目 | 专项审查项 |
|---|---|
| **YiVad** | `query` vs `filter` 参数名（RPC 契约）、`target_file` vs `path`、Pinia Store 中是否直接使用 axios、是否使用 Options API |
| **YiAi** | RPC 信封格式（`module_name.method_name.parameters`）、错误码映射完整性、SSE 流式响应的心跳和超时 |
| **YiPet** | `ApiClient` 封装是否绕过、content script 和 service worker 的通信边界、chrome.storage 使用是否正确 |
| **通用** | 跨项目参数名契约（`filter` 非 `query`、`target_file` 非 `path`）、Conventional Commits 格式 |

## 反模式

| 反模式 | 为什么失败 | 修复方案 |
|---|---|---|
| 无上下文审查 | AI 将设计选择标记为"问题"，产生大量噪声 | 提供 PR 描述或模块背景信息 |
| 一次审查代码过多 | AI 在长文件中遗漏关键问题 | 单次审查一个函数或一个文件，分批次进行 |
| Temperature > 0.3 | 同一段代码每次给出不同的审查意见，失去可信度 | 代码审查使用 temperature 0.0-0.2 |
| 盲目接受所有 AI 建议 | AI 的建议可能破坏系统的其他部分，建议不等同于真理 | 每个建议都需人工判断后再应用，特别是"重构"类建议 |
| 审查不考虑项目约定 | AI 标记"命名不规范"但实际是项目约定 | 在审查 Prompt 中嵌入项目编码规范作为上下文 |
