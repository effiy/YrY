# 思维链提示模式

> **适用场景：** 需要多步推理的任务——调试、架构决策、代码生成、数据分析。思维链（Chain-of-Thought, CoT）提示可使复杂任务的准确率提升 20-50%。**核心原理：让模型在给出最终答案之前，先将推理过程显式地写出来。**

## 模式一：零样本思维链

在任意 Prompt 末尾添加"让我们一步步思考"（Let's think step by step.）。

### 适用场景

快速提升任意推理任务的准确率。不需要提供示例（因此称为"零样本"）。适合场景多变、无法预先准备示例的情况。

### 示例

```
为什么 YiVad 发送的文件写入请求在 YiAi 返回 422 错误？

让我们一步步思考。
```

**预期输出：** 模型会逐步推理 —— YiVad 发送 `path` 参数 → YiAi 的文件写入端点期望 `target_file` 参数 → 参数名称不匹配 → FastAPI 参数校验失败 → 返回 HTTP 422。

### 注意事项

- 零样本 CoT 的效果不稳定，某些模型可能只是重复问题而非真正推理
- 对于非常复杂的任务（7 步以上推理），零样本 CoT 的准确率显著低于少样本或结构化 CoT
- 可以在 System Prompt 中预设"请逐步推理"作为默认行为

## 模式二：少样本思维链

在正式问题之前提供 2-3 个完整的推理示例。

### 适用场景

当零样本 CoT 不够可靠时，或者需要特定推理格式时。示例相当于给模型一个"推理模板"，让它模仿这个格式来处理新问题。

### 示例

```
示例 1:
问题: 为什么从 YiPet 调用 query_documents 时返回了空结果？
推理: 让我追踪调用链路：
1. YiPet 的 ApiClient 发送 { query: {status: "active"} } 给 data_service.query_documents
2. 后端的 _build_filter 函数查找参数中的 `filter` 字段，而非 `query`
3. `query` 参数被静默忽略，filter 为空对象
4. MongoDB 查询没有过滤条件 → 应该返回全部文档而非空
等一下——如果 filter 为空，应该返回全部文档，不是空。
5. 检查分页：pageSize 默认 10，pageNum 默认 1
6. 如果集合中根本没有任何文档，才返回空列表
答案: `query` 参数被静默忽略。正确参数名是 `filter` 而非 `query`。

示例 2:
问题: 为什么 macOS 上知识监视器检测不到文件变化？
推理: 让我追踪监视器的配置：
1. watcher.py 使用 apscheduler 每 5 秒轮询一次
2. macOS 上的初始实现尝试使用文件系统事件（FSEvents）
3. macOS 的 FSEvents 有一个已知问题：在网络驱动器上静默丢弃事件
4. 因此监视器改为轮询模式（apscheduler，5 秒间隔）
答案: macOS FSEvents 静默丢弃事件。当前方案使用 5 秒间隔的轮询替代。

现在请回答：
问题: {{question}}
```

### 示例设计原则

- **示例必须来自同一领域** — 代码调试的 CoT 示例不能用来教模型做医疗诊断
- **示例应覆盖典型失败模式** — 让模型学会如何处理"排查后发现初始假设错误"的情况
- **2-3 个示例最佳** — 过少则模板不够清晰，过多则 Token 成本上升且模型可能过拟合示例

## 模式三：结构化思维链

定义模型必须遵循的特定推理结构。结构本身成为输出格式约束，让推理过程可验证。

### 适用场景

当推理结果需要被审查、验证，或需要提取中间步骤用于后续处理时。

### 示例一：Bug 诊断

```
请按以下结构诊断下列 Bug：

## 1. 症状描述
观察到的行为是什么？与期望行为有何差异？

## 2. 复现步骤
列出精确的复现步骤（含环境信息）

## 3. 假设分析
最可能的原因是什么？（标注置信度：高/中/低）
其他可能原因有哪些？

## 4. 验证方法
如何验证或排除上述假设？
具体需要检查什么日志、代码或数据？

## 5. 修复方案
最小化修复方案是什么？（附代码示例）
是否需要同步修改其他相关模块？

## Bug 报告
{{bug_description}}
```

### 示例二：架构决策评估

```
请按以下结构评估下列架构决策：

## 1. 问题背景
我们在解决什么问题？为什么需要做这个决策？

## 2. 候选方案
列出 2-3 个候选方案，每个方案说明：
- 核心思路（一句话）
- 优势（至少 2 点）
- 劣势（至少 2 点）

## 3. 权衡分析
- 选择各方案我们获得什么？失去什么？
- 关键约束是什么（时间、资源、兼容性）？

## 4. 推荐方案
推荐哪个方案？为什么？（标注置信度：高/中/低）
推荐的方案有哪些已知风险？如何缓解？

## 决策上下文
{{decision_context}}
```

### 结构化 CoT 的核心价值

- **可复现** — 相同输入产生相同结构的输出，便于自动化解析
- **可审查** — 每个推理步骤独立可验证，而非一个黑盒结论
- **可集成** — 中间步骤可被下游系统消费（如自动提取假设用于搜索相关文档）

## 模式四：自洽性（Self-Consistency）

同一个 Prompt 运行 3-5 次（temperature > 0），取出现最频繁的答案。

### 适用场景

当准确性至关重要且可以承受多次 API 调用成本时。最适合数学推理、逻辑推理和调试诊断。

### 实现

```python
from collections import Counter

def self_consistent_answer(prompt: str, n: int = 5, temperature: float = 0.7) -> str:
    """运行 n 次推理，返回最一致的答案。"""
    answers = []
    for _ in range(n):
        response = llm.chat(prompt, temperature=temperature)
        answers.append(extract_final_answer(response))

    # 返回出现次数最多的答案
    counter = Counter(answers)
    most_common, count = counter.most_common(1)[0]
    agreement_rate = count / n
    print(f"自洽性: {agreement_rate:.0%} ({count}/{n})")
    return most_common
```

### 不适用场景

- 成本敏感型应用（每次推理需要 5 倍 API 调用）
- 延迟敏感型应用（5 倍的等待时间）
- 简单任务（零样本 CoT 已经足够）
- Temperature = 0 时（所有运行结果一致，没有多样性）

## 模式选择决策树

```
任务复杂度分析
├─ 简单（单步即可完成）
│   → 不需要 CoT
│   例："1 + 1 等于几？"
│
├─ 中等（2-3 步推理）
│   → 零样本 CoT（"让我们一步步思考"）
│   例："为什么这个 API 返回 422？"
│
├─ 复杂（4-6 步推理）
│   → 少样本 CoT（2-3 个同领域示例）
│   例："这段代码的生产环境风险有哪些？"
│
├─ 非常复杂（7+ 步推理）
│   → 结构化 CoT（定义推理框架）
│   例："设计一个支持多租户的 RAG 系统架构"
│
└─ 关键决策（不容出错）
    → 自洽性（3-5 次推理，多数投票）
    例："这个数据库迁移脚本是否安全？是否会导致数据丢失？"
```

## 反模式

| 反模式 | 为什么失败 | 修复方案 |
|---|---|---|
| 对简单任务使用 CoT | 增加推理开销却没有质量收益，响应更慢 | CoT 仅在需要多步推理时使用 |
| 自洽性使用时 temperature=0 | 所有运行结果一致，多数投票失去意义 | 自洽性需要 temperature ≥ 0.5 以产生多样性 |
| 少样本示例与目标任务领域不匹配 | 模型模仿错误的推理模式 | 使用同领域、同类型的推理示例 |
| 结构化 CoT 不验证中间步骤 | 模型按格式输出了推理步骤但内容可能是错的 | 审查中间步骤的正确性，不要仅依赖结构完整性 |
| 推理链太长导致注意力分散 | 超过 15 步后模型在链条中间丢失关键信息 | 将长推理链拆分为多个子问题，逐个求解 |
