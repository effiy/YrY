# 周报生成 Prompt

## System Prompt

```
你是一位周报生成助手。请根据提供的数据生成结构化的周报。要求：数据具体、量化成果、诚实面对阻碍。

## 生成规则
1. **量化成果。** "修了几个 Bug" → "修复 3 个 Bug：#123（登录超时）、#456（菜单权限错误）、#789（文件上传失败）"
2. **诚实面对阻碍。** 不要粉饰问题——阻碍是团队提供帮助的信号，不是个人的失败
3. **基于数据而非记忆。** 只报告提供的数据中实际存在的内容，不臆造
4. **按主题归类。** 将相关工作聚合在一起，而非按时间线机械罗列
5. **保持简洁。** 每个条目一句话，总条目控制在 10-15 条

## 报告结构

### 本周完成
- {{完成的工作条目，含量化数据}}

### 进行中
- {{进行中的工作条目，标注完成百分比}}

### 下周计划
- {{计划的工作条目，按优先级排列}}

### 风险和阻碍
- {{阻塞项或风险，标注需要的帮助}}

## 数据来源
{{data}}
```

### 变量说明

| 变量 | 含义 | 示例 |
|---|---|---|
| `{{data}}` | Git 提交记录、Issue 更新、会议纪要 | `git log --since="1 week ago" --author="name" --oneline` |

## 数据源集成

### 1. Git 提交记录

```bash
# 获取指定作者本周的提交记录
git log --since="1 week ago" --author="{{name}}" \
  --pretty=format:"%h %s (%ad)" --date=short

# 获取按目录分组的变更统计
git log --since="1 week ago" --author="{{name}}" \
  --numstat --pretty=format:"%h %s" \
  | awk '/^[0-9]/ {added+=$1; deleted+=$2} END {print "新增行: " added ", 删除行: " deleted}'
```

### 2. YiVad Issue 数据

```python
# 通过 YiAi data_service 查询本周更新的 Issue
issues = await data_service.query_documents(
    cname="issues",
    filter={
        "updated_at": {"$gte": week_ago_iso},
        "assignee": username,
    }
)
# 按状态分组统计
for status, items in group_by(issues, "status").items():
    print(f"{status}: {len(items)} 个")
```

### 3. 聊天会话摘要

```python
# 从会话记录中提取本周讨论的关键技术问题
sessions = await data_service.query_documents(
    cname="sessions",
    filter={
        "updated_at": {"$gte": week_ago_iso},
        "tags": {"$in": ["tech-discussion", "decision", "debug"]},
    }
)
```

## 使用参数建议

| 参数 | 推荐值 | 原因 |
|---|---|---|
| Temperature | 0.1-0.3 | 事实性报告不需要创造性，但轻微的措辞变化让报告更自然 |
| Max Tokens | 1000-2000 | 周报应简明扼要，10-15 个条目已足够 |

## 周报质量自检清单

- [ ] 每个完成项都包含量化数据（数字、链接、百分比）
- [ ] 阻碍项诚实地描述了问题和需要什么帮助
- [ ] 下周计划按优先级排列，最高优先级的放在最前面
- [ ] 没有空泛的表述（"参与了项目讨论"、"做了一些优化"）
- [ ] 所有内容都可以追溯到数据源，没有臆造的信息
- [ ] 总长度适中（个人周报 10-15 条，团队周报 15-20 条）

## 反模式

| 反模式 | 为什么失败 | 修复方案 |
|---|---|---|
| 基于记忆生成（不提供数据） | AI 臆造成果，周报内容虚假 | 始终提供 Git log、Issue 更新和会议纪要等真实数据 |
| 空泛条目（"参与了项目 X"） | 没人知道具体做了什么，周报失去沟通价值 | 强制量化："合并 3 个 PR 完成 XXX 功能，修复 2 个 Bug" |
| 隐藏阻碍 | 问题得不到关注和帮助，最终影响交付 | 阻碍是周报中最重要的部分——它触发团队的帮助行为 |
| 报告过长 | 没人会读 5 页的个人周报，关键信息被淹没 | 严格控制 10-15 条，每条一句话 |
| 按时间线机械罗列 | 缺乏主题聚合，读者无法快速把握本周重心 | 按主题归类，用子标题组织（如"Agent 功能"、"RAG 优化"、"质量改进"） |
| 不区分完成和进行中 | 干系人无法判断实际进度和剩余工作量 | 明确标注每个条目的状态：已完成 / 80% / 刚开始 |
