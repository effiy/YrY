# 头脑风暴 —— 结构化需求澄清与方案探讨

> **核心信条：先问再做。** 在不确定方向时写代码 = 在不知道目的地时开车。头脑风暴的价值不在于产生想法，而在于**排除错误的想法**——用 10 分钟讨论省下 2 小时返工。

## 为什么需要这个技能？

superpowers 的 `/brainstorm` 是社区公认最有价值的技能——不是因为它能生成代码，而是因为它**阻止了错误的代码被生成**。统计表明，跳过需求澄清直接编码的返工率高达 40-60%。

本技能的设计原则：
1. **不写代码** — 头脑风暴阶段禁止实现，只讨论方案
2. **不假设** — 所有不确定的信息必须与用户确认
3. **不推销** — 呈现多个方案及取舍，由用户决策

---

### 进入标准
- [ ] 用户有一个想法/需求/改进方向，但具体方案不明确
- [ ] 存在多种可能的实现路径需要对比
- [ ] 涉及架构或技术选型层面的决策
- [ ] 不是已有明确 PRD 可以直接执行的任务

### 退出标准
- [ ] 设计方向已确认（用户明确选择了一个方案）
- [ ] 设计摘要已产出（含核心决策、选定方案、关键风险）
- [ ] 下一步明确：→ prd-creator（撰写正式需求）或 → task-planning（直接规划实现）

## 工作流

```
捕获意图 → 澄清边界 → 方案探讨 → 确认方向 → 产出摘要
```

### 阶段 1：捕获意图 —— 理解用户真正想要什么

从用户的消息中提取关键信息。**不要让用户重复自己**——从上下文中提取你能获取的所有信息。

提炼为以下结构：

```markdown
## 我理解的需求

**目标**：[一句话描述用户想要达成的结果]
**动机**：[为什么要做？解决了什么问题？]
**当前状态**：[现有系统/流程是什么样的]
**涉及范围**：[初步判断涉及哪些模块/项目]
```

向用户确认：「以上理解是否正确？有没有需要补充或纠正的？」

### 阶段 2：澄清边界 —— 问对的问题

需求模糊的地方，通过结构化提问澄清。不是泛泛地问「还有什么补充？」，而是针对具体缺口提问。

#### 澄清框架

| 维度 | 关键问题 | 为什么重要 |
|------|---------|-----------|
| **范围** | 这次要做到什么程度？哪些明确不做？ | 防止范围蔓延 |
| **约束** | 技术栈限制？时间限制？兼容性要求？ | 排除不可行的方案 |
| **优先级** | 什么是最重要的？速度/质量/完整性？ | 指导方案取舍 |
| **用户** | 谁会使用？使用频率？技术能力？ | 影响交互设计和错误处理 |
| **数据** | 涉及哪些数据？从哪里来？存哪里？ | 影响数据流设计 |
| **集成** | 需要和哪些现有系统交互？ | 发现隐藏的依赖 |

#### 检查项目知识库

在提问之前，先检查 `YiKnowledge/projects/` 中是否有相关上下文：

- `projects/<project>/architecture/` — 现有架构约束
- `projects/<project>/prds/` — 是否有相关 PRD
- `projects/<project>/bugs/` — 相关模块的历史问题
- `projects/<project>/architecture/` — 跨项目架构报告

### 阶段 3：方案探讨 —— 多方案对比

对于非平凡的需求，提出 2-3 个可行方案。每个方案包含：

```markdown
### 方案 A：[名称]

**思路**：[一句话概述]
**优点**：
  - [具体优点 1]
  - [具体优点 2]
**缺点**：
  - [具体缺点 1]
  - [具体缺点 2]
**复杂度**：低 / 中 / 高
**涉及变更**：
  - `path/to/file` — [变更说明]
**风险**：[主要风险及缓解措施]
**与现有架构的关系**：[是否符合现有模式？是否需要引入新模式？]
```

#### 方案选择原则

- **简单优先** — 同等条件下，选择更简单的方案
- **渐进式** — 如果可能，方案应该可以分阶段实施
- **可逆** — 优先选择容易回滚的方案
- **符合现有模式** — 新方案应尽量遵循项目已有的架构模式

### 阶段 4：确认方向 —— 锁定决策

用户选择方案后，确认关键设计决策：

```markdown
## 确认的设计决策

1. **[决策点]**：[选择方案 A，因为...]
2. **[决策点]**：[选择方案 A，因为...]

## 明确排除

- [X] 不做什么
- [X] 不涉及什么
```

确认后告知用户下一步：「方向已确认。可以用 **prd-creator** 撰写正式 PRD，或用 **task-planning** 直接开始实现规划。」

### 阶段 5：产出摘要 —— 可执行的输出

头脑风暴完成后，产出结构化摘要，方便后续技能衔接：

```markdown
# 头脑风暴摘要：[主题]

**日期**：YYYY-MM-DD
**状态**：方向已确认

## 核心决策

[3-5 条关键决策]

## 选定方案

[方案名称]：[一句话描述]

## 涉及范围

- 项目：[yiai / yivad / yipet]
- 模块：[具体模块名]
- 预估文件数：~N 个

## 关键风险

| 风险 | 缓解措施 |
|------|---------|
| [风险] | [措施] |

## 下一步

建议使用 [prd-creator / task-planning] 继续推进。
```

## 常见场景

### 场景 1：模糊的功能需求

```
用户：我想给 YiVad 加个搜索功能

助手：[头脑风暴模式]
  我理解你想为 YiVad 添加搜索功能。在讨论方案之前，先确认几点：
  
  1. 搜索范围 — 全局搜索还是某个模块内搜索？
  2. 搜索对象 — 搜索什么内容？菜单？数据？文件？
  3. 搜索方式 — 关键词匹配还是全文检索？
  4. 性能要求 — 数据量有多大？实时搜索还是异步索引？

用户：全局搜索，主要搜菜单和数据，关键词就行，数据量不大

助手：明白了。有两种方案：
  
  方案 A：前端静态搜索 — 数据量不大时，直接在前端对已加载数据做过滤
  方案 B：后端全文检索 — 通过 YiAi RAG 的向量检索做语义搜索
  
  YiVad 目前数据通过 ProTable 服务端分页加载，方案 A 只能搜当前页...
```

### 场景 2：技术选型讨论

```
用户：我们在考虑要不要把 YiVad 的状态管理从 Pinia 换成别的

助手：[头脑风暴模式]
  先确认一下动机——当前 Pinia 方案遇到了什么具体问题？
  
  [用户描述问题后]
  
  了解了。三个选项供参考：
  
  | 选项 | 适合场景 | 不适合 |
  |------|---------|--------|
  | 保持 Pinia | 当前方案没有根本性问题 | — |
  | Pinia + 优化 | 问题是使用方式而非库本身 | — |
  | 替换为 X | Pinia 有无法解决的根本限制 | 迁移成本高 |
  
  基于你描述的「跨组件状态共享繁琐」，这更可能是使用模式问题...
```

### 场景 3：架构决策

```
用户：YiAi 的模块越来越多，路由文件 500 行了，怎么重构？

助手：[头脑风暴模式]
  先确认当前 YiAi 的路由结构...
  [检查项目代码后]
  
  当前状态：单一路由文件注册所有 RPC 方法，500+ 行。
  
  三个方案：
  
  方案 A：按 domain 拆分路由文件
    - 每个 domain 有自己的 router
    - 主路由只做聚合
    - 风险：低，纯文件组织变更
  
  方案 B：引入自动路由发现
    - 装饰器标注 RPC 方法，自动注册
    - 风险：中，改变了路由注册机制
  
  方案 C：引入 API 版本化
    - /v1/ /v2/ 路径前缀
    - 风险：高，影响所有调用方
  
  考虑到「只解决文件组织问题，不改变 RPC 协议」，建议方案 A。
```

## YrY 实战速览

### 例：跨项目数据流设计讨论

用户提出「YiPet 的翻译数据需要统一分析」。应用 brainstorming 流程：

```
捕获意图 → 用户需要在 YiVad 看到翻译统计
澄清边界 → 数据源：YiPet 的翻译记录 | 展示端：YiVad Dashboard
方案探讨 → 
  方案 A：各项目独立上报 → YiAi 聚合查询（符合现有架构）
  方案 B：直接读取对方数据库（破坏模块边界 ❌）
确认方向 → 方案 A，新增 translation_records 集合 + provider_health RPC
产出摘要 → DDR: translation-analytics-api-spec
  参考 YiKnowledge/projects/yiai/workflows/开发规范/08-规范-翻译分析API规范.md
  参考 YiKnowledge/projects/yiai/workflows/架构设计/06-架构-跨项目数据流全景.md
```

**关键教训**：跨项目需求必须检查现有架构文档和模块边界。brainstorming 发现的「方案 B 破坏模块边界」节省了至少 2 天返工。

### 例：技术选型讨论

用户问「YiVad 状态管理要不要从 Pinia 换掉」。检查项目文档后发现：

```
- projects/yivad/devs/ 中所有组件使用 Pinia + Composition API
- 项目强制 Options API 禁止（CLAUDE.md）
- 当前 41 个测试全部基于 Pinia

结论：没有替换的合理理由。建议聚焦使用模式优化（如 storeToRefs 规范），而非替换库。
```

## 原则

- **不写代码。** 头脑风暴阶段禁止实现——只讨论、对比、决策。
- **不假设用户意图。** 宁可多问一句，不要猜错方向。
- **从上下文提取。** 用户已在对话中描述的内容，不要让他重复。
- **提供选择，不推销方案。** 列出多个方案及其取舍，由用户决策。不要只说「我建议...」。
- **控制范围。** 如果讨论涉及太多「未来可能需要」的内容，主动拉回到当前需求。
- **记录决策。** 每个设计决策都记录选择理由——未来回顾时知道「为什么当时这样做」。
- **衔接下游技能。** 头脑风暴完成后，明确指出下一步用什么技能（prd-creator / task-planning）。
