# 设计决策记录（DDR）模板

## 为什么需要 DDR？

头脑风暴中做出的每个非平凡决策都应该记录。DDR 回答「为什么当时选择这样做」——这是代码注释和 git 历史无法提供的信息。

## 模板

```markdown
# DDR-[编号]: [决策标题]

**日期**：YYYY-MM-DD
**状态**：proposed / accepted / deprecated / superseded
**决策者**：[人/AI]

## 背景

[需要做决策的上下文——什么问题触发了这个决策？有什么约束？]

## 决策

[一句话描述做出的决策]

## 考虑的方案

### 方案 A：[名称]（已选择）

**描述**：[方案概要]
**优点**：
- [优点]
**缺点**：
- [缺点]

### 方案 B：[名称]（未选择）

**描述**：[方案概要]
**排除原因**：[为什么不选]

### 方案 C：[名称]（未选择）

**描述**：[方案概要]
**排除原因**：[为什么不选]

## 影响

**涉及模块**：[受影响的模块/文件]
**破坏性变更**：是 / 否
**迁移路径**：[如有破坏性变更，描述迁移步骤]

## 后果

[决策实施后回顾——实际效果是否符合预期？有什么意外后果？]
```

## 何时需要 DDR

- 涉及架构层面的选择（选型、模式、分层）
- 需要在多个可行方案中做取舍
- 决策会影响其他模块或项目
- 决策理由不是显而易见的

## 何时不需要 DDR

- 显而易见的决策（遵循已有模式）
- 纯风格偏好（能用 linter 规范）
- 临时决策（会在未来迭代中重访）

## 归档位置

DDR 归档到项目中：

```
YiKnowledge/projects/<project>/architecture/decisions/
```
