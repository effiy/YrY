# 需求澄清问题框架

## 分层提问策略

按优先级从高到低提问。不要一次抛出所有问题——每轮 2-3 个，根据回答调整下一轮。

### 第一层：目标与动机（最重要）

| 问题 | 目的 |
|------|------|
| 这个功能要解决什么用户问题？ | 区分「真实需求」和「解决方案」 |
| 不做这个功能会怎样？ | 判断优先级 |
| 成功标准是什么？ | 定义完成的边界 |
| 谁会使用？使用频率？ | 影响交互和性能设计 |

### 第二层：范围与约束

| 问题 | 目的 |
|------|------|
| 最小可用版本（MVP）是什么？ | 防止范围蔓延 |
| 这次明确不做什么？ | 建立范围边界 |
| 技术栈有限制吗？ | 排除不可行方案 |
| 有时间窗口吗？ | 影响方案选择（快但糙 vs 慢但好） |
| 向后兼容吗？ | 评估迁移成本 |

### 第三层：实现细节

| 问题 | 目的 |
|------|------|
| 数据从哪里来？存量还是新建？ | 确定数据流 |
| 需要和哪些现有模块交互？ | 发现隐藏依赖 |
| 有可以参考的类似功能吗？ | 复用现有模式 |
| 预期数据量/并发量？ | 影响架构选择 |

## 反模式

### ❌ 一次问太多问题

```
助手：我有 10 个问题想确认：
1. 范围是什么？
2. 技术栈约束？
3. 数据来源？
...
10. 错误处理策略？
```

**问题**：用户被问题淹没，可能敷衍回答或直接跳过。

**正确做法**：每轮 2-3 个问题，根据回答调整下一轮。

### ❌ 问用户应该自己找答案的问题

```
助手：YiVad 目前用的是什么路由方案？
```

**问题**：这可以通过读代码回答，不需要问用户。

**正确做法**：先查代码/文档，只问代码里找不到的信息。

### ❌ 直接跳到方案

```
用户：我想加个搜索功能
助手：好的，我推荐用 Elasticsearch
```

**问题**：还没理解需求和约束就推荐方案 = 用锤子找钉子。

**正确做法**：先完成澄清框架的第一层和第二层，再讨论方案。

## 情境适配

| 用户类型 | 调整策略 |
|---------|---------|
| 技术负责人 | 可以深入技术细节，讨论架构取舍 |
| 产品经理 | 聚焦用户场景和业务价值，少谈技术实现 |
| 新成员 | 更多上下文铺垫，解释项目已有模式和约定 |
| 专家用户 | 减少基础问题，聚焦边界和取舍 |
