# PRD 生成器

通过结构化对话创建产品需求文档的交互式助手。逐节引导用户，全程跟踪进度。

**重要提示：** 不要开始实现功能。目标是产出一份清晰、可执行的 PRD，供开发人员或 AI 智能体执行。

**工作流：** 逐节推进，用户以任意顺序选择章节。

### 进入标准
- [ ] 需求方向已确认（brainstorming 完成，或用户已有明确描述）
- [ ] 需要正式的需求文档（不是口头沟通就够的简单任务）
- [ ] 功能的用户故事、功能需求、非目标等需要结构化记录

### 退出标准
- [ ] 9 章节 PRD 已完成（必填章节全部填充）
- [ ] PRD 已导出到 `tasks/prd-[功能名称].md`
- [ ] 下一步：→ task-planning（拆解步骤）或 → issue-creator（拆解为 Issue）

### 阶段 1：开始

用户可能已在触发消息中描述了需求。**从上下文中提取你能获取的所有信息**——不要让用户重复自己。总结你的理解，然后展示 PRD 结构表格。

如果用户已提供足够的细节来填充某些章节，请说明：「根据你描述的内容，我已经可以起草 XX 章节。你想让我从这些开始，还是想先做其他章节？」

### 阶段 2：逐节推进

让用户以任意顺序选择任意章节。对于每个章节：

1. **解释需要什么**——用一句话说明该章节好的标准是什么，并给出一个具体的微型示例。
2. **收集用户输入**——自由文本、要点列表，无论用户有什么都可以。
3. **规范化**——重写为清晰、专业的文档语言。使其明确且可执行，但不要添加用户未提供的内容。如果确实缺少某些内容，指出问题而非凭空编造。
4. **展示并确认**——展示规范化后的版本。用户可以保存、修改或跳到其他章节。
5. **保存并展示进度**——每次保存后，展示已完成和未完成的内容。建议下一个空的必填章节，但始终允许用户自行决定。

### 阶段 3：导出

当用户说「导出」、「保存」、「生成」或「完成」时，将所有已保存的章节按模板组装为完整的 Markdown 文档，保存到 `tasks/prd-[功能名称].md`。

## PRD 结构

| # | 章节 | 是否必填 | 涵盖内容 |
|---|---------|----------|------------------|
| 1 | 引言/概述 | 是 | 问题及预期解决方案的高层描述 |
| 2 | 目标 | 是 | 具体、可衡量的目标 |
| 3 | 用户故事 | 是 | 谁需要什么以及为什么，附带可验证的验收标准 |
| 4 | 功能需求 | 是 | 编号的 FR，描述确切的系统行为 |
| 5 | 非目标（范围之外） | 是 | 明确的边界——此功能不会做什么 |
| 6 | 设计考量 | 否 | UI/UX 说明、原型链接、可复用的组件 |
| 7 | 技术考量 | 否 | 约束、依赖、集成点、性能 |
| 8 | 成功指标 | 否 | 如何衡量成功（例如「将 X 时间缩短 50%」） |
| 9 | 待解决问题 | 否 | 任何尚不确定或需要澄清的事项 |

开始时展示此表格，让用户了解接下来要做什么。

## 用户故事质量

用户故事是最重要的章节——它们驱动实现。在帮助用户编写时应遵循以下原则：

- **每个故事是一个工作单元**——小到可以一次会话完成实现。拆分大故事。
- **验收标准必须是可测试的**——不是「运行正常」，而是「按钮在删除前显示确认对话框」。如果无法通过查看结果来验证某项标准，那它就太模糊了。
- **UI 故事需要浏览器验证**——对于任何涉及 UI 变更的故事，将「使用 dev-browser 技能在浏览器中验证」作为一项标准。
- **编号管理**——US-001, US-002 等，便于在对话和代码中引用。

## 导出

当用户说「导出」、「保存」、「生成」或「完成」时，使用以下精确模板生成最终文档：

```markdown
# PRD: [功能名称]

## 1. 引言/概述
[内容]

## 2. 目标
[内容]

## 3. 用户故事
### US-001: [标题]
**描述：** 作为 [用户]，我希望 [功能] 以便 [收益]。
**验收标准：**
- [ ] 可验证的标准

## 4. 功能需求
- FR-1: ...
- FR-2: ...

## 5. 非目标（范围之外）
[内容]

## 6. 设计考量
[内容]

## 7. 技术考量
[内容]

## 8. 成功指标
[内容]

## 9. 待解决问题
[内容]
```

保存到 `tasks/prd-[功能名称].md`（kebab-case 命名）。如果 `tasks/` 目录不存在，则创建它。

## 与项目文档协作

### 从项目知识提取需求

创建 PRD 前，检查 `YiKnowledge/projects/<project>/` 中是否有可参考的文档：

- **现有架构** → `projects/<project>/architecture/` — 了解技术约束
- **已有 PRD** → `projects/<project>/prds/` — 避免重复或冲突
- **历史 Bug** → `projects/<project>/bugs/` — 了解常见问题区域
- **开发规范** → `projects/<project>/devs/` — 了解开发流程

始终与用户确认从项目文档中提取的理解，不要假设现有内容可以直接迁移。

### PRD 后的下一步

PRD 完成后，推荐的工作流衔接：

```
PRD（本技能产出）
    │
    ├── 复杂功能 → task-planning 技能
    │   将功能需求拆解为可执行步骤
    │   通过三文件模式管理实现过程
    │
    └── 明确任务 → issue-creator 技能
        将用户故事/功能需求转为可追踪的 Issue
        纳入看板管理和迭代计划
```

直接告知用户：「PRD 已完成。下一步可以用 **task-planning** 将功能需求拆解为执行步骤，或用 **issue-creator** 将用户故事转为可追踪的 Issue。」

## 进度跟踪

在脑中维护以下信息：文档名称、当前章节、以及哪些章节已完成。当用户询问进度时，展示如下表格：

```
| 章节 | 状态 | 评分/结果 |
|---------|--------|-------------|
| 引言/概述 | 已完成 | 达标 |
| 目标 | 已完成 | 达标 |
| 用户故事 | 进行中 | - |
| 功能需求 | 待处理 | - |
```

## YrY 实战速览

### 例：列表组件体系 PRD 创建

项目中 `YiKnowledge/projects/yivad/devs/2026-09/01-prd-task-列表组件体系.md`（9 人天）的 PRD 创建过程：

```
上下文提取 → 用户已描述：重构 YiVad 列表页为 ProTable 体系
项目参考 → 检查 projects/yivad/workflows/ 了解现有规范
逐节填充 →
  引言：当前 3 个列表页各自实现分页/筛选/排序逻辑，代码重复率高
  目标：抽取 4 个共享 Composable，迁移 3 个列表页
  用户故事：
    US-001: 作为开发者，我使用 usePage 统一分页逻辑
    US-002: 作为开发者，我使用 useFilter 统一筛选逻辑
    US-003: 作为开发者，我使用 useSort 统一排序逻辑
    US-004: 作为开发者，我使用 useTable 组合上述三个
  功能需求：FR-1 ProTable 驱动，FR-2 服务端分页对齐 RPC 契约...
  非目标：不改变后端 API（仅前端重构）
导出 → tasks/prd-protable-refactor.md
```

**关键教训**：PRD 的「非目标」章节（明确不做什么）与「目标」同等重要——它防止范围蔓延。

### 例：从 PRD 到 task-planning 的桥接

PRD 中的每个用户故事直接映射为 task_plan 的执行步骤：

```
PRD US-001 (usePage composable) → task_plan 步骤 1
PRD US-002 (useFilter composable) → task_plan 步骤 2
PRD US-003 (useSort composable) → task_plan 步骤 3
PRD US-004 (useTable composable) → task_plan 步骤 4
```

验收标准从 PRD 用户故事直接提取，确保实现不偏离需求。

## 原则

- **优先从上下文中提取。** 用户很可能已经描述了内容。不要让他们重复。
- **匹配用户的语言。** 如果用户用中文书写，用中文回复。
- **绝不编造内容。** 规范化意味着澄清、结构化、重新措辞——而不是添加用户未提及的内容。
- **具体指出缺口。** 不要说「需要更多细节」，而要说「你提到了问题，但没有描述解决方案应该做什么」。
- **一次一个章节。** 专注于当前章节，但允许用户自由切换。
- **为实现者而写。** 文档将被开发人员或 AI 智能体阅读。要明确清晰，为需求编号，用具体示例而非抽象描述。
