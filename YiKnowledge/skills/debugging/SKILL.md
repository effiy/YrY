# 系统化调试

> 调试不是猜测——是科学方法在软件中的应用。每个 Bug 都是一次实验机会。

### 进入标准
- [ ] 观察到了错误、异常或非预期行为
- [ ] 问题可复现或至少可描述清楚
- [ ] 不是已知的设计行为（先查文档）

### 退出标准
- [ ] 根因已确认（不是猜测，是验证过的结论）
- [ ] 修复已应用且验证有效
- [ ] 值得记录的 Bug → Bug 文档已创建
- [ ] 下一步：→ code-review（审查修复）→ verification（验证修复）

## 核心方法论

```
观察（Observe） → 假设（Hypothesize） → 实验（Experiment） → 结论（Conclude）
      ↑                                                          │
      └──────────────────────────────────────────────────────────┘
                        循环直到根因确认
```

**为什么结构化调试比试错更有效？**

试错式调试（「改一下这里试试...不行，再改那里...」）有三个致命缺陷：
1. **可能引入新 Bug** — 不理解根因的修改是在代码中随机游走
2. **失去学习机会** — 不知道为什么修复有效，下次还会犯同样的错误
3. **浪费时间** — 没有假设引导的实验是盲目的

## 阶段 1：观察 —— 精确描述问题

### 收集信息

在动手修改任何代码之前，收集以下信息：

```markdown
## Bug 报告

**现象**：[用户看到的/发生的情况，用具体数据而非主观描述]
**预期行为**：[应该发生什么]
**实际行为**：[实际发生了什么，包含精确的错误消息]
**复现步骤**：
  1. [精确操作步骤 1]
  2. [精确操作步骤 2]
  3. [观察到的结果]
**环境信息**：
  - 项目：[yiai / yivad / yipet]
  - 分支/提交：[git 信息]
  - Node/Python 版本：
  - 浏览器（如适用）：
  - 操作系统：
**发生频率**：[每次必现 / 偶现 / 特定条件触发]
**最近变更**：[可能相关的近期代码修改]
```

### 不要跳过这一步

常见的陷阱是在问题描述不清晰时就开始「修复」。如果无法用一句话精确描述问题，你就还没准备好解决它。

**好的问题描述**：
> 「YiVad 项目列表翻到第 2 页后返回第 1 页，表头列名消失。每次必现。昨天 ProTable 组件重构了分页逻辑。」

**差的问题描述**：
> 「表格有问题，分页后显示不对。」

### 搜索已知问题

在写任何诊断代码之前，先检查：

1. `YiKnowledge/projects/<project>/bugs/` — 项目已知 Bug 记录
2. `git log --oneline -20` — 最近的提交是否引入
3. `git bisect` — 如果怀疑是回归，二分查找引入的提交

## 阶段 2：假设 —— 提出可验证的根因猜测

### 生成假设

基于观察，提出 1-3 个根因假设。每个假设必须：

- **具体** — 指向具体的代码位置或数据流
- **可验证** — 可以通过实验证实或证伪
- **排他** — 假设 A 和假设 B 不能同时为真

```markdown
## 假设 A：[一句话描述根因]

**置信度**：高 / 中 / 低
**依据**：[支撑这个假设的观察]
**验证方法**：[如何证实或证伪]
**如果为真**：[修复方案概要]
**如果为假**：[排除了什么，下一步假设]
```

### 常见根因模式

参考 `YiKnowledge/projects/` 中的 Bug 历史，以下是 YrY 项目中高频根因：

| 模式 | 典型表现 | 检查方向 |
|------|---------|---------|
| **参数名不匹配** | API 调用静默失败，无报错但数据不对 | 检查 RPC 参数名（filter/query、target_file/path） |
| **异步未 await** | 操作顺序错乱、数据竞态 | Python：检查 Motor 调用是否 await；JS：检查 Promise 处理 |
| **空值传播** | TypeError/Cannot read properties of undefined | 追溯空值来源，检查 API 响应和 store 初始化 |
| **状态残留** | 页面切换后旧数据仍然显示 | 检查组件/模块的清理逻辑（onUnmounted、reset） |
| **连接池耗尽** | 偶发超时、数据库操作变慢 | 检查连接是否正确释放、是否有连接泄漏 |
| **类型不匹配** | 前端显示异常但无 JS 报错 | 检查后端返回类型是否与前端类型定义一致 |
| **SSE 流断连** | 聊天回复中断、部分内容丢失 | 检查 SSE 重连逻辑、流结束信号处理 |

## 阶段 3：实验 —— 设计最小验证

### 实验设计原则

1. **最小化** — 每次实验只验证一个假设
2. **可逆** — 实验性修改应该容易撤销
3. **可测量** — 有明确的通过/失败标准
4. **安全** — 不在生产环境做实验

### 实验工具箱

| 工具 | 适用场景 | 用法 |
|------|---------|------|
| **精确日志** | 数据流追踪 | 在关键路径添加 `console.log`/`print`，标注变量值 |
| **断点/调试器** | 复杂逻辑 | VS Code/Chrome DevTools 断点逐步执行 |
| **单元测试** | 可隔离的逻辑 | 写一个最小复现测试，验证假设 |
| **git bisect** | 回归 Bug | `git bisect start; git bisect bad; git bisect good <commit>` |
| **最小复现** | 复杂系统 | 将问题从完整应用中剥离，创建最简复现脚本 |
| **网络面板** | API 调用问题 | Chrome DevTools Network 面板检查请求/响应 |
| **数据库直接查询** | 数据问题 | 用 mongo shell 直接查数据，排除 API 层干扰 |

### 实验记录

```markdown
## 实验 1：[验证假设 A]

**方法**：[具体操作]
**预期结果（如果假设 A 为真）**：[应该看到什么]
**实际结果**：[实际看到什么]
**结论**：假设 A 成立 / 不成立
**下一步**：[如果为真 → 修复；如果为假 → 提出假设 B]
```

## 阶段 4：结论 —— 修复并防止复发

### 修复原则

1. **修复根因而非症状** — 如果错误是因为空值，不要只加空值检查，要追溯为什么会产生空值
2. **最小修改** — 用最少的代码变更修复问题，不要顺手重构
3. **添加防护** — 在修复的同时添加测试，防止回归
4. **更新知识库** — 如果发现了新的 Bug 模式，记录到 `YiKnowledge/projects/<project>/bugs/`

### 修复确认清单

- [ ] 原始复现步骤不再触发 Bug
- [ ] 相关测试全部通过
- [ ] 类型检查通过（`vue-tsc --noEmit` / `tsc --noEmit` / `mypy`）
- [ ] 没有引入新的 lint 错误
- [ ] 如适用，添加了回归测试
- [ ] 如发现新模式，已创建 `YiKnowledge/projects/<project>/bugs/` Bug 文档

### Bug 文档模板

如果这是一个值得记录的 Bug，使用以下模板：

```markdown
---
title: "[简短描述]"
tags: [bug, module-name]
category: bugs
created: YYYY-MM-DD
updated: YYYY-MM-DD
source: internal
type: bug
status: stable
---

# Bug: [标题]

**严重程度**：critical / high / medium / low
**状态**：fixed / open / wont-fix
**发现日期**：YYYY-MM-DD
**修复日期**：YYYY-MM-DD

## 现象

[用户看到的问题]

## 根因

[导致问题的根本原因，不是症状]

## 修复

[修复方案和代码变更]

## 预防

[如何防止类似问题再次发生]

## 相关文件

- [修改的文件路径]
```

## YrY 实战速览

### 例：MongoDB 连接池耗尽排查

**现象**：YiVad 列表页同时加载时，部分统计卡片显示 "--"，日志 `ServerSelectionTimeoutError`。

**应用科学方法**：

```
观察  → 偶发超时，重启恢复，并发高时频率增加
假设  → MongoDB 连接池耗尽（而非网络问题或慢查询）
实验  → 检查 Motor client 创建方式：
        grep "AsyncIOMotorClient" → 发现每次查询都 new 一个新 client
结论  → 根因：未使用单例模式，每个请求创建新连接池
修复  → 改为模块级单例 + 连接池参数调优
        参考 YiKnowledge/projects/yiai/bugs/2026-09/数据/01-数据-MongoDB连接池耗尽.md
```

**关键教训**：连接池耗尽的表现是偶发超时→容易被当作「网络抖动」忽略→实际是资源泄漏。

### 例：静默失败排查

**现象**：前端显示全量数据，但请求明确传了 `status: "open"` 过滤条件。

**应用科学方法**：

```
观察  → HTTP 200, RPC code:0，但数据未过滤
假设  → 后端未使用过滤参数（参数名不匹配）
实验  → 在后端 parameters.get("filter") 前打印 parameters.keys()
        → 输出：["cname", "query", "pageSize"]
        → filter_dict 始终为 {}（因为 key 是 "query" 不是 "filter"）
结论  → RPC 参数名错误：前端传 query，后端期望 filter
修复  → 前端改为 filter + 后端加参数白名单校验
```

## 原则

- **先理解，再修改。** 不理解根因的修复 = 在黑暗中修表。
- **一次一个变量。** 每次实验只改变一个因素，否则无法确定哪个因素起了作用。
- **记录一切。** 失败的实验和成功的实验同样有价值——前者排除了可能性。
- **最小复现。** 能在 10 行代码中复现的问题，不要在 10000 行代码中排查。
- **修根因，不修症状。** 加 null check 消除报错是修症状；追溯 null 为什么会产生才是修根因。
- **不要假设。** 「应该是这里的问题」不是实验结论——验证它。
