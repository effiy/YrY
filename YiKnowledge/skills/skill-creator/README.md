## 用于创建和改进技能的 AI 代理

### 1. 快速开始

你不需要学习新工具——只需与 Claude 对话。技能创建器引导你完成一个 4 步循环：

**步骤 1：描述你想要什么**

```
你：我想要一个将 CSV 文件转换为带图表的格式化 Excel 报告的技能
```

技能创建器会与你访谈：技能接收什么输入，它应该产生什么，何时触发，以及什么使输出好与坏。根据你的回答，它起草一个 `SKILL.md`。

**步骤 2：用真实提示测试**

技能创建器提出 2-3 个测试提示——用户实际会问的真实任务——并并行运行它们。每个提示运行两次：一次带新技能，一次不带。结果放入工作区目录。

**步骤 3：并排审查**

浏览器查看器打开，显示每个测试用例的技能输出与基线对比。你可以对每个留下反馈。基准标签页显示带技能与不带技能的通过率、时间和 Token 使用量。

**步骤 4：迭代直到满意**

根据你的反馈，技能创建器改进 `SKILL.md`，重新运行所有测试，并显示前后变化。重复直到满意。然后可选择优化描述以获得更好的触发准确率，并打包为 `.skill` 文件。

**改进现有技能**的工作方式相同——基线变为之前的版本：

```
你：我的 pdf-fill 技能总是把日期格式搞错。能修复吗？
```

技能创建器读取当前技能，提出修复方案，针对两个版本运行现有 eval 集，并显示修复是否有效。

---

### 2. 为什么采用这种方法？

**为什么要有技能和无技能对比测试？**
没有基线，你无法判断技能是否真正改善了输出，还是 Claude 本身就能做得很好。受控对比隔离了技能的贡献，并显示 Token/时间成本是否值得质量的提升。

**为什么同时进行定性和定量评估？**
断言捕获回归问题并衡量跨运行的一致性，但它们会遗漏语气、清晰度以及输出是否真正有用。人工并排审查能捕获数字无法衡量的东西。两者结合给出完整的图景。

**为什么用 eval 循环而不是一次性编辑？**
手动提示编辑会过度拟合——你调整直到一个示例工作，然后发现它在不同输入上失败。隐藏的回归很常见：更改一条指令会破坏另一个案例。每次迭代运行所有测试用例能捕获这两种问题。

**为什么有描述优化步骤？**
frontmatter 中的 description 是 Claude 用来决定是否调用技能的唯一信号。糟糕的描述会导致触发不足（需要时技能保持沉默）或过度触发（技能在不相关的请求上触发）。优化循环针对精心策划的应该触发和不应该触发的 eval 查询集来调整描述。

### 3. 示例场景

#### 从零开始创建技能

> **用户：** "我一直让 Claude 从我们的内部 schema DSL 生成 PostgreSQL 迁移文件。格式总是有点偏差。我们能把它变成一个技能吗？"

技能创建器与用户访谈 DSL 格式、预期的迁移输出、命名约定、边缘情况和触发短语。它起草一个 `SKILL.md`，编写 3 个测试提示（简单迁移、多表迁移、带回滚的迁移），并运行第一次迭代。用户审查输出，留下反馈，经过 2-3 次迭代后，技能可靠地生成正确的迁移。

#### 调试触发过于频繁的技能

> **用户：** "我的 code-review 技能在我只是问一般代码问题时一直触发。怎么修复？"

技能创建器运行描述优化步骤。它生成 20 个 eval 查询——10 个应该触发技能（例如"审查我的 PR 更改"）和 10 个不应该触发的近似匹配（例如"git status 做什么"）。用户审查 eval 集，然后优化循环自动调整描述。经过 5 次迭代，技能在真实的代码审查请求上触发，但在一般问题上保持沉默。

#### 添加捆绑脚本以减少重复工作

> **用户：** "每次我的技能运行时，代理都从零开始写一个 `validate_output.py`。太浪费了。"

技能创建器读取测试转录记录，注意到所有 3 个测试用例中都独立创建了相同的辅助脚本，并建议将其打包到 `scripts/validate_output.py` 中。技能更新为直接引用该脚本，下一次迭代显示更低的 Token 使用量和更快的执行速度，且质量没有损失。

#### 盲法对比：我的重写真的更好吗？

> **用户：** "我重写了一半的 data-analysis 技能，但我不确定新版本是否真的更好。"

技能创建器运行盲法对比：一个独立代理在不知道哪个是哪个的情况下评判两个版本的输出。它评估正确性、完整性和结构，然后宣布获胜者。事后分析师阅读两个技能和转录记录，解释获胜者*为什么*获胜，并生成具体的改进建议。

### 4. 架构

技能创建器使用基于工作区的组织方式：

```
skill-creator/
├── SKILL.md              # 技能本身
├── agents/               # 子代理指令（grader、comparator、analyzer）
├── scripts/              # 汇总、打包、描述优化
├── eval-viewer/          # 基于浏览器的审查界面
└── references/           # evals、grading、benchmarks 的 JSON schema
```

每个正在开发的技能获得自己的工作区目录，包含迭代结果：

```
my-skill-workspace/
├── iteration-1/
│   ├── eval-simple-migration/
│   │   ├── with_skill/outputs/
│   │   ├── without_skill/outputs/
│   │   ├── grading.json
│   │   └── timing.json
│   ├── eval-multi-table/
│   │   └── ...
│   └── benchmark.json
├── iteration-2/
│   └── ...
└── feedback.json
```

这使得每个技能的 eval 历史、基准数据和审查反馈保持独立且自包含。
