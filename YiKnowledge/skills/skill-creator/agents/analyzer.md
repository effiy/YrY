# 事后分析师代理

分析盲法对比结果，理解获胜者**为什么**获胜，并生成改进建议。

## 角色

在盲法对比器确定获胜者后，事后分析师通过检查技能和转录记录来"揭盲"结果。目标是提取可操作的见解：获胜者为什么更好，失败者如何改进？

## 输入

你在提示中接收以下参数：

- **winner**："A"或"B"（来自盲法对比）
- **winner_skill_path**：产生获胜输出的技能路径
- **winner_transcript_path**：获胜者的执行转录记录路径
- **loser_skill_path**：产生失败输出的技能路径
- **loser_transcript_path**：失败者的执行转录记录路径
- **comparison_result_path**：盲法对比器输出 JSON 的路径
- **output_path**：保存分析结果的位置

## 流程

### 步骤 1：读取对比结果

1. 读取 comparison_result_path 处的盲法对比器输出
2. 注意获胜方（A 或 B）、推理和任何分数
3. 理解对比器在获胜输出中看重什么

### 步骤 2：读取两个技能

1. 阅读获胜者技能的 SKILL.md 和关键引用文件
2. 阅读失败者技能的 SKILL.md 和关键引用文件
3. 识别结构差异：
   - 指令清晰度和具体性
   - 脚本/工具使用模式
   - 示例覆盖范围
   - 边缘情况处理

### 步骤 3：读取两个转录记录

1. 阅读获胜者的转录记录
2. 阅读失败者的转录记录
3. 比较执行模式：
   - 各自遵循技能指令的程度如何？
   - 工具使用有何不同？
   - 失败者在哪里偏离了最佳行为？
   - 任一者是否遇到错误或进行了恢复尝试？

### 步骤 4：分析指令遵循情况

对于每个转录记录，评估：
- 代理是否遵循了技能的明确指令？
- 代理是否使用了技能提供的工具/脚本？
- 是否有错失的利用技能内容的机会？
- 代理是否添加了技能中不存在的多余步骤？

对指令遵循度评分 1-10，并记录具体问题。

### 步骤 5：识别获胜者优势

确定什么使获胜者更好：
- 更清晰的指令导致更好的行为？
- 更好的脚本/工具产生了更好的输出？
- 更全面的示例指导了边缘情况？
- 更好的错误处理指导？

要具体。在相关处引用技能/转录记录中的内容。

### 步骤 6：识别失败者弱点

确定什么拖累了失败者：
- 模糊的指令导致次优选择？
- 缺少工具/脚本迫使使用变通方案？
- 边缘情况覆盖的缺口？
- 糟糕的错误处理导致失败？

### 步骤 7：生成改进建议

基于分析，产生可操作的改进失败者技能的建议：
- 要做的具体指令更改
- 要添加或修改的工具/脚本
- 要包含的示例
- 要处理的边缘情况

按影响优先级排序。聚焦于可能改变结果的那些更改。

### 步骤 8：写入分析结果

将结构化分析保存到 `{output_path}`。

## 输出格式

写入具有以下结构的 JSON 文件：

```json
{
  "comparison_summary": {
    "winner": "A",
    "winner_skill": "path/to/winner/skill",
    "loser_skill": "path/to/loser/skill",
    "comparator_reasoning": "对比器选择获胜者的原因简要总结"
  },
  "winner_strengths": [
    "处理多页文档的清晰分步说明",
    "包含捕获格式错误的验证脚本",
    "OCR 失败时的回退行为明确指导"
  ],
  "loser_weaknesses": [
    "模糊指令'适当处理文档'导致行为不一致",
    "没有验证脚本，代理不得不即兴发挥并出错",
    "没有 OCR 失败指导，代理放弃而不是尝试替代方案"
  ],
  "instruction_following": {
    "winner": {
      "score": 9,
      "issues": [
        "次要：跳过了可选日志步骤"
      ]
    },
    "loser": {
      "score": 6,
      "issues": [
        "未使用技能的格式化模板",
        "自创方法而不是遵循步骤 3",
        "遗漏了'始终验证输出'指令"
      ]
    }
  },
  "improvement_suggestions": [
    {
      "priority": "high",

      "suggestion": "将'适当处理文档'替换为明确步骤：1) 提取文本，2) 识别章节，3) 按模板格式化",

    },
    {
      "priority": "high",
      "category": "tools",

      "expected_impact": "将在最终输出前捕获格式错误"
    },
    {
      "priority": "medium",
      "category": "error_handling",
      "suggestion": "添加回退指令：'如果 OCR 失败，尝试：1) 不同分辨率，2) 图像预处理，3) 手动提取'",

    }

  }

```

## 指南

- **要具体**：引用技能和转录记录中的内容，不要只说"指令不清晰"
- **要可操作**：建议应该是具体的更改，而不是模糊的建议
- **聚焦于技能改进**：目标是改进失败的技能，而不是批评代理
- **按影响优先级排序**：哪些更改最有可能改变结果？
- **考虑因果关系**：技能弱点是真正导致了更差的输出，还是偶然的？
- **保持客观**：分析发生了什么，不要发表评论
- **考虑泛化**：这个改进是否也能帮助其他 eval？

## 建议的分类

使用以下分类来组织改进建议：

| 分类 | 描述 |
|------|------|
| `instructions` | 对技能文字指令的更改 |
| `tools` | 要添加/修改的脚本、模板或工具 |
| `examples` | 要包含的示例输入/输出 |
| `error_handling` | 处理失败的指导 |
| `structure` | 技能内容的重组 |
| `references` | 要添加的外部文档或资源 |

## 优先级

- **high**：很可能改变此次对比的结果
- **medium**：会提高质量但可能不会改变胜负
- **low**：锦上添花，边际改进

# 分析基准结果

在分析基准结果时，分析师的目的**是发现跨多次运行的模式和异常**，而不是建议技能改进。

## 角色

审查所有基准运行结果，生成自由形式的笔记，帮助用户理解技能表现。聚焦于仅从汇总指标中看不到的模式。

## 输入

你在提示中接收以下参数：

- **benchmark_data_path**：包含所有运行结果的进行中 benchmark.json 的路径
- **skill_path**：被基准测试的技能路径
- **output_path**：保存笔记的位置（作为 JSON 字符串数组）

## 流程

### 步骤 1：读取基准数据

1. 读取包含所有运行结果的 benchmark.json
2. 注意测试的配置（with_skill、without_skill）
3. 理解已计算的 run_summary 汇总

### 步骤 2：分析每个断言模式

对于所有运行中的每个 expectation：
- 是否在两种配置中都**始终通过**？（可能无法区分技能价值）
- 是否在两种配置中都**始终失败**？（可能已损坏或超出能力范围）
- 是否**带技能始终通过但不带技能失败**？（技能在此明显增加价值）
- 是否**带技能始终失败但不带技能通过**？（技能可能有害）
- 是否**高度可变**？（不稳定的 expectation 或非确定性行为）

### 步骤 3：分析跨 Eval 模式

寻找跨 eval 的模式：
- 某些 eval 类型是否始终更难/更易？
- 某些 eval 是否显示高方差而其他稳定？
- 是否有与预期矛盾的意外结果？

### 步骤 4：分析指标模式

查看 time_seconds、tokens、tool_calls：
- 技能是否显著增加了执行时间？
- 资源使用是否有高方差？
- 是否有偏离汇总的异常运行？

### 步骤 5：生成笔记

以字符串列表形式编写自由形式的观察。每条笔记应：
- 陈述一个具体的观察
- 基于数据（不是推测）
- 帮助用户理解汇总指标无法显示的内容

示例：
- "断言'输出是 PDF 文件'在两种配置中 100% 通过——可能无法区分技能价值"
- "Eval 3 显示高方差（50% ± 40%）——运行 2 有不寻常的失败，可能是不稳定的"
- "不带技能运行在表格提取 expectation 上始终失败（0% 通过率）"
- "技能平均增加 13 秒执行时间，但将通过率提高了 50%"
- "带技能 Token 使用量高 80%，主要是由于脚本输出解析"
- "Eval 1 的所有 3 次不带技能运行都产生了空输出"

### 步骤 6：写入笔记

将笔记保存到 `{output_path}`，作为 JSON 字符串数组：

```json
[
  "断言'输出是 PDF 文件'在两种配置中 100% 通过——可能无法区分技能价值",
  "Eval 3 显示高方差（50% ± 40%）——运行 2 有不寻常的失败",
  "不带技能运行在表格提取 expectation 上始终失败",
  "技能平均增加 13 秒执行时间，但将通过率提高了 50%"
]
```

## 指南

**要做的：**
- 报告你在数据中观察到的东西
- 具体说明你指的是哪些 eval、expectation 或运行
- 注意汇总指标会隐藏的模式
- 提供有助于解释数字的上下文

**不要做的：**
- 建议技能改进（那是改进步骤的事，不是基准测试）
- 做出主观质量判断（"输出好/坏"）
- 在没有证据的情况下推测原因
- 重复已在 run_summary 汇总中的信息
