# 请求代码审查

> **早审查，常审查。** 审查不是在全部完成后做一次——而是在每个关键节点都做。小审查发现的问题修复成本远低于大审查。

## Review 三角

代码审查是一个完整闭环，三个技能各司其职：

```
requesting-code-review  →  code-review  →  receiving-code-review
    (请求审查)              (执行审查)         (处理反馈)
```

- **requesting** — 准备上下文、确定范围、提交请求（你在这里）
- **code-review** — 六维审查、分级问题、生成报告
- **receiving** — 接收反馈、验证再实现、技术性反驳

## 何时请求审查

### 必须请求

| 场景 | 时机 | 原因 |
|------|------|------|
| 独立步骤完成后 | task-planning 每个步骤结束时 | 小审查 → 修复成本低 |
| 主要功能完成后 | 跨步骤的完整功能实现后 | 检查跨步骤的集成问题 |
| 合并到 main 前 | 完成前验证通过后 | 最后的安全网 |

### 建议请求

| 场景 | 时机 | 原因 |
|------|------|------|
| 遇到困难时 | 卡住超过 30 分钟 | 新鲜视角往往能找到盲点 |
| 重构前 | 准备大规模改动时 | 建立基线，确认出发点是正确的 |
| 复杂 Bug 修复后 | debugging 完成后 | 验证修复没有引入新问题 |

## 请求流程

### 1. 确定审查范围

```bash
# 单步骤审查
git diff HEAD~1

# 功能审查（多个提交）
BASE=$(git merge-base origin/main HEAD)
git diff $BASE...HEAD

# 完整分支审查
git diff main...HEAD
```

**选择合适的范围**：
- 单步骤 → 1-3 个文件的 diff
- 功能 → 相关步骤的所有文件
- 分支 → 所有变更

### 2. 准备审查上下文

审查者需要的不只是代码——需要**理解意图**。准备：

```markdown
## 审查请求

**变更摘要**：[一句话描述做了什么]
**关联文档**：
  - PRD: [路径或链接]
  - task_plan: [任务计划路径]
**测试状态**：[测试通过数/总数]
**类型检查**：[0 errors / N errors]
**自审备注**：[自己已经发现的已知问题或关注点]
```

**给审查者的上下文，不是你的会话历史。** 审查者不需要知道你怎么找到解决方案的——只需要知道：要达成什么、改了什么、怎么验证。

### 3. 提交审查

#### 方式 A：同会话内审查（推荐）

在 Claude Code 中直接触发 code-review 技能：

```
审查范围：当前步骤的 git diff
上下文：task_plan 中的步骤描述和验收标准
```

#### 方式 B：PR 审查

```
1. 推送分支到远端
2. 创建 PR（用 finishing 技能的 PR 模板）
3. 在 PR 描述中标注：需要关注的区域、已知风险、测试状态
```

### 4. 处理反馈

审查完成后，按严重级别处理：

| 级别 | 行动 | 时机 |
|------|------|------|
| P0 🔴 | 必须修复 | 立即 |
| P1 🟠 | 应该修复 | 继续下一步之前 |
| P2 🟡 | 建议修复 | 可在后续迭代处理 |
| P3 🟢 | 自行决定 | 开发者判断 |

处理反馈时使用 receiving-code-review 技能——验证再实现，不盲目同意。

## 常见借口与真相

| 借口 | 真相 |
|------|------|
| 「我自己看一遍 diff 就行了」 | 你看 diff 用的是同一个上下文——你已经在代码里沉浸太久，看不出自己的盲点 |
| 「改动很小，不需要审查」 | 「改动很小」的 Bug 数量远超「改动很大」的 Bug。一行拼写错误可能让整个页面白屏 |
| 「等全部做完再审吧」 | 全部做完后的审查 = 返回去改第一步的成本 × 10。早审早修 |
| 「赶时间，跳过审查」 | 跳过的审查时间以 10 倍的形式在调试中补回来 |

## 原则

- **小审查，常审查。** 一次审查 ≤500 行变更。超过就拆成多次。
- **给上下文，不给历史。** 告诉审查者意图和约束，不要让他们从 diff 里猜。
- **审查是学习，不是考核。** 被发现问题是好事——它们在被合并前而不是合并后被发现。
- **不辩护，讨论。** 审查意见不是攻击，回应不是辩护。技术讨论找到最优解。
