# 接收代码审查反馈

> **核心原则：验证再实现。质疑再澄清。技术正确优于社交舒适。**

代码审查反馈需要技术评估，不是情感表演。盲目同意所有意见和盲目拒绝一样危险。

## 响应模式

```
收到审查反馈 → 逐条处理：

1. 读全 — 完整读完所有意见，不跳读、不预判
2. 理解 — 用自己的话复述技术要求（不清楚就问）
3. 验证 — 对照代码库实际情况
4. 评估 — 在 THIS 代码库的上下文中，技术上正确吗？
5. 响应 — 技术性确认或有理据的反驳
6. 实现 — 逐条修改，每条改完验证
```

## 禁止的回应

这些是来自 superpowers 的明确禁令——Claude 倾向于过度同意用户：

**永远不说：**
- 「你说得对！」 — 表演性同意
- 「好主意！」「非常好的建议！」 — 情感表演
- 「让我现在来实现」 — 在验证之前不承诺实现
- 「完全正确」 — 你在讨好，不是在评估

**应该说：**
- 复述技术要求
- 问澄清性问题
- 用技术理由反驳（如果意见确实有问题）
- 直接开始改（行动胜于言语）

## 按来源处理

### 来自代码审查报告（code-review 技能产出）

审查报告中的问题已经过分级（P0-P3），信任度高：
- P0/P1 → 直接修复，确认每条修复后结果
- P2 → 逐条评估是否值得现在修复
- P3 → 自行决定，不争论风格偏好

```
处理 P0 问题：
  → 理解问题 → 确认影响 → 修复 → 验证修复 → 标记完成

处理 P1 问题：
  → 理解问题 → 如同意则修复 → 如有疑虑则讨论 → 记录决定
```

### 来自人工 Reviewer（PR/当面）

人工反馈可能不完整或缺少上下文：
- 信任但要确认范围
- 不需表演性同意
- 技术性确认或直接行动

```
你的同事：这里应该用 useMemo 优化一下

❌ 错误：你说得对，让我加上 useMemo
✅ 正确：这个计算在什么场景下会成为性能瓶颈？
        当前渲染耗时 <1ms，加 memo 的实际收益是什么？
        [如果确实需要] → 加上并加入性能测试
        [如果不必要] → 解释当前场景下不需要的原因
```

## 模糊反馈的处理

```
如果任何一条意见不清楚：
  停下来 — 不要先实现清楚的部分
  一次性问清楚所有不清楚的项

原因：意见之间可能有关联。部分理解 = 错误实现。
```

**示例：**

```
Reviewer：「修复 1-6 项」

你理解了 1, 2, 3, 6 项。4 和 5 不清楚。

❌ 错误：先实现 1,2,3,6，然后再问 4,5
✅ 正确：「我理解了 1,2,3,6。需要澄清 4 和 5 的具体要求再继续。」
```

## 技术性反驳

当审查意见在技术上不正确或不适用时，有理据地反驳——不要默默接受。

```
反驳模板：

「关于 [具体意见]：
  当前实现是因为 [具体原因]。
  建议的方案在 [具体情况] 下会有 [具体问题]。
  
  替代方案：[如果有更好的方案]。
  
  如果你同意，我保持当前实现。或者你更倾向于 [折中方案]？」
```

**什么情况下反驳**：
- 意见在技术上不适用于当前代码库
- 意见会破坏已有功能
- 意见不了解当前实现的完整上下文
- 意见要求不合理的变更（范围蔓延）

**什么情况下不反驳**：
- 纯风格偏好（与项目约定不冲突）
- 有明确安全/性能收益的优化
- 意见来自你信任的领域专家

## 与 YrY 项目的关联

收到审查反馈时，注意 YrY 项目的特有约束：

- **RPC 契约**：修改 YiAi 的参数处理 → 检查 YiVad/YiPet 调用方是否受影响
- **模块边界**：不要因为一条反馈打破模块边界（如让 YiPet 直接访问 MongoDB）
- **CLAUDE.md 规则**：修改是否违反了项目铁律（如 Options API、裸 fetch）
- **Type Check**：每次修改后运行类型检查（`vue-tsc --noEmit` / `tsc --noEmit`）

## 命令

| 命令 | 操作 |
|------|------|
| 「处理 review 意见」 | 逐条读入→验证→实现 |
| 「反驳第 N 条」 | 对有问题的意见提出技术性反驳 |
| 「澄清第 N 条」 | 向 reviewer 请求澄清 |
| 「跳过第 N 条」 | 记录跳过原因，继续下一条 |

## 原则

- **验证再实现。** 理解 → 验证 → 确认 → 实现。不跳过验证。
- **不表演性同意。** 「你说得对」不增加任何价值。行动或技术讨论才是回应。
- **技术正确优于社交舒适。** 错误的意见应该被有理据地反驳——这对项目更有利。
- **澄清优于猜测。** 模糊的意见问清楚再做，部分理解 = 错误实现。
- **逐条处理。** 一次一条，改完验证，避免多线并发互相干扰。
- **检查跨项目影响。** YrY 是单体仓库——改 YiAi 可能影响 YiVad 和 YiPet。
