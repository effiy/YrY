# Issues —— Issue 追踪管理

一个交互式 Issue 管理助手，根据用户意图自动选择操作模式。覆盖 Issue 全生命周期：创建、分类、排期、流转、评审、交付。

## 模式选择

分析用户意图，自动选择以下五种操作模式之一。**开始执行前，先说明当前选中的模式及其理由**，让用户确认后再继续。

---

### 创建模式

当用户想要创建新的 Issue 时触发。采用逐项引导策略，不要求用户一次性提供所有信息。

**引导顺序（按重要性排列）：**

1. **标题** —— 动词开头，简洁描述核心问题。
   - 正确示例："修复登录超时"、"添加批量删除功能"
   - 错误示例："登录问题"（太模糊）、"用户在登录页面输入凭证后等待较长时间最终被服务器断开连接需要修复"（太冗长）
2. **类型** —— bug / task / feature / improvement / requirement（默认 task）
3. **优先级** —— urgent / high / medium / low（默认 medium）
4. **描述** —— 背景、涉及模块、复现步骤（针对 bug）、预期效果
5. **可选补充** —— 负责人、截止日期、标签、验收标准、预估工时

**使用示例：**

```
用户：帮我创建一个 Bug

助手：[创建模式]
  好的，我来逐项引导你创建一个 Bug Issue。
  首先，请用一句话描述这个 Bug 的关键问题：
  （示例：「修复项目列表分页后列头丢失」）

用户：修复项目列表分页后列头丢失

助手：收到。下一步，这个 Bug 的优先级如何？
  1. urgent — 立即处理，阻塞其他工作
  2. high   — 当前迭代内必须完成
  3. medium — 按正常节奏处理（默认）
  4. low    — 有空闲时处理
```

**输出格式：** 将收集到的内容整理为 Issue 卡片：

```
## [🐛] 修复项目列表分页后列头丢失

| 字段 | 值 |
|------|-----|
| 类型 | bug |
| 优先级 | high |
| 状态 | backlog |
| 负责人 | @张三 |
| 截止日期 | 2026-09-15 |
| 标签 | frontend, pro-table |

### 描述
ProTable 组件在翻页后重新渲染时，列头配置丢失，导致表头显示空白。
涉及模块：YiVad 项目列表页、ProTable 组件。

复现步骤：
1. 进入项目列表页，确认列头正常显示
2. 点击第 2 页
3. 返回第 1 页，列头消失

### 验收标准
- [ ] 翻页后列头保持正常显示
- [ ] 切换每页条数后列头不丢失
- [ ] 添加单元测试覆盖分页场景
```

### 流转模式

当用户想要修改 Issue 状态时触发。核心状态机规则：

- **backlog → todo**：排期确认，必须明确迭代计划（哪个 Sprint、预期开始时间）
- **todo → in_progress**：开始执行，自动记录开始时间
- **in_progress → in_review**：提交评审/代码审查，附上 PR 链接或审查请求
- **in_review → done**：评审通过，验收完成
- **in_review → in_progress**：评审不通过，退回修改，附上驳回原因
- 任意非终态 → **cancelled**：需要明确取消原因

**终态规则**：`done` 和 `cancelled` 是终态，不可再流转。

**使用示例：**

```
用户：把 YR-1024 从 in_progress 改为 in_review

助手：[流转模式]
  确认状态变更：
  当前状态：in_progress → 目标状态：in_review
  Issue：YR-1024「添加批量删除功能」
  
  评审前检查清单：
  - [ ] 代码已提交并推送到远端
  - [ ] 已创建 PR 并关联本 Issue
  - [ ] 自测通过，无已知阻塞问题
  
  确认变更？（是/否，可补充评审说明）
```

**配置选项：**

| 配置项 | 默认值 | 说明 |
|---|---|---|
| 流转必填评审说明 | 开启 | in_progress → in_review 时必须填写评审说明 |
| 取消需二次确认 | 开启 | 流转到 cancelled 时弹出二次确认 |
| 自动记录时间戳 | 开启 | 状态变更时自动记录 `updated_at` |

### 筛选模式

当用户想要查看/搜索 Issue 时触发。支持多维度组合筛选。

**筛选维度：**

| 维度 | 可选值 | 示例用法 |
|------|------|----------|
| 状态 | `backlog`, `todo`, `in_progress`, `in_review`, `done`, `cancelled` | "正在进行的 Issue" |
| 优先级 | `urgent`, `high`, `medium`, `low` | "紧急和高优先级的任务" |
| 类型 | `bug`, `task`, `feature`, `improvement`, `requirement` | "所有 Bug" |
| 负责人 | `@<用户名>` | "@张三 的 Issue" |
| 标签 | 任意标签名 | "带 frontend 标签的 Issue" |
| 时间 | 本周截止、已逾期、最近 7 天创建 | "本周截止的任务" |

**快捷视角（预设筛选条件）：**

| 视角 | 预设条件 | 使用场景 |
|---|---|---|
| **我的 Issue** | `assignee = 当前用户 AND status NOT IN (done, cancelled)` | 每日开工查看自己的工作 |
| **高优先级** | `priority IN (urgent, high) AND status NOT IN (done, cancelled)` | Sprint 评审前确认关键项 |
| **本周截止** | `due_date <= 今天 + 7 天 AND status NOT IN (done, cancelled)` | 规划本周工作节奏 |
| **阻塞项** | `blocked_by IS NOT EMPTY AND status != cancelled` | 识别并解除依赖阻塞 |
| **已逾期** | `due_date < 今天 AND status NOT IN (done, cancelled)` | Sprint 回顾前清理逾期项 |
| **未分配** | `assignee IS NULL AND status IN (todo, in_progress)` | 每日站会分配遗漏项 |
| **长期停滞** | `updated_at < 14 天前 AND status = in_progress` | 识别僵尸任务 |

**使用示例：**

```
用户：帮我看看本周截止的高优先级 Bug

助手：[筛选模式]
  筛选条件：优先级(urgent + high) + 类型(bug) + 本周截止 + 未完成
  结果：共 3 个 Issue

  | Key | 标题 | 优先级 | 截止日期 | 负责人 |
  |-----|------|--------|----------|--------|
  | YR-1028 | 修复 SSE 流断连后状态残留 | urgent | 09-12 | @李四 |
  | YR-1040 | 修复 RAG 增量索引遗漏文件 | high | 09-14 | @王五 |
  | YR-1045 | 修复 YiPet Service Worker 唤醒失败 | high | 09-15 | — |

  ⚠️ YR-1045 未分配负责人，是否需要现在分配？
```

### 看板模式

当用户想要查看整体工作流时触发。按状态分列展示：

```
Backlog (5)  | Todo (8)  | In Progress (6)  | In Review (3)  | Done (12)
```

**每列展示信息：**
- Issue 标题（截断至 40 字）
- 负责人头像/用户名
- 优先级标记（红色 urgent、橙色 high、灰色 medium/low）
- 阻塞标记（⚠ 表示被阻塞）
- 逾期标记（🔴 表示已逾期）

**看板交互：**
- 点击 Issue 卡片 → 展开详情
- 拖拽 Issue → 触发流转模式（需确认）
- 点击列头数字 → 切换为该列的筛选视图

**使用示例：**

```
用户：看板

助手：[看板模式]

  ╔══════════════════════════════════════════════════════════════════╗
  ║  Backlog (5)  │  Todo (8)       │  In Progress (6) │ In Review (3) │ Done (12) ║
  ╠══════════════════════════════════════════════════════════════════╣
  ║               │                 │                   │               │           ║
  ║  🔴 支付超时   │  📊 数据导出    │  🔒 权限重构      │  📝 API 文档   │  ...      ║
  ║     urgent    │     high  @赵六  │     high  @张三   │     medium     │           ║
  ║               │                 │                   │               │           ║
  ║  ⚠ 批量删除   │  📱 移动适配    │  ⚠ 搜索优化      │  🧹 代码清理   │           ║
  ║     high      │     medium      │     high  @李四   │     low        │           ║
  ║               │                 │     逾期 3 天      │               │           ║
  ╚══════════════════════════════════════════════════════════════════╝

  ⚠ 警告项：
  - 「搜索优化」逾期 3 天，已在 In Progress 停留 10 天
  - In Progress 列堆积 6 项，超过建议上限（4 项）
```

**看板健康指标：**

| 指标 | 健康线 | 当前状态说明 |
|---|---|---|
| Backlog 膨胀率 | < 20 项 | 超过 20 项时建议做一次 Backlog 梳理会议 |
| In Progress 并发数 | <= 4 项 | 超过 4 项提示工作并行度过高 |
| In Review 停留时间 | <= 2 天 | 超过 2 天未处理的评审项高亮提醒 |
| Todo 无负责人 | 0 | 任何无负责人的待办项发出警告 |

### 诊断模式

当用户想要检查数据质量或工作流健康度时触发。自动扫描全量 Issue 并生成诊断报告。

**检查维度与健康线：**

| 指标 | 检查项 | 健康线 | 警告线 | 严重线 |
|------|--------|--------|--------|--------|
| 负责人分配率 | 活跃 Issue 中有 assignee 的比例 | >= 80% | 60-79% | < 60% |
| 截止日期设置率 | 活跃 Issue 中有 due_date 的比例 | >= 80% | 50-79% | < 50% |
| 标签使用率 | 有 labels 的 Issue 比例 | >= 60% | 30-59% | < 30% |
| 描述填写率 | description 非空的比例 | >= 90% | 70-89% | < 70% |
| 验收标准率 | acceptance_criteria 非空的比例 | >= 70% | 40-69% | < 40% |
| 预估工时率 | estimate_points 或 time_estimate 非空的比例 | >= 60% | 30-59% | < 30% |

**异常清单（自动生成）：**

| 异常类型 | 判定条件 | 建议操作 |
|---|---|---|
| 逾期未完成 | `due_date < 今天 AND status NOT IN (done, cancelled)` | 重新评估排期或拆分为更小的子任务 |
| 未分配 | `assignee IS NULL AND status IN (todo, in_progress)` | 在下次站会上明确负责人 |
| 长期停滞 | `status = in_progress AND updated_at < 14 天前` | 与负责人确认阻塞原因或决定是否搁置 |
| 阻塞未解除 | `blocked_by IS NOT EMPTY AND updated_at > 7 天前` | 联系阻塞源的负责人推进依赖解除 |
| 缺乏验收标准 | `acceptance_criteria IS NULL AND status IN (in_progress, in_review)` | 补充可验证的验收条件 |
| 评审积压 | `status = in_review AND updated_at > 3 天前` | 提醒评审人优先处理 |

## 核心概念

### Issue 类型

| 类型 | 说明 | 典型场景 | 标题动词示例 |
|------|------|----------|------------|
| `bug` | 缺陷 | 线上问题、功能异常、体验问题 | 修复、解决 |
| `task` | 任务 | 开发任务、运维操作、日常事务 | 完成、执行、处理 |
| `feature` | 功能 | 新功能开发、能力建设 | 添加、实现、支持 |
| `improvement` | 改进 | 性能优化、代码重构、流程优化 | 优化、重构、提升 |
| `requirement` | 需求 | 业务需求文档化、需求拆解 | 设计、规划、调研 |

### 优先级

| 优先级 | 响应要求 | 典型场景 | In Progress 数量上限 |
|--------|----------|----------|-------------------|
| `urgent` | 立即处理，阻塞其他工作 | 线上故障、安全漏洞、数据丢失 | 同时最多 1 个 |
| `high` | 当前迭代内必须完成 | 核心功能阻塞、客户承诺交付 | 同时最多 2 个 |
| `medium` | 按正常节奏处理 | 常规功能开发、技术改进 | 无限制 |
| `low` | 有空闲时处理 | 体验优化、文档完善 | 无限制 |

### 状态流转详情

```
           ┌─────────────────────────────────────────┐
           │                                         │
           ▼                                         │
backlog ──→ todo ──→ in_progress ──→ in_review ──→ done
  │          │           │               │            │
  │          │           │               │            │
  └──────────┴───────────┴───────────────┴─────→ cancelled
```

**状态说明：**

| 状态 | 含义 | 准入条件 | 退出条件 |
|------|------|----------|----------|
| `backlog` | 待办池，尚未排期 | 创建时默认状态 | 明确迭代计划后转入 todo |
| `todo` | 已排期，待开始 | 有明确迭代和优先级 | 开发者认领后转入 in_progress |
| `in_progress` | 进行中 | 有负责人、有预估工时 | 代码提交并创建 PR 后转入 in_review |
| `in_review` | 评审中 | 有 PR 链接、有验收标准 | 评审通过 → done；驳回 → in_progress |
| `done` | 已完成（终态） | 评审通过、验收标准全部满足 | 不可流转 |
| `cancelled` | 已取消（终态） | 有取消原因 | 不可流转 |

### 依赖关系

| 关系 | 含义 | 使用建议 |
|------|------|----------|
| `blocked_by` | 被其他 Issue 阻塞，依赖完成后才能开始 | 建立后通知阻塞源的负责人 |
| `blocks` | 阻塞其他 Issue | 完成后自动通知被阻塞的 Issue 负责人 |
| `related` | 一般关联，无强制依赖 | 用于追踪相关但无阻塞关系的 Issue |
| `parent_key` | 父 Issue，用于大需求拆分子任务 | 父 Issue 进度 = 子 Issue 完成度的加权平均 |

## 与 PRD 的关系

```
PRD（产品规格）──→ Issue（可执行工作项）
```

- PRD 中的需求 → 拆解为 `requirement` 类型 Issue（可选父子拆分）
- PRD 中的功能点 → 拆解为 `feature` 或 `task` 类型 Issue
- 测试/线上反馈 → 创建 `bug` 类型 Issue
- 技术优化需求 → 创建 `improvement` 类型 Issue

**转换流程：**
1. 需求拆解：PRD → 多个 requirement Issue（如有）
2. 功能指派：requirement → 多个 feature/task Issue（父子关系）
3. 反馈闭环：bug → 关联到原始 requirement Issue

## 常见问题与故障排查

### 创建模式

| 问题 | 原因 | 解决方法 |
|------|------|----------|
| Issue 创建后找不到 | 创建时未指定负责人，默认不在「我的 Issue」视图中 | 使用筛选模式按标题搜索，或让管理员在 backlog 中查找 |
| 标题格式被拒绝 | 标题以标点开头或包含特殊字符 | 以动词开头，纯中文/英文/数字，长度 5-100 字符 |
| 优先级默认 medium 不符合预期 | 未明确指定优先级 | 创建时主动说明优先级，或创建后通过流转模式修改 |

### 流转模式

| 问题 | 原因 | 解决方法 |
|------|------|----------|
| 无法从 done 转回 in_progress | done 是终态，不可流转 | 创建新 Issue，在描述中引用原 Issue key |
| 评审退回后状态丢失 | in_review → in_progress 时未保留评审意见 | 退回时自动将评审意见追加到 Issue 评论中 |
| 取消操作的 Issue 仍在看板中显示 | 取消不等于删除，仍显示在各视图中 | 在筛选条件中排除 `cancelled` 状态 |

### 筛选模式

| 问题 | 原因 | 解决方法 |
|------|------|----------|
| 组合筛选结果为空 | 筛选条件过于严格，交集为空 | 逐步放宽条件，先用单一维度确认数据存在 |
| "本周截止"包含已完成的 Issue | 默认快捷视角未排除终态 | 使用自定义筛选增加 `status NOT IN (done, cancelled)` |

### 看板模式

| 问题 | 原因 | 解决方法 |
|------|------|----------|
| In Progress 列堆积过多 | 工作并行度过高 | 优先完成接近 done 的项，暂缓新开始的项 |
| Backlog 超过 50 项 | 长期未做 backlog 梳理 | 安排一次 Backlog Grooming 会议 |

### 诊断模式

| 问题 | 原因 | 解决方法 |
|------|------|----------|
| 验收标准率持续下降 | 新创建的 Issue 缺少验收标准 | 在创建模式中增加验收标准为必填引导项 |
| 预估工时率长期为 0 | 团队未养成预估习惯 | 在 todo → in_progress 流转时要求填写 estimate_points |
