# 技术选型决策

> **作为**CTO 和高管，**我想要**在技术选型时超越个人偏好和潮流驱动，做出能支撑业务 3-5 年的理性决策。
>
> **核心洞见**：选错技术栈的代价不是"重写 3 个月"——是 3 年内的每一次改动都多花 30% 的时间，每个新人上手多花 2 周，每次遇到边界情况都在和一个不合适的抽象搏斗。选对的标志不是"开发体验好"——是"3 年后你仍然觉得当初的选择是合理的"。

## 选型五维评估

| 维度 | 权重 | 评估问题 | 数据来源 |
|---|---|---|---|
| **业务适配** | 30% | 这个技术解决的核心问题与我们产品的核心需求匹配吗？ | 需求分析、原型验证 |
| **生态健康** | 25% | 社区活跃度、维护频率、issue 响应速度、文档质量 | GitHub Star/Issue/PR 趋势、Stack Overflow 问答数 |
| **团队匹配** | 20% | 团队现有技能匹配度？学习曲线多陡？招聘市场上该技能的供给？ | 团队自评、招聘数据 |
| **长期风险** | 15% | 项目被放弃的风险？许可证风险？供应商锁定的程度？ | 维护历史、组织背景、许可证类型 |
| **性能与规模** | 10% | 在可预见的规模下性能是否足够？架构是否支持扩展？ | 基准测试、案例研究 |

### 生态健康的量化信号

不要只看 Star 数——那是人气竞赛。看这些：

| 信号 | 健康 | 不健康 |
|---|---|---|
| Issue 关闭率 | 每月关闭 ≥ 80% 的新 Issue | 积累越来越多未解决的 Issue |
| PR 合并周期 | 非 trivial PR 在 1 周内合并 | PR 挂几个月没人管 |
| 维护者多样性 | ≥ 3 个来自不同组织的核心维护者 | 1 个人或 1 个公司维护一切 |
| 发布频率 | 每 1-3 个月有稳定发布 | 6 个月以上没有新版本 |
| 文档 | 有入门指南、API 文档、变更日志 | 只有自动生成的 API 文档 |

## 决策流程

### 步骤 1：定义"足够好"的标准

在开始评估之前，先定义这项技术选择的不可协商条件：

| 条件 | 示例（YrY 的 LLM 推理方案选择） |
|---|---|
| 必须满足 | 支持本地部署（数据不出域）、支持模型热切换、Python SDK |
| 应该满足 | 支持 GPU 推理、社区活跃 |
| 最好有 | 支持分布式推理、有可视化管理界面 |
| 不可接受 | 闭源且供应商锁定、推理速度低于 X ms/token |

### 步骤 2：候选方案筛选

| 筛选阶段 | 方法 |
|---|---|
| **初筛** | 用"必须满足"条件快速排除——不可协商的条件不满足就直接淘汰 |
| **详细评估** | 对剩余 2-3 个候选做五维评分 + PoC 验证 |
| **PoC 验证** | 花 1-3 天在最关键的 1-2 个场景上做原型——文档说"支持"不代表在你的场景中好用 |

### 步骤 3：记录决策 (ADR)

每个重大技术选型决策写一份架构决策记录：

```
# ADR: {标题}

## 背景
我们需要选择 {什么} 来解决 {什么问题}。

## 决策
我们选择 {X}。

## 考虑的替代方案
- {Y}：优点/缺点
- {Z}：优点/缺点

## 后果
### 正面
- {选择 X 带来的好处}

### 负面
- {选择 X 的代价和风险}

### 中性
- {需要注意的事项}
```

## 技术选型中高管的作用

CTO 做技术推荐，CEO/高管关注这些：

| 高管关注点 | 要问的问题 |
|---|---|
| **业务连续性** | 如果这个技术背后的组织出问题，我们的迁移成本是多少？需要多久？ |
| **人才可行性** | 我们能招聘到用这个技术的人吗？现有团队的转型成本是多少？ |
| **战略锁死** | 这个选择会在多大程度上限制我们未来的选择？（如：选了这个数据库，以后要换的代价） |
| **隐性成本** | 除了开发成本，运维、培训、工具链的长期成本是多少？ |
| **时机** | 这个技术在这个时间点是"成熟可靠"还是"过早在风口"？ |

## 核心产出

- 技术选型五维评估表
- PoC 验证结果
- ADR 文档

## 反模式

| 反模式 | 为何失败 | 正确做法 |
|---|---|---|
| 追逐新技术 | 选最热的新框架——但它的生态、稳定性、人才池都未成熟 | 选"无聊但可靠"的技术——让差异化在业务层而非技术栈层 |
| 个人偏好主导 | "我一直想用 Rust"——不是选型理由 | 用五维评估——业务适配的权重最高 |
| 只看不提风险 | 选型文档只讲优点 | ADR 的"后果-负面"章节强制列出来 |
| 选后不重评 | 3 年前的选择放在今天不一定对 | 每 18 个月重评关键技术选型 |
| 忽视许可证 | 用了 GPL/AGPL 的库——商业模式被许可证绑架 | 选型前确认许可证的兼容性 |
