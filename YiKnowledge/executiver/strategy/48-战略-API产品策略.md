# API 产品策略

> **作为**高管，**我想要**将 YiAi RPC 从内部工具升级为可对外开放的 API 产品，**以便**在适当的时机从"管道模式"扩展到具有网络效应的"平台模式"。
>
> **核心洞见**：API 不是技术输出——是产品。内部 API 和产品级 API 的差距，就像内部用的小脚本和公开发行的软件之间的差距。API 产品化的标志不是"能调通"，是"一个外部开发者在 15 分钟内不看源码就能完成第一次成功调用"。

## API 产品化的四个层次

| 层次 | 特征 | 用户 | 标志 |
|---|---|---|---|
| **L1：内部 API** | 为内部团队设计——文档可有可无、错误信息不友好、靠口碑传播 | 内部同事 | "你看看源码就知道怎么调了" |
| **L2：私有 Beta API** | 对少数信任的合作伙伴开放——有基本文档但需要人工支持 | 3-5 个信任的合作伙伴 | "有问题直接找我" |
| **L3：公开 Beta API** | 对注册开发者开放——自服务文档、基本错误处理、速率限制 | 注册开发者 | "看文档能独立完成首次调用" |
| **L4：产品级 API** | 成熟的商业产品——SLA、计费、多区域、开发者生态 | 付费客户 | "5 分钟从注册到第一次成功调用" |

**YrY 当前**：L1。YiAi RPC 是为 YiVad/YiPet 设计的高效内部协议——但离产品级 API 还有距离。

## API 产品化的六大要素

### 1. 开发者体验 (DX)

| 要素 | 标准 | YrY 当前状态 |
|---|---|---|
| **首次调用时间 (TTFC)** | < 15 分钟 | 未测量——但需要理解 RPC 信封协议 |
| **文档** | 交互式文档 + 每个端点有示例请求和响应 + 常见错误及解决方案 | 有基本 RPC 规范，无交互式文档 |
| **SDK** | 至少支持 2 种主流语言 | 无 |
| **错误信息** | 可操作的——不只是返回错误码，要告诉开发者怎么修正 | RPC 信封有 code/message——够用但不够友好 |
| **沙箱环境** | 不消耗配额的免费测试环境 | 无 |

### 2. API 设计

| 原则 | 说明 |
|---|---|
| **一致性 > 完美** | 所有端点遵循相同的命名、错误格式、分页方式——即使个别设计不够优雅 |
| **向后兼容** | 已有端点的响应结构不能改变——只能加字段，不能删或改 |
| **版本策略** | 通过 URL 路径 (v1/v2) 或 Header 做版本管理——不要在同一个端点里做不兼容改动 |
| **最小权限** | 每个 API Key 应有明确的权限范围——一个 Key 不应该能访问所有端点 |

### 3. 认证和安全

| 要素 | 说明 |
|---|---|
| **API Key 管理** | 开发者自服务生成、轮换、撤销 Key——不需要发邮件找管理员 |
| **速率限制** | 按 API Key 限制——返回 429 时在响应头中包含重试时间 |
| **日志和审计** | 开发者能查看自己 API 的调用日志 |

### 4. 监控和可靠性

| 要素 | 说明 |
|---|---|
| **SLA 承诺** | 可用性承诺（如 99.9%）——只在能做到时才承诺 |
| **状态页** | 公开的服务状态页——不隐瞒故障 |
| **变更日志** | 每次 API 变更都有公开的 changelog |
| **弃用策略** | 弃用一个端点的最低通知期（如 3 个月） |

### 5. 商业模型

| 模式 | 适合 | 不适合 |
|---|---|---|
| **免费层 + 按用量** | 需要吸引开发者试用 | 推理成本高的端点——免费层的用量上限必须硬 |
| **按调用次数** | 调用量可控、成本可预测 | 调用量波动极大 |
| **分级订阅** | 有明确的"个人→团队→企业"升级路径 | 只有一种用户类型 |
| **收入分成** | 开发者在你的平台上构建并卖给他们的用户 | 你的 API 是基础设施而非平台 |

### 6. 开发者关系

| 阶段 | 活动 |
|---|---|
| **早期 (L2-L3)** | 创始人亲自做开发者支持——前 20 个外部开发者就是你的设计伙伴 |
| **成长期 (L3-L4)** | 社区论坛、技术博客、示例项目、定期 Office Hours |
| **成熟期 (L4+)** | 开发者大会、认证计划、Solution Architect 团队 |

## YiAi RPC 从 L1 → L2 的路径

要在当前阶段启动 API 产品化，不需要也不可能同时做完以上所有。分三步走：

### 第一步：让内部 API 值得被外部看到（2-4 周）

- [ ] 补充 RPC 信封的交互式文档（OpenAPI/Swagger 格式）
- [ ] 每个端点：请求示例 + 响应示例 + 错误示例
- [ ] 标准化错误响应——让 code/message 包含可操作的信息
- [ ] 创建一个沙箱端点——不消耗真实 AI 推理资源

### 第二步：找 3-5 个设计伙伴（1-2 个月）

- [ ] 识别 3-5 个信任的开发团队或个人——给他们免费访问
- [ ] 观察他们第一次调用的摩擦点——记录每个"卡住"的时刻
- [ ] 根据反馈迭代文档和错误信息
- [ ] 不要在这个阶段做计费——学习比收入重要

### 第三步：决定是否继续投入产品化

评审点（第二步结束）：

| 信号 | 继续 | 暂停 |
|---|---|---|
| 设计伙伴的留存 | ≥ 3 个仍在活跃使用 | < 2 个 |
| 开发者独立上手率 | ≥ 50% 不看源码能完成首次调用 | < 50% |
| API 调用的商业价值信号 | 至少 1 个伙伴表示愿意付费 | 0 个 |
| 对核心产品的拖累 | API 产品化没有挤占核心研发 > 20% | 挤占 > 20% |

## YrY API 的独特定位

YiAi RPC 不是通用 AI API（OpenAI/Claude API 已经占满了这个定位）。YiAi API 的独特价值是：

| 维度 | 通用 AI API | YiAi API 的差异化 |
|---|---|---|
| 提供什么 | 模型推理 | 模型推理 + 知识检索 (RAG) |
| 上下文 | 无上下文——每次调用独立 | 有 YiKnowledge 的行业/竞品知识作为上下文 |
| 部署方式 | 云端 API | 云端 + 自托管（Ollama） |
| 目标用户 | 需要 AI 能力的开发者 | 需要"有业务上下文的 AI"的开发者 |

## 核心产出

- API 产品化路线图（L1→L2→L3→L4）
- 开发者体验测试报告（前 5 个外部开发者的首次调用记录）
- API 商业模型选择及理由
- Go/No-Go 评审决策记录

## 反模式

| 反模式 | 为何失败 | 正确做法 |
|---|---|---|
| 内部 API 直接对外 | 开发体验差——错误信息看不懂、没文档、没沙箱 | 先做 L1→L2 的产品化改造 |
| 完美主义延迟 | 想等 API 完美再发布——永远在等 | L2 就是用来不完美的——找设计伙伴帮你迭代 |
| 过早计费 | 还没验证价值就开始收钱——阻挡了早期用户的进入 | L2 阶段免费——收入不重要，学习最重要 |
| 忽视开发者体验 | 只关注后端性能不关注文档和 SDK——"功能强但不会用" | TTFC（首次调用时间）是最重要的 KPI |
| 无版本策略 | API 改了直接部署——下游开发者的代码全挂 | 版本化——不兼容改变必须发新版本 |
