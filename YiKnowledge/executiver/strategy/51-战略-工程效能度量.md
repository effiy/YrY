# 工程效能度量

> **作为**CTO 和高管，**我想要**用真正反映团队效能的度量体系替代虚假的生产力度量，**以便**不因追逐指标而伤害真正的产出，也不因缺乏度量而无视改进机会。
>
> **核心洞见**：度量工程效能最危险的不是度量的不准确——是被度量的行为会变形。如果你用代码行数衡量产出，你会得到很多行代码——但产品不一定更好。如果你用故事点衡量速度，你会得到膨胀的故事点——但交付不一定更快。好的度量体系追踪**结果**而非**产出**，追踪**趋势**而非**绝对值**。

## SPACE 框架

业界最全面的工程效能度量框架：

| 维度 | 定义 | 指标示例 | 数据来源 |
|---|---|---|---|
| **Satisfaction（满意度）** | 开发者对工作环境、工具和流程的主观感受 | 开发者 NPS、工具满意度调查、离职意向 | 匿名调研 |
| **Performance（绩效）** | 交付结果的质量和影响 | 功能采用率、用户满意度、故障数 | 产品分析、监控 |
| **Activity（活动量）** | 开发活动的基本计数 | 提交数、PR 数、代码评审数 | Git 日志 |
| **Communication（沟通）** | 团队内和团队间的信息流动 | 文档更新频率、知识分享次数、PR 评审参与度 | 文档系统、Git |
| **Efficiency（效率）** | 在活动和交付中消除浪费的能力 | 从 PR 创建到合并的中位时间、CI 通过率、部署频率 | CI/CD、Git |

**关键**：只用单一维度 = 糟糕的管理。只看 Activity（提交数）会催生无意义的提交。只看 Satisfaction（满意度）可能忽视交付问题。

## DORA + SPACE 整合

| 维度 | DORA 指标（交付） | SPACE 补充（团队健康） |
|---|---|---|
| 交付速度 | 部署频率、变更前置时间 | 从 PR 到合并的时间、未合并 PR 的存留时间 |
| 交付质量 | 变更失败率、故障恢复时间 | 用户感知的故障数、测试覆盖率趋势 |
| 团队健康 | — | 开发者满意度、倦怠信号、知识文档化率 |
| 效率 | — | 每周深度工作时间占比、会议时间占比 |

### 团队健康维度（月度匿名调研）

| 指标 | 问题 | 健康阈值 |
|---|---|---|
| 开发者 NPS | "你会推荐团队给朋友吗？" (0-10) | ≥ 30 |
| 工具满意度 | "日常使用的工具让你更高效还是更沮丧？" (1-5) | ≥ 4.0 |
| 知识可获性 | "你需要的信息能在 5 分钟内找到吗？" | ≥ 80% 回答"是" |
| 心理安全 | "在团队中表达不同意见是安全的吗？" (1-5) | ≥ 4.0 |

**原则**：月度——过于频繁会被厌烦，过于稀疏发现不了趋势。

## 反度量：不要追踪的指标

| 指标 | 为什么有害 | 替代 |
|---|---|---|
| 代码行数 | 催生冗余代码——"多写"不等于"多交付" | 功能采用率、用户价值指标 |
| 故事点速度 | 点会膨胀——团队学会"估大一点"来让曲线好看 | 实际的交付周期时间 |
| 提交数 | 催生无意义的微提交 | 合并的 PR 数（有意义的工作单元） |
| Bug 修复数 | 激励写 Bug 后修 Bug | 逃逸到生产的 Bug 数——重点是预防 |
| 加班时长 | 激励无效加班——"看起来很努力" | 可持续交付节奏、倦怠信号 |

## YrY 的工程效能基线

当前最优先的三个度量：

1. **YiKnowledge 更新频率**：每月新增/更新的知识文件数 → 衡量知识库建设的速度
2. **RAG 检索质量**：检索准确率和用户满意度 → 衡量核心差异化的质量
3. **三项目交付周期**：从需求到上线的中位时间 → 衡量整体交付效能

## 核心产出

- 工程效能仪表盘（交付 + 质量 + 健康）
- 月度匿名调研
- 季度效能趋势分析和改进计划

## 反模式

| 反模式 | 为何失败 | 正确做法 |
|---|---|---|
| 度量当考核 | 故事点速度决定奖金 → 速度立即"提升"（但质量下降） | 度量用于团队自我改进——不用于个人考核 |
| 只看交付不看质量 | 速度快了但故障率也在涨 | 交付 + 质量指标必须同屏展示 |
| 团队之间横向对比 | "A 团队速度 50，B 团队 30"——不同上下文不可比 | 只对比团队自己随时间的变化 |
| 指标太多 | 20 个指标的仪表盘——没人看 | 核心指标 ≤ 10 个——这 10 个能驱动决策 |
| 设了指标但无行动 | 仪表盘很漂亮但什么都没改变 | 每个指标的负责人 + 每季度至少 1 个基于数据的改进行动 |
