# Now / Next / Later 路线图

> **作为**产品负责人，**我想要**将工作组织到三个基于成果的时间视野中，**以便**利益相关方对齐优先级而不被困在必然变化的日期上。
>
> **核心洞见**：传统的基于时间线的路线图给了一个虚假的精确感——在快速变化的环境中，超过一个季度的日期基本都是错的。Now/Next/Later 承认不确定性，承诺成果而非交付日期。

## 定义

Now / Next / Later (NNL) 是一种路线图格式，用三个时间视野替代固定日期时间线：

```
┌──────────────────────────────────────────────────────────┐
│  NOW (当前)              │  NEXT (下一个)      │  LATER (以后) │
│  (本季度)                │  (未来 1–2 季度)     │  (未来)        │
│                         │                    │               │
│  • 已承诺的成果          │  • 已规划的成果      │  • 想法        │
│  • 团队正在积极投入      │  • 发现阶段进行中    │  • 赌注        │
│  • 明确的成功标准        │  • 范围正在清晰      │  • 选项        │
│                         │                    │  • 尚未确定范围 │
│                         │                    │               │
│  高置信度               │  中置信度           │  低置信度     │
└──────────────────────────────────────────────────────────┘
```

与时间线路线图的关键区别：**你承诺的是成果，不是日期**。优先级清晰，但"Next"和"Later"项的确切时机是有意灵活的。

## 适用场景

- 需要向利益相关方沟通优先级但不想锚定日期
- 环境变化频繁（日期在几周内就会出错）
- 想将会话从"X 什么时候交付？"转变为"我们在驱动什么成果？"
- 多团队围绕共享优先级对齐
- 将战略（[产品战略框架](./08-战略-产品战略框架.md)）转化为执行

## 分步操作

### 步骤 1：定义成果而非功能

成果是用户行为或业务指标的可衡量变化。功能是解决方案。

| 功能（坏的路线图项） | 成果（好的路线图项） |
|---|---|
| "构建暗色模式" | "通过减少夜间使用时眼部疲劳来增加移动端参与度" |
| "添加 CSV 导出" | "使用户无需请求自定义报告即可自行分析" |
| "集成 Slack" | "将通知到达时间从 30 分钟降至 < 1 分钟" |

**成果的衡量标准**：
- 有明确的数值变化（从 X 到 Y）
- 可以归因（我们能追踪这个变化是否由我们的行动产生）
- 对业务或用户有意义（不是中间指标）

### 步骤 2：从战略获取输入

路线图从以下来源获取输入：
- [产品战略框架](./08-战略-产品战略框架.md) — 战略选择 → 路线图成果
- [价值主张画布](./11-战略-价值主张画布.md) — 发现的客户痛点 → 功能机会
- [商业模式画布](./02-战略-商业模式画布.md) — 商业模式缺口 → 项目

每条路线图项必须能追溯到某份战略文档或经过验证的客户需求。

### 步骤 3：分配到 Now / Next / Later

| 视野 | 标准 | 容量指引 | 项数上限 |
|---|---|---|---|
| **Now** | 正在积极投入；成功标准已定义；团队已指定 | 容量 60–70% | 3–5 个成果/团队 |
| **Next** | 发现阶段进行中；范围正在形成；可能在 1–2 季度内启动 | 容量 20–30%（仅发现） | 5–8 个成果 |
| **Later** | 已验证的想法；尚未确定范围；无承诺时间线 | 0–10%（仅轻量研究） | 不限 |

保留 10–20% 的容量不分配，用于意外工作和缓冲。

### 步骤 4：写成功标准

每项 Now 项必须有明确的成功标准：

```
成果："新用户首次价值时间从 3 天降到 1 小时"

成功标准：
  - 80% 新用户在 1 小时内完成新手引导
  - 首次价值时间 p50 < 60 分钟
  - 新用户激活率从 40% 增至 60%
  - 上线后 30 天内衡量
```

### 步骤 5：评审与再平衡

月度评审：
1. 将已完成的 Now 项移至"已完成"（庆祝！）
2. 当容量释放时将 Next 项提升到 Now
3. 发现完成后将 Later 项提升到 Next
4. 移除不再与战略对齐的项
5. 从最新战略输入添加新项

## 决策要点与分支

| 决策点 | 选项 | 指引 |
|---|---|---|
| 项太大，一个季度做不完 | 分解为更小的成果 | 一个 Now 项应在 4–6 周内可完成 |
| 利益相关方要求日期 | 展示计划，而非日程 | "这是我们在做什么以及为什么。日期会变；优先级不变。" |
| 所有事都是"Now" | 在 Now 内强制排序 | 若所有事都是第一优先级，那就没有优先级 |
| 紧急事项打断路线图 | 吸收到缓冲中或做权衡替换 | 将同等大小的 Now 项换到 Next 腾出空间 |
| 季中战略变化 | 对照新战略重评估 Now 项 | 若战略不再支持，可以停掉 Now 项 |
| Later 变"坟墓" | 项永远待在 Later 里 | 每次评审要么提升、删除、或明确决定保留在 Later |

## 阶段核心产出

| 阶段 | 交付物 |
|---|---|
| 初始创建 | NNL 看板含成果、成功标准、战略可追溯性 |
| 月度评审 | 更新看板；移动/完成的项已记录 |
| 季度评审 | 对照更新后的战略输入全面重评估 |
| 利益相关方沟通 | 一页摘要展示 Now/Next/Later 含成果和进展 |

## 反模式与常见陷阱

| 反模式 | 为何失败 | 正确做法 |
|---|---|---|
| NNL 伪装成时间线 | "Next"变成"下季度"含暗示日期 | 绝不给列附日期；讨论成果，不是时间线 |
| 成果其实是功能 | "构建 X"不是成果 | 问："这会产生什么用户行为变化？" |
| Later 作为坟场 | 项待在 Later 中永远不被评审 | 每次评审，要么提升、移除、或明确决定保留 |
| Now 过载 | 团队有 15 个"Now"项，什么都完不成 | 限制 Now 为每团队 3–5 个成果 |
| 无成功标准 | 无法判断 Now 项是否真正交付了价值 | 每项 Now 必须有至少一个可衡量的标准 |
