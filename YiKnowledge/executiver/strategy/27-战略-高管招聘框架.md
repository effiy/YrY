# 高管招聘框架

> **作为**高管，**我想要**用结构化方法评估和招聘关键岗位人才，**以便**降低高管招聘的错配率——一次错配的代价是 6-18 个月的停滞和团队动荡。
>
> **核心洞见**：高管招聘的错误成本是普通招聘的 10-50 倍。不是工资高低的问题——一个不合适的高管会让整个团队方向混乱、核心人才流失、战略窗口错失。而大多数招聘失误不是因为能力不够，是因为"对的技能，错的阶段"。

## 招聘前：定义而非寻找

最常见的招聘错误是还没想清楚需要什么人，就开始看简历。

### 阶段匹配：公司阶段决定需要什么人

| 公司阶段 | 团队规模 | 最需要的能力 | 典型画像 |
|---|---|---|---|
| 0→1（探索） | < 10 人 | 动手能力强、模糊耐受度高、能做任何事 | 全栈创业者型——不喜欢管理和流程 |
| 1→10（验证） | 10-30 人 | 能建小团队、确立流程、从 0 到 1 的体系化 | 建设者型——既能写代码也能带 3-5 人 |
| 10→50（规模化） | 30-100 人 | 管理经验、规模化流程、组织建设 | 组织建设者型——擅长带团队和跨部门协作 |
| 50+（成熟） | 100+ 人 | 政治智慧、跨组织管理、维护文化 | 职业经理人型——擅长在复杂组织中运作 |

**YrY 当前阶段**：0→1 / 1→10。最需要的是"既能动手又能动脑"的人——能写代码、能想战略、能带小团队。不适合"只能管人不能做事"的大公司经理。

### 定义成功画像

在写 JD 之前，先写成功画像——这是一份内部对齐文档，不对外发布：

| 要素 | 说明 | 示例 |
|---|---|---|
| **使命** | 这个人在未来 12-18 个月要完成的最重要的 3 件事 | "1) 将 YiKnowledge RAG 检索准确率从 70% 提升到 85% 2) 建立知识文件贡献和审核流程 3) 招聘并培养知识工程团队" |
| **能力** | 必须掌握的核心技能（不超过 5 项） | "Python/llama_index、知识图谱、评估指标体系、团队管理" |
| **适配** | 与我们现有团队和文化互补的特质 | "在资源受限的环境中工作过、能接受模糊性、能写代码也能写文档" |
| **红线** | 绝对不能接受的特征 | "只能指挥不能动手、需要完善流程才能工作、对 AI 行业无热情" |

### 招聘渠道策略

| 渠道 | 适合 | 不适合 |
|---|---|---|
| 个人网络/内推 | 关键岗位（成功率最高） | 需要大量筛选的岗位 |
| 行业社区/开源贡献者 | 技术深度岗位 | 非技术岗位 |
| 招聘平台 | 有一定量需求的岗位 | 极其小众的方向 |
| 猎头 | C-level 和 VP 级别 | 预算有限的早期公司 |

## 面试：寻找信号而非确认偏见

### 面试结构（60-90 分钟）

| 时间 | 环节 | 考察什么 | 技巧 |
|---|---|---|---|
| 5 分钟 | 建立连接 | 沟通风格和状态 | 不要问"介绍一下你自己"——你已经有简历了 |
| 15 分钟 | 能力深潜 | 在声称擅长的领域到底有多深 | 追问 3 层："你做了什么具体决定？为什么这样？如果重来会怎么做？" |
| 15 分钟 | 情景测试 | 解决真实问题的思路 | 给一个 YrY 当前面临的实际问题（脱敏），看对方的解题过程 |
| 15 分钟 | 文化适配 | 价值观和工作方式是否匹配 | 不要问"你认同我们的价值观吗"——人人都会说是。给情景："如果 X 和 Y 冲突，你怎么选？" |
| 10 分钟 | 候选人提问 | 候选人关心什么、问题质量如何 | 高质量的提问是最好的信号之一 |
| 5 分钟 | 收尾和下一步 | 设定预期 | 明确告知后续流程和时间线 |

### 信号收集技术

**反确认偏见技术**：
- 在面试前写下你对此人的预期（基于简历），然后在面试中主动寻找推翻预期的证据
- 如果你觉得"这个人不错"，追问一个对方简历上最弱的领域

**行为面试的 STAR + L**：
- Situation / Task / Action / Result + Learning
- 最后一个 L 最关键："你从这次经历中学到了什么？如果重来，你会怎么做？"

**判断力的测试**：
- "告诉我一个你做过的错误决定。谁受到了影响？你什么时候意识到的？你做了什么？"
- 看点是对方是否坦诚、是否有反思、是否把失败归结为外部原因

### 信号权重

| 信号 | 权重 | 如何获取 |
|---|---|---|
| 过去产出的质量（非工作时间长度） | 40% | 看作品、看项目、追问具体贡献 |
| 解决问题的能力 | 25% | 情景测试、案例讨论 |
| 反思和成长意愿 | 15% | 行为面试的 L 部分 |
| 文化适配 | 10% | 情景选择题、团队成员直觉 |
| 学历/背景/大厂光环 | 10% | 简历——这是最不重要的信号 |

## 评估：用一致性对抗偏见

### 统一评分卡

每个面试官独立打分，面试前不互相讨论：

| 维度 | 评分 (1-5) | 证据 |
|---|---|---|
| 专业能力深度 | | 追问 3 层后的表现 |
| 解决问题能力 | | 情景测试的表现 |
| 沟通和协作 | | 讨论中的表达能力、倾听能力 |
| 反思和成长 | | 对失败的回答 |
| 文化适配 | | 在价值观相关情境中的回答 |
| 总体推荐 | | 强推 / 推荐 / 不确定 / 不推荐 |

面试官讨论时：先展示评分和证据，再表达结论。分歧大的地方就是需要追加信息的地方。

### 背景调查

不只做 HR 标准背景调查——找到共同认识的人获取非正式反馈：

| 要问的人 | 要问的问题 |
|---|---|
| 前同事/下属 | "如果有机会，你会再次和这个人一起工作吗？" |
| 前上级 | "这个人在什么类型的任务和环境中表现最好？什么类型中最挣扎？" |
| 行业联系人 | "你在行业活动中观察到的这个人的行为模式是什么？" |

**关键问题**："这个人的'操作系统'——他们的决策模式和价值观——是否适合我们公司的当前阶段？"

## YrY 招聘考量

### 当前招聘优先级

| 优先级 | 角色 | 为什么是现在 | 阶段匹配 |
|---|---|---|---|
| P0 | AI/RAG 工程师 | YiKnowledge RAG 是核心差异化 | 1→10 建设者型 |
| P1 | 前端工程师（YiPet） | Chrome 扩展独立开发压力大 | 0→1 全栈型 |
| P2 | 产品运营 | 知识库维护和内容运营需要专人 | 1→10 建设者型 |

### 小团队的招聘原则

- **宁缺毋滥**：一个不合适的人对 5 人团队的伤害比例远大于 50 人团队
- **写代码的能力**：在当前阶段，任何人（包括管理岗）都应该有能力直接贡献代码或内容
- **模糊舒适度**：在 YrY，方向会调整、优先级会变化——不适应模糊性的人会痛苦

## 反模式

| 反模式 | 为何失败 | 正确做法 |
|---|---|---|
| 招大厂光环 | 大厂的"做得好"在早期公司可能是"活不下来" | 问"你在混乱和资源紧缺时的表现" |
| 招一个"像我的人" | 团队同质化，创新力和韧性下降 | 主动寻找补你短板而非像你的人 |
| 为了填坑降低标准 | 不合适的坑填了比空着更糟 | 宁可自己或团队多扛 3 个月 |
| 面试只评估不说服 | 好候选人有选择——你需要卖出机会 | 面试是双向的；展示愿景和成长空间 |
| 忽视入职后前 90 天 | 再好的人在错误的环境中也会失败 | 前 90 天：明确使命、快速胜利、建立关系 |
