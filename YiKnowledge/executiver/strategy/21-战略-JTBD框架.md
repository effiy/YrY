# Jobs-to-be-Done 框架

> **作为**高管和产品负责人，**我想要**理解用户雇佣产品完成的真正任务，**以便**不被人口统计特征和用户画像蒙蔽，发现突破性的创新机会。
>
> **核心洞见**：用户不"买"你的产品——他们"雇佣"你的产品来完成某个任务。如果你只研究"35 岁的男性开发者用什么 IDE"，你不会知道他们为什么在某个时刻切换到 Cursor。JTBD 问的是"什么任务驱使他们寻找新工具？"

## 定义

JTBD 由 Clayton Christensen 提出，核心主张：

- 用户不是简单地"购买产品"，他们**雇佣**产品来完成特定的**待办任务**
- 理解用户的人口统计特征（年龄、性别、收入）不能解释他们**为什么**选择或切换产品
- 真正的创新来自发现用户有但现有解决方案无法完成的任务

```
传统视角                          JTBD 视角
────────                         ────────
用户画像：35岁男性开发者          待办任务：我需要在上线前 2 小时内
痛点：代码补全不够快              理解一个 5000 行 PR 的改动范围和风险
需求：更快的 AI 代码补全
                                  → 解决方案不一定是"更快的补全"
                                  → 可能是：变更影响分析 + 风险可视化
```

## 适用场景

- 发现颠覆性创新机会——当现有方案对某个任务严重过度服务或服务不足
- 理解用户为什么会"切换"产品——旧产品完成了任务但做得不够好
- 定义产品路线图的优先级——按任务的紧迫性和普遍性排序
- 评估竞品威胁——竞品是否在解决同一个任务？
- 指导营销信息——不说"我们有什么功能"，说"我们能帮你完成什么任务"

## JTBD 的核心概念

### 功能任务、情感任务和社会任务

每个待办任务都有三个维度：

| 维度 | 定义 | 示例（以 AI 开发工具为例） |
|---|---|---|
| **功能任务** | 用户想完成的具体操作目标 | "在 30 分钟内理解一个新模块的代码结构" |
| **情感任务** | 用户在任务过程中想有的感受 | "我不想因为看不懂代码而在代码评审中出丑" |
| **社会任务** | 用户想向他人展示的形象 | "我想让团队觉得我对代码库有全局掌控力" |

**原则**：功能任务解释"用什么"，情感和社会任务解释"为什么选这个"。B2B 工具往往忽视情感和社会任务，但它们是品牌忠诚度的核心驱动。

### 推力和拉力

用户切换产品不是随机行为，而是被"推力"推出旧方案、被"拉力"拉入新方案：

| 力量 | 定义 | 示例 |
|---|---|---|
| **推力** | 旧方案让用户无法完成任务的痛点 | "Cursor 虽然补全快，但无法帮我理解跨文件的业务逻辑" |
| **拉力** | 新方案吸引用户完成任务的亮点 | "YiKnowledge 的 RAG 能帮我在 10 分钟内找到相关代码和文档" |
| **惯性** | 阻碍用户切换的现有投入和习惯 | "我的团队已经在 Cursor 上积累了大量配置和记忆" |
| **焦虑** | 用户对新方案的担忧 | "切换到新工具会不会影响现有工作流？" |

**切换公式**：推力 + 拉力 > 惯性 + 焦虑 → 用户切换。

## 发现 JTBD 的方法

### 切换访谈

最有价值的 JTBD 洞察来自最近切换过产品的用户。访谈结构：

```
1. 触发：是什么特定时刻让你开始寻找新方案？
   → 不要接受"我就是想试试"——追问具体场景

2. 旧方案：你之前用什么？它在什么场景下让你失望？
   → 追问"当时发生了什么，让你觉得'这不行'"？

3. 选择：你考虑了哪些替代方案？为什么选了现在的？
   → 了解竞争集——用户考虑的不仅是你的直接竞品

4. 新方案：新方案有什么旧方案做不到的事？
   → 追问具体的使用场景，不要接受笼统的"更好用"

5. 补偿行为：新方案有没有什么让你觉得不够好的地方？你是怎么补偿的？
   → 补偿行为 = 未满足的任务 = 创新机会

6. 焦虑：在决定切换前，你最担心什么？
   → 了解阻碍切换的焦虑来源
```

### 非消费洞察

有时最有价值的 JTBD 不是来自竞品用户，而是来自**根本不使用任何解决方案的人**——他们用 Excel、邮件、白板这些"非产品"来完成这个任务。

**问题**：有没有一个重要的任务，人们现在用"非产品"的方式在完成？

对于 YrY：有没有开发者现在用"手动翻代码 + 问同事"来完成"理解大型代码变更"的任务？

## JTBD 机会评估

对发现的每个 JTBD，评估其创新价值：

| 标准 | 说明 | 评分 (1-5) |
|---|---|---|
| **重要性** | 用户有多需要完成这个任务？完不成的代价是什么？ | |
| **普遍性** | 有多少用户有这个任务？ | |
| **不满足度** | 现有方案完成这个任务的程度？ | |
| **支付意愿** | 用户愿意为更好的方案付出什么（钱/时间/切换成本）？ | |
| **解决可行性** | 我们有能力解决吗？或者解决的技术可行性？ | |

总分最高的 JTBD = 最值得押注的方向。

## 核心产出

- 用户切换访谈记录（至少 5-10 份）
- JTBD 机会矩阵（按重要性和不满足度排序）
- 每个 JTBD 的推拉惯性焦虑分析
- 产品路线图到 JTBD 的映射

## 反模式

| 反模式 | 为何失败 | 正确做法 |
|---|---|---|
| 把功能当 JTBD | "用户需要 AI 代码补全"——这是方案，不是任务 | 追问：用户用 AI 代码补全完成什么任务？ |
| JTBD 写得太大 | "管理软件开发"——太大，无法产生具体洞察 | 缩小到具体场景：在什么时刻、遇到什么困难 |
| 只分析功能任务 | 忽略情感和社会任务——你以为用户在比较功能，实际上在选择身份 | 每个 JTBD 三个维度都写 |
| 只访谈现有用户 | 现有用户自带选择偏误——不选你的人提供更多洞察 | 访谈已切换走的和非消费者 |
| JTBD 做一次就归档 | 用户的任务随环境变化——AI 工具出现后，很多旧任务消失了 | 季度重访 JTBD 列表 |
