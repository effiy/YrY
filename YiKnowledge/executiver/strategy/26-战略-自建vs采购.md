# 自建 vs 采购决策框架

> **作为**高管，**我想要**在自建和采购之间做出理性的资源分配决策，**以便**工程资源投入到真正能产生差异化的事情上，不差异化的事情尽可能买。
>
> **核心洞见**：技术决策中最贵的错误不是买错了，而是自建了不该自建的东西。自建一个不差的CRM系统花了 6 个人月——这些人本可以在核心产品上交付差异化功能。机会成本是自建vs采购分析中最大的隐性成本。

## 决策矩阵

四个核心判断标准：

```
自建更优 ←──────────────────────────→ 采购更优
        差异化    战略控制    成本     速度
```

| 标准 | 倾向自建 | 倾向采购 |
|---|---|---|
| **差异化潜力** | 这个能力能让我们与竞品拉开差距 | 这是行业标配，做得好不好用户不太在意 |
| **战略控制** | 依赖外部供应商的后果不可接受 | 供应商可替换、迁移成本低 |
| **总成本** | 长期自建成本 < 采购成本 | 采购成本 < 自建成本（含维护和机会成本） |
| **落地速度** | 自建速度能满足时间窗口 | 采购能更快上线、更快获取反馈 |

## 决策流程

### 步骤 1：界定能力

不是所有"技术需求"都是同一个粒度。用能力分层避免错误比较：

| 层级 | 定义 | 示例 | 决策重点 |
|---|---|---|---|
| **行业基础** | 每个同行都需要的 | 邮件服务、数据库、监控 | 几乎总是采购——不带来任何差异化 |
| **行业增强** | 头部同行都在采用的 | CI/CD 平台、云基础设施 | 通常采购——除非有独特需求 |
| **产品支撑** | 支撑你产品核心功能的基础设施 | YrY 的 RAG 引擎、RPC 协议 | 通常自建——这些是产品的一部分 |
| **产品核心** | 产品本身的独特能力 | YiKnowledge 的知识结构化方式 | 必须自建——这是你存在的理由 |

### 步骤 2：多维度评分

| 标准 | 权重 | 评分指引 |
|---|---|---|
| **差异化潜力** | 30% | 10=核心差异化，用户因它选我们；1=行业标配，差异化贡献为0 |
| **战略控制** | 25% | 10=供应商锁定后果不可接受；1=随时可换 |
| **总成本**（3年TCO） | 25% | 含：自建人力成本 + 维护成本 + 机会成本 vs 采购费用 + 集成成本 |
| **落地速度** | 15% | 10=时间窗口极紧，采购能赢得的周数是关键；1=时间充裕 |
| **内部能力匹配** | 5% | 10=团队有深度经验；1=完全不熟悉，学习曲线会很陡 |

### 步骤 3：计算总成本

**自建的 3 年总成本**：
```
自建成本 = 开发人力成本 + 持续维护人力成本 + 基础设施成本 + 机会成本

机会成本 = 开发人力 × 同期可交付的核心产品功能价值
```

**采购的 3 年总成本**：
```
采购成本 = 许可/订阅费用 + 集成开发成本 + 迁移成本 + 供应商风险评估溢价
```

**易忽略的成本**：
- 自建：文档编写、新人培训、技术债务、负责人的离职风险
- 采购：供应商谈判时间、合规审查、年度续费涨价、供应商倒闭的迁移成本

### 步骤 4：战略适配性测试

即使采购在成本和速度上占优，以下情况也应考虑自建：

| 测试 | 如果答案为"是" | YrY 示例 |
|---|---|---|
| 三年后，这个能力是否会变成核心竞争力？ | 倾向自建 | RAG 引擎——当前可以采购，但两年后一定是核心 |
| 供应商倒闭或被收购，我们能否在 1 个月内迁移？ | 如果"不能"，倾向自建 | Ollama——开源且模型无关，迁移成本低，采购安全 |
| 这个能力的独特需求是否无法被标准产品满足？ | 倾向自建 | YiKnowledge 的 RAG 原生架构——标准产品不能满足 |
| 我们的数据和知识是否因为这个决策而变得不可迁移？ | 如果"是"，倾向自建 | 用户数据在自有 MongoDB 中——数据主权可控 |

### 步骤 5：做出决定并设定重评时间

自建vs采购不是一次性决定。设定重评触发器：

| 触发器 | 说明 |
|---|---|
| 采购方案的关键功能发布 | 供应商发布了重大功能——是否改变了成本-价值方程？ |
| 自建方案的成本超预期 30%+ | 开发时间、维护复杂度超出估算？ |
| 新供应商进入市场 | 有更好的采购选项出现？ |
| 产品战略变更 | 这个能力从行业增强变成了产品核心（或相反）？ |

## 常见决策场景

### "工程师想自建"场景

工程师天生喜欢自建——这是热情，不是问题。但需要引导热情到正确的地方。

**应对**：问三个问题：
1. "这个自建的功能，我们的用户会为它付更多钱吗？还是会为它选择我们而非竞品？"
2. "如果自建，我们放弃了什么核心产品功能？"
3. "有没有一个采购+定制的中间方案？"

### "用开源还是用SaaS"场景

开源 ≠ 免费。开源的总成本 = 部署维护成本 + 定制成本 + 升级风险。

| 情境 | 倾向 |
|---|---|
| 需要深度定制，且团队有能力维护 | 开源 |
| 标准需求，不想花时间维护基础设施 | SaaS |
| 数据敏感，必须自托管 | 开源自托管 |
| 快速验证想法，不想投入运维 | SaaS |
| 长期战略能力（如 LLM 推理） | 开源 + 自建 |

## YrY 自建vs采购分析

| 能力 | 层级 | 当前方案 | 建议 | 理由 |
|---|---|---|---|---|
| LLM 推理 | 产品支撑 | Ollama（开源自托管） | 保持 | 开源+模型无关，战略控制和成本双优 |
| RAG 引擎 | 产品核心 | llama_index（开源） | 保持+深化 | 核心差异化——应该持续自建 |
| MongoDB | 行业基础 | 自托管 MongoDB | 保持 | 数据主权；迁移到 Atlas 可考虑 |
| 前端框架 | 行业增强 | Vue 3（开源） | 保持 | 开源生态成熟，无采购必要 |
| 监控告警 | 行业增强 | — | 评估 | 不是核心差异化，优先考虑 SaaS |
| CI/CD | 行业增强 | — | 评估 | 不是核心差异化，GitHub Actions 或类似 |
| Chrome 扩展分发 | 行业基础 | Chrome Web Store | 保持 | 唯一选择，没得选 |

## 反模式

| 反模式 | 为何失败 | 正确做法 |
|---|---|---|
| 工程师默认自建 | 在非核心能力上浪费宝贵人力 | 问"这个能力让用户选择我们吗？" |
| 采购默认买 | 在核心能力上依赖外部，差异化消失 | 核心能力必须自建——这是战略控制的底线 |
| 只比首年成本 | 忽略了维护、扩展、迁移的长期成本 | 用 3 年 TCO 做对比 |
| 忽略机会成本 | 自建 3 个月的核心产品功能损失是最大的隐形成本 | 每次评估都列出"放弃了什么" |
| 决定后不重评 | 市场和产品在变，昨天的正确可能今天是错误 | 设定重评触发器 |
