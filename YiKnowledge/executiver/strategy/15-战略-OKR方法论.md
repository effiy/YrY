# OKR 方法论

> **作为**高管和团队负责人，**我想要**掌握 OKR 方法论的核心原则和实践，**以便**在组织中有效落地目标管理，驱动对齐和聚焦。
>
> **核心洞见**：OKR 的核心不是考核，是对齐。一个好的 OKR 系统让每个人都清楚"公司当前最重要的是什么"以及"我的工作如何贡献于此"。如果 OKR 变成了填写表格的行政负担，你已经做错了。

## 定义

OKR (Objectives and Key Results) 是一套目标管理框架：

- **Objective (目标)**：定性描述——我们要去哪里？方向性的、有抱负的、有时限的。
- **Key Results (关键结果)**：定量衡量——我们怎么知道到达了？可衡量的、有挑战的、3-5 个。

```
Objective: 定性、鼓舞人心、有时限
  ├── KR1: 定量结果（从 X 到 Y）
  ├── KR2: 定量结果（从 X 到 Y）
  ├── KR3: 定量结果（从 X 到 Y）
  └── KR4: 定量结果（从 X 到 Y，可选）
```

## 适用场景

- 组织需要聚焦：太多方向，需要明确优先级
- 目标需要对齐：不同团队的目标互相冲突或脱节
- 执行需要追踪：目标设定了但没有定期追踪机制
- 团队需要自主：想给团队方向但不希望 micro-manage
- 战略需要落地：年度战略需要通过季度 OKR 转化为行动

## 好的 OKR vs. 差的 OKR

### Objective（目标）

| 好的 O | 差的 O | 为什么差 |
|---|---|---|
| 成为东南亚开发者首选的 AI 编程助手 | 提升产品质量 | 太模糊，无法判断是否达成 |
| 将 YiKnowledge 打造成可检索的决策知识库 | 做好知识管理 | 无方向性，无时间感 |
| 让 YiPet 用户离不开每天的 AI 陪伴 | 提高用户活跃度 | 无情感驱动，无独特价值 |

**O 的撰写法则**：
- 用动词开头（成为、打造、让、建立）
- 一句话能说清楚（不要用"and"连接多个目标）
- 读起来有激励性（团队愿意为之努力）
- 有明确的边界（知道什么在这个 O 的范围内，什么不在）

### Key Results（关键结果）

| 好的 KR | 差的 KR | 为什么差 |
|---|---|---|
| RAG 检索准确率从 70% 提升到 85% | 提高检索质量 | 不可衡量 |
| YiPet 日活用户从 50 增长到 200 | 增加用户 | 无基线，无目标 |
| 从需求提出到代码上线的中位周期从 8 天缩短到 5 天 | 加快交付 | 无指标，无目标 |
| 完成 6 篇第三方行业报告摘要并入库 | 多看行业报告 | 无数量，无交付标准 |

**KR 的撰写法则**：
- 包含基线（从 X）和目标（到 Y）
- 可客观验证（不是"我觉得达成了"）
- 是结果而非任务（"上线功能 A"是任务，"功能 A 的日活使用率达到 30%"是结果）
- 有挑战但可达（0.7 完成度被认为是"做得好"）

## OKR 周期

```
季度开始前 2 周            季度中                    季度末
──────────────────────────────────────────────────────────
设定 OKR                  追踪 + 对齐                评分 + 反思
    │                         │                         │
    ├── 公司级 OKR            ├── 每周检查 KR 进度      ├── 每个 KR 评分
    ├── 团队级 OKR            ├── 每月 OKR 对齐会       ├── 团队反思
    ├── 对齐检查              ├── 季中调整（如需）      ├── QBR 输入
    └── 沟通发布              └── 风险标记              └── 下季度 OKR 草稿
```

### 设定阶段（季度开始前 2 周）

1. **公司级 OKR**：高管团队基于年度战略提出 3-4 个公司级 O
2. **团队级 OKR**：各团队基于公司 O 撰写自己的 OKR
3. **对齐检查**：验证团队 OKR 是否真正支撑公司 O（而非只是"看起来相关"）
4. **沟通发布**：全员大会宣讲，书面发布

**对齐检查清单**：
- [ ] 每个团队 OKR 至少支撑一个公司级 O
- [ ] 检查是否存在"孤岛 OKR"（无人支撑的 O 或无支撑的来源）
- [ ] 检查是否存在"过度对齐"（一个团队 OKR 声称支撑所有公司 O——要么在撒谎，要么团队过载）

### 追踪阶段（季度中）

| 频率 | 活动 | 参与者 | 产出 |
|---|---|---|---|
| 每周 | 团队站会：KR 进度更新 | 团队 | 进度百分比 + 阻碍标记 |
| 每月 | OKR 对齐会：跨团队协调 | 团队负责人 | 依赖项解决 + 风险标记 |
| 季中 | 调整决策：是否需要调整 OKR | 高管 | 调整后的 OKR（如有） |

**进度更新的信号灯规则**：
- 绿灯（70-100% 目标进度）：按计划进行
- 黄灯（30-70%）：有风险，需要关注
- 红灯（< 30%）：严重偏离，需要决策（加速投入还是放弃）

### 评分阶段（季度末）

对每个 KR 评分（0.0 到 1.0）：

| 分数 | 含义 | 行动 |
|---|---|---|
| 0.7-1.0 | 达成或超额达成 | 做得很好——O 可能不够挑战 |
| 0.4-0.7 | 实质进展 | 做得好——进展符合预期 |
| 0.1-0.4 | 进展不足 | 需要分析：O 太大？执行有问题？优先级被挤占？ |
| 0.0 | 未启动 | 需要严肃反思：这个 O 是否应该存在？ |

**评分不是绩效考核**。0.7 被认为是"好成绩"——说明目标有足够的挑战性。如果每季度都是 1.0，说明 O 定得太保守了。

### 反思阶段

每季度评分后必须回答三个问题：

1. **这个 O 还重要吗？** 如果战略方向变了，下季度应该放弃或重写。
2. **为什么是这个分数？** 是目标定得不合理、执行有问题、还是外部环境变化？
3. **下季度我们有什么不同做法？** 用具体的行动改进 OKR 流程本身。

## OKR 级联

### 对齐模式（推荐）

```
公司 O1 ────────┬──→ 团队 A O1 (支撑 O1 的某一方面)
                ├──→ 团队 B O1 (支撑 O1 的另一面)
                └──→ 团队 C O1 (支撑 O1 的另一面)

公司 O2 ────────┬──→ 团队 A O2 (支撑 O2)
                └──→ 团队 B O2 (支撑 O2)
```

### 反模式：瀑布式分解

```
公司 O1 → 部门 O1 → 团队 O1 → 个人 O1
公司 O2 → 部门 O2 → 团队 O2 → 个人 O2
```

这种模式的问题：层级太多导致目标失真；个人失去自主性（OKR 变成命令下达工具）；无法处理跨团队目标。

**原则**：
- 团队 OKR 由团队自己写，不是上级下达
- 最多 3 层 OKR：公司 → 团队 → （大团队内的）小组
- 个人不设正式 OKR，个人目标在 1:1 中讨论

## OKR 与 KPI 的区别

| 维度 | OKR | KPI |
|---|---|---|
| 目的 | 驱动改变和进步 | 监控业务健康 |
| 性质 | 有时限的挑战目标 | 持续追踪的指标 |
| 设定 | 季度设定、季度结束 | 持续存在、定期调整阈值 |
| 评分 | 0.0-1.0，0.7 是"好" | 红黄绿灯 |
| 数量 | 3-4 个 O，每 O 3-5 个 KR | 可能更多 |
| 典型使用 | "本季度我们要..." | "我们持续监控..." |

**两者的关系**：KPI 告诉你哪里有问题，OKR 告诉你这个季度要改进什么。如果某个 KPI 持续红灯，它应该成为下季度的一个 OKR。

## YrY OKR 实施建议

### 适合 YrY 的 OKR 结构

| 层级 | 数量 | 设定人 | 评审频率 |
|---|---|---|---|
| 公司 OKR | 3-4 个 O | CEO + 高管 | 月度对齐 |
| 项目 OKR | 2-3 个 O / 项目 | YiVad/YiAi/YiPet 负责人 | 双周 |
| 小组 OKR | 1-2 个 O / 组 | 组内讨论产出 | 周 |

### YrY 三项目协同的特殊考量

- **共享 O**：涉及 YiVad + YiAi + YiPet 协同的目标，设立跨项目 OKR
- **独立 O**：各项目独立的目标在各自的 OKR 中
- **知识库 O**：YiKnowledge 的维护目标可放在 exec-003 或其他相关 O 中

## 核心产出

- 公司级 OKR 文档（含评分历史）
- 团队级 OKR 文档（含对齐映射）
- 季度评分和反思记录
- OKR 仪表盘（进度可视化）

## 反模式

| 反模式 | 为何失败 | 正确做法 |
|---|---|---|
| OKR 当 KPI 考核 | 团队设保守目标，失去挑战性 | OKR 与绩效薪酬脱钩；0.7 是"好" |
| O 写成任务清单 | "完成 10 次客户访谈"是任务不是目标 | O 写结果（"深度理解客户痛点"），KR 写衡量 |
| KR 不可衡量 | 无法客观评分 | 每个 KR 有数字、有基线、有目标 |
| 塞太多 OKR | 8 个 O 每个 7 个 KR = 没人记得住 | 3-4 个 O，每 O 3-5 个 KR |
| 设完不管 | 季度末想起来已经晚了 | 每周站会更新进度，每月对齐会 |
| 忽视对齐质量 | 团队 OKR 仅"名义上支撑"公司 O | 对齐检查：去掉公司 O 后，团队 OKR 仍然成立吗？ |
