# 用户研究与客户发现

> **作为**高管和产品负责人，**我想要**系统性地理解用户的行为、动机和痛点，**以便**产品决策有据可依——不是"CEO觉得用户想要这个"，而是"我们和 20 个用户聊过，其中 15 个独立提到了同一个痛点"。
>
> **核心洞见**：产品失败的第一原因不是技术不行，是没人要。而"没人要"是可以提前发现的——不是靠猜，是靠系统性地和用户对话。用户研究不是"找个UX研究员来做的事"——在早期公司，这是CEO和产品负责人最重要的工作之一。

## 用户研究的四种核心方法

### 1. 用户访谈（发现问题和需求）

**目的**：理解用户的背景、行为、痛点和目标——不是验证你的方案，是发现问题。

| 要素 | 做法 |
|---|---|
| **频率** | 持续——每周至少 2-3 次用户访谈 |
| **时长** | 30-45 分钟 |
| **对象** | 现有用户、流失用户、从未用过的目标用户——三类都要覆盖 |
| **结构** | 开放式问题为主——"告诉我你上次做 X 是什么情况"而非"你会用 Y 功能吗" |

**访谈问题清单**：

| 阶段 | 问题示例 |
|---|---|
| 背景 | "能描述一下你平时怎么完成 X 任务吗？" |
| 痛点 | "在这个过程中，最让你头疼的是什么？" |
| 当前方案 | "你现在怎么解决这个问题？用什么工具或方法？" |
| 理想状态 | "如果有一个魔法棒能解决这个问题——你希望它做什么？" |
| 行为证据 | "能不能给我看一下你上次做这件事的过程？"（看实际操作比听描述更有价值） |

**禁止的问题**：
- "你会用这个功能吗？" → 人会礼貌地说"会"——问"上次你遇到这个问题时怎么解决的？"
- "你觉得这个怎么样？" → 人会礼貌地说"不错"——问"这个解决了你什么问题？或者没有？"
- "你愿意付多少钱？" → 人会高估——看行为不看表态

### 2. 可用性测试（发现使用摩擦）

**目的**：观察用户实际使用产品的过程，发现他们卡住的地方。

| 要素 | 做法 |
|---|---|
| **任务设计** | 给用户一个具体任务（如"在 YiKnowledge 中找到关于竞品分析的文件"），观察他们怎么做 |
| **出声思维** | 要求用户在操作时说出脑子里在想什么——"我在找...我以为这个按钮会..." |
| **不帮助** | 当用户卡住时——先沉默 10 秒。如果还在卡——问"你期望发生什么？"而非"你应该点这里" |
| **频率** | 每 2-4 周一次——每次 3-5 个用户 |

### 3. 问卷调查（验证规模和模式）

**目的**：量化访谈中发现的模式——"5 个用户提到了这个痛点，这是普遍的还是偶发的？"

| 何时用 | 何时不用 |
|---|---|
| 需要量化已知的问题或模式 | 你不知道该问什么问题（先做访谈） |
| 需要按用户群细分数据 | 样本量太小（< 50 份回复） |
| 需要追踪 NPS 或满意度的时间趋势 | 代替用户访谈——问卷不能替代对话 |

### 4. 数据分析（观察实际行为）

**目的**：看用户实际做了什么——而非他们说了什么。

| 数据 | 能回答的问题 |
|---|---|
| 留存率 | 用户回来吗？多久回来一次？ |
| 功能采用率 | 新功能有多少人在用？用了一次就放弃了还是在持续用？ |
| 用户路径 | 用户通常怎么走？在哪一步流失了？ |
| 核心行为频次 | 真正在使用核心功能的人有多少？ |

## 客户发现的节奏

### 持续发现 vs 项目式研究

| 模式 | 说明 | 适用 |
|---|---|---|
| **持续发现** | 每周固定时间和用户对话——不断积累理解 | **推荐**——尤其是早期公司 |
| **项目式研究** | 启动新功能/产品前集中做一批研究 | 适用于重大方向决策前的深度验证 |

持续发现的每周节奏：
- 周一：确定本周要聊的用户（2-3 个）
- 周二-周四：访谈
- 周五：团队分享——30 分钟，每人分享本周最重要的 3 个发现

### 洞察存储和行动

从原始对话到可行动的洞察：

```
原始对话 → 关键引用 → 行为模式 → 机会或问题 → 产品行动
```

| 步骤 | 方法 | 产出 |
|---|---|---|
| 捕捉 | 访谈后 1 小时内记录关键引用和观察 | 原始笔记 |
| 聚类 | 每周/每月将观察按主题聚类 | 亲和图、主题列表 |
| 优先级排序 | 用频次 × 严重性 = 机会大小 | 排好序的机会列表 |
| 行动 | 将机会转化为产品假设 → 实验或功能 | PRD、实验设计 |

## YrY 用户研究实践

### 当前阶段推荐

| 活动 | 频率 | 对象 | 负责人 |
|---|---|---|---|
| YiVad 用户访谈 | 每周 2 次 | 吃自己狗粮——内部团队就是用户 | 产品负责人 |
| YiPet 用户观察 | 每周 1-2 次 | 邀请同事或朋友试用新功能 | YiPet 开发者 |
| RAG 检索质量观察 | 持续——查看查询日志 | 所有使用 RAG 的用户 | AI 工程师 |
| YiKnowledge 可用性 | 每月 1 次 | 团队中不熟悉知识库的人——能否找到信息？ | 知识库维护者 |

### 吃自己狗粮 (Dogfooding)

YrY 最大的用户研究优势：团队自己就是用户。

| 做法 | 目的 |
|---|---|
| 用 YiKnowledge 做所有技术决策 | 体验 RAG 检索的真实体验 |
| 用 YiVad 管理所有内部流程 | 体验管理后台的痛点和摩擦 |
| 用 YiPet 做日常 AI 查询 | 体验浏览器扩展的便利和不足 |

**原则**：如果团队自己都不喜欢用自己的产品——用户也不会。团队自己用的过程中发现的问题是最可信的需求信号。

## 核心产出

- 每周用户访谈记录（3-5 个关键发现）
- 月度用户洞察聚类（按主题排序）
- 机会-解决方案假设列表
- 用户反馈 → 产品行动的追踪

## 反模式

| 反模式 | 为何失败 | 正确做法 |
|---|---|---|
| 不问用户就做产品 | "我知道用户要什么"——最危险的假设 | 每周至少和 2 个用户对话 |
| 只和喜欢你的用户聊 | 确认偏误——只听到你想听的话 | 流失用户、竞品用户的洞察更有价值 |
| "用户说要什么就做什么" | 用户说方案，你的工作是理解问题 | 问"你遇到了什么问题"而非"你想要什么功能" |
| 做了研究但不行动 | 访谈记录堆在文件夹里——白做了 | 每周分享发现 + 至少一个发现转化为产品行动 |
| 告诉用户答案 | "你会用这个 AI 功能吗？"——暗示期待的回答 | 问开放式问题——让对方说，你听 |
