# McKinsey 7S 框架

> **作为**高管，**我想要**诊断战略执行中组织层面的障碍，**以便**在战略失败之前发现并修复组织要素之间的不一致。
>
> **核心洞见**：战略失败 80% 不是战略本身的问题，是组织要素不协调。7S 框架的价值在于揭示"我们说了什么"（战略）和"我们实际上在做什么"（系统、风格、技能）之间的差距。

## 定义

7S 框架将组织分为 7 个相互关联的要素：

```
        硬要素（容易定义和改变）
    ┌─────────────────────────────┐
    │  Strategy    Structure      │
    │  战略         结构           │
    │                           Systems│
    │                           系统    │
    │   Shared Values               │
    │   共享价值观（核心）            │
    │  Style       Staff          │
    │  风格         人员           │
    │            Skills           │
    │            技能             │
    └─────────────────────────────┘
        软要素（难以定义但同样重要）
```

**硬要素**（3 个）：战略 (Strategy)、结构 (Structure)、系统 (Systems) —— 可文档化、可直接改变。
**软要素**（4 个）：共享价值观 (Shared Values)、风格 (Style)、人员 (Staff)、技能 (Skills) —— 文化层面的，改变需要时间。
**核心**：共享价值观——所有要素都围绕它旋转。

## 适用场景

- 战略执行不力：方向对但推不动，7S 帮你找到卡在哪
- 组织变革：大到并购整合，小到团队重组
- 快速增长后的组织混乱：人多了但效率没提升
- 新 CEO/新高管上任：快速诊断组织现状
- 跨部门协作困难：可能不是人的问题，是系统或结构的问题

## 七个要素详解

### 硬要素

#### 1. 战略 (Strategy)

**核心问题**：我们的竞争方式是什么？如何在市场中取胜？

| 检查点 | 诊断问题 |
|---|---|
| 清晰度 | 团队成员能否独立说清战略？ |
| 取舍 | 战略是否明确了"不做什么"？ |
| 一致性 | 各部门的工作是否对齐同一个战略？ |
| 适应性 | 战略是否仍适用于当前的市场环境？ |

#### 2. 结构 (Structure)

**核心问题**：组织架构图是什么样？权力和信息如何流动？

| 检查点 | 诊断问题 |
|---|---|
| 架构形态 | 职能制 / 事业部制 / 矩阵制 / 项目制？ |
| 汇报线 | 每个人都知道自己汇报给谁、谁汇报给自己？ |
| 控制跨度 | 每个管理者的直接下属数量是否合理（5-9 为最佳）？ |
| 决策权 | 谁有权决定什么——有没有明确的授权边界？ |

#### 3. 系统 (Systems)

**核心问题**：工作实际上是怎么完成的？流程和工具是什么？

| 检查点 | 诊断问题 |
|---|---|
| 核心流程 | 需求→开发→上线→运维的流程是什么？每一步有负责人吗？ |
| 信息系统 | 用什么工具沟通、协作、追踪？信息在哪里流转？ |
| 激励系统 | 奖励什么行为？惩罚什么行为？和战略对齐吗？ |
| 控制机制 | 怎么发现偏差？怎么纠正？ |

### 软要素

#### 4. 共享价值观 (Shared Values)

**核心问题**：我们真正相信什么？什么驱动我们的行为？

| 检查点 | 诊断问题 |
|---|---|
| 言行一致 | 墙上挂的价值观和实际奖惩的行为是否一致？ |
| 优先级共识 | 质量、速度、成本、创新——发生冲突时选哪个？ |
| 信任水平 | 团队成员是否敢于表达不同意见？ |

#### 5. 风格 (Style)

**核心问题**：领导团队的决策和行为模式是什么？

| 检查点 | 诊断问题 |
|---|---|
| 决策风格 | 自上而下 / 共识驱动 / 数据驱动 / 直觉驱动？ |
| 沟通风格 | 正式 / 非正式？书面 / 口头？透明 / 按需？ |
| 冲突处理 | 直接面对还是绕道走？ |

#### 6. 人员 (Staff)

**核心问题**：我们有什么样的人？人才结构如何？

| 检查点 | 诊断问题 |
|---|---|
| 关键角色 | 不是按职称，而是按"如果这个人离职，什么会断裂"来找关键角色 |
| 人才密度 | 每个岗位上是否是最合适的人？ |
| 多样性 | 背景、经验和思维方式的多样性是否足够？ |

#### 7. 技能 (Skills)

**核心问题**：组织作为一个整体擅长什么？

| 检查点 | 诊断问题 |
|---|---|
| 核心能力 | 组织 3-5 个最擅长的能力是什么？ |
| 能力缺口 | 战略需要的但组织现在不具备的能力？ |
| 能力可复制性 | 核心能力能否在团队间传递，还是集中在少数人？ |

## 使用流程

### 步骤 1：逐一评估每个 S

对每个要素，评估当前状态和理想状态之间的差距（1-5 分）：

| S | 当前状态 | 理想状态 | 差距 | 优先级 |
|---|---|---|---|---|
| Strategy | 3 | 5 | -2 | 中 |
| Structure | 4 | 4 | 0 | — |
| Systems | 2 | 4 | -2 | 高 |
| Shared Values | 3 | 5 | -2 | 中 |
| Style | 4 | 4 | 0 | — |
| Staff | 3 | 4 | -1 | 低 |
| Skills | 3 | 5 | -2 | 高 |

### 步骤 2：检查要素间的对齐度

最关键的不是单个要素的分数，而是要素之间是否一致：

| 对齐检查 | 不一致的信号 |
|---|---|
| 战略 vs. 系统 | 战略要求快速迭代，但系统是瀑布式审批流程 |
| 战略 vs. 技能 | 战略要求 AI 驱动，但团队以传统开发技能为主 |
| 战略 vs. 共享价值观 | 战略说要创新，但犯错的惩罚很重 |
| 结构 vs. 风格 | 结构是扁平的，但风格是自上而下的命令 |
| 系统 vs. 共享价值观 | 价值观说透明度，但系统对信息访问有层层权限 |

### 步骤 3：识别杠杆点

不是所有差距都需要同时解决。找到"改变一个就能撬动多个"的杠杆点：

**杠杆点识别法则**：
- 如果改变一个 S 能让 3+ 个其他 S 自动改善 → 这是杠杆点
- 通常系统 (Systems) 和共享价值观 (Shared Values) 是最常见的杠杆点

### 步骤 4：制定改进计划

| 优先改进的 S | 具体行动 | 预期连锁效应 | 时间线 |
|---|---|---|---|
| Systems | 简化上线审批流程，从 3 级到 1 级 | 改善：战略执行速度、工程师满意度（Staff/Skills） | 4 周 |
| Skills | 引入 AI 工程培训 + 外部招聘 | 改善：战略可行性、系统效能 | 12 周 |

## YrY 7S 诊断

| S | 当前状态 | 评估 |
|---|---|---|
| Strategy | 明确——全流程 AI 开发平台差异化 | 强：方向清晰 |
| Structure | 三项目独立 + 共享 YiAi 后端 | 中：三项目协同有摩擦 |
| Systems | Git + RPC 信封 + 知识监视器 | 强：有统一的 RPC 协议和信息流 |
| Shared Values | 代码质量、知识驱动、简洁优先 | 中：隐含但未显性化 |
| Style | 小型团队、快速迭代、数据驱动 | 强：适合当前阶段 |
| Staff | 全栈能力覆盖，但关键角色单点 | 弱：关键人依赖高 |
| Skills | 全栈开发 + AI 集成能力 | 中：RAG 能力在建设中 |

**最大差距**：Staff（关键角色单点依赖）和 Systems（YiKnowledge 维护流程需更自动化）。

## 核心产出

- 7S 评估矩阵（现状 vs. 理想 vs. 差距）
- 要素对齐检查表（不一致的地方是高优先级）
- 改进路线图（杠杆点优先）

## 反模式

| 反模式 | 为何失败 | 正确做法 |
|---|---|---|
| 只关注硬要素 | 战略-结构-系统的调整如果没有软要素配合，推不动 | 7 个 S 一起诊断，尤其不能忽视共享价值观 |
| 7S 当一次性快照 | 组织在变化，要素间的对齐度也在变化 | 每半年或重大变化后重新评估 |
| 试图同时改变所有差距 | 资源和管理注意力分散 | 识别 1-2 个杠杆点，集中力量改变 |
| 软要素用硬手段 | 共享价值观不能靠行政命令改变 | 软要素通过榜样、故事、奖惩来塑造 |
