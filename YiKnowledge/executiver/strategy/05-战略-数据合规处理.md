# 处理数据合规

> **作为**合规负责人，**我想要**建立和维护数据合规实践，**以便**组织避免监管罚款并保持客户信任。
>
> **核心原则**：数据合规不是一次性项目——它是一种持续的运营能力。法规变、数据变、系统变——每季度重新评估，每月监控法规变化。

## 适用场景

- 建立持续的数据合规项目
- 季度合规基线评审
- 新产品上线涉及个人信息收集
- 新的数据处理方式或目的变更
- 收到客户的数据主体访问请求 (DSAR)
- 数据泄露后的合规强化

## 触发条件

这是一个**持续**的旅程，按季度评审节奏。以下情况触发全面重评估：

- 适用于你数据类型或辖区的新法规
- 数据泄露或安全事故
- 涉及个人信息收集的新产品上线
- 进入新司法管辖区（尤其是欧盟、中国或有隐私法的美国各州）
- 第三方审计或客户尽职调查请求
- 数据处理发生重大变更（新数据类型、新处理方、新目的）

## 分步操作

### 步骤 1：数据清单 — 知道你拥有什么

绘制所有数据资产：

| 属性 | 示例 |
|---|---|
| **数据类型** | PII、行为、财务、健康、生物特征、位置 |
| **来源** | 用户输入、API 集成、日志、第三方、推断 |
| **存储位置** | 哪个数据库、哪个区域、哪个云服务商 |
| **处理目的** | 为什么收集？是否仍然需要？ |
| **数据主体** | 客户、员工、合作伙伴、访客 |
| **留存期** | 保留多久？是否有策略？ |
| **访问控制** | 谁可以访问？访问是否被记录？ |

产出：数据清单电子表格或数据目录条目。

### 步骤 2：法规映射 — 知道什么适用于你

将每种数据类型映射到适用法规：

| 法规 | 司法管辖区 | 关键要求 | 与我方相关？ |
|---|---|---|---|
| GDPR | EU/EEA | 同意、访问权、删除权、DPO、DPIA、72h 泄露通知 | {{是/否}} |
| CCPA/CPRA | 加利福尼亚 | 知情权、删除权、不出售权、数据最小化 | {{是/否}} |
| PIPL（个人信息保护法） | 中国 | 同意、数据本地化、跨境传输评估、个人信息保护负责人 | {{是/否}} |
| LGPD | 巴西 | 类似 GDPR；同意、权利、DPO | {{是/否}} |
| HIPAA | 美国（医疗） | PHI 保护、商业合作协议、最小必要标准 | {{是/否}} |
| SOC 2 | 全球（自愿） | 安全、可用、保密、处理完整性、隐私 | {{是/否}} |

### 步骤 3：差距分析 — 知道缺少什么

对每项适用法规评估合规状态：

| 要求 | 状态 | 差距 | 优先级 |
|---|---|---|---|
| 同意管理 | ✅ 已实施 | — | — |
| 数据主体访问请求 (DSAR) | 🔶 部分 | 无自动化工作流；人工流程需 2 周 | 高 |
| 跨境数据传输保障 | ❌ 缺失 | 无欧盟数据的标准合同条款 | 严重 |
| 泄露通知流程 | ✅ 已实施 | — | — |

### 步骤 4：修复计划

按风险排优先级：

```
风险 = 执法可能性 × 罚款影响
```

**优先级时限**：
- 严重：30 天内解决
- 高：90 天内解决
- 中：180 天内解决

### 步骤 5：运营化

将合规嵌入运营，而非一次性项目：

| 实践 | 节奏 | 负责人 |
|---|---|---|
| 数据清单更新 | 每季度 | 数据管理 |
| 法规监控 | 每月 | 法务/合规 |
| 同意审计 | 每季度 | 合规 |
| 访问评审 | 每半年 | 安全 |
| 员工培训 | 每年 | HR + 合规 |
| 泄露演练 | 每年 | 安全 |
| 新处理的 DPIA | 每次变更 | 合规 + 产品 |

## 数据合规检查清单

**季度基线检查清单**：

- [ ] 数据清单已更新（新增的数据类型和来源）
- [ ] 法规监控已完成（新法规或修订法规）
- [ ] 同意机制已验证（用户可查看和撤回同意）
- [ ] DSAR 流程已测试（能否在 30 天内响应？）
- [ ] 第三方处理方列表已更新
- [ ] 数据留存策略已执行（清理计划按时运行）
- [ ] 访问控制已审计（权限与实际需要是否匹配）
- [ ] 员工培训已完成（新员工入职培训 + 全员年度刷新）

## YrY 特定数据合规考量

| 数据 | YiAi 存储位置 | 敏感度 | 合规要求 |
|---|---|---|---|
| 用户聊天消息 (sessions) | MongoDB | 中 | 用户可请求删除；需数据留存策略 |
| 知识库文件 (knowledge_files) | MongoDB + 文件系统 | 低 | 公开知识，无 PII |
| 静态文件 (static_files) | MongoDB | 低-中 | 需审计上传内容 |
| 缺陷报告 (bugs) | MongoDB | 低 | 可能含截图，需评估 PII 风险 |
| 用户数据 (users) | MongoDB | 高 | 密码哈希、角色、权限——最高保护级别 |

## 决策要点与分支

| 决策点 | 选项 | 指引 |
|---|---|---|
| 是否需要数据本地化？ | 本地化 vs 用标准合同条款 vs 停止处理 | 若法规要求，本地化；GDPR 用标准合同条款；收益 < 合规成本则停止 |
| 同意模式 | 主动同意 vs 被动退出 vs 合法利益 | 敏感数据主动同意；仅在可证明必要时用合法利益 |
| 数据留存期 | 固定期 vs 按目的 vs 无限期 | 按目的：目的达成即删除；绝不可无限期 |
| 第三方处理方 | 审计 vs 依赖认证 vs 不使用 | 严重/高风险处理方审计；标准处理方看认证（SOC 2, ISO 27001） |

## 阶段核心产出

| 阶段 | 交付物 |
|---|---|
| 数据清单 | 数据地图电子表格含所有属性 |
| 法规映射 | 适用法规列表附要求 |
| 差距分析 | 排优先级差距报告附风险评级 |
| 修复 | 修复路线图含负责人和截止日期 |
| 运营化 | 合规日历含经常性任务 |

## 反模式与常见陷阱

| 反模式 | 为何失败 | 正确做法 |
|---|---|---|
| 合规是一次性项目 | 法规变化、数据变化、系统变化 | 建立季度评审节奏；尽可能自动化监控 |
| "我们没有欧盟客户"当作辩护 | GDPR 适用于欧盟居民，不是欧盟客户；相似法律在蔓延 | 主动映射法规；不要等到违规再行动 |
| "以防万一"过度收集数据 | 增大合规面和泄露风险 | 仅为特定、已记录的目的收集数据 |
| 仅有律师做合规 | 律师识别了差距但无法落地修复 | 跨职能团队：法务 + 工程 + 产品 + 安全 |
| 忽视第三方处理方 | 你的合规取决于最薄弱的处理方 | 供应商评估检查清单；所有处理方的合同要求 |
| 合规政策不透明 | 用户不知道你如何处理其数据 | 隐私政策需清晰可读、公开可访问 |
