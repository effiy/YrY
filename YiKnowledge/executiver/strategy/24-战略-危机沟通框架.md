# 危机沟通框架

> **作为**高管，**我想要**在危机时刻知道该说什么、对谁说、什么时候说，**以便**在不确定中保护信任，将声誉损害降到最低。
>
> **核心洞见**：危机中的信任不是靠说"我们没问题"赢得的，而是靠说"这是我们知道的、这是我们还不知道的、这是我们正在做的"。在不确定中展现掌控感，比假装一切正常更令人信任。

## 危机分级

不是每个问题都是危机。用分级决定响应的级别和速度：

| 级别 | 定义 | 响应时间 | 沟通范围 | 示例 |
|---|---|---|---|---|
| **L1 紧急** | 威胁用户安全、数据泄露、重大服务中断 | 1 小时内首次沟通 | 全员 + 用户 + 公众 | 数据泄露、安全事故、核心服务全挂 |
| **L2 严重** | 影响重大客户、媒体关注、监管问询 | 4 小时内首次沟通 | 受影响用户 + 团队 | 大客户体验严重受损、负面媒体报道 |
| **L3 关注** | 内部重大问题、潜在风险 | 24 小时内 | 内部团队 + 相关方 | 关键人员离职、竞品重大动作 |
| **L4 日常** | 常规问题和投诉 | 正常节奏 | 直接相关方 | 个别用户投诉、小范围故障 |

## 危机沟通的黄金 4 小时

### H+0（危机确认后的第一时间）

| 行动 | 负责人 | 产出 |
|---|---|---|
| 激活危机小组（CEO + CTO + 相关职能负责人） | CEO | 拉群/开会 |
| 收集已知事实：什么发生了、影响范围、时间线 | CTO / 负责人 | 事实清单 |
| 决定沟通等级（L1-L4） | CEO | 等级确认 |
| 暂停所有对外营销/社交媒体发布 | 市场/运营 | 排期暂停 |
| 指定唯一对外发言人 | CEO（或指定 1 人） | 发言人 |

### H+1：首次对外沟通

**原则**：速度 > 完美。宁可 1 小时内发一段不完美的声明，也不要 6 小时后发一份完美的声明。信息真空会被猜测和谣言填满。

**首次沟通模板**（对内或对外）：

```
我们注意到 [发生了什么]。

目前我们知道：
- [确定的事实 1]
- [确定的事实 2]

我们正在调查：
- [不确定但在查的事 1]

我们已经采取的行动：
- [行动 1]
- [行动 2]

下一步沟通时间：[具体时间，不要用"稍后"]

如有紧急问题，联系：[渠道]
```

**为什么这个模板有效**：
- 区分"已知"和"正在查" → 诚实建立信任
- 列出已采取的行动 → 展现掌控感
- 承诺下次更新时间 → 减少焦虑

### H+4：首次详细更新

| 要素 | 内容 |
|---|---|
| 发生了什么 | 事件的清晰描述（技术或业务层面） |
| 影响范围 | 谁受影响、多大范围、持续多久 |
| 根本原因 | 如果已知就说明；如果未知就说"仍在调查，将在 [时间] 更新" |
| 我们正在做什么 | 具体的、可验证的行动 |
| 用户应该做什么 | 如果是数据泄露：改密码；如果是服务中断：备用方案 |
| 下次更新时间 | 具体的下一次沟通时间 |

### 危机中的"不要说"

| 不要说 | 为什么 | 应该说 |
|---|---|---|
| "没有数据受到影响" | 如果后来发现有，信任彻底崩塌 | "根据我们目前的调查，暂未发现数据泄露的证据。调查仍在继续。" |
| "只是一个小问题" | 对受影响的人来说不是小事 | "我们理解这对您的影响，我们正在全力解决。" |
| "这是供应商/第三方的错" | 推卸责任，不解决任何问题 | "我们正在与合作伙伴一起解决这个问题。" |
| "不会再有下次" | 没人能保证 | "这是我们为防止再次发生而采取的措施：[列出来]" |
| "无可奉告" | 等于"我有事隐瞒" | "这个问题我们正在调查中，将在 [时间] 给出答复。" |

## 不同受众的沟通策略

| 受众 | 首要关心 | 沟通渠道 | 节奏 |
|---|---|---|---|
| 受影响用户 | 我的数据安全吗？服务什么时候恢复？ | 应用内通知、邮件、状态页 | 即时 + 每 2 小时更新 |
| 全体员工 | 公司会怎样？我该做什么？ | 全员会议、Slack/钉钉 | H+2 内首次，每天一次 |
| 核心团队 | 我负责什么？需要我做什么？ | 危机小组群、1:1 电话 | 持续 |
| 投资人/董事会 | 影响多大？对估值/业务的影响？ | CEO 直接电话/邮件 | H+4 内首次 |
| 媒体/公众 | 发生了什么？谁的责任？ | 官方声明、发言人 | 按需，L1/L2 必须 |

## 危机后的恢复

### 危机结束后 1 周内

| 行动 | 产出 |
|---|---|
| 事后复盘 (Postmortem) | 时间线、根因、5 Whys 分析 |
| 公布复盘结果（如适当） | 对外透明的复盘报告（脱敏） |
| 与受影响用户沟通 | 致歉 + 说明改进措施 |
| 内部全员复盘 | 经验教训分享 |

### 复盘报告模板

```
# 事件复盘：[事件名称]

## 时间线
- [时间]：[发生了什么]
- [时间]：[检测到/被通知]
- [时间]：[响应开始]
- [时间]：[问题解决]

## 根因分析
- 直接原因：[技术/操作层面的原因]
- 系统原因：[为什么系统允许这个错误发生？]

## 影响
- 用户影响：[多少人、多长时间、什么程度]
- 业务影响：[如有]

## 我们做对了什么
- [响应中的正确做法]

## 我们做错了什么
- [需要改进的地方]

## 行动项
| 行动 | 负责人 | 截止日期 |
|---|---|---|
| [避免再次发生的措施] | | |
```

## YrY 危机场景预案

| 场景 | 等级 | 首次沟通时间 | 发言人 | 关键信息 |
|---|---|---|---|---|
| YiAi 服务中断（> 1 小时） | L1 | H+1 | CTO | 影响范围、预计恢复时间、备选方案 |
| YiPet 用户数据泄露 | L1 | H+1 | CEO | 影响范围、用户应采取的行动、调查状态 |
| YiVad 出现严重安全漏洞 | L2 | H+4 | CTO | 漏洞详情、修复时间、用户无需担心的事 |
| YiKnowledge 内容被外部批评 | L3 | H+24 | CEO | 立场声明、处理措施 |
| 核心团队成员离职 | L3 | 内部 H+24 | CEO | 过渡计划、不影响业务的证据 |

## 核心产出

- 危机分级和响应时间标准
- 危机小组名单和联系信息（提前建好，不要等出事再找）
- 危机沟通模板（对内 + 对外）
- 事后复盘报告

## 反模式

| 反模式 | 为何失败 | 正确做法 |
|---|---|---|
| 沉默等待 | 信息真空被谣言和猜测填充 | 1 小时内首次沟通，即使信息不全 |
| 过度承诺 | "绝对不会再发生"——不可信也不诚实 | 说"我们学到的教训"和"我们采取的措施" |
| 隐瞒真相 | 一旦被发现（几乎必然），信任彻底崩塌 | 主动披露已知事实 |
| 多人发言 | 信息不一致，混乱加剧 | 指定唯一发言人；其他人统一口径"请联系发言人" |
| 危机后才建流程 | 出事时手忙脚乱 | 提前建立危机小组、模板、联系人和响应标准 |
