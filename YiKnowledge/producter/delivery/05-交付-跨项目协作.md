# 跨项目协作手册

> **适用场景**：当某个需求涉及 YiAi + YiVad + YiPet 中两个或三个项目时。YrY 是共享后端的单体仓库——YiAi 的每一次 API 变更都会波及 YiVad 和 YiPet。不协调的跨项目开发 = 两个项目等一个项目 = 三个项目的节奏全乱。

## YrY 的依赖拓扑

```
YiAi（后端核心）
  ├── 被 YiVad 依赖：聊天、数据 CRUD、文件管理、知识库、RAG、Agent
  └── 被 YiPet 依赖：聊天、会话管理、数据查询、知识库、RAG

YiPet ←→ YiVad（跨项目桥接）
  └── Session key 桥接到 YiVad aiChat、Bug 报告
```

**关键事实**：
- 涉及新 API 的功能，YiAi 必须先于消费方完成
- API 变更（参数增减、返回结构变化）同时影响两个消费方
- YiPet 和 YiVad 之间的桥接不经过 YiAi（直接通过 URL 参数传递 session key）

## 跨项目功能的三类模式

### 模式一：后端驱动型（YiAi 先行）

```
时间线：
Week 1-2: YiAi 开发新 API + 提供 Mock 数据
Week 2-3: YiVad/YiPet 并行开发前端（使用 Mock 数据）
Week 3:   YiAi API 就绪，联调
Week 4:   联合测试 + 发布
```

**适用**：新功能需要新的 API 端点。如 Agent 报告生成——YiAi 需要新增 `agent_service.generate_report` 方法。

**关键成功因素**：YiAi 必须在 Week 1 结束前提供可用的 Mock 数据（格式和真实 API 一致），否则消费方无法并行开发。

### 模式二：前端驱动型（YiVad/YiPet 先行）

```
时间线：
Week 1-2: YiVad/YiPet 设计和开发 UI，使用已有 API
Week 2-3: 发现需要 API 小改动（如增加字段），YiAi 跟进
Week 3:   联调
```

**适用**：功能主要是前端变更，后端只需小调整。如 YiVad 新增一个数据管理页面——大部分 API 已存在，可能只需要调整返回字段。

**关键成功因素**：尽早确认"已有 API 够不够用"。不要开发到一半才发现需要新 API——那时 YiAi 的容量可能已经被其他需求占满。

### 模式三：桥接型（YiPet + YiVad，不经过 YiAi）

```
时间线：
Week 1: YiVad 和 YiPet PM 对齐桥接协议（session key 格式、跳转参数）
Week 1-2: YiVad 先完成目标页面
Week 2-3: YiPet 完成后台触发跳转
Week 3: 联合测试端到端流程
```

**适用**：YiPet 需要跳转到 YiVad 的特定页面并传递上下文。如从 YiPet 聊天界面跳转到 YiVad aiChat 页面。

**关键成功因素**：桥接协议（URL 参数、session key 格式）必须在开发开始前对齐并文档化。口头约定 = 联调时必然不匹配。

## API 依赖生命周期管理

### 阶段对照表

| 阶段 | YiAi（提供方）| YiVad/YiPet（消费方）| 检查点 |
|---|---|---|---|
| **提案** | PM 在 PRD 中定义 RPC 契约（module_name, method_name, parameters） | PM 确认契约满足前端需求 | RPC 契约评审通过 |
| **开发** | 实现 API + 提供 Mock 数据 | 基于 Mock 数据并行开发前端 | Mock 数据格式与真实 API 一致 |
| **联调** | API 在预发布环境可用 | 切换到真实 API，验证端到端流程 | 自动化契约测试通过 |
| **发布** | YiAi 先发布 API（保持向后兼容） | YiVad/YiPet 在 API 就绪后发布 | 消费方发布前确认 API 可用 |
| **维护** | API 变更提前通知、保持向后兼容至少一个版本周期 | 在迁移窗口内完成适配 | 旧版本调用不报错 |

### RPC 契约变更通知流程

当 YiAi 需要变更已有 API（参数增减、返回结构调整）：

1. **YiAi PM** 在变更 PRD 中标注影响：哪些 module_name.method_name 变更、变更类型（新增参数/废弃参数/返回结构调整）、向后兼容性
2. **通知消费方 PM**（YiVad 和 YiPet）：在变更开发的 Sprint 第一天就通知，不要等到联调时才发现
3. **消费方 PM** 评估适配成本：前端需要改多少地方？测试回归范围多大？
4. **三方对齐迁移窗口**：YiAi 的新 API 和旧 API 同时运行的窗口期（建议 1 个 Sprint，即 2 周）
5. **窗口期结束后**：YiAi 移除旧 API，消费方必须已完成适配

### 常见 API 依赖故障及预防

| 故障 | 根因 | 预防 |
|---|---|---|
| 联调时发现参数名不匹配——前端传 `query`，后端期待 `filter` | RPC 契约未在开发前文档化，双方各自理解参数名 | 开发前 PRD 必须包含 RPC 契约表，参数名严格使用契约规范 |
| YiVad 前端开发完成了但 YiAi API 还没好——前端闲置等后端 | 两个项目按各自 Sprint 节奏走，没有对齐依赖 | 跨项目依赖必须在三个项目联合的 Sprint 规划会上对齐 |
| API 变更后 YiPet 突然不可用——"我们不知道这个 API 变了" | YiAi 变更后未通知消费方，或通知太晚 | API 变更必须有迁移窗口（≥ 1 Sprint），消费方 PM 收到通知后必须确认 |
| Mock 数据格式与真实 API 不一致——联调时大量返工 | Mock 数据由前端自行构造，格式猜测 | YiAi 提供 Mock 数据或 Mock Server，格式与真实 API 严格一致 |

## 跨项目规划和里程碑对齐

### 联合 Sprint 规划（涉及跨项目依赖时）

在常规 Sprint 规划之前，三个项目的 PM 和技术负责人先做 30 分钟联合规划：

**议程**：
1. **依赖声明**（5 分钟）：本轮有哪些需求涉及跨项目 API 调用？——YiAi PM 列出本轮涉及的 API 变更
2. **依赖排序**（10 分钟）：API 变更的优先级排序——先做哪个、后做哪个。按"谁的消费方先需要"排序
3. **容量确认**（10 分钟）：YiAi 本轮的开发容量是否支撑所有 API 变更？如果不能，哪些可以延后？
4. **里程碑定义**（5 分钟）：联合里程碑——"本 Sprint 结束时，三个项目联合演示 {{端到端场景}}"

### 联合里程碑示例

```
Sprint 目标：Agent 报告生成端到端流程可演示

依赖链：
  YiAi 完成 agent_service.generate_report API → 
  YiVad 完成 Agent 聊天界面和报告草稿展示

联合演示场景：
  用户在 YiVad aiChat 中输入案例数据 → 
  点击"生成报告" → 
  YiAi Agent 基于 YiKnowledge RAG 检索生成报告草稿 → 
  YiVad 展示报告草稿，用户可逐段编辑 → 
  提交保存
```

## 跨项目沟通模板

### API 变更通知

**从 YiAi PM 发给 YiVad/YiPet PM：**

```
变更类型：新增 API / 修改 API / 废弃 API
module_name.method_name：services.ai.agent_service.generate_report
变更内容：
  - 新增 parameters.report_type 字段（必填，枚举值：after_sales / technical）
  - 返回结构中新增 data.sources 字段（可选，引用来源列表）
向后兼容性：新增字段不影响旧调用方式，旧格式仍可用
计划就绪时间：本周五（Sprint 1 Day 5）预发布环境可用
迁移窗口：Sprint 2 结束时旧调用方式将废弃
联系人：YiAi 后端 @姓名
```

### 依赖阻塞升级

**当消费方因等待 API 而被阻塞时：**

```
阻塞项：YiVad Agent 报告生成前端等待 YiAi generate_report API
当前状态：API 开发延迟 3 天，预计本周三可提供 Mock 数据
影响：YiVad Sprint 中的 Agent 功能有 2 天无法推进
需要的决策：
  A. 等 YiAi API（YiVad Agent 功能可能延期 2 天）
  B. YiVad 先做 UI 和交互（编辑界面、状态处理），等 API 就绪后补数据流部分
建议：选 B——编辑界面和数据流可以并行，延期风险可控
```

## 三个项目的 PM 协作清单

每个 Sprint 边界（2 周），三个项目的 PM 需要检查：

- [ ] 本轮有哪些需求涉及跨项目 API？——PRD 中是否标注了 RPC 契约？
- [ ] YiAi 的 API 开发顺序是否正确？——是否按消费方的依赖紧急程度排序？
- [ ] Mock 数据是否已就绪？——格式是否与预期 API 返回一致？
- [ ] 上一轮的 API 变更是否在消费方已完成适配？——迁移窗口到期了吗？
- [ ] 联合演示的端到端场景是否定义清楚？——谁在什么时候演示什么？
- [ ] 有没有一个项目在"等"另一个项目？——等待是否必要？能否通过 Mock 或 Stub 绕开？

## 实践建议

1. **接口先行——API 定义在开发开始前完成评审**：不要"边开发边定 API"。API 的 module_name、method_name、parameters 格式——这三个事情必须在第一个 Sprint Day 1 之前定下来并文档化
2. **Mock 数据由提供方（YiAi）提供，而非消费方自行构造**：消费方自行构造的 Mock 数据大概率与实际 API 返回不一致。联调时发现不一致 = 返工。提供方给出 Mock 数据的边际成本是 30 分钟，消费方返工的边际成本是一整天
3. **向后兼容不是可选项——是硬约束**：YiAi API 变更必须保持向后兼容至少一个 Sprint 周期。不能在发布新 API 的同时废弃旧 API——给消费方 2 周的适配窗口
4. **三方联合演示是最诚实的进度报告**：PPT 可以说谎，端到端演示不能。如果一个 Sprint 结束时不能做联合演示，说明哪里出了问题——通常是某个依赖没有按时就绪。联合演示比站会更诚实
5. **跨项目 Bug 先定责再修复**：Bug 出现时先判断是哪个项目的问题——YiAi API 返回错误？YiVad 调用方式不对？参数不匹配是哪边的文档没跟上？先定责、再修复、最后补文档防止重复

## 反模式

| 反模式 | 为什么失败 | 正确做法 |
|---|---|---|
| 各项目按自己的 Sprint 节奏独立走——"我们做完了通知你们" | YiVad 做完了等 YiAi 的 API，YiAi 在做另一个和 YiVad 无关的需求。全仓库最贵的资源是"一个项目等另一个项目" | 涉及跨项目依赖的需求，三个项目的 Sprint 规划必须联合进行。依赖方的 API 是消费方的"阻塞项"，必须在依赖方 Sprint 中优先交付 |
| API 变更口头通知——"我在群里说了，你没看到" | 聊天记录 2 周后就沉了，新加入的同事永远不知道这个 API 为什么长这样 | API 变更必须文档化——更新 PRD 中的 RPC 契约定义，通知消费方 PM 并得到确认回复 |
| 联调时才第一次见到 API——"开发都是对着文档做的，联调就合一下" | 文档和现实总有差距。联调时发现的 API 不一致意味着至少一方需要返工——而返工时间是开发时间的 2 倍 | 联调不应该是"第一次见面"。API 提供方在开发过程中就应该提供可调用的 Sandbox，消费方每周至少联调一次 |
| Mock 数据太简单——"{code: 0, data: {}}" | 前端开发只能处理"快乐路径"——数据正常返回的情况。数据为空、超长、格式异常的情况完全没测试到 | Mock 数据至少覆盖三种情况：正常数据、空数据、错误返回。消费方在 Mock 阶段就能覆盖边界处理 |
| 跨项目需求只有一个 PM 在管——"我是 YiVad PM，YiAi 那边你们自己协调吧" | 没人对"端到端用户价值"负责——每个 PM 只对自己的项目负责，用户最终看到的完整流程没有 owner | 跨项目需求必须有一个"端到端 PM"——通常是最接近用户的消费方 PM（YiVad 或 YiPet），负责协调依赖和确保最终体验 |
