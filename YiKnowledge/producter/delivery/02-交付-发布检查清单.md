# 发布检查清单

> **适用场景**：每次面向用户的版本发布之前。不是所有的检查项每次都适用——根据版本的影响范围和风险级别调整。核心原则：**发布前发现的问题只需要修复，发布后发现的问题需要道歉**。

## 风险分级

不同规模的版本需要不同程度的发布检查：

| 风险级别 | 典型范围 | 触发条件 | 适用清单 |
|---|---|---|---|
| **低风险** | Bug 修复、文案更新、配置调整 | 不改变用户流程、不涉及数据迁移 | 仅运行核心检查（12 项） |
| **中风险** | 新增功能、UI 改版、性能优化 | 改变现有用户流程或新增页面 | 运行完整清单（全部 24 项） |
| **高风险** | 跨服务变更、数据迁移、API 破坏性变更 | 影响多个项目或涉及数据完整性 | 完整清单 + 灰度发布 + 回滚演练 |

## 一、发布前 7 天

### 功能完整性

- [ ] 所有 Must have 功能已开发完成并通过 code review。任何 Must have 功能未完成 = 不得发布
- [ ] 所有功能需求可追溯到 PRD 中的验收标准。每项验收标准有对应的测试用例通过记录
- [ ] 未完成的 Should have/Could have 功能已确认延后——所有干系人已知悉且同意
- [ ] API 变更（如有）已更新 RPC 契约文档，参数名称符合契约规范（`filter`/`target_file`/`cname`）

### 质量保障

- [ ] 全量测试用例通过（手动 + 自动化）。零失败不是目标——所有失败都有明确的"已知不阻塞"判定
- [ ] 新功能的边界条件已测试：空数据、超长输入、并发操作、网络中断恢复
- [ ] UX 检查清单已完成（参见 [01-体验-UX检查清单.md](../discovery/ux/01-体验-UX检查清单.md)）：加载/空/错误/边界状态已覆盖
- [ ] 无障碍检查（键盘操作、屏幕阅读器、颜色对比度）中风险以上版本必须完成

### 性能与稳定性

- [ ] P95 响应时间不劣于上一版本。如新增功能导致性能退化，必须有明确的缓解计划
- [ ] 内存泄漏检查通过。长时间运行（30 分钟+）无持续内存增长
- [ ] 错误率和崩溃率在可接受范围内。新增功能不应引入新的高频错误

### 数据与迁移

- [ ] 数据库变更（如有）的迁移脚本已测试且可回滚。迁移脚本必须在生产数据库的副本上验证
- [ ] 新增的数据字段有默认值，不影响旧数据的读取和展示
- [ ] 如有数据迁移，迁移耗时已评估且不超过维护窗口

### 监控与告警

- [ ] 新功能的监控指标已配置：功能使用率、错误率、P95 延迟。无监控上线 = 盲飞
- [ ] 告警阈值已设定，告警通知已关联到正确的负责人/群组

### 文档与沟通

- [ ] 版本 Changelog 已编写，面向用户的更新说明语言通俗（非技术术语）
- [ ] 内部干系人已知悉发布日期和影响范围
- [ ] YiKnowledge 中的相关文档已更新（如涉及工作流或架构变更）
- [ ] 如有破坏性变更，已提前通知所有消费方（YiVad、YiPet），并给出适配时间

## 二、发布当天

### 发布前确认

- [ ] 生产环境与预发布环境的配置差异已确认。环境变量、数据库连接串、第三方 API Key 必须逐一核对
- [ ] 回滚方案已确认可用：上一个版本的构建产物或镜像仍然可用，回滚步骤已演练或文档化
- [ ] 发布窗口已确认：避开通勤高峰期、用户活跃高峰期、团队大部分成员休假期间
- [ ] 发布人员已确认在岗，且有权执行发布和紧急回滚操作

### 灰度发布（中风险以上版本必须执行）

| 灰度阶段 | 流量比例 | 观察时长 | 通过条件 |
|---|---|---|---|
| 金丝雀 | 1-5% | ≥ 30 分钟 | 错误率不高于基线、无新增告警 |
| 小规模 | 10-25% | ≥ 2 小时 | 核心指标无退化、用户反馈无重大问题 |
| 半量 | 50% | ≥ 4 小时 | 所有指标正常、手动测试核心流程通过 |
| 全量 | 100% | — | 持续监控 |

**YrY 项目灰度建议**：
- YiVad 前端：通过 Rsbuild 多环境构建，先部署到预发布域名验证，再切换生产域名
- YiAi 后端：通过端口转发或 Nginx 分流实现灰度。模块级变更可在 RPC 路由层做 A/B
- YiPet 扩展：Chrome 扩展无传统灰度机制。替代方案——先在 Chrome Canary 中发布，确认稳定后提交正式版审核

### 全量发布后

- [ ] 核心用户流程手动验证通过：发布者本人在生产环境中走一遍最关键的 3 个流程
- [ ] 监控大盘确认所有指标正常（前 15 分钟持续关注）
- [ ] 发布通知已发送：团队群聊/邮件告知版本已上线，附带 Changelog 链接

## 三、发布后 48 小时

### 持续监控

| 时间点 | 检查内容 | 通过标准 |
|---|---|---|
| 发布后 1 小时 | 错误率、P95 延迟、核心流程可用 | 所有指标与发布前基线偏差 ≤ 10% |
| 发布后 4 小时 | 用户行为数据（新功能使用率、漏斗转化率） | 无异常下降，新功能有用户触达 |
| 发布后 24 小时 | 用户反馈（Bug 报告、客服工单、评价） | 无集中的负面反馈，bug 数量在预期范围内 |
| 发布后 48 小时 | 全面复盘判断 | 所有异常已分类处理（修复/延后/驳回） |

### 用户反馈处理

- [ ] 用户提交的 Bug 已分类分流：P0（立即修复）→ P1（48 小时内修复）→ P2（下个 Sprint）
- [ ] 用户反馈的体验问题已记录，排入下个版本的评审池
- [ ] 用户表扬（如有）收集并分享给团队——正向反馈和 bug 同等重要

## 发布复盘

每次发布后 48 小时内完成 15 分钟轻量复盘（中风险以上版本延长到 30 分钟）：

| 复盘问题 | 说明 |
|---|---|
| 这次发布有意外吗？ | 哪些事情没按计划走？根本原因是什么？ |
| 用户的第一反应是什么？ | 看数据（使用率）和看反馈（评价/bug）——两件事要分开看 |
| 如果再发布一次，我们会改变什么？ | 流程改进建议，不超过 3 条，落实到下一个版本的发布计划中 |
| 发布了什么没被使用的功能？ | 零使用的功能是信号——可能入口隐蔽或用户不觉得有用 |

## 回滚决策

回滚不是失败——带着已知严重问题继续运行才是失败。

### 立即回滚的条件

满足**任意一条**即触发回滚：
- 核心用户流程出现阻断性 Bug（用户无法完成主要任务）
- P0 错误率超过基线的 3 倍
- 数据完整性风险（数据错写、丢失、重复写入）
- 安全漏洞被发现

### 可以不回滚、热修复的情况

- 非核心流程的 Bug，有 workaround
- 影响 ≤ 5% 用户的 UI 显示问题
- P95 延迟轻微上升（≤ 20%），且无用户投诉

### 回滚后

- [ ] 回滚完成后通知所有干系人
- [ ] 24 小时内产出根因分析，确定修复计划
- [ ] 修复后的重新发布必须走完整检查清单（不能因为是"修复"就跳过）

## YrY 跨项目发布协调

当版本涉及多个 YrY 项目时（如 YiAi 新增 API + YiVad 和 YiPet 同时适配）：

1. **发布顺序**：YiAi 后端先发布（确保新 API 可用）→ YiVad 和 YiPet 后发布（使用新 API）
2. **向后兼容**：YiAi API 变更必须保持向后兼容至少一个版本周期，给消费方留出适配时间
3. **联合监控**：跨项目发布时，三方监控大盘同时关注——YiAi 的 API 错误率可能体现在 YiVad 或 YiPet 的用户投诉中
4. **联合回滚**：如果 YiAi 因新 API 问题需要回滚，YiVad 和 YiPet 的新版本也需要回滚（因为它们依赖新 API）

## 反模式

| 反模式 | 为什么失败 | 正确做法 |
|---|---|---|
| 周五下午 5 点发布 | 团队下班后无人处理问题；用户周末遇到问题无处反馈 | 周二到周四上午发布。给团队足够的白天时间处理问题 |
| "这个版本很小，不用走清单" | 小改动引发大故障。80% 的线上事故来自"小改动" | 至少运行核心检查（12 项）。清单的边际成本是 5 分钟，事故的边际成本无法估量 |
| 发布后不监控直接下班 | 问题在夜间发酵，第二天面对的是愤怒的用户和堆积的 bug | 发布后至少监控 1 小时，确认指标正常后再离开 |
| 没有回滚方案就发布 | 出了问题束手无策，用户受影响时间从分钟变成小时 | 每次发布前确认：上一个版本是否可在一键/一条命令内恢复 |
| 跳过灰度直接全量 | 问题暴露时已影响 100% 用户，回滚也无法恢复已经造成的影响 | 中风险以上版本必须灰度。灰度不是"谨慎"，是"最小的爆炸半径" |
| 只在开发环境测试 | 生产环境的配置、数据量、并发压力无法在开发环境复现 | 预发布环境（staging）必须与生产环境配置一致。至少在 staging 上完成一轮全量回归 |
