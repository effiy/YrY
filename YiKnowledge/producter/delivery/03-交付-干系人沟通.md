# 干系人沟通指南

> **适用场景**：当需要向不同类型的人传达同一件事但需要不同角度时。PM 的核心工作不是画画原型、排排优先级——是确保所有相关方对"我们在做什么、为什么、进展如何"有清晰、一致的理解。

## 核心原则

**干系人管理的目标不是让所有人开心，而是让没有人感到意外。** 坏消息提前说、好消息及时说、不确定的不瞎说。

沟通的黄金公式：

```
信息 = 事实（发生了什么） + 影响（这意味着什么） + 下一步（接下来做什么）
```

缺少任何一个要素，接收方会自己脑补——而脑补的内容通常比现实更糟。

## 干系人地图

不是所有干系人都需要同等程度的沟通。用影响力/兴趣矩阵决定沟通策略：

```
        高
        │
  影响力 │  满足需求          紧密合作
        │  （定期汇报）       （深度参与）
        │
        │  最低维护          持续告知
        │  （有变化再通知）    （主动同步）
        │
        低──────────────────────高
                兴趣程度
```

| 象限 | 沟通策略 | 典型角色 | YrY 对应 |
|---|---|---|---|
| **紧密合作**（高影响力+高兴趣） | 深度参与决策、周度同步、重大变更即时沟通 | 直属技术负责人、核心工程师 | YiAi 的 RAG 模块负责人、YiVad 的前端负责人 |
| **满足需求**（高影响力+低兴趣） | 月度摘要、关键节点同步、不打扰日常 | 高管、项目出资人 | YrY 项目决策者 |
| **持续告知**（低影响力+高兴趣） | 周度更新、主动同步进展、征求意见 | 设计师、QA、关联团队 | YiPet 团队的 PM（如果你的主要项目是 YiVad） |
| **最低维护**（低影响力+低兴趣） | 季度通报、重大变化通知 | 非紧密协作的同事 | — |

## 信息分层

不同层级的干系人需要不同粒度的信息：

| 层级 | 适合角色 | 信息粒度 | 频率 | 格式 |
|---|---|---|---|---|
| **战略层** | 高管、决策者 | "我们解决了什么问题、对业务指标有何影响" | 月度 | 一页摘要，3-5 条要点 |
| **执行层** | 技术负责人、协作团队 PM | "当前进展、阻塞项、下一步计划" | 周度 | 结构化更新（进展/阻塞/计划/风险 四段式） |
| **操作层** | 工程师、设计师 | "具体任务状态、技术决策、验收标准变更" | 日度/站会 | 站会 + 项目管理工具 |

**关键规则**：不要给高管站会级别的细节（"昨天我把按钮从 24px 改成了 28px"），也不要给工程师战略层面的模糊描述（"我们要提升用户体验"）。

## 四种核心沟通场景

### 1. 周度进展更新

发给：技术负责人 + 协作团队 PM。

**结构化模板**：

```
本周进展（用过去式，说结果）
- Agent 报告生成接入 YiKnowledge RAG 检索，端到端流程已跑通
- 知识树入口从二级菜单提到工具栏首位，等待可用性测试

下周计划（用将来式，说重点）
- 报告生成错误处理：文档检索失败时的降级方案
- 开始准备 Sprint 评审演示

阻塞项（说问题 + 影响 + 需要的帮助）
- Ollama 模型加载偶尔超时（影响：报告生成的 P95 延迟不稳定）
  需要：YiAi 团队协助排查加载超时根因

风险（可能出问题但还没发生的）
- 如果多语言输出依赖的翻译模型本周不能就绪，可能影响下周的多语言输出开发
```

**原则**：
- 先说好消息还是坏消息？**先说最重要的**，不管好坏
- 阻塞项必须有"需要什么帮助"——只说"这里有阻塞"不提供解决方案，等于把问题丢给别人

### 2. 月度战略同步

发给：高管、决策者。

**结构**：一页纸，不超过 5 条要点，每条 ≤ 3 句话。

```
本月要点：
1. Agent 报告生成 MVP 进入内部测试
   — 3 名售后工程师试用，报告生成时间从 4-6 小时降到 12 分钟
   — 下月目标：扩展到 10 人测试、增加多语言输出

2. 知识底座使用率从 15% 提升到 28%
   — 入口优化（一级工具栏）是主要驱动因素
   — 距离 40% 的目标还有差距，下月计划加入首次使用引导

3. 需要决策：Agent 多智能体分工的架构方案
   — 两个方案（单 Agent 多功能 vs 多 Agent 分工）各有优劣
   — 需要技术评审决策，预计下月带来提案

指标趋势：
- 北极星指标：↑ 8%
- 用户满意度：→ 持平
- 系统可用性：↓ 2%（一次 Ollama 超时事件）

下月重点：
- Agent 多语言输出 + 内部测试扩大到 10 人
- 知识底座首次使用引导流程
```

**原则**：
- 高管最关心的是：事情在朝正确的方向走吗？有没有需要我介入解决的问题？
- 永远附带数据趋势——高管的判断建立在趋势上，不是单点数值上
- "需要决策"是高管最愿意看到的章节——你在请求方向，而非汇报问题

### 3. 说"不"——范围蔓延时的拒绝

当干系人要求在当前版本中加入新功能时，说"不"的方式决定了对方是理解还是不满。

**错误说法**："不行，我们现在做不了这个。"——对方听到的是拒绝，而非理由。

**正确框架**：

```
确认需求 + 解释约束 + 提供替代方案 + 明确下一步
```

**示例**：

> "我理解审批工作流对售后主管很重要（确认需求）。当前版本的范围已经锁定——Agent 报告生成的 MVP 功能占据了全部开发容量（解释约束）。我可以把审批工作流排入下个版本的优先评估项，并在下周一之前给你一个大致的时间窗口（替代方案）。如果你认为审批工作流的紧迫度高于当前版本的其他功能，我们可以安排一次优先级评审来讨论（明确下一步）。"

**关键诀窍**：永远不要说"不"之后没有下文。拒绝了一个请求的同时，必须给出一个替代路径——即使那个路径是"下个版本重新评估"。

### 4. 传递延迟消息

延迟是最难沟通的消息，因为干系人听到的不是"客观原因"而是"你们搞砸了"。

**错误做法**：最后一刻才说、找借口、模糊新时间。

**正确做法**：

```
1. 尽早说——有延迟迹象时就说，别等到截止日期
2. 先说影响——"我们预计 Agent 多语言输出功能将延迟 2 周"
3. 说原因——不找借口，但说明根因："Ollama 模型加载超时问题比预期复杂，需要架构调整"
4. 说新计划——"新的预计完成时间是 X，这是到达那里的路径"
5. 说教训——"我们学到了什么，下次如何避免"（不要说"下次不会了"——说具体的流程改进）
```

**延迟沟通检查清单**：
- [ ] 在预计延迟发生前至少 48 小时通知干系人
- [ ] 解释了为什么（不找借口，说根因）
- [ ] 给出了新的时间线和到达路径
- [ ] 说明了正在做什么来减少延迟的影响
- [ ] 识别了流程改进点，防止重复发生

## YrY 特定的沟通场景

### 跨项目 API 变更通知

当 YiAi 的 API 变更即将影响 YiVad/YiPet 时：

**通知模板**：

```
变更类型：API 变更 / 新增 API / 废弃 API
影响项目：YiVad / YiPet / 两者
变更内容：<module_name.method_name> 的参数 X 从可选变为必填
迁移窗口：<日期>之前完成适配
不迁移的后果：<日期>之后旧格式请求将返回 1001 错误
联系人：<谁可以回答技术问题>
```

### 跨项目分支桥接

当 YiPet 的功能依赖 YiVad 的页面时（如 session key 桥接），需要确保双方的 PM 和开发者在开发前已对齐接口约定。

**对齐检查清单**：
- [ ] 双方 PM 已确认功能范围和对接口约定
- [ ] 桥接使用的 session key 或参数格式已文档化
- [ ] 双方的开发和测试时间线已对齐（YiVad 的页面必须在前，YiPet 的跳转在后）

## 沟通节奏总览

| 频率 | 沟通内容 | 受众 | 渠道 |
|---|---|---|---|
| 日度 | 站会：昨天做了什么、今天要做什么、有什么阻碍 | 开发团队 | 站会/即时消息 |
| 周度 | 进展更新：本周完成、下周计划、阻塞项、风险 | 技术负责人 + 协作团队 PM | 书面（即时消息/邮件）+ 可选口头同步 |
| 月度 | 战略同步：关键成果、指标趋势、需决策项 | 高管、决策者 | 一页摘要 + 可选会议 |
| 季度 | 路线图评审：Now 回顾 + Next/Later 重新规划 | 所有干系人 | 评审会（60 分钟） |

## 实践建议

1. **过度沟通好于沟通不足**：干系人抱怨"信息太多"的频率远低于抱怨"我不知道发生了什么"
2. **书面记录口头决策**：任何在口头沟通中达成的决策，24 小时内发一条书面确认。口头决策是最容易产生"我以为你说的是..."歧义的来源
3. **坏消息亲自说，不要通过文档**：延迟、范围缩减、资源不足——这些消息需要对话，不是冷冰冰的文档。先口头沟通，再书面跟进记录
4. **统一信息来源**：团队应该知道去哪里看最新进展。YiVad 的项目管理页面、YiKnowledge 中的 PRD 文件——选一个作为权威信息源，所有沟通引用它
5. **干系人风格不同，调整你的风格**：有人要细节（给数据），有人要结论（给要点），有人要过程（给叙事）。了解你的干系人偏好哪种风格

## 反模式

| 反模式 | 为什么失败 | 正确做法 |
|---|---|---|
| 报喜不报忧——只说好消息，隐藏问题 | 问题在被发现时通常还小，被隐瞒 2 周后变成危机。被发现时信任也一并崩塌 | 坏消息尽早、亲自、面对面沟通。附带：原因 + 新计划 + 教训 |
| 给所有人都发同样的更新——信息颗粒度一刀切 | 高管收到技术细节轰炸看不懂，工程师收到战略模糊描述没价值 | 信息分层：战略层/执行层/操作层，三层不同的颗粒度和频率 |
| 沟通只在出了问题之后——平时沉默、出事炸群 | 干系人只在收到坏消息时才听到你的声音，形成了负面条件反射 | 建立定期沟通节奏（周度 + 月度）。好消息也值得同步——让干系人对你的声音不只有负面联想 |
| 口头决策不书面确认——"会上说了就算" | 两周后双方对"会上说了什么"有完全不同的记忆。无法追溯 | 会议结束后 24 小时内发一条书面纪要："今天讨论的结论是 X，下一步是 Y。如有补充请在 24 小时内回复。" |
| 过多"正在推进中"——进展描述空洞无物 | "Agent 功能正在推进中"说了等于没说——是卡住了还是在路上？ | 用完成时描述进展："Agent 报告生成端到端流程已跑通" > "Agent 功能正在推进中" |
