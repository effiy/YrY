# Beta 测试与早期访问指南

> **适用场景**：在新功能首次面向真实用户发布之前。Beta 测试的核心价值不是"找 Bug"（那是 QA 做的事），而是回答三个问题：**用户会主动用吗？用了之后行为变了吗？有什么意外的使用方式？**

## Beta 测试解决什么问题

即使内部测试全部通过，真实用户的行为仍然会让你意外：
- 用户在你想不到的场景下使用功能
- 用户按你意想不到的方式理解界面文案
- 用户的数据量、网络环境、设备组合超出了你的测试范围

Beta 测试是用最少量的用户曝光，换取最大量的"意外发现"。

## 三阶段测试模型

| 阶段 | 参与者 | 人数 | 目标 | 典型时长 |
|---|---|---|---|---|
| **内测（Alpha）** | 内部团队成员 | 5-15 人 | 验证核心流程是否跑通、找明显的 Bug | 1-2 周 |
| **封闭测试（Closed Beta）** | 受邀的友好用户 | 15-50 人 | 验证功能价值、收集使用反馈、发现边缘场景 | 2-4 周 |
| **开放测试（Open Beta）** | 自愿报名的用户 | 50-200+ 人 | 在更广泛场景下验证稳定性、为全量发布积累信心 | 2-4 周 |

### 何时跳过某些阶段

| 条件 | 处理方式 |
|---|---|
| 功能极小——单页面文案变更、配置调整 | 跳过全部 Beta，直接发布 + 发布后监控 |
| 用户量极小的内部工具（如 YiVad 管理后台） | Alpha = 全量。内部用户就是你的全部用户 |
| Chrome 扩展（如 YiPet）| Alpha（内部）+ Closed Beta（外部友好用户），无 Open Beta（Chrome Store 审核周期替代了 Open Beta） |

## 内测（Alpha）— 内部验证

### 目标

不是验证"用户喜不喜欢"——内部团队的反馈不能代表真实用户。Alpha 验证的是：**功能在技术上能跑通，且核心流程没有阻断性 Bug**。

### 参与者

- PM（功能设计者）
- 开发工程师（功能实现者）
- 团队内 3-5 名不直接参与开发的同事（"新鲜眼睛"——没有参与开发的人更容易发现意料之外的问题）
- 如适用，1-2 名真实的友好用户（"design partner"）

### Alpha 检查清单

- [ ] 核心用户流程端到端跑通——从头到尾 0 阻断
- [ ] 边界数据测试通过：空数据、超长输入、并发操作、网络中断后恢复
- [ ] 错误状态覆盖：API 不可用、超时、权限不足时用户看到的信息正确且可行动
- [ ] 所有验收标准在真实环境中通过（不只是开发环境）

### Alpha 中"说不"的信号

以下任一情况出现，说明不应该进入 Closed Beta：

- 核心用户流程在任何参与者的测试中出现阻断——无法完成流程
- 同一类 Bug 在 3 个以上的独立测试中被发现——说明问题可能是系统性的
- 产品核心假设在内部测试中就被证伪——"我们觉得用户会 X"但内部测试发现根本做不到 X

## 封闭测试（Closed Beta）— 受邀验证

### 目标

真实用户验证功能价值。回答：**用户在真实场景下会主动使用这个功能吗？他们的行为符合预期吗？**

### 如何选择参与者

| 标准 | 为什么重要 |
|---|---|
| 目标用户的代表——有真实的使用场景 | 脱离了真实场景的反馈没有参考价值 |
| 愿意提供反馈——不是"试试就算了"的人 | Beta 的核心产出是反馈，不是使用数据 |
| 不会因为遇到 Bug 就永久离开——对产品有基本信任 | Beta 阶段 Bug 多，如果参与者是潜在付费用户，Beta 反而会赶走他们 |
| 多样性——不要都是同一类用户 | 不同角色的用户使用方式不同，5 个同类用户 = 1 个用户 × 5 |

### 招募渠道

| 渠道 | 适合 | 不适合 |
|---|---|---|
| 现有活跃用户（通过产品内提示或邮件邀请） | 大多数功能 | 对"可能破坏现有工作流"的功能（如 UI 大改版） |
| 用户反馈中表达过需求的人 | 功能直接对应已知需求 | — |
| 内部干系人推荐的友好用户 | 需要快速招募时 | 避免只用干系人的朋友——他们的反馈倾向于更"礼貌" |
| 社交媒体/社群 | 面向开发者的工具 | 面向非技术用户的工具 |

### 激励

Beta 参与者付出了时间和容忍 Bug 的风险，他们应该得到回报：

| 激励类型 | 适合场景 | 示例 |
|---|---|---|
| 提前使用特权 | 新功能有吸引力 | "你将是第一批使用 Agent 报告生成功能的人" |
| 直接影响产品方向 | 参与者关心产品 | "你的反馈将直接决定这个功能的优先级" |
| 物质激励 | 需要快速大量招募 | 50-100 元礼品卡 |

### 反馈收集

**结构化反馈 vs 开放式反馈——两者都需要。**

| 方式 | 工具/渠道 | 能收集到什么 | 频率 |
|---|---|---|---|
| 关键行为埋点 | 产品内埋点 | 用户实际做了什么（vs. 他们说做了什么） | 持续 |
| 反馈表单 | Google Form / 产品内嵌入 | 结构化的满意度评分和建议 | 每周发送一次 |
| 1:1 访谈 | 视频通话 20-30 分钟 | 深度的使用体验、未说出口的困惑 | Beta 中期至少 5 场 |
| 即时反馈通道 | 微信群/Slack 频道 | 即时 Bug 报告、及时的使用感受 | 持续 |

### Beta 期间的处理节奏

```
Beta 开始
  │
  ├─ 第 1 周：密集观察
  │   不看数据，看行为——用户最先做了什么？在哪卡住了？
  │
  ├─ 第 2-3 周：深度访谈
  │   访谈 5-8 名参与者，了解"为什么"背后的"为什么"
  │
  └─ 第 4 周：判断毕业
      数据 + 反馈 → 通过（准备发布）/ 有条件通过（修几个关键问题后发布）/ 不通过（回炉重做）
```

## 开放测试（Open Beta）— 规模验证

### 目标

在更广泛、更多样的用户场景下验证稳定性。发现封闭测试中因为参与者同质性而遗漏的边缘场景。

### 与封闭测试的区别

| 维度 | 封闭测试 | 开放测试 |
|---|---|---|
| 用户获取 | 主动邀请、筛选 | 用户自愿报名 |
| 用户多样性 | 受限于招募渠道 | 自然多样化 |
| Bug 容忍度 | 高——参与者知道是 Beta | 中——部分用户可能会把 Beta 当正式功能 |
| 反馈质量 | 高——受邀者倾向于提供详细反馈 | 中——自愿者反馈质量参差不齐 |

### 开放测试的准入标准

进入开放测试前必须满足：
- [ ] 封闭测试中无阻断性 Bug 残留
- [ ] 核心用户流程的使用完成率 ≥ 80%
- [ ] 封闭测试参与者中，≥ 60% 表示"会继续使用这个功能"
- [ ] 如果功能涉及数据，回滚和数据恢复方案已验证

## Beta 毕业标准

Beta 结束、可以全量发布的判断标准：

| 信号 | 通过 | 有条件通过 | 不通过 |
|---|---|---|---|
| 使用频率 | ≥ 60% 的 Beta 用户每周使用 | 30-59% | < 30% |
| 任务完成率 | ≥ 80% 的尝试可以成功完成 | 60-79% | < 60% |
| 用户满意度 | ≥ 70% 表示"会推荐" | 50-69% | < 50% |
| Bug 密度 | 新 Bug 发现速率持续下降并在最后一周无 P0/P1 | P1 Bug 仍偶有发现 | P0 Bug 持续出现 |
| 自发推荐 | 有 Beta 用户在没有被要求的情况下主动推荐 | — | — |

**判断规则**：
- 全部"通过" → 全量发布
- 1-2 项"有条件通过" + 无"不通过" → 修复关键问题后发布，不需要重新 Beta
- 任何一项"不通过" → 回炉——问题不在执行，在产品方向。回到发现阶段重新审视

## YrY 各项目的 Beta 测试场景

### YiVad — Agent 报告生成功能

| 项目 | 说明 |
|---|---|
| Alpha | 内部 5 人（PM + 2 名工程师 + 2 名非开发同事）用真实案例数据测试。重点验证：报告格式正确性、生成速度、编辑保存流程 |
| Closed Beta | 邀请 10-15 名售后工程师（从现有 YiVad 活跃用户中筛选）。提供微信反馈群 + 每周 1 次反馈表单 |
| 毕业条件 | 60%+ 用户每周使用、报告编辑次数 ≤ 2/份、用户满意度 ≥ 70% |
| 特殊考量 | 报告内容涉及真实案例数据——Beta 参与者需签署数据保密协议。生成的报告不得外传 |

### YiPet — 知识底座首次使用引导

| 项目 | 说明 |
|---|---|
| Alpha | 内部 8 人在 Chrome 正式版 + Canary 中测试引导流程。验证：引导弹窗不遮挡核心交互、引导后行为符合预期 |
| Closed Beta | 邀请 20 名现有 YiPet 用户（从从未使用过知识底座的用户中筛选）。A/B 分组：10 人收到引导 vs 10 人不收到 |
| 毕业条件 | 引导组知识底座首周使用率 ≥ 30%（vs 无引导组 10%）、引导不被用户主动关闭（关闭率 < 20%） |
| 特殊考量 | Chrome 扩展无传统灰度——需要手动打包不同版本给不同组。引导太激进了可能导致用户关闭扩展 |

### YiAi — 新 API 端点

| 项目 | 说明 |
|---|---|
| Alpha | YiVad 和 YiPet 的开发者在预发布环境中调用新 API。验证：参数格式、返回结构、错误码符合 RPC 契约 |
| Closed Beta | 和 Alpha 合并——API 的消费者就是内部团队，没有外部用户 |
| 毕业条件 | 所有 RPC 契约验收标准通过、P95 响应时间不劣于同类 API、YiVad 和 YiPet 适配完成 |
| 特殊考量 | API 变更必须向后兼容——旧版本 YiVad/YiPet 调用新 API 不能报错。Beta 期间同时运行旧版和新版客户端 |

## 实践建议

1. **Beta 不是 QA 的替代品**：进入 Beta 之前，功能应该已经完全测试通过。Beta 找的是"用户行为意外"而非"代码 Bug"——那是 QA 在 Alpha 之前就该找完的
2. **Beta 用户数不是越多越好**：15 个能给出深度反馈的用户 > 100 个沉默的用户。Beta 的质量取决于反馈深度，而非参与人数
3. **反馈必须闭环**：Beta 参与者花了时间给你反馈，你必须告诉他们"你的反馈导致了什么改变"——即使改变是"我们评估后决定不做"。反馈不被回应 = 下次没人给你反馈
4. **Beta 发现的严重问题不应感到羞耻**：Beta 的目的就是发现问题。如果在 Beta 中没有发现任何需要改的地方，说明要么 Beta 参与者在敷衍你，要么你招募的用户不对

## 反模式

| 反模式 | 为什么失败 | 正确做法 |
|---|---|---|
| Beta 只是为了"看起来专业"——走了个流程但没收集有效反馈 | Beta 结束了，产品没有任何改动就发布了。Beta 变成了形式主义 | 预设 Beta 要回答的 3 个核心问题。如果在 Beta 中没有得到任何新信息，检查你的参与者是否选对了、问题是否问对了 |
| 只找"友好用户"——全是有利益关系的内部人员 | 反馈过于礼貌、全是好评。真用户上线后 Bug 和投诉涌来 | 至少 50% 的 Beta 参与者与团队没有个人关系。批评性的反馈才是 Beta 最值钱的产出 |
| Beta 周期太长——"我们再测一个月吧，感觉还不够" | 功能拖在 Beta 里不敢发布，市场窗口过去。Beta 参与者也在流失 | Beta 预设结束日期和毕业标准。到时间就做"通过/有条件通过/不通过"的判断，不要无限延期 |
| 忽视沉默的 Beta 用户——只听取积极反馈的参与者 | 沉默的 Beta 用户是最重要的信号——他们可能觉得功能没用但不好意思说 | 主动联系沉默的 Beta 用户，问"为什么不怎么用了？"。沉默反馈本身就是数据 |
| Beta 参与者下结论——"Beta 用户提出了 5 个建议，我们全做" | Beta 用户的建议反映的是他们的个人偏好，不一定是大多数用户的需求。按照个别 Beta 用户的要求改产品 = 为一个人做产品 | 归纳多个 Beta 用户的共性反馈——3 个以上独立用户提到的同一个痛点才是真痛点 |
