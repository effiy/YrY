# 产品路线图设计

> **适用场景**：当需要向团队和干系人传达产品方向时。路线图是沟通工具，不是项目计划——它传递的是"我们要去哪里、为什么、大概什么时候"，而非"我们精确到周的交付承诺"。

## 路线图是什么、不是什么

| 路线图是 | 路线图不是 |
|---|---|
| 战略意图的可视化表达 | 带日期的功能清单 |
| 传达方向和优先级 | 承诺"3 月 15 日一定上线 X" |
| 引发对话和讨论的工具 | 单方面下达的指令 |
| 随时间演化的活文档 | 年初做完管一年的静态文件 |
| 聚焦要解决的问题 | 列举要做的功能 |

**一句话定义**：路线图是对"我们接下来打算解决什么问题、按什么优先级、大概什么时候"的当前最佳理解。

## 两种路线图格式

### 时间线路线图（传统格式）

```
Q1                 Q2                 Q3                 Q4
────               ────               ────               ────
Agent 报告生成      多语言输出          审批工作流          外部系统对接
知识底座 MVP        知识树搜索          多文件选择          离线知识缓存
```

**优点**：直观、干系人一看就懂、适合对外展示。

**致命缺陷**：时间线路线图被干系人当作承诺——"你说了 Q2 上线的，怎么还没好？"当产品方向因用户反馈而调整时，时间线上的每一项都在质问"为什么变了"。

**适用场景**：仅用于对外/对客户的宏观方向沟通（且必须标注"路线图反映当前计划，可能因用户反馈和市场变化而调整"）。

### Now/Next/Later 路线图（推荐格式）

```
Now（本季度）             Next（下季度）            Later（未来）
────────                 ────────                  ──────
Agent 报告生成 MVP        多语言输出                 审批工作流
  目标：售后工程师能在      目标：服务海外客户          目标：多人协作审核
  15 分钟内生成草稿
                         知识树搜索                  外部系统对接
知识底座端到端打通          目标：快速定位知识文件       目标：与 CRM 数据联动
  目标：浏览→选择→提问
  →查看流程完整可用
```

**优点**：
- Now 是承诺——当前季度全力交付的目标
- Next 是方向——我们已经做过初步调研，大概率做，但如果 Now 阶段发现更重要的事会调整
- Later 是想法——值得探索，但不承诺时间

**适用场景**：内部团队对齐、季度规划评审。推荐 YrY 所有项目默认使用此格式。

## 主题式路线图

### 为什么主题优于功能列表

功能列表路线图的问题是：它只说了"做什么"，没说"为什么"。团队盲目执行功能，却忘了这些功能要解决什么问题。

**主题式路线图将功能组织为要解决的问题，而非要交付的东西。**

| 功能列表式（差） | 主题式（好） |
|---|---|
| Q2：添加搜索框、文件树展开、面包屑导航 | Q2 主题：用户能在 3 秒内找到任何知识文件 |
| Q2：多语言 API、翻译模块、语言检测 | Q2 主题：非中文用户能无障碍使用核心功能 |

主题的好处：
- 给团队解决问题的自主权——"让用户 3 秒内找到文件"可能有 5 种实现方式，团队可以选择最优解
- 干系人理解"为什么"——不只是"我们要做搜索框"，而是"用户找不到文件，所以我们要解决发现性"
- 主题更稳定——具体功能可能因技术约束而调整，但"让用户快速找到文件"这个目标不变

### 如何确定主题

1. **列出用户的核心痛点**（来自用户研究、数据分析、用户反馈）
2. **将相关痛点聚合成主题**：每个主题解决一类问题
3. **为主题设定成功指标**：完成后如何知道成功了？
4. **按影响力排序主题**：RICE 评分适用——不是排功能，是排主题

### YrY 主题式路线图示例

**YiVad 路线图主题：**

| 时段 | 主题 | 解决的用户问题 | 成功指标 |
|---|---|---|---|
| Now | **从查找变管理** — 项目管理不靠记忆 | 管理员无法快速了解项目全局状态 | 项目仪表盘：问题分布、进度、阻塞项一目了然 |
| Next | **从数据变洞察** — AI 主动发现问题 | 管理员靠手动检查发现异常，滞后严重 | 智能提醒：过期未处理问题自动通知，减少遗漏 50% |
| Later | **从工具变伙伴** — AI 辅助项目管理决策 | 项目规划依赖 PM 个人经验，缺乏数据支撑 | Agent 辅助 Sprint 规划建议 |

**YiPet 路线图主题：**

| 时段 | 主题 | 解决的用户问题 | 成功指标 |
|---|---|---|---|
| Now | **知识底座无处不在** — 任意网页都能基于 YrY 知识提问 | 知识底座功能入口太深，使用率 15% | 知识底座会话占比从 15% → 40% |
| Next | **从问答变助手** — AI 不只是回答问题 | 用户除了提问不知道 AI 还能做什么 | 主动建议：选中文字即可查知识、翻译、总结 |
| Later | **从独立变连接** — YiPet 成为 YrY 生态的入口 | YiPet 与 YiVad 数据不互通 | 在 YiPet 中查看 YiVad 项目状态、创建 Bug |

## 路线图更新节奏

| 频率 | 活动 | 参与者 | 产出 |
|---|---|---|---|
| 每周 | 检查 Now 的目标进度是否有阻塞 | PM + 技术负责人 | 无阻塞记录，阻塞项升级 |
| 每月 | 回顾 Now 的交付进度、检查 Next 是否仍然合理 | PM + 团队 | 更新后的 Next 列，新增/移除条目 |
| 每季度 | 完整的路线图评审——Now 变回顾、Next 变 Now、重新规划 Next 和 Later | PM + 团队 + 干系人 | 新季度的完整 Now/Next/Later 路线图 |

## 与干系人对齐路线图

路线图失败的头号原因不是"做不完"，而是"做完了但干系人说这不是他们想要的"。对齐必须在开始之前。

### 路线图评审会议程（60 分钟）

| 环节 | 时长 | 内容 |
|---|---|---|
| 背景回顾 | 5 分钟 | 上次路线图评审后，市场/用户/竞品有什么变化？ |
| 候选主题介绍 | 15 分钟 | PM 介绍候选主题：要解决什么问题、为什么现在做 |
| 干系人输入 | 20 分钟 | 干系人补充：有没有 PM 不知道的信息（客户投诉、合规要求、技术债务）会改变优先级 |
| 容量现实检查 | 10 分钟 | 技术负责人评估：Now 里的主题在容量上是否可行 |
| 达成共识 | 10 分钟 | 确认 Now/Next/Later 的最终排列，明确各自的成功标准 |

### 不同干系人关注路线图的不同部分

| 干系人 | 他们关心 | 给他们看 | 不给他们看 |
|---|---|---|---|
| 高管/投资者 | 方向是否正确、资源是否用在刀刃上 | Now/Next/Later 主题 + 成功指标 | 具体功能细节、Sprint 任务拆解 |
| 工程师 | 接下来要做什么、为什么这个优先级 | Now 列的主题 + 用户故事预览 | Later 列的远期模糊想法 |
| 设计师 | 哪些主题需要设计支持、时间窗口多大 | Now 和 Next 列 + 设计需求说明 | Sprint 级别的容量规划细节 |
| 销售/客服 | 什么时候能告诉客户 X 功能可用 | 仅 Now 列（且标注"基于当前计划"） | Next 和 Later 列——不应该作为对客户的承诺 |

## YrY 跨项目路线图协调

YrY 有三个产品共享一个后端，路线图必须在项目间对齐：

```
YiAi（后端）
  Now: RAG 混合检索优化、Agent 循环稳定化
  Next: 多厂商 LLM 支持、检索缓存
  Later: 多智能体协作、知识图谱增强检索
  
  影响 ↓
  
YiVad（管理后台）                    YiPet（浏览器扩展）
  Now: Agent 报告生成 MVP              Now: 知识底座入口优化
  Next: 项目仪表盘、智能提醒           Next: 选中文字即提问
  Later: Agent 辅助规划                Later: YiVad 数据连通
```

**协调规则**：
- YiAi 的 Now 必须在 YiVad/YiPet 依赖它之前完成。如果 YiVad 的 Now 依赖 YiAi 的新 API，YiAi 的新 API 必须在同一季度或更早交付
- 季度路线图评审时，三个项目的 PM 必须先对齐依赖关系，再各自规划

## 实践建议

1. **路线图的受众决定格式**：给团队看用 Now/Next/Later（强调方向），给外部看用时间线（标注免责声明）
2. **主题不超过 3 个/时段**：超过 3 个主题意味着没有真正的优先级。团队一次只能聚焦 2-3 个主题
3. **Later 列是观点的停车场**：好的想法但暂时没资源做的事放 Later。它不会消失，每季度重新审视
4. **路线图是承诺的程度不同**：Now 是承诺（我们全力交付），Next 是高置信度意图（大概率做），Later 是探索方向（可能做也可能永远不做）
5. **路线图被批评是正常的**：有人觉得某件事应该放在 Now 而不是 Later——这正是路线图的价值。它引发了优先级对话

## 反模式

| 反模式 | 为什么失败 | 正确做法 |
|---|---|---|
| 路线图是带日期的功能清单——"Q2 我们要做功能 A、B、C、D、E" | 没人读日期以外的内容；任何延迟都被视为失信 | 用主题代替功能清单，用 Now/Next/Later 代替精确日期 |
| 路线图全年不变——年初做完就锁定了 | 市场在变、用户在变、竞品在变——6 个月的路线图在 3 个月时已严重过时 | 季度更新路线图。Later 列可以每季度大改，Next 列微调，Now 列不变 |
| PM 独自画路线图——闭门造车然后宣布 | 工程师说做不完、设计师没参与、干系人不认可 | 路线图是集体对齐的结果。PM 负责提议，团队负责确认可行性，干系人负责确认方向 |
| Later 列是垃圾场——什么都往里面丢，从不清理 | Later 列有 50 个想法，每季度还要往里加新的。团队不再相信 Later 列的东西真的会被考虑 | Later 列最多保留 10 个候选主题。超过 1 年未活动的主题从 Later 中删除 |
| 路线图没有成功指标——"我们要做 X 功能"成功了没有？ | 不知道。做了就是成功？用户用了才算成功 | 每个 Now 主题必须有一个可衡量的成功指标。"做完了"不等于"做成了" |
