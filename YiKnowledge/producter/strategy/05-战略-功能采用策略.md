# 功能采用策略

> **适用场景**：每次重要功能上线之后。发布让功能"可用"，采用让功能"被用"——这是两件完全不同的事。大多数产品团队的精力 90% 花在"怎么做出来"，10% 花在"怎么让人用"——这个比例应该反过来。

## 发布 ≠ 采用

| 发布（Release）意味着 | 采用（Adoption）意味着 |
|---|---|
| 功能在代码层面可用 | 用户发现了这个功能 |
| 测试用例全部通过 | 用户理解了它的价值 |
| 发布检查清单全部打勾 | 用户在真实场景中主动使用 |
| 你可以宣布"上线了" | 用户养成了使用习惯 |

**关键数据**：大多数新功能在发布后 30 天内，采用率不超过目标用户群的 20%。不是因为功能不好——是因为用户不知道它存在、不理解它的价值、或者没有在正确的场景下遇到它。

## 采用漏斗

```
知晓（Awareness）   100% 知道这个功能存在
    ↓
理解（Understanding）  理解了能帮我解决什么问题
    ↓
尝试（Trial）           第一次使用
    ↓
习惯（Habit）           在合适的场景下自然想到使用
    ↓
传播（Advocacy）        主动推荐给别人
```

### 漏斗各阶段的推动手段

| 阶段 | 用户在想什么 | 推动手段 |
|---|---|---|
| **知晓** | "有这个功能吗？" | 发布公告、Changelog、产品内提示、首次使用引导 |
| **理解** | "对我有什么用？" | 场景化示例、对比"有 vs 没有"的效果、用户故事 |
| **尝试** | "真的像说的那么好吗？" | 低门槛首次体验、预填充数据、Demo 模式 |
| **习惯** | "我又遇到了那个场景——想起来了" | 场景触发、快捷入口、使用反馈强化 |
| **传播** | "我同事也需要这个" | 分享机制、邀请协作、成果展示 |

**关键洞察**：每跨越一个阶段，用户主动性的比例大幅上升。知晓→理解主要靠"推"（你告诉用户），尝试→习惯主要靠"拉"（功能本身的价值让用户回来）。如果"推"的阶段投入不足，用户永远不会进入"拉"的阶段。

## 功能公告策略

### 公告的内容结构（适用于 Changelog/邮件/内部通知）

```
标题：新功能 + 一句话价值

{{功能名称}}：{{解决了什么痛点}}

以前：{{用户之前怎么做，痛点是什么}}
现在：{{用这个功能怎么做，改变了什么}}
```

**差的公告**："Agent 报告生成功能已上线。支持从案例数据自动生成售后报告。"

**好的公告**：

> **Agent 报告生成 — 报告撰写时间从 4 小时缩短到 15 分钟**
>
> **以前**：售后工程师每天花 4-6 小时手工撰写报告——复制粘贴模板、调整格式、逐段排版。格式工作占用了本应用于内容质量的时间。
>
> **现在**：在 aiChat 中输入案例数据，Agent 自动基于 YiKnowledge 生成包含"问题描述、原因分析、解决方案、处理结果"四个标准章节的报告草稿。你只需要审核和微调内容，格式由系统自动处理。
>
> **试试看**：打开 aiChat → 输入案例编号 → 点击"生成报告"

### 公告渠道的优先级

| 渠道 | 触达率 | 适合的场景 | YrY 示例 |
|---|---|---|---|
| 产品内提示（最优先） | 高——使用产品的用户才能看到，意味着他们是目标用户 | 所有功能，尤其是需要用户主动操作的新功能 | YiVad 顶部通知栏、YiPet 聊天界面提示气泡 |
| 团队即时消息 | 中——取决于团队是否查看群消息 | 内部工具的功能、需要团队协作的功能 | 企业微信群通知 |
| 邮件/Newsletter | 低——打开率通常 10-20% | 重要功能、破坏性变更预警 | — |
| Changelog 页面 | 低——大多数用户不会主动查看 | 作为历史记录供查阅，不作为主要触达手段 | YiKnowledge 中的版本记录 |

## 产品内引导模式

引导的目标不是"教会用户每个按钮的用途"——是**帮用户完成第一次成功使用**。第一次成功的体验比十页帮助文档更有效。

### 四种引导模式及选择

| 模式 | 描述 | 适用场景 | 不适用的场景 |
|---|---|---|---|
| **空状态引导** | 用户打开一个空的功能区域时，用示例数据和引导文案替代"暂无数据" | 有明确"初始状态"的功能——空列表、空白页面 | 功能已存在且用户已有数据 |
| **渐进式提示** | 用户操作过程中逐步出现小提示，解释下一步可以做什么 | 多步骤流程，用户可能在中间卡住 | 单步骤操作、用户已经很熟悉的流程 |
| **首次使用教程** | 用户第一次进入时的 2-4 步引导，展示核心功能和价值 | 复杂功能、需要改变用户心智模型的新概念 | 简单功能、用户已有类似工具使用经验 |
| **场景触发** | 在用户执行相关操作时出现提示——"你正在做 X，这个新功能可以帮你" | 功能的价值需要在特定场景下才能体现 | 通用功能、与任何特定场景关联不强的功能 |

### YrY 引导设计示例

**YiPet 知识底座 — 空状态引导**

用户第一次打开知识树（空状态）时，不显示"暂无文件"，显示：


**YiVad Agent 报告生成 — 场景触发**

用户正在手动编辑报告格式时：

```
┌────────────────────────────────────────┐
│  💡 你正在花时间调格式？                │
│                                        │
│  Agent 可以自动生成标准格式的报告草稿，  │
│  你只需要审核内容。试试看？              │
│                                        │
│  [现在不]  [试 试]                      │
│                                        │
└────────────────────────────────────────┘
```

**场景触发的黄金规则**：
- 用户在做**高摩擦操作**时触发——既帮了用户，又展示了功能的核心价值
- 每个场景**只触发一次**——重复提醒是骚扰
- 始终提供"不，谢谢"的关闭选项——且关闭后再也不触发同一个场景的提示

## 采用指标

功能上线后追踪什么？不是"多少人点了这个功能"——是"多少人在解决真实问题时用了这个功能"。

| 指标 | 测量方式 | 健康值 | 危险信号 |
|---|---|---|---|
| **触达率** | 看到过功能入口的用户/目标用户总数 | ≥ 80% | < 50%——功能入口可能不可见 |
| **首次尝试率** | 至少使用过 1 次的用户/触达用户 | ≥ 30% | < 15%——用户不理解功能价值或入口门槛太高 |
| **周活跃采用率** | 每周至少使用 1 次的用户/目标用户总数 | ≥ 20% | < 10%——功能没有被整合到用户日常流程中 |
| **替代率** | 使用新功能的用户中，旧方式使用频率下降的比例 | ≥ 50% | < 30%——新功能没有被视为旧方式的替代品 |
| **扩展使用率** | 使用过 ≥ 3 次不同功能点的用户/活跃用户 | ≥ 15% | < 5%——用户只用最基础的功能，没有探索深层价值 |

## 采用失败诊断

当功能发布 4 周后采用率仍低于预期，按以下顺序排查：

```
采用率低
  │
  ├── 1. 用户知道这个功能存在吗？
  │   检查：触达率 < 目标用户 50%
  │   行动：改善入口可见性、增加产品内提示
  │
  ├── 2. 用户理解了功能的价值吗？
  │   检查：看到入口但是没有点击的用户比例 > 70%
  │   行动：改善功能描述——从"功能名"改为"解决什么问题"
  │        用具体场景描述替代抽象功能名
  │
  ├── 3. 用户尝试后觉得有用吗？
  │   检查：首次尝试后 7 天内未再次使用 > 60%
  │   行动：首次体验没让用户感受到价值——
  │        检查首次使用流程中是否有阻断、数据为空、价值不显的情况
  │
  ├── 4. 功能入口在用户最需要的场景下可见吗？
  │   检查：用户的自然使用路径中，是否会在合适时机碰到这个功能
  │   行动：入口不应只在菜单里——应在用户有相关需求的操作路径上出现
  │
  └── 5. 功能解决的痛点不够痛吗？
      检查：深度访谈 5 名未采用用户，问"为什么不？"
      行动：如果答案是"我不觉得需要它"——
           说明功能可能没有解决真问题。回到发现阶段重新审视
```

## YrY 功能采用案例

### 案例 1：YiPet 知识底座 — 高价值但低触达

**问题**：知识底座功能上线 4 周，触达率 45%（55% 用户不知道存在），但深度用户满意度 85%。

| 诊断结果 | 不是功能不好——用了的人觉得好。问题是 55% 的用户不知道它存在 |
|---|---|
| **干预措施** | 1. 知识树入口从二级菜单提到聊天工具栏首位（提升触达）<br>2. 首次聊天时展示"选知识文件 vs 不选"的对比示例（促进理解）<br>3. 用户首次选择知识文件后给出正面反馈：" 已选择 2 个知识文件，AI 回答将基于这些文件"（强化首次体验） |
| **4 周后结果** | 触达率 45% → 72%，采用率 15% → 28% |

### 案例 2：YiVad ProTable 列自定义 — 知道但不用

**问题**：功能入口在表格右上角，触达率 80%，但首次尝试率仅 8%。用户知道有这个按钮但从不点击。

| 诊断结果 | 用户不觉得自定义列有必要——"默认的列已经够了"。功能解决的问题不够痛 |
|---|---|
| **干预措施** | 当用户反复横向滚动表格（表明默认列不符合需求）时，场景触发提示："你频繁左右滚动——试试自定义显示列？" |
| **4 周后结果** | 尝试率 8% → 22%，虽然仍不高，但尝试过的用户留存率 80%——说明功能对需要的人确实有价值，只是需要的人本身就是少数 |

## 实践建议

1. **发布计划必须包含采用计划**：不要把"上线"当作功能完成的终点。每份 PRD 的最后一部分应该是"上线后 30 天采用计划"——公告渠道、引导模式、采用指标目标、失败诊断时间点
2. **第一周是黄金窗口**：新功能上线第一周的用户好奇心和容忍度最高——这周是引导和公告的最佳时机。错过这一周，用户对它的"新功能"新鲜感消失，再推广的边际效果大幅下降
3. **不同功能采用曲线的预期不同**：基础设施改进（如 API 性能提升）的采用是"被动"的——用户不需要做什么。面向用户的新流程（如知识底座）的采用需要主动推动——预期 30 天内 < 30% 是正常的
4. **采用失败不是功能的死刑**：低采用 ≠ 功能失败。首先诊断是"用户不知道/不理解"还是"用户不需要"——前者的解决方案是引导和场景触发，后者才是功能方向问题

## 反模式

| 反模式 | 为什么失败 | 正确做法 |
|---|---|---|
| 功能上线 = 发布公告邮件 = 完事——"公告发了我就可以做下个功能了" | 公告邮件的打开率 10-20%。80% 的目标用户根本不知道这个功能存在——而你认为"已经通知过了" | 公告只是采用漏斗的第一步（知晓）。接下来还有理解（场景示例）、尝试（低门槛首次体验）、习惯（场景触发）——缺一步都不算完 |
| 用弹窗轰炸用户——"首次登录弹 5 个新功能引导" | 用户 3 秒内关掉所有弹窗，一个引导都没看进去 | 首次使用只引导最核心的一个功能。其他功能用场景触发——在用户有相关需求时出现，而非登录时统一轰炸 |
| 所有功能都给同等推广资源——Changelog 里每个功能一段话 | 真正有用户价值的功能被埋没在一堆小修小补里 | 区分功能层级：核心新功能 → 产品内引导 + 场景触发 + 公告；小改进 → Changelog 里一句话；Bug 修复 → 不必主动告知 |
| 采用率低就直接判定功能失败——"4 周了才 10%，砍掉吧" | 没有诊断就下结论。可能 10% 的采用率是因为入口在产品深处，而非功能本身没用 | 先诊断再决策。按采用失败诊断框架走完 5 层排查，确定是"不知道"还是"不需要"，再决定是优化引导还是调整方向 |
| 引导只有"下一步"没有跳过——强迫用户接受教程 | 用户的学习动力被"强迫"消耗殆尽；跳过按钮藏在角落——用户被迫点完每一步但什么也没记住 | 每一步引导提供"跳过教程"。如果用户选择跳过，用场景触发在 ta 有需求时补上——而不是在 ta 不需要时强制灌输 |
