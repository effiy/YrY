# YiAi 项目管理

> **作为**产品经理/工程师，**我想要**了解 YiAi 项目管理上下文，**以便**协调跨项目工作并理解当前交付节奏。

## 项目定位

YiAi 是 YrY 仓库的后端核心——基于 FastAPI 的 AI 服务平台，负责：
- RPC 信封路由（所有前端请求的统一入口）
- Ollama LLM 推理（AI 聊天和 Agent 循环的核心引擎）
- RAG 引擎（llama_index 混合检索，支持向量 + BM25）
- 数据持久化（MongoDB，通过 Motor 异步驱动）
- 知识库扫描（apscheduler 每 5 秒轮询 YiKnowledge 目录树）

YiAi 是 YiVad 和 YiPet 的共同后端——任何 API 变更同时影响两个消费方。

## 关键架构决策

- **RPC 信封作为唯一协议**：前端不直接访问 MongoDB，所有数据操作通过 RPC 信封（`{module_name, method_name, parameters}`）路由
- **参数名称契约**：`filter` 而非 `query`、`target_file` 而非 `path`、`cname` 而非 `collection_name`。不匹配曾导致真实 bug
- **Motor 异步 MongoDB 驱动**：全异步数据访问层，避免阻塞事件循环
- **apscheduler 轮询模式**：知识库每 5 秒扫描一次（非实时监听文件系统——兼顾性能和及时性）

## 风险与注意事项

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| Ollama 模型不可用 | YiVad 和 YiPet 聊天功能完全中断 | 健康检查 + 降级提示 + 重试机制 |
| RAG 索引与 YiKnowledge 不同步 | AI 回答基于过时知识 | apscheduler 5 秒轮询保持及时性；计划增加手动触发重建索引的 API |
| RPC 契约被破坏 | 前端请求静默失败 | 新增 PRD 必须包含 RPC 契约定义（module_name、method_name、parameters 格式） |
| 单点故障 | 所有前端依赖此服务 | 计划增加健康检查和监控告警 |

## 跨项目依赖

- **YiVad**：消费聊天、数据 CRUD、文件管理、知识库、RAG、Agent 服务
- **YiPet**：消费聊天、会话管理、数据查询、知识库、RAG 服务
- **YiKnowledge**：被 YiAi 的知识库监视器扫描并索引到 MongoDB + 向量索引

### PM 操作指南

**新增 API 时**：
1. 在 PRD 中定义 RPC 契约（module_name、method_name、parameters 格式和字段说明）
2. 确认参数名称符合契约规范（尤其是 `filter`/`target_file`/`cname`）
3. 通知 YiVad 和 YiPet 的 PM 更新各自的 API 调用代码
4. 在 YiKnowledge 中更新 API 文档

**报告 bug 时**：
1. 在 YiVad 的 bugs 集合中创建记录
2. 标注影响的消费方（YiVad/YiPet/两者）
3. 严重 bug（影响所有消费方）标记为 P0
