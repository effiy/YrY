# YiPet 项目管理

> **作为**产品经理/工程师，**我想要**了解 YiPet 项目管理上下文，**以便**协调跨项目工作并理解当前交付节奏。

## 项目定位

YiPet 是 YrY 仓库的 Chrome MV3 浏览器扩展，核心价值主张是"在任意网页浏览时获得基于 YrY 知识库的 AI 辅助"。关键特性：
- 知识底座对话（基于 YiKnowledge 的 RAG 聊天）
- 跨项目桥接（与 YiVad 的 session key 桥接）
- 多角色聊天（不同 AI 角色提供不同风格的辅助）
- 双重世界执行（content script + service worker 隔离架构）

## 产品愿景

让用户在任意网页浏览时，一键获得基于 YrY 自有知识库的 AI 辅助。YiPet 不是"又一个 ChatGPT 扩展"——它是 YrY 知识生态的浏览器入口，把团队积累的知识变成随时可用的 AI 对话。

## 目标用户

| 用户角色 | 使用场景 | 核心需求 |
|---|---|---|
| 售后工程师 | 浏览售后案例时基于知识库提问 | 回答基于真实知识、源可追溯 |
| 开发者 | 浏览技术文档时获取 YrY 特有的技术建议 | 上下文感知、快速响应 |

## 关键架构决策

| 决策 | 内容 | 原因 |
|---|---|---|
| 双重世界隔离（ISOLATED + MAIN） | content script 运行在 ISOLATED 世界，通过 bootstrap 自注入模式访问 MAIN 世界 | Chrome MV3 的 CSP 限制 + 需要与宿主页面共享 DOM |
| 4 层 API 架构 | client → endpoints → types → services | 关注点分离：API 调用格式、端点定义、类型约束、业务逻辑各司其职 |
| CDN 资源注入 | 从本地 `chrome-extension://` URL 加载 Ant Design 等资源 | MV3 CSP 禁止远程 CDN 脚本，必须打包本地资源 |
| AiCR 功能整合 | AiCR（AI Code Review）功能融入聊天窗口 | 避免多个独立入口，统一 AI 交互体验 |

## 风险与注意事项

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| Chrome MV3 策略变更 | 扩展可能因 API 废弃而失效 | 关注 Chrome 扩展更新日志；定期在 Chrome Canary 中测试 |
| Content script 破坏宿主页面 | 用户投诉、卸载扩展 | 注入前检测页面兼容性；在主流网站（百度、掘金、GitHub）做冒烟测试 |
| 知识底座回答质量依赖 YiKnowledge 内容 | RAG 回答无源可引 | 持续补充高频问题域的知识内容；识别知识盲区作为内容创建优先级 |
| CDN 资源包体积 | 扩展加载慢、Chrome Store 审核问题 | 按需加载非核心资源；定期审查包体积 |

## 跨项目依赖

- **YiAi**：消费聊天、会话管理、数据查询、知识库、RAG 服务。YiAi 不可用时，YiPet 聊天功能完全不可用
- **YiVad**：跨项目桥接——通过 session key 从 YiPet 跳转到 YiVad 的 aiChat 页面；bug 报告从 YiPet 提交到 YiVad 的 bugs 集合

### PM 操作指南

**新增涉及 YiAi API 的功能时**：
1. 确认所需 API 在 YiAi 中已实现或已列入开发计划
2. 在 PRD 中明确 API 调用的 module_name、method_name 和 parameters 格式
3. 开发期间使用 Mock 数据并行推进，等待 YiAi API 就绪后联调

**发布前的测试检查**：
1. 在 Chrome 正式版 + Canary 版中均加载扩展测试
2. 在 3 个以上不同网站测试 content script 注入兼容性
3. 测试扩展的离线和弱网表现（Chrome DevTools 网络节流）
4. 验证知识底座功能端到端可用（YiAi 服务必须运行）
