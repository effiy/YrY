# 用户访谈综合分析

> **适用场景**：每轮用户访谈（3-8 场）结束后。综合分析的目的是把"我听到了什么"变成"这意味着什么"再变成"我们应该做什么"——大多数人停在第一步。

## 为什么综合比访谈本身更重要

原始笔记不是洞察。以下三句话的差距就是综合的价值：

| 层级 | 示例 | 能驱动决策吗？ |
|---|---|---|
| **原始笔记** | "P3 说他在搜索文件时花了 10 分钟才找到" | 不能——这是一个人的故事 |
| **模式发现** | "8 个受访者中有 5 个提到搜索文件很慢或找不到" | 不能——知道普遍但不知道为什么 |
| **洞察** | "用户找不到文件不是因为搜索慢，而是因为不知道该用什么关键词搜索——知识库里的术语和用户理解的术语不一致" | 能——洞察揭示了根因而非表象 |

大多数人访谈完就写一份"用户说..."的报告——这是笔记整理，不是综合。综合的价值在于**找出模式、解释原因、建议行动**。

## 五步综合流程

### 第一步：在访谈中还新鲜的阶段就开始（访谈结束后立即做）

不要等 5 场访谈都做完才开始综合。两个原因：
- 记忆衰减——24 小时后你会忘记访谈中最微妙的语气和停顿
- 早期综合可以指导后续访谈——如果前 3 场都出现了同一个模式，后 2 场可以专门深挖这个方向

**每场结束后立即记录（5-10 分钟）**：
- 3 个最突出的发现——不管有没有被验证
- 1 个最意外的事情——你没想到用户会这么说/这么做
- 1 个你想在下一场深入追问的话题

### 第二步：摘录关键引用（30 分钟/场）

不要逐字誊写——你不是在做转录，你是在做**筛选**。摘录的标准：

| 值得摘录 | 不值得摘录 |
|---|---|
| 用户描述的具体行为——"我上一次做 X 花了 4 个小时" | 用户笼统的评论——"这个产品还行" |
| 带有情绪的表达——"最让我头疼的是..." | 礼貌性的客套——"做得挺好的" |
| 关于痛点的故事——用户如何绕过去、为什么痛苦 | 关于功能的随意建议——"如果能加个按钮就好了" |
| 用户自发做的对比——"在 A 产品里我可以 X，但这里不行" | 引导性问题得到的敷衍回答 |
| 用户的替代方案——用了什么土办法、为什么不满意 | — |

**摘录格式**：

```
[来源：P3 — 售后工程师，5 年经验]
痛点："我每天花在格式化上的时间比写内容还多。标题编号、表格样式、段落间距——每次都复制粘贴上份报告的格式。"
当前替代方案："我存了一个模板文件，每次复制一份然后往里填内容。但模板经常被同事不小心改掉，然后我又得重新调。"
情绪标记：疲惫（语气）、无奈（提到"不小心改掉"时叹气）
```

### 第三步：打标签（每场 15 分钟）

给每一条关键引用打上标签。标签是归纳的第一步——它是"这条引用讲的是什么"的分类。

**标签类型**：

| 标签类型 | 示例 | 为什么有用 |
|---|---|---|
| 痛点标签 | `#搜索困难`、`#格式耗时`、`#知识过时` | 揭示用户遇到了什么问题 |
| 行为标签 | `#使用替代方案`、`#绕过功能`、`#频繁求助` | 揭示用户实际怎么做 |
| 情感标签 | `#焦虑`、`#疲惫`、`#惊喜` | 揭示用户的情绪状态 |
| 需求标签 | `#想要更快`、`#想要更准`、`#想要更简单` | 揭示用户的期望 |

**打标签规则**：
- 一条引用可以有多个标签
- 标签要具体——`#搜索`太宽泛，`#搜索-不知道关键词`更具体
- 如果一条引用无法打标签，可能它就不值得摘录——重新审视是否该保留

### 第四步：亲和图聚类（1-2 小时，团队活动）

将打了标签的引用归类——相同主题的引用聚类在一起。这是从"多个独立故事"到"共性模式"的转折点。

**方法**（物理白板或在线白板）：
1. 把所有引用贴在白板上
2. 团队成员（PM + 设计师 + 工程师，3-4 人）协作将相关的引用移动到临近位置
3. 当一组引用形成自然聚集时，为它命名——这就是你的**模式**
4. 不属于任何聚集的引用放在旁边——它们是离群值，可能不重要，也可能是你没发现的新方向

**聚类维度**：

| 维度 | 聚类示例 |
|---|---|
| 按用户任务 | "文件搜索相关"、"报告生成相关"、"权限检查相关" |
| 按痛感类型 | "费时"、"费脑"、"不可靠" |
| 按用户群体 | "新人特有"、"资深用户特有" |

### 第五步：撰写洞察和行动建议（1 小时）

每条洞察遵循统一格式：

```
洞察（Insight）：
{{一句话总结模式}}。

证据（Evidence）：
- {{几场访谈、几个受访者}} 提到了 {{具体行为或痛点}}
- {{具体的引用摘录}}

影响（Impact）：
{{如果这个洞察不解决，会对用户行为/业务指标产生什么影响？}}

建议（Recommendation）：
{{基于这个洞察，建议做什么？}}
```

## 完整 YrY 综合示例

以下是从 8 场 YiPet 知识底座用户访谈中综合出的核心洞察。

### 洞察 1：发现而非搜索——用户不知道怎么找文件

**证据**：
- 5/8 受访者提到"搜索文件很慢"或"找不到想要的文件"
- P2："搜索'售后报告模板'搜不到，但我知道知识库里肯定有这个文件——我就是不知道它的文件名是什么"
- P5："我每次浏览知识树时都像在逛陌生的图书馆——分类标签不是我用惯的词"
- P7："我明明知道有个文件讲充电桩故障处理的，但搜'充电桩'没结果——因为文件名用的是'EV 充电设施'"

**影响**：如果文件发现性问题不解决，知识底座的核心价值会被阻断——用户知道知识库里有答案但取不出来。这比"不知道有知识库"更致命——因为用户会尝试但失败，然后用"这功能不好使"来标记它。

**建议**（按优先级）：
1. 语义搜索替代关键词搜索——"充电桩"应能匹配到文件名中的"EV 充电设施"
2. 知识树上的浏览增强——文件旁边显示标签/摘要，而非仅文件名
3. 搜索结果中显示"你可能在找"的语义相关文件

### 洞察 2："知识是不是最新的？"——信任缺失

**证据**：
- 3/8 受访者自发提到对知识新鲜度的担忧
- P4："它引用了一个文件，但我不知道那个文件是上周更新的还是去年的——这决定了我是直接用还是去核实一下"
- P8："我们公司的售后政策每个月都在变，我不确定 AI 回答是基于最新版本的知识"
- 尽管所有知识的 frontmatter 都标注了更新日期，但 0/8 的受访者注意到这个信息

**影响**：知识的可信度 = 引用质量 × 新鲜度透明度。当前信任度受限于"不知道知识有多新鲜"——即使知识实际上很新，用户不感知就等于不信任。

**建议**：
1. RAG 回答中每条引用旁边显示"最后更新：2026-09-10"——让新鲜度可见
2. 超过 3 个月未更新的知识文件在引用时标注"信息可能已过时"

### 洞察 3：知识底座的新手激活不靠功能演示——靠场景触发

**证据**：
- 7/8 的受访者表示，第一次使用知识底座是因为"遇到了一个具体案例，想看看有没有类似的处理方案"
- 没有人是因为"看到了功能介绍"或"别人推荐"而首次使用
- P3："我是在处理一个没见过的故障案例时才点了知识树——之前它就在那里，但我从没觉得需要点"

**影响**：知识底座的激活靠的是"用户遇到具体需求时功能恰好在手边"，而非"告诉用户这个功能很好"。当前入口被动等待触发——需要更主动的场景识别。

**建议**：
1. 当用户在聊天中提到特定产品名称或故障现象时，提示"知识库中有相关文件，需要我帮你查吗？"
2. 不要在全聊天场景做通用推广——在用户有具体信息需求的瞬间做精准触发

## 综合质量自检

综合完成后，用以下标准检查质量：

- [ ] 每条洞察能用一句话说清楚，不依赖补充解释
- [ ] 每条洞察有至少 3 条来自不同受访者的独立证据支撑
- [ ] 每条洞察有明确的"所以呢？"——如果这条洞察为真，我们应该做什么不同的事？
- [ ] 有没有哪个洞察让你觉得"这我一直都知道"？如果有，删除它——综合的价值在于发现你不知道的，而非确认你已知道的
- [ ] 有没有引用被忽略？——离群值也是信号，可能指向一个被忽视的细分群体

## 知识沉淀

综合完成后，不要只留在研究报告里——将关键洞察沉淀到知识库：

| 洞察产出 | 沉淀到 | 作用 |
|---|---|---|
| 用户行为模式 | 用户画像文件（更新画像的行为特征） | 让画像基于证据而非假设 |
| 核心痛点 | PRD 的问题陈述部分 | 让需求定义基于真实的用户痛点 |
| 需求信号 | OST 的机会层 | 为产品发现提供证据支撑 |
| 竞品相关发现 | 竞品分析文件 | 补充竞品弱点/用户流失原因 |
| 意外发现 | YiKnowledge lessons | 记录"我们当时意外学到的" |

## 实践建议

1. **24 小时内完成单场综合笔记**：记忆半衰期很短——超过 24 小时的笔记会丢失语气、停顿和微表情这些关键信息
2. **团队一起做亲和图，不要一个人**：PM 看到的模式、设计师看到的模式、工程师看到的模式通常不同。三人各自聚类然后对比——分歧越大的地方越需要深入讨论
3. **洞察数量控制在 3-5 条**：超过 5 条说明你可能在列举发现而非综合模式。核心洞察应该少而精——团队能记住并在后续决策中引用的数量就是 3-5 条
4. **区分"有趣的发现"和"可行动的洞察"**："用户喜欢蓝色"是有趣的发现。"用户选择蓝色是因为蓝色让他们觉得可信和专业——在需要建立信任的场景（支付、认证）用蓝色"是可行动的洞察

## 反模式

| 反模式 | 为什么失败 | 正确做法 |
|---|---|---|
| 逐字转录当综合——"这是 8 场访谈的完整记录" | 50 页的转录文档没人读。团队继续凭直觉做决策，用户研究的投入全浪费 | 综合 = 筛选 + 归类 + 解释。产出不超过 2 页。原始记录保留给需要验证的人查阅，但不依赖它传递洞察 |
| 只找支持自己假设的证据——"你看，用户都说 X 是个问题" | 忽略反面证据；错过了"X 只在特定条件下是问题，其他时候不是"的微妙发现 | 刻意寻找反面证据：有没有用户觉得 X 不是问题？他们在什么条件下觉得不是？反面证据往往揭示解决方案的边界 |
| 每场访谈后不立即记录——"周末一起整理吧" | 到周末时只记得最后两场的内容；早期访谈中的重要细节已丢失 | 每场结束后 30 分钟内完成单场综合笔记。5 分钟的即时记录 > 30 分钟的延时回忆 |
| 综合只做一次不分发——"我总结了一篇报告发邮件了" | 邮件被标记已读就忘了。团队 2 周后在做决策时不会想起"哦用户研究里提到过这个" | 洞察沉淀到知识库的具体位置（画像、PRD、OST、竞品分析）。下次团队在这些地方工作时自动看到洞察 |
| 洞察写成不可验证的断言——"用户体验很差" | 无法验证、无法证伪。"差"是基于什么标准？谁来定义？ | 每条洞察附带具体证据（几场/几个受访者 + 引用）。不可验证的洞察 = 个人观点，不是用户研究的产出 |
