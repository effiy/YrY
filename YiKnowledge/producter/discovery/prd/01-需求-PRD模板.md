# PRD 模板 — 产品需求文档

> **PRD = 问题 + 用户 + 范围 + 成功标准。** PRD 定义做什么、为谁做、如何衡量成功。它不定义如何构建（→ engineer/），也不定义使用什么技术（→ leader/）。

## 使用说明

本模板适用于 YrY 仓库中任何项目的新功能 PRD。使用方式：

1. **复制模板到新文件**：在 `YiKnowledge/producter/discovery/prd/` 下创建新文件，命名格式为 `{项目}-{功能描述}.md`
2. **按章节填写**：不需要填完所有章节再分享——完成问题陈述和范围两章后就可发起早期评审
3. **保持迭代**：PRD 是活文档，开发过程中发现的新信息应及时更新

## 模板正文

### 1. 问题陈述

这个功能解决什么问题？一段话描述。要具体说明痛点，不要抽象概括。

**示例**："海外售后团队每人每天花费 4-6 小时手工撰写和格式化售后文档。文档格式标准化但内容因案例而异。自动生成草稿可将这个时间缩短到 15 分钟审核确认。"

**自检**：读完问题陈述后，一个不了解这个功能的人能否复述出"谁在什么场景下遇到什么痛点"？

### 2. 目标用户

谁有这个痛点？明确角色和场景。

| 用户 | 角色 | 使用场景 | 当前行为 | 痛点严重程度 |
|---|---|---|---|---|
| 售后工程师 | 文档作者 | 收到售后案例后，需要产出标准格式的售后报告 | 在 Word 中手工撰写，逐段复制粘贴模板内容 | 高 — 每天 4-6 小时，高频重复 |
| 售后主管 | 审核者 | 审核提交的售后报告并批准 | 在 Word 中逐字阅读，在 Word 批注中给出修改意见 | 中 — 每天 1-2 小时 |

### 3. 范围

本版本包含什么？明确排除什么？

**本版本包含**：
- 从案例数据和知识库自动生成售后报告草稿
- 中文和英文双语输出
- 草稿提交前可在线编辑修改
- 在草稿中标注信息来源文件

**本版本不包含**：
- 多级审批工作流（独立功能，后续 PRD）
- 自定义报告模板（V2 版本规划）
- 与外部系统（CRM、ERP）的对接
- 移动端适配

**为什么"不包含"很重要**：明确的排除项不仅约束开发范围，更管理干系人预期。每次评审时，总有人会问"能不能也加上 X？"——"不包含"部分就是你的事先防御。

### 4. 成功指标

如何知道这个功能成功了？每个指标必须可测量。

| 指标 | 基准值 | 目标值 | 测量方式 |
|---|---|---|---|
| 草稿生成时间 | 4-6 小时/份 | ≤ 15 分钟/份 | 从案例开启到草稿就绪的时间戳差值 |
| 草稿采纳率 | 0% | ≥ 80% 的草稿修改次数 ≤ 2 | 每份草稿的修改次数统计 |
| 用户采用率 | 0% | ≥ 70% 的售后工程师使用 | 功能使用埋点统计 |
| 报告审核时间 | 1-2 小时/份 | ≤ 30 分钟/份 | 审核通过的时间戳差值 |

### 5. 用户故事

每个故事遵循格式："作为 {{角色}}，我想要 {{做什么}}，以便 {{获得什么价值}}。"

1. 作为售后工程师，我想要从案例数据一键生成报告草稿，以便我不再花费数小时手工格式化文档。
2. 作为售后工程师，我想要在提交前编辑生成的草稿，以便纠正 AI 可能产生的任何不准确内容。
3. 作为售后主管，我想要在草稿旁边看到源数据引用，以便快速验证草稿的准确性。
4. 作为售后工程师，我想要草稿同时支持中文和英文输出，以便服务不同地区的客户。

### 6. 功能需求

系统必须做什么？每条需求可测试。

| ID | 需求描述 | 优先级 | 备注 |
|---|---|---|---|
| F1 | 接受案例数据输入（案例编号、客户、产品、问题描述） | P0 | 支持手动输入和系统对接两种方式 |
| F2 | 通过 RAG 从 YiKnowledge 检索相关知识 | P0 | 依赖 YiAi RAG 模块的混合检索能力 |
| F3 | 按标准格式生成报告草稿，包含所有必需章节 | P0 | 标准格式定义见依赖项 |
| F4 | 支持中文和英文输出 | P1 | 两种语言输出质量等同，非机器翻译 |
| F5 | 草稿支持在线逐段编辑 | P1 | 编辑后自动保存，防止丢失 |
| F6 | 每个生成段落标注源文件引用 | P2 | 点击引用可跳转到源文件预览 |

### 7. 验收标准

功能完成必须满足什么条件？

- [ ] 输入完整的案例数据后，60 秒内生成包含所有必需章节的报告草稿
- [ ] 草稿中每个生成段落都标注了源知识文件的引用链接
- [ ] 用户可以在提交前编辑草稿的任意段落，修改后自动保存
- [ ] 中文和英文输出内容等同（不是先写中文再机器翻译成英文）
- [ ] 草稿格式符合标准规范（章节名称、顺序、术语统一）

### 8. 依赖项

在开始开发前，什么必须就绪？

| 依赖项 | 当前状态 | 负责人 | 预计就绪时间 |
|---|---|---|---|
| YiKnowledge 知识库内容（RAG 源） | 活跃更新中 | curator | 已完成 |
| RAG 混合检索（向量 + BM25） | 已完成 | engineer (YiAi) | 已完成 |
| 报告标准格式定义 | 待完成 | producter | Sprint 1 前半段 |
| 具备足够上下文窗口的 LLM | 已完成（Ollama，模型可配置） | engineer (YiAi) | 已完成 |
| 案例数据输入接口 | 待完成 | engineer (YiAi) | Sprint 1 前半段 |

## 实践建议

1. **先写问题陈述，再写功能需求**：如果在问题陈述阶段就想到解决方案，先记下来放在一边，不要往回修改问题陈述去适配方案
2. **范围用"是/否"测试**：对一个功能需求，如果能用"是/否"快速判断是否在范围内，说明范围定义清晰
3. **成功指标要有基准值**：如果基准值是"不知道"，先花一周收集数据再继续写 PRD。没有基准的目标是空谈
4. **用户故事不超过 5 条**：超过 5 条说明要么功能范围太广（需要拆成多个 PRD），要么故事写得太细（合并相似故事）

## 反模式

- **在 PRD 中写实现细节。** "使用 MongoDB 聚合管道查询"属于技术评审，不属于 PRD。PRD 描述用户需要什么，而非如何构建。技术方案的讨论应该在对工程团队的 PRD 讲解会上进行，而非写在 PRD 正文中
- **模糊的成功指标。** "用户体验更好"不可测量。"报告撰写时间从 4 小时降低到 15 分钟"可测量。可测量的标准是：两个独立的人用同一指标对同一功能评估，能得出一致的结论
- **没有"不包含"部分。** 没有明确边界，范围就会在评审和开发过程中不断蔓延。列出你明确不做的事情——这既保护团队，也管理干系人预期
- **PRD 写完后从不更新。** 开发中发现的方案调整（如技术约束导致的妥协）没有同步回 PRD，导致文档与实现脱节。PRD 是活文档，开发期间的重大调整必须回溯到 PRD

## 完整示例：YiVad Agent 报告生成功能 PRD

以下是用本模板撰写的一份 YrY 真实 PRD 示例。对比模板和示例，理解每个章节的填写尺度。

### 1. 问题陈述

售后工程师每人每天花费 4-6 小时手工撰写和格式化售后文档。文档格式标准化（章节名称、术语、排版要求固定），但内容因案例而异。工程师将大部分时间花在格式化而非内容质量上——调整标题编号、复制粘贴模板段落、逐段检查排版一致性。

自动生成报告草稿可将这个时间缩短到 15 分钟审核确认，让工程师将精力集中在内容准确性和客户沟通上。

### 2. 目标用户

| 用户 | 角色 | 使用场景 | 当前行为 | 痛点严重程度 |
|---|---|---|---|
| 售后工程师 | 文档作者 | 收到售后案例后，需要产出标准格式的售后报告 | 在 Word 中手工撰写，打开旧报告复制粘贴段落作为模板 | 高 — 每天 4-6 小时，高频重复，影响核心工作产出 |
| 售后主管 | 审核者 | 审核售后工程师提交的报告并给出修改意见 | 在 Word 中逐段阅读，在批注中标记需要修改的地方 | 中 — 每天 1-2 小时，主要痛点在于"改完一遍又来一遍"的反复沟通 |

### 3. 范围

**本版本包含**：
- 从案例数据和 YiKnowledge 自动生成售后报告草稿（包含"问题描述"、"原因分析"、"解决方案"、"处理结果"四个标准章节）
- 草稿提交前可在线逐段编辑修改
- 草稿中标注信息来源文件（来自哪个 YiKnowledge 文件）
- 草稿保存和提交功能

**本版本不包含**：
- 多级审批工作流（独立功能，后续 PRD）
- 自定义报告模板（V2 版本）
- 外部系统（CRM、ERP）的数据对接
- 移动端适配
- 报告导出为 Word/PDF（V1 仅支持在线查看和编辑）

### 4. 成功指标

| 指标 | 基准值 | 目标值 | 测量方式 |
|---|---|---|---|
| 草稿生成时间 | 4-6 小时/份 | ≤ 15 分钟/份 | 从"开始生成"到"草稿就绪"的时间戳差值 |
| 草稿采纳率 | 0% | ≥ 80% 的草稿修改次数 ≤ 2 | 每份草稿的编辑次数统计 |
| 用户采用率 | 0% | ≥ 70% 的售后工程师在上线 4 周内至少使用 1 次 | 功能使用埋点 |
| 报告审核时间 | 1-2 小时/份 | ≤ 30 分钟/份 | 审核通过的时间戳差值 |

### 5. 用户故事

1. 作为售后工程师，我想要从案例数据一键生成报告草稿，以便我不再花费数小时手工格式化文档。
2. 作为售后工程师，我想要在提交前编辑草稿的任意段落，以便纠正 AI 可能产生的任何不准确内容。
3. 作为售后主管，我想要在草稿旁边看到每个段落的源数据引用，以便快速验证草稿的准确性而无需打开原始案例。
4. 作为售后工程师，我想要草稿自动保存，以便浏览器意外关闭时不会丢失我的编辑内容。

### 6. 功能需求

| ID | 需求描述 | 优先级 | 备注 |
|---|---|---|---|
| F1 | 接受案例数据输入（案例编号、客户名、产品型号、问题描述） | P0 | 支持手动输入和从项目管理页面快捷创建两种方式 |
| F2 | 通过 RAG 从 YiKnowledge 检索相关知识，生成报告草稿 | P0 | 依赖 YiAi RAG 模块的混合检索能力 |
| F3 | 按标准四段式格式输出草稿（问题描述、原因分析、解决方案、处理结果） | P0 | 格式定义见 YiKnowledge 售后报告标准模板 |
| F4 | 草稿支持在线逐段编辑，编辑后自动保存 | P1 | 编辑草稿时自动保存到草稿箱，防止丢失 |
| F5 | 每个生成段落标注源知识文件引用链接 | P2 | 点击引用可跳转到 YiKnowledge 源文件预览 |
| F6 | 草稿提交后不可再编辑（需联系主管重新打开） | P2 | 防止提交后被私下修改 |

### 7. 验收标准

- [ ] Given 输入完整的案例数据（案例编号、客户、产品、问题描述），When 用户点击"生成草稿"，Then 60 秒内生成包含四个标准章节的报告草稿
- [ ] Given 草稿已生成，When 用户点击任意段落，Then 该段落进入编辑模式，修改内容自动保存
- [ ] Given 草稿已生成，When 用户查看草稿，Then 每个生成段落标注了源知识文件的引用链接
- [ ] Given 用户已编辑草稿，When 用户关闭浏览器窗口后重新打开，Then 之前编辑的内容仍然保留
- [ ] Given 用户已提交草稿，When 用户尝试编辑已提交的草稿，Then 显示"已提交的报告不可编辑，请联系主管"提示

### 8. 依赖项

| 依赖项 | 当前状态 | 负责人 | 预计就绪 |
|---|---|---|---|
| YiKnowledge 售后知识内容（RAG 源） | 活跃更新中 | curator | 已完成 |
| RAG 混合检索 API（向量 + BM25） | 已完成 | YiAi 后端 | 已完成 |
| 售后报告标准格式定义（四段式） | 待完成 | PM | Sprint 1 前半段 |
| LLM 模型可用且上下文窗口足够 | 已完成（Ollama，模型可配置） | YiAi 后端 | 已完成 |
| 案例数据输入接口（从项目管理页面传入） | 待完成 | YiAi 后端 + YiVad 前端 | Sprint 1 前半段 |

### RPC 契约定义

本功能涉及以下 YiAi API 调用：

| module_name | method_name | parameters | 说明 |
|---|---|---|---|
| `services.ai.agent_service` | `generate_report` | `{case_id: str, case_data: dict, template: str}` | 触发报告生成，返回草稿 ID |
| `services.ai.agent_service` | `get_draft` | `{draft_id: str}` | 获取草稿内容和状态 |
| `services.ai.agent_service` | `update_draft` | `{draft_id: str, section: str, content: str}` | 编辑草稿指定段落 |
| `services.ai.agent_service` | `submit_draft` | `{draft_id: str}` | 提交草稿，提交后不可编辑 |
