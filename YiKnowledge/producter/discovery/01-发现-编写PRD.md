# 编写 PRD — 产品需求文档

> **适用场景**：在任何重要功能开发之前。PRD 是产品、工程和设计之间的契约——它定义了"做什么"和"为什么做"，不定义"怎么做"和"用什么技术"。

## 什么是 PRD

PRD（产品需求文档）是一份描述产品功能的文档，它回答三个核心问题：

1. **为谁做？** — 目标用户是谁，他们在什么场景下有这个需求
2. **做什么？** — 功能的具体范围，包含哪些、不包含哪些
3. **为什么做？** — 这个功能解决什么问题，成功的标准是什么

一份好的 PRD 让工程师不需要猜测产品意图，让设计师不需要反复确认交互逻辑，让测试人员清楚知道"完成"的定义。

## 何时需要写 PRD

| 需要写 PRD | 可以跳过 PRD |
|---|---|
| 影响多个服务或模块的新功能 | 单行修改的 bug 修复 |
| 涉及用户界面变更（新页面、新流程） | 纯配置修改、文案更新 |
| API 变更影响前端消费者 | 不改变外部行为的内部重构 |
| 跨团队协作（产品 + 工程 + 设计） | 需求明确清晰的单人任务 |

**判断原则**：如果开发需要超过一天，就写 PRD。如果超过一周，先写一页 PRD 再开始动手。PRD 的长度与功能的复杂度和风险成正比——一个简单功能可能只需要半页纸，一个跨项目功能可能需要 3-5 页。

## PRD 撰写流程

### 第一步：从用户问题出发（而非解决方案）

这是 PRD 中最重要的一步，也是最容易被跳过的一步。产品经理最容易犯的错误是直接跳到解决方案，而忽略了"我们到底在解决什么问题"。

**错误写法**："在设置页添加一个深色模式开关。"
这种写法直接给了解决方案，但没有解释为什么需要它。工程师无法评估是否有更好的替代方案。

**正确写法**："夜间工作的用户反馈屏幕亮度过高导致眼睛疲劳，20% 的用户在晚上 8 点后停止使用产品。"
这种写法描述了真实的用户痛点，让工程师可以参与方案讨论（比如是否可以通过系统级深色模式自动切换来实现）。

### 第二步：定义目标用户画像

谁有这个痛点？要具体，避免"所有用户"这种模糊定义。

**示例（YiVad 深色模式）**：
- **角色**：YiVad 管理员用户
- **场景**：深夜管理项目，屏幕亮度刺眼导致不适
- **当前替代方案**：通过浏览器开发者工具注入自定义深色 CSS
- **痛点严重程度**：高频（每天使用）、高影响（直接影响使用意愿）

### 第三步：撰写用户故事

| 优先级 | 用户故事 | 验收标准 |
|---|---|---|
| P0 | 作为管理员，我可以切换到深色模式，以便在夜间舒适地工作 | 设置页可见深色模式开关；切换后所有页面应用深色主题；偏好跨会话保持 |
| P1 | 作为管理员，深色模式覆盖所有页面，无需逐页设置 | 所有 YiVad 页面（数据管理、聊天、知识库、文件管理）均支持深色模式 |
| P2 | 作为管理员，深色模式可跟随系统设置自动切换 | 当操作系统切换到深色模式时，YiVad 自动切换 |

### 第四步：定义范围（明确包含与不包含）

范围定义是防止需求蔓延的第一道防线。每个 PRD 都必须有明确的"不包含"部分。

**本版本包含**：
- 设置页深色模式开关
- 覆盖 YiVad 所有页面的深色主题
- 偏好存储在 localStorage 中跨会话保持

**本版本不包含**：
- 跟随操作系统自动切换（下一版本 PRD）
- 自定义主题颜色（下一版本 PRD）
- YiPet 深色模式（独立项目，单独评估）

### 第五步：定义成功指标

| 指标 | 基准值 | 目标值 | 测量方式 |
|---|---|---|---|
| 深色模式使用率 | 0% | 30 天内 > 20% 用户 | localStorage 偏好统计 |
| 夜间使用率（20:00-06:00） | 日均 5% | 30 天内 > 日均 10% | 活跃时段分析 |
| 用户满意度 | 无数据 | NPS 提升 5 分 | 功能上线后定向问卷 |

### 第六步：识别风险与缓解措施

| 风险 | 可能性 | 缓解措施 |
|---|---|---|
| 部分第三方组件不支持深色模式 | 中 | 提前审查 Ant Design 组件深色模式兼容性；不支持的组件用 CSS 覆盖 |
| 深色模式增加 QA 回归范围 | 高 | 将深色模式加入视觉回归测试用例；建立深色模式组件截图基准 |
| 用户找不到深色模式入口 | 低 | 首次上线时通过通知提示用户新功能；设置页入口放在显眼位置 |

## PRD 生命周期

```
草稿 → 评审中 → 已批准 → 开发中 → 已交付 → 已归档
  │      │        │        │        │        │
  │      │        │        │        │        └─ PRD 作为历史参考存档，供后续类似功能查阅
  │      │        │        │        └─ 功能上线后 PRD 状态更新为"已交付"
  │      │        │        └─ 开发期间 PRD 是实现的事实依据，变更需走修订流程
  │      │        └─ PRD 锁定，后续修改需要创建修订版本并重新评审
  │      └─ 团队评审可行性、范围、清晰度；PM 和工程师共同确认
  └─ 作者撰写初稿，完成自检后提交评审
```

## 实践建议

1. **PRD 在动手开发前完成评审**：评审后的修改不应超过 20%。如果评审发现大量问题，说明初稿需要返工
2. **PRD 不是一次性文档**：开发过程中发现的问题（如技术约束导致的方案调整）应及时更新到 PRD 中，保持文档与实现一致
3. **使用 PRD 模板**：统一格式减少沟通成本。参考 [01-需求-PRD模板.md](./prd/01-需求-PRD模板.md) 快速起稿
4. **PRD 写完让工程师复述**：验证他们理解是否正确。如果复述有偏差，说明 PRD 写得不够清晰
5. **YrY 跨项目 PRD 额外要求**：涉及 YiAi API 变更的 PRD 必须包含 RPC 契约定义（module_name、method_name、parameters 格式和参数名称契约）

## 反模式

| 反模式 | 为什么失败 | 正确做法 |
|---|---|---|
| PRD 写成 20 页的长篇小说 | 没人完整阅读；细节在开发开始时就已过时 | 保持简洁（2-5 页），详细设计文档单独链接。控制信息密度：每段话都要有决策价值 |
| 方案优先型 PRD（"我们将添加一个按钮用于..."） | 跳过了问题定义；工程师无法评估替代方案 | 从用户问题出发，让工程团队参与方案讨论。PRD 定义"做什么"和"为什么"，不定义"怎么做" |
| PRD 没有验收标准 | "完成"的定义模棱两可；QA 不知道测什么 | 每个用户故事至少一条可验证、可测试的验收标准。使用 Given-When-Then 格式 |
| PRD 在草稿状态搁置数周 | 需求腐化；背景信息丢失；团队失去动力 | PRD 撰写限时 2-3 天完成；要么推进要么终止。超过一周未更新的 PRD 需要重新评估必要性 |
| PRD 缺少"不包含"部分 | 范围不断蔓延；评审时各方往 PRD 里塞自己的需求 | 明确列出本版本不做的内容。这不是拒绝这些需求，而是把它们放入后续版本的待评估池 |
