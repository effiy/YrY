# 用户画像方法

> **适用场景**：在任何涉及用户界面或用户流程的功能设计之前。用户画像让团队在讨论"用户"时不再是一个模糊的概念，而是一个具体的人——有名字、有场景、有痛点、有动机。

## 为什么需要用户画像

没有画像的团队在讨论功能时，每个人脑中的"用户"都不一样：
- PM 想的是"需要提升效率的资深用户"
- 设计师想的是"喜欢简洁界面的新用户"
- 工程师想的是"能接受一定学习曲线的技术用户"

结果：做出来的功能谁也不满意，因为团队从第一天起就在为三个不同的人做产品。

用户画像的核心价值不是"精准描述用户是谁"，而是**让团队对"我们在为谁做产品"有一致的理解**。精准度重要，一致性更重要。

## 两种画像方法

| 维度 | 原型画像（Proto-Persona） | 调研画像（Research Persona） |
|---|---|---|
| 数据来源 | 团队经验和假设 | 用户访谈 + 行为数据 |
| 制作时间 | 2-4 小时 | 1-2 周 |
| 精度 | 中等——可能有偏差 | 高——数据支撑 |
| 适用阶段 | 产品早期、快速验证想法 | 产品成熟期、重大功能决策 |
| 制作方式 | 工作坊：PM + 设计师 + 工程师一起画 | PM 主导：基于用户研究数据综合 |

**建议**：永远从原型画像开始。如果等数据完美了再画画像，你永远不会开始。原型画像的价值在于**让团队开始讨论"用户"**——后续的用户研究可以逐步验证和修正它。

## 画像的五要素

一份有用的画像不追求面面俱到，聚焦五个关键要素：

### 1. 身份标识

给画像一个名字、一张照片（或简笔画）、一个角色标签。

**为什么需要名字**：说"我们的目标用户需要这个功能"和说"张工需要这个功能"——后者让团队在讨论时有了具体的指代对象。名字让抽象的用户变成了可以共情的人。

### 2. 人口和行为特征

| 维度 | 示例 | 为什么重要 |
|---|---|---|
| 角色/职位 | 售后工程师 | 决定核心使用场景 |
| 经验水平 | 5 年售后经验，熟悉产品但不懂技术 | 决定界面复杂度 |
| 使用频率 | 每天使用 4-6 小时 | 决定功能深度 |
| 设备环境 | Windows 笔记本、Chrome 浏览器 | 决定技术约束 |
| 团队规模 | 20 人售后团队中的一员 | 决定协作需求 |

### 3. 目标和动机

用户在工作和生活中想要完成什么？区分功能性目标和情感性目标：

| 类型 | 示例 | 对产品设计的影响 |
|---|---|---|
| 功能性目标 | "在 15 分钟内生成一份标准格式的售后报告" | 决定核心功能范围 |
| 情感性目标 | "对报告质量有信心，不担心格式和遗漏" | 决定反馈机制和状态提示 |
| 社交性目标 | "在主管面前展现专业的报告撰写能力" | 决定分享和展示功能 |

### 4. 当前痛点和替代方案

用户现在怎么解决这个问题的？为什么不满意？

- **当前方案**：在 Word 中手工撰写报告，复制粘贴模板内容
- **痛点**：每天花 4-6 小时在格式化上、容易遗漏关键章节、修改后格式混乱
- **为什么困扰**：高频（每天）、核心（不写报告没法交差）、无替代（工具限制）

### 5. 使用场景

用户在什么情境下使用产品？

| 情境要素 | 描述 |
|---|---|
| 时间 | 上午 9 点处理昨天积累的案例，下午 3 点提交报告给主管审核 |
| 地点 | 办公室工位，双显示器 |
| 情绪 | 希望快速处理完案例积压，对重复劳动感到疲惫 |
| 干扰 | 经常被同事打断询问案例进展 |
| 工具链 | 公司 CRM 系统 → Word → 邮件发送给主管 |

## 用户画像模板

```markdown
## {{名字}} — {{角色标签}}

### 一句话描述
{{名字}} 是 {{角色/背景}}，ta 最核心的需求是 {{核心目标}}。

### 身份标识
- 角色：{{职位}}
- 经验：{{行业经验 + 产品使用经验}}
- 使用频率：{{每日/每周/每月}}
- 设备：{{操作系统 + 浏览器/应用}}

### 目标
- 功能性：{{具体要完成什么任务}}
- 情感性：{{希望在使用中/后获得什么感觉}}
- 社交性：{{希望被同事/上级如何看待}}

### 当前状态
- 当前方案：{{现在怎么解决这个问题的}}
- 最大痛点：{{最让 ta 痛苦的是什么}}
- 痛点程度：高/中/低（频率 × 影响）

### 使用场景
- 时间：{{什么时候使用}}
- 地点：{{在哪使用}}
- 情境：{{使用时的情绪、干扰、上下文}}

### 对产品的期望
- 必须有：{{没这个就不会用}}
- 最好有：{{有了会大幅提升体验}}
- 无所谓：{{不太关心的事情}}
```

## YrY 用户画像示例

### 画像 1：张工 — YiVad 项目管理员

**一句话描述**：张工是 5 年经验的售后团队主管，ta 最核心的需求是快速掌控项目全局状态，确保问题不遗漏。

**身份标识**：
- 角色：售后团队主管
- 经验：5 年售后经验，用 YiVad 管理项目 3 个月
- 使用频率：每天 2-3 小时
- 设备：Windows 笔记本，Chrome 浏览器

**目标**：
- 功能性：每天早晨 5 分钟内了解所有项目的问题状态和进度
- 情感性：对项目全局有掌控感——"没有一件重要的事在我不知情的情况下发生"
- 社交性：在周会上用数据（而非直觉）向上级汇报项目状态

**当前状态**：
- 当前方案：Excel 追踪 + 每天早上逐一检查各项目的问题列表
- 最大痛点：项目多了以后（5+ 个项目），逐个翻看项目页面耗时且容易遗漏
- 痛点程度：高（每天发生、影响管理效率）

**使用场景**：
- 时间：上午 9:00-9:30 检查项目状态，下午 4:00 分配新问题
- 地点：办公室工位，外接显示器
- 情境：早晨需要快速评估"今天要盯什么"——如果信息分散在多个页面，ta 会感到焦虑

**对产品的期望**：
- 必须有：一个页面看到所有项目的关键状态（问题数、逾期数、进度）
- 最好有：自动提醒——哪些问题快过期了、哪些项目停滞了
- 无所谓：移动端访问（ta 不用手机处理工作）

### 画像 2：小李 — YiPet 知识底座使用者

**一句话描述**：小李是入职 3 个月的新售后工程师，ta 最核心的需求是快速找到 YrY 知识库中与当前案例相关的知识。

**身份标识**：
- 角色：售后工程师（新人）
- 经验：3 个月售后经验，产品知识还在学习中
- 使用频率：遇到不熟悉的案例时使用，每天 3-5 次
- 设备：Windows 笔记本，Chrome 浏览器

**目标**：
- 功能性：遇到不熟悉的售后案例时，快速查到类似案例的处理方案
- 情感性：不想频繁向老同事求助——"我自己能查到"是一种安全感
- 社交性：希望给主管留下独立解决问题的印象

**当前状态**：
- 当前方案：微信问老同事 + 在 YiKnowledge 文件夹中手动搜索
- 最大痛点：不知道用什么关键词搜索——知识库里的术语和 ta 理解的术语不一样
- 痛点程度：高（学习期的核心瓶颈）

**使用场景**：
- 时间：收到新案例后的第一时间（上午 10 点、下午 2 点是案例高峰期）
- 地点：办公室工位
- 情境：拿到案例编号后，需要快速判断"这个案例以前有人处理过吗？怎么处理的？"

**对产品的期望**：
- 必须有：选中案例描述文字就能基于知识库提问——不用自己想关键词
- 最好有：自动推荐与当前案例相关的历史文件
- 无所谓：多轮对话（一轮问答能解决就不需要追问）

### 画像 3：陈工 — YiAi API 消费者

**一句话描述**：陈工是 YiVad 前端开发者，ta 最核心的需求是调用 YiAi API 时遇到问题能快速定位是前端调用有误还是后端返回有误。

**身份标识**：
- 角色：前端开发者
- 经验：3 年前端开发，熟悉 YiVad 架构，了解但不深入 YiAi 内部
- 使用频率：开发新功能时每天调用 YiAi API 数十次
- 设备：MacBook，VS Code + Chrome DevTools

**目标**：
- 功能性：调用 API 出错时，错误信息足够具体，不需要去看 YiAi 源码
- 情感性：对自己调用的 API 有信心——不是"这次碰巧没报错"而是"我知道它按预期工作了"
- 社交性：不需要频繁打扰 YiAi 后端开发者问"这个错误是什么意思？"

**当前状态**：
- 当前方案：看 YiAi 源码 + 在即时消息中问后端同事
- 最大痛点：参数名不匹配（`filter`/`query`）导致的静默失败——API 返回 200 但数据不对
- 痛点程度：高（调试时间浪费、后端同事被打断）

**对产品的期望**：
- 必须有：RPC 契约清晰文档化、参数名严格一致、错误码有中文说明
- 最好有：API 变更前 1 周的提前通知和迁移指南
- 无所谓：API 的 HTTP 层面设计（JsonRPC vs REST——只要文档清楚就行）

## 如何使用画像

### 在 PRD 中引用画像

不要只在 PRD 开头贴画像——在每个关键决策点引用画像：

**差**："用户需要快速找到文件"——谁是"用户"？张工还是小李？

**好**："小李（新人售后工程师）遇到新案例时，需要在不知道专业术语的情况下找到相关历史案例。因此搜索功能需要支持模糊语义匹配，而非精确关键词匹配。"

画像让 PRD 中的每个"用户需要 X"都有了具体的指代——你能判断"小李会不会这样用？"

### 在优先级排序中参考画像

| 功能 | 张工（主管） | 小李（新人） | 陈工（开发者） | 优先级判断 |
|---|---|---|---|---|
| 项目仪表盘 | 必须有 | 无所谓 | 无所谓 | 张工是核心用户，优先级高 |
| 模糊语义搜索 | 可以有 | 必须有 | 无所谓 | 小李的核心需求，中等优先级 |
| API 错误信息改进 | 无所谓 | 无所谓 | 必须有 | 陈工的核心需求，但用户量小，中等优先级 |

### 在可用性测试中招募对应用户

如果画像说"小李是不懂技术术语的新人"，你的可用性测试应该招募符合这个特征的人——而不是找团队内部的同事。内部同事太了解产品了，他们的反馈不能代表真实用户。

## 实践建议

1. **3-5 个画像覆盖核心用户群**：少于 3 个会遗漏重要用户视角，超过 5 个团队记不住。如果你有 10 个画像，等于没有画像——没人能在讨论中清晰区分 10 个虚构人物
2. **从原型画像开始，用调研修正**：花 2 小时和团队画原型画像，然后通过用户访谈验证和修正。不要等"完美的调研数据"——完美的画像是迭代出来的，不是一次性画对的
3. **画像是活文档**：用户行为变化、产品覆盖新人群、竞品改变了用户预期——这些都会让画像过时。每半年回顾一次画像是否仍然准确
4. **画像必须有"反画像"——明确谁不是你的用户**：知道"我们不是为谁而做"和知道"我们为谁而做"同样重要。如果某个功能是为"所有人"做的，你需要重新审视你的范围

## 反模式

| 反模式 | 为什么失败 | 正确做法 |
|---|---|---|
| 画像只有人口信息没有行为场景——"25-35 岁、本科学历、一线城市" | 这是营销画像，不是产品画像。知道年龄和学历不能告诉你用户为什么用/不用你的产品 | 聚焦行为、场景、目标和痛点。年龄和学历在有行为上下文时才有意义 |
| 画像画完贴墙上就忘——PRD 中不引用、评审时不对照 | 画像变成了墙上的装饰画，对实际工作零影响 | 每个用户故事关联一个画像。评审时问："张工会怎么用这个功能？小李会怎么理解这个提示文案？" |
| 只画理想用户——画像全是"重度用户、技术达人、爱尝鲜" | 团队只为理想用户设计功能，忽略了真实用户的多样性和"不完美"的使用行为 | 必须包含至少一个"非理想用户"画像——新用户、偶尔使用者、被动使用者 |
| 一个人画完画像发给团队——没有协作产出的画像没有认同感 | 团队成员不认同画像（"这不是我们的用户"），继续按各自脑中的用户设计 | 工作坊模式：PM + 设计师 + 工程师 2-4 小时共同产出。参与即认同 |
| 画像过于详细——3 页文档描述一个虚构人物的生平细节 | 没人读完；核心信息被细节淹没 | 一页纸/人。只保留对产品决策有直接影响的 5 个要素。不是传记，是决策工具 |
