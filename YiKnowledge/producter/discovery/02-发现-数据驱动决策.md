# 数据驱动产品决策

> **适用场景**：当在多个产品方向间犹豫不决、当需要验证功能是否真的有效、或当干系人对下一步方向有分歧时。数据不能替你做决策，但能让决策从"我觉得"变成"数据表明"。

## 核心原则

数据驱动决策不是"让数据替你决策"。数据告诉你**正在发生什么**和**发生了什么变化**，用户研究告诉你**为什么会这样**。数据 + 洞察 = 决策。只有数据 = 盲人摸象。

四种核心方法的使用顺序：

```
指标拆解 → 找到瓶颈 → 漏斗分析 → 定位问题 → A/B 测试 → 验证方案 → 用户分群 → 细化策略
```

## 方法一：指标拆解树

### 适用场景

当北极星指标出现波动（上升或下降）时，你需要知道**到底是哪个环节在变化**。

### 方法

将北极星指标按用户行为路径拆解为输入指标的乘积，逐个排查。

**公式**：

```
北极星指标 = 流量 × 激活率 × 使用频率 × 留存率
```

### YrY 案例：YiPet 知识底座会话数下降

**问题**：本周有知识底座的日活跃会话数下降了 30%。

**拆解**：

```
日知识底座会话数
  = 日活跃用户数 × 知识树打开率 × 文件选择率 × 每次会话的消息数
     ↓               ↓               ↓              ↓
  100 → 95        40% → 35%       60% → 61%      5.2 → 5.1
  （-5%）         （-12.5%⚠️）    （+1.7%）      （-2%）
```

**结论**：用户数基本稳定，但知识树打开率下降了 12.5%。问题不在"用户少了"，而在"用户不用知识树了"。

**下一步**：检查知识树的入口是否有变更？最近版本中入口是否被移动或隐藏了？

### 拆解步骤

1. **列出北极星指标的乘法公式**：指标 = A × B × C。确保公式是数学恒等式（等号两边单位一致）
2. **拉取各因子的趋势数据**：过去 4 周的周均值，找出变化最剧烈的因子
3. **对变化最大的因子做进一步拆解**：重复直到无法再拆解或找到可行动的瓶颈点
4. **确认不是一个因子早已存在**：有些"发现"其实一直在那里，只是你第一次看数据而已

## 方法二：漏斗分析

### 适用场景

当用户没有像你预期的那样走完核心流程时——比如很多人到了注册页但很少完成注册，或者很多人看了功能但没使用。

### 方法

将用户的核心行为路径可视化，找出流失最严重的步骤。

**不是为了看"总转化率"，而是找出"哪一步流失最多"**。

### YrY 案例：YiVad 项目创建漏斗

假设数据如下：

```
进入 YiVad                   100%  (10,000 次访问)
  → 打开项目管理页            45%   (4,500)
    → 点击"创建项目"按钮      22%   (2,200)
      → 填写项目信息并提交     8%    (800)
        → 创建后 7 天内活跃   3%    (300)
```

| 步骤间转化 | 转化率 | 流失率 | 判断 |
|---|---|---|---|
| 访问 → 打开项目管理 | 45% | 55% | 入口可见性可能不足——55% 的访问者根本没看到项目管理入口 |
| 打开 → 点击创建 | 49% | 51% | CTA 不够突出或有其他因素分散注意力 |
| 点击 → 填写提交 | 36% | 64% | 创建表单可能太复杂、必填字段太多——这是最大流失点 |
| 提交 → 7 天活跃 | 38% | 62% | 项目创建后缺乏引导，用户不知道下一步该做什么 |

**行动建议**：
- 优先解决最大流失点——"填写提交"环节 64% 流失率。减少必填字段、提供 Demo 数据预填充、支持从模板创建
- 其次解决"7 天活跃"——创建成功后给出引导提示："下一步：创建第一个任务"、"导入你的数据"

### 漏斗分析黄金规则

1. **每一步只看上一步的转化率**，不累积计算。累积转化率掩盖了具体哪一步出问题
2. **对比不同时间段的漏斗**：本周 vs 上周、新用户 vs 老用户。差异揭示问题
3. **区分必要流失和可避免流失**：有些步骤用户"必须"离开（如查看产品介绍后离开的非目标用户），这不叫流失

## 方法三：A/B 测试设计

### 适用场景

当你有两个方案但不确定哪个更好，且两者的差异可以通过数据衡量时。

### 不是所有决策都需要 A/B 测试

| 适合 A/B 测试 | 不适合 A/B 测试 |
|---|---|
| UI 元素的颜色/位置/文案对比 | 全新功能的有无对比（先上线再说，不做测试会错过窗口） |
| 流程步骤数量的增减 | 战略级产品方向变更（不能靠一周的用户行为决定产品方向） |
| 算法参数的微调 | 用户量太小（< 1000 DAU，结果无统计意义） |

### A/B 测试设计模板

**测试目标**：一句话说清楚要验证什么。"提升 YiPet 知识树打开率"不是目标——"验证将知识树入口从二级菜单改到工具栏首位能否提升打开率"才是。

**假设**：如果 {{变更}}，则 {{指标}} 会 {{方向}}，因为 {{理由}}。

示例："如果将知识树入口从二级菜单改到工具栏首位，则知识树打开率会提升，因为用户在聊天界面始终能看到入口，减少了一步点击。"

| 设计要素 | 内容 |
|---|---|
| 对照组 A | 现有设计——知识树入口在菜单中 |
| 实验组 B | 新设计——知识树入口在聊天工具栏首位，带图标 + 文字 |
| 核心指标 | 知识树打开率（首要指标） |
| 辅助指标 | 聊天会话数（不能因为打开率提升而聊天少了）、工具栏其他按钮点击率（不能因为新增入口而稀释其他功能） |
| 样本量 | 每组至少 500 用户（基于当前 DAU 和预期效应量估算） |
| 测试时长 | 至少 7 天（覆盖一周的用户行为周期） |
| 成功标准 | 知识树打开率提升 ≥ 15%，且辅助指标无显著下降 |

### 结果解读

| 结果 | 核心指标 | 辅助指标 | 下一步 |
|---|---|---|---|
| 明确成功 | 显著提升 | 无下降 | 全量发布 |
| 明确失败 | 无变化或下降 | — | 回退，分析为什么假设不成立 |
| 部分成功 | 提升但未达标 | 无下降 | 结合用户反馈判断——可能优化方向对了但力度不够 |
| 可疑 | 提升 | 辅助指标下降 | 这是最危险的结果——可能是以损害其他功能为代价。需要进一步分析 |

### 统计陷阱

- **过早下结论**：测了 2 天看到提升就全量。用户行为的前 2 天有新奇效应（novelty effect）——新东西总会被多看一眼
- **频繁看结果**：每天看一次结果，看到显著就停。这是"偷看效应"（peeking）——应该预设测试时长，到期再做判断
- **忽视负面指标**：只看核心指标上升，不管辅助指标下降。用户体验是系统的，一个环节的提升可能导致另一个环节的恶化

## 方法四：用户分群分析

### 适用场景

当整体指标看起来正常，但你想知道"是所有用户都正常，还是有人特别好、有人特别差"。

### 常用分群维度

| 分群维度 | 分群示例 | 可用于回答的问题 |
|---|---|---|
| 行为 | 重度/中度/轻度用户 | "核心功能是哪些用户在深度使用？有没有我们不知道的超级用户？" |
| 来源 | 自然流量/推广流量/直接访问 | "推广来的用户留存率如何？和自然用户有差距吗？" |
| 时间 | 本周新用户/本月新用户/老用户 | "新用户的第一周行为和老用户当初有什么不同？" |
| 角色 | 管理员/编辑者/查看者 | "不同权限级别的用户使用模式有什么差异？" |

### YrY 案例：YiPet 用户分群

将 YiPet 用户按使用知识底座的频率分群：

| 分群 | 占比 | 每周会话数 | 会话满意度 | 典型行为 |
|---|---|---|---|---|
| 知识底座深度用户 | 15% | 20+ | 85% | 每次聊天都设置知识范围，频繁切换知识文件 |
| 偶尔使用者 | 30% | 5-10 | 60% | 偶尔使用知识底座，大多数时候用通用模式聊天 |
| 从未使用 | 55% | 3-5 | 50% | 只使用通用 AI 聊天，不知道/不理解知识底座功能 |

**关键洞察**：深度用户不仅用得更多，满意度也显著更高（85% vs 50%）。这说明知识底座功能一旦被理解和采用，用户价值显著。55% 的未使用用户是最大机会。

**行动**：针对 55% 未使用用户的引导策略——首次打开知识树时展示引导提示，说明"知识底座能让你基于 YrY 自己的知识库提问，而不是通用 AI 回答"。

## 数据质量检查

在相信数据告诉你的事情之前，先检查数据本身是否可靠：

- [ ] **数据来源一致**：同一指标的数值在多个数据源中是否一致？前端埋点和后端日志的数据如果差 30%，以哪个为准？选定一个权威数据源，在指标定义中明确标注
- [ ] **定义没有歧义**："活跃用户"在团队中有统一定义吗？登录=活跃？还是执行了核心操作=活跃？
- [ ] **没有跟踪中断**：埋点代码是否因为最近的代码变更而失效？一次无关的重构可能改掉关键埋点的事件名称
- [ ] **时间段可比**：在做同比/环比比较时，时间段是否可比？包含节假日的一周和不含节假日的一周不可比
- [ ] **样本量足够**：基于 30 个用户的数据做出的决策和基于 300 个用户的数据做出的决策，可信度完全不同

## YrY 项目的数据源

| 项目 | 可用数据源 | 能回答的问题 |
|---|---|---|
| YiVad | `sessions` 集合（聊天行为）、`bugs` 集合（用户反馈）、`projects` 集合（项目活跃度） | 哪些项目最活跃？用户什么时候在聊天？什么类型的 bug 最多？ |
| YiAi | 服务日志（API 调用量、响应时间、错误率、模型加载状态） | API 性能如何？哪些模块调用最多？什么错误最常见？ |
| YiPet | Chrome 扩展使用数据（通过 YiAi 会话记录） | 用户在什么网页上使用扩展？知识底座功能的使用频率？ |

**当前数据能力的限制**：YrY 项目尚未建立统一的数据埋点和分析平台。大部分数据需要通过 YiAi 的 MongoDB 集合查询获得。建议在核心用户流程中逐步加入关键事件埋点。

## 实践建议

1. **先用数据发现问题，再用用户研究理解原因**：数据告诉你"知识树打开率下降了 12.5%"，用户访谈告诉你"因为我找不到入口了"
2. **指标要少而精**：追踪 5 个关键指标并理解它们的驱动因素 > 追踪 50 个指标但从不深入分析任何一个
3. **数据不是答案，是提问的线索**：数据告诉你"这里有问题"，但不告诉你"怎么解决"。解决方案仍然需要产品判断
4. **定期做数据回顾**：每周花 30 分钟看关键指标趋势。不是等"出问题"才看数据——健康检查的价值在于提前发现异常

## 反模式

| 反模式 | 为什么失败 | 正确做法 |
|---|---|---|
| 数据挑选（Cherry-picking） | 只看支持自己观点的数据，忽略反面证据。"这个功能上线后 3 个用户说好"不等于"功能成功" | 预设成功标准再上线。上线后看全量数据，包括负面指标 |
| 用数据替代用户研究 | "数据说用户在这个页面停留了 3 分钟"——是在认真阅读还是在困惑地找东西？数据不说原因 | 数据告诉你发生了什么，用户研究告诉你为什么。两者互补 |
| 过度分析（Analysis Paralysis） | 花了 2 周分析数据，市场窗口已经过去。完美的数据不如及时的决策 | 分析限时：小决策 1 天内完成分析，大决策 1 周内。到时间就基于现有最佳数据做决策 |
| 忽视小样本偏差 | 基于 20 个用户的 A/B 测试结果做决策。小样本的统计波动可以轻松掩盖或夸大数据差异 | 在分析中标注样本量。样本量 < 100 时结论仅供参考，不做决策依据 |
| 把所有指标都当目标 | 设了 10 个 KPI，团队不知道该优化哪个。指标之间经常互斥 | 北极星指标只有一个（参见 [01-指标-北极星指标.md](./metrics/01-指标-北极星指标.md)），其他都是诊断指标 |
