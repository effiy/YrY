# MoSCoW 优先级排序

> **MoSCoW 通过将每个功能分入四个桶中，强制做出明确的范围决策。** 它是最简单的优先级排序框架——没有数字、没有公式，只有清晰的分类。它的力量不在于"算出"优先级，而在于"对话出"优先级：MoSCoW 是一个对话工具，而非计算工具。

## 四大分类

| 分类 | 含义 | 经验占比 | YrY 示例（YiVad Agent 功能） |
|---|---|---|---|
| **Must have（必须有）** | 没有它，这个版本就是失败的。不可协商。 | ≤ 总工作量的 60% | Agent 能从案例数据中生成报告草稿 |
| **Should have（应该有）** | 重要但非关键。实在不行可以延后。 | 约 20% | 多语言输出（中文 + 英文） |
| **Could have（可以有）** | 锦上添花。有时间就做，没时间就延。 | 约 20% | 报告草稿中标注来源文件引用 |
| **Won't have（不做）** | 明确排除在本版本之外。不是说"也许以后"——是"这版不做"。 | 记录在案 | 多级审批工作流 |

## 使用方法

1. **列出所有候选功能** — 任何人提过的任何想法都放上来
2. **先圈 Must have** — 问自己：哪些功能的缺失会导致本版本无法发布？
3. **执行 60% 规则** — 如果 Must have 估算工作量超过总量的 60%，说明你圈了太多。挑其中一部分降级为 Should have
4. **明确 Won't have** — 任何不在 Must/Should/Could 里的，都属于 Won't have。不要留空——Won't have 列表越明确，需求蔓延越少
5. **与干系人对齐** — MoSCoW 是对话工具，不是独自做完就通知。与工程和业务干系人一起评审分类，确保技术可行性和业务优先级一致

## Must have 判定测试

每当你标记一个功能为 Must have，问自己：

> "如果这个版本发布时不包含这个功能，我们会不会选择推迟发布？"

- **"会推迟"** → Must have（这个功能确实是版本的基石）
- **"不会推迟，但会很遗憾"** → Should have（重要但不致命）
- **"不会推迟，下次做也行"** → Could have

## MoSCoW 与 RICE 的配合使用

MoSCoW 给你四个桶，但它不告诉你同一个桶里先做哪个。这就是 RICE 的用武之地：

```
第一步（MoSCoW）：将所有功能分为 M / S / C / W 四个桶
第二步（RICE）：在每个桶内用 RICE 评分排序
```

**示例（YiVad Agent 功能的优先级排序）**：

| 桶 | 功能 | RICE 评分 | 排序 |
|---|---|---|---|
| Must | 报告草稿生成 | 600 | 1 |
| Must | 案例数据解析 | 450 | 2 |
| Must | 标准格式输出 | 320 | 3 |
| Should | 多语言输出 | 200 | 4 |
| Should | 在线编辑草稿 | 180 | 5 |
| Could | 来源引用标注 | 90 | 6 |
| Could | 导出为 Word | 75 | 7 |

## 在 YrY 中的实践

### 单项目版本规划（YiVad 示例）

YiVad 的某个版本要上线 Agent 功能。使用 MoSCoW 做范围控制：

| 分类 | 功能 |
|---|---|
| **Must** | Agent 对话界面、报告草稿生成、草稿提交保存 |
| **Should** | 报告中文/英文切换、草稿编辑功能 |
| **Could** | 报告导出 PDF/Word、报告模板选择 |
| **Won't** | 审批流程、外部系统对接、自定义品牌样式 |

### 跨项目版本规划

当 YiPet 和 YiAi 需要协作时，MoSCoW 帮助双方对齐优先级：

| 分类 | YiPet | YiAi |
|---|---|---|
| **Must** | 知识树浏览 + 范围选择 UI | RAG 混合检索 API |
| **Should** | 来源引用预览 | 检索结果高亮标记 |
| **Could** | 多文件同时选择 | 检索缓存优化 |
| **Won't** | 离线知识缓存 | 多模型检索 A/B 测试 |

## 实践建议

1. **用故事点而非功能数量来算占比**："Must have 有 3 个功能"不等于"工作量 30%"。一个 Must have 可能需要 13 个故事点，而 3 个 Could have 各需要 1 个点。始终用工时/故事点来计算 60% 规则
2. **Won't have 写得和 Must have 一样详细**：明确的 Won't have 列表管理干系人预期。评审时有人说"能不能也加上 X"，你可以指着 Won't have 列表说"X 已经明确在这个版本不做了"
3. **工程师参与 Must have 工作量评估**：PM 标记一个功能为 Must have，但如果工程师评估它需要 8 周而整个版本只有 4 周，那它就不是 Must have——因为不可能完成。Must have 的判断必须结合工程可行性
4. **版本范围锁定后不再加 Must**：版本规划一旦确定，只降不升（功能只能从 Must 往 Should/Could 降，不能反向）。中途新需求进 Won't have 列表，下个版本再评估

## 反模式

- **所有东西都是 Must have。** 如果每个功能都"必须"，那就没有一个真的必须。严格执行 60% 规则：如果 Must have 超过 60%，就削减。这是 MoSCoW 最重要也最难遵守的规则
- **Won't have 是空的。** 一个空的 Won't have 列表示你没有做真正的取舍。每个版本都有不做的东西——Won't have 列应该是最长的列之一
- **只用 MoSCoW 做排序。** MoSCoW 给你四个桶，不给桶内顺序。在 Must have 桶中，你仍然需要知道先做哪个。配合 RICE/ICE 使用
- **干系人定义 Must have 而不咨询工程团队。** 一个功能如果需要 80% 的版本预算，那它不能是 Must have——除非它是唯一的功能。工作量评估限制着 Must have 桶的大小
- **MoSCoW 做完了但团队不知道。** 如果你在会议室里做好分类但没和开发团队同步，那等于没做。MoSCoW 的结果必须在 Sprint 规划时与团队共享和确认

## 完整实操示例：YiVad Q4 版本规划

以下是从零开始完成一次 MoSCoW 版本规划的完整过程。

### 背景

YiVad Q4 版本的目标是"从查找变管理"——让项目管理员不再靠翻页面和记笔记来掌控项目状态。团队 2 名工程师，4 周开发时间，根据容量公式：

```
可用工时 = 2 人 × 20 工作日 × 6 小时 = 240 小时
实际容量 = 240 × 0.8（预留 20% 用于会议和 Bug 修复）= 192 小时 ≈ 24 故事点
```

### 候选功能清单

团队头脑风暴 + 用户反馈收集后产生的候选功能：

| ID | 功能 | 描述 | 预估故事点 |
|---|---|---|---|
| F1 | 项目仪表盘 | 首页展示所有项目的关键状态：问题分布、进度、阻塞项 | 8 |
| F2 | 逾期问题自动标记 | 超过截止日期的问题红色标记 + 排序置顶 | 3 |
| F3 | 一键项目周报 | 选择项目自动生成包含问题/周期/风险的周报摘要 | 5 |
| F4 | 项目模板 | 从模板创建新项目（预设问题类型、周期配置） | 5 |
| F5 | 批量操作 | 多选问题后批量更改状态/指派人 | 3 |
| F6 | 深色模式全站覆盖 | 所有页面支持深色主题切换 | 5 |
| F7 | ProTable 列自定义 | 用户可自定义表格的显示列和顺序 | 3 |
| F8 | 数据导出 Excel | 问题列表、项目数据导出为 Excel 文件 | 2 |
| F9 | 智能提醒推送 | 过期问题桌面通知 + YiPet 扩展通知 | 8 |
| F10 | 移动端适配 | 核心页面（项目列表、问题详情）移动端可用 | 13 |

**总候选故事点：55 点。可用容量：24 点。必须砍掉 56%。**

### 第一轮：圈 Must have（执行 60% 规则）

Must have 判定测试：**"如果这个版本不包含这个功能，我们会不会推迟发布？"**

| 功能 | 判定 | 理由 |
|---|---|---|
| F1 项目仪表盘 | **会推迟** → Must | 这是版本目标"从查找变管理"的核心载体——没有仪表盘等于没有这个版本 |
| F2 逾期问题自动标记 | **会推迟** → Must | 用户在仪表盘上看到问题但不能一眼识别哪些是紧急的——仪表盘的价值减半 |
| F3 一键项目周报 | 不会推迟 → Should | 重要但非致命。手动收集数据也能写周报，只是慢 |
| F4 项目模板 | 不会推迟 → Should | 新用户的痛点，但不影响现有用户的核心流程 |
| F5 批量操作 | 不会推迟 → Should | 省时间但不改变管理方式 |
| F6-F10 | 逐个判定 | 见下文 |

**Must have 故事点：F1(8) + F2(3) = 11 点。占比 11/24 = 46%。** 在 60% 以内，合理。

### 第二轮：分配 Should/Could/Won't

剩余 14 故事点空间（24 - 11 = 13 点，预留 1 点缓冲）。

| 功能 | 故事点 | 分配 | 理由 |
|---|---|---|---|
| F3 一键项目周报 | 5 | Should | 仪表盘给了"看到问题"的能力，周报给了"汇报问题"的能力——两者互补 |
| F4 项目模板 | 5 | Should | 降低新用户上手门槛，间接推动北极星指标（活跃项目数） |
| F5 批量操作 | 3 | Should | 3 点换日常效率，投入产出比高 |
| F7 ProTable 列自定义 | 3 | Could | 锦上添花，有仪表盘后表格使用频率可能下降 |
| F8 数据导出 Excel | 2 | Could | 部分用户需要，但 Dashboard 的在线查看会降低导出需求 |
| F6 深色模式 | 5 | Won't | 重要但本版本目标不在此。放入下一个版本的 Should |
| F9 智能提醒 | 8 | Won't | 依赖 YiAi 通知机制，跨项目依赖未就绪。放入下下版本 |
| F10 移动端适配 | 13 | Won't | 13 点一个人做不完、两个人做不值得。明确的远期功能 |

**Should 合计：5+5+3 = 13 点。刚好填满剩余容量。**

### 第三轮：桶内 RICE 排序

MoSCoW 给了桶，桶内用 RICE 排顺序：

| 桶 | 功能 | RICE | 排序 | 建议开发顺序 |
|---|---|---|---|---|
| Must | F1 项目仪表盘 | 480 | 1 | Week 1-2 主力 |
| Must | F2 逾期自动标记 | 320 | 2 | Week 2（仪表盘骨架完成后） |
| Should | F5 批量操作 | 200 | 3 | Week 3（性价比最高，3 点换日常效率） |
| Should | F3 一键周报 | 150 | 4 | Week 3-4 |
| Should | F4 项目模板 | 120 | 5 | Week 4 |
| Could | F7 列自定义 | 80 | 6 | 时间有剩才做 |
| Could | F8 数据导出 | 60 | 7 | 时间有剩才做 |

### 第四轮：干系人对齐

与 YiVad 开发团队 + 设计干系人的评审会（30 分钟）：

| 讨论点 | 结论 |
|---|---|
| "项目模板不应该只是 Should——我们一直在说新用户上手难" | 同意优先级上调。但它仍是 Should 而非 Must——因为它解决的是新用户问题，而本版本目标是现有用户的"管理效率"——不冲突但是次优先级 |
| "数据导出和仪表盘会不会互斥——仪表盘是让人在线看，导出是下载了看" | 观察点——如果仪表盘做得好，导出需求自然下降。如果仪表盘上线后导出需求仍在，说明仪表盘没有替代导出场景。下个版本根据数据判断 |
| "Won't 里的智能提醒——我们什么时候做？" | 需要 YiAi 先提供通知机制 API。YiAi PM 确认 Q1 可能就绪。届时本功能进入下个版本的 Should |

### 第五轮：版本锁定

MoSCoW 结果正式锁定——任何要求将 Could/Won't 升级的请求必须附带"你愿意用 Must/Should 里的哪个来换？"

**本版本（YiVad Q4）MoSCoW 一览：**

| 分类 | 功能 | 故事点 |
|---|---|---|
| **Must** | 项目仪表盘、逾期问题自动标记 | 11 |
| **Should** | 批量操作、一键项目周报、项目模板 | 13 |
| **Could** | ProTable 列自定义、数据导出 Excel | 5 |
| **Won't** | 深色模式、智能提醒、移动端适配、其他未列出的所有功能 | 31 |

**容量检查**：Must(11) + Should(13) = 24 点 ≤ 24 点可用容量。Must 占比 46%，满足 60% 规则。版本锁定。
