# 机会解决方案树（OST）

> **适用场景**：当你有一个明确的业务成果目标，但不确定"从哪开始"和"先做什么"时。OST 不是另一个优先级框架——它是帮助你在发现阶段结构化思考"我们有哪些选择，为什么选这个而不选那个"的视觉工具。

## OST 解决什么问题

传统的产品发现流程通常是：

```
有一个想法 → 验证这个想法好不好 → 好就做，不好就再想一个
```

这个流程的问题：**你只验证了你的第一个想法**。如果有 10 个可能的方案，你可能选了第 3 好的那个，因为它恰好是你先想到的。

OST 将流程变成：

```
有一个成果目标 → 识别所有可能的机会 → 对每个机会生成多个方案 → 选最好的方案实验验证
```

关键转变：**先穷举机会空间，再收敛到最优方案**。不是在第一个想法上优化，而是在所有可能的方向中找到最好的。

## OST 的四层结构

```
                     ┌─────────────┐
                     │   业务成果   │  ← 一个明确的、可衡量的目标
                     │  （Outcome） │
                     └──────┬──────┘
                            │
              ┌─────────────┼─────────────┐
              │             │             │
         ┌────▼────┐  ┌────▼────┐  ┌────▼────┐
         │ 机会 A   │  │ 机会 B   │  │ 机会 C   │  ← 用户未满足的需求/痛点
         │          │  │          │  │          │
         └────┬─────┘  └────┬─────┘  └────┬─────┘
              │             │             │
        ┌─────┼───┐    ┌────┼────┐   ┌────┼────┐
        │     │   │    │    │    │   │    │    │
      方案  方案 方案  方案 方案 方案  方案 方案 方案  ← 解决机会的具体方案
       A1   A2  A3   B1  B2  B3   C1  C2  C3
        │             │
    ┌───▼───┐     ┌───▼───┐
    │ 实验   │     │ 实验   │  ← 验证方案的最小可行测试
    └───────┘     └───────┘
```

### 第一层：业务成果（Outcome）

不是"我们要做什么功能"，而是"我们想要什么业务结果"。

| 差的成果描述 | 好的成果描述 |
|---|---|
| "做一个更好的搜索功能" | "用户能在 3 秒内找到目标知识文件" |
| "提升用户体验" | "新用户首周留存率从 20% 提升到 40%" |
| "增加用户活跃度" | "周活跃项目数翻倍" |

**成果的三个标准**：
1. **可衡量**：必须有量化的当前值和目标值
2. **有时间范围**：通常按季度或 Sprint 周期衡量
3. **业务导向**：不是功能完成（"上线搜索功能"），而是用户行为改变（"用户找到文件的时间缩短"）

### 第二层：机会（Opportunity）

机会是"用户未满足的需求、痛点或渴望"。它们是你实现成果的**路径**——每条机会回答"什么在阻碍用户达成我们想要的行为？"

**识别机会的方法**（按可靠性排序）：
1. **用户访谈**：问"你上一次做 X 的时候遇到了什么困难？"
2. **数据分析**：看漏斗中流失最严重的步骤
3. **用户反馈**：整理 Bug 报告和功能请求中的共性模式
4. **竞品分析**：竞品在哪方面比我们好？用户为什么选他们？

**机会陈述格式**：

```
{{用户群体}} 在 {{情境}} 下想要/需要 {{需求}}，但 {{障碍}}。
```

每个机会陈述必须基于证据——不能是你觉得"可能有"的机会。标注每一条机会的证据来源。

### 第三层：方案（Solution）

每个机会可以有多个解决方案。这一层的目标是**穷举再收敛**——先不评判方案好坏，把能想到的都列出来，再评估。

**方案生成规则**：
- 每个机会至少 3 个方案——迫使自己超过第一个想到的想法
- 方案可以是功能、流程优化、内容改进、引导设计——不只是"加个按钮"
- 方案之间可以互补——A 方案和 B 方案可以同时做

### 第四层：实验（Experiment）

不是对每个方案都做完整开发。先做最小可行实验来验证方案是否真的解决了机会。

| 方案类型 | 最小实验 |
|---|---|
| 新功能 | 手工模拟（Wizard of Oz）——后台由人手工完成，看起来像系统在运行 |
| UI 改版 | 可交互原型 + 5 人可用性测试 |
| 新流程 | 对 3 个用户做概念验证访谈："如果产品这样运作，你会用吗？" |
| 算法优化 | 离线数据集上跑新旧算法对比 |

## 如何构建 OST（工作坊 2-3 小时）

### 参与者：PM + 技术负责人 + 设计师

### Step 1：定义成果（15 分钟）

团队对"我们要达成什么业务成果"达成一致。如果对成果有分歧，停下来解决分歧——后面的所有工作都建立在这个共识上。

### Step 2：识别机会（45 分钟）

- 每人独立列出自己能想到的机会（5-10 分钟）
- 合并去重，贴在白板/在线白板上
- 每条机会标注证据来源（用户访谈/数据/反馈）
- 没有证据的机会标注为"待验证"——这不是说扔掉它，而是说你需要先验证它

### Step 3：评估机会（30 分钟）

对每条机会打分（1-5 分）：

| 评估维度 | 含义 |
|---|---|
| 影响范围 | 多少用户受这个痛点影响？ |
| 痛感强度 | 用户有多痛苦？是"有点烦"还是"没法工作"？ |
| 发生频率 | 用户多频繁遇到这个痛点？ |
| 与成果的关联 | 解决这个痛点多大程度上推动我们的成果？ |

得分最高的 2-3 个机会是你当前的重点。

### Step 4：生成方案（45 分钟）

对每个重点机会，头脑风暴可能的方案。先谈量（能想多少想多少），再谈质（评估可行性）。

### Step 5：选择实验（15 分钟）

选 1-3 个方案做实验验证。每个实验应有明确的"通过/不通过"标准。

## YrY OST 实例：YiPet 知识底座使用率

### 业务成果

> 有知识底座的会话占比从 15% 提升到 40%（H2 2026）

### 机会层

| 机会 | 证据来源 | 影响 × 痛感 × 频率 | 优先级 |
|---|---|---|---|
| O1：用户不知道知识底座存在——55% 的用户从未使用过 | 使用数据：从未使用者占 55%，其中 80% 在首次使用后 2 周内仍活跃（说明不是产品不好，是不知道） | 5×5×5 = 125 | **最高** |
| O2：找到需要的知识文件很慢——知道有这个功能但找不到对的文件 | 用户访谈：3/8 受访者说"不知道怎么搜到我想要的文件" | 3×4×3 = 36 | 中 |
| O3：不理解知识底座的价值——不清楚"基于知识库的回答"和"通用回答"有什么区别 | 用户反馈：新用户首周会话中，通用模式占 90% | 4×3×2 = 24 | 中 |
| O4：担心知识库内容太旧——不信任 AI 引用的知识 | 用户访谈：2/8 受访者提到"不确定这些知识是不是最新的" | 2×4×1 = 8 | 低（先解决，但不是最高优先级） |

### 方案层（以最高优先级机会 O1 为例）

**O1：用户不知道知识底座存在**

| 方案 | 描述 | 预期效果 | 实施难度 | 优先级 |
|---|---|---|---|---|
| S1：首次使用引导 | 用户第一次打开聊天窗口时，弹出一个 3 步引导，展示"试试知识底座" | 新用户知识底座首周使用率从 10% → 40% | 低 | **首选实验** |
| S2：知识树入口提到工具栏首位 | 将知识树入口从菜单移到聊天输入框上方，始终可见 | 知识树打开率从当前值提升 50% | 低 | 已在规划中 |
| S3：在聊天输入框内提示 | 用户在输入框输入文字时，如果未选择知识范围，显示灰色提示"选择知识文件，让回答更精准" | — | 低 | 备选 |
| S4：主动触发场景 | 当用户打开 YiPet 但未使用知识底座时，小气泡提示"你正在浏览的页面可能和 YiKnowledge 中的 X 文件相关" | — | 高 | 远期 |

### 实验层（S1：首次使用引导）

**实验**：为 20 个新用户提供首次使用引导，对比未收到引导的对照组。

| 实验设计 | 内容 |
|---|---|
| 假设 | 如果新用户首次打开聊天窗口时看到知识底座的 3 步引导，则首周知识底座使用率会从 10% 提升到 30%+，因为用户知道了这个功能的存在和价值 |
| 实验组 | 20 个新用户，首次打开聊天窗口时显示 3 步引导 |
| 对照组 | 20 个新用户，无引导 |
| 核心指标 | 首周至少使用 1 次知识底座的比例 |
| 成功标准 | 实验组 ≥ 30%（对照组预期 10%） |
| 实验周期 | 2 周 |

## OST 与其他框架的关系

| 框架 | 在 OST 中的位置 | 如何衔接 |
|---|---|---|
| **北极星指标** | 业务成果层 | 北极星指标是 OST 的起点——你希望推动什么成果？ |
| **JTBD** | 机会层 | JTBD 帮助你识别机会——用户想要完成什么任务但做不到？ |
| **用户画像** | 机会层 | 画像帮你判断"这个痛点是所有用户都有，还是只有某一类用户有？" |
| **用户故事地图** | 方案层 | 确定了优先方案后，用故事地图将方案展开为用户旅程中的具体故事 |
| **RICE/ICE** | 方案评估 | 多个方案间有分歧时，用 RICE 量化排序 |

**使用顺序**：OST（发现方向）→ 故事地图（展开细节）→ PRD（定义范围）→ RICE（排优先级）

## 实践建议

1. **OST 是活文档——每周更新**：每完成一个实验，把结果标注在树上。验证通过的方案向上推进，失败的方案标注"已验证不可行"并记录原因。一棵不更新的 OST 在 2 周内就会过时
2. **机会必须来自证据，不是来自脑补**：如果你列了 10 个机会但只有 3 个有证据支持，你的树只有 3 个有效的分支。其余 7 个是假设——标注"待验证"，然后去做用户研究
3. **不要跳过机会层直接跳到方案**：大多数 PM 犯的错误是"我有一个想法（方案），让我验证它"。跳过机会层意味着你不知道这个方案是对应哪个机会的——如果方案失败了，你不知道是方案本身不行还是机会不存在
4. **一棵树聚焦一个成果**：不要试图用一棵树解决所有问题。如果有 3 个不相关的成果目标，画 3 棵树
5. **分享 OST，而非只分享结论**：把树画出来给团队和干系人看——让他们看到"我们有哪些机会、为什么选这个方案、我们已经在实验中排除过哪些方案"。透明度建立信任

## 反模式

| 反模式 | 为什么失败 | 正确做法 |
|---|---|---|
| 方案在机会之前——"我觉得应该加一个 X 功能"，然后往上补机会 | OST 变成了给已有想法找借口的工具，失去了"穷举再收敛"的价值 | 严格从上到下：先定义成果，再识别机会，最后生成方案。如果脑中已经有方案，先记下来放在一边，等到了方案层再拿出来 |
| 机会层全是模糊的形容词——"用户觉得不好用"、"体验不够好" | 这些"机会"无法指导方案设计。什么叫"不好用"？哪个环节不好用？ | 机会必须是具体的、可观察的用户行为或反馈。用用户原话或数据事实描述，不用抽象的形容词 |
| 一棵树上挂太多成果——"我们要同时提升留存、活跃、转化、NPS" | 团队不知道在树上的哪个分支用力。每棵 OST 树只对应一个成果 | 一个成果一棵树。如果真的有 4 个成果需要推动，就画 4 棵独立的树，然后看哪些机会在树之间互相支撑 |
| 实验没有失败标准——每个实验都"学到了东西"但永远不排除方向 | 方案永远在验证中，永远不推进也不终止。OST 的目的是快速排除错误方向，而非无限探索 | 每个实验预设"通过/不通过"标准。通不过的方案标注"已验证不可行"并从树上移除。排除错误方向也是进展 |
| OST 画完锁在抽屉里——不和团队共享 | 团队不知道 PM 的决策逻辑，继续按各自的理解做事 | OST 应该贴在团队可见的地方（物理白板或在线白板）。评审和站会上引用 OST：我们当前在验证哪个机会的哪个方案？ |
