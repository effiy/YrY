# Kano 模型摘要

> **Kano 模型将功能按对用户满意度的影响分为五类。** 并非所有功能生而平等——有些是惊喜，有些是标配，有些用户根本不在乎。知道一个功能属于哪一类，决定了你该投入多少资源。

## 为什么需要 Kano 模型

产品经理经常面临一个困境：用户说"我想要 X 功能"，但 X 功能做出来以后，用户满意度没有提升。原因在于用户"想要"和用户"会因为有了它更满意"是两回事。Kano 模型帮你区分这两者。

## 五大功能类别

```
用户满意度 ↑
           │  ╱ 魅力型（超出预期 — 有了惊喜，没有也无所谓）
           │ ╱
           │╱
  ─────────┼───────────→ 功能实现程度
          ╱│
         ╱ │
        ╱  │ 基本型（标配 — 没有会愤怒，有了是应该的）
           │
           │  无差异型（用户不在乎）
           │  反向型（部分用户喜欢、部分用户厌恶）
```

| 类别 | 描述 | 满意度影响 | YrY 示例 |
|---|---|---|---|
| **基本型（Must-Be）** | 用户认为理所当然该有的——没有会非常不满，有了不会增加满意度 | 有：不加分；缺：大幅减分 | YiAi 生成的报告内容准确。准确是基本要求，不准确用户会离开 |
| **期望型（Performance）** | 越多越好——满意度随实现程度线性增长 | 实现越好满意度越高；实现越差满意度越低 | YiAi 生成报告的速度。30 秒比 60 秒更好，用户感知明显 |
| **魅力型（Attractive）** | 用户没想到但非常喜欢的——有了会大幅加分，没有也无所谓 | 有：大幅加分；缺：不减分 | 生成的报告自动标注每个段落的来源文件引用 |
| **无差异型（Indifferent）** | 用户不关心有还是没有 | 有无均无影响 | 改变报告生成按钮的颜色 |
| **反向型（Reverse）** | 部分用户喜欢，部分用户讨厌 | 效果因用户群体不同而分化 | 强制所有报告使用同一套模板（有人喜欢标准化，有人觉得死板） |

## Kano 类别随时间退化

功能类别会随时间按可预测的路径退化：

```
魅力型 → 期望型 → 基本型
```

今天让人惊艳的功能（魅力型），明天就是行业标配的竞争差异（期望型），后天就是用户觉得理所当然的基础功能（基本型）。

**经典案例**：Google Docs 的自动保存功能在 2010 年是魅力型功能（"太神奇了，我不用按 Ctrl+S 了！"）。今天，任何一个编辑器不支持自动保存都会被用户视为基本缺陷。这就是 Kano 退化的完整路径。

### 对 YrY 的启示

| 功能 | 当前类别 | 6 个月后 | 12 个月后 |
|---|---|---|---|
| YiPet 知识底座 RAG 回答 | 魅力型 | 期望型 | — |
| YiVad Agent 自动生成报告 | 魅力型 | 期望型 | — |
| YiAi API 响应速度 < 1 秒 | 期望型 | 基本型 | 基本型 |
| 移动端适配 | 魅力型 | 期望型 | — |

**策略建议**：不要把研发资源只投入基本型和期望型功能。基本型功能是"入场券"——做好是本分。魅力型功能是"差异化"——至少需要一个魅力型功能才能让用户选择你而非竞品。

## Kano 问卷法

对每个功能问两个问题，通过矩阵分析确定分类：

1. **功能性问题**："如果这个功能**有**，你感觉如何？"
2. **反向问题**："如果这个功能**没有**，你感觉如何？"

答案选项：喜欢 / 理所当然 / 无所谓 / 勉强接受 / 不喜欢

### 评估矩阵

| 功能性问题 ↓ / 反向问题 → | 喜欢 | 理所当然 | 无所谓 | 勉强接受 | 不喜欢 |
|---|---|---|---|---|---|
| **喜欢** | Q（可疑） | A（魅力） | A（魅力） | A（魅力） | P（期望） |
| **理所当然** | R（反向） | I（无差异） | I（无差异） | I（无差异） | M（基本） |
| **无所谓** | R（反向） | I（无差异） | I（无差异） | I（无差异） | M（基本） |
| **勉强接受** | R（反向） | I（无差异） | I（无差异） | I（无差异） | M（基本） |
| **不喜欢** | R（反向） | R（反向） | R（反向） | R（反向） | Q（可疑） |

> A=魅力型，P=期望型，M=基本型，I=无差异型，R=反向型，Q=可疑结果（逻辑矛盾，通常表示问题没被理解）

## 适用场景

- **功能发现阶段**：头脑风暴产生功能清单后，用 Kano 分类找出魅力型功能作为差异化重点
- **MVP 范围界定**：MVP 应包含所有基本型 + 评分最高的期望型 + 至少 1 个魅力型。一个魅力型功能抵十个无差异型功能
- **竞品分析**：将竞品功能映射到 Kano 类别中，找到竞品尚未覆盖的魅力型机会空间

## 如何在 YrY 中实践 Kano

### 实操流程（轻量版，适合小团队）

1. **列出候选功能**（10-20 个）：团队头脑风暴后产出功能清单
2. **团队打分**（每人 15 分钟）：PM + 技术负责人各自将功能分类为 M/P/A/I/R
3. **讨论分歧**（30 分钟）：重点讨论分类不一致的功能。有分歧通常意味着对用户需求理解不一致
4. **确定分类**：绝大多数同意即为最终分类。无人同意的功能通常是可放弃的

### YiPet Kano 分类示例

| 功能 | 分类 | 理由 |
|---|---|---|
| 知识树浏览和选择 | 基本型 | 知识底座的入口，没有这个功能整个特性无法使用 |
| RAG 回答质量（引用准确性） | 基本型 | 引用不准确会直接摧毁用户对功能的信任 |
| 回答速度 | 期望型 | 越快越好，用户感知明显 |
| 选中文字即可提问 | 魅力型 | 超出用户预期——他们没想过浏览器里选中文字就能查知识库 |
| 多文件同时选为知识范围 | 期望型 | 用户有组合查询的需求，但不是所有场景都需要 |
| 自动推荐相关文件 | 魅力型 | 用户选了一个文件后系统智能推荐相关文件 |

## 反模式

- **只做基本型功能。** 这样永远不会流失用户，但也永远不会赢得用户。基本型是入场券，不是竞争力。如果你做的所有功能都是"应该有的"，用户不会因为你的产品更好而选择你
- **凭感觉猜测魅力型功能。** 魅力型功能的定义是"出乎意料的惊喜"——如果产品经理能猜出来，那就不叫惊喜了。必须通过用户调研（Kano 问卷）来发现，而非在会议室里头脑风暴
- **过度投入无差异型功能。** "用户说他们想要这个"不等于"有了这个他们会更满意"。用户礼貌地说"这个挺好"和用户真正在乎是两回事。用 Kano 问卷区分真实需求和礼貌性反馈
- **忽视 Kano 退化。** 一个去年还是魅力型的功能，今年可能已经退化到基本型。你的差异化优势在持续缩水。每半年重新评估一次关键功能的 Kano 分类
