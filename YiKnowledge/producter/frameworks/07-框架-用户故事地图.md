# 用户故事地图

> **适用场景**：在新功能或新产品启动时。故事地图将扁平的积压需求转化为可视化的用户旅程图谱——清晰地展示先做什么、后做什么、以及明确不做什么。它让团队在动手编码之前，对"我们要构建什么"达成一致的视觉理解。

## 为什么需要故事地图

传统的需求积压是一个扁平的列表——第 1 项和第 50 项之间没有任何关系。团队成员在讨论"这个版本要做什么"时，面对一个 50 项的列表，通常只能靠直觉挑选。结果往往是：做出来的功能覆盖了某些用户步骤但遗漏了另一些，导致整个流程不可用。

故事地图通过两个维度（横向的用户旅程 + 纵向的优先级）解决这个问题。它让团队一眼看到：
- 用户从头到尾要经历哪些步骤
- 每个步骤下有哪些功能
- 第一个版本（MVP）的最小范围在哪

## 故事地图的结构

故事地图有两个维度：

```
横向：用户旅程（从左到右）—— 地图的主干
纵向：优先级（从上到下）—— 必须有 → 应该有 → 可以有 → 不做
```

### 主干（用户活动）

主干描述用户从头到尾的活动流程：

```
浏览商品  →  搜索商品  →  对比商品  →  加入购物车  →  结账  →  追踪订单
```

每项活动用一个简洁的动词短语描述，从左到右按用户执行的时间顺序排列。

### 用户故事层

在每个活动下方，按优先级纵向堆叠用户故事：

```
浏览商品
├─ [必须有]   查看带图片和价格的商品列表
├─ [必须有]   按分类筛选
├─ [应该有]   按价格、评分、最新排序
├─ [可以有]   网格/列表视图切换
└─ [这版不做]  AR 预览商品在房间中的效果
```

## 故事地图工作坊

### 参与者（3-5 人）

| 角色 | 职责 | 为什么需要 |
|---|---|---|
| 产品经理（主持） | 引导流程、控制节奏、确保不偏离目标 | PM 对用户需求最了解 |
| 1-2 名工程师 | 补充技术可行性判断、估算复杂度 | 防止地图上有"技术上不可能"的故事 |
| 设计师（如果团队有） | 补充交互逻辑、视觉流 | 避免忽略关键交互状态 |
| 干系人（可选） | 提供业务上下文 | 确保地图覆盖业务需求 |

### 流程（2-3 小时）

#### 1. 明确目标（10 分钟）

一句话："我们要构建 {{产品/功能}}，让 {{用户}} 能够 {{成果}}。"

举例："我们要构建 YiPet 的知识底座功能，让用户在浏览任意网页时能够基于 YrY 知识库发起精准的 AI 对话。"

#### 2. 绘制主干（20 分钟）

- 把每个用户活动写在一张便利贴上
- 从左到右按时间顺序排列
- 不用担心是否完整——后续可以补
- 检验标准：一个不了解你产品的人能不能顺着主干看懂用户的整体流程？

#### 3. 添加用户故事（45 分钟）

- 对每个活动，头脑风暴可能需要的用户故事
- 每个故事写一张便利贴
- 放在对应活动下面
- 这个阶段不排优先级——先穷举再收敛

#### 4. 纵向优先级排序（30 分钟）

- 第一行：**必须有** — 没有这些，用户根本无法完成目标
- 第二行：**应该有** — 重要但非致命，第一版可以没有
- 第三行：**可以有** — 锦上添花
- 最底行：**本版不做** — 明确排除，写入 Won't have 清单

### 排序判定标准

当你和团队对某个故事的位置有分歧时，问三个问题：
1. "没有这个故事，用户还能完成他们的目标吗？"（不能 = 必须有）
2. "没有这个故事，用户体验会显著下降吗？"（会 = 应该有）
3. "这个故事是我们主动推迟到下一版也不会有人强烈反对的吗？"（是 = 可以有/不做）

## 版本切片

在地图上画一条水平线，定义每个版本的范围：

```
版本 1 (MVP)：仅"必须有"行
版本 2：      "必须有" + "应该有"行
版本 3：      全部（"必须有" + "应该有" + "可以有"）
```

### MVP 定义

MVP 是能交付用户价值的最薄横切面：

> "我们能构建的、用户真正会使用的最小东西是什么？"

**MVP 切片的三项验证**：
- [ ] 是否覆盖了完整的用户旅程（从左到右无断点）？如果某个步骤完全空白，用户在中间就卡住了
- [ ] 仅靠 MVP 中的故事，用户能否完成他们的核心目标？能完成但体验不够好 → 这是 MVP。根本完不成 → 这不是 MVP
- [ ] MVP 中是否有可以进一步延迟的内容？如果还能砍，说明 MVP 还不够小。精益求精地裁剪是 MVP 定义的核心能力

## YrY 案例：YiPet 知识底座功能

### 主干

```
浏览知识树  →  选择范围  →  提问  →  查看回答  →  优化范围
```

### 故事矩阵

| 活动 | 必须有 | 应该有 | 可以有 |
|---|---|---|---|
| **浏览知识树** | 扫描 YiKnowledge 目录树；展示文件夹和文件 | 在树内搜索文件 | 拖拽文件到聊天窗口 |
| **选择范围** | 点击文件/文件夹设置为 RAG 范围 | 当前活跃范围以标签形式显示 | 同时选择多个文件 |
| **提问** | 发送带知识底座的聊天消息 | 发送前预览将引用的源文件 | 自动拆解复杂问题为多个子问题 |
| **查看回答** | 带引用来源的流式回答 | 内联引用标注 | 源文件片段预览 |
| **优化范围** | 清除当前范围重新选择 | 在聊天输入框中 @mention 文件 | 自动推荐相关文件 |

### MVP 切片（版本 1）

仅包含 5 个活动中每个的"必须有"行 = 用户可以完成完整流程：浏览 → 选择 → 提问 → 查看 → 优化。

**不包含在 MVP 中**：搜索、多文件选择、@mention、自动推荐。这些功能本身有价值，但缺少它们不妨碍用户完成核心目标——选择一个知识文件然后基于它提问。

### 版本 2 规划

在 MVP 基础上加入所有"应该有"行 = 显著提升体验：搜索文件、多文件选择、@mention 文件。

## 实践建议

1. **地图是活文档**：每个 Sprint 结束后更新地图——删掉已完成的故事，调整剩余故事的优先级。地图腐烂只需两个 Sprint
2. **地图挂在墙上**：物理可视化优于数字工具。团队成员走过时看到地图，持续感知"我们在构建什么"。如果是远程团队，用 Miro/Figma 在线白板替代
3. **地图驱动价值交付而非功能堆积**：每个版本的切片应该是一个完整的用户旅程横截面，而非"把左边的功能全做完再做右边的"。用户从第一天起就能走通整个流程
4. **工作坊后拍照存档**：地图在讨论中是最有价值的，讨论结束后照片作为参考。不要让美化地图格式消耗宝贵时间

## 反模式

| 反模式 | 为什么失败 | 正确做法 |
|---|---|---|
| 只有扁平的积压列表（没有主干） | 缺乏用户旅程上下文；看不到流程中缺失的步骤 | 始终从主干开始——用户的端到端旅程。任何不放进旅程上下文中的故事都是没有方向的故事 |
| 所有故事都是"必须有" | 没有优先级；MVP 变成了完整产品。不排优先级的故事地图 = 无用的故事地图 | 严格区分：必须有 = 没有它功能就完全不可用。如果一个故事降级后功能仍然可用，那它就不是必须有 |
| PM 独自画地图 | 缺少工程可行性视角和设计交互视角。PM 画的地图往往技术不可行或设计不可用 | 工作坊模式：3-5 人，跨角色。故事地图是团队协作的产物，不是 PM 的独立交付物 |
| 地图静态不变 | 地图在两个 Sprint 后严重偏离现实；团队不再相信它 | 每个 Sprint 边界更新地图。最少在 Sprint 规划前花 15 分钟检查地图是否仍然准确 |
| 地图过于详细 | 每个活动下有 20 个故事；团队陷入细节讨论而忽略全局 | 工作坊控制在 2-3 小时内。如果一个活动的故事超过 8 个，应该拆分成更细的活动步骤 |
