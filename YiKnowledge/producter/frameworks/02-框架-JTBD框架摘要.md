# Jobs-to-Be-Done (JTBD) 框架摘要

> **JTBD 将产品思维从"用户想要什么功能"转变为"用户雇佣这个产品来完成什么任务"。** 功能会过时，技术会变迁，但用户的核心任务相对稳定。

## 核心概念

人们不"购买"产品——他们"雇佣"产品来完成某项任务。一项"任务"（Job）是人在特定情境下想要取得的进步。

### 任务陈述格式

```
当 {{情境}} 时，我想要 {{动机}}，以便 {{预期结果}}。
```

**示例**："当我收到一个新的售后案例时，我想要快速生成一份报告草稿，以便将时间集中在审核内容而非排版格式上。"

注意：这个表述完全没有提到任何技术方案（"AI 生成"、"大模型"、"RAG"）——它描述的只是用户在特定情境下想要完成的任务。技术方案是完成这个任务的手段，而非任务本身。

## 推动变革的四种力量

```
                    ┌─────────────────┐
     推力 ──────────→│                 │←────────── 拉力
  （现有方案的痛点）  │  切换到新方案   │  （新方案的吸引力）
                    └─────────────────┘
                            ↑
                            │
              ┌─────────────┴─────────────┐
              │                           │
          焦虑感                         惯性
     （对新方案的担忧）            （现有方案的使用习惯）
```

| 力量 | 核心问题 | YrY 示例（以 YiPet 知识底座功能为例）|
|---|---|---|
| **推力** | 现有方案有什么痛点？ | 用户需要手动在 YiKnowledge 中搜索相关信息，然后复制粘贴到聊天中；流程碎片化 |
| **拉力** | 新方案的吸引力在哪？ | 在聊天界面中直接选择知识范围，AI 回答自动基于 YrY 真实知识库，无需切换工具 |
| **焦虑感** | 用户对切换有什么担忧？ | 担心 AI 引用的知识是过时的；担心知识底座会增加回答延迟 |
| **惯性** | 什么让用户坚持使用现有方案？ | 已经习惯了直接问 AI 通用问题；不确定知识底座是否真的比通用回答更好 |

**应用方法**：在设计新功能时，用四力框架检查。如果推力和拉力不够强，用户不会切换。如果焦虑感和惯性太强，需要设计降低摩擦的功能（如展示知识文件最后更新时间，以降低"知识过时"的焦虑）。

## 三类任务：功能、情感、社交

| 类型 | 核心问题 | 示例（YiVad 项目管理功能）|
|---|---|---|
| **功能性任务** | 用户需要完成什么操作？ | "追踪项目进度和问题状态" |
| **情感性任务** | 用户希望感觉如何？ | "对项目全局有掌控感，不会遗漏关键问题" |
| **社交性任务** | 用户希望被如何看待？ | "在团队面前展示专业的项目管理能力" |

**产品经理容易忽略后两类任务。** 仅满足功能性任务的产品"能用"，同时满足情感和社交任务的产品"让人想用"。Slack 不仅是信息工具——它满足了"看起来高效"和"团队协作顺畅"的社交与情感需求。

## JTBD 与用户故事的区别

| JTBD | 用户故事 |
|---|---|
| 技术无关，描述任务本身 | 与特定解决方案绑定 |
| "生成一份报告草稿" | "点击'生成'按钮" |
| 长期稳定，不随产品演化而变 | 随产品演化而变 |
| 用于发现机会空间 | 用于定义具体实现 |

**使用顺序**：先用 JTBD 发现用户的核心任务（发现阶段），再将这些任务转化为用户故事来定义具体功能（定义阶段）。跳过 JTBD 直接写用户故事 = 在没搞清楚"用户到底要什么"之前就开始设计按钮。

## 如何在 YrY 中实践 JTBD

### YiVad 的 JTBD 示例

| 核心任务（JTBD） | 当前方案 | 功能机会 |
|---|---|---|
| 快速了解项目全局状态 | 手动翻阅各模块（问题、周期、版本） | 项目仪表盘：一眼看到问题分布、周期进度、阻塞项 |
| 确保团队不遗漏重要问题 | 依赖记忆或手动检查 | 智能提醒：过期未处理的问题自动通知 |
| 向领导汇报项目进展 | 手动截图拼 PPT | 一键生成项目周报，包含关键指标和风险项 |

### YiPet 的 JTBD 示例

| 核心任务（JTBD） | 当前方案 | 功能机会 |
|---|---|---|
| 浏览网页时快速获取知识 | 打开新标签页搜索 | 选中文字即可基于 YrY 知识库提问 |
| 确保 AI 回答基于真实知识 | 信任 AI 的通用回答 | 知识底座 + 引用来源：每条回答都标注来自哪个知识文件 |
| 将聊天中有价值的信息保存下来 | 手动复制粘贴 | 会话导出 + 分支管理 |

## 实践建议

1. **访谈时问"上一次"而非"通常"**："你上一次写售后报告是什么时候？怎么写的？" 比 "你通常怎么写售后报告？" 能获得更具体、更真实的信息
2. **关注替代方案**：用户现在用什么"土办法"在完成这个任务？替代方案越痛苦，你的机会越大
3. **区分任务和任务链**：一个大的 JTBD（"管理项目"）包含多个子任务（"追踪进度"、"分配问题"、"汇报进展"）。不要试图用一个功能解决所有子任务
4. **JTBD 不替代功能需求**：JTBD 帮你发现要做什么，PRD 帮你定义做什么。两者互补，不可偏废

## 反模式

- **混淆任务与操作。** "点击生成按钮"是操作。"生成报告草稿"是任务。任务是方案无关的——也许未来不用点击，语音指令也可以完成同样的任务。在定义需求时，先写任务陈述，再设计具体操作流程
- **只捕获功能性任务。** 情感和社交任务往往是用户采用产品的真正驱动力。"感觉有掌控感"可能比"节省时间"更能说服用户切换产品
- **围绕功能做用户访谈。** JTBD 访谈问的是"你上一次做这个任务是什么时候？怎么做的？"——不问"你希望这个产品有什么功能？"。后者得到的是用户对功能的想象，前者得到的是真实的用户行为
- **把 JTBD 当成一次性练习。** 随着产品成熟和用户群体扩大，核心任务可能变化。每季度回顾一次：用户的 JTBD 变了吗？有新的任务出现吗？
