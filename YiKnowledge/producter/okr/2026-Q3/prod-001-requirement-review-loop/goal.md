# 需求评审可闭环

> **目标**：建立标准化的需求评审流程——为每条闭环需求产出完整 PRD、可被测试门禁直接判定的验收标准、以及 WSJF 优先级评分。评审记录沉淀知识库，需求到任务的拆解使用可复用模板。

## 目标概述

本 OKR 的目标是让 YiAi 项目的需求评审从"口头对齐"演进为"可追溯、可验证、可复用的标准化流程"。在实施前，YiAi 的需求评审主要依赖即时沟通——需求记录分散在聊天记录中，没有统一的 PRD 格式，验收标准靠口头约定，优先级排序缺乏数据支撑。这导致工程师在开发中途反复确认需求细节、测试人员不清楚"做完"的定义、回顾时找不到当初的决策依据。

### KR 详解

**KR1 - PRD 完整输出**：每项需求从"一句话需求"升级为包含 5 个必要字段的结构化 PRD——背景（为什么要做）、目标（做了要达到什么效果）、范围（什么做、什么不做）、非目标（明确不做什么）、干系人（谁需要参与评审）。

**KR2 - 验收标准可判定**：验收标准从"大概能跑通就行"变为"Given-When-Then"格式。测试人员可以直接将验收标准转化为测试用例，无需再次向 PM 确认"这里应该是什么行为"。

**KR3 - WSJF 优先级评分**：使用加权最短作业优先（Weighted Shortest Job First）公式 —— `WSJF = (业务价值 × 时间紧迫度) / 实施难度`。相比直觉排序，WSJF 提供了可论证的、可追溯的优先级决策依据。

**KR4 - 评审记录知识化**：每次需求评审的结果（讨论了什么、决策了什么、争议点和结论）写入 YiKnowledge 中的对应知识文件。后续团队成员可以通过知识库回顾历史决策的来龙去脉。

**KR5 - 拆解模板复用**：将 PRD 到 Sprint 任务项的拆解过程模板化。后续新需求的拆解只需要在模板上填空，而非每次从零开始设计拆解结构。

## 实施成果与经验总结

### 实施前 vs 实施后

| 维度 | 实施前 | 实施后 |
|---|---|---|
| 需求记录方式 | 聊天记录 + 口头约定 | 结构化 PRD 存入知识库 |
| 验收标准 | 口头沟通、"看着办" | Given-When-Then 格式，测试门禁可直接判定 |
| 优先级决策 | 直觉和经验 | WSJF 量化评分（价值 × 紧迫度 / 难度） |
| 评审可追溯性 | 无记录，依赖当事人记忆 | 每次评审记录入知识库 |
| 需求拆解效率 | 每次从零设计拆解方案 | 复用模板，填空即可 |

### 关键经验

1. **PRD 模板比方法论更重要**：团队接受 PRD 格式的关键是"有模板可填"而非"先理解方法论"。先给模板，再逐步解释每个字段的设计逻辑
2. **WSJF 评分初期会高估紧迫度**：团队倾向于把所有需求标记为"高紧迫度"。需要校准——如果所有需求都是"本周必须做"，说明紧迫度维度需要更精细的定义
3. **验收标准最难写**：将模糊预期转化为机器可判定的"Given-When-Then"需要练习。前 3 个 PRD 的验收标准通常需要 2-3 轮修订
