## 指标说明

### 为什么要追踪这个指标

验收标准是 PRD 中最容易被敷衍的部分。常见的敷衍形式：
- "功能正常工作" —— 无法判定。什么叫"正常"？
- "用户体验良好" —— 无法判定。谁来定义"良好"？
- "响应速度够快" —— 无法判定。多快算够快？

这些模糊的验收标准导致两个问题：
1. **工程师不确定做到什么程度算完成**——反复确认浪费双方时间
2. **测试人员无法编写测试用例**——只能"按照我的理解测一下"，漏测是必然的

"验收标准完备率"关注的是验收标准的**可判定性**——一个不了解需求背景的人（如新加入的测试人员）能否仅凭验收标准判断功能是否通过？

### 可判定验收标准的三项要求

一项验收标准被计数为"完备"必须同时满足：

1. **有明确的触发条件**（Given）：前置状态是什么？什么操作触发？
2. **有明确的行为描述**（When 和 Then）：用户做什么？系统应该产生什么可观测的结果？
3. **结果是二元的**（通过/不通过）：不存在"酌情判断"的空间

### 示例对比

| 不完备的验收标准 | 完备的验收标准 | 为什么之前不完备 |
|---|---|---|
| "Agent 生成的报告格式正确" | "Given：输入完整的案例数据，When：Agent 生成报告，Then：报告包含'问题描述'、'原因分析'、'解决方案'三个章节，章节标题与标准模板一致" | 没有定义"格式正确"的具体含义——章节名称和数量都需要明确定义 |
| "API 响应速度可接受" | "Given：正常网络环境，When：调用报告生成 API，Then：P95 响应时间 ≤ 3 秒" | 没有量化"可接受"——需要具体的数值和时间度量（P50/P95/P99） |
| "多语言输出正常" | "Given：输入中文案例数据并指定英文输出，When：Agent 生成报告，Then：输出为英文，且内容与中文版本语义一致（非字面翻译）" | 没有明确"正常"的判断标准——语义一致性比字面翻译更重要 |

### 测量方法

```
验收标准完备率 = 完备的验收标准数 / 总验收标准数 × 100%
```

数据来源：各 PRD 文件中的"验收标准"章节。逐一检查每条标准是否满足 Given-When-Then 的三要素。

## 实践建议

### 验收标准自查清单

在提交 PRD 评审前，对每一条验收标准做以下检查：

- [ ] 如果换一个人来执行这个验收标准，ta 会和我得出同样的"通过/不通过"结论吗？
- [ ] 验收标准中是否包含模糊词汇（"正常"、"良好"、"够快"、"合理"）？如果有，替换为具体的数值或条件
- [ ] 验收标准是否覆盖了失败路径（如果 API 返回错误怎么办？如果输入数据不完整怎么办？）
- [ ] 验收标准是否可自动化检查？如果不能，人工检查的步骤是否足够明确？

### 常见陷阱

1. **只写"快乐路径"**：验收标准只描述一切正常时的行为，没有定义异常处理。补充至少一条异常路径的验收标准
2. **验收标准过于技术化**："数据库写入成功"不是用户可感知的结果。验收标准应描述用户可观测的表现，而非内部实现
3. **验收标准与用户故事脱节**：每条用户故事至少对应一条验收标准。如果一个故事没有验收标准，说明它还没有被充分理解
