margin: 16px 16px 0px; line-height: 1.75em;"><img class="rich_pages wxw-img" src="https://static.leiphone.com/uploads/new/images/20260828/6a91365a824cf.png?imageMogr2/quality/90" style="background-color: transparent; font-size: 14px; font-family: Arial, Helvetica, sans-serif;"><span style="color: #888888;">https://platform.claude.com/docs/en/build-with-claude/context-windows</span></span></em></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">一个文件可能先后被修改几次；某个 bug 最初被判断成缓存问题，后来发现来自并发；一个测试可能先失败、随后通过，又因为新的修改重新失败。旧内容不会随着状态变化自动删除，新内容只是继续追加在后面。</span></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">这里出现的问题已经不只是 retrieval。模型不仅要找到和当前任务相关的信息，还要判断这些信息现在是否仍然有效。</span></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">旧版函数和新版函数高度相似，旧测试日志和新测试日志包含大量相同 token，已经被推翻的分析也可能和当前问题在语义上高度相关。Attention 找到这些内容并不困难，困难的是确定它们之间的覆盖关系。</span></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">数据库可以靠版本号、更新时间、事务和显式字段维护 current state，自然语言 context 通常没有这种结构。它更接近 append-only log，模型需要自己从事件顺序中恢复现在的世界是什么样。</span></p><section style="text-align: justify; margin: 16px 16px 0px; line-height: 1.75em;"><img class="rich_pages wxw-img" src="https://static.leiphone.com/uploads/new/images/20260828/6a91365acbf44.png?imageMogr2/quality/90" style="background-color: transparent; width: 100%;" /></section><p style="text-align: left; margin: 16px 16px 24px; line-height: 1.75em;"><em><span style="font-style: italic; font-size: 14px; font-family: Arial, Helvetica, sans-serif;"><span style="color: #888888;">参考链接：</span></span></em><em><span style="font-style: italic; font-size: 14px; font-family: Arial, Helvetica, sans-serif;"><span style="color: #888888;">https://platform.claude.com/docs/en/build-with-claude/context-windows</span></span></em></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">因此，长上下文的复杂度并不和 token 占用比例简单对应。250K token 的静态文档可能比 250K token 的 Agent 历史容易处理得多，因为后者包含大量被修改过的对象、阶段性判断、工具结果和已经失效的状态。</span></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">Thinking history 还会进一步增加这种复杂度。会话里保存的不只是“发生过什么”，还可能包含“当时为什么这么判断”。如果早期 reasoning 建立在一个后来被推翻的假设上，那段推理仍然可能因为和当前问题高度相关而继续参与后续判断。</span></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">所以 1M context 的真正限制不只是能放多少信息，而是当同一个对象出现越来越多历史版本以后，模型还能不能稳定恢复当前版本。</span></p><section><section><section style="width: 100%; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">摘要文章时少掉一个例子，影响通常只是信息完整度；压缩 Agent 轨迹时，遗漏一个仍然有效的限制条件，后面的执行路径可能直接改变。</span></p><section style="text-align: justify; margin: 16px 16px 0px; line-height: 1.75em;"><img class="rich_pages wxw-img" src="https://static.leiphone.com/uploads/new/images/20260828/6a91365b4ef34.png?imageMogr2/quality/90" style="background-color: transparent; font-size: 14px; font-family: Arial, Helvetica, sans-serif;"><span style="color: #888888;">https://platform.claude.com/cookbook/tool-use-context-engineering-context-engineering-tools</span></span></em></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">因为 compaction 必须解决的不是“哪些内容重要”，而是“哪些内容现在还算数”。一段历史里可能同时存在已经完成的任务、后来被推翻的判断、当前仍然成立的接口约束、过期测试结果和临时 workaround。压缩器需要把这些时间状态重新整理成一个能够供下一轮继续工作的表示。</span></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">如果“目前怀疑问题来自缓存”被压成“问题来自缓存”，临时假设就变成了事实；如果一个已经废弃的方案仍然进入摘要，后面的 Agent 可能重新沿旧路径执行；如果某项关键限制没有进入摘要，它之后甚至不会再被模型看到。</span></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">所以 compaction 的关键指标不是压缩率，而是状态保真。这也是 Git、测试、任务文件、memory 和结构化 handoff 在长时 Agent 中越来越重要的原因。</span></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">它们不是单纯增加模型能看到的信息，而是在把一些需要长期成立的状态，从自然语言历史中移到外部系统。Git 明确当前代码版本，测试给出可验证结果，任务文件记录完成情况，结构化状态区分当前结论和历史尝试。</span></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">Context 可以保留丰富历史，但不能长期承担全部状态管理职责。</span></p><section style="text-align: justify; margin: 16px 16px 0px; line-height: 1.75em;"><img class="rich_pages wxw-img" src="https://static.leiphone.com/uploads/new/images/20260828/6a91365b93bb9.png?imageMogr2/quality/90" style="background-color: transparent; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">很多 benchmark 测的是：给模型一个初始化好的环境，它能不能完成任务。真实 Agent 多了一层困难：环境会随着模型自己的动作不断变化。因此两个最终通过率接近的模型，真实体验可能完全不同。</span></p><p style="text-align: justify;
