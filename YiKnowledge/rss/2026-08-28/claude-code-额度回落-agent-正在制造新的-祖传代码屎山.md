font-family: Arial, Helvetica, sans-serif;">Agent 里的情况是，一次 tool output 被写进执行历史，随后跟着后面的推理一起移动。</span></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">于是长任务陷入一个两难：留下过多历史，后续每一步越来越重；清理得过于激进，Agent 又会不断重新获取以前见过的信息。</span></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">这也解释了为什么 context 管理不能简化成“少塞一点 Token”。真正需要解决的是&nbsp;</span><strong style="text-align: justify; line-height: 1.75em; font-weight: bold; font-size: 15px; font-family: Arial, Helvetica, sans-serif;"><span style="text-align: justify; line-height: 1.75em; font-weight: bold; font-size: 15px; font-family: Arial, Helvetica, sans-serif;"><span style="color: #4499E7;">working set selection</span></span></strong><span style="text-align: justify; line-height: 1.75em; font-weight: bold; font-size: 15px; font-family: Arial, Helvetica, sans-serif;"><span style="color: #4499E7;">：</span></span><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">此刻有哪些信息必须留在工作区，哪些只是已经完成使命的中间产物。</span></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">到了这里，compaction、memory 和 sub-agent 才真正有了存在的理由。</span></p><section style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><img class="rich_pages wxw-img" src="https://static.leiphone.com/uploads/new/images/20260828/6a913742a2247.png?imageMogr2/quality/90" style="background-color: transparent; width: 100%;" /></section><section><section><section style="width: 100%; display: flex; padding: 0px 14px 0px 14px;"><section style="display: flex;"><section><img alt="图片" class="rich_pages wxw-img __bg_gif" src="https://static.leiphone.com/uploads/new/images/20260828/6a913742d457a.jpg?imageMogr2/quality/90" style="display: block; height: auto !important; width: 38px !important; background-color: transparent;" /></section><section style="text-align: center;"><p style="font-size: 36px; color: #333333; line-height: 50px;"><strong><span>04</span><span><br /></span></strong></p><h2><span><br /></span></h2><h2><strong><strong style="text-align: center; font-size: 18px;">什么信息可以被忘掉？</span><span><br /></span></strong></strong></strong></h2></section></section></section></section></section><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">Claude Code 接近 context 边界时会自动压缩会话，同时还会清理部分较旧的工具结果。官方也提醒，长 session 里的无关对话、文件内容和命令结果可能占满窗口并干扰模型表现。</span></p><p style="text-align: justify; margin: 16px 16px 24px; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">后者难得多。例如早期有这样一段设计结论：某个模块不能自己缓存用户状态，因为系统要求状态只有一个 owner，所有修改必须经过 service。</span></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">几十步之后，如果这段信息被压成：“之前通过 service 调整解决了状态问题。”事实没有错，但信息已经发生了变化。原始内容包含的是&nbsp;</span><strong style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">它的代价也很有意思：主 Agent 得到了更干净的状态，却失去了部分原始证据；多个 Agent 同时运行，还会建立各自的 context。因此 compaction、memory、sub-agent 放在一起看，其实已经很像一套 Agent 时代的内存层级：</span></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">当前 context 是昂贵工作内存，compaction 负责压缩，memory 保存跨 session 状态，sub-agent 用独立地址空间隔离噪声。问题也从“context 够不够大”变成了另一个层级：</span></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><strong style="text-align: justify; line-height: 1.75em; font-weight: bold; font-size: 15px; font-family: Arial, Helvetica, sans-serif;"><span style="text-align: justify; line-height: 1.75em; font-weight: bold; font-size: 15px; font-family: Arial, Helvetica, sans-serif;"><span style="color: #4499E7;">哪些状态需要高保真保存，哪些状态只需要留下摘要。</span></span></strong><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">另一套是设计状态&nbsp;</span><code><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">M_t</span></code><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">。为什么这里需要&nbsp;</span><code><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">retry</span></code><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">，为什么那个缓存只能放在 service，为什么这个状态不能有两个 owner，为什么一个看起来多余的判断暂时不能删，这些信息属于设计因果。</span></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><code><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">M_t</span></code><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">&nbsp;没有像 Git 一样天然的无损存储。它分散在对话、推理、工具返回、memory、规则文件和 compaction summary 里。任务不断推进以后，部分内容被清理，部分内容被摘要，部分内容需要重新检索。</span></p><section style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><img class="rich_pages wxw-img" src="https://static.leiphone.com/uploads/new/images/20260828/6a913744cc756.png?imageMogr2/quality/90" style="background-color: transparent; width: 100%;" /></section><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">于是会产生一个很关键的不对称：</span><strong style="text-align: justify; line-height: 1.75em; font-weight: bold; font-size: 15px; font-family: Arial, Helvetica, sans-serif;"><span style="text-align: justify; line-height: 1.75em; font-weight: bold; font-size: 15px; font-family: Arial, Helvetica, sans-serif;"><span style="color: #4499E7;">实现结果能够高保真累积，生成这些结果的因果关系却会不断降采样。</span></span></strong><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">这比单纯说“Agent 会忘东西”严重得多。</span></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">假设一次并发问题中，Agent 分析后加入了一个 queue。当时它掌握的完整结论是：只有写路径 A 存在竞争，因此 queue 只能包住 A；写路径 B 需要低延迟，不能进入这个队列。</span></p><section style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><img class="rich_pages wxw-img" src="https://static.leiphone.com/uploads/new/images/20260828/6a91374505ef0.png?imageMogr2/quality/90" style="background-color: transparent; width: 100%;" /></section><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">代码把 queue 完整保存下来了。经过长时间执行以后，设计状态可能只剩下“这里用 queue 解决 race condition”。</span></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">后来 B 也出现一个偶发错误。Agent 再次读到代码时，很自然地把 B 也接进现有 queue。</span></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">随后延迟上升，于是再加 bypass。bypass 又引出偶发状态不一致，于是外围补 retry。到了这里，没有任何一次修改必然是荒谬的。每个补丁在当时看到的局部状态下甚至可能相当合理。代码却已经从“一个明确的并发模型”，变成了 queue、bypass 和 retry 互相补偿。</span></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">AI 代码屎山很可能就是这样长出来的。它不一定表现成模型突然写出一团垃圾，更可能表现成</span><strong style="text-align: justify; line-height: 1.75em; font-weight: bold; font-size: 15px; font-family: Arial, Helvetica, sans-serif;"><span style="text-align: justify; line-height: 1.75em; font-weight: bold; font-size: 15px; font-family: Arial, Helvetica, sans-serif;"><span style="color: #4499E7;">局部正确不断累积，整体模型逐渐消失</span></span></strong><span style="text-align: justify; line-height: 1.75em; font-weight: bold; font-size: 15px; font-family: Arial, Helvetica, sans-serif;"><span style="color: #4499E7;">。</span></span></p><section style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><img class="rich_pages wxw-img" src="https://static.leiphone.com/uploads/new/images/20260828/6a91374560027.png?imageMogr2/quality/90" style="background-color: transparent; width: 100%;" /></section><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">传统软件里这类问题通常经过人员交接慢慢形成。原作者离开，新开发者看到旧代码，却不知道它为什么存在，于是在外面再包一层兼容逻辑。</span></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">Coding Agent 把“人员交接”变成了“上下文交接”。第 20 步和第 100 步看起来还是同一个 Claude Code session，但它们实际拿到的设计状态已经不完全相同。从信息角度看，更像两名工程师通过一份不断缩水的交接文档维护同一个仓库。</span></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">测试也只能解决其中一部分。测试擅长保护行为：接口应该返回什么，某种输入不能崩溃，过去的 bug 不能重新出现。很多架构约束却不天然表现成输入输出。</span></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">状态只能有一个 owner、领域层不能反向依赖 UI、某个 package 不允许直连数据库、写操作必须经过统一事务边界，这些约束如果只存在于文档或者 Agent 记忆里，就很容易在局部修复中被穿过去。</span></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">结果会出现一种很麻烦的工程状态：</span><strong style="text-align: justify; line-height: 1.75em; font-weight: bold; font-size: 15px; font-family: Arial, Helvetica, sans-serif;"><span style="text-align: justify; line-height: 1.75em; font-weight: bold; font-size: 15px; font-family: Arial, Helvetica, sans-serif;"><span style="color: #4499E7;">测试还是绿的，代码已经越来越难解释。</span></span></strong><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">更危险的是，这里面存在反馈回路。</span></p><section style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><img class="rich_pages wxw-img" src="https://static.leiphone.com/uploads/new/images/20260828/6a9137459b8a8.png?imageMogr2/quality/90" style="background-color: transparent; width: 100%;" /></section><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">架构开始变乱，Agent 下一次理解功能就需要读取更多文件；依赖关系越绕，working set 越大；工作集越重，系统越需要清理和压缩；设计因果保存得越薄，后面的修改又越容易依赖眼前代码和局部测试。</span></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">于是代码复杂度开始提高 Token 成本，Token 压力又反过来鼓励更短的状态保留和更局部的修补。这才是 Agent coding 里“越迭代问题越多”背后比较值得警惕的机制。</span></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">它不是一个单独的模型能力问题，而是一种</span><strong style="text-align: justify; line-height: 1.75em; font-weight: bold; font-size: 15px; font-family: Arial, Helvetica, sans-serif;"><span style="text-align: justify; line-height: 1.75em; font-weight: bold; font-size: 15px; font-family: Arial, Helvetica, sans-serif;"><span style="color: #4499E7;">代码状态和设计状态保存精度不一致</span></span></strong><span style="text-align: justify; line-height: 1.75em; font-weight: bold; font-size: 15px; font-family: Arial, Helvetica, sans-serif;"><span style="color: #000000; font-weight: normal;">的系统问题。</span></span></p><section><section><section style="width: 100%; display: flex; padding: 0px 14px 0px 14px;"><section style="display: flex;"><section><img alt="图片" class="rich_pages wxw-img __bg_gif" src="https://static.leiphone.com/uploads/new/images/20260828/6a913745d1e22.jpg?imageMogr2/quality/90" style="display: block; height: auto !important; width: 38px !important; background-color: transparent;" /></section><section style="text-align: center;"><p style="font-size: 36px; color: #333333; line-height: 50px;"><strong><span>07</span><span><br /></span></strong></p><h2><span><br /></span></h2><h2><strong><strong style="text-align: center; font-size: 18px;">Agent 需要「状态保真率」</span><span><br /></span></strong></strong></strong></h2></section></section></section></section></section><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">Coding Agent 已经越来越能长时间行动，但“能跑几个小时”本身未必是一个很好的能力指标。</span></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">如果一个 Agent 工作 3 小时以后，需要重新阅读自己 2 小时前改过的文件，重新推理某个抽象为什么存在，再重新跑一次此前已经跑过的测试，那么这 3 小时里有相当一部分计算其实花在了状态恢复上。</span></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">接下来的问题会变成：一个 Agent 在经历 50 步、100 步之后，还能保留多少对后续决策有价值的因果信息。</span></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">可以把它叫作</span><strong style="text-align: justify; line-height: 1.75em; font-weight: bold; font-size: 15px; font-family: Arial, Helvetica, sans-serif;"><span style="font-weight: bold; font-size: 15px; font-family: Arial, Helvetica, sans-serif;"><span style="color: #4499E7; font-weight: bold;">状态保真率</span></span></strong><span style="text-align: justify; line-height: 1.75em; font-weight: bold; font-size: 15px; font-family: Arial, Helvetica, sans-serif;"><span style="color: #4499E7; font-weight: bold;">。</span></span></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">因为它衡量的不是 context 能塞多少 Token，而是经过工具调用、压缩、跨 session 和记忆检索之后，多少关键设计信息仍然以可用的形式存在。这也意味着，Agent 的长期记忆不能只靠更长的 context。</span></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">有些知识适合存在 memory 里，比如项目构建方式和开发习惯；有些决策应该进入结构化的 ADR 或代码索引；而那些一旦违反就会破坏系统的架构边界，更适合直接写进类型、测试、 lint、依赖规则和 CI。</span></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">一条规则如果已经变成软件可以执行的约束，Agent 就不需要“记住”它。下一轮 Agent 可以忘掉一段对话，却无法轻易越过编译器和测试。</span></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><strong><span style="text-align: justify; line-height: 1.75em; font-weight: bold; font-size: 15px; font-family: Arial, Helvetica, sans-serif;"><span style="color: #4499E7; font-weight: bold;">如果保真率低，Agent 跑得越久，其实是在给系统埋越多的地雷。</span></span></strong></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">这可能也是 Coding Agent 从“会写代码”走向“能长期维护软件”需要跨过去的一道线：把设计知识从概率性的语言记忆，逐渐迁移到可检索、可验证、可执行的软件状态里。</span></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">否则自主运行时间越长，会出现一个很荒诞的场景。Agent 写代码的速度越来越快，项目也在飞快变化，可每隔一段时间，它又要重新理解上一段时间留下来的世界。</span></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">传统祖传代码常见的一句话是：“这段别动，不知道为什么会炸。”</span></p><p style="text-align: justify; margin: 16px 16px 24px; line-height: 1.75em;"><span style="font-size: 15px; font-family: Arial, Helvetica, sans-serif;">AI 祖传代码可能更离谱：</span><strong style="text-align: justify; line-height: 1.75em; font-weight: bold; font-size: 15px;
