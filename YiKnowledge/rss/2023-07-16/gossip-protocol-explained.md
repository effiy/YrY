The original article was published on <a href="https://systemdesign.one/gossip-protocol/?ref=highscalability.com">systemdesign.one</a> website.</h4><p><br /></p><hr /><h3 id="what-is-gossip-protocol">What Is Gossip Protocol?</h3><p>The typical problems in a distributed system are the following [1], [11]:</p><ul><li>maintaining the system state (liveness of nodes)</li><li>communication between nodes</li></ul><p>The potential solutions to these problems are as follows [1]:</p><ul><li>centralized state management service</li><li>peer-to-peer state management service</li></ul><h3 id="centralized-state-management-service">Centralized State Management Service</h3><p>A centralized state management service such as Apache Zookeeper can be configured as the <a href="https://systemdesign.one/what-is-service-discovery/?ref=highscalability.com" rel="noopener">service discovery</a> to keep track of the state of every node in the system. Although this approach provides a strong consistency guarantee, the primary drawbacks are the state management service becomes a single point of failure and runs into scalability problems for a large distributed system [1], [11].</p><h3 id="peer-to-peer-state-management-service">Peer-To-Peer State Management Service</h3><p>The peer-to-peer state management approach is inclined towards high availability and eventual consistency. The gossip protocol algorithms can be used to implement peer-to-peer state management services with high scalability and improved resilience [1].</p><p>The gossip protocol is also known as the <strong>epidemic protocol </strong>because<strong> </strong>the<strong> </strong>transmission of the messages is similar to the way how <a href="https://en.wikipedia.org/wiki/Epidemic?ref=highscalability.com" rel="noopener">epidemics</a> spread. The concept of communication in gossip protocol is analogous to the spread of rumors among the office staff or the dissemination of information on a social media website [4], [8].</p><h2 id="broadcast-protocols">Broadcast Protocols</h2><p>The popular message broadcasting techniques in a distributed system are the following:</p><ul><li>point-to-point broadcast</li><li>eager reliable broadcast</li><li>gossip protocol</li></ul><h3 id="point-to-point-broadcast">Point-To-Point Broadcast</h3><figure class="kg-card kg-image-card"><img alt="alt" class="kg-image" height="413" src="https://storage.ghost.io/c/64/72/647204cd-7ad2-4539-b98a-3489074b932d/content/images/2024/02/ege6ztj-__squarespace_cacheversion-1689515329345.png" width="752" /></figure><p>The producer sends a message directly to the consumers in a point-to-point broadcast. The retry mechanism on the producer and deduplication mechanism on the consumers makes the point-to-point broadcast reliable. The messages will be lost when the producer and the consumer fail simultaneously [3].</p><h4 id="eager-reliable-broadcast"><strong>Eager Reliable Broadcast</strong></h4><p>Every node re-broadcasts the messages to every other node via reliable network links. This approach provides improved fault tolerance because messages are not lost when both the producer and the consumer fail simultaneously. The message will be re-broadcast by the remaining nodes. The caveats of eager reliable broadcast are the following [3], [8]:</p><ul><li>significant network bandwidth usage due to O(n&#xb2;) messages being broadcast for <em>n</em> number of nodes</li><li>sending node can become a bottleneck due to O(n) linear broadcast</li><li>every node stores the list of all the nodes in the system causing increased storage costs</li></ul><h3 id="gossip-protocol">Gossip Protocol</h3><p>The gossip protocol is a decentralized peer-to-peer communication technique to transmit messages in an enormous distributed system [1], [8]. The key concept of gossip protocol is that every node periodically sends out a message to a subset of other random nodes [8], [2]. The entire system will receive the particular message eventually with a high probability [11], [3]. In layman&#x2019;s terms, the gossip protocol is a technique for nodes to build a global map through limited local interactions [1].</p><figure class="kg-card kg-image-card"><img alt="alt" class="kg-image" height="377" src="https://storage.ghost.io/c/64/72/647204cd-7ad2-4539-b98a-3489074b932d/content/images/2024/02/1nu8hxn-__squarespace_cacheversion-1689515298461.gif" width="685" /></figure><p>The gossip protocol is built on a robust, scalable, and eventually consistent  algorithm. The gossip protocol is typically used to maintain the node membership list, achieve consensus, and  fault detection in a distributed system [2]. In addition, additional information such as application-level data can be piggybacked on gossip messages [1].</p><p>The gossip protocol is reliable because a node failure can be overcome by the retransmission of a message by another node. First-in-first-out (<strong>FIFO</strong>) broadcast, causality broadcast, and total order broadcast can be implemented with gossip protocol [3].</p><p>The gossip protocol parameters such as cycle and fanout can be tuned to improve the probabilistic guarantees of the gossip protocol. The following tools offer a high-end simulation and visualization of the gossip protocol [8], [5]:</p><ul><li><a href="https://www.serf.io/docs/internals/simulator.html?ref=highscalability.com" rel="noopener">serf convergence simulator</a></li><li><a href="https://flopezluis.github.io/gossip-simulator/?ref=highscalability.com" rel="noopener">gossip simulator</a></li></ul><p>The following characteristics of the gossip protocol make it an optimal choice as the communication protocol in a large-scale distributed system [12]:</p><ul><li>limits the number of messages transmitted by each node</li><li>limits the bandwidth consumption to prevent the degradation of application performance</li><li>tolerates network and node failures</li></ul><p>The gossip protocol can be used to keep nodes consistent only when the operations executed are commutative and serializability is not necessary. The <strong>tombstone</strong> is a special entry to invalidate the data entries that have a matching key without actual deletion of the data. The gossip protocol deletes the data from a node using a tombstone.</p><h2 id="types-of-gossip-protocol">Types of Gossip Protocol</h2><p>The time required by the gossip protocol to propagate a message across the system and the network traffic generated in propagating a message must be taken into consideration while choosing the type of gossip protocol for a particular use case [10]. The gossip protocol can be broadly categorized into the following types [8], [10]:</p><ul><li>anti-entropy model</li><li>rumor-mongering model</li><li>aggregation model</li></ul><h3 id="anti-entropy-gossip-protocol"><strong>Anti-Entropy Gossip Protocol</strong></h3><p>The anti-entropy algorithm was introduced to reduce the entropy between replicas of a stateful service such as the database. The replicated data is compared and the difference between replicas are patched [10]. The node with the newest message shares it with other nodes in every gossip round [8].</p><p>The anti-entropy model usually transfers the whole dataset resulting in unnecessary bandwidth usage. The techniques such as checksum, recent update list, and <a href="https://en.wikipedia.org/wiki/Merkle_tree?ref=highscalability.com" rel="noopener">Merkle tree</a> can be used to identify the differences between nodes to avoid transmission of the entire dataset and reduce network bandwidth usage. The anti-entropy gossip protocol will send an unbounded number of messages without termination [8].</p><h3 id="rumor-mongering-gossip-protocol"><strong>Rumor-Mongering Gossip Protocol</strong></h3><p>The rumor-mongering protocol is also known as the <strong>dissemination protocol</strong>. The rumor-mongering cycle occurs relatively more frequently than anti-entropy cycles and floods the network with the worst-case load [10]. The rumor-mongering model utilizes fewer resources such as network bandwidth as only the latest updates are transferred across nodes [8].</p><p>A message will be marked as removed after a few rounds of communication to limit the number of messages. There is usually a high probability that a message will reach all the nodes [8].</p><h3 id="aggregation-gossip-protocol"><strong>Aggregation Gossip Protocol</strong></h3><p>The aggregation gossip protocol computes a system-wide aggregate by sampling information across every node and combining the values to generate a system-wide value [10].</p><h2 id="further-system-design-learning-resources">Further system design learning resources</h2><p><a href="https://systemdesignone.substack.com/" rel="noopener noreffer "><strong>Subscribe to the system design newsletter</strong></a> and never miss a new blog post again. You will also receive the <strong>ultimate guide</strong> to approaching <strong>system design interviews</strong> on <a href="https://systemdesignone.substack.com/" rel="noopener noreffer ">newsletter sign-up</a>.</p><h2 id="strategies-to-spread-a-message-through-gossip-protocol">Strategies to Spread a Message through Gossip Protocol</h2><p>The gossip protocol is an optimal framework to build a highly available service. The strategy to spread a message through gossip protocol should be chosen based on the service requirements and available network conditions. There are tradeoffs in terms of bandwidth, latency, and reliability with each strategy to spread a message. The strategies to spread a message apply to both anti-entropy and rumor-mongering models. The different strategies to spread a message with the gossip protocol are as follows [8], [5], [2]:</p><ul><li>push model</li><li>pull model</li><li>push-pull model</li></ul><p><strong>Push Model</strong></p><p>The push model is efficient when there are only a few update messages due to the traffic overhead. The node with the latest message sends the message to a random subset of other nodes in the push model [8].</p><p><strong>Pull Model</strong></p><p>Every node will actively poll a random subset of nodes for any update messages in the pull model. This approach is efficient when there are many update messages because it is highly likely to find a node with the latest update message [8].</p><p><strong>Push-Pull Model</strong></p><p>The push-pull model is optimal to disseminate update messages quickly and reliably [2]. The node can push a new update message and the node can also poll for new update messages. The push approach is efficient during the initial phase when there are only a very few nodes with update messages. The pull approach is efficient during the final phase when there are numerous nodes with many update messages [8].</p><h2 id="gossip-protocol-performance">Gossip Protocol Performance</h2><p>The number of nodes that will receive the message from a particular node is known as the <strong>fanout</strong>. The count of gossip rounds required to spread a message across the entire cluster is known as the <strong>cycle </strong>[8], [5].</p><blockquote>cycles necessary to spread a message across the cluster = O(log n) to the base of fanout, where n = total number of nodes</blockquote><p>For instance, it takes approximately 15 gossip rounds to propagate a message across 25,000 nodes. The gossip interval can be set to a value as low as 10 ms to propagate a message across a big data center in roughly 3 seconds. The propagation of a message in the gossip protocol should automatically age out to reduce the unnecessary load [4]. The performance of a gossip protocol implementation can be measured with the following metrics [8]:</p><ul><li>residue: number of remaining nodes that haven&#x2019;t received the messages should be minimum</li><li>traffic: average number of messages sent between nodes should be minimum</li><li>convergence: every node should receive the message as quickly as possible</li><li>time average: average time taken to send the message to every node should be low</li><li>time last: the time taken for the last node to receive the message should be low</li></ul><p>A case study showed that a system with 128 nodes consumed less than 2 percent of CPU and less than 60 KBps of bandwidth to run gossip protocol [11].</p><h3 id="gossip-protocol-properties">Gossip Protocol Properties</h3><p>There is no formal way to define gossip protocol. In general, the gossip protocol is expected to satisfy the following properties [8]:</p><ul><li>node selection must be random to perform a fanout</li><li>only local information is available to every node and the nodes are oblivious to the state of the cluster</li><li>communication between nodes involves periodic, pairwise, interprocess interactions</li><li>bounded size transmission capacity per gossip round</li><li>every node deploys the same gossip protocol</li><li>unreliable network paths between nodes are assumed</li><li>node interaction frequency is low</li><li>node interactions result in a state exchange</li></ul><h3 id="gossip-algorithm">Gossip Algorithm</h3><p>The high-level overview of the gossip algorithm is the following [6], [1]:</p><ol><li>every node maintains a list of the subset of nodes and their metadata</li><li>gossip to a random live peer node&#x2019;s endpoint periodically</li><li>every node inspects the received gossip message to merge the highest version number to the local dataset</li></ol><p>The heartbeat counter of a node is incremented whenever a particular node participates in the gossip exchange. The node is labeled healthy when the heartbeat counter keeps incrementing. On the other hand, the node is considered to be unhealthy when the heartbeat counter has not changed for an extended period due to a network partition or node failure [1]. The following are the different criteria for peer node selection in the gossip protocol [12]:</p><ul><li>utilize library offered by programming languages such as java.util.random</li><li>interact with the least contacted node</li><li>enforce <a href="https://dl.acm.org/doi/10.1109/TPDS.2006.85?ref=highscalability.com" rel="noopener">network-topology-aware</a> interaction</li></ul><h3 id="gossip-protocol-implementation">Gossip Protocol Implementation</h3><p>The gossip protocol transports messages over User Datagram Protocol (<strong>UDP</strong>) or Transmission Control Protocol (<strong>TCP</strong>) with a configurable but fixed fanout and interval [12]. The <strong>peer sampling service</strong> is used by the gossip protocol to identify the peer nodes for gossip message exchange. The peer sampling service uses a randomized algorithm for the selection of a peer node. The application programming interface (<strong>API</strong>) of the peer sampling service should provide the following endpoints [8]:</p><ul><li>/gossip/init: returns the list of nodes known to a particular node at startup</li><li>/gossip/get-peer: returns the address (IP address and port number) of an independent peer node</li></ul><p>The workflow of the peer sampling service execution is as follows [8]:</p><ol><li>initialize every node with a partial view of the system (a list with the subset of nodes)</li><li>merge the node&#x2019;s view with the peer node&#x2019;s view on the gossip exchange</li></ol><p>Put another way, every node maintains a small local membership table with a partial view of the system and periodically refreshes the table through gossip messages. The gossip protocol can leverage probabilistic distribution for selecting a peer node to reduce duplicate message transmission to the same node [4].</p><p>The application state can be transferred as key-value pairs via the gossip protocol. The most recent value must be transferred when multiple changes are performed to the same key by a node. The API provided by the gossip protocol to orchestrate application state exchange is the following [6]:</p><ul><li>/gossip/on-join</li><li>/gossip/on-alive</li><li>/gossip/on-dead</li><li>/gossip/on-change</li></ul><p>The <strong>seed nodes</strong> are fully functional nodes that are based on static configuration. Every node in the system must be aware of the seed nodes. The gossip system interacts with the seed nodes to prevent logical divisions [4], [12]. The following is the high-level workflow when a node receives a gossip message with the node metadata of a peer node [12]:</p><ol><li>compares the incoming gossip message to identify the missing values on the local node&#x2019;s dataset</li><li>compare the incoming gossip message to identify the missing values on the peer node&#x2019;s dataset</li><li>higher version value is chosen when the node already contains the values present in the incoming gossip message</li><li>append the missing values in the local node&#x2019;s dataset</li><li>return the missing values on the peer node&#x2019;s dataset in the response</li><li>update the peer node&#x2019;s dataset with the received response</li></ol><p>It is typical to transfer the entire node metadata through the gossip protocol on a node startup. An in-memory version number can be maintained by each node to send only incremental updates of the node metadata through the gossip protocol.</p><p>The <a href="https://martinfowler.com/articles/patterns-of-distributed-systems/generation.html?ref=highscalability.com" rel="noopener">generation clock</a> is a monotonically increasing number indicating the generation of the server. The generation clock is incremented whenever the node restarts. The version number guarantees the ordering and versioning of the application state. The version number can only be incremented [6]. The generation clock can be used along with the version number to detect node metadata changes correctly on node restarts [12].</p><p>The <strong>gossiper timer</strong> is a component of the gossip protocol that will ensure every node eventually contains the crucial metadata about peer nodes, including the nodes that are behind a network partition. Every node includes a heartbeat associated with it. The heartbeat state consists of the generation and version number. The application state consists of key-value pairs representing the node state and a version number [6].</p><p>A node initiating a gossip exchange sends a <strong>gossip digest synchronization</strong> message that consists of a list of <strong>gossip digests</strong>. The gossip digest consists of an endpoint address, a generation number, and a version number. The gossip digest acknowledgment message consists of a gossip digest list and an endpoint state list. The sample schema for the gossip digest is the following [6]:EndPointState: 10.0.1.42<br />  HeartBeatState: generation: 1259904231, version: 761<br />  ApplicationState: &quot;average-load&quot;: 2.4, generation: 1659909691, version: 42<br />  ApplicationState: &quot;bootstrapping&quot;: pxLpassF9XD8Kymj, generation: 1259909615, version: 90</p><h3 id="gossip-protocol-use-cases">Gossip Protocol Use Cases</h3><p>The gossip protocol is used in a multitude of applications where eventual consistency is favored. The popular applications of the gossip protocol are as follows [8], [5], [4], [7], [12]:</p><ul><li>database replication</li><li>information dissemination</li><li>maintaining cluster membership</li><li>failure detection</li><li>generate aggregations (calculate average, maximum, sum)</li><li>generate <a href="https://en.wikipedia.org/wiki/Overlay_network?ref=highscalability.com" rel="noopener">overlay networks</a></li><li>leader election</li></ul><p>The gossip protocol can be used to detect the failure of a node in a distributed system with high probability. The failure detection of nodes can save resources such as CPU, bandwidth, and  queue space. In a distributed system, it is not sufficient to assert a node failure when a single client cannot interact with the particular node because there might be an occurrence of network partition or client failure [1]. It can be concluded with certainty the failure of a particular node when several nodes (<strong>clients</strong>) confirm the liveness of the particular node through gossip protocol [4], [11].</p><p>The gossip protocol is significantly more reliable for data exchange and command and control than through TCP connections. The gossip protocol enables abstracting communication about node and subsystem properties out of the application logic [11]. The node statistics such as the average load and free memory can be transmitted in gossip messages to improve the local decision-making on fanout.</p><p>The subsystem information such as queue depth, key metadata such as configuration changes, and even request-response can be transmitted through the gossip protocol. The aggregation of node update messages via gossip protocol allows sending data in a single chunk instead of multiple small messages to reduce the communication overhead [11].</p><p>The messages can be routed across the cluster optimally by identifying the liveness of nodes [9]. The decision-making at the local node level without involving a centralized service is the key to scaling the gossip protocol [4], [11]. The messages can be versioned with a vector clock to ignore the older message versions by the node [9], [2]. The real-world use cases of the gossip protocol are the following [12], [8], [4], [9], [11]:</p><ul><li><a href="https://cassandra.apache.org/_/index.html?ref=highscalability.com" rel="noopener">Apache Cassandra</a> employs the gossip protocol to maintain cluster membership, transfer node metadata (token assignment), repair unread data using Merkle trees, and node failure detection</li><li><a href="https://www.consul.io/?ref=highscalability.com" rel="noopener">Consul</a> utilizes the <a href="https://www.cs.cornell.edu/projects/Quicksilver/public_pdfs/SWIM.pdf?ref=highscalability.com" rel="noopener">swim-gossip</a> protocol variant for group membership, leader election, and failure detection of consul agents</li><li><a href="https://www.cockroachlabs.com/docs/stable/?ref=highscalability.com" rel="noopener">CockroachDB</a> operates the gossip protocol to propagate the node metadata</li><li><a href="https://hyperledger-fabric.readthedocs.io/en/release-2.2/gossip.html?ref=highscalability.com" rel="noopener">Hyperledger Fabric</a> blockchain uses the gossip protocol for group membership and ledger metadata transfer</li><li><a href="https://riak.com/?ref=highscalability.com" rel="noopener">Riak</a> utilizes the gossip protocol to transmit <a href="https://systemdesign.one/consistent-hashing-explained/?ref=highscalability.com" rel="noopener">consistent hash ring</a> state and node metadata around the cluster</li><li><a href="https://aws.amazon.com/s3/?ref=highscalability.com" rel="noopener">Amazon S3</a> uses the gossip protocol to spread server state across the system</li><li><a href="https://aws.amazon.com/dynamodb/?ref=highscalability.com" rel="noopener">Amazon Dynamo</a> employs the gossip protocol for failure detection, and keeping track of node membership</li><li><a href="https://redis.io/?ref=highscalability.com" rel="noopener">Redis</a> cluster uses the gossip protocol to propagate the node metadata</li><li>Bitcoin uses the gossip protocol to spread the nonce value across the mining nodes</li></ul><h3 id="gossip-protocol-advantages">Gossip Protocol Advantages</h3><p>The advantages of gossip protocol are the following [8], [2], [7], [4], [5]:</p><ul><li>scalable</li><li>fault tolerant</li><li>robust</li><li>convergent consistency</li><li>decentralized</li><li>simplicity</li><li>integration and interoperability</li><li>bounded load</li></ul><h4 id="scalability">Scalability</h4><p>Scalability is the ability of the system to handle the increasing load without degradation of the performance [2]. The gossip protocol cycle requires logarithmic time to achieve convergence. In addition, every node interacts with only a fixed number of nodes and sends only a fixed number of messages independent of the  number of nodes in the system. A node doesn&#x2019;t wait for an acknowledgment to improve latency [8], [4], [5].</p><h4 id="fault-tolerance">Fault Tolerance</h4><p>Fault tolerance is the ability of the system to remain functional in the occurrence of failures such as node crashes, network partitions, or message loss. The distributed system employing the gossip protocol is fault tolerant due to tolerance towards unreliable networks. The redundancy, parallelism, and randomness offered by the gossip protocol improve the fault tolerance of the system [2].</p><p>Furthermore, the symmetric and decentralized nature of the nodes strengthens the fault tolerance of the gossip protocol [5]. The same message is usually transmitted several times across multiple nodes. Put another way, there are many routes for the message flow between the source and destination. So, a node failure is overcome via message transmission through another node [8], [4].</p><h4 id="robustness">Robustness</h4><p>The symmetric nature of the nodes participating in the gossip protocol improves the robustness of the system [5], [4]. A node failure will not disrupt the system quality. The gossip protocol is also robust against transient network partitions. However, the gossip protocol is not robust against a malfunctioning node or a malicious gossip message unless the data is self-verified [8], [7].</p><p>A score-based reputation system for nodes can be used to prevent gossip system corruption by malicious nodes. Appropriate mechanisms and policies such as encryption, authentication, and authorization must be implemented to enforce the privacy and security of the gossip system [2].</p><h4 id="convergent-consistency"><strong>Convergent Consistency</strong></h4><p>Consistency is the technique of ensuring the same state view across every node in the system. The different consistency levels  such as strong, eventual, causal, and probabilistic consistency have different implications on the performance, availability, and correctness of the system [2]. The gossip protocol converges to a consistent state in logarithmic time complexity through the exponential spread of data [8], [5].</p><h4 id="decentralization">Decentralization</h4><p>The gossip protocol offers an extremely decentralized model of information discovery through peer-to-peer communication [8], [4], [5].</p><h4 id="simplicity">Simplicity</h4><p>Most variants of the gossip protocol can be implemented with very little code and low complexity [8], [5]. The symmetric nature of the nodes makes it trivial to execute the gossip protocol [7].</p><h4 id="integration-and-interoperability">Integration and Interoperability</h4><p>The gossip protocol can be integrated and interoperated with distributed system components such as the database, cache, and queue. Common interfaces, data formats, and protocols must be defined to implement the gossip protocol across different distributed system components [2].</p><h4 id="bounded-load">Bounded Load</h4><p>The classic distributed system protocols usually generate high surge loads that might overload individual distributed system components. The gossip protocol will produce only a strictly bounded worst-case load on individual distributed system components to avoid the disruption of service quality. The peer node selection in the gossip protocol can be tuned to reduce the load on network links. In practice, the load generated by the gossip protocol is not only bounded but also negligible compared to the available bandwidth [7].</p><h3 id="gossip-protocol-disadvantages">Gossip Protocol Disadvantages</h3><p>The disadvantages of the gossip protocol are the following [1], [5], [8], [2], [7]:</p><ul><li>eventual consistency</li><li>unawareness of network partitions</li><li>relatively high bandwidth consumption</li><li>increased latency</li><li>difficulty in debugging and testing</li><li>membership protocol is not scalable</li><li>prone to computational errors</li></ul><h4 id="eventually-consistent">Eventually Consistent</h4><p>The gossip protocol is inherently eventually consistent [1]. The gossip protocol is relatively slower compared to multicast [5]. There is also an overhead associated with gossip messages and the gossip behavior depends on the network topology and node heterogeneity [2]. Therefore, there will be some delay to recognize a new node or a node failure by the cluster [12].</p><h4 id="network-partition-unawareness">Network Partition Unawareness</h4><p>When a network partition occurs, the nodes in the sub-partition will still gossip with each other. Hence, the gossip protocol is unaware of network partitions and might significantly delay message propagation [1], [7].</p><h4 id="bandwidth">Bandwidth</h4><p>The gossip protocol is not known for efficiency as the same message might be retransmitted to the same node multiple times consuming unnecessary bandwidth [5], [8]. Although the bandwidth usage by the gossip protocol is limited due to bounded message size and periodic exchange of messages, the effective fanout by gossip exchange might degrade when the amount of information that a node should gossip exceeds the bounded message size [7].</p><p>The saturation point of the gossip protocol depends on different parameters such as the rate of generation of messages, message size, fanout, and the type of gossip protocol [7], [8].</p><h4 id="latency">Latency</h4><p>The usage of the gossip protocol results in increased latency because the node must wait for the next gossip cycle (interval) to transmit the message [5]. The message doesn&#x2019;t trigger the gossip exchange but the gossip protocol interval timer does. The time complexity required to spread the message across the system is logarithmic [8], [4].</p><h4 id="debugging-and-testing">Debugging and Testing</h4><p>Debugging is identifying and fixing the failures that cause the gossip protocol to deviate from the expected behavior. Testing is the ability to verify whether the gossip protocol meets functional and non-functional requirements such as performance, reliability, and security [2].</p><p>The inherent non-determinism and distributed nature of the gossip protocol make it hard to debug and reproduce the failures [8], [5], [2]. Tools and techniques such as simulation, emulation, logging, tracing, monitoring, and visualization can be used to test and debug the gossip system [2].</p><h4 id="scalability-1">Scalability</h4><p>Most variants of the gossip protocol rely on a non-scalable membership protocol [5].</p><h4 id="computational-error">Computational Error</h4><p>The gossip protocol is inclined to computational errors due to malicious nodes. The nodes should implement a self-correcting mechanism because the robustness of the gossip protocol is limited to certain classes of failures [7]. Nevertheless, the gossip protocol is extremely reliable, and outcomes with a probability of one are typical [8].</p><h3 id="summary">Summary</h3><p>Gossiping in a distributed system is a boon while gossiping in the meat world is a curse.
