This is a repost from her Medium article, approved by the author.</blockquote><img alt="Capturing A Billion Emo(j)i-ons" src="https://storage.ghost.io/c/64/72/647204cd-7ad2-4539-b98a-3489074b932d/content/images/2024/03/1-rSRWALA4XzOdDcn-5vv7Zw.gif" /><p>In stadiums, sports fans love to express themselves by cheering for their favorite teams, holding up placards and team logos. Emoji&#x2019;s allow fans at home to rapidly express themselves, and when millions of fans do it simultaneously, that&#x2019;s a technical problem that we solved!</p><p>At Hotstar, we strive to build features that make the viewing experience more engaging to users with an interactive Social Feed. We discussed the &#x201c;<a href="https://blog.hotstar.com/the-hotstar-sports-bar-a7fcfd870a12?ref=highscalability.com" rel="noopener ugc nofollow">Hotstar Sports Bar</a>&#x201d; from a design and product point of view. Here we talk about how we built this feature from a technical perspective.</p><figure class="kg-card kg-image-card kg-card-hascaption"><img alt="Capturing A Billion Emo(j)i-ons" class="kg-image" height="894" src="https://miro.medium.com/v2/resize:fit:1190/1*rSRWALA4XzOdDcn-5vv7Zw.gif" width="595" /><figcaption><span style="white-space: pre-wrap;">Social Feed GIF</span></figcaption></figure><p>Emojis show the real-time changes in the opinions of the audience. When Dhoni bats, people want a boundary shot on every ball but when he is keeping, people want to see the wickets fall. Collecting these user-generated signals in real-time, condensing these opinions to an emoji swarm that shows the mood of the audience and displaying the changing moods in real-time is challenging when you plan to receive billions of such emoji submissions during a tournament.</p><p>For a while, we used a third-party service to power this feature. However, we could not achieve the performance and stability we hoped for, while also not being a cost-effective. The time had come to bring this core service, in-house.</p><p>In this article, we&#x2019;ll discuss the architecture of&#xa0;<strong><em>Emojis</em></strong>, key design principles involved in building it, the impact created and how it paved the way for building other features like&#xa0;<strong>Voting.</strong></p><h2 id="high-level-design">High-Level Design</h2><figure class="kg-card kg-image-card kg-card-hascaption"><img alt="Capturing A Billion Emo(j)i-ons" class="kg-image" height="427" src="https://miro.medium.com/v2/resize:fit:1400/1*8OmnTXV8SPUDwH68FdSD5Q.png" width="719" /><figcaption><span style="white-space: pre-wrap;">Architecture Diagram</span></figcaption></figure><h3 id="key-design-principles">Key Design Principles</h3><h3 id="scalability">Scalability</h3><p>The system should be horizontally scalable to be able to support the increasing traffic. We achieved horizontal scalability with the help of load balancers and configured auto-scaling to scale the resources up or down.</p><h3 id="decomposition">Decomposition</h3><p>The system needs to be decomposed into smaller components each being able to carry out the assigned task independent of each other. This also provides us with the ability to scale each component as needed.</p><h3 id="asynchronous">Asynchronous</h3><p>Asynchronous processing enables execution without blocking resources and thus supports higher concurrency. We will talk more about this later.</p><h2 id="implementation">Implementation</h2><h3 id="how-are-client-requests-handled">How are client requests handled?</h3><figure class="kg-card kg-image-card"><img alt="Capturing A Billion Emo(j)i-ons" class="kg-image" height="127" src="https://miro.medium.com/v2/resize:fit:1202/1*-CMOfVvMvEeoRFXrJtCxXg.png" width="601" /></figure><p>Clients send user&#x2019;s submitted emojis via HTTP API. To prevent hogging the client connection, heavy processing on the API needs to be done offline. We need to write the data somewhere so processing applications can consume it.&#xa0;<strong>Message Queue</strong>&#xa0;is a commonly used mechanism for asynchronous communication between applications.</p><p>There are a lot of message queues available out there. A comparison of some of the available Message Queues is reviewed in this&#xa0;<a href="https://blog.scottlogic.com/2018/04/17/comparing-big-data-messaging.html?ref=highscalability.com" rel="noopener ugc nofollow">blog</a>. For&#xa0;<strong>Emojis</strong>, we needed a technology that offered high throughput, availability, low latency and supports consumer groups.&#xa0;<strong>Kafka</strong>&#xa0;seemed like the best option but managing Kafka on our own takes significant effort. Thankfully, Hotstar has an amazing data platform called&#xa0;<a href="https://blog.hotstar.com/data-democratisation-hotstar-93ebfb1e688d?ref=highscalability.com" rel="noopener ugc nofollow"><strong><em>Knol</em></strong></a>&#xa0;built on top of Kafka which is flexible for all our use cases.</p><h2 id="how-do-we-write-messages-to-the-queue"><strong>How do we write messages to the queue?</strong></h2><figure class="kg-card kg-image-card"><img alt="Capturing A Billion Emo(j)i-ons" class="kg-image" height="127" src="https://miro.medium.com/v2/resize:fit:1202/1*JISr-cM9nj3wbtYcAGvqTw.png" width="601" /></figure><p><strong>Synchronous</strong>: Wait for the acknowledgment that the message is written before sending a success response to clients. In case of a failure, we could have retries configured at both server and client. If your data is transactional or cannot suffer any loss, this approach is preferable.</p><p><strong>Asynchronous:&#xa0;</strong>Write the message to a local buffer and respond with success to clients. Messages from the buffer could be written asynchronously to the queue. The downside is that if not handled properly, this could result in data loss.</p><p>For&#xa0;<em>Emojis</em>, we need very low latency and data loss in rare scenarios is not a big concern (<em>although we haven&#x2019;t seen any so far</em>). So we chose the Asynchronous approach.</p><p><strong><em>Golang</em></strong>&#xa0;has great support for concurrency. It ships with an implementation called Goroutines. Goroutines are lightweight threads that can execute functions asynchronously. We just need to say&#xa0;<code>go do_something()</code>. We use&#xa0;<a href="https://tour.golang.org/concurrency/1?ref=highscalability.com" rel="noopener ugc nofollow">Goroutines</a>&#xa0;and&#xa0;<a href="https://tour.golang.org/concurrency/2?ref=highscalability.com" rel="noopener ugc nofollow">Channels</a>&#xa0;in Golang to write messages to Kafka. Messages to be produced are written to a Channel. A Producer runs in the background as a Goroutine and flushes the data periodically to Kafka. Using client libraries like&#xa0;<a href="https://github.com/confluentinc/confluent-kafka-go?ref=highscalability.com" rel="noopener ugc nofollow"><em>Confluent</em></a>&#xa0;or&#xa0;<a href="https://github.com/Shopify/sarama?ref=highscalability.com" rel="noopener ugc nofollow"><em>Sarama</em></a>, we can provide the flush configuration to achieve optimal performance. We configured our flush interval to&#xa0;<code>500ms</code>&#xa0;and maximum messages sent to Kafka broker in a single request to&#xa0;<code>20000</code>.</p><h2 id="how-does-the-processing-happen"><strong>How does the processing happen?</strong></h2><figure class="kg-card kg-image-card"><img alt="Capturing A Billion Emo(j)i-ons" class="kg-image" height="127" src="https://miro.medium.com/v2/resize:fit:1202/1*dUoAgXg2ck-bsthn4sKiPw.png" width="601" /></figure><p><strong>Goal</strong>: Consume a stream of data from Kafka and compute aggregates of the data over an interval. Time interval should be small enough to provide a real-time experience to users.</p><p>After considering different streaming frameworks like Flink, Spark, Storm, Kafka Streams we decided to go with Spark. Spark has support for micro batching and aggregations which are essential for our use case and better community support compared to competitors like Flink. Check out&#xa0;<a href="https://medium.com/@chandanbaranwal/spark-streaming-vs-flink-vs-storm-vs-kafka-streams-vs-samza-choose-your-stream-processing-91ea3f04675b?ref=highscalability.com" rel="noopener">this blog</a>for more details about different streaming frameworks.</p><p>We wrote a Spark streaming job that computes aggregates over a batch of 2 seconds and writes computed data to another Kafka queue.</p><h2 id="what-about-data-delivery"><strong>What about data delivery?</strong></h2><figure class="kg-card kg-image-card"><img alt="Capturing A Billion Emo(j)i-ons" class="kg-image" height="161" src="https://miro.medium.com/v2/resize:fit:1202/1*aIpj5dcl1sHZ_DnSgYGYgA.png" width="601" /></figure><p>We use PubSub as our delivery mechanism. PubSub is a real-time messaging infrastructure built at Hotstar to deliver messages to users in our Social Feed. You can dig deeper into the journey of PubSub in&#xa0;<a href="https://blog.hotstar.com/building-pubsub-for-50m-concurrent-socket-connections-5506e3c3dabf?ref=highscalability.com" rel="noopener ugc nofollow">this article</a>.</p><p>We wrote a simple Kafka consumer in Python. Consumption rate depends on the batch duration configured in the Spark job. Let&#x2019;s say that it&#x2019;s set to 1 second, this consumer would receive a message per second. We perform normalization over the data and send top (relatively more popular) emojis to PubSub. Clients receive messages from PubSub and show&#xa0;<em>Emojis&#xa0;</em>animation to users.</p><h2 id="impact">Impact</h2><p>Emojis are a huge hit at Hotstar. We received around 5 Billion Emojis from 55.83 Million users during the ICC Cricket World Cup 2019. This system has captured more than 6.5 Billion Emojis to date. Here&#x2019;s what we achieved from building this in-house.</p><figure class="kg-card kg-image-card"><img alt="Capturing A Billion Emo(j)i-ons" class="kg-image" height="221" src="https://miro.medium.com/v2/resize:fit:1342/1*OezlTnyeY2eQaU1wmolc9g.png" width="671" /></figure><h2 id="voting-and-more">Voting and more</h2><p>If we think about it,&#xa0;<em>Emojis</em>&#xa0;and&#xa0;<em>Voting</em>&#xa0;have a common problem statement</p><blockquote><strong>Process quantifiable user responses in near real-time</strong></blockquote><p>So we extended this system to build the&#xa0;<strong>Voting</strong>&#xa0;feature. Hotstar is currently the sole voting platform for a few big Indian reality shows like&#xa0;<strong>Dance Plus</strong>and&#xa0;<strong>Bigg Boss</strong>&#xa0;(Telugu, Tamil, Malayalam). This infrastructure equipped to power Emojis and Voting for Hotstar, can now also power Polls and Trivia contests out of the box.</p><figure class="kg-card kg-image-card"><img alt="Capturing A Billion Emo(j)i-ons" class="kg-image" height="384" src="https://miro.medium.com/v2/resize:fit:694/1*eMjSPgKgB0iCCEt_F8WMBQ.png" width="347" /></figure><blockquote>We have received around 3 Billion votes to date!</blockquote><figure class="kg-card kg-image-card kg-card-hascaption"><img alt="Capturing A Billion Emo(j)i-ons" class="kg-image" height="539" src="https://miro.medium.com/v2/resize:fit:1400/1*kIzYvy84FsMGW4UUlaYjXw.png" width="1400" /><figcaption><span style="white-space: pre-wrap;">Collection of Emojis on Social Feed</span></figcaption></figure><p>Next time you visit our Social Feed, tap away on these.</p><p>Want to work with us?
