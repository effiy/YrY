# Architecting Offline-First Generative AI for Edge Deployments on AWS

> **As an** AI engineer deploying to edge environments, **I want to** build generative AI applications that work without cloud connectivity, **so that** industrial operators in remote locations get instant access to equipment documentation, troubleshooting, and safety procedures.

## Summary

- A reference architecture for deploying generative AI at the edge using AWS services, addressing environments where cloud connectivity is unreliable or unavailable (offshore platforms, remote agriculture, manufacturing).
- The architecture spans three layers: cloud-side model customization (Amazon Bedrock, SageMaker AI), deployment orchestration (IoT Greengrass), and edge-side inference (Ollama, Strands Agents, ChromaDB).
- The recommended approach is hybrid (FT + RAG): fine-tune a small language model for domain-specific behavior, and use RAG for up-to-date knowledge retrieval without retraining.
- Evaluation results: fine-tuned gpt-oss-20b + RAG scored 81% average across three LLM judges, compared to 68% for the base model + RAG.

## Core viewpoints

### 1. Model customization strategy is the primary architectural decision
The choice between fine-tuning (FT), continued pre-training (CPT), and RAG is not just about model quality -- it is about architectural complexity, hardware constraints, and data pipeline requirements. The hybrid FT + RAG approach balances compactness (fine-tuning keeps the model task-specific) with freshness (RAG provides up-to-date knowledge without retraining). The full RAG pipeline runs on CPU/SSD with zero GPU VRAM consumption, keeping GPU memory dedicated to the LLM.

### 2. The cloud-to-edge feedback loop is the differentiator
The architecture is not just "deploy and forget." When connectivity is available, user interactions and feedback flow back to the cloud, enabling ongoing model refinement through the FMOps pipeline. Feedback is queued locally and synchronized opportunistically, making the system resilient to connectivity gaps. This creates a virtuous cycle: edge usage data improves the next model version, which Greengrass deploys back to the device.

### 3. Security perimeter shifts to the edge device
Moving inference to the edge means you own the full security stack. The reference architecture includes: full-disk encryption, TLS 1.2+ for all communication (including loopback), input validation with prompt guardrails, network segmentation, and IAM least privilege on the cloud side. The edge device is now the security boundary, not the cloud.

### 4. Hardware selection is a binding constraint
The edge device needs sufficient VRAM (16GB+ recommended) to run a quantized small language model. The architecture was tested on g4dn.12xlarge (4x NVIDIA T4 GPUs, 16GB each) and NVIDIA Jetson Xavier. Two deployment strategies are available: model replication (full copy on each GPU for throughput) and tensor parallelism (model sharded across GPUs for longer context).

### 5. The evaluation methodology must mirror the deployment reality
The architecture was evaluated using three different LLM judges (Claude 4.5 Haiku, Sonnet, Nova Pro) on a 12-point scale, producing an average score of 81% for the fine-tuned model + RAG. This multi-judge approach is critical because single-judge evaluations are unreliable -- different models have different biases and scoring tendencies. The evaluation methodology is as important as the architecture itself, because without trustworthy evaluation, you cannot iterate on the model customization strategy.

## Key info

- The architecture uses gpt-oss-20b (MoE: 21B total, 3.6B active per token, 32 experts, 128K context).
- ChromaDB with sentence-transformer embeddings (384 dimensions) runs on CPU; retrieval latency under 50ms for datasets up to 5GB.
- Fine-tuning used QLoRA on 30 domain-specific Q&A pairs generated by Amazon Nova Pro.
- Three LLM judges (Claude 4.5 Haiku, Sonnet, Nova Pro) scored responses on a 12-point scale.
- Fortune 500 companies lose an estimated $1.4 trillion annually due to unplanned downtime -- the primary use case driver.

## Action recommendations

1. Start by identifying a use case with clear connectivity constraints and work backward from edge hardware requirements to select a model customization strategy.
2. Use the hybrid FT + RAG approach as the default starting point: it balances capability with complexity for most edge deployments.
3. Design the feedback loop from day one: edge usage data should flow back to the cloud for continuous model improvement when connectivity permits.
4. Treat edge security as a first-class concern: implement full-disk encryption, TLS everywhere, prompt guardrails, and network segmentation.
5. Choose your GPU deployment strategy based on workload: model replication for high-concurrency short queries, tensor parallelism for fewer users with longer interactions.

## Anti-patterns

- **Deploying a cloud-sized model to the edge.** The model must fit within edge hardware constraints (typically 16GB VRAM).

- **Treating the edge deployment as static.** Without the feedback loop, the model stagnates and does not improve with usage.

- **Assuming cloud security patterns apply unchanged to the edge.** The trust boundary shifts, and the device owner now owns the full security stack.

- **Using RAG alone without fine-tuning for domain-specific tasks.** The evaluation showed FT + RAG significantly outperforms base model + RAG.

- **Over-investing in model customization before validating the data pipeline.** The quality of fine-tuning is limited by the quality and quantity of domain-specific Q&A pairs. If the data pipeline for generating and curating these pairs is not in place, the fine-tuning investment will produce a model that is worse than the base model on edge cases. Build the data pipeline first, then fine-tune.
