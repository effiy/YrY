# 服务容量规划

> Yi 家族基础设施的容量规划指南。在资源有限的自托管环境中，容量规划不是"买多少服务器"的问题，而是"当前的瓶颈在哪里、下一个瓶颈会是什么"的问题。

## 当前基线

YrY 当前运行在单机开发环境中，所有服务共用一台机器：

| 服务 | 当前负载 | 峰值负载 | 余量 | 瓶颈 |
|---|---|---|---|---|
| YiAi (FastAPI) | 单用户 | 约 5 并发 | 高 | uvicorn 单 worker，CPU 绑定 |
| MongoDB | < 1GB 数据 | — | 高 | 磁盘空间、内存（WiredTiger cache） |
| Ollama | 单模型（qwen3.5:4b） | 1 并发推理 | **低（GPU 绑定）** | GPU 显存（4B 模型约需 2.5-3GB VRAM） |

### 资源消耗详情

| 组件 | CPU | 内存 | 磁盘 | 网络 |
|---|---|---|---|---|
| YiAi uvicorn | 空闲 < 1%，请求时 5-15% | 约 200-400MB | 日志 + RAG 索引：约 500MB | 内网无限制 |
| MongoDB | 空闲 < 1%，查询时 2-5% | WiredTiger cache：约 200MB + 数据 | 数据文件：按集合增长 | 内网无限制 |
| Ollama | 推理时 100%（单核） | 模型加载：约 3-4GB | 模型文件：约 2.5GB | 内网无限制 |

## 关键监控指标

### YiAi（FastAPI 应用）

| 指标 | 含义 | 当前基线 | 关注阈值 |
|---|---|---|---|
| 请求延迟 p50 | 50% 请求的响应时间 | < 50ms（简单查询） | > 200ms |
| 请求延迟 p95 | 95% 请求的响应时间 | < 200ms | > 500ms |
| 并发连接数 | 活跃的 SSE 和其他连接 | < 5 | > 20（单 worker 限制） |
| 错误率 | 5xx + 网络错误比例 | < 1% | > 5% |

### MongoDB

| 指标 | 含义 | 当前基线 | 关注阈值 |
|---|---|---|---|
| 存储大小 | 数据文件占用磁盘 | < 1GB | > 80% 磁盘空间（macOS 通常 256-512GB） |
| 连接池活跃连接 | Motor async 连接池使用 | < 5 | > 80% 连接池（pool_size=10） |
| 查询延迟 | CRUD 操作耗时 | < 10ms | > 100ms（考虑建索引） |

### Ollama（LLM 推理）

| 指标 | 含义 | 当前基线 | 关注阈值 |
|---|---|---|---|
| 推理时间 | 单次 chat 请求耗时 | 取决于 prompt 长度 | 主观：用户感知 > 10s 为慢 |
| 队列深度 | 等待推理的请求数 | 0-1 | > 3（用户感知排队） |
| GPU 显存使用 | 模型占用的 VRAM | 2.5-3GB（4B 模型） | > 可用 VRAM（无法加载模型） |

## 扩缩容决策表

| 症状 | 判断 | 操作 |
|---|---|---|
| YiAi p95 延迟 > 500ms | Python GIL 或 CPU 瓶颈 | 增加 uvicorn workers（`--workers 4`） |
| MongoDB 存储 > 80% 磁盘 | 数据累积 | 归档旧数据或扩展磁盘 |
| MongoDB 查询延迟 > 100ms | 缺少索引或全表扫描 | 分析慢查询 → 添加索引 |
| Ollama 队列深度 > 3 | GPU 推理成为瓶颈 | 使用更小模型（1.5B）、添加 GPU 或切换到云 API |
| Ollama 推理超时频繁 | 弱模型处理长 prompt | 设置更长的超时、优化 prompt 长度或切换到更强模型 |

## 规划节奏

| 频率 | 活动 | 产出 |
|---|---|---|
| 每月 | 审查关键指标，更新基线数据 | 更新本文档的"当前基线"表 |
| 每季度 | 预测下季度的负载增长，推荐变更 | 容量预测报告（口头或简短文档） |
| 重大功能上线前 | 审查受影响服务的容量，必要时做压力测试 | 上线前的容量检查清单 |

## 适用场景

| 场景 | 使用方式 |
|---|---|
| 新功能上线前 | 评估新功能对 MongoDB 查询模式的影响——新集合？新索引？数据量预估？ |
| 用户量增长 | 监控并发连接数，评估单 worker 是否够用 |
| 模型升级/切换 | 检查新模型的 VRAM 需求和推理速度——7B 模型约需 5-6GB VRAM |
| 磁盘空间告警 | MongoDB 数据归档方案——压缩、删除旧数据、迁移到 OSS |

## 反模式

| 反模式 | 为什么有问题 | 正确做法 |
|---|---|---|
| 没有监控就开始优化 | 不知道真正的瓶颈在哪里，凭直觉优化 | 先建立监控，量化瓶颈，再优化 |
| 过早优化容量 | 单用户环境下优化并发性能是浪费 | 在用户量真实增长到接近阈值时再扩容 |
| 所有服务用同一阈值 | 不同服务的瓶颈类型不同——CPU/内存/IO/网络 | 按服务类型分别设置监控阈值 |
| 忽视 Ollama 的 GPU 约束 | LLM 推理是计算密集型，不是 IO 密集型 | 评估模型大小时始终先查 VRAM 需求 |
