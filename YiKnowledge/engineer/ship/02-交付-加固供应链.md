# 加固软件供应链

> **适用时机**：每次发布前和新增依赖时。供应链攻击是增长最快的攻击向量——一个被攻破的依赖可以暴露整个系统的所有数据。

## YiAi —— Python 供应链

### 依赖审计

```bash
# 检查已知漏洞
pip-audit

# 检查过期包
pip list --outdated

# 生成带哈希锁定的 requirements.txt
pip freeze --require-hashes > requirements.txt
```

### 锁文件完整性

```bash
# 验证已安装的包与 requirements 一致
pip check

# 检查依赖混淆攻击（typosquatting）
pip list --format=json | python3 -c "
import json, sys
packages = json.load(sys.stdin)
for p in packages:
    name = p['name'].lower()
    # 标记可疑：连字符被替换为下划线、额外字符
    if name.startswith('python-') or name.endswith('-py'):
        print(f'SUSPICIOUS: {p[\"name\"]}=={p[\"version\"]}')
"
```

### 依赖最小化原则

```txt
# requirements.txt —— 保持最小化
fastapi==0.115.*
uvicorn[standard]==0.34.*
motor==3.7.*
pydantic==2.10.*
pydantic-settings==2.7.*
pyyaml==6.0.*
tenacity==9.0.*
httpx==0.28.*
apscheduler==3.11.*
llama-index==0.12.*
ollama==0.4.*
```

**规则**：每个依赖必须证明自己的价值。新增依赖前回答四个问题：
1. 能否在 50 行内自行实现？（如果可以，自己写）
2. 包是否在积极维护？（最近 3 个月有 > 1 次 commit）
3. 是否有已知漏洞？（执行 `pip-audit`）
4. 会引入多少传递依赖？（检查依赖树）

### YrY Python 依赖的已识别高风险区域

| 依赖 | 风险 | 缓解措施 |
|---|---|---|
| `llama-index` | 传递依赖极多（50+），更新频繁 | 锁定主版本，每月检查兼容性 |
| `ollama` | 直接调用本地 AI 服务，输入注入风险 | 限制 prompt 长度，对用户输入进行基本验证 |
| `aiohttp`（llama-index 传递依赖） | HTTP 客户端曾有多起 CVE | 通过 pip-audit 定期检查，固定次要版本 |

## YiVad/YiPet —— Node.js 供应链

### 依赖审计

```bash
# 检查已知漏洞
npm audit

# 自动修复（不破坏 API 的变更）
npm audit fix

# 检查过期包
npm outdated

# 检查包体积影响
npx bundlesize
```

### 锁文件完整性

```bash
# 验证 package-lock.json 与 package.json 一致
npm ci  #（如果不匹配则失败）

# 检查签名完整性
npm audit signatures
```

### ESLint + Prettier 保证代码质量基线

YiVad 和 YiPet 使用 ESLint 10 + Prettier 3 进行代码检查和格式化。虽然这些工具链有较多的传递依赖，但它们是 Vue 3 + TypeScript 生态系统的成熟标准：

```javascript
// eslint.config.mjs
import eslint from '@eslint/js';
import tsPlugin from '@typescript-eslint/eslint-plugin';

export default [
  eslint.configs.recommended,
  // TypeScript + Vue 规则
];
```

**权衡**：ESLint + Prettier 的传递依赖比单工具方案（如 Biome）多，但它们在 Vue 3 + TypeScript 支持上更成熟。通过以下措施管理风险：
- 定期运行 `npm audit`（每次发布前至少一次）
- 锁定精确版本（`package-lock.json` 已提交）
- CI 中使用 `npm ci` 而非 `npm install`

### YrY Node.js 依赖的已识别高风险区域

| 依赖 | 风险 | 缓解措施 |
|---|---|---|
| `element-plus` / `@element-plus/icons-vue` | UI 组件库体积大、更新频繁 | 锁定主版本，使用按需导入（`unplugin-vue-components`） |
| `echarts` | 体积大（完整版约 1MB），按需引入复杂 | 只引入使用的图表类型，而非完整库 |
| `marked`（Markdown 解析） | 渲染用户输入时需防范 XSS | 使用 DOMPurify 或类似方案在渲染前清除 HTML |

## 构建可重现性

### Python

```bash
# 锁定精确版本和哈希
pip-compile --generate-hashes requirements.in -o requirements.txt

# 从锁定版本安装
pip install --require-hashes -r requirements.txt
```

### Node.js

```bash
# 在 CI 中使用 ci（clean install）替代 install
npm ci

# 绝不使用 npm install（可能修改 lockfile）
```

## 供应链事故教训（来自 YiKnowledge）

知识库中记录了 [无锁文件导致的供应链事故复盘](../../srer/incident-response/tl-postmortem-no-lockfile-supply-chain-2026-07.md)：

| 教训 | 行动 |
|---|---|
| 无锁文件导致构建不可重现 | **始终提交** `package-lock.json` / `requirements.txt` |
| 一次依赖更新可能破坏生产 | 锁定精确版本；使用 `npm ci` / `pip install --require-hashes` |
| 发布前不做依赖审计 | 将 `npm audit` / `pip-audit` 添加到 CI 流水线 |

## 季度供应链检查清单

每季度执行以下检查：

- [ ] 运行 `pip-audit` / `npm audit` —— 修复所有严重和高危漏洞
- [ ] 审查本季度新增的依赖 —— 它们仍然需要吗？
- [ ] 检查被遗弃的依赖（> 6 个月无 commit）—— 寻找替代或自己维护
- [ ] 验证锁文件完整性（`npm ci` / `pip check`）
- [ ] 更新所有依赖到最新补丁版本（`npm update` / `pip install --upgrade`）
- [ ] 移除未使用的依赖（`npx depcheck` / 手动检查 `requirements.txt`）

## 适用场景

| 场景 | 操作 |
|---|---|
| 每次发布前 | 运行依赖审计（`npm audit` / `pip-audit`），修复高危漏洞 |
| 新增依赖时 | 执行依赖最小化四问 + 检查传递依赖树 |
| 季度检查 | 执行完整的检查清单 |
| 安全事故后 | 检查是否受影响的 CVE 影响，如果受影响则立即更新 |

## 反模式

| 反模式 | 为什么失败 | 正确做法 |
|---|---|---|
| CI 中使用 `npm install` | 可能修改 lockfile；构建不可重现 | 在 CI 中始终使用 `npm ci`；绝不使用 `npm install` |
| 不提交 lockfile | 依赖漂移；构建意外断开 | 始终提交 lockfile（`package-lock.json` / `requirements.txt`） |
| "只是一个小工具包，不需要审计" | Left-pad 事件：11 行代码破坏了数千个项目 | 审计每个依赖；优先自行编写小工具 |
| 忽略 `npm audit` 警告 | 已知漏洞累积；一个被利用就足以攻破 | 修复所有严重/高危漏洞；跟踪中低危漏洞 |
