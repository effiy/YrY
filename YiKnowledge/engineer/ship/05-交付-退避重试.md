# 指数退避重试

> **适用时机**：任何瞬态故障——网络超时、连接重置、限流、临时服务不可用。重试能够将瞬态故障变为用户无感知的成功响应。

## 何时重试（以及何时不重试）

| 应该重试 | 不应该重试 |
|---|---|
| 网络超时（请求未到达服务器） | 400 Bad Request（请求本身无效，重试不会变有效） |
| 连接重置（TCP 连接中断） | 401 Unauthorized（认证失败，不是瞬态问题） |
| 503 Service Unavailable（服务暂时不可用） | 403 Forbidden（权限不足，不是瞬态问题） |
| 429 Rate Limited（可等待后重试） | 404 Not Found（资源不存在，重试不会出现） |
| 数据库死锁（并发冲突，可重试） | 422 Unprocessable Entity（数据验证失败） |
| 临时 DNS 解析失败 | 任何 4xx 客户端错误 |

**核心规则**：只在 5xx 和网络错误上重试。永远不要在 4xx 上重试——修复请求内容，而非重试它。

### 为什么重复 4xx 请求是危险的

- **浪费资源**：同样的无效请求每次都会失败，重试只是在浪费客户端和服务器的资源
- **可能造成副作用**：如果请求已经部分执行（如数据库写入），多次重试可能创建重复数据
- **掩盖真正的 Bug**：看到重试后成功，开发者可能认为是"网络波动"而非代码错误

## Python 模式（YiAi —— tenacity）

### LLM 调用重试

```python
from tenacity import (
    retry,
    stop_after_attempt,
    wait_exponential,
    retry_if_exception_type,
    before_sleep_log,
)
import logging

logger = logging.getLogger(__name__)

# YiAi LLM 重试模式
@retry(
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=1, min=1, max=10),
    retry=retry_if_exception_type((ConnectionError, TimeoutError)),
    before_sleep=before_sleep_log(logger, logging.WARNING),
)
async def call_ollama_with_retry(prompt: str) -> dict:
    """调用 Ollama，在瞬态故障时重试。"""
    return await ollama_client.chat(prompt)
```

### MongoDB 操作重试

```python
@retry(
    stop=stop_after_attempt(5),
    wait=wait_exponential(multiplier=1, min=1, max=30),

async def mongodb_operation_with_retry(collection: str, query: dict):
```

### 退避时间示意

| 尝试次数 | 延迟（multiplier=1, min=1, max=10） |
|---|---|
| 第 1 次重试 | 1 秒 |
| 第 2 次重试 | 2 秒 |
| 第 3 次重试 | 4 秒 |
| 第 4 次重试 | 8 秒 |
| 第 5 次重试 | 10 秒（达到 max 上限） |

## TypeScript 模式（YiPet —— ApiClient）

```typescript
// YiPet/src/api/client.ts —— 带退避的重试
async function fetchWithRetry(
  url: string,
  options: RequestInit,
  maxRetries = 3,
): Promise<Response> {
  let lastError: Error;

  for (let attempt = 0; attempt <= maxRetries; attempt++) {
    try {
      const response = await fetch(url, options);

      // 只在 5xx 和网络错误上重试
      if (response.status < 500 || attempt === maxRetries) {
        return response;
      }

      // 429 Rate Limited —— 使用 Retry-After 响应头
      if (response.status === 429) {
        const retryAfter = response.headers.get('Retry-After');
        const delay = retryAfter
          ? parseInt(retryAfter) * 1000
          : (2 ** attempt) * 1000;
        await sleep(delay);
        continue;
      }
    } catch (err) {
      lastError = err as Error;
      if (attempt === maxRetries) throw lastError;
    }

    // 指数退避 + 随机抖动
    const delay = Math.min((2 ** attempt) * 1000, 30000);
    const jitter = Math.random() * 1000;
    await sleep(delay + jitter);
  }

  throw lastError!;
}
```

## 抖动（Jitter）—— 为什么重要

没有抖动，所有重试客户端在同一时刻同时发起请求 → 惊群效应（Thundering Herd）。

```
无抖动:
客户端 A: 在 1s, 2s, 4s, 8s 重试
客户端 B: 在 1s, 2s, 4s, 8s 重试  ← 完全同步 → 服务器瞬间过载

有抖动:
客户端 A: 在 1.3s, 2.7s, 4.1s, 8.9s 重试
客户端 B: 在 1.8s, 2.2s, 4.6s, 8.1s 重试  ← 分散分布 → 服务器平滑处理
```

## YiAi 各类操作的重试配置

| 组件 | 最大重试次数 | 退避策略 | 原因 |
|---|---|---|---|
| Ollama API 调用 | 2 次 | 1s, 2s | LLM 加载到 VRAM 中，短暂不可用 |
| MongoDB 操作 | 5 次 | 1s-30s 指数退避 | 连接池耗尽后会自动恢复 |
| OSS 文件操作 | 3 次 | 1s, 2s, 4s | 网络偶发波动 |
| Agent LLM 重试 | 2 次 | 1s, 2s | XML 解析错误、瞬态失败 |
| SSE 流重建 | 1 次 | 1s | 连接中断后快速尝试重建 |

## 熔断器 —— 当重试不够时

当服务持续不可用时，不断重试只会加剧问题。引入熔断器（Circuit Breaker）：

```python
# 简化版熔断器模式
class CircuitBreaker:
    def __init__(self, failure_threshold=5, recovery_timeout=60):
        self.failures = 0
        self.threshold = failure_threshold
        self.recovery = recovery_timeout
        self.last_failure = 0

    async def call(self, func, *args, **kwargs):
        # 熔断器打开时直接拒绝，快速失败
        if self.failures >= self.threshold:
            if time.time() - self.last_failure < self.recovery:
                raise Exception("熔断器已打开——请稍后重试")
            self.failures = 0  # 恢复超时后尝试半开

        try:
            result = await func(*args, **kwargs)
            self.failures = 0  # 成功则重置计数器
            return result
        except Exception:
            self.failures += 1
            self.last_failure = time.time()
            raise
```

熔断器有三个状态：
- **关闭**（正常）：请求正常通过，失败计数归零
- **打开**（熔断）：连续失败达到阈值，立即拒绝所有请求（快速失败而非长时间等待）
- **半开**（尝试恢复）：超时后允许一个请求探测，成功则关闭，失败则重新打开

## 适用场景

| 场景 | 重试策略 | 理由 |
|---|---|---|
| YiAi 调用 Ollama 推理 | 2 次，1s-2s | 模型可能在加载中，极其短暂 |
| YiVad/YiPet 调用 YiAi 数据接口 | 3 次，1s-4s-8s + jitter | 网络波动或服务短暂的不可用 |
| MongoDB 连接失败 | 5 次，1s-30s | 连接池恢复可能需要更长时间 |
| SSE 流中断 | 1 次，1s | 流不可幂等，仅尝试一次重建 |
| OSS 上传失败 | 3 次，1s-2s-4s | 对象存储的偶发网络问题 |

## 反模式

| 反模式 | 为什么失败 | 正确做法 |
|---|---|---|
| 无退避的重试 | 所有重试以相同间隔发起；服务器持续过载 | 使用指数退避 + 随机抖动 |
| 在 4xx 错误上重试 | 同样的无效请求每次都失败；浪费资源 | 只在 5xx 和网络错误上重试 |
| 无限重试 | 服务宕机数小时；重试永不停止 | 始终设置最大重试次数（通常 3-5 次） |
| 重试时无日志 | 重试不可见；无法调试"慢"请求 | 每次重试尝试时记录 WARNING 级别日志 |
