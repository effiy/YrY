# YiVad 流水线闭环 —— 需求到部署的完整流程

> YiVad 的 PM 模块实现了一个从需求收集到部署反馈的完整软件交付流水线。每个阶段都有专用页面和特定的数据模型，它们通过闭环反馈连接在一起。

## 流水线概览

```
需求收集        规划            实施            发布            监控与反馈
────────        ────            ────            ────            ────────
Issues          Cycles          Kanban          Releases        Activity
Pages           Sprint Plann.   Gantt                          Analytics
                Roadmap         Modules                        Bugs
```

## 阶段 1：需求 —— 定义要构建什么

### Issues (`/issue`)
- **用途**：所有工作项的中央仓库——用户故事、任务、Bug、功能
- **数据模型**：`{ key, title, description, issue_type, status, priority, assignee, project_key, cycle_key, labels, created_at, updated_at }`
- **详情页**：`/issue/:key` —— 完整任务视图（评论、附件、活动日志）
- **流水线角色**：所有工作的入口。任务从 Issues 向下游流转进入迭代和 Sprint
- **YiKnowledge 对应**：[producter/](../../../producter/) —— PRD、用户故事、优先级排序

### Pages (`/page`)
- **用途**：文档页面——Wiki、规格说明、设计文档，关联到项目
- **数据模型**：`{ key, title, content, project_key, created_at, updated_at }`
- **流水线角色**：需求和设计决策的支持文档

## 阶段 2：规划 —— 将工作组织为迭代

### Cycles (`/cycle`)
- **用途**：时间盒迭代（Sprint），将任务分组为可交付批次
- **数据模型**：`{ key, name, goal, status (active/upcoming/completed), start_date, end_date, issue_keys, project_key }`
- **详情页**：`/cycle/:key` —— 迭代详情与任务规划面板
- **流水线角色**：桥接需求和实施。任务在 Sprint 规划期间分配到迭代中

### Sprint Planning (`/sprintPlanning`)
- **用途**：拖拽界面，将 Backlog 任务分配到当前迭代
- **数据模型**：消费 `cycles` 和 `issues` 集合。列：Backlog → Current Sprint
- **流水线角色**：主动的规划活动。将任务从"做什么"移到"什么时候做"

### Roadmap (`/roadmap`)
- **用途**：项目、迭代和里程碑的高级时间线视图
- **数据模型**：聚合 `projects`、`cycles`、`releases` 到时间线
- **流水线角色**：战略规划概览。回答"什么时间会有什么"

### Gantt (`/gantt`)
- **用途**：任务及其依赖/时间线的甘特图视图
- **数据模型**：消费带日期范围和依赖关系的 `issues`
- **流水线角色**：战术时间线规划。可视化任务持续时间和依赖关系

## 阶段 3：实施 —— 构建和跟踪

### Kanban (`/kanban`)
- **用途**：按状态列分组的任务看板视图
- **数据模型**：消费按迭代/项目过滤的 `issues`，按 `status` 分组
- **流水线角色**：主要的实施跟踪工具。任务从左到右流动

### Modules (`/module`)
- **用途**：项目内任务的逻辑分组（Epic、功能区域）
- **数据模型**：`{ key, name, description, project_key, issue_keys }`
- **详情页**：`/module/:key`
- **流水线角色**：将实施工作组织为可管理的块

### Projects (`/project`)
- **用途**：所有工作的顶层容器——每个项目有自己的 Issues、Cycles、Modules、Releases
- **数据模型**：`{ key, name, identifier, description, status (active/archived), cover_image, members, created_at, updated_at }`
- **详情页**：`/project/:key` —— 项目概览（活动流、成员列表、设置链接）
- **流水线角色**：整个流水线的容器。所有其他 PM 页面都按项目过滤

## 阶段 4：发布 —— 交付到生产

### Releases (`/release`)
- **用途**：打包已完成任务的版本化发布，用于部署
- **数据模型**：`{ key, name, version, description, status (planned/in_progress/released), release_date, issue_keys, project_key }`
- **详情页**：`/release/:key`
- **流水线角色**：部署关口。任务从"完成"移动到"已发布"
- **YiKnowledge 对应**：[srer/release/](../../../srer/release/) —— 发布流程、回滚、金丝雀部署

## 阶段 5：监控与反馈 —— 学习和改进

### Activity (`/activity`)
- **用途**：跨项目所有动作的按时间顺序排列的流水
- **数据模型**：消费活动日志条目：`{ key, type, action, target_type, target_key, user, timestamp, details }`
- **流水线角色**：实时了解流水线中发生的一切

### Analytics (`/analytics`)
- **用途**：流水线指标仪表盘——吞吐量、周期时间、燃尽图、速率
- **数据模型**：聚合 `issues`、`cycles`、`releases` 为图表和指标
- **流水线角色**：数据驱动的洞察。回答"交付有多快"和"瓶颈在哪里"

### Bugs (`/bug`)
- **用途**：缺陷跟踪——严重程度、复现步骤、解决状态
- **数据模型**：`{ key, title, description, severity, status, repro_steps, linked_issue_key, project_key, created_at, updated_at }`
- **详情页**：`/bug/:key`
- **流水线角色**：**反馈环的闭合点**。生产环境中发现的 Bug 回流到 Issues 流水线，完成闭环

## 闭环反馈

```
                    ┌──────────────────────────────────────────┐
                    │                                          │
                    ▼                                          │
┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
│  Issues  │──▶│  Cycles  │──▶│  Kanban  │──▶│ Releases │──▶│ Activity │
│  Pages   │   │  Sprint  │   │  Gantt   │   │          │   │ Analytics│
└──────────┘   │ Planning │   │ Modules  │   └──────────┘   └──────────┘
     ▲         └──────────┘   └──────────┘        │              │
     │                                            │              │
     │                                            ▼              ▼
     │         ┌──────────────────────────────────────────────────┘
     │         │
     └─────────┘
        Bugs（反馈 → 新 Issues）
```

1. **需求**以 Issues 形式进入（用户故事、任务、功能）
2. **规划**通过 Sprint Planning 将 Issues 组织到 Cycles，在 Roadmap 和 Gantt 中可视化
3. **实施**在 Kanban 看板上跟踪进度，通过 Modules 在 Projects 内组织
4. **发布**将完成的 Issues 打包为版本化 Releases 进行部署
5. **监控**通过 Activity 和 Analytics 跟踪可见性
6. **反馈**通过生产环境中发现的 Bugs 创建新的 Issues，闭合循环
