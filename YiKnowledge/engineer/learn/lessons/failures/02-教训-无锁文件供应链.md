# 失败复盘：无锁文件导致构建不可重现

> **影响范围：YrY 所有 Node.js 项目。** 开发环境和 CI 环境安装了不同版本的传递依赖，导致 CI 构建成功但生产构建失败——而失败原因在开发环境中无法复现。

## 发生了什么

### 时间线

| 时间 | 事件 |
|------|------|
| Day 1 上午 | 开发者 push 代码，CI 构建通过（使用了 `npm install`） |
| Day 1 下午 | 另一台机器 `npm install` 后构建失败——`TypeError: xxx is not a function` |
| Day 1 晚上 | 两台机器对比 `node_modules`，发现同一个包的次要版本差了一级 |
| Day 2 上午 | 确认根因：`package-lock.json` 未被提交到 Git |
| Day 2 下午 | 修复：提交 lockfile，CI 改用 `npm ci` |

### 具体症状

```
# 开发机器 A：构建成功
$ npm install && npm run build
✓ Build completed in 12.3s

# 开发机器 B：构建失败
$ npm install && npm run build
✗ TypeError: somePlugin.transform is not a function
```

两台机器使用相同的 `package.json`、相同的 Node.js 版本，但安装的依赖版本不同——因为 `package.json` 中的 `^1.2.3` 允许安装 `1.2.3` 到 `1.9.9` 之间的任何版本。

## 根因分析

### 直接原因

`package-lock.json` 未被加入 Git 版本控制。`package.json` 使用语义化版本范围（`^` 和 `~`），而非精确版本。不同时间、不同机器运行 `npm install` 会解析出不同的依赖树。

### 为什么没有提交 lockfile

1. **对 lockfile 的作用理解不足**：开发者认为 lockfile 只是"本地缓存"，不影响最终构建结果
2. **`.gitignore` 配置错误**：lockfile 被误加入 `.gitignore`
3. **开发环境单一**：很长一段时间只有一个开发者、一台机器，lockfile 缺失的问题从未暴露

### 为什么 CI 没有发现问题

CI 流水线使用了 `npm install` 而非 `npm ci`。`npm install` 即使有 lockfile 存在，也可能更新它。`npm ci` 则在 lockfile 与 `package.json` 不一致时直接失败——这是一种安全机制。

### 系统性原因

- **开发环境同质化**：当只有一个开发者时，lockfile 的缺失是不可见的——因为没有第二台机器来暴露差异
- **CI 检查缺失**：CI 中没有"验证 lockfile 已提交"或"验证构建可重现"的步骤

## 修复措施

### 立即修复

```bash
# 1. 将 lockfile 加入版本控制
git add package-lock.json
git commit -m "chore: add package-lock.json for reproducible builds"

# 2. CI 改用 npm ci
# .github/workflows/ci.yml 中:
- run: npm ci    # 替代 npm install
```

### 长期预防

| 措施 | 实施方式 | 效果 |
|------|---------|------|
| lockfile 必须提交 | `.gitignore` 审计：确保不含 `package-lock.json` | 构建可重现 |
| CI 使用 `npm ci` | 修改所有 CI 配置文件 | lockfile 漂移时立即失败 |
| 新增依赖时审查 lockfile diff | PR 检查清单：确认 lockfile 变更合理 | 防止意外引入大量传递依赖 |
| 定期运行 `npm ci` 测试 | 每月在干净环境中 `git clone && npm ci && npm run build` | 验证构建可重现性 |

## 预防措施

### 检查清单

新项目或新开发者入职时必须确认：

- [ ] `package-lock.json` / `pnpm-lock.yaml` 已提交到 Git
- [ ] CI 中使用 `npm ci` / `pnpm install --frozen-lockfile`
- [ ] `.gitignore` 中不包含 lockfile
- [ ] `requirements.txt` 锁定精确版本号（Python 项目）

### 自动化检测

```bash
# 快速检查：lockfile 是否在版本控制中
git ls-files package-lock.json pnpm-lock.yaml

# 预期输出: package-lock.json 或 pnpm-lock.yaml
# 如果无输出 → lockfile 未被追踪 → 立即修复
```

## 这个失败为什么重要

- **不可重现的构建是定时炸弹**：它可能在几周甚至几个月后才爆炸——当新机器加入、依赖发布新版本、或需要回滚到旧版本时
- **单一开发环境掩盖问题**：lockfile 缺失在单开发者场景下完全不可见，但团队一旦扩展就会暴露
- **CI 通过不代表构建可靠**：如果 CI 和开发环境使用相同的依赖安装方式（`npm install`），它们可能同时"成功"，但在不同的依赖版本上

## 适用场景

这不仅是 Node.js 的问题——任何使用语义化版本范围的包管理器都有这个风险：

| 项目 | 锁文件 | CI 命令 |
|------|--------|---------|
| YiVad (pnpm) | `pnpm-lock.yaml` | `pnpm install --frozen-lockfile` |
| YiPet (npm) | `package-lock.json` | `npm ci` |
| YiAi (pip) | `requirements.txt`（精确版本 + 哈希） | `pip install --require-hashes -r requirements.txt` |

## 核心教训

**始终提交 lockfile。始终在 CI 中使用 `ci` 命令而非 `install`。** 这 10 秒钟的操作可以避免数小时的构建调试。lockfile 不是你一个人的本地缓存——它是整个团队和 CI 系统之间关于"什么是正确的依赖集合"的唯一共识机制。
