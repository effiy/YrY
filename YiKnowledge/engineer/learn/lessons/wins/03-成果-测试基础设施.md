# 成功案例：测试基础设施——从零到 76 个测试、92% shared 覆盖率

> **时间：YiAi 项目中期。** 在没有任何测试的情况下，YiAi 引入了 pytest 测试框架。现在测试套件包含 76+ 个测试，shared/ 模块覆盖率达到 92%。关键成功因素：从最容易测试的纯函数开始，逐步扩展到集成测试。

## 构建了什么

1. **pytest 测试框架**集成到 YiAi——`pytest + pytest-asyncio + httpx + pytest-cov`
2. **76+ 个测试**覆盖 shared/ 模块（92% 覆盖率）和部分 services/
3. **CI 集成**——每次 push 自动运行测试，覆盖率门槛设为 50%
4. **测试模式文档**——纯函数测试、异步测试、错误码测试、集成测试

## 为什么成功——四个关键决策

### 1. 从纯函数开始，而非 API 端点

最初的技术债清单上，"无测试覆盖"是所有三个项目的高严重度问题。选择从哪里开始是关键：

```
易测试程度：纯函数 > 服务层 > 路由层 > 端到端
         ↑ 从这里开始
```

YiAi 的 `shared/` 模块提供了大量纯函数——`estimateTokens()`、`cleanText()`、`ErrorCode` 枚举——这些函数没有外部依赖，测试成本极低。

```python
# 第一个测试——30 秒写完，立即产出价值
def test_estimate_tokens_english():
    assert estimateTokens("Hello world") == 2
```

**启示**：不要从最难的部分开始。纯函数测试的投入产出比最高——它们最容易写、运行最快、最不容易因重构而失效。

### 2. 先建立 CI 门禁，再追求覆盖率

测试框架搭建的第二步是把它接入 CI——而不是追求覆盖率：

```yaml
# 初始设置: 覆盖率门槛 0%（只要跑通就行）
- run: python -m pytest tests/ -v

# 逐步提升:
# 第 1 周: --cov-fail-under=0   （只要求运行通过）
# 第 2 周: --cov-fail-under=30  （适度提升）
# 稳定后: --cov-fail-under=50  （当前门槛）
```

**启示**：测试的价值首先体现在"发现问题"而非"覆盖率数字"。先让测试在 CI 中跑起来，让团队养成习惯，再逐步提高门槛。

### 3. 错误码和响应格式的确定性测试

`ErrorCode` 枚举和 `StandardResponse` 是 YiAi 中所有 API 响应的基石。为它们编写了确定性测试：

```python
def test_error_code_values_are_unique():
    """错误码必须唯一——重复的错误码会导致前端误判。"""
    values = [e.value for e in ErrorCode]
    assert len(values) == len(set(values))

def test_success_response_format():
    """成功响应必须符合规范格式。"""
    resp = success({"data": "test"})
    assert resp.code == 0
    assert resp.message == "ok"
    assert resp.data == {"data": "test"}
```

这类测试不测试业务逻辑，而是测试系统的**不变量**（invariant）——那些"必须永远为真"的约束。一旦有人不小心修改了错误码值或响应格式，测试会立即发现。

### 4. 异步测试的正确处理

YiAi 大量使用 `async/await`。通过 `pytest-asyncio` 正确标记异步测试：

```python
@pytest.mark.asyncio
async def test_query_documents_returns_paginated():
    result = await query_documents("test", filter={"status": "active"})
    assert "list" in result
    assert "total" in result
```

**常见错误**：在异步测试中忘记 `@pytest.mark.asyncio` 装饰器，或者混用同步和异步调用。

## 量化结果

| 指标 | 起始状态 | 当前状态 |
|------|---------|---------|
| 测试总数 | 0 | 76+ |
| shared/ 覆盖率 | 0% | 92% |
| 发现的 Bug | — | 3 个（参数验证缺失、响应格式不一致、错误码重复） |
| CI 运行时间 | — | < 10 秒 |
| 新增功能是否写测试 | 从不 | 视情况而定（纯函数必写） |

## 可复用模式——"从内向外"测试策略

这个策略可以复制到 YiVad 和 YiPet：

```
1. 测试纯函数和工具（utils/、config/、shared/）
   → 最快、最稳定、最高投入产出比

2. 测试数据模型和类型定义
   → 验证枚举值、类型约束

3. 测试 API 封装层（请求形状、响应处理）
   → 重点关注 RPC 参数名的正确性

4. 测试 Store 和服务层
   → 需要 mock 依赖

5. 端到端测试（E2E）
   → 最后补充，覆盖关键路径
```

## 对 YiVad/YiPet 的启示

YiVad 和 YiPet 目前测试覆盖率为 0（YiVad）和有限（YiPet 97 个测试但主要是 config）。同样的策略适用：

1. **YiVad 优先测试**：`src/utils/` 下的纯函数、`src/enums/` 下的枚举
2. **YiPet 优先测试**：`src/api/` 下的端点函数和类型定义
3. **两个项目共同优先**：RPC 请求形状验证——确认参数名正确

## 关键启示

1. **从最容易的开始**：纯函数测试的投入产出比远超集成测试。先写 10 个纯函数测试，再考虑 API 测试。

2. **测试不变量而非实现细节**：`ErrorCode` 枚举值的唯一性、响应格式的一致性——这些约束是架构的基石，测试它们比测试具体的业务逻辑更有长期价值。

3. **CI 集成先于覆盖率**：让测试在 CI 中跑起来比提高覆盖率数字更重要。先养成习惯，再设定目标。

4. **测试能发现文档无法发现的 Bug**：yml 配置文件中的错误码重复、响应格式的不一致——这些是文档审查无法捕获的，但测试可以。
