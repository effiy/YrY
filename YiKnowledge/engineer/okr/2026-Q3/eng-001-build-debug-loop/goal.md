## 实施上下文

### 背景与动机

Q3 之前，YiVad 前端的代码修改流程中存在两个痛点：
1. **人工编码介入**：AI 生成的代码往往不能直接通过类型检查和构建，需要开发者手动修复类型错误和构建错误
2. **调试过程丢失**：修复过程中的问题诊断、解决方案和验证步骤没有记录，导致同类问题重复出现时团队缺乏参考

本目标的核心诉求是建立"AI 生成→类型检查→构建验证→调试记录"的完整闭环，让需求的代码实现不需要人工编码介入。

### 关键决策

| 决策 | 说明 |
|------|------|
| 0 人工编码介入 | AI 必须生成可直接通过所有门禁的代码，不允许"先生成再让人修"的工作模式 |
| vue-tsc + build 双门禁 | 类型检查（vue-tsc --noEmit）和构建（npm run build）双重验证，任一失败则退回 AI 修复 |
| 调试记录模板 03-build-debug | 每个调试过程强制记录：问题描述→根因分析→修复方案→验证结果，模板化存储 |
| 构建门禁集成 CI | 构建检查集成到 git pre-commit hook，阻止未通过门禁的代码提交 |

### 实施路径

1. **第一阶段**：建立 vue-tsc + build 双门禁流程，集成到 AI Agent 的执行循环
2. **第二阶段**：设计 03-build-debug 记录模板，确保调试信息结构化
3. **第三阶段**：AI Agent 自动循环——生成代码→类型检查→失败→诊断→修复→重新检查→通过
4. **第四阶段**：全流程验证，确保 0 人工编码介入的稳定达成

## 影响范围

| 受影响模块 | 影响说明 |

| YiVad 前端代码库 | 所有代码变更必须通过 vue-tsc + build 双重门禁 |

## 预防措施

1. **类型错误修复循环上限**：单文件类型错误修复不超过 5 轮，超过则标记为"需人工介入"并生成详细诊断报告
2. **构建缓存策略**：每次修复后增量构建而非全量构建，减少验证等待时间
3. **调试记录模板严格执行**：缺少任一字段（问题描述/根因/修复/验证）的记录需补充完整

## 经验教训

1. **vue-tsc 是比 build 更早暴露问题的门禁**：约 80% 的问题在 vue-tsc 阶段就被捕获，build 失败通常意味着更严重的架构问题
2. **0 人工编码介入需要稳定的 prompt 工程**：AI 对 Vue 3 TypeScript 的类型系统理解有限，需要在 prompt 中显式提供组件 props、emit、slot 的类型签名示例
3. **调试记录的投入回报周期长但价值持久**：每条调试记录平均花费 5 分钟编写，但同类问题复发时排查时间从 30 分钟降到 5 分钟
