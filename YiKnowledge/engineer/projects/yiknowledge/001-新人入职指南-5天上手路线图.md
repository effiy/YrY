## Day 1｜目录结构与命名规范入门

**目标**：掌握 YiKnowledge 7 大角色目录 + 5 流水线命名规范

| 序号 | 任务内容 | 估计时间 | 交付物 |
|------|----------|----------|--------|
| ① | 完整浏览 7 大顶层目录：`engineer/` / `curator/` / `product/` / `leader/` / `executive/` / `aier/` / `projects/`，每个目录读至少 3 篇示例文档 | 120 min | 目录结构思维导图（手绘或 Mermaid） |
| ② | 学习 2026-09 命名规范：`PRD` / `Dev` / `Test` 三联文档、编号规则（00/01/02…、001/002…）、日期格式 | 60 min | 命名规范速查表（1 页纸笔记） |
| ③ | 追溯一个真实 OKR 示例：从 `OKR` → `PRD` → `Dev` → `Test` → `Bug` 完整闭环链路（找任一个已有项目） | 90 min | 追溯笔记 1 份，含 5 个链接 |
| ④ | 学习 Mermaid 语法，至少看懂：流程图、时序图、架构图各 1 个现有示例 | 30 min | 用 Mermaid 画出一张「5 阶段流水线」流程图 |

**验收 Checklist**：
- [ ] 能不假思索地说出 7 大角色目录的名称与各自定位
- [ ] 能说出 5 流水线阶段：OKR → PRD → Dev → Test → Bug 的顺序与前后关系
- [ ] 能区分「2 位编号」与「3 位编号」适用场景
- [ ] 能读懂至少 1 张 Mermaid 图（流程/时序/架构任选）

### Day 1 常见坑

| 坑位 | 现象 | 解决方式 |
|------|------|----------|
| frontmatter YAML 缩进错误 | YiAi 知识扫描报「解析失败」 | YAML 强制 2 空格缩进，冒号后必须 1 空格，字符串若含 `:` / `#` 必须用双引号包住 |
| 3 位 / 2 位编号混淆 | 文档放错层级导致知识网断裂 | 顶层目录 → 子模块 → 单篇文档：一般用 `01-`（2 位，大节） + `001-`（3 位，小节）组合，参考同级已有文件 |
| 命名用了数字开头 CSS 变量 | 文档中自定义变量名以数字开头 | 命名禁止以数字开头，CSS/自定义变量必须以字母或 `_` 开头 |
| `source_okr` / `related` 链接断裂 | 点击打不开关联文档 | 永远用 **相对路径**（如 `../01-okr.md`），不要硬编码绝对路径或 GitHub URL |
| 目录命名中英文混用 | 项目目录一会儿 `YiAi` 一会儿 `yiai` | 目录命名统一用 **全小写英文**（如 `yiai`），项目名 4 字规范（YiAi / YiVad / YiPet / YiKnowledge / YiPot） |

### Day 1 进一步学习路径

3. 尝试用 VSCode + `YAML` 插件体验 frontmatter 语法校验

## Day 2｜架构知识网与核心规范精读

**目标**：读懂 YiKnowledge 5 阶段流水线 + 7 角色协作网

| 序号 | 任务内容 | 估计时间 | 交付物 |
|------|----------|----------|--------|
| ① | 精读 `0001-项目-架构设计.md` / `0002-项目-开发规范.md`，标记出你仍不清楚的 5 个问题 | 120 min | 架构/规范精读笔记 + 疑问列表 |
| ② | 把疑问列表逐个在知识库中搜索答案（用 `source_*` 字段、tags、category 反查），找不到就记下来 | 90 min | 「已解决 / 待 Mentor 解答」对照表 |
| ③ | 选择 1 个已有项目（如 YiAi），把它下面所有文档按 5 流水线（OKR/PRD/Dev/Test/Bug）分类整理成表 | 90 min | 项目文档分类表（Excel / Markdown 表格） |
| ④ | 画出 YiKnowledge 整体架构图：7 角色 × 5 阶段矩阵，每个格子放 1 个示例文档链接 | 60 min | Mermaid 矩阵 / 架构图 .md 片段 |

**验收 Checklist**：
- [ ] 能讲清 5 流水线阶段每个阶段的产物、owner、输入/输出
- [ ] 能讲清 3 个以上「跨角色协作点」（如 product 写 PRD → engineer 写 Dev）
- [ ] 能独立使用「source_* / related / tags / category」4 个字段反查关联文档

### Day 2 常见坑

| 坑位 | 现象 | 解决方式 |
|------|------|----------|
| 项目名不遵守 4 字规范 | 文档中一会儿 `YiAI` 一会儿 `yi-ai` | 强制统一：文档标题用 4 字写法（YiAi / YiVad / YiPet / YiKnowledge / YiPot），目录名全小写（yiai / yivad / yipet / yiknowledge / yipot） |
| OKR 到 PRD 追溯断链 | `source_okr` 指向不存在文档 | 写 PRD 时必须先确认 OKR 文档已存在并合入 main，否则先补 OKR 再写 PRD |
| frontmatter 关键字段缺失 | 知识扫描后分类错误 | 参考同目录已有文档，保证至少有：title / tags / category / created / updated / source / type / status |
| Mermaid 代码块在阅读器中不渲染 | GitHub / Markdown 编辑器显示源码 | 检查围栏代码块语言标识是否为 `mermaid`（严格小写，不要写成 `Mermaid`） |
| tags 拼写不一致 | 同样是「新人入职」出现 `onboarding` / `on boarding` / `新员工入职` | tags 强制参考 `02-规范` 中《受控标签表》，不要自创 |

2. 阅读 `curator/` 策展人目录的文档，理解「策展」在知识网中的角色
3. 通读 `aier/`（AI 工程师）目录 2 篇以上文档，理解 AI 角色怎么用 YiKnowledge

## Day 3｜知识库扫描验证与坏味道修复

**目标**：独立判断一篇文档是否合规，并修复坏味道

| 序号 | 任务内容 | 估计时间 | 交付物 |
|------|----------|----------|--------|
| ① | 运行 YiAi 知识库扫描接口（或本地 lint 脚本）对 `projects/` 任一个子目录做扫描，记录扫描结果 | 60 min | 扫描结果截图 + 错误/告警列表 |
| ② | 从错误列表中挑 3 篇「坏味道」文档，分别修复：frontmatter 规范 / 命名 / 断链 / 编号 等问题 | 120 min | 3 个修复 commit 或 diff 截图 |
| ③ | 编写 1 个自定义「文档合规 Checklist」，参考 `02-规范` + 你前 2 天踩过的坑 | 60 min | Checklist.md 1 份（至少 15 项） |
| ④ | 用你自己的 Checklist 交叉检查同项目另外 5 篇文档，记录发现的问题 | 60 min | 交叉检查报告 1 份 |

**验收 Checklist**：
- [ ] 成功运行 YiAi 扫描（或 lint 脚本）并读懂输出
- [ ] 修复的 3 个坏味道中至少包含 frontmatter + 断链 + 命名 三类各 1 个
- [ ] 自定义 Checklist 覆盖「结构 / frontmatter / 内容 / 链接 / 命名」5 个维度
- [ ] 交叉检查至少发现 3 个真实问题（不是误报）

### Day 3 常见坑

| 坑位 | 现象 | 解决方式 |
|------|------|----------|
| YiAi 扫描接口报「服务未启动」 | 10086 端口没开 | 先按 YiAi Day1 启动后端服务，或用仓库根 `scripts/lint-md.sh` 本地 lint（如存在） |
| 修复 frontmatter 后又引入新的 YAML 错误 | 改完扫描反而挂了 | 改完立刻用 `yamllint` / VSCode YAML 插件校验，不要没测就提交 |
| 修复断链后相对路径还是错 | `./` `../` 层数算错 | 打开文档所在目录 + 目标文档目录，画路径树再写相对路径，必要时点击预览验证 |
| 编号改了但同目录下其他文档 `related` 没更新 | 引入新的断链 | 改编号前先全局搜索「旧编号.md」，把所有引用一起改，或者保留原编号建立 redirect |
| 自定义 Checklist 和项目已有规范冲突 | 自己写的和 `02-规范` 不一致 | 以 `0002-项目-开发规范.md` 为准，Checklist 只能加严不能放松，冲突项去问 Curator / Mentor |

3. 通读 `bugs/yiknowledge/` 下已有的 bug 报告，了解常见知识缺陷类型

## Day 4｜第一篇独立文档（PRD / Dev / Test 三联或 bug 报告）

**目标**：独立写出 1 组（或 1 篇）符合规范的文档

| 序号 | 任务内容 | 估计时间 | 交付物 |
|------|----------|----------|--------|
| ① | 从以下 3 个候选中挑 1 个：(a) 为一个现有项目补 3 篇 PRD/Dev/Test 三联文档（frontmatter 完整） (b) 为 `bugs/yiknowledge/` 下 1 篇 bug 报告并关联 `source_prd` (c) 坏味道修复：深度清理一篇文档 frontmatter + 命名 + 断链 | 150 min | 符合规范的 .md 文档（1～3 篇） |
| ② | 为自己写的每篇文档完整填写 frontmatter 全部必填字段，并在 `related` 中至少关联 3 篇已存在文档 | 45 min | 文档 frontmatter 校验通过截图 |
| ③ | 运行知识库扫描 / lint 脚本验证 + 自己的 Checklist 自检，确保 0 error | 60 min | 扫描通过截图 + Checklist 勾选记录 |
| ④ | 请同组同事（或 Mentor）做一次 peer review，根据反馈修改 | 45 min | peer review 反馈截图 + 修改 diff |

**验收 Checklist**：
- [ ] 文档 frontmatter 全部必填字段正确，tags 来自受控标签表
- [ ] `source_*` 字段指向真实存在文档，`related` 至少 3 个真实链接
- [ ] 知识库扫描 0 error，lint 0 warning（或仅有 pre-existing）
- [ ] 通过至少 1 次 peer review 并完成相应修改

### Day 4 常见坑

| 坑位 | 现象 | 解决方式 |
|------|------|----------|
| PRD/Dev/Test 三联中 source 字段断裂 | `source_prd` 指向不存在文件 | 写的时候顺序：先写 PRD（source_okr）→ 再写 Dev（source_prd）→ 最后写 Test（source_dev），每写完一篇合入 main 再写下一篇，或在同一分支下确保路径正确 |
| bug 报告缺少 `severity` / `reproduce_steps` | 扫描报字段缺失 | 参考 `bugs/yiknowledge/` 下已有 bug 模板，所有受控字段一个都不能少 |
| frontmatter 日期格式不对 | `created` 不是 ISO 格式 | 统一用 `YYYY-MM-DD`（如 2026-10-07），不要写 `10/7/2026` 或中文 |
| 文档正文出现数字开头 CSS 变量 | 自定义变量 `2026-color` 违规 | 所有自定义命名（变量、锚点、id）必须字母/下划线开头，改成 `color-2026` |
| 把 `status: draft` 的文档放进了正式目录 | 评审中版本和稳定版混在一起 | draft 文档先放自己的个人分支或 `drafts/<username>/` 目录，评审通过再正式迁入 |

## Day 5｜PR 准备与跨项目知识关联

**目标**：提 PR + 跨项目知识链接

| 序号 | 任务内容 | 估计时间 | 交付物 |
|------|----------|----------|--------|
| ① | 用 Conventional Commits 写 commit message（文档改动用 `docs(<scope>): <subject>`） | 20 min | 符合规范的 git log |
| ② | 按仓库 PR / MR 模板提交 PR，模板中的「文档自检」项逐行勾选 | 40 min | PR 链接 1 个 |
| ③ | 跨项目关联：为你写的文档在至少 2 个其他项目的 `related` 或 `000-INDEX.md` 中挂上链接 | 60 min | 跨项目链接 PR diff 截图 |
| ④ | 准备 10 分钟 Demo 给 Mentor：展示你的文档 + 扫描结果 + 知识网回溯路径 | 60 min | Demo 验收通过 |

**验收 Checklist**：
- [ ] PR 包含自检项勾选（Code Review + 文档自检全部勾上）
- [ ] 关联项目知识文件 1 篇以上 + 跨项目链接 2 处以上
- [ ] commit message 符合 Conventional Commits 规范（docs: 前缀）
- [ ] Mentor 验收通过并在 PR 中 Comment / Approve

---

### Day 5 常见坑

| 坑位 | 现象 | 解决方式 |
|------|------|----------|
| commit 用了 `feat:` 而不是 `docs:` | commitlint 校验挂掉 | 纯文档改动必须用 `docs(<scope>): xxx`，只有改代码才用 `feat/fix` |
| PR 描述里没贴扫描结果 | Reviewer 让你补证据 | PR 模板的「验证步骤」里必须贴：lint 截图 + 扫描截图 + peer review 截图，缺一不可 |
| 跨项目链接写到其他项目但没一起提交 PR | 其他项目找不到链接 | 如果跨项目修改同仓库，用 **一个 PR** 改多个目录，或多个 PR 之间在描述里互相 `#xxx` 关联 |
| Demo 现场扫描写不出新文档 | 本地没跑 YiAi | 提前一天跑通，或准备录屏备份 + 扫描结果 PDF 导出 |
| 命名规范又写错了（如用了 YiAI / Yi-Knowledge） | 终审时被 Curator 打回 | 提交前最后 1 分钟：全局搜索「YiAI」「Yi-Knowledge」等不规范写法，一键替换 |

### Day 5 进一步学习路径
1. 完成 **2 周成长计划**：独立为 1 个真实需求从 OKR 到 Bug 全流程产出整套知识文档，并被策展人收录
2. 完成 **1 月成长计划**：尝试担任「子项目 Curator」，负责 1 个项目目录下所有文档的质量
3. 尝试写一篇 `projects/yiknowledge/stories/` 技术/策展分享，沉淀新人写文档的避坑指南
