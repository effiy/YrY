# YiVad Menu Catalog Management

> **As an** engineer, **I want to** manage the menu catalog, **so that** sidebar navigation and routes can be adjusted without frontend code changes.

## Summary

YiVad's sidebar menu and dynamic routes share a single source of truth: the **menu tree** stored in MongoDB's `menus` collection. The menu tree is fetched at app startup via `GET /auth/menu/list` (falling back to `authMenuList.json`), flattened into Vue Router routes, and rendered as the sidebar. A built-in management page at `System > Menu Management` provides full CRUD on the menu tree — no code changes needed to add, hide, reorder, or delete menu entries.

## Core viewpoints

- **Menu = route = sidebar entry** — one menu node produces one sidebar item and one Vue Router route. The `component` field maps to a `.vue` file under `src/views/`.
- **Static routes are the skeleton** — login, layout, error pages, and detail sub-routes (code-review/BRD/tech-leadership detail pages) are hard-coded in `staticRouter.ts`. Everything else comes from the menu tree.
- **Management page is self-service** — `src/views/system/menuMange/index.vue` is a ProTable tree editor; create/edit/delete menus without touching the database directly.
- **Fallback ensures offline dev** — when the YiAi backend is unreachable, the frontend loads `src/assets/json/authMenuList.json` so the app is still navigable.

## Key information

### Menu data model

Each menu node (`Menu.MenuOptions` in `src/typings/global.d.ts`):

| Field | Type | Required | Description |
|---|---|---|---|
| `path` | string | yes | Route path, e.g. `/code-review/summary` |
| `name` | string | yes | Route name, used for KeepAlive cache key and button permission filtering |
| `component` | string | — | View file path relative to `src/views/`, e.g. `/code-review/summary/index`. Leave empty for parent menus that only redirect. |
| `redirect` | string | — | Redirect target path |
| `meta.icon` | string | — | Element Plus icon name, e.g. `DocumentChecked`, `Menu`, `HomeFilled` |
| `meta.title` | string | yes | Display name in sidebar and browser tab |
| `meta.activeMenu` | string | — | Parent menu path to highlight when on a detail child page |
| `meta.isLink` | string | — | External link URL (renders as `<a>` instead of router-link) |
| `meta.isHide` | boolean | — | Hide from sidebar (used for detail pages, default `false`) |
| `meta.isFull` | boolean | — | Full-screen page (skips layout chrome, default `false`) |
| `meta.isAffix` | boolean | — | Pin tab so it can't be closed (default `false`) |
| `meta.isKeepAlive` | boolean | — | Cache the page component (default `true`) |
| `children` | array | — | Child menu nodes (recursive) |
| `key` | string | — | MongoDB document key (auto-generated by system.ts) |
| `parent` | string | — | Parent menu path (used by menuMange for tree relationships) |
| `order` | number | — | Display order (lower = first, used by backend `queryDocuments` sort) |

### MongoDB document shape (`MenuDocument` in `src/api/interface/yiweb.ts`)

The `menus` collection stores a flat document per menu node. The `MenuDocument` interface flattens `meta` fields to top-level:

```
key, path, name, component, redirect, parentId, sort,
icon, title, isLink, isHide, isFull, isAffix, isKeepAlive,
createdAt, updatedAt
```

The backend `GET /auth/menu/list` reassembles the flat list into a tree using `parentId` references.

### Static vs dynamic routes

| Layer | File | What it contains |
|---|---|---|
| Static | `src/routers/modules/staticRouter.ts` | Login, layout shell, aiChat, RSS sub-routes, Story Board, RAG sub-routes, FDE Resume, all code-review/BRD/tech-leadership detail routes, error pages |
| Dynamic | `src/routers/modules/dynamicRouter.ts` | Loaded from `GET /auth/menu/list` → flat menu list → `router.addRoute("layout", ...)` |
| Fallback | `src/assets/json/authMenuList.json` | BRD Management (9 children), Code Review (18 children), Tech Leadership (19 children), FDE Resume, Story Board, RSS Feeds (4 children) |

**Key rule**: detail pages (list-item detail views) are registered as **static hidden routes** with `isHide: true` — they appear in the router but not in the sidebar. List pages come from the dynamic menu tree.

### Route initialization flow

```
App boot → router.beforeEach guard
  → authStore.authMenuList empty?
    → initDynamicRouter()
      → getAuthMenuList() → GET /auth/menu/list (or fallback JSON)
      → getAuthButtonList() → GET /auth/buttons
      → flatMenuListGet → forEach item:
        → resolve component via viewsGlob map
        → router.addRoute("layout", item)
      → guard re-enters with the now-available route
```

### Menu management page

**Path**: `src/views/system/menuMange/index.vue`  
**Route**: loaded dynamically from the menu tree (typically under System)  
**Tech**: ProTable with `tree-props` for hierarchy rendering

**Features**:
- Tree table showing all menus with parent-child indentation
- Search/filter by menu name, route name, route path
- Add menu dialog (keyboard shortcut: `N`)
- Edit menu dialog (double-click or Edit button)
- Delete menu with orphan warning (children become top-level on refresh)
- Keyboard shortcuts: `N` new, `/` focus search, `Cmd+S` save, `?` help, `Esc` close

**Form fields in the edit dialog**:

| Field | Control | Notes |
|---|---|---|
| Menu Name | text input | Required, becomes `meta.title` |
| Parent Menu | tree-select | Leave empty for top-level |
| Route Path | text input | Required, e.g. `/my-feature` |
| Route Name | text input | Required, unique route name |
| Component Path | text input | Relative to `src/views/`, e.g. `/my-feature/index` |
| Redirect | text input | Optional redirect target |
| Icon | text input | Element Plus icon name |
| External Link | text input | Optional external URL |
| Order | number input | Display order |
| Hidden Menu | switch | `isHide` |
| Full Screen | switch | `isFull` |
| Fixed Tab | switch | `isAffix` |
| Page Cache | switch | `isKeepAlive` |

### API layer

| Operation | Function | RPC target |
|---|---|---|
| List menus | `getMenuList()` | `data_service.query_documents({cname: "menus"})` |
| Create menu | `createMenu(params)` | `data_service.create_document("menus", ...)` |
| Update menu | `updateMenu(key, params)` | `data_service.update_document("menus", key, ...)` |
| Delete menu | `deleteMenu(key)` | `data_service.delete_document("menus", key)` |
| Load for routing | `getAuthMenuListApi()` | `GET /auth/menu/list` (falls back to local JSON) |

All defined in `src/api/modules/system.ts` and `src/api/modules/login.ts`.

## Action recommendations

1. **Add a new top-level menu** — open Menu Management, press `N`, fill in path/name/component/icon, leave parent empty, save. The view file must exist under `src/views/<component-path>.vue`.
2. **Add a child menu** — same as above, but select a parent from the tree-select.
3. **Hide a menu without deleting** — edit the menu, toggle "Hidden Menu" on. It stays registered as a route but disappears from the sidebar.
4. **Reorder menus** — the backend sorts by the `sort`/`order` field; adjust the Order number in the edit dialog.
5. **Delete a menu** — click Delete; if the menu has children, they become top-level after refresh (no cascade delete).
6. **After any menu change** — the page calls `authStore.getAuthMenuList()` to refresh the sidebar. A full page reload is recommended to re-register routes.
7. **Register a new detail route** — add a static route in `staticRouter.ts` with `isHide: true` and `isKeepAlive: true`. Do NOT add detail routes to the menu tree — they are navigation targets, not sidebar entries.



- **Adding a menu without a corresponding view file** — the dynamic router silently skips entries whose component path doesn't resolve via `viewsGlob`. The menu appears in the sidebar but clicking it does nothing.
- **Editing the fallback JSON instead of the database** — `authMenuList.json` is only a fallback. Changes to it won't affect production (which loads from YiAi). Use the Menu Management page instead.
- **Putting detail routes in the menu tree** — detail pages (`/xxx/detail/:id?`) should be static hidden routes in `staticRouter.ts`, not menu entries. The menu tree is for navigable list pages.
- **Deleting a parent menu expecting cascade** — children are orphaned to top-level, not deleted. Delete children first if you want them gone.
- **Forgetting to create the view file** — the menuMange page doesn't create `.vue` files. Create the component under `src/views/<path>/index.vue` before or right after adding the menu.

## Anti-patterns

- **Editing `authMenuList.json` as if it were the production menu source.** The fallback JSON is only loaded when the YiAi backend is unreachable. Changes to this file are invisible to all users in normal operation, creating a false sense that the menu was updated. Always use the Menu Management page or the `data_service` API to modify the live menu tree in MongoDB.
- **Using the menu tree to register detail/dynamic-parameter routes.** Routes like `/code-review/detail/:id` belong in `staticRouter.ts` as hidden routes, not in the menu tree. Putting them in the menu tree creates a sidebar entry for a page that cannot render without a parameter, and clutters the navigation with dead-end links.
- **Deleting a parent menu node and assuming children are cascade-deleted.** The menu management page orphans children to the top level on parent deletion. If you expect the entire subtree to disappear, delete the children first, then the parent. Orphaned top-level menus are confusing to users and difficult to clean up afterward.
- **Creating a menu entry with a component path that does not yet exist on disk.** The dynamic router silently skips entries whose `component` field does not resolve via `viewsGlob`. The menu appears in the sidebar but clicking it navigates to a blank page with no error. Always create the `.vue` file under `src/views/` before or immediately after adding the menu record.
- **Changing the `name` field of an existing menu without updating all references to it.** The `name` field is used as the KeepAlive cache key and as the button-permission filter string. Renaming it breaks the page cache for that route and silently disables all `v-auth` directives that reference the old name. Audit all usages of the old name in `v-auth` directives and `include` lists before renaming.
