# 调试与排错指南

> 从症状到根因的诊断方法论。YrY 中最常见的 Bug 类型按频率排序：RPC 参数名不匹配 > SSE 流中止处理 > MongoDB 连接问题 > 依赖版本不一致。

## 诊断方法论

### 四步定位法

```
1. 确认症状范围
   → 影响一个项目还是所有项目？
   → 影响一个页面还是所有页面？
   → 最近改了什么？

2. 追踪请求链路
   → 前端发了什么请求？（Network 面板）
   → 后端收到了什么？（日志）
   → 后端返回了什么？（响应）

3. 隔离变量
   → 用 curl 直接调后端（排除前端问题）
   → 用 mongosh 直接查数据库（排除 API 层问题）
   → 换一个浏览器/设备（排除环境问题）

4. 查已知陷阱
   → 对照 gotchas/ 目录检查是否有匹配的已知问题
```

## 按症状诊断

### 症状：数据列表为空，但应该有数据

**最常见原因——RPC 参数名用了 `query` 而非 `filter`**

```
诊断步骤：
1. 打开浏览器 DevTools → Network 面板
2. 找到 POST / 的请求
3. 查看 Request Payload → parameters 对象
4. 检查是否有 "query" 键 → 如果有，改为 "filter"

快速验证（curl）:
curl -X POST http://localhost:10086/ \
  -H "Content-Type: application/json" \
  -d '{"module_name":"services.database.data_service","method_name":"query_documents","parameters":{"cname":"projects","filter":{},"pageNum":1,"pageSize":5}}'

如果 filter 返回正常数据但 query 返回空 → 确认是参数名问题
```

### 症状：文件读写返回 422

**原因——参数名用了 `path` 而非 `target_file`**

```
诊断：
1. Network 面板 → 找到 /read-file 或 /write-file 请求
2. 查看 Request Payload → 确认字段名是 target_file 不是 path

正确请求:
curl "http://localhost:10086/read-file?target_file=YiKnowledge/README.md"

错误请求（422）:
curl "http://localhost:10086/read-file?path=YiKnowledge/README.md"
```

### 症状：AI 聊天消息不完整或重复发送

**原因——SSE 流中止后 onDone 回调仍触发**

```
诊断：
1. 快速输入消息后立即点停止按钮
2. 检查是否仍有消息被自动转发/保存
3. 如果有无头消息 → onDone 缺少 isAborted 守卫

修复：在 onDone 回调开头加 if (isAborted.value) return;
详见: learn/lessons/gotchas/03-陷阱-SSE-onDone守卫.md
```

### 症状：MongoDB 连接超时

```
诊断命令：
mongosh --eval "db.runCommand({ping: 1})"
# 期望: { ok: 1 }
# 超时: MongoDB 未运行或端口不通

lsof -i :27017
# 期望: mongod 进程监听
# 空: MongoDB 未启动

修复：
brew services start mongodb-community  # macOS
# 或
mongod --dbpath /usr/local/var/mongodb
```

### 症状：Ollama 推理长时间无响应

```
诊断：
curl http://localhost:11434/api/tags
# 期望: {"models": [...]}
# 无响应: Ollama 未运行

ollama list
# 期望: 列出已下载的模型
# 空: 需要下载模型

修复：
ollama serve                 # 启动 Ollama
ollama pull qwen2.5:3b      # 下载模型
```

### 症状：YiVad 页面白屏，控制台无报错

```
诊断步骤：
1. 检查 YiAi 是否运行: curl http://localhost:10086/health
2. 检查 DevTools → Application → Local Storage → token 是否存在
3. 检查 DevTools → Network → 菜单 API 请求是否成功
4. 如果菜单 API 返回空 → 种子数据未导入 → 重启 YiAi

常见原因：
- YiAi 未运行
- 种子数据未导入（首次启动 YiAi 需要等待 seeds 完成）
- 菜单 API 返回的数据格式不对
```

### 症状：TypeScript 类型检查通过但构建失败

```
诊断：
# YiVad
pnpm type:check  # 通过
pnpm build:dev   # 失败 → 不是类型问题

常见原因：
- 未使用的导入（ESLint 或构建工具的 tree-shaking 报错）
- 环境变量未设置（.env 文件缺失或变量名没有 RSBUILD_ENV_ 前缀）
- SCSS 变量未定义（全局注入配置问题）

修复：
# 检查构建日志中的第一个错误
pnpm build:dev 2>&1 | head -50
```

## 请求链路追踪

### 追踪一个完整的 RPC 调用

```
1. 浏览器 DevTools → Network → 过滤 POST /
2. 点击具体请求 → Payload 标签 → 确认:
   - module_name 正确
   - method_name 正确
   - parameters 键名与后端一致
3. Response 标签 → 确认:
   - code: 0 (成功)
   - data 结构符合预期
4. 如果 code !== 0:
   - 1001: 参数验证失败 → 检查必填参数
   - 1002: 资源不存在 → 检查 filter 条件
   - 5001: 数据库错误 → 检查 MongoDB 是否运行
```

### 追踪 SSE 流

```
1. Network → 过滤 agent/chat
2. 点击请求 → EventStream 标签（或 Response 标签）
3. 观察 data: 帧 → 确认每个 token 正常到达
4. 如果流中断:
   - 检查是否有 AbortError → 用户中止
   - 检查是否有 NetworkError → 网络问题
   - 检查是否超时 → 服务端推理超时
```

## 日志分析

### YiAi 日志关键字

```bash
# 查看 YiAi 输出中的关键信息
python main.py 2>&1 | grep -E "ERROR|WARNING|Reloading|knowledge"

# 常见日志模式:
"Reloading ...""        → 代码热重载
"MongoDB connection .." → 数据库连接状态
"knowledge watcher .."  → 知识库扫描状态
"RPC call: .."         → RPC 请求日志
```

### 浏览器控制台关键输出

```
检查项:
- 红色错误 → 立即处理
- 黄色警告 → 关注但不紧急
- CORS 错误 → YiAi 的 allow_origins 配置
- Failed to fetch → YiAi 未运行或网络不通
- 401 Unauthorized → Token 过期
```

## 不同项目共用的诊断命令

```bash
# 端口检查
lsof -i :10086  # YiAi
lsof -i :8848   # YiVad
lsof -i :27017  # MongoDB
lsof -i :11434  # Ollama

# 进程检查
ps aux | grep python   # YiAi 进程
ps aux | grep node     # YiVad/YiPet 进程
ps aux | grep mongod   # MongoDB 进程
ps aux | grep ollama   # Ollama 进程

# 系统资源
top -l 1 | head -10    # CPU/内存概览
df -h                  # 磁盘空间
```

## 无法定位时的终极手段

1. **二分法排除**：注释掉一半代码，看 Bug 是否消失 → 缩小范围
2. **Git bisect**：如果最近才出现，用 `git bisect` 找引入 Bug 的 commit
3. **对比法**：在另一个浏览器/设备上测试，排除环境问题
4. **最小复现**：写一个最小化的 curl/脚本复现问题，剥离业务逻辑干扰

## 反模式

| 反模式 | 正确做法 |
|---|---|
| 看到空列表就怀疑数据库没数据 | 先用 curl 直接调后端验证 API 是否正常返回 |
| 前端报错就先改前端代码 | 追踪请求链路——可能是后端返回格式不对 |
| 凭直觉猜 Bug 原因 | 按诊断方法论系统排查，每一步都验证假设 |
| 改了很多处代码再测试 | 每次只改一处，立即验证 |
