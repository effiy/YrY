# 发布冻结管理

> **适用场景**：重大事件（节假日、大型会议、季末）前、关键业务时段内，或系统状态不稳定时。

## 为什么需要发布冻结

发布冻结不是官僚主义的枷锁，而是在特定时段降低风险的务实措施。核心逻辑很简单：

| 场景 | 风险 | 冻结的价值 |
|---|---|---|
| **长假期间** | 人手不足，故障响应慢 | 冻结确保故障窗口内没有新增风险 |
| **季末财务结算** | 系统故障导致业务损失 | 冻结保护关键业务时段 |
| **大型活动前** | 任何故障都会产生放大效应 | 冻结给系统留出稳定窗口 |
| **系统不稳定期** | 持续变更阻碍根因定位 | 冻结给系统留出"烧入"时间 |

## 冻结类型

| 类型 | 冻结内容 | 典型时长 | 何时使用 |
|---|---|---|---|
| **硬冻结** | 完全禁止部署 | 1-7 天 | 重大节假日、关键业务事件 |
| **软冻结** | 仅允许 Bug 修复和热修复 | 1-2 周 | 季末前、大型会议前 |
| **代码冻结** | 禁止新代码；允许配置变更 | 1-3 天 | 重大发布前 |

## 冻结范围细则

### 硬冻结

| 冻结 | 不冻结 |
|---|---|
| 新功能部署 | 紧急热修复（仅限 P1 事件）|
| 基础设施变更 | 关键安全补丁（高危 CVE）|
| 数据库迁移 | 功能开关关闭（禁用有问题的功能）|
| 依赖更新 | 数据修复（无 Schema 变更）|

### 软冻结

| 冻结 | 不冻结 |
|---|---|
| 新功能 | Bug 修复 |
| 大规模重构 | 热修复 |
| 基础设施变更 | 安全依赖补丁 |
| 新服务上线 | 低风险性能优化 |

## 豁免流程

### 紧急豁免（仅限 P1）

1. **on-call** 识别出冻结期间必须部署的关键问题
2. **指挥官**（或工程经理）批准豁免
3. **部署**时加强监控（正常观察期的 2 倍）
4. **冻结结束后评审**——豁免是否合理？

### 豁免请求模板

```
豁免请求：{{标题}}

冻结时段：{{起止日期}}
变更内容：{{需要部署什么}}
风险：{{可能出现的问题}}
回滚方案：{{如何撤销}}
紧急理由：{{为什么等不到冻结结束？}}

审批人：{{姓名}} — 批准 / 拒绝
```

## 冻结沟通

### 提前一周公告

```
主题：发布冻结通知 — {{起止日期}}（{{冻结类型}}）

发布冻结将于 {{开始日期}} 至 {{结束日期}} 生效。

冻结期间：
- 冻结内容：{{列举冻结项}}
- 豁免条件：{{列举豁免场景}}

豁免需经 {{审批人}} 批准。

冻结日历：{{链接}}
```

### 提前一天提醒

```
主题：提醒：发布冻结明天开始

发布冻结：{{开始日期}} — {{结束日期}}
今天是非关键变更的最后发布窗口。
请检查是否有需要抢在冻结前发布的变更。
```

## 冻结最佳实践

| 实践 | 原因 | 反例 |
|---|---|---|
| **提前 1 周公告** | 团队可以围绕冻结安排工作 | 冻结开始当天才通知，打乱团队计划 |
| **豁免条件定义清晰** | 消除"能不能部署"的歧义 | "必须的就可以部署"——每个人对此有不同理解 |
| **单一审批人** | 责任明确；不会出现"我以为 X 批准了" | 多人审批导致互相推诿 |
| **冻结后评审** | 从豁免中学习；改进冻结策略 | 冻结一结束就当没发生过 |
| **不要过于频繁冻结** | 全年超过 25% 时间处于冻结 = 流程问题 | 每个月都有冻结窗口 = 团队对发布流程缺乏信心 |

## 常见反模式

| 反模式 | 为何失败 | 正确做法 |
|---|---|---|
| 冻结但不设豁免条件 | 发现关键 Bug；团队无所适从 | 明确定义豁免标准和审批流程 |
| 冻结但不通知 | 团队不知道；照样部署 | 提前 1 周公告，提前 1 天提醒 |
| 永久冻结（全年 > 25% 时间）| 交付速度瘫痪；冻结是流程异味 | 审查为什么需要如此多的冻结；修复底层的不稳定因素 |
| 非紧急事项申请紧急豁免 | "就是个很小的改动"——在冻结期间 | 豁免仅限 P1 事件；其他一律等到冻结结束 |
