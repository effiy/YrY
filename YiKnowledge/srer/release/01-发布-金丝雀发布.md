# 金丝雀发布流程

> **适用场景**：任何存在一定风险的变更——新功能、基础设施变更、数据库迁移。金丝雀发布通过先向小比例用户开放变更来减少爆炸半径。

## 为什么需要金丝雀发布

全量发布的理想世界：变更在预发布环境通过测试，部署到生产环境，一切正常。

全量发布的现实世界：预发布环境永远无法完全模拟生产环境的流量模式、数据特征和用户行为。一个在预发布完全通过的变更，到了生产环境可能因为真实数据触发边界条件而崩溃。

金丝雀发布的核心思想：**如果变更必然带着风险上线，那就让风险只影响一小部分用户。**

## 金丝雀比例指南

| 风险等级 | 初始金丝雀比例 | 示例场景 | 放量节奏 |
|---|---|---|---|
| 低（配置变更、文案更新）| 10% | 修改 YiAi `config.yaml` 中的超时时间 | 30 分钟内放量完成 |
| 中（新功能、依赖更新）| 5% | 新增 RAG 检索策略、升级 Ollama 版本 | 2 小时内放量完成 |
| 高（数据库迁移、认证变更）| 1% | MongoDB Schema 变更、JWT Token 格式变更 | 24 小时内放量完成 |
| 关键（数据格式变更、API 不兼容）| 0.1%（仅内部流量）| RPC 信封协议变更、YiAi 接口不兼容升级 | 48 小时内放量完成 |

## 阶段一：准备

### 金丝雀前检查清单

- [ ] 所有测试在预发布环境通过
- [ ] 回滚方案已文档化且经过测试（参照 [回滚演练](./05-发布-回滚演练.md)）
- [ ] 监控仪表盘已就绪（可同期对比金丝雀与基线版本）
- [ ] 功能开关已就位（如适用）
- [ ] on-call 工程师已通知
- [ ] 金丝雀公告已在 `#releases` 频道发布

### 定义成功标准

| 指标 | 基线（当前版本）| 可接受范围 | 触发回滚的条件 |
|---|---|---|---|
| 错误率 | {{X%}} | <= 基线的 1.2 倍 | > 基线的 2 倍 |
| P99 延迟 | {{Yms}} | <= 基线的 1.3 倍 | > 基线的 3 倍 |
| 吞吐量 | {{Z rps}} | >= 基线的 0.9 倍 | < 基线的 0.5 倍 |
| 崩溃率 | 0 | 0 | 出现任何崩溃 |

**YrY 环境的基线数据示例**（请在执行金丝雀前用实际数据替换）：

| 指标 | YiAi API 基线 | 可接受 | 回滚 |
|---|---|---|---|
| 错误率 | 当前实际值 | <= 1.2x | > 2x |
| P99 延迟（聊天）| 当前实际值 | <= 1.3x | > 3x |
| 崩溃（uvicorn 重启）| 0 | 0 | > 0 |

## 阶段二：部署金丝雀

1. 将新版本部署到金丝雀实例（1-10% 的流量）
2. 验证部署健康（所有实例启动，无崩溃循环）
3. 将金丝雀流量路由到新实例
4. 启动观测计时器

**YrY 当前环境**：由于 YrY 目前为单机部署，金丝雀的"实例"概念需要通过以下方式之一实现：
- 方案 A：运行两个 uvicorn 进程（不同端口），Nginx 按比例分流
- 方案 B：发布到预发布环境，使用真实流量重放进行验证
- 方案 C：内测——先让内部用户使用新版本 24 小时

## 阶段三：验证金丝雀

### 观察期

| 风险等级 | 最短观察时间 | 说明 |
|---|---|---|
| 低 | 15 分钟 | 足以覆盖基础指标异常 |
| 中 | 1 小时 | 需覆盖日常流量波动 |
| 高 | 4 小时 | 需覆盖至少一个流量峰值周期 |
| 关键 | 24 小时 | 需覆盖完整的日周期 |

### 监控对比维度

| 信号 | 对比方式 | 工具 |
|---|---|---|
| 错误率 | 金丝雀 vs. 基线版本 | Grafana、错误追踪（Sentry）|
| 延迟（P50, P95, P99）| 金丝雀 vs. 基线版本 | Grafana、APM |
| 崩溃率 | 仅金丝雀 | 进程监控、系统日志 |
| 业务指标 | 金丝雀 vs. 基线版本 | 分析工具、营收追踪 |
| 用户反馈 | 是否有新增投诉 | 客服工单、社交媒体 |

### Go / No-Go 决策

观察期结束后：

- **GO（通过）** → 所有指标在可接受范围内 → 进入阶段四
- **NO-GO（不通过）** → 任一指标超出阈值 → 立即回滚

## 阶段四：逐步放量

逐步增加金丝雀比例，每一步都需重新验证指标：

```
1%   → 观察 30 分钟 → ✓ 指标正常
5%   → 观察 30 分钟 → ✓ 指标正常
10%  → 观察 30 分钟 → ✓ 指标正常
25%  → 观察 30 分钟 → ✓ 指标正常
50%  → 观察 30 分钟 → ✓ 指标正常
100% 全量发布
```

任一步骤验证失败，立即回滚。

**放量阶梯设计原则**：
- 每一步的流量增量不应超过上一步的两倍（避免跳跃式增长）
- 每一步的观察时间应足够暴露指标异常（30 分钟是下限）
- 在非工作时段放量时，延长观察时间（用户量少可能导致指标失真）

## 阶段五：全量发布

1. 部署到 100% 实例
2. 全量发布后持续监控 30 分钟
3. 保留金丝雀实例运行 24 小时（如果需要快速回滚）
4. 24 小时平稳运行后，下线金丝雀实例
5. 在 `#releases` 频道发布完成公告

## 回滚决策矩阵

| 条件 | 行动 | 响应时间 |
|---|---|---|
| 错误率 > 基线的 2 倍，持续超过 2 分钟 | 立即回滚 | 2 分钟内 |
| P99 延迟 > 基线的 3 倍，持续超过 5 分钟 | 立即回滚 | 5 分钟内 |
| 金丝雀中出现任何崩溃 | 立即回滚 | 立即 |
| 业务指标下降超过 10% | 与 PM 讨论；大概率回滚 | 15 分钟内决策 |
| 用户投诉激增 | 调查确认是否由变更引起；确认则回滚 | 30 分钟内决策 |

## 常见反模式

| 反模式 | 为何失败 | 正确做法 |
|---|---|---|
| 首次部署就放量 50% | 爆炸半径太大；违背金丝雀的初衷 | 从 1-5% 起步，逐步放量 |
| 不设对比指标 | 无法判断金丝雀版本是更好还是更差 | 始终将金丝雀指标与基线版本进行同窗口并列对比 |
| "变更很小，跳过金丝雀" | 小改动引发大故障（配置拼写错误、依赖升级导致的不兼容）| 所有变更都做金丝雀；观察期长短根据风险调整 |
| 放量期间忽视金丝雀监控 | 每个放量步之后指标可能漂移；错过异常信号 | 每个放量步之后都重新验证指标，通过后才放下一步 |
