# 回滚演练流程

> **适用场景**：每月演练回滚。演练中 2 分钟能完成的回滚，在实际故障压力下需要 20 分钟。演练将恐慌反应转化为肌肉记忆。

## 回滚演练的价值

回滚是 SRE 工具箱中最强大但最少被练习的工具。大多数团队只在真正需要回滚时才第一次执行它——也就是说，在最大压力、最需要速度和准确性的时候，团队却在执行一个不熟悉的流程。

| 未演练 | 每月演练 |
|---|---|
| 回滚耗时 20-30 分钟（在故障压力下）| 回滚耗时 2-5 分钟（肌肉记忆）|
| 回滚过程中出现操作错误 | 回滚流程滚瓜烂熟 |
| 不确定回滚后如何验证 | 验证步骤已经自动化 |
| 第一个发现"我们没法回滚"→ 在故障中 | 演练中提前发现并修复回滚障碍 |

## 演练计划

- **频率**：每月一次（固定在团队日历上）
- **时长**：30 分钟
- **参与人员**：on-call 工程师 + 另一名工程师（双人搭档制）
- **环境**：先在预发布环境，预发布环境通过后再在生产环境中进行

## 何时执行回滚（决策触发条件）

满足以下任一条件时，应执行回滚：

| 触发条件 | 阈值 | 原因 |
|---|---|---|
| 错误率飙升 | > 基线的 5 倍，持续超过 2 分钟 | 系统不可靠，需要快速恢复 |
| P99 延迟飙升 | > 基线的 3 倍，持续超过 2 分钟 | 用户体验严重下降 |
| 关键用户路径中断 | 用户无法完成核心操作 | 任何程度的路径中断都应回滚 |
| 数据损坏或丢失 | 检测到数据异常 | 数据完整性高于一切 |
| 安全漏洞 | 新版本中发现安全漏洞 | 安全优先 |

**不应回滚的情况**：问题轻微、有快速的向前修复方案、且不影响关键用户路径。安全的向前修复始终优于回滚。

## 回滚流程四阶段

### 阶段一：决策（2 分钟）

| 步骤 | 执行人 | 操作 |
|---|---|---|
| 1 | on-call | 确认告警/问题 |
| 2 | on-call | 对照上方决策触发条件评估严重程度 |
| 3 | on-call | 在 `#incidents` 频道宣布决策："正在回滚 {{服务}} {{版本}}，原因：{{原因}}" |

### 阶段二：执行（5 分钟）

| 步骤 | 执行人 | 操作 |
|---|---|---|
| 1 | on-call | 执行回滚命令 |
| 2 | on-call | 验证部署状态 |
| 3 | 搭档 | 在回滚过程中监控仪表盘，注意异常 |

**YrY 各服务回滚命令**：

| 服务 | 回滚命令 |
|---|---|
| YiAi | `git checkout <上一个提交> && pip install -r requirements.txt && pkill -f uvicorn && python main.py &` |
| YiVad | `git checkout <上一个提交> && pnpm install && pnpm build:pro` |
| YiPet | `git checkout <上一个提交> && npm install && npm run build` |
| YiKnowledge | `git checkout <上一个提交>`（监视器自动检测）|

### 阶段三：验证（5 分钟）

| 步骤 | 执行人 | 操作 |
|---|---|---|
| 1 | on-call | 对回滚后的版本运行冒烟测试 |
| 2 | on-call | 验证错误率、延迟和吞吐量恢复到基线水平 |
| 3 | 搭档 | 确认关键用户路径正常工作 |
| 4 | on-call | 在 `#incidents` 宣布完成："回滚完成。{{服务}} 已恢复至 {{之前的版本}}。正在持续监控。"

### 阶段四：回滚后跟进

| 步骤 | 执行人 | 操作 |
|---|---|---|
| 1 | on-call | 回滚后持续监控 15 分钟 |
| 2 | on-call | 为导致回滚的问题创建 Bug 工单 |
| 3 | 团队 | 24 小时内完成事后复盘（参照 [../incident-response/04-事件-响应事件.md](../incident-response/04-事件-响应事件.md)）|

## 手动回滚（后备方案）

如果自动化回滚失败，采用手动回滚路径：

| 层面 | 手动回滚操作 |
|---|---|
| **数据库** | 运行反向迁移脚本 |
| **基础设施** | 恢复到上一个基础设施版本 |
| **应用** | 部署上一个版本的构建产物 |
| **配置** | 恢复到上一个版本的配置文件 |

## 演练成功标准

演练通过需满足以下全部条件：

- [ ] 决策后 10 分钟内完成回滚
- [ ] 无数据丢失
- [ ] 回滚后所有冒烟测试通过
- [ ] on-call 和搭档都参与了
- [ ] 演练后记录了所有摩擦点

## 演练后复盘

| 复盘问题 | 记录 |
|---|---|
| 回滚耗时多久？ | {{分钟}} |
| 什么拖慢了我们的速度？ | {{摩擦点}} |
| 自动化回滚是否工作正常？ | {{是/否——如否，为什么？}} |
| 回滚过程中仪表盘是否清晰？ | {{是/否}} |
| 下月演练前应改进什么？ | {{行动项}} |

## 常见反模式

| 反模式 | 为何失败 | 正确做法 |
|---|---|---|
| 只在预发布环境练习 | 生产环境有不同的配置、规模和压力 | 在生产环境用低风险变更进行演练 |
| "需要时我们自然会回滚" | 第一次真实回滚需要 30+ 分钟的惊慌失措 | 每月演练使回滚变成 5 分钟的例行操作 |
| 没有双人搭档 | on-call 独自在压力下操作；错误叠加 | 回滚期间始终有第二个人在场 |
| 演练后不进行复盘 | 摩擦点被遗忘；下月同样的问题再次出现 | 记录每个摩擦点，在下一次演练前修复 |
| 只演练正常路径，不演练异常场景 | 真实回滚往往伴随数据库状态不一致等复杂情况 | 演练中穿插异常注入——模拟数据库迁移失败、配置文件损坏等 |
