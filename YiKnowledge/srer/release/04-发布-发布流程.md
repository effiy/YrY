# 发布流程

> **发布 = 构建 + 验证 + 部署 + 监控。** 每个 Yi 家族服务有各自的发布路径。所有发布遵循相同的"发布前 → 部署 → 验证 → 回滚"模式。

## 发布的核心原则

1. **后端先行**——当变更涉及 RPC 契约时，YiAi 必须先于 YiVad/YiPet 发布
2. **可回滚**——每次发布前写好回滚方案。不在发布时"边想边做"
3. **验证完才算发布成功**——部署完成不等于发布成功。只有验证通过才算
4. **不选周五下午**——当前无自动化监控，周五部署意味着周一才发现问题

## 全服务通用发布前检查清单

- [ ] 所有测试通过（`npm test`、`pnpm type:check`、`vue-tsc --noEmit`）
- [ ] Lint 通过（`npm run lint`、`pnpm lint:eslint`、`ruff check`）
- [ ] 构建成功（`npm run build`、`pnpm build:pro`）
- [ ] 不兼容变更已记录在对应项目的 CLAUDE.md "Recent Changes" 中
- [ ] 跨项目契约变更已记录在 RPC 协议参考中
- [ ] 回滚方案已写好（见各服务下方的回滚步骤）

## YiAi（Python 后端）

### 部署步骤
```bash
cd YiAi
git pull
pip install -r requirements.txt

# 重启 uvicorn
pkill -f uvicorn
python main.py &
```

### 验证
```bash
# 健康检查
curl http://localhost:10086/health/observer
# 预期返回：{"status": "ok", "mongodb": "connected", "ollama": "available"}

# RPC 信封调用验证
curl -X POST http://localhost:10086/ \
  -H "Content-Type: application/json" \
  -d '{"module_name":"services.database.data_service","method_name":"query_documents","parameters":{"cname":"menus","pageSize":1}}'
# 预期返回：{"code": 0, "data": {"list": [...]}}

# RAG 状态验证
curl http://localhost:10086/rag-status
# 预期返回：{"built": true, "num_docs": N}
```

### 回滚
```bash
git checkout <上一个提交的 hash>
pip install -r requirements.txt
pkill -f uvicorn
python main.py &
# 重新执行上述验证步骤
```

## YiVad（Vue 3 SPA）

### 部署步骤
```bash
cd YiVad
git pull
pnpm install
pnpm build:pro
# 将 dist/ 部署到 Web 服务器或本地服务
pnpm dev   # 仅本地开发
```

### 验证
```bash
# 检查构建产物
ls dist/index.html

# 验证 TypeScript 类型
pnpm type:check

# 浏览器验证清单：
# - 登录功能正常
# - 菜单正常加载（从后端获取动态路由）
# - ProTable 页面正常渲染
# - aiChat SSE 流式传输正常
# - 浏览器控制台无新增错误
```

### 回滚
```bash
git checkout <上一个提交的 hash>
pnpm install
pnpm build:pro
# 重新部署构建产物
```

npm test   # 所有测试通过

# Chrome 中验证：
# - 扩展图标出现在任意页面上
# - Ctrl+Shift+X 可打开聊天窗口
# - 聊天 SSE 流式传输正常
# - Popup 打开且设置持久化有效

### 回滚

git checkout <上一个提交的 hash>

## 多服务发布协调

当变更跨多个服务时（例如新增 RPC 参数），按以下顺序发布：

1. **YiAi 优先发布**——后端必须先支持新契约，前端才能使用
2. **YiVad + YiPet 并行发布**——YiAi 验证通过后可同时发布两个前端
3. **YiKnowledge 最后发布**——如果变更包含文档更新

**重要提示**：禁止在 YiAi 发布前部署 YiVad 或 YiPet！破坏性契约变更的发布顺序错误会导致前端报 422 错误或静默忽略参数。

## 发布后监控

每次发布后，**持续监控 15 分钟**：

- [ ] YiAi `/health/observer` 返回正常（MongoDB 连接、Ollama 可用）
- [ ] YiVad 页面加载无控制台错误
- [ ] YiPet 聊天流式传输正常
- [ ] 无 401（Token）、422（参数不匹配）或 500 错误的异常飙升
- [ ] 知识监视器同步成功（检查日志中无异常）

## 常见反模式

- **当变更新增 API 参数时，先部署 YiVad 再部署 YiAi。** YiVad 发送新参数，YiAi 不识别，错误行为取决于参数是被静默忽略（结果错误）还是被拒绝（422 错误）。
- **跳过回滚方案。** "出问题了到时再说"是 15 分钟故障变成 2 小时故障的原因。部署前必须写好回滚方案。
- **周五下午发布。** Yi 家族没有自动化告警和监控，周五部署意味着周一才发现问题。错过整个故障窗口。
- **一次部署多个不相关的变更。** 如果出现问题，无法快速判断是哪个变更导致的。每次部署只包含一个逻辑变更。
- **部署后不验证就认为成功。** 部署命令执行成功不等于服务正常工作。必须执行验证步骤。特别是健康检查端点可能返回正常但实际数据层有问题。
