# 热修复发布流程

> **适用场景**：当生产环境出现严重 Bug 必须立即修复时——正常发布流程太慢，且故障影响足以证明跳过标准流程是合理的。

## 热修复的适用条件

一个变更应该作为热修复处理，当且仅当**全部**以下条件成立：

- [ ] Bug 影响关键用户路径（用户无法完成核心操作）
- [ ] 影响正在持续（不是一次性事件）
- [ ] 正常发布流程需要超过 1 小时（时间等不起）
- [ ] 修复方案清晰且低风险

以下情况**不应该**走热修复：
- 非关键 Bug（视觉问题、边缘场景、存在临时方案）
- 可以等到下一个排期发布的 Bug
- 需要设计评审的复杂修复

## 热修复与正常发布的区别

| 维度 | 正常发布 | 热修复 |
|---|---|---|
| **审批流程** | 完整 CR + QA | 加速 CR：关注正确性而非风格 |
| **测试要求** | 完整测试套件通过 | 至少本地验证修复有效 |
| **部署节奏** | 标准金丝雀放量 | 10% → 5 分钟观察 → 100% |
| **变更范围** | 可以有多个特性 | 一个提交，最小改动 |
| **事后要求** | 正常发布记录 | 必须撰写事后复盘 + 回归测试 |

## 阶段一：评估（5 分钟）

| 步骤 | 执行人 | 操作 |
|---|---|---|
| 1 | on-call | 确认 Bug 符合热修复条件 |
| 2 | on-call | 定位引入 Bug 的精确提交 |
| 3 | 工程师 | 草拟修复方案（一个提交，最小改动）|
| 4 | on-call | 获取热修复审批 |

### 热修复审批

| 时段 | 审批人 | 说明 |
|---|---|---|
| **工作时间** | 工程经理或技术负责人 | 单人审批即可 |
| **非工作时间** | on-call 工程师 + 备份 on-call | 双人原则——两人都确认修复方案合理 |

**双人原则的目的**：非工作时间人员少，个人判断更容易出现偏差。两个人确认修复方案可以大幅降低"仓促修复导致更大问题"的概率。

## 阶段二：修复（尽可能快但确保安全）

### 热修复分支操作

```bash
git checkout main
git pull
git checkout -b hotfix/<描述>
# 做出修复 —— 一个提交，最小改动
git commit -m "hotfix: <描述>"
git push
```

### 热修复铁律

- **一个提交**——修复必须原子化、可单独回退
- **最小改动**——只修 Bug；不重构、不"顺便修一下"
- **本地验证修复**——至少确认 Bug 已被修复
- **无新功能**——热修复不是功能开发的捷径

**"顺便修一下"的危害**：
热修复中混入的额外改动未经正常发布流程的审查，是生产环境故障的第二大来源（仅次于热修复本身解决的那个 Bug）。每次热修复只能包含一个原子化变更。

## 阶段三：审查（加速流程）

| 步骤 | 执行人 | 操作 |
|---|---|---|
| 1 | 修复者 | 创建 PR，标题加 `[HOTFIX]` 前缀 |
| 2 | 审查者 | 15 分钟内完成审查——关注正确性，不关注代码风格 |
| 3 | 审查者 | 批准或要求修改 |
| 4 | 修复者 | 合并到主分支 |

审查清单（这四项必须全部通过）：
- [ ] 修复是否真正解决了 Bug？
- [ ] 是否引入了明显的新 Bug？
- [ ] 变更是否最小化（无无关改动）？
- [ ] 是否有数据迁移方面的顾虑？

## 阶段四：部署（加速流程）

### YrY 各服务热修复部署

**YiAi**：
```bash
cd YiAi
git pull
pip install -r requirements.txt
pkill -f uvicorn
python main.py &
# 验证：curl http://localhost:10086/health/observer
```

**YiVad**：
```bash
cd YiVad
git pull
pnpm install
pnpm build:pro
# 部署 dist/ 到 Web 服务器
```

**YiPet**：
```bash
cd YiPet
git pull
npm install
npm run build
# 在 Chrome 中重新加载扩展
```

### 部署后监控

热修复部署后持续监控 **15 分钟**：
- [ ] YiAi `/health/observer` 返回正常
- [ ] 确认 Bug 已被修复（手动验证）
- [ ] 无新增错误模式
- [ ] 核心指标（错误率、延迟、吞吐量）未恶化

### 回滚准备

部署前准备好回滚命令：

```bash
git checkout <上一个提交的 hash>
# 重复上述服务部署步骤
```

## 阶段五：热修复后清理（24 小时内完成）

### 必须完成的跟进事项

- [ ] 撰写事后复盘（参照 [../incident-response/04-事件-响应事件.md](../incident-response/04-事件-响应事件.md)）
- [ ] **为该 Bug 添加回归测试**——这是热修复后最重要的行动项
- [ ] 审查为什么这个 Bug 没有在预发布环境/CI 中被发现
- [ ] 如果热修复代码仓促，安排后续 PR 进行代码清理
- [ ] 将新发现的故障模式更新到 runbook

### 热修复日志

| 日期 | 热修复提交 | Bug 描述 | 修复耗时 | 根因 |
|---|---|---|---|---|
| {{YYYY-MM-DD}} | {{commit}} | {{描述}} | {{分钟}} | {{为什么发生}} |

**热修复日志的价值**：如果同一类 Bug 频繁出现，日志会揭示系统性问题。偶尔的热修复是正常的；同一模块每月一次热修复则意味着更深层的设计缺陷。

## 紧急覆盖

在极端情况下（安全漏洞、数据丢失），双人原则可以被豁免：

1. **立即修复**——止血优先
2. **事后通知**——第一时间告知工程经理
3. **事后复盘强制要求**——紧急覆盖情况必须写事后复盘

## 常见反模式

| 反模式 | 为何失败 | 正确做法 |
|---|---|---|
| 把热修复当功能发布捷径 | 破坏发布流程；质量下降 | 热修复仅限关键 Bug；新功能走正常发布流程 |
| "紧急"为由跳过代码审查 | 热修复引入新 Bug；事故叠加 | 始终需要第二双眼睛审查，即使是加速审查 |
| 热修复后不写事后复盘 | 根因从未被解决；同类 Bug 反复出现 | 24 小时内完成复盘；48 小时内添加回归测试 |
| 复杂热修复（多个提交、包含重构）| 故障期间引入额外风险的概率极高 | 一个提交，最小改动；重构留到后续 PR |
