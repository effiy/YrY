# 生产就绪审查 — 服务上线前的最后一道质量门

> **适用场景**：新服务首次上线、重大架构变更后重新上线、或每季度对已有服务的定期审查。生产就绪审查（PRR）防止"功能做完了但运维跟不上"的常见上线失败模式。

## 为什么需要 PRR

"功能已经开发好了，可以上线了"——这是最常见的上线失败起点。功能完成 ≠ 生产就绪。一个服务要在生产环境中稳定运行，需要可观测性、容错能力、安全加固和运维流程的支撑。

| 无 PRR | 有 PRR |
|---|---|
| 上线后发现没有监控，故障靠用户通知 | 上线前确认健康检查、告警、仪表盘就位 |
| 第一次故障时发现没有 runbook | 上线前已有 3 个常见故障的 runbook |
| 磁盘满导致写入静默失败 | 上线前磁盘告警已配置 |
| 不知道服务的容量上限 | 上线前已完成基础负载测试 |

## 审查域总览

| 域 | 核心问题 | 检查项数 | 不通过后果 |
|---|---|---|---|
| **可观测性** | 能不能知道服务在做什么？ | 5 | 生产盲区——故障靠猜 |
| **容错与恢复** | 出问题了能不能自动恢复？ | 5 | 每次故障需人工介入 |
| **安全** | 会不会成为攻击入口？ | 4 | 数据泄露风险 |
| **容量** | 能扛多少流量？ | 4 | 流量突增时崩溃 |
| **运维流程** | 谁负责运维？出问题找谁？ | 5 | 故障时无人响应 |

## 一、可观测性审查

| # | 检查项 | 通过标准 | 验证方法 | YrY 示例 |
|---|---|---|---|---|
| 1 | **健康检查端点** | 存活/就绪/深度三类端点为 200 | `curl /health/observer` | YiAi 已实现 `/health/observer` |
| 2 | **结构化日志** | 日志包含 timestamp/service/trace_id/level | 手动触发请求，检查日志格式 | YiAi stdout → 需改为 JSON 格式 |
| 3 | **关键指标暴露** | 至少暴露 4 个黄金信号中的 3 个 | 检查 metrics 端点或 Prometheus 配置 | 延迟/错误率/吞吐量/饱和度 |
| 4 | **告警规则就位** | 至少 3 条告警规则已配置并测试 | 模拟故障，确认告警触发 | MongoDB 不可达、Ollama 不可用、磁盘 > 80% |
| 5 | **仪表盘可用** | 至少 1 个仪表盘展示关键指标 | 截图确认仪表盘正常渲染 | 服务健康概览仪表盘 |

**不通过示例**：
- 健康检查只返回 `{"status": "ok"}` 但不检查依赖 → 不通过
- 日志无 trace_id → 不通过（无法跨服务关联请求）

## 二、容错与恢复审查

| # | 检查项 | 通过标准 | 验证方法 | YrY 示例 |
|---|---|---|---|---|
| 1 | **依赖降级** | 每个外部依赖不可用时，服务优雅降级而非崩溃 | 逐个断开依赖，观察行为 | Ollama 不可用 → 聊天返回错误码 2001，非 500 |
| 2 | **回滚方案** | 有文档化的回滚步骤，且最近一次演练在 30 天内 | 检查回滚演练记录 | YiAi 回滚：`git checkout + pkill + 重启` |
| 3 | **数据备份** | 关键数据有定时备份，最近一次恢复验证在 90 天内 | 检查备份日志和恢复演练记录 | MongoDB 每日备份 + 季度恢复演练 |
| 4 | **启动顺序** | 服务启动不依赖其他服务的启动顺序 | 先启动该服务，再启动其依赖，验证自动重连 | YiAi 应在 MongoDB 就绪后自动连接 |
| 5 | **资源限制** | CPU/内存有上限配置，防止单服务耗尽整机资源 | 检查 systemd/Docker 资源限制配置 | uvicorn workers 数量、Docker memory limit |

**不通过示例**：
- 依赖不可用但服务返回 500 堆栈 → 不通过（应返回类型化错误）
- 3 个月未验证备份可恢复 → 不通过

## 三、安全审查

| # | 检查项 | 通过标准 | 验证方法 | YrY 示例 |
|---|---|---|---|---|
| 1 | **密钥不硬编码** | 所有密钥/Token/密码从环境变量或密钥管理获取 | `grep` 代码中是否有硬编码密钥 | YiAi `config.yaml` 中的 MongoDB URI |
| 2 | **最小权限** | 服务使用的数据库账号只有必要权限 | 检查 MongoDB 用户角色 | YiAi 只需 readWrite，不需 root |
| 3 | **API 认证** | 非公开端点有认证（X-Token 或 API Key） | 不带 Token 请求应返回 401 | RPC 端点需验证 Token（如启用认证） |
| 4 | **依赖安全** | 无已知高危 CVE 的依赖 | 运行 `pip audit` / `npm audit` | Python 依赖、Node 依赖定期扫描 |

**不通过示例**：
- MongoDB 连接串含密码硬编码在 `config.yaml` → 不通过
- `npm audit` 显示 Critical 级别的 CVE → 不通过

## 四、容量审查

| # | 检查项 | 通过标准 | 验证方法 | YrY 示例 |
|---|---|---|---|---|
| 1 | **负载测试** | 在预期 2 倍负载下，P99 延迟不超过 SLO | 运行负载测试并记录结果 | vegeta 对 YiAi 做 2× 预期并发测试 |
| 2 | **性能基线** | 有文档化的性能基线（并发量、P99 延迟、资源使用） | 检查性能基线文档 | 首次上线记录基线 |
| 3 | **扩容方案** | 有明确的扩容触发条件和操作步骤 | 检查扩容 runbook | CPU > 70% 持续 10 分钟 → 增加 worker |
| 4 | **资源容量评估** | 当前硬件资源有 ≥ 30% 余量 | 检查 `df -h` / `nvidia-smi` / 连接池使用率 | 磁盘余量 > 30%，MongoDB 连接池余量 > 30% |

**不通过示例**：
- 从未做过负载测试 → 不通过（不知道服务能扛多少流量）
- 磁盘使用率已 85% → 不通过（余量不足）

## 五、运维流程审查

| # | 检查项 | 通过标准 | 验证方法 | YrY 示例 |
|---|---|---|---|---|
| 1 | **Runbook 就位** | 至少 3 个常见故障有 runbook | 检查 runbook 文档 | MongoDB 不可达、Ollama 不可用、磁盘满 |
| 2 | **值班覆盖** | 服务纳入 on-call 轮值范围 | 检查 on-call 排班表 | 值班人知道新增了此服务 |
| 3 | **告警响应人** | 每条告警规则有明确的响应人/团队 | 检查告警配置中的 `runbook` 字段 | 告警指向具体 runbook 链接 |
| 4 | **变更流程** | 该服务的变更纳入变更管理流程 | 检查变更管理文档中是否包含此服务 | 服务的变更风险分级定义 |
| 5 | **交接文档** | 服务关键信息纳入值班交接模板 | 检查交接模板是否包含此服务 | 健康检查端点、关键告警、已知问题 |

**不通过示例**：
- 新服务上线但 on-call 不知道 → 不通过
- 有告警但没有 runbook → 不通过

## PRR 执行流程

### 参与角色

| 角色 | 职责 |
|---|---|
| **服务负责人**（工程师） | 逐项自检，提供验证证据 |
| **SRE 审查人** | 独立验证每项检查，记录不通过项 |
| **Tech Lead**（高风险变更） | 终审高风险服务的 PRR 结果 |

### 审查节奏

```
开发完成 → 自检（服务负责人，提前 2 天完成）→ PRR 会议（30-60 分钟）
    │                                                    │
    │  ✓ 全部通过？                                       │  ✗ 有不通过项？
    │  进入发布流程                                        │  记录到问题清单
    │                                                    │  修复后重新审查
    ▼                                                    ▼
  上线                                                修复 → 复查
```

### PRR 结论

| 结论 | 含义 | 后续行动 |
|---|---|---|
| **通过** | 23 项全部满足 | 进入正常发布流程 |
| **有条件通过** | 1-3 项不满足，但不阻塞上线（如仪表盘美化） | 上线 + 问题项限期修复（≤ 1 周） |
| **不通过** | > 3 项不满足，或任一安全/容错项不满足 | 修复后重新审查，不得上线 |

**底线规则**：安全（域三）和容错（域二）中的任何一项不通过 = PRR 不通过，无论其他项如何。

## 常见反模式

| 反模式 | 为何失败 | 正确做法 |
|---|---|---|
| 审查走过场（全部秒批通过） | 上线后才发现问题；PRR 失去意义 | SRE 独立验证每项——不依赖服务负责人的自述 |
| 先上线再补 PRR | PRR 变成事后橡皮图章 | PRR 是上线门禁，未通过不得上线 |
| PRR 只做一次 | 系统演进后原先通过的项目可能不再满足 | 重大变更后重新审查；已有服务每季度复检 |
| 安全项"以后再说" | 上线即暴露攻击面 | 安全审查中的任何红色项 = 一票否决 |
| PRR 清单从不更新 | 新的最佳实践反映不进去 | 每次审查后回顾：是否有应该加入清单的新检查项？ |
