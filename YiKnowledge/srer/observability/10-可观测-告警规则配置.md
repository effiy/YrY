# 告警规则配置 — 从零搭建可操作的告警体系

> **适用场景**：为 YrY 服务搭建告警体系时。好的告警是精准的信号；坏的告警是噪音。告警的目标不是"什么都知道"，而是"知道什么需要人立即行动"。

## 告警设计原则

| 原则 | 含义 | 反例 |
|---|---|---|
| **可操作** | 每条告警都需要人工执行具体操作 | "CPU 用了 50%"——然后呢？ |
| **有 runbook** | 每条告警都有对应的处理步骤 | 告警触发后值班人不知道该做什么 |
| **非重复** | 同一根因只触发一条告警 | 一个 MongoDB 故障触发 5 条不同的告警 |
| **面向用户** | 基于用户体验定义，而非技术指标 | 只告警"内存使用率高"而不告警"用户请求超时" |
| **有优先级** | 告警分紧急程度，值班人知道先处理什么 | 所有告警同一级别 |

### 告警vs通知

不是所有异常都需要叫醒人。区分两类信号：

| 类型 | 定义 | 通知方式 | 示例 |
|---|---|---|---|
| **告警（Alert）** | 需要立即人工干预 | 电话/Pager/即时消息 | MongoDB 不可达、5xx 错误率 > 5% |
| **通知（Notification）** | 需要关注但不紧急 | 邮件/频道消息 | 证书 30 天后过期、磁盘使用率增长趋势 |

规则：**如果不需要人立刻起床处理，就不要发告警**。

## 告警分级

| 级别 | 定义 | 响应要求 | 通知方式 | 示例 |
|---|---|---|---|---|
| **P0 - 紧急** | 关键用户路径中断 | 5 分钟内响应 | 电话 + Pager + IM | YiAi 不可达、数据库损坏 |
| **P1 - 严重** | 核心功能降级 | 15 分钟内响应 | Pager + IM | Ollama 不可用、API 错误率 > 2% |
| **P2 - 警告** | 非关键功能异常 | 1 小时内响应 | IM 通知 | RAG 索引过期、慢查询增多 |
| **P3 - 信息** | 趋势性指标偏离 | 下个工作日处理 | 邮件/频道消息 | 磁盘使用率增长加速、证书即将过期 |

## YrY 告警规则

### YiAi 核心告警

```yaml
# 规则 1：YiAi 不可用
- alert: YiAiDown
  expr: up{job="yiai"} == 0
  for: 1m
  severity: P0
  summary: "YiAi 服务不可达"
  runbook: RB-001

# 规则 2：MongoDB 不可达
- alert: YiAiMongoDBDisconnected
  expr: yiai_health_mongodb_connected == 0
  for: 2m
  severity: P0
  summary: "YiAi 无法连接 MongoDB"
  runbook: RB-001

# 规则 3：Ollama 不可用
- alert: YiAiOllamaUnavailable
  expr: yiai_health_ollama_available == 0
  for: 2m
  severity: P1
  summary: "YiAi 无法连接 Ollama，聊天功能受影响"
  runbook: RB-002

# 规则 4：API 错误率过高
- alert: YiAiHighErrorRate
  expr: rate(yiai_http_requests_total{status=~"5.."}[5m]) / rate(yiai_http_requests_total[5m]) > 0.02
  for: 5m
  severity: P1
  summary: "YiAi API 5xx 错误率超过 2%，持续 5 分钟"

# 规则 5：P99 延迟过高
- alert: YiAiHighLatency
  expr: histogram_quantile(0.99, rate(yiai_request_duration_seconds_bucket[5m])) > 2
  for: 10m
  severity: P2
  summary: "YiAi API P99 延迟 > 2 秒，持续 10 分钟"

# 规则 6：RAG 索引为空
- alert: YiAiEmptyRAGIndex
  expr: yiai_rag_num_docs == 0
  for: 15m
  severity: P2
  summary: "RAG 索引文档数为 0，知识库检索失效"
```

### 基础设施告警

```yaml
# 规则 7：磁盘空间不足
- alert: DiskSpaceLow
  expr: (node_filesystem_avail_bytes / node_filesystem_size_bytes) < 0.2
  for: 10m
  severity: P1
  summary: "磁盘可用空间不足 20%"
  runbook: RB-003

# 规则 8：磁盘空间严重不足
- alert: DiskSpaceCritical
  expr: (node_filesystem_avail_bytes / node_filesystem_size_bytes) < 0.1
  for: 5m
  severity: P0
  summary: "磁盘可用空间不足 10%"
  runbook: RB-003

# 规则 9：内存使用率过高
- alert: HighMemoryUsage
  expr: (1 - node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes) > 0.9
  for: 15m
  severity: P1
  summary: "内存使用率超过 90%，持续 15 分钟"

# 规则 10：CPU 使用率过高
- alert: HighCPUUsage
  expr: 100 - (avg by(instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100) > 90
  for: 15m
  severity: P2
  summary: "CPU 使用率超过 90%，持续 15 分钟"
```

### 应用层告警

```yaml
# 规则 11：知识监视器同步失败
- alert: KnowledgeWatcherSyncFailed
  expr: rate(yiai_knowledge_sync_errors_total[15m]) > 0
  for: 15m
  severity: P2
  summary: "知识监视器同步连续失败"

# 规则 12：MongoDB 连接池接近耗尽
- alert: MongoDBConnectionPoolNearExhaustion
  expr: yiai_mongodb_active_connections / yiai_mongodb_max_connections > 0.8
  for: 10m
  severity: P2
  summary: "MongoDB 连接池使用率超过 80%"

# 规则 13：Ollama 推理队列积压
- alert: OllamaQueueBacklog
  expr: yiai_ollama_queue_depth > 10
  for: 10m
  severity: P2
  summary: "Ollama 推理请求排队超过 10 个"
```

## 告警路由

### 按时间和级别路由

| 时段 | P0 | P1 | P2/P3 |
|---|---|---|---|
| **工作时间**（9:00-18:00 工作日） | 值班人电话 + #incidents | 值班人 IM + #incidents | #sre-alerts 频道 |
| **非工作时间** | 值班人电话 + 备份值班人电话 | 值班人电话 + IM | #sre-alerts 频道（不打电话） |

### 告警分组

同一故障引发多条告警时，只发送一条通知，避免告警风暴：

```yaml
# 告警分组配置
group_by: ['alertname', 'service']
group_wait: 30s          # 等待 30 秒收集同组告警
group_interval: 5m       # 同一组每 5 分钟最多发送一次
repeat_interval: 4h      # 同一告警 4 小时内不重复发送
```

## 告警静默

### 计划内静默

以下场景应提前设置告警静默：

| 场景 | 静默范围 | 静默时长 |
|---|---|---|
| **计划内维护** | 受影响服务的所有告警 | 维护窗口 + 前后各 15 分钟 |
| **发布窗口** | 预期的错误率/延迟告警 | 发布窗口 + 30 分钟 |
| **已知问题** | 与该问题相关的特定告警 | 直到修复部署完成 |
| **Game Day 演练** | 演练涉及的所有告警 | 演练窗口 |

### 静默原则

- **必须设定过期时间**——永不过期的静默 = 未来某天真故障无人知晓
- **必须注明原因**——"静默 YiAi API 告警，计划维护 14:00-15:00"
- **维护结束立即撤销静默**

## 告警测试

### 新告警上线前

- [ ] 在预发布环境验证告警表达式正确
- [ ] 确认告警能正确触发（注入对应故障）
- [ ] 确认告警通知能送达正确的人/频道
- [ ] 确认对应的 runbook 已存在
- [ ] 确认告警级别和响应时间合理

### 告警健康度季度审查

| 检查项 | 标准 | 不达标处理 |
|---|---|---|
| **信噪比** | > 50% 的告警需要人工响应 | 低于 50% → 降级为通知或调高阈值 |
| **误报率** | < 10% | 超过 10% → 调整告警条件 |
| **未覆盖故障** | 上季度是否有未被告警捕获的故障 | 有 → 添加对应告警规则 |
| **runbook 覆盖率** | 每条告警有对应 runbook | 不覆盖 → 补齐 runbook |

## 快速接入：从健康检查脚本到告警

YrY 当前最小可用方案——每 5 分钟的 cron 健康检查 + 飞书 Webhook 告警：

```bash
#!/bin/bash
# /opt/yiai/scripts/check-and-alert.sh
# crontab: */5 * * * * /opt/yiai/scripts/check-and-alert.sh

WEBHOOK_URL="https://open.feishu.cn/open-apis/bot/v2/hook/your-token"

HEALTH=$(curl -s http://localhost:10086/health/observer)

# 检查 MongoDB 连接状态
if echo "$HEALTH" | grep -q '"mongodb":"disconnected"'; then
  curl -s -X POST "$WEBHOOK_URL" \
    -H "Content-Type: application/json" \
    -d "{\"msg_type\":\"text\",\"content\":{\"text\":\"P0 告警：YiAi MongoDB 不可达\"}}"
fi

# 检查 Ollama 状态
if echo "$HEALTH" | grep -q '"ollama":"unavailable"'; then
  curl -s -X POST "$WEBHOOK_URL" \
    -H "Content-Type: application/json" \
    -d "{\"msg_type\":\"text\",\"content\":{\"text\":\"P1 告警：YiAi Ollama 不可用\"}}"
fi

# 检查磁盘空间
DISK_USAGE=$(df -h / | tail -1 | awk '{print $5}' | tr -d '%')
if [ "$DISK_USAGE" -gt 85 ]; then
  curl -s -X POST "$WEBHOOK_URL" \
    -H "Content-Type: application/json" \
    -d "{\"msg_type\":\"text\",\"content\":{\"text\":\"P1 告警：磁盘使用率 ${DISK_USAGE}%\"}}"
fi
```

## 常见反模式

| 反模式 | 为何失败 | 正确做法 |
|---|---|---|
| 对所有指标都设告警 | 告警疲劳——值班人开始忽略所有告警 | 只对需要人工干预的条件设告警；其余设为通知或仪表盘观察 |
| 告警阈值凭感觉设定 | 太灵敏 → 误报；太迟钝 → 漏报 | 基于历史数据设定：用过去 30 天 P95 值 + 20% 余量作为阈值 |
| 没有 runbook 就上线告警 | 告警触发后值班人不知道该做什么 | 每条告警上线前先写好 runbook |
| 不设告警静默 | 计划内维护触发大量告警 | 维护窗口设置告警静默，维护后撤销 |
| 告警不分级 | 所有告警看起来一样紧急 | 按 P0-P3 分级，不同级别不同通知方式 |
