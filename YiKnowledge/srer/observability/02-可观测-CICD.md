# CI/CD 流水线设计

> **适用场景**：为任何 YrY 项目搭建或改进部署流水线时。好的 CI/CD 流水线在问题到达生产环境之前就发现它们。

## CI 与 CD 的区别

| 术语 | 含义 | YrY 实践 |
|---|---|---|
| **CI**（持续集成） | 每次代码推送触发构建 + 测试 | `npm run typecheck && npm run build && npm test` |
| **CD**（持续交付） | 每次合并到主分支的代码都是可发布的 | 主分支始终处于可发布状态，发布由人工触发 |
| **CD**（持续部署） | 每次合并到主分支自动部署到生产环境 | 合并即上线（不需要人工审核） |

**YrY 建议**：采用**持续交付**（而非持续部署）。主分支始终保持可发布状态，但部署需要人工触发。这平衡了交付速度和发布安全性。

**选择依据**：
- 持续交付适合团队规模较小、需要上线审核的场景
- 持续部署适合高度自动化、具备完善的自动化回滚和灰度能力的场景
- YrY 目前应选择持续交付，待可观测性和自动化测试成熟后再考虑持续部署

## 流水线阶段

```
代码推送 → Lint → 类型检查 → 测试 → 构建 → 预发布部署 → 冒烟测试 → 生产部署
   │         │        │        │      │         │            │           │
   │         │        │        │      │         │            │           │
   └── 快速反馈 (< 2 分钟) ──┘         └── 较慢但更全面 (< 10 分钟) ──┘
```

### 阶段一：Lint（约 30 秒）

快速的机械性检查，用于发现语法错误和风格问题。

| 项目 | 命令 | 说明 |
|---|---|---|
| YiVad | `npx biome check --max-diagnostics=0` | Biome 集成了 ESLint + Prettier |
| YiAi | `ruff check src/` | Ruff 是 Python 的快速 Linter |
| YiPet | `npx biome check --max-diagnostics=0` | 与 YiVad 配置一致 |

### 阶段二：类型检查（1-2 分钟）

发现 Lint 无法检测到的类型错误。类型检查是性价比最高的质量门禁——成本低但能发现一整类 Bug。

| 项目 | 命令 | 说明 |
|---|---|---|
| YiVad | `vue-tsc --noEmit` | Vue 的类型检查，确保组件和模板类型正确 |
| YiPet | `tsc --noEmit` | TypeScript 严格模式类型检查 |
| YiAi | Python 类型注解由 IDE 检查或配置 mypy | Python 的类型系统是可选的 |

### 阶段三：测试（2-5 分钟）

单元测试 + 集成测试。采用快速失败策略——先运行最快的单元测试，再运行较慢的集成测试。

| 项目 | 命令 | 测试框架 |
|---|---|---|
| YiVad | `vitest run` | Vitest + @vue/test-utils |
| YiAi | `python -m pytest tests/ -v` | pytest + pytest-asyncio |
| YiPet | `vitest run` | Vitest 2 + jsdom 29 |

### 阶段四：构建（1-3 分钟）

生产构建。发现构建时错误（导入解析、打包问题）。

| 项目 | 命令 | 构建工具 |
|---|---|---|
| YiVad | `pnpm build` | Rsbuild |
| YiPet | `npm run build` | Rsbuild |

### 阶段五：预发布部署（1-2 分钟）

部署到与生产环境镜像的预发布环境。预发布环境需要尽可能接近生产配置。

### 阶段六：冒烟测试（1-2 分钟）

快速验证部署是否存活、核心流程是否正常：

- 健康检查端点返回 200
- 能否正常登录
- 能否执行基础操作（创建一条数据、打开一个页面）
- YiAi RPC 信封调用返回正确的 `code: 0`

### 阶段七：生产部署（人工触发）

部署到生产环境，配合金丝雀发布逐步放量。部署流程详见 [发布流程](../release/04-发布-发布流程.md) 和 [金丝雀发布](../release/01-发布-金丝雀发布.md)。

## 流水线健康度指标

| 指标 | 健康 | 警告 | 严重 | 说明 |
|---|---|---|---|---|
| **流水线耗时** | < 10 分钟 | 10-20 分钟 | > 20 分钟 | 超过 20 分钟开发者会失去耐心，开始跳过 CI |
| **流水线成功率** | > 95% | 85-95% | < 85% | 成功率低说明流水线自身不稳定 |
| **平均恢复时间** | < 5 分钟 | 5-15 分钟 | > 15 分钟 | 流水线故障的恢复速度 |
| **不稳定测试率** | < 1% | 1-5% | > 5% | 不稳定测试会破坏团队对 CI 的信任 |

## YrY 当前流水线状态

| 项目 | CI 检查 | 部署方式 | 当前状态 |
|---|---|---|---|
| YiVad | `vue-tsc --noEmit` + `vite build` | 手动部署 | 可运行 |
| YiAi | `pytest` + `ruff` | 手动重启 uvicorn | 可运行 |
| YiPet | `tsc --noEmit` + `npm run build` + `vitest` | 手动加载 Chrome 扩展 | 可运行 |

### 快速改进建议

| 改进项 | 投入时间 | 收益 |
|---|---|---|
| **添加 pre-push hook** | 约 30 分钟 | 在推送前自动运行 lint + typecheck |
| **添加冒烟测试** | 约 1 小时 | 每次部署后自动验证系统可用性 |
| **添加流水线耗时追踪** | 约 1 小时 | 量化衡量流水线性能，在变慢时告警 |
| **添加不稳定测试检测** | 约 2 小时 | 跟踪测试失败模式；自动隔离不稳定的测试 |

## 常见反模式

| 反模式 | 为何失败 | 正确做法 |
|---|---|---|
| 流水线耗时超过 20 分钟 | 开发者上下文切换；流水线被忽视或跳过 | 拆分为快速阶段（< 5 分钟）+ 慢速阶段（并行执行，< 10 分钟）|
| "小改动"跳过 CI | 小改动引发大故障（配置错误、依赖升级）| 所有改动都通过 CI；无例外 |
| 部署后没有冒烟测试 | 部署成功但应用实际无法正常工作 | 每次部署后运行冒烟测试；失败则自动回滚 |
| 流水线中存在不稳定测试 | 团队不再信任 CI；真正的失败被忽视 | 立即隔离不稳定测试；1 个迭代内修复 |
