# 性能测试指南 — 在故障发生前找到系统的性能边界

> **适用场景**：新服务上线前、重大架构变更后、容量规划时、以及每季度一次的性能基线更新。性能测试不是一次性活动，而是持续验证系统能力的过程。

## 为什么需要性能测试

生产环境中"先扛不住再扩容"的模式，意味着每次容量瓶颈的发现都是以用户受损为代价。性能测试的目标是在故障发生前回答以下问题：

| 问题 | 性能测试如何回答 |
|---|---|
| 系统能支撑多少并发用户？ | 逐步加压直到系统违反 SLO |
| 瓶颈在哪个组件？ | 逐组件测试（API → DB → LLM 推理） |
| 扩容阈值是多少？ | 找到性能拐点——资源使用率对应吞吐量的非线性增长点 |
| 新版本是否引入了性能退化？ | 版本间性能基线对比 |

## 四种性能测试类型

| 类型 | 目的 | 频率 | 执行环境 | YrY 示例 |
|---|---|---|---|---|
| **负载测试** | 验证系统在预期负载下满足 SLO | 每次重大变更后 | 预发布 | 模拟 50 个并发用户聊天请求 |
| **压力测试** | 找到系统的性能拐点和崩溃边界 | 每季度 | 预发布 | 持续增加并发直到 P99 延迟 > 2s |
| **浸泡测试** | 发现内存泄漏和资源逐渐耗尽 | 每季度 | 预发布 | 持续 4 小时发送正常流量 |
| **尖峰测试** | 验证系统应对突发流量的能力 | 每季度 | 预发布 | 瞬时将并发从 10 提升到 200 |

## YrY 服务性能测试方案

### YiAi — 聊天 API

**关键指标**：并发聊天请求数、P99 延迟、Ollama 推理队列深度

```bash
# 使用 vegeta 进行 HTTP 负载测试
# 安装：brew install vegeta

# 1. 准备测试请求（RPC 信封格式）
cat > /tmp/chat-targets.txt << 'EOF'
POST http://localhost:10086/
Content-Type: application/json
@/tmp/chat-body.json
EOF

# 2. 准备请求体
cat > /tmp/chat-body.json << 'EOF'
{
  "module_name": "services.ai.chat_service",
  "method_name": "chat",
  "parameters": {
    "model": "qwen3.5:7b-q4_K_M",
    "messages": [{"role": "user", "content": "用 50 字总结什么是可观测性"}],
    "stream": false
  }
}
EOF

# 3. 执行负载测试（逐步加压）
# 10 并发，持续 30 秒 — 基准
vegeta attack -targets=/tmp/chat-targets.txt -rate=10 -duration=30s | vegeta report

# 20 并发，持续 30 秒 — 逐步加压
vegeta attack -targets=/tmp/chat-targets.txt -rate=20 -duration=30s | vegeta report

# 50 并发，持续 30 秒 — 找拐点
vegeta attack -targets=/tmp/chat-targets.txt -rate=50 -duration=60s | vegeta report
```

**关注指标**：
- 成功率（非 5xx 响应比例）
- P50/P95/P99 延迟
- Ollama 队列深度（在测试期间运行 `nvidia-smi` 监控 GPU 利用率）
- uvicorn 内存使用（`ps aux | grep uvicorn`）

### YiAi — 数据 API

```bash
# 测试数据查询（不涉及 AI 推理的纯数据操作）
cat > /tmp/data-body.json << 'EOF'
{
  "module_name": "services.database.data_service",
  "method_name": "query_documents",
  "parameters": {"cname": "sessions", "pageSize": 50, "filter": {}}
}
EOF

# 逐步加压
vegeta attack -targets=/tmp/data-targets.txt -rate=50 -duration=30s | vegeta report
vegeta attack -targets=/tmp/data-targets.txt -rate=100 -duration=30s | vegeta report
vegeta attack -targets=/tmp/data-targets.txt -rate=200 -duration=30s | vegeta report
```

**关键对比**：数据 API（纯 MongoDB）应远快于聊天 API（含 Ollama 推理），对比两者延迟可定位瓶颈位置。

### YiVad — 前端加载

```bash
# 使用 Lighthouse CLI 测试前端性能
npm install -g lighthouse
lighthouse http://localhost:8848 --output json --output-path /tmp/lighthouse.json

# 关注指标
# FCP (First Contentful Paint) — < 2s
# LCP (Largest Contentful Paint) — < 3s
# TTI (Time to Interactive) — < 5s
```

### 性能测试 Checklist

```markdown
## 测试前
- [ ] 确认测试环境与生产环境配置一致（或比例缩放）
- [ ] 关闭非必要的后台进程（释放资源给测试）
- [ ] 记录基准数据（当前版本的吞吐量、延迟、资源使用率）
- [ ] 准备监控面板（CPU、内存、磁盘、网络、GPU 显存）
- [ ] 设置 SLO 阈值（超过阈值 = 测试未通过）

## 测试中
- [ ] 从低并发开始，逐步增加（不要直接跳到高并发）
- [ ] 每个并发级别至少运行 30 秒（覆盖流量波动）
- [ ] 实时监控资源使用率，观察拐点
- [ ] 记录每次加压的完整数据（成功率、延迟分布、资源使用率）

## 测试后
- [ ] 对比基准数据，计算性能变化百分比
- [ ] 标注性能拐点（哪个并发量开始违反 SLO）
- [ ] 识别瓶颈组件（CPU 先满？内存先满？连接池先耗尽？）
- [ ] 输出容量规划建议（当前硬件可支撑 X 并发，扩容到 Y 需要 Z 资源）
```

## 性能基线

### 首次建立基线

选择一个稳定的版本，执行完整的负载测试，记录结果作为基线：

```markdown
## YiAi 性能基线 — {{版本号}} — {{日期}}

| 并发 | 场景 | 成功率 | P50 | P95 | P99 | 资源瓶颈 |
|---|---|---|---|---|---|---|
| 10 | 聊天 | 100% | 1.2s | 2.1s | 3.5s | 无 |
| 10 | 数据查询 | 100% | 50ms | 120ms | 200ms | 无 |
| 20 | 聊天 | 100% | 1.8s | 3.2s | 5.1s | GPU 利用率 80% |
| 50 | 聊天 | 98% | 3.5s | 8.2s | 12.3s | GPU 利用率 100%，队列积压 |
| 50 | 数据查询 | 100% | 80ms | 180ms | 350ms | MongoDB 连接池 60% |
| 100 | 数据查询 | 100% | 120ms | 300ms | 600ms | MongoDB 连接池 95% |
```

### 性能退化检测

每次重大变更后，用相同参数重新测试，对比基线：

| 指标 | 基线 | 当前 | 变化 | 是否退化 |
|---|---|---|---|---|
| 10 并发聊天 P99 | 3.5s | 3.7s | +5.7% | 否（在可接受范围内） |
| 50 并发聊天成功率 | 98% | 92% | -6% | ⚠️ 是——需要排查 |

**退化阈值**：P99 延迟增加 > 20% 或成功率下降 > 5% → 触发性能回归调查。

## 性能拐点分析

找到系统中第一个成为瓶颈的资源：

```
并发 → 增加
    │
    ├─ 10 并发：GPU 50%，P99 2s ← 正常
    ├─ 20 并发：GPU 80%，P99 3s ← 接近拐点
    ├─ 30 并发：GPU 95%，P99 6s ← 拐点！延迟非线性增长
    ├─ 40 并发：GPU 100%，P99 15s + 部分失败 ← 超出容量
    └─ 50 并发：GPU 100%，成功率 90% ← 严重过载
```

**拐点处的瓶颈 = GPU 推理能力** → 扩容方向：升级 GPU 或添加推理实例。

## 工具选择

| 工具 | 适用场景 | 优点 | 缺点 |
|---|---|---|---|
| **vegeta** | HTTP API 负载测试 | 轻量、简单、输出友好 | 仅 HTTP |
| **k6** | 复杂场景的性能脚本 | 支持 JavaScript 编写测试脚本 | 需要编写代码 |
| **Lighthouse** | 前端性能分析 | 开箱即用，报告详细 | 仅前端 |
| **wrk** | 快速 HTTP 压测 | 性能极高 | 不支持复杂请求体 |
| **nvidia-smi** | GPU 监控 | GPU 标准工具 | 仅 GPU |

**YrY 推荐**：vegeta（API 压测）+ nvidia-smi（GPU 监控）+ Lighthouse（前端分析）。

| 阶段 | 内容 | 当前状态 |

## 常见反模式

| 反模式 | 为何失败 | 正确做法 |
|---|---|---|
| 只在生产环境"测试" | 用户是第一批发现性能瓶颈的人 | 预发布环境负载测试 → 已知容量 → 金丝雀验证 → 生产 |
| 只测一次就认为知道系统性能 | 系统在持续变化——新功能、新数据量、新依赖 | 建立基线后每季度更新，重大变更后立即测试 |
| 只测低并发 | 不知道系统在高负载下是优雅降级还是崩溃 | 必须测到性能拐点（延迟非线性增长或成功率下降） |
| 只看平均延迟 | P50 看起来很好，P99 可能已经不能用 | 性能基线必须包含 P50/P95/P99 |
| 测试时不监控资源 | 不知道瓶颈在哪，只知道"慢了" | 测试期间同时监控 CPU/内存/GPU/连接池/磁盘 |
