# 可观测性搭建

> **当前状态：通过健康端点和日志进行人工监控。** 无自动化告警、无仪表盘、无指标管线。本文档描述当前可用的工具以及如何有效使用它们。

## 当前可观测性全景

```
┌─────────────────────────────────────────────────────┐
│                    当前状态                          │
│                                                     │
│  ✓ 健康检查端点  ✓ stdout 日志  ✓ 人工检查清单       │
│  ✗ 自动化告警    ✗ 指标仪表盘  ✗ 日志聚合           │
│  ✗ 分布式追踪    ✗ SLO 追踪    ✗ 告警通知           │
└─────────────────────────────────────────────────────┘
```

## 健康检查端点

### YiAi

| 端点 | 用途 | 预期响应 | 检查频率 |
|---|---|---|---|
| `GET /health/observer` | YiAi 整体健康 | `{"status":"ok","mongodb":"connected","ollama":"available"}` | 每 5 分钟 |
| `GET /rag-status` | RAG 索引状态 | `{"built":true,"num_docs":N,"last_built_at":"..."}` | 知识库变更后 |
| `GET /knowledge-scan` | 知识库扫描 | `{"files":N,"categories":[...]}` | 验证监视器是否同步 |

**健康检查解读**：

| 响应内容 | 含义 | 应采取措施 |
|---|---|---|
| `mongodb: disconnected` | MongoDB 不可达 | P0 事件——立即排查 MongoDB 状态 |
| `ollama: unavailable` | Ollama 不可达 | P1 事件——聊天不可用但数据 CRUD 正常 |
| `status: ok` 但 `num_docs=0` | RAG 索引为空 | P2——检查知识监视器日志 |

### 健康检查脚本

```bash
#!/bin/bash
# check-health.sh — 通过 cron 每 5 分钟运行一次

echo "=== YiAi 健康状态 ==="
curl -s http://localhost:10086/health/observer | python3 -m json.tool

echo "=== RAG 状态 ==="
curl -s http://localhost:10086/rag-status | python3 -m json.tool

echo "=== Ollama 模型列表 ==="
curl -s http://localhost:11434/api/tags | python3 -c "import sys,json; [print(m['name']) for m in json.load(sys.stdin)['models']]"
```

**脚本部署位置**：`/opt/yiai/scripts/check-health.sh`
**Cron 配置**：`*/5 * * * * /opt/yiai/scripts/check-health.sh`

## 日志

### YiAi 日志

| 日志来源 | 位置 | 关注内容 | 典型日志量 |
|---|---|---|---|
| uvicorn stdout | 运行 `python main.py` 的终端 | 请求日志、错误、堆栈追踪 | 中等 |
| Agent 循环 | stdout（带 `[Agent]` 前缀）| 轮次进度、工具调用、确认、升级 | 低 |
| 知识监视器 | stdout（带 `[Knowledge]` 前缀）| 同步周期、文件数量、错误 | 低 |
| Python 异常 | stdout | 堆栈追踪（含 `file:line`）| 低（无异常时）|

### 关键日志模式监控

```bash
# Agent 错误
tail -f /dev/stdout | grep "\[Agent\].*error"

# 监视器同步失败
tail -f /dev/stdout | grep "\[Knowledge\].*failed"

# MongoDB 连接错误
tail -f /dev/stdout | grep "pymongo.errors"

# Ollama 连接错误
tail -f /dev/stdout | grep "ConnectionError.*11434"

# 磁盘写入失败（YiAi 双写文件）
tail -f /dev/stdout | grep "OSError\|PermissionError"
```

### YiVad 日志

| 日志来源 | 位置 | 关注内容 | 操作 |
|---|---|---|---|
| 浏览器控制台 | Chrome DevTools → Console | 401（Token 过期）、422（参数不匹配）、SSE 错误 | 打开 DevTools 查看 |
| Network 面板 | Chrome DevTools → Network | 失败的请求、缓慢的响应 | 检查 Failed 状态的请求 |
| 构建输出 | 终端 | `vue-tsc` 错误、构建警告 | 每次构建时检查 |

### YiPet 日志

| 日志来源 | 位置 | 关注内容 | 操作 |
|---|---|---|---|
| Service Worker 控制台 | `chrome://extensions` → YiPet → Service Worker | 扩展错误 | 点击"检查视图" |
| Popup 控制台 | 右键点击 Popup → 检查 | Popup 错误 | 独立 DevTools 窗口 |
| 聊天窗口控制台 | 聊天窗口 → 检查 | SSE 错误、API 错误 | 独立 DevTools 窗口 |
| 调试日志 | 控制台（设置 `RSBUILD_LOG_LEVEL=debug`）| API 客户端详细日志 | 仅调试时启用 |

## 人工监控检查清单

### 每日检查（约 5 分钟）

- [ ] 运行 `check-health.sh` — 确认所有端点返回 `ok`
- [ ] 检查 YiAi stdout 最后 50 行是否有错误模式
- [ ] 确认知识监视器已同步：`curl http://localhost:10086/rag-status`
- [ ] 检查磁盘空间（YiAi 双写文件到磁盘）：`df -h`

### 每周检查（约 15 分钟）

- [ ] 审查 YiAi 日志中的 Agent 错误和升级事件
- [ ] 检查 MongoDB 集合大小：在 mongo shell 中运行 `db.stats()`
- [ ] 确认 RAG 索引文档数与 YiKnowledge 文件数一致
- [ ] 检查是否有过期的知识库文件：`rg "last_verified: 2025" YiKnowledge -l`

### 部署后检查（约 15 分钟）

- [ ] 对所有端点运行健康检查
- [ ] 通过 YiVad 和 YiPet 各发送一条测试聊天消息
- [ ] 验证知识监视器检测到新文件
- [ ] 检查浏览器控制台是否有新错误

## 已知监控盲区

| 盲区 | 影响 | 当前缓解措施 | 改进方向 |
|---|---|---|---|
| 无自动化告警 | 故障由用户发现，而非运维人员 | 人工健康检查；考虑添加基于 cron 的告警 | 接入飞书 Webhook 推送告警 |
| 无指标管线 | 无 Uptime、延迟、错误率的历史数据 | 健康检查端点提供实时快照 | 引入 Prometheus + Grafana |
| 无日志聚合 | 日志分散在不同终端窗口 | 手动 `tail` 和 `grep` | 添加日志文件 + 日志轮转 |
| 无磁盘使用监控 | YiAi 双写可能悄悄填满磁盘 | `df -h` 纳入每日检查清单 | 添加磁盘使用率 cron 告警 |
| 无 MongoDB 连接池指标 | 连接耗尽无法提前检测 | 监控 `pymongo.errors` 日志 | 暴露连接池指标到健康端点 |

## 快速搭建基础告警（推荐下一步）

添加一个 cron 任务，每 5 分钟运行 `check-health.sh`，失败时发送通知：

```bash
# crontab -e
*/5 * * * * /opt/yiai/scripts/check-health.sh || echo "YiAi 健康检查失败于 $(date)" >> /tmp/yiai-alerts.log
```

**从日志到告警的升级路径**：
1. 第一步：cron + 健康检查 + 日志文件 → 发现问题
2. 第二步：健康检查失败时 curl 飞书 Webhook → 即时通知
3. 第三步：接入 Prometheus → 结构化指标
4. 第四步：Grafana 仪表盘 + 告警规则 → 可视化 + 自动化

## 常见反模式

- **只检查 YiAi 的健康端点。** YiAi 可以正常，但 YiVad 构建失败或 YiPet 加载 CDN 资源失败。每日检查清单应覆盖所有服务。
- **忽视磁盘空间。** YiAi 双写文件到磁盘。磁盘满会导致静默写入失败。磁盘空间是最常见的可避免故障。
- **不建立"正常"的错误率基线。** 不知道"正常"是什么，就无法检测异常。先记录一周内每天的错误次数，建立基线。
- **手动操作无记录。** 每次执行健康检查后应随手记录结果趋势。没有趋势数据，无法判断系统是在改善还是恶化。
