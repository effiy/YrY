# 错误预算策略 — 让 SLO 驱动实际决策

> **适用场景**：定义了 SLO 之后。SLO 定义了目标，错误预算策略定义了当可靠性偏离目标时**具体做什么**。没有策略的 SLO 只是仪表盘上的数字。

## 核心概念

### 什么是错误预算

错误预算 = SLO 允许的"不可靠"空间。

```
错误预算 = 1 - SLO 目标值

示例：
SLO = 99.9% 可用性（30 天窗口）
错误预算 = 0.1% = 30 天 × 24 小时 × 60 分钟 × 0.1% = 每月 43.2 分钟
```

含义：一个月内，服务最多可以故障 43 分钟而不违反 SLO。

### 错误预算的核心用途

| 用途 | 说明 | 反模式 |
|---|---|---|
| **发布阀门** | 预算充足 → 可以发布；预算不足 → 冻结发布 | 预算耗尽后仍正常发布 |
| **优先级仲裁** | 可靠性工作 vs 功能工作的客观仲裁标准 | "我觉得可靠性更重要"——主观 |
| **风险承担** | 有预算 = 可以承担更高的发布风险 | 预算充足但过度保守 |
| **告警阈值** | 消耗速率过快时提前告警 | 预算耗尽才告警——太晚了 |

## 错误预算计算

### 单一 SLI 的错误预算

```python
# 伪代码：计算 30 天窗口的可用性错误预算
total_minutes = 30 * 24 * 60  # 43200 分钟
slo_target = 0.999            # 99.9%
error_budget_minutes = total_minutes * (1 - slo_target)
# = 43.2 分钟
```

### 消耗追踪

```python
# 计算已消耗的错误预算
failed_requests = 150          # 30 天内失败的请求数
total_requests = 1_000_000     # 30 天内的总请求数
error_rate = failed_requests / total_requests  # 0.015%

error_budget_consumed_pct = error_rate / (1 - slo_target) * 100
# = 0.015% / 0.1% * 100 = 15% 已消耗
```

## 错误预算策略

### 策略总览

| 预算剩余 | 状态 | 功能发布 | 变更风险承受 | 可靠性工作 |
|---|---|---|---|---|
| > 50% | 🟢 正常 | 无限制 | 可承担中高风险变更 | 正常排期 |
| 20-50% | 🟡 谨慎 | 暂停高风险变更 | 仅低风险变更 | 每迭代 20% 产能用于可靠性 |
| 1-20% | 🟠 冻结 | 冻结全部功能发布 | 仅热修复 | 全部产能投入可靠性改进 |
| 0% | 🔴 违约 | 停止一切非紧急变更 | 仅 P0 安全热修复 | 全员投入可靠性；每新增一次故障 = SLA 违约风险 |

### 策略细则

#### 🟢 预算充足（> 50%）

- **发布**：正常节奏，所有等级变更正常走流程
- **变更风险**：可承担中高风险变更
- **可靠性投入**：迭代产能的 10% 常规维护

#### 🟡 预算紧张（20-50%）

- **发布**：暂停高风险变更；中低风险变更正常
- **变更审查**：中风险变更需 Tech Lead 审批
- **可靠性投入**：每迭代 20% 产能用于可靠性改进
- **通知**：在 #sre-alerts 频道通知团队当前预算状态
- **根因分析**：审查近期预算消耗的主要原因，制定针对性改进

#### 🟠 预算严重不足（1-20%）

- **发布**：冻结所有功能发布。仅允许：
  - 修复导致预算消耗的问题
  - 提高可靠性的变更
  - P0 安全热修复
- **可靠性投入**：停止功能开发，全团队投入可靠性改进
- **每日站会**：每日审查预算消耗趋势和可靠性改进进展
- **管理层通知**：通知工程经理和技术 VP

#### 🔴 预算耗尽（0%）

- **停止一切非紧急变更**
- **全员投入恢复可靠性**
- **每个新事件必须做完整复盘**
- **触发 SLO 审查**：
  - SLO 是否设定不合理（太严格）？
  - 服务是否存在系统性问题需要重建？
  - 是否需要调整架构？

### 预算恢复

预算不会立即恢复——它是在滚动时间窗口内逐步恢复的。

```
30 天滚动窗口的预算恢复：
- 每天恢复约 3.3%（1/30）
- 从预算耗尽恢复到 50% 需要约 15 天（如果没有新故障）
```

在此期间，即使不再发生故障，发布冻结也需要持续。

## 消耗速率告警

### 告警阈值

| 消耗速率 | 含义 | 告警级别 | 剩余时间 | 响应 |
|---|---|---|---|---|
| **14.4x** | 按此速率，1 小时内耗尽预算 | P0 | 1 小时 | 立即响应，启动作战室 |
| **6x** | 按此速率，6 小时内耗尽预算 | P1 | 6 小时 | 紧急排查，暂缓所有新发布 |
| **1x** | 按此速率，月底恰好耗尽 | P2 | 3 天 | 通知团队，降低发布频率 |

### 消耗速率计算

```
消耗速率 = 最近一段时间的错误率 / 整个窗口允许的错误率

示例：
最近 1 小时错误率 = 1.2%（0.012）
30 天允许的错误率 = 0.1%（0.001）
消耗速率 = 0.012 / 0.001 = 12x
→ 触发告警：按此速率，预算将在 30*24/12 = 60 小时内耗尽
```

### Prometheus 告警规则

```yaml
# 错误预算消耗过快告警
- alert: ErrorBudgetBurnRate14x
  expr: |
    (
      rate(http_requests_total{status=~"5.."}[1h]) /
      rate(http_requests_total[1h])
    ) / (1 - 0.999) > 14.4
  for: 5m
  severity: P0
  summary: "错误预算消耗速率 14.4x——1 小时内将耗尽预算"

- alert: ErrorBudgetBurnRate6x
  expr: |
    (
      rate(http_requests_total{status=~"5.."}[6h]) /
      rate(http_requests_total[6h])
    ) / (1 - 0.999) > 6
  for: 15m
  severity: P1
  summary: "错误预算消耗速率 6x——6 小时内将耗尽预算"

- alert: ErrorBudgetExhausted
  expr: |
    (
      rate(http_requests_total{status=~"5.."}[30d]) /
      rate(http_requests_total[30d])
    ) / (1 - 0.999) > 1
  for: 5m
  severity: P0
  summary: "30 天错误预算已耗尽"
```

## YrY 当前错误预算策略

### 起步阶段（当前）

YrY 尚未建立自动化指标采集，错误预算追踪暂时采用**人工方式**：

| 做法 | 说明 |
|---|---|
| **手动计算** | 每月从健康检查日志和事件记录中统计故障时间 |
| **简化为故障分钟数** | 当前不区分可用性/延迟，统一按"服务不可用分钟数"计算 |
| **月度审查** | 每月团队会议上审查故障分钟数 |
| **发布决策** | 月度故障 > 30 分钟 → 下月暂停高风险变更 |

### 目标阶段（Prometheus 上线后）

- 自动化错误预算追踪（Prometheus + Grafana）
- 消耗速率告警
- 按服务、按 SLI 维度的精细化预算
- 发布流水线与错误预算联动

## 常见反模式

| 反模式 | 为何失败 | 正确做法 |
|---|---|---|
| 只定义 SLO 不定错误预算策略 | SLO 只是数字，没有驱动任何决策 | 明确定义每个预算阈值对应的行动 |
| 预算耗尽后人工判断是否冻结发布 | 每次都"这次情况特殊，下次一定严格执行" | 策略自动触发；除非技术 VP 特批，否则不可豁免 |
| 错误预算只用于惩罚 | "又出故障了，这个月预算用完了"——团队开始隐瞒小问题 | 错误预算是中立的度量工具，不用于个人绩效考核 |
| 消耗速率告警不分级 | 所有消耗速率同一个告警级别 | 按 14.4x / 6x / 1x 分级，不同级别不同响应 |
| 不追踪预算消耗趋势 | 不知道预算是在月初消耗的还是月末 | 追踪消耗时间分布；月初大量消耗需要更谨慎的后续策略 |
