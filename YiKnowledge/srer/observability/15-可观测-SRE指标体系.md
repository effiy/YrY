# SRE 指标体系 — 用数据衡量运维效能

> **适用场景**：建立 SRE 团队的量化管理时，或向管理层汇报运维效能时。主观的"系统挺稳定的"无法指导改进；量化的指标可以。

## 为什么 SRE 需要指标体系

SRE 工作有两个特点使指标体系必不可少：
1. **运维工作是隐形的**——系统正常运行时，没人知道 SRE 做了什么；指标让隐性的工作显性化
2. **改进需要方向**——没有指标，你不知道该优化故障发现速度还是修复速度

## 六大核心指标

### 指标全景

| 指标 | 衡量什么 | 方向 | 谷歌 SRE 基准 | 数据来源 |
|---|---|---|---|---|
| **MTTD** | 故障发现速度 | 越短越好 | < 5 分钟 | 告警时间 - 故障开始时间 |
| **MTTR** | 故障恢复速度 | 越短越好 | < 60 分钟 | 恢复时间 - 故障开始时间 |
| **MTBF** | 系统稳定性 | 越长越好 | > 7 天 | 两次故障之间的平均时间 |
| **变更失败率** | 发布质量 | 越低越好 | < 15% | 触发回滚的变更 / 总变更数 |
| **错误预算消耗率** | 可靠性趋势 | 越低越好 | < 100%/窗口 | SLO 追踪 |
| **重复劳动占比** | 运维效率 | 越低越好 | < 50% | 手工操作耗时 / 总工作时间 |

### MTTD — 平均检测时间

```
MTTD = 告警触发时间 - 故障实际开始时间
```

**含义**：从故障发生到 SRE 团队知道故障存在的时间。

| MTTD | 评级 | 典型场景 |
|---|---|---|
| < 1 分钟 | 优秀 | 自动化监控 + 告警 |
| 1-5 分钟 | 良好 | 健康检查轮询（cron 每 5 分钟） |
| 5-15 分钟 | 需改进 | 监控间隔过长 |
| > 15 分钟 | 差 | 依赖用户反馈才发现故障 |

**YrY 当前 MTTD**：依赖人工健康检查（每 5 分钟 cron）或用户反馈 → 估计 5-30 分钟。

**改进方向**：
1. 当前：Cron 每 5 分钟健康检查 → MTTD 约 5-15 分钟
2. 下一步：Prometheus + Alertmanager → MTTD 约 1-2 分钟

### MTTR — 平均恢复时间

```
MTTR = 服务恢复时间 - 故障开始时间
```

**注意**：MTTR 包含检测时间 + 响应时间 + 修复时间。它不是单纯的"修复耗时"。

| MTTR | 评级 | 含义 |
|---|---|---|
| < 15 分钟 | 优秀 | 有 runbook + 熟练的值班人 |
| 15-60 分钟 | 良好 | 有 runbook 但排查需要时间 |
| 1-4 小时 | 需改进 | 复杂故障或缺少 runbook |
| > 4 小时 | 差 | 缺少恢复流程或依赖外部资源 |

**YrY MTTR 估算**（注：目前无正式追踪）：

| 故障类型 | 典型 MTTR | 瓶颈 |
|---|---|---|
| Ollama 不可用 | 5-10 分钟 | 重启 Ollama + 加载模型 |
| MongoDB 不可达 | 10-20 分钟 | 排查连接池 + 重启 MongoDB |
| 磁盘满 | 15-30 分钟 | 清理空间 + 排查写入源 |
| 代码 Bug | 30-120 分钟 | 定位代码 + 热修复 + 部署 |

**改进方向**：为每个常见故障维护 runbook → 见 [Runbook 模板](../incident-response/09-事件-Runbook模板.md)

### MTBF — 平均故障间隔

```
MTBF = 总运行时间 / 故障次数
```

**含义**：系统平均多久出一次问题。MTBF 上升 = 系统更稳定。

**YrY 当前 MTBF**：无正式追踪。建议从今天开始记录每次 P1+ 事件的发生时间，一个月后即可计算基准。

### 变更失败率

```
变更失败率 = 触发回滚或引发事件的变更数 / 总变更数
```

| 变更失败率 | 评级 | 行动 |
|---|---|---|
| < 5% | 优秀 | 保持 |
| 5-15% | 正常 | 关注趋势 |
| 15-25% | 需改进 | 审查高风险变更流程 |
| > 25% | 差 | 暂停发布，修复 CI/测试/审查流程 |

**降低变更失败率的杠杆**：
- 更完善的预发布验证（冒烟测试、集成测试）
- 金丝雀发布 → 见 [金丝雀发布](../release/01-发布-金丝雀发布.md)
- 变更风险分级 → 见 [变更管理流程](../release/06-发布-变更管理流程.md)

### 错误预算消耗率

```
错误预算消耗率 = 窗口内实际消耗 / 窗口总预算
目标：< 100%（整个窗口内）
```

详细策略见 [错误预算策略](./12-可观测-错误预算策略.md)。

### 重复劳动占比

```
重复劳动占比 = 手工重复操作耗时 / 总工作时间
```

**什么是重复劳动**：
- 每次发布都手动执行的相同命令
- 健康检查完全依赖人工执行
- 日志排查每次都手动 `grep`
- 值班交接每次从零写文档

**YrY 当前重复劳动占比估算**：当前自动化程度低 → 估计 > 50%。

详细内容见后续将创建的重复劳动消除指南。

## 指标采集方法

### YrY 当前最小可用方案

在自动化指标系统上线前，使用事件日志手动追踪：

```markdown
## SRE 事件日志 — {{月份}}

| 日期 | 事件 | 级别 | 故障开始 | 告警触发 | 恢复 | MTTD | MTTR | 回滚？ |
|---|---|---|---|---|---|---|---|---|
| 09/12 | Ollama 无响应 | P1 | 14:32 | 14:37 | 14:45 | 5 min | 13 min | 否 |
| 09/18 | MongoDB 连接池耗尽 | P0 | 10:15 | 10:18 | 10:52 | 3 min | 37 min | 否 |
| 09/25 | 配置变更导致 500 | P1 | 16:00 | 16:02 | 16:20 | 2 min | 20 min | 是 |

### 月度汇总
- 事件总数：3（P0: 1, P1: 2）
- 平均 MTTD：3.3 分钟
- 平均 MTTR：23.3 分钟
- 变更总数：8
- 变更失败率：12.5%（1/8）
- 错误预算消耗：估算 X%
```

### 目标状态（Prometheus + Grafana 上线后）

```yaml
# 关键 Prometheus 指标
# MTTD — 使用告警触发时间
alertmanager_alerts_received_total

# MTTR — 使用告警解决时间
alertmanager_alerts_resolved_total

# 变更失败率 — 需要 CI/CD 集成
deployment_total

# 错误预算 — 基于 SLO 计算
error_budget_remaining_ratio
```

```markdown
### 关键发现
- MTTR 改善：新的 MongoDB runbook 使恢复快了 13 分钟
- 重复劳动仍然偏高：每天手工健康检查占约 20 分钟
```

## 如何使用指标

### 指标驱动的决策

| 指标信号 | 决策 |
|---|---|
| MTTD > 15 分钟 | 投资自动化监控和告警 |
| MTTR > 60 分钟 | 完善 runbook；增加演练频率 |
| 变更失败率 > 20% | 暂停高风险发布；审查 CI/测试流程 |
| 错误预算消耗 > 50% | 触发谨慎模式；暂停高风险变更 |
| 重复劳动占比 > 50% | 识别 Top 3 重复任务并自动化 |

### 指标不要用于

| 错误用途 | 为什么错误 | 正确做法 |
|---|---|---|
| 个人绩效考核 | 导致隐瞒事件；MTTR 造假 | 指标用于团队改进，不用于个人考核 |
| 与其他团队横向对比 | 不同服务有不同可靠性要求 | 只与自己历史基线对比 |
| 设定不切实际的目标 | "MTTR 必须 < 5 分钟"——做不到导致作弊 | 基于历史基线设定渐进目标 |
| 只公布不讨论 | 指标变成摆设；无人关注 | 每周团队会议上审查指标趋势 |

## YrY 指标成熟度路线图

| 阶段 | 能力 | 当前状态 |
|---|---|---|
| **L0 — 无追踪** | 事件靠记忆，无从量化 | ← 刚脱离此阶段 |
| **L1 — 人工日志** | 每次事件手动记录到事件日志 | ✅ 本文档建立后开始 |
| **L2 — 基础自动化** | Prometheus 采集关键指标（可用性、延迟） | 目标：下一季度 |
| **L3 — 全面自动化** | 所有指标自动采集 + Grafana 仪表盘 | 目标：下下季度 |
| **L4 — 智能告警** | 指标异常自动告警 + 趋势预测 | 远期 |

## 常见反模式

| 反模式 | 为何失败 | 正确做法 |
|---|---|---|
| 只看可用性不看 MTTR | 系统可用 99.9%，但每次故障恢复要 4 小时——说明恢复流程有问题 | 六大指标并重；MTTR 揭示流程问题 |
| 指标只看不行动 | "这个月 MTTR 又升了"——然后没有任何改进 | 每个恶化的指标必须有对应的改进行动项 |
| 数据不准确仍强行汇报 | 基于不完整的数据做决策 | 标注数据质量（手动 vs 自动采集）；推动自动化采集 |
| MTTR 计算不包含检测时间 | 看起来恢复很快，实际是发现得太慢 | MTTR 计时从故障开始算起，不是从发现算起 |
