# 健康检查设计模式 — 让健康端点真正反映服务状态

> **适用场景**：设计或改进健康检查端点时。好的健康检查告诉正确的受众正确的事情；坏的健康检查让负载均衡器把流量打到已经坏了的服务上。

## 三类健康检查

不是所有"健康"是同一个概念。不同受众需要不同深度的检查：

| 类型 | 问题 | 受众 | 失败时做什么 | 频率 | 超时 |
|---|---|---|---|---|---|
| **存活检查** (Liveness) | 进程是否在运行？ | 进程管理器（systemd/K8s） | 重启服务 | 每 10-30 秒 | 1 秒 |
| **就绪检查** (Readiness) | 服务能否处理请求？ | 负载均衡器 | 停止发送流量 | 每 5-10 秒 | 3 秒 |
| **深度检查** (Health) | 所有依赖是否正常？ | 监控系统/SRE | 触发告警 | 每 30-60 秒 | 10 秒 |

### 为什么需要三种检查

一个真实场景说明三者的区别：

```
存活 √ — uvicorn 进程在运行
就绪 ✗ — 但连接池在初始化中，还不能处理请求
深度 ✗ — MongoDB 不可达，但服务可以返回缓存的错误响应

结果：
- 存活检查通过 → K8s 不重启 Pod（正确）
- 就绪检查失败 → 负载均衡器移除该 Pod（正确——它确实不能处理请求）
- 深度检查失败 → 触发 P0 告警（正确——MongoDB 需要修复）
```

## 检查深度设计

### 存活检查 — 越简单越好

存活检查的唯一目的是告诉进程管理器"我还活着，别杀我"。失败意味着进程已死或死锁。

```python
# YiAi 存活检查端点 — GET /health/liveness
@app.get("/health/liveness")
async def liveness():
    return {"status": "alive"}
```

**原则**：
- 不做外部依赖检查——MongoDB 挂了不该导致 K8s 把你的 Pod 杀光
- 不做耗时操作——1 秒内必须返回
- 不返回复杂数据——是/否就够了

### 就绪检查 — 连接池就绪 + 关键初始化完成

就绪检查告诉负载均衡器"现在可以给我发流量了"。它需要验证服务内部的初始化状态。

```python
# YiAi 就绪检查端点 — GET /health/readiness
@app.get("/health/readiness")
async def readiness():
    checks = {
        "ready": True,
        "mongodb_pool": db.client is not None,  # MongoDB 连接已建立
        "model_loaded": ollama_client.model_loaded,  # Ollama 模型已加载
    }
    all_ready = all(checks.values())
    status_code = 200 if all_ready else 503
    return JSONResponse(content=checks, status_code=status_code)
```

**原则**：
- 启动时不立即可达——给服务 5-15 秒建立连接
- 检查连接池而非单次连接——单次 ping 通过不代表连接池可用
- 失败返回 503 而非 500——503 = 临时不可用（负载均衡器会重试），500 = 内部错误

### 深度健康检查 — 验证所有依赖

深度检查用于监控告警。它验证每个外部依赖的可达性和功能。

```python
# YiAi 深度检查端点 — GET /health/observer（当前已实现）
@app.get("/health/observer")
async def health_observer():
    checks = {
        "status": "ok",
        "mongodb": await check_mongodb(),    # "connected" / "disconnected"
        "ollama": await check_ollama(),      # "available" / "unavailable"
        "rag_index": await check_rag(),      # {"built": True, "num_docs": N}
    }
    # 任一依赖不可用 → 仍然返回 200（这是给监控系统看的，不是给负载均衡器）
    # 告警系统根据返回内容决定是否告警
    return checks

async def check_mongodb():
    try:
        await db.client.admin.command("ping")
        return "connected"
    except Exception:
        return "disconnected"

async def check_ollama():
    try:
        async with httpx.AsyncClient() as client:
            resp = await client.get("http://localhost:11434/api/tags", timeout=5.0)
            return "available" if resp.status_code == 200 else "unavailable"
    except Exception:
        return "unavailable"
```

**原则**：
- 检查所有依赖，但独立报告每个依赖的状态
- 不因为一个依赖挂了就返回 500——监控系统需要完整的依赖状态图
- 超时设置的足够长（5-10 秒）——依赖慢总比误报好
- 失败时返回具体原因（`mongodb: disconnected`），不是泛泛的 `unhealthy`

## YrY 服务健康检查矩阵

| 服务 | 存活 | 就绪 | 深度 | 当前实现 |
|---|---|---|---|---|
| YiAi | `/health/liveness` | `/health/readiness` | `/health/observer` | 仅实现了 `/health/observer` |
| MongoDB | N/A（数据库不提供 HTTP 端点） | — | ping 检查 | 通过 YiAi `/health/observer` 间接检查 |
| Ollama | 进程检查 | 模型加载检查 | `/api/tags` | 通过 YiAi `/health/observer` 间接检查 |
| YiVad | 静态站点 HTTP 200 | 菜单 API 可达 | 菜单 API 返回数据 | 通过浏览器加载检查 |
| YiPet | Service Worker 存活 | API 可达 | 聊天功能可用 | 通过扩展加载检查 |

### 当前缺失的健康检查

| 检查 | 缺失影响 | 建议 |
|---|---|---|
| YiAi 存活检查 | K8s 环境下无法知道该不该重启 Pod | 添加 `GET /health/liveness` → 200 |
| YiAi 就绪检查 | 负载均衡器不知道 Pod 能否接流量 | 添加 `GET /health/readiness` → 200/503 |
| YiVad 健康检查 | 无法自动化验证前端是否可用 | 添加 `GET /health` → 验证菜单 API 可达 |
| 磁盘空间检查 | YiAi 双写可能悄悄填满磁盘 | 在深度检查中加 `disk_usage_pct` |

## 健康检查的调用方

| 调用方 | 检查什么端点 | 频率 | 失败响应 |
|---|---|---|---|
| **systemd** | 存活 | 每 30 秒 | 重启服务 |
| **K8s livenessProbe** | 存活 | 每 10 秒 | 重启 Pod |
| **K8s readinessProbe** | 就绪 | 每 5 秒 | 停止发送流量到该 Pod |
| **Nginx upstream** | 就绪（被动） | 每个请求 | `max_fails` 次失败后暂时移除 |
| **Prometheus** | 深度 | 每 60 秒 | 触发告警规则 |
| **Cron 脚本** | 深度 | 每 5 分钟 | 飞书 Webhook 通知 |

## 健康检查反模式

| 反模式 | 问题 | 修复 |
|---|---|---|
| **存活检查访问数据库** | 数据库挂了 → 存活检查失败 → K8s 重启所有 Pod → 雪崩 | 存活检查只检查进程是否活着，不检查外部依赖 |
| **就绪检查永远返回 200** | 服务启动后立即可达，但实际还不能处理请求 | 启动时返回 503，连接池和关键初始化完成后返回 200 |
| **深度检查失败返回 500** | 监控系统以为是服务问题，实际是依赖问题 | 返回 200 + 详细的状态 JSON，让监控系统自行判断 |
| **健康检查没有超时** | 依赖慢了，健康检查线程卡住，负载均衡器认为服务死了 | 每个检查项独立超时，不互相影响 |
| **就绪和存活检查相同** | K8s 分不清该重启还是该摘流量 | 存活检查极简（进程活着），就绪检查验证内部状态 |
| **健康检查太"重"** | 10 秒超时 + 每秒调用 = 对服务造成额外负载 | 存活/就绪在毫秒级完成；深度检查降低频率 |
