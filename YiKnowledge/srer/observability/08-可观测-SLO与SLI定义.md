# SLO 与 SLI 定义指南

> **适用场景**：为新服务搭建可观测性时，或审查现有可靠性目标时。SLO 是工程工作和用户体验之间的桥梁。

## 核心概念

| 术语 | 定义 | 谁定义 | 实例 |
|---|---|---|---|
| **SLI**（服务水平指标）| 对服务某个方面的量化度量 | SRE / 工程师 | 请求延迟、错误率、可用率 |
| **SLO**（服务水平目标）| 在时间窗口内 SLI 的目标值 | SRE + 产品 | 30 天内 99.9% 的请求在 300ms 内完成 |
| **SLA**（服务水平协议）| 有违约后果的合同性承诺 | 法律 + 商务 | 99.95% 可用率，否则提供服务积分 |
| **错误预算** | SLO 允许的不可靠空间 | SRE | 0.1% 错误预算 = 30 天内允许 43 分钟故障 |

**核心关系**：SLI 是测量值，SLO 是目标值，错误预算是 SLO 允许的"不可靠"额度，SLA 是将 SLO 变成有法律约束力的合同承诺。

### 为什么 SLO 重要

- **量化可靠性**——不再用"系统很稳定"这种模糊描述，而是用数据说话
- **指导决策**——错误预算耗尽时应停止功能开发，优先修复可靠性问题
- **管理期望**——产品团队知道系统能做到什么程度，不会提出不切实际的可靠性要求
- **驱动告警**——告警阈值基于 SLO 设定，而非凭感觉

## SLI 菜单

> 从四大黄金信号开始。在掌握这些之前，不要创建自定义 SLI。

| SLI 类别 | 度量什么 | 适用场景 | 不适用场景 |
|---|---|---|---|
| **延迟** | 请求耗时的 P50、P95、P99 | 面向用户的 API、数据库查询 | 后台异步任务 |
| **可用性** | 成功请求比例（非 5xx）| 任何 HTTP 服务 | 非请求-响应模式的系统 |
| **吞吐量** | 每秒请求数 | 容量规划、自动扩缩 | 用户体验度量 |
| **错误率** | 失败请求比例（5xx）| 可靠性追踪 | 区分业务错误和系统错误 |

### 选择正确的延迟分位数

| 分位数 | 含义 | 使用场景 |
|---|---|---|
| P50 | 典型用户体验 | 判断系统在正常工作条件下的性能 |
| P95 | 包含大多数慢用户的体验 | 日常监控的健康指标 |
| P99 | 最差的可接受体验 | **SLO 应基于此设定**——代表"最差但仍可接受"的体验 |

## 定义 SLO 的六步法

### 第一步：识别关键用户路径

你的服务对用户来说最核心的操作是什么？其他都是次要的。

**示例**：
- YiAi 聊天服务 → "用户发送消息并接收到流式响应"
- YiAi 数据服务 → "用户查询文档并获取结果"
- YiVad 管理后台 → "用户登录并加载菜单"

**不要做什么**：不要为"管理系统配置"这类少数人使用的路径定义 SLO。SLO 只服务于关键用户路径。

### 第二步：为每个路径挑选 1-3 个 SLI

| 服务 | SLI | 度量方式 | 为什么选它 |
|---|---|---|---|
| YiAi 聊天 | 可用性 | `rate(5xx) / rate(all)` | 服务是否可用？ |
| YiAi 聊天 | 延迟 | `histogram_quantile(0.99, request_duration_seconds)` | 响应是否够快？ |
| YiAi 数据 | 可用性 | `rate(5xx) / rate(all)` | 数据操作是否正常？ |
| YiVad SPA | 加载可用性 | 菜单 API 返回 200 的比例 | 关键页面是否可加载？ |

### 第三步：设定 SLO 目标

从保守开始，随时间收紧。一个好的起始 SLO：

| 服务类型 | 可用性 SLO | 延迟 P99 SLO | 说明 |
|---|---|---|---|
| API 接口 | 99.9%（每月 43 分钟故障）| < 500ms | 数据查询类接口 |
| 聊天/流式 | 99.5%（每月 3.6 小时故障）| < 2s | 流式传输天然延迟更大 |
| 静态前端 | 99.95%（每月 21 分钟故障）| < 1s | CDN 边缘节点应有更高可用性 |

### 第四步：定义测量窗口

| 窗口长度 | 适用场景 | YrY 适用 |
|---|---|---|
| 30 天 | 大多数服务的标准滚动窗口 | YiAi 聊天服务 |
| 7 天 | 快速迭代的服务、早期产品 | YiAi 新功能 |
| 90 天 | 成熟稳定的服务、严格合规要求 | 远期目标 |

### 第五步：定义错误预算策略

> 错误预算耗尽时会发生什么？

| 错误预算剩余 | 行动 | 影响 |
|---|---|---|
| > 50% | 正常运作——功能开发继续 | 发布节奏不受限制 |
| 50% — 20% | 谨慎——可靠性优先于功能 | 暂停高风险发布；加强发布审查 |
| < 20% | 冻结功能发布，直到预算恢复 | 所有工程师聚焦可靠性改进 |
| 0%（已耗尽）| 全员投入可靠性；停止所有功能开发 | 每新增一次故障 = SLA 违约风险 |

### 第六步：设置消耗速率告警

| 消耗速率 | 告警触发 | 含义 |
|---|---|---|
| 14.4x | 1 小时后告警 | 严重：按此速度，1 小时耗尽整个预算窗口 |
| 6x | 6 小时后告警 | 警告：按此速度，6 小时耗尽整个预算窗口 |
| 1x | 3 天后告警 | 提示：按此速度，月底耗尽预算 |

## 实例：YiAi 聊天服务 SLO

```yaml
service: yi-ai-chat
slos:
  - sli: availability
    target: 99.9%
    window: 30d
    measurement: rate(5xx) / rate(all_requests)

  - sli: latency_p99
    target: 2000ms
    window: 30d
    measurement: histogram_quantile(0.99, chat_request_duration_ms)

  - sli: sse_first_byte_p99
    target: 500ms
    window: 30d
    measurement: histogram_quantile(0.99, sse_first_byte_ms)

error_budget_policy:
  burn_rate_alerts:
    - rate: 14.4x
      severity: critical
      channel: "#on-call"
    - rate: 6x
      severity: warning
      channel: "#sre-alerts"
```

## 常见反模式

| 反模式 | 为何失败 | 正确做法 |
|---|---|---|
| SLI 太多（每个服务超过 5 个）| 告警疲劳；团队无法聚焦真正重要的事情 | 每个服务 1-3 个 SLI，只关注关键用户路径 |
| SLO 设为 100% | 不可能实现；错误预算永远是 0 | 从 99.9% 开始；持续稳定达成后再收紧 |
| 有 SLO 但没有错误预算策略 | SLO 只是仪表盘上的数字；没有触发任何行动 | 定义每个错误预算阈值对应的具体行动 |
| 直接照搬其他服务的 SLO | 不同服务有不同的用户期望 | 基于自己的关键用户路径定义 SLO |
| SLO 定义后从不调整 | 服务的用户期望和性能基线会随时间变化 | 每季度审查并调整 SLO 目标 |
