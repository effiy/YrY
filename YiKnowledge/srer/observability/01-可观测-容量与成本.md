# 容量与成本监控

> **适用场景**：为任何服务搭建监控时，或基础设施成本增长快于使用量增长时。容量监控回答"系统还有多少余量"，成本监控回答"这些余量花了多少钱"。

## 核心概念

容量监控和成本监控是 SRE 工作中同一枚硬币的两面：

| 维度 | 容量监控 | 成本监控 |
|---|---|---|
| **关注点** | 系统是否会在负载增加时崩溃？ | 当前资源使用是否经济高效？ |
| **关键问题** | "CPU 使用率 70%：什么时候需要扩容？" | "每个聊天请求的成本是上升还是下降？" |
| **告警目的** | 预防资源耗尽导致服务中断 | 预防成本失控；发现资源浪费 |
| **典型受众** | SRE、值班 on-call | SRE、工程经理、财务 |

## 容量监控

### 需要监控的资源

| 资源 | 监控指标 | 为什么重要 | 典型故障模式 |
|---|---|---|---|
| **CPU** | 使用率 %、CPU 限流 | CPU 饱和 = 延迟飙升 | 突发流量导致请求排队 |
| **内存** | 使用率 %、OOM Kill 次数 | 内存耗尽 = 进程崩溃 | 内存泄漏导致渐进式性能下降 |
| **磁盘** | 使用率 %、IOPS、吞吐量 | 磁盘满 = 写入失败；磁盘慢 = 整体变慢 | YiAi 双写文件填满磁盘 |
| **网络** | 带宽、连接数、丢包率 | 网络饱和 = 请求超时 | 大文件下载占用全部带宽 |
| **数据库连接** | 活跃连接数、连接池利用率 | 连接耗尽 = 服务不可用 | MongoDB 连接池达到上限 |
| **GPU** | 显存使用、利用率 % | 显存溢出 = 推理失败 | Ollama 模型占用超过 GPU 可用显存 |

### 告警阈值

| 资源 | 警告阈值 | 严重阈值 | 说明 |
|---|---|---|---|
| CPU | 持续 10 分钟 > 70% | 持续 5 分钟 > 90% | CPU 超过 80% 时响应延迟开始非线性增长 |
| 内存 | 持续 10 分钟 > 80% | 持续 5 分钟 > 95% | 接近 100% 时系统开始使用 swap，性能急剧下降 |
| 磁盘 | > 80% | > 90% | YiAi 双写文件需特别关注；磁盘满导致静默写入失败 |
| 数据库连接 | > 70% 最大连接数 | > 90% 最大连接数 | MongoDB 默认最大连接数为 100 |
| GPU 显存 | > 80% | > 95% | 上下文窗口较大时容易触发 |

**告警阈值设计原则**：
- 警告阈值应给运维人员留出至少数小时的响应时间
- 严重阈值应在资源耗尽前至少 30 分钟触发
- 阈值不是一成不变的——每季度根据实际负载趋势调整

### 容量规划公式

```
扩容触发点：当前使用率 / 总容量 > 0.7
扩容规模：当前使用率 × (1 + 月增长速率 × 采购周期月数)
```

**YrY 实际示例**：YiAi MongoDB 连接数当前为 70/100（使用率 70%）。流量月增长 20%。新资源采购需要 1 个月。

```
1 个月后需要：70 × (1 + 0.2 × 1) = 84 个连接
措施：将最大连接数调整为 150（提供约 6 个月的余量）
```

## 成本监控

### 成本仪表盘

按服务和环境追踪以下维度：

| 成本维度 | YiAi 的计量指标 | 数据来源 |
|---|---|---|
| **计算** | GPU + CPU 服务器成本 | 云服务商账单 / 自建硬件折旧 |
| **数据库** | MongoDB Atlas 套餐费用 | MongoDB Atlas 账单 |
| **存储** | OSS 存储 GB + 请求次数 | OSS 服务商账单 |
| **网络** | 数据传输 GB | 云服务商账单 |
| **合计** | 以上所有维度之和 | 计算汇总 |

### 成本效率指标

| 指标 | 计算公式 | 目标 | 说明 |
|---|---|---|---|
| **每次聊天请求成本** | 总成本 / 聊天请求数 | 跟踪趋势（下降为优） | 反映推理效率 |
| **每次 RAG 查询成本** | RAG 相关成本 / RAG 查询数 | 跟踪趋势 | 反映检索效率 |
| **每位活跃用户成本** | 总成本 / MAU | 跟踪趋势 | 反映系统的规模经济 |
| **空闲资源占比** | (空闲资源成本 / 总成本) × 100 | < 20% | 越高说明浪费越大 |

### YiAi 成本追踪中间件

```python
# 在 YiAi 中追踪每次请求的成本（FastAPI 中间件）
import time

async def cost_tracking_middleware(request, call_next):
    start = time.time()
    response = await call_next(request)
    duration_ms = (time.time() - start) * 1000

    # 记录成本指标
    cost = estimate_cost(request, duration_ms)
    metrics.increment("request_cost_total", cost, tags={
        "endpoint": request.url.path,
        "method": request.method,
    })

    return response

def estimate_cost(request, duration_ms):
    """根据资源使用估算请求成本。"""
    # Ollama GPU：假设 $X/小时 → $X/3600000 每毫秒
    gpu_cost = duration_ms * (GPU_HOURLY_COST / 3_600_000)
    # MongoDB：约 $0.0001 每次查询
    db_cost = 0.0001
    return gpu_cost + db_cost
```

## 常见反模式

| 反模式 | 为何失败 | 正确做法 |
|---|---|---|
| 只监控 CPU 不监控数据库连接 | CPU 正常但数据库连接耗尽，整个应用不可用 | 监控应用依赖的每一项资源 |
| 告警阈值设在 99% | 收到告警时资源已即将耗尽，无时间反应 | 警告阈值设在 70%，严重阈值设在 90% |
| 没有单位成本指标 | 总成本上升，但无法判断是因为增长还是浪费 | 追踪每次请求、每个用户、每次查询的成本 |
| 容量规划只在故障时做 | 被动响应；故障期间手忙脚乱地扩容 | 每月审查容量；规划 3-6 个月的需求 |
| 只看平均值不关注分布 | P50 健康但 P99 已严重超时 | 容量指标同时展示平均值和 P95/P99 |
