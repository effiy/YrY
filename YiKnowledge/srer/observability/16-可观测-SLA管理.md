# SLA 管理 — 从内部目标到外部承诺

> **适用场景**：当 YrY 服务从内部工具转变为对外提供的服务时。SLA 是一份有法律约束力的承诺，写错一个数字可能意味着赔偿。本指南帮助你在正确的时间以正确的方式建立 SLA。

## SLI → SLO → SLA：三层递进

这三个概念常被混淆，但它们回答的是三个完全不同的问题：

| 概念 | 问题 | 受众 | 约束力 | 变更频率 | 示例 |
|---|---|---|---|---|---|
| **SLI** | 实际表现如何？ | SRE 团队 | 无 | 实时变化 | 本月可用性 = 99.95% |
| **SLO** | 目标是什么？ | 工程团队 | 内部目标 | 每季度可调 | 可用性目标 ≥ 99.9% |
| **SLA** | 对客户的承诺是什么？ | 客户/法务 | 合同约束 | 仅在合同续签时调整 | 可用性 ≥ 99.5%，否则赔偿 |

核心规则：**SLO 应比 SLA 更严格**。

```
SLO（内部目标，99.9%）
    │  比 SLA 严格 0.4%
    │  这 0.4% = 错误预算 = 安全缓冲
    ▼
SLA（外部承诺，99.5%）
    │  低于 SLA → 触发违约
```

如果你的 SLO 和 SLA 是同一个数字，那么错误预算为零——每次故障都是 SLA 违约。

## 何时需要 SLA

不是所有服务都需要 SLA。建立 SLA 需要满足以下条件：

| 条件 | 说明 | YrY 当前状态 |
|---|---|---|
| **对外提供服务** | 有外部付费客户 | 尚未——仅内部使用 |
| **有稳定基线** | 至少有 3 个月的 SLO 追踪数据 | 尚未——无自动化指标 |
| **有赔偿能力** | 组织愿意并有能力为违约提供赔偿 | 需评估 |
| **有运维能力** | 7×24 值班、自动化告警、runbook | 建设中 |

**YrY 建议**：当前阶段先建立 SLO（内部目标），积累 3-6 个月稳定性数据后，再根据业务需要决定是否对外承诺 SLA。

## SLA 文档结构

### SLA 标准模板

```markdown
# 服务水平协议 (SLA) — {{服务名}}

**版本**：v{{N}}
**生效日期**：YYYY-MM-DD
**协议方**：{{服务提供方}} 与 {{客户}}

## 1. 服务描述
{{用非技术语言描述服务的核心功能，客户能理解的内容}}

## 2. 服务水平目标

| 指标 | 目标 | 测量窗口 | 测量方法 | 排除情况 |
|---|---|---|---|---|
| **可用性** | ≥ 99.5% | 月度 | (总分钟 - 不可用分钟) / 总分钟 | 计划内维护 |
| **P99 延迟** | < 3 秒 | 月度 | 99%分位请求耗时 | — |
| **支持响应** | < 1 小时 (P0) | 单次 | 从客户报障到首次人工响应 | 非工作时间可延长至 4 小时 |

## 3. 不可用定义

"不可用"指服务完全无法响应客户请求，且持续超过 1 分钟。以下情况不计入不可用：
- 计划内维护（提前 24 小时通知）
- 客户自身网络问题
- 第三方依赖故障（如云服务商区域性故障）
- 不可抗力（自然灾害、战争等）

## 4. 服务信用与赔偿

| 月度可用性 | 服务信用 |
|---|---|
| ≥ 99.5% | 0%（满足 SLA） |
| 99.0% — 99.5% | 10% 月度费用退还 |
| 95.0% — 99.0% | 25% 月度费用退还 |
| < 95.0% | 50% 月度费用退还 |

服务信用以退还费用的方式提供，不可兑换现金。客户须在违约发生后 30 天内申请。

## 5. 报告与审计

- 提供方每月 5 日前公布上月 SLA 报告
- 客户可在收到报告后 14 天内提出质疑
- 提供方保留年度第三方审计的权利

## 6. 协议变更

- 变更需提前 30 天通知
- 重大变更（降低服务目标）客户可无责终止合同
```

### SLA 中常见的"排除情况"

每个排除情况都降低了你的 SLA 风险暴露：

| 排除 | 原因 | 示例 |
|---|---|---|
| **计划内维护** | 你不能 24/7 永远在线——维护是必要的 | 提前 24 小时通知的维护窗口 |
| **客户导致** | 客户自己的配置、代码或网络问题 | 客户防火墙误封你的 IP |
| **第三方故障** | 你无法控制的底层基础设施 | 云服务商区域性故障 |
| **不可抗力** | 超出合理控制范围的事件 | 自然灾害、战争、大规模 DDoS |
| **测试/预发布环境** | 非生产环境不应受 SLA 约束 | 预发布环境因实验性变更不可用 |

## SLA 违约处理流程

### 当 SLA 违约发生时

```
SLA 违约被确认
    │
    ├─ 1. 内部确认（4 小时内）
    │    SRE 团队确认违约是否成立
    │    检查：是否在排除范围内？测量方法是否正确？
    │
    ├─ 2. 客户通知（8 小时内）
    │    主动告知客户 SLA 违约已发生
    │    不要等客户来问——主动通知体现诚信
    │
    ├─ 3. 根因分析与修复（24-48 小时）
    │    使用事后复盘流程分析根因
    │    制定预防措施
    │
    ├─ 4. 赔偿执行（下次账单中体现）
    │    按 SLA 约定计算服务信用
    │    在账单中明确标注
    │
    └─ 5. 复盘与改进（1 周内）
        审查：SLO 是否够严格？告警是否够灵敏？
        调整 SLO 或加强预防措施
```

## SLA 与 SLO 的协调

当有 SLA 时，SLO 的设定必须服从 SLA 的约束：

```
如果你的 SLA 可用性是 99.5%（月度允许 216 分钟故障）

错误预算分配：
├─ SLO 缓冲（99.9% → 99.5% 的差值）：173 分钟
│   用于：功能发布风险、非关键变更
│
└─ SLA 底线（低于 99.5%）：43 分钟
    用于：仅紧急热修复和关键安全补丁
    低于此线 = SLA 违约 = 赔偿
```

这个分层确保 SLA 违约之前，团队有充足的错误预算进行正常的发布活动。

## 常见陷阱

| 陷阱 | 后果 | 预防 |
|---|---|---|
| SLO = SLA（无缓冲） | 每次故障都是违约，无错误预算可用 | SLO 至少比 SLA 严格 0.3-0.5% |
| 可用性定义过于简单 | "返回 200 就算可用"——实际用户无法完成操作 | 用关键用户路径的成功率定义可用性，而非 HTTP 状态码 |
| 赔偿上限缺失 | 一次重大故障的赔偿足以让公司破产 | SLA 中明确"月度赔偿上限 = 100% 月度费用" |
| 口头 SLA | "我们口头承诺了 99.9%"——发生争议时无据可依 | SLA 必须是书面文档，双方签字 |
| SLA 只定义没有追踪 | 违约了都不知道 | 每月 5 日前出 SLA 报告，自动化追踪 |
