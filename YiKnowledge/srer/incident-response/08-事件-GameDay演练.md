# Game Day 演练 — 通过受控故障提升系统韧性

> **适用场景**：每季度一次，在非业务高峰期执行。Game Day 的核心思想是：与其等待故障在凌晨 3 点找上门，不如在受控条件下主动制造故障，检验系统的韧性。

## 什么是 Game Day

Game Day 是一次计划内的韧性演练——团队在受控条件下向系统注入故障，观察系统如何响应，记录暴露的薄弱点，并在真实故障发生前修复它们。

它与回滚演练的区别：

| 维度 | 回滚演练 | Game Day |
|---|---|---|
| **目标** | 验证回滚流程可行 | 发现系统未知的薄弱点 |
| **范围** | 单个服务的部署回退 | 跨服务的故障传播和恢复 |
| **频率** | 每月 | 每季度 |
| **注入方式** | 部署一个有问题的版本然后回滚 | 注入特定故障（断网、CPU 满载、磁盘满等） |
| **预期结果** | 回滚成功 | 暴露出需要修复的问题 |

## 演练场景库

### YrY 环境适用的故障注入场景

| # | 场景 | 注入方式 | 难度 | 影响范围 |
|---|---|---|---|---|
| 1 | **MongoDB 不可达** | `brew services stop mongodb-community` | 低 | YiAi 数据操作全部失败 |
| 2 | **Ollama 不可用** | `ollama stop` 或防火墙阻断 11434 端口 | 低 | 聊天功能不可用，数据 CRUD 正常 |
| 3 | **磁盘空间耗尽** | `dd if=/dev/zero of=/tmp/fill bs=1M count=1000` | 中 | YiAi 双写失败 |
| 4 | **CPU 满载** | `stress --cpu 4 --timeout 300s` | 中 | 所有服务响应变慢 |
| 5 | **网络延迟注入** | `tc qdisc add dev eth0 root netem delay 500ms` | 高 | 跨服务调用超时 |

### 场景选择原则

- **第一次 Game Day**：从场景 1 或 2 开始（影响可控、恢复简单）
- **团队经验丰富后**：组合场景（如 MongoDB 不可达 + Ollama 不可达同时发生）
- **每次只注入一个故障**：否则无法确定是哪个故障触发了哪个行为

## Game Day 生命周期

### 阶段一：规划（演练前 1 周）

**确定范围**：
- 本次演练涉及哪些服务？（建议每次只覆盖 1-2 个服务）
- 在什么环境进行？（首次在预发布环境，验证通过后可上生产）
- 故障注入的具体方式和参数是什么？

**定义成功标准**：
- 监控系统是否在 X 分钟内检测到故障？
- 告警是否在 Y 分钟内触达值班人？
- 值班人是否在 Z 分钟内启动了正确的响应流程？
- 服务是否按预期降级（而非崩溃）？

**爆炸半径控制**：
- 故障只影响预发布环境或特定比例的生产流量
- 设定硬性终止条件（如错误率超过 X% 持续 Y 分钟 → 立即停止演练）
- 准备即时回滚方案（如何快速撤销注入的故障）

### 阶段二：执行（演练当天，约 2 小时）

```markdown
| 时间 | 环节 | 内容 | 负责人 |
|---|---|---|---|
| 14:00-14:15 | 就位确认 | 所有参与者在线；监控仪表盘就绪；终止条件已确认 | 组织者 |
| 14:15-14:20 | 故障注入 | 执行故障注入命令 | 注入者 |
| 14:20-14:50 | 观察与响应 | 观察系统行为；值班人按流程响应；记录员记录时间线 | 全体 |
| 14:50-15:00 | 故障撤销 | 撤销注入的故障；验证系统恢复正常 | 注入者 |
| 15:00-15:30 | 即时复盘 | 讨论发现的问题；记录改进项 | 全体 |
```

**角色分配**：

| 角色 | 职责 | 关键约束 |
|---|---|---|
| **组织者** | 设计场景、控制节奏、拥有终止权 | 不参与具体响应 |
| **注入者** | 执行和撤销故障注入 | 确保能随时一键撤销 |
| **响应者** | 作为值班人响应故障 | 不知道故障是注入的（首次演练）或知道但按真实流程响应 |
| **观察者** | 记录时间线、监控指标、观察响应行为 | 不干预响应过程 |

### 阶段三：复盘（演练后 1 周内）

复盘围绕以下问题展开：

```markdown
## 检测
- 监控系统在故障注入后多久检测到异常？
- 告警是否正确触发？
- 有没有应该告警但没有告警的情况？

## 响应
- 值班人的第一步操作是否正确？
- 有没有查阅 runbook？runbook 的内容是否准确？
- 故障定级是否正确？

## 降级
- 系统的降级行为是否符合预期？
- 非关键功能是否被正确降级，保护了关键路径？
- 有没有级联故障？（一个故障引发了另一个故障）

## 恢复
- 故障撤销后系统多久完全恢复？
- 有没有残留问题？（连接池未释放、缓存未刷新等）
```

### 阶段四：行动项追踪

Game Day 暴露的每个问题必须转化为行动项：

| # | 发现 | 严重度 | 行动项 | 负责人 | 截止时间 |
|---|---|---|---|---|---|
| 1 | Ollama 不可用时，聊天接口返回 500 而非降级提示 | 高 | 修改错误处理，返回明确的降级信息 | — | — |
| 2 | 磁盘空间告警缺失 | 中 | 添加磁盘使用率告警规则 | — | — |

## YrY 首次 Game Day 推荐方案

### 场景：Ollama 服务不可用

**难度**：低 | **时长**：1 小时 | **参与人**：2-3 人

**步骤**：
1. 确认 YiAi 和监控仪表盘正常运行
2. 执行 `ollama stop` 或在 config 中将 Ollama host 指向不存在地址
3. 观察 YiAi 的行为：聊天请求返回什么？健康检查端点显示什么？
4. 确认降级行为是否符合预期
5. 恢复 Ollama 服务
6. 验证系统完全恢复

**预期观察点**：
- YiAi `/health/observer` 应显示 `ollama: unavailable`
- 聊天请求应返回明确的错误码（2001）而非 500
- 数据 CRUD 操作不受影响
- 如果配置了告警，应在 Ollama 不可用后告警

## 爆炸半径控制

| 措施 | 说明 |
|---|---|
| **预发布优先** | 首次执行任何场景都在预发布环境 |
| **硬性终止条件** | 故障持续超过 30 分钟、影响真实用户、出现数据损坏 → 立即终止 |
| **一键撤销** | 每个故障注入命令都有对应的撤销命令，演练前验证撤销命令可用 |
| **避开业务高峰** | 选择周末或工作日晚间进行 |
| **提前通知** | 有真实用户的系统，提前通知可能受影响的团队 |

## 常见反模式

| 反模式 | 为何失败 | 正确做法 |
|---|---|---|
| 没有终止条件就开始 | 故障失控时不知何时该停 | 提前定义硬性终止条件并取得全体参与者确认 |
| 只注入预期中的故障 | 真正的故障往往是意料之外的 | 逐步增加注入的随机性和组合复杂度 |
| 发现了问题但无行动项 | Game Day 变成一场表演，没有实际产出 | 每个发现的问题都必须有对应的行动项 |
| 响应者提前知道所有故障细节 | 无法检验真实的响应能力 | 首次演练可以预知，后续演练逐步减少预知信息 |
| 每年只做一次 | 系统持续变化，去年的薄弱点不代表今年的薄弱点 | 每季度一次；系统有重大变更后增加一次 |
