# 处理值班轮班

> **适用场景**：每次 on-call 值班开始前翻阅此文档。结构化值班流程可防止漏掉告警、上下文过时和交接遗漏。

## 值班工程师的核心职责

值班期间，on-call 工程师是系统可靠性的第一道防线。主要职责包括：

| 职责 | 说明 | 时限要求 |
|---|---|---|
| **告警响应** | 接收并确认所有告警通知 | 5 分钟内确认 |
| **故障定级** | 按照严重程度判定标准确定事件等级 | 确认告警后 10 分钟内 |
| **故障处理** | 执行事件响应流程，恢复服务 | 按严重程度响应时限 |
| **沟通协调** | 在 `#incidents` 频道发布状态更新 | 每 30 分钟一次更新 |
| **交接准备** | 准备值班交接文档 | 轮班结束前完成 |

## 阶段一：值班开始（前 30 分钟）

### 系统访问检查

值班前必须确认以下系统可正常访问。这看似基础，却是最常见的值班失败模式——在事件发生时才发现无法登录。

- [ ] 能访问所有监控仪表盘：Grafana、MongoDB Atlas 控制台、服务器日志
- [ ] 能访问事件管理工具（如飞书多维表格 / Jira）
- [ ] 能访问所有 runbook 和文档（本知识库、YiAi/YiVad/YiPet 的 CLAUDE.md）
- [ ] 告警通道工作正常：`#on-call`、`#incidents` 群聊可接收消息
- [ ] 手机/Pager 正常接收告警通知，铃声已开启

### 上下文加载

- [ ] 阅读上一班次的交接文档
- [ ] 审查所有进行中的事件及其当前状态
- [ ] 查看部署日历，了解值班期间是否有计划变更
- [ ] 检查关键服务的错误预算剩余情况
- [ ] 确认所有未处理的告警

### 值班开始通知

- [ ] 在 `#on-call` 频道发送值班开始消息
- [ ] 确认联系方式（手机号、飞书/微信）已更新
- [ ] 确认升级路径：谁是今天的备份值班人？

```
值班开始通知模板：
"本周 on-call 值班开始：{{姓名}}
 值班时间：{{开始日期}} — {{结束日期}}
 联系方式：{{手机}} / {{飞书}}
 备份值班：{{备份值班人姓名}}"
```

## 阶段二：值班进行中

### 每日例行检查

| 时间 | 检查项 | 具体操作 |
|---|---|---|
| 上班时 | 检查仪表盘 | 夜间是否有异常？CPU/内存/磁盘/数据库连接是否正常？ |
| 上午 | 审查进行中的事件 | 是否有事件需要升级？是否需要协调资源？ |
| 中午后 | 检查部署流水线 | 是否有卡住的部署？是否有人计划今天发布？ |
| 下班前 | 告警快扫 | 检查所有未处理告警，确认无遗漏 |

### 收到告警时的处理流程

1. **确认**（5 分钟内）——在告警通道中确认收到，停止重复通知
2. **定级**（10 分钟内）——这是真实故障还是噪音？
3. **响应**——按照 [响应事件](./04-事件-响应事件.md) 流程处理
4. **通报**——在 `#incidents` 频道发布事件状态更新
5. **记录**——在事件工单中实时更新进展

### 何时升级

| 场景 | 升级对象 | 触发条件 |
|---|---|---|
| 事件超出个人专业能力 | 备份值班 | 10 分钟内无法定位根因 |
| 事件 30 分钟未解决 | 工程经理 | 任何级别事件超过 30 分钟 |
| 安全事件 | 安全值班 + 安全负责人 | 确认或高度怀疑安全事件 |
| 数据丢失或损坏 | DBA + 工程总监 | 任何数据库写入异常 |
| 用户面故障超过 1 小时 | 技术 VP | 用户可见的服务中断 |

### 自我关怀

- **定时休息**——疲劳的值班工程师更容易做出错误决策
- 如果单次事件处理超过 2 小时，呼叫备份值班人接手
- 不要在值班期间独自进行高风险变更——始终需要双人检查

## 阶段三：值班结束

### 交接前检查清单

- [ ] 所有事件已解决或已升级
- [ ] 所有事件工单已更新为最新状态
- [ ] 所有临时修复方案（workaround）已记录到 runbook
- [ ] 无过时告警（所有告警已确认）
- [ ] 交接文档已撰写（参照 [值班交接](./03-事件-值班交接.md) 模板）

### 交接通话（15-20 分钟）

1. 向接班的 on-call 逐项讲解交接文档
2. 重点说明未解决的问题和即将面临的风险
3. 回答接班人的问题
4. 双方确认交接完成

### 值班结束后

- [ ] 在 `#on-call` 频道发送值班结束消息
- [ ] 确认 Pager 已静音（如非自动切换）
- [ ] 记录值班期间发现的流程改进点

## 常见反模式

| 反模式 | 为何失败 | 正确做法 |
|---|---|---|
| 跳过系统访问检查 | 事件发生时才发现无法登录，延误响应 | 值班开始时逐一验证所有系统可访问 |
| 不读交接文档 | 对进行中的事件毫无了解，踩坑 | 值班开始前必须读完交接文档 |
| "英雄模式"——从不升级 | 个人疲劳 + 单点故障风险；事故扩大时无人知道 | 尽早升级；升级不是能力不足的标志，而是良好判断力的体现 |
| 值班期间进行高风险变更 | "修复"引发新故障，事件叠加恶化 | 任何变更都需要双人检查；非紧急变更推迟到值班结束后 |
| 值班期间不写事件记录 | 交接时只能凭记忆描述，遗漏关键信息 | 事件工单实时更新；每个操作都记录时间戳和执行人 |
