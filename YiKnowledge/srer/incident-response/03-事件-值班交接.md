# 值班交接流程

> **适用场景**：每次 on-call 值班结束时执行。结构化的交接确保接班工程师拥有有效响应所需的一切信息。

## 交接的价值

值班交接是 SRE 运维中信息传递的关键环节。良好的交接可以：

- **避免信息断层**——接班人对进行中的事件一无所知，是大多数响应延迟的根因
- **降低新人上手成本**——值班工程师轮换频繁时，交接文档是最重要的上下文来源
- **积累团队知识**——交接文档是事件响应模式演化的活档案

## 交接频率与渠道

- **频率**：每个轮班周期结束时（每周或双周，取决于轮换设置）
- **渠道**：专用 `#on-call` 频道 + 交接文档（飞书文档 / Notion / Markdown）
- **时长**：15-30 分钟同步交接通话
- **参与人**：交班 on-call + 接班 on-call（必须两者同时参与）

## 交班前检查清单

交接前，交班 on-call 必须完成：

- [ ] 所有进行中的事件已解决或已升级
- [ ] 所有事件工单已更新为最新状态
- [ ] 值班期间应用的临时修复方案（workaround）已记录
- [ ] 所有告警已确认（无过期未处理告警）
- [ ] runbook 中已更新任何新发现（新的故障模式、新的恢复步骤）
- [ ] 交接文档已准备完成（使用下方模板）
- [ ] 已检查部署日历中接班期间的变更计划

## 交接通话流程

1. **交班人逐项讲解交接文档**（约 10 分钟）——先讲进行中的事件，再讲已知问题，最后讲待处理事项
2. **接班人提问**（约 5 分钟）——澄清不清楚的地方，询问边界情况
3. **双方确认交接**——交班人正式退出值班状态，接班人正式承担值班责任

## 接班后的操作

- [ ] 验证所有系统访问权限（仪表盘、runbook、事件管理系统）
- [ ] 确认所有未处理告警
- [ ] 审查过去 24 小时的告警历史
- [ ] 确认联系方式在值班轮换表中已更新
- [ ] 在 `#on-call` 发送接班确认消息

## 常见反模式

| 反模式 | 为何失败 | 正确做法 |
|---|---|---|
| "没出事，不需要交接" | 接班人零上下文；无法察觉细微异常 | 即使值班安静无事件，也必须执行交接。安静值班同样需要说明"一切正常"的原因 |
| 纯口头交接（无文档） | 信息丢失；接班人无法异步参考 | 通话前务必写好交接文档；文档是异步参考的唯一可靠来源 |
| 交接文档 5 分钟临时赶工 | 仓促、不完整，遗漏重要上下文 | 值班期间随时更新文档中的关键事件；交接时只需收尾润色 |
| 没有"计划变更"栏目 | 接班人不知道值班期间有部署计划，被打个措手不及 | 交接前检查部署日历，纳入交接文档 |
| 交班人未确认接班人已理解 | 看似交接了，实际接班人对关键问题一知半解 | 通话结束前请接班人用自己的话复述关键事件和风险点 |
