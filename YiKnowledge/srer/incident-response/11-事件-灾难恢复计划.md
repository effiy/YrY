# 灾难恢复计划 — 当最坏情况发生时

> **适用场景**：灾难性故障发生时——数据丢失、服务器物理损坏、关键服务全面瘫痪。这不是日常事件响应，而是"从零重建"级别的恢复。

## 什么是灾难恢复

灾难恢复（DR）与事件响应的区别在于规模：

| 维度 | 事件响应 | 灾难恢复 |
|---|---|---|
| **范围** | 单个服务或依赖故障 | 整个环境或多服务全面瘫痪 |
| **目标** | 恢复特定服务 | 重建可用的最小系统 |
| **时间** | 分钟到小时 | 小时到天 |
| **触发** | 告警 | 确认环境级别灾难 |
| **优先级** | 恢复受影响的功能 | 先恢复核心功能，再逐步恢复其他 |

## 灾难场景分级

| 级别 | 场景 | 恢复时间目标 | 恢复策略 | 触发条件 |
|---|---|---|---|---|
| **L1 — 轻度** | 单服务数据损坏、配置错误导致服务不可用 | < 4 小时 | 从备份恢复单服务 | MongoDB 单集合损坏 |
| **L2 — 中度** | 服务器崩溃、磁盘损坏、主机不可用 | < 12 小时 | 在新主机上重建环境 + 恢复备份 | 宿主机硬件故障 |
| **L3 — 重度** | 数据中心故障、云服务区域故障 | < 24 小时 | 切换到备用环境或重建 | 机房断电/断网超过 4 小时 |
| **L4 — 灾难** | 数据完全丢失、所有备份失效 | < 72 小时 | 从零重建 + 最小数据恢复 | 备份和主数据同时丢失 |

**YrY 当前实际 RTO**：由于无灾备环境，L2+ 场景的实际恢复时间 = 从零搭建的时间（约 4-8 小时）+ 备份恢复时间。

## 灾难恢复优先级

不是所有服务都同等重要。恢复顺序由业务影响决定：

### YrY 服务恢复优先级

| 优先级 | 服务 | 原因 | 依赖 |
|---|---|---|---|
| **P0 — 最先恢复** | MongoDB | 所有数据的持久化层 | 无 |
| **P0 — 最先恢复** | YiAi API | 所有前端的唯一后端 | MongoDB |
| **P1 — 随后恢复** | YiVad SPA | 主要管理界面 | YiAi |
| **P2 — 最后恢复** | YiPet 扩展 | 用户自行安装，非服务端控制 | YiAi |
| **P3 — 可延迟** | Ollama 模型 | AI 功能；数据 CRUD 不受影响 | GPU 硬件 |
| **P3 — 可延迟** | RAG 索引 | 可从 YiKnowledge 重建 | YiKnowledge 文件 |

### 最小可运行系统

在 L3/L4 场景下，首要目标是恢复**最小可运行系统**——只包含 P0 + P1 服务：

```
最小可运行系统 = MongoDB + YiAi API + YiVad SPA
目标：用户能登录、能查询数据
非目标：聊天功能、RAG 增强、扩展
```

## L1 恢复流程 — 单服务数据损坏

### 场景：MongoDB 中 sessions 集合意外清空

**恢复步骤**：

1. **隔离**（5 分钟）——停止 YiAi（防止写入覆盖备份点）
2. **确认备份**（2 分钟）——检查最近备份文件是否可用
   ```bash
   ls -lh /opt/backups/mongodb/latest_backup.txt
   cat /opt/backups/mongodb/latest_backup.txt
   ```
3. **恢复**（15 分钟）——恢复受影响的集合
   ```bash
   mongorestore --uri="mongodb://localhost:27017" \
     --db=yry --collection=sessions --drop \
     /tmp/mongo-restore/yry/sessions.bson
   ```
4. **验证**（5 分钟）——确认文档数恢复
   ```bash
   mongosh --eval "use yry; db.sessions.countDocuments()"
   ```
5. **重启 YiAi**（2 分钟）并验证
6. **事后复盘**（24 小时内）

## L2 恢复流程 — 服务器不可用

### 场景：运行 YiAi 的服务器硬件故障，需要迁移到新机器

**前置条件**：备份文件存储在外部位置（OSS/另一台机器），而非故障服务器本地。

**恢复步骤**：

1. **确认故障**（10 分钟）——服务器是否可远程访问？硬件状态？
2. **准备新环境**（2 小时）
   ```bash
   # 在新机器上安装依赖
   # Python 3.12, MongoDB 7, Ollama, Nginx
   
   # 克隆代码
   git clone <repo-url> /opt/yry
   cd /opt/yry/YiAi
   pip install -r requirements.txt
   ```
3. **恢复 MongoDB 数据**（30 分钟）
   ```bash
   # 从 OSS 下载最近备份
   # 恢复全部数据库
   mongorestore --uri="mongodb://localhost:27017" /path/to/backup/
   ```
4. **恢复配置文件**（15 分钟）
   - `YiAi/config.yaml` — 从 Git 获取
   - SSL 证书 — 重新申请或从安全存储获取
   - 环境变量 — 重新配置
5. **拉取 Ollama 模型**（30-60 分钟，取决于模型大小和网络）
   ```bash
   ollama pull qwen3.5:7b-q4_K_M
   ```
6. **启动 YiAi 并验证**（15 分钟）
7. **切换 DNS/负载均衡** 指向新服务器（取决于 DNS TTL）
8. **启动 YiVad 前端**（如也在同一服务器上）
9. **通知用户** 系统已恢复

**总预计时间**：4-6 小时（模型下载时间占大头）。

## L3 恢复流程 — 从零重建

在极端情况下（无服务器、无备份立即可用），按以下步骤从零重建：

### 重建 Makefile（预先准备好）

```bash
#!/bin/bash
# /opt/yry/scripts/disaster-recovery-rebuild.sh
# 从零重建 YrY 环境 — L3 灾难恢复脚本

set -e

echo "=== YrY 灾难恢复 — 从零重建 ==="

# 1. 安装基础依赖
echo "[1/8] 安装基础依赖..."
# macOS
brew install python@3.12 mongodb-community nginx
# Linux
# apt-get install python3.12 mongodb-7 nginx

# 2. 克隆代码
echo "[2/8] 克隆代码..."
git clone <REPO_URL> /opt/yry
cd /opt/yry/YiAi
pip install -r requirements.txt

# 3. 恢复配置
echo "[3/8] 恢复配置..."
# 从安全存储或 Git 获取 config.yaml

# 4. 启动 MongoDB
echo "[4/8] 启动 MongoDB..."
brew services start mongodb-community

# 5. 恢复数据（从最可靠的备份源）
echo "[5/8] 恢复数据..."
# 从 OSS/S3/异地备份下载最近的备份文件
# mongorestore --uri="mongodb://localhost:27017" /path/to/backup/

# 6. 安装 Ollama 并拉取模型
echo "[6/8] 安装 Ollama 并拉取模型..."
# 安装 Ollama
ollama pull qwen3.5:7b-q4_K_M

# 7. 启动 YiAi
echo "[7/8] 启动 YiAi..."
python main.py &
sleep 5
curl http://localhost:10086/health/observer

# 8. 构建并部署 YiVad
echo "[8/8] 构建 YiVad..."
cd /opt/yry/YiVad
pnpm install
pnpm build:pro

echo "=== 恢复完成 ==="
```

## 备份依赖清单

灾难恢复依赖以下资源。每一项缺失都会增加恢复时间：

| 资源 | 存储位置 | 缺失时的后果 | 恢复方式 |
|---|---|---|---|
| **Git 仓库** | GitHub/GitLab | 无法获取当前代码 | 从本地 clone 或另一台机器获取 |
| **MongoDB 备份** | `/opt/backups/mongodb/` + OSS 异地 | 数据丢失 | 从 OSS 异地备份恢复 |
| **Ollama 模型** | `/root/.ollama/` | 需重新下载（30-60 分钟） | 重新下载或从模型备份恢复 |
| **SSL 证书** | `/etc/ssl/` | HTTPS 不可用 | 重新申请或从安全存储获取 |
| **config.yaml** | Git 仓库 | 服务无法启动 | 从 Git 获取（不含密钥） |
| **环境变量/密钥** | 安全存储/密码管理器 | MongoDB 和 API 认证失败 | 从安全存储获取 |
| **YiKnowledge 文件** | Git 仓库 | RAG 索引为空 | Git clone 即可恢复 |

## 灾难恢复演练

### 演练级别

| 级别 | 内容 | 频率 | 参与人 |
|---|---|---|---|
| **桌面推演** | 团队围坐，口头走过灾难恢复步骤 | 每季度 | SRE 团队 |
| **部分实战** | 从备份恢复单个服务（如仅恢复 MongoDB） | 每半年 | SRE + 1 名工程师 |
| **全栈实战** | 在新环境中从零重建整个 YrY 系统 | 每年 | 全体 SRE |

### 全栈实战演练步骤

1. **提前准备**：租用一台临时云服务器（或使用本地另一台机器）
2. **执行恢复脚本**：运行 `disaster-recovery-rebuild.sh`
3. **计时**：从执行脚本到 YiVad 可正常登录的总时长
4. **验证**：
   - [ ] YiAi 健康检查通过
   - [ ] YiVad 可登录，菜单正常加载
   - [ ] 聊天功能可用（Ollama 模型加载完成）
   - [ ] 历史数据可查询（备份恢复验证）
5. **复盘**：记录恢复过程中遇到的障碍和脚本错误
6. **更新**：根据演练发现更新本恢复计划和脚本

## YrY 灾备能力现状

| 能力 | 当前状态 | 差距 | 优先级 |
|---|---|---|---|
| **备份可用** | mongodump 每日备份到本地 | 无异地备份 | 高——添加 OSS 异地备份 |
| **恢复脚本** | 本文档中的手动步骤 | 无自动化恢复脚本 | 中——完善并测试脚本 |
| **备用环境** | 无 | 无可切换的备用环境 | 低——当前单机部署，不需要 |
| **演练** | 无 | 从未执行过全栈恢复 | 中——安排首次桌面推演 |
| **RTO 承诺** | 无正式定义 | 无对用户的恢复时间承诺 | 低——当前面向内部，不对外承诺 |

## 常见反模式

| 反模式 | 为何失败 | 正确做法 |
|---|---|---|
| 备份和主数据在同一台物理机上 | 服务器硬件故障 = 备份和数据同时丢失 | 备份至少存到一台不同的机器或 OSS |
| 恢复脚本从未被执行过 | 灾难发生时发现脚本中某个命令已失效 | 每半年执行一次部分实战演练 |
| 只备份数据库不备份配置 | 数据库恢复了但 config.yaml 丢了，服务起不来 | 配置和密钥同样需要纳入备份计划 |
| DR 计划只存在某人脑子里 | 那个人的脑子在灾难发生时恰好不在 | DR 计划写成文档，定期演练，多人掌握 |
| 恢复顺序不考虑依赖 | 先恢复 YiVad 再恢复 YiAi——YiVad 没有后端可用 | 按依赖关系倒序恢复：数据库 → 后端 → 前端 |
