# 事后复盘：MongoDB 连接池耗尽导致 YiAi 服务中断

> **注意**：本文是基于 YrY 典型故障模式编写的**示例复盘**，用于展示高质量复盘的格式和深度。事件细节为合理虚构，但根因和修复方案适用于 YrY 实际环境。

## 四、根因分析（5-Why）

1. **为什么** YiAi 返回 5xx 错误？
   → MongoDB 连接池 100 个连接全部被占用，新请求无法获取连接

2. **为什么** 连接池会满载？
   → 部分查询耗时超过 20 秒，持有连接不放。高并发下连接被逐渐占满

3. **为什么** 会有超过 20 秒的慢查询？
   → `sessions` 集合的 `created_at` 字段缺少索引，查询历史会话时需要全表扫描。sessions 集合已积累 50 万条记录，全表扫描耗时 20-40 秒

4. **为什么** 缺少索引没有被提前发现？
   → 数据库巡检不包含索引覆盖检查；慢查询没有被监控；MongoDB 的 `system.profile` 未开启

5. **为什么** 慢查询监控和索引巡检没有被建立？
   → 可观测性搭建时遗漏了数据库层面的指标；新集合创建时没有索引审查环节

**系统性根因**：数据库运维缺乏两项基础能力——（1）慢查询监控，（2）索引覆盖审查。这两个缺失共同导致了"索引缺失→慢查询→连接池耗尽→服务中断"的故障链。

## 五、缓解与修复

| 措施 | 类型 | 状态 |
|---|---|---|
| `db.sessions.createIndex({created_at: 1})` | 永久修复 | ✅ 已完成 |
| `db.sessions.createIndex({key: 1})` — 高频查询字段 | 预防加强 | ✅ 已完成 |
| 开启 MongoDB profiler：`db.setProfilingLevel(1, {slowms: 100})` | 监控改进 | ✅ 已完成 |
| 添加 MongoDB 慢查询告警规则 | 监控改进 | 🔄 进行中 |
| 审查所有集合的索引覆盖情况 | 预防措施 | ⬜ 待安排 |

## 六、经验教训

### 做得好的

- 用户报障后 3 分钟内 on-call 确认告警并接管
- 第一次重启恢复了服务（虽然只是临时缓解）
- 没有止步于"重启就好了"——持续监控发现了连接数再次攀升，推动了根因定位

### 需要改进的

- **首次修复只治标**：重启释放了连接池，但没有追问为什么连接池会满载。如果 15:02 宣布解决后就停止关注，连接会在 30 分钟内再次耗尽
- **排查效率偏低**：从发现连接池满（14:45）到定位慢查询（15:12）用了 27 分钟——值班人对 MongoDB 诊断命令不够熟悉
- **缺少数据库层面监控**：如果有慢查询告警，这个问题会在变成 P0 之前就被发现

### 意外发现

- sessions 集合已增长到 50 万条记录——半年前才 5 万条。增长速度超出预期，但容量规划没有反映这个变化
- MongoDB 默认连接池大小（100）在当前并发下偏紧——留 20% 余量的话，实际可用只有 80 个
