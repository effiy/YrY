# 作战室运作

> **适用场景**：P0 或 P1 级别事件，尤其是影响核心用户路径的重大故障。作战室是重大事件的指挥中枢——不是普通会议，而是指挥中心。

## 作战室的价值

在日常运维中，on-call 工程师独立处理绝大多数告警和事件。但当故障满足以下条件时，单打独斗反而有害：

- 故障涉及多个服务，需要跨团队协作
- 故障影响核心用户路径，需要快速决策
- 故障超出 on-call 工程师的知识范围

作战室通过**角色分工**和**结构化沟通**，将混乱的排查过程转变为有组织的应急响应。

## 何时开启作战室

| 触发条件 | 行动 | 说明 |
|---|---|---|
| P0 事件（核心用户路径中断） | 立即开启作战室 | 无条件立即启动 |
| P1 事件持续 30 分钟未解决 | 升级为作战室 | 无法快速定位的 P1 应与 P0 同等对待 |
| 多个服务同时受影响 | 开启作战室协调 | 防止各团队各自为战 |
| 用户可见的服务中断 | 开启作战室 + 指定通信官 | 需要统一对外口径 |

## 作战室角色分工

| 角色 | 担任者 | 职责 | 关键要求 |
|---|---|---|---|
| **指挥官** | 最资深的 on-call | 决策、定方向、分配任务 | 不亲自排查；保持全局视野 |
| **响应者** | 工程师（可多人） | 调查根因、执行修复 | 每 5-10 分钟向指挥官汇报进展 |
| **通信官** | PM 或经理 | 更新干系人、客户、状态页 | 每隔 30 分钟发布状态更新 |
| **记录员** | 任何人 | 实时记录时间线、操作和决策 | 捕捉每一个操作的时间戳和执行人 |
| **联络员** | 可选 | 协调外部团队（安全、法务、客服） | 作为跨团队的信息桥梁 |

**最低人员配置**：指挥官 + 响应者。其余角色可兼任。

## 作战室生命周期

### 1. 开启（前 5 分钟）

```
指挥官："作战室已开启。事件：{{一句话描述}}。
         指挥官：{{姓名}}。响应者：{{姓名}}。
         频道：#incidents。共享文档：{{链接}}。"
```

**立即执行的操作**：
- [ ] 创建时间线共享文档（飞书文档 / Notion / Google Docs）
- [ ] 开启语音或视频通话（飞书 / Zoom / 腾讯会议）
- [ ] 分配角色（明确告知每个人的职责）
- [ ] 发布第一条状态更新

### 2. 调查（持续进行中）

```
指挥官设定方向：
  "假设：{{最可能的原因}}。
   响应者：请检查 {{具体事项}}。
   通信官：起草面向客户的状态更新。"
```

**作战室规则**：
- 指挥官一次只设定一个调查方向——多方向并行会导致混乱
- 响应者每 5-10 分钟汇报一次调查进展
- 记录员实时记录每个操作和发现到时间线文档
- 没有人独自行动——所有操作对团队可见

**指挥官应避免的行为**：
- 亲自查看代码或日志——这会丧失全局视角
- 同时给出多个调查方向——响应者会不知道从哪里开始
- 在未收集足够信息前过早下结论——"这就是 X 的问题"在没有证据时是有害的

### 3. 解决

```
指挥官："根因已定位为 {{原因}}。
         修复方案：{{操作}}。预计恢复时间：{{时间}}。
         响应者：执行修复。
         通信官：准备解决公告。"
```

**关闭前的验证**：
- [ ] 修复方案已部署并验证生效
- [ ] 监控显示系统指标恢复正常
- [ ] 用户侧问题已解决
- [ ] 回滚方案已准备就绪（以防修复引发新问题）

### 4. 关闭

```
指挥官："作战室于 {{时间}} 关闭。
         持续时间：{{时长}}。
         根因：{{原因}}。
         修复方案：{{操作}}。
         事后复盘：{{日期}} 进行。
         感谢所有人。"
```

**关闭后的行动**：
- [ ] 发布完整的事件时间线文档
- [ ] 对外发布解决公告
- [ ] 安排事后复盘（24 小时内）
- [ ] 公开具体地感谢参与人员
- [ ] 审查作战室效果——什么做得好？什么可以改进？

## 沟通模板

### 状态更新（每 30 分钟发布一次）

```
事件更新 #{{N}} — {{HH:MM}} (北京时间)

状态：{{调查中 / 缓解中 / 已解决}}
影响：{{用户的实际体验}}
范围：{{受影响的服务/区域}}
进展：{{团队正在做什么}}
预计：{{下次更新时间 / 预计解决时间}}
```

**状态更新原则**：
- **诚实**——不要粉饰事故的严重程度
- **具体**——避免"正在调查"，改为"正在检查 MongoDB 连接池配置"
- **准时**——即使没有进展，也要按时更新："仍在调查中，暂无新发现"

### 解决公告

```
事件已解决 — {{HH:MM}} (北京时间)

持续时间：{{开始时间}} — {{结束时间}}（{{时长}}）
根因：{{1-2 句话}}
修复方案：{{1-2 句话}}
影响范围：{{受影响的用户、数据、业务}}
预防措施：{{我们将采取什么改进}}

完整的事后复盘将在 24 小时内发布。
```

## 作战室最佳实践

| 实践 | 原因 |
|---|---|
| **一次只有一个人说话** | 多人同时说话 = 混乱；指挥官控制发言顺序 |
| **指挥官不亲自排查** | 指挥官需要看到全局；亲自排查会丧失战略视角 |
| **禁止沉默调查** | 如果响应者超过 10 分钟没有汇报，很可能出问题了 |
| **为调查设定时间盒** | "尝试 X 方案 10 分钟，然后汇报结果"——防止无限制深挖 |
| **无责文化** | 作战室的目的是解决问题，不是追究责任 |
| **定时轮换** | 2 小时后，如果可能，轮换指挥官和响应者角色 |

## 作战室结束后的跟进

- [ ] 24 小时内安排事后复盘
- [ ] 发布完整时间线文档
- [ ] 公开具体地感谢团队
- [ ] 审查作战室运作效果——什么做得好？什么可以改进？
- [ ] 将新发现的故障模式和恢复方法更新到 runbook

## 常见反模式

| 反模式 | 为何失败 | 正确做法 |
|---|---|---|
| 没有指挥官 | 所有人各自朝不同方向调查；无协调 | 作战室开启的第一个动作就是指定指挥官 |
| 指挥官亲自排查 | 指挥官丧失全局视角；错过重大决策窗口 | 指挥官分配调查任务；聚焦决策和方向 |
| 没有记录员 | 时间线完全依赖事后回忆重建；事后复盘不准确 | 指定记录员；实时记录每个操作及其时间戳 |
| 事件解决后作战室不关闭 | 团队疲于响应却无明确结束信号 | 指挥官明确宣布作战室关闭并感谢所有人 |
| 作战室讨论追责而非修复 | 团队成员害怕被指责而不敢说出真实想法 | 严格执行无责文化；复盘时再分析流程问题 |
