# 事后复盘指南 — 从事件中学习

> **适用场景**：每次 P0/P1 事件解决后的 24 小时内。事后复盘不是追责工具，而是学习机制——目标是确保同一类事件不会发生第二次。

## 为什么需要事后复盘

没有复盘的事件是浪费的危机。每次生产故障都暴露了系统的薄弱点——设计假设的错误、监控的盲区、流程的缺陷。复盘将这些隐性的薄弱点变为显性的改进项。

| 无复盘 | 有复盘 |
|---|---|
| 同类事件反复发生 | 每个事件推动一项系统性改进 |
| 只有当事人知道发生了什么 | 整个团队从每次事件中学习 |
| 故障原因归结为"人为失误" | 找到导致"人为失误"的系统性因素 |
| 改进靠个人记忆和善意 | 改进靠追踪到完成的行项 |

## 无责文化

事后复盘的第一原则：**无责（Blameless）**。

指责个人会:
- 让工程师在事件中不敢坦诚沟通
- 导致事件细节被隐瞒或美化
- 错失改进系统的机会

**正确做法**：假设每个参与事件的人在当时的信息、能力和工具条件下，已经尽了最大努力。复盘的问题是"系统和流程哪里出了问题，导致一个善意的工程师做出了错误的决策"，而非"谁犯了错"。

### 语言对照

| 追责语言 | 无责语言 |
|---|---|
| "张三没有检查告警" | "告警通知机制未能有效触达值班人" |
| "李四写了有 Bug 的代码" | "Code Review 和测试流程未能捕获这个边界条件" |
| "运维没有及时发现磁盘满" | "磁盘使用率监控缺少自动化告警" |
| "为什么不回滚？" | "回滚决策缺少明确的触发条件，导致犹豫" |

## 复盘模板

### 一、事件概述

```markdown
| 项目 | 内容 |
|---|---|
| **事件标题** | 一句话描述（如：YiAi 聊天服务中断 47 分钟） |
| **事件级别** | P0 / P1 / P2 |
| **日期** | YYYY-MM-DD |
| **持续时间** | HH:MM — HH:MM（共 N 分钟） |
| **参与人员** | 指挥官、响应者、通信官 |
| **影响范围** | 受影响的服务、用户数、业务指标 |
```

### 二、时间线（精确到分钟）

以表格形式重建事件全过程，每一行一个操作：

```markdown
| 时间 | 事件 | 来源 |
|---|---|---|
| 14:32 | Grafana 告警：YiAi API 5xx 错误率攀升至 15% | 告警通知 |
| 14:35 | On-call 确认告警，开始排查 | #incidents 频道 |
| 14:42 | 定位到 MongoDB 连接池耗尽 | mongosh 检查 |
| 14:50 | 决定重启 YiAi 释放连接 | 指挥官决策 |
| 14:55 | YiAi 重启完成，错误率恢复正常 | 监控确认 |
| 15:02 | 确认所有服务恢复 | 冒烟测试通过 |
```

**时间线编写的关键要求**：
- 每个条目必须有确切时间（精确到分钟）
- 每个条目必须注明信息来源（告警、人工观察、用户反馈）
- 不要合并相近的操作——细节在复盘时比想象的重要
- 标注出**决策点**（谁决定做什么、基于什么信息）

### 三、影响评估

```markdown
| 维度 | 详情 |
|---|---|
| **受影响服务** | YiAi / YiVad / YiPet 中的哪些功能 |
| **用户影响** | 用户的实际体验是什么（不是技术描述） |
| **受影响请求数** | 失败的请求数量 / 占比 |
| **数据影响** | 是否有数据丢失或损坏 |
| **业务影响** | 对业务指标的影响（如有） |
| **检测时间** | 从故障发生到被发现的时间 |
| **恢复时间** | 从被发现到完全恢复的时间 |
```

### 四、根因分析（5-Why）

每个根因至少追问 5 层"为什么"：

```markdown
1. **为什么** YiAi 返回 5xx 错误？
   → MongoDB 连接池耗尽，新请求无法获取连接

2. **为什么** 连接池会耗尽？
   → 某个慢查询持有连接超过 30 秒，连接池中的连接被逐渐占满

3. **为什么** 会有慢查询？
   → sessions 集合缺少 `created_at` 索引，全表扫描耗时过长

4. **为什么** 缺少索引没有被发现？
   → 没有慢查询监控；数据库性能没有被纳入日常巡检

5. **为什么** 慢查询监控没有被建立？
   → 可观测性搭建时遗漏了数据库层面的指标
```

**5-Why 常见陷阱**：
- 在第 2-3 层停住（"人为失误"不是根因，是现象）
- 回答太笼统（"流程不完善"→ 具体哪个流程的哪个环节？）
- 过早跳到解决方案（"加个索引就好了"——先问清楚为什么没加）

### 五、缓解与修复

```markdown
| 措施 | 类型 | 状态 |
|---|---|---|
| 为 sessions.created_at 添加索引 | 永久修复 | 已完成 |
| 添加 MongoDB 慢查询监控告警 | 监控改进 | 进行中 |
| 将数据库巡检纳入每周检查清单 | 流程改进 | 已完成 |
| 审查其他集合是否缺少关键索引 | 预防措施 | 待安排 |
```

### 六、经验教训

```markdown
| 类别 | 教训 |
|---|---|
| **做得好的** | 告警在 3 分钟内被确认；作战室在 10 分钟内启动 |
| **需要改进的** | 值班人对 MongoDB 连接池机制不够熟悉，排查时间过长 |
| **意外发现** | 连接池配置的默认值（100）在当前负载下偏小 |
```

### 七、行动项

每条行动项必须有负责人和截止时间：

```markdown
| # | 行动项 | 负责人 | 截止时间 | 优先级 | 状态 |
|---|---|---|---|---|---|
| 1 | 为 sessions 集合添加 created_at 索引 | 张三 | 2026-09-17 | P0 | ✅ 已完成 |
| 2 | 配置 MongoDB 慢查询告警（> 100ms） | 李四 | 2026-09-20 | P1 | 🔄 进行中 |
| 3 | 审查所有集合的索引覆盖情况 | 张三 | 2026-09-25 | P2 | ⬜ 待开始 |
| 4 | 将数据库巡检纳入值班交接检查清单 | 王五 | 2026-09-18 | P1 | ⬜ 待开始 |
```

## 复盘审查流程

### 时间要求

| 事件级别 | 复盘完成时限 | 审查人 |
|---|---|---|
| P0 | 24 小时内完成初稿，48 小时内完成审查 | 工程经理 + 技术负责人 |
| P1 | 48 小时内完成初稿，1 周内完成审查 | 工程经理 |
| P2 | 1 周内完成 | 团队内部审查 |

### 审查关注点

- [ ] 时间线是否完整、准确？
- [ ] 根因分析是否到达了系统性层面（不是停在"人为失误"）？
- [ ] 行动项是否具体、可执行、有负责人和截止时间？
- [ ] 是否避免了追责语言？
- [ ] 经验教训是否对团队有普遍参考价值？

## 复盘归档

复盘完成后存入 `incident-response/` 目录，命名格式：`tl-postmortem-{简短描述}-{YYYY-MM}.md`

例子：
- `tl-postmortem-mongodb-connection-pool-exhaustion-2026-09.md`
- `tl-postmortem-sse-stream-interruption-2026-08.md`

## 复盘的反模式

| 反模式 | 为何失败 | 正确做法 |
|---|---|---|
| 事件解决后跳过复盘 | 根因从未被修复；同类事件反复发生 | P0/P1 事件必须复盘，无例外 |
| 复盘变成追责会 | 团队成员从此隐瞒信息；复盘流于形式 | 严格执行无责原则；使用无责语言 |
| 行动项没有负责人和截止时间 | 每个人都以为别人会做；最终无人执行 | 每条行动项指定负责人 + 截止时间 |
| 根因停在"人为失误" | 没有找到系统性原因；改进措施是"下次小心点" | 追问为什么这个人会失误——缺少培训？流程不清？工具不好用？ |
| 复盘中只有技术分析没有流程反思 | 修复了技术 Bug，没修复流程缺陷 | 技术和流程并重；流程缺陷往往是根因的上游 |
| 复盘写完后无人审查 | 低质量复盘变成常态；团队不再重视 | P0/P1 复盘必须由管理者审查 |
