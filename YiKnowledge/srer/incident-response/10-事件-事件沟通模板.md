# 事件沟通模板 — 对内对外的事件信息传递

> **适用场景**：每次 P0/P1 事件期间的沟通。事件中最大的信任杀手不是故障本身，而是沉默。即使没有进展，也要准时更新。

## 沟通的黄金法则

1. **诚实**——不要粉饰。说"我们正在调查"比说"影响很小"然后被打脸要好
2. **准时**——即使没有进展，也要按时更新："仍在调查中，暂无新发现"
3. **面向受众**——给工程师的技术细节不同于给用户的业务影响描述
4. **一致**——所有人使用统一模板，避免"不同人说不同话"

## 受众与渠道

| 受众 | 渠道 | 频率 | 内容重点 |
|---|---|---|---|
| **内部工程团队** | `#incidents` 频道 | 每 15-30 分钟 | 技术排查进展、下一步操作、需要谁协助 |
| **管理层** | 专用 IM 群或邮件 | P0 每 30 分钟，P1 每 1 小时 | 业务影响、预计恢复时间、是否需要升级资源 |
| **受影响用户** | 应用内通知/状态页 | 事件开始时 + 每 1-2 小时 | 用户影响、替代方案、预计恢复时间 |
| **全体用户（事后）** | 邮件/公告 | 事件解决后 24 小时内 | 事件概述、已采取的修复和预防措施 |

## 模板一：内部工程团队（#incidents 频道）

### 事件声明（事件开始时发送）

```
🚨 事件声明 — {{HH:MM}}

事件：{{一句话描述}}
级别：P0 / P1 / P2
影响：{{用户实际体验到什么}}
服务：{{受影响的服务列表}}
指挥官：{{姓名}}
响应者：{{姓名}}
通信官：{{姓名}}

当前操作：{{团队正在做什么}}
下次更新：{{时间}}
```

### 状态更新（每 15-30 分钟发送）

```
📡 事件更新 #{{N}} — {{HH:MM}}

状态：🟢 已解决 / 🟡 缓解中 / 🔴 调查中
持续时间：{{开始时间}} — 当前（{{已过时长}}）

进展：
• {{排查发现 #1}}
• {{排查发现 #2}}

当前操作：
• {{正在执行的操作}}

根因：{{已定位 / 仍在排查}}

预计恢复：{{HH:MM 或 "暂无法估计"}}
下次更新：{{HH:MM}}
```

### 事件解决（事件结束时发送）

```
✅ 事件已解决 — {{HH:MM}}

事件：{{标题}}
级别：P0 / P1
持续时间：{{开始}} — {{结束}}（共 {{N}} 分钟）

根因：{{1-2 句话}}
修复方案：{{1-2 句话}}
影响范围：{{受影响的用户数、请求数、数据}}

事后复盘：{{日期}} 进行
复盘文档：{{链接}}

感谢 @{{参与者}} 在此次事件中的响应。
```

## 模板二：管理层通报

管理层关心的是业务影响和恢复时间，不是技术细节。

### 初始通报（事件开始后 15 分钟内）

```
主题：P0 事件通报 — {{服务名}} 中断

当前状况：
{{服务名}} 自 {{HH:MM}} 起出现 {{用户可见的故障现象}}。

业务影响：
• {{影响的业务指标或用户数}}
• {{是否涉及数据安全/合规}}

正在采取的行动：
• 事件响应团队已于 {{HH:MM}} 启动
• 指挥官：{{姓名}}，联系电话：{{手机}}
• 已通知相关团队（安全/法务/客服 — 按需列出）

预计恢复时间：{{如有 / "正在评估中"}}
下次通报：{{HH:MM}}
```

### 重大升级通报

满足以下条件时，立即升级通报管理层：

- P0 事件持续超过 30 分钟
- 确认发生数据泄露或丢失
- 需要管理层决策（如：是否对外公告、是否启用灾备方案）
- 事件可能引发媒体或监管关注

```
⚠️ 事件升级通报 — {{HH:MM}}

升级原因：{{为什么需要管理层关注}}

当前状况：{{简述}}
决策需要：{{管理层需要决定什么}}
时间窗口：{{需要在什么时间前做决定}}

联系方式：指挥官 {{姓名}} — {{手机}}
```

### 恢复通报

```
✅ 事件恢复通报 — {{HH:MM}}

事件：{{标题}}
总停机时间：{{N}} 分钟
影响范围：{{简述业务影响}}
根因：{{1 句话}}
已采取的修复和预防措施：{{简述}}

事后复盘计划：{{日期}}
复盘报告将发送至：{{谁需要收到}}
```

## 模板三：面向用户的通知

### 应用内通知

```
⚠️ 系统通知

{{服务功能}} 当前暂时不可用。我们正在紧急修复中，预计 {{时间内}} 恢复。

受影响的功能：{{列出}}
替代方案：{{如有替代路径，引导用户}}

如有紧急需求，请联系：{{客服/支持联系方式}}
```

### 状态页更新

```markdown
## {{事件标题}}

**状态**：🔴 调查中 / 🟡 已识别 / 🟢 已解决
**开始时间**：YYYY-MM-DD HH:MM (北京时间)
**受影响服务**：{{服务列表}}

### 最新更新
**[HH:MM]** {{更新内容}}

### 更新历史
**[HH:MM]** {{历史更新}}
**[HH:MM]** 事件开始 — {{初始描述}}
```

### 事件事后公告（面向用户，事件解决后 24 小时内）

```
主题：关于 {{日期}} {{服务名}} 服务中断的说明

尊敬的客户：

{{日期}} {{时间段}}，{{服务}} 出现了 {{故障描述}}，导致 {{用户影响}}。我们深表歉意。

发生了什么：
{{用通俗语言解释根因，1-2 段}}

我们做了什么：
{{采取的恢复措施}}

我们如何防止再次发生：
{{已实施或计划中的预防措施，2-3 条}}

如果您仍有疑问，请通过 {{联系方式}} 联系我们。

真诚地，
{{团队名称}}
```

## 模板四：客服/支持团队简报

客服团队是用户的第一接触点，需要在事件开始时立即获得标准口径。

```
📋 客服口径 — {{事件标题}}

用户可能会问：
"为什么{{功能}}用不了？"
"什么时候能恢复？"
"我的数据安全吗？"

标准回复话术：
====================================
我们已注意到 {{功能}} 的问题，技术团队正在紧急修复中。
预计 {{时间}} 恢复正常。
您的数据是安全的，此次问题仅影响 {{功能}} 的可用性。
====================================

请勿对用户做出任何超出上述话术的承诺。
如有用户要求赔偿或投诉升级，请转接至 {{处理人}}。

状态更新请关注 #incidents 频道。
```

## 沟通角色

| 角色 | 职责 | 由谁担任 |
|---|---|---|
| **通信官** | 撰写和发布所有状态更新；确保模板一致、频率达标 | PM 或指定的工程师（非指挥官） |
| **审批人** | 审查对外公告和事后公告的内容 | 工程经理或技术负责人 |
| **客服联络员** | 将技术信息转化为客服口径；更新客服团队 | 指定的客服负责人 |

**关键原则**：指挥官不负责对外沟通。指挥官的唯一职责是指挥技术响应。通信官从指挥官获取信息，转化为面向受众的内容。

## 沟通节奏

| 事件级别 | 内部更新频率 | 用户更新频率 | 管理层更新频率 |
|---|---|---|---|
| P0 | 每 15 分钟 | 每 30 分钟 | 每 30 分钟 |
| P1 | 每 30 分钟 | 每 1 小时 | 每 1 小时 |
| P2 | 事件开始 + 事件结束 | 不需要（或事件结束时一次公告） | 不需要 |

**准时不缺席原则**：到了更新预定时间但没有任何进展，也必须发送更新："仍在调查中，暂无新发现。下次更新 {{HH:MM}}。"沉默比"没有进展"更让受众焦虑。

## 沟通反模式

| 反模式 | 为何失败 | 正确做法 |
|---|---|---|
| 事件中对外保持沉默 | 用户自行猜测、传播恐慌；信任崩塌 | 事件开始时立即发第一条公告，之后准时更新 |
| 给用户看技术细节 | "MongoDB 连接池耗尽了"——用户不知道这意味着什么 | 用用户语言描述影响："数据加载功能暂时不可用" |
| 过早给出恢复时间 | 2 次错过承诺的恢复时间 = 彻底失去信任 | 给出时间范围而非精确时间；表示"暂无法估计"也不丢人 |
| 管理层和技术团队用同一份更新 | 管理层不需要技术细节；技术团队不需要业务指标 | 为不同受众准备不同版本 |
| 事件解决后不发事后公告 | 用户只经历了故障，没看到你的改进 | 事件解决后 24 小时内向受影响用户发送事后公告 |
