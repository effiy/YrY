# 处理数据泄露

> **适用场景**：当确认或高度怀疑发生未经授权的数据访问时。数据泄露事件对时间极其敏感——每一分钟都关乎能否有效控制损失范围。

## 适用场景

- 发现 MongoDB 中存在异常查询记录，且涉及敏感数据集合
- 接收到第三方安全研究人员的漏洞报告
- 日志中出现可疑的大批量数据导出操作
- 发现 YiAi API 访问日志中出现异常请求模式
- 配置文件或凭据意外泄露到公开仓库

## 阶段一：隔离（前 15 分钟）

### 立即行动

| 步骤 | 执行人 | 操作 | 时限 |
|---|---|---|---|
| 1 | 值班 on-call | **隔离**受影响系统——吊销访问权限、轮换密钥、必要时关闭服务 | 5 分钟 |
| 2 | 值班 on-call | **保全证据**——在进行任何修改前，截取日志、数据库快照和访问记录 | 5 分钟 |
| 3 | 值班 on-call | **止血**——封堵攻击入口（IP、Token、账号） | 5 分钟 |

### 绝对禁止的操作

- **不要删除任何数据**——这会破坏取证分析所需的证据
- **不要重启系统**——内存中可能包含攻击者的操作痕迹
- **暂时不要通知用户**——先在内部完成范围评估，避免发布模糊不清的信息引发恐慌
- **不要修改数据库中的数据**——保留原始状态以便追溯被访问的记录

## 阶段二：评估（第一个小时）

### 确定泄露范围

| 问题 | 如何回答 | 数据来源 |
|---|---|---|
| 哪些数据被访问了？ | 检查访问日志、查询历史、文件访问记录 | MongoDB `system.access_log`、YiAi 应用日志 |
| 涉及多少条记录？ | 统计被访问的唯一文档/用户数 | 数据库查询分析 |
| 何时开始泄露？ | 找到最早的未授权访问时间戳 | 日志时间线分析 |
| 攻击者如何进入？ | 追踪攻击路径（Token 失窃、注入攻击、ACL 配置错误） | 日志关联分析 |
| 攻击是否仍在进行？ | 检查当前是否存在持续的未授权访问模式 | 实时监控 |

### 严重程度分级

| 级别 | 判定标准 | 通知时限 | 典型场景 |
|---|---|---|---|
| **严重** (P0) | 个人信息、凭据、支付数据、或超过 1000 条记录泄露 | 24 小时内通知 | 用户密码哈希泄露、会话 Token 泄露 |
| **高** (P1) | 内部文档、非敏感数据、少于 1000 条记录 | 72 小时内通知 | 内部技术文档被访问、知识库文件泄露 |
| **中** (P2) | 仅元数据泄露，无实际内容暴露 | 1 周内通知 | 文件目录结构暴露、用户 ID 列表泄露 |
| **低** (P3) | 尝试攻击但未成功 | 无需外部通知 | 端口扫描、暴力破解被拦截 |

### 证据收集命令

```bash
# 保全 YiAi 访问日志
cp /var/log/yi-ai/access.log /tmp/breach-$(date +%Y%m%d-%H%M)/

# 快照 MongoDB 访问日志
mongodump --uri="mongodb://localhost:27017" --db=admin --collection=system.access_log

# 捕获当前网络连接状态
ss -tunap > /tmp/breach/connections.txt

# 捕获正在运行的进程
ps auxf > /tmp/breach/processes.txt

# 保全 Ollama API 访问日志（如适用）
journalctl -u ollama --since "24 hours ago" > /tmp/breach/ollama-logs.txt
```

## 阶段三：通知（按严重程度时间线执行）

### 内部通知升级路径

1. **安全团队** — 立即通知
2. **工程经理** — 1 小时内
3. **技术 VP / CTO** — 严重/高级别 2 小时内通知
4. **法务 / 合规团队** — 严重级别 4 小时内通知（满足监管要求）

### 外部通知合规要求

| 法规 | 要求 | 适用范围 |
|---|---|---|
| GDPR（欧盟通用数据保护条例） | 72 小时内通知监管机构 | 涉及欧盟用户数据 |
| CCPA（加州消费者隐私法案） | "无不合理延迟"通知受影响用户 | 涉及加州居民数据 |
| PIPL（中国个人信息保护法） | 24 小时内通知有关部门 | 涉及中国境内个人信息 |
| 网安法（中国网络安全法） | 立即采取技术措施，并向主管部门报告 | 网络运营者在境内收集产生的个人信息 |

### 外部通知模板

```
主题：安全事件通知 — {{日期}}

尊敬的客户：

我们正在向您通报一起可能涉及您数据的安全事件。

事件经过：{{1-2 句话描述}}
涉及的数据类型：{{数据类型描述，不要列出具体数据值}}
我们采取的措施：{{隔离和修复步骤}}
您需要做什么：{{用户应采取的行动，如有}}

我们将在调查继续的过程中提供后续更新。
如有疑问，请联系：{{安全团队邮箱}}
```

## 阶段四：修复

### 根因修复映射表

| 攻击入口 | 修复方案 | 预防措施 |
|---|---|---|
| API Token 失窃 | 轮换所有 Token；实施 Token 过期策略；审查 Token 权限范围 | 使用短期 Token + 自动轮换 |
| SQL/NoSQL 注入 | 修复漏洞查询；审计所有同类查询模式 | 参数化查询；输入校验 |
| ACL 配置错误 | 修复 ACL；审计所有集合的权限配置 | 最小权限原则；定期权限审计 |
| 依赖漏洞 | 更新漏洞依赖；审计所有项目的依赖安全 | 依赖扫描自动化；SBOM |
| 内部威胁 | 吊销访问权限；审查访问日志；实施最小权限原则 | 操作审计日志；异常行为告警 |

### 防止复发检查清单

- [ ] 针对此次攻击模式增加监控规则
- [ ] 针对此次数据访问模式增加告警规则
- [ ] 将此次发现更新到安全检查清单
- [ ] 安排针对此类攻击入口的渗透测试
- [ ] 检查 YiAi `config.yaml` 中是否有硬编码凭据
- [ ] 确认 Ollama API（端口 11434）已配置防火墙规则
- [ ] 确认 YiKnowledge 目录的文件系统权限为只读

## 阶段五：事后复盘

使用 [../../leader/risk/write-a-postmortem.md](../../leader/risk/write-a-postmortem.md) 模板撰写事后复盘。核心问题：

1. 根因是什么？（5-Why 分析法）
2. 数据暴露了多长时间？（时间线重建）
3. 影响范围如何？（涉及记录数、用户数、数据类型）
4. 哪些流程变更可以预防此类事件再次发生？

## YrY 特定注意事项

| YiAi 相关考量 | 防护措施 |
|---|---|
| `config.yaml` 中的 MongoDB 连接串 | 使用环境变量存储，绝不可提交到 Git |
| Ollama API 仅本地监听 | 确保防火墙阻止对端口 11434 的外部访问 |
| YiKnowledge Markdown 文件在磁盘上 | 文件系统权限：API 用户设为只读 |
| MongoDB 中的会话数据 | 实施会话 TTL（如 90 天自动过期）|
| YiVad 的 `authMenuList.json` 静态文件 | 不要在静态文件中存放敏感路由配置 |
| YiPet 的 `chrome.storage.local` | 提醒用户敏感会话数据存在浏览器本地存储中 |

## 常见反模式

| 反模式 | 为何失败 | 正确做法 |
|---|---|---|
| 隔离阶段删除证据 | 无法确定泄露范围，无法满足合规要求 | 在清理之前先保全日志、快照和内存转储 |
| 在评估完成前通知用户 | "我们被攻击了"但没有任何细节，引发恐慌 | 先评估范围，再发送包含具体、可操作信息的通知 |
| 保密的事后复盘 | 团队无法学习，同类泄露再次发生 | 与整个工程团队分享事后复盘；敏感细节可脱敏处理 |
| 忽略监管通知要求 | 面临罚款、法律诉讼和信任丧失 | 了解适用的监管要求；在规定的时限内完成通知 |
| 只处理攻击入口而不检查影响范围 | 修复了漏洞但不知道哪些数据已被泄露 | 隔离、评估、修复三者必须按顺序完整执行 |
