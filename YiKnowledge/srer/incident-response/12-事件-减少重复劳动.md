# 减少重复劳动 — 把时间还给工程工作

> **适用场景**：当你感觉每天都疲于处理相同的事情、没有时间做改进时。Google SRE 的核心原则之一：SRE 的重复劳动不应超过 50% 的工作时间。其余时间应投入到真正改善系统可靠性的工程工作中。

## 什么是重复劳动

重复劳动（Toil）是指运维工作中**手动、重复、可自动化、没有持久价值、随服务规模线性增长**的操作。

| 是重复劳动 | 不是重复劳动 |
|---|---|
| 每次发布都手动执行相同的部署命令 | 设计新的部署流水线（工程工作） |
| 每天手动运行健康检查 | 搭建自动化健康检查（工程工作） |
| 每次排查都要手动 grep 同一组日志 | 编写日志聚合查询（工程工作） |
| 手工回复相同的用户报障 | 修复导致报障的根因（工程工作） |
| 手动拷贝粘贴的值班交接文档 | 改进交接模板使其更快填写（工程工作） |

### 重复劳动的五个特征

所有五个特征同时满足 = 重复劳动：

1. **手动**——需要人执行，不是自动触发的
2. **重复**——不是一次性的，而是反复出现的
3. **可自动化**——机器可以完成（如果不能自动化则是必要的工程工作）
4. **没有持久价值**——做完后系统状态没有变好，只是维持了现状
5. **随规模线性增长**——服务越多、用户越多，这项工作越多

## 消除重复劳动的优先级

### 优先级矩阵

按 **(每日耗时 × 频率) / 自动化难度** 排序：

| 排名 | 重复劳动 | 每日耗时 × 频率 | 难度 | 得分 | 自动化方案 |
|---|---|---|---|---|---|
| 1 | 健康检查 | 15 分钟/天 | 低 | 15 | Cron + 异常时飞书 Webhook 告警 |
| 2 | 磁盘空间检查 | 2 分钟/天 | 低 | 2 | 磁盘使用率 > 80% 告警 |
| 3 | RAG 同步确认 | 3 分钟/天 | 低 | 3 | 知识监视器失败时告警 |
| 4 | 部署验证 | 10 分钟/次 | 低 | 取决于发布频率 | 冒烟测试脚本 |
| 5 | 日志审查 | 5 分钟/天 | 中 | 2.5 | 错误模式自动告警 |
| 6 | 值班交接文档 | 15 分钟/周 | 低 | ~2 | 模板 + Git log 自动生成变更列表 |
| 7 | 部署操作 | 5 分钟/次 | 中 | 取决于频率 | CI/CD 自动部署 |

**起步建议**：先自动化前 3 项（健康检查、磁盘、RAG），每天可节省约 20 分钟。

## 自动化方案

### 方案 1：健康检查自动化（节省 15 分钟/天）

**当前**：值班人每天 3 次手动运行 `check-health.sh`。

**自动化**：改造脚本，异常时自动通知，正常时静默。

```bash
#!/bin/bash
# check-and-alert.sh — crontab: */5 * * * *
# 改造点：正常时静默，异常时告警

WEBHOOK="https://open.feishu.cn/open-apis/bot/v2/hook/YOUR_TOKEN"
HEALTH=$(curl -s localhost:10086/health/observer)

# 只在异常时告警
if echo "$HEALTH" | grep -q '"disconnected"\|"unavailable"'; then
  curl -s -X POST "$WEBHOOK" \
    -H "Content-Type: application/json" \
    -d "{\"msg_type\":\"text\",\"content\":{\"text\":\"健康检查异常：$HEALTH\"}}"
fi
```

**效果**：无需人工巡检；系统正常时零干预；异常时秒级通知。

### 方案 2：部署冒烟测试脚本（节省 10 分钟/次）

```bash
#!/bin/bash
# smoke-test.sh — 部署后运行
# 验证核心功能是否正常，任何失败返回非 0

ENDPOINT="http://localhost:10086"

# 1. 健康检查
curl -sf "$ENDPOINT/health/observer" > /dev/null || exit 1

# 2. RPC 基础调用
curl -sf -X POST "$ENDPOINT/" \
  -H "Content-Type: application/json" \
  -d '{"module_name":"services.database.data_service","method_name":"query_documents","parameters":{"cname":"menus","pageSize":1}}' | grep -q '"code":0' || exit 1

# 3. RAG 状态
curl -sf "$ENDPOINT/rag-status" | grep -q '"built":true' || exit 1

echo "冒烟测试通过"
```

### 方案 3：值班交接文档半自动化

**当前**：每次手写交接文档，格式靠记忆。

**改进**：准备一个 Markdown 模板 + 用 Git log 自动填充"本周变更"部分。

```bash
# 生成本周变更摘要
echo "## 本周变更"
git log --since="1 week ago" --oneline --no-merges | while read line; do
  echo "- $line"
done
```

## 自动化优先级决策框架

每季度评审重复劳动清单，决定哪些值得自动化：

```
这个重复劳动...
├─ 每天耗时 > 10 分钟？ → 高优先级
├─ 自动化需要 < 1 天？ → 立即做
├─ 需要人工判断？ → 不能全自动，但可以半自动（如预先填充信息）
├─ 仅在紧急时发生？ → 低优先级——runbook 就够
└─ 发生频率 < 每月一次？ → 低优先级——不值得自动化
```

### 不值得自动化的重复劳动

| 操作 | 为什么不值得 | 替代策略 |
|---|---|---|
| 每半年一次的 SSL 证书更换 | 频率太低，自动化投入 > 收益 | 写一个清晰的 runbook + 日历提醒 |
| 年度灾难恢复演练 | 每一次环境都不同，需人工判断 | 维护恢复脚本但接受每次需人工监督 |
| 复杂故障的根因分析 | 每次故障都不同，无法标准化 | 保持高质量复盘流程即可 |

## 重复劳动预算

如同错误预算，为重复劳动设定上限：

| 重复劳动占比 | 状态 | 行动 |
|---|---|---|
| < 30% | 健康 | 保持当前自动化水平 |
| 30-50% | 警戒 | 识别 Top 3 重复劳动并排期自动化 |
| > 50% | 超标 | 暂停非紧急工作，集中自动化 Top 5 |

**YrY 当前估算**：重复劳动占比 > 50%（高度依赖人工操作）→ 优先自动化前 3 项。

## 常见反模式

| 反模式 | 为何失败 | 正确做法 |
|---|---|---|
| "先忍忍，以后有空再自动化" | "以后有空"永远不会来；重复劳动变成常态 | 设定重复劳动预算——超过 50% 强制暂停其他工作 |
| 为只发生一次的事情写自动化脚本 | 编写自动化脚本的时间 > 手工操作 × 发生次数 | 估算手动总耗时 vs 自动化投入；低频操作写 runbook 即可 |
| 自动化了但没监控 | 自动化静默失败，没有人知道——比手动还危险 | 每个自动化必须有失败告警 |
| "全部自动化" | 有些工作需要人工判断——强行自动化引入风险 | 区分可自动化和需人工判断的操作；后者半自动化 |
