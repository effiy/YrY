# 事件响应流程

> **4 阶段响应：发现 → 定级 → 缓解 → 学习。** 每个事件都遵循此流程。目标：先恢复服务，后理解根因。

## 流程概览

```
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│  1. 发现  │ → │  2. 定级  │ → │  3. 缓解  │ → │  4. 学习  │
│  Detect   │    │  Triage   │    │ Mitigate  │    │  Learn    │
└──────────┘    └──────────┘    └──────────┘    └──────────┘
  1-5 分钟        5-15 分钟      15分钟-2小时      24小时内
```

## 阶段一：发现

### 监控来源

| 来源 | 可检测的问题 | 检查方式 |
|---|---|---|
| YiAi `/health/observer` | MongoDB 连接状态、Ollama 可用性 | `GET /health/observer` |
| YiAi 日志 | Agent 错误、SSE 流失败、监视器同步失败 | uvicorn stdout |
| YiVad 浏览器控制台 | 401（Token 过期）、422（参数不匹配）、SSE 中断 | Chrome DevTools |
| YiPet 聊天窗口 | API 客户端错误、SSE 流中断 | 聊天窗口错误提示 |

### Yi 家族服务降级应对表

当某个依赖不可用时，各服务的行为如下。这张表是定级时的重要参考——如果符合表中的降级行为，说明是已知的依赖故障模式。

| 服务 | 条件 | 降级行为 | 用户影响 |
|---|---|---|---|
| YiAi — MongoDB | 不可达 | 写入快速失败；读取返回空结果 | 数据查询和写入全部不可用 |
| YiAi — Ollama | 不可达 | 聊天返回 `ErrorCode.AI_UNAVAILABLE`；图片处理返回 503 | 聊天功能不可用，数据 CRUD 仍正常 |
| YiAi — OSS | 不可达 | 文件存储回退到本地磁盘 | 文件仍可访问，但缺少云端备份 |
| YiVad — 菜单 API | 不可用 | 回退到 `authMenuList.json` 静态文件 | 菜单渲染可能不完整 |
| YiVad — Token | 过期 | 401 拦截器重定向到登录页 | 用户被强制登出 |
| YiPet — YiAi | 不可达 | API 客户端指数退避重试，显示类型化错误提示 | 聊天不可用，知识树无法加载 |

### 健康检查端点

| 端点 | 用途 | 预期响应 |
|---|---|---|
| `GET /health/observer` | YiAi 整体健康 | `{"status": "ok", "mongodb": "connected", "ollama": "available"}` |
| `GET /rag-status` | RAG 索引状态 | `{"built": true, "num_docs": N, "last_built_at": "ISO时间戳"}` |
| `GET /knowledge-scan` | 知识库扫描 | `{"files": N, "categories": [...]}` |

## 阶段二：定级

### 严重程度定义

| 级别 | 定义 | 响应时限 | 典型示例 |
|---|---|---|---|
| **P0 — 严重** | YiAi 宕机，所有 Yi 家族服务不可用 | 立即响应 | MongoDB 不可达、uvicorn 进程崩溃 |
| **P1 — 重大** | 单个服务降级，存在替代方案 | 30 分钟内 | Ollama 不可达（聊天中断，但数据 CRUD 正常）|
| **P2 — 一般** | 非核心功能异常 | 4 小时内 | 知识监视器数据陈旧（RAG 索引过期）|
| **P3 — 轻微** | 视觉问题，无功能影响 | 下一个工作日 | UI 布局问题、国际化缺失字段 |

### 定级问题清单

1. **哪个服务受影响？**（YiAi / YiVad / YiPet / YiKnowledge）
2. **用户影响是什么？**（用户还能完成核心操作吗？）
3. **是否有临时替代方案？**（用户能否切换到备选路径？）
4. **是否是已知的降级场景？**（对照上方降级应对表）

### 定级示例

| 现象 | 定级 | 理由 |
|---|---|---|
| `curl localhost:10086/health/observer` 返回 `mongodb: disconnected` | P0 | YiAi 的数据库不可达，所有前端依赖的数据操作全部失败 |
| 聊天功能返回 "AI 服务暂时不可用" | P1 | 聊天中断但数据管理功能正常 |
| RAG 索引显示 `num_docs=0` | P2 | RAG 失效但不影响基本聊天和数据功能 |
| YiVad 某个页面加载了旧版菜单 | P3 | 功能正常，仅显示不完整 |

## 阶段三：缓解

### 前 5 分钟紧急操作

1. **检查 YiAi 健康**：`curl http://localhost:10086/health/observer`
2. **检查 MongoDB**：MongoDB 进程是否运行？YiAi 能否连接？
3. **检查 Ollama**：Ollama 是否运行？`curl http://localhost:11434/api/tags`
4. **检查磁盘**：磁盘是否已满？（YiAi 会双写文件到磁盘）
5. **检查最近变更**：受影响项目执行 `git log --oneline -5`

### 分服务恢复操作

**YiAi 不响应**：
```bash
# 检查 uvicorn 是否运行
ps aux | grep uvicorn
# 如需重启
cd YiAi && python main.py
```

**MongoDB 不可达**：
```bash
# 检查 MongoDB 状态
brew services list | grep mongodb
# 如需重启
brew services restart mongodb-community
```

**Ollama 不可达**：
```bash
# 检查 Ollama 状态
curl http://localhost:11434/api/tags
# 如需重启
ollama serve
```

**知识监视器数据陈旧**：
```bash
# 检查监视器日志中是否有 "0 files synced"
# 手动触发同步
curl -X POST http://localhost:10086/knowledge-sync
```

## 阶段四：学习

### 事后复盘模板

每个 P0 或 P1 事件，必须在 24 小时内完成事后复盘：

```markdown
# 事件事后复盘：<标题>

## 时间线
- [HH:MM] 事件被发现（如何发现？）
- [HH:MM] 响应启动（谁响应？）
- [HH:MM] 根因定位
- [HH:MM] 缓解措施执行
- [HH:MM] 服务恢复
- 总停机时间：<N> 分钟

## 影响
- 哪些服务受影响？
- 影响多少用户？
- 是否有数据丢失或损坏？

## 根因
- 导致故障的具体原因是什么？
- 为什么之前没有发现？

## 解决方案
- 采取了什么措施恢复服务？
- 修复是临时方案还是永久方案？

## 行动项
- [ ] 短期修复（本周内）
- [ ] 长期预防（本迭代内）
- [ ] 监控改进（为此故障模式添加告警）

## 经验教训
- 下次遇到类似情况会怎么做？
- 在响应过程中哪些做法是有效的？
```

### 事后复盘关键原则

- **无责文化**——事后复盘的目的是学习和改进，而非追责。使用"我们"而非"你"
- **5-Why 分析法**——每个根因至少追问 5 层"为什么"，直到找到系统性原因
- **行动项可追踪**——每条行动项必须有负责人和截止时间

## 常见反模式

- **不查看日志就重启服务。** 日志包含根因信息。重启会销毁证据。永远先 `tail -100`，再 `restart`。
- **P1 事件不写事后复盘。** "很快就修好了"不是跳过复盘的理由。事后复盘的价值是预防下一次事件，而非记录这一次。
- **只治标、不治本。** MongoDB 不可达 → 重启 MongoDB。但为什么不可达？磁盘满了？OOM？网络分区？必须修复根因。
- **事件中多人各自独立排查。** 缺乏协调导致效率低下。P0/P1 事件应立即升级到作战室模式，由指挥官统一协调。
