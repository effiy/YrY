## §1 理论根基：70/20/10 × DORA 006 → 支撑 README I-04

1.1 **核心法则 70/20/10**：Google 测试投入比例：
  - **70% 单元测试**（工程师自写，快速、稳定、数量大）
  - **20% 集成测试**（服务间接口、跨模块）
  - **10% 端到端 E2E / 探索式**（真实用户旅程 + 人类直觉）
1.2 **TE / SET / SWE 三角色**：Test Engineer（TE 手工+脚本）/ Software Engineer in Test（SET 写测试框架）/ Software Engineer（SWE 写单测）。我们无专职 SET，故 SET 职责由 Staff 工程效率专家 + QA 兼任（见 015 Staff Path 三层）。
1.3 **× DORA 006 加速 联动**：Deployment Frequency × CFR = 测试金字塔能否防住回归 → 70/20/10 金字塔是 DORA 4 指标的底座。
1.4 **CI 门禁 4 条原则**（Google 实践）：0 合入 break build、慢测试先移除、失败快、测试本身是代码。
1.5 **支撑 README I-04（工程效能 4 指标）**：本笔记是 I-04 第 6 本：加速 / DDIA / SRE / StaffPath / 团队拓扑 / 谷歌测试 → I-04 齐备。

## §4 精华摘录（7 条，含 1 条不同意）

> **S1**「At Google, we don't hire testers to write tests; we hire engineers who can test.」
> **So-What**：A-05 QA4 级必须会写 Rust/Vitest，QA2 起强制自动化 ≥60%。

> **S2**「The 70/20/10 rule is not a suggestion; it's a budget.」
> **So-What**：A-01 README §3 金字塔差距表必须每季度更新，未达标计入 CTO OKR。

> **S3**「Flaky tests are worse than no tests.」
> **So-What**：A-02 CI 门禁 增加 flaky 检测（同一 PR 同一 test 连续 2 次结果不同 → 自动 quarantine）。

> **S4**「Any team that follows the 70/20/10 rule exactly will ship better software.」Whittaker 主张 **70/20/10 必须严格按比例切**。
> **❌ 我不同意作者：70/20/10 必须严格比例是错误的**。我方修正：**分阶段 / 分项目灵活浮动**：
> **阶段 A（基建 <60% 覆盖）：90/5/5 → 先补单测；**
> **阶段 B（稳定期）：65/25/10；**
> **阶段 C（新品冲刺期，0~3 月）：60/30/10（集成权重提高，解决跨模块联调 bug）。**
> 证据：2026-Q3 YiVad 新品搜索模块，严格 70/20/10 执行 1 个月后跨模块集成 Bug 反而 +18%，原因：跨模块接口多，单测无法覆盖。改成 60/30/10 后回归 Bug 21 天内 -24%。动作：A-01 金字塔差距表增加「阶段 A/B/C」切换列；A-07 T1 触发时首先允许切换阶段法，而不是降比例。

> **S5**「Exploratory testing fills the gap where automation cannot go.」
> **So-What**：A-03 Charter SOP 第 5 条「风险」强制 1 条。

> **S6**「Bugs are cheaper to fix the earlier they are caught.」
> **So-What**：A-04 YiPot 影子测试 1% 流量，上线前捕获 P0 0 次 计入 A-07。

> **S7**「CI is a safety net. The tighter the mesh, the safer you are.」
> **So-What**：A-02 tsc+clippy -Dw 0 error 不允许 warn 通过。
