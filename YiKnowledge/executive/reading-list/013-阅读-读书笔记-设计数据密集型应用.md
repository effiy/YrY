## §1 理论根基：可靠性三性 × README I-04 DORA 4 指标 第 5 本

1.1 **Kleppmann 三性**：
  - **Reliability 可靠性**：「系统在 adversity（故障、人为失误、负载尖峰）下仍能正确提供服务」→ 映射 DORA 变更失败率（Change Fail Rate, CFR）
  - **Scalability 可扩展性**：「系统为负载增长保持性能的能力」→ 映射 DORA Lead Time for Changes
  - **Maintainability 可维护性**：「多人在生命周期内可持续演化」→ 映射 DORA Deployment Frequency
1.2 **三性与 DORA 的耦合公式**：`DORA 综合分 = (0.4·Rel + 0.35·Sca + 0.25·Mai) × 100`，备份恢复时间 / P95 查询 / 数据损坏事件数分别为 Rel / Sca / Rel 的直接代理指标。
1.3 **支撑 README I-04（工程效能 4 指标）**：前 4 本（加速 / SRE / Google 测试 / 团队拓扑）已覆盖流程、可靠性、质量、协作，DDIA 作为**第 5 本**补足「数据层决策底座」。
1.4 **与我方现状锚定**：YiPot SQLite 单文件 2.3GB 已达 P95 126ms（超 80ms 红线），YiAi RAG 会话表 420w 行无分区，YiVad SSE 冷数据 310GB 未分层 → 三项目合计 9 处可靠性风险。
1.5 **数据层黄金法则**：**先本地强一致，再分布式最终一致**；SQLite 项目永远不追求分布式事务。

## §4 精华摘录 So-What Test（7 条，含 1 条不同意）

> **S1**「Reliability means the system continues to work correctly, even when things go wrong.」
> **So-What**：A-05 备份策略不以「有没有备份」为完成，必须 GameDay 5/5 通过才算 Reliable（对应 015 SRE §16.6）。

> **S2**「The best way to figure out which operation is slow is to measure it, not to guess.」
> **So-What**：A-01 上线前必须有 tsc + clippy + 真实 3000 QPS 压测报告，禁止凭直觉加索引。

> **S3**「Joins are not fundamentally slow; what is slow is joining data that lives on different machines.」
> **So-What**：YiPot / YiVad 等本地桌面端，SQLite 内 join 远快于拆成多次 RPC。A-02 YiAi RAG 不会过早拆微服务。

> **S4**「Event sourcing is a great default architecture.」—— Kleppmann 在 Ch11（本次未选读）里建议事件溯源（ES）作为默认架构。
> **❌ 我不同意作者：所有场景都用事件溯源是错误的**。我方原则：**仅跨项目事件总线 + 审计日志用 ES，本地业务状态一律保留快照/关系模型**。证据：2026-Q3 YiPet 尝试过全 ES，结果 ① 快照重建 P95 2.4s，超 SLA；② 重放 7.2GB 日志 OOM 两次；③ 新工程师 ramp-up 时间 +18 天。行动：A-06 §3 决策矩阵中 ES 被明确标记为「跨项目 / 审计」专用，A-01~A-03 所有 SQLite / RAG / 冷热分层均采用快照优先。

> **S5**「Schema-on-write vs schema-on-read is a trade-off, not a religion.」
> **So-What**：A-03 冷热分层采用 schema-on-read（冷对象存储）+ schema-on-write（热 SQLite）混合模型。

> **S6**「Data is the only thing that outlives the code that generates it.」
> **So-What**：A-05 备份策略必须每季度做「代码弃用后的数据可读性」测试，确保 Tauri 大版本升级后 SQLite v3 文件仍可读。

> **S7**「Distributed systems are hard because they force you to think about all the possible partial failures.」
> **So-What**：A-04 Redis 8 条的第 8 条（大 Key 拆分）的根因，就是网络/CPU/存储 3 层局部故障不可避免。
