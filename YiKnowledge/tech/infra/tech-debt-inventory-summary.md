# 技术债务盘点（Tech Debt Inventory）摘要

> 本摘要说明技术债是什么、怎么分类、怎么管；空白可填表单见 [tech-debt-inventory-template.md](./tech-debt-inventory-template.md)。

## 1. 是什么

技术债：为了短期速度而做的次优技术决策留下的"利息"。Martin Fowler 用金融比喻：

- **故意债务**：明知不优但快速出 demo，计划后续偿还（合理）
- **意外债务**：当时不知不优，后期才发现（不可避免）
- **鲁莽债务**：明知不优且无偿还计划（应避免）

技术债本身不是问题，**没盘点也没偿还计划**才是问题。

## 2. 为什么管

技术债有"利息"：随时间增长，新增功能成本上升、bug 率上升、新人上手慢。常见后果：

- 改一个简单功能要动 5 处代码
- 测试覆盖率低，回归靠手测
- 同样的 bug 反复出现
- 新成员要 3 个月才能独立

无偿还计划时，利息复利——最终产品发布速度从 1 周变 1 月。

## 3. 分类

按域 + 严重度二维分类。

### 按域

| 域 | 典型债 |
|---|---|
| 代码 | 重复代码、长函数、深嵌套 |
| 测试 | 覆盖率低、依赖手测、flaky test |
| 架构 | 服务边界不清、循环依赖、共享数据库 |
| 依赖 | 旧版本、CVE、废弃库 |
| 数据 | schema 混乱、无迁移脚本、脏数据 |
| 文档 | 缺失、过时、与代码不同步 |
| 部署 | 手动步骤、配置散落 |
| 监控 | 黑盒、无告警、误报多 |

### 按严重度

| 等级 | 含义 | 利率 |
|---|---|---|
| 高 | 阻碍日常开发，每迭代都受影响 | 利率高，优先偿还 |
| 中 | 影响特定模块或新功能 | 利率中，季度内还 |
| 低 | 不影响日常但迟早要还 | 利率低，机会偿还 |

## 4. 利息评估

每条债务估两个数：

1. **当前利息**：每月因此债损失的时间 / 人力（人天 / 月）
2. **偿还成本**：还清需要的人天

若 利息 > 偿还成本 / 3 → 应立刻偿还。

## 5. 季度清偿优先级

### 决策矩阵

| 影响范围 | 利率 | 偿还成本 | 优先级 |
|---|---|---|---|
| 阻碍战略主题 | 高 | 低 | P0（立刻） |
| 阻碍战略主题 | 高 | 高 | P1（季度内） |
| 阻碍日常开发 | 高 | 低 | P1 |
| 阻碍日常开发 | 中 | 中 | P2 |
| 单点问题 | 低 | 低 | P3（机会时） |
| 单点问题 | 低 | 高 | 不还（不值得） |

### 偿还节奏

- 每迭代分配 15-20% 产能给债务偿还
- P0 / P1 进入迭代规划
- P2 / P3 机会主义偿还（碰巧改相关代码时一起还）

## 6. 评估方法

### 定量

- 每条债务：当前利息（人天 / 月） + 偿还成本
- 总债务规模（人天）
- 季度清偿数 vs 新增数

### 定性

- 开发满意度（"你被什么拖慢"）
- 新人 onboarding 时长
- bug 回归率

## 7. 反模式

| 反模式 | 现象 | 修复 |
|---|---|---|
| 只记不还 | 债务清单涨不还 | 强制每迭代分配产能 |
| 不区分类型 | 全叫"重构" | 分类 + 严重度 |
| 偿还无 PRD | 业务不批 | 把债与业务收益挂钩 |
| 大爆炸重构 | 一切重写 | 增量偿还（strangler fig） |
| 一次性偿还 | 季末突击 | 每迭代稳态偿还 |
| 不衡量 | 上线后不知是否还清 | 加监控指标验证 |

## 9. 落地节奏

| 时点 | 事项 |
|---|---|
| 季初 | 盘点全债，标 P0-P3 |
| 每迭代 | 偿还 P0/P1 一两条 |
| 季末 | 复审清单，新增 / 还清 / 撤销 |
| 半年 | 战略级债务重审，可能需要项目立项 |
