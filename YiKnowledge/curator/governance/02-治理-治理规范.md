# 知识库治理流程

> **4 种角色，3 层节奏，1 条生命周期。** 治理模型保障 YiKnowledge 持续健康、可检索、可信任。

## 治理角色

| 角色 | 担任者 | 职责 |
|---|---|---|
| **Curator（管理者）** | 知识库维护者 | 掌管目录结构、命名规范、frontmatter 合规。执行定期审查。批准新增内容分类。 |
| **Author（作者）** | 任意团队成员 | 创建和更新知识文件。发布前执行[就绪检查清单](./readiness-checklist.md)。 |
| **Reviewer（审查者）** | 领域专家（角色负责人） | 审查所属领域内容的准确性和新鲜度。标记过时或待废弃内容。 |
| **Archivist（归档员）** | Curator（可委派） | 将废弃内容移至归档区。维护[归档索引](../archive/README.md)。 |

### 角色协作关系

```
Author 创建内容 → Curator 门禁检查 → Reviewer 领域审查 → Archivist 生命周期收尾
```

四种角色形成一条完整的质量保障链：作者负责产生内容，管理者负责结构合规，审查者负责领域准确性，归档员负责善终。

### 适用场景

- 新增团队成员时，分配 Author 角色并引导阅读[就绪检查清单](./readiness-checklist.md)
- 季度审查时，Reviewer 对所属目录逐一核查内容准确性
- 内容废弃时，Archivist 按归档流程执行（保留 6 个月宽限期后迁移）

## 审查节奏

### 每日（轻量级）

- **收件箱扫描** — 检查 `inbox.md` 中是否有新的未分类内容。24 小时内完成分类到对应角色目录。
- **Frontmatter 抽查** — 核验当日新增文件的 `title`、`tags`、`category`、`status` 是否齐全。

### 每周（中等强度）

- **分类队列清空** — 处理 `triage.md` 队列。每项已分类内容分配角色目录并标记 `lifecycle: triage`。
- **新鲜度扫描** — 执行 `rg "^last_verified: 202[0-5]" YiKnowledge -l` 查找超过一年未验证的文件，标记待审查。
- **死链检查** — 验证最近修改文件中交叉引用的链接是否仍可解析。

### 每季度（深度审查）

- **全面审计** — 逐一审查所有文件。更新 `last_verified` 日期。将过时内容标记为 `status: deprecated`。
- **角色边界检查** — 验证无内容漂移到错误的角色目录。对照[流水线阶段定义](../../README.md#pipeline-stages)进行交叉检查。
- **归档清理** — `status: deprecated` 超过 6 个月的文件移至 `curator/archive/`。
- **指标更新** — 更新[知识健康看板](./dashboard-knowledge-health.md)，刷新文件计数、生命周期分布和 frontmatter 合规率。

### 审查节奏的执行优先级

| 节奏 | 预计耗时 | 执行者 | 失败后果 |
|---|---|---|---|
| 每日 | 5-10 分钟 | Curator | 未分类内容堆积，收件箱膨胀 |
| 每周 | 15-30 分钟 | Curator + Reviewer | 分类队列积压，内容精炼停滞 |
| 每季度 | 1-2 小时 | 全体角色 | 知识库整体老化，信任度下降 |

## 知识生命周期

```
inbox → triage → active → reference → archive
  │        │        │         │           │
  │        │        │         │           └─ 废弃超过 6 个月，移至 curator/archive/
  │        │        │         └─ 稳定的参考材料，每年审查
  │        │        └─ 活跃维护内容，每季度审查
  │        └─ 已分类但未精炼，每周审查
  └─ 未分类的新内容，每日审查
```

### 生命周期转换规则

| 从 | 到 | 触发条件 | 执行动作 |
|---|---|---|---|
| `inbox` | `triage` | 内容已分类到角色目录 | 设置 `lifecycle: triage`，添加角色特定的 `tags` |
| `triage` | `active` | 内容已精炼并格式化 | 设置 `lifecycle: active`、`status: stable`，补充 `benefit` 和 `acceptance_criteria` |
| `active` | `reference` | 内容稳定，不再频繁更新 | 设置 `lifecycle: reference`、`review_cycle: yearly` |
| `active` | `archive` | 内容被取代或不再相关 | 设置 `status: deprecated`，原地保留 6 个月，然后移至 `curator/archive/` |
| `reference` | `archive` | 内容过时 | 同 active → archive 流程 |

### 生命周期决策树

```
内容是否仍有参考价值？
├── 是 → 是否需要持续更新？
│   ├── 是 → lifecycle: active（每季度审查）
│   └── 否 → lifecycle: reference（每年审查）
└── 否 → 是否有替代内容？
    ├── 是 → lifecycle: archive（添加 superseded_by 链接）
    └── 否 → lifecycle: archive（注明废弃原因）
```

## 内容标准

所有知识文件在离开 `triage` 前必须满足以下最低标准：

1. **Frontmatter 完整** — 所有必填字段齐全（`title`、`tags`、`category`、`created`、`updated`、`source`、`type`、`status`）
2. **命名合规** — kebab-case，仅使用连字符，不使用下划线或数字
3. **角色边界正确** — 内容属于且仅属于一个角色目录
4. **收益说明** — `benefit:` 字段回答"读者能获得什么？"
5. **验收标准可验证** — `acceptance_criteria:` 条目是可证伪的陈述
6. **无死链** — 所有 `related:` 和正文中的链接均指向已存在文件

## 治理流程详解

### 新增内容

1. Author 执行[就绪检查清单](./readiness-checklist.md)（10 题门禁）
2. Author 将文件放置在正确的角色目录中（最多 3 级深度）
3. Curator 在 24 小时内验证 frontmatter 和命名（每日扫描）
4. 文件进入 `lifecycle: triage` → 每周审查将其提升为 `active`

### 审查已有内容

1. 季度审计识别 `last_verified` 日期陈旧的文件
2. Reviewer 对照当前实际情况检查内容准确性
3. 更新 `last_verified` 和 `updated` 日期
4. 如果内容不再准确 → 标记为 `status: deprecated` 或进行更新

### 归档内容

1. 文件标记为 `status: deprecated` 并附说明（解释废弃原因）
2. 原地保留 6 个月（宽限期，允许撤销）
3. 6 个月后，Curator 将文件移至 `curator/archive/` 并在归档索引中添加条目
4. 更新所有指向该归档文件的交叉引用

### 归档操作的升级路径

```
文件标记 deprecated
    ↓
6 个月宽限期（期间可恢复为 active）
    ↓
Curator 确认无交叉引用阻断
    ↓
移至 archive/ 目录
    ↓
在归档索引中记录（日期 / 原因 / 替代文件）
```

## 治理指标

每季度跟踪以下指标以衡量知识库健康度：

| 指标 | 目标值 | 测量方式 |
|---|---|---|
| Frontmatter 合规率 | ≥ 95% | 必填字段齐全的文件数 / 总文件数 |
| 死链数量 | 0 | 自动化交叉引用检查 |
| 陈旧内容比例 | ≤ 10% | `last_verified` 超 1 年的文件数 / 总文件数 |
| 收件箱滞留时间 | ≤ 24h | 收件箱项目的最大滞留时长 |
| 分类队列积压 | ≤ 20 项 | `lifecycle: triage` 文件计数 |
| 角色均衡度 | 无角色 < 5% | 每个角色的文件数 / 总文件数 |

### 指标异常的处置

| 指标告警 | 紧急程度 | 应对措施 |
|---|---|---|
| 收件箱滞留 > 48h | 高 | 立即分类，暂停新内容收集 |
| 分类队列 > 30 项 | 中 | 本周内完成队列清空，延期不超过一周 |
| 陈旧内容 > 20% | 中 | 季度审查中优先处理，逐文件更新 last_verified |
| 死链 > 0 | 低 | 修复或移除对应链接，记录在审查日志中 |

## 反模式

- **为"快速"添加而跳过就绪检查清单。** 缺乏 proper frontmatter 的文件对 RAG 检索和基于 grep 的搜索不可见。检查清单需要 2 分钟；6 个月后找到一个未分类的文件需要 20 分钟。
- **将内容归档到错误的角色目录。** "差不多就行了"会造成交叉引用断裂和流水线模型混乱。使用[角色边界决策树](../../README.md#role-boundary-quick-reference)。
- **归档时不更新交叉引用。** 死链会降低整个知识库的信任度。归档前务必用 `rg` 搜索文件路径。
- **让分类队列无限增长。** 大量分类积压表明内容在被收集但未被精炼。上限设为 20 项；超过此限制，暂停新收集直到积压清空。
- **将治理流程视为一次性工作。** 治理是持续性运营活动，不是上线前的 checklist。每日/每周/每季度节奏是维持知识库健康的必要条件。
