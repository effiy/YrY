# 知识库收件箱

> **未分类内容的统一入口。** 此处的条目需在 24 小时内分类到对应角色目录，并移至 `triage.md`。若列表超过 10 项，暂停新内容收集直至积压清空。

## 适用场景

收件箱是知识进入知识库的第一个站点。所有新想法、外部链接、会议笔记、灵感碎片都先进入此处，经过分类后再进入知识库主体。这一机制确保：

- **无遗漏** — 所有知识输入都有迹可循
- **无污染** — 未经分类的原始内容不会直接进入角色目录
- **可追溯** — 每条知识的来源和时间可回溯

## 使用说明

1. **添加新条目** — 在此表格中新增一行，填写日期、来源（如"用户反馈""Slack 讨论""技术博客"）和简要描述
2. **每日清空** — Curator 每天花 5-10 分钟扫描收件箱，将条目分类到对应角色目录
3. **升级机制** — 超过 7 天未处理的条目升级给 Curator 做决策

## 条目格式说明

每条收件箱记录至少包含以下信息：

- **日期** — 条目进入收件箱的时间（`YYYY-MM-DD` 格式）
- **来源** — 谁/什么系统生成了这条内容（如"Ruiyi Slack""RSS 摘要""用户访谈记录"）
- **描述** — 一句话概括内容主题，便于 Curator 快速判断归属角色
- **处理动作** — 清空时填写，记录分类到哪个角色目录

## 清空流程

1. 对每条条目，使用[角色边界决策树](../../README.md#role-boundary-quick-reference)确定正确的角色目录
2. 在目标目录中创建 stub 文件，包含最少 frontmatter（`title`、`tags`、`category`、`created`、`source`、`type: original`、`status: draft`、`lifecycle: triage`）
3. 将条目从此表移至 `triage.md`
4. 如果角色归属不明确，保留在收件箱并标记 `[待分类]`

### 清空流程的常见决策场景

| 内容类型 | 典型归属角色 | 判定依据 |
|---|---|---|
| "RAG 检索不准的排查过程" | engineer/ | 工程实现类 → engineer |
| "新模型评测结果对比" | aier/ | AI 技术选型 → aier |
| "竞品最新功能分析" | executiver/ | 行业情报 → executiver |
| "用户访谈原始记录" | producter/ | 需求发现 → producter |
| "部署故障处理经过" | srer/ | 运维操作 → srer |
| "技术选型的权衡讨论" | leader/ | 架构决策 → leader |
| "知识库结构优化建议" | curator/ | KB 治理 → curator |

## 升级机制

条目在收件箱中超过 7 天时，升级给 Curator 做决策：

- **立即分类** — 内容有价值但被遗漏，立即执行分类
- **归档处理** — 内容已失去时效性，归档为 `lifecycle: archive` 并注明未分类原因

### 升级的判断标准

- **内容是否仍有参考价值？** 是 → 分类；否 → 归档
- **内容的来源是否可回溯？** 是 → 保留来源信息后分类；否 → 标注来源缺失后决定
- **是否有人在等待这条知识？** 是 → 优先分类；否 → 正常节奏处理

## 反模式

| 反模式 | 失效原因 | 正确做法 |
|---|---|---|
| 收件箱长期为空（从不收集） | 知识只能靠记忆，隐性知识持续流失 | 建立收集习惯：每次会议、每篇好文章、每个 bug 都有一条收件箱记录 |
| 收件箱条目写得过于简略 | 一周后无法回忆起上下文 | 每条描述至少包含一个具体名词（谁、什么系统、什么问题） |
| 跳过收件箱直接放入角色目录 | 未经审查的内容混入知识库主体 | 所有新内容必须先经过收件箱 → 分类队列流程 |
| 收件箱条目超过 10 条仍不处理 | 积压造成心理负担，清空变成艰难任务 | 设置硬性上限 10 条，超过后暂停收集 |
