# 知识库就绪检查清单

> **10 题门禁。** 发布任何新知识文件前执行。全部 10 题必须通过。若某题不适用，在提交信息中说明原因。

## 适用场景

- **新建知识文件** — 发布前必检，确保格式合规
- **大幅修改已有文件** — 修改后重新执行（特别关注第 5、6、8 题）
- **从 triage 提升到 active** — 提升前完整执行，作为提升的门禁条件

## 使用说明

1. 逐题执行，每通过一题打勾
2. 失败项先修复、再重新检查
3. 全部通过后发布
4. Curator 在每日扫描中将执行二次验证

## 检查清单

### 1. 文件是否有清晰、描述性的标题？

- [ ] **通过** — `title:` 是完整的句子或描述性短语，不是模糊标签
- **失败** — `title: "笔记"`、`title: "杂项"`、`title: "其他"`
- **正例**：`title: "RPC 参数名称跨项目契约 —— filter 而非 query"`、`title: "YiVad ProTable 泛型约束修复策略"`
- **判定要点**：读者只读标题能否判断该文件与自己是否相关

### 2. 文件是否在正确的角色目录中？

- [ ] **通过** — 文件位于且仅位于一个角色目录下（`aier/`、`curator/`、`engineer/`、`executiver/`、`leader/`、`producter/`、`srer/`）
- **失败** — 文件在根目录、在错误的角色目录、或在多个角色目录中重复
- **提示**：使用[角色边界决策树](../../README.md#role-boundary-quick-reference)

### 3. 文件名是否遵循 kebab-case 规范？

- [ ] **通过** — `lowercase-with-hyphens.md`，无下划线、无数字、无空格
- **失败** — `My_File.md`、`file123.md`、`File Name.md`
- **正例**：`implement-an-api.md`、`respond-to-an-incident.md`
- **含中文名规则**：`{序号}-{中文描述}.md`，如 `01-需求评审模板.md`

### 4. 是否所有必填 frontmatter 字段齐全？

- [ ] **通过** — `title`、`tags`（3-5 个）、`category`、`created`、`updated`、`source`、`type`、`status` 全部存在
- **失败** — 任一必填字段缺失或为空
- **检查方法**：肉眼扫描文件头部的 YAML 区块，对照此列表逐字段确认

### 5. `benefit:` 字段是否具体且面向读者？

- [ ] **通过** — 用一句话回答"读者能获得什么？"。正例：`"Engineers find the right API pattern for cross-service communication"`
- **失败** — `benefit: "有用"`、`benefit: "值得了解"`、或从其他文件复制
- **编写技巧**：使用"角色 + 动词 + 具体收益"句式，如"产品经理找到合适的优先级评估框架"

### 6. `acceptance_criteria:` 是否可验证？

- [ ] **通过** — 每条标准是可证伪的陈述。正例：`"列出 3 个反模式及失效原因"`
- **失败** — 模糊标准如 `"内容优质"`、`"信息有用"`
- **编写技巧**：使用数字量化——"X 个 Y 包含 Z"的形式最容易验证

### 7. `category:` 字段是否正确？

- [ ] **通过** — `category: <role>/<subdir>` 与文件实际路径匹配。根目录文件使用 `category: root`
- **失败** — 文件在 `engineer/build/` 中但 `category: engineer`（应为 `category: engineer/build`）
- **检查方法**：对比文件路径后两段目录名与 category 字段值

### 8. 所有 `related:` 链接是否指向存在的文件？

- [ ] **通过** — `related:` 中的每个路径指向一个实际存在的文件或目录
- **失败** — 死链（逐个点击链接或在终端执行 `ls` 验证每个路径）
- **检查方法**：
  ```bash
  # 提取 related 字段中的路径并在文件系统验证
  grep -A5 "^related:" <file> | grep "^  -" | awk '{print $2}' | while read p; do
    ls "$(dirname <file>)/$p" > /dev/null 2>&1 || echo "DEAD: $p"
  done
  ```

### 9. 内容是否在角色的边界内？

- [ ] **通过** — 内容回答该角色的核心问题（例如：engineer = "如何实现"，leader = "如何决策"）
- **失败** — 架构决策放在 `engineer/` 而非 `leader/`，或实现模式放在 `leader/` 而非 `engineer/`
- **速查表**：

| 角色 | 核心问题 | 反面示例 |
|---|---|---|
| engineer | "如何实现 X？" | 不放 PRD、不放投资决策 |
| leader | "如何决策 Y？" | 不放代码示例、不放部署步骤 |
| producter | "用户需要什么？" | 不放技术架构图、不放代码审查 |
| srer | "如何运维 Z？" | 不放需求文档、不放战略分析 |
| aier | "AI 能做什么？" | 不放传统开发模式、不放业务指标 |
| executiver | "市场往哪走？" | 不放具体 API 设计、不放运维故障 |
| curator | "知识库如何管理？" | 不创建任何领域内容 |

- **快速判定**：如果文件回答的是"如何做 X"，X 是哪种工作，就放在对应该工作的角色目录

### 10. 内容是否新增信息（非重复已有内容）？

- [ ] **通过** — 内容要么覆盖新主题，要么为已有主题提供真正不同的视角
- **失败** — 内容只是重述已有文件，无新增洞察
- **检查方法**：
  ```bash
  rg "^title:" YiKnowledge -l | xargs rg -l "<关键词>" 
  ```
  先全局搜索相关关键词，确认无重复后再创建

## 发布后

文件发布后，Curator 将在下一次每日扫描中验证：

- Frontmatter 合规（自动化检查）
- 命名规范（自动化检查）
- 角色边界（人工审查）
- 交叉引用有效性（自动化检查）

## 常见失败

| 失败类型 | 出现频率 | 修复方法 |
|---|---|---|
| `category:` 字段错误 | 常见 | 将 `category:` 与文件目录路径对齐 |
| 缺少 `benefit:` | 常见 | 添加一句话回答"读者能获得什么？" |
| `related:` 死链 | 常见 | 提交前对每个路径执行 `ls` 验证 |
| 角色目录错误 | 偶发 | 使用角色边界决策树 |
| 文件名含下划线 | 少见 | 改为连字符，更新所有交叉引用 |
| `acceptance_criteria:` 过于模糊 | 常见 | 用数字量化——"3 个例子""5 个步骤" |

## 反模式

- **因为"只是快速笔记"而跳过检查清单。** 没有 frontmatter 的快速笔记对 RAG 和 grep 不可见。写都写了，花 2 分钟走完检查清单是值得的。
- **从另一个文件复制 frontmatter 而不更新。** 过时的 `category:`、`tags:` 和 `benefit:` 字段误导搜索和检索。每个字段都应反映实际内容。
- **将内容归档到"最接近的"角色而非正确的角色。** "这跟工程有点关系"不是把商业战略文档放在 `engineer/` 的有效理由。使用决策树。
- **检查清单形同虚设——只是打勾而不真正审查。** 走形式的检查清单比没有更糟糕，因为它让团队产生虚假的安全感。每道题都要认真验证。
