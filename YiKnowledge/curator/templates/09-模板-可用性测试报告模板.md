# 可用性测试报告模板

> **何时使用：** 可用性测试会话结束后。文档化测试了什么、观察到了什么、应该改什么。区别于用户研究访谈（探索需求）——可用性测试评估的是**具体的设计方案**。用户研究问"你需要什么"，可用性测试问"你能用这个吗"。

## 适用场景

- 新功能或重大 UI 改进上线前的设计验证
- 原型阶段的交互流程测试
- 关键用户流程的可用性评估（如注册、支付、复杂搜索）
- 不适用于：需求探索（用用户研究访谈模板）、bug 收集（bug 应走 bug 报告流程）

## 使用说明

1. 测试前定义测试任务和成功标准
2. 参与者应来自目标用户群体（不要用团队成员）
3. 测试中观察但不引导——让用户自己探索
4. 每条发现必须包含严重度评级

### 参与者招募原则

- **最少 5 人** — Jakob Nielsen 的研究表明 5 个用户能发现约 85% 的可用性问题
- **目标用户** — 不要用团队成员（他们太了解产品）
- **多样性** — 包含新手和专家用户，覆盖不同的使用频率

### 严重度评级详细定义

| 级别 | 定义 | 举例 |
|---|---|---|
| Critical | 用户无法完成任务，或反复尝试后放弃 | "支付按钮点击无效，所有用户都无法完成购买" |
| Major | 用户遇到显著困难，但最终能通过绕路完成 | "用户花 2 分钟才找到搜索框，预期应该在 5 秒内" |
| Minor | 用户感到困扰但不影响任务完成 | "按钮文案不清晰，用户犹豫了 3 秒才点击" |
| Cosmetic | 纯视觉问题或不影响使用的细节 | "间距稍大，但不影响可读性" |

## 反模式

| 反模式 | 失效原因 | 正确做法 |
|---|---|---|
| 报告无严重度评级 | 团队无法排优；每条都感觉很紧急 | 每条发现评级：Critical → Major → Minor → Cosmetic |
| 用团队成员做测试 | 他们太了解产品；无法模拟真实用户 | 招募匹配目标用户画像的参与者 |
| 无任务完成数据 | 无法判断设计是否真的有效 | 测量并报告完成率和每个任务的耗时 |
| 发现无建议 | 把问题抛给团队却不提供解决方案 | 每条发现应附带具体建议 |
| 只有 1-2 个参与者 | 样本太小，无法发现大多数问题 | 最少 5 人（每类用户角色） |
