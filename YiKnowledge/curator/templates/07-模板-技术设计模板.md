# 技术设计模板

> **何时使用：** 对于跨多个服务、引入新模式或具有显著实现复杂度的功能。技术设计是 PRD（定义*什么*）和代码（定义*如何*）之间的桥梁。技术设计的目标是**降低实现风险**——在开始编码之前暴露架构决策和边界情况。

## 适用场景

- 新服务或新模块的开发
- 引入新的设计模式或技术栈
- 跨团队（YiAi/YiVad/YiPet）的功能
- 对现有架构有重大影响的修改
- 不适用于：单文件 bug 修复、微小 UI 调整、已有明确模式的常规 CRUD 功能

## 使用说明

1. PRD 完成后开始编写技术设计
2. 专注于架构和数据流，代码具体实现放在"实现细节"部分
3. 非功能性需求（性能、安全、可观测性）与功能性需求同等重要
4. "刚好够"的设计——不要为一周的开发量写三周的设计文档

## 反模式

| 反模式 | 失效原因 | 正确做法 |
|---|---|---|
| 设计文档全是代码片段 | 缺失架构推理；审查者无法评估权衡 | 从架构和数据流开始；代码放在最后 |
| 没有边界情况 | 实现过程中遇到意外状态而崩溃 | 列出至少 3 个边界情况及预期行为 |
| 跳过非功能性需求 | 性能、安全、可观测性沦为事后补救 | 在实现开始前定义 NFR |
| 设计文档写成瀑布式产物 | 团队花一周写、一周审查、然后才开始编码 | 写刚好够用的设计来降低风险；实现过程中持续迭代 |
| 只有正常路径（happy path） | 一旦有异常就不知道该如何处理 | 至少覆盖：空数据、超时、并发冲突、权限不足 |
