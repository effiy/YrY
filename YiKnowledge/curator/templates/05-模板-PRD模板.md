# PRD 模板 — 产品需求文档

> **何时使用：** 任何重要功能开发之前。PRD 定义*构建什么*和*为什么*——不指定*如何构建*（那是技术设计的事）或*选什么技术*（那是 ADR 的事）。PRD 是产品需求的"Why + What"，而非"How"。

## 适用场景

- 新功能开发（预计 > 1 周的开发量）
- 重大功能改造（影响用户使用流程）
- 跨团队协作的功能（需要多方对齐需求）
- 不适用于：微小的 bug 修复、纯技术重构（无用户可见变化）

## 使用说明

1. 从用户问题和证据出发，而非从解决方案出发
2. 范围（in/out of scope）必须明确写出——这是 PRD 中最容易被忽略但最重要的部分
3. 成功指标必须可测量——没有数字的 PRD 等于没说
4. 写完后找一个工程师通读一遍，确认没有过度指定实现细节

## 2. 用户问题（User Problem）

> 谁有这个问题？我们怎么知道的？

- **目标用户：** {{用户画像或角色}}
- **问题陈述：** {{一句话："作为 [用户]，我想要 [目标] 以便 [原因]"}}
- **证据：** {{用户研究、支持工单、分析数据}}

### 证据的质量级别

| 级别 | 证据类型 | 可信度 |
|---|---|---|
| 强 | 用户行为数据（埋点、转化率） | 高 |
| 中 | 用户访谈（5+ 人） | 中 |
| 弱 | 个人直觉/竞品在做/有人反馈过一次 | 低 |

优先使用强证据驱动决策。如果仅有弱证据，PRD 应标注为"实验性"并包含更小的初始范围。

### 用户故事（User Stories）

| 优先级 | 故事 | 验收标准 |
|---|---|---|
| P0 | {{作为 [用户]，我可以 [行动]}} | {{可验证的条件}} |
| P1 | {{作为 [用户]，我可以 [行动]}} | {{可验证的条件}} |

### 优先级定义

- **P0** — 没有这一条，功能完全不可用（must-have）
- **P1** — 没有这一条，功能可用但体验不完整（should-have）
- **P2** — 锦上添花，可推迟（nice-to-have）

## 4. 成功指标（Success Metrics）

> 我们如何知道这个功能成功了？定义可衡量的结果。

| 指标 | 基线值 | 目标值 | 测量方法 |
|---|---|---|---|
| {{指标名称}} | {{当前值}} | {{目标值}} | {{如何测量}} |

### 指标类型指南

- **用户行为指标** — 如使用率、留存率、完成率
- **业务指标** — 如转化率、收入影响
- **质量指标** — 如错误率、加载时间、用户满意度评分

每项指标必须回答三个问题：（1）现在的值是多少 （2）目标值是多少 （3）用什么工具/方法测量。

## 反模式

| 反模式 | 失效原因 | 正确做法 |
|---|---|---|
| 在 PRD 中写实现细节 | 模糊了产品和工程的边界；工程师失去参与感 | 描述用户*体验*到什么，而非代码*如何*工作 |
| 没有范围外部分 | 利益相关方默认包含所有 | 明确列出推迟或排除的内容 |
| 模糊的成功指标（"更好的 UX"） | 无法判断功能是否成功 | 定义可测量的指标，含基线和目标 |
| PRD 写成小说 | 没人读 20 页的 PRD | 保持精炼；详细设计用链接单独放 |
| 跳过用户问题直接写解决方案 | PRD 变成了"我想要这个按钮"的愿望清单 | 始终从用户问题和证据出发 |
