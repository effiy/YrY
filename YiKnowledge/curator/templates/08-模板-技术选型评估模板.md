# 技术选型评估模板

> **何时使用：** 当需要在多个技术选项间做选择时（库、框架、数据库、服务）。评估结果为最终决策的 ADR 提供输入。选型评估是 ADR 的前置步骤——先评估、再决策、再记录。

## 适用场景

- 选择新的前端/后端框架或库
- 选择数据库或存储方案
- 选择第三方服务（如邮件、支付、AI 平台）
- 选择工具链（如构建工具、测试框架、监控方案）

## 使用说明

1. 先定义"必须满足的需求"——如果候选方案不满足任何一条必须需求，直接淘汰
2. 权重加起来必须是 1.0（或 100%）
3. PoC 不是必需的——但如果是锁定时间超过 6 个月的关键决策，必须做 PoC
4. 评分是主观的——让至少 2 个人独立打分，取平均值

### 评估标准指南

| 标准 | 评估要点 |
|---|---|
| 功能匹配度 | 是否解决问题？功能完整度 vs. 我们的必需求 |
| 性能 | 基准测试、延迟、在预期负载下的吞吐量 |
| 开发体验 | 文档质量、API 设计、调试工具、本地开发体验 |
| 社区与生态 | GitHub Star、贡献者、Stack Overflow 活跃度、插件生态 |
| 运营成本 | 许可、托管、维护、学习曲线 |
| 团队熟悉度 | 团队是否已有经验？上手时间需要多长？ |
| 安全性 | CVE 历史、依赖数、维护者响应速度 |

### 评分准则

| 分数 | 含义 |
|---|---|
| 5 | 优秀——超出预期 |
| 4 | 良好——满足大部分需求 |
| 3 | 可接受——满足基本需求但有不足 |
| 2 | 差——多项不足 |
| 1 | 不可用——严重缺陷 |

## 反模式

| 反模式 | 失效原因 | 正确做法 |
|---|---|---|
| 无权重评估 | 标准并非同等重要；无权重的分数有误导性 | 按对项目的重要性对每个标准加权 |
| 简历驱动选型（选最流行的） | 团队无法维护；对问题来说过度设计 | 技术匹配问题，而非匹配简历 |
| 关键决策不做 PoC | 规格书上看起来好但实践中失败 | 对任何锁定超过 6 个月的决策，至少对前 2 名做 PoC |
| 忽略团队熟悉度 | 团队花 3 个月学习而非构建 | 诚实地评估团队技能权重；把上手时间计入时间线 |
| 评分过于慷慨 | 所有候选方案都 4 分以上，失去了筛选意义 | 使用严格的评分标准，给最差候选方案打 1-2 分是正常的 |
