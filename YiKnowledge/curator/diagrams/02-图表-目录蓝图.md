# 目录蓝图 — 用户如何找到内容

> **目的：** YiKnowledge 目录树的可视化地图。每个目录标注了用途。用户应在 2 次跳转内触达任意内容。这张图是知识库的导航骨架——新成员用它理解结构，老成员用它验证新内容的位置。

## 适用场景

- **新人入职** — 目录蓝图是新成员理解知识库结构的入口地图
- **新增目录** — 添加新目录时更新蓝图，确保不超过 3 级深度
- **季度审查** — 验证目录结构是否仍合理，是否需要调整
- **内容归属决策** — 不确定内容放在哪个目录时，对照蓝图矩阵判断

## 使用说明

1. 新增子目录时在此蓝图中更新对应的角色行
2. 重命名目录时同步更新所有交叉引用
3. 每季度审查一次，确认目录结构未出现超过 3 级的深层嵌套
4. 如果某个子目录文件过多（> 30），考虑在该子目录下按主题再分一级

## 导航规则：最多 2 跳

```
第一跳：角色目录（如 engineer/）
第二跳：问题域（如 engineer/build/）
  → 找到文件：engineer/build/implement-an-api.md
```

**违规：** 如果用户需要 3 跳以上才能找到文件，目录层级过深。重构。

### 2 跳规则的原理

认知科学表明，人类在工作记忆中能舒适地保持 2 层上下文。第 3 层会显著增加认知负荷，降低导航效率。对于 AI（RAG 检索），深层嵌套也会增加目录过滤的复杂度。

## 目录命名的设计原则

1. **角色目录用英文小写** — 保持与 GitHub/文件系统的最佳兼容
2. **子目录用英文短名** — build/ship/learn/run 比 implementation/deployment/lessons/processes 更短且同样描述性
3. **中文内容文件允许中文名** — 当内容是中文时，文件名使用 `{序号}-{中文描述}.md` 格式
4. **禁止缩写** — `srer` 是角色名（Site Reliability Engineer），是可接受的。但子目录不使用缩写，`obs` 不替代 `observability`

## 反模式

| 反模式 | 失效原因 | 正确做法 |
|---|---|---|
| 目录超过 3 级深度 | 用户找不到内容；导航违反 2 跳规则 | 扁平化：合并子目录或将内容上提 |
| 两个目录范围重叠 | 内容归档到错误位置；出现重复 | 明确边界；使用 README.md 中的决策树 |
| 蓝图从不更新 | 蓝图显示旧结构；新目录对用户不可见 | 新增或重命名目录时同步更新蓝图 |
| 任务速查表过时 | 链接指向已被移动的文件 | 每季度验证速查表的每个链接 |
