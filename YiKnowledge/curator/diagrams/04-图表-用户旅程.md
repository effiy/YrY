# 用户旅程地图 — 知识如何流转

> **目的：** 描绘不同用户如何浏览知识库以达成目标。识别用户卡住的断点。每条旅程追踪从"我需要 X"到"我找到了 X"的完整路径，标注每一步的顺畅程度和摩擦点。

## 适用场景

- **知识库优化** — 当用户反馈"找不到东西"时，从旅程地图中找到断点
- **新角色目录建设** — 参考已有角色的旅程模式，设计新角色的导航路径
- **季度审查** — 验证每条旅程是否仍然顺畅，断点是否已修复
- **RAG 质量排查** — 当 AI 检索质量下降时，对照 AI 旅程的断点进行分析

## 使用说明

1. 每季度选择一条旅程走一遍：假扮该角色，从真实任务出发，看能否在 2 跳内找到所需文件
2. 遇到断点时记录在断点总结表中
3. 将修复断点纳入下个迭代的任务中
4. 添加新的消费者角色时（如 YiVad 的 PM 用户），补充对应的旅程

## 旅程 1：Engineer — "如何实现 X？"

```
起点：任务分配
  │
  ▼
1. 进入：阅读 PRD → producter/discovery/
  │ ✓ 路径清晰：PRD → ADR → 实现模式
  │
  ▼
2. 决策：阅读 ADR → leader/decisions/
  │ ✓ 按项目组织：yiai/、yivad/、yipet/
  │
  ▼
3. 实现：查找模式 → engineer/build/ 或 engineer/ship/
  │ ⚠ 断点：50 个文件，难以浏览。需要 grep 或 INDEX。
  │
  ▼
4. 参考：检查踩坑 → engineer/learn/lessons/gotchas/
  │ ✓ 按失败类型组织有序
  │
  ▼
终点：代码编写完成
```

**断点分析：** engineer/ 在 build/ship/learn/run 之间有 50 个文件。找到正确的模式需要 grep 搜索或预先知道文件名。

**改进措施：** 添加"按任务"索引："我想要..." → 文件路径。

### Engineer 旅程的优化路径

```
当前状态：需要 grep 才知道文件位置
    ↓
短期修复：在 engineer/ 的 INDEX 或 README 中添加"按任务"速查表
    ↓
中长期改进：在 YiVad aiChat 中实现"知识问答"功能，AI 直接根据任务推荐文件
```

## 旅程 2：Producter — "我们应该构建什么？"

```
起点：收到市场信号
  │
  ▼
1. 调研：查看行业 → executiver/industry/
  │ ⚠ 断点：reports/ 和 competitors/ 曾为空（现已填充）
  │
  ▼
2. 战略：评估框架 → executiver/strategy/
  │ ✓ Porter、SWOT、Blue Ocean、VRIO 均已存在
  │
  ▼
3. 定义：撰写 PRD → producter/discovery/write-a-prd.md
  │ ✓ 模板存在于 curator/templates/prd.md
  │
  ▼
4. 优先级：评分功能 → producter/frameworks/rice-ice-prioritization.md
  │ ✓ RICE/ICE、MoSCoW、Kano 均已存在
  │
  ▼
终点：PRD 获批
```

**断点分析：** 行业报告内容较薄。市场数据依赖外部来源。

**改进措施：** 接入 RSS 监控以追踪竞品；集成到 executiver/industry/reports/。

## 旅程 3：Leader — "我们应该选哪个技术？"

```
起点：需要做技术决策
  │
  ▼
1. 评估：使用选型模板 → curator/templates/tech-selection-evaluation.md
  │ ✓ 模板已存在，含评分矩阵
  │
  ▼
2. 决策：撰写 ADR → curator/templates/adr.md
  │ ✓ 模板已存在，含 Context/Decision/Alternatives/Consequences
  │
  ▼
3. 归档：存入 → leader/decisions/<project>/
  │ ✓ 按项目组织：yiai/、yivad/、yipet/
  │
  ▼
4. 参考：检查历史决策 → leader/decisions/
  │ ⚠ 断点：决策分散在不同项目间；缺少跨项目 ADR 索引
  │
  ▼
终点：ADR 发布
```

**断点分析：** 跨项目决策（如参数名称契约）没有明确的位置。

**改进措施：** 在 leader/decisions/ 中添加跨项目 ADR 分类。

## 旅程 4：AI — "RAG 引擎如何找到知识？"

```
起点：用户提问
  │
  ▼
1. 查询：RAG 引擎接收问题
  │ ✓ llama_index QueryFusionRetriever
  │
  ▼
2. 检索：混合搜索（向量 + 关键词）
  │ ⚠ 断点：检索质量取决于 frontmatter 质量
  │
  ▼
3. 排序：LLM 重排候选结果
  │ ✓ 配置中可选 LLMRerank
  │
  ▼
4. 合成：LLM 生成含引用的回答
  │ ✓ NumberSourcesPostprocessor 提供内联引用
  │
  ▼
5. 范围过滤：按 file_path、category 或 tags 过滤
  │ ⚠ 断点：范围过滤基于子串匹配；可能漏掉相关文件
  │
  ▼
终点：回答返回给用户
```

**断点 1：** Frontmatter 质量不一致。缺少 `benefit:` 或 `acceptance_criteria:` 字段降低检索准确度。

**断点 2：** 基于子串的范围过滤脆弱。`engineer` 匹配 `engineering` 但不匹配 `implementation`。

**改进措施：** 每周运行 frontmatter 合规检查；引入基于标签的范围过滤作为子串匹配的替代方案。

## 断点总结

| 断点 | 严重度 | 修复方案 | 负责人 |
|---|---|---|---|
| engineer/ 文件多难以浏览 | 中 | 添加"按任务"索引 | Curator |
| 行业报告内容较薄 | 低 | 接入 RSS 监控 | Executiver |
| 缺少跨项目 ADR 索引 | 低 | 添加跨项目分类 | Leader |
| Frontmatter 质量不一致 | 高 | 每周合规检查 | Curator |
| 基于子串的范围过滤 | 中 | 引入基于标签的范围过滤替代方案 | Engineer |

### 断点严重度定义

| 级别 | 定义 | 处置时间线 |
|---|---|---|
| 高 | 阻碍用户完成核心任务或导致 AI 回答错误 | 本周内修复 |
| 中 | 增加用户操作成本但可通过绕路解决 | 本月内修复 |
| 低 | 用户体验不够好但不影响完成任务 | 下季度内修复 |

## 反模式

| 反模式 | 失效原因 | 正确做法 |
|---|---|---|
| 旅程地图从不更新 | 断点变化了；旧地图误导 | 每季度更新；验证每条旅程仍然可用 |
| 断点只识别不修复 | 地图变成抱怨列表而非改进工具 | 每个断点指定负责人，追踪到解决为止 |
| 旅程只画"理想路径" | 用户实际走的路和理想路径不同 | 实际走一遍旅程，记录真实的摩擦点 |
