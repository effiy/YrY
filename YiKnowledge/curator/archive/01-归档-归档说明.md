# 归档索引 — 废弃内容登记表

> **目的：** 登记所有已废弃和已移除的内容。文件归档时，在此添加记录。永不删除记录——这是永久性的审计线索。归档不是删除，而是保留"我们曾经尝试过这个路径"的历史记忆。

## 适用场景

- **内容废弃** — 文件被新版本替代时，保留旧版本在归档区
- **审计回溯** — 需要了解某个决策的历史演变过程
- **季度清理** — `status: deprecated` 超过 6 个月的文件正式迁移至归档区
- **避免重复工作** — 查询归档记录可避免"重新发明已经被否决的轮子"

## 使用说明

1. 归档时在此表添加一条新记录
2. 记录中必须包含：废弃日期、完整文件路径、废弃原因、替代文件
3. 如果文件没有替代品，在"替代"列填写"无 — 直接废弃"
4. 每年审查归档区时考虑是否可物理删除（彻底不相关内容）

|---|---|---|---|
| （暂无记录） | — | — | — |

### 废弃记录格式说明

- **文件** — 文件在原角色目录中的相对路径，而非归档后的路径
- **废弃日期** — 标记 `status: deprecated` 的日期（不是实际移至 archive/ 的日期）
- **原因** — 一句话说明为何废弃。必须回答"未来的读者看了这条记录能否理解决策"
- **替代文件** — 如果有新版本替代，填写新文件的路径链接；如果没有，填写"无"

## 归档流程

1. 将文件从原角色目录移至 `curator/archive/`
2. 在上表中添加一条记录
3. 更新其他文件中指向该废弃文件的 `related:` 链接
4. 如果文件有替代品，在废弃文件的 frontmatter 中添加 `superseded_by:` 字段
5. 在审查日志中记录归档操作

### 归档流程图

```
文件标记 status: deprecated
    ↓
原地保留 6 个月宽限期（可撤销）
    ↓
Curator 确认无交叉引用阻断
    ↓
物理移至 curator/archive/
    ↓
在归档索引中登记（本文档）
    ↓
在审查日志中记录归档操作
    ↓
更新所有外部 related: 链接
```

## 废弃判定标准

| 判定条件 | 处置动作 |
|---|---|
| `last_verified` 超过 6 个月 | 标记 `status: deprecated`；30 天内无人更新则归档 |
| 内容被新文件替代 | 立即归档；添加 `superseded_by:` 链接 |
| 内容不再相关（功能已删除、项目已结束等） | 移至归档；在记录中注明原因 |
| 内容有严重错误或断裂 | 尽可能修复；如果主题本身不再相关则归档 |
| 内容重复（与另一文件高度重合） | 保留更完整/更新的版本，归档另一个 |

### 废弃判定的判断逻辑

```
该文件的内容是否仍然准确？
├── 是 → 更新 last_verified，保持 active
└── 否 → 是否有新的替代文件？
    ├── 是 → 立即归档，添加 superseded_by 链接
    └── 否 → 该主题本身是否仍然需要？
        ├── 是 → 修复/重写内容
        └── 否 → 标记 deprecated，6 个月后归档
```

## 归档区物理清理策略

| 条件 | 操作 |
|---|---|
| 归档超过 2 年 | 评估是否可物理删除（从 git 历史中仍可恢复） |
| 替代文件也已废弃 | 考虑同时清除新旧文件，保留最终版本的记录 |
| 引用了已不存在的系统/概念 | 可物理删除（内容已失去参考意义） |

## 反模式

| 反模式 | 失效原因 | 正确做法 |
|---|---|---|
| 直接删除废弃文件 | 审计线索丢失；无法看到曾经尝试过但放弃的路径 | 始终移至归档而非删除 |
| 归档时不更新交叉引用 | 其他文件中出现死链；RAG 召回断裂引用 | 归档前更新所有 `related:` 链接 |
| 归档记录无废弃原因 | 未来的读者不知道为何移除 | 每条记录必须包含原因和替代方案 |
| 归档区从不清理 | 归档区无限膨胀，失去"索引"的意义 | 每年物理清理一次，移除超过 2 年且无参考价值的文件 |
| 归档即遗忘 | 有价值的教训随文件一起被遗忘 | 归档时评估是否需将关键教训提取到 lessons/ 目录 |
