❔ How to read this report (click to collapse)

The §0–§4 lifecycle

Every scene follows the same five-section contract: §0 Effect Sketch (what + why), §1 Test Design (verification steps), §2 Output Inventory (artifacts produced), §3 Test Report (pass/fail matrix), §4 Self-Improvement (edge cases, improvements, limitations).

Verdict thresholds

Coverage = passedChecks / totalChecks per scene. pass ≥ 90%, partial 50–89%, fail < 50%. The composite score is the mean of all six scenes' coverage × 100, mapped to a letter grade (A ≥ 90, B ≥ 75, C ≥ 60, D ≥ 40, F < 40).

Keyboard shortcuts

1–6 jump to a scene · t back to top · l toggle theme · p print / save as PDF.

Refreshing the data

Verdicts are computed statically by scripts/analyze.mjs — the page never recomputes. Re-run node scripts/analyze.mjs <scope> <outDir> after source changes to refresh data.js.

Methodology & Limitations

What this report measures

Static analysis of the project filesystem: file inventory, facet detection (tests, docs, security, refs, deps), and per-scene verdict computation. The analyzer does NOT execute tests, run linters, or make network requests.

Verdict computation

Per-scene coverage = passedChecks / totalChecks. Composite score = mean(scene.coverage) × 100, rounded. Verdicts are frozen at generation time — re-run scripts/analyze.mjs to refresh.

Exclusions

node_modules, .git, dist, build, .next, .turbo, coverage, .memory, .claude, target, intermediate, .DS_Store.

Known limitations

Cannot detect runtime vulnerabilities, transitive dependencies, external link rot, or test framework misconfiguration. Staleness checks require a registry round-trip. Coverage here is structural, not behavioral.
